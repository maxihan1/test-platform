# tpx-author — 표준 기획서로 옮기기

프롬프트에 `--- 표준 기획서 ---` 절이 있으면 이 파일을 따른다. 없으면 상관없다.
**정본은 `docs/spec/도메인/작성.md` §3.6 「★ 표준 기획서」 「옮기기」다.** 여기는 자식이 할 일만 적는다.

자료(기획서 · 피그마)를 플랫폼의 표준 기획서 항목으로 옮겨 결과 파일 하나에 쓴다. **자식은 파일만 쓴다** —
에이전트가 끝난 뒤 읽어 원장과 기계로 대조하고 서버에 올린다. 어긋나도 거절하지 않고 PR 본문 머리에 남는다.
**케이스는 지금처럼 자료로 만든다** — 케이스가 표준 기획서를 읽는 것은 다음 단계(PRD-F3-02)다. 요구사항 표 출처 칸도 지금처럼 원장 번호다.

## 1. 언제

- 자료를 다 읽은 뒤(§1), 요구사항 표(§2) 앞에 `[단계] 표준 기획서` 를 말하고 옮긴다
- §4 화면 탐침 뒤 화면에서만 본 항목(아래 4)을 더한다. 더하는 것은 메인(자식) 하나다 — 서브에이전트는 이 파일을 쓰지 않고, 본 것을 적어 두면 메인이 팬아웃 뒤 합치는 단계에서 더한다(`fanout.md`)
- 이어하기면 결과 파일이 이미 있을 수 있다 — 새로 쓰지 말고 이어서 고친다. 지금 판 파일은 에이전트가 새로 받아 둔 것이라 번호를 다시 맞춰 본다

## 2. 결과 파일 꼴

절의 「결과를 쓸 곳」에 JSON 하나다. 항목 키는 서버 항목과 같다.

```json
{
  "items": [
    {
      "reqId": "MKT-REQ-003",
      "feature": "회원가입",
      "text": "비밀번호는 8~16자로 입력한다",
      "basis": [{ "from": "회원가입_기획서.docx", "ref": "REQ-MEM-002", "quote": "비밀번호는 영문·숫자 조합 8~16자로 입력한다" }],
      "status": "CONFIRMED"
    }
  ],
  "removed": ["MKT-REQ-007"],
  "notRequirements": [{ "ref": "SCR-001", "reason": "화면 ID" }]
}
```

| 키 | 적는 것 |
|---|---|
| `items` | **이번 자료에서 나온 항목만.** 지금 판의 항목과 같은 요구면 그 `reqId` 를 적는다(문장을 고쳤어도). 새 요구면 `reqId` 를 뺀다 — 번호는 서버가 매긴다 |
| `removed` | 이번 자료가 다루는 기능에서 없어진 요구의 지금 판 번호. 적은 번호만 지워진다 |
| `notRequirements` | 원장 번호 가운데 요구가 아닌 것(화면 ID · 오류 코드 · 표 번호)과 까닭 한 줄 |

- **이번 자료가 다루지 않는 기능의 항목은 적지 않는다** — 에이전트가 지금 판에서 그대로 남긴다. 적지 않은 항목은 지워지지 않는다
- `byPerson` 이 붙은 지금 판 항목은 사람이 고친 것이다. 문서와 달라도 서버가 사람 것을 남기고 PR 머리에 번호를 띄운다 — 맞추려 애쓰지 않는다
- 다 쓰면 `node -e "JSON.parse(require('fs').readFileSync(process.argv[1],'utf8'))" <결과 파일>` 로 JSON 이 안 깨졌는지 본다

## 3. 쪼개기 · 문장 · 근거

1. **규칙 하나에 항목 하나**(ISO/IEC/IEEE 29148 singular). 원본 요구 하나에 확인할 규칙이 여럿이면 쪼갠다 — 「8~16자 · 형식에 맞지 않으면 안내」는 항목 둘이다
2. **숫자 · 조건 낱말은 원문 글자 그대로** — 이상 · 이하 · 초과 · 미만 · 까지 · 이내 · 만 · 없으면 · 최대 · 최소 · N개씩 · N회 연속 · 「맞지 않으면」 같은 조건. 에이전트가 원본 글과 항목 문장에서 같은 판정 함수로 경계 값 · 예외를 뽑아 견준다. 바꿔 쓰거나 빠뜨리면 「설계 잃음」이 된다.
   **API 표 「로그인」 열은 규칙 문장으로 옮긴다** — 예면 「로그인이 필요하다」, 관리자면 「관리자만 …」, 「작성만 예」면 「작성은 로그인이 필요하다」. 원장이 그 열을 예외로 읽어서 빠뜨리면 「설계 잃음」이다. 「아니오」 행은 로그인 문장을 따로 적지 않는다
3. **근거** — `from` 은 자료 목록의 원래 이름, `ref` 는 원장 사본의 `번호`(번호 모드면 기획서 번호, 문단 모드면 `P-012`), `quote` 는 원본 문장을 그대로 베낀다. 줄이거나 고쳐 쓰지 않는다. 원장이 없는 자료(PDF · 피그마)는 `ref` 를 빼고 `quote` 만 적는다
4. **원장 번호마다** 그 번호를 근거로 단 항목이 하나 이상 있거나 `notRequirements` 에 있어야 한다. 없으면 「빠짐」이다
5. `feature` 는 기획서의 기능 이름이다. 지금 판에 같은 기능이 있으면 그 이름을 그대로 쓴다
6. 상한은 `apps/admin/src/prd/rules.ts` 의 `상한` 이다(항목 수 · 기능 묶음 · 요구 문장 · 근거 수 · 근거 자리 · 근거 문장 글자 수). 쓰기 전에 연다. 어긴 항목은 에이전트가 버리고 PR 머리에 자리를 띄운다
7. 비밀번호 · 토큰 값을 적지 않는다. 가림표 `••••••` 는 그대로 둔다 — 비밀값이 들면 에이전트가 판 전체를 올리지 않는다

## 4. 상태 — 확정은 사람이 판단한 것만

| 경우 | `status` · 근거 |
|---|---|
| 문서에서 온 항목(문서끼리 같거나 하나뿐) | `CONFIRMED` — 기획서가 사람이 판단한 것이다 |
| 문서끼리 다르다 | 화면을 보고 화면과 같은 쪽으로 `text` 를 적고 `NEEDS_CHECK`. 근거에 두 문장을 다 싣는다 |
| 문서끼리 다른데 화면을 못 본다(대상 주소 없음 · 그 화면에 못 닿음) | 두 문장 근거 + `NEEDS_CHECK`. `text` 는 자료 목록에서 뒤에 온 자료 쪽 |
| 화면에서만 본 입력 규칙(필수 표시 · 글자 수 제한 · 형식 안내) · 오류 문구 | 항목을 더한다 — `{ "from": "화면", "ref": "<화면 주소>", "quote": "<화면에 보인 글 그대로>" }` · `NEEDS_CHECK`. 예외(네거티브) 케이스의 근거가 여기서 생긴다. 기획서가 다루는 화면 안에서만 본다(`tpx-cases` `two-kinds.md` 「화면에만 있는 입력 규칙」과 같은 범위). 근거가 화면뿐이면 무엇을 적든 에이전트가 `NEEDS_CHECK` 로 올린다 |

- 문서와 화면이 다른 것(문서에만 있다 · 화면이 다르다)은 문서 쪽이 `CONFIRMED` 다 — 테스트가 실패로 남아 버그로 보인다(§3.6 「★ 역방향」 「문서에만 있다」)
- 화면에서만 본 입력 규칙의 미확정 케이스는 지금처럼 `two-kinds.md` 대로 만든다 — 항목과 케이스를 둘 다 남긴다
