# tpx-author — 표준 기획서로 옮기고 그것만 읽는다

프롬프트에 `--- 표준 기획서 ---` 절이 있으면 이 파일을 따른다. 없으면(이어 작성) 아래 5 만 따른다. 원장 절이 「옛 표다」라고 하면 6 도 따른다.
**정본은 `docs/spec/도메인/작성.md` §3.6 「★ 표준 기획서」 「옮기기」 · 「작성은 표준 기획서만 읽는다」다.** 여기는 자식이 할 일만 적는다.

자료(기획서 · 피그마 · 화면)를 플랫폼의 표준 기획서 항목으로 옮겨 결과 파일 하나에 쓴다. 에이전트가 끝난 뒤 읽어 원본 원장과
기계로 대조하고 서버에 올린다 — 대조가 어긋나도 거절하지 않고 PR 본문 머리에 남는다. **못 올리면(파일 없음 · 깨짐 · 비밀값) 올리기 거절이다** —
표가 표준 기획서 번호를 가리키므로 판 없이 PR 을 세우지 않는다. 이어하기가 그 까닭을 주면 결과 파일을 고친다.
**요구사항 표와 케이스는 옮긴 표준 기획서만 보고 쓴다**(아래 5) — 원본 자료를 다시 읽어 표를 쓰지 않는다.

## 1. 언제

- 자료를 다 읽은 뒤(§1), 요구사항 표(§2) 앞에 `[단계] 표준 기획서` 를 말하고 옮긴다. 화면만이면 화면을 훑은 뒤 본 것을 옮긴다(`reverse.md` §6)
- 결과 파일을 쓰거나 고칠 때마다 절의 `npm run prd:ledger -- <자료 폴더>` 로 원장 사본을 다시 만든다 — 표 · 관문 0 · 번호 명령 · 설계 목록이 그 사본을 읽는다
- §4 화면 탐침 뒤 화면에서만 본 항목(아래 4)을 더한다. 더하는 것은 메인(자식) 하나다 — 서브에이전트는 이 파일을 쓰지 않고, 본 것을 적어 두면 메인이 팬아웃 뒤 합치는 단계에서 더한다(`fanout.md`). 더한 뒤 원장 사본을 다시 만들고 그 항목을 덮는 줄을 표에 더한다
- 이어하기면 결과 파일이 이미 있을 수 있다 — 새로 쓰지 말고 이어서 고친다. 지금 판 파일은 에이전트가 새로 받아 둔 것이라 번호를 다시 맞춰 본다. 앞 실행이 올렸으면 임시 번호가 받은 번호로 바뀌어 있다

## 2. 결과 파일 꼴

절의 「결과를 쓸 곳」에 JSON 하나다. 항목 키는 서버 항목과 같다.

```json
{
  "items": [
    {
      "reqId": "MKT-REQ-003",
      "feature": "회원가입",
      "text": "비밀번호는 8~16자로 입력한다",
      "basis": [{ "from": "회원가입_기획서.docx", "ref": "REQ-MEM-002", "quote": "비밀번호는 영문·숫자 조합 8~16자로 입력한다" }],
      "status": "CONFIRMED"
    }
  ],
  "removed": ["MKT-REQ-007"],
  "notRequirements": [{ "ref": "SCR-001", "reason": "화면 ID" }]
}
```

| 키 | 적는 것 |
|---|---|
| `items` | **이번 자료에서 나온 항목만.** 지금 판의 항목과 같은 요구면 그 `reqId` 를 적는다(문장을 고쳤어도). 새 요구면 `reqId` 에 **임시 번호** `<접두사>-NEW-001` 부터 차례로 적는다 — 진짜 번호는 서버가 올릴 때 매긴다(아래 5) |
| `removed` | 이번 자료가 다루는 기능에서 없어진 요구의 지금 판 번호. 적은 번호만 지워진다 |
| `notRequirements` | 원본 원장 번호 가운데 요구가 아닌 것(화면 ID · 오류 코드 · 표 번호)과 까닭 한 줄 |

- **이번 자료가 다루지 않는 기능의 항목은 적지 않는다** — 에이전트가 지금 판에서 그대로 남긴다. 적지 않은 항목은 지워지지 않는다
- `byPerson` 이 붙은 지금 판 항목은 사람이 고친 것이다. 문서와 달라도 서버가 사람 것을 남기고 PR 머리에 번호를 띄운다 — 맞추려 애쓰지 않는다
- 다 쓰면 `npm run prd:ledger -- <자료 폴더>` 를 돌린다 — JSON 이 깨졌으면 여기서 오류가 나고, 버린 항목(모양 · 상한 · 겹친 번호)과 임시 번호 목록이 찍힌다.
  번호 없이 쓴 새 항목에는 명령이 임시 번호를 붙여 결과 파일에 적어 준다. 지금 판에 없는 `REQ` 번호를 적으면 그 번호는 버리고 새 임시 번호가 붙는다 — 원장 사본에서 번호를 다시 보고 표에 적는다

## 3. 쪼개기 · 문장 · 근거

1. **규칙 하나에 항목 하나**(ISO/IEC/IEEE 29148 singular). 원본 요구 하나에 확인할 규칙이 여럿이면 쪼갠다 — 「8~16자 · 형식에 맞지 않으면 안내」는 항목 둘이다
2. **숫자 · 조건 낱말은 원문 글자 그대로** — 이상 · 이하 · 초과 · 미만 · 까지 · 이내 · 만 · 없으면 · 최대 · 최소 · N개씩 · N회 연속 · 「맞지 않으면」 같은 조건. 에이전트가 원본 글과 항목 문장에서 같은 판정 함수로 경계 값 · 예외를 뽑아 견준다. 바꿔 쓰거나 빠뜨리면 「설계 잃음」이 된다.
   **API 표 「로그인」 열은 규칙 문장으로 옮긴다** — 예 · 필요 · O · ✓ 면 「로그인이 필요하다」, 관리자면 「관리자만 …」, 「작성만 예」면 「작성은 로그인이 필요하다」. 원장이 그 열을 예외로 읽어서 빠뜨리면 「설계 잃음」이다.
   같은 행에 다른 동등 분할 근거(「비로그인이면 401」 · 「본인」)가 있으면 대조가 기법 이름으로만 견줘 못 잡는다 — 그래도 적는다. 「아니오」 행은 로그인 문장을 따로 적지 않는다
3. **근거** — `from` 은 자료 목록의 원래 이름, `ref` 는 원본 원장 사본(절의 「원본 원장」 · `source-ledger.json`)의 `번호`(번호 모드면 기획서 번호, 문단 모드면 `P-012`), `quote` 는 원본 문장을 그대로 베낀다. 줄이거나 고쳐 쓰지 않는다. 원장이 없는 자료(PDF · 피그마)는 `ref` 를 빼고 `quote` 만 적는다
4. **원본 원장 번호마다** 그 번호를 근거로 단 항목이 하나 이상 있거나 `notRequirements` 에 있어야 한다. 없으면 「빠짐」이다
5. `feature` 는 기획서의 기능 이름이다. 지금 판에 같은 기능이 있으면 그 이름을 그대로 쓴다
6. 상한은 `apps/admin/src/prd/rules.ts` 의 `상한` 이다(항목 수 · 기능 묶음 · 요구 문장 · 근거 수 · 근거 자리 · 근거 문장 글자 수). 쓰기 전에 연다. 어긴 항목은 에이전트가 버리고 PR 머리에 자리를 띄운다
7. 비밀번호 · 토큰 값을 적지 않는다. 가림표 `••••••` 는 그대로 둔다 — 비밀값이 들면 에이전트가 판 전체를 올리지 않는다

## 4. 상태 — 확정은 사람이 판단한 것만

| 경우 | `status` · 근거 |
|---|---|
| 문서에서 온 항목(문서끼리 같거나 하나뿐) | `CONFIRMED` — 기획서가 사람이 판단한 것이다 |
| 문서끼리 다르다 | 화면을 보고 화면과 같은 쪽으로 `text` 를 적고 `NEEDS_CHECK`. 근거에 두 문장을 다 싣는다 |
| 문서끼리 다른데 화면을 못 본다(대상 주소 없음 · 그 화면에 못 닿음) | 두 문장 근거 + `NEEDS_CHECK`. `text` 는 자료 목록에서 뒤에 온 자료 쪽 |
| 화면에서만 본 입력 규칙(필수 표시 · 글자 수 제한 · 형식 안내) · 오류 문구 · 오류 추정 점검 목록으로 본 결과 | 항목을 더한다 — `{ "from": "화면", "ref": "<화면 주소>", "quote": "<화면에 보인 글 그대로>" }` · `NEEDS_CHECK`. 예외(네거티브) 케이스의 근거가 여기서 생긴다. 기획서가 다루는 화면 안에서만 본다(`tpx-cases` `two-kinds.md` 「화면에만 있는 입력 규칙」과 같은 범위). 근거가 화면뿐이면 무엇을 적든 에이전트가 `NEEDS_CHECK` 로 올린다 |

- 문서와 화면이 다른 것(문서에만 있다 · 화면이 다르다)은 문서 쪽이 `CONFIRMED` 다 — 테스트가 실패로 남아 버그로 보인다(§3.6 「★ 역방향」 「문서에만 있다」)
- 화면에서만 본 입력 규칙의 미확정 케이스는 지금처럼 `two-kinds.md` 대로 만든다 — 항목과 케이스를 둘 다 남긴다
- 오류 추정 결과의 `text` 는 점검 목록 기준을 그 화면 말로 적는다 — 「주문 상세를 없는 주문 번호로 열면 「주문을 찾을 수 없습니다」 안내가 보인다」. 기준을 어긴 화면이어도 기준 문장으로 적는다(케이스도 기준대로다)

## 5. 표와 케이스 — 표준 기획서만 읽는다

- **원장은 표준 기획서 항목이다** — 프롬프트 원장 절의 사본(`ledger.json`)에 항목마다 `번호` · `문장` · `확인필요` · `설계` 가 있다. 늘 번호 모드다
- **요구사항 표 출처 칸에 그 번호를 적는다** — `MKT-REQ-012` · 새 항목은 임시 번호 `MKT-NEW-003`. 원본 기획서 번호(`REQ-MEM-002`)는 적지 않는다 — 원본 번호는 표준 기획서 항목 근거(`ref`)에만 있다
- **표 문장은 그 항목의 `문장` 에서 쓴다** — 숫자 · 조건 낱말은 그대로. 원본을 다시 열어 다른 말로 쓰지 않는다. 경계 · 예외 칸은 `npm run ledger:design -- <원장 사본>` 이 그 문장으로 정한다
- **임시 번호는 손으로 바꾸지 않는다** — 올린 뒤 에이전트가 표와 결과 파일의 임시 번호를 서버가 준 번호로 바꿔 적는다. tcId 는 그대로다
- **`확인필요` 항목을 덮는 줄에는 미확정 표시를 단다**(`tpx-cases` `wording.md` 「출처 칸의 상태 표시」) — 정방향은 `화면 검사 — <요소>`(오류 추정 줄은 `오류 추정 — <항목>`), 역방향은 `화면에만 — <요소>` · 기획서끼리 다름은 `차이 D<번호>` 다. 그 항목은 화면 기준이라 케이스에 `unconfirmed` 를 단다(사유 머리는 `wording.md` 「사유 머리」 — 정방향 기획서끼리 다름은 `기획서끼리 다름 — `).
  안 달면 화면 값이 꼬리표 없이 기대값이 된다. 미확정을 표준 기획서에서 계산하게 되면(PRD-F4-02) 표시와 꼬리표를 걷는다
- **화면에서 더한 `확인필요` 항목도 원장에 든다 — 그것을 확인하는 줄의 출처에 번호를 적는다.** 새 케이스를 따로 만들지 않는다. 입력 규칙은 그 입력 규칙 줄, 오류 문구는 그 문구를 확인하는 입력 규칙 · 예외 줄,
  오류 추정 결과는 그 오류 추정 줄(원래 요구 번호 뒤에 같이 — `MKT-REQ-012 · MKT-NEW-007 · 오류 추정 — 두 번 누르기`). 번호를 안 적으면
  관문 0 · 올리기 판정에 「빠짐」으로 남는다. 오류 추정 줄로만 덮인 항목은 설계 대조가 건너뛴다
- **확정 항목이 화면과 다르면 확정 항목대로 쓰고 실패로 남긴다** — 문서가 맞고 화면이 버그일 수 있다(§3.6 「★ 역방향」 「문서에만 있다」). 다른 것은 `diffs.json` 에 적어 원본에 표시한다
- 이어 작성은 결과 파일을 쓰지 않는다 — 뿌리 요청이 옮겼다. 원장 사본의 번호로 표를 쓴다. 화면에서만 본 입력 규칙은 가까운 요구 번호 뒤에 `화면 검사 —` 를 달아 지금처럼 쓴다

## 6. 옛 표 — 표준 기획서 전에 만든 표 (PRD-F3-03)

원장 절이 「옛 표다」라고 하면 main 표 요구 줄의 출처가 표준 기획서 번호가 아니라 원본 번호(`기획서.docx §2 REQ-COM-001`)다.
그 줄은 원장을 덮지 못한다 — 그대로 두고 줄을 더하면 케이스가 한 벌 더 생긴다. **이번 작성이 옛 표를 표준 기획서 번호로 갈아쓴다.**
정본은 `docs/spec/도메인/작성.md` §3.6 「★ 표준 기획서」 「기존 서비스」다.

1. **표를 표준 기획서 번호로 새로 쓴다** — 옛 줄(출처가 원본 번호뿐인 줄)은 다 지운다. 위 5 대로 원장 사본의 문장으로 쓴다. 「제외」 표도 표준 기획서 번호로 다시 적는다.
   옛 「사람이 뺌」 줄은 사람 결정이라 지우지 않고 결과 요약에 번호를 적는다 — 사람이 표준 기획서 번호로 옮긴다. 옛 「다음 요청」 줄의 요구는 이번에 덮는다(자식은 「다음 요청」을 새로 못 쓴다)
2. **tcId 는 번호 명령이 물려준다** — `npm run ledger:number` 가 항목 근거의 원본 번호로 옛 줄을 찾아 같은 칸(갈래 · 축 · 상태)의 옛 tcId 를 준다.
   원본 요구 하나를 항목 여럿으로 쪼갰으면 원장 차례로 첫 항목이 옛 번호를 받고 나머지는 새 번호다. 손으로 옛 번호를 적지 않는다.
   물려받은 번호의 케이스 파일은 그 자리에서 새 표대로 고쳐 쓴다(파일 이름 그대로)
3. **옛 미확정 줄**(출처에 `화면에만 —` · `화면 검사 —` · `차이 D<번호>`)은 화면에서 본 규칙이다 — 케이스의 `unconfirmed` 꼬리표가 그 표시다.
   그 규칙을 `확인 필요` 항목으로 옮긴다(위 4 「화면에서만 본」 줄). 근거는 둘 — 화면 근거와 **그 줄 출처의 원본 번호를 단 문서 근거**
   (`{ "from": "기획서.docx", "ref": "REQ-COM-009", "quote": "<그 번호의 원본 문장>" }`)다. 문서 근거가 있으면 에이전트가 확인 필요로 바꿔 주지 않으니 `status` 를 `NEEDS_CHECK` 로 직접 적는다.
   번호 명령이 그 원본 번호로 옛 미확정 케이스 번호를 물려준다. 그 항목을 덮는 줄은 위 5 대로 미확정 표시와 `unconfirmed` 를 단다(PRD-F4-02 전까지).
   화면이 문서가 적은 것과 **반대로** 돌면(문서에 적힌 값 · 문구가 다르다) 확인 필요가 아니라 문서 쪽 `CONFIRMED` 다 — 케이스는 문서대로 쓰고 실패로 남는다(위 4 첫 줄 아래)
