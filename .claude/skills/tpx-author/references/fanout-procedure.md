# 팬아웃 두 단계 — 화면 파일 먼저, 그다음 프로시저 (2026-11-25 · TP-F5-31)

프롬프트 머리에 「이 애플리케이션은 테스트 프로시저로 쓴다.」 줄이 있을 때만 `fanout.md` 에 이어 연다. 여기 적은 것만 다르고 나머지(언제 나누나 · 동시 넷 · 물러서기 · 백그라운드 금지 · 공용 도우미 · 합치기 · 실패했을 때)는 `fanout.md` 그대로다. 게임은 `fanout-game.md` 도 같이 지킨다.
정본은 명세 `docs/spec/도메인/작성.md` §3.6 「★ 테스트 프로시저 작성」 「팬아웃 두 단계」다.

**왜 두 단계인가** — 흐름은 화면을 넘나든다. 화면 묶음으로만 나누면 한 보조가 흐름 하나를 끝까지 못 쓴다.
**나누지 않는 작성**(화면 묶음 하나 · 케이스 8건 미만)도 자식이 화면 파일 → 프로시저 차례로 쓴다.

## 띄우기 전

- 표 · 케이스 번호 · **프로시저 절**(`tpx-cases` `procedure.md` §3)까지 끝낸다. 절은 여기서 언다 — 보조가 케이스를 옮기거나 차례를 바꾸지 않는다. 바꿔야 하면 돌려받아 자식이 고친다
- 공용 부품 · 도우미를 만든다(`fanout.md` §2). **공용 부품 표본(`한번`)은 돌지 않는다** — 그 명령은 폰 케이스를 안 돈다
- 폰으로 볼 것은 자식이 미리 본다. 앱은 조작 맵 경로 검색(`app.md` §7)과 찍어 둔 화면, 게임은 `fanout-game.md` 의 셋이다. 보조는 폰을 만지지 않는다

## 1단계 — 화면 파일

화면 묶음(게임은 창 묶음)마다 보조 하나 · 넷까지. 한 화면은 한 보조다. `fanout.md` §4 뼈대에서 이렇게 바꾼다.

- **첫 줄** — 훅이 이 줄의 묶음 이름으로 단계마다 넷 상한 · 다시 띄우기 한 번을 센다. 이름 앞 `화면 단계 — ` 를 빼지 않는다
  > `<접두사>` 서비스의 테스트케이스 가운데 「화면 단계 — <묶음 이름>」 묶음을 만든다. **케이스는 쓰지 않는다 — 맡은 화면의 Page Object · Component 만 쓴다.**
- **역할** — 목록의 줄을 케이스 코드로 옮기는 대신 그 줄이 쓸 화면 파일을 만든다. 요소를 안정된 주소로 찾고 누르기 · 읽기 · 기다리기를 짧은 메서드로 둔다. 판정은 담지 않는다
- **맡은 줄** — 그 화면을 지나는 표 줄(전제 · 조작 · 결과). 메서드는 그 줄들이 쓸 것만 만든다. tcId · 설계 목록 줄은 뺀다
- **맡은 화면의 Page Object** — 1단계 보조가 그 파일의 주인이다. 다른 묶음의 화면을 지나는 줄은 자기 화면 몫만 쓴다
- **먼저 Read 로 연다** — `example.md` · `two-kinds.md` 「Page Object」 · `5-stable.md` 와 종류 뗀 파일만. `5-writing.md` · `5-inputs.md` · `5-data.md` · `test-design.md` · `6-gates.md` 는 뺀다
- **묶음 slug** — `scr-<영문>`
- **지킬 것** — 9 ~ 13(준비 판정 · 글자 수 경계 · 설계 칸 · `techniques` · 오류 추정)은 뺀다
- **관문** — `npm run -s authoring:check -- 보조 <맡은 화면 파일들>` 하나. 한 판 · 1번 돌려 보기 · 입력값 두 번은 없다
- **돌려줄 것** — 만든 파일 · 화면마다 메서드(이름 · 인자 · 돌려주는 것 · 하는 일) · 관문 결과 · 필요한 도우미 · 막힌 것(못 찾은 주소 · 눌러 볼 것) · CSS · XPath 를 쓴 까닭 · 테스트 요령. 보고는 `<자리>/summary-<slug>.md`, 용어 조각은 `<자리>/glossary/<묶음>.md`

**모이면 자식이 합친다** — ① 막힌 것 · 「눌러 볼 것」을 모아 폰에서 한 번에 보고 화면 파일을 마저 쓴다 ② 두 화면 이상에 나오는 같은 조각을 Component 로 모은다(`fanout.md` 「자식이 합칠 때」 ⑥) ③ 임시 도우미를 공용으로 옮긴다 ④ `npm run -s authoring:check -- 보조 tests/<폴더>/pages/*.page.ts tests/<폴더>/components/*.component.ts tests/<폴더>/helpers/*.helper.ts`(없는 폴더는 뺀다)로 타입을 본다 ⑤ 화면 파일 · 부품 · 도우미의 메서드 목록을 뽑는다

## 2단계 — 프로시저

프로시저 절의 줄을 **케이스 수가 고르게** 넷까지로 나눈다. 프로시저 하나는 보조 하나가 쓴다. 같은 화면을 지나는 프로시저는 되도록 한 보조에 모은다. `fanout.md` §4 뼈대에서 이렇게 바꾼다.

- **첫 줄**
  > `<접두사>` 서비스의 테스트케이스 가운데 「프로시저 단계 — <묶음 이름>」 묶음을 만든다.
- **맡은 줄** — 프로시저 절의 맡은 줄(프로시저 번호 · 흐름 · 케이스 차례)과 그 케이스들의 표 줄을 같이 붙인다. **번호 · 차례 · 묶음을 바꾸지 않는다**
- **맡은 파일** — `tests/<폴더>/<프로시저 번호>.spec.ts`. 케이스 번호 이름의 파일은 만들지 않는다
- **화면 파일은 가져다 쓰기만 한다** — 「맡은 화면의 Page Object」 줄 대신 1단계가 만든 메서드 목록을 붙인다. 모자란 메서드는 화면 파일을 고치지 말고 `helpers/draft-<slug>.helper.ts` 에 적고 「필요한 도우미」로 돌려준다
- **먼저 Read 로 연다** — `fanout.md` §4 의 줄과 종류 입구가 더한 것에 `procedure.md` 를 더한다
- **묶음 slug** — `proc-<영문>`(35자까지)
- **지킬 것 5** — 맡은 프로시저 파일 · 보고 파일 · `helpers/draft-<slug>.helper.ts` 말고는 고치지 않는다. 용어 조각은 쓰지 않는다
- **지킬 것 10 · 13** — 화면을 못 보므로 칸 한도는 재지 않고, 오류 추정 줄은 표의 「~해야 한다」대로 쓰고 결과는 `화면 안 봄` 으로 돌려준다
- **관문** — `npm run -s authoring:check -- 보조 <맡은 프로시저 파일들>` 하나. 한 판 · 1번 돌려 보기 · 입력값 두 번은 돌지 않고 `안 돌림(폰 케이스 — 메인이 폰에서 돌림)` 을 적는다
- **돌려줄 것** — `fanout.md` §4 그대로에 「절에서 고칠 것」(흐름이 안 이어지는 자리 · 한 번에 못 끝날 것 같은 프로시저)을 더한다. 화면 입력 규칙 · 버튼 반응은 「없음」이다

**모이면 자식이 합친다** — `fanout.md` 「자식이 합칠 때」 그대로다. 다른 것은 셋이다.

1. 「절에서 고칠 것」을 절 · `cases` · `test.case` 차례에 같이 반영한다
2. ③ · ④ 로 더한 줄(화면 입력 규칙 · 버튼 반응)의 케이스는 절에도 넣는다(`procedure.md` §3)
3. ⑧ 의 빠른 검사 다음에 폰에서 프로시저마다 통째로 1번 돌린다(`procedure.md` §6). 스모크 표시(게임)는 다 합친 뒤 자식이 단다

결과 요약 `보조 AI 나눠 맡기기:` 줄은 `화면 파일 N명 · 프로시저 N명(사람마다 케이스 수)` 로 적는다. 단계 표지는 두 단계 다 `보조 AI 에게 나눠 맡기기 — <N>명` · `보조 AI 결과 합치기` 다.
