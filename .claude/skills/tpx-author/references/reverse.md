# tpx-author — 역방향 (실제 화면과 대조 · 화면만)

프롬프트에 `--- 역방향 ---` 절이 있으면 이 파일을 따른다. 없으면 이 파일은 상관없다.
**정본은 `docs/spec/도메인/작성.md` §3.6 「★ 역방향」이다.** 여기는 자식이 할 일만 적는다.
**Android 앱 · 게임** — 역방향 절에 「Android 앱」이 있으면 §2~§3.5(웹 크롤러 · 탐침 · 훑기 보조 · 바뀐 화면 케이스) 대신 `app.md` §6 을, 「게임」이 있으면 `game.md` §7 을 따른다. §2 「끝내기 직전」 비밀번호 점검과 §4~§7 은 그대로다(2026-11-04 APP-F2-05 · 게임 APP-F2-06).

**단계 표지** — `SKILL.md` 「단계 표지」 이름에 더해 크롤러를 돌릴 때 `[단계] 화면 모으기`(`scan-fanout.md` §2), §3 에 들어갈 때 `[단계] 화면 살펴보기`, §3.5 에 `[단계] 바뀐 화면 케이스 고치기`, §5 에 `[단계] 기획서와 화면 차이 정리`,
§2 「끝내기 직전」 점검에 `[단계] 비밀번호 노출 점검` 을 말한다. 대조 요청에서는 훑기가 가장 길 수 있어 다른 단계에 묻히지 않게 따로 잰다.

**순서 (2026-10-03)** — 훑기(§3) → 바뀐 화면 케이스(§3.5) → 표 · 차이 목록 · 미확정 줄을 한 번에(§4 · §5) → 케이스 팬아웃 → 관문. **차이 목록은 케이스 팬아웃 전에 끝낸다** — 미확정 케이스도 서브에이전트가 같이 쓴다. 합친 뒤 관문 0 을 연 다음에는 차이 · 미확정 줄을 더하지 않는다(표 직후 「관문 0 일찍」은 세지 않는다 · 11204 는 관문 뒤에 6건을 더해 전체 3회를 다시 돌았다). 그래서 `[단계] 기획서와 화면 차이 정리` 는 목록 단계 바로 뒤에 말한다

| 갈래 | 입력 | 산출물 |
|---|---|---|
| **대조** | 기획서 자료 + 대상 서버(시작 주소는 있을 수도) | 표준 기획서 결과 파일 + 케이스(확정 항목은 정식 · 화면에만 있으면 미확정) + `diffs.json` |
| **화면만** | 시작 주소(없으면 대상 서버 주소)뿐 — 기획서가 없다. **PRD 에 아직 없는 화면만** 쓴다 | 표준 기획서 결과 파일(항목 전부 확인 필요) + 케이스(전부 미확정) + `diffs.json`(비어도 된다) |

**케이스는 표준 기획서만 읽는다** (2026-10-10 · PRD-F3-02) — 대조도 화면만도 본 것을 먼저 표준 기획서 결과 파일에 옮기고(`prd.md`), 표 · 케이스는 그 항목으로 쓴다.
역기획서 원고는 쓰지 않는다 — 사람은 「PRD 관리」 메뉴의 워드 내보내기로 받는다.

## 1. 받는 것

**`••••••` 는 에이전트가 가린 비밀번호다** (2026-09-29) — 기획서 글자본 · 앞 실행이 남긴 파일에서 테스트 계정 비밀번호를 자식을 띄우기 전에 가린다.
실제 값으로 읽지 않는다 — 로그인 칸에 넣지 않고, 「기획서 비밀번호 ≠ 화면」 같은 차이로 적지 않는다. 계정은 아래 환경 변수로만 쓴다.

- 환경 변수 `TARGET_ENV` · `TARGET_BASE_URL` · `TARGET_START_URL`(없을 수 있다) · `TARGET_LOGIN_ID` · `TARGET_LOGIN_PASSWORD`(일반 회원)
- 환경 변수 `PLATFORM_BASE_URL` — `TARGET_BASE_URL` 과 같은 주소로 에이전트가 넣어 둔다(2026-10-22 PRD-F14-01). 돌려 보기 명령(1번 돌려 보기 `한번` 도)은 앞에 붙이지 않고 그대로 부른다. `npx playwright test` 는 손으로 부르지 않는다(`fanout.md` §4 「1번 돌려 보기」) — 보조 프롬프트의 대상 서버 줄에도 이 이름을 적는다
- 환경 변수 `PLATFORM_ACCOUNTS` — 그 줄의 계정 전부 JSON `[{ baseUrl, role, loginId, loginPassword }]`(일반 회원 role 은 `일반 회원`, 그다음 관리자 같은 역할 계정. 2026-10-12).
  playwright 를 그대로 돌리면 kit 이 `PLATFORM_BASE_URL` 과 출처가 같은 줄의 계정으로 케이스의 비밀값 칸을 채운다 — `PLATFORM_PARAMS` 를 손으로 만들지 않는다.
  관리자 화면을 직접 열어 볼 때는 아래 §2 로그인 스크립트에서 `JSON.parse(process.env.PLATFORM_ACCOUNTS)` 로 그 역할 줄을 골라 쓴다. **필요한 역할이 없으면 그 요구는 원장 「제외」 `계정 미등록`**(`tpx-cases` `2-requirements.md` §2)
- 산출물 폴더 — 프롬프트가 준 경로. 없으면 만든다(`mkdir -p`). **저장소 트리 밖이다** — 거기 쓴 것은 커밋되지 않고 에이전트가 읽어 올린다

### 끝내기 직전 — 비밀번호 점검 (2026-09-28 · 명령은 2026-10-19)

**결과 요약을 찍기 전에 한 번 돌린다.** 에이전트 올리기 검사가 보는 것 중 자식이 고칠 수 있는 것을 먼저 본다 —
5873 은 케이스 26개를 다 만들고 올리기에서 걸려 멈췄다. 여기서 찾으면 그 자리에서 고치고 끝낸다.
회원가입 예시 비밀번호가 우연히 계정 값과 같아도 걸린다 — 그때는 다른 예시 값으로 바꾼다.

```bash
npm run -s authoring:check -- 비밀번호 tests/<폴더> docs/cases/<접두사>.md <산출물 폴더>[ docs/cases/<접두사>.guide.md — 있으면 꼭 넣는다]; echo "EXIT=$?"
```

`scripts/authoring-check.ts` 비밀자리들 — 비밀번호는 환경 변수로만 읽는다(`TARGET_LOGIN_PASSWORD` 와 `PLATFORM_ACCOUNTS` 의 역할 계정 비밀번호 전부 — `환경비밀번호들`). 값은 인자 · 출력에 두지 않고 자리(파일:줄)만 찍는다(위 ★).
원문과 JSON 이스케이프 꼴(따옴표 · 역슬래시 든 값은 코드 · JSON 에 이스케이프돼 적힌다)을 줄마다 보고, `.json` 은 푼 값에서도 본다(diffs.json — 이스케이프가 날 글자를 가린다). 링크 · FIFO 는 따라가지 않는다 — 에이전트가 모양 검사로 따로 거절한다.
**없는 경로는 「없는 경로」로 어긋난다** — 경로를 틀려 안 보고 「깨끗」이 나오는 거짓 초록을 막는다. `EXIT` 0 = 「통과」(계정이 없으면 「계정 없음」) · 1 = 찾음

- **찾으면 그 줄을 고친다** — 계정이면 `params` 비밀값 칸(K9), 로그인 스크립트면 `process.env`, 예시 값이면 다른 값으로. 고친 뒤 **「통과」가 나올 때까지** 다시 돌린다
- 고쳤으면 관문 1~3 을 다시 돈다(표를 고쳤으면 관문 2 가 거기 든다). 케이스 구조를 바꿨으면(`params` 칸 추가) 관문 4 도
- **없는 경로라고 나오면 경로를 바로잡고 다시 돌린다** — 「통과」 없이 결과 요약으로 가지 않는다
- **결과 요약에도 계정 값을 쓰지 않는다** — 에이전트가 요약을 PR 본문에 싣고 거기까지 본다
- **이 점검이 못 보는 것** — 기획서 원본의 워드 속성 · 문서 정보 칸에만 적힌 계정 값 · PDF · 피그마(에이전트가 원본 표시 사본을 본다). 이때는 올리기에서 걸려 멈춘다 — 앞엣것은 자식이 고칠 수 없다

## 4. 차이마다 — 무엇을 만드나

| 기획서와 화면 | 케이스 | `diffs.json` 의 `kind` |
|---|---|---|
| 같다 | **정식** — 기대값은 기획서(R10). 화면에서는 요소 주소만 | 안 싣는다 |
| 다르다 | **정식** — 표준 기획서는 문서 쪽(확정)이다. 기대값은 문서 쪽이고 실패할 것이다(2026-10-10 · PRD-F3-02 — 이전 버전은 화면 기준 미확정) | `DIFFERENT` |
| 화면에만 있다 | **미확정** — 표준 기획서에 `확인 필요` 항목으로 더하고 화면 기준으로 쓴다 | `SCREEN_ONLY` |
| 문서에만 있다 | **정식** — 기대값은 기획서. 실패할 것이고 그게 맞는 신호다 | `DOC_ONLY` |

- 기획서끼리 다른 것은 화면 쪽으로 `확인 필요` 항목이 된다(`prd.md` §4) — 그 항목을 덮는 케이스도 미확정이다
- **케이스 파일에 `unconfirmed` 꼬리표는 달지 않는다** (2026-10-11 PRD-F4-05 — kit 이 그 칸을 안 받는다). 미확정은 그 줄 출처의 `확인 필요` 항목 번호가 정한다
- **표의 미확정 줄은 출처 칸에 표준 기획서 번호(새 항목은 임시 번호) 뒤 `차이 D<번호>` · `화면에만 — <요소>` 를 단다**(`wording.md` 「출처 칸의 상태 표시」) — 안 달면 번호 명령이 정식 줄과 한 케이스로 묶어 정식 확인까지 미확정에 묶인다 (2026-10-04)
- **`확인 필요` 항목을 덮지 않는 줄에 화면 값을 기대값으로 쓰지 않는다** (R10 예외는 미확정뿐)
- **이미 있는 케이스(같은 tcId)를 미확정으로 돌리지 않는다** — 그 줄 출처에 `확인 필요` 항목 번호를 새로 붙이지 않는다. 확정 실패를 숨기는 길이다. 차이만 `diffs.json` 에 적고 `tcId` 를 싣는다
- 케이스의 계정은 `params` 비밀값 칸으로만 받는다(K9). 역할 계정이면 `.meta({ secret: true, account: '<역할>' })` 로 역할을 단다. 케이스 파일에 계정 값을 쓰지 않는다

## 5. `diffs.json` — 차이 목록

산출물 폴더에 JSON 배열 하나. 차이가 없으면 `[]`.

```json
[
  { "no": "D1", "kind": "DIFFERENT", "where": "결제-기획서.docx · 3쪽", "doc": "저장", "screen": "확인", "tcId": "PAY-012",
    "asset": 7, "anchor": "저장 버튼을 누르면 주문이 저장된다" },
  { "no": "D2", "kind": "SCREEN_ONLY", "where": "주문 화면", "doc": null, "screen": "쿠폰 칸", "tcId": "PAY-013",
    "asset": 8, "node": "12:34" }
]
```

- 번호는 `D1` 부터. 케이스 사유의 번호와 같게
- `doc`·`screen` 은 짧게 — 문장 하나. **표시 여부(`marked`)는 적지 않는다** — 원본 표시는 에이전트가 하고 결과도 에이전트가 적는다
- **표시 자리 세 칸** — 에이전트가 이것으로 원본에 표시한다. 틀리면 그 차이만 「표시 못 함」이 된다
  - `asset` — 어느 자료의 차이인지. 프롬프트 자료 목록의 `(자료 번호 N)` 그대로
  - `anchor` — 워드 기획서에서 그 차이가 걸린 **문장을 그대로** 20~120자 베낀다. 자료 파일(글자로 바꾼 것)에서 줄 하나를 고르면 된다.
    바꿔 쓰거나 줄이면 원본에서 못 찾는다. 기획서에 없는 차이(`SCREEN_ONLY`)는 빼도 된다 — 문서 마지막에 붙는다
  - `node` — 피그마 차이면 그 화면의 노드(`12:34`). 모르면 빼도 된다 — 자료 주소의 노드에 붙는다
- 칸은 이 아홉뿐이다(에이전트가 나머지는 버린다)

## 6. 화면만 — 표준 기획서로 옮긴다

훑기를 마치면 `[단계] 표준 기획서로 옮기기` 를 말하고 화면 기록으로 표준 기획서 결과 파일을 쓴다(`prd.md`). 역기획서 원고는 쓰지 않는다.

- 기능 묶음은 **현재 버전에 그 화면이 든 묶음이 있으면 그 묶음**이다 — 「글쓰기 · 수정」이 있는데 「글쓰기」 · 「로그인 · 로그아웃」이 있는데 「로그인」 · 「고객센터」가 있는데 「1:1 문의」 · 「FAQ」처럼 화면 이름으로 새 묶음을 지으면 PRD 목차가 쪼개진다(DMW · 2026-11-11 사용자 「목차에 왜 들어갔지」). 현재 버전에 맞는 묶음이 없을 때만 화면 묶음(머리 메뉴 직속)으로 새로 짓는다. 그래도 어긋난 이름은 PRD 목차가 「정리 필요」로 띄운다(도메인/작성 §3.6 「목차」). 화면마다 본 규칙 · 동작 · 오류 문구를 규칙 하나에 항목 하나로 적는다
- **한 번 본 값으로 일반 규칙을 쓰지 않는다** (PRD-F9-28 — MKS 가 「결제 예정 금액 = 줄 금액 합」(배송비 빠짐) · 「수량 상한 10」(재고와 10 중 작은 값인데 재고 빠짐)으로 적었다).
  계산 값은 화면에 보인 칸을 다 넣는다 — 배송비 0원도 칸이다. 화면 기록에 조건이 한 가지뿐이면 그 조건을 문장에 남긴다(「줄 금액 합이 5만 2천 원일 때 배송비는 0원이다」).
  조건이 다른 경우(금액이 작은 상품 · 재고 1개 상품)를 본 기록이 있으면 둘을 합쳐 조건 규칙으로 쓴다. 혼자 훑을 때도 그런 데이터를 한 번 더 연다
- 근거는 `{ "from": "화면", "ref": "<화면 주소>", "quote": "<화면에 보인 글 그대로>" }` — 근거가 화면뿐이라 에이전트가 전부 `확인 필요` 로 올린다
- 새 항목이라 `reqId` 는 임시 번호(`<접두사>-NEW-001` …)다. 다 쓰면 원장 사본을 다시 만들고 그 번호로 표를 쓴다
- 케이스는 **전부 미확정**이다. 사유 예 `'화면만 — 기획서 없음 (작성 요청 5870)'`
- `덮음: true` 인 화면은 항목 · 케이스도 만들지 않는다. **훑을 화면이 하나도 없으면 표준 기획서 · 표 · 새 케이스는 아무것도 쓰지 말고** 결과 요약 역방향 줄에 「PRD 에 없는 화면 0」을 적고 끝낸다(에이전트가 실패로 닫는다). §3.5 에서 고친 케이스가 있으면 그것만 올라간다

## 7. 결과 요약에 더한다
