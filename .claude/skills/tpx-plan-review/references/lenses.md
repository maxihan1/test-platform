# 계획 검토 렌즈

gstack 스킬 대신 쓰는 저장소 안 기준이다. 항목마다 계획 파일의 근거 줄을 붙여 지적한다. 해당 없으면 「해당 없음」 한 줄이면 된다.

## 공학

2등급 이상 전부.

- **E1 범위** — 이미 있는 스크립트 · 검사로 되나. 더 작은 길이 있나. `files` 가 범위 밖이면 이유가 적혀 있나.
- **E2 계약 · 정본** — CLAUDE.md §1.2 넷(타입 · 러너 엔드포인트 · DB · Admin API)을 건드리나. 같은 규칙을 두 곳에 적나.
- **E3 실패 경로** — 새 길마다 현실적인 실패 하나를 다루나. 에러를 삼키나. 비밀값이 응답 · 로그 · 기록에 원문으로 남나. 부르는 쪽이 적는 값으로 권한을 우회하나.
- **E4 테스트** — RED 가 지금 정말 실패하나. 회귀를 지키는 검사가 있나. 바뀌는 동작을 전제로 쓴 기존 검사를 찾았나(`tpx-plan` §3). 항진명제 단언은 없나. `검증` 칸이 채워졌나.
- **E5 시간** — 검사 · 대기가 늘어나나. 같은 일을 두 번 하나.

## 제품

3등급만.

- **P1 문제 정의** — 계획이 푸는 문제가 사용자 요청과 맞나.
- **P2 이미 정한 결정** — CLAUDE.md · LEARNINGS · 명세의 날짜 붙은 사용자 결정과 어긋나나.
- **P3 크기 · 되돌리기** — 더 작게 내고 나중에 키울 수 있나. 되돌리기 쉬운가.

## 화면

화면(`apps/admin/src/web/**`)을 건드릴 때만.

- **D1 원칙** — `docs/DESIGN.md` 원칙과 맞나.
- **D2 시안** — 바꾸기 전에 시안(A · B · C)을 보여 줬나.
- **D3 문구** — 화면 한글 문구가 CLAUDE.md §3 을 지키나. 영어 표(`messages/*.ts`) 키도 같이 바꾸나.
- **D4 폭 · 테마** — 폭 · 밝게/어둡게 확인이 할 일 `검증` 에 들어 있나(`tpx-impl` Step 3 표).
