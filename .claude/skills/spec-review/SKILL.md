# spec-review

`docs/SPEC.md`에 적힌 계약과 불변식을 코드가 실제로 지켰는지 **예/아니오로** 검사한다.

## 이 스킬이 존재하는 이유

이 프로젝트의 가장 큰 리스크는 버그가 아니라 **"돌아가긴 하는데 SPEC과 다르게 만든 것"** 이다.
화면은 똑같이 보이고 테스트도 통과하는데, 나중에 파라미터를 바꾸고 과거 증적을 열었을 때
값이 달라져 있는 식으로 드러난다. 그때는 이미 되돌리기 어렵다.

사용자는 코드를 직접 읽어 이런 어긋남을 잡지 못한다. 이 검사가 사실상 유일한 방어선이다.

## 두 가지 철칙

**1. 만든 세션이 아닌 다른 세션이 검사한다.**
자기가 짠 코드를 자기가 검사하면 자기 가정을 그대로 통과시킨다.
이 스킬이 실행 중인 세션이 대상 코드를 작성한 세션이라면, 그 사실을 먼저 알리고 검사를 진행하되
결과에 `[자기검사]`를 표시한다.

**2. 고치지 않는다. 보고만 한다.**
위반을 발견해도 코드를 수정하지 마라. 어느 항목이 어디서 깨졌는지만 알린다.
수정은 해당 워크스트림 담당 세션이 한다. 검사자가 고치면 소유 경로 규칙이 무너진다.

## 절차

1. `docs/SPEC.md`와 `CLAUDE.md`, `docs/LEARNINGS.md`를 읽는다
   LEARNINGS에 적힌 과거 위반은 재발 여부를 반드시 확인한다
2. 검사 범위를 확인한다 — 특정 워크스트림인가, 전체 병합 전 검사인가
   범위가 불분명하면 묻는다
3. 아래 체크리스트를 순서대로 검사한다. 각 항목은 예/아니오로 답이 나와야 한다
4. 지정된 형식으로 보고한다
5. 보고 내용을 **그대로** `docs/reviews/<YYYY-MM-DD>-<범위>.md`에 저장한다
   (예: `docs/reviews/2026-10-02-WS-C.md`, 전체 검사는 `-ALL`)
   이 파일이 없으면 응답이 끝날 때마다 경고가 뜨고, pre-push 훅이 푸시를 막는다

전체 검사는 코드베이스 전체를 훑어야 하므로, 규모가 크면 dynamic workflow로 병렬 처리해도 된다.
워크스트림 단위 검사는 일반 세션으로 충분하다.

## 체크리스트

### A. 계약 위반 — 치명

한 곳이라도 깨지면 병렬 작업 전체가 어긋난다.

| # | 검사 | 통과 조건 |
|---|------|----------|
| A1 | `packages/kit/src/types.ts`가 Phase 0 이후 변경됐는가 | 변경 없음 |
| A2 | `db/migrations/`가 Phase 0 이후 변경됐는가 | 변경 없음 |
| A3 | `docker-compose.yml`이 Phase 0 이후 변경됐는가 | 변경 없음 |
| A4 | 러너 HTTP 요청·응답이 `ExecuteRequest` / `ExecuteResponse`와 필드까지 일치하는가 | 일치 |
| A5 | Admin API 경로와 응답 형태가 SPEC §7과 일치하는가 | 일치 |
| A6 | DB 컬럼명이 SPEC §6과 일치하는가 | 일치 |

A1~A3은 `git log --oneline -- <경로>`로 Phase 0 커밋 이후 변경이 있는지 본다.

### B. 도메인 불변식 — 치명

SPEC §3에 적힌 불변식. 깨지면 데이터가 조용히 거짓이 된다.

| # | 검사 | 통과 조건 |
|---|------|----------|
| B1 | `run_item`의 `params`/`expected`가 실행 시점 **스냅샷 복사**인가, `param_set` 참조인가 | 스냅샷 복사 |
| B2 | `run_item`의 `tc_name`·`precondition`도 스냅샷인가 | 스냅샷 |
| B3 | 러너 코드가 DB에 접근하는가 (DB 클라이언트 import, 커넥션 문자열, SQL) | 접근 없음 |
| B4 | 스캔 시 `tcId` 중복을 검출해 실패시키는가 | 검출함 |
| B5 | 코드에서 사라진 케이스를 삭제하는가, `is_active=false`로 두는가 | false 처리 |
| B6 | 동시 실행 수가 설정값(기본 2)으로 제한되는가 | 제한됨 |
| B7 | Reporting 컨텍스트가 `evidence_document` 외 테이블에 write 하는가 | write 없음 |
| B8 | `platforms` 배열 길이만큼 `run_item`이 생성되는가 | 생성됨 |

B1이 가장 자주 깨지고 가장 늦게 발견된다. **매번 최우선으로 검사한다.**

### C. 경계 침범 — 중대

| # | 검사 | 통과 조건 |
|---|------|----------|
| C1 | 각 워크스트림이 `docs/WORKSTREAMS.md`의 소유 경로 밖 파일을 수정했는가 | 수정 없음 |
| C2 | Catalog / Execution / Reporting이 서로의 모듈을 직접 import 하는가 | 직접 import 없음 |
| C3 | 러너가 공유 볼륨(`artifacts/`) 외 경로에 파일을 쓰는가 | 쓰지 않음 |

C1은 `git diff --name-only <phase0-커밋>..HEAD`로 변경 파일 목록을 뽑아 대조한다.

### D. 용어 — 중대

| # | 검사 | 통과 조건 |
|---|------|----------|
| D1 | `testId`, `caseId`, `test_case_id` 등 `tcId` 외 표기가 있는가 | 없음 |
| D2 | `tcId` 값이 `<도메인 2~6자 대문자>-<3자리>` 형식인가 | 일치 |
| D3 | Playwright `projects` 이름이 `desktop` / `mobile`과 철자까지 일치하는가 | 일치 |
| D4 | 화면 표기가 `PC` / `모바일`인가 (`desktop`/`mobile`은 코드 안에서만) | 일치 |

D1은 `grep -rn "testId\|caseId\|test_case_id" --include=*.ts` 로 확인한다.

### E. 테스트 코드 규칙 — 중대

`tests/**` 에만 적용된다.

| # | 검사 | 통과 조건 |
|---|------|----------|
| E1 | `npm run check:tests`가 통과하는가 (주석·expect·명세·describe·문장 — SPEC §4 K1~K8은 기계가 본다) | 통과 |
| E2 | 데모 케이스 10건이 모두 있는가 (`DEMO-001`~`DEMO-010`) | 전부 있음 |
| E3 | `DEMO-008`~`010`이 디바이스 축을 실제로 검증하는가 | 검증함 |
| E4 | `name`·절차 제목·검증 문장이 검수자가 읽을 만한 한국어 문장인가 (기계가 못 보는 품질) | 읽힘 |

**E1은 검사기가 스텁이면 통과로 세지 않는다.** `apps/admin/src/catalog/check.ts`를 열어
K1~K8을 실제로 검사하는지부터 본다. Phase 0가 둔 exit 0 스텁은 무조건 초록불이라
CI가 통과해도 규칙이 지켜졌다는 뜻이 아니다. 스텁 상태면 `해당 없음(WS-A 미구현)`으로 적고,
그 범위에서 테스트 코드 규칙은 사람이 봤다는 것을 보고에 명시한다.

### F. 화면 규칙 — 경미

| # | 검사 | 통과 조건 |
|---|------|----------|
| F1 | 목록 화면에 JSON 원문이 노출되는가 | 노출 없음 |
| F2 | 결과 목록이 케이스 1행에 디바이스별 판정을 묶어 표시하는가 | 묶음 |
| F3 | 입력 폼 라벨이 `describe()` 값에서 오는가, 하드코딩인가 | describe에서 옴 |
| F4 | 코드 뷰가 기본 접힌 상태인가 | 접힘 |
| F5 | 증적 문서에 코드나 `httpTrace`가 포함되는가 | 미포함 |
| F6 | 판정을 색만으로 전달하는 곳이 있는가 (글자 없이 색만) | 없음 |

| # | 검사 | 통과 조건 |
|---|------|----------|
| G1 | 각 기능에 대응하는 테스트가 있는가 | 있음 |

## 보고 형식

코드 지적이 아니라 **항목별 판정**으로 쓴다. 사용자는 코드를 읽지 않는다.

```markdown
# SPEC 검사 결과 — <범위> (<날짜>)

## 요약
치명 2건 · 중대 1건 · 경미 0건 — **병합 불가**

## 치명

### B1 — params가 스냅샷이 아님
어디:   apps/admin/src/execution/run-service.ts:84
무엇:   run_item에 param_set_id를 넣고 조회 시 JOIN으로 값을 가져옴
왜 문제: 입력값을 수정하면 과거 실행 기록의 값도 같이 바뀐다.
        증적 문서가 실제로 돌린 값과 달라진다.
고칠 곳: WS-B

### B3 — 러너가 DB에 접근함
어디:   apps/runner/src/execute.ts:12
무엇:   pg 클라이언트를 import해 run_item을 직접 업데이트
왜 문제: 컨테이너 분리가 무의미해지고, 나중에 큐로 교체할 수 없다.
고칠 곳: WS-C

## 중대
...

## 통과한 항목
A1~A6, B2, B4~B8, C1~C3, D1~D4, E1~E4, F1~F6, G1~G2
```

- 위반이 없으면 `**병합 가능**`으로 쓰고 통과 목록만 남긴다
- 치명이 1건이라도 있으면 병합 불가다. 중대는 사용자가 판단한다
- `왜 문제` 줄은 **나중에 무엇이 잘못되는지**를 적는다. 코드 설명이 아니다
- 체크리스트에 없는 문제를 발견하면 `기타` 절에 따로 적고, 체크리스트 항목으로
  추가할 만한지 한 줄로 제안한다
- **같은 항목이 두 번째로 걸렸으면** 보고에 `[재발]`을 붙인다.
  재발은 개별 수정으로 끝내면 안 되고, SPEC이 애매하거나 규칙이 없다는 신호다.
  어디를 고쳐야 재발이 멈추는지 한 줄로 제안한다

## 하지 말 것

- 코드 수정
- 보안·성능·가독성 지적 (gstack `/review` 또는 `/ponytail-review` 담당)
- SPEC 자체가 틀렸다는 판단 — 어긋남만 보고하고, SPEC 변경 제안은 별도로 한 줄만
- 통과 항목을 길게 설명하기 — 번호만 나열한다
