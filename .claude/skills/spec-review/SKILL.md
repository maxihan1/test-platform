# spec-review

SPEC 에 적힌 계약과 불변식을 코드가 실제로 지켰는지 **예/아니오로** 검사한다.
SPEC 본문은 `docs/spec/` 아래 공통 7장·도메인 5장으로 나뉘어 있고 `docs/SPEC.md`가 색인이다.

## 이 스킬이 존재하는 이유

이 프로젝트의 가장 큰 리스크는 버그가 아니라 **"돌아가긴 하는데 SPEC과 다르게 만든 것"** 이다.
화면은 똑같이 보이고 테스트도 통과하는데, 나중에 파라미터를 바꾸고 과거 증적을 열었을 때
값이 달라져 있는 식으로 드러난다. 그때는 이미 되돌리기 어렵다.

사용자는 코드를 직접 읽어 이런 어긋남을 잡지 못한다. 이 검사가 사실상 유일한 방어선이다.

## 두 가지 철칙

**1. 만든 세션이 아닌 다른 세션이 검사한다.**
자기가 짠 코드를 자기가 검사하면 자기 가정을 그대로 통과시킨다.
이 스킬이 실행 중인 세션이 대상 코드를 작성한 세션이라면, 그 사실을 먼저 알리고 검사를 진행하되
결과에 `[자기검사]`를 표시한다.

**2. 고치지 않는다. 보고만 한다.**
위반을 발견해도 코드를 수정하지 마라. 어느 항목이 어디서 깨졌는지만 알린다.
**검사자가 고치면 검사자가 아니게 된다** — 자기가 고친 것을 자기가 통과시킨다.
철칙 1 과 같은 이유다. (2026-09-18 까지 이 자리의 근거가 「소유 경로 규칙이 무너진다」였다.
그 규칙은 이제 없다 — 근거만 바뀌었고 철칙은 그대로다.)

## 절차

1. `docs/SPEC.md`(색인)를 읽고 **검사 범위에 해당하는 장**을 읽는다. 전체 범위 검사면 12장을 전부 읽는다.
   `CLAUDE.md`, `docs/LEARNINGS.md`도 읽는다.
   LEARNINGS에 적힌 과거 위반은 재발 여부를 반드시 확인한다
2. 검사 범위를 확인한다 — 특정 워크스트림인가, 전체 병합 전 검사인가
   범위가 불분명하면 묻는다
3. 아래 체크리스트를 순서대로 검사한다. 각 항목은 예/아니오로 답이 나와야 한다
4. 지정된 형식으로 보고한다
5. 보고 내용을 **그대로** `docs/reviews/<YYYY-MM-DD>-<범위>.md`에 저장한다
   (예: `docs/reviews/2026-10-02-WS-C.md`, 전체 검사는 `-ALL`)
   이 파일이 없으면 응답이 끝날 때마다 경고가 뜨고, pre-push 훅이 푸시를 막는다

전체 검사는 코드베이스 전체를 훑어야 하므로, 규모가 크면 dynamic workflow로 병렬 처리해도 된다.
워크스트림 단위 검사는 일반 세션으로 충분하다.

## 체크리스트

### A. 계약 위반 — 치명

한 곳이라도 깨지면 병렬 작업 전체가 어긋난다.

| # | 검사 | 통과 조건 |
|---|------|----------|
| A1 | `packages/kit/src/types.ts` 변경이 **SPEC §5.1에 적힌 것과 일치**하는가 | 일치 (또는 변경 없음) |
| A2 | `db/migrations/` 변경이 **SPEC §6에 적힌 것과 일치**하는가 | 일치 (또는 변경 없음) |
| A3 | `docker-compose.yml` **과 `apps/*/Dockerfile`** 변경이 **SPEC §9에 적힌 것과 일치**하는가 | 일치 (또는 변경 없음) |
| A4 | 러너 HTTP 요청·응답이 `ExecuteRequest` / `ExecuteResponse`와 필드까지 일치하는가 | 일치 |
| A5 | Admin API 경로와 응답 형태가 SPEC §7과 일치하는가 | 일치 |
| A6 | DB 컬럼명이 SPEC §6과 일치하는가 | 일치 |

**A1~A3은 2026-09-17부터 "변경 없음"이 아니라 "SPEC 대로인가"를 본다.** 개정 SPEC 이 세 파일의 변경을
이미 승인했고 훅의 잠금 목록(`guard.mjs`의 `LOCKED`)도 그날 비웠다. 이제 변경되는 것이 정상이다.

`git diff origin/main...HEAD -- packages/kit/src/types.ts db/migrations/ docker-compose.yml apps/*/Dockerfile` 로 무엇이 바뀌었는지 뽑아
SPEC 해당 절과 **한 줄씩 대조한다. SPEC 에 없는 변경이 하나라도 있으면 치명이다.**
잠금이 사라졌으므로 이 검사가 유일한 방어선이다 — 변경이 없으면 "변경 없음"으로 적고 넘어간다.

### C. 경계 침범 — 중대

| # | 검사 | 통과 조건 |
|---|------|----------|
| C1 | 이번 작업 범위 밖 폴더를 건드렸는가. 건드렸으면 **계획이나 게이트 2 요약에** 이유가 적혀 있는가 | 이유가 있음 (계획이 없는 0·1등급은 게이트 2 요약만 본다) |
| C2 | Catalog / Execution / Reporting이 서로의 모듈을 직접 import 하는가 | 직접 import 없음 |
| C3 | 러너가 공유 볼륨(`artifacts/`) 외 경로에 파일을 쓰는가 | 쓰지 않음 |
| C4 | 주석이 **다른 파일이 막아 준다**를 근거로 위험을 안 막았으면, 그 파일을 열어 확인했는가 | 확인함 (또는 그런 주석 없음) |

C1은 `git diff --name-only origin/main...HEAD` 로 변경 파일 목록을 뽑아
계획의 `files` 와 대조한다.

**C4 는 2026-09-19 에 생겼다** (LEARNINGS 「문서가 규정한 것이 코드에 안 걸려 있다」 3회차).
러너의 `abort()` 주석이 "admin이 닫는 UPDATE마다 `finished_at IS NULL`을 붙여 이미 막고 있다"를 근거로
경합을 안 막았는데, 그 가드는 `store.ts` 의 `CLOSE_UNFINISHED` 에만 있고 `finishItem()` 에는 **없었다.**
근거로 든 자리 바로 위 주석이 「언제나 붙인다」라고 규정하고 있어서 그 말을 확인 없이 믿었다.
**같은 파일의 다른 주석이 그렇게 말한다는 것은 근거가 아니다.** 해당 SQL·조건을 눈으로 센다.

**2026-09-18 부터 기계가 안 본다.** `ownership` 훅을 걷어냈다 — 구현은 멀쩡했지만
켜는 자리(`settings.local.json` 의 `env`)를 아무도 안 채워 한 번도 안 돌았고, 쓰지 않기로 정했다.

그래서 이 항목은 「막았는가」가 아니라 **「범위를 벗어난 이유가 어딘가에 적혀 있는가」**를 본다.
벗어나는 것 자체는 금지가 아니다 (`CLAUDE.md §1.1`).

**어디를 보는지는 등급에 따라 다르다.** 계획 파일은 2등급 이상에만 있다.

| 등급 | 어디를 보나 |
|---|---|
| 0 · 1 | 게이트 2 요약 (계획 파일이 없다) |
| 2 · 3 | 계획의 `files` — 구현 중에 늘었으면 게이트 2 요약 |
| 병합 전 전체 검사 | 게이트 2 요약. **다른 세션이 돌리므로 계획을 안 들고 있다** |

### G. TDD — 경미

| # | 검사 | 통과 조건 |
|---|------|----------|
| G1 | 각 기능에 대응하는 테스트가 있는가 | 있음 |
| G2 | 테스트를 통과시키려고 테스트 자체를 느슨하게 고친 흔적이 있는가 | 없음 |
| G3 | DB 테스트의 정리 구문(`DELETE ... LIKE`)이 **자기 fixture에만** 맞는가 | 자기 것만 |
| G4 | 표를 **일괄로 갱신하는 제품 코드**(`UPDATE ... WHERE` 에 키 목록만 있는 것)에 범위 조건이 있는가 | 있음 |
| G5 | 한 검사 파일이 「**없어야 한다**」고 단언하는 이름을 다른 검사 파일이 만드는가 (접두사·아이디·제목) | 만들지 않음 |
| G6 | 화면을 브라우저로 확인했으면 **새로고침·재진입 없이** 되는지 봤는가 | 봤음 |
| G7 | 경계·권한 검사가 **부르는 쪽이 적는 값**(질의 문자열·헤더·본문)으로 우회되는가. 그리고 검사가 **그 축을 바꿔 가며** 돌리는가 | 우회 안 됨 · 축을 바꿔 돌림 |

**G3는 연속 3회로 본다.** Vitest는 파일을 병렬로 돌리므로 1회 통과는 증거가 못 된다.
`DATABASE_URL='postgres://platform:platform@localhost:5433/platform' npx vitest run` 을 세 번.
갈래별 접두사 — WS-A `ZZA` · WS-B `XBS`·`XBR`·`XBQ`·`XBX` · WS-F `xfu1`~`xfu4`·`XFS1`~`XFS4`.
**WS-D는 `ZZ`로 시작하는 것을 쓰지 않는다** (WS-A의 `ZZA%` 정리에 지워진다).
파일이 여러 개면 파일마다 또 가른다.

**G5는 접두사를 갈래마다 갈랐는데도 흔들릴 때 보는 자리다** (2026-09-18 신설).
`store.test.ts` 가 「`XBQ` 는 등록되지 않은 서비스」라고 단언하는데 `queries.test.ts` 가
`beforeAll` 에서 `XBQ` 를 등록했다. **같은 갈래 안이라 접두사 규칙은 지켜져 있었다.**
정리 구문도 범위 조건도 문제가 없다 — 두 파일이 같은 이름을 두고 **반대로 단언**한 것이다.
9회 중 2회 깨졌다. 「없어야 한다」는 단언은 **아무도 만들지 않는 이름**으로 해야 한다.

**G4는 G3이 통과했는데도 테스트가 흔들릴 때 보는 자리다** (2026-09-18 신설).
`save()` 의 비활성 처리가 DB 전체를 범위로 잡고 있어, 실제 스캔이 돌 때마다 남의 fixture를 내렸다.
**접두사를 갈래마다 나눠 써도 이런 코드 앞에서는 소용이 없다.** 증상이 양방향이라
어느 쪽이 범인인지 가리기 어렵다 — 정리 구문만 보지 말고 그 표를 일괄 갱신하는 제품 코드를 본다.

**G6 은 「확인 방법이 버그를 가린다」를 보는 자리다** (2026-09-19 신설, 같은 유형 2회차).

브라우저로 눌러 봤다는 것이 증거가 되려면 **사람이 실제로 하는 것과 같아야 한다.**
새로고침하거나 화면을 다시 열어서 확인하면 **폴링·상태 갱신이 안 돌아도 결과가 맞게 보인다.**

| 언제 | 무엇이 가려졌나 |
|---|---|
| 2026-09-19 (② 증적) | `location.reload()` 로 확인해서, 2초 폴링이 안 도는 것을 못 봤다. 실제로는 버튼이 「만드는 중입니다」에서 **영영 굳는다** |
| 2026-09-19 (① 로그인) | 로그인 **뒤** 경로만 눌러 봐서, 도중에 세션이 끊겼을 때 로그인 화면이 안 뜨는 것을 못 봤다 |

**둘 다 자기검사가 놓치고 바깥 렌즈(`/code-review`)가 잡았다.** 코드를 덜 읽어서가 아니라
**확인하는 방법이 그 경로를 안 밟아서**다. 그래서 「읽었는가」가 아니라 「어떻게 확인했는가」를 묻는다.

무엇에 걸리나 — 자동 갱신(폴링)에 기대는 것 · 한 번 닫으면 다시 안 뜨는 것 ·
세션이 도중에 끊기는 것 · 도는 중에 상태가 바뀌는 것. **화면을 안 건드렸으면 해당 없음이다.**

### H. 문서 정합 — 중대

SPEC 이 12장으로 갈려 있어 절 번호가 유일한 주소다. 주소가 깨지면 다음 세션이 본문을 못 찾는다.

| # | 검사 | 통과 조건 |
|---|------|----------|
| H1 | `npm run check:spec` 이 통과하는가 (가리킨 §번호가 실재하는가 · 장 사이 링크가 살아 있는가) | 통과 |
| H2 | 같은 규칙이 두 장에 적혀 있으면 내용이 같은가 (장이 갈린 뒤로 이 위험이 커졌다) | 같음 |
| H3 | 절을 새로 만들었다면 `docs/SPEC.md` 색인에 올렸는가 — 장 목록 · 절 번호 · 표 주인 **셋에 더해, 「기능을 더하거나 고칠 때」 라우터 표에도** 새 개념의 줄이 있는가 | 올림 |
| H4 | 기존 절 번호를 바꾸지 않았는가 (번호는 영구 주소다. 새 내용은 뒤에 번호를 더한다) | 안 바꿈 |
| H5 | 손으로 적어 둔 **숫자**가 실제와 맞는가 (「검색 조건 다섯」·「바꿀 것 여섯」·「221군데」·장별 줄 수) | 맞음 |

**H1은 기계가 본다. H2는 사람이 본다.** 같은 내용이 두 장에 적히면 한쪽이 반드시 뒤처진다.
발견하면 정본을 한 장으로 정하고 나머지는 그 장을 가리키게 고친다.

**H5는 반쯤 기계가 본다.** `check:spec` 이 장별 줄 수와 절 참조 수를 세어 대조한다.
산문 속의 개수(「조건 다섯」 같은 것)는 아직 사람이 본다 — 발견하면 **숫자를 빼고 정본 표를 가리키게** 고친다.
2026-09-18 에 이 항목이 생긴 이유는 같은 유형이 세 번 나왔기 때문이다 (분량 12곳 · 「221군데」 · 「조건 다섯」 3곳).

## 보고 형식

코드 지적이 아니라 **항목별 판정**으로 쓴다. 사용자는 코드를 읽지 않는다.

```markdown
# SPEC 검사 결과 — <범위> (<날짜>)

## 요약
치명 2건 · 중대 1건 · 경미 0건 — **병합 불가**

## 치명

### B1 — params가 스냅샷이 아님
어디:   apps/admin/src/execution/run-service.ts:84
무엇:   run_item에 param_set_id를 넣고 조회 시 JOIN으로 값을 가져옴
왜 문제: 입력값을 수정하면 과거 실행 기록의 값도 같이 바뀐다.
        증적 문서가 실제로 돌린 값과 달라진다.
고칠 곳: WS-B

### B3 — 러너가 DB에 접근함
어디:   apps/runner/src/execute.ts:12
무엇:   pg 클라이언트를 import해 run_item을 직접 업데이트
왜 문제: 컨테이너 분리가 무의미해지고, 나중에 큐로 교체할 수 없다.
고칠 곳: WS-C

## 중대
...

## 통과한 항목
A1~A6, B2, B4~B8, C1~C3, D1~D5, E1~E4, F1~F8, G1~G7
```

- 위반이 없으면 `**병합 가능**`으로 쓰고 통과 목록만 남긴다
- 치명이 1건이라도 있으면 병합 불가다. 중대는 사용자가 판단한다
- `왜 문제` 줄은 **나중에 무엇이 잘못되는지**를 적는다. 코드 설명이 아니다
- 체크리스트에 없는 문제를 발견하면 `기타` 절에 따로 적고, 체크리스트 항목으로
  추가할 만한지 한 줄로 제안한다
- **같은 항목이 두 번째로 걸렸으면** 보고에 `[재발]`을 붙인다.
  재발은 개별 수정으로 끝내면 안 되고, SPEC이 애매하거나 규칙이 없다는 신호다.
  어디를 고쳐야 재발이 멈추는지 한 줄로 제안한다

## 하지 말 것

- 코드 수정
- 보안·성능·가독성 지적 (gstack `/review` 또는 `/ponytail-review` 담당)
- SPEC 자체가 틀렸다는 판단 — 어긋남만 보고하고, SPEC 변경 제안은 별도로 한 줄만
- 통과 항목을 길게 설명하기 — 번호만 나열한다
