# spec-review

SPEC 에 적힌 계약과 불변식을 코드가 실제로 지켰는지 **예/아니오로** 검사한다.
SPEC 본문은 `docs/spec/` 아래 **공통**과 **도메인** 두 무리로 나뉘어 있고 `docs/SPEC.md`가 색인이다.
**몇 장인지는 여기 적지 않는다** — 장이 늘거나 줄면 한쪽만 고쳐진다 (`CLAUDE.md §2.7 ⑤`). 정본은 색인의 장 목록이다.

## 이 스킬이 존재하는 이유

이 프로젝트의 가장 큰 리스크는 버그가 아니라 **"돌아가긴 하는데 SPEC과 다르게 만든 것"** 이다.
화면은 똑같이 보이고 테스트도 통과하는데, 나중에 파라미터를 바꾸고 과거 증적을 열었을 때
값이 달라져 있는 식으로 드러난다. 그때는 이미 되돌리기 어렵다.

사용자는 코드를 직접 읽어 이런 어긋남을 잡지 못한다. 이 검사가 사실상 유일한 방어선이다.

## 두 가지 철칙

**1. 만든 세션이 아닌 다른 세션이 검사한다.**
자기가 짠 코드를 자기가 검사하면 자기 가정을 그대로 통과시킨다.
이 스킬이 실행 중인 세션이 대상 코드를 작성한 세션이라면, 그 사실을 먼저 알리고 검사를 진행하되
결과에 `[자기검사]`를 표시한다.

**2. 고치지 않는다. 보고만 한다.**
위반을 발견해도 코드를 수정하지 마라. 어느 항목이 어디서 깨졌는지만 알린다.
**검사자가 고치면 검사자가 아니게 된다** — 자기가 고친 것을 자기가 통과시킨다.
철칙 1 과 같은 이유다. (2026-09-18 까지 이 자리의 근거가 「소유 경로 규칙이 무너진다」였다.
그 규칙은 이제 없다 — 근거만 바뀌었고 철칙은 그대로다.)

## 절차

1. `docs/SPEC.md`(색인)를 읽고 **검사 범위에 해당하는 장**을 읽는다. 전체 범위 검사면 `docs/spec/` 아래 장을 전부 읽는다.
   `CLAUDE.md`, `docs/LEARNINGS.md`도 읽는다.
   LEARNINGS에 적힌 과거 위반은 재발 여부를 반드시 확인한다
2. 검사 범위를 확인한다 — 특정 워크스트림인가, 전체 병합 전 검사인가
   범위가 불분명하면 묻는다
3. 체크리스트(아래 §체크리스트는 references 에 있다 — 파일 셋)를 순서대로 검사한다. 각 항목은 예/아니오로 답이 나와야 한다
4. 지정된 형식으로 보고한다
5. 보고 내용을 **그대로** `docs/reviews/<YYYY-MM-DD>-<범위>.md`에 저장한다
   (예: `docs/reviews/2026-10-02-WS-C.md`, 전체 검사는 `-ALL`)
   이 파일이 없으면 응답이 끝날 때마다 경고가 뜨고, pre-push 훅이 푸시를 막는다

전체 검사는 코드베이스 전체를 훑어야 하므로, 규모가 크면 dynamic workflow로 병렬 처리해도 된다.
워크스트림 단위 검사는 일반 세션으로 충분하다.

## 체크리스트는 references 에 있다 — 빠짐없이 전부 연다

**검사에 들어가기 전에 아래 파일 셋을 Read 로 연다 — 기억으로 하지 않는다.**
**범위에 상관없이 빠짐없이 전부 연다.** 항목이 해당 없으면 열어 본 뒤 `해당 없음` 으로 적는다.

| 절 | 등급 | 파일 |
|---|---|---|
| A. 계약 위반 | 치명 | `references/checklist-a-c.md` |
| B. 도메인 불변식 | 치명 | `references/checklist-a-c.md` |
| C. 경계 침범 | 중대 | `references/checklist-a-c.md` |
| D. 용어 | 중대 | `references/checklist-d-f.md` |
| E. 테스트 코드 규칙 | 중대 | `references/checklist-d-f.md` |
| F. 화면 규칙 | 경미 | `references/checklist-d-f.md` |
| G. TDD | 경미 | `references/checklist-g-h.md` |
| H. 문서 정합 | 중대 | `references/checklist-g-h.md` |

## 보고 형식

코드 지적이 아니라 **항목별 판정**으로 쓴다. 사용자는 코드를 읽지 않는다.

```markdown
# SPEC 검사 결과 — <범위> (<날짜>)

## 요약
치명 2건 · 중대 1건 · 경미 0건 — **병합 불가**

## 치명

### B1 — params가 스냅샷이 아님
어디:   apps/admin/src/execution/run-service.ts:84
무엇:   run_item에 param_set_id를 넣고 조회 시 JOIN으로 값을 가져옴
왜 문제: 입력값을 수정하면 과거 실행 기록의 값도 같이 바뀐다.
        증적 문서가 실제로 돌린 값과 달라진다.
고칠 곳: WS-B

### B3 — 러너가 DB에 접근함
어디:   apps/runner/src/execute.ts:12
무엇:   pg 클라이언트를 import해 run_item을 직접 업데이트
왜 문제: 컨테이너 분리가 무의미해지고, 나중에 큐로 교체할 수 없다.
고칠 곳: WS-C

## 중대
...

## 통과한 항목
A1~A6, B2, B4~B8, C1~C6, D1~D5, E1~E4, F1~F8, G1~G8
```

- 위반이 없으면 `**병합 가능**`으로 쓰고 통과 목록만 남긴다
- 치명이 1건이라도 있으면 병합 불가다. 중대는 사용자가 판단한다
- `왜 문제` 줄은 **나중에 무엇이 잘못되는지**를 적는다. 코드 설명이 아니다
- 체크리스트에 없는 문제를 발견하면 `기타` 절에 따로 적고, 체크리스트 항목으로
  추가할 만한지 한 줄로 제안한다
- **같은 항목이 두 번째로 걸렸으면** 보고에 `[재발]`을 붙인다.
  재발은 개별 수정으로 끝내면 안 되고, SPEC이 애매하거나 규칙이 없다는 신호다.
  어디를 고쳐야 재발이 멈추는지 한 줄로 제안한다

## 하지 말 것

- 코드 수정
- 보안·성능·가독성 지적 (gstack `/review` 또는 `/ponytail-review` 담당)
- SPEC 자체가 틀렸다는 판단 — 어긋남만 보고하고, SPEC 변경 제안은 별도로 한 줄만
- 통과 항목을 길게 설명하기 — 번호만 나열한다
