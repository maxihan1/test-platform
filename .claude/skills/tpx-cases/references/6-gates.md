## §6. 검증 관문 넷

관문 0 을 더해 지금은 다섯이다(2026-09-30). 절 이름은 영구 주소라 그대로 둔다.

**파이프로 넘기지 않는다** — `| tail` 은 종료 코드를 `tail` 것으로 바꾼다.

**관문 0 — 원장 대조 (2026-09-30).** 기획서 → 표 방향이다. 관문 1~4 는 전부 표 → 코드만 봐서
**표에 아예 안 오른 요구는 어느 관문도 못 봤다.** 관문 2 가 표 → 코드라면 관문 0 은 그 앞 칸이다. 규칙은 §2 「원장」.

```bash
npm run check:ledger -- <원장 사본> docs/cases/<접두사>.md --tests tests/<폴더> --agent > /tmp/cl.log 2>&1; echo "EXIT=$?"
```

- `EXIT=0` 이어야 넘어간다. `1` 이면 로그의 `빠짐:` · `형식 오류:` 줄대로 표에 케이스 줄이나 제외 줄을 더한다.
  `칸 번호 어긋남:` 줄(작성 에이전트 — 2026-10-04)은 `npm run ledger:number` 를 다시 돌리고 케이스 파일 이름 · `tcId` 를 표에 맞춘다. 「출처에 요구 번호가 둘 이상」이면 그 줄을 번호마다 나눈다(2026-10-13)
  `경고:`(원장에 없는 번호)는 막지 않지만 출처 칸 오타인지 본다
  `설계 칸 빠짐:` · `설계 거절 형식 오류:` 줄(작성 에이전트 — 2026-10-05)은 `references/test-design.md` 「관문 0 의 설계 줄과 대처」대로 줄을 더하거나 오판이면 설계 거절로 뺀다
  `기법 어긋남:` 줄(작성 에이전트 · `--tests` 를 줄 때 — 2026-10-05)은 같은 파일 「기법 표시」대로 케이스 파일의 `techniques` 를 「」 안대로 고친다
- **사람 세션은 `--agent` 를 뺀다** — 그 표시가 「사람이 뺌」 · 「다음 요청」을 형식 오류로 친다(원장 사본의 `사람이뺌` · `다음요청` 에 든 번호 — 에이전트가 main 표에서 뽑은 것 — 만 예외). 칸 번호 · 설계 대조도 `--agent` 일 때만 한다. 원장 사본은 §1 「원장을 뽑는다」의 `ledger.json` 이다
- 표만 쓴 §2 끝에서 `--tests` 없이 한 번 돌려 빠짐을 일찍 본다. 관문으로는 `--tests` 를 붙인다 — 빼면 tcId 파일이 있는지 안 본다
- 사본이 원장 없음이면 `EXIT=0` 으로 끝난다. **건너뛴 것이지 통과한 것이 아니다** — 결과에 `원장 없음 — <까닭>`
- **작성 에이전트는 올리기 직전에 메모리의 원장으로 같은 대조를 다시 한다.** 자식이 고친 사본과 자식의 요약을 안 믿는다 —
  빠져도 거절하지 않고(2026-09-30 게이트 1) 그 셈을 PR 본문 머리 · 요청의 셈(상세 화면 · 대시보드)에 「빠짐」으로 남긴다.
  여기서 초록이어도 사본을 고쳐 만든 초록이면 거기서 빠짐으로 드러난다

**관문 1 — 형식.**

```bash
npm run typecheck   > /tmp/tc.log 2>&1; echo "EXIT=$?"
npm run check:tests > /tmp/ct.log 2>&1; echo "EXIT=$?"
```

**관문 2 — 표를 따랐나.** 실행을 안 하므로 관문 0 다음으로 싸다. **대조는 표 기준 한 방향이다** — 기획서 → 표는 관문 0 이 본다.

|---|---|
| 전제 | `precondition` 배열에 그 문장이 있다 |
| 조작 | `test.step` 제목 중 하나가 그 문장이다 |
| 결과 | `verify` 문장 중 하나가 그 문장이다. **`tcId` 를 혼자 쓰는 케이스는 `name` 도 그 문장이다** |

**합친 케이스(R15)의 `name` 은 여기서 대조하지 않는다.** `결과` 칸이 둘인데 `name` 은 하나라
글자 대조가 성립하지 않는다 — 그 문장은 §3 내부 게이트가 **선택지로 따로 물어** 받은 것이고,
**여기 아래 「`결과` 칸의 문장이 서로 다른가」가 그 문장까지 범위에 넣는다.**
**`결과` 칸 쪽은 그대로 전부 대조한다** — 둘 다 `verify` 문장으로 남아 있어야 한다.

**약한 어설션을 금지 목록 없이 잡는 자리가 여기다.** 「목록이 비어있지 않다」는 금지어에 없지만
표의 문장과 다르므로 걸린다.

**★ 코드에만 있는 준비 스텝은 위반이 아니다 — 그 안의 판정 문장도 마찬가지다.**
R7 이 준비 스텝을, **R14 가 그 안의 판정을**, **R16 이 그것을 「만들기 / 확인」 둘로** 시킨 것이다.
표에는 그 칸이 아예 없다.
**반대 방향(코드 → 표)으로 훑으면 준비 스텝이 전부 걸린다** (2026-09-21 실측).
그렇게 훑고 「고치면」 길이 둘 다 나쁘다 — 표를 케이스 수의 두 배로 늘리거나
**전제 판정을 지우거나**(R14 가 붙인 `blocker` 가 같이 사라진다).
**★ 관문 2 는 글자만 본다.** 문장과 코드의 **의미**가 어긋나는 것은 R12 로 사람이 본다.

**여기서 같이 보는 것 둘** — 둘 다 `check:tests` 의 K 규칙이 안 보는 자리다.
**아직 기계가 없다.** 옮기려면 `apps/admin/src/catalog/check.ts` 인데 그 파일은 2등급이라
작업 등급이 올라간다 — 그것만 따로 잡는다 (2026-09-21 판단).
**작성 에이전트는 위 글자 대조와 둘째(결과 문장이 서로 다른가 · 아래 인용의 「결과이면서 다른 케이스의 준비 판정」까지)를 `npm run authoring:check` 가 프로그램으로 본다** (2026-10-19 — `tpx-author` `SKILL.md` 관문 명령). 첫째(blocker 겹 수)와 사람 세션은 그대로다.
**「확인 하나에 값 하나」(`5-writing.md` R12 아래 — `verify` 실제 값을 배열 · 객체로 묶었나)도 같은 명령이 본다.** 사람 세션은 여기서 눈으로 본다.

- **준비 겹마다 `{ blocker: true }` 가 있나** (R14). **개수를 손으로 적지 않는다** —
  기준은 케이스 수가 아니라 **그 케이스의 준비 겹 수**다 (CLAUDE.md §2.7 ⑤).
  **R16 으로 가른 케이스는 「확인」 절차에서 찾는다** — 「만들기」 절차에는 판정이 없는 것이 맞다
- **`결과` 칸의 문장이 서로 다른가.** 범위는 **표의 `결과` 칸과, 합친 케이스(R15)의 `name` 이다.**
  **합친 이름은 위 글자 대조에서 빠지므로 여기서라도 봐야 한다** — 안 그러면 그 문장을 아무도 안 본다.
  합친 이름끼리도, 합친 이름과 다른 `결과` 문장 사이에서도 겹치면 안 된다.
  K 규칙은 `tcId` 만 유일하면 통과시키므로 글자까지 같은 `name` 이 둘이면 실행 목록과 증적에
  **같은 줄이 둘씩** 떠서 읽는 사람이 같은 케이스가 두 번 도는 줄 안다
  (2026-09-21 실측 — PR #43 에서 둘이 겹쳤다). 겹치면 **전제·조작의 차이를 결과 문장에 싣는다**
>
> **전제 판정 문장의 중복은 막지 않는다.** 「화면 제목 todos가 보인다」는 여러 케이스에 있다 —
> 준비가 같으면 문장도 같은 것이 옳고, 그것까지 유일하게 만들면 **같은 준비에 다른 이름**을
> 지어내게 된다. 다만 **한 문장이 어디선 `결과`이고 어디선 전제이면** 증적에서
> 「결과 FAIL」과 「전제 실행 중단」으로 갈려 읽는 사람이 헷갈린다 — 그때는 `결과` 쪽을 고친다

```bash
PLATFORM_SLOW_API=1 npx playwright test tests/<폴더> --project=desktop --repeat-each=3 --reporter=line > /tmp/pw.log 2>&1; echo "EXIT=$?"
```

**관문 3 — 3회 연속 초록.** 2/3 면 초록이 아니라 **불안정**이고 대개 대기 누락이다.
**느린 망으로 돈다** (2026-10-13 PRD-F9-35) — `PLATFORM_SLOW_API=1` 이면 kit 이 화면이 부르는 API 응답을 0.1~1.5초씩 늦춘다(케이스의 모킹 응답은 그대로). 데모는 응답이 빨라 기다림이 빠져도 초록이라, 여기서 빨개지면 `5-stable.md` 대로 기다림을 고친다.
**한도 + 1 을 넣은 뒤 오류 문구를 기다리다 시간 초과면 기다림 탓이 아니다** — 그 칸 길이를 잰다(`4-selector.md` 「입력 칸 한도」). 한도면 칸이 막는 것이고 §4 에서 재지 않고 쓴 것이다. 기다림을 늘리지 않는다(2026-10-16 · PRD-F9-12).
표를 아직 고칠 수 있으면(관문 0 을 열기 전) `two-kinds.md` 「화면에만 있는 입력 규칙」의 한도 줄대로 고친다 — 기획서가 오류를 말했으면 차이 · 미확정이다. 관문 0 을 연 뒤면 기대값을 화면에 맞추지 않고 `held: '보류 — <칸>이 한도 N 에서 막는다'` 를 단다(종료 조건 3).
이번에 새로 쓴 케이스 이야기다 — 이미 있던 케이스가 이렇게 빨개지면 기대값이 사람 것이라 고치지 않는다(`tpx-author` `reverse.md` §3.5 「값 다름」).
`mobile` 을 선언한 케이스가 있으면 `--project=mobile` 도 돈다 — 크롤러 판정이 반응형 · 적응형이면 한 명령에 `--project=desktop --project=mobile --workers=2` 로 동시에(`two-kinds.md` 「화면 크기 판정」 · 2026-10-16 PRD-F10-07), 아니면 한 번 더.
**작성 에이전트가 팬아웃했으면 분담이 다르다** — `tpx-author` `references/fanout.md` §5(서브에이전트는 다 쓴 뒤 자기 파일 한 판 — 1회 · 빨강만 다시, 자식은 마지막 전체 돌려 보기 — 이번 작성이 닿은 케이스를 3회 · 2026-10-03 · 2026-10-13 · 2026-10-26). 사람 세션은 이 절 그대로다.
**held 케이스는 kit 이 건너뛴다** — 요약 줄에 `N skipped` 로 잡히고 관문을 막지 않는다. 값이 들어간 뒤 3회 실행은 반영 때 에이전트가 한다.

**★ 인자 없이 돌리지 않는다.** `DEMO-002` 는 일부러 실패하고 `DEMO-009` 는 모바일에서 실패한다
(SPEC §10). 전체를 돌리면 **빨강이 정상값**이라 내 실패가 묻힌다.
**★ `--repeat-each` 는 같은 프로세스에서 이어 돈다** (`playwright.config.ts` 의 `workers: 1`).
렌더 타이밍은 보지만 **냉시작과 실행 순서는 안 본다.**

**관문 4 — 일부러 부러뜨린다.** `spec-review` **G8** 이 요구하는 절차다. 그것을 따르고
결과를 PR 에 적는다. 파일을 고치지 않고 `PLATFORM_PARAMS` 로 기대값만 주입해도 된다.
**held 케이스는 빼고 부순다** — 돌지 않으니 부러져도 빨개지지 않는다.
**기본 계정으로 로그인 실패를 내지 않는다** (2026-10-19) — 비밀번호 · 아이디를 틀리게 넣는 부수기와 아래 입력값 ②(범위 밖)는 일회용 회원으로 한다. 로그인 실패가 쌓이면 계정을 잠그는 서비스가 많다 —
#303 은 관문 4 가 기본 계정을 10분 잠가 그동안 그 계정을 쓰는 실행이 다 빨개질 수 있었다. 서브에이전트 넷이 나란히 돌면 한 명이 잠근 계정에 나머지 셋이 걸린다.

**★ 기대값만 뒤집으면 절반만 본다.** 기대값을 틀리게 하면 판정이 빨개지는 것은 당연하다 —
그건 **판정이 살아 있나**를 볼 뿐이고 **앵커가 판정을 삼켰나**는 못 본다.
**조작을 틀리게 바꿔서도 한 번 부러뜨린다** — 누를 곳을 옆 것으로 바꾸거나 한 단계를 뺀다.

**★★ 기대값을 `params` 에서 가져온 판정은 기대값 주입으로 아예 안 부러진다.**
`verify(..., innerText(), params.todo)` 는 **입력과 기대가 같이 움직이는 항등식**이라
`PLATFORM_PARAMS` 로 무엇을 넣어도 양쪽이 같이 바뀌어 **그대로 통과한다.**
2026-09-21 실측 — `TODO-005` 에 `params.active` 를 엉뚱한 값으로 주입했더니 **1 passed** 였다.
**이런 판정은 반드시 조작을 바꿔서 부러뜨린다.** 대개 `blocker` 가 붙은 전제 판정이다.
**이유를 안 적으면 바쁠 때 제일 먼저 생략된다.**

그리고 **어느 문장이 죽었는지**를 본다. `firstFailure` 가 **원인 자리의 문장**이어야 한다.
두 단계 뒤 문장이 대신 죽었으면 **앞 판정이 그 고장을 통과시킨 것**이다 (R13 ★).

2026-09-21 실측 — `TODO-005` 의 「Active」를 「Completed」로 바꿔 필터가 뒤집힌 고장을 흉내 냈더니
전제 판정이 통과하고 **두 단계 뒤 문장이 죽었다.** 기대값만 뒤집는 부수기로는 안 나왔을 것이다.

**★ 입력값 칸은 기본값 말고 다른 값으로 두 번 돌린다 (2026-10-12 사용자 · PRD-F9-24).** 비밀값이 아닌 입력값 칸(`5-inputs.md`)이 있는 케이스가 대상이고 held 케이스는 뺀다.
파일을 고치지 않고 `PLATFORM_PARAMS='{"params":{…}}'` 로 넣는다 — 작성 에이전트는 `PLATFORM_PARAMS='…' npm run -s authoring:run -- 한번 <묶음> <파일들>` 로 돈다. 관문 3 에 쓴 환경 변수(대상 서버 · 계정)는 그대로 두되 **`PLATFORM_SLOW_API` 는 빼고 돈다** (2026-10-19 사용자 — 케이스가 칸 값을 쓰는지만 보는 확인이라 응답을 늦출 까닭이 없다. 기다림은 3회 실행이 본다. #303 은 178건을 늦춘 채 두 번 넘게 돌아 관문 4 가 22분이었다). 거기서 `PLATFORM_PARAMS` 를 썼으면 그 값에 더해 담는다.
**작성 에이전트가 팬아웃했으면 서브에이전트가 자기 케이스 몫을 자기 한 판 바로 앞에 돈다** — 넷이 나란히 돌고 빨개진 것은 서브에이전트가 그 자리에서 고친다. 자식은 합친 뒤 고친 케이스만 돈다(`tpx-author` `references/fanout.md` §4 · §5).

| 넣는 값 | 나와야 할 것 | 어기면 |
|---|---|---|
| ① 범위 안의 다른 값 — `.describe()` 범위 안에서 기본값과 다른 값을 칸마다 | 초록 | 기대값이 기본값에 묶였다(기본 상품의 가격을 글자로 적었다) — 기획서 규칙으로 계산하게 고친다. 범위 글이 틀렸으면 범위를 고친다 |
| ② 범위 밖 값 — 한 번에 한 칸만 | 빨강 | 그 칸을 안 쓴다(본문이 기본값을 글자로 적었다) — 칸 값을 쓰게 고친다 |

- **여러 케이스를 한 번에 돌린다** — 케이스는 자기 명세에 있는 칸만 읽고 나머지는 버린다. 그래서 ① 은 대상 케이스의 값을 한 `PLATFORM_PARAMS` 에 다 담아 한 번 돈다.
  ② 는 케이스마다 한 칸씩 담아 한 번 돌고, 칸이 둘 이상인 케이스가 있으면 다음 칸으로 한 번 더 돈다. 같은 이름 칸의 범위가 케이스마다 달라 한 값으로 못 담으면 나눠 돈다
- ② 의 빨강은 요소 못 찾음 · 시간 초과여도 된다 — 칸을 쓰는지만 본다. 범위 밖이 없는 칸(아무 값이나 같은 결과)은 ② 에서 빼고 결과에 칸 이름을 적는다
- 결과는 관문 4 결과 뒤에 한 줄로 붙인다 — `입력값 ① N건 초록 · ② N건 빨강 · 뺀 칸 <이름들 / 없음>`(작성 에이전트는 결과 요약의 `입력값 바꿔 돌려 보기:` 줄)

### 관문이 빨개지면 — trace 로 까닭부터 가른다 (2026-10-16 PRD-F10-04)

관문 3 · 관문 4 · 마지막 돌려 보기 · 묶음별 한 판은 trace 없이 돈다. 빨개진 케이스가 있으면 긴 오류 글을 읽기 전에 이렇게 한다.

1. **그 케이스만 trace 를 켜고 한 번 더 돈다** — 관문에 쓴 환경 변수(`PLATFORM_SLOW_API=1` · `PLATFORM_BASE_URL` · `PLATFORM_PARAMS`)는 그대로 두고 출력 폴더만 따로 준다.
   ```bash
   PLATFORM_OUTPUT_ID=heal-<tcId> PLATFORM_SLOW_API=1 npx playwright test <케이스 파일> --project=desktop --trace on --reporter=line > /tmp/heal.log 2>&1; echo "EXIT=$?"
   npm run trace:summary -- artifacts/playwright/heal-<tcId>
   ```
   작성 에이전트(자식 · 보조)는 손으로 부르지 않고 `PLATFORM_SLOW_API=1 npm run -s authoring:run -- 한번 heal-<묶음 slug, 자식은 main> <케이스 파일> --trace` 로 돈다 — 브라우저 자리를 받고 찍힌 trace 폴더를 요약에 넘긴다(`tpx-author` `references/fanout.md` §4 「1번 돌려 보기」).
   1번은 기기 하나만 돈다 — **휴대폰에서만 빨간 케이스는 끝에 `--mobile-only` 를 붙인다.** 안 붙이면 PC 로 돌아 초록이 나오고, 아래 줄대로 흔들림으로 잘못 가른다
   초록이면 그 자체가 흔들림 근거다 — `5-stable.md` 대로 기다림 · 남의 데이터를 본다. 「화면이 맞음」 요청은 프롬프트가 알려 준 `traces/RUN<번호>-<케이스>.txt`(서버가 가린 그 실행의 요약)를 먼저 읽는다
2. **요약 몇 줄로 가른다** — `가름:` 줄이 스크립트의 판정이다. 실패한 조작 · 앞 조작 · 그 단계의 API · 콘솔을 보고 맞는지 확인한다.
   자료 폴더 `api-map.txt`(서비스 지도)에 그 화면이 늘 부르는 API 가 있는데 요약에 안 보이면 그 응답을 안 기다린 「대기 부족」을 먼저 의심한다(`4-selector.md` 「서비스 지도」 — 기대값 근거는 아니다)
   | 가름 | 하는 일 |
   |---|---|
   | 서버 오류(5xx) · 끊김 | 케이스를 고치지 않는다. 다시 돌려 같은 까닭으로 3회면 `held: '보류 — 서버 오류(5xx): <요청 줄>'`(끊김은 `'보류 — 끊김: <요청 줄>'`) |
   | 깨짐 | 요소 주소 · 기다림 · 가는 길을 고친다(§4 탐침). `한도:` 줄이 있으면 기다림을 늘리기 전에 칸 길이부터 잰다(`4-selector.md` 「입력 칸 한도」 · 위 관문 3 문단) |
   | 값 다름 | 기대값을 안 건드린다(종료 조건 3). 이번에 새로 쓴 케이스면 표의 문장과 코드가 맞는지만 본다 |
   | 모름 | 단계 밖(준비 · 테스트 제한 시간)에서 멈췄다 — 로그의 첫 오류 줄을 본다 |
   `4xx` 줄은 근거로만 쓴다 — 입력 오류 케이스는 4xx 가 정상이다. 요약의 API 응답 · 화면 값은 기대값의 근거가 아니다(R10)
   held 는 이번에 새로 쓰거나 다시 쓴 케이스에만 단다 — 역방향의 바뀐 화면 케이스(기존 케이스)는 `tpx-author` `reverse.md` §3.5 대로 보류 없이 둔다
3. **그래도 모르면 멈춘 화면에 붙는다** — `--debug=cli` 는 첫 조작에서 멈추고 세션 이름을 찍는다. 백그라운드로 띄우고 그 이름으로 붙은 뒤 다 보면 끈다.
   작성 컨테이너는 화면이 없어 `xvfb-run -a` 로 감싼다(맥은 창이 뜬다).
   ```bash
   PLATFORM_OUTPUT_ID=heal-<tcId> xvfb-run -a npx playwright test <케이스 파일> --project=desktop --debug=cli --reporter=line > /tmp/dbg.log 2>&1 &
   npx playwright cli attach <찍힌 세션 이름>     # 그 뒤 -s=<세션 이름> 으로 snapshot · step-over · resume
   ```

### 종료 조건 (CLAUDE.md §6)

1. 같은 케이스가 **같은 이유로 3회** 빨강 → **그 케이스만 멈춘다.** 파일을 지우지 않고
   `held: '보류 — <에러 첫 줄>'` 을 달아 두고(§5) **나머지는 계속 간다** — 케이스마다 문제가 다르다.
   서버 오류 · 끊김으로 갈랐으면 사유 머리를 그 이름으로 둔다(위 「관문이 빨개지면」) — 사람이 케이스 탓인지 서버 탓인지 보류 목록에서 바로 가른다.
   채울 칸이 없으면 사람은 그 케이스를 제거만 할 수 있다 — 고칠지 뺄지 사람이 정한다.
   **작성 에이전트의 서브에이전트는 held 를 달지 않고 돌려준다** (2026-10-26 PRD-F15-01) — 한 판과 다시 돈 판에서 같은 이유로 3번 빨간 케이스는 더 고치지 않고 빨강과 첫 실패 문장을 돌려준다.
   held 는 자식이 마지막 3회를 보고 정한다(`tpx-author` `references/fanout.md` §5)
2. 끝난 뒤 보류 목록을 CLAUDE.md §6 형식으로 한 번에 보고
3. **초록을 만들려고 케이스를 느슨하게 고치지 않는다** (CLAUDE.md §5).
   `verify` 를 지우거나 기대값을 실제값에 맞추는 것은 고친 게 아니라 **보류**다
4. **오류 추정 줄의 케이스는 화면이 점검 목록 기준을 어겨 빨간 것이면 `held` 를 달지 않는다** — 빨간 채로 두고 결과 요약 `오류 추정:` 줄(사람 세션은 끝 보고)에 싣는다(`two-kinds.md` 「오류 추정 점검 목록」).
   케이스가 틀려 빨간 것은 1 대로다
