## §5. 흔들리지 않게 쓰기 (2026-10-12 PRD-F9-25 · 26)

⑧ 시험에서 MKT 472건을 응답이 늦고 가끔 실패하는 데모(`DEMO_UNSTABLE=1`)에 5번씩 돌렸더니 기준선 모드에서는 안 나던 실패가 9건 나왔다. MKU · MKF · MKS 920건을 같은 데모에 한 번 돌리니 12건이 더 나왔다.
원인은 세 갈래였다. 기다릴 것을 잘못 골랐고, 남이 만든 데이터를 집었고, 날짜로 만들어지는 값을 코드에 적었다. 실행은 두 건씩 같이 돌고 반복 실행은 같은 케이스의 회차가 나란히 돈다(실행 동시 수 2).

### 기다린 뒤 누르고 읽는다

- **화면이 API 로 채우는 내용은 그 내용으로 기다린다.** HTML 에 처음부터 있는 제목은 앵커가 못 된다 — MKT 주문 상세는 「주문 상세」 제목이 바로 뜨고 주문 내용은 API 뒤에 그려져, 제목만 기다리고 주문 번호를 읽은 FN-231 이 늘 실패했다
- **Page Object 의 `열기` 는 그 화면이 다 그려질 때까지 기다린다.** 「다 그려짐」 앵커는 화면마다 한 번 정해 Page Object 에 둔다(성공 화면과 오류 화면이 다르면 `.or()` 로 둘 다). 케이스마다 따로 기다리지 않는다
- **로그인 확인 뒤에 그려지는 공통 영역(머리글 · 바닥글)에 기대는 조작은 그 영역이 그려진 뒤에 한다.** 공통 영역 부품에 `그려질때까지()` 를 두고 화면 Page Object 의 기다리기가 부른다 —
  MKT 「장바구니 담기」는 로그인 확인 전에 누르면 아무 일도 안 하고(FN-180), 「맨 위로」 버튼은 바닥글이 그려지기 전에 내리면 끝내 안 나타났다(FN-017 · 018)
- **「사라질 때까지」(`state: 'detached'`)는 그 요소가 먼저 그려진 뒤에만 앵커가 된다.** 아직 안 그려졌으면 바로 통과한다 — MKS-FN-402 는 로그인 화면 머리글이 그려지기 전에 「로그인」을 눌러 「머리글 로그인 링크가 사라졌다」가 곧장 참이 됐다
- **숨은 요소는 역할로 못 기다린다.** `getByRole(...).waitFor({ state: 'attached' })` 도 숨은 요소는 잡지 않는다 — 숨은 요소는 역할 트리에 없다. 숨은 버튼이 생겼는지를 기다려야 하면 그 버튼을 그리는 영역을 기다린다

### 남이 만든 데이터를 집지 않는다

- **목록의 「첫 줄」 · 「아무 상품」처럼 다른 케이스가 만들고 지울 수 있는 것을 집지 않는다.** 케이스가 만든 것을 이름 · 번호로 집는다 —
  MKT-UI-124 는 목록 첫 글을 열었다가 같이 돈 회차가 지운 임시 글을 열어 「삭제된 글」을 만났다
- **수가 적은 공용 데이터(재고 1개뿐인 상품)에 기대면 같은 케이스 회차끼리 부딪힌다.** 넉넉한 데이터가 있으면 그것을 쓴다(MKT-FN-228 은 데모에 재고 1~10 상품이 하나뿐이라 남은 한계다)
- **서버 전체를 초기화하는 요청은 같이 도는 케이스를 깨뜨린다**(MKT-FN-281 `POST /api/reset`) — 케이스 쪽에서 막을 길이 없어 끝 보고에 적는다

### 날짜 · 순번으로 만들어지는 값은 찾아 쓴다

- **서버가 날짜 · 순번으로 만드는 값(주문 번호 `DM20260614-0003` 꼴)을 코드에 적지 않는다.** 데모를 다른 날 켜면 없는 값이다(MKS-FN-390 ~ 393)
- 조건(상태 · 기간 · 내가 만든 것)으로 화면이나 API 에서 찾아 쓴다 — 도우미 하나로 둔다(MKS `상태별주문번호` · `석달넘은주문번호`, MKF `배송중주문번호`). 표의 `조작` · `결과` 칸에도 그 값을 적지 않는다
- 가짜 응답(모킹) 안에 넣는 값은 서버 데이터가 아니라 상관없다
