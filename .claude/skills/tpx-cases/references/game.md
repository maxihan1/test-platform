## 게임 케이스 — 꼴 · 상태 도우미 · 확인 수단 · 스모크 · 배치 확인 (2026-10-23 · GAME-F1-11)

종류 「게임」 애플리케이션(프롬프트에 `--- 게임 화면 ---` 절이 있다)의 케이스를 쓸 때 연다. 화면을 읽는 법(첫 화면 · 폰 잡기 · 창 훑기 · 게임 지도)은 `tpx-author` `references/game.md` 다 — 이 파일은 그 뒤 케이스를 쓰는 법이다.
정본은 명세 `docs/spec/도메인/게임.md` §3.10 「케이스 꼴」 · 「확률 세 겹」 · 「설계 칸」 · 「빌드마다 돌리기」 · 「화면 잘림 검사」, 타입은 `docs/spec/공통/3-공유계약.md` 「게임 테스트 타입」이다.
표의 칸 · 줄 쓰는 법(확률 세 겹 · 데이터 표 · 끊김)은 `test-design.md` 「게임 애플리케이션」, 기다림은 `5-stable.md` 「게임」이다.

**게임 테스트는 기능 · 게임 시나리오 두 갈래다** (2026-11-18 · 명세 결정 18). 버튼 한 번에 결과가 바로 나오면 이 파일의 기능 케이스, 플레이를 해야 값이 생기면(준 피해 · 경험치 · 드랍) **`game-scenario.md`** 의 미션이다(가르는 기준은 그 파일 §1 「로그 줄 종류」) — 표를 쓰기 전에 둘 다 Read 로 연다.

- **기능 케이스에 넣는 것** — 기획서 규칙 · 경계값 · 화면에 보이는 것 · 버튼 반응 · 화면 잘림(§6) · 확률 세 겹 · 데이터 표 대조 · 오류 추정. 웹이 UI 케이스로 따로 쓰던 몫(보이는 것 · 배치)도 그 창을 다루는 요구의 기능 줄 안에서 본다 — **게임은 축 `UI` 줄을 새로 쓰지 않는다**
- **버튼 반응** — 기획서가 적은 반응은 그 요구의 기능 줄이다. 기획서가 적지 않은 반응은 지금처럼 `버튼 반응 —` 줄로 쓴다(`two-kinds.md` 「버튼 반응 케이스」) — 번호 명령이 이 줄을 축 `UI` 로 묶어 `-UI-` 번호가 남는다(`scripts/authoring-slots.ts`)
- 이미 있는 `-UI-` 케이스는 그대로 둔다 — 고쳐 쓰지 않는다

### 1. 케이스 한 건의 꼴

```ts
import { defineCase, test, verify } from '@platform/kit';

import { 결과고정, 새캐릭터, 아이템주기, 캐릭터지우기 } from './helpers/game-state.helper.js';
import { 강화창 } from './pages/enhance.page.js';

export const spec = defineCase({
  tcId: 'ASH-FN-012',
  name: '강화 결과를 파괴로 고정하고 +7 강화를 하면 장검이 가방에서 사라진다',
  platforms: ['android'],
  precondition: ['+6 장검을 가진 새 캐릭터로 마을에 있다', '강화 결과가 파괴로 고정돼 있다'],
  techniques: ['결정 테이블'],
  elements: ['item:sword_long', 'rate:enchant_7'],
  params: null,
  expected: null,
});

test(spec, async ({ game, admin }) => {
  await test.cleanup('강화 결과 고정 풀기 · 케이스 캐릭터 지우기', async () => {
    await 결과고정(admin, 'enchant', null);
    await 캐릭터지우기(admin, 'qa012');
  });
  const 캐릭터 = await 새캐릭터(admin, 'qa012');
  await 아이템주기(admin, 캐릭터, 'sword_long', { 강화: 6 });
  await 결과고정(admin, 'enchant', '파괴');
  await test.step('강화사에게 장검 +7 강화를 맡긴다', async () => {
    const 창 = await 강화창.열기(game);
    await 창.강화하기('sword_long');
    await verify('장검이 가방에서 사라진다', await game.find('/HudCanvas/Inventory/Grid/sword_long'), null);
  });
});
```

- **정리는 `test.cleanup` 이다** (2026-11-18 · 명세 결정 20) — 몸통 맨 앞에서 부르면 kit 이 그 자리에서 한 번(시작 정리) · 몸통이 어떻게 끝나든 한 번 더(끝 정리) 돌린다. 정리가 실패해도 항목 판정은 그대로이고 「정리 실패」 표시만 남는다. 시작에도 도는 까닭은 사람이 멈추거나 러너가 끊으면 끝 정리가 안 돌아서다 — 그래서 정리는 앞 실행이 남긴 것도 찾아 치우게 쓴다(이름 앞머리 · 고정 결과 풀기). **치울 것이 없어도 성공하게 쓴다** — 처음 도는 실행의 시작 정리에는 지울 캐릭터가 없다. 그 도우미는 「없음」(404 같은 응답)을 성공으로 보고, 그 밖의 응답만 던진다 — 안 그러면 매번 「정리 실패」가 찍혀 진짜 실패가 묻힌다. 판정에 드는 `finally` 정리는 새 케이스에 쓰지 않는다. 정리 안에서는 `verify` · `test.step` 을 부르지 않는다(kit 이 던진다)

- **몸통은 `{ game, driver, admin, request, api, params, expected }` 다**(정본 명세 공통/2 「게임 케이스」) — `page` 가 없다. `game` 이 게임 안 오브젝트를, `admin` 이 어드민 키를 붙인 서버 요청을, `request` 가 키 없는 서버 요청을, `driver` 가 Appium(앱 끄고 켜기 · 와이파이)을 맡는다
- `platforms: ['android']` 만 적는다 — **PC 게임이면 `['windows']`** 이고 버튼 그림 케이스 하나만 지원 패드 값이다(§8). 게임 하나에 플랫폼 하나라 둘을 같이 적지 않는다. 기능 케이스의 `techniques` 는 웹과 같다(`test-design.md` 「기법 표시」)
- **`elements` 는 그 케이스가 닿는 게임 요소 열쇠다** — `game-elements.json` 에 이번에 쓴 열쇠나 `game-map.txt` 에 있는 열쇠만 적는다. 지어낸 열쇠는 쓰지 않는다. 닿는 요소가 없으면 칸을 빼고, 리터럴 배열로 적는다(`techniques` 와 같다)
- **주소는 오브젝트 이름(하나뿐일 때) 아니면 `/` 로 시작하는 경로다** — 같은 이름 형제는 `[순번]`(0부터). 주소는 CLI 의 `Ran:` 줄 · 창 기록 · 메인이 찍어 둔 트리 파일에서만 옮긴다. 좌표를 받는 메서드는 없다
  - `/` 로 시작하지 않으면 주소 전체가 이름 하나다 — `Ready Btn/Text (TMP)` 는 그런 이름의 오브젝트를 찾는다. 자식으로 내려가려면 `/` 로 시작하는 경로를 쓴다
  - 경로 안의 `/` 는 바로 아래 자식, `//` 는 아래 어디서나다. 글자 조건(`*[contains(@text,…)]`)으로 찾는 글은 보통 손주(`Label/Text`)에 있다 — `/창//*[contains(@text,…)]` 로 쓴다
  - `[순번]` 은 같은 부모 아래에서 맞은 형제 중 몇 번째다 — `//` 로 찾아도 부모마다 따로 센다. 그래서 `목록//*[contains(@text,…)][-1]` 은 그 글이 두 줄에 있으면 둘이 맞고, 여럿이 맞은 찾기는 실패한다(BRM-FN-303 — 채팅에 접속 알림 줄이 둘). 같은 글이 여러 줄에 올 수 있으면(알림 · 채팅 · 목록) 줄(`Toasts/Toast[n]` · `Row[-n]`)마다 읽어 찾고 센다
  - 잠깐 떴다 사라지는 것(머리 위 숫자 · 알림)의 주소는 가이드에 적힌 전체 경로나, 뜨게 만든 직후 찍은 트리에서 옮긴다. 트리에 보이는 비슷한 이름(숫자를 만드는 빈 오브젝트 `ShowcaseDamageNumbers`) 아래를 짐작하지 않는다(BRM-FN-077 · 133~135)
- **`game.get` 의 컴포넌트 이름은 트리 줄 머리로 짐작하지 않는다** — 트리 줄 머리 `Text` 는 글자가 있다는 표시일 뿐이라 TextMeshPro 글자도 `Text` 로 찍히고, 버튼 머리도 실제 클래스(`Button` 을 물려받은 `UIHUDButton`)와 다를 수 있다. 글은 `game.text` 로 읽고, 그 밖의 칸은 `npx control-cli -s=g components <주소>` 가 찍은 이름을 옮긴다(BRM-FN-017 · 098 — 「Text 에 Text 컴포넌트가 없습니다」). 막대 · 게이지가 얼마나 찼는지는 너비가 아니라 그 그림의 `Image.fillAmount` 다(BRM-FN-146)
- **어드민 키를 글자로 쓰지 않는다** — `admin` 이 대상 서버 줄의 키를 머리로 붙이고 기록에서 가린다. 머리 이름(`X-Admin-Key`)도 케이스에 적지 않는다
- **기대값은 표준 기획서에서만 온다.** 화면 · 창 기록 · 게임 지도 · 서비스 가이드는 근거가 아니다(웹과 같다)
- **손가락을 올려 둔 동안만 보이는 것(말풍선)은 눌러 두고 확인한 뒤 뗀다** (2026-11-17) — `const 손가락 = await game.touchDown(주소)` → `await game.waitFor(<말풍선 오브젝트>)` 와 글자 확인 → `await game.touchUp(손가락)`. 떼기는 `finally` 에 둔다(안 떼고 끝나도 kit 이 거두지만 같은 케이스의 뒤 단계가 눌린 채로 돈다). 주소만 받는다 — 좌표는 안 된다. 길게 누르기는 없다 — 눌렀다 뗀 뒤라 말풍선이 이미 사라져 있다
- **1초 안쪽 간격을 다투는 연속 동작을 두 명령으로 하지 않는다** — 명령 하나가 팜을 거쳐 수백 ms 다. 함께 보낼 것은 한꺼번에 보내고, 결과(횟수 · 잠금)를 먼저 본 뒤 그 결과가 버그를 가리킬 때만 「제때 눌렀나」를 따진다(ASH-FN-645 · UI-215)

### 2. 창 화면 객체 — `pages/<창>.page.ts`

웹 Page Object 와 같은 자리 · 같은 규칙이다(`two-kinds.md` 「Page Object」). 창 하나에 파일 하나고, 생성자가 `GameDriver` 를 받는다.

```ts
import type { GameDriver } from '@platform/kit';

export class 강화창 {
  static readonly 주소 = 'game:World/HudCanvas/EnhancePanel';

  private constructor(private readonly game: GameDriver) {}

  static async 열기(game: GameDriver): Promise<강화창> {
    await game.click('EnhanceButton');
    await game.waitFor('/HudCanvas/EnhancePanel');
    return new 강화창(game);
  }

  async 강화하기(아이템: string): Promise<void> {
    await this.game.click(`/HudCanvas/EnhancePanel/Slots/${아이템}`);
    await this.game.click('/HudCanvas/EnhancePanel/Confirm');
  }
}
```

- **`주소` 는 그 창의 화면 기록 열쇠 글자 그대로다** — `game:<장면>/<창 경로>`(창 경로는 같은 이름 형제 순번을 뗀 틀), 시작 화면은 `game:<장면>`. 스캔이 이 값으로 케이스와 창 기록을 잇는다. 견주기 명령 · `game-kept/` 기록 머리에 찍힌 열쇠를 옮긴다
- `열기` 는 창이 다 뜬 것(창 루트)을 기다리고 돌아온다. 두 창 이상에 나오는 조각(HUD 바 · 알림 띠)만 `components/` 다
- **목록 줄의 버튼을 누르는 메서드는 그 줄을 먼저 화면 안으로 끌어 올린다** — 스크롤 칸 아래 줄은 화면 밖이거나 「닫기」 띠에 가려 눌러도 안 먹는다. 탐색 때 보인 줄도 상품 · 우편이 늘면 밀려난다. 끌어 올리기는 화면 객체 메서드 하나에 두고 케이스 · 도우미는 그 메서드로만 누른다(BRM 상점 — 같은 코드가 도우미 한 파일에만 있고 나머지 구매 케이스 14건은 화면 밖 줄을 눌렀다)
- **같은 일을 하는 메서드 · 도우미가 이미 있는지 `helpers/` · `pages/` 를 grep 하고 쓴다** — 나눠 쓰면 묶음마다 비슷한 것을 새로 만들어, 고친 쪽만 고쳐진다

### 3. 상태 도우미 — `helpers/game-state.helper.ts`

케이스 준비는 걸어가거나 사냥해서 만들지 않는다. 새 캐릭터 · 골드 · 아이템 · 위치 · 레벨 · 결과 고정 · 확률 설정 · 몬스터 놓기 · 봇 치우기를 서버에 시켜 바로 만든다(명세 결정 16). 도우미는 서비스마다 한 파일이고 다음 작성이 그대로 다시 쓴다 — 이미 있으면 **더하기만** 한다.

**조작 맵의 상태 설정 행과 도우미는 짝이다** (2026-11-20 GAME-F5-08 · 명세 게임 §3.10 「탐색 플레이 · 조작 맵」).

- **준비 차례는 경로 검색이 찍은 차례 그대로다** — `npx tsx scripts/authoring-game-route.ts <자료 폴더> <목표 열쇠…>` 의 `[상태 설정]` 줄을 위에서부터 도우미 부르기로 옮긴다. 경고(⚠) 달린 행이 먼저 오도록 명령이 이미 짰다 — 차례를 바꾸지 않는다
- **행에 `도우미 <이름>` 이 있으면 그 도우미를 부른다** — 같은 일을 하는 도우미를 새로 쓰지 않는다
- **없으면 도우미를 만들고 `game-route.json` 의 그 행 `helper` 에 함수 이름을 적는다**(파일 이름이 아니다 — `GM골드`). 행이 맵에만 있으면(`game-route.txt`) 그 행의 종류 · 출발 · 동작을 글자 그대로 옮겨(따옴표로 감싼 칸은 JSON 글로 풀어 옮긴다 — `"a · b"` 는 `a · b`, 안의 `\"` 는 `"`) `rows` 에 `status: "OK"` 로 한 줄 더하고 `helper` 만 채운다 — 안 실은 칸은 서버가 지난 값을 지키고, 빌드 없는 확인은 「재확인 필요」를 풀지 않는다. 화면 객체 함수로 만든 이동 · 조작 행의 `fields.fn` 도 같은 꼴로 채운다. 정식 실행이 이 이름으로 그 행을 찾아 빌드를 적고, 실패하면 「재확인 필요」로 바꾼다
- **도우미 하나에 명령 하나로 나눠 쓴다** — 한 도우미가 명령 둘을 치면 두 행에 같은 이름이 붙어, 하나만 실패해도 두 행이 같이 「재확인 필요」가 된다
- 맵에 없는 준비가 필요하면 지금처럼 가이드대로 도우미를 쓰고 불러 본 뒤(아래), 통과하면 상태 설정 행으로 더한다(`tpx-author` `game.md` §8.3)

| 서비스 가이드에 | 도우미 | 예 |
|---|---|---|
| 게임 서버 어드민 API | 첫 인자가 `admin: APIRequestContext` | `결과고정(admin, 'enchant', '파괴')` → `POST /admin/forced` |
| GM 명령만 | 첫 인자가 `game: GameDriver` — 채팅 칸에 명령을 넣고 보낸 뒤 결과 글자를 기다린다 | `골드주기(game, 1000)` → `/gold 1000` |
| 둘 다 없다 | 만들지 않는다 | 그 케이스는 보류 — 출처에 `보류 — 상태 만드는 길 없음(어드민 API · GM 명령)` |

- **경로 · 본문 · 명령은 서비스 가이드(`docs/cases/<접두사>.guide.md` · 가이드 첨부)에 적힌 그대로만 쓴다.** 가이드에 없는 경로를 짐작하지 않는다 — 그 준비가 필요한 케이스는 보류다
- **응답 칸 · 기록 꼴도 짐작하지 않는다** — 가이드에 칸 이름이 없으면 부르기 명령으로 한 번 불러 찍힌 응답에서 옮긴다. `status ?? state ?? claimStatus` 처럼 이름을 늘어놓지 않는다(BRM-FN-271 — 셋 다 없어 빈 값). 봇 · 시험 주소 기록에서 찾는 글은 원문이다 — 화면이 붙이는 머리(「[알림]」)는 기록에 없고, 줄 종류(`toast` · `chat`)를 화면에 뜨는 자리로 짐작하지 않는다(BRM 의 GM 값 줄은 채팅 시스템 줄이라 `chat` 이다). 도우미를 쓴 뒤 기록을 한 번 찍어 종류 · 글을 맞춘다
- **준비가 실제로 됐는지 blocker 확인 하나를 둔다** — 대상이 없어도 오류 없이 끝나는 명령이 있다(캐릭터를 지운 뒤 값 넣기 · 적을 다 치운 뒤 그 적 누르기). 실패 걸기는 그 흐름이 실제로 부르는 요청에만 건다 — 어느 동작이 그 요청을 부르는지 가이드에 없으면 짐작하지 않는다(BRM-FN-425 — 로그인은 서버 상태 읽기를 안 불러 걸어 둔 실패가 안 쓰였다). 준비가 기획서에 없는 기능에 기대면(첨부 없는 우편을 지급 API 로 보내기 — 지급은 첨부가 하나 이상이어야 한다) 기획서가 말하는 길(지급 우편을 받아 비우기)로 만든다
- **쓴 도우미는 바로 불러 본다** — `npx tsx scripts/authoring-game-state.ts <폴더> <함수> '<인자 JSON 배열>'`. 어드민 API 꼴(첫 인자 `admin`)만 부른다. 케이스와 같은 키 · 같은 서버로 불러 돌려준 값을 찍는다. 던지면 경로 · 본문을 가이드와 다시 맞춘다. 「어드민 키가 없다」로 2 가 나오면 그 준비가 필요한 케이스는 보류다. 불러서 만든 것(캐릭터 · 고정 결과)은 같은 명령으로 지우거나 되돌린다
- 키 값은 환경값(`PLATFORM_ADMIN_KEY`)에만 있다 — 명령 · 케이스 · 파일 · 결과 요약에 글자로 적지 않는다. 빠른 검사가 키 글자를 찾으면 막는다
- 응답 코드가 기대와 다르면 문맥을 붙여 던진다 — `throw new Error(\`결과 고정 실패: ${String(res.status())} ${await res.text()}\`)`. 삼키지 않는다
- **간섭을 막는다** — 캐릭터 이름은 케이스 번호를 붙인 앞머리로 짓고(`qa012-…`), 다른 몬스터 · 봇은 치운 뒤 정해진 자리에 하나만 둔다. 폰이 움직여 자리를 못 박는 봇은 `5-stable.md` 「게임」의 「폰이 움직이는 것」대로 다시 고른다. 만든 것 · 고정한 결과 · 바꾼 확률표는 `test.cleanup` 에서 지우고 되돌린다(§1)
- **서버 초기화를 쓰지 않는다 — 계정 초기화만 쓴다** (2026-11-18 · 명세 결정 20) — 세계 전체를 되돌리는 명령(Ashveil `/admin/world/reset`)은 같은 서버를 쓰는 다른 실행을 깬다. 자기가 부르거나 자기 자리에 있는 것만 치운다
- **준비 명령이 시작 조건을 바꾸는지 본다** — 맵 행의 경고(⚠)가 그것이다. 맵에 없는 명령을 새로 쓰면 앞뒤로 레벨 · 골드 · 위치를 읽어 견주고, 바뀌었으면 그 행 `warning` 에 적는다. 레벨 · 장비 같은 시작 조건은 흔드는 명령이 다 끝난 뒤에 맞춘다
- **쌓이는 아이템을 받는 케이스는 준비 때 가방의 같은 아이템을 치운다** (2026-10-25 GAME-F2-13) — 물약 · 재료처럼 한 칸에 수량으로 합쳐지는 아이템을 줍기 · 전리품 · 구매 · 지급으로 받는 케이스다. 남아 있으면 받은 것이 그 묶음에 합쳐져 「자리 없음」이 안 나거나 수량이 합친 값으로 온다. 새 캐릭터의 시작 가방에도 들어 있을 수 있다 — 가방을 읽어 같은 아이템을 지운 뒤 시작한다(GAME-F1-14 의 줍기 · 봇 전리품 케이스 셋이 같은 까닭으로 빨갰다)
- 크롤 전용 캐릭터(`qacrawl`)는 케이스가 쓰지 않는다

### 4. 무엇으로 확인하나

| 값 | 확인 | 꼴 |
|---|---|---|
| 보이는 글자(창 제목 · 안내 · 숫자 표시) | 화면 | `await game.text('/HudCanvas/Gold/Value')` |
| 서버가 정하는 값(재화 · 아이템 · 강화 결과) | **서버와 화면 둘 다** — 값마다 `verify` 따로 | `admin.get(…)` 로 서버 값 · `game.text` 로 화면 값 |
| 게임이 폰에서 셈하는 값(이동 속도 · 데미지) | 게임 안 속성 | `await game.get('Player', 'PlayerController.moveSpeed')` |
| 데이터 표 줄 | 줄마다 `verify.element(문장, 열쇠, 서버값, 기대값)` | 아래 `test-design.md` 「데이터 표」 |
| 확률 ③ 분포 | `verify.rates(문장, 결과마다 횟수, 결과마다 기대 확률, 허용 오차)` | 아래 `test-design.md` 「확률 세 겹」 |

- 어드민 API 가 없고 GM 명령만 있으면 화면 값 · GM 조회 명령으로 보고, 결과 요약에 `서버 값 확인 없음 — <tcId 앞 10개>` 한 줄을 적는다
- 「확인 하나에 값 하나」(`5-writing.md` R12 아래)는 게임도 같다

### 5. 스모크 표시 — `smoke: true`

빌드마다 먼저 도는 케이스다(명세 「빌드마다 돌리기」). **핵심 경로를 한 번씩 지나는 정상 기능 케이스**에만 단다 — 로그인 → 캐릭터 고르기 → 월드 입장 → 사냥 한 번 → 상점 한 번.
경로 한 마디에 케이스 하나, 다 해서 5~10건이다. 경계 · 예외 · 오류 추정 · 확률 ③ 처럼 오래 걸리거나 일부러 틀리게 하는 케이스에는 달지 않는다.

- **게임 화면을 거치는 케이스로 고른다** — 어드민 API 만 부르고 끝나는 케이스는 빌드가 깨져도 초록이다. 상태는 도우미로 만들어도 되지만 그 경로 마디의 조작 · 확인은 `game` 으로 한다(1차 작성 PR #442 의 6건이 모두 서버 API 였다)
- **게임은 꼭 단다 — 웹의 「애매하면 빼 둔다」를 따르지 않는다** (2026-10-25 GAME-F2-13). 스모크가 없으면 빌드를 올리자마자 회귀 전체가 돈다. 경로 마디에 꼭 맞는 케이스가 없으면 가장 가까운 정상 기능 케이스에 단다
- **보조 AI 에게 나눠 맡겼으면 메인이 다 합친 뒤 폴더 전체를 보고 고른다** — 보조 AI 는 묶음 하나만 봐 다 빼 두므로 **보조 AI 는 `smoke` 를 달지 않는다**(PR #443 — 287건에 0건). 이어서 쓰는 작성은 앞 작성이 단 것을 먼저 세고, 빈 마디는 이번에 쓴 정상 기능 케이스가 맞을 때만 채운다 — 앞 작성 케이스는 고치지 않는다(`tpx-author` `references/continue.md`)
- 빠른 검사(`authoring:check -- 마지막`)의 「게임 케이스 형식」 줄이 폴더의 스모크를 세어 0건이면 짚는다. 머리 줄에 `스모크 N건` 이 찍힌다. 이번 작성이 폴더를 다 썼을 때만 센다 — 고친 요구만 다시 쓰는 작성은 안 짚는다

### 6. 화면 잘림 — 창마다 기능 케이스 하나에 배치 확인 한 줄

그 창을 여는 기능 케이스 하나에 창을 연 뒤 이 줄을 넣는다(게임은 UI 케이스를 새로 쓰지 않는다 — 위 「두 갈래」). 누를 수 있는 UI 가 화면 안전 영역(노치 · 둥근 모서리 제외) 밖이거나 서로 겹치면 실패한다.

```ts
const 배치 = await game.layout('/HudCanvas/EnhancePanel');
await verify('강화 창의 누를 수 있는 것이 화면 안에 있고 서로 겹치지 않는다', 배치.problems, []);
```

이 `verify` 문장은 표의 줄 결과 칸이 아니라 덧붙인 판정이다(`wording.md` 첫 표 「그 밖의 판정 문장」 꼴). 창 하나에 한 번만 넣는다.

### 7. 눌러 보기 · 나눠 쓰기 · 돌려 보기

- **폰을 만지는 것은 메인 하나다** — 눌러 보기 · 창 훑기는 메인만 한다(`tpx-author` `references/game.md` §3). 팬아웃이면 메인이 띄우기 전에 창마다 트리를 찍어 두고, 서브에이전트는 그 파일로만 쓴다(`tpx-author` `references/fanout.md` §7)
- **마지막에 잡은 폰에서 케이스마다 1번 돌린다** — 형식 관문(`check:tests`)을 통과시킨 뒤 `npx control-cli hold --minutes 30` 으로 잡고, 열린 CLI 세션은 `npx control-cli -s=g close` 로 닫고 `npm run -s authoring:run -- 게임 <폴더>` 를 부른다. 3 이면 같은 명령을 다시, 1 이면 빨간 케이스를 고치고 다시 부른다. 끝나면 `npx control-cli release`. 결과 요약 `3번 돌려 보기` 줄에 `폰 1번 — 초록 N · 빨강 M` 을 적는다 — 앱 줄에 「일반 회원 2」 같은 계정이 있으면 명령이 빈 폰을 더 잡아 폰마다 다른 게임 계정으로 나눠 돈다(같은 계정 두 폰은 「이미 접속 중」). 출력의 `폰 차이` · `계정 차이` 를 보는 법은 `tpx-author` `references/app.md` §4 와 같다(폰을 살필 때만 `control-cli hold --udid <그 폰>`). 도우미 · 창 객체를 고쳐도 그것을 쓰는 기존 케이스는 표본만 돈다 — 명령이 찍은 `안 돈 기존 게임 케이스 N개` 를 요약 줄에 `기존 표본만 — 안 돈 N` 으로 덧붙이고 손으로 대상을 좁히지 않는다
- **먼저 한 바퀴를 다 돌리고 빨간 것만 고친다** (2026-11-17 사용자) — 한 번 초록이던 케이스는 도우미 · 창 객체를 고쳐도 다시 안 돈다(명령이 `도우미 · 화면 파일을 고친 뒤 폰에서 다시 안 돈 초록 게임 케이스 N개` 를 찍는다). 그러니 도중에 빨강이 보여도 남은 케이스를 끝까지 돌린 뒤 빨간 것을 모아 한꺼번에 고친다. 고친 뒤에는 빨갛던 케이스 · 아직 안 돈 케이스 · 케이스 파일을 고친 것만 다시 돈다. 초록 케이스를 다시 돌리려고 케이스 파일을 건드리지 않는다. 결과 요약 `3번 돌려 보기` 줄에 `초록 유지 — 다시 안 돈 N` 을 덧붙인다 (SPEC 작성 §3.6 「한 번 초록이던 케이스는 다시 안 돈다」)
- **빨간 케이스를 고칠 때 확인을 약하게 바꾸지 않는다** (2026-10-25 GAME-F2-13) — 「누르면 ~가 된다」를 「보이고 누를 수 있다」(`find(…)?.interactable`)로 낮추면 그 버튼이 고장 나도 초록이다(PR #443 — GM 콘솔 버튼 다섯 개 등 12줄). 눌러도 반응이 없으면 먼저 까닭을 가른다
  - **목록 · 스크롤 칸 아래라 화면 밖** — 끌어 올려 보이게 한 뒤 누른다. `game.drag(<목록 아래쪽 항목>, <위쪽 항목>)` 로 끌고 `game.layout('<창>')` 의 `problems` 에 그 버튼의 `outside` 가 없어졌는지 본다. 끄는 일은 그 창 화면 객체의 메서드로 둔다
  - **스크롤 칸이 없는데 화면 밖**(배치 확인에 `outside`) — 게임의 화면 잘림이다. 확인은 그대로 두고 빨간 채로 두며 결과 요약에 `화면 잘림 — <tcId> <오브젝트 경로>` 를 적는다. 그 버튼을 눌러야 다음 단계로 가는 케이스면 `held: '보류 — 화면 잘림(<오브젝트 경로>)'`
  - **화면 안인데 반응이 없다** — 기다림(`5-stable.md` 「게임」)과 주소(같은 이름 형제)를 먼저 본다. 그래도 없으면 기획서와 다른 것이라 빨간 채로 둔다
- 폰을 못 잡거나 팜이 없거나 앱 줄을 몰라(어드민 키 · 계정이 둘 다 없다) 명령이 2 로 끝나면 `안 돌림(<까닭>)` 을 적는다 — 에이전트가 PR 머리에 「폰에서 돌려 보지 않은 게임 케이스」를 싣는다. 건너뜀을 초록으로 적지 않는다
- **빠른 검사(`authoring:check`)에 「게임 케이스 형식」 줄이 붙는다** (2026-10-23 GAME-F1-12) — 이번에 바뀐 케이스의 `elements` 가 지도(`game-map.txt` + 이번 `game-elements.json` − 그 `remove`)에 있나 · `platforms: ['android']`(PC 게임은 윈도우 값만) · 몸통에 `page` 가 없나, 바뀐 파일 전부(화면 객체 · 도우미 포함)에서 `driver` 동작에 `{ x, y }` 좌표를 넘기지 않나를 본다(순간이동 본문 · 위치 기대값은 괜찮다). 폴더를 다 쓴 작성이면 스모크 0건도 짚는다(§5). 그래서 **`game-elements.json` 을 먼저 쓰고 케이스를 쓴다** — 지도에 없다고 찍히면 열쇠를 지어내지 말고 요소를 파일에 더하거나(근거 요구 번호가 있을 때만) 칸에서 뺀다

### 8. PC 게임 — 키 · 패드 · 버튼 그림 케이스 (2026-11-20 GAME-F4-07)

프롬프트 게임 화면 절이 「PC 게임(Windows)」이면 이 절을 더한다. 정본은 명세 게임 §3.10 「윈도우 PC」다.

- **보통 케이스는 `platforms: ['windows']`** 다 — 키보드 · 마우스로 한 번 돈다. 키는 `await game.key('Escape')` · `game.key('A+LeftShift', { duration: 0.5 })`, 눌러 두기는 `game.keyDown('W')` → `finally` 에서 `game.keyUp('W')` 다. 이름은 Unity KeyCode 다(CLI `key` 의 `Ran:` 줄에서 옮긴다). 좌표 금지는 그대로다
- **버튼 그림 케이스는 하나만 쓴다** — 「연결한 패드의 버튼 그림이 화면에 뜨나」. `platforms` 에 절이 적은 지원 패드 값을 모두 적는다(`['windows-ps5', 'windows-xbox']`) — 실행이 패드마다 한 항목씩 돈다. 지원 패드가 없으면 이 케이스를 쓰지 않는다. 다른 케이스에는 패드 값을 적지 않는다
- **케이스는 패드를 바꾸지 않는다** — kit 이 선언한 값으로 몸통 앞에 정한다. 몸통은 `const { type } = await game.pad()` 로 지금 패드를 읽어 누를 버튼과 기대할 그림 이름을 갈라 고른다. 확인 · 취소 자리가 패드마다 다르다 — Switch 는 오른쪽 A 가 확인 · 아래 B 가 취소, Xbox 는 아래 A 가 확인이다. 다른 패드의 버튼 이름(`windows-switch` 에서 `Pad.Cross`)을 쓰면 SDK 가 거절해 그 항목이 실패한다
- **기대할 그림 이름은 표준 기획서에서 온다** — 기획서가 패드마다 그림을 적지 않았으면 그 항목은 `확인 필요` 라 미확정 케이스다. 화면에서 그림 오브젝트 · 스프라이트 이름을 목록(트리 · 창 기록)으로 못 읽으면 주소를 짐작하지 않고 결과 요약 `개발팀에 요청할 것:` 줄에 `버튼 그림 이름을 읽을 길 — <창>` 을 올린다(명세 게임 결정 25)
- **돌려 보기는 잡은 PC 에서 값마다 따로 돈다** — §7 그대로 부르되 PC 는 `npx control-cli hold --pc --minutes 30` 으로 잡고, 탐색 때 `open` 이 찍은 게임 이름을 넘긴다 — `PLATFORM_PC_GAME=<이름> npm run -s authoring:run -- 게임 <폴더>`. 덤 PC 는 안 잡는다. 출력의 `폰 차이` 는 PC 에서는 패드 차이다 — `PS5 패드 pc-pc1:ps5 에서만 빨강` 이면 그 패드의 버튼 이름 · 그림 갈래를 고친다. 결과 요약 `3번 돌려 보기` 줄에는 `PC 1번 — 초록 N · 빨강 M` 을 적는다
