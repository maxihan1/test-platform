## 게임 시나리오 — 미션 목록 · 로그 견주기 (2026-11-18 · GAME-F3-03)

종류 「게임」 애플리케이션에서 기능 케이스(`game.md`)와 같이 연다. 플레이를 해야 생기는 값(준 피해 · 받은 피해 · 회복 · 경험치 · 골드 · 드랍 · 레벨 업)은 기능 케이스가 아니라 여기 적은 미션으로 본다.
정본은 명세 `docs/spec/도메인/게임.md` §3.10 「케이스 꼴」 결정 18 ~ 25, 도구 꼴은 `docs/spec/공통/3-공유계약.md` 「게임 시나리오 도구」다.

### 1. 기능인가 게임 시나리오인가

| 기획서 규칙 | 갈래 | 예 |
|---|---|---|
| 버튼 한 번에 결과가 바로 나온다 | 기능(`game.md`) | 상점 가격 · 강화 결과 · 우편 받기 · 친구 · 길드 · 장착 |
| 플레이를 해야 값이 생긴다 — 서비스 가이드에 적힌 로그 줄 종류(조작 맵 로그 행의 줄 종류와 같다)에 그 값이 찍힌다 | 게임 시나리오(이 파일) | 임프에게 받는 피해 · 처치 경험치 · 사냥 골드 · 드랍 |

- **가르는 기준은 로그 줄 종류다** — 뜻으로 짐작하지 않는다. 버튼 한 번에 바로 나오는 값은 기능이다(상점 가격). 플레이로 생기는 값은 가이드의 로그 줄 종류에 찍히면 미션이고, 찍히는 줄 종류가 없으면(로그 주소가 없거나 회복 줄이 빠졌거나) 기능 케이스로 돌리지 않고 §6 `개발팀에 요청할 것:` 에 올린다. **화면에 보여야 하는 값은 로그에 찍혀도 기능이다**(머리 위 피해 숫자 · 화면 골드 — 아래 셋째 줄). 표준 기획서에는 플레이 값 표시가 없다(명세 작성 §3.6 「게임 기획서 빈 곳」 · 2026-11-18 AUT-F4-12)
- 한 규칙을 두 갈래가 같이 볼 수 있다 — 상점 가격은 기능, 사냥으로 얻은 골드는 게임 시나리오다
- **플레이 값을 마지막 값 하나로 읽는 기능 케이스를 쓰지 않는다** — GM 조회 명령처럼 마지막 값 하나를 읽으면 준비 중에 먼저 맞은 값이 잡힌다(ARG-FN-104 — 12 대신 13)
- **화면에 보여야 하는 값**(머리 위 피해 숫자)은 로그로 못 본다 — 그 확인은 기능 케이스다
- **경계값 미션은 만들지 않는다** — 경계값은 기능 케이스에서 본다
- **게임 종류는 서비스 가이드에 적힌 것을 따른다** — 전투형(타격 · 처치마다 로그)만 쓴다. 판 규칙형 · 성장 재화형이거나 가이드에 로그 받는 법이 없으면 미션을 쓰지 않고 아래 §6 줄로 올린다

### 2. 미션 목록 — 조작 맵으로 쓴다

미션 하나가 게임 시나리오 테스트 하나다. 표준 기획서의 플레이 값 규칙을 읽고 케이스 목록 파일 `docs/cases/<접두사>.md` 맨 끝에 `## 게임 시나리오 미션` 절을 두어 이 꼴로 쓴다.

**양식 칸은 조작 맵에서 옮긴다** (2026-11-20 GAME-F5-08 · 명세 게임 §3.10 결정 33) — 미션의 시작 상태 · 자리를 목표 열쇠로 경로 검색(`npx tsx scripts/authoring-game-route.ts <자료 폴더> <열쇠…>`)을 부르고 찍힌 줄을 옮긴다.

| 양식 칸 | 어디서 |
|---|---|
| 시작 조건 | `[상태 설정]` 줄들의 도착 상태 |
| 할 일 | 「그 자리에서 하는 동작」 줄 — 되풀이 동작과 그 `진행 값` |
| 성공 조건 | 「남는 로그」 줄 — 줄 종류와 `칸` |
| 확인할 로그 기대값 | 맵이 아니라 표준 기획서 공식 |

- **경로 검색이 1 로 끝나면 그 미션은 쓰지 않는다** — 탐색 플레이가 「진행 불가」로 둔 기능 단위다. 결과 요약 `게임 시나리오 미션:` 줄 「못 쓴 미션」 칸에 까닭(행의 진행 불가 까닭)을 적는다
- **남는 로그 줄이 「로그 없음」이면 그 규칙의 미션을 쓰지 않고** §6 `개발팀에 요청할 것:` 에 올린다
- 맵 행의 값(진행 값 · 칸 이름)은 「어떻게 하나」일 뿐이다 — 기대값은 맵에서 오지 않는다

````markdown
## 게임 시나리오 미션

### M01 레벨 1 탱커가 임프 3마리를 잡는다
```
미션: 레벨 1 탱커가 임프 3마리를 잡는다
시작 조건: 탱커 · 레벨 1 · 전투 망치 · 사슬 갑옷 · 혼자
할 일: 전투 망치로 임프 3마리 처치
성공 조건: 처치 줄 3줄
확인할 로그
 - 받은 피해 줄: 전부 6 (최소 1줄) — ARG-REQ-041
 - 처치 줄 경험치: 전부 12 (최소 3줄) — ARG-REQ-052
```

### 공식 빈칸
```
 - ARG-REQ-070 — 공식의 보정 조건 칸이 비어 있다
```
````

- **시작 조건은 미션 하나에 하나다** — 레벨 · 직업 · 장비 · 인원이 다르면 미션을 나눈다
- **여럿이 든 던전에서 「내가 맞는」 미션은 누가 맞을지부터 정한다** (2026-11-22 BRM-GS-004 · 011) — 적은 가장 가까운 상대를 노려 가만히 선 봇이 대신 맞는다. 인원만 채우는 봇은 쓰러뜨려 두고(쓰러져도 던전 인원에 든다) 시작 조건에 「쓰러져 있음」을 적는다
- **폰 조작으로 값을 못 박는 조건(누른 길이에 따라 차는 충전률 등)은 기대값을 하나로 고정하지도 범위로 느슨하게 하지도 않는다** — 게임이 그 조건을 로그 줄에 적게 하고(게임 고칠 거리로 돌려보냄) 줄마다 공식에 넣어 셈한다. 로그에 적힌 값이 반올림돼 있으면 그 폭 안의 공식 값은 맞음으로 본다(2026-11-22 BRM-GS-011 · 방패 충전률 `shield`)
- **확인할 로그 한 줄이 기획서 규칙 하나다** — 줄 끝에 표준 기획서 번호를 단다. 기대값은 그 규칙의 공식에 시작 조건을 넣어 계산한 값이고, 랜덤이면 `10 ~ 14` 처럼 범위로 쓴다. 기획서에 없는 값을 짐작하지 않는다 — 공식에 빈 칸이 있으면 그 줄은 적지 않고 미션 절 맨 끝 `### 공식 빈칸` 코드 덩이에 ` - <규칙 번호> — <무엇이 비었나>` 로 적는다. 결과 요약 `게임 시나리오 미션:` 줄의 `공식 빈칸` 칸에도 규칙 번호를 적는다(에이전트가 절을 읽어 올린다). 그 공식 항목은 표준 기획서로 옮길 때 `확인 필요` 로 잡았어야 한다(`tpx-author` `prd-game.md` §2 「공식 칸」) — 첫 작성에서 그 항목이 `CONFIRMED` 면 표준 기획서 결과 파일에서 `NEEDS_CHECK` 로 고치고 `prd:ledger` 를 다시 돌린다. 빈 칸 이름은 둘이 같게 쓴다
- **최소 줄 수**는 할 일이 확실히 남기는 줄 수다(임프 3마리면 처치 줄 3). 받은 피해처럼 몇 번 맞을지 모르면 1
- **미션이 없는 플레이 값 규칙이 남지 않게 한다** — 표준 기획서의 플레이 값 규칙마다 확인할 로그 줄이 하나 이상 있는지 스스로 대 본다
- 이 절은 표가 아니라 코드 덩이로 쓴다 — 대조가 `## 요구사항` · `## 제외` 표만 이름으로 읽어 이 절은 안 건드린다
- 이어 작성 · 반영처럼 이미 절이 있으면 고친 규칙의 미션만 고치고 나머지는 그대로 둔다

**미션 목록과 게임 시나리오 케이스는 같은 작성이 쓴다** — 사람 승인은 없다(결정 33 — 2026-11-19. 앞 판은 사람이 「미션 승인」에서 체크한 미션만 따로 선 작성이 썼다). 미션 절을 다 쓰면 이어서 §3 대로 미션마다 케이스를 쓴다. 에이전트는 끝에 이 절을 읽어 PR 머리 한 줄로 남긴다 — 서버에 올리지 않는다.
기능 테스트는 미션과 상관없이 지금처럼 쓴다.
**플레이 값 규칙은 게임 시나리오 표 줄로 덮는다** — 공통 절차 「관문 0 이 빨강」과 이어 작성(`tpx-author` `references/continue.md` §2)은 빠진 번호마다 케이스나 「제외」를 쓰라고 하지만, 이 규칙들은 기능 케이스(마지막 값 하나 읽기)로도 「제외」로도 덮지 않고 §3 표 줄로 덮는다. 공식 빈칸이라 확인할 로그 줄을 못 쓴 규칙만 빠진 채 둔다 — 그 항목은 `확인 필요` 라 사람이 「결정 필요」 요구사항 확인에서 정한다(현재 동작이 붙으면 판정 요청 카드). 이어 작성이 이 번호를 받으면 미션 절에 미션이 있는지 보고(없으면 더한다) §3 대로 그 미션의 케이스를 쓴다. 결과 요약에 `게임 시나리오 미션:` 줄을 단다(`tpx-author-game` 「결과 요약에 더하는 줄」).

### 3. 게임 시나리오 케이스 꼴

미션 절의 미션마다 케이스 파일 하나(`<접두사>-GS-<3자리>`)와 「요구사항」 표 줄을 쓴다. 이어 작성 · 반영은 고친 규칙의 미션 케이스만 고친다.

**표 줄 꼴** — 확인할 로그 한 줄이 표 한 줄이다. 같은 미션의 줄은 번호 명령(`npm run ledger:number`)이 한 번호로 묶는다. 줄 수 상한은 미션에 안 걸리고 번호는 GS 끼리 센다.

```
| <n> | 미션 | <시작 조건> | <할 일> | <확인할 로그 줄의 글> | <규칙 번호> · 미션 M01 | <접두사>-GS-001 | <날짜> |
```

- 축은 `미션`, 출처 칸은 `<규칙 번호> · 미션 <미션 번호>` 다. 번호 명령이 미션 번호로 줄을 묶고, 기준(main) 표에 같은 미션이 있으면 그 번호를 물려준다
- 규칙 번호는 줄 하나에 하나다. 원장 대조는 이 번호를 덮은 것으로 센다. 설계 칸(경계 · 예외) 대조는 미션 줄을 세지 않는다

```ts
import { defineCase, gameLog, repeatUntil, test, verify } from '@platform/kit';

import {
  type 로그줄,
  로그읽기,
  받은피해,
  설명안되는줄,
  시작조건맞추기,
  임프부르기,
  임프치우기,
  처치줄,
} from './helpers/game-state.helper.js';
import { 던전 } from './pages/dungeon.page.js';

export const spec = defineCase({
  tcId: 'ARG-GS-001',
  name: '레벨 1 탱커가 임프 3마리를 잡는 동안 받은 피해 · 처치 경험치가 기획서 값이다',
  platforms: ['android'],
  precondition: ['탱커 · 레벨 1 · 전투 망치 · 사슬 갑옷으로 혼자 던전에 있다', '곁에 임프 3마리만 있다'],
  params: null,
  expected: null,
});

test(spec, async ({ game, admin }) => {
  await test.cleanup('부른 임프 치우기', () => 임프치우기(game));
  await 임프부르기(game, 3);
  await 시작조건맞추기(game, { 직업: '탱커', 레벨: 1, 무기: '전투 망치', 갑옷: '사슬 갑옷' });
  const 로그 = await gameLog((since) => 로그읽기(admin, since));
  const 창 = await 던전.열기(game);
  await test.step('임프 3마리를 잡는 동안 쌓인 로그를 기획서 값과 견준다', async () => {
    let 줄들: 로그줄[] = [];
    let 멈춤: unknown;
    try {
      await repeatUntil(() => 창.가까운적공격({ 초: 5 }), {
        progress: async () => 처치줄((줄들 = await 로그.lines())).length,
        goal: 3,
        stallMs: 60_000,
      });
    } catch (e) {
      멈춤 = e;
    }
    await verify.log('ARG-REQ-041 임프에게 받은 피해는 6이다', 받은피해(줄들).map((줄) => 줄.value), 6);
    await verify.log('ARG-REQ-052 임프 처치 경험치는 12이다', 처치줄(줄들).map((줄) => 줄.exp), 12, { least: 3 });
    for (const 줄 of 설명안되는줄(줄들)) await verify.note('설명 안 되는 줄', 줄);
    if (멈춤 !== undefined) throw 멈춤;
  });
});
```

- **번호는 `<접두사>-GS-<3자리>`** 이고 GS 끼리 센다(ARG-GS-001 과 ARG-FN-001 이 같이 있어도 된다). `techniques` 는 달지 않는다
- **정리는 `test.cleanup`** — 몸통 맨 앞에서 부른다. 시작에 한 번, 끝에 한 번 더 돈다. 실패해도 판정에 안 든다. 부른 몬스터 · 켠 치트(무적) · 바꾼 설정을 여기서 치운다. 판정에 드는 `finally` 정리는 쓰지 않는다
- **`gameLog` 는 준비가 다 끝난 뒤 · 할 일 직전에 연다** — 준비 중 줄(부르기 · 레벨 맞추기)이 구간에 안 들게
- **조작과 판정을 한 절차에 두고, 멈춤 오류는 들고 있다가 판정 뒤에 다시 던진다** — 절차 하나가 던지면 kit 은 그 뒤 `test.step` 을 아예 안 돌린다(`run.stopped`). 그래서 판정을 다음 절차나 `finally` 의 절차로 빼면 미션이 멈췄을 때 규칙별 판정 문장이 하나도 안 남는다. 판정은 `progress` 가 마지막으로 받은 줄로 한다 — 판정 앞에서 로그를 다시 받지 않는다(그 읽기가 던지면 멈춘 까닭이 덮인다). 성공으로 끝나면 마지막 `progress` 읽기가 마지막 처치까지 담는다
- **`act` 는 몇 초 분량으로 쓴다** — `progress` 가 `act` 마다 로그 구간 전체를 받아 오므로, 공격 한 번마다 읽으면 같은 서버를 쓰는 실행 모두에 부담이다. 「5초 동안 가까운 적 공격」처럼 묶고 안의 기다림은 한도를 둔다. 멈춤은 `act` 사이에서만 보니 너무 길게 잡지 않는다. `stallMs` 는 진행 값(처치 줄 수) 하나가 늘기까지 넉넉한 시간이다 — 처치 하나가 30초면 60초
- **판정은 `verify.log` 로 규칙마다 한 번** — 문장 머리에 표준 기획서 번호를 단다. 값 배열이 비면 kit 이 「확인 못 함 — 」을 붙여 실패로 남긴다. 성공 조건(처치 3줄)은 `repeatUntil` 이 본다
- **「설명 안 되는 줄」은 `verify.note`** — 미션 양식에 없는 종류의 줄 · 시작 조건과 다르게 찍힌 줄(파티 인원이 다름)이다. 판정에 안 든다. 사람이 보고 기획서에 없는 규칙(인원 보정)인지 가른다
- 제한 시간은 없다 — kit 이 `-GS-` 번호를 보고 Playwright 한도를 끈다. 잡는 것은 `waitFor` 한도와 `repeatUntil` 멈춤 둘이다

### 4. 로그 읽기 도우미 — `helpers/game-state.helper.ts`

`gameLog` 에 넘기는 `read(since)` 는 상태 도우미가 만든다. 로그 주소 · 줄 꼴은 서비스 가이드에 적힌 것만 쓴다.

- `since` 가 `null` 이면 마지막 번호만 알면 된다 — 줄은 비워도 된다
- **줄이 하나도 없으면 빈 목록을 돌려준다** — 아직 찍힌 게 없을 뿐이다. 던지지 않는다
- **받은 첫 줄 번호가 `since + 1` 인지 본다 — 계정으로 고르기 전에** — 아니면 서버가 다시 켜졌거나 앞 줄이 밀려난 것이다. `throw new Error(\`게임 로그 줄이 빠졌습니다 (since ${since} · 첫 줄 ${첫번호})\`)`. 고른 뒤에 보면 다른 실행의 줄이 끼어 멀쩡한 구간도 던진다. kit 은 번호가 줄었는지만 본다
- **로그를 지우지 않는다** — 가이드에 로그를 비우는 옵션이 있어도 쓰지 않는다. 같은 서버를 다른 실행이 같이 쓴다
- **그다음 자기 계정 줄만 고른다** — 어느 칸이 계정인지는 맵 로그 행의 `칸` 과 서비스 가이드의 줄 꼴로 본다
- 줄을 고르는 함수(`받은피해` · `처치줄` · `설명안되는줄`)도 같은 파일에 둔다 — 다음 미션이 다시 쓴다
- **기대값은 줄에 찍힌 조건(레벨 · 직업 · 장비 · 인원)을 기획서 공식에 넣어 다시 계산한 값이다** — 게임이 셈한 배율을 그대로 믿지 않는다. 공식 계산은 케이스에 둔다

### 5. 준비 · 조작 · 이동

- **서버 초기화를 쓰지 않는다** — 세계 전체를 되돌리는 명령(Ashveil `/admin/world/reset`)은 안 쓰고 계정 초기화만 쓴다
- **준비 · 조작 · 이동은 경로 검색이 찍은 차례다** — 그 게임에서 어떻게 조작하나(적을 누른 뒤 무엇을 눌러야 치나 · 어느 준비 명령이 레벨을 흔드나)는 조작 맵 행이 정본이다(명세 게임 결정 35). 이 지침에 특정 게임의 조작을 적지 않는다
- **준비 명령이 시작 조건을 바꾸는지 본다** — 경고(⚠) 달린 상태 설정 행이 그것이다. 경로 검색이 그 행을 먼저 치게 차례를 짠다 — 레벨 · 장비는 흔드는 명령이 다 끝난 뒤에 맞춘다(`game.md` §3)
- **조작은 되풀이 스크립트다** — 「적이 남아 있는 동안 가까운 적을 골라 공격」. 한 번의 공격은 이동 · 조작 행의 동작 그대로 쓴다(그 행에 `함수` 가 있으면 그 화면 객체 함수). 판정이 로그라서 조작이 서툴러도 로그만 찍히면 된다. `repeatUntil` 의 `progress` 는 그 행의 `진행 값` 을 센다
- **이동 차례** — ① 이동을 확인하지 않으면 순간이동 — 도착이 `zone:` 인 상태 설정 행 ② 게임에 자동 이동이 있으면 그것을 쓰고 도착만 기다린다 ③ 둘 다 없거나 이동 자체를 보면 이동 · 조작 행을 따라 내 위치를 읽으며 이동 입력을 되풀이한다(`repeatUntil` 의 진행 값 = 지점까지 줄어든 거리). 게임 안 위치 `{ x, y }` 는 값이라 쓴다 — 금지인 좌표는 화면 좌표다
- 미션을 폰에서 끝까지 돌려 보는 것은 메인 AI 만 한다 — 전투 되풀이 조작은 눌러 봐야 맞출 수 있다. 작성 중 폰 잡기는 30분이라 그보다 긴 미션은 끊긴다(결과 요약에 적는다)

### 6. 길이 없을 때 — 개발팀에 요청할 것

미션에 필요한 것(로그 · 치트 · 싸우는 봇)이 게임에 없으면 먼저 치트 · 테스트 주소 · 봇 · 화면 조작으로 해낼 길을 찾는다. 그래도 없을 때만 결과 요약에 `개발팀에 요청할 것:` 줄로 올린다.

- 한 줄에 하나 — `<무엇이 없나> — <어느 미션 · 규칙 번호가 막히나>`. 예 `전투 로그 주소 — M01 ~ M06 · ARG-REQ-041 외 12`
- 보류(`held`) · 「테스트 절차를 고칠 것」과 섞지 않는다 — 게임 쪽에 무엇을 더해 달라는 요청만 적는다
- 로그 주소가 없는 게임은 미션도 쓰지 않는다 — 그 규칙들은 이 줄 하나로 올린다
- 오류 추정 「서버 실패」에 쓸 요청 실패 걸기 길이 가이드에 없을 때도 이 줄이다 — 예 `요청 실패 걸기 — 오류 추정 서버 실패 줄을 못 씀`(`two-kinds.md` 「오류 추정 점검 목록」 · 2026-11-18 AUT-F4-12)
