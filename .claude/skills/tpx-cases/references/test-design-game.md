### 게임 애플리케이션 — 게임 관점 칸 (2026-10-23 · GAME-F1-11)

종류 「게임」이면 에이전트가 원장 사본을 만들 때 설계에 게임 관점 칸을 더 싣는다. 설계 목록 · 관문 0 · 「설계 거절」 · 기법 표시는 위 그대로다 — 칸은 경계 · 예외이고 기법도 kit `TECHNIQUES` 다섯 안이다. 낱말 정본은 `scripts/authoring-design.ts` 의 게임 판정, 명세는 도메인/게임 §3.10 「설계 칸」 · 「확률 세 겹」이다. 케이스 꼴은 `game.md`.

| 관점 | 목록에 이렇게 나온다 | 줄 쓰는 법 |
|---|---|---|
| 확률 세 겹 | 경계 「성공 40%」 0% · 100% · 예외 결정 테이블 「실패 50%」 | 아래 「확률 규칙 줄 하나 = 케이스 셋」 |
| 재화 흐름 · 쓰는 곳 | 경계 「1,000골드」 999골드 · 1,000골드 — 금액이 없으면 「가격」 비용 − 1 · 비용 | 상태 도우미로 비용보다 1 적게 준 뒤 막히고 재화가 그대로인지, 정확히 비용만큼 준 뒤 되고 0 이 되는지. 비용은 표준 기획서 값(데이터 표의 가격)이다 |
| 재화 모자람 | 예외 동등 분할 「골드가 모자라」 | 모자랄 때 기획서가 적은 안내 · 막힘 하나 |
| 상태 바뀜 | 예외 상태 전이 「PK」 · 「사망」 · 「장착」 | 막혀야 할 바뀜 하나(마을 안 PK · 죽은 채 상점). 허용된 바뀜은 정상 줄이다 |
| 시간 | 경계 「리젠 20초」 19초 · 20초 | 정해 둔 시간을 쉬지 않는다 — 시작 시각을 적고 `game.waitFor` 로 뜰 때까지 기다린 뒤 걸린 시간이 19초를 넘고 20초 + 오차 안인지 본다. 오차는 입력값 칸(기본 2초) |
| 공간 · 구역 | 경계 「반경 25m」 24m · 25m · 「Z 200」 Z 199 · Z 200 | 걸어가지 않고 상태 도우미로 그 자리에 순간이동한 뒤 본다 |
| 끊김 | 예외 상태 전이 「다시 접속」 · 「저장된다」 | 아래 「끊김」 |

- **플레이 값 규칙에는 칸을 쓰지 않는다** (2026-11-18 · GAME-F3-03) — 준 피해 · 받은 피해 · 경험치 · 사냥 골드 · 드랍처럼 플레이를 해야 생기는 값은 「요구사항」 표에 줄을 두지 않고 `game-scenario.md` §2 의 미션 목록으로 보낸다. 표에 줄이 없는 요구라 설계 칸도 안 본다(위 「안 보는 요구」). 경계값 미션은 만들지 않는다 — 그 규칙의 경계는 버튼 한 번으로 볼 수 있을 때만 기능 줄로 쓴다
- **판정은 낱말로 짐작한다** — 「거리」 · 「범위」가 경계가 아니거나 「가격」이 쓰는 곳이 아니면 오판이다. 위 「설계 거절」 표에 까닭과 함께 적는다
- **상태 도우미가 없어 못 만드는 칸은 보류 줄이다** — 출처 `보류 — 상태 만드는 길 없음(<무엇>)`. 사냥 · 걷기로 준비하지 않는다(`game.md` §3)

**확률 규칙 줄 하나 = 케이스 셋** — 「+7 강화 성공 40% · 실패 50% · 파괴 10%」는 표준 기획서 항목 하나(규칙 표는 줄마다 항목)이고 칸 셋을 다 쓴다.

| 칸 | 겹 | 케이스 |
|---|---|---|
| 정상 | ③ 분포 | API 로 N번 시도하고 결과마다 센 뒤 `verify.rates(문장, { 성공: a, 실패: b, 파괴: c }, { 성공: 0.4, 실패: 0.5, 파괴: 0.1 }, 허용 오차)`. 기대 확률은 기획서 숫자 그대로다. N 과 허용 오차는 입력값 칸으로 연다(`5-inputs.md`) — 기본 N 1,000 · 허용 오차는 결과마다 3 × √(p(1−p)/N) 가운데 가장 큰 값을 0.01 단위로 올린 것(40% 면 0.05). 사람이 고친다. 스모크는 달지 않는다 |
| 경계 | ② 표를 읽나 | 상태 도우미로 확률표의 그 줄을 100% 로 바꾸고 화면으로 N번(입력값 칸 · 기본 5) 해 늘 성공, 0% 로 바꿔 늘 실패인지. 표는 `test.cleanup` 에서 되돌린다(`game.md` §1) |
| 예외 | ① 결과 처리 | 결과를 고정하고 한 번 한다 — 성공이 아닌 결과(실패 · 파괴)마다 절차 하나. 화면 값과 서버 값(아이템 · 재료 · 골드)을 둘 다 본다 |

- **③ 과 ② 의 0% 는 시도마다 독립인 확률에만 쓴다** (2026-11-18 AUT-F4-12) — 기획서가 천장 · 실패 누적을 적었으면 그 보정이 자기 규칙이다(「5번 연속 실패하면 다음은 성공」 → 0% 로 두고 6번째가 성공하나). 독립인지 안 적어 그 항목이 `확인 필요` 면 ① 과 ② 의 100% 만 쓴다(`tpx-author` `prd-game.md` 「공식 칸」)

**데이터 표 — 칸을 따로 뽑지 않는다.** 데이터 표 항목(「아이템 표의 값대로 게임이 준다」)은 정상 기능 케이스 하나에 절차 둘이다.
① 서비스 가이드의 게임 서버 데이터 API 로 표 전 줄을 읽어 줄마다 `verify.element(문장, '<DATA 열쇠>', 서버 값, 기획서 값)` — 열쇠는 `game-elements.json` 의 `DATA` 열쇠 ② 화면은 대표 줄만 — 가장 싼 · 가장 비싼 · 판매 불가 줄.
데이터 API 가 가이드에 없으면 ① 은 보류 줄이다.

**끊김** — 기획서가 끊김 뒤를 적었으면(「다시 접속해도 위치가 유지된다」) 위 표의 예외 칸으로 쓰고, 안 적었으면 오류 추정 줄이다(`two-kinds.md` 「오류 추정 점검 목록」의 게임 항목 「통신 끊기」 · 「다시 켜기」 · 「내렸다 올리기」).

- 와이파이 끊기 — `await 폰상태에서(driver, { 네트워크: '끊김' }, async () => undefined)`(`@platform/kit/parts` — 끊었다가 구간이 끝나면 다시 켠다. 끊긴 채 볼 것은 구간 안에 쓴다). 모바일 데이터는 팜 폰에 SIM 이 없어 켜져 있지 않다 — 부품이 켜진 것만 끈다
- 내렸다 올리기 — `await 뒤로보냈다오기(driver, 30)`(`@platform/kit/parts`) 뒤 첫 확인을 `game.waitForValue` 로 한다
- 앱 다시 켜기 — `driver.terminateApp` · `driver.activateApp` 뒤 첫 확인을 `game.waitForValue` 로 한다. 켜지는 동안 오는 오류도 한도까지 다시 보므로 기다림과 확인이 한 값이다(`timeoutMs: 120000`). 꼴은 `5-stable.md` 「게임」
