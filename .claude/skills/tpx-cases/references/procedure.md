## 테스트 프로시저 — 케이스를 사용 흐름으로 묶어 쓴다 (2026-11-25 · TP-F5-31)

**언제** — 작성 에이전트의 자식은 프롬프트 머리에 「이 애플리케이션은 테스트 프로시저로 쓴다.」 줄이 있을 때만 따른다(종류 「Android 앱」 · 「게임」에만 온다). 그 줄이 없으면 이 파일을 닫고 지금처럼 케이스 하나를 파일 하나로 쓴다. 사람 세션은 맨 아래 「사람 세션」이다.
다른 지침 파일이 「케이스마다 파일」 · 「케이스마다 준비」를 전제로 적은 문장과 어긋나면 **이 파일이 이긴다**(반영 · 이어 작성은 `apply.md` · `continue.md` 의 프로시저 줄이 먼저다). 종류마다 더 볼 것은 앱이 `5-writing-app.md`, 게임이 `game.md` §9 다.
정본은 명세 `docs/spec/도메인/작성.md` §3.6 「★ 테스트 프로시저 작성」(짜는 법 · 절 · 관문 · 돌려 보기)과 `docs/spec/공통/2-명세선언.md` §4 「테스트 프로시저」(코드 꼴 · K19 ~ K22 · 판정)다.

### 1. 무엇이 그대로이고 무엇이 바뀌나

- **그대로** — 요구사항 표 · 축 · 케이스 번호(`npm run ledger:number`) · 설계 기법 · 원장 대조 · 문장 규칙 · Page Object · 도우미. 케이스 경계를 다시 쪼개거나 합치지 않는다
- **바뀌는 것** — 번호가 매겨진 케이스를 사용 흐름으로 묶어 프로시저 파일 `tests/<폴더>/<접두사>-TP-<3자리>.spec.ts` 하나에 쓴다. 테스트 하나가 케이스 여럿을 차례로 확인하고 결과는 케이스마다 붙는다
- **R7 은 프로시저에 건다** — 스스로 준비하는 단위가 프로시저다. 앞 케이스가 만든 상태를 뒤 케이스가 쓰는 것이 흐름이고, **프로시저끼리는 기대지 않는다**(데이터 · 로그인 · 화면 상태 · 도는 차례). 실행이 프로시저 하나만 골라 돌린다
- **R16(만들기 · 확인 가르기)은 프로시저에 걸지 않는다** — 그 규칙은 E2E 가 준비를 건너뛰려고 있는데 E2E 는 프로시저를 통째로 돈다. 그 아래 「준비 도우미는 시작 상태를 스스로 맞춘다」는 그대로다 — E2E 는 앱을 다시 켜지 않아 첫 케이스의 첫 절차가 지금 화면을 보고 맞춘다
- **UI 케이스(`-UI-`)도 같은 흐름에 든다** — 화면에 들어서면 그 화면의 요소 확인을 먼저 하고 조작 결과를 본다. 따로 도는 「UI 테스트」는 없다
- **프로시저로 쓰지 않는 것** — 게임 미션(`-GS-`)은 지금처럼 파일 하나다. **main 에 옛 꼴 파일로 있는 케이스는 옮기지 않는다** — 고칠 일이 있으면 옛 꼴 그대로 고친다. 새로 쓰는 케이스만 프로시저에 넣는다
- 이미 반영된 프로시저를 고치거나 케이스를 지우는 법은 `tpx-author` `references/apply.md` §3 · §7 · §8, 이어 작성은 `continue.md` §2 다

### 2. 흐름을 짠다 — 표를 확정하고 케이스 번호를 매긴 뒤

1. **프로시저 하나는 사용자가 한 번에 이어서 하는 일 하나다** — 글쓰기 화면을 열어 입력 제한을 보고 게시까지. 흐름 도중에 못 바꾸는 것이 다르면 나눈다 — 로그인 계정 · 역할 · 앱을 다시 켜야 하는 것(게임은 캐릭터 · 직업도). 글 · 장바구니 · 골드 · 아이템처럼 지름길로 맞출 수 있는 것은 나누지 않고 그 케이스의 준비에서 맞춘다
2. **케이스는 1개 이상 10개 이하**(K19)이고, 혼자 돌려 한 번 부름(7분 30초) 안에 끝나야 한다 — 도중부터 이어 돌 수 없다
3. **안 바꾸는 확인을 앞에, 바꾸는 확인을 뒤에** — 화면 요소 · 문구 · 처음 상태 → 입력 검사 · 오류 안내 → 저장 · 게시 · 삭제
4. **실패할 수 있는 케이스는 뒤에** — 통과할 정식 케이스 → 값 다름으로 빨간 채 두는 케이스 → 미확정 · 오류 추정 → 보류. 값 다름은 돌려 보기 전에는 모르니 §6 에서 옮긴다. 뒤에 둔 케이스끼리 서로의 결과에 기대면 따로 프로시저로 뗀다
5. **버튼 반응 케이스는 화면(창)마다 따로 프로시저다** — 그 화면의 버튼 반응 케이스만 든다. 화면 이름 `공통` 도 하나다. 열 줄이 넘어 나뉜 덩이는 같은 프로시저에 둔다
6. **준비는 지름길로** — 로그인된 채 켜기 · 딥링크 · API · 시드 · GM 명령 · 어드민 API. 케이스 사이에서 다음 시작 상태를 맞출 때도 같다. 화면 조작으로 가는 것은 그 조작을 확인할 때뿐이다
7. **케이스 하나는 준비까지 120초 안에** — 한도는 케이스마다 걸리고 첫 케이스에는 폰 연결 · 앱 켜기 · 로그인까지 든다. 그래서 첫 케이스는 화면 요소 확인처럼 가벼운 것으로 고른다. 한도에 걸리면 남은 케이스가 다 Blocked 다
8. **일회용 역할 계정을 쓰는 케이스**(`5-data.md`)는 케이스 하나짜리 프로시저로 둔다 — 계정 하나를 케이스 하나만 쓴다
9. **같은 프로시저에 드는 케이스는 `조작` 칸 문장이 서로 달라야 한다** — 절차 제목은 조작 칸 글자 그대로인데(R11) 프로시저 안에서 제목이 겹치면 K12 에 걸린다(준비 절차 제목도 같이 센다). 겹치면 무엇이 다른지를 조작 칸에 적거나(「본문을 비운 채 「게시」를 누른다」) 다른 프로시저에 둔다. 조작 칸을 고치면 결과 칸의 「<조작>하면」 도 같이 맞춘다. 케이스 번호는 조작 칸으로 매기지 않아 안 바뀐다. 이미 반영된 줄(main 표)은 고치지 않으니 다른 프로시저에 둔다

### 3. 프로시저 절 — 케이스 목록 문서 끝에 쓴다

`docs/cases/<접두사>.md` 끝에 이 절을 쓴다. **이번 작성이 새로 쓰는 케이스**(정식 · 미확정 · 오류 추정 · 보류)를 빠짐없이 **한 줄에만** 넣는다. 게임 미션과 「제거함」 줄, main 에 옛 꼴 파일로 있는 케이스(이 작성이 고치는 것도)는 안 넣는다. 이미 반영된 프로시저의 줄은 그대로 둔다.

```markdown
## 테스트 프로시저

| 프로시저 | 흐름 | 케이스 |
|---|---|---|
|  | 글쓰기 — 입력 제한부터 게시까지 | MTA-UI-031 · MTA-FN-101 · MTA-FN-102 · MTA-FN-104 |
|  | 글쓰기 화면 버튼 반응 | MTA-UI-044 |
```

- **프로시저 칸은 비워 두고 `npm run ledger:number -- <원장 사본> docs/cases/<접두사>.md` 를 다시 돌린다** — 빈 칸에만 `<접두사>-TP-<3자리>` 를 채운다. 종료 코드 2 면 절과 tests 폴더에 쓰인 가장 큰 번호 다음을 적는다. 이미 적힌 번호는 바꾸지 않는다
- 케이스 칸은 **도는 차례 그대로**다. 프로시저 파일의 `cases` 와 글자까지 같아야 한다
- 절은 **자식 혼자 쓴다.** 보조는 고치지 않고 「절에서 고칠 것」으로 돌려준다
- 뒤에 표 줄을 더하면(화면 입력 규칙 · 버튼 반응 · 오류 추정) 케이스 번호를 매긴 뒤 절에도 넣는다 — 차례(§2 의 3 · 4)가 맞는 이번 작성의 프로시저 뒤쪽이나 새 줄이다. 이미 반영된 프로시저에는 끼우지 않는다(바뀐 요구 때문에 어차피 다시 쓰는 프로시저에는 그 요구의 새 케이스를 넣어도 된다 — `apply.md` §3)
- 이어받은 작업방에 절이 있으면 새로 쓰지 않는다 — 절에 없는 케이스만 더한다

### 4. 파일 꼴 — 이 본보기대로 쓴다

```ts
import { defineCase, defineProcedure, test, verify } from '@platform/kit';
import { z } from 'zod';

import { 로그인된채켜기 } from './helpers/login-inject.helper.js';
import { type 계정, 계정꺼내기, 홈에들어가기 } from './helpers/login.helper.js';
import { 내글지우기 } from './helpers/post.helper.js';
import { 글쓰기화면 } from './pages/compose.page.js';

const 본문없음 = defineCase({
  tcId: 'MTA-FN-901',
  name: '글쓰기 화면에서 본문을 비우면 「게시」 버튼이 꺼진다',
  platforms: ['android'],
  precondition: [],
  params: z.object({
    loginId: z.string().describe('일반 회원 아이디').optional().meta({ secret: true }),
    loginPassword: z.string().describe('일반 회원 비밀번호').optional().meta({ secret: true }),
  }),
  expected: null,
});

const 글자수초과 = defineCase({
  tcId: 'MTA-FN-902',
  name: '본문에 501자를 넣으면 남은 글자 수가 「-1」이다',
  platforms: ['android'],
  precondition: [],
  techniques: ['경계값 분석'],
  params: z.object({ 본문: z.string().min(501).describe('넣을 글 — 501자').default('가'.repeat(501)) }),
  expected: z.object({ 남은글자: z.string().describe('남은 글자 수').default('-1') }),
});

const 게시확인 = defineCase({
  tcId: 'MTA-FN-903',
  name: '본문을 적고 「게시」를 누르면 홈 맨 위에 그 글이 보인다',
  platforms: ['android'],
  precondition: ['본문에 글이 적혀 있다'],
  params: z.object({ 본문: z.string().min(1).max(500).describe('올릴 글 — 「QA TP 901」로 시작하는 500자까지').default('QA TP 901') }),
  expected: null,
});

export const procedure = defineProcedure({
  procId: 'MTA-TP-901',
  name: '글쓰기 — 입력 제한부터 게시까지',
  platforms: ['android'],
  precondition: ['일반 회원으로 로그인해 있다'],
  launchIntent: 로그인된채켜기('loginId', 'loginPassword'),
  cases: [본문없음, 글자수초과, 게시확인],
});

test(procedure, async ({ driver }) => {
  const 글쓰기 = new 글쓰기화면(driver);
  let 나: 계정 | undefined;

  await test.cleanup('올린 글을 지운다', async () => {
    if (나 !== undefined) await 내글지우기(나, 'QA TP 901');
  });

  await test.case(본문없음, async ({ params }) => {
    const 회원 = 계정꺼내기(params.loginId, params.loginPassword);
    나 = 회원;
    await test.step('일반 회원으로 홈에 들어가 글쓰기 화면을 연다', async () => {
      await 내글지우기(회원, 'QA TP 901');
      await 홈에들어가기(driver, 회원);
      await 글쓰기.열기();
      await verify('글쓰기 화면이 보인다', await 글쓰기.떴나(), true, { blocker: true });
    });
    await test.step('글쓰기 화면에서 본문을 비운다', async () => {
      await 글쓰기.본문넣기('');
      await verify('글쓰기 화면에서 본문을 비우면 「게시」 버튼이 꺼진다', await 글쓰기.게시버튼꺼질때까지(), true);
    });
  });

  await test.case(글자수초과, async ({ params, expected }) => {
    await test.step('본문에 501자를 넣는다', async () => {
      await 글쓰기.본문넣기(params.본문);
      await verify('본문에 501자를 넣으면 남은 글자 수가 「-1」이다', await 글쓰기.남은글자(), expected.남은글자);
    });
  });

  await test.case(게시확인, async ({ params }) => {
    await test.step('본문에 올릴 글을 적는다', async () => {
      await 글쓰기.본문넣기(params.본문);
    });
    await test.step('「게시」를 누른다', async () => {
      const 홈 = await 글쓰기.게시하기();
      await verify('본문을 적고 「게시」를 누르면 홈 맨 위에 그 글이 보인다', await 홈.맨위글보일때까지(params.본문), true);
    });
  });
});
```

- **케이스 선언은 파일 맨 위 `const` 이고 내보내지 않는다.** 내보내는 것은 `procedure` 하나다. `cases` 에는 그 이름만 적는다 — 변수 · 펼침 · 다른 파일의 케이스는 위반이다(K19). `techniques` · `elements` · `smoke` · `held` 는 지금처럼 케이스마다 적는다
- **`test.case` 는 본문 맨 바깥에서 `cases` 차례대로 한 번씩** — 조건문 · 반복문 · `test.step` 안에서 부르지 않는다(K20). 구간마다 판정 확인이 하나 이상이다(K6)
- **`verify` 는 `test.step` 안에서만.** 케이스 사이에 둔 `test.step` 은 다음 케이스의 준비다. 준비는 되도록 그 케이스의 `test.case` 안 앞쪽 절차로 쓴다. 조작 칸 문장의 절차와 결과 문장의 `verify` 는 꼭 그 케이스 구간 안에 둔다
- **`platforms` 는 프로시저와 안 케이스가 모두 같다**(K21). 앱 켜기 설정(`launchIntent` · `keepAppData`)은 프로시저에만 적는다(K22)
- **계정 값은 `test.case` 본문의 `params` 로만 온다** — `test(procedure, …)` 본문에는 `params` · `expected` 가 없다(꺼내면 던진다). 그래서 로그인할 계정 칸은 **첫 케이스의 `params`** 에 두고(`launchIntent` 도 첫 케이스 값을 받는다) 화면으로 들어가는 준비도 첫 케이스 구간 안 첫 절차에 둔다. 로그인된 채 켜기가 안 먹어도 그 준비 도우미가 화면으로 로그인한다
- **정리(`test.cleanup`)는 본문 맨 앞, 첫 케이스 앞에** 프로시저마다 한 번. 계정 값이 필요하면 본보기처럼 변수를 첫 케이스에서 채우고, 비어 있으면(시작 정리) 건너뛴다 — 그때는 첫 절차에서 앞 실행이 남긴 것까지 되돌린다. 마지막 `test.case` 뒤에는 아무것도 두지 않는다(K20)
- **`blocker` 확인은 지름길로 맞춘 상태와 첫 화면에만 쓴다** — `blocker` 가 틀리면 그 케이스가 실패로 남는다. 앞 케이스가 만든 상태를 이어받는 준비는 던지는 기다림(앱 `waitForDisplayed` · 게임 `game.waitFor`)으로 본다. 그래야 앞 케이스가 실패해서 못 온 것이 실패가 아니라 Blocked 로 남는다. PR 품질 숫자의 「전제 확인」이 낮게 나와도 올리려고 `blocker` 를 더하지 않는다
- **판정이 틀려도 흐름은 계속 간다** — 다음 케이스의 준비는 앞 케이스의 결과 화면이 기대와 달라도 되도록 스스로 그 화면으로 간다(뒤로 · 닫기 · 딥링크)
- 보류 케이스는 그 구간만 건너뛴다. 그 케이스가 만들 상태에 기대는 케이스를 뒤에 두지 않는다
- `name` · 절차 제목 · 전제 · 판정 문장은 지금처럼 표 글자 그대로다(R11). 표의 전제는 프로시저 `precondition` 이나 그 케이스 `precondition` 어느 쪽에 있어도 된다 — 흐름 전체의 시작 상태는 프로시저에, 그 케이스만의 것은 케이스에 적는다
- 앱 · 게임 케이스의 주석 · 좌표 · `page` 금지는 그대로다

### 5. 관문에서 달라지는 것

- **빠른 검사(`authoring:check -- 마지막`)에 「프로시저 절」 줄이 붙는다** — 절에 빠진 케이스 · 두 줄에 든 케이스 · 파일과 다른 차례 · 빈 프로시저 번호 · 섞인 버튼 반응 · 뒤로 간 정식 케이스를 짚는다. 파일이나 절을 고쳐 맞춘다
- **맞춰 보기(관문 2)** — 같은 프로시저 안에서는 앞 케이스의 결과 문장이 뒤 케이스의 준비 판정과 같아도 안 걸린다. 걸리지 않는다는 것이지 그런 판정을 두라는 뜻이 아니다 — 이어받는 상태는 §4 대로 던지는 기다림으로 본다. 다른 프로시저와는 그대로 걸린다
- **입력값 두 번 · 일부러 고장 내 보기(관문 4)는 파일을 잠깐 고쳐 한다** — `PLATFORM_PARAMS` 는 프로시저에 안 먹는다. 그 케이스의 `.default(…)` 나 조작을 바꿔 프로시저를 통째로 돌리고 그 케이스의 그 자리 문장이 빨개졌는지만 본 뒤 되돌린다. 뒤 케이스가 Blocked 나 빨강이 되는 것은 세지 않는다. 되돌린 파일은 폰 돌려 보기를 한 번 더 부르면 다시 돈다. 몇 건을 하는지는 지금 앱 · 게임 규칙 그대로다

### 6. 돌려 보기 — 프로시저를 통째로 1번

명령은 그대로다(`npm run -s authoring:run -- 앱 <폴더>` · `게임 <폴더>`). 고르고 도는 단위가 프로시저이고 찍는 것은 케이스마다 한 줄(`<파일> <케이스 번호>`)이다.

| 명령이 찍는 것 | 할 일 |
|---|---|
| 빨강 | 지금처럼 까닭을 가른다(깨짐 · 값 다름 · 서버 오류). 고치면 프로시저를 통째로 다시 돈다 — 케이스 하나만 도는 길은 없다 |
| 막힘(`<케이스> 에 막힘`) | **남긴 채 끝내지 않는다** — 못 돌려 본 케이스다. 막은 케이스가 깨짐이면 고쳐 다시 돈다. 값 다름이라 빨간 채 둘 것이면 정식 케이스의 맨 뒤로 옮기고, 그래도 막히면 따로 프로시저로 뗀다. 막은 케이스가 빨간 채 두는 오류 추정 · 미확정이면 막힌 케이스를 그 앞으로 옮기거나(둘 다 뒤쪽 케이스라 차례 검사에 안 걸린다) 따로 프로시저로 뗀다. 서버 오류 · 끊김 · 못 고친 깨짐으로 보류가 된 케이스는 맨 뒤로 옮긴다 |
| 한 번에 못 끝낸 프로시저 | 케이스를 나눠 프로시저 둘로 뗀다 — 다시 불러도 같다 |

- 옮기거나 떼면 **절 · `cases` · `test.case` 차례를 같이** 고치고(새 줄은 `ledger:number`) 빠른 검사와 돌려 보기를 다시 부른다. 이미 반영된 프로시저는 나누거나 합치지 않고, 차례는 **보류 · 미확정이 됐거나 빨간 채 두게 된 케이스만** 뒤로 옮긴다(`apply.md` §3). 그래도 막히면 막힌 채 두고 결과 요약에 적는다
- 먼저 한 바퀴를 다 돌리고 빨간 것만 고치는 것은 그대로다. 프로시저의 케이스가 다 초록(보류 건너뜀 포함)이면 도우미 · 화면 파일을 고쳐도 다시 안 돈다
- **결과 요약은 케이스로 센다** — 첫 줄은 `… → 케이스 M건(프로시저 P개)`, `3번 돌려 보기` 줄은 `폰 1번 — 초록 N · 빨강 M · 막힘 K` 다. 값 다름 · 오류 추정 줄은 지금 그대로다

### 7. 사람 세션 (`/tpx-cases`)

- 스위치(설정 › 애플리케이션 「프로시저 작성」)를 세션이 읽을 길이 없다. **Android 앱 · 게임 케이스를 새로 쓰면 표를 쓰기 전에 켜져 있는지 한 번 묻고(`SKILL.md`), 켜져 있다고 할 때만 프로시저로 쓴다.** 꺼진 애플리케이션에 프로시저 파일을 올리면 스캐너가 그 케이스를 활성으로 올리지 않는다
- 절은 같은 꼴로 쓰고 프로시저 번호는 절과 `tests/<폴더>` 에 쓰인 가장 큰 번호 다음을 적는다. §3 게이트에서 표와 같이 승인받는다
- 빠른 검사의 절 검사는 사람 세션에서 안 돈다 — `npm run check:tests`(K19 ~ K22)를 돌리고 절과 `cases` 차례는 눈으로 맞댄다. 폰 돌려 보기 명령도 작성 에이전트 것이라 못 돌린 케이스를 §8 반환에 적는다
