## §2 테스트 설계 기법 — 경계 · 예외 칸 (2026-10-05 사용자 · PR #157)

작성 에이전트의 경계 · 예외 칸은 요구 글의 문구로 코드가 정한다. 이 파일은 그 칸을 읽고 줄을 쓰는 법의 정본이다.
명세 정본은 도메인/작성 §3.6 「★ 원장」 「설계 기법」, 코드 정본은 `scripts/authoring-design.ts`(판정 · 목록 글) · `scripts/authoring-design-check.ts`(대조 · PR 머리 줄)다.
`2-requirements.md`(R3 · R4 · 표 형식) · `two-kinds.md`(R18 · R19) · `tpx-author` 가 여기를 가리킨다.

**왜** — 「칸과 번호」가 케이스 경계와 tcId 를 고정한 뒤에도 요구마다 경계 · 예외 칸을 만들지는 AI 가 골라 실행마다 갈렸다.
두 실행(#137 · #144)이 어긋난 칸 86 중 경계 · 예외가 34 였다. 사용자 지시는 「경계값 분석 등 테스트 설계 기법으로 정하라 — 예외 케이스 포함」이다.

| 누구 | 어떻게 |
|---|---|
| 작성 에이전트(자식) | 설계 목록의 칸을 **뺄 수 없다.** 관문 0(`--agent`)이 빠진 칸을 막는다. 오판만 「설계 거절」로 뺀다 |
| 사람 세션(`/tpx-cases`) | R18 로 판단한다. 목록은 참고로 본다. 관문 0 을 `--agent` 없이 돌리므로 설계 대조는 안 돈다 |

기법 낱말 · 단위 목록은 코드가 정본이다 — 여기 옮겨 적지 않는다. 아래 표의 문구는 예다.

### 설계 목록 — 표를 쓰기 전에 본다

```bash
npm run ledger:design -- <원장 사본>
```

설계가 있는 요구만 한 줄씩 나오고 끝에 셈 한 줄이 붙는다.

```
REQ-MEM-001 · 경계 「4~12자」 3자 · 4자 · 12자 · 13자 · 예외 동등 분할 「맞지 않으면」
설계: 요구 N 중 경계 a · 예외 b
```

- 경계는 「」 안이 판정이 잡은 근거 문구, 그 뒤가 시험 값이다. 예외는 기법 이름과 근거 문구다
- 목록에 없는 요구는 설계가 없다 — 경계 · 예외를 만들지는 R18 대로 판단한다(아래 「설계 밖 칸」)
- 설계는 에이전트 스크립트가 원장 사본에 싣는다. 원장이 없으면(화면만 · PDF · 피그마) 설계도 없다

### 기법 — 어느 칸을 무엇으로 정하나 (ISTQB CTFL 4.0 · ISO/IEC/IEEE 29119-4)

| 기법 | 칸 | 코드가 보는 것(예) | 줄 쓰는 법 |
|---|---|---|---|
| 경계값 분석 | 경계 | 숫자 · 한도 단위 · 한도 낱말 — 「4~12자」 · 「20자를 초과」 · 「최대 3개」 · 「5번 연속」 | 목록의 값 하나에 확인 줄 하나 |
| 0건 | 경계 | 「없으면 · 비어 있으면 … 보이지 않는다」 — 시험 값 0건 · 1건 | 0건 줄 하나 · 1건 줄 하나(아래 「0건」) |
| 동등 분할 | 예외 | 틀린 입력 묶음 — 형식 · 필수 · 허용 목록 밖 · 없는 대상 · 사용자 묶음(남의 것 · 비로그인) · 실패 응답 | 틀린 묶음 하나에 줄 하나 |
| 결정 테이블 | 예외 | 「~해야 눌린다」 · 「~면 저장하지 않는다」 · 「미입력 시 비활성」 | 조건을 하나씩 어긴 줄 |
| 상태 전이 | 예외 | 「~상태에서만」 · 「잠기」 · 「~까지만」 | 금지된 전이 하나에 줄 하나 |
| 조합 | — | 안 본다 | R18 「칸끼리 곱하지 않는다」 — 값마다 한 번 |
| 오류 추정 | — | **안 한다** | 기획서가 결과를 안 적은 곳을 찌르므로 R18 「근거에 적힌 것만」을 바꿔야 한다(아래 「다음 PR」) |
| 시나리오 | — | 안 본다 | E2E 시나리오(명세 도메인/시나리오 §3.7)가 맡는다 |

**경계값은 2값이다** — 한도마다 한도와 바로 밖 하나. R18 「숫자 하나에 경계 ±1 두 줄까지」와 같다.

- 범위 a~b 는 a−1 · a · b · b+1(「4~12자」 → 3 · 4 · 12 · 13자), 「5번 연속」은 4 · 5번. 같은 한도가 두 번 나와도(「3개까지」 · 「최대 3개」) 경계 하나다
- 연속 단위(MB 등)는 바로 다음 정수가 없어 「초과」 · 「미만」으로 적힌다(「5MB 이하」 → 5MB · 5MB 초과)
- `px` 는 조작 한도만 잡는다 — 「80px 이상 내리면」은 79 · 80px. 「768px 이하에서는 2개」 같은 화면 너비는 안 잡는다. 화면 배치는 UI 몫이다(R19 · 사용자 「FN 에만」)

**줄을 쓸 때**

- 경계 줄은 목록의 시험 값을 그대로 쓴다. 값을 짐작해 바꾸거나 줄을 늘리지 않는다. `결과` 칸은 요구 글이 그 값에서 정한 결과다 — 한도 안과 밖이 어떻게 다른지 보여야 한다
- 한 줄은 칸 하나만 틀리게 하고 나머지 칸은 정상 값을 넣는다(R18). 결정 테이블도 조건 하나만 어기고 나머지 조건은 지킨다
- 입력 칸이 한도를 넘는 글자를 아예 막으면 케이스를 빼지 않는다 — 꼴은 `two-kinds.md` 「화면에만 있는 입력 규칙」의 「한도 + 1」 줄
- 한 요구의 경계 줄들은 같은 칸(요구 × 갈래 × 축 × 상태)이라 케이스 하나가 된다. 번호는 `npm run ledger:number` 가 매긴다(도메인/작성 §3.6 「칸과 번호」)

### 0건 — R2 의 경계

「없으면 · 비어 있으면 … 보여 준다」는 R2 의 경계(0건 · 최대 · 마지막 하나)다. 숫자가 없어도 경계 칸이다(R3).

- **빈 상태에서 하나가 생기면 바뀌는 것까지가 기능 경계 칸이다** — 0건 줄은 「목록이 비어 있다 → 남은 개수 영역이 보이지 않는다」, 1건 줄은 하나를 더했을 때 바뀌는 결과다
- 빈 상태의 처음 화면 모양(안내 문구 · 배치)은 UI 칸이 따로 덮는다(R19). 칸은 축이 같은 줄만 채우므로 UI 줄이 경계 칸을 채우지 못한다

### 무엇이 칸을 채우나

- 출처 칸에 그 요구 번호가 든 줄 가운데 **축이 같은 줄 하나.** 번호가 여럿이거나 범위(`REQ-R-001~003`)여도 든 번호 전부를 채운다 — 원장 대조의 「덮음」과 같은 기준이다
- 상태(정식 · 미확정 · 보류 · 모킹)와 기준 줄(main 표에 있던 줄)인지는 안 가린다 — 값을 못 정해 보류로 쓴 경계 줄도 칸을 채운다
- 또는 아래 「설계 거절」 줄 하나
- **안 보는 요구** — 설계가 없는 요구 · 「제외」 표에 든 요구 · 표에 줄이 없는 요구(원장 대조가 「빠짐」으로 센다) · 줄이 전부 기준 줄인 요구(기준 줄은 고쳐 쓰지 않는다)

### 「설계 거절」 표 — 오판만 뺀다

꼴의 정본은 여기다. 표 파일(`docs/cases/<접두사>.md`)에 `## 설계 거절` 절을 더하고 이 꼴로 쓴다.

```markdown
## 설계 거절

| 요구 | 축 | 까닭 |
|------|----|------|
| REQ-SVY-002 | 경계 | 「5~15초 뒤 아무 때나」는 설문이 뜨는 무작위 시점이다 — 지킬 한도가 없다 |
```

- 한 줄에 원장 번호 하나. 범위(`~`) · 번호 둘 이상 · `경계` · `예외` 밖의 축 · 빈 까닭은 **형식 오류**다 — 관문 0 이 종료 코드 1 로 막는다
- 모든 칸이 빈 줄(표 틀의 예시 행)과 설계가 요구하지 않는 칸의 줄은 무시한다 — 앞 실행이 main 에 남긴 거절 줄이 기획서 개정으로 쓸모없어져도 막지 않게(2026-10-05 구현 검토)
- 거절한 칸은 채운 것으로 친다. PR 머리에 `설계 거절 N — <앞 10개>` 로 세어 사람이 본다
- 절 이름과 머리 이름(`요구` · `축` · `까닭`)을 바꾸지 않는다 — 대조가 이름으로 찾는다

**쓰는 때는 판정이 잘못 잡은 칸(오판)뿐이다.** 판정은 글자 문구로 짐작할 뿐 뜻은 모른다.
무작위 시점 · 날짜 · 화면 너비처럼 기능으로 시험할 수 없는 것을 한도나 예외 근거로 잡았을 때 쓴다.

- 귀찮거나 어려워서 쓰지 않는다. 한도는 맞는데 값을 정말 못 만들면 거절이 아니라 보류 줄이다(아래 「관문 0」)
- 오판 칸을 「제외」나 보류 줄로 비키지 않는다 — 제외는 케이스가 있는 요구면 무시되고, 보류 줄은 보류 케이스를 지어내게 한다. 빼려면 까닭을 남긴다(2026-10-05 계획 검토)

### 설계 밖 칸 — 더해도 된다

설계에 없는 축의 경계 · 예외 칸도 R18 근거 넷(PRD · 화면 입력 검사 · API 스키마 · 명시된 업무 규칙)에 적혀 있으면 더한다. 막지 않는다.

- 정식 줄(상태 표시 없음 · 기준 줄 아님)의 출처 원장 번호가 모두 그 축을 설계에 안 가졌으면 설계 밖 칸이다. PR 머리에 `설계 밖 칸 N — <요구 축 앞 10개>` 로 센다(사용자 기본값 — 허용 · 보고)
- 근거 넷 어디에도 없는 칸은 지금처럼 만들지 않는다 — 「있을 법하다」는 근거가 아니다(R18)
- 예 — API 표 「로그인 필요: 예」로 만든 401 예외. 코드가 아직 못 보는 근거다(아래 「다음 PR」 ②)

### 관문 0 의 설계 줄과 대처

관문 0(`npm run check:ledger -- … --agent`)은 `설계: 요구 N 중 경계 a · 예외 b` 한 줄을 늘 찍고, 칸 재료가 있으면 설계 대조를 돌려 아래 줄을 찍는다. 줄 꼴의 정본은 `scripts/ledger.ts` · `scripts/authoring-design-check.ts` 다.

| 줄 | 막나 | 대처 |
|---|---|---|
| `설계 칸 빠짐: REQ-… 경계 · …` | 종료 코드 1 | 아래 셋 가운데 하나 |
| `설계 거절 형식 오류: …` | 종료 코드 1 | 위 꼴대로 고친다 — 번호 하나 · 축 · 까닭 |
| `설계 거절: …` | 보고만 | 사람이 PR 머리에서 본다 |
| `설계 밖 칸: …` | 보고만 | 근거가 R18 넷에 있는지 다시 본다 |

**설계 칸 빠짐이면** 위에서부터 대 본다.

1. **줄을 더한다** — 기본이다. 목록의 값대로 줄을 더하고 `npm run ledger:number` 를 다시 돌린 뒤 케이스를 쓴다
2. **오판이면 「설계 거절」 한 줄** — 위 「쓰는 때」
3. **한도는 맞는데 시험 값을 정말 못 만들면 보류 줄** — 시계를 못 움직이는 시간 한도(일 · 시간 · 분 · 초) 같은 것. 먼저 §5 「빼기 전에」 표를 대 본다(`page.clock` 등).
   안 풀리면 출처에 `보류 — <무엇이 없는가>` 를 달고(`wording.md` 「출처 칸의 상태 표시」) held 케이스로 쓴다(§5 「판정 불가 · 보류 요구도 케이스로 쓴다」). 보류 줄도 칸을 채운다

- 칸 재료가 없으면(`npm run ledger:number` 종료 코드 2) 관문 0 은 설계 · 기법 대조를 건너뛰고, PR 머리에 「칸 번호 · 설계 칸 · 기법 — 기준 표를 못 읽어 안 봤다」가 실린다. 그래도 목록의 칸은 다 쓰고 기법도 아래 「기법 표시」대로 적는다
- 올리기 판정은 거절하지 않고 PR 머리에 같은 줄을 싣는다. 빠진 채 올라가도 `⚠️ 설계 칸 빠짐 N` 이 남아 사람이 본다

### 기법 표시 — 기능 케이스에 `techniques` 를 적는다 (2026-10-05 사용자 · PR #158)

기능 케이스는 그 칸을 정한 기법을 `defineCase` 의 `techniques` 에 적는다. 목록 화면이 태그로 보이고 기법으로 거른다(명세 도메인/카탈로그 §8.1).
낱말 목록의 정본은 kit `TECHNIQUES` 다. 칸마다 무엇을 적나의 정본은 도메인/작성 §3.6 「설계 기법」 「칸의 기대 기법」이다.

| 줄의 축 | `techniques` |
|---|---|
| 경계(0건 · 설계 밖 경계 칸도) | `['경계값 분석']` |
| 예외 | 출처의 원장 번호 전부에서 설계 목록이 낸 예외 기법(겹치면 하나). 설계 밖 예외 칸이면 안 적는다 |
| 정상 | 안 적는다 — 목록에서 「기법 없음」으로 걸린다 |
| UI | **안 적는다** — 빈 배열도 K14 위반이다(`npm run check:tests`) |

- 꼴은 리터럴 배열이다 — `techniques: ['동등 분할', '상태 전이']`. 변수 · 펼치기 · 목록 밖 낱말 · 같은 낱말 둘은 K14 위반이다
- 한 케이스가 표의 줄 여럿을 덮으면 첫 줄과 축이 같은 줄들의 출처를 모은다
- 관문 0(`--agent` · `--tests`)이 칸의 기대와 견준다. `기법 어긋남: <tcId> — 「…」이어야 한다(지금 「…」)` 면 종료 코드 1 — 케이스 파일의 `techniques` 를 「」 안대로 고친다.
  표의 축을 잘못 적은 것이면 표를 고치고 `npm run ledger:number` 를 다시 돌린다. 올리기 판정은 거절하지 않고 PR 머리에 `⚠️ 기법 어긋남 N` 을 싣는다
- 기준 줄(main 표에 있던 줄)의 케이스는 안 본다 — 고쳐 쓰지 않는다. 사람 세션은 `--agent` 없이 돌리므로 대조가 안 돈다. 적으면 이 표대로 적는다
