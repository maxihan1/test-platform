## §2 · §5 테스트 두 갈래 — UI Test · Functional Test (2026-10-02 사용자)

`2-requirements.md`(표를 쓸 때)와 `5-writing.md`(코드를 쓸 때)가 여기를 가리킨다. 두 파일이 200줄 상한에 닿아 뗐다.
문장 꼴은 `wording.md` 가 정본이다.

### 갈래 · 근거 · 커버리지 — R17 · R18 · R19

> **R17. 케이스는 두 갈래 중 하나다.** 한 요구가 둘 다 필요하면 표 줄을 둘로 나눈다. 세 층은 2026-10-16 사용자가 정했다 —
> UI 는 모든 버튼을 넓게, 기능은 기획서 규칙을 깊게, E2E 는 기능 테스트를 이어 붙인다.
> **가르는 질문 하나** — 「누른 직후 화면이 반응했나」만 보면 UI, 「그 결과 값이 기획서 규칙대로인가」를 보면 기능이다.
> 같은 「담기」를 UI 는 토스트가 뜨는지, 기능은 개수가 하나 느는지로 본다 — 보는 깊이가 달라 둘 다 쓴다.
>
> - **UI Test** — 「화면이 제대로 그려져 있고, 그 화면에서 누를 수 있는 것이 전부 누른 직후 제 반응을 하는가?」
>   요소가 있다 · 보인다 · 문구 · 처음 상태(꺼진 버튼 · 필수 표시) · 누른 직후 반응(다른 화면으로 간다 · 창 · 팝업이 뜬다 · 펼쳐지고 접힌다 · 탭이 바뀐다 · 선택 상태가 바뀐다).
>   **입력은 넣지 않는다** — 입력값에 따른 결과(오류 안내 · 계산 · 저장 · 개수 변화)와 서버에 남는 것은 안 본다. 화면에 닿으려는 이동은 가는 길이다.
>   누른 직후 반응은 아래 「버튼 반응 케이스」로 쓴다. `축` 칸에 `UI` 를 적는다. `techniques` 를 달지 않는다(K14 — `test-design.md` 「기법 표시」)
> - **Functional Test** — 「사용자가 입력하거나 조작해서 시스템이 기획서 규칙대로 결과를 만드는가?」 —
>   오류 안내 문구 · 개수 · 합계 변화 · 저장 · 흐름 끝 결과(완료 화면) · 경계값 · 예외 · 권한. 로그인이면 화면 이동 → ID 입력 → 비밀번호 입력 → 로그인 누르기 → 성공 확인이 한 케이스다.
>   `축` 칸은 `정상`(Positive) · `예외`(Negative) · `경계`(Boundary) 중 하나다 (R2)
> - **비싼 조작(결제 · 가입) 뒤의 화면은 그 Functional 케이스 안에서 확인한다.** 그 화면만 보는 UI 케이스를 따로 만들면 회귀 때마다 결제를 한 번 더 한다
>
> **E2E 시나리오는 Functional Test 만 부품으로 잇는다** (명세 도메인/시나리오 §3.7). 그래서 Functional Test 는 R7(스스로 준비)과
> R16(만들기 · 확인 가르기)을 지킨다. 다른 케이스가 남긴 상태에 기대면 부품으로 못 쓴다.
>
> **새 tcId 는 종류 글자를 단다** (2026-10-02 사용자 · 명세 도메인/작성 §3.6 「★ 테스트 두 갈래」).
> 작성 에이전트는 아래 「가장 큰 번호 다음」 대신 `npm run ledger:number` 가 칸마다 매긴다(2026-10-04 · 같은 절 「★ 원장」 「칸과 번호」). 명령이 종료 코드 2 일 때만 아래대로 센다.
>
> - UI Test 는 `<접두사>-UI-NNN` 이다. UI 번호열은 `001` 부터 따로 센다. 이미 있으면 가장 큰 UI 번호 다음부터다
> - Functional Test 는 `<접두사>-FN-NNN` 이다. 옛 꼴 `<접두사>-NNN` 과 FN 을 통틀어 가장 큰 숫자 다음부터 센다 — 같은 숫자를 두 번 쓰지 않는다
> - 옛 꼴 `<접두사>-NNN` 은 기능 테스트로 본다. 다시 매기지 않는다
>
> **R18. 근거에 적힌 것만 만든다 — 조합을 늘리지 않는다.** `예외` · `경계` 축은 아래 넷 중 하나에 적힌 것으로만 만든다.
> R3 · R4 의 「기획서가 적었을 때」는 이 넷으로 읽는다. 원장 대조는 출처 칸의 요구 번호를 읽으므로 **번호를 빼고 근거만 적지 않는다.**
>
> | 근거 | 무엇 | `출처` 칸 — 요구 번호 뒤에 붙인다 |
> |---|---|---|
> | PRD(기획서) | 요구 문장 · 표 · 화면 설계 | `기획.md §2 REQ-…` (지금 그대로) |
> | 화면 입력 검사(UI validation) | 실제 화면이 막는 규칙 — §4 탐침으로 본 필수 표시 · 글자 수 제한 · 형식 안내 | `<확인 필요 항목 번호> · 화면 검사 — <요소>` |
> | API 스키마 | 자료로 받은 스키마의 필수 · 형식 · 최소 · 최대 | `REQ-… · API — <경로> <칸>` |
> | 명시된 업무 규칙 | 자료에 글로 적힌 규칙(한도 · 권한 · 상태 전이) | `REQ-… · 규칙 — <자료 이름> <자리>` |
>
> - 예외 축 예 — 필수값 누락 · 잘못된 ID · 잘못된 비밀번호 · 형식 오류 · 권한 부족 · 없는 데이터 · 중복 · 허용되지 않는 상태. **근거에 적혀 있을 때만**이다
> - 경계 축 — 최소 · 최대 길이, 최소 · 최대 값, 경계 ±1(숫자 바로 위 · 바로 아래 한 칸). **근거가 숫자나 0건을 적었을 때만**이다. 숫자 하나에 경계 ±1 두 줄까지다
> - **칸끼리 곱하지 않는다.** 한 줄은 칸 하나만 틀리게 하고 나머지는 정상값을 넣는다. 칸 셋이 각각 틀릴 수 있으면 세 줄이지 아홉 줄이 아니다
> - 넷 어디에도 없는 예외 · 경계는 만들지 않는다. 「있을 법하다」는 근거가 아니다 — 예외는 아래 「오류 추정 점검 목록」 하나다
> - **경계 숫자가 없으면 경계 줄을 만들지 않는다**(0건은 빼고 — 아래 줄) — 숫자를 짐작해 줄을 늘리지 않는다. 정상 줄은 그대로 쓴다.
>   **정상 줄의 기대값이 그 빠진 숫자에 기대면** 기준 없이 되는 꼴로 쓴다(§5 「기준 없는 말」)
> - **작성 에이전트는 설계 목록의 칸을 뺄 수 없다** (2026-10-05 사용자) — 오판이나 미리 아는 환경 한계면 「설계 거절」로 까닭을 남긴다. **0건**(「없으면 … 보여 준다」)은 R2 의 경계다.
>   기법 · 줄 쓰는 법 · 거절 꼴은 `test-design.md`
>
> **화면에만 있는 입력 규칙 — 정방향에서도 미확정 케이스로 만든다** (2026-10-02 사용자).
>
> - 대상은 **입력 규칙만**(필수 표시 · 글자 수 제한 · 형식 안내)이고 **기획서가 다루는 화면 안에서만** 본다. 기획서에 없는 메뉴 · 화면은 만들지 않는다 — 역방향 「대조」가 맡는다(그 화면 안 버튼의 누른 직후 반응은 아래 「버튼 반응 케이스」)
> - 표는 §3 에서 얼지만 이 줄만 예외다. **§4 탐침에서 본 사람(자식 혼자면 자식, 팬아웃이면 서브에이전트)은 적어 두고, 표에 줄을 더하는 것은 메인(자식) 하나다** —
>   같은 규칙을 두 번 찾았으면 하나로 합친다. 줄은 그 규칙을 더한 표준 기획서 항목의 임시 번호를 출처로 쓰고(`MKT-NEW-003 · 화면 검사 — <요소>` · `tpx-author` `prd.md` §5) 번호는 이어서 매긴다(작성 에이전트는 `npm run ledger:number` 를 다시 돌린다 — `화면 검사 —` 표시로 정식 줄과 다른 케이스가 된다).
>   더하는 것은 팬아웃 뒤 합치는 단계까지다 — 관문 0 을 연 뒤에는 더하지 않는다. 작성 에이전트에서는 더한 케이스를 메인이 쓰고 마지막 전체 돌려 보기가 3회로 덮는다(`tpx-author` `references/fanout.md` §5). 「관문 0」은 합친 뒤의 것이고 표를 쓴 직후의 「관문 0 일찍」은 세지 않는다
> - `축` 은 필수 표시 · 형식 안내가 `예외`, 글자 수 제한이 `경계` 다 — 규칙을 어긴 입력이 막히는지 보는 줄이라 Functional 이다
> - **입력 칸이 한도를 넘는 글자를 아예 막으면** 「한도 + 1 을 넣으면 한도까지만 들어간다」는 경계 케이스로 쓴다. 기획서가 넘었을 때의 오류를 말하면 차이 · 미확정이다.
>   **막는지는 짐작하지 않고 §4 탐침이 잰다** — 그 칸에 쓸 입력 방법(Page Object 도 그 방법으로 쓴다)으로 한도 + 1 을 넣고 남은 길이를 읽는다(`4-selector.md` 「입력 칸 한도」 · 2026-10-16)
>   케이스를 빼고 「사람 판단」으로 미루지 않는다 — 정본은 도메인/작성 §3.6 「★ 테스트 두 갈래」(2026-10-03, CDY 와 MKT 가 같은 상황을 다르게 처리했다)
>   **이 줄을 더하면 같은 칸의 기획서 경계 줄 「한도 + 1 → 오류 문구 · 등록 안 됨」은 표에서 뺀다** (2026-10-12 PRD-F9-12) — 표가 화면을 보기 전에 얼어 그 줄이 남고, 그 값은 칸에 들어가지도 않아 늘 실패한다(MKT 8건).
>   결과 문장으로 바꿔 남기면 이 줄과 같은 문장이 두 케이스에 생긴다(관문 2 「결과 칸의 문장이 서로 다른가」). 뺀 줄 뒤 칸 번호는 다시 매긴다. 이 줄을 못 쓰는 작성(아래)은 그 줄의 결과를 「한도까지만 들어간다」로 바꾸고 끝 보고에 적는다
> - 미확정은 그 줄 출처의 `확인 필요` 항목 번호가 정한다 — 케이스 파일에 꼬리표는 달지 않는다(2026-10-11 PRD-F4-05). 사람이 테스트 작성 「결정 필요」에서 그 항목을 확정하거나 「PRD 관리」에서 지운다.
>   기대값은 사람이 판정한 것에서만 온다는 원칙(CLAUDE.md 「playwright-cli」)의 예외는 `확인 필요` 항목을 덮는 미확정 케이스뿐이다.
>   **표준 기획서 절이 없는 작성(사람 세션 · 이어 작성)은 이 줄을 쓰지 않는다** — 항목을 올릴 길이 없어 쓰면 확정으로 돈다. 본 규칙은 끝 보고(작성 에이전트는 결과 요약)에 적는다
> - 「화면만」 요청은 지금처럼 전부 미확정이다 — 이 규칙과 상관없다
>
> **오류 추정 점검 목록 — 기획서가 결과를 안 적은 곳을 미확정 케이스로 만든다** (2026-10-10 사용자 · 정본 도메인/작성 §3.6 「설계 기법」 「오류 추정」).
>
> | 항목 | 어디에 | 해 보는 것 | 「~해야 한다」 |
> |---|---|---|---|
> | 빈 값 | 입력 칸이 있는 제출 | 칸을 비우고 제출 | 화면이 보인 대로 |
> | 공백만 | 빈 값이 막히는 글 칸 | 공백만 넣고 제출 | 빈 값처럼 막힌다 |
> | 두 번 누르기 | 만들기 · 결제 · 저장 버튼(게임은 구매 · 강화 · 판매도) | 빠르게 두 번 누른다 | 하나만 생긴다 |
> | 남의 것 | 주소에 번호가 든 내 것 화면(주문 상세 · 글 수정) | 다른 계정의 번호로 연다 | 남의 내용이 안 보인다 |
> | 없는 주소 | 같은 화면 | 없는 번호로 연다 | 깨지지 않고 안내가 보인다 |
> | 서버 실패 | 화면의 주 동작 | 그 응답을 모킹 500 으로 | 깨지지 않고 오류 안내가 보인다 |
> | 통신 끊기 | 게임만 — 구매 · 강화 · 판매 · 저장 버튼 | 누른 직후 와이파이를 끊었다 다시 켠다 | 한 번만 반영되고 게임이 멈추지 않는다 |
> | 다시 켜기 | 게임만 — 위치 · 진행이 바뀌는 동작 | 동작 뒤 앱을 끄고 다시 켠다 | 바뀐 위치 · 진행이 남는다 |
>
> - **게임만 항목 둘(통신 끊기 · 다시 켜기)은 종류 「게임」 애플리케이션에만 쓴다** — 웹 · 앱은 여섯 그대로다. 해 보는 법은 `test-design.md` 「게임 애플리케이션」 「끊김」 (2026-10-23 GAME-F1-11)
> - **표를 쓸 때(§2) 기획서로 줄을 더한다** — 기획서가 다루는 화면마다 맞는 항목을, 화면마다 항목당 한 줄까지. 출처는 그 화면 · 동작을 다루는 요구 가운데 원장 차례가 가장 앞인 번호다. 칸끼리 곱하지 않는다.
>   **케이스 하나에 항목 하나다** — 번호 명령이 항목마다 칸을 따로 센다. 한 줄에 항목 둘을 적지 않는다
> - **근거 넷이 그 결과를 적었으면 오류 추정이 아니다** — 정식 예외 줄(설계 칸이면 설계 줄)로 쓴다. 같은 자리를 두 번 쓰지 않는다
> - 출처 칸은 `REQ-… · <확인 필요 항목 번호> · 오류 추정 — <항목>`, 축은 `예외`, Functional 이다. 번호 명령이 따로 센다 — 설계 칸을 못 채우고 설계 밖 칸으로도 안 센다(`test-design.md` 「무엇이 칸을 채우나」)
> - 케이스를 쓸 때 화면에서 해 보고 문구 · 요소를 읽는다. 「~해야 한다」는 위 표가 정한다 — **화면이 그것을 어기면(두 건 생김 · 남의 주문이 보임 · 빈 화면) 표대로 쓰고 빨간 채로 둔다.**
>   `held` 를 달지 않고 결과 요약 `오류 추정:` 줄(사람 세션은 끝 보고)에 싣는다 — §6 「같은 이유로 3회 빨강」의 예외다
> - 해 볼 수 없으면(주소에 번호가 없음 · 다른 계정을 못 만듦) 케이스를 쓰지 않고 「표에서 고칠 것」으로 그 줄을 뺀다 — `보류 —` 표시를 달지 않는다
> - 케이스에 `techniques: ['오류 추정']` 을 단다(꼬리표는 안 단다). 서버 실패는 모킹으로 만든다(R4)
> - 본 결과를 결과 파일에 `확인 필요` 항목으로 더하고 그 번호를 줄 출처의 원래 요구 번호 뒤에 같이 적는다 — 그 번호가 미확정을 정한다(`tpx-author` `references/prd.md` §4 · §5).
>   **표준 기획서 절이 없는 작성(사람 세션 · 이어 작성)은 오류 추정 줄을 쓰지 않는다** — 위 「화면에만 있는 입력 규칙」과 같은 까닭이다
>
> **버튼 반응 케이스 — 화면마다 하나** (2026-10-16 사용자 · PRD-F10-09 · 정본 도메인/작성 §3.6 「★ 테스트 두 갈래」 「버튼 반응」).
>
> - **어느 버튼** — 기획서가 다루는 화면에서 누를 수 있는 것 전부(버튼 · 버튼처럼 도는 링크 · 탭 · 펼치기 · 켜고 끄기). 머리 메뉴 · 바닥 링크처럼 화면마다 같은 것은
>   화면 이름 `공통` 으로 사이트에 한 번, 목록 줄마다 되풀이되는 버튼(「삭제」)은 대표 하나다 — 크롤러 누르기 규칙과 같다
> - **보는 것** — 누른 직후 반응 하나. 이동이면 도착 화면, 창 · 팝업이면 그 창이 보임, 펼치기 · 탭 · 켜고 끄기면 바뀐 상태. 저장됐나 · 숫자가 맞나는 기능 몫이다.
>   반응을 본 뒤 다음 버튼 앞에서 원래 화면으로 되돌린다(창은 닫고, 이동했으면 화면 파일 주소로 다시 연다)
> - **입력이 있어야 도는 제출 버튼은 누르지 않고 「보이고 누를 수 있다」까지만 본다** — 빈 값 · 틀린 값 제출은 기능(예외 · 오류 추정)이 맡는다. 크롤러도 채워야 하는 폼의 제출은 안 누른다
> - **위험 버튼(삭제 · 결제 · 탈퇴 · 발송)은 확인 창이 뜨는 데까지 보고 취소한다.** 확인 창 없이 바로 도는 버튼은 줄을 만들지 않는다 — 기능이 맡는다
> - **표** — 버튼마다 한 줄, 축 `UI`, 출처는 `<그 화면을 다루는 요구 가운데 원장 차례가 가장 앞인 번호> · <반응을 적은 요구 번호 또는 그 화면의 확인 필요 항목 번호> · 버튼 반응 — <화면 이름>`.
>   첫 번호의 요구가 그 반응을 적었으면 번호 하나다(`MKT-REQ-030 · 버튼 반응 — 장바구니`). 첫 번호는 화면을 잡으려고 적은 것이라 덮음으로 안 센다 — 오류 추정과 같다. 번호가 하나뿐인 줄(첫 요구가 그 반응을 적었다)은 그 번호를 센다.
>   **화면 이름은 그 화면의 줄마다 글자 하나 다르지 않게 쓰고 `·` 를 넣지 않는다** — 번호 명령이 표시 뒤부터 다음 `·` 앞까지를 화면 이름으로 읽어 칸을 가른다. 그 화면의 줄은 모두 같은 첫 번호로 시작한다 — `공통` 은 원장 첫 번호다. 화면 하나가 케이스 하나이고 열 줄이 넘으면 번호 명령이 둘로 나눈다
> - **기대값** — 근거 넷(R18)이 그 반응을 적었으면 그대로(확정). 안 적었으면 눌러 본 반응을 쓰고, 그 화면의 `확인 필요` 항목 **하나**(「<화면> 버튼 반응」 — 버튼 → 반응 목록)를 결과 파일에 더해
>   그 번호를 화면에서만 본 줄의 출처에 적는다(`tpx-author` `references/prd.md` §4). 버튼마다 항목을 만들지 않는다. 사람이 테스트 작성 「결정 필요」에서 그 항목을 한 번에 확정한다.
>   그런 줄이 하나라도 있으면 그 화면 케이스는 통째로 미확정이다(확정 반응 줄까지) — 화면 하나를 케이스 하나로 둔 대가다. 그림 설명 메모(「버튼 누르면 팝업 뜸」)처럼 `확인 필요` 로 올라간 문서 항목이 반응을 적었으면 그 번호를 줄 출처에 적는다
> - **언제 · 누가** — §4 탐침에서 버튼을 하나씩 눌러 본 뒤 메인(자식) 하나가 표에 더한다 — 「화면에만 있는 입력 규칙」과 같은 때 · 같은 사람이다.
>   크롤러가 남긴 화면 연결(누른 버튼 → 도착 화면)과 크롤 파일의 버튼 목록은 출발점이다. 쓰기 전에 직접 눌러 본다
> - **케이스** — 버튼마다 `test.step` 하나에 `verify` 하나. blocker 를 달지 않는다 — 판정 하나가 실패해도 다음 버튼을 돈다. R5 의 절차 · 화면 전환 상한은 안 건다(칸 하나가 케이스 하나다). E2E 부품이 아니다
> - **표준 기획서 절이 없는 작성(사람 세션 · 이어 작성)은 근거 넷이 적은 반응 줄만 쓴다** — 화면에서만 본 반응은 항목을 올릴 길이 없다. 본 것은 끝 보고(작성 에이전트는 결과 요약)에 적는다
> - 이미 있는 케이스는 건드리지 않는다 — 새 작성부터다
>
> **R19. 커버리지는 갈래에 맞는 케이스로 채운다** (2026-10-02 사용자 — 「UI 는 UI 만」).
>
> - **동작을 적은 요구(누가 무엇을 하면 무엇이 된다)는 Functional 케이스가 덮는다.** 「버튼이 보인다」 같은 UI 케이스나 버튼 반응 줄 하나로 그 번호를 덮었다고 치지 않는다 —
>   원장 대조(관문 0)는 출처 칸의 번호만 보므로 이 어긋남을 못 잡는다. 사람이 PR 에서 본다
> - **화면 모양만 적은 요구(문구 · 배치 · 보임 · 처음 상태)와 누른 직후 반응만 적은 요구(「누르면 팝업이 뜬다」)는 UI 케이스가 덮는다.** 이것을 업무 흐름 끝까지 가는 Functional 케이스로 키우지 않는다
> - **0건 상태의 기능 경계(빈 상태에서 하나가 생기면 바뀌는 것)는 처음 화면의 UI 칸과 따로 쓴다** (2026-10-05) — 한쪽이 다른 쪽을 덮지 않는다(`test-design.md` 「0건」)
> - 한 요구 번호에 둘 다 있으면 줄 둘에 같은 번호를 적는다. 둘 다 있어야 덮은 것이다.
>   **동작 쪽을 `## 제외` 로 빼면서 UI 줄만 남기지 않는다** — 원장 셈은 그 번호를 덮은 것으로 센다. 동작이 정말 빠지면 UI 줄도 같이 빼고 제외 사유에 둘 다 적는다
> - **예전 커버리지 규칙은 Functional 쪽에 그대로 산다** — 장 단위로 빼지 않기 · 모킹으로 예외 만들기(R4 · §5 「빼기 전에」) · API 케이스(§5) · 기준 없는 말 케이스(§5). 달라진 것은 R18 로 근거 없는 줄을 막는 것뿐이다

### Page Object

UI Test 와 Functional Test 는 Page Object 를 쓴다. locator 를 케이스 파일에 직접 적지 않는다 (명세 도메인/작성 §3.6 「★ 테스트 두 갈래」).
올리기 허용 목록(`.claude/scripts/cases-only.mjs`)과 CI 가 아래 세 자리를 받는다. **이름은 `^[a-z][a-z0-9-]{0,40}$`** — 소문자로 시작하고 소문자 · 숫자 · 하이픈만 쓴다. 꼴이 다르면 올리기가 거절된다.

| 무엇 | 규칙 |
|---|---|
| 자리 · 이름 | `tests/<폴더>/pages/<화면>.page.ts` · 두 화면 이상에 나오는 화면 조각(머리 메뉴 · 토스트 · 모달)만 `tests/<폴더>/components/<조각>.component.ts` · 로그인 · 계정(가입 · 탈퇴) · 자료 만들고 지우기 같은 공용 도우미는 `tests/<폴더>/helpers/<이름>.helper.ts`. **도우미를 `components/` 에 두지 않는다** — 스캔이 케이스가 가져오는 `pages/` · `components/` 로 「케이스 ↔ 화면」 지도를 채우는데, 거의 모든 케이스가 쓰는 로그인 도구가 거기 있으면 모든 케이스가 그 조각에 닿는다(명세 도메인/작성 §3.6 「지도」). 화면 하나에 파일 하나 · 클래스 하나 · 생성자는 `page` 만 받는다(적응형만 기기마다 둘 — 아래 「화면 크기 판정」). **`.spec.ts` · `.test.ts` 로 끝나는 이름 금지** — Playwright 가 테스트로 집는다 |
| 화면 주소 | 화면 파일(`pages/`) 클래스 첫 줄에 그 화면의 주소를 값으로 둔다 — `static readonly 주소 = '/cart';`. 따옴표 안 글자 그대로만 읽는다(계산식이면 지도에 주소가 비어 들어간다). 주석이 아니라 값인 까닭은 테스트 코드에 주석을 못 쓰기 때문이다. 화면 조각 · 도우미에는 두지 않는다 |
| 담는 것 | §4 에서 확정한 locator(우선순위 그대로)와 짧은 동작(채우기 · 누르기 · 이동). **찾는 법의 정본은 여기다** — 용어 사전에는 이름과 뜻만 남긴다 |
| 담지 않는 것 | `test.step` · `verify` · 기대값 · 판정. **K6 · K12 와 증적 문서가 케이스 파일의 절차 제목과 판정 문장을 글자로 읽는다** — Page Object 안의 `verify` 는 판정 0 건으로 센다 |
| 금지 | 주석 · `expect` — `tests/**` 전체에 걸리는 규칙이라 Page Object 파일도 훅과 CI(`check:tests` K7)가 막는다. 가져오기는 같은 `tests/` 안 파일 · `@playwright/test`(`test` · `expect` 말고) · kit 의 타입뿐이다(명세 공통/2-명세선언 「Page Object 파일」) |
| 부르는 법 | `import { 로그인화면 } from './pages/login.page.js'` (저장소가 `NodeNext` 라 `.js` 로 적는다). 관문 1 의 타입 검사와 관문 3 실행이 확인한다 |
| 여럿이 같이 쓰기 | 이미 있으면 **고치거나 이름을 바꾸지 말고 더한다** — 다른 케이스가 그 주소를 쓴다. 공용 Component · 도우미는 팬아웃 전에 메인이 먼저 만들고 서브에이전트는 읽기만 한다(모자란 도우미는 자기 묶음의 `helpers/draft-<slug>.helper.ts` 에만 적고 메인이 공용으로 옮긴다 — `tpx-author` `fanout.md`). 요청 둘이 같은 Page Object 를 고치면 반영 때 AI 가 합치지만, 같은 멤버를 서로 다르게 바꿨으면 못 합쳐 반영이 실패한다(「같은 자료로 다시 작성」) |

**Functional Test 도 Page Object 를 쓴다** (2026-10-02 사용자 · PR #130). E2E 시나리오의 「만들기」 판별(`catalog/steps.ts`)이 Page Object 호출을 믿는다 —
Page Object 파일은 판정 · 절차를 부르지도 들여오지도 못하기 때문이다. 그래서 **Page Object 메서드에 함수를 넘기지 않는다**(콜백 안의 판정이 안 보여 그 절차를 건너뛸 수 없게 된다).
**Page Object 에서 `request` 를 쓰지 않는다** — E2E 의 모킹 경고(`usesRequest`)는 케이스 파일만 읽는다. API 케이스(R17 · §5)는 케이스 파일에서 `request` 를 직접 쓴다.
찾는 법의 정본은 두 갈래 다 Page Object 이고 용어 사전에는 이름과 뜻만 둔다.

### 화면 크기 판정 — 케이스 기기 고르기 (2026-10-16 PRD-F10-07 · 사용자 D3)

크롤러 요약 줄의 「화면 크기 판정 …」으로 **새 케이스**의 `platforms` 를 정한다. 이미 있는 케이스의 `platforms` 는 고치지 않는다. 판정 규칙의 정본은 명세 도메인/작성 §3.6 「화면 기록과 크롤러」 「화면 크기」다.

| 판정 | 새 케이스 `platforms` | 화면 파일 | 관문 3 |
|---|---|---|---|
| PC 전용 · 판정 없음(크롤러를 안 돌린 정방향 · 모바일로 연 화면 0장) | 생략(`['desktop']`). 기획서가 모바일을 말한 요구만 `['desktop', 'mobile']`(R8) | 화면 하나에 파일 하나 | `--project=desktop` |
| 반응형 | **전부** `['desktop', 'mobile']` | 화면 하나에 파일 하나. `<크롤 폴더>/viewport.json` 에 그 화면이 있고 `PC만` · `모바일만` 에 케이스가 쓰는 요소가 있으면 모바일 길(메뉴 열기 등)을 그 화면 파일 메서드 안에 넣는다 — 좁은 화면(`this.page.viewportSize()!.width < 768`)일 때만 먼저 메뉴를 연다. 케이스 파일은 기기를 모른다 | PC · 모바일을 **동시에** — 아래 |
| 적응형 | **전부** `['desktop', 'mobile']` — 케이스는 하나다(칸 하나 = 번호 하나 · 2026-10-16 사용자 「가」) | **기기마다 따로** — PC `pages/<화면>.page.ts` · 모바일 `pages/m-<화면>.page.ts`(모바일 화면 주소를 `주소` 값으로). 두 파일은 **메서드 이름 · 인자가 같다**. 케이스는 공용 도우미 `helpers/device.helper.ts` 의 `모바일인가(page)`(화면 폭 768 미만)로 둘 중 하나를 만든다 — `const 장바구니 = 모바일인가(page) ? new 모바일장바구니화면(page) : new 장바구니화면(page);` | PC · 모바일을 동시에 — 아래. 팬아웃은 `tpx-author` `fanout.md` 「적응형」 |

**PC · 모바일을 동시에 돌린다** — 한 명령에 `--project=desktop --project=mobile --workers=2` 를 준다. 차례로 두 번 돌면 관문 시간이 두 배다(D2).
작성 에이전트는 돌려 보기 명령(보조 한 판 · 마지막)에 `--mobile` 을 붙인다 — 명령이 기기마다 따로 나란히 띄운다. 에이전트가 PC 기록으로 하나씩(`--workers=1`) 돌았는지 보기 때문이다(`tpx-author` `SKILL.md` 관문 명령). 1번 돌려 보기는 기기 하나만 돈다(기본 PC · 휴대폰은 `--mobile-only`).
3회 결과 파일의 `expected` 는 케이스 수 × 3 × 2 다(작성 에이전트 보조 AI 의 한 판 기록은 기기마다 케이스 수 × 1). 모바일에서만 빨간 케이스도 빨강이다 — 까닭은 PC 와 같이 가른다(`6-gates.md` 「관문이 빨개지면」 — trace 를 켜고 다시 돌릴 때 `--project=mobile`, 작성 에이전트는 1번 돌려 보기에 `--mobile-only`).
