## §2 · §5 테스트 두 갈래 — UI Test · Functional Test (2026-10-02 사용자)

`2-requirements.md`(표를 쓸 때)와 `5-writing.md`(코드를 쓸 때)가 여기를 가리킨다. 두 파일이 200줄 상한에 닿아 뗐다.
문장 꼴은 `wording.md` 가 정본이다.

### 갈래 · 근거 · 커버리지 — R17 · R18 · R19

> **R17. 케이스는 두 갈래 중 하나다.** 한 요구가 둘 다 필요하면 표 줄을 둘로 나눈다. 가르는 물음은 사용자 문장 그대로다.
>
> - **UI Test** — 「사용자의 조작 없이도 해당 화면 자체가 올바르게 구성되어 있는가?」 요소가 있다 · 보인다 · 문구 · 처음부터 꺼진 버튼 · 필수 표시.
>   화면에 닿으려는 이동 · 메뉴 열기 · 탭 전환은 조작으로 치지 않는다 — 결과가 아니라 가는 길이다. `축` 칸에 `UI` 를 적는다
> - **Functional Test** — 「사용자의 조작에 의해 시스템이 의도한 기능적 결과를 만들어내는가?」 입력하거나 눌러서 생긴 결과는 전부 여기다 —
>   오류 안내 문구 · 개수 변화 · 이동 · 완료 화면. 로그인이면 화면 이동 → ID 입력 → 비밀번호 입력 → 로그인 누르기 → 성공 확인이 한 케이스다.
>   `축` 칸은 `정상`(Positive) · `예외`(Negative) · `경계`(Boundary) 중 하나다 (R2)
> - **비싼 조작(결제 · 가입) 뒤의 화면은 그 Functional 케이스 안에서 확인한다.** 그 화면만 보는 UI 케이스를 따로 만들면 회귀 때마다 결제를 한 번 더 한다
>
> **E2E 시나리오는 Functional Test 만 부품으로 잇는다** (명세 도메인/시나리오 §3.7). 그래서 Functional Test 는 R7(스스로 준비)과
> R16(만들기 · 확인 가르기)을 지킨다. 다른 케이스가 남긴 상태에 기대면 부품으로 못 쓴다.
>
> **tcId 의 종류 글자**(`PAY-UI-001` · `PAY-FN-001`)는 명세가 정했지만 검사기와 서버가 아직 모른다 —
> 반영되기 전에는 지금 형식(`PAY-001`)을 쓰고 종류는 `축` 칸으로만 가른다 (명세 도메인/작성 §3.6 「★ 테스트 두 갈래」).
>
> **R18. 근거에 적힌 것만 만든다 — 조합을 늘리지 않는다.** `예외` · `경계` 축은 아래 넷 중 하나에 적힌 것으로만 만든다.
> R3 · R4 의 「기획서가 적었을 때」는 이 넷으로 읽는다. 원장 대조는 출처 칸의 요구 번호를 읽으므로 **번호를 빼고 근거만 적지 않는다.**
>
> | 근거 | 무엇 | `출처` 칸 — 요구 번호 뒤에 붙인다 |
> |---|---|---|
> | PRD(기획서) | 요구 문장 · 표 · 화면 설계 | `기획.md §2 REQ-…` (지금 그대로) |
> | 화면 입력 검사(UI validation) | 실제 화면이 막는 규칙 — §4 탐침으로 본 필수 표시 · 글자 수 제한 · 형식 안내 | `REQ-… · 화면 검사 — <요소>` |
> | API 스키마 | 자료로 받은 스키마의 필수 · 형식 · 최소 · 최대 | `REQ-… · API — <경로> <칸>` |
> | 명시된 업무 규칙 | 자료에 글로 적힌 규칙(한도 · 권한 · 상태 전이) | `REQ-… · 규칙 — <자료 이름> <자리>` |
>
> - 예외 축 예 — 필수값 누락 · 잘못된 ID · 잘못된 비밀번호 · 형식 오류 · 권한 부족 · 없는 데이터 · 중복 · 허용되지 않는 상태. **근거에 적혀 있을 때만**이다
> - 경계 축 — 최소 · 최대 길이, 최소 · 최대 값, 경계 ±1(숫자 바로 위 · 바로 아래 한 칸). **근거가 숫자를 적었을 때만**이다. 숫자 하나에 경계 ±1 두 줄까지다
> - **칸끼리 곱하지 않는다.** 한 줄은 칸 하나만 틀리게 하고 나머지는 정상값을 넣는다. 칸 셋이 각각 틀릴 수 있으면 세 줄이지 아홉 줄이 아니다
> - 넷 어디에도 없는 예외 · 경계는 만들지 않는다. 「있을 법하다」는 근거가 아니다
> - **경계 숫자가 없으면 경계 줄을 만들지 않는다** — 숫자를 짐작해 줄을 늘리지 않는다. 정상 줄은 그대로 쓴다.
>   **정상 줄의 기대값이 그 빠진 숫자에 기댈 때만** `판정 불가` 케이스로 남긴다(§5 「판정 불가 · 보류 요구도 케이스로 쓴다」)
>
> **화면에만 있는 입력 규칙 — 정방향에서도 미확정 케이스로 만든다** (2026-10-02 사용자).
>
> - 대상은 **입력 규칙만**(필수 표시 · 글자 수 제한 · 형식 안내)이고 **기획서가 다루는 화면 안에서만** 본다. 기획서에 없는 버튼 · 메뉴는 만들지 않는다 — 역방향 「대조」가 맡는다
> - 표는 §3 에서 얼지만 이 줄만 예외다. **§4 탐침에서 본 사람(자식 혼자면 자식, 팬아웃이면 서브에이전트)은 적어 두고, 표에 줄을 더하는 것은 메인(자식) 하나다** —
>   같은 규칙을 두 번 찾았으면 하나로 합친다. 줄은 그 칸을 다루는 요구의 번호를 출처로 쓰고(`REQ-… · 화면 검사 — <요소>`) 번호는 이어서 매긴다
> - 그 케이스에 `unconfirmed` 를 단다 — 사유 꼴은 `wording.md` 「사유 머리」. 기대값을 화면에서 읽었으므로 사람이 「케이스 고치기」로 확정하거나 지운다.
>   기대값은 사람이 판정한 것에서만 온다는 원칙(CLAUDE.md 「playwright-cli」)의 예외는 미확정 꼬리표뿐이다
> - 「화면만」 요청은 지금처럼 전부 미확정이다 — 이 규칙과 상관없다
>
> **R19. 커버리지는 갈래에 맞는 케이스로 채운다** (2026-10-02 사용자 — 「UI 는 UI 만」).
>
> - **동작을 적은 요구(누가 무엇을 하면 무엇이 된다)는 Functional 케이스가 덮는다.** 「버튼이 보인다」 같은 UI 케이스 하나로 그 번호를 덮었다고 치지 않는다 —
>   원장 대조(관문 0)는 출처 칸의 번호만 보므로 이 어긋남을 못 잡는다. 사람이 PR 에서 본다
> - **화면 모양만 적은 요구(문구 · 배치 · 보임 · 처음 상태)는 UI 케이스가 덮는다.** 이것을 업무 흐름 끝까지 가는 Functional 케이스로 키우지 않는다
> - 한 요구 번호에 둘 다 있으면 줄 둘에 같은 번호를 적는다. 둘 다 있어야 덮은 것이다.
>   **동작 쪽을 `## 제외` 로 빼면서 UI 줄만 남기지 않는다** — 원장 셈은 그 번호를 덮은 것으로 센다. 동작이 정말 빠지면 UI 줄도 같이 빼고 제외 사유에 둘 다 적는다
> - **예전 커버리지 규칙은 Functional 쪽에 그대로 산다** — 장 단위로 빼지 않기 · 모킹으로 예외 만들기(R4 · §5 「빼기 전에」) · API 케이스(§5) · 판정 불가 케이스. 달라진 것은 R18 로 근거 없는 줄을 막는 것뿐이다

### Page Object — UI Test · **대기 (#129 에서 켠다)**

**아직 쓰지 않는다.** 작성 에이전트의 올리기 허용 목록(`.claude/scripts/cases-only.mjs`)과 CI 의 서비스 폴더 판정이 `pages/` 파일을 받지 않아,
지금 만들면 작성 요청이 실패한다. #129 전까지 UI Test 도 지금처럼 케이스 파일 안에서 locator 를 쓰고 용어 사전을 따른다.
아래는 #129 가 켤 규칙이다 (명세 도메인/작성 §3.6 「★ 테스트 두 갈래」).

| 무엇 | 규칙 |
|---|---|
| 자리 · 이름 | `tests/<폴더>/pages/<화면>.page.ts` · 두 화면 이상에 나오는 부품만 `tests/<폴더>/components/<부품>.component.ts`. 화면 하나에 파일 하나 · 클래스 하나 · 생성자는 `page` 만 받는다. **`.spec.ts` · `.test.ts` 로 끝나는 이름 금지** — Playwright 가 테스트로 집는다 |
| 담는 것 | §4 에서 확정한 locator(우선순위 그대로)와 짧은 동작(채우기 · 누르기 · 이동). **찾는 법의 정본은 여기다** — 용어 사전에는 이름과 뜻만 남긴다 |
| 담지 않는 것 | `test.step` · `verify` · 기대값 · 판정. **K6 · K12 와 증적 문서가 케이스 파일의 절차 제목과 판정 문장을 글자로 읽는다** — Page Object 안의 `verify` 는 판정 0 건으로 센다 |
| 금지 | 주석 · `expect` — `tests/**` 전체에 걸리는 규칙이라 Page Object 파일도 훅이 막는다 |
| 부르는 법 | `import { 로그인화면 } from './pages/login.page.js'` (저장소가 `NodeNext` 라 `.js` 로 적는다). 관문 1 의 타입 검사와 관문 3 실행이 확인한다 |
| 여럿이 같이 쓰기 | 이미 있으면 **고치거나 이름을 바꾸지 말고 더한다** — 다른 케이스가 그 주소를 쓴다. 공용 Component 는 팬아웃 전에 메인이 먼저 만들고 서브에이전트는 읽기만 한다. 요청끼리 부딪히면 반영 때 AI 가 한 번 더 판단하고, 그래도 헷갈리면 사람이 고른다 |

**Functional Test 는 #130 직후부터 Page Object 를 쓴다** (2026-10-02 사용자). 그 전에는 `page` 를 직접 쓴다 —
E2E 시나리오의 「만들기」 판별(`catalog/steps.ts`)이 `page` 로 시작하는 호출만 건너뛸 수 있는 절차로 알아보기 때문이다.
그때까지 Functional 의 locator 는 용어 사전의 `locator` 칸이 정본이다.
