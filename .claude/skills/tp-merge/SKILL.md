# /tp-merge

체인 [7] 마지막. **이 절차는 사고를 구조적으로 막으려고 고정됐다** — 순서를 건너뛰지 않는다.

## 선행 조건

게이트 2 승인이 끝났다. 승인 전에 이 스킬을 부르지 않는다.

## 선행 읽기

**SPEC 은 다시 읽지 않는다. 재로드 금지.** 기록을 쓰기 위해 아래 둘의 **해당 부분만** 연다.

- `docs/progress/<갈래>.md` — 형식을 맞추려 마지막 항목 하나
- `docs/LEARNINGS.md` — `grep -n '^## '` 로 헤딩만. 같은 유형이 이미 있는지 보려는 것이다

## Step 1. 병합 전 전수 확인 — 소실 방지

작업방에 커밋 안 된 산출물(특히 계획·문서)이 남아 있으면 작업방을 지울 때 **영구 소실**된다.

```bash
git status --porcelain                       # 비어야 한다
git log origin/<브랜치>..HEAD --oneline      # 미푸시 0
gh pr checks                                 # 아래 3분기로 읽는다
```

| `gh pr checks` | 판정 |
|---|---|
| 초록 | 통과 |
| 빨강 | **병합하지 않는다.** 고치고 다시 |
| **체크 0건** | **통과가 아니다.** CI 자동 실행이 없어 보통 여기다. [6] 의 종료 코드가 유일한 근거이므로 그것을 확인하고 그 사실을 게이트 2 요약에 적는다. 확인 못 하면 병합하지 않는다 |

미커밋이 있으면 그 작업의 산출물인지 보고 커밋·푸시한다. **계획·문서가 1순위 소실 위험**이다.

## Step 2. ★ 여기서 처음 초안 잠금을 푼다

**`gh pr ready` 는 체인 전체에서 이 줄 하나뿐이다.** 판별식 `pr-draft-guard` 가 강제한다.

```bash
gh pr ready <번호>
gh pr edit <번호> --title "<`[작업중]` 을 뗀 제목>"
```

초안이 잠금 역할을 한다 — 2026-09-17 에 두 번 난 사고(#4→#5, #6→#7, 먼저 병합돼서
뒤 커밋 누락)를 막는 장치다. **작업 중에는 병합하고 싶어도 버튼이 안 눌린다.**

## Step 3. 병합

```bash
gh pr merge <번호> --merge
gh pr view <번호> --json state -q .state      # MERGED 확인
```

충돌이 나면 `git pull --rebase origin main` 후 충돌 파일을 표시하고 사용자에게 넘긴다.

**`--force` push · 브랜치 삭제 · 마이그레이션 되돌리기는 하지 않는다** (CLAUDE.md §5).

## Step 4. 작업방 정리

```bash
cd <저장소 루트>
git worktree remove .claude/worktrees/<이름> 2>/dev/null || echo "이미 제거됨"
git worktree prune
```

**`--force` 를 먼저 쓰지 않는다.** 거부당하면 남은 것이 있다는 뜻이니 Step 1 로 돌아간다.

작업방을 다음 작업에 이어 쓸 거면 **지우지 않는다.** 사용자에게 남긴다고 알린다.

## Step 5. 기록 — 이게 다음 세션의 입력이다

### 진행 기록 (항상)

`docs/progress/<갈래>.md` 에 **추가**한다. 덮어쓰지 않는다.

```markdown
## <날짜>
- 완료: <무엇을>
- 미완: <남은 것 또는 "없음">
- 막힌 것: <있으면>
- 다음 세션이 알아야 할 것: <진입점 한 줄>
```

갈래가 없는 작업이면 `docs/progress/` 대신 PR 코멘트로 갈음한다.

### LEARNINGS (해당할 때만)

CLAUDE.md §2.5 의 「적는 기준」에 맞는 것만 적는다.

- 처음에 틀리게 만들었다가 고쳤다 (**왜 틀렸는지까지**)
- 이 환경에서만 걸리는 문제를 만났다
- SPEC 이 애매해서 판단이 필요했다
- 되돌린 결정이 있다

**없으면 적지 않는다.** 잘 된 작업은 진행 기록에만 남긴다.

**같은 유형이 이미 한 번 적혀 있으면 또 추가하지 않는다. 두 번째면 기계가 막도록 옮긴다.**
옮긴 뒤 그 항목을 한 줄로 줄이고 `→ <어디>로 승격 (<날짜>)` 를 붙인다. 지우지는 않는다.

직접 고쳐도 되는 곳 — `spec-review` 체크리스트 · `npm run check:*` · `.claude/scripts/` 훅 ·
안내 문서. SPEC 과 CLAUDE.md 기존 규칙은 승인을 받는다.

## Step 6. PR 을 닫는 코멘트

```bash
node .claude/scripts/pr-update.mjs --pr <번호> --tier <등급> --step 7 --gate 2 --next "없음 — 병합"
node .claude/scripts/pr-update.mjs --pr <번호> --comment "### [7/7] 병합 완료
<무엇이 main 에 들어갔나 · 사용자가 어디서 확인하나>"
```

## 출력

```
✅ 한 줄   <비전문가 한 문장 — 무엇이 반영됐나>
💡 의미   <어디서 결과를 확인할 수 있는지>
🔧 기술 상세 (안 봐도 됨)
🔄 [7/7] tp-merge
   ├─ 미커밋 0 ✅ · 미푸시 0 ✅ · 검사 근거 확인 ✅
   ├─ gh pr ready → 초안 해제 · `[작업중]` 뗌
   ├─ 병합: PR #<번호> merged
   ├─ 작업방: 정리 또는 유지
   └─ 기록: progress ✅ · LEARNINGS <N건 또는 해당 없음>
```

## 실패 / 엣지

- **Step 1 에서 미커밋 발견** — 작업방 제거 전에 커밋·푸시. 계획·문서 소실이 1순위 위험
- **병합 충돌** — `git pull --rebase origin main`, 충돌 파일 표시, 사용자 개입
- **작업방 제거가 거부된다** — `--force` 를 붙이지 말고 Step 1 로 돌아가 남은 것을 본다
- **병합은 됐는데 브랜치 삭제가 실패** — 정상일 수 있다. `gh pr view --json state` 로 실제를 확인한다
