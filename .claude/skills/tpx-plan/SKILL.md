# /tpx-plan

체인 [3]. 할 일 하나 = TDD 사이클 하나. 0·1등급은 진입하지 않는다.

## 선행 읽기

**없음.** `/tpx` 가 실었고 `/tpx-spec` 이 장을 좁혀 읽었다. **재로드 금지.**

## 같이 쓰는 스킬

계획 단계가 가장 싼 자리다. 같은 일을 구현 때 하면 코드를 다시 쓴다.

| 스킬 | 여기서 하는 몫 |
|---|---|
| `superpowers:writing-plans` | 분해 craft — 무엇을 먼저 하면 나머지가 서는가 |
| `superpowers:test-driven-development` | 할 일 하나 = 사이클 하나로 모양 잡기 |
| `ponytail:ponytail` | **할 일 개수를 줄인다.** 세션 시작 훅으로 이미 켜져 있다 |

**서식은 이 문서가 이긴다.** `writing-plans` 가 다른 모양을 제안해도 아래 §2 를 쓴다 —
메타 세 칸이 [5] 의 묶음 계산 **유일한 입력**이라 바뀌면 구현이 깨진다.

## §1. 분해 규칙

1. **할 일 1개 = RED(실패 테스트) → GREEN(최소 코드) → REFACTOR** 한 사이클
2. **할 일 단위는 2~5분.** 크면 쪼개고 작으면 합친다
3. **메타 세 칸(`files` · `depends-on` · `검증`)은 필수.** 하나라도 빠지면 묶음 계산이 성립하지 않는다
4. LEARNINGS 발췌를 **근거로 첨부**한다 — 사고가 있던 자리는 그 사고를 재현하는 테스트가 RED 가 된다
5. **형식이 어긋나면 재호출하지 않고 그 자리에서 고친다.** 왕복만 늘고 결과가 같다
6. **`files` 가 이번 범위를 벗어나면 멈추지 말고 이유를 적는다.** 다른 갈래 폴더가 들어왔으면
   그 갈래에 넘길 항목으로 적을지, 이번에 같이 고칠지를 계획에 밝힌다 (CLAUDE.md §1.1 — 막는 장치는 없다).
   **구현 중에 늘어난 것은 계획에 못 넣는다** — 그건 게이트 2 요약에 싣는다. `spec-review` C1 이 둘 다 본다

## §2. 서식

```markdown
### 할 일 N. <한 줄>

- **RED** — <무엇을 단언하는 테스트. 왜 지금 실패하는지>
- **GREEN** — <통과시키는 최소 코드>
- **REFACTOR** — <정리할 것. 없으면 "없음">

**files**: <이 할 일이 새로 쓰거나 고치는 파일 전부. 저장소 루트 기준>
**depends-on**: [<선행 할 일 번호>] 또는 []
**검증**: <이 할 일만 확인하는 명령>
```

- `files` 가 겹치는 두 할 일은 `depends-on` 이 없어도 **자동으로 직렬화된다**
- `검증` 칸은 버리는 값이 아니다. [5] 가 이 명령을 하위 작업자에게 실어 보낸다.
  **비면 BLOCKED** 로 되돌린다 — 조용히 전량으로 대체하지 않는다

## §3. ★ SPEC 을 고치면 §2.7 을 할 일로 만든다

`/tpx-spec` 이 §2.7 동반 수정 목록을 넘겼으면 **그것을 할 일로 박는다.**
계획에 안 들어가면 구현이 빠뜨리고, 빠뜨린 것을 아무도 못 본다.

**2026-09-17~18 개정에서 「같은 규칙이 두 곳에서 다른 말을 하는」 일이 아홉 번 났고 전부 사후에 찾았다.**

최소 이 넷을 할 일로 만든다. 해당 없으면 「해당 없음」을 명시한다 — **절을 통째로 지우지 않는다.**

| 할 일 | 무엇 | 검증 |
|---|---|---|
| 같은 규칙 찾기 | 고친 문장의 **핵심 낱말로 `docs/spec/` 아래를 전부 grep.** 절 번호로 찾지 않는다 | `grep -rn "<낱말>" docs/spec/` 결과를 계획에 붙인다 |
| 색인 네 곳 | 장 목록 · 절 번호 표 · 표 주인 · **라우터 표** | `npm run check:spec` |
| SPEC 밖 여섯 곳 | WORKSTREAMS 킥오프 · spec-review·check:* · SETUP·HOOKS·DESIGN · WORKFLOW · design-mockup.html · **코드에 박힌 상수** | 곳마다 눈으로 |
| 숫자 빼기 | 손으로 적은 개수를 **정본 표 가리키기로** 바꾼다 | `check:spec` 이 분량을 센다 |

**라우터 표와 코드에 박힌 상수를 가장 잘 빠뜨린다.** 라우터 표는 *새 개념을 쓰려는 사람*이
길을 찾는 자리고, 코드 상수는 가장 늦게 드러난다.

판별식 `spec-change-companion` 이 **`docs/spec/**` 가 diff 에 있는데 계획에 이 절이 없으면**
빨간불을 낸다.

## §4. 할 일 수를 기록한다

```bash
grep -cE '^### 할 일 [0-9]+\.' docs/plans/<날짜>-<이름>.md
```

게이트 1 요약이 이 값을 읽는다. 0 이 나오면 서식이 깨진 것이다.

## §5. 계획 파일

`docs/plans/<YYYY-MM-DD>-<이름>.md` 에 쓴다. 머리에 **등급 행 필수** — 판별식이 읽는다.

```markdown
# <제목>

등급: <N> · 갈래: <A~F 또는 없음> · <날짜>

## 도메인 정리
<BC · 영향 표 · 관련 절. 하네스 작업이면 "제품 도메인 건드리지 않음">

## 왜
<한두 문단. 근거가 있으면 실측을 적는다>

## Plan
<할 일 N개 — §2 서식>

## SPEC 동반 수정 (§2.7)
<§3 의 할 일. 해당 없으면 "해당 없음 — SPEC 안 건드림">

## Plan 메타
할 일 N개 · 예상 묶음 N개 · 구현 규율: TDD · 추가 검증: <명령>

## 리뷰 결과
(계획 검토가 채운다)
```

## PR 갱신

```bash
node .claude/scripts/pr-update.mjs --pr <번호> --tier <등급> --step 3 --next "게이트 1"
node .claude/scripts/pr-update.mjs --pr <번호> --comment "### [3/7] 할 일 쪼개기 완료
...
**다음.** 계획 검토"
```

## 출력

```
🔄 [3/7] tpx-plan
   ├─ 할 일 N개 · 묶음 N개
   ├─ SPEC 동반 수정: 해당 없음 | 할 일 N개
   └─ 다음. 계획 검토
```

## 실패 / 엣지

- **할 일이 0개 또는 1개** — 명세가 모호하거나 분해가 과했다. `/tpx-spec` 으로 되돌린다
- **할 일이 10개 초과** — 작업이 크다. 「N개 PR 로 쪼갤까요?」 `AskUserQuestion`
- **`depends-on` 순환** — 그래프를 출력하고 그 자리에서 끊는다
- **다른 갈래 폴더가 필요하다** — 계약이나 API 로 접근할 수 있는지 먼저 본다.
  그래도 필요하면 이유를 계획에 적고 진행한다 (§1.1)
