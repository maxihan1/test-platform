## 바깥 렌즈가 잡은 것 — 자기검사가 아홉을 놓쳤다

### 심각 1 — 실패한 테스트에 「러너에 닿지 못했습니다」가 붙었다

어디: `apps/admin/src/web/RunResult.tsx:213` (고치기 전)
무엇: 사유를 고를 때 `status` 를 안 가렸다. 러너는 **`FAIL` 이 예외로 끝났을 때도 `error` 를 채운다**
(`packages/kit` 의 리포터). 그 영문 메시지가 `미실행사유()` 를 거쳐 「러너에 닿지 못했습니다」가 됐다.
왜 문제: **§8.3 이 「둘을 구분할 수 없으면 원인을 못 찾는다」고 한 자리를 오히려 뒤섞었다.**
Playwright 타임아웃으로 그냥 실패한 테스트가 러너 장애로 보인다 —
사람이 인프라를 뒤지다 테스트 자체가 깨진 것을 못 본다.
고친 것: `칸사유()` 가 **NA 항목만** 본다. 실측 확인 — 영문 예외로 실패한 행에는 사유가 안 붙고
진짜 미실행에만 붙는다.

### 심각 2 — 증적 문서가 「만드는 중입니다」에서 굳었다

어디: `apps/admin/src/web/RunResult.tsx:108` (고치기 전)
무엇: 서버는 `PENDING` 행을 즉시 돌려주고 뒤에서 만드는데, 2초 폴링이 **실행이 도는 중일 때만** 돌았다.
끝난 실행에서 증적을 만들면 `reload` 한 번으로 `PENDING` 을 받고 그 뒤로 안 묻는다.
왜 문제: 버튼이 비활성 「만드는 중입니다」로 굳고 완성된 문서도 안 뜬다.
**사람이 직접 새로고침해야 한다** — 그러라고 알려 주는 것도 없다.
**내 브라우저 확인이 이것을 못 본 이유** — 확인할 때 `location.reload()` 를 했다.
고친 것: `PENDING` 행이 있을 때도 묻는다. 실측 확인 — 새로고침 없이 9초 만에 목록으로 쌓였다.

### 나머지 일곱

| 무엇 | 안 고쳤으면 |
|---|---|

**내가 확인한 방법(새로고침) 때문에** 안 보였다. ① 에서 얻은 교훈이 그대로 반복됐다.

## 보안 검토 — 취약점 없음

3등급이 요구하는 렌즈다 (아래 「중대」가 지적한 것을 그 자리에서 돌렸다).

| 본 것 | 판정 |
|---|---|
| `viewer` 에게 `baseUrl` 노출 | **권한 경계 위반 아님** (확신도 9) — `LEFT JOIN user_service` 로 **배정받은 서비스만** 접는다. 같은 값이 `GET /api/runs` 로 이미 viewer 에게 나가고 §8.3 이 그것을 요구한다. 새로 드러나는 것은 「아직 실행되지 않은 env 의 주소」뿐 |
| 새 CTE 쿼리의 SQL injection | **없음** (확신도 10) — 전체가 상수 템플릿이고 변수는 `$1` 하나다. 웹훅 주소 컬럼은 SELECT 목록에 없다 |
| `--env <키>=<주소>` 파싱 | **문제 없음** (확신도 9) — 첫 `=` 에서만 가르고 빈 키·빈 값을 거른다. 값은 파라미터 바인딩된다 |
| 돌아갈 자리의 open redirect | **없음** (확신도 10) — `location.hash` 대입은 **현재 문서의 프래그먼트만** 바꾼다. `href`·`location.assign` 으로 흐르는 경로가 없다 |
| `한줄로()` 가 비밀값을 흘리나 | **안 흘린다** (확신도 9) — `fieldsOf()` 가 `********` 로 바꾼 **뒤에** 잇고 자른다. 자르기는 글자를 없애는 연산이라 가려진 값을 되살릴 수 없다 |
| 새 React 조각 | **없음** (확신도 9) — `dangerouslySetInnerHTML`·`innerHTML`·`eval` 없음. `target="_blank"` 에 `rel="noreferrer"` |

### ⚠️ 이번 범위 밖의 기존 문제 — 게이트 2 에서 판단해 주십시오

보안 렌즈가 `origin/main` 에 이미 있는 것을 하나 보고했다.

**`apps/admin/src/auth/gate.ts` 의 `닿는서비스()` 가 `GET /api/runs/:runId` 와
`/items/:historyId` 에 서비스 배정 검사를 걸지 않는다.** `?service=` 쿼리가 있거나
`POST /api/runs` 일 때만 서비스를 뽑기 때문이다 — **로그인한 사람이 번호만 바꿔
남의 서비스 실행 기록을 읽을 수 있다** (IDOR).

**이번 브랜치가 만든 것이 아니다.** 다만 이번 변경이 `RunItemSummary` 에 `params` 를 실어
**같은 요청 한 번으로 전 항목 입력값이 통째로** 나오게 했다. 렌즈는 「노출되는 데이터 종류는
그대로이고(전에도 `historyId` 로 상세를 하나씩 부르면 됐다) 편의만 늘어난 것」이라
이번 취약점으로 세지 않았다.

고칠 곳은 **WS-F(인증)** 다 — `닿는서비스()` 가 그 경로에서 run 의 `service_id` 를 조회해
배정과 대조하게 하면 된다. 이번 범위 밖이라 손대지 않았다.

**게이트 0 통과 시점은 선언을 다시 잴 자리**다 — 거기서 SPEC 변경이 확정되기 때문이다.
