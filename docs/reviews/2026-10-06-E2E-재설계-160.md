### H2 — 케이스가 직접 만든 창 · API 연결에는 모킹과 이어 주기가 안 따라가는데, 명세는 표본 하나로 「없다」고 적었다
어디:   `docs/spec/도메인/시나리오.md:113`(결정 6) · `:236`(한계 표 첫 줄) · `docs/spec/공통/3-공유계약.md:250`(③) ·
        `.claude/skills/tpx-cases/references/5-writing.md:158` · `:161` · `docs/LEARNINGS.md:33~36`
무엇:   결정 6 은 「케이스가 브라우저 창을 직접 새로 만들면 모킹이 안 따라간다. 2026-10-06 MKT · CDY 표본에 그런 케이스는 없다」라고 적었다.
        그런데 10-04 표본(`mkt-run-pr144`)에는 6건이 있다(MKT-FN-025 · 044 · 052 · 061 · 062 · 063, `page.context().browser().newContext`).
        이 PR 이 지운 WORKSTREAMS 줄도 「browser.newContext 6(명세 「없다」는 낡음)」이었다. 작성 규칙(5-writing.md 「다른 역할 계정」 · 「브라우저를 닫았다 열기 — 새 context 로 옮긴다」)이 이 모양을 계속 낳는다.
        10-06 표본의 API 연결 18건은 kit 이 건넨 도구로 만든 것이 아니다. `import { request as 요청도구 } from '@playwright/test'` 로 모듈에서 바로 만든다.
        공유계약 ③ 은 「케이스에 건네는 API 도구를 감싼다」인데, 건네지 않은 모듈 값을 어떻게 감싸는지가 없다. 한계 표는 실측 전에 ✅ 를 매겼고 실측이 실패하면 어떻게 할지도 적지 않았다.
        이 PR 이 LEARNINGS 에 남긴 교훈은 「작성마다 갈리는 무늬는 양쪽 다 견디는 장치로 푼다」다. 창을 직접 만드는 길만 10-06 표본 하나에 기댔다.
왜 문제: 모킹 구간 안의 케이스가 새 창이나 새 연결로 결제 같은 요청을 보내면 진짜 서버로 간다. 결정 6 이 「가장 나쁜 실패」라 부른 바로 그 경우다.
        지금 경고(`usesRequest`, `apps/admin/src/catalog/steps.ts:201~221`)도 `요청도구.newContext` 와 `browser().newContext` 는 못 본다.
        명세는 감싸기가 들어가면 그 경고마저 뺀다. 그래서 일부만 감싸진 채 들어가면 아무 표시도 남지 않는다.
고칠 곳: 이 PR(명세). 한계 표에 「창을 직접 만든다」 · 「모듈에서 API 연결을 직접 만든다」를 따로 두고 장치를 정한다.
        예를 들어 러너가 쥔 Browser 인스턴스의 `newContext` 와 `@playwright/test` 의 `request` 값을 감싸 모킹 · 이어 주기를 다시 건다. 러너 이미지에서 안 되면 소스 판별로 조립 화면에 「모킹되지 않음」을 띄운다.
        `usesRequest` 를 빼는 조건은 「직접 만든 창 · 연결까지 감싸지는 것을 러너 이미지에서 확인한 뒤」로 좁힌다. 결정 6 의 「표본에 없다」는 두 표본의 숫자로 고친다. 어느 장치를 쓸지는 사용자가 고른다.

### H2 — 저장값으로 채운 비밀값과 값 꽂기로 넣은 값(`bound`)을 가리는 규칙이 없다
어디:   `docs/spec/도메인/시나리오.md:397`(§7 「시험 실행 규칙」 「비밀값을 가린다」) · `:360`(「부품 행 스냅샷의 입력값」 · 시험 실행도 같은 순서) ·
        §7 `GET /api/runs/:runId/scenario` 의 `bound` · `docs/spec/도메인/리포팅.md:213`(§8.4 「이어 주기」의 값 꽂기 줄)
무엇:   시험 실행은 「그 조립의 케이스 부품 `params` · `expected` 중 비밀 칸 값」을 가린다. 이 PR 은 시험 실행도 조립에 없는 칸을 저장값으로 채워 러너에 보내게 했다.
        조립에서 비워 둔 비밀번호는 조립 본문에 없으니 가릴 목록에 안 들어간다. 지금 코드(`apps/admin/src/scenario/trial.ts:100~105`)도 조립 본문의 `p.params` 로 목록을 만든다.
        값 꽂기로 넣은 값은 러너가 앞 응답에서 꺼내 오므로 admin 이 미리 알 수 없다. `bound` 를 가린다는 말은 결과 통로에도, 화면(§8.11)에도, 증적(§8.4)에도 없다.
왜 문제: 저장값을 쓰게 한 까닭이 「부품마다 테스트 계정 비밀번호를 다시 적지 않으려고」였다. 바로 그 비밀번호가 시험 결과의 오류 글이나 판정 글에 원문으로 실릴 수 있다.
        저장값의 비밀 칸은 저장값 통로도 원문을 돌려주지 않는다(도메인/실행 §8.2). 시험 실행이 그 원문이 새는 길이 된다.
        비밀 칸에 값 꽂기를 걸면 `bound` 와 증적의 「값 꽂기 · <칸> = <값>」 줄도 원문 그대로다.
고칠 곳: 이 PR(명세). 「비밀값을 가린다」를 「채운 뒤의 `params` · `expected` 와 `bound` 의 비밀 칸」으로 고친다.
        리포팅 §8.4 이어 주기 줄과 §8.11 결과에 「비밀 칸에 꽂은 값은 `********`(공통/2-명세선언 §4.1)」을 적고, WORKSTREAMS ⓒ 할 일에 싣는다.

### H2 — 미확정 부품이 든 실행이 목록 집계에서는 그냥 통과로 셈해진다
어디:   `docs/spec/도메인/시나리오.md:371`(§7 「판정 접기」) · `:374`(「실행 목록의 E2E 탭」 `summary.allPass`) · §7 목록 `lastRun.verdict` · §8.11 목록 ↔
        `docs/spec/도메인/실행.md:66~75`(§3.2 「미확정 항목은 따로 센다」) · CLAUDE.md 「저장소에 담아 둔 남의 스킬」 절의 미확정 꼬리표 문단
무엇:   결정 12 는 「시나리오가 초록이어도 정식 통과로 굳지 않게 표시가 따라간다」라 하고, 표시는 조립 칩 · 결과 머리 · 증적에만 붙였다.
        판정 접기는 PASS · FAIL · NA 셋뿐이라 미확정 부품이 섞여도 PASS 가 된다. E2E 탭의 `allPass` 와 시나리오 목록의 마지막 결과는 그 PASS 를 그대로 센다.
        케이스 실행은 「통과·실패·미실행은 확정 항목만 센다」로 미확정을 따로 묶는다.
왜 문제: 사람은 목록과 탭 숫자를 먼저 본다. 미확정이 섞인 초록이 확정 초록과 같은 칸에 들어가면, CLAUDE.md 가 꼬리표로 막으려 한 「버그가 정식 초록으로 굳는」 일이 E2E 쪽에서 생긴다.
고칠 곳: 이 PR(명세) — 게이트 2 에서 정한다. E2E 탭 집계 · 목록 줄 · `lastRun` 에 미확정 여부를 싣는지(예: `lastRun.unconfirmed` · 집계에서 따로 셈) 정해 §7 「판정 접기」 곁에 적는다.
        싣지 않기로 하면 그 까닭을 결정 12 「미확정 · 보류 케이스」에 적는다.

- **결정 8 · 실행 §8.2 · SPEC 색인** — 「조립에 없는 칸만 저장값」이 세 곳에서 같은 말이고, 순서의 정본을 시나리오 §3.7 「부품 입력값을 채우는 순서」 한 곳으로 가리킨다. 「부품은 저장값을 안 쓴다」 옛 말은 안 남았다
