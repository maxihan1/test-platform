### C2 — 리포팅이 실행 컨텍스트의 모듈을 직접 import 한다

어디:   `apps/admin/src/reporting/generate.ts:9` — `import { enqueue } from '../execution/dispatcher.js';`
무엇:   체크리스트 C2 는 Catalog · Execution · Reporting 이 서로의 모듈을 **직접 import 하지 않을 것**을 요구한다.
        PDF 변환의 Chromium 동시 기동을 막으려고 실행의 대기줄을 그대로 가져다 쓴다.
왜 문제: 실행의 대기줄 상한(`EXECUTION_CONCURRENCY`, 기본 2)이 이제 증적 생성과 **한 줄을 나눠 쓴다.**
        실행이 2개 도는 동안 증적 만들기가 뒤에서 기다리고, 반대로 증적 PDF 가 줄을 잡으면 실행이 밀린다.
        나중에 실행 쪽이 대기줄을 큐로 갈아 끼울 때(§5.3 이음새) 리포팅이 같이 깨진다.
판단:   **계획에 적혀 있고 게이트 1 에서 승인된 결정이다** —
        `docs/plans/2026-09-19-ws-d-reporting.md:154~156` 이 「`enqueue()` 재사용 · import 한 줄이고
        그 파일을 고치지 않는다」로 명시했고, `plan-eng-review` 주의 5 가 그렇게 하라고 지적했다.
        같은 파일 `generate.ts:23` 은 `artifactsDir()` 에 대해 정반대로 「execution 의 같은 함수를
        가져다 쓰지 않는다 — 갈래 사이에 의존을 만들면 한쪽을 고칠 때 남이 깨진다」고 적고 있다.
        **한 파일 안에서 같은 질문에 두 번 다르게 답했다.**
고칠 곳: 셋 중 하나 — ① `enqueue` 를 컨텍스트 밖 공용 자리로 옮긴다 ② 리포팅이 자기 대기줄을 하나 갖는다
        ③ 「브라우저 기동 대기줄은 공유한다」를 SPEC 이나 체크리스트 C2 의 예외로 적는다.
        **어느 쪽이든 지금은 체크리스트가 금지한 것을 계획이 허용한 상태이고, 둘이 어긋나 있다.**

### §4.1 — 박제 이전 행의 비밀값이 평문으로 증적에 나간다

어디:   `apps/admin/src/reporting/collect.ts:135~151` (`toFields()`) ·
        단언으로 못 박힌 자리 `apps/admin/src/reporting/collect.test.ts:313~317`
무엇:   §4.1 은 「비밀값 칸은 **어느 형식에서든** `********`」라고 못 박는다.
        마스킹 판정은 `param_schema.properties.<키>.secret === true` 하나에만 걸려 있다.
        `param_schema` 가 `'{}'` 인 박제 이전 행은 그 정보가 없어 **값을 그대로 찍는다.**
        검사 파일이 이 동작을 「키 이름을 쓰되 값은 손대지 않는다」로 단언해 두었다.
왜 문제: 마이그레이션(`20260917000001`) 이전에 쌓인 실행의 증적을 오늘 뽑으면
        `password` 칸이 PDF · 엑셀 · HTML 에 평문으로 박힌다. 그 문서가 검수처로 나간다.
        §3.1 K9 가 스캔 때 비밀값 이름에 꼬리표를 강제하므로 **플랫폼은 이미 이름 목록을 갖고 있다**
        (`apps/admin/src/catalog/rules.ts:172` 의 `SECRET_NAMES`). 라벨은 지어낼 수 없어도 마스킹은 할 수 있다.
        지금은 「모르면 가린다」가 아니라 「모르면 보여준다」로 되어 있다.
고칠 곳: WS-D. 스키마가 비면 칸 이름으로라도 가리거나(`SECRET_NAMES` 재사용),
        아니면 값 자체를 `기록 없음`으로 적는다. **어느 쪽이든 평문보다 낫다.**
        박제 이전 행이 이 배포의 DB 에 실제로 없다면 위험은 이론이지만, 검사 단언이 그 동작을
        「맞다」고 고정해 두었으므로 나중에 누가 고치려 할 때 빨간불이 난다.

### §8.3 — 미실행 사유 문구가 SPEC 이 적은 낱말과 다르다

어디:   `apps/admin/src/reporting/collect.ts:124` · `:181` — `실행이 멈춰 돌지 못했습니다`
무엇:   `docs/spec/도메인/실행.md` §8.3 은 사람이 멈춘 항목의 사유를 **`사용자가 멈춤`** 이라고 적고,
        러너 미도달(`러너에 닿지 못했습니다`)과 「같은 자리에 다른 문장」이어야 한다고 못 박는다.
왜 문제: 화면(§8.3)과 문서(§8.4)가 같은 항목에 다른 문장을 쓰게 된다.
        지금은 드러나지 않는다 — `apps/admin/src/web/RunResult.tsx:76` 이 아직 사유를 안 그린다.
        WS-E 가 §8.3 대로 `사용자가 멈춤`을 그리는 날, 같은 항목이 화면과 증적에서 다르게 읽힌다.
판단:   **코드가 든 근거는 사실이다.** `apps/admin/src/execution/store.ts:296 · 318 · 349` 를 확인했다 —
        `abortRun()`(사람이 멈춤)과 `recoverRunning()`(서버가 죽어 끊김)이 **둘 다** `error.message = 'ABORTED'`
        를 쓴다. DB 가 두 원인을 구분하지 못하므로 `사용자가 멈춤`이라고 단정하면 거짓이 될 수 있다.
        **구현이 옳고 SPEC 의 낱말이 지금 상태를 못 따라온 쪽에 가깝다.**
고칠 곳: 정본을 한 곳으로 정한다 — ① §8.3 의 `사용자가 멈춤`을 구분 가능한 경우로 좁혀 다시 적거나
        ② WS-B 가 두 경로에 다른 표를 남기게 해서 원래 낱말을 살린다. **WS-D 범위 밖이다.**
