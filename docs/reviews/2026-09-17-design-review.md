## 확정된 결정 6건

### D1. 서비스는 「골라서 그 안에서 일한다」

한 번에 한 서비스만 본다. 맨 위에서 바꾼다. 여러 서비스가 한 목록에 섞이지 않는다.

```
┌─────────────────────────────────────┐
│ ▼ 결제 서비스      김철수 · 로그아웃 │  ← 여기서 서비스를 바꾼다
├─────────────────────────────────────┤
│ 케이스 목록                          │
│ PAY-001  결제하면 주문이 생긴다  통과 │
│ PAY-002  카드가 거절되면 안내   실패 │
└─────────────────────────────────────┘
```

**왜** — 지금 §8 의 화면 명세가 그대로 살아남는다. 「엉뚱한 서비스에서 실행을 누르는 사고」를 막던 상단 띠의 역할도 그대로다.
**비용** — 세 서비스를 맡은 사람이 「오늘 다 괜찮나」를 보려면 세 번 전환해야 한다. 그 갈증은 Grafana 쪽에서 푼다.

### D2. 케이스 목록이 집. 위에 자리 셋. 도는 중이면 한 줄 알린다

```
│  케이스   실행 기록   그래프 ↗  │  ← 밑줄 = 지금 여기
├─────────────────────────────────┤
│ ▶ RUN 2113 이 도는 중입니다 12/40│  ← 도는 게 있을 때만
```

**왜** — 이 도구의 일은 「무엇을 돌릴까」에서 시작한다. 다만 한 번 돌리면 최악 50분이라 자리를 떴다 돌아오는 진입이 흔하다. 알림 줄 하나로 두 상황을 다 받는다.

**부수 발견** — **`실행 기록 목록` 화면이 설계서 §8 에 없다.** 코드에는 있다(`apps/admin/src/web/RunList.tsx`). 명세 없이 만들어진 화면이므로 §8 에 절을 새로 쓴다.

### D3. 빈 목록을 세 갈래로 가른다

지금은 0건이면 언제나 `찾는 케이스가 없습니다.` 하나다 (`CaseList.tsx:108`). 검색한 적 없는 사람에게도 「찾는」이라고 말한다.

| 왜 비었나 | 무엇을 보여주나 | 다음 행동 |
|----------|---------------|----------|
| 아직 한 번도 안 불러옴 | `아직 케이스를 불러오지 않았습니다` + 설명 두 줄 | 가운데 큰 `케이스 불러오기` 버튼 |
| 불러왔는데 0건 | `불러왔지만 케이스가 하나도 없습니다` | `규칙에 걸린 파일 N건 · 사유 보기` |
| 검색·필터에 안 걸림 | `'장바구니' 에 맞는 케이스가 없습니다` | `검색 지우기` |

**왜** — 첫째 줄이 이 도구를 처음 켠 사람이 만나는 화면이다. 여기서 막히면 도구가 고장난 것처럼 보인다.

### D4. 증적 문서는 새 창으로 열어서 보고, 거기서 저장한다

```
│  증적 문서                       │
│  · 9월 15일 17:22 만듦  [열기 ↗] │
│  · 9월 15일 17:20 만듦  [열기 ↗] │
│                  [다시 만들기]     │
```

**왜** — 화면의 `항목 상세`는 항목 **한 건**이고 증적 문서는 실행 **전체 한 부**다. 지금 명세대로면 사람은 검수처에 내는 문서 전체를 한 번도 못 보고 낸다. 브라우저가 이미 문서를 보여주는 기능을 갖고 있으므로 새로 만들 것이 없다.
**같이 정해진 것** — 만든 것이 여러 개면 만든 시각과 함께 줄로 쌓인다. 파일 이름에 `(1)`, `(2)` 가 붙어 어느 것이 최신인지 모르게 되는 일이 없다.

### D5. 서비스 색은 맨 위 띠 한 줄에서만

디자인 기준 문서의 금지 목록에 **「판정 외의 색 사용」** 이 있다. 서비스마다 색을 주면 이 약속이 깨진다.

**결정** — 띠에만 서비스 색을 허용하고 본문은 판정 색만 쓴다. 기준 문서에 **「맨 위 띠는 예외」** 를 한 줄 적는다.
**왜** — D1 으로 한 화면에 두 서비스가 같이 나올 일이 없어졌다. 그러면 본문에 서비스 색이 있을 이유도 없다. 본문에서 색을 보면 언제나 판정이다.

### D6. 휴대폰으로 하는 일은 「끝났나 보기」 하나

| 좁은 화면에서 제대로 | 책상에서만 |
|---|---|
| 실행 기록 목록 · 실행 결과 보기 | 입력 폼 채우기 · 증적 문서 보기 · 실패 지점 코드 보기 |

**왜** — 규칙은 기준 문서에 있는데 설계서에는 없고, 만든 세션도 「눈으로 확인하지 못했다」고 남겼다. 확인해야 할 곳을 좁혀야 실제로 확인이 끝난다. 증적 문서는 A4 고정폭이라 애초에 좁은 화면 대상이 아니다.
**따라오는 것** — 손가락으로 누르는 영역 최소 크기(44px)는 **실행 기록·실행 결과 두 화면에만** 건다.

## 손댈 것이 없는 축 — 흔한 AI 디자인 위험 9/10

기준 문서의 「금지」 목록이 요즘 AI 가 만드는 화면의 특징을 하나씩 반대로 막아 놓았다.

| 흔한 AI 디자인 | 이 프로젝트 |
|---|---|
| 보라색 그라데이션 배경 | 그라데이션 금지 |
| 아이콘을 원에 넣은 3단 카드 | 카드 대신 괘선. 아이콘으로 판정 표시 금지 |
| 모든 요소에 같은 둥근 모서리 | 컨트롤 2px만 |
| 알록달록한 색 | 판정 외의 색 사용 금지 |
| 시스템 기본 글꼴 | Pretendard 지정 |

이 축은 이미 10점에 가깝다. 위 5번(글꼴 외부 주소)만 확인하면 된다.

## 검토 범위 밖

- **실제 화면을 열어서 보는 검사** — `/design-review` 가 따로 담당한다. 지금은 화면 빌드 단계가 없어 컨테이너로 화면이 안 뜬다(기술 검토에서 찾은 문제). 그것부터 고쳐야 한다
- **AI 목업 생성** — 기준 문서가 이미 확고하고, 생성기는 그 반대 방향(둥근 카드·그라데이션)을 만들어 낸다. 대신 이 문서의 글자 그림으로 결정했다
- **권한별로 화면이 어떻게 달라지나** — 서비스 통합이 설계서에 반영된 뒤에 본다
- **Grafana 대시보드 구성** — 별도 도구라 이 플랫폼 화면 규칙 밖이다
