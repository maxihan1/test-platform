# 발표 스크립트 대조 — 추가해야 할 기능 (2026-09-16)

토스페이먼츠 테스트 자동화 플랫폼 발표 스크립트를 `docs/SPEC.md`와 대조해,
**SPEC에 없어서 추가를 검토해야 하는 것**을 추린 결과다.

스크립트에서 기능 49건을 뽑아 한 건씩 SPEC·킥오프(`WORKSTREAMS.md`)·목업(`design-mockup.html`)·코드와 맞댔고,
살아남은 후보는 다시 "이 규모에서도 정말 필요한가"를 반박해 걸러냈다. 반박에 실패한 것만 남겼다.

이 문서는 **무엇을 넣을지 고르기 위한 것**이지 구현 지시가 아니다.
계약 변경이 필요한 항목은 CLAUDE.md §1.2 절차가 먼저다.

| 판정 | 건수 |
|---|---|
| 이미 있음 (수단이 달라도 목적 달성) | 29 |
| 의도적 제외 (SPEC §1 명시) | 4 |
| 부분만 있음 · 없음 → 후보 | 16 |
| **반박 후 남은 것** | **지금 11 · 나중 7 · 불필요 8** |

## 1. 지금 — 승인이 필요한 3건

늦출수록 비싸진다. WS-E(화면)·WS-D(리포팅)가 시작되기 전이 마지막 결정 시점이다.

### 1-1. 민감 파라미터 마스킹 — **2026-09-16 결정됨**

**무엇이 없는가.** 어느 입력 칸이 비밀값인지 시스템이 아는 방법이 없다.
SPEC §8.4의 증적 포맷은 `비밀번호    ********` 로 그려 놓았지만, 그 `********` 를 만드는 규칙이 어디에도 없다.
`run_item.params` 는 실행 시점 값을 JSONB 스냅샷으로 영구 보존하므로(§3.2 불변식) 평문이 그대로 남는다.

**왜 지금인가.** `docs/SETUP.md:159` 가 이 결정을 "민감 파라미터 마스킹 규칙 — WS-E 시작 전까지"로 미뤄 뒀고,
WS-E가 다음 차례다. 한 번 평문으로 저장된 실행 기록은 되돌릴 수 없다.

**결정 (사용자 승인).** **저장 시점에 마스킹한다.** 화면 표시가 아니라 DB에 넣기 전에 바꾼다.

- `defineCase` 의 params 스키마에 "이건 비밀값" 표시를 하나 더한다 (§4 K4에 규칙 추가)
- `createRun` 이 `run_item` 에 넣기 직전 그 키만 `****` 로 치환한다. 치환 자리는 한 곳이면 된다
- 암호화·볼트는 만들지 않는다

| 담당 | 공수 | 계약 영향 |
|---|---|---|
| WS-C(선언 규칙) + WS-B(저장 시 치환) | S | DB·API 무변경. kit의 케이스 선언 규칙(§4 K4)이 바뀌므로 §1.2 절차 필요 |

**확인 방법.** 비밀번호를 쓰는 케이스를 한 번 실행한 뒤,
결과 상세의 "입력값" 칸과 뽑은 증적 PDF 양쪽에서 비밀번호 자리가 `****` 로 보이면 정상이다.

### 1-2. 중단된 실행 복구 (`ABORTED`)

**무엇이 없는가.** `ABORTED` 가 마이그레이션 주석에만 있고 **쓰는 코드가 0건**이다
(`db/migrations/20260916000001_init.sql:35` 외 전 저장소 검색 결과 없음).
대기줄이 모듈 전역 메모리에 있어서(`apps/admin/src/execution/dispatcher.ts`),
admin이 재기동되거나 러너가 `mem_limit 4g` 에 걸려 죽으면 남은 항목은 영영 실행되지 않고
`run_item.finished_at` 은 NULL, `test_run.status` 는 `RUNNING` 으로 고착된다. §3.2 불변식이 깨진 채 남는다.

**왜 지금인가.** `docs/SETUP.md:160` 이 이 결정을 "`test_run.ABORTED` 를 누가 언제 넣는가 — WS-B 시작 전까지"로
적어 뒀는데 **WS-B는 이미 끝났다.** 기한이 지난 미결 항목이다.
그리고 이게 없으면 아래 2-3(진행 표시)이 영원히 도는 로딩 화면을 그리게 된다. 순서가 뒤집히면 안 된다.

**형태.** admin 부팅 직후 SQL 한 번. `status='RUNNING'` 인 `test_run` 의 미완 `run_item` 을
`status='NA'`, `error='INTERRUPTED'` 로 닫고 그 `test_run` 을 `ABORTED` 로 바꾼다.
프로세스가 죽었으면 진행 중이던 실행은 정의상 전부 남의 것이므로 조건은 이 하나면 된다.
`docker-compose.yml` 에 재시작 정책 한 줄을 같이 넣는다.

| 담당 | 공수 | 계약 영향 |
|---|---|---|
| WS-B | S | DB 구조·API 응답 무변경. `docker-compose.yml` 한 줄만 잠긴 파일이라 §1.2 보고 필요 |

**확인 방법.** 실행을 시작한 직후 `docker compose restart admin` 을 치고 실행 상세를 새로 고친다.
상태가 "중단됨"으로 바뀌고 진행 표시가 멈추면 정상이다.

### 1-3. 대상 환경 전환

**무엇이 없는가.** `test_run.env` 컬럼이 `DEFAULT 'demo'` 로 있는데 **INSERT 에 없다.**
읽기만 하고(`apps/admin/src/execution/queries.ts:57,85`) 채울 길이 없는 컬럼이다.
`playwright.config.ts` 에는 `baseURL` 자체가 없어 대상 주소가 각 테스트 파일 안에 박혀 있다.

**왜 지금인가.** 핵심 가치 1번이 "코드 재배포 없이 파라미터·기대값 변경"인데
가장 자주 바뀌는 값인 대상 서버 주소만 예외로 남았다.
데모 사이트를 떠나 실제 대상에 붙이는 순간 같은 케이스를 다른 환경에 돌릴 방법이 없다.
WS-C가 다시 들어가야 하는 작업이라 늦을수록 조율 비용이 크다.

**형태.** `POST /api/runs` 에 `env` 한 칸(기본 `'demo'`)을 받아 `test_run.env` 에 그대로 넣고,
`ExecuteRequest` 에 `baseUrl` 을 실어 러너가 `PLATFORM_BASE_URL` 환경변수로 넘긴다.
`playwright.config.ts` 는 `use: { baseURL: process.env.PLATFORM_BASE_URL }` 한 줄.
환경 목록 테이블은 만들지 않는다 — 문자열 한 칸이면 된다.

| 담당 | 공수 | 계약 영향 |
|---|---|---|
| WS-B(요청·저장) + WS-C(타입·러너 주입) | M | `packages/kit/src/types.ts`(잠김) + Admin API + 러너 HTTP. §1.2 절차가 선행해야 한다 |

**확인 방법.** 실행 설정 화면에서 환경을 골라 실행한 뒤,
결과 화면 머리말과 증적 문서의 환경 칸이 고른 값으로 뜨면 정상이다.

## 2. 지금 — 화면 안에서 끝나는 6건 (계약 변경 없음)

전부 WS-E 소유 폴더(`apps/admin/src/web/`) 안에서 끝나고 서버 코드와 잠긴 파일을 건드리지 않는다.
다만 SPEC §8 화면 절에 각 한 줄씩 추가하는 문서 수정은 필요하다.

### 2-1. 케이스 목록 검색창 ★ 가장 놓치기 쉬운 것

SPEC §8.1의 칸은 `TC ID | 케이스명(문장형) | 지원 환경 | 마지막 결과 | [실행]` 다섯 개이고,
목록 위에 두는 것은 "다시 스캔하기" 버튼과 마지막 스캔 결과뿐이다. WS-E 킥오프 1번도 같다. **검색창이 없다.**

`GET /api/catalog/cases?q=` 는 이미 만들어져 있다(WS-A 완료). 누를 자리만 없다.
**자연어 검색은 SPEC §1 핵심 가치 2위**인데, 지금 명세대로 만들면 WS-E는 검색창을 만들지 않는다.

> 주의 — `docs/design-mockup.html:151` 의 `케이스 이름이나 ID로 찾기` 입력칸은
> 화면 1 "실행 결과 목록"(같은 파일 132행)의 툴바이지 케이스 목록의 것이 아니다.

- **담당 / 공수** — WS-E / S
- **확인 방법** — 케이스 목록에서 "장바구니"를 치면 해당 케이스만 남는다

### 2-2. 증적 문서 생성·다운로드 버튼 ★

SPEC §8의 화면 4절(8.1~8.4) 어디에도 증적 관련 버튼이 없고,
WS-E 킥오프의 "만들 것" 4개에도 증적이 빠져 있다.
목업의 액션도 "이 케이스 이력 보기"·"같은 값으로 다시 실행" 둘뿐이다(`design-mockup.html:296-297`).

그런데 SPEC §11 Phase 1 완료 기준에는 "증적 문서 PDF가 §8.4 포맷으로 생성됨"이 있다.
지금 명세대로 만들면 `POST /api/runs/:runId/evidence` 를 **터미널에서만 부를 수 있고**,
"코드를 몰라도 쓴다"는 §1 제품 정의가 마지막 한 걸음에서 깨진다.

- **담당 / 공수** — WS-E / S
- **확인 방법** — 실행 상세에서 [증적 문서 만들기]를 누르면 PDF가 받아진다

### 2-3. 실행 진행 상황 표시

케이스 1건 기본 제한시간이 300000ms(5분)이고 동시 실행이 2 고정이라,
데모 10건 × 환경 2개 = 20항목이면 최악 50분 동안 화면이 아무것도 못 보여준다.

**서버는 이미 다 내려준다** — `GET /api/runs/:runId` 의 `counts: {total, pass, fail, na, running}`
(`apps/admin/src/execution/queries.ts:56-62`). 새 기능이 아니라 **미연결 상태**다.

실행 버튼이 받은 `runId` 로 결과 화면(§8.3)으로 바로 이동하고,
2초 간격으로 다시 물어 "20건 중 12건 완료"와 진행바를 그린다.
`status` 가 `FINISHED` 또는 `ABORTED` 가 되면 멈춘다. 새 엔드포인트·실시간 통신은 쓰지 않는다.

> **함정 하나.** 아직 안 끝난 항목도 `status` 는 `NA` 로 내려온다.
> 화면이 `finishedAt` 이 비었는지를 같이 보지 않으면 실행하자마자 전부 빨간 실패로 보인다.
> `ItemStatus` 타입은 3종 그대로 두면 된다 — 타입 변경은 필요 없다.

- **담당 / 공수** — WS-E / S (서버 작업 0건)
- **확인 방법** — 케이스 2건을 환경 2개로 실행하면 "4건 중 0건 완료"가 뜨고 숫자가 저절로 올라간다

### 2-4. 케이스 다중 선택 후 일괄 실행

케이스 목록에 체크박스가 0건이라 모든 실행이 1건짜리가 된다.
`POST /api/runs` 의 `items[]` 는 이미 배열을 받는다(`apps/admin/src/execution/routes.ts:29-40`).

이게 처리량 문제가 아닌 이유 — **증적 문서는 실행(run) 단위로 1부**다(§8.4).
다중 선택이 없으면 증적이 케이스당 1부씩 쪼개지고 집계 숫자가 영원히 1이 된다.
대량 실행 대응 장치가 아니라 **핵심 가치 4번(증적 자동 생성)의 성립 조건**이다.

목록 왼쪽에 체크박스 열, 상단에 `[선택한 N건 실행]` 버튼,
다음 화면에서 이미 만들 입력 폼을 선택한 수만큼 반복해 쌓고 한 번에 제출한다.

> **함정 하나.** 데모 10건 중 여러 건이 입력값을 필수로 쓴다.
> "체크만 하고 바로 실행" 지름길을 만들면 그 케이스들이 원인 모를 실패로 떨어진다.
> 반드시 케이스마다 폼을 띄우고 제출 전에 막아야 한다.

- **담당 / 공수** — WS-E / S
- **확인 방법** — 2건을 체크하고 실행 → 입력 화면에 폼이 2개 뜨고, 결과에 실행 번호 하나 아래 2행이 나란히 뜬다

### 2-5. 실행자 이름 입력 칸

`triggeredBy` 를 적어 보낼 자리가 화면에 없어 모든 증적의 실행자가 `'admin'` 한 값이 된다
(`apps/admin/src/execution/routes.ts:27-28` 의 기본값).
목업(`design-mockup.html:137`)에는 "실행자 maxi" **표시** 자리만 있고 입력 칸이 없다.

실행 설정 폼 맨 위에 텍스트 칸 하나. 비우면 필드를 통째로 빼서 기존 기본값이 그대로 남는다(계약 무변경).

> 인증·계정·세션은 **넣지 않는다.** 단일 서버·1인 운영·대상이 공개 데모 사이트라 인증이 막을 위협이 없고,
> SPEC 전체에 인증 언급이 0건이라 넣으려면 구현이 아니라 SPEC 변경 안건이다.

- **담당 / 공수** — WS-E / S

### 2-6. 같은 값으로 다시 실행 · 케이스 절차 미리보기

| 항목 | 한 줄 | 공수 |
|---|---|---|
| 같은 값으로 다시 실행 | 목업(`:296-297`)에는 버튼이 있는데 SPEC §8.4 본문에 없다. `GET /api/runs/:runId/items/:historyId` 가 실행 시점 스냅샷을 이미 주므로 그대로 `POST /api/runs` 에 실으면 끝이다. **문서만 맞추면 된다** | S |
| 케이스 절차 미리보기 | 한 번도 안 돌린 케이스는 무슨 절차로 무엇을 검증하는지 볼 수 없다. `test_case` 에는 이름·사전조건·스키마만 있고 절차·판정 문장은 실행해야 `run_item_step` 에 생긴다. 그 케이스의 마지막 실행 절차를 "지난 실행의 시험 절차"로 그대로 보여준다 | S |

- **담당** — WS-E (둘 다 기존 API만 쓴다)

| 증적 문서 합치기 | 일부만 재실행하면 제출물이 2부로 쪼개져 사람이 손으로 합치게 된다. 다만 실제 실행 표본이 아직 없다 | 실제 검수 제출 건이 생기고 "전 항목 1부" 요구가 확인될 때 |
| 완료 알림(웹훅) | 화면 앞에 있는 사람은 2-3 진행 표시로 충분하다 | 정기 실행이 붙는 순간. 새벽 결과를 아무도 안 보면 안 돌린 것과 같다 |
| artifacts 보관 기간 | §4가 "디스크가 금방 찬다"를 근거로 자동 캡처를 실패 스텝으로 제한해 놓고, 쌓인 것을 지우는 규칙은 없다 | 디스크 사용량이 눈에 띄거나 trace 보관을 정할 때. 두 건은 같이 결정한다 |
| Playwright trace 보관 | `playwright.config.ts:12` 가 `reporter: 'line'` 이고 trace·video 설정이 없다. 실패 재현 수단이 스크린샷·줄번호뿐이다 | 스크린샷으로 원인이 안 잡히는 실패가 반복될 때. 보관 기간과 함께 |
| 러너 이미지 재빌드 절차 | 테스트가 새 패키지를 쓰면 `git pull` 만으로는 절대 안 도는데 절차·담당자가 문서에 없다. CI의 `check:tests` 는 호스트에서 통과하고 러너에서만 깨져 증상이 조용하다 | 테스트가 새 패키지를 처음 쓸 때. 지금은 문서 한 줄이면 된다 |
| tcId 도메인별 현황 패널 | 데모 케이스가 전부 `DEMO-` 접두사라 지금 붙이면 표에 한 줄만 뜬다 | 실제 케이스(`AUTH`·`PROD` 등)가 생긴 뒤. §8.5가 패널을 4종으로 못박아 SPEC 변경 제안이 먼저다 |
| 실행 시점 코드 버전 기록 | 증적이 주장하는 것은 "이 코드 버전"이 아니라 "이 사전조건·입력·절차·판정으로 이렇게 나왔다"이고, 그 명세는 이미 스냅샷으로 박제된다 | 같은 케이스가 코드 변경 전후로 다르게 나와 원인을 못 가릴 때 |

## 5. 이 규모엔 불필요 (8건) — 왜 안 하는지를 남긴다

| 항목 | 왜 불필요한가 |
|---|---|
| 메시지 큐 · 러너 수평 확장 · S3 · 배포 서버 | SPEC §1이 "대량 실행 대응 장치이며 현재 규모에서는 불필요"로 이미 명시. §5.3에 이음새가 남아 있다 |
| 실행 요청 건수 상한 | `dispatcher.ts` 의 모듈 전역 대기줄이 동시 실행을 2로 이미 묶고, 화면이 만들 수 있는 최대치가 20건이다. 상한을 넣어도 진짜 통증(진행 표시 없음)은 그대로 남는다 |
| 인증 · 세션 · API 키 | 단일 서버·1인 운영·대상이 공개 데모 사이트라 인증이 막을 위협이 없다. 실행자 이름 칸(2-5)만 따로 살렸다 |
| 전용 감사 로그 | "결과에 영향을 준 값의 변천"은 실행 시점 스냅샷으로 이미 복원된다(§3.2). 신원 확인이 없는 상태의 감사 로그는 신뢰할 수 없는 기록을 신뢰할 수 있어 보이게 만들어 없느니만 못하다 |
| JaCoCo 코드 커버리지 | 대상 서버가 우리 것이 아니라(§10 공개 데모 사이트) 계측이 물리적으로 불가능하다 |
| 테스트 누락 배포 식별 | 배포 이벤트를 알 방법이 코드에 0건이고 SPEC에 배포 개념 자체가 없다 |
| 케이스 사전 등록 (자동화 진척률) | 분모(수동 케이스 인벤토리)가 없어 "내가 적은 숫자 분의 내가 쓴 코드"가 된다. §3.1 "코드가 진실의 원천" 불변식과 정면 충돌한다 |
| 멀티 저장소 · 멀티 팀 | 스캔 대상이 `/tests` 마운트 하나이고 §6에 조직 구분 컬럼이 없다. "단일 조직 단일 저장소 전제"를 §1에 적는 쪽이 맞다 |
