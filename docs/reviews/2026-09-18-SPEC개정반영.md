# SPEC 검사 결과 — 개정 결정 13건 반영 (2026-09-18) `[자기검사]`

**범위** — `worktree-manifest-contracts` 브랜치가 main 대비 바꾼 전부.
2026-09-17 기술 검토(D1~D5)와 화면 검토(D1~D8)를 `docs/spec/` 12장에 반영한 작업,
그리고 그에 딸린 색인·검사기·킥오프·목업 갱신.

**`[자기검사]`** — 이 세션이 반영도 하고 검사도 했다. CLAUDE.md §2.3이 요구하는
「다른 세션이 하는 검사」는 병합 직전에 한 번 더 받아야 한다.

## 요약

치명 **0건** · 중대 **10건 (전부 이 세션에서 고치고 재검사 통과)** · 경미 0건 — **병합 가능**

7건은 스스로 훑어 찾았고, **3건은 사용자가 「색인에도 반영해야 하지 않나」라고 짚어 찾았다.**
색인의 숫자·표만 고치고 **색인이 안내하는 동선**은 안 봤던 것이 이번 자기검사의 구멍이다.

## 검사 범위가 좁은 이유 — 코드 변경 0건

```
git diff --name-status main...HEAD -- apps packages tests db docker-compose.yml
→ (없음)
```

`apps/` · `packages/` · `tests/` · `db/` · `docker-compose.yml` 에 변경이 **한 줄도 없다.**
바뀐 것은 문서 12장 + 색인 + `.claude/` 검사기·훅·스킬 + 목업이다.
그래서 **A(계약) · B(도메인 불변식) · C2·C3(경계) · D1·D3·D4(용어 표기) · E(테스트 코드) ·
F(화면 구현) · G(TDD)는 「해당 없음」** 이다 — 검사할 코드가 없다.
이번 검사의 무게는 전부 **H(문서 정합)** 에 있다.

## 중대 — H2 같은 규칙이 두 장에서 다른 말을 했다

**7건 전부 발견 즉시 고쳤고 재검사에서 0건이다.** 아래는 무엇이 어긋나 있었는지의 기록이다.

### H2-1 — §3.2 불변식이 「반복 상한을 두지 않는다」로 남아 있었다

```
어디:   docs/spec/도메인/실행.md:28 (§3.2 Execution 불변식)
무엇:   "반복 횟수에 상한을 두지 않는다. 동시 실행 2 제한이 이미 있어 서버가 죽지 않는다"
문제:   같은 파일 §8.2 가 1000건 상한을 새로 넣었다. 한 장 안에서 앞뒤가 반대다
왜 문제: 세션은 도메인 절(§3.x)을 불변식으로 읽는다. §8.2 를 안 본 세션이 상한 없이 만든다
고침:   §8.2 를 정본으로 가리키게 고치고, 미룬 근거가 왜 틀렸는지를 같이 적었다
```

**이것이 eng-review D1 이 지적한 것과 정확히 같은 유형이다** — 인증 경계가 §7 과 §8.6 에서
반대를 말하던 그 일. 그 발견 때문에 체크리스트에 H2 가 들어왔고, **그 H2 가 이번에 바로 걸렸다.**

### H2-2·3 — 리포팅 장이 자기 자신과 모순됐다

```
어디:   docs/spec/도메인/리포팅.md:23 (§3.3) · :34 (§3.3)
무엇:   "인스턴스 이름, 테스트 저장소 주소" · "증적 문서 머리말에는 인스턴스 이름과…"
문제:   같은 파일 §8.4 는 개정판이라 "서비스 이름"이라고 적는다
왜 문제: 증적 머리말은 검수처에 내는 문서의 첫 줄이다. 두 절이 다른 칸을 가리키면
        WS-D 가 어느 쪽을 구현해도 다른 절과 어긋난다
고침:   둘 다 서비스 이름으로. §6 `test_run.service_name` 이 정본이다
```

### H2-4·5·6 — 「검색 조건 다섯」이 세 장에 남았다

```
어디:   도메인/카탈로그.md:20 · 도메인/인증.md:153 · 공통/3-공유계약.md:88
무엇:   "검색 조건 다섯과 화면 규칙은 §8.1이 정본이다"
문제:   §8.1 표는 2026-09-17 에 넷이 됐다 (「기능 영역」이 맨 위 띠의 서비스 선택으로 올라갔다)
고침:   숫자를 빼고 "검색 조건"으로. §8.1 표 제목도 「검색 조건 (2026-09-16 결정 · 2026-09-17 넷으로)」
```

숫자를 여러 장에 적어 두면 바뀔 때마다 전부 찾아야 한다. **정본 한 곳만 세고 나머지는 가리키게 한다.**

### H2-7 — WS-D 킥오프가 옛 칸을 시켰다

## 재검사에서 더 나온 것 (사용자 지적)

> "spec 개정 반영된 거 SPEC.md 에 반영해야 하는 거 아니야?"

맞았다. **색인의 숫자와 표는 고쳤는데 색인이 안내하는 동선은 옛 상태였다.** 3건.

| # | 무엇 | 왜 문제 |
|---|------|--------|
| H2-8 | 절 번호 표가 `§8 인스턴스 띠` | 장 목록은 「서비스 띠」로 고쳤는데 **절 번호 표만 안 고쳤다.** 같은 색인 안에서 두 표가 다른 이름을 부른다 |
| H3-1 | 「기능을 더하거나 고칠 때」 표에 **서비스·등급 줄이 없었다** | 이 표는 "무엇을 하려는가 → 무엇을 읽는가" 라우터다. 개정이 만든 개념에 줄이 없으면 세션이 어느 장을 열지 모른다. 「설정값·포트·컨테이너 → §9」 줄도 이제 반만 맞다 |
| H5-1 | 「221군데」가 실제 **242군데** | 손으로 적는 숫자라 조용히 썩었다. 분량 숫자와 **같은 유형의 두 번째** 재발이다 |

**H5-1 은 기계로 옮겼다** (CLAUDE.md §2.5). `check:spec` 이 돌 때마다 세어 찍고,
색인은 숫자를 적지 않는다. 분량 숫자를 옮긴 것과 같은 조치다.

색인에 **「2026-09-17 판이 뒤집은 것 넷」** 표도 더했다. 앞 판을 기억하는 세션이
옛 전제로 일하지 않게 하는 자리다. 규칙을 다시 적지 않고 **정본 절만 가리킨다** —
내용을 옮겨 적으면 그것이 바로 H2 를 만든다.

## 승격한 것 — `spec-review` 에 H5 를 더했다

> **H5 — 손으로 적어 둔 숫자가 실제와 맞는가**

같은 유형이 **세 번** 나왔다 — 장별 분량 12곳 · 「221군데」 · 「검색 조건 다섯」 3곳.
규칙 자체는 정본 한 장에 있는데 **개수만** 다른 곳에 흩어져 있었고, 규칙이 바뀔 때 조용히 틀려졌다.
CLAUDE.md §2.5 의 「두 번째면 기계로 옮긴다」에 걸리므로 **제안이 아니라 반영했다.**

- 기계가 보는 부분 — 장별 줄 수와 절 참조 수를 `check:spec` 이 센다
- 사람이 보는 부분 — 산문 속의 개수. 발견하면 **숫자를 빼고 정본 표를 가리키게** 고친다

`H3` 도 같이 넓혔다 — 색인의 세 표뿐 아니라 **「기능을 더하거나 고칠 때」 라우터 표**까지 본다.
이번에 빠진 자리가 정확히 거기였다.
