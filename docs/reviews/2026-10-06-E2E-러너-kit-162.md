## 중대

### 1. 기타(명세 ↔ 코드, 회귀) — 미룬 삭제가 프로젝트의 기본 인증을 잃는다
어디:   `apps/runner/scenario/window.ts:146`(`묶음` — `httpCredentials: options?.httpCredentials`) · `:81`(`미룸.push({ …, httpCredentials: 묶음.만들때.httpCredentials })`) · `:243`(`sendDelete` — `httpCredentials: d.httpCredentials`)
무엇:   47e5528 이 「도구 묶음 하나」로 합치면서 조건부 펼치기(`...(x === undefined ? {} : { httpCredentials: x })`)를 늘 열쇠를 넣는 꼴로 바꿨다(1021a20 의 `window.ts:77 · 151 · 167 · 237` 은 열쇠를 안 넣었다).
        Playwright 는 `runBeforeCreateRequestContext` 에서 `if (!(key in options))` 일 때만 프로젝트 `use` 값을 채운다. 부품 `request` · `page.request` 로 모은 삭제(가장 흔한 길)는 `만들때` 가 비어 `httpCredentials: undefined` 열쇠가 실리고, 그 연결에는 프로젝트 `use.httpCredentials` 가 안 붙는다.
        같은 까닭으로 머리글은 `기본머리` 로 아래에 깔았는데 기본 인증은 깔지 않았다. 이 값을 지키는 검사가 없다.
왜 문제: 시나리오 전용 설정은 「회사 서버의 기본 인증」을 이어받으려고 루트 `use` 를 펼친다(`apps/runner/scenario/playwright.config.ts:26-27` · 러너 §5.2). 기본 인증 뒤에 있는 회사 서버에서는 케이스 실행 중 요청이 다 통과해도 미룬 삭제만 전부 401 이 되고, 앞 부품이 만든 데이터가 대상 서버에 남는다.
        시나리오 §3.7 결정 12 표의 「모을 때의 로그인 상태(쿠키 · 그 호출과 연결의 머리글 · 기본 인증)로 보낸다」와 어긋난다.
고칠 것: 열쇠를 값이 있을 때만 넣는 꼴로 되돌리거나, `기본머리` 처럼 프로젝트 `use.httpCredentials` 를 아래에 깐다. 러너 §5.2 「프로젝트 `use` 의 `extraHTTPHeaders` 를 아래에 깐다」 줄에 기본 인증도 같은 까닭이라고 반 줄을 더한다.
        `sendDelete` 가 원래 연결 만들기에 넘기는 옵션을 단언하는 검사를 하나 둔다(가짜 `요청도구.newContext` 로 충분하다).
고칠 곳: WS-시나리오(러너)

### 4. H2 — 「..」 사유 글자가 명세에 값으로 박혀 있다
어디:   `docs/spec/도메인/시나리오.md:223` 「사유 `<N>번 부품 응답의 <jsonPath> 값 「..」 은 주소에 넣을 수 없다`」 · `apps/runner/scenario/links.ts:197`(`값 「${글자}」`)
무엇:   다른 사유는 `<N>` · `<jsonPath>` 처럼 자리를 적는데 이 사유만 값 자리를 `..` 로 박았다. 코드는 실제 값을 넣어 `.` 이면 「.」이 나온다.
고칠 것: 명세 사유를 `… 값 「<값>」 은 주소에 넣을 수 없다` 로 적는다.

### 5. H2 — 응답 적기 규칙이 정본(시나리오 「요청 고르기」)에 없고, 코드 주석이 그 자리를 가리킨다
어디:   `apps/runner/scenario/links.ts:207`(API 가짜 응답 적기 — 「SPEC 도메인/시나리오 §3.7 결정 12 「요청 고르기」」) · `docs/spec/도메인/시나리오.md:216-220` · 러너 §5.2 164줄
무엇:   「3xx 는 안 적는다 · API 가짜 응답도 적는다」는 러너 §5.2 에만 있다. 결정 12 표가 「이 표가 정본이다. 다른 절 · 코드 · 화면은 이 표를 가리킨다」인데 「요청 고르기」의 「앞 부품의 응답은 그 부품에서 무늬에 처음 맞은 응답이다」는 이 둘을 모른다.
        같은 절의 「API 쪽 무늬 맞추기는 Playwright 의 glob 변환을 옮겨 쓴다」도 브라우저 응답을 적을 때(`적기` → `무늬맞음`) 옮긴 맞추기를 쓴다는 것을 안 적는다. 상대 무늬면 브라우저 응답이 안 적혀 뒤 부품이 「맞는 응답이 없다」로 떨어진다(조용히 새지는 않는다).
고칠 것: 「요청 고르기」에 「3xx 는 안 치고 막기 · 돌려주기 · 모킹으로 준 응답은 친다 · 응답 적기는 두 채널 모두 옮긴 맞추기를 쓴다(러너 §5.2)」 한 줄을 더하거나, 주석을 러너 §5.2 「이어 주기를 건다」로 바꾼다.

### 6. H2 — `{}` 규칙이 러너와 admin 에서 다른 말을 하고, 작성 쪽 결정 항목이 없다
어디:   러너 §5.2 186줄 「`{}` 자리가 있음」 · `apps/runner/src/routes.ts:51`(`p.includes('{}')`) · 시나리오 §3.7 222줄 「`{}` 가 없으면 조립을 거절한다(러너 입구 400)」 · 시나리오 §7 366줄 「`{}` 가 꼭 하나가 아니다」 · `docs/WORKSTREAMS.md:130` 「admin 이 먼저 같은 글자로 400 으로 막는다」
무엇:   admin 은 「꼭 하나」, 러너 · 「값 꺼내기」는 「있음」이다. 러너는 `{}` 가 둘이면 받아서 첫 자리만 바꾸고(`links.ts:199` `replace`) 둘째 `{}` 를 주소에 그대로 싣는다. WORKSTREAMS 는 둘이 「같은 글자」라 적는다.
        1차 5번의 뒤 절반(작성 쪽이 `5-writing.md` · `two-kinds.md` 두 문장을 남길지 정하는 일)도 아직 ⓒ 줄 산문에만 있다.
왜 문제: admin 이 먼저 막아 지금은 해가 없다. 다만 ⓒ 세션이 WORKSTREAMS 의 「같은 글자로」를 따라 러너 규칙(있음)을 admin 에 옮기면 §7 의 「꼭 하나」가 조용히 느슨해진다.
고칠 것: 러너 입구를 「꼭 하나」(`p.split('{}').length === 2`)로 맞추고 러너 §5.2 · 「값 꺼내기」 글자도 「꼭 하나가 아니면」으로 바꾼다. 아니면 WORKSTREAMS 를 「admin 은 §7 대로(꼭 하나) 더 좁게」로 고친다. 작성 쪽 결정은 `docs/wbs.md` 에 한 줄 항목으로 남긴다.
