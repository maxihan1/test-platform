# SPEC 검사 결과 — WS-0 (Phase 0 골격) (2026-09-16) `[자기검사]`

이 검사를 돌린 세션이 대상 코드를 작성한 세션이다. 스킬의 철칙 1에 따라 `[자기검사]`로 표시한다.
병합 직전 전체 검사는 반드시 다른 세션이 다시 돌려야 한다 (WORKFLOW.md [3]).

## 요약
치명 0건 · 중대 0건 · 경미 0건 — **G1 확인 가능**

Phase 0는 기능 구현이 아니라 계약 확정 단계다. 체크리스트 항목 중 아직 만들지 않은 컨텍스트에
해당하는 것은 판정 대상이 아니라 `해당 없음`으로 적는다.

## 통과한 항목

A1~A4, A6, B1~B3, C1~C3, D1~D3, E2~E4, G1~G2

근거가 필요한 것만 적는다.

- **A4** 러너 요청·응답이 `ExecuteRequest`/`ExecuteResponse`와 필드까지 일치.
  요청은 zod로 경계에서 검증하고, 타임아웃은 200 + `NA` + `TIMEOUT`, 500은 러너 고장 전용이다
- **A6** DB 컬럼을 실제 기동한 DB에서 뽑아 SPEC §6과 대조. 테이블 6종 컬럼 전부 일치
- **B1** `run_item`의 `params`/`expected`가 스냅샷 복사다.
  `npm run smoke`가 실행 후 `param_set`을 바꾸고 `run_item`을 다시 읽어 보여준다.
  확인값: `param_set`은 `example.com/바뀐-값`, `run_item`은 `demo.playwright.dev/todomvc` 그대로
- **B2** `tc_name`·`precondition`도 같은 자리에서 복사해 넣는다
- **B3** 러너 소스에 DB 클라이언트·연결 문자열·SQL이 하나도 없다 (grep 확인)
- **C3** 러너는 `artifacts` 볼륨 밖에 파일을 쓰지 않는다. Playwright 산출물 경로도 `PLATFORM_ARTIFACTS_DIR` 아래다
- **D1** `testId`·`caseId`·`test_case_id` 표기 없음 (grep 확인)
- **D3** Playwright `projects`가 `desktop`·`mobile`. `--project=desktop`으로 실제 실행해 확인
- **G1** 러너의 판정 규칙과 경로 이탈 차단에 단위 테스트 6건. 관통은 실행으로 확인

## 기타 — 다음 갈래가 알아야 할 것

세 건 모두 Phase 0 설계상 의도된 상태이며 위반이 아니다. 놓치면 나중에 헷갈릴 것들이라 적는다.

1. **CI 초록불이 "테스트 코드 규칙 통과"를 뜻하지 않는다.**
   `npm run check:tests`는 아직 아무것도 검사하지 않고 exit 0만 한다. WS-A가 채우기 전까지
   K1~K8은 사람이 봐야 한다. → 체크리스트 E1에 "검사기가 스텁이면 통과로 세지 않는다" 한 줄 추가를 제안한다
   → `spec-review` SKILL.md의 E 표 아래에 반영됨 (2026-09-16)

2. **DEMO-008~010의 환경 축은 절반만 검증된다.**
   Phase 0에는 `defineCase`가 없어 `platforms`를 선언할 수 없다. 대신 뷰포트 폭으로 동작을 갈라
   DEMO-009는 데스크톱만, DEMO-010은 모바일만 통과하게 해 뒀다. "모바일 전용 케이스의 PC 칸이
   `—`로 빈다"는 화면 확인은 WS-C가 `platforms`를 선언한 뒤에야 가능하다

3. **A3은 형식상 통과지만 사실관계를 적어둔다.**
   `docker-compose.yml`은 Phase 0 안에서 한 번 더 고쳤다 (호스트 PostgreSQL 충돌로 5432 → 5433).
   Phase 0 종료 시점 상태가 기준선이므로 위반이 아니다. G1 이후부터 잠긴다
