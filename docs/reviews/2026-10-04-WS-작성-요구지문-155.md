## 중대

### 중대 1 — H2 · 반영 때 세 갈래를 언제 · 어느 순서로 타는지가 명세와 코드에서 다르다
어디:   `docs/spec/도메인/작성.md` 504행 「반영 충돌」 · 672행 「요구사항 표 합치기」 ↔ `scripts/authoring-main-merge.ts` `main합치기` 의 충돌 처리 블록 뒤 `if (main바뀐것.includes(지문경로(표경로)))`
무엇:   명세 두 자리는 「지문 파일이 충돌하면 먼저 세 갈래로 합치고 표 처리는 표가 충돌했을 때만」이라고 적는다. 코드는 충돌이 없어도 main 이 지문 파일을 바꿨으면 세 판(바탕 · main · 요청)에서 다시 계산하고, 그것도 표 처리를 마친 뒤에 한다. WORKSTREAMS #155 줄과 커밋 635f780 은 「세 판에서 다시 계산」이라 코드와 같다. 명세만 다르다
왜 문제: 코드 주석이 든 까닭(git 줄 합치기는 충돌 없이도 JSON 을 깨뜨릴 수 있다)이 명세에 없다. 다음 세션이 명세대로 「충돌 때만」으로 좁히면 깨진 지문 파일이 main 에 들어간다. 그 뒤 작성은 「⚠️ 앞 판 지문을 못 읽음」이 되고, 이번 자료 항목만 남겨 다른 자료 항목을 잃는다
고칠 곳: WS-작성(명세) — 두 자리를 「main 이 지문 파일을 바꿨으면 충돌이 안 나도 세 판에서 다시 계산한다(git 줄 합치기는 JSON 을 깨뜨릴 수 있다)」로 고치고, 「먼저」는 빼거나 코드 순서(표 처리 → 지문 파일)로 맞춘다

### 중대 2 — H2 · 지문 단위의 「줄 첫머리(표 테두리 · 목록 표시 뒤)」를 코드가 좁게 읽는다
어디:   `docs/spec/도메인/작성.md` 499행 「지문 단위」 ↔ `scripts/authoring-ledger.ts` `첫머리번호`(앞말 `[\s│|*•-]`) · `머리글` · `번호지문`
무엇:   코드는 목록 표시로 `*` · `•` · `-` 만 본다. 「1. REQ-A-001 로그인」 같은 번호 목록 줄은 주인이 되지 못하고, 40자 이하라 머리글로 잡혀 주인을 끊는다. 그래서 그 아래 설명 줄이 어느 번호에도 안 붙는다. 임시 스크립트로 확인했다 — 설명 줄을 고쳐도 차이가 `[]`(바뀜 0)다. 문장으로 끝나는 긴 번호 목록 줄은 머리글이 아니라서 앞 요구에 붙는다. 「원장 번호 없는 표 행은 어디에도 안 붙는다」도 `|` · `│` 로 시작하는 행만 알아본다. pandoc · textutil 꼴의 표 머리 행은 바로 앞에 머리글이 있을 때만 안 붙는다(데모마켓은 표마다 장 제목이 앞에 있어 실측에 안 드러났다)
왜 문제: 지금은 보고만 하지만 다음 단계는 이 차이로 「바뀐 요구만」 다시 만든다. 번호 목록으로 쓴 기획서는 요구 설명을 고쳐도 「안 바뀜」으로 나와 옛 케이스가 그대로 남는다. 실측이 표 꼴 기획서 하나뿐이라 이 꼴은 아무도 안 봤다
고칠 곳: WS-작성 — 코드가 번호 목록 표시(`1.` · `1)`)를 첫머리 앞말로 받게 하거나, 명세 문장을 코드대로 좁히고 「남는 한계」에 적는다. 어느 쪽이든 그 꼴의 검사를 더한다

## 경미

### 경미 1 — H2 · 앞 판 지문을 git 으로 못 읽은 갈래가 명세에 없고, 그때는 되돌리기도 안 한다
어디:   `docs/spec/도메인/작성.md` 501행 「쓰기」 · 503행 「PR 머리 줄」 ↔ `scripts/authoring-ledger-io.ts` `지문쓰기` 첫 줄(`if (앞 === null)`)
무엇:   명세는 「원장이 없으면 앞 판 글로 되돌린다 — 자식이 만진 파일이 올라가지 않게」라고 적는다. 코드는 앞 판을 git 으로 못 읽으면(`앞지문읽기` 가 null) 원장이 있든 없든 트리를 그대로 두고 끝난다. 자식이 지문 파일을 만졌으면 그대로 커밋된다. 원장이 있을 때 「안 쓴다」는 갈래도 명세에 없다. 원장이 없는데 폴더 확인에 걸리면 경고 줄이 생겨 「원장이 없으면 줄이 없다」와도 어긋난다
왜 문제: 드문 갈래지만 걸리면 자식 손을 탄 지문이 반영 뒤 main 의 「앞 판」이 되고, 다음 단계가 그 차이로 케이스를 고친다. 남는 것은 스킬 한 줄뿐이다 — 계획 검토 주의 4 가 「스킬 한 줄은 장치가 아니다」로 막으려던 길이다
고칠 곳: WS-작성 — 못 읽은 갈래를 명세 「쓰기」 행에 적는다. 코드는 그때도 지문 파일을 바뀐 파일 목록에서 빼거나 올리기를 막는다

### 경미 2 — H2 · 「같은 번호는 하나」로 읽히는 명세 문장과, 자료 이름이 열쇠인 코드
어디:   `docs/spec/도메인/작성.md` 500행 「파일」(같은 번호가 자료 둘에 나오면 먼저 나온 자료 것) · 504행 「반영 충돌」(바탕이 없으면 같은 번호는 요청 것) ↔ `scripts/authoring-ledger-diff.ts` `지문합치기` · `지문세갈래`(열쇠 = 자료 + 번호)
무엇:   「먼저 나온 자료 것」은 한 실행의 원장 안에서만 맞다. 자료마다 합치기 때문에 이름을 바꾼 새 판(예 「기획서_v2.docx」)을 보내면 앞 이름의 항목을 물려받아 같은 번호가 자료 둘로 파일에 남는다. 이름을 바꿀 때마다 쌓이고 1MiB 를 넘으면 「못 읽음」으로 떨어진다. 차이는 「새 자료」로만 나온다. 세 갈래도 자료가 다르면 같은 번호를 둘 다 남긴다. 「남는 한계」에 이 내용이 없다
왜 문제: 판마다 파일 이름을 바꾸는 회사가 흔하다. 다음 단계가 기대하는 차이가 실제로는 거의 안 나올 수 있다. 명세를 믿은 다음 세션이 번호 하나를 열쇠로 지문 파일을 읽으면 틀린 항목을 집는다
고칠 곳: WS-작성(명세) — 두 문장을 「한 실행의 원장 안에서」 · 「같은 자료의 같은 번호」로 좁히고, 「남는 한계」에 「이름을 바꾼 새 판은 차이가 안 나오고 앞 이름 항목이 파일에 남는다」를 더한다

## 기타
1. 기획서가 요구마다 마크다운 머리글을 쓰면(「### REQ-L-001 로그인」 + 설명 문단) 명세 문장 그대로 머리글이 주인을 끊어, 설명을 고쳐도 바뀜 0 이다(임시 스크립트로 확인). 코드와 명세는 같은 말을 한다. 명세 변경 제안 한 줄 — 「머리글 줄 첫머리(`#` 뒤)에 원장 번호가 있으면 그 번호가 주인이다」를 지문 단위에 더한다. 체크리스트 항목 제안 — 「글 모양 규칙(원장 · 지문)을 표 꼴 말고 번호 목록 · 머리글 꼴 예제로도 검사했는가」
2. 세 갈래는 항목마다 고르고 꼴은 요청 것을 쓴다. 같은 자료를 서버(pandoc) 요청과 맥(textutil) 요청이 동시에 바꾸면 항목 지문이 두 꼴로 섞인 채 한 꼴로 적힌다. 쓰기 규칙(자료마다 합친다)처럼 반영도 자료 단위로 고르면 맞는다. 드문 경우라 한 줄만 남긴다
3. `지문쓰기` 가 폴더 확인 중 예외(예: mkdir 권한)를 잡아 「진짜 폴더가 아니다」로 바꿔 말한다. 실제 까닭이 사라진다(CLAUDE.md §3 「에러」)

## 반영 (게이트 2 전 · 구현 세션)
- 중대 1 — 명세 「반영 충돌」 · 「요구사항 표 합치기」를 코드대로 「main 이 지문 파일을 바꿨으면 충돌이 없어도 표 처리 뒤 세 판에서 다시 계산」으로 고쳤다
- 중대 2 — 첫머리 표시에 번호 목록(`1.` · `1)`) · `#` · 괄호 · `■◦` 등을 더하고 검사를 붙였다(「1. REQ-A-001 로그인」 · 「### REQ-M-001」 · 「[REQ-S-001]」)
- 경미 3 — 앞 판을 못 읽었거나 쓰기 · 되돌리기 실패면 트리 지문 파일을 커밋에서 뺀다(보안 검토와 같은 지적) · 원장이 없으면 줄이 없다 · 명세 「쓰기」 행에 적었다
- 경미 4 — 번호 모드를 번호 열쇠로 바꿨다(이름 바꾼 새 판도 바뀐 요구가 나온다 · 합칠 때 겹친 번호를 뺀다) · 명세 「파일」 · 「차이」 행
- 경미 5 — 역방향 319행에 요구 지문 파일을 넣었다
- 경미 6 — 계획에 「구현 중 바뀐 결정」 표를 더했다
- 경미 7 — 새 판단 다섯(세 갈래 고르기 · 폴더 링크 확인 · 원장 없을 때 되돌리기 · 꼴 다름 · 조사 붙은 언급)을 부쉈다. 넷은 검사가 빨개졌고, 폴더 링크 확인은 두 겹(링크인지 · 실제 경로가 트리 안인지)이라 한 겹만 지우면 나머지가 막아 초록이다. PR 코멘트 [5/7] 의 「분모 · tcId 거름」은 #154 것이라 바로잡았다
