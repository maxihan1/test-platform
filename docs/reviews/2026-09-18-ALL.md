## 병합 판정

**예 — 병합 가능.** 치명 0건이다.

- 1차 치명 2건은 **실물로 닫힌 것을 확인했다.** 치1 은 인증 §7 과 같은 말로 바뀌었고,
  치2 는 WS-B·WS-C 가 되살아났으며 새로 붙인 15개 항목이 **전부 SPEC 근거를 갖는다** — 지어낸 것이 없다
- 계약 파일(`types.ts`·`db/migrations/`·`docker-compose.yml`)은 **한 글자도 안 바뀌었다.** A1~A3 이 유일한 방어선인데
  방어할 것이 없다. 코드 위험 0
- 중대 3건 중 둘(중1·중2)은 **문서 수정**이고 세 번째(중3)는 **이 브랜치가 만든 것이 아니다.**
  중1·중2 는 합치기 전에 고치는 편이 낫다 — 둘 다 「갈래 세션이 SPEC 보다 먼저 읽는 글」이고,
  WS-D 와 WS-F 가 그 글을 들고 출발하면 잘못 만든 것을 나중에 되돌려야 한다.
  고쳐도 `npm run check:spec` 만 다시 돌리면 된다
- 중3 은 WS-A 갈래에서 고친다. 병합을 막지는 않지만 **그 전에 고치지 않으면 파이프라인이 QA 단계에서
  절반쯤 멈춘다.** 이 브랜치가 건드릴 자리가 아니므로 WS-A 킥오프에 항목으로 넘기는 것을 권한다
