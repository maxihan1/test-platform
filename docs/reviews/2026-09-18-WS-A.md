왜 문제: 소유 경로 규칙이 병렬 작업을 지탱한다. 계약을 바꾼 단위가 남의 폴더까지 손대기 시작하면

고칠 곳: 사용자 판단. 그대로 두려면 `docs/WORKSTREAMS.md` 의 contracts 정의에
        「계약 변경이 컴파일을 깨뜨린 자리는 값 없이 칸만 채운다」를 한 줄 더한다.

## 기타

### 1. `execution` 테스트 18건이 빨간불이다 — 예고된 것이고 WS-B 몫이다

`test_run.env` 의 `DEFAULT 'demo'` 를 뺀 결과다. SPEC §6 이 **이 상황을 미리 적어 뒀다** —
「지금 실행 생성 코드가 실제로 `env` 를 넣지 않고 INSERT 하고 있어 이미 그 상태다」.
고치려면 실행 요청에 `env` 를 받아야 하고 그것이 WS-B 킥오프 E 다.
임의 값을 채우면 SPEC 이 경고한 「빈 칸이 아니라 틀린 값이 남는다」가 된다.

**세 번 돌려 전부 같은 18건이었다.** 산발적이지 않다.

### 2. 화면이 `?service=` 없이 부르고 있다 — WS-E 몫이다

`apps/admin/src/web/api.ts:156` 의 `cases()` 가 `?q=&page=` 만 보낸다. 이제 400 을 받는다.
서비스 띠를 붙이는 WS-E 가 같이 고친다. 소유 밖이라 건드리지 않았다.

### 3. 에러 코드 이름을 새로 정했다

`SERVICE_REQUIRED`(400) · `SERVICE_FORBIDDEN`(403). §7 은 403 이라고만 적고 본문 모양을 정하지 않았다.
기존 관례(`CASE_NOT_FOUND` · `MIXED_SERVICE`)와 같은 꼴로 맞췄다. 화면이 이 문자열을 읽게 되므로
합칠 때 WS-E 와 맞춰 본다.

### 4. 체크리스트에 항목 하나를 더했다

**G4 — 표를 일괄 갱신하는 제품 코드에 범위 조건이 있는가.**
G3(정리 구문)이 통과하는데도 테스트가 흔들리면 여기를 본다. 이번에 실제로 그랬다.
