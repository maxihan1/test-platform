## 8. 화면

### 껍데기 — 왼쪽 줄 · 사이드바 · 푸터 (2026-09-21 결정 · 2026-10-30 위쪽 바를 걷었다)

한 벌이 서비스 여럿을 감당하므로(§1) **지금 어느 서비스를 보고 있는지**가 늘 보여야 한다.
엉뚱한 서비스에서 `실행`을 누르는 사고를 막는 장치가 고른 애플리케이션을 늘 같은 자리에 보여 주는 것이다(2026-10-29 부터 왼쪽 줄의 애플리케이션 칸과 사이드바 머리 · 2026-11-05 부터 머리 자리는 위치 카드).
**2026-10-19 사용자 결정 — 화면에서 서비스의 이름은 「애플리케이션」이고, 그 위에 프로젝트 층이 생겼다**(공통/1-제품과-구조 §2 「프로젝트 · 애플리케이션 · API 서버는 다른 층이다」). 이 절의 「서비스 고르개」는 화면에서 **애플리케이션 고르개**였고, 그 앞에 **프로젝트 고르개**가 섰다(아래 「프로젝트 고르기」). 2026-11-05 부터 둘은 **위치 카드**(위 칸 프로젝트 · 아래 칸 애플리케이션) 하나다(아래 「사이드바」). 코드 · 표 이름 `service` 는 그대로다.
**2026-10-29 사용자 결정(PR #517) — PC 에서는 애플리케이션 고르개를 헤더에서 빼고 사이드바 왼쪽 「애플리케이션 줄」로 옮겼다**(아래). 헤더에는 프로젝트 고르개만 남는다(2026-10-30 헤더를 걷어 그 고르개는 사이드바 바닥으로 갔다가 2026-11-02 사이드바 맨 위로 올라갔고, 2026-11-05 사이드바 머리와 합쳐 위치 카드가 됐다 — 아래). 휴대폰은 2026-10-30 부터 위 줄에 애플리케이션 고르개만 두고 프로젝트 고르개는 「전체」 메뉴판에 두었다가, 2026-11-05 부터 위 줄 판이 프로젝트까지 고른다(아래 「휴대폰 화면」).
**2026-10-13 사용자 결정 — 서비스 고르개는 맨 위 헤더로 옮겼고 앱 대시보드에서도 둔다(PC 헤더 — 휴대폰 위 줄은 계속 숨겼다. 2026-10-29 에 PC 의 자리는 사이드바 왼쪽 애플리케이션 줄로 옮겼고 대시보드에도 선다. 2026-10-30 부터 휴대폰 위 줄도 대시보드에서 고르개를 보인다).** 앞 판(2026-10-07)은 대시보드에서만 고르개를 숨겼다 —
여러 서비스를 함께 보는 화면에서 고르개가 「이 서비스만」으로 읽힌다는 까닭이었다. 사용자가 대시보드에서 칸이 사라지는 것을 되돌려 달라고 했다.
**대시보드의 내용은 고른 프로젝트(2026-11-05 부터 사이드바 맨 위 위치 카드) 안의 배정 애플리케이션 전체다**(2026-10-20 ⑬-3 — 정본은 아래 「프로젝트 고르기」). 애플리케이션 줄(2026-10-29 까지는 헤더의 애플리케이션 칸)은 내용을 거르지 않고, 다른 메뉴로 갈 때 쓸 애플리케이션을 미리 고르는 용도다.
읽는 사람이 헷갈릴 수 있다는 근거는 남아 있어 탭 제목 · 바닥 글에는 서비스 이름을 계속 걸지 않는다(아래). 그 화면에는 `실행` 단추가 없다.

**2026-10-30 사용자 결정(시안 11판 · 진행판 WEB-F7-01 · 코드는 WEB-F7-04) — 위쪽 바(맨 위 헤더)를 걷었다.** 그 자리에 있던 것은 왼쪽 줄과 사이드바로 옮긴다 — 알림 · 설정 · 내 메뉴는 왼쪽 줄 아래, 찾기는 사이드바 머리, 프로젝트 고르개와 밝게 · 어둡게 단추는 사이드바 바닥, 언어 고르개는 내 메뉴 안이다. 프로젝트 고르개는 2026-11-02 사이드바 맨 위로 올렸다(아래 「사이드바」 「맨 위」).
**왜** — 위쪽 바 · 머리 판 · 거르기 두 줄 · 표 머리가 쌓여 케이스 목록 첫 화면에 케이스가 서너 건만 보였고, 사용자가 「스크립트 화면이 답답 — 위 메뉴가 공간 차지」라고 했다. 위쪽 바에 남은 것이 프로젝트 고르개와 버튼 넷뿐이라 줄 하나를 통째로 내줄 까닭이 없었다.

**2026-11-05 사용자 결정(시안 3판 https://claude.ai/artifact/GcP1wVJYKxFyH551q8uqsb · PR #620) — 사이드바 맨 위의 프로젝트 고르개와 머리를 「위치 카드」 하나로 합치고, 왼쪽 줄은 머물면 펼친다.**
**왜** — 처음 온 사람이 프로젝트 · 애플리케이션을 바꾸는 곳을 못 찾았다(사용자 「처음 접한 사람은 찾기가 어려워」). 프로젝트 고르개는 테두리 없는 회색 작은 글자라 로고 밑 설명으로 읽혔고, 사이드바에서 가장 큰 이름인 머리는 눌러도 반응이 없었고, 왼쪽 줄 칸은 접두사뿐이라 이름은 마우스를 올려야 떴다. 같은 층(프로젝트 ⊃ 애플리케이션)이 화면 두 곳으로 쪼개져 관계도 안 보였다.
시안은 A(위치 카드) · B(왼쪽 줄 펼치기) · C(화면 머리 위치 줄에서 바꾸기) 셋이었고 사용자가 A 와 B 를 섞자고 했다. C 는 대시보드 · 설정처럼 위치 줄에 애플리케이션 이름을 안 붙이는 화면에서 고를 곳이 사라져 버렸다. 섞을 때 프로젝트 바꾸기는 카드 한 곳에만 둔다 — 줄에도 두면 바꾸는 곳이 다시 둘이 된다. 3판에서 사용자가 「프로젝트와 어플리케이션 명이 더 잘 보였으면」이라 해 두 이름을 한 단씩 키웠다.

맨 왼쪽 얇은 칸이 왼쪽 줄이다 — 로고 · 애플리케이션 칸(종류 아이콘 + 접두사, 지금 칸에 막대) · `+` · 알림 · 설정 · 내 동그라미. 그 옆이 사이드바다 — 맨 위(로고 · 접기 단추) · 위치 카드(프로젝트 이름 / 지금 애플리케이션 이름 / `종류 · 접두사`) · 찾기 · 메뉴 · 바닥(밝게 · 어둡게). 본문 맨 위가 화면 머리 한 줄이다(아래 「화면 머리」).

- **위쪽 바는 없다 (2026-10-30).** 앞 판(2026-10-13 사용자 · 시안 A ~ 10-29)은 가로 한 줄 머리에 로고 · 프로젝트 고르개 · 알림 · 언어 고르개 · 계정 메뉴를 두었다. 본문은 창 맨 위부터 시작한다
- **제품 이름은 「Test Commander」 하나다** (2026-11-02 사용자 — 앞 이름 「QA Hub」) — 로고 · 탭 제목 · 바닥 글 · 로그인 · 가입 · 비밀번호 변경 · 프로젝트 고르기 · `index.html` 이 같은 이름을 쓰고 영어에서도 그대로다.
  **「QA Hub」는 제품군 전체 이름이 됐다** — Test Commander(테스트 지휘 · 이 저장소) · Device VISION(기기 관제 · 앞 이름 디바이스 팜) · Issue Bunker(이슈 트래킹 · 앞 이름 BTS)를 묶는다. 화면에서 「QA Hub」는 제품군을 가리키는 자리(`QA Hub 통합계정으로 로그인` · 계정 이름 「QA Hub AI」)에만 남는다.
  서버가 만드는 글(오류 문장 · 리포트 · 이슈 본문 · 댓글 · PR 본문)과 명세가 옮겨 적은 화면 · 서버 글도 같은 날 새 이름으로 맞췄다(PR #567).
  **옛 이름이 남는 자리** — 명세 · 코드 용어(절 이름 「디바이스 팜 접속 방식」 · `bts/` 폴더 · `DEVICE_FARM_URL` · `X-BTS-Signature`), Issue Bunker 에 저장돼 이름으로 다시 찾는 규칙 이름(`QA Hub · PR 병합`) · 라벨(`QA Hub`), 이력 문장 · 사용자 말 인용, AI 에게 주는 지시문(모델 동작이 바뀔 수 있어 따로 정한다).
  이미 저장된 실패 까닭은 옛 이름 그대로라 실패 유형 정규식(`reporting/failureType.ts`)은 두 이름을 다 받는다
  2026-10-19 ⑫-14 에 이름이 둘인 것을 「테스트 플랫폼」 쪽으로 맞췄다가 2026-10-20 사용자가 「QA Hub 가 맞다」고 해 이쪽으로 다시 맞췄다(진행판 WEB-F5-01)
- **왼쪽 줄 (2026-10-29 애플리케이션 줄 · 2026-10-30 알림 · 설정 · 내 메뉴를 더했다)** — 사이드바 왼쪽의 얇은 세로 줄이다. 위에서부터
  - **로고** — 맨 위. 대표색 바탕의 표지(위 대표색 목록 「로고」). 누르면 「집」으로 간다(아래 「집」 줄). 읽어 주는 이름은 `Test Commander 홈`(2026-11-02 — 앞 이름 `QA Hub`)
  - **애플리케이션 칸 (2026-10-29 사용자 · PR #517 · 구분 B안)** — 앞 판은 헤더의 애플리케이션 고르개(접두사 칩 + 이름 상자를 눌러 펼치는 목록)였다. **고른 프로젝트 안의, 권한이 있는 애플리케이션만** 종류 아이콘 + 접두사로 세로로 늘 세운다 — 펼치지 않아도 다 보인다.
    - **차례** — 앞 고르개의 종류별 묶음 차례(`웹` · `Android 앱` · `게임` · `API`, 2026-10-21 사용자 · 시안 C · APP-F1-14 · 게임 묶음 GAME-F1-08)와 같고 같은 종류 안은 앞 고르개 차례 그대로다. 묶음 제목은 줄에 달지 않는다 — 아이콘이 종류를 말한다. 애플리케이션이 하나뿐이어도 줄은 선다
    - **지금 연 애플리케이션 칸에 대표색 막대가 선다** — 「지금 있는 자리」 표시와 같은 뜻이다(위 「대표색」). 애플리케이션 색을 쓰는 것이 아니다 — 아래 「서비스 색을 화면에서 쓰지 않는다」는 그대로다. 칸을 바꾸면 막대가 미끄러져 옮겨 간다(DESIGN.md 원칙 4 표)
    - **누르면 그 애플리케이션으로 바뀐다.** 앞 헤더 고르개에서 골랐을 때와 같은 동작이다(마지막에 연 애플리케이션을 브라우저에 적어 둔다 — 「프로젝트 고르기」). 마우스를 올리면 `이름 · 종류`(예: `DEMO 프론트 페이지 · 웹`)가 뜨고 화면 읽기 프로그램도 같은 말을 읽어 준다 — 칸에는 접두사만 보여서 이름을 알 길이 이것이었다(2026-11-05 부터는 줄을 펼치면 이름이 보인다 — 아래 「펼치기」)
    - **애플리케이션 칸 맨 아래 `+`** — 설정을 열 수 있는 사람(운영 admin 계정 — 아래 「자리 목록」 「설정」 줄)에게만 보인다. 누르면 설정의 새로 만들기 마법사(`#/settings/new`, 도메인/인증 §8.8)로 간다. 읽어 주는 이름은 `애플리케이션 추가`다 — 설정 왼쪽 메뉴의 「+ 애플리케이션 추가」와 같은 일이라 같은 말을 쓴다
    - **종류 아이콘** — 웹은 지구 모양, Android 앱은 폰, 게임은 게임패드, API 는 앞 판 사이드바 `API` 묶음에 쓰던 아이콘이다. **웹에도 아이콘을 단다 (2026-10-29 사용자).** 앞 판은 「웹이 대부분이라 웹에는 달지 않는다」(내 결정)였다. 그 근거(웹이 대부분이라 아이콘이 늘 같은 모양이면 군더더기)는 여전히 사실이지만, 웹만 빈칸이면 「아이콘이 없으면 웹」을 외워야 해서 뒤집었다. 종류의 정본은 도메인/러너 §5.2 「애플리케이션 종류 「Android 앱」」
  - **펼치기 (2026-11-05 사용자 · 시안 3판 B)** — 줄 위에 마우스가 **0.3초 머물거나** Tab 으로 줄 안 단추에 들어오면 줄이 사이드바 칸 폭만큼 넓어지며 칸마다 이름이 선다 — 애플리케이션 칸은 이름(굵게)과 종류, `+` 는 `애플리케이션 추가`, 알림 · 설정 · 내 동그라미는 `알림` · `설정` · 사람 이름. 애플리케이션 칸 위에는 `<프로젝트 이름>의 애플리케이션` 꼬리표가 선다.
    - **사이드바를 밀지 않고 덮는다** — 본문이 움찔거리면 마우스를 지나가게만 해도 화면이 흔들린다. 줄이 차지하는 자리는 60px 그대로다

    - 마우스가 줄 밖으로 나가거나 포커스가 줄을 떠나면 접힌다. 내 메뉴 판 위에 마우스가 있는 동안은 판이 줄 안이라 접히지 않는다

### 프로젝트 고르기 — 로그인한 직후 (2026-10-19 사용자 · PRJ-F1-03 시안 A)

회사에 제품이 여럿이고 제품마다 사이트 · 앱이 여럿이라, 애플리케이션이 한 줄로 쭉 나오면 어느 제품 것인지 헷갈렸다(사용자 「화면만 보고 이게 어느 서비스다 알기도 힘들고」). 그래서 **로그인하면 프로젝트부터 고른다**(「로그인하면 프로젝트 먼저 선택하는 걸로」).

  **집은 사이드바 순서와 따로 정한다** (2026-10-13 사용자 — 사이드바에서 `테스트 작성` 이 `테스트 실행` 보다 앞에 와도 집은 바뀌지 않는다).
  집은 대시보드 → `테스트 실행` → `테스트 작성` → `실행 기록` 순으로 남은 자리 중 첫 자리다 — 앞이 `none` 이면 다음이 집이다. 집을 바꾸려면 이 줄과 `route.ts` 의 `집()` 을 같이 고친다.
  **`PRD 관리` 는 집이 되지 않는다** (2026-10-10) — 같은 작성 칸이라 `테스트 작성` 이 집이다.

- **하위 메뉴 — 테스트 종류 (2026-10-02 사용자 시안 A · PR #132).** `테스트 실행` 과 `실행 기록` 아래에 `기능 테스트` · `UI 테스트` 를 이 순서로 둔다 — 펼치는 것은 지금 자리가 든 묶음뿐이다(위 「지금 자리가 든 묶음만 펼친다」, 2026-10-30 — 앞 판은 늘 펼쳐 두었다).
  영어는 `Functional tests` · `UI tests`. 주소는 `#/cases/fn` · `#/cases/ui` · `#/runs/fn` · `#/runs/ui` 이고 **종류 없는 옛 주소와 묶음 이름은 기능 테스트로 간다** — 지금 케이스가 전부 기능이라서다.
  기능이 첫 하위다 — 묶음을 누르면 열리는 화면이 첫 하위여야 누른 자리와 열린 화면이 맞는다(2026-10-20 사용자 — 앞 판은 UI 가 위에 있는데 기능이 열려 이상했다)
  - 지금 자리가 하위면 **하위가 표시(막대)를 갖고 묶음은 글자만 밝힌다.** 종류를 모르는 상세(실행 결과 · 항목 · 옛 주소 `#/cases/:id/run`)에서는 묶음만 펼친 표시를 받는다 —
    묶음 링크는 기능 목록으로 가므로 「지금 자리」(`aria-current`)라고 하지 않는다. 접힌 레일에서는 펼친 묶음이 막대를 받는다. 묶음은 이름 붙은 묶음(`role="group"`)으로 읽힌다
  - 같은 글자가 두 묶음에 나오므로 하위 링크는 `실행 기록 · UI 테스트` 처럼 묶음 이름을 단 이름(aria-label)으로 읽힌다
  - **사이드바를 접어도 하위를 지우지 않는다** — 위 자리 목록과 같이 글자만 숨겨 탭이 닿게 두고, 접힌 레일에서는 지금 자리를 가진 묶음이 표시를 받는다. 접힌 묶음(지금 자리가 없는 묶음)의 하위는 숨긴다 — 묶음 줄이 키보드로 닿고 누르면 첫 하위로 가서 잃는 길이 없다
  - 휴대폰에는 사이드바가 없다 — 「전체」 메뉴판이 묶음마다 하위를 다 펼쳐 보이고, 실행 기록은 목록 위에 하위 고르개 줄을 그대로 둔다(아래 「휴대폰 화면」)
  - **API 애플리케이션은 예외다 (2026-10-29)** — 화면이 없어 UI 테스트가 없다. `테스트 실행` 은 하위 없이 한 줄이고 누르면 기능 테스트 목록(`#/cases/fn`)이 열린다 — 그 줄이 지금 자리(`aria-current`)를 받는다. `실행 기록` 묶음의 하위는 `기능 테스트` · `E2E` 둘이고 제목은 다른 종류와 같은 꼴(`실행 기록 › 기능 테스트`)이다. 2026-10-28 에 `API` 아래로 옮겼던 `실행 기록` · `E2E 실행 기록` 은 되돌렸다(위 「메뉴는 고른 애플리케이션의 종류 하나로만 정한다」)
  - **`실행 기록 › E2E` 는 셋째 하위 메뉴다** — 시나리오 실행 화면과 함께 넣었다(PR #165, 2026-10-07). 누를 곳이 없는 메뉴는 두지 않는다(§8.6). `E2E 시나리오` 자리(`#/scenarios`)와는 다른 것이다(만드는 곳 ↔ 돌린 기록)
  - 종류를 바꾸면 목록을 새로 그린다 — 고른 것 · 쪽 · 검색어가 남으면 UI 와 기능을 섞어 골라 실행이 거절된다(도메인/실행 §7 `MIXED_KIND`)
  - **이름 「테스트 케이스」를 「테스트 스크립트」로 바꿨다** (2026-10-02 사용자 「나중에」 → 2026-10-09 반영 — 위 「세 번째로 바뀌었다」 줄)
- **`none` 인 자리의 주소를 직접 치면 집으로 보낸다** (2026-09-28 사용자). 이유 한 줄을 띄우지 않는다 —
  설정 화면(도메인/인증 §8.8)이 머리 없이 이유를 보이는 것과 다르다. 설정은 admin 이 아니면 **영영** 못 여는 자리이고,
  기능 자리는 서비스를 바꾸면 열릴 수 있어 안내보다 옮기는 편이 덜 헷갈린다
  **「자리」는 목록 주소다**(`#/cases` · `#/prd` · `#/authoring` · `#/scenarios` · `#/runs`). 한 건 주소(실행 · 항목 · 옛 주소 `#/cases/:id/run` · 작성 상세)는
  띠가 아니라 **그 건의 서비스**로 화면이 버튼을 가르고 서버가 막는다 — 띠와 다른 서비스의 실행 링크를 열어도 튕기지 않는다 (2026-09-28 코드 검토)

  시나리오 조립 화면은 버튼 · 저장을 열 때의 서비스로 가르고 조립 중 띠를 바꾸면 안내 한 줄만 뜬다(도메인/시나리오 §8.11 「조립」, 2026-10-16 E2E-F1-23).
  자리는 `#/scenarios/:id` 만 한 건 주소이고, `#/scenarios/new`(마법사) · `#/scenarios/new/build`(빈 조립 화면 — 2026-10-23 도메인/시나리오 결정 15) 는 띠 서비스의 실행 칸으로 본다 — 실행 칸이 `none` 인 서비스로 띠를 바꾸면 집으로 옮긴다

#### 알림 — 본문 위 줄 · 「알림」 버튼 · 알림 서랍 (2026-10-11 사용자 · 묶음 3 시안 B · WEB-F3-04)

한 번 돌리면 최악 50분, 작성은 30분 넘게 걸려 자리를 떴다 돌아오는 진입이 흔하다.
본문 맨 위 한 줄로 「지금 무엇이 돌고 얼마나 남았나」와 「아까 그거 끝났나」를 다 받는다.
**앞 판은 진행 중인 실행 하나만 카드로 띄웠다** — 작성과 E2E 실행은 안 보였고, 끝난 소식은 탭을 닫으면 사라졌다.

- **왼쪽 줄에 「알림」 단추가 늘 있다**(2026-10-30 시안 11판 — 위 「껍데기」. 2026-10-13 시안 A 는 맨 위 헤더 오른쪽, 그 앞 판은 본문 맨 위 오른쪽이었다. 휴대폰은 위 줄의 종 — 아래 「휴대폰 화면」). 단추는 종 아이콘이고, 안 읽은 것이 있으면 대표색 점을 단다(위 대표색 목록 「알림 개수 배지」). 수는 읽어 주는 이름(`알림 3건`)과 마우스를 올리면 뜨는 글자가 말한다 — 60px 줄에 숫자 배지를 달면 칸을 넘는다. 0 이면 점이 없다. 새 알림이 오면 점이 한 번 커졌다 돌아온다(DESIGN.md 원칙 4 표).
  누르면 오른쪽에서(휴대폰은 아래에서 전체 화면 판으로) **알림 서랍**이 열린다 — 하던 일을 가로막지 않는 패널이라 뒤를 어둡게 하지 않는다
- **알릴 것이 있으면 본문 맨 위에 줄을 띄운다.** 하나마다 한 줄, 도는 것 먼저(케이스 실행 → E2E 실행 → 작성) 그다음 끝난 것, 각각 새것 먼저.
  **최대 세 줄**이고 넘으면 셋째 자리를 `외 N건 — 알림 열기` 로 쓴다
  - **문구는 `RUN 2113 실행 …` · `#57 작성 요청이 …` 꼴이다** (2026-10-19 ⑫ 사용자 「지금 → 바꿀 문구」 표 A안 · 점검 5.5) — 앞 판 `RUN 2113 이 …` 는 조사가 고정돼 번호 끝소리에 따라 틀렸다(이만천백십삼 → 「이」, 20914 → 「가」여야 한다).
    번호 뒤에 「실행」 · 「작성 요청」을 둬 조사를 그 낱말에 붙인다. 진행 창 · 완료 창 · 중단 확인 창(도메인/실행 §8.3 · §8.9)도 같은 꼴이다
  - **실행 줄에는 제목 · 종류 · 대상 서버를 같이 적는다** (2026-10-19 ⑫ · 점검 5.6) — 번호만으로는 무엇을 어느 서버에 돌린 실행인지 몰랐다. 종류는 `UI 테스트` · `기능 테스트`, 서버는 `대상 서버 qa`
  - 도는 실행 — `RUN 2113 실행 중 · 기능 전체 382건 · 기능 테스트 · 대상 서버 qa · 12 / 40 완료 · 실패 2 · 약 6분 남음 · 14:32 종료 예상` + 작은 진행 막대. 누르면 그 실행 결과(§8.3)

### 등급이 낮아서 못 하는 것은 보이지 않는다

§3.5의 권한을 화면이 지키는 방법은 하나다 — **없앤다.** 제목의 「등급」은 이름으로 불리는 자리라 그대로 둔다 (2026-09-28 기능별 권한으로 바뀜).
흐리게 두면 사람이 그것이 올 때까지 기다린다 (§8.6).
**예외 — 테스트 작성 결정 목록** (2026-10-26) — 버튼은 없애되 항목은 남기고 버튼 자리에 누가 할 일인지 한 줄(「승인 · 반려는 관리자가 합니다」)을 적는다. 고를 일을 한 곳에 모은 목록이라 항목이 사라지면 그 일이 있는 줄 모른다(도메인/작성 §3.6 「★ 결정 목록」)

| 이 권한이 모자라면 | 화면에 없는 것 |
|------|--------------|
| 케이스 `write` | `입력값 묶음 저장` · 지우기 · 다시 스캔 |
| 실행 `write` | `실행` · `실행 멈추기` · **`리포트 생성` 메뉴**(도메인/리포팅 §8.4. 글자를 여기 다시 적지 않는다) · 결정 목록 「결함 판정」 탭의 「이슈 등록」(작성 `write` 와 같이 — 2026-10-26 WEB-F6-05 에 실패 카드 `버그`(2026-10-11)를 옮겼다) |

**★ 어느 할 일이 어느 등급인지는 이 표가 정본이 아니다** (2026-09-22 검토가 잡았다).

- **「입력이 필요한 케이스」가 두 머리를 묶고, 줄의 칩이 무엇을 넣을지로 가른다** — `UNDECIDABLE` 은 `기대값 없음`, `ON_HOLD` 는 `테스트 데이터 없음`(2026-10-19 사용자 · ⑫-10 시작 질문). 왜 넣는지는 그 줄의 「필요한 것」 문장이 말한다.
  같은 날 앞서(⑫-1) 「값 필요」 한 낱말로 두 머리를 대신하고 머리 글자로 가르지 않기로 했다 — 「판정 불가 · 보류」가 QA 말이 아니라서였다. 칩을 QA 말(기대값 · 테스트 데이터)로 바꾸면서 그 까닭이 사라져 다시 갈랐다. 묶는 낱말 「값 필요」는 「입력 필요」로 바꿨다(버튼 「입력」과 같은 말)
- **메뉴 이름과 제품 용어 「케이스」는 이 표가 뒤집지 않는다** — 메뉴는 위 「자리 목록」이 정한다(2026-11-05 부터 「테스트 실행」, 앞 이름 「테스트 스크립트」)
- 화면 글자는 영어 표(`messages/*.ts`)의 키라 글자를 바꾸면 키와 화면 테스트가 찾는 글자도 같이 바꾼다(아래 「키는 한국어 원문이다」)
- **다른 절이 「」로 박아 둔 화면 문구에 왼쪽에 없는 말이 있으면**(예: 리포팅 「실패 요구사항」의 「앞 요청이 반영되거나 폐기되면 시작합니다」 · 작성 §3.6 의 「반영되면 …」) 그 문구가 바뀔 때까지 그 절이 정본이다.
  화면 글자를 이 표대로 바꾼 진행판 WEB-F4-14(2026-10-19)가 그 절의 문구도 같이 고쳤다 — 한쪽만 바꾸면 두 곳이 다른 말을 한다
- **개발자 말은 아래처럼 바꾼다** (2026-10-19 사용자 · WEB-F4-14 시작 질문의 「지금 → 바꿀 문구」 표 승인). 화면 글자만 바꾼다 — 서버가 주는 문장 · 코드 식별자 · 명세 용어는 그대로다.

### 화면을 오가도 하던 일이 풀리지 않는다 (2026-10-19 사용자 · ⑫-2 · 점검 3.3 · 4.2 · 4.5 · 7.3 · 8.4 · 9.1 · 10.3 · 11.4 · 14.1)

상세에 갔다 돌아오거나 메뉴를 잘못 눌러도 고른 것 · 쓴 것이 남아야 한다. 앞 판은 돌아오면 1쪽 · 빈 조건이었고, 쓰던 글이 묻지 않고 사라졌고, 실행할 때마다 대상 서버를 다시 골랐다.

- **목록의 검색 조건과 쪽은 주소에 남는다** — 케이스 목록(도메인/카탈로그 §8.1 「검색 조건」의 조건 전부) · 테스트 작성 목록(쪽 · 「결정 필요」 `todo=1`) · PRD 관리(찾기 글자).
  `#/cases/fn?q=로그인&page=2` 꼴이고, 기본값인 조건은 적지 않는다. 새로고침 · 뒤로 가기 · 상세에 갔다 돌아오기에 풀리지 않는다.
  조건을 바꿀 때 **방문 기록을 쌓지 않고 지금 칸을 고친다** — 칩을 누를 때마다 칸이 쌓이면 뒤로 가기로 목록을 떠날 수 없다. 다른 화면에서 메뉴로 들어오면 빈 조건이다. 보고 있는 목록의 메뉴를 다시 누르면 화면이 든 조건이 그대로 남고 주소도 그 조건으로 되돌린다 — 화면과 주소가 갈리면 새로고침이 조건을 잃는다.
  펼친 줄 · 고른 줄 · 고친 입력값은 주소에 남기지 않는다. 예외는 실행 기록에서 고른 실행(도메인/실행 §8.7 「A안」)과 케이스 목록에서 오른쪽 상세 칸에 연 케이스(`case=<tcId>` · 도메인/카탈로그 §8.1, 2026-10-19 ⑫) · 실행 결과(아래)다. 그 주소가 정본이다.
  **실행 결과도 예외다** (2026-11-04 사용자 · 2026-11-05 ⑱ WEB-F8-03 반영) — 결과 화면(`#/runs/<번호>`)과 실행 기록의 결과 칸의 거르개 · 쪽 · 펼친 카드를 주소에 담는다. 칸은 판정 `status`(`PASS` · `FAIL` · `NA`) · 디바이스 `device` · 직전 대비 `change`(회귀 실패 `new` · 기존 실패 `kept`) · 통과 · 미실행 줄의 쪽 `rowpage` · 실패 카드 쪽 `cardpage` · 실패 원인 칩 `cause` · 「판정 안 한 카드」 `unjudged=1` · 펼친 카드 `open`(케이스 번호를 쉼표로 잇는다)이다(`apps/admin/src/web/runResultView.ts`). 「판정 안 한 카드」는 처음 정할 때 빠졌지만 다른 칩만 남고 그것만 풀리면 이상해 같이 담았다. 모르는 값은 기본값으로 읽는다. 실행 결과는 항목 상세에 갔다 돌아오는 일이 잦아, 돌아올 때마다 1쪽 · 접힌 카드로 풀리면 보던 자리를 다시 찾아야 한다. 다른 목록의 펼친 줄은 그대로 안 남긴다 — 「주소가 길어지고 펼침 하나하나는 다시 찾기 쉽다」는 까닭이 거기서는 여전히 맞다.
  칩 · 쪽 · 카드 펼치기는 기록을 쌓지 않는다(위 검색 조건과 같다). 카드 쪽이나 디바이스를 바꾸면 다른 카드가 서니 펼친 카드를 비운다 — 디바이스를 바꾸면 카드 쪽 · 원인 칩 · 「판정 안 한 카드」도 처음으로 돌아간다. 돌아오면 마지막에 편 카드로 화면을 옮긴다. 다른 화면의 고리가 보내는 `tc=`(도메인/실행 §8.3 「주소로 카드를 펼친 채 연다」)는 어디서 왔든 펼친 카드 `open` 으로 받는다. 그 실행에 풀 단추가 없는 직전 대비(직전 실행이 없거나 그 건수가 0)가 주소로 오면 안 건 것으로 본다 — 단추가 없거나 꺼져 카드가 다 사라진 채 풀 길이 없다. 원인 칩은 그 실행에 없는 유형이면 거르지 않는다. E2E 시나리오 결과(도메인/시나리오 §8.11)는 화면 짜임이 달라 아직 안 담는다
  성능 실행 기록(성능 §8.14)의 「시나리오」 · 「판정」 고르개도 이 줄의 「목록의 검색 조건」에 든다 — `#/perf/runs?scenario=<번호>&verdict=FAIL` 꼴(2026-11-05 ⑱ WEB-F8-03 반영). 애플리케이션을 바꿔 다시 그려질 때 주소의 시나리오 번호가 새 애플리케이션의 목록에 없으면 「전체」로 본다
- **하나를 여는 일은 뒤로 가기 기록을 쌓는다** (2026-11-04 사용자 · ⑱ WEB-F8-01) — 실행 기록의 실행 줄 고르기와 좁은 화면 「목록으로」 · 케이스 목록의 상세 칸 열기와 닫기 · 테스트 작성 「결정 필요」의 탭 · 마법사(새 E2E 시나리오 · 부하 시나리오 · 설정 새로 만들기)의 단계다. 뒤로 가기가 앞에 고른 실행 · 닫힌 상세 · 앞 탭 · 앞 단계로 한 칸씩 돌아간다.
  주소 칸은 실행 `run` · 케이스 `case` · 결정 필요 탭 `decide`(`approve` · `fail` · `check` · `update` — 목록 조건 `todo=1` 과 같이 쓴다) · 마법사 단계 `step`(첫 단계는 적지 않는다)이다. 이 넷만 바뀌면 쌓고, 다른 칸이 바뀌거나 다른 칸도 같이 바뀌면(칩 · 애플리케이션 바꾸기로 화면이 고른 실행을 비울 때 등) 지금 칸을 고친다(`apps/admin/src/web/leaveGuard.tsx` `use주소조건` 의 `쌓는칸` · 마법사는 `useWizardStep.ts` `use단계주소`).
  실행 기록 결과 칸의 칸들(위 「실행 결과도 예외다」)은 고른 실행 `run` 에 딸려, 실행과 같이 바뀌어도 쌓는다(`use주소조건` 의 `딸린칸`) — 다른 실행을 고르면 앞 실행의 거르개가 풀리는 것이 당연하고, 뒤로 가면 앞 실행에 걸어 둔 거르개 · 펼친 카드가 다시 선다. 결과 칸 칸만 바뀌면 지금 칸을 고친다. 애플리케이션을 바꿔 화면이 고른 실행을 버릴 때는 위대로 지금 칸을 고친다 — 사람이 연 것이 아니다(`use주소조건` 의 `스스로`).
  마법사는 단계를 뒤로 가도 쓴 값이 남는다. 첫 단계에서 뒤로 가면 마법사를 떠난다(아래 떠나기 상자가 있는 곳은 묻는다). `step=` 이 든 주소를 새로 열면(새로고침 · 링크) 첫 단계부터다 — 쓴 값은 그 탭의 화면에만 있다.
  케이스 상세 · 결정 필요 · 마법사는 뒤로 가기에 화면을 다시 그리지 않고 칸만 고쳐 고치던 값이 남는다. 실행 기록은 그 칸의 주소대로 다시 그린다.
  떠나기 상자는 그 화면 자기 칸만 바뀌는 뒤로 가기에는 안 뜨고, 다른 칸(쪽 등)도 같이 바뀌면 묻는다.
  **마법사 단계** — 앞으로 가기와 손으로 고친 `step=` 은 그 마법사의 단계 검사를 통과하는 데까지만 가고 주소를 실제 단계로 덮어쓴다(뒤로는 그대로 간다). 마법사가 스스로 옮기는 단계(검사 실패 · 서버 오류로 되돌리기)는 덮어쓴다 — 쌓으면 뒤로 가기가 오류 난 단계로 돌아간다.
  부하 시나리오 마법사는 처음 저장해도 주소 길이 `#/perf/scenarios/new` 그대로이고 번호를 `id=` 칸에 단다 — 길이 바뀌면 화면이 새로 그려져 앞 단계로 돌아갔을 때 쓴 값이 사라지고, 거기서 저장하면 시나리오가 둘 생긴다. 이미 있는 시나리오를 여는 `#/perf/scenarios/<번호>` 는 그대로다 검색 조건 · 칩 · 쪽은 위대로 쌓지 않는다 — 칩마다 쌓이면 목록을 못 떠난다는 까닭이 그대로다.
  앞 판은 고른 실행 · 연 케이스도 조건과 같이 지금 칸을 고쳐서, 실행 셋을 차례로 보다 뒤로 가기를 누르면 실행 기록 밖으로 나갔다. 꼬리표 · 찾기로 하나를 연 뒤에는 뒤로 가기를 두 번 눌러야 떠났다
- **화면이 스스로 옮기는 주소는 기록을 덮어쓴다** (⑱ WEB-F8-01) — 권한이 없는 자리에서 첫 화면으로 · 옛 작성 번호에서 지금 번호로 · 읽기만 하는 사람을 마법사에서 내보낼 때 · 측정 종류에 맞는 성능 화면으로 옮길 때 · 옛 실행 설정 주소의 창을 닫을 때 · 자리 없이 연 설정을 연 애플리케이션 자리로 채울 때(아래 「링크에 애플리케이션이 담긴다」) · 애플리케이션이 하나도 없어 설정을 새로 만들기 마법사로 열 때 · 애플리케이션을 바꿔 다른 애플리케이션의 요구 번호 주소를 맨 PRD(`#/prd`)로 바꿀 때다. 쌓으면 뒤로 가기가 옮기기 전 주소로 가서 다시 옮겨져 그 자리에 갇힌다.
  앱 안의 해시 주소를 덮을 때 `location.replace` 를 쓰지 않는다(2026-11-05 ⑱ WEB-F8-03 — Auth_platform 처럼 앱을 떠나는 이동은 그대로 쓴다, 도메인/인증 §8.6) — 기록 칸 번호(`history.state`)까지 지워 떠나기 막기가 그 칸을 새 칸으로 알고 한 칸씩 어긋난다. `leaveGuard.tsx` `주소덮기` 가 칸 번호를 두고 주소만 바꾼다
- **링크에 애플리케이션이 담긴다** (2026-11-05 ⑱ WEB-F8-02) — 케이스 목록 · 맨 PRD(`#/prd`) · 테스트 작성 목록 · E2E 실행 기록(`#/runs/e2e`)의 주소는 `service=<접두사>`(`service=MKT` — 접두사는 DB 가 겹치지 않게 막는다)를 늘 단다. 다른 화면의 케이스 고리(`route.ts` `케이스주소`)도 번호의 접두사를 단다. 자리 없이 연 설정(`#/settings`)은 연 애플리케이션 자리(`#/settings/MKT`)로 채운다.
  **주소가 띠를 다른 애플리케이션으로 옮기는 길은 여기에 모은다** — 요구 번호 주소(`#/prd/MKT-REQ-001` — 번호의 접두사) · `service=` 칸 · 실행 기록 UI · 기능의 고른 실행(`run=` — 그 실행의 애플리케이션, 도메인/실행 §8.7 「A안」) · 작성 상세(그 요청의 애플리케이션, DESIGN.md 「번호는 하나 · 실행 기록」)다.
  `service=` 는 어느 화면에서나 읽는다(`routeService.ts` `주소의서비스`). 대시보드가 쓰는 번호 꼴(`service=12`)도 받는다 — 붙여 둔 고리가 썩으면 안 된다. `all`(대시보드의 전체)은 아무것도 고르지 않는다.
  연 사람이 그 애플리케이션을 배정받지 않았거나 그 화면의 칸(케이스 · 작성 · 실행)이 `none` 이면 지금 고른 애플리케이션을 그대로 두고 `링크의 애플리케이션은 볼 권한이 없어 지금 고른 애플리케이션으로 엽니다` 한 줄을 5초 띄운다 — 비밀번호를 바꾼 뒤의 확인 줄과 같은 자리 · 같은 모양이고 한 번에 하나만 선다(나중 것이 이긴다). 목록은 주소의 칸을 지금 애플리케이션으로 고친다. 칸이 `none` 인 애플리케이션으로 띠를 옮기면 집으로 튕겨 링크가 가리킨 화면을 아예 못 본다 — 그래서 옮기지 않는다.
  지금 애플리케이션에서도 그 화면을 못 보면 안내 없이 집으로 옮긴다(위 「`none` 인 자리의 주소를 직접 치면」 — 「지금 고른 애플리케이션으로 엽니다」가 틀린 말이 된다). 대시보드도 안내하지 않는다 — 못 보는 번호면 「전체」로 되돌린다(도메인/리포팅 §8.12).
  애플리케이션을 바꾸면(왼쪽 줄 · 대시보드 고르개 · 로그인 뒤 프로젝트 고르기) 주소의 `service=` 칸도 새 것으로 고친다(기록은 안 쌓는다) — 안 고치면 새로고침 · 뒤로 가기가 띠를 앞 애플리케이션으로 되돌린다. 대시보드 주소는 자기 고르개가 번호로 고친다. 설정은 보던 애플리케이션의 자리면 새 것의 자리로 따라가고, 설정 메뉴로 다른 것을 골라 둔 자리는 그대로 둔다. `service=` 는 위 쌓는 칸 넷에 들지 않는다 — 같이 바뀌면 지금 칸을 고친다.
  실행 기록 UI · 기능은 칸을 달지 않는다 — 고른 실행이 띠를 옮긴다. E2E 는 애플리케이션 여럿을 섞어 실행 번호로 하나를 못 고른다 — 그래서 칸이 든다. E2E 시나리오 목록 · 성능 테스트 · 서비스 가이드 · API 문서는 아직 안 단다(띠를 따른다).
  앞 판은 PRD 요구 번호 · 작성 요청 · 실행 기록 UI · 기능 · 결정 필요 고리만 애플리케이션을 따라가서, 다른 애플리케이션을 고른 사람이 케이스 링크를 열면 「조건에 맞는 케이스 없음」이 떴다
- **다시 로그인하면 보던 화면으로 돌아간다** (⑱ WEB-F8-01) — 세션이 끊겨 로그인 화면으로 갔을 때와 로그인 안 된 채 링크를 열었을 때(SSO 설치는 Auth_platform 에 갔다 오는 동안도) 보던 주소를 이 탭에 적어 두고, 로그인되면 그 주소를 기록을 덮어쓰며 연다. 로그인 · 가입 · 비밀번호 주소는 적지 않는다.
  세션이 끊길 때 적는 자리는 먼저 적힌 것이 이긴다(끊김이 잇따라도 처음 보던 화면). 로그인 화면에 있는 동안 주소를 바꾸면 그 주소로 고쳐 적는다. 로그인 화면으로 보내는 칸도 바꿔 끼운다 — 쌓으면 로그인 뒤 같은 주소 칸이 둘 생겨 첫 뒤로 가기가 아무 일도 안 한다.
  서버는 안 바뀐다 — SSO 는 지금처럼 `/?sso=ok` 로 돌아오고 화면이 적어 둔 주소를 꺼낸다(도메인/인증 §8.6 「로그인 화면」). 앞 판은 늘 첫 화면이었다
- **저장 안 한 내용이 있으면 떠나기 전에 묻는다** — 서비스 가이드의 글 · PRD 관리에서 고치던 요구 줄 · 설정의 서비스 칸 · 설정의 새로 만들기 마법사(도메인/인증 §8.8 「새로 만들기 마법사」, 2026-10-23) · E2E 시나리오 조립(도메인/시나리오 §8.11).
  테스트 작성 「결정 필요」의 고른 판정 · 고친 글 · 새 작성 서랍에 쓴 것 · 부하 시나리오 마법사 · 케이스 목록에서 고친 값도 묻는다(2026-11-04 사용자 · 2026-11-05 ⑱ WEB-F8-03 반영 — 앞 판은 다른 화면에 갔다 오면 묻지 않고 사라졌다). 결정 필요는 판정을 하나라도 골랐거나 글이 원래 글과 달라졌을 때(고치기 칸을 열기만 했으면 안 묻는다), 새 작성 서랍은 파일 · 피그마 주소 · 시작 주소를 하나라도 넣었을 때, 부하 마법사는 네 단계 값이 마지막 저장(처음 연 값)과 다를 때, 케이스 목록은 상세 칸에서 값을 고쳤을 때다(저장해 비운 칸은 고친 것이 아니다). 서랍 ✕ 닫기는 주소가 안 바뀌어 묻지 않고, 부하 마법사의 「실행」은 저장한 뒤 실행 화면으로 가는 자기 이동이라 묻지 않는다
  주소가 바뀌는 이동(메뉴 · 고리 · 뒤로 가기)과 프로젝트 · 애플리케이션 고르개를 바꾸는 일(그 화면이 애플리케이션마다 새로 그려질 때만 — 가이드 · PRD)을 멈추고 DESIGN.md 「모달」 ①의 `저장 안 된 변경 있음` 상자를 띄운다 — `머무르기`(첫 포커스) · `저장하지 않고 떠나기`.
  PRD 관리에서 쓴 것이 있는 줄을 접거나 · 그 줄이 든 묶음을 접거나(`모두 접기` 포함) · 다른 줄의 `고치기` 를 누를 때도 같은 상자로 묻는다 — 칸이 내려가 쓴 것이 사라진다(점검 8.4). 아무것도 안 고쳤으면 묻지 않는다.
  고치는 줄은 찾기 글자가 걸러 내지 않는다 — 치는 동안 칸이 사라지면 안 된다. 새 요구 칸에 쓴 글은 줄 접기 · 다른 줄 고치기로 사라지지 않아 그때 묻지 않는다.
  창을 닫거나 새로 고칠 때는 브라우저가 묻는 기본 확인을 쓴다
- **실행 창은 값을 고친 뒤 `Esc` · `취소`로 닫으려 하면 한 번 묻는다** — 상자 안에 상자를 열지 않고 아래 버튼 줄이 `고친 값이 사라집니다` · `계속 고치기` · `닫기`로 바뀐다. 이때 `Esc` 는 `계속 고치기`다. 값을 안 고쳤으면 바로 닫힌다 — 「고쳤다」의 뜻(이 창에서 고쳤고 저장값과도 다르다)은 도메인/실행 §8.10 이 정본이다.
  고친 입력값을 저장할 권한이 있으면 `저장 안 하고 닫기` · `저장하고 닫기`까지 묻는다 — 무엇을 「고쳤다」로 보는지와 그 줄은 도메인/실행 §8.10 「저장 안 한 채 닫으면」이 정본이다 (2026-10-30 WEB-F7-09)
- **대상 서버는 그 서비스에서 마지막으로 고른 것을 미리 고른다** — 실행 창(목록 ▶ · 고른 N건 · 입력 값 수정 후 다시 실행 · 옛 실행 설정 주소) · E2E 시나리오 목록 · 조립 화면 시험 실행. 고르개를 바꿀 때 서비스마다 하나씩 이 브라우저에 적는다(서버는 모른다).
  **고를 수 있는 대상 서버가 하나뿐이면 그것을 미리 고른다**(2026-10-25 GAME-F2-17 — E2E 는 든 애플리케이션 모두에 있는 서버로 센다 · 도메인/시나리오 §8.11) — 고를 것이 하나라 틀린 값이 남을 수 없다. 앞 판은 서버가 qa 하나뿐인 게임도 처음 실행마다 「고르세요」로 떴다.
  화면은 실서비스 서버 표시를 못 받아서(`/auth/me`) 그 하나가 실서비스 서버여도 고른다 — 실행 단추는 사람이 누른다. 성능 테스트의 마법사 · 페이지 성능 · 기기 성능 · 가져오기도 같은 규칙을 쓴다(정기 실행 상자는 이 규칙 밖이라 빈 칸으로 연다). 실서비스 서버 부하는 서버가 막는다(400 `PROD_ENV_BLOCKED`). E2E 마법사의 `지난번에 고른 서버를 미리 골라 두었습니다` 는 이때 안 뜬다.
  **시스템이 정한 기본값은 여전히 없다**(도메인/실행 §8.2) — 이어 쓰는 것은 사람이 직접 고른 값과 하나뿐인 서버다. 서버가 둘 이상인데 처음이거나 고른 서버가 서비스에서 지워졌으면 빈 칸이고 반드시 고른다.
  여는 쪽이 서버를 정해 주면(실패 다시 실행 — 그 실행의 서버) 그것이 이긴다

### 다국어 — 화면 글자는 한국어와 영어 (2026-09-22 결정)

**언어는 둘이다.** `ko` 가 기본이고 `en` 이 있다. 고르개는 **내 메뉴 안**이다(2026-10-30 시안 11판 — 왼쪽 줄 맨 아래 동그라미를 누르면 `한국어 · English` 줄이 있다. 휴대폰은 「전체」 메뉴판의 계정 묶음. 2026-10-13 판은 맨 위 헤더 오른쪽 알림 버튼과 계정 메뉴 사이, 그 앞 판은 사이드바 아래 로그인한 사람 이름 옆이었다). 고른 언어는 **브라우저에 남아 새로고침해도 유지된다.**

- 언어를 바꾸면 **`<html lang>` 과 탭 제목도 따라간다.** `lang` 이 틀리면
  화면 낭독기가 한국어 목소리로 영어를 읽는다
- **언어 고르개는 내 메뉴 안이라 사이드바를 접어도 그대로다**(2026-10-30 — 내 메뉴는 접지 않는 왼쪽 줄에 있다. 2026-10-13 판은 헤더). 앞 판은 사이드바 바닥에 있어 접어도 지우지 않는 규칙이 따로 있었다
- 날짜·시각·숫자 형식도 언어를 따른다. 형식을 손으로 짜지 않는다

#### 키는 한국어 원문이다

표를 **영어 한 벌만** 둔다. 한국어는 키 자체가 답이다.

| | 왜 |
|---|---|
| 표가 하나다 | 두 벌이면 같은 글자를 두 곳에 적고 한쪽이 뒤처진다 |
| 코드가 읽힌다 | `t('진행 중')` 은 무엇이 나올지 그 자리에서 보인다 |
| 빠진 번역이 화면을 안 깨뜨린다 | 표에 없으면 **한국어가 그대로 나온다.** 키가 그대로 나오지 않는다 |

대신 **워딩을 고치면 표의 키도 같이 고쳐야 한다.** 이것이 이 선택의 유일한 약점이고,
**기계가 본다** — 소스와 표를 양방향으로 대조한다 (`apps/admin/src/web/messages.test.ts`).

- **값이 박힌 글자는 자리표로 넣는다** — `t('RUN {번호} 실행 중', { 번호 })`.
  **키는 언제나 정적 문자열이다.** 템플릿 문자열로 쓰면 대조가 그 줄을 못 보고 지나간다.
  그래서 **못 잡는 대신 금지한다** — 첫 인자가 문자열 리터럴이 아닌 호출이 하나라도 있으면 검사가 빨개진다
- **같은 한국어가 자리마다 다른 영어여야 하면** 키 뒤에 괄호로 자리를 붙인다
  (`실행 (버튼)` · `실행 (집계)`). 괄호는 화면에 나오지 않는다
- **새 자리 `테스트 작성` 의 영어는 `Authoring` 이다 (2026-09-22).** 명세가 여기서 못 박는다 —
  다음 세션이 지어내면 자리 이름만 다른 말이 된다.
  **어느 파일에 적을지는 명세가 지목하지 않는다.** 자리 이름들이 이미 messages 표 두 파일로 갈려 있고,
  옆 자리 `테스트 실행`(앞 이름 `테스트 스크립트`) 의 영어는 `messages/shell.ts` 가 아니라 `messages/cases.ts` 쪽에 있다 (실측).
  **어느 쪽에 둘지는 다음 PR 이 정한다.**
  **기계가 이 갈림을 안 잡는다** — 위 대조는 소스와 표를 양방향으로 맞추는 것이라 갈려 있어도 초록이다

#### 옮기지 않는 글자 둘

| 무엇 | 왜 | 어디 |
|---|---|---|
| **케이스가 주는 글자** — 케이스 이름 · 사전조건 · 입력 칸 라벨 | 코드가 진실의 원천이고(§3.1) 폼 라벨은 케이스의 `describe()` 에서 온다([실행.md](../도메인/실행.md) §8.2). 화면이 지어내면 그 순간 둘이 갈린다 | 케이스 파일 |
| **증적 문서** | 검수처에 내는 산출물이다([리포팅.md](../도메인/리포팅.md) §8.4). 화면 언어를 따라가면 **같은 실행의 문서가 둘이 된다** | `reporting/` |

**그래서 영어로 바꿔도 화면의 일부는 한국어로 남는다.** 숨기지 않고 적어 둔다 —
케이스 이름과 입력 칸 라벨은 이 화면에서 사람이 가장 많이 읽는 값이다.

**영어를 쓰는 사람이 실제로 오면 다음 레버는 껍데기가 아니라 케이스다.**
케이스를 영어로 쓰게 하거나 `packages/kit` 의 `describe()` 가 두 언어를 받게 해야 하고,
**뒤엣것은 계약 변경이다** — 그때는 CLAUDE.md §1.2 의 절차로 연다.
여기에 적어 두지 않으면 다음 세션이 껍데기 번역을 더 하는 쪽으로 간다.
