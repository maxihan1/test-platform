## 5. 계약 (변경 시 반드시 이 문서부터 수정)

### 5.1 Shared Kernel 타입

`packages/kit/src/types.ts`. 모든 컨텍스트가 이 타입만 주고받는다.

```ts
export type TcId = string;                         // 'AUTH-002'
export type BrowserPlatform = 'desktop' | 'mobile';   // 브라우저 디바이스. E2E 시나리오는 이것만 받는다
export type Platform = BrowserPlatform | 'android';   // android 는 Appium 으로 폰에서 도는 앱 케이스 (아래 계약 블록)
export type ItemStatus = 'PASS' | 'FAIL' | 'NA';   // 3종을 늘리지 않는다. 늘리면 화면·문서·조회가 동시에 멈춘다.
                                                   // '아직 안 끝남'은 finished_at이 NULL인 것으로 구분한다 (§3.2)
export type JsonSchema = Record<string, unknown>;  // zod 내장 z.toJSONSchema(schema, { io: 'input' }) 출력. 검증하지 않고 그대로 저장·전달한다
export const TECHNIQUES = ['경계값 분석', '동등 분할', '결정 테이블', '상태 전이'] as const;  // 설계 기법 이름. 바꾸지 않는 식별자다 (아래 계약 블록)
export type Technique = (typeof TECHNIQUES)[number];

export interface CaseSpec {
  tcId: TcId;
  name: string;
  platforms: Platform[];        // 비면 ['desktop']. android 는 다른 디바이스와 섞지 않는다 (defineCase 가 던진다)
  precondition: string[];
  paramSchema: JsonSchema;      // zod 내장 변환 결과. 코드에서 null이면 빈 객체 스키마. 비밀값 칸에는 secret: true가 실려 온다 (§4.1)
  expectedSchema: JsonSchema;
  filePath: string;             // 소스 루트 기준 상대 경로
  unconfirmed?: string;         // 있으면 미확정 케이스, 값은 사유 한 문장. 역방향 작성과 정방향의 화면 입력 규칙만 단다 (아래 계약 블록 · 반영 완료)
                                // ↳ 없어진다 (2026-10-10 · 대기 — 아래 「표준 기획서 타입」)
  held?: string;                // 있으면 보류 케이스, 값은 「판정 불가 — 」·「보류 — 」로 시작하는 사유 한 문장. 실행 때 건너뛴다 (아래 계약 블록)
  techniques?: Technique[];     // 그 케이스를 만든 설계 기법. 기능 테스트에만 단다. 비면 키가 없다 (아래 계약 블록)
}

export interface AssertionResult {
  statement: string;            // '응답 코드가 정상이다'
  status: ItemStatus;
  actual: unknown;
  expected: unknown;
  blocker?: boolean;            // true면 이 실패로 실행을 중단했다 (§4 verify 실패 규칙)
}

export interface StepResult {
  seq: number;
  title: string;                // '로그인 API를 호출한다'
  status: ItemStatus;
  durationMs: number;
  assertions: AssertionResult[];
  line?: number;                // 실패한 소스 줄 번호. 코드 뷰가 이 줄을 중심으로 연다
  screenshotPath?: string;      // 실패 시 자동, 또는 capture:true인 스텝
  httpTrace?: { request: unknown; response: unknown };  // API 테스트용
  error?: { message: string; stack?: string };
  skipped?: true;               // 사람이 체크를 풀어 건너뛴 「만들기」 절차 (아래 「E2E 시나리오 타입」 · 반영 완료)
}

export interface ExecuteRequest {
  runId: number;                // 스크린샷 경로 artifacts/runs/{runId}/{historyId}/ 를 만들 때만 쓴다
  historyId: number;
  tcId: TcId;
  platform: Platform;           // Playwright project 이름과 일치시킨다
  filePath: string;
  baseUrl: string;              // 이번 실행이 두드릴 주소. admin이 대상 서버 이름을 주소로 바꿔 싣는다 (§5.2)
  params: Record<string, unknown>;
  expected: Record<string, unknown>;
  timeoutMs: number;            // 기본 300000
}

export interface ExecuteResponse {
  historyId: number;
  status: ItemStatus;
  durationMs: number;
  steps: StepResult[];
  error?: { message: string; stack?: string };
}

export interface StepProgress {   // 절차가 시작될 때 킷이 stdout으로 흘리는 것 (§5.2). 아직 흐른 시간이 없다
  historyId: number;
  seq: number;
  title: string;                  // '로그인 API를 호출한다'. StepResult.title과 같은 문장이다
}

export interface RunningStep extends StepProgress {   // 러너가 GET /progress로 답하는 것 (§5.2)
  elapsedMs: number;              // 이 절차에 머문 시간. 킷이 아니라 러너가 자기 시계로 잰다
}
```

**`totalSteps`(분모)는 없다.** 절차는 케이스 코드가 돌면서 `seq`를 하나씩 올려 선언한다 —
끝나기 전에는 전체 개수를 Playwright도 모르고, 조건에 따라 절차 수가 갈리는 케이스도 있다.
없는 수를 지어내면 「거의 다 됐다」는 **거짓 신호**가 되고, 그것은 모르는 것보다 나쁘다.
분모를 대신하는 것은 **경과 시간과 제한 시간**이다 (§8.9).

`RunningStep`을 화면까지 나르는 admin 조회는 여기에 `timeoutMs`를 하나 더 얹는다 (§7).
러너는 제한 시간을 모른다 — 박제된 자리가 admin의 `run_item`이다 (§7.1).

**`unconfirmed` 는 미확정 꼬리표다** (2026-09-25 · **2026-10-10 대기 — 없어진다**, 아래 「표준 기획서 타입」). 역방향이 기획서와 다른 화면을 보고 만든 임시 케이스와, 정방향이 화면에서 본 기획서에 없는 입력 규칙 케이스(2026-10-02)에만 붙는다.
왜 있는지·언제 풀리는지는 [도메인/작성.md](../도메인/작성.md) §3.6 「★ 역방향 — 화면과 대조한다」가 정본이고,
선언에서 어떻게 적는지(K11)는 [2-명세선언.md](2-명세선언.md) §4 다.

```
[계약 변경 필요]
대상:    CaseSpec (packages/kit/src/types.ts) · defineCase 입력
현재:    CaseSpec 에 미확정 여부가 없다. 화면 값을 기대값으로 쓴 케이스와 기획서로 판정한 케이스를 가를 수 없다
제안:    CaseSpec.unconfirmed?: string — 있으면 미확정, 값은 사유 한 문장
         (예 '기획서와 다름 — 차이 D3: 저장 버튼 이름이 「확인」이다 (작성 요청 5870)'). defineCase({ ..., unconfirmed }) 로 선언한다
이유:    역방향(모드 B) — 도메인/작성 §3.6 「★ 역방향」 (2026-09-25 사용자 · 게이트 0)
영향:    WS-A(kit 타입 · 스캐너 · check:tests K11) · WS-B(run_item 박제 · 실행 집계) · WS-D(증적 미확정 묶음) · WS-작성(역방향 작성)
상태:    반영 완료 (2026-09-25, packages/kit/src/types.ts · packages/kit/src/runtime/defineCase.ts)
```

**`held` 는 보류 꼬리표다** (2026-09-29). 판정 불가 · 보류 요구를 자식이 케이스로 쓰되 사람이 채울 칸을 비워 둔 것에만 붙는다.
공백뿐이면 키가 없는 것으로 친다(`unconfirmed` 와 같은 규칙). `test(spec)` 은 `held` 면 건너뛴다(skip).
왜 있는지 · 언제 풀리는지는 [도메인/작성.md](../도메인/작성.md) §3.6 「★ 보류 케이스 — 사람이 값을 채운다」가 정본이고,
선언에서 어떻게 적는지(K10 예외 · K13)는 [2-명세선언.md](2-명세선언.md) §4 다.

```
[계약 변경 필요]
대상:    CaseSpec (packages/kit/src/types.ts) · defineCase 입력 · test(spec)
현재:    값이 비어 돌 수 없는 케이스를 선언할 길이 없다. 판정 불가 · 보류 요구는 케이스로 안 만든다
제안:    CaseSpec.held?: string — 있으면 보류, 값은 사유 한 문장(머리 「판정 불가 — 」 · 「보류 — 」).
         defineCase({ ..., held }) 로 선언한다. 공백뿐이면 키 없음. test(spec) 은 held 면 건너뛴다
이유:    5877 의 판정 불가 · 보류 15건을 사람이 값을 채워 케이스로 — 도메인/작성 §3.6 「★ 보류 케이스」 (2026-09-29 사용자 · 게이트 0)
영향:    KIT(타입 · defineCase · test) · WS-A(check:tests K10 예외 · K13) · WS-작성(자식 스킬 · 에이전트)
상태:    반영 완료 (2026-09-29, PR #108)
```

**`techniques` 는 설계 기법 목록이다** (2026-10-05). 기능 테스트(`-FN-` · 옛 꼴)에 그 케이스를 만든 기법을 적는다. UI 테스트에는 안 단다.
빈 배열 · 안 적음이면 키가 없다(`unconfirmed` 와 같은 규칙). `defineCase` 는 `TECHNIQUES` 차례로 맞추고 중복을 뺀다.
칸마다 어떤 기법이어야 하는지는 [도메인/작성.md](../도메인/작성.md) §3.6 「설계 기법」, 선언에서 어떻게 적는지(K14)는 [2-명세선언.md](2-명세선언.md) §4,
저장 · 이름을 바꾸지 않는 규칙은 [도메인/카탈로그.md](../도메인/카탈로그.md) §3.1 「설계 기법」, 목록 · 거르기는 같은 장 §7 · §8.1 이 정본이다.

```
[계약 변경 필요]
대상:    CaseSpec (packages/kit/src/types.ts) · defineCase 입력
현재:    케이스가 어떤 설계 기법으로 만들어졌는지 적을 자리가 없다. 기법으로 케이스를 거르지 못한다
제안:    TECHNIQUES = ['경계값 분석', '동등 분할', '결정 테이블', '상태 전이'] as const · Technique ·
         CaseSpec.techniques?: Technique[] — defineCase({ ..., techniques }) 로 선언한다. 비면 키 없음 · TECHNIQUES 차례로 맞추고 중복을 뺀다
이유:    기능 테스트에 설계 기법 표시 · 거르기 — 도메인/작성 §3.6 「설계 기법」 (2026-10-05 사용자 · 게이트 0 · 1)
영향:    KIT(타입 · defineCase) · WS-A(check:tests K14 · 스캐너 · 목록 · 엑셀) · WS-E(목록 화면) · WS-작성(자식 스킬 · 관문 0 · 올리기 판정)
상태:    반영 완료 (2026-10-05, PR #158)
```

**`Platform` 에 `android` 가 더해졌다** (2026-10-07). 앱 케이스는 브라우저가 아니라 Appium 으로 연결한 폰에서 돈다.
브라우저 디바이스만 따로 `BrowserPlatform` 으로 묶어 E2E 시나리오 요청이 그것만 받게 했다. 앱 케이스를 어떻게 적는지는 [2-명세선언.md](2-명세선언.md) §4 「Android 앱 케이스」,
러너가 어떻게 돌리는지 · 환경값 · 한계는 [도메인/러너.md](../도메인/러너.md) §5.2 「앱 실행」이 정본이다.

```
[계약 변경 필요]
대상:    Platform (packages/kit/src/types.ts) · CaseSpec.platforms · ExecuteRequest.platform · K5
현재:    Platform = 'desktop' | 'mobile'. 폰에서 도는 앱 케이스를 선언할 길이 없다
제안:    BrowserPlatform = 'desktop' | 'mobile' · Platform = BrowserPlatform | 'android'.
         android 는 다른 디바이스와 함께 선언하지 않는다 — defineCase 가 「<tcId>: android 는 다른 디바이스와 함께 선언하지 않는다」로 던지고 스캐너가 실패 사유로 싣는다.
         K5 허용 값은 desktop · mobile · android. ScenarioExecuteRequest.platform 은 BrowserPlatform 으로 좁힌다
이유:    Android 앱 자동화(Appium) — 도메인/러너 §5.2 「앱 실행」 (2026-10-07 사용자 · 게이트 1)
영향:    KIT(타입 · defineCase) · WS-A(K5 · 스캐너) · WS-C(러너 /execute · playwright.config.ts) · WS-B(실행 통로가 android 를 보내는 것 — 다음 PR) · WS-E(디바이스 고르기 · 표시 — 다음 PR) · WS-D(증적 디바이스 칸 — 다음 PR)
상태:    반영 완료 (2026-10-07, packages/kit/src/types.ts · packages/kit/src/runtime/defineCase.ts · apps/admin/src/catalog/rules.ts — PR #171)
```

```
[계약 변경 필요]
대상:    kit test(spec, body) 본문 인자
현재:    본문 인자는 { page, request, params, expected } 뿐이다
제안:    platforms 에 android 가 있으면 앱 케이스다. 본문 인자는 { driver, request, params, expected } — driver 는 WebdriverIO(Appium) 연결이고 page 가 없다.
```

#### E2E 시나리오 타입 (2026-09-28)

**무엇이고 왜인지는 [도메인/시나리오.md](../도메인/시나리오.md) §3.7 이 정본이다.** 여기는 admin 과 러너가 주고받는 모양만 적는다.

```ts
export type ScenarioPart =                         // 부품 목록의 정본은 도메인/시나리오 §3.7 「부품」 표
  | { kind: 'case'; tcId: TcId; params: Record<string, unknown>; expected: Record<string, unknown>;
      skipSteps: string[];                         // 건너뛸 「만들기」 절차 제목. 비면 전부 돈다
      carryOver?: boolean;                         // 넘겨받기. 없으면 true. false 면 skipSteps · links 가 비어야 한다 (결정 12)
      links?: ScenarioLink[] }                     // 이어 주기. 비면 없다 (결정 12)
  | { kind: 'api'; method: 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE'; path: string;   // '/' 로 시작. baseUrl 기준
      body?: unknown; expectStatus: number }
  | { kind: 'mock'; urlPattern: string; status: number; contentType: string; body: string }  // urlPattern 은 Playwright glob
  | { kind: 'unmock'; urlPattern: string }         // 같은 글자로 건 mock 을 푼다
  | { kind: 'wait'; ms: number };                  // 60000 까지

// 이어 주기 중 조립하는 사람이 거는 넷. 무엇을 · 언제만 거는지는 도메인/시나리오 §3.7 결정 12 표가 정본이다 (2026-10-06)
export type ScenarioLink =
  | { kind: 'reuse'; method: ScenarioMethod; urlPattern: string; fromSeq: number }   // 앞 응답 돌려주기
  | { kind: 'block'; method: ScenarioMethod; urlPattern: string }                    // 요청 막기. 200 {} 를 준다
  | { kind: 'rewrite'; method: ScenarioMethod; urlPattern: string;                   // 바꿔 보내기. 본문은 그대로
      to: { method: 'PUT' | 'PATCH'; path: string; value: ScenarioResponseRef } }   // path 의 {} 자리에 value
  | { kind: 'bind'; param: string; value: ScenarioResponseRef };                      // 값 꽂기. params 의 그 칸

export type ScenarioMethod = 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';

export interface ScenarioResponseRef {             // 앞 부품이 받은 응답에서 값 하나
  fromSeq: number;                                 // 자기보다 앞의 case 부품
  method: ScenarioMethod;
  urlPattern: string;                              // 그 부품에서 이 무늬에 처음 맞은 응답
  jsonPath: string;                                // 응답 JSON 본문의 점 표기 경로. 'data.id'
}

export interface ScenarioExecuteRequest {          // POST /execute-scenario (도메인/러너 §5.2)
  runId: number | null;                            // null 이면 시험 실행. 기록이 없다
  trialId?: string;                                // 시험 실행일 때만. admin 이 만든 UUID
  platform: BrowserPlatform;
  baseUrl: string;
  parts: Array<ScenarioPart & { filePath?: string }>;   // case 부품에만 filePath 를 admin 이 채워 보낸다
  timeoutMs: number;
}

export interface ScenarioPartResult {
  seq: number;                                     // 1부터. 부품 순서
  status: ItemStatus;                              // 안 돈 부품은 NA + error.message 'NOT_RUN'
  durationMs: number;
  steps: StepResult[];                             // case 부품만 찬다. 순번은 시나리오 전체에서 이어진다
  mocks: string[];                                 // 이 부품이 도는 동안 걸려 있던 mock 의 urlPattern
  bound?: Record<string, unknown>;                 // 값 꽂기로 넣은 값 (결정 12)
  error?: { message: string; stack?: string };
}

export interface ScenarioExecuteResponse {
  status: ItemStatus;                              // 부품이 전부 PASS 일 때만 PASS. 뒷정리 결과는 판정에 안 든다
  durationMs: number;
  parts: ScenarioPartResult[];
  cleanup?: ScenarioCleanup[];                     // 시나리오 끝에 보낸 미룬 삭제, 보낸 순서대로. 제한 시간에 끊기면 없다 (결정 12)
  error?: { message: string; stack?: string };     // TIMEOUT · 러너 고장
}

export interface ScenarioCleanup {
  fromSeq: number;                                 // 삭제를 미룬 부품
  method: 'DELETE';
  url: string;
  status?: number;                                 // 응답 코드. 못 보냈으면 없고 error 가 찬다
  error?: string;
}
```

**`StepResult` 에 `skipped?: true` 가 붙는다.** 사람이 체크를 풀어 건너뛴 「만들기」 절차다 — 판정이 없고 `PASS` 로 적되
증적이 「준비 실행 건너뜀」으로 그린다. 없는 절차로 빼 버리면 순번이 비고 「이 케이스가 준비를 세웠다」로 읽힌다.

**kit 이 두 가지를 새로 할 줄 알아야 한다** (설계서 「13. 새로 만들 것」의 kit 행).
① **케이스 본체를 꺼내 쓴다** — `defineTest` 첫 줄의 `PLATFORM_SCAN` 분기와 같은 자리에 시나리오 모드를 하나 더 낸다.
그 모드에서는 Playwright 에 등록하지 않고 본체를 넘겨준다. **`RunScope` 하나를 여러 본체에 꿴다** — 본체마다 새로 만들면 스크린샷 순번이 다시 1부터라 서로를 덮는다.
**넘겨주는 것은 본체가 아니라 그 케이스의 kit 으로 감싼 실행 함수다** (2026-09-28 구현) — 본체 안 `step()` 은 자기 kit 의 문맥을 읽으므로 다른 kit 인스턴스가 감싸면 문맥을 못 찾는다.
실행 함수는 `globalThis` 등록부에 `tcId` 로 오르고(`@platform/kit/scenario`), 앞 부품까지 쓴 순번을 받아 이어 매긴다 — 「`RunScope` 하나」는 **순번이 이어진다**는 뜻으로 지켰다.
부를 때마다 실패 표시·건너뛸 제목·결과 모으기를 새로 세우고, 본체 예외도 안에서 잡아 `{ steps, failed, error }` 로 돌려준다
② **절차를 제목으로 건너뛴다** — `step()` 이 `RunScope` 의 「건너뛸 제목」에 든 절차를 돌리지 않고 `skipped` 로 적는다.
번호는 `runStep` 이 매기므로 번호가 아니라 제목으로 지목한다. 그래서 K12 가 제목을 케이스 안에서 유일하게 가둔다([2-명세선언.md](2-명세선언.md) §4)

### 5.3 나중을 위한 이음새

이음새는 '나중에 갈아 끼울 수 있다'는 뜻이지 '지금 아무 준비도 필요 없다'는 뜻이 아니다.
전제를 안 적어 두면 갈아 끼우는 날 조용히 틀린 결과가 나온다. (2026-09-16 결정)

| 확장 | 바꿀 곳 | 전제와 영향 |
|------|--------|-----------|
| 러너 여러 대 | Execution의 디스패처가 러너 URL 목록을 라운드로빈. 중단(`POST /abort`)은 그 항목을 맡은 러너에게만 보낸다. **진행(`GET /progress`)은 반대로 모든 러너에게 물어 합친다** — 당김이라(§5.2) 어느 러너가 무엇을 들고 있는지는 묻기 전에 알 수 없다 | **artifacts 볼륨을 모든 러너가 같이 본다는 것이 전제다.** 스크린샷 경로가 `artifacts/runs/…` 한 뿌리뿐이라(§9 — 시나리오 실행·시험 실행도 같은 뿌리 아래다, 2026-09-28), 러너마다 다른 디스크에 쓰면 admin이 절반을 못 찾는다. 파일시스템을 못 나누면 러너를 늘리기 전에 S3 쪽을 먼저 해야 한다. **진행을 합치는 것 자체는 안전하다** — admin이 자기 `run_item`의 `historyId`와 교집합만 내므로(§7) 러너가 몇 대든 남의 것이 섞이지 않는다. 한 대에 못 닿으면 **그 러너 몫만 빠진다.** 전체를 실패로 만들지 않는다 |
| 메시지 큐 도입 | `POST /execute` 호출부를 큐 발행으로 교체 + 콜백 수신 엔드포인트 추가 | 큐는 같은 메시지를 **두 번 줄 수 있다.** 중복인지는 `historyId`로 가려내고, 결과 되쓰기 UPDATE에는 `AND finished_at IS NULL`을 붙여 **먼저 온 것만** 기록한다. 이 가드는 중단과 결과 도착이 겹칠 때도 같은 일을 하므로 큐 없이도 지금 넣어 둔다. Runner 내부 로직은 안 바뀐다 |
| S3 배포 | 테스트 소스를 내려받아 `PLATFORM_TESTS_DIR` 폴더를 **채우는 단계**만 앞에 붙인다 | 경로 자체를 `s3://`로 바꾸지 않는다. 스캐너는 파일을 동적 import 하고 러너는 그 경로로 `npx playwright test`를 돌리므로, 로컬 경로가 아니면 둘 다 깨진다. 바꾸는 것은 '어디서 받아오는가'이고 '무엇을 읽는가'는 그대로다 |
| 검색엔진 도입 | Catalog의 검색 함수 **하나**를 엔진 질의로 교체 | 전제가 넷이다. ① 검색 호출이 함수 하나에 모여 있어야 한다. 화면이나 라우트에서 SQL을 직접 짜면 갈아 끼울 자리가 여러 곳이 된다 ② 색인 대상은 **케이스 속성**뿐이다. `마지막 결과`는 색인하지 않는다 — 실행할 때마다 바뀌어 색인이 조용히 어긋난다 ③ 정렬이 **관련도순**으로 바뀐다. 응답의 `sort`에 정렬 기준을 실어 보내고 화면은 순서를 전제하지 않는다 ④ `총 N건`이 **근사치일 수 있다.** `totalIsExact`가 false면 화면은 이 값으로 페이지 수를 계산하지 않는다 |

검색엔진을 지금 붙이지 않는 이유는 §1 「범위 밖」에, 검색 조건과 화면 규칙은 §8.1에 있다.

**이 이음새를 지키는 유일한 규칙: 러너는 DB를 모른다.**

### 7.1 Execution · 검색 · 인증에 대한 결정 (2026-09-16)

| 무엇 | 정한 것 | 왜 |
|------|--------|-----|
| `triggeredBy` | **요청에 싣지 않는다.** 로그인한 세션의 아이디가 `test_run.triggered_by`로, 그때의 이름이 `test_run.triggered_by_name`으로 들어간다 (2026-09-16 수정) | 화면이 보내는 값은 아무나 적을 수 있어 실행자를 가리지 못한다. 인증이 생겼으므로 요청이 정할 자리가 아니다 |
| `timeoutMs` | 항목마다 생략 가능. 없으면 `300000`. 쓴 값을 `run_item.timeout_ms`에 박제한다. `300000` 을 넘으면 400 — 기본값이 곧 상한이다(2026-10-07 · 정본 도메인/실행 §7 `POST /api/runs`) | §10의 `DEMO-007`을 "`timeoutMs`를 5000으로 준 실행"으로 검증하려면 요청에서 정할 수 있어야 한다. 박제하지 않으면 나중에 타임아웃 `NA`를 볼 때 몇 초를 줬는지 알 수 없다 |
| `GET /api/runs` | `?service=` 는 필수. `?q=`(제목 일부) · `?state=running\|failed` · `?env=` 로 좁힌다 (2026-09-22 ②). **`?kind=ui\|fn\|case\|scenario` 로 가른다 — 없으면 `case`(UI · FN 둘 다)** (2026-09-28, 도메인/시나리오 §3.7 결정 10. 기본값이 `case` 여야 옛 화면이 시나리오 실행을 케이스 실행으로 안 읽는다. `ui` · `fn` 은 2026-10-02 PR #131 — 종류는 공통/4-데이터모델 「실행 종류」). 응답에 `summary` 가 실린다 — **거른 뒤의 집합**을 센 실행 횟수 · 성공 · 실패 · 평균 소요. **`state` 의 `failed` 는 `test_run.status` 가 아니다** — 「실패 항목이 하나라도 있는 실행」이라 집계에서 나온다 | §8.7 실행 기록 화면의 집계 띠와 거르개 때문이다. **화면이 거르면 안 된다** — 목록이 쪽으로 나뉘어 오므로 받은 쪽만 거르면 뒤쪽이 조용히 빠진다. 집계도 같은 조건으로 좁힌다 — 안 그러면 세 줄 보이는 화면이 「42회」라고 말한다 |
| `GET /api/runs/last-by-case` | 끝난 항목만, 케이스×디바이스마다 **최신 1건 + 최근 5회 판정**(`recent`, 새 것부터. 2026-09-21 ② 에 더했다). **최신은 「가장 마지막 회차」다** — 반복 5회 중 3승 2패면 마지막 회차의 판정이 그대로 배지가 된다. 승패를 요약하지 않는다 (2026-09-17 확정. 회차별 승패는 §8.3 회차 요약에서 본다). **`recent` 도 요약이 아니다** — 다섯 판정을 그대로 늘어놓는 것이고 배지는 여전히 맨 앞 하나다 | §8.1 목록의 `마지막 결과` 칸과 **판정 흐름 막대** 때문이다. 케이스마다 이력을 따로 부르면 10건일 때 요청이 11번이 된다. **흐름을 같은 응답에 얹은 이유가 그것이다** — 부르는 횟수는 그대로 1회다. 카탈로그가 `run_item`을 읽으면 컨텍스트 경계가 깨지므로 실행 쪽이 낸다 |
| `env` · `base_url` | 요청은 **키만** 싣는다. 주소는 **그 서비스의** `service_env` 표(§6)에서 찾아 `test_run.base_url`에 박는다 | 요청이 주소를 실으면 아무 데나 쏠 수 있다. 매핑은 바뀌므로 그날 친 주소는 따로 남겨야 한다 |
| `repeat` | 요청 **최상위에 1개**. 기본 1. `repeat` 자체에는 상한을 두지 않고 **만들어질 실행 항목 건수**로 막는다 (2026-09-17 수정) | 목적은 새로 쓴 테스트 코드가 안정적인지 여러 번 돌려 보는 것이다. 항목마다 두면 `run_item` 개수 계산이 항목별로 갈라져 §8.2의 안내 문구를 못 만든다. **상한을 「두지 않는다」였던 것을 고쳤다** — 근거였던 동시 실행 2는 *돌아가는 프로세스 수*를 막지 *INSERT 건수*를 막지 않는다. 디바이스를 둘씩 선언한 케이스 10건이면 디바이스 수의 합이 20이고, `repeat` 10만이면 `run_item` 200만 행이 요청 한 번에 들어간다. **상한의 자리와 숫자도, 건수를 세는 식도 §8.2가 정본이다** (2026-09-21에 예시를 §8.2의 합 식에 맞췄다 — 앞 판의 `케이스 10 × 디바이스 2 × repeat 10만`은 모든 케이스의 디바이스 수가 같을 때만 맞는 곱셈이었다) |
| 자동 재시도 | Playwright의 `retries`는 **0으로 고정한다.** 켜려면 SPEC 변경이 먼저다 | 실패를 가리려고 다시 돌리는 것과, 실패를 드러내려고 여러 번 돌리는 것은 다른 일이다. 반복은 `repeat`가 한다 |
| `POST /api/runs/:runId/abort` | 대기 중 항목은 줄에서 빼고 `NA` + 사유로 닫고, **진행 중 항목도 끊는다.** `test_run.status = ABORTED` | `ABORTED`가 스키마에 있는데 쓰는 코드가 한 줄도 없었다. 대기만 취소하면 5분짜리가 계속 돌아 사용자에게는 멈추지 않은 것으로 보인다 |
| 중단과 결과의 경합 | 결과 되쓰기 UPDATE에 `AND finished_at IS NULL`을 붙인다 | 중단이 닫은 항목에 뒤늦게 도착한 결과가 덮어쓰면 무엇이 진짜인지 알 수 없다. **먼저 온 것만** 기록한다 |
| admin 재기동 복구 | 부팅 직후 `status = 'RUNNING'`인 실행의 미완 항목을 닫고 실행을 `ABORTED`로 바꾼다. 중단과 같은 처리다 | 디스패처는 메모리에만 있다. 재기동하면 이어갈 주체가 없는데 `RUNNING`으로 남아 영원히 진행 중인 것처럼 보인다 |
| 서비스 이름 · 테스트 저장소 | 요청은 서비스를 싣지 않는다. 서버가 `tcId` 접두사로 서비스를 알아내 `test_run.service_id`와 스냅샷 `service_name`·`tests_repo`에 박는다. 플랫폼이 저장소에서 직접 받아오지는 않는다 | 서비스마다 다른 저장소를 본다. "어디서 무엇을 시험한 것인가"가 증적 문서에 남아야 한다. 접두사가 섞인 요청은 400이다 — **한 실행은 한 서비스**다 (§7 인증 적용 범위) |
| 검색 조건 | 케이스 속성(§8.1 검색 조건 표에서 거르는 곳이 「서버」인 줄)은 **서버가**, `마지막 결과`는 **화면이** 거른다. 서비스는 조건이 아니라 **사이드바 서비스 고르개의 선택**이고 서버가 늘 적용한다 (고르개의 정본은 공통/5-화면공통 §8) (2026-09-17 수정 — 목록이 한 서비스로 좁혀지면 그 안의 접두사는 전부 같아서 거를 것이 없다). 조건 정의는 §8.1이 정본이다 | 마지막 결과는 실행할 때마다 바뀐다. 카탈로그가 `run_item`을 읽으면 컨텍스트 경계가 깨진다 (§3.1) |
| 검색 응답 | `sort`와 `totalIsExact`를 같이 준다 | 나중에 검색엔진을 붙이면 정렬이 관련도순으로 바뀌고 건수가 근사치가 된다. 화면이 지금 모양을 전제하면 그때 깨진다 (§5.3) |
| 로그인 | 아이디·비밀번호 1종. **권한은 운영 여부 + 서비스마다 기능 셋 × 세 칸 + 대시보드 한 칸**, 계정은 회원가입 → admin 수락. 팀·실행 승인 절차는 만들지 않는다 (2026-09-17 수정 · 2026-09-28 기능별 권한) | 공용 비밀번호 하나는 누가 눌렀는지 못 가린다. 권한 구분은 설정 화면(§8.8)이 생기면서 필요해졌고, 설치형 납품에서 회사마다 역할이 달라 등급 셋이 기능별 칸으로 바뀌었다. 뒤집은 근거는 §3.5 와 §6의 「권한 칸」 문단에 남겨 뒀다 |

`POST /api/runs`가 실행이 끝날 때까지 기다리지 않는 이유도 같은 자리에 적어 둔다.
케이스 1건에 최대 5분을 줄 수 있으므로 기다리면 화면이 그만큼 멈춘다.
끝났는지는 `GET /api/runs/:runId`의 `status`가 `FINISHED`인지로 본다 (§3.2 불변식).

**인증 이전에 쌓인 실행의 실행자는 믿을 수 없다** (2026-09-16 결정).
로그인이 없던 동안 `triggered_by`에는 요청이 적어 보낸 값이나 기본값 `'admin'`이 들어갔다.
그 값을 사람 이름처럼 보여주면 증적 문서가 없는 근거를 만들어 낸다.

**구분 규칙.** `test_run.triggered_by_name`이 `NULL`이면 인증 도입 이전 실행이다.
화면과 증적 문서의 실행자 칸에 **`실행자 미상 (인증 도입 이전)`** 이라고 쓴다.
실행 시각으로 가르지 않는다. 마이그레이션 적용 시각과 배포 시각이 어긋나면
경계에 걸친 실행을 잘못 분류한다.
`triggered_by`에 남아 있는 옛 값은 지우지 않고 그대로 두되 사람 이름 자리에 쓰지 않는다.
지우면 그 자리에 무엇이 있었는지조차 알 수 없어진다.
