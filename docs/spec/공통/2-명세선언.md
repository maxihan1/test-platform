# 명세 선언 방식

> **이 장이 담는 절** — §4 명세 선언 · §4.1 비밀값 꼬리표
> 케이스를 만들거나 읽는 갈래(WS-A 카탈로그 · WS-C 러너)가 읽는다. 선언 하나가 입력 폼·검증·증적 문서를 전부 만든다.
> 전체 목차와 작업별 읽기 동선은 [SPEC.md](../../SPEC.md).

---

## 4. 명세 선언 방식 (가장 중요)

테스트 코드 안에 명세를 함께 선언한다. 이 선언 하나가 **입력 폼 · 검증 · 증적 문서**를 전부 만든다.

```ts
// tests/auth/login.spec.ts
import { defineCase, test, verify } from '@platform/kit';
import { z } from 'zod';

export const spec = defineCase({
  tcId: 'AUTH-002',
  name: '유효한 이메일과 비밀번호로 로그인하면 토큰이 발급된다',
  platforms: ['desktop', 'mobile'],     // 생략 시 ['desktop']
  precondition: [
    '가입 완료된 사용자 계정이 존재한다',
    '계정이 잠금 상태가 아니다',
  ],
  params: z.object({
    username: z.string().min(1).describe('아이디'),
    password: z.string().min(1).describe('비밀번호').meta({ secret: true }),
  }),
  expected: z.object({
    statusCode: z.number().describe('응답 코드'),
    hasToken:   z.boolean().describe('토큰이 발급되는지'),
  }),
});

test(spec, async ({ page, request, params, expected }) => {
  const res = await test.step('로그인 API를 호출한다', async () => {
    const res = await request.post('/api/login', { data: params });
    await verify('응답 코드가 기대값과 같다', res.status(), expected.statusCode, { blocker: true });
    return res;
  });

  await test.step('토큰을 확인한다', async () => {
    const body = await res.json();
    await verify('토큰이 발급된다', !!body.token, expected.hasToken);
  });

  await test.step('로그인 후 화면을 확인한다', async () => {
    await page.goto('/dashboard');
  }, { capture: true });
});
```

### 각 필드가 어디에 쓰이는가

| 필드 | 쓰이는 곳 |
|------|----------|
| `tcId` | 검색, 파라미터 주입 키, 증적 문서 항목 번호, 이력 추적 |
| `platforms` | 실행 화면의 디바이스 선택지, 실행 시 생성될 `RunItem` 개수. 값은 `desktop` · `mobile` · `android` 이고 `android` 는 다른 값과 섞지 않는다 — 폰에서 도는 앱 케이스다 (아래 「Android 앱 케이스」) |
| `name` | 목록 화면, 증적 문서 "검증 항목" 칸 |
| `precondition` | 증적 문서 "사전조건" 칸 |
| `params` | **입력 폼 자동 생성** (`describe`가 한글 라벨, `enum`이면 드롭다운, `optional`이면 선택 입력), 실행 전 검증 |
| `expected` | 기대값 입력 폼, 증적 문서 "기대결과" 칸 |
| `test.step` | 증적 문서 "시험 절차" 칸, 실패 지점 표시 |
| `verify` | 증적 문서 "판정" 칸, 검증 문장 단위 PASS/FAIL |
| `unconfirmed` | **없앴다 (2026-10-11 PRD-F4-05)** — 앞 판의 미확정 꼬리표(사유 한 문장)였다. kit 이 이 칸을 받지 않아 적으면 타입 검사가 막는다. 미확정은 케이스가 덮는 표준 기획서 항목 상태에서 계산하고 목록 · 실행 · 증적에 「미확정」으로 보인다([작성.md](../도메인/작성.md) §3.6 「★ 표준 기획서」 「미확정」 · [3-공유계약.md](3-공유계약.md) 「표준 기획서 타입」) |
| `held` | 보류 케이스 꼬리표. 값은 머리(`판정 불가 — ` · `보류 — `)로 시작하는 사유 한 문장이다. 있으면 실행 때 건너뛰고, 사람이 작성 상세에서 비운 칸을 채우거나 케이스를 제거한 뒤 반영된다. **초안 PR 에만 있다** — main 에 들어가지 않는다. 정본은 [작성.md](../도메인/작성.md) §3.6 「★ 보류 케이스 — 사람이 값을 채운다」 (2026-09-29) |
| `techniques` | 기능 테스트 목록 줄의 기법 태그와 「설계 기법」 고르개, 케이스 상세의 「설계 기법」 구획, 케이스 엑셀 시트 ① 맨 끝의 「설계 기법」 열(UI 테스트만 받을 때는 없다)([카탈로그.md](../도메인/카탈로그.md) §7 · §8.1). 값은 설계 기법 이름의 배열이고 **낱말 목록의 정본은 kit `TECHNIQUES`** 다. **기능 테스트(`-FN-` · 옛 꼴)에만 단다** — UI 테스트에는 안 단다(K14). 작성 에이전트가 적고 관문 0 · 올리기 판정이 그 칸의 기대 기법과 견준다 — 칸마다 무엇이어야 하는지는 [작성.md](../도메인/작성.md) §3.6 「설계 기법」. 사람이 쓴 케이스는 안 적어도 된다. 실행 기록 · 증적에는 안 남는다 (2026-10-05 · PR #158) |
| `elements` | 게임 케이스만 · 닿는 게임 요소 열쇠(`item:sword_long` · `zone:Town`)의 배열. kit 이 겹침을 빼고 차례를 맞추며 비면 키를 안 싣는다. 작성 빠른 검사가 게임 지도에 있는지 보고 스캐너가 `test_case.elements` 와 요소를 거친 케이스 표에 넣는다(2026-10-23 GAME-F1-12 — 저장소 전체 형식 검사 K 표는 안 본다. 어느 케이스가 게임인지 작성 에이전트만 안다). 꼴은 [3-공유계약.md](3-공유계약.md) 「게임 테스트 타입」 (2026-10-23 GAME-F1-09) |
| `smoke` | 스모크 표시(`true` 일 때만 싣는다). 빌드마다 먼저 도는 핵심 경로 케이스 — 웹 · 앱 · 게임 다 쓴다([실행.md](../도메인/실행.md) §3.11 「빌드마다 돌리기」). 스캐너가 `test_case.smoke` 에 담고 사람이 목록에서 고친 값은 `smoke_set` 이 이긴다 (2026-10-23 GAME-F1-09 · 스캐너 · 목록은 2026-10-24 GAME-F1-13) |

`spec`은 반드시 `export const spec`으로 내보낸다. 스캐너가 이 이름을 찾는다 (§3.1).

`verify(문장, 실제값, 기대값, { blocker?: true })` — 앞의 세 인자를 그대로 결과에 남긴다.
`expect`를 직접 쓰면 문장이 남지 않으므로 **테스트 코드에서 `expect` 직접 사용을 금지**한다.

### verify 실패 규칙 (2026-09-16 결정)

- `verify`는 **절차(`test.step`) 안에서만** 부른다. 밖에서 부르면 kit이 에러를 던진다.
  화면과 증적 문서가 절차 아래에 검증 문장을 보여주는 구조이기 때문이다
- 실패해도 **기본은 계속 간다.** 그 문장은 FAIL로 기록되고 다음 문장·다음 절차를 계속 돌린다.
  화면 문구가 바뀐 정도의 실패로 뒤 절차까지 버리지 않기 위해서다
- 뒤를 돌릴 의미가 없는 검증에는 `{ blocker: true }`를 붙인다. 이 문장이 실패하면 **그 절차를 끝으로 멈춘다.**
  로그인 실패처럼 뒤 절차의 전제가 무너지는 경우다. 시스템은 값만 보고 사유를 알 수 없으므로 작성자가 표시한다
- 예외(요소를 못 찾음, 페이지가 안 뜸 등)는 코드가 더 갈 수 없으므로 **항상 멈춘다.** 그 절차는 FAIL + `error`
- 판정: 검증 문장이 하나라도 FAIL이면 절차도 항목도 FAIL. 멈춘 뒤 돌지 않은 절차는 문서에 나오지 않는다
  (절차는 실행해 봐야 알 수 있다). 대신 멈추게 한 문장에 `실행 중단`을 표시해 뒤가 왜 없는지 알린다

### 테스트 코드에는 주석을 쓰지 않는다

주석이 들어갈 자리를 이미 선언이 가져갔다.

| 적고 싶은 것 | 적을 자리 |
|-------------|----------|
| 이 테스트가 무엇을 검증하는가 | `name` |
| 어떤 상태를 전제하는가 | `precondition` |
| 이 단계에서 무엇을 하는가 | `test.step`의 제목 |
| 여기서 무엇을 확인하는가 | `verify`의 문장 |

주석은 화면에도 증적 문서에도 나오지 않는다. 같은 설명이 두 군데 생기면
코드를 고칠 때 한쪽만 고쳐져 주석이 거짓말을 시작한다.

**적용 범위**: `tests/**` 만. 러너·스캐너 등 플랫폼 코드는 CLAUDE.md의
기존 규칙(왜만 적는다)을 따른다.

### 케이스 파일 규칙 — `npm run check:tests`가 기계로 검사한다 (2026-09-16 결정)

테스트 코드는 사람이 쓸 수도 있다. 그래서 아래 규칙은 Claude 훅이 아니라 **CI가** 검사한다.
2026-09-18 부터 CI 는 **PR 을 Ready 로 바꿀 때와 Ready 상태에서 푸시할 때** 돈다 —
초안 PR 에서는 돌지 않는다 (`docs/HOOKS.md` 「CI 와 병합 차단」).
**테스트만 바뀐 PR 은 가벼운 길로 돈다** (2026-09-23) — 이 표(아래 K 표 가운데 검사기에 반영된 것)와 타입·비밀값 이름은 보지만 케이스를 실행하지 않는다.
무엇이 「테스트만」인지의 정본은 같은 `docs/HOOKS.md` 절이고, 병합 근거가 무엇인지는 [작성.md](../도메인/작성.md) §3.6 「작성 에이전트는 전용 체인이다」.

검사기는 WS-A의 스캐너를 저장 없이 돌리는 모드이며, 어긋나면 `파일:줄 — 무엇이 — 왜 문제` 한 줄로 알린다.
파일을 주면(`npm run check:tests -- <파일…>`) 그 파일만 보고 K2 겹침만 나머지 케이스와 견준다 — 작성 보조가 쓴다([작성.md](../도메인/작성.md) §3.6 「빠른 검사 명령」 · 2026-10-22 PRD-F14-04).
**아래 표 가운데 검사기에 반영된 것을 CI 가 본다** (K9·K10 은 2026-09-18, K11 은 2026-09-25(2026-10-11 PRD-F4-05 에서 뺐다), K12 는 2026-09-29, K13 과 K10 의 `held` 예외는 2026-09-29 PR #108, K14 는 2026-10-05 PR #158, K15 는 2026-10-16 PRD-F10-02 에 반영됐다).

| # | 규칙 | 어기면 무엇이 안 되나 |
|---|------|---------------------|
| K1 | 파일 1개 = 케이스 1건. `export const spec = defineCase(...)`가 정확히 하나 | 스캐너가 명세를 못 찾는다 |
| K2 | `tcId`가 `<접두사>-<3자리>` · `<접두사>-UI-<3자리>` · `<접두사>-FN-<3자리>` 셋 중 하나이고 전체에서 유일(2026-10-02 · PR #129 에서 두 꼴을 더했다). 접두사는 `^[A-Z][A-Z0-9]{0,11}$` (§2. **2026-09-17에 「대문자 2~6자」에서 자유 형식으로 바뀌었다**) | 검색·이력·문서 번호가 깨진다 |
| K3 | `name`이 비어 있지 않은 문장 | 목록과 문서의 "검증 항목" 칸이 빈다 |
| K4 | `precondition`·`params`·`expected`는 생략 불가. 없으면 `precondition: []`, `params: null`, `expected: null`로 **없다고 적는다.** 스키마가 있으면 모든 필드에 `.describe()` | 깜빡한 것과 정말 없는 것을 구분할 수 없다. `.describe()`가 없으면 입력 폼 라벨을 못 만든다 |
| K5 | `platforms`가 `desktop`·`mobile`·`android`만, `android` 는 다른 디바이스와 섞지 않는다 (2026-10-07 · 섞으면 `defineCase` 가 던지고 `check:tests` 는 그것을 K8 로 찍는다) | 러너의 `--project`가 실패한다 |
| K6 | `test.step`의 제목과 `verify`의 문장이 비어 있지 않은 문자열 리터럴이고, `verify`가 1개 이상. 밑 도우미 `verify.element` · `verify.rates` 도 판정으로 센다(2026-10-23 GAME-F1-09) | 절차·판정 칸이 비어 증적이 못 된다 |
| K7 | 주석 없음, `expect` 직접 호출 없음. 케이스가 아닌 파일은 아래 「Page Object 파일」의 금지도 진다 | 위 "테스트 코드에는 주석을 쓰지 않는다" |
| K8 | `npx playwright test --list`가 파일마다 테스트 1개를 등록 | 문법 오류, import 실패 |
| K9 | `params` 스키마의 비밀값 칸에 `.meta({ secret: true })`가 붙어 있다. 칸 이름에 `password`·`passwd`·`pw`·`token`·`secret`·`apiKey`·`credential`이 들어 있는데 꼬리표가 없으면 위반 (§4.1) | 비밀번호가 화면과 증적 문서에 평문으로 박힌다 |
| K10 | **값을 반드시 받아야 하는 칸이 없다.** `params`·`expected`의 모든 칸이 `.default()`를 갖거나 `.optional()`이다. 변환된 스키마의 `required`가 비어 있지 않으면 위반 (2026-09-16 결정). **예외 — `held` 가 달린 케이스는 기본값 없는 칸을 허용한다** — 사람이 채울 자리다 (2026-09-29 · [작성.md](../도메인/작성.md) §3.6 「★ 보류 케이스」). 대신 `check:tests --no-held` 가 `held` 를 main 에 못 들이게 막는다(K13 아래) | 정기 실행이 그 케이스를 돌리지 못한다. 사람이 값을 채워야만 도는 케이스는 매일 자동으로 돌 수 없다 (§9.2) |
| K11 | **없앴다 (2026-10-11 PRD-F4-05)** — `unconfirmed` 꼬리표의 모양 검사였다(2026-09-25). 같은 모양 규칙은 K13 이 `held` 에 쓴다. 번호는 다시 쓰지 않는다 | 꼬리표가 없어져 지킬 것이 없다. 남은 꼬리표는 타입 검사가 막는다 |
| K12 | **한 케이스 안에서 `test.step` 제목이 서로 다르다** (2026-09-28 · 검사기 반영 2026-09-29 · 글자 그대로 비교 · [시나리오.md](../도메인/시나리오.md) §3.7 결정 4) | 시나리오가 건너뛸 절차를 **제목으로** 지목한다. 제목이 겹치면 하나를 풀다 둘을 건너뛰고, 둘째가 「확인」이면 막는 판정까지 사라진다 |
| K13 | `held`는 있으면 **비지 않은 문자열 리터럴**이다. 빈 문자열(공백뿐 포함)·변수·식·축약 속성(`{ held }`)이면 위반. `defineCase` 인자에 펼침(`...base`)이나 계산된 키(`[k]`)가 있으면 꼬리표가 숨었는지 글자로 알 수 없으므로 꼬리표가 없어도 위반. **`check:tests --no-held` 는 `held` 가 하나라도 있으면 위반이다** — CI 가 초안이 아닌 PR 에서 이 모드로 돈다 (2026-09-29 · [작성.md](../도메인/작성.md) §3.6 「★ 보류 케이스」) | 스캐너가 사유를 못 읽어 보류 케이스가 정식으로 섞인다. 값 없이 건너뛰는 케이스가 main 에 들어가면 아무것도 안 지키는 초록이 된다 |
| K14 | `techniques`는 있으면 **문자열 리터럴의 배열 리터럴**이고 원소는 kit `TECHNIQUES` 안의 낱말이다. 같은 낱말 둘 · 변수 · 식 · 축약 속성(`{ techniques }`)이면 위반. 빈 배열은 「기법 없음」으로 받는다. **UI 케이스(`-UI-`)에 키가 있으면 빈 배열이어도 위반**이다 — UI 인지는 실행한 tcId 로 가린다(변수 · `as const` tcId 도) (2026-10-05 · PR #158 · [작성.md](../도메인/작성.md) §3.6 「설계 기법」) | 목록 밖 낱말이나 글자로 못 읽는 값이 들어가면 「설계 기법」 고르개로 못 거르는 케이스가 생기고 엑셀 열이 틀린다. UI 케이스에 기법이 붙으면 「기능 테스트에만」이 깨진다 — UI 목록에는 고르개가 없어 그 값으로 거를 수 없는데 줄에는 태그가 그려진다 |
| K15 | **고정 대기가 없다.** `waitForTimeout` 이라는 이름(`.waitForTimeout(...)` · 꺼내 쓰기)이나 글자(`page['waitForTimeout']`)와 `'networkidle'` 글자(`waitForLoadState` · `goto` 의 `waitUntil` 어디든)가 있으면 위반이다. 케이스와 Page Object · 도우미 파일 모두에 건다(아래 「Page Object 파일」). `setTimeout` 은 안 막는다 — `route` 안 응답 지연과 데드라인(`Promise.race`)이 쓴다. 무엇으로 바꾸나는 자식 스킬 `tpx-cases` `references/5-stable.md` 「정해 둔 시간을 기다리지 않는다」 (2026-10-16 PRD-F10-02) | 정해 둔 시간은 느린 망에서는 모자라 흔들리고 빠른 망에서는 시간만 버린다. `networkidle` 은 늘 열린 연결(알림 · 상담 창 · 주기 요청)이 있으면 안 오고, 오더라도 「화면이 다 그려졌다」는 뜻이 아니다 |

**K13 은 모양만 본다** — 보류 사유의 머리(`판정 불가 — ` · `보류 — `)는 자식 스킬이 지킨다.
화면 값을 기대값으로 쓴 케이스가 표준 기획서 `확인 필요` 항목을 덮는가는 검사기가 없고 **늘 사람이 본다**(spec-review B10).

```
[계약 변경 필요]
대상:    K표 · check:tests (apps/admin/src/catalog/pageObject.ts k15)
현재:    고정 대기 금지는 자식 스킬 문서(5-writing.md R13)뿐이라 waitForTimeout 21건 · networkidle 5건이 들어와 있었다
제안:    K15 — tests/ 아래 케이스 · Page Object · 도우미에서 waitForTimeout 호출과 'networkidle' 글자를 막는다. 26건은 조건 대기로 먼저 고친다
이유:    느린 망 · 동시 실행에서 흔들리지 않게, 빠른 망에서 시간을 버리지 않게 (2026-10-16 사용자 · 작성 개선 계획 PR 2)
영향:    WS-A(check:tests) · WS-작성(자식 스킬 R13 · 관문 0) · 사람이 쓰는 케이스
상태:    반영 완료 (2026-10-16, PR #272)
```

미확정 케이스도 계정 값은 `params`의 비밀값 칸(`.meta({ secret: true })`, K9)으로만 받는다. 역방향이 화면을 훑을 때 쓴 테스트 계정을 케이스에 글자로 박지 않는다.

문장이 검수자가 읽을 만한가(품질)는 기계가 못 본다. 그건 갈래를 끝낼 때 spec-review가 본다.

**없으면 없다고 적는다.** (2026-09-16 결정) `null`은 선언에서만 쓴다. 스캐너는 빈 객체 스키마로 기록하고
(`param_schema`·`expected_schema`는 `NOT NULL` 그대로), 실행 때 kit은 빈 객체를 넘긴다.
화면은 입력칸을 만들지 않고, 문서는 "입력 없음"으로 쓴다. `platforms`만 생략할 수 있다 — 기본값 `['desktop']`이 의도된 것이다.

입력값·기대값이 없는 케이스는 이렇게 생긴다.

```ts
export const spec = defineCase({
  tcId: 'DEMO-001',
  name: '메인 화면이 열린다',
  precondition: [],
  params: null,
  expected: null,
});
```

### Android 앱 케이스 (2026-10-07)

`platforms: ['android']` 인 케이스는 브라우저가 아니라 **Appium 으로 연결한 폰**에서 돈다. `android` 는 다른 디바이스와 함께 적지 않는다 —
`defineCase` 가 `<tcId>: android 는 다른 디바이스와 함께 선언하지 않는다` 로 던지고 스캐너가 그 문장을 실패 사유로 싣는다. `check:tests` 는 던져진 것을 K5 가 아니라 K8(문법 오류 · import 실패)로 찍는다 — 문장은 그대로 실린다.
선언 · `test.step` · `verify` · 비밀값 꼬리표 · K 표는 브라우저 케이스와 같다. 다른 것은 본문 인자 하나다.

```ts
export const spec = defineCase({
  tcId: 'MDA-FN-001',
  name: '상품 하나를 장바구니에 담으면 장바구니 수가 1이 된다',
  platforms: ['android'],
  precondition: ['My Demo App 이 설치될 Android 폰이 연결돼 있다', '앱을 새로 연 상태라 장바구니가 비어 있다'],
  params: null,
  expected: null,
});

test(spec, async ({ driver }) => {
  await test.step('첫 상품을 연다', async () => {
    await (await driver.$$('~store item'))[0].click();
    await verify('상품 화면이 열린다', await driver.$('~product screen').isDisplayed(), true);
  });

  await test.step('장바구니에 담는다', async () => {
    await driver.$('~Add To Cart button').click();
    await verify('장바구니 수가 1이다', await driver.$('~cart badge').$('android.widget.TextView').getText(), '1');
  }, { capture: true });
});
```

- 본문 인자는 `{ driver, request, params, expected }` 다. `driver` 는 WebdriverIO 로 연 Appium 연결이고 `page` 는 없다
- 없는 쪽을 꺼내면 kit 이 던진다 — 앱 케이스의 `page` 는 `<tcId>은 Android 앱 케이스라 page 가 없다 — driver 를 쓴다`,
  브라우저 케이스와 E2E 시나리오 부품의 `driver` 는 `<tcId>은 브라우저 케이스라 driver 가 없다`. 없는 쪽을 이름으로 꺼낼 때만 던진다 — 펼치기(`{ ...args }`)나 그 이름을 빼고 받는 꼴(브라우저 케이스의 `({ page, ...rest })`)에는 안 걸린다
- 요소는 `~이름` 으로 찾는다 — accessibility id 이고 Android 에서는 `content-desc` 다. 없으면 `id=` 에 화면 글의 resource-id 를 그대로 쓴다(꾸러미 자동 붙이기는 끈다 — [러너.md](../도메인/러너.md) §5.2 「앱 실행」)
- **기대값을 화면에서 읽어 담지 않는다** — 브라우저 케이스와 같은 규칙이다(CLAUDE.md 「저장소에 담아 둔 남의 스킬」). 화면에서 읽는 것은 요소 주소뿐이다
- 돌리는 법 · 환경값 · 한계는 [러너.md](../도메인/러너.md) §5.2 「앱 실행」이 정본이다. 폰 연결 정보는 케이스가 아니라 러너 환경값이 정한다

### API 케이스 (2026-10-20 · API-F1-01)

종류 「API」 애플리케이션의 케이스다. 화면이 없고 요청 도구로만 돈다. **무엇을 왜 하는지는 [도메인/API.md](../도메인/API.md) §3.8 이 정본이다.**
선언 · `test.step` · `verify` · 비밀값 꼬리표 · K 표는 브라우저 케이스와 같다. 다른 것은 머리 `apiDoc` 과 본문 인자 `api` 둘이다.

```ts
export const spec = defineCase({
  tcId: 'NTF-FN-014',
  name: '예약 발송 시각이 5분 안이면 400 이다',
  apiDoc: 3,
  precondition: ['고객사 A 기기가 하나 등록돼 있다'],
  params: null,
  expected: null,
});

test(spec, async ({ api }) => {
  const 고객사A = api('고객사 A');
  let 기기 = '';

  await test.step('고객사 A 기기를 하나 등록한다', async () => {
    기기 = await 기기등록(고객사A);
  });

  await test.step('scheduledAt 을 지금+1분으로 푸시를 보낸다', async () => {
    const res = await 고객사A.post('/v1/pushes', { data: { deviceId: 기기, title: '예약', scheduledAt: 분뒤(1) } });
    await verify('응답 코드가 400 이다', res.status(), 400);
    await verify('오류 코드가 SCHEDULE_TOO_SOON 이다', (await res.json()).code, 'SCHEDULE_TOO_SOON');
  });

  await test.step('등록한 기기를 지운다', async () => {
    await 기기지우기(고객사A, 기기);
  });
});
```

- **`apiDoc` 은 케이스를 만든 API 문서 판 번호다** — 실행 때 그 판과 응답 모양을 견준다. API 애플리케이션 케이스에만 단다. 1 이상의 정수가 아니면 `defineCase` 가 던진다(K8 로 찍힌다)
- 본문 인자에 `api` 가 는다 — `api('이름')` 이 그 대상 서버 줄의 API 인증으로 토큰을 붙인 요청 도구를 준다. `request` 는 「인증 없이」다(401 시험). 이름은 케이스에 글자로 적고 비밀값 칸으로 받지 않는다 — 비밀값은 설정에만 있다
- `page` · `driver` 는 쓰지 않는다. 디바이스는 `desktop` 하나다 — `apiDoc` 이 있는데 `platforms` 가 `['desktop']` 이 아니면 `defineCase` 가 던진다(도메인/API §3.8 「꼬리표와 다르다」)
- 반복 동작(`기기등록` · `기기지우기`)은 `helpers/api.helper.ts` 에 둔다 — 아래 Page Object 파일과 같은 자리 규칙이다

### 게임 케이스 (2026-10-23 · GAME-F1-09)

종류 「게임」 애플리케이션의 `platforms: ['android']` 케이스다. Appium 이 게임을 깔고 켠 뒤 kit 이 게임 안 SDK 에 붙는다. **무엇을 왜 하는지는 [도메인/게임.md](../도메인/게임.md) §3.10 이 정본이고, 몸통 칸 · 도우미의 꼴은 [3-공유계약.md](3-공유계약.md) 「게임 테스트 타입」이 정본이다.**
선언 · `test.step` · `verify` · 비밀값 꼬리표 · K 표는 Android 앱 케이스와 같다. 다른 것은 머리 `elements` · `smoke` 와 본문 인자 `game` · `admin`, 도우미 `verify.element` · `verify.rates` 다.

- 본문 인자는 `{ game, driver, admin, request, api, params, expected }` 다. `game` 은 게임 애플리케이션 항목에만, `admin` 은 대상 서버 줄에 어드민 키가 있을 때만 있다 — 없는 쪽을 꺼내면 kit 이 던진다(Android 앱 케이스의 `page` 와 같은 규칙)
- 주소는 오브젝트 이름 → 겹치면 `/` 경로(`[순번]`). 좌표 · 고정 시간 쉬기는 쓰지 않는다 — 기다림은 `game.waitFor` · `game.waitForValue`([게임.md](../도메인/게임.md) §3.10 「케이스 꼴」)
- 쓰는 규칙(준비 · 확인 수단 · 간섭 차단 · 스모크 · 배치 확인)은 작성 지침 `tpx-cases` `references/game.md`(2026-10-23 GAME-F1-11)가 맡는다. 창 화면 객체는 웹 Page Object 와 같은 `pages/<창>.page.ts` 이고 `주소` 값이 창 열쇠(`game:<장면>/<창 경로>`)다

### Page Object 파일 (2026-10-02 · PR #129 · 기능 테스트는 PR #130)

`tests/<폴더>/pages/<이름>.page.ts` · `tests/<폴더>/components/<이름>.component.ts` · `tests/<폴더>/helpers/<이름>.helper.ts`(로그인 · 계정 · 자료 도우미, 2026-10-11 PRD-F4-04 — 도메인/작성 §3.6 「지도」)는 케이스가 아니다. 이름 꼴은 `^[a-z][a-z0-9-]{0,40}$` 다.
스캐너와 케이스 규칙은 `.spec.ts` 만 보고, Playwright 도 `.spec.ts` · `.test.ts` 만 테스트로 집는다. 그래서 **`.spec.ts` 로 끝나지 않게** 짓는다.
이 파일에는 **K7(주석 · `expect` 금지)과 `test.step` · `verify` 호출 금지, 아래 가져오기 제한, K15(고정 대기 금지)**를 걸고 `check:tests` 가 건다(`catalog/pageObject.ts`) — 케이스 규칙을 걸면 멀쩡한 파일이 위반으로 찍힌다.
**가져올 수 있는 곳은 셋뿐이다** (2026-10-02 PR #130) — 같은 `tests/` 안 파일(그 파일도 이 검사를 받는다) · `@playwright/test`(`test` · `expect` · 통째로 가져오기 말고) · `@platform/kit` 과 그 하위 경로의 **타입**.
그 밖(다른 패키지 · `tests/` 밖 상대 경로 · `import = require` · `require()` · 동적 `import()` · `tests/` 밖을 다시 내보내기)은 K7 이다 — 이름을 바꿔 판정 · 절차를 들여오는 길을 막는다.
**`tests/` 아래 JS 파일(`.js` · `.mjs` · `.cjs`)도 K7 이다** — 타입 검사와 이 검사를 피한 채 import 로 불린다.
E2E 「만들기」 판별(도메인/시나리오 §3.7 결정 4)이 이 금지를 근거로 Page Object 호출을 믿는다. 여기가 새면 판정이 든 절차가 건너뛰어진다.
같은 검사가 `tests/` 아래 **케이스(`.spec.ts`)가 아닌 `.ts` 전부**에 걸린다 — 이름 꼴이 틀린 파일도 검사를 비켜 가지 못한다. 이름 꼴은 올리기 허용 목록이 본다.
올리기 허용 목록에 들고 CI 서비스 폴더 판정에서는 면제된다.
`test.step` · `verify` 는 케이스 파일에 둔다 — K6 · K12 와 증적이 거기서 읽는다. 언제 쓰나는 [작성.md](../도메인/작성.md) §3.6 「★ 테스트 두 갈래」.

### 스크린샷

- **실패한 스텝은 자동으로 찍는다.** 통과한 화면은 아무도 열어보지 않고,
  전부 찍으면 실행 한 번에 수십 장이 쌓여 디스크가 금방 찬다
- **증적용으로 명시 지정**: `test.step(제목, fn, { capture: true })`.
  인자 순서는 Playwright의 `test.step(title, body, options)`와 같다. kit의 `test`는 Playwright를
  감싼 래퍼이고 `capture`는 kit이 추가한 옵션이다.
  검수 문서에 "이 화면이 이렇게 나왔다"를 넣어야 할 때 쓴다. 기본값은 false
- API 테스트는 화면이 없으므로 대신 요청·응답 원문을 같은 자리에 남긴다
- 앱 케이스(`android`)는 브라우저 화면이 아니라 **폰 화면**을 찍는다. 경로 규칙은 같다 (2026-10-07)
- **실패 사진에는 그 절차가 처음 실패한 때까지 마지막으로 다룬 요소를 빨갛게 표시한다** (2026-10-29 사용자) — 사진만으로는 어디가 문제인지 찾기 어려웠다. 실패 뒤에 다룬 요소로는 옮겨 가지 않는다.
  웹은 kit 이 넘기는 `page` 에서 나온 Locator 중 마지막으로 메서드를 부른 것을 반투명 빨간 상자로 덮는다(Playwright 사진의 `mask` — 따로 부른 동작이 trace 조작 목록에 섞이지 않게 사진 찍기 한 번 안에서 한다). `page` 에서 바로 부른 것(`page.fill('#x')` · `page.url()`)은 짚을 요소가 없어 표시를 비운다.
  앱은 Appium 으로 마지막으로 찾은 요소 둘레에 빨간 테두리를 그린다. 사진 파일에 직접 그려서 실행 기록 · 증적 · 엑셀이 따로 손댈 것 없이 같은 사진을 쓴다.
  `verify` 는 값만 받으므로 요소와 상관없는 값(주소 · API 응답)을 견주다 틀리면 그 절차의 다른 요소를 짚을 수 있다. 요소를 못 찾았거나 숨었으면 표시 없이 사진만 남긴다. 같은 Locator 에 맞는 요소가 여럿이면 웹은 다 덮는다.
  앱은 폰 연결에 오르는 찾기(`driver.$`)만 본다 — 여럿 찾기(`$$`)는 표시가 없고, 요소 안에서 이어 찾은 것(`$('a').$('b')`)은 바깥 요소(a)를 짚는다.
  `capture: true` 로 찍은 통과 절차에는 그리지 않는다. 코드는 `packages/kit/src/runtime/highlight.ts`

### 4.1 비밀값 꼬리표 (2026-09-16 결정)

로그인 케이스의 `password`처럼 **문서에 남으면 안 되는 입력값**이 있다. 이것을 **비밀값**이라 부른다.
선언에서 그 칸에 꼬리표를 달아 둔다.

```ts
params: z.object({
  username: z.string().min(1).describe('아이디'),
  password: z.string().min(1).describe('비밀번호').meta({ secret: true }),
}),
```

`.meta({ ... })`는 zod가 스키마에 꼬리표(메타데이터, 값 자체가 아니라 값에 붙이는 설명표)를 다는 기능이다.
JSON Schema로 바꿀 때 그 칸 아래에 `"secret": true`로 그대로 살아남고 `.describe()`도 함께 남는다.
이 저장소에 깔린 zod로 확인했다. **꼬리표를 다는 데는 kit에 새 함수를 만들지 않는다.** 이미 있는 기능이라 추가할 코드가 0줄이다.

**계정 칸에는 역할 이름을 단다** (2026-10-12 · 진행판 PRD-F9-01) — `.meta({ secret: true, account: '관리자' })`. 실행 · 반영 때 대상 서버 줄의 그 역할 계정으로 비어 있는 칸을 채운다.
`account` 가 없는 비밀값 칸은 일반 회원 계정이다. 아이디인지 비밀번호인지는 칸 이름으로 가린다. 판정 함수는 `packages/kit/src/accounts.ts` 하나이고(서버 · kit 실행이 같이 쓴다),
규칙의 정본은 [도메인/작성.md](../도메인/작성.md) §3.6 「★ 역할별 계정」이다. `account` 도 JSON Schema 에 그대로 살아남는다. **K 규칙은 더하지 않는다** — 틀린 역할 이름은 실행이 「비밀값이 비어 있다」로 드러낸다

**가리는 것은 화면과 문서뿐이다. DB에는 평문 그대로 넣는다.** 예외는 둘 — trace 를 푼 세 표(`run_network` · `run_action` · `run_console`)는 넣을 때 가리고(2026-10-16), 성능 녹화(HAR)는 남기기 전에 가린다(2026-10-21 대기). 아래 표 끝 줄들이다.

| 어디 | 무엇을 한다 |
|------|------------|
| 실행 창 (실행 §8.2 · §8.10) | 타이핑할 때 글자가 보이지 않는 입력칸으로 만든다 |
| 실행 결과 목록·항목 상세 (§8.3·§8.4) | 값을 `********`로 바꿔 보여준다 |
| 실행 조회 응답 `GET /api/runs/:runId` · `/items/:historyId` (2026-09-29) | 응답에서도 `********`로 바꿔 싣는다(`params` · `expected`). DB 는 평문 그대로다 — 화면만 가리면 개발자 도구로 원문이 보인다. 그 비밀 값이 확인의 기대 · 실제 값 · 절차 오류 · 절차 기록(`httpTrace`) · 항목 오류에 되비치면 그 글자도 가린다(2026-10-12 진행판 WEB-F3-13 — 시나리오 실행 결과와 같은 규칙). 실패 카드 `GET /api/runs/:runId/failures` 의 `item` 도 같은 함수로 읽는다. 견주기 `GET /api/runs/:runId/insights` 의 실패덩어리 대표 문장과 대시보드 `GET /api/dashboard` 의 신규 실패 사유도 가린 뒤 자르고 가린 글자로 묶는다. 숫자로 적은 비밀은 키 칸만 가려진다(도메인/시나리오 §7 의 한계와 같다) |
| 시나리오 실행 결과 응답 `GET /api/runs/:runId/scenario` (2026-10-06) | 부품 `part.params` · `part.expected` · `bound` 를 박제 스키마로 `********` 로 바꾸고, 그 비밀 값이 절차 기록 · 오류 · 뒷정리 주소에 되비치면 그 글자도 가린다 — 저장값으로 채운 비밀번호가 부품에 박제되기 때문이다. 시험 실행 결과도 같다. 정본은 도메인/시나리오 §7 |
| 증적 문서 (§8.4) | 같다. `********`만 들어간다. 확인의 기대 · 실제 값과 판정 못 낸 사유 · 예외로 깨진 `FAIL` 사유에 되비친 비밀 글자도 가린다(2026-10-12 · 예외 `FAIL` 은 2026-10-17). 객체 값 안쪽의 비밀값 이름 칸도 가린다 |
| `run_item.params` (§6) | **평문 그대로 저장한다** |
| trace 기록 `run_network` · `run_action` · `run_console` (2026-10-16 · 진행판 PRD-F10-03) | **가린 뒤 저장한다** — 다시 실행할 재료가 아니라 화면에 그대로 보일 기록이고, 응답 본문의 토큰처럼 실행 값 목록에 없는 비밀이 섞인다. 위 값 목록 가림에 비밀 칸 이름(과 인증 머리 · 세션 · 쿠키 · api_key)에 붙은 값 · 비밀번호 칸에 넣은 값을 더한다. 주소 경로(물음표 · # 앞)에서는 계정 아이디 칸 값을 안 가린다 — 케이스 정식 실행 기록만이고 서비스 지도를 채우는 기록이라서다(2026-10-26 WEB-F6-03 · 실행 §3.2 「trace」). 항목 상세 `/items/:historyId` 의 `trace` 칸은 저장된 그대로 싣는다. 정본은 도메인/실행 §3.2 「trace」. E2E 실패 부품의 `scenario_run_part.trace` · 시험 실행 결과의 `trace` 도 같은 가림이다(2026-10-17 · 도메인/시나리오 §7 「실패 기록」) |
| API 인증 비밀값 · 받은 토큰 (2026-10-20 · 도메인/API §3.8 「API 인증」) | **kit 이 절차 기록(`httpTrace`)에 남기기 전에 가린다** — 실행 값이 아니라 설정에서 오는 비밀이라 위 값 목록 가림에 안 걸린다. 설정 응답은 끝 4자리만 싣는다 |
| 저장값 `case_input.params` (§6 · §8.2, 2026-09-29) | **평문 그대로 저장한다.** 다만 케이스 응답(`savedInput`)에는 원문을 싣지 않고 칸 이름만 `savedSecrets` 로 알린다 — 목록 응답에 서비스 전체 분량이 실린다. 지금 명세에 없는 칸은 응답에서 뺀다. 실행을 만들 때 서버가 채운다 (§3.2) |
| 성능 녹화 HAR `artifacts/perf-record/` (2026-10-21 PERF-F1-04 — 도메인/성능 §7 「PERF-F1-04 가 연 통로」) | **남기기 전에 가린다** — trace 와 같은 가림(비밀번호 칸에 넣은 값 · 인증 머리 · 세션 · 쿠키 · 토큰)이고 가리기 전 원본은 지운다. AI 에 넘기는 재료라 원문이 남을 까닭이 없다. 가린 자리는 꼬리표로 바꾼다 — 테스트 계정은 `${username}` · `${password}`, 나머지는 같은 값이면 같은 `<<비밀N>>` 이다(변수 추출을 찾으려면 값이 같은 자리가 이어져 보여야 한다) |
| 성능 시나리오 계정 CSV `perf_scenario.accounts_csv` (2026-10-21 · PERF-F1-03 반영) | **평문 그대로 저장한다** — 대상 서버 줄의 테스트 계정 비밀번호와 같다. 응답 · 화면에는 행 수만 싣고, 실행 때 에이전트에 그 몫의 줄만 준다 |

저장 시점에 가리면 그 실행을 다시 돌릴 수 없고, 값이 틀려서 실패한 것인지 알 방법도 같이 사라진다.
여기 들어오는 것은 테스트 전용 계정뿐이므로 저장을 막아서 얻는 것보다 잃는 것이 크다.

**기계가 못 잡는 자리가 있다.** K9는 칸 **이름**만 보고 판단한다.
`answer`·`code`처럼 이름만으로는 비밀값인지 알 수 없는 칸은 검사기가 그냥 지나친다.
그건 케이스를 쓰는 사람이 직접 달아야 하고, 갈래를 끝낼 때 spec-review가 사람 눈으로 본다.
이 한계를 메우려고 값의 생김새를 추측하는 규칙은 넣지 않는다. 오탐이 늘면 아무도 검사기를 안 믿는다.
