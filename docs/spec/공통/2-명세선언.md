# 명세 선언 방식

> **이 장이 담는 절** — §4 명세 선언 · §4.1 비밀값 꼬리표
> 케이스를 만들거나 읽는 갈래(WS-A 카탈로그 · WS-C 러너)가 읽는다. 선언 하나가 입력 폼·검증·증적 문서를 전부 만든다.
> 전체 목차와 작업별 읽기 동선은 [SPEC.md](../../SPEC.md).

## 4. 명세 선언 방식 (가장 중요)

테스트 코드 안에 명세를 함께 선언한다. 이 선언 하나가 **입력 폼 · 검증 · 증적 문서**를 전부 만든다.

```ts
// tests/auth/login.spec.ts
import { defineCase, test, verify } from '@platform/kit';
import { z } from 'zod';

export const spec = defineCase({
  tcId: 'AUTH-002',
  name: '유효한 이메일과 비밀번호로 로그인하면 토큰이 발급된다',
  platforms: ['desktop', 'mobile'],     // 생략 시 ['desktop']
  precondition: [
    '가입 완료된 사용자 계정이 존재한다',
    '계정이 잠금 상태가 아니다',
  ],
  params: z.object({
    username: z.string().min(1).describe('아이디'),
    password: z.string().min(1).describe('비밀번호').meta({ secret: true }),
  }),
  expected: z.object({
    statusCode: z.number().describe('응답 코드'),
    hasToken:   z.boolean().describe('토큰이 발급되는지'),
  }),
});

test(spec, async ({ page, request, params, expected }) => {
  const res = await test.step('로그인 API를 호출한다', async () => {
    const res = await request.post('/api/login', { data: params });
    await verify('응답 코드가 기대값과 같다', res.status(), expected.statusCode, { blocker: true });
    return res;
  });

  await test.step('토큰을 확인한다', async () => {
    const body = await res.json();
    await verify('토큰이 발급된다', !!body.token, expected.hasToken);
  });

  await test.step('로그인 후 화면을 확인한다', async () => {
    await page.goto('/dashboard');
  }, { capture: true });
});
```

### 각 필드가 어디에 쓰이는가

| 필드 | 쓰이는 곳 |
|------|----------|
| `tcId` | 검색, 파라미터 주입 키, 증적 문서 항목 번호, 이력 추적 |
| `platforms` | 실행 화면의 디바이스 선택지, 실행 시 생성될 `RunItem` 개수. 값은 `desktop` · `mobile` · `android` 이고 `android` 는 다른 값과 섞지 않는다 — 폰에서 도는 앱 케이스다 (아래 「Android 앱 케이스」). 2026-11-19 PC 게임 케이스에 윈도우 값 다섯(`windows` · `windows-ps5` · `windows-ps4` · `windows-switch` · `windows-xbox`)이 는다 — 보통 케이스는 `windows`, 버튼 그림 케이스만 패드 값을 적고 `android` 와 같이 적지 않는다 (아래 「게임 케이스」 · GAME-F4-02 · 2026-11-19 게임 하나에 플랫폼 하나 — 반영 GAME-F4-05) |
| `name` | 목록 화면, 증적 문서 "검증 항목" 칸 |
| `precondition` | 증적 문서 "사전조건" 칸 |
| `params` | **입력 폼 자동 생성** (`describe`가 한글 라벨, `enum`이면 드롭다운, `optional`이면 선택 입력), 실행 전 검증 |
| `expected` | 기대값 입력 폼, 증적 문서 "기대결과" 칸 |
| `test.step` | 증적 문서 "시험 절차" 칸, 실패 지점 표시 |
| `verify` | 증적 문서 "판정" 칸, 검증 문장 단위 PASS/FAIL |
| `unconfirmed` | **없앴다 (2026-10-11 PRD-F4-05)** — 앞 판의 미확정 꼬리표(사유 한 문장)였다. kit 이 이 칸을 받지 않아 적으면 타입 검사가 막는다. 미확정은 케이스가 덮는 표준 기획서 항목 상태에서 계산하고 목록 · 실행 · 증적에 「미확정」으로 보인다([작성.md](../도메인/작성.md) §3.6 「★ 표준 기획서」 「미확정」 · [3-공유계약.md](3-공유계약.md) 「표준 기획서 타입」) |
| `held` | 보류 케이스 꼬리표. 값은 머리(`판정 불가 — ` · `보류 — `)로 시작하는 사유 한 문장이다. 있으면 실행 때 건너뛰고, 사람이 작성 상세에서 비운 칸을 채우거나 케이스를 제거한 뒤 반영된다. **초안 PR 에만 있다** — main 에 들어가지 않는다. 정본은 [작성.md](../도메인/작성.md) §3.6 「★ 보류 케이스 — 사람이 값을 채운다」 (2026-09-29) |
| `techniques` | 기능 테스트 목록 줄의 기법 태그와 필터 판의 「설계 기법」 줄, 케이스 상세의 「설계 기법」 구획, 케이스 엑셀 시트 ① 맨 끝의 「설계 기법」 열(UI 테스트만 받을 때는 없다)([카탈로그.md](../도메인/카탈로그.md) §7 · §8.1). 값은 설계 기법 이름의 배열이고 **낱말 목록의 정본은 kit `TECHNIQUES`** 다. **기능 테스트(`-FN-` · 옛 꼴)에만 단다** — UI 테스트에는 안 단다(K14). 작성 에이전트가 적고 관문 0 · 올리기 판정이 그 칸의 기대 기법과 견준다 — 칸마다 무엇이어야 하는지는 [작성.md](../도메인/작성.md) §3.6 「설계 기법」. 사람이 쓴 케이스는 안 적어도 된다. 실행 기록 · 증적에는 안 남는다 (2026-10-05 · PR #158) |
| `elements` | 게임 케이스만 · 닿는 게임 요소 열쇠(`item:sword_long` · `zone:Town`)의 배열. kit 이 겹침을 빼고 차례를 맞추며 비면 키를 안 싣는다. 작성 빠른 검사가 게임 지도에 있는지 보고 스캐너가 `test_case.elements` 와 요소를 거친 케이스 표에 넣는다(2026-10-23 GAME-F1-12 — 저장소 전체 형식 검사 K 표는 안 본다. 어느 케이스가 게임인지 작성 에이전트만 안다). 꼴은 [3-공유계약.md](3-공유계약.md) 「게임 테스트 타입」 (2026-10-23 GAME-F1-09) |
| `smoke` | 스모크 표시(`true` 일 때만 싣는다). 빌드마다 먼저 도는 핵심 경로 케이스 — 웹 · 앱 · 게임 다 쓴다([실행.md](../도메인/실행.md) §3.11 「빌드마다 돌리기」). 스캐너가 `test_case.smoke` 에 담고 사람이 목록에서 고친 값은 `smoke_set` 이 이긴다 (2026-10-23 GAME-F1-09 · 스캐너 · 목록은 2026-10-24 GAME-F1-13) |
| `keepAppData` | Android 앱 케이스만 · `true` 면 연결 때 앱 데이터를 지우지 않고 앱만 다시 켠다 — 앞 케이스의 로그인을 이어 쓴다. 안 적으면 지우고 시작한다. 명세 · 스캐너 · DB 에는 안 싣는다. 이어지는 범위 · 케이스가 지킬 것은 [러너.md](../도메인/러너.md) §5.2 「데이터 남기고 시작」 (2026-11-15). 프로시저 안 케이스에는 못 적고 프로시저에 적는다(아래 「테스트 프로시저」 · K22 — 케이스에 적으면 `defineProcedure` 가 던진다 · 2026-11-24 TP-F2-06) |
| `launchIntent` | Android 앱 케이스만 · 케이스의 입력값을 받아 켤 화면과 실행 값(`{ activity, extras }`)을 돌려주는 함수. 단독 앱 항목을 열 때 kit 이 그 값을 실어 켠다 — 테스트 빌드의 입구로 로그인된 채 시작한다. 못 만들거나 못 실으면 그냥 켠다. E2E 단계는 보지 않는다. 명세 · 스캐너 · DB 에는 안 싣는다. 정본은 [러너.md](../도메인/러너.md) §5.2 「값을 실어 켜기」 (2026-11-16). 프로시저 안 케이스에는 못 적고 프로시저에 적는다 — 프로시저의 것은 첫 케이스의 입력값을 받는다(아래 「테스트 프로시저」 · K22 — 케이스에 적으면 `defineProcedure` 가 던진다 · 2026-11-24 TP-F2-06. 프로시저의 값으로 켜는 것은 2026-11-24 TP-F2-07 반영) |

`spec`은 반드시 `export const spec`으로 내보낸다. 스캐너가 이 이름을 찾는다 (§3.1). 프로시저 파일은 `export const procedure` 를 내보낸다(K1 · 아래 「테스트 프로시저」 — kit 은 2026-11-24 TP-F2-06 · 스캐너가 읽는 것은 2026-11-24 TP-F2-09).

`verify(문장, 실제값, 기대값, { blocker?: true })` — 앞의 세 인자를 그대로 결과에 남긴다.
`expect`를 직접 쓰면 문장이 남지 않으므로 **테스트 코드에서 `expect` 직접 사용을 금지**한다.

### verify 실패 규칙 (2026-09-16 결정)

- `verify`는 **절차(`test.step`) 안에서만** 부른다. 밖에서 부르면 kit이 에러를 던진다.
  화면과 증적 문서가 절차 아래에 검증 문장을 보여주는 구조이기 때문이다
- 실패해도 **기본은 계속 간다.** 그 문장은 FAIL로 기록되고 다음 문장·다음 절차를 계속 돌린다.
  화면 문구가 바뀐 정도의 실패로 뒤 절차까지 버리지 않기 위해서다
- 뒤를 돌릴 의미가 없는 검증에는 `{ blocker: true }`를 붙인다. 이 문장이 실패하면 **그 절차를 끝으로 멈춘다.**
  로그인 실패처럼 뒤 절차의 전제가 무너지는 경우다. 시스템은 값만 보고 사유를 알 수 없으므로 작성자가 표시한다
- 예외(요소를 못 찾음, 페이지가 안 뜸 등)는 코드가 더 갈 수 없으므로 **항상 멈춘다.** 그 절차는 FAIL + `error`
- 판정: 검증 문장이 하나라도 FAIL이면 절차도 항목도 FAIL. 멈춘 뒤 돌지 않은 절차는 문서에 나오지 않는다
  (절차는 실행해 봐야 알 수 있다). 대신 멈추게 한 문장에 `실행 중단`을 표시해 뒤가 왜 없는지 알린다

### 글 비교 — 띄어쓰기 · 구두점 · 빈칸 자리만 다르면 「Pass · 알림」 (2026-11-21 사용자)

`verify` 의 실제값과 기대값이 **둘 다 글**이고 글자까지 같지 않으면 한 번 더 본다. `verify.element` · `rates` · `log` 는 그대로 글자까지 견준다.

- 양쪽 글에서 띄어쓰기와 구두점(유니코드 구두점)을 걷어 낸다. 다만 `-` · `%` 와 숫자 사이 구두점(`1,100` · `1.5`)은 수의 뜻을 바꿔 남긴다. 기대 글은 걷어 낸 자리마다 잘라 낱말 조각을 만든다
- **홀로 선 부호(`+` · `＋` · `−`)와 바로 뒤 숫자 사이의 띄어쓰기는 지워 부호를 숫자에 붙인다** — 「+ 50」과 「+50」은 같은 수다(BRM-FN-296 · 2026-11-21 사용자). 부호가 있고 없음이 다르면 다른 수다 — 「보상 100」은 「보상 + 100」에서 못 찾고 「보상 + 100」은 「보상 100」에서 못 찾는다. 부호로 시작하는 조각(「+50」)은 아래 숫자로 시작하는 조각과 같이 본다.
  홀로 선 부호는 바로 앞이 글 처음 · 띄어쓰기 · 구두점이고 띄어쓰기를 건너 앞 글자가 숫자가 아닌 것이다 — 이름에 붙은 「C++ 20」 · 「A+ 20」과 셈을 하는 「3 + 10」의 `+` 는 붙이지 않는다. ASCII `-` 는 목록 머리표(「- 50 골드」) · 범위(「3 - 10」)로 더 자주 써서 붙이지 않는다
- 조각이 화면 글에 **차례대로 다 있으면** PASS 로 남기고 `notice` 에 `기획서 문장과 글자가 다름` 을 적는다. 기대 · 화면 글은 `expected` · `actual` 에 이미 있어 넣지 않는다 — 비밀값을 가려 잘라 붙이는 일은 결과를 보여 주는 admin 이 한다. 화면 글이 더 길어도 된다 — 빈칸 자리에 든 값(「보스 처치! <아이템 이름> 획득」의 아이템 이름)이다
- **숫자로 시작하거나 끝나는 조각은 그 자리에 숫자 · 남긴 구두점 · 기호(`+` · `$`)가 붙거나 뒤에 수 단위(만 · 천 · 억 · 조 · k · m)가 붙으면 안 맞는 것으로 본다** — 「골드 100」은 「골드 1100」 · 「골드 1,100」 · 「골드 -100」 · 「골드 100만」 · 「+100」에서 못 찾고, 「P1」은 「P12」에서, 「할인 50」은 「할인 50%」에서 못 찾는다. 걷어 낸 띄어쓰기 · 구두점 너머의 글자는 붙은 것으로 치지 않는다 — 위에서 부호에 붙인 띄어쓰기만 빼고
- **글자로 시작하는 두 글자 이상 조각은 낱말 가운데서 시작하면 안 맞는 것으로 본다** — 「가능」은 「불가능」에서, 「완료」는 「미완료」에서 못 찾는다. 뒤에 붙는 글자(조사 · 어미 — 「보스를」의 「보스」)와 한 글자 조각(빈칸 뒤에 남은 조사 「을」)은 그대로 맞는다. 이름 · 개수가 다르면 조각이 없으니 지금처럼 FAIL 이다
- 조각이 하나도 없으면(빈 글 · 구두점뿐) 이 규칙을 쓰지 않는다 — 「글이 비었다」를 확인하는 문장이 늘 통과하면 안 된다
- 까닭 — 기획서 docx 를 만들 때 원본의 빈칸 표시(`<아이템 이름>` · `<번호>` · `<레벨>`) 66곳이 빠져 확정 요구 문장이 「보스 처치! 획득」 · 「Lv. · 골드 」가 됐고 게임 화면은 「보스 처치! 보스의 왕관 조각 획득」 · 「Lv.1 · 골드 200」이었다(BRM-FN-166 · 524). 문서를 다시 만드는 대신 이 규칙으로 푼다
- 한계 — 「로그인」과 「로그인 실패」도 통과 · 알림이다. 그래서 알림은 케이스 실행 결과 요약 띠에 모아 보인다([실행.md](../도메인/실행.md) §8.3 「Pass · 알림」). E2E 시나리오 · 호환성 실행도 같은 `verify` 라 항목에 알림이 붙지만 모아 보는 자리는 아직 없다. 도우미가 안에서 글을 견주고 참 · 거짓만 넘기면 이 규칙이 닿지 않는다 — 글을 그대로 `verify` 에 넘긴다

### 테스트 코드에는 주석을 쓰지 않는다

주석이 들어갈 자리를 이미 선언이 가져갔다.

| 적고 싶은 것 | 적을 자리 |
|-------------|----------|
| 이 테스트가 무엇을 검증하는가 | `name` |
| 어떤 상태를 전제하는가 | `precondition` |
| 이 단계에서 무엇을 하는가 | `test.step`의 제목 |
| 여기서 무엇을 확인하는가 | `verify`의 문장 |

주석은 화면에도 증적 문서에도 나오지 않는다. 같은 설명이 두 군데 생기면
코드를 고칠 때 한쪽만 고쳐져 주석이 거짓말을 시작한다.

**적용 범위**: `tests/**` 만. 러너·스캐너 등 플랫폼 코드는 CLAUDE.md의
기존 규칙(왜만 적는다)을 따른다.

### 케이스 파일 규칙 — `npm run check:tests`가 기계로 검사한다 (2026-09-16 결정)

테스트 코드는 사람이 쓸 수도 있다. 그래서 아래 규칙은 Claude 훅이 아니라 **CI가** 검사한다.

초안 PR 에서는 돌지 않는다 (`docs/HOOKS.md` 「CI 와 병합 차단」).

### Android 앱 케이스 (2026-10-07)

`platforms: ['android']` 인 케이스는 브라우저가 아니라 **Appium 으로 연결한 폰**에서 돈다. `android` 는 다른 값과 함께 적지 않는다 —
`desktop` · `mobile` 과 섞으면 `defineCase` 가 `<tcId>: android · windows 는 desktop · mobile 과 함께 선언하지 않는다` 로, 윈도우 값과 섞으면 `<tcId>: android 와 windows 는 함께 선언하지 않는다 — 게임 하나에 플랫폼 하나다` 로 던지고(2026-11-19 반영 GAME-F4-05 · 정본 [3-공유계약.md](3-공유계약.md) 「윈도우 PC 게임」. 앞 판 GAME-F4-02 는 게임 케이스가 `windows` 와 같이 적었다) 스캐너가 그 문장을 실패 사유로 싣는다. `check:tests` 는 던져진 것을 K5 가 아니라 K8(문법 오류 · import 실패)로 찍는다 — 문장은 그대로 실린다
선언 · `test.step` · `verify` · 비밀값 꼬리표 · K 표는 브라우저 케이스와 같다. 다른 것은 본문 인자 하나다.

```ts
export const spec = defineCase({
  tcId: 'MDA-FN-001',
  name: '상품 하나를 장바구니에 담으면 장바구니 수가 1이 된다',
  platforms: ['android'],
  precondition: ['My Demo App 이 설치될 Android 폰이 연결돼 있다', '앱을 새로 연 상태라 장바구니가 비어 있다'],
  params: null,
  expected: null,
});

test(spec, async ({ driver }) => {
  await test.step('첫 상품을 연다', async () => {
    await (await driver.$$('~store item'))[0].click();
    await verify('상품 화면이 열린다', await driver.$('~product screen').isDisplayed(), true);
  });

  await test.step('장바구니에 담는다', async () => {
    await driver.$('~Add To Cart button').click();
    await verify('장바구니 수가 1이다', await driver.$('~cart badge').$('android.widget.TextView').getText(), '1');
  }, { capture: true });
});
```

- 본문 인자는 `{ driver, request, params, expected }` 다. `driver` 는 WebdriverIO 로 연 Appium 연결이고 `page` 는 없다
- 없는 쪽을 꺼내면 kit 이 던진다 — 앱 케이스의 `page` 는 `<tcId>은 Android 앱 케이스라 page 가 없다 — driver 를 쓴다`,
  브라우저 케이스와 E2E 시나리오 부품의 `driver` 는 `<tcId>은 브라우저 케이스라 driver 가 없다`. 없는 쪽을 이름으로 꺼낼 때만 던진다 — 펼치기(`{ ...args }`)나 그 이름을 빼고 받는 꼴(브라우저 케이스의 `({ page, ...rest })`)에는 안 걸린다
- 요소는 `~이름` 으로 찾는다 — accessibility id 이고 Android 에서는 `content-desc` 다. 없으면 `id=` 에 화면 글의 resource-id 를 그대로 쓴다(꾸러미 자동 붙이기는 끈다 — [러너.md](../도메인/러너.md) §5.2 「앱 실행」)
- **둘 다 없으면 id 가 있는 부모 요소 안에서 순서나 글자로 찾는다** (2026-11-14 사용자 — 앞 판은 보류였다. MTA 보류 80건 가운데 약 14건이 「요소 주소 없음」이었다) — UiSelector 꼴 하나만 쓴다.
  `android=new UiSelector().resourceId("<부모 id>").childSelector(new UiSelector().className("<클래스>").instance(<n>))`(순서 — `instance` 는 0 부터) 또는 `….childSelector(new UiSelector().text("<글자>"))`(글자).
  지키는 것 —
  ① **부모는 트리상의 조상이다** — 그 요소를 품은 조상 가운데 resource-id 가 있는 가장 가까운 것. 위치 상자가 겹칠 뿐인 요소(덮개 · 옆 칸)는 부모가 아니다(`childSelector` 는 자손만 찾는다)
  ② **부모 id 는 그 화면에 하나뿐이어야 한다** — 목록 줄처럼 같은 id 가 되풀이되면 늘 첫 줄을 잡는다. 그런 id 는 부모로 쓰지 않고 그 위의 하나뿐인 조상을 고른다. 굴리는 목록 안의 순서는 줄이 바뀌면 어긋나므로 쓰지 않는다
  ③ **요소 하나만** 찾게 짓는다 — 같은 글자가 둘 이상이면 순서를 쓴다. 순서(`instance`)는 실제 트리의 같은 클래스 자손을 다 센다 — 화면 글은 글자 · 이름표 · id 없는 껍데기를 빼므로 화면 글로 센 순서가 틀릴 수 있다
  ④ **글자는 화면 글 그대로 다 옮긴다**(`text()` 는 전체가 같아야 맞는다). 따옴표 · 역슬래시가 든 글자는 순서를 쓴다. resource-id 도 화면 글 그대로다 — 꾸러미 이름을 붙이거나 떼지 않는다
  ⑤ **찾는 데 쓴 글자를 그 요소의 판정 기대값으로 쓰지 않는다** — 그 글자로 찾았으니 늘 맞는다. 글자로 찾는 것은 누를 대상(버튼 · 칩 · 항목)의 이름이 기획서에 적혀 있을 때다
  ⑥ 주소는 앱 화면 파일(`pages/<화면>.page.ts`)에 둔다 — 화면이 바뀌면 한 곳만 고친다
  ⑦ **맞게 찾는지는 작성의 폰 1번 돌려 보기로 확인한다** — 폰에서 안 돈 케이스가 이 꼴을 쓰면 결과 요약에 `부모 꼴 주소 미확인 — <tcId>` 를 적는다.

  - **부품이 있는 동작은 부품으로 부른다** — kit 에 부품이 있는 동작을 케이스 · 화면 파일 · 도우미가 `driver.execute('mobile: …')` 로 직접 부르지 않는다. 부품이 디바이스 팜이 막는 명령의 까닭을 실어 던지고, 바꾼 폰 상태를 되돌린다. 이미 쓰는 WebdriverIO 동작(`click` · `setValue` · `back` · `swipe` · `terminateApp` · `activateApp`)은 그대로 쓴다. 앞서 쓴 케이스의 직접 호출(네트워크 끊기 · 폰 시각 읽기 · 앱 데이터 지우기 · 화면 열기)은 그 부품을 더하는 줄(APP-F3-08 · 09)이 부품으로 옮긴다 — 앱 데이터 지우기 · 화면 열기는 2026-11-16 APP-F3-08 이 `앱비우기` · `인자로켜기` 로, 네트워크 끊기 · 폰 시각 읽기는 같은 날 APP-F3-09 가 `폰상태에서` · `폰시각` 으로 옮겼다. **표에도 없는 `mobile:` 명령은 케이스에서 부르지 않는다** (2026-11-16 사용자 APP-F3-11 시작 질문) — 부품이 없으면 되돌리기 · 팜이 막는 까닭을 맡을 곳이 없다. appium-cli `exec` 가 읽기만 하는 명령을 부르지만 AI 가 폰을 살펴보는 데만 쓰고 `Ran:` 은 주석이다([작성.md](../도메인/작성.md) §3.6 「범용 앱」). 케이스에 그 동작이 필요하면 보류하고 부품을 더하는 줄로 묻는다
  - **앱 안 웹 화면(웹뷰)** — `웹뷰에서(driver, async () => { … })` 구간 안에서 쓴다. 구간 안의 `driver` 는 웹 맥락이고 끝나면(던져도) kit 이 네이티브로 되돌린다. **구간 안의 요소는 웹 케이스와 같은 순서로 찾는다**(2026-11-15 사용자) — testid → role → label → placeholder → text → CSS → XPath([작성.md](../도메인/작성.md) §3.6 「★ 테스트 두 갈래」 「locator 순서」). CSS · XPath 는 웹 케이스처럼 까닭을 용어 사전에 남긴다. WebdriverIO 에 옮긴 꼴은 APP-F3-04 가 `tpx-author` `app.md` 에 적는다. 네이티브 주소(`~` · `id=` · 부모 꼴)와 네이티브 전용 부품(`뜰때까지` · `보이나` · `키보드완료` · `토스트글` 등)은 구간 안에서 쓰지 않는다 — 부르면 kit 이 「웹 맥락에서는 못 쓴다」로 던진다. 증적(단계 사진 · 실패한 요소 표시)은 구간 안에서도 남는다 — kit 이 맡는다(러너 §5.2 「범용 앱 부품」)
    웹 맥락은 **앱이 웹뷰 디버깅을 켠 빌드**에서만 보인다(러너 §5.2 「앱 공용 부품」 「앱 쪽이 준비할 것」). 안 보이는 앱(스토어에서 깐 앱이 대개 그렇다)은 웹뷰 안도 네이티브 주소 규칙(위 이름표 → id → 부모 꼴)으로만 찾고, 그것으로 안 되면 보류한다(`앱 — <요구 번호> — 웹뷰 맥락 없음`)
  - **요소가 없는 자리는 누르지 않는다** (2026-11-15 사용자 — 좌표 금지를 그대로 둔다) — 지도 핀처럼 화면 글에 요소가 없는 자리는 좌표로만 누를 수 있고 좌표는 폰 크기가 바뀌면 어긋난다. appium-cli 의 좌표 누르기는 눌러 보는 데만 쓰고 케이스에 옮길 코드를 내지 않는다. 그 자리가 필요한 케이스는 보류한다(`앱 — <요구 번호> — 요소 없는 자리`). 손동작 부품(요소 안에서 밀기 · 끌어 놓기 · 두 손가락)은 요소 주소를 받는다
    - **예외 — 요소 하나 안의 자리는 그 요소 안 % 로 긋는다** (2026-11-16 사용자 APP-F3-11 시작 질문) — 서명 칸 · 패턴 잠금 · 그림판처럼 요소가 칸 하나뿐이고 그 안의 자리를 눌러야 하는 화면은 `요소위에그리기(driver, '<요소 주소>', [[가로 %, 세로 %], …])` 로 쓴다. 점은 그 요소 상자 안의 %(0~100)라 폰 크기가 달라도 칸 안의 같은 자리를 긋는다 — 좌표 금지의 까닭(폰 크기마다 어긋남)에 걸리지 않는다. 점 하나면 그 자리 누르기, 여럿이면 누른 채 이어 긋기다. **같은 % 가 늘 같은 것을 가리키는 칸에만 쓴다** — 지도는 확대 · 위치에 따라 같은 % 가 다른 곳이라 지도 핀 누르기는 여전히 보류다. 화면 좌표 누르기와 요소가 아예 없는 화면(게임 엔진이 그린 화면 — control_cli)은 그대로 금지 · 보류다

  - **권한은 시험 대상 앱의 것만 바꾼다** — 「위치 권한을 거절한 상태」 같은 시작 상태는 `권한상태에서(driver, { 준다 · 뺀다 }, async () => { … })` 구간으로 만든다. 구간이 끝나면(던져도) kit 이 앞 권한으로 되돌린다 — 연결 하나를 이어 쓰는 길(E2E 시나리오의 앱 단계 · `keepAppData` 케이스)에서 바꾼 권한이 뒤로 넘어가지 않게 한다. 권한을 빼면 Android 가 그 앱을 끈다 — 부품이 다시 켠다
  - **다른 앱 · 시스템 화면** — 권한 창은 `권한창답하기` 만 쓴다. 알림 창 · 공유 창 · 사진 고르개 · 다른 앱(Chrome · 소셜 로그인 · 결제)은 그 화면의 요소를 네이티브 주소 규칙으로 찾되, 주소는 서비스 도우미 파일에 모은다(폰 기종 · OS 판마다 달라 한 곳만 고친다). **폰에 원래 깔린 앱의 데이터 · 설정 · 계정은 바꾸지 않는다** — 읽고, 고르고, 돌아오는 데까지다. 케이스가 끝나기 전에 시험 대상 앱을 다시 앞에 둔다
  - **앱 깔기 · 지우기는 시험 대상 앱만** (2026-11-15 사용자) — 디바이스 팜이 이번 실행에 깐 앱(APK 경로 · 주소로 준 앱)만이다. 패키지 이름으로 준 스토어 앱과 폰에 원래 깔린 앱은 지우지 않는다 — 팜이 「남길 앱」으로 둔 것이라 지우면 다음 실행이 그 폰을 못 잡는다(러너 §5.2 「플레이스토어 앱 — 패키지 이름」). 처음 깐 상태는 `앱다시깔기(driver)`, 옛 판에서 새 판으로 올리기는 `옛판에서올리기(driver, async () => { … })` 구간(구간 안은 옛 판 — 로그인 · 데이터 만들기, 구간 뒤에 올린 판에서 verify)으로 쓴다. 옛 판은 빌드 목록의 바로 앞 빌드다(2026-11-16 사용자 — 러너 §5.2 「범용 앱 부품」 「앞 빌드」). 앞 빌드가 없는 줄에서는 부품이 던져 그 케이스가 실패한다
  - **앱이 받은 파일은 받기 전 · 뒤를 둘 다 본다** (2026-11-16 APP-F3-10) — 영수증 · 내보내기처럼 앱이 폰에 받은 파일은 `폰파일있나(driver, 폴더, 이름)` 로 본다. 받기 전에 같은 이름이 없는지 먼저 `verify` 한다 — 같은 폰을 잡은 동안 앞 케이스가 받은 파일이 남아 있으면 받기가 안 돼도 통과한다(팜은 폰을 돌려받을 때 다운로드를 비운다). 케이스는 앱이 받은 파일을 지우지 않는다 — 지우는 것은 `폰에파일넣기` 로 넣은 파일뿐이다
  - **넣어도 못 덮는 것** — 생체 인증 · 카메라에 QR 을 비추는 것 · 캡차 · 실제 문자 수신은 실제 폰에서 자동으로 못 한다. 테스트 서버가 우회 길(고정 인증번호 · 건너뛰기 설정)을 열어 준 것만 쓰고, 없으면 보류한다(`앱 — <요구 번호> — <까닭>`). 화면 캡처를 막은 화면은 증적 사진이 검게 나온다 — 요소는 읽히므로 케이스는 돈다. AI 가 화면 사진을 보고 요소를 찾는 길은 두지 않는다 — 돌려받는 것이 좌표다. 요소 안 % 자리 긋기(`요소위에그리기`)는 이와 다르다 — 요소는 주소로 찾고 사진은 그 요소 안의 % 를 어림하는 데만 쓴다(위 「요소가 없는 자리는 누르지 않는다」 예외)
- **기대값을 화면에서 읽어 담지 않는다** — 브라우저 케이스와 같은 규칙이다(CLAUDE.md 「저장소에 담아 둔 남의 스킬」). 화면에서 읽는 것은 요소 주소뿐이다. 웹뷰 · 알림 창 · 다른 앱 화면에서 읽은 글도 같다
- 돌리는 법 · 환경값 · 한계는 [러너.md](../도메인/러너.md) §5.2 「앱 실행」이 정본이다. 폰 연결 정보는 케이스가 아니라 러너 환경값이 정한다

### API 케이스 (2026-10-20 · API-F1-01)

종류 「API」 애플리케이션의 케이스다. 화면이 없고 요청 도구로만 돈다. **무엇을 왜 하는지는 [도메인/API.md](../도메인/API.md) §3.8 이 정본이다.**
선언 · `test.step` · `verify` · 비밀값 꼬리표 · K 표는 브라우저 케이스와 같다. 다른 것은 머리 `apiDoc` 과 본문 인자 `api` 둘이다.

```ts
export const spec = defineCase({
  tcId: 'NTF-FN-014',
  name: '예약 발송 시각이 5분 안이면 400 이다',
  apiDoc: 3,
  precondition: ['고객사 A 기기가 하나 등록돼 있다'],
  params: null,
  expected: null,
});

test(spec, async ({ api }) => {
  const 고객사A = api('고객사 A');
  let 기기 = '';

  await test.step('고객사 A 기기를 하나 등록한다', async () => {
    기기 = await 기기등록(고객사A);
  });

  await test.step('scheduledAt 을 지금+1분으로 푸시를 보낸다', async () => {
    const res = await 고객사A.post('/v1/pushes', { data: { deviceId: 기기, title: '예약', scheduledAt: 분뒤(1) } });
    await verify('응답 코드가 400 이다', res.status(), 400);
    await verify('오류 코드가 SCHEDULE_TOO_SOON 이다', (await res.json()).code, 'SCHEDULE_TOO_SOON');
  });

  await test.step('등록한 기기를 지운다', async () => {
    await 기기지우기(고객사A, 기기);
  });
});
```

- **`apiDoc` 은 케이스를 만든 API 문서 판 번호다** — 실행 때 그 판과 응답 모양을 견준다. API 애플리케이션 케이스에만 단다. 1 이상의 정수가 아니면 `defineCase` 가 던진다(K8 로 찍힌다)
- 본문 인자에 `api` 가 는다 — `api('이름')` 이 그 대상 서버 줄의 API 인증으로 토큰을 붙인 요청 도구를 준다. `request` 는 「인증 없이」다(401 시험). 이름은 케이스에 글자로 적고 비밀값 칸으로 받지 않는다 — 비밀값은 설정에만 있다
- 대상 서버 줄에 어드민 키가 있으면 본문 인자 `admin` 도 있다 — 아래 「게임 케이스」의 `admin` 과 같다(그 키를 머리로 붙인 요청 도구 · 없는데 꺼내면 kit 이 던진다 · 2026-11-03). 키 값을 케이스에 적지 않는다. E2E 단계에서는 아직 없다(도메인/API §3.8 「어드민 키」 한계)
- `page` · `driver` 는 쓰지 않는다. 디바이스는 `desktop` 하나다 — `apiDoc` 이 있는데 `platforms` 가 `['desktop']` 이 아니면 `defineCase` 가 던진다(도메인/API §3.8 「꼬리표와 다르다」)
- 반복 동작(`기기등록` · `기기지우기`)은 `helpers/api.helper.ts` 에 둔다 — 아래 Page Object 파일과 같은 자리 규칙이다

### 게임 케이스 (2026-10-23 · GAME-F1-09)

종류 「게임」 애플리케이션의 케이스다 — 모바일 게임은 `platforms: ['android']`, PC 게임은 윈도우 값이다(아래 넷째 줄 · 게임 하나에 플랫폼 하나 — [게임.md](../도메인/게임.md) §3.10 결정 27). 폰에서는 Appium 이 게임을 깔고 kit 이 켠 뒤(도메인/러너 §5.2 「앱 켜기」) 게임 안 SDK 에 붙는다. **무엇을 왜 하는지는 [도메인/게임.md](../도메인/게임.md) §3.10 이 정본이고, 몸통 칸 · 도우미의 꼴은 [3-공유계약.md](3-공유계약.md) 「게임 테스트 타입」이 정본이다.**
선언 · `test.step` · `verify` · 비밀값 꼬리표 · K 표는 Android 앱 케이스와 같다. 다른 것은 머리 `elements` · `smoke` 와 본문 인자 `game` · `admin`, 도우미 `verify.element` · `verify.rates` 다.

- 본문 인자는 `{ game, driver, admin, request, api, params, expected }` 다. `game` 은 게임 애플리케이션 항목에만, `admin` 은 대상 서버 줄에 어드민 키가 있을 때만 있다 — 없는 쪽을 꺼내면 kit 이 던진다(Android 앱 케이스의 `page` 와 같은 규칙)
- 주소는 오브젝트 이름 → 겹치면 `/` 경로(`[순번]`). 좌표 · 고정 시간 쉬기는 쓰지 않는다 — 기다림은 `game.waitFor` · `game.waitForValue`([게임.md](../도메인/게임.md) §3.10 「케이스 꼴」)
- **PC 게임 케이스는 윈도우 값을 적는다** — 보통 케이스는 `['windows']`(키보드 · 마우스로 한 번), 「연결한 패드의 버튼 그림이 화면에 뜨나」 케이스만 애플리케이션의 지원 패드 값(예 `['windows-ps5', 'windows-xbox']` — 지원 패드에 남은 패드마다 한 번 · 펼치는 규칙의 정본은 [게임.md](../도메인/게임.md) §7 마지막 블록)이다. `android` 와 같이 적지 않는다(2026-11-19 · 반영 GAME-F4-05 — 앞 판은 `['android', 'windows']` 를 받고 패드는 실행할 때 골랐다). PC 항목에는 Appium 이 없어 `driver` 를 꺼내면 던진다. 키 · 패드는 `game.key` · `keyDown` · `keyUp` · `game.pad()`(읽기만) — 2026-11-19 · GAME-F4-02, 마우스 올리기 · 휠 · 케이스 도중 껐다 켜기는 `game.mouseMove` · `game.scroll` · `game.restart()` — 2026-11-22, 무엇을 왜는 [게임.md](../도메인/게임.md) §3.10 「윈도우 PC」, 꼴은 [3-공유계약.md](3-공유계약.md) 「윈도우 PC 게임」
- 쓰는 규칙(준비 · 확인 수단 · 간섭 차단 · 스모크 · 배치 확인)은 작성 지침 `tpx-cases` `references/game.md`(2026-10-23 GAME-F1-11)가 맡는다. 창 화면 객체는 웹 Page Object 와 같은 `pages/<창>.page.ts` 이고 `주소` 값이 창 열쇠(`game:<장면>/<창 경로>`)다

### 테스트 프로시저 (2026-11-23 사용자 · TP-F1-02 — 선언은 2026-11-24 TP-F2-06 · 실행과 케이스 판정은 2026-11-24 TP-F2-07 · 판정 흘려보내기와 케이스별 입력은 2026-11-24 TP-F2-08 · 검사기와 스캐너는 2026-11-24 TP-F2-09 반영)

**테스트 하나가 사용 흐름을 따라 케이스 여럿을 확인한다. 결과는 케이스마다 붙고 프로시저는 돌리는 단위다.**
ISTQB · ISO/IEC/IEEE 29119 의 Test Procedure 다 — 실행 순서대로 놓인 케이스 묶음에 시작 상태 준비와 끝 정리가 붙는다.
앞 판은 파일 하나 = 테스트 하나 = 확인 하나라 폰 연결 · 앱 켜기 · 게임 입장 같은 비싼 준비를 케이스마다 되풀이했다
(`tests/ash/ASH-FN-016.spec.ts` 는 캐릭터 생성 → 이동 → 구역 확인 하나 → 캐릭터 삭제다).

- **쓰는 곳은 Android 앱 · 게임이다** (K21). 웹은 지금 꼴(케이스 하나 = 테스트 하나)에 로그인 이어 쓰기만 보탰고(K18 · 2026-11-23 TP-F0-01) API 와 게임 미션(`-GS-`)도 지금 꼴 그대로다.
  웹은 테스트끼리 독립 · 깨끗한 시작이 표준 권고이고(Selenium · Playwright · Cypress 공식 문서) 웹 기능 케이스의 앞 절차가 겹치는 것은 로그인뿐이었다. 미션은 이미 흐름 하나짜리 테스트이고 규칙을 끝에 한꺼번에 판정해 차례 구간으로 못 쪼갠다
- **옛 꼴 `test(spec, body)` 는 그대로 돈다.** 기존 파일은 한꺼번에 옮기지 않는다 — 애플리케이션마다 다시 작성할 때 옮기고 그때까지 두 꼴이 같이 돈다.
  애플리케이션이 프로시저 방식인지는 「프로시저 작성」 스위치가 정하고 프로시저 파일은 스위치를 켠 애플리케이션에만 둔다([실행.md](../도메인/실행.md) §3.2 「테스트 프로시저 실행」 「프로시저 작성 스위치」)
- **케이스 번호는 지금처럼 코드가 매긴다.** 작성 AI 는 번호가 매겨진 케이스를 흐름으로 묶고 차례를 정하는 일만 한다.
  묶는 규칙(흐름 하나 · 화면과 데이터를 안 바꾸는 확인 먼저 · 빨간 채 두는 케이스와 미확정 · 오류 추정 · 보류 케이스는 맨 뒤나 따로 · 버튼 반응은 화면마다 따로)과 프로시저 번호를 매기는 법 · 관문 · 돌려 보기 · 고치기는 [작성.md](../도메인/작성.md) §3.6 「★ 테스트 프로시저 작성」이 정본이다
- **프로시저끼리는 기대지 않는다** — 프로시저 하나가 자기 시작 상태를 스스로 맞춘다. 준비는 지금처럼 지름길(GM · 로그인된 채 켜기 · API)을 쓴다

```ts
// tests/mta/MTA-TP-012.spec.ts
import { defineCase, defineProcedure, test, verify } from '@platform/kit';
import { z } from 'zod';

import { 로그인된채켜기 } from './helpers/login-inject.helper.js';
import { 내글지우기 } from './helpers/post.helper.js';
import { 글쓰기화면 } from './pages/compose.page.js';

const 본문없음 = defineCase({
  tcId: 'MTA-FN-101',
  name: '본문이 비어 있으면 게시 버튼을 누를 수 없다',
  platforms: ['android'],
  precondition: [],
  params: z.object({
    loginId: z.string().describe('일반 회원 아이디').optional().meta({ secret: true }),
    loginPassword: z.string().describe('일반 회원 비밀번호').optional().meta({ secret: true }),
  }),
  expected: null,
});

const 글자수초과 = defineCase({
  tcId: 'MTA-FN-102',
  name: '본문이 500자를 넘으면 남은 글자 수가 음수로 보인다',
  platforms: ['android'],
  precondition: [],
  params: z.object({ 본문: z.string().default('가'.repeat(501)).describe('본문') }),
  expected: z.object({ 남은글자: z.string().default('-1').describe('남은 글자 수') }),
});

export const procedure = defineProcedure({
  procId: 'MTA-TP-012',
  name: '글쓰기 — 입력 제한부터 게시까지',
  platforms: ['android'],
  precondition: ['일반 회원으로 로그인해 있다'],
  launchIntent: 로그인된채켜기('loginId', 'loginPassword'),
  cases: [본문없음, 글자수초과],
});

test(procedure, async ({ driver }) => {
  const 글쓰기 = new 글쓰기화면(driver);

  await test.cleanup('올린 글을 지운다', async () => {
    await 내글지우기(driver);
  });

  await test.step('글쓰기 화면을 연다', async () => {
    await 글쓰기.연다();
  });

  await test.case(본문없음, async () => {
    await test.step('본문을 비운다', async () => {
      await 글쓰기.본문을넣는다('');
      await verify('게시 버튼이 꺼져 있다', await 글쓰기.게시버튼이켜졌나(), false);
    });
  });

  await test.case(글자수초과, async ({ params, expected }) => {
    await test.step('본문에 501자를 넣는다', async () => {
      await 글쓰기.본문을넣는다(params.본문);
      await verify('남은 글자 수가 기대값과 같다', await 글쓰기.남은글자(), expected.남은글자);
    });
  });
});
```

| 칸 | 뜻 |
|----|----|
| `procId` | 프로시저 번호 `<접두사>-TP-<3자리>`. 파일 이름이 `<procId>.spec.ts` 다(K2). **케이스 번호가 아니다** — 다시 작성하면 달라질 수 있다. 그래서 DB · 설정이 저장하는 참조(E2E 단계 · 정기 실행 목록 · 호환성 추가 · 성능 설정 · 이슈)는 전부 케이스 번호로 두고 돌릴 때 그 케이스가 든 프로시저를 찾는다 |
| `name` | 흐름 이름. 목록의 프로시저 묶음 머리와 증적에 나온다 |
| `platforms` | `android` 하나이거나 윈도우 값이다. 안 케이스가 모두 같은 값을 적는다(K21) |
| `precondition` | 흐름 전체의 시작 상태. 스캐너가 케이스마다 그 케이스 `precondition` 앞에 붙여 저장한다 — 증적의 사전조건 칸이 지금 길 그대로 읽는다 |
| `cases` | 도는 차례대로 놓은 케이스 선언. 1개 이상 10개 이하(K19). 케이스 선언은 옛 꼴과 같은 `defineCase({...})` 이고 내보내지 않는다 |
| `launchIntent` · `keepAppData` | 앱 켜기 설정. 폰 연결과 앱 켜기가 프로시저에 한 번이라 여기에 적는다(K22). `launchIntent` 는 `cases` 첫 케이스의 입력값을 받는다 — 로그인할 계정 칸은 첫 케이스의 `params` 에 둔다(위 본보기의 `loginId` · `loginPassword`). 값을 못 만들면 지금 규칙대로 그냥 켠다 — 첫 케이스가 보류일 때도 그렇다(채울 값이 비어 있다) |

- `test(procedure, 본문)` — 본문 인자는 옛 꼴과 같다(`driver` · `game` · `admin` · `request` · `api`). `params` · `expected` 는 없다 — 케이스마다 `test.case` 가 넘긴다
- `test.case(케이스, 본문)` — 그 케이스의 확인 구간이다. 본문 인자는 `{ params, expected }` 이고 그 케이스 선언의 스키마로 검증한 값이다. 부르는 자리는 K20 이 정한다.
  값이 스키마와 안 맞으면 그 케이스가 준비 구간에서 깨진 것이다(아래 「케이스 판정」). `test(procedure, 본문)` 의 인자에서 `params` · `expected` 를 꺼내면 던진다
- `test.step` · `verify` · `test.cleanup` · 비밀값 꼬리표는 옛 꼴과 같다. `verify` 는 지금처럼 `test.step` 안에서만 부른다. 절차 번호(`seq`)는 프로시저 전체에서 이어진다(E2E 부품과 같다)
- 케이스 선언의 `techniques` · `elements` · `smoke` · `held` 는 케이스마다 그대로 적는다. 스모크는 케이스 표시다 — 스모크 실행이 프로시저를 어떻게 돌리는지는 [실행.md](../도메인/실행.md) §3.2 「테스트 프로시저 실행」 「스모크」
- **`held` 케이스는 그 구간만 건너뛴다** — 미실행으로 남고 뒤 케이스는 그대로 돈다. **건너뛴 케이스는 뒤 케이스를 막지 않는다** — 아무것도 깨뜨리지 않았으므로 아래 케이스 판정의 「통과가 아닌 앞 케이스」로 치지 않고 막은 케이스도 되지 않는다.
  케이스가 모두 보류인 프로시저는 폰 연결을 열지 않고 통째로 건너뛴다. 보류 케이스를 프로시저 어디에 두는지는 작성 규칙이다(위).
  보류 케이스의 판정(미실행 + 보류 사유)은 프로시저가 시작할 때 난다 — 통째로 건너뛸 때도 케이스마다 판정 줄이 나간다([러너.md](../도메인/러너.md) §5.2 「프로시저 실행」 「보류 케이스의 줄은 시작할 때 낸다」 · 2026-11-24 TP-F2-08).
  **보류 케이스 바로 앞의 준비 절차는 그 뒤에 오는 보류 아닌 케이스의 준비 구간이다** (2026-11-24 사용자 · TP-F2-07 시작 질문) — 보류 케이스는 건너뛰므로 그 절차가 깨지면 실제로 못 도는 것은 다음 케이스다.
  뒤에 보류 아닌 케이스가 없으면 그 절차는 돌지 않는다 — 붙을 케이스가 없다(K20 이 마지막 케이스 뒤에 절차를 두지 않는 것과 같은 까닭이다)
- **지금 kit 에 있는 것은 선언 · 스캔 내보내기 · 프로시저 실행 · 판정 흘려보내기다.** 스캔 때(`PLATFORM_SCAN=1`) 프로시저 파일은 옛 꼴처럼 Playwright 에 등록하지 않고 `procedure` 만 내보낸다 — 케이스 선언마다 프로시저 번호(`procId`)와 차례(`procSeq`)가 실려 있다(2026-11-24 TP-F2-06).
  돌릴 때는 `test(procedure, …)` 가 Playwright 테스트 하나로 등록되고(K8) `test.case` 가 구간을 가르며 kit 이 아래 표대로 케이스마다 판정(`CaseResult`)을 정한다(2026-11-24 TP-F2-07 — `packages/kit/src/runtime/procedure.ts`).
  **판정은 케이스가 끝나는 대로 kit 밖으로 나간다** (2026-11-24 TP-F2-08) — Playwright 첨부와 stdout 줄 둘이다. 케이스 입력값은 러너가 넘긴 케이스별 값이고, 사람이 손으로 돌리면 스키마 기본값에 계정 칸만 채운다.
  줄의 꼴 · 내는 때 · 러너가 그 줄로 답을 만드는 법은 [러너.md](../도메인/러너.md) §5.2 「프로시저 실행」이 정본이다.
  케이스가 하나라도 통과가 아니면(보류는 뺀다) Playwright 테스트가 실패로 끝나고 절차 결과에는 그 절차가 든 케이스(`StepResult.tcId`)가 실린다 — 손으로 돌려도 빨강 · 초록이 맞다.
  E2E 단계로도 돈다 — 시나리오 모드에서는 Playwright 에 등록하지 않고 그 프로시저의 케이스 번호마다 실행 함수를 등록부에 올린다. 어느 케이스로 꺼내도 프로시저 전체가 돌고 판정은 같은 규칙이다(2026-11-24 TP-F4-24 — [시나리오.md](../도메인/시나리오.md) §3.7 결정 17)
- **돌릴 때 kit 이 막는 것** (2026-11-24 사용자 · TP-F2-07 시작 질문) — K20 은 검사기가 글자로 보지만(2026-11-24 TP-F2-09) 어긋난 파일이 돌더라도 조용히 초록이 되지 않게 한다.
  `test.case` 를 부르지 않고 본문이 끝났거나 `cases` 차례와 다른 케이스를 불렀으면 그 차례 케이스가 깨진 것이다(예외 — 아래 표대로 실패나 Blocked 가 되고 남은 케이스는 Blocked 다).
  `test.case` 를 프로시저 밖에서나 `test.step` 안에서 불러도 던진다.
  **본문이 절차의 예외를 삼키고(`try` · `catch`) 넘어가도 그 케이스는 깨진 것이다** — 멈춘 뒤라 다음 절차가 돌지 않고, 틀린 `blocker` 확인이 없는 멈춤은 판정이 아니라 깨짐으로 가른다(사유는 그 절차에 남은 오류다).
  **마지막 케이스가 끝난 뒤에 절차를 더 두었거나 `test.case` 를 한 번 더 불렀으면 그 뒤는 돌지 않고 Playwright 테스트가 실패로 끝난다** — 붙을 케이스가 없어 케이스 판정에는 남지 않는다(K20 의 까닭 그대로다). 뒤에 보류 케이스가 남았으면 그 케이스의 준비 절차라 그냥 넘긴다.
  마지막 케이스 뒤의 절차 밖 코드가 깨지거나 한도에 걸려도 같다 — 테스트만 실패로 끝나고 케이스 판정은 그대로다. 판정이 다 난 뒤에 프로세스가 실패로 끝난 것은 러너가 케이스 판정을 그대로 두고 답 맨 위 `error` 에 싣는다([러너.md](../도메인/러너.md) §5.2 「프로시저 실행」 · 2026-11-24 TP-F2-08).
  케이스 구간에 판정 확인이 하나도 없는 것(K6)과 마지막 케이스 뒤에 둔 절차 밖 코드(K20)는 kit 이 보지 않는다 — 옛 꼴과 같이 검사기 몫이다
- **`defineProcedure` 가 던지는 것** (2026-11-24 TP-F2-06) — 선언만 보고 아는 어긋남은 선언할 때 던진다. `defineCase` 가 섞인 `platforms` 를 던지는 것(K5)과 같은 방식이다.
  `cases` 가 비었거나 10개를 넘는다(K19) · 같은 케이스(번호가 같은 다른 선언도)를 두 번 넣었거나 다른 프로시저에 든 케이스를 넣었다(K2 · K19) · 다른 파일에서 선언한 케이스를 넣었다(K19) · 게임 미션 케이스를 넣었다(K19) ·
  프로시저의 `platforms` 가 `android` 하나도 윈도우 값도 아니거나 안 케이스와 다르다(K21) · 케이스에 앱 켜기 설정을 적었다(K22) · 윈도우 프로시저에 앱 켜기 설정을 달았다(케이스 선언과 같은 규칙).
  글자로 봐야 아는 것(맨 위 선언 이름 · `test.case` 차례와 자리 · 케이스 구간마다 판정 · 제목 겹침 · 번호 꼴)은 검사기 몫이다(2026-11-24 TP-F2-09 — `apps/admin/src/catalog/procedure.ts` · `rules.ts`).
  던진 것은 스캐너가 그 파일을 못 읽은 것으로 남기고 `check:tests` 가 K8 「명세를 읽지 못했다」에 그 글을 실어 찍는다
- 스캐너는 프로시저 파일 하나에서 케이스 여럿을 읽는다(2026-11-24 TP-F2-09). 케이스의 프로시저 번호 · 차례는 `defineProcedure` 가 실어 둔 것을 그대로 담는다 — 스캐너가 다시 매기지 않는다([3-공유계약.md](3-공유계약.md) 「테스트 프로시저 타입」).
  파일을 케이스 구간으로 가르는 규칙과 구간별 단계 제목 · 화면 연결 · 지문은 [카탈로그.md](../도메인/카탈로그.md) §3.1 「케이스 구간」이 정본이다

#### 케이스 구간과 준비 구간

- **케이스 구간**은 `test.case(케이스, 본문)` 하나다
- **준비 구간**은 앞 케이스 구간이 끝난 뒤부터(첫 케이스는 본문 시작부터 — 폰 연결과 앱 켜기도 든다) 그 케이스의 **첫 판정 확인(`verify`) 전까지**다.
  케이스 사이의 `test.step` 과, 케이스 구간 안에서 첫 `verify` 를 부르기 전의 조작이 여기 든다.
  **작성자가 표시를 달지 않는다** — kit 이 첫 `verify` 를 보고 안다(E2E 가 쓰는 준비 구간 표시 `phase.judged` 와 같은 뜻이고 같은 표시를 쓴다 — `blocker` 확인은 준비가 됐는지 보는 것이라 준비 구간을 끝내지 않는다)
- **절차는 그 절차가 든 케이스에 붙는다.** 케이스 사이의 절차는 다음 케이스 것이다(`StepResult.tcId`). 마지막 케이스 뒤에는 절차를 두지 않는다(K20)
- **정리 절차(`test.cleanup`)는 케이스 판정을 바꾸지 않는다** — 지금 규칙 그대로 실패해도 그 절차만 `NA` 다. 시작 때 도는 정리는 처음 도는 케이스(보류가 아닌 첫 케이스)에 붙고, 끝 정리는 마지막으로 돈 케이스의 절차 뒤에 붙는다. 정리 자리는 옛 꼴처럼 본문 맨 앞이다 — kit 은 정리를 부른 그때 차례인 케이스에 시작 정리를 붙인다.
  끝 정리는 그 케이스의 판정이 난 뒤에 돌므로 kit 이 정리 절차를 더한 판정 줄을 한 번 더 낸다([러너.md](../도메인/러너.md) §5.2 「프로시저 실행」)

#### 케이스 판정 — Blocked 는 미실행의 사유다

「깨졌다」는 예외(요소를 못 찾음 · 화면이 안 뜸)와 케이스 한도 초과다. 판정 확인이 틀린 것은 깨진 것이 아니다.
「통과가 아닌 앞 케이스」는 실패 · 한도 초과 · Blocked 로 끝난 케이스다. 보류로 건너뛴 케이스는 치지 않는다(위).

| 무슨 일이 났나 | 그 케이스 | 흐름 |
|---|---|---|
| 구간이 끝까지 돌고 판정 확인이 다 맞다 | `PASS` | 다음 케이스로 간다 |
| 판정 확인이 틀렸다(`blocker` 아님) | `FAIL` | **계속 간다** — 그 케이스의 남은 절차도, 다음 케이스도 돈다 |
| `blocker` 확인이 틀렸다 | `FAIL` | 멈춘다 |
| **준비 구간에서 깨졌고 앞 케이스 가운데 통과가 아닌 것이 있다** | **Blocked** | 멈춘다 |
| 준비 구간에서 깨졌고 앞 케이스가 다 통과다(첫 케이스도 여기다) | 예외면 `FAIL` + `error` · 한도 초과면 `NA` + 제한 시간 초과 글 | 멈춘다 |
| 첫 판정 확인 뒤에 깨졌다 | 윗줄과 같다 | 멈춘다 |
| 흐름이 멈춘 뒤 남은 케이스 | **Blocked** | — |

- **Blocked 는 판정값이 아니다.** `status: 'NA'` + `error.message: 'BLOCKED'` + 막은 케이스 번호(`blockedBy`)로 남긴다. 판정값은 그대로 셋이다([3-공유계약.md](3-공유계약.md) §5.1 `ItemStatus`).
  화면 · 리포트에는 「Blocked」로 따로 보이고 따로 센다 — 글자는 시안(TP-F1-05)이 정한다
- **막은 케이스**는 통과가 아닌 앞 케이스 가운데 가장 가까운 것이다. 그 케이스가 Blocked 면 그 케이스의 막은 케이스를 물려받는다 — 그래서 막은 케이스는 늘 스스로 깨지거나 틀린 케이스를 가리킨다.
  흐름이 멈춘 뒤 남은 케이스의 막은 케이스는 흐름을 멈춘 케이스다(그 케이스가 Blocked 면 물려받는다).
  **Blocked 를 정하는 것은 kit 한 곳이다** — 흐름이 멈추면 kit 이 남은 케이스의 Blocked 판정까지 스스로 낸다
- **앞 케이스가 실패해도 할 수 있으면 그대로 돈다** (2026-11-23 사용자). 판정 확인이 틀린 뒤 다음 케이스의 준비가 되면 그 케이스는 돌아 통과 · 실패가 난다. Blocked 는 준비가 깨졌을 때만이다
- **한도 초과는 지금처럼 `NA` 다** — 옛 꼴 케이스의 Playwright 제한 시간 초과와 같은 꼴로 남긴다([러너.md](../도메인/러너.md) §5.2 「프로시저 실행」 「케이스별 한도」)
- **러너가 프로세스를 끊었거나(`TIMEOUT`) 사람이 중단했으면(`ABORTED`) Blocked 가 아니다.** 끝난 케이스의 판정은 남고 돌던 케이스와 못 간 케이스는 그 사유의 `NA` 다 — 막은 것이 케이스가 아니다. 채우는 쪽은 러너다([러너.md](../도메인/러너.md) §5.2 「프로시저 실행」 「못 간 케이스 채우기」)
- **미실행으로 끝난 줄은 판정이 아닌 결과다** — 무엇이 여기 드는지 · 무엇을 덮지 않는지 · 가르는 한 곳은 [실행.md](../도메인/실행.md) §3.2 「테스트 프로시저 실행」 「판정이 아닌 결과」가 정본이다

예 — `MTA-TP-012` 가 케이스 넷을 돈다.

```
로그인된 채 앱 켜기 → 글쓰기 화면 열기
본문 비우고 게시 누르기          → MTA-FN-101  통과
500자 넘게 넣기                  → MTA-FN-102  통과
```

### Page Object 파일 (2026-10-02 · PR #129 · 기능 테스트는 PR #130)

`tests/<폴더>/pages/<이름>.page.ts` · `tests/<폴더>/components/<이름>.component.ts` · `tests/<폴더>/helpers/<이름>.helper.ts`(로그인 · 계정 · 자료 도우미, 2026-10-11 PRD-F4-04 — 도메인/작성 §3.6 「지도」)는 케이스가 아니다. 이름 꼴은 `^[a-z][a-z0-9-]{0,40}$` 다.
스캐너와 케이스 규칙은 `.spec.ts` 만 보고, Playwright 도 `.spec.ts` · `.test.ts` 만 테스트로 집는다. 그래서 **`.spec.ts` 로 끝나지 않게** 짓는다.
이 파일에는 **K7(주석 · `expect` 금지)과 `test.step` · `verify` 호출 금지, 아래 가져오기 제한, K15(고정 대기 금지) · K16(작성 환경 주소 금지) · K17(공용 부품 밖 CSS · XPath 금지 — `components/` · `helpers/` 는 세지 않는다) · K18(`helpers/login.helper.ts` 만 — 화면 로그인은 `로그인이어쓰기` 로)**를 걸고 `check:tests` 가 건다(`catalog/pageObject.ts`) — 케이스 규칙을 걸면 멀쩡한 파일이 위반으로 찍힌다.
**가져올 수 있는 곳은 셋뿐이다** (2026-10-02 PR #130) — 같은 `tests/` 안 파일(그 파일도 이 검사를 받는다) · `@playwright/test`(`test` · `expect` · 통째로 가져오기 말고) · `@platform/kit` 과 그 하위 경로의 **타입**. **2026-11-15 부터 `@platform/kit/parts` 는 값도 가져온다**(통째로 가져오기는 안 된다) — 공용 부품(기다리기 · 지금 화면 가르기 · 권한 창 · 로그인 이어 쓰기 — [러너.md](../도메인/러너.md) §5.2 「앱 공용 부품」 · 「웹 공용 부품」)만 모은 입구라 판정 · 절차가 없다. kit `src/parts.ts` 가 판정 · 절차를 품은 것을 내보내지 않는 것이 이 약속이다 — 검사(`webParts.test.ts`)가 내보내는 이름을 목록과 글자까지 맞춰 봐, 부품을 더하면 그 목록을 고치며 다시 보게 된다.
그 밖(다른 패키지 · `tests/` 밖 상대 경로 · `import = require` · `require()` · 동적 `import()` · `tests/` 밖을 다시 내보내기)은 K7 이다 — 이름을 바꿔 판정 · 절차를 들여오는 길을 막는다.
**`tests/` 아래 JS 파일(`.js` · `.mjs` · `.cjs`)도 K7 이다** — 타입 검사와 이 검사를 피한 채 import 로 불린다.
E2E 「만들기」 판별(도메인/시나리오 §3.7 결정 4)이 이 금지를 근거로 Page Object 호출을 믿는다. 여기가 새면 판정이 든 절차가 건너뛰어진다.
같은 검사가 `tests/` 아래 **케이스(`.spec.ts`)가 아닌 `.ts` 전부**에 걸린다 — 이름 꼴이 틀린 파일도 검사를 비켜 가지 못한다. 이름 꼴은 올리기 허용 목록이 본다.
올리기 허용 목록에 들고 CI 서비스 폴더 판정에서는 면제된다.
`test.step` · `verify` 는 케이스 파일에 둔다 — K6 · K12 와 증적이 거기서 읽는다. 언제 쓰나는 [작성.md](../도메인/작성.md) §3.6 「★ 테스트 두 갈래」.

### 스크린샷

- **실패한 스텝은 자동으로 찍는다.** 통과한 화면은 아무도 열어보지 않고,
  전부 찍으면 실행 한 번에 수십 장이 쌓여 디스크가 금방 찬다
- **증적용으로 명시 지정**: `test.step(제목, fn, { capture: true })`.
  인자 순서는 Playwright의 `test.step(title, body, options)`와 같다. kit의 `test`는 Playwright를
  감싼 래퍼이고 `capture`는 kit이 추가한 옵션이다.
  검수 문서에 "이 화면이 이렇게 나왔다"를 넣어야 할 때 쓴다. 기본값은 false
- API 테스트는 화면이 없으므로 대신 요청·응답 원문을 같은 자리에 남긴다
- 앱 케이스(`android`)는 브라우저 화면이 아니라 **폰 화면**을 찍는다. 경로 규칙은 같다 (2026-10-07)
- **실패 사진에는 그 절차가 처음 실패한 때까지 마지막으로 다룬 요소를 빨갛게 표시한다** (2026-10-29 사용자) — 사진만으로는 어디가 문제인지 찾기 어려웠다. 실패 뒤에 다룬 요소로는 옮겨 가지 않는다.
  웹은 kit 이 넘기는 `page` 에서 나온 Locator 중 마지막으로 메서드를 부른 것을 반투명 빨간 상자로 덮는다(Playwright 사진의 `mask` — 따로 부른 동작이 trace 조작 목록에 섞이지 않게 사진 찍기 한 번 안에서 한다). `page` 에서 바로 부른 것(`page.fill('#x')` · `page.url()`)은 짚을 요소가 없어 표시를 비운다.
  앱은 Appium 으로 마지막으로 다룬 요소(찾기 · 누르기 · 글 읽기처럼 그 요소로 간 명령)를 웹과 같은 반투명 빨강으로 덮고 둘레에 굵은 빨간 테두리를 그린다(2026-10-29 사용자 — 첫 판의 3화소 테두리는 1080×2400 폰 사진에서 안 보였다). 사진 파일에 직접 그려서 실행 기록 · 증적 · 엑셀이 따로 손댈 것 없이 같은 사진을 쓴다.
  `verify` 는 값만 받으므로 요소와 상관없는 값(주소 · API 응답)을 견주다 틀리면 그 절차의 다른 요소를 짚을 수 있다. 요소를 못 찾았거나 숨었으면 표시 없이 사진만 남긴다. 같은 Locator 에 맞는 요소가 여럿이면 웹은 다 덮는다.
  앱은 `$$` 목록의 줄 · 요소 안에서 이어 찾은 요소(`줄.$('id=수량')`)도 그 요소로 명령을 보내면 짚는다 — 첫 판은 `driver.$` 찾기만 봐서 DMA-FN-401(장바구니 줄의 수량)에 표시가 없었다. 찾기가 실패하면 표시를 비운다.
  `capture: true` 로 찍은 통과 절차에는 그리지 않는다. 코드는 `packages/kit/src/runtime/highlight.ts`

### 4.1 비밀값 꼬리표 (2026-09-16 결정)

로그인 케이스의 `password`처럼 **문서에 남으면 안 되는 입력값**이 있다. 이것을 **비밀값**이라 부른다.
선언에서 그 칸에 꼬리표를 달아 둔다.

```ts
params: z.object({
  username: z.string().min(1).describe('아이디'),
  password: z.string().min(1).describe('비밀번호').meta({ secret: true }),
}),
```

`.meta({ ... })`는 zod가 스키마에 꼬리표(메타데이터, 값 자체가 아니라 값에 붙이는 설명표)를 다는 기능이다.
JSON Schema로 바꿀 때 그 칸 아래에 `"secret": true`로 그대로 살아남고 `.describe()`도 함께 남는다.
이 저장소에 깔린 zod로 확인했다. **꼬리표를 다는 데는 kit에 새 함수를 만들지 않는다.** 이미 있는 기능이라 추가할 코드가 0줄이다.

**계정 칸에는 역할 이름을 단다** (2026-10-12 · 진행판 PRD-F9-01) — `.meta({ secret: true, account: '관리자' })`. 실행 · 반영 때 대상 서버 줄의 그 역할 계정으로 비어 있는 칸을 채운다.
`account` 가 없는 비밀값 칸은 일반 회원 계정이다. 아이디인지 비밀번호인지는 칸 이름으로 가린다. 판정 함수는 `packages/kit/src/accounts.ts` 하나이고(서버 · kit 실행이 같이 쓴다),
규칙의 정본은 [도메인/작성.md](../도메인/작성.md) §3.6 「★ 역할별 계정」이다. `account` 도 JSON Schema 에 그대로 살아남는다. **K 규칙은 더하지 않는다** — 틀린 역할 이름은 실행이 「비밀값이 비어 있다」로 드러낸다

**가리는 것은 화면과 문서뿐이다. DB에는 평문 그대로 넣는다.** 예외는 둘 — trace 를 푼 세 표(`run_network` · `run_action` · `run_console`)는 넣을 때 가리고(2026-10-16), 성능 녹화(HAR)는 남기기 전에 가린다(2026-10-21 대기). 아래 표 끝 줄들이다.

| 어디 | 무엇을 한다 |
|------|------------|
| 실행 창 (실행 §8.2 · §8.10) | 타이핑할 때 글자가 보이지 않는 입력칸으로 만든다 |
| 실행 결과 목록·항목 상세 (§8.3·§8.4) | 값을 `********`로 바꿔 보여준다 |
| 실행 조회 응답 `GET /api/runs/:runId` · `/items/:historyId` (2026-09-29) | 응답에서도 `********`로 바꿔 싣는다(`params` · `expected`). DB 는 평문 그대로다 — 화면만 가리면 개발자 도구로 원문이 보인다. 그 비밀 값이 확인의 기대 · 실제 값 · 절차 오류 · 절차 기록(`httpTrace`) · 항목 오류에 되비치면 그 글자도 가린다(2026-10-12 진행판 WEB-F3-13 — 시나리오 실행 결과와 같은 규칙). 실패 카드 `GET /api/runs/:runId/failures` 의 `item` 도 같은 함수로 읽는다. 견주기 `GET /api/runs/:runId/insights` 의 실패덩어리 대표 문장과 대시보드 `GET /api/dashboard` 의 회귀 실패 사유도 가린 뒤 자르고 가린 글자로 묶는다. 숫자로 적은 비밀은 키 칸만 가려진다(도메인/시나리오 §7 의 한계와 같다) |
| 시나리오 실행 결과 응답 `GET /api/runs/:runId/scenario` (2026-10-06) | 부품 `part.params` · `part.expected` · `bound` 를 박제 스키마로 `********` 로 바꾸고, 그 비밀 값이 절차 기록 · 오류 · 뒷정리 주소에 되비치면 그 글자도 가린다 — 저장값으로 채운 비밀번호가 부품에 박제되기 때문이다. 시험 실행 결과도 같다. 정본은 도메인/시나리오 §7 |
| 증적 문서 (§8.4) | 같다. `********`만 들어간다. 확인의 기대 · 실제 값과 판정 못 낸 사유 · 예외로 깨진 `FAIL` 사유에 되비친 비밀 글자도 가린다(2026-10-12 · 예외 `FAIL` 은 2026-10-17). 객체 값 안쪽의 비밀값 이름 칸도 가린다 |
| `run_item.params` (§6) | **평문 그대로 저장한다** |
| trace 기록 `run_network` · `run_action` · `run_console` (2026-10-16 · 진행판 PRD-F10-03) | **가린 뒤 저장한다** — 다시 실행할 재료가 아니라 화면에 그대로 보일 기록이고, 응답 본문의 토큰처럼 실행 값 목록에 없는 비밀이 섞인다. 위 값 목록 가림에 비밀 칸 이름(과 인증 머리 · 세션 · 쿠키 · api_key)에 붙은 값 · 비밀번호 칸에 넣은 값을 더한다. 주소 경로(물음표 · # 앞)에서는 계정 아이디 칸 값을 안 가린다 — 케이스 정식 실행 기록만이고 서비스 지도를 채우는 기록이라서다(2026-10-26 WEB-F6-03 · 실행 §3.2 「trace」). 항목 상세 `/items/:historyId` 의 `trace` 칸은 저장된 그대로 싣는다. 정본은 도메인/실행 §3.2 「trace」. E2E 실패 부품의 `scenario_run_part.trace` · 시험 실행 결과의 `trace` 도 같은 가림이다(2026-10-17 · 도메인/시나리오 §7 「실패 기록」) |
| API 인증 비밀값 · 받은 토큰 (2026-10-20 · 도메인/API §3.8 「API 인증」) | **kit 이 절차 기록(`httpTrace`)에 남기기 전에 가린다** — 실행 값이 아니라 설정에서 오는 비밀이라 위 값 목록 가림에 안 걸린다. 설정 응답은 끝 4자리만 싣는다 |
| 저장값 `case_input.params` (§6 · §8.2, 2026-09-29) | **평문 그대로 저장한다.** 다만 케이스 응답(`savedInput`)에는 원문을 싣지 않고 칸 이름만 `savedSecrets` 로 알린다 — 목록 응답에 서비스 전체 분량이 실린다. 지금 명세에 없는 칸은 응답에서 뺀다. 실행을 만들 때 서버가 채운다 (§3.2) |
| 성능 녹화 HAR `artifacts/perf-record/` (2026-10-21 PERF-F1-04 — 도메인/성능 §7 「PERF-F1-04 가 연 통로」) | **남기기 전에 가린다** — trace 와 같은 가림(비밀번호 칸에 넣은 값 · 인증 머리 · 세션 · 쿠키 · 토큰)이고 가리기 전 원본은 지운다. AI 에 넘기는 재료라 원문이 남을 까닭이 없다. 가린 자리는 꼬리표로 바꾼다 — 테스트 계정은 `${username}` · `${password}`, 나머지는 같은 값이면 같은 `<<비밀N>>` 이다(변수 추출을 찾으려면 값이 같은 자리가 이어져 보여야 한다) |
| 성능 시나리오 계정 CSV `perf_scenario.accounts_csv` (2026-10-21 · PERF-F1-03 반영) | **평문 그대로 저장한다** — 대상 서버 줄의 테스트 계정 비밀번호와 같다. 응답 · 화면에는 행 수만 싣고, 실행 때 에이전트에 그 몫의 줄만 준다 |

저장 시점에 가리면 그 실행을 다시 돌릴 수 없고, 값이 틀려서 실패한 것인지 알 방법도 같이 사라진다.
여기 들어오는 것은 테스트 전용 계정뿐이므로 저장을 막아서 얻는 것보다 잃는 것이 크다.

**기계가 못 잡는 자리가 있다.** K9는 칸 **이름**만 보고 판단한다.
`answer`·`code`처럼 이름만으로는 비밀값인지 알 수 없는 칸은 검사기가 그냥 지나친다.
그건 케이스를 쓰는 사람이 직접 달아야 하고, 갈래를 끝낼 때 spec-review가 사람 눈으로 본다.
이 한계를 메우려고 값의 생김새를 추측하는 규칙은 넣지 않는다. 오탐이 늘면 아무도 검사기를 안 믿는다.
