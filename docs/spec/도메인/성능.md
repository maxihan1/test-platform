### 3.9 성능 테스트 — JMeter · nGrinder 가 하는 일을 쉽게, AI 와 함께 (2026-10-21 사용자)

사용자(2026-10-21) 「QA Hub에 웹과 서버 성능 테스트도 넣으려고 하는데 같이 구상 해볼까?」 · 「JMeter나 ngrinder 와 동일한 기능이지만 사용성이 편하고 AI가 관여할수 있는 부분등을 고려해줘」 · 「게임이나 모바일 성능은 어떻게 하지?」.
아래 결정 표는 같은 날 대화로 하나씩 정했고 시작 질문(PERF-F1-01)에서 묶음을 승인받았다. 다시 묻지 않는다. 「(내 결정)」이 붙은 줄은 대화에서 알렸고 반대가 없던 것이다.

#### 누가 무엇을 하나

```
화면 ── admin ──┬── 부하 발생 에이전트 N대 (k6) ───→ 대상 서버
                │     일을 받아 가고 1초마다 숫자를 보낸다 (§5.4)
                ├── 모니터링 에이전트 (대상 서버 위) ── CPU · 메모리 · 디스크 · 네트워크
                ├── author 컨테이너 ── AI 일 (트랜잭션 목록 · 산정 · 추천 · 분석)
                └── 러너 · 디바이스 팜 · 내 컴퓨터 러너 ── 녹화 실행 · 기기 측정
```

- **admin 이 하는 일** — 스크립트 생성 · 가상 사용자 나누기 · 1초 숫자 합치기 · 판정 · 자동 중단 · 저장. **판정과 저장은 admin 만 한다** — 에이전트는 DB 를 모른다(러너와 같은 규칙, 도메인/러너 §3.4)
- 에이전트는 QA Hub 로 **나가는 연결만** 한다 — 일을 받아 가고(claim) 숫자를 보낸다. 회사 안 기계에 띄워도 들어오는 포트를 열 필요가 없다

#### 스크립트는 생성기가 만든다

- 시나리오의 정본은 트랜잭션 목록(JSON)이다. admin 의 생성기가 실행마다 그 목록 · 부하 설정 · 성능 목표로 k6 스크립트를 만든다. **사람도 AI 도 k6 스크립트를 직접 쓰지 않는다** — 대상 호스트 · 비밀값 · 트랜잭션 꼬리표를 한 곳에서 지킨다
- **트랜잭션 한 줄** — 이름 · 메서드 · 주소(대상 서버 주소 아래 경로) · 헤더 · 본문 · 변수 추출 · 응답 검증(상태 코드 · 본문에 든 글자) · Think Time. 요청마다 꼬리표 `tx=<트랜잭션 이름>` 을 달아 트랜잭션별로 센다. 응답 검증을 쓰는 법(에러를 두 번 세지 않게)은 §5.4 「요청 수 · 에러 수」
- **변수 추출** — `{ 변수, 어느 트랜잭션 응답, 위치(JSON 경로 · 헤더 · 쿠키), 방식(첫 값 · 무작위 1개) }`. 로그인 토큰은 가상 사용자마다 자기 것을 쓴다
- **테스트 계정** — 계정 CSV(아이디 · 비밀번호 · 역할)를 올리면 가상 사용자마다 한 줄씩 차례로 나눠 쓴다(모자라면 처음부터 다시). 없으면 대상 서버 줄의 테스트 계정 하나를 모두 같이 쓴다. CSV 는 비밀값이다 — 응답 · 화면에는 행 수만 보인다
- **허용 호스트** — 트랜잭션 주소는 대상 서버 주소 아래 경로(상대 주소)가 기본이다. 다른 호스트는 같은 프로젝트의 API 서버 꼬리표(공통/1 §2 「API 서버」)에 이름이 붙은 호스트만 절대 주소로 쓴다.
  두 번 본다 — 저장(`POST` · `PUT /api/perf/scenarios`)은 절대 주소가 그 API 서버 호스트인지 보고, 실행 만들기는 고른 대상 서버 주소의 호스트와 그 API 서버 호스트로 `allowedHosts` 를 만들어 에이전트에 넘긴다. 어긋나면 400 `HOST_NOT_ALLOWED` 다.
  녹화에 섞인 외부 호스트(CDN · 분석 · 결제사)는 AI 가 빼고 「제외 목록」에 남긴다
- **더미 클라이언트 시나리오는 예외다** — 트랜잭션 목록 대신 `body.dummyClient`(올린 더미 클라이언트 번호)를 들고, 생성기는 k6 스크립트를 만들지 않는다(아래 「게임 서버 부하」)

#### 시나리오 만들기 — 세 길 (결정 4)

1. **E2E · 케이스 녹화** — 고른 케이스나 E2E 시나리오를 서버 러너로 한 번 돌리며 브라우저가 주고받은 요청 전부(HAR)를 남긴다. 이 「녹화 실행」은 기록 · 증적에 안 남는다(도메인/러너 「성능 테스트 — 녹화 실행 · 기기 측정」). 정식 실행 기록(`run_network`)은 값을 가리고 본문을 버려 쓸 수 없다.
   admin 이 이미지 · 폰트 · CSS · 미디어를 먼저 빼고, AI 가 남은 정적 리소스(분석 스크립트) · 외부 호스트를 뺀 뒤 트랜잭션 이름 · 변수 추출 · Think Time(녹화 사이 간격을 1초 단위로 반올림 — 간격은 admin 이 센다)을 채운다(2026-10-21 PERF-F1-04). 녹화 원본은 비밀번호 · 토큰을 가려 시나리오 버전 옆에 남긴다
2. **Swagger** — API 애플리케이션의 API 문서 판(도메인/API §3.8)에서 API 를 골라 차례를 정하면 AI 가 요청 본문 예시 · 변수 추출을 채운다
3. **JMeter · nGrinder 가져오기** — `.jmx` · nGrinder 스크립트(Groovy · Jython)를 올리면 AI 가 트랜잭션 목록으로 옮긴다. 옮긴 뒤 스모크 테스트로 확인한다. 옮기지 못한 요소(BeanShell · 자바 코드)는 「옮기지 못한 부분」으로 남겨 사람이 고친다

셋 다 결과는 마법사 1단계의 트랜잭션 목록이다. 저장할 때마다 버전이 오른다(E2E 시나리오와 같다 — 도메인/시나리오 §3.7).

#### 부하 설정 (결정 5)

| 테스트 유형 | 모양 | k6 |
|---|---|---|
| 부하 테스트 | 램프업 → 목표 가상 사용자 유지 → 내리기 | `ramping-vus` |
| 스트레스 테스트 | 피크까지 올려 머문 뒤 최대 가상 사용자까지 램프업. 성능 목표를 벗어나면 자동 중단 | `ramping-vus` |
| 스파이크 테스트 | 기준 부하 → 10초 안에 최대로 → 유지 → 급감 → 기준 | `ramping-vus` |
| 내구성 테스트 | 램프업 → 목표 부하를 몇 시간 유지 | `ramping-vus` |

- 목표 TPS 기준으로 바꾸면 같은 모양을 `ramping-arrival-rate` 로 만든다
- **상세 설정**은 구간 목록 `[{ 시간(초), 목표 가상 사용자 또는 목표 TPS }]` 이다. 유형을 고르면 채워지고 사람이 고친다
- **AI 동시 사용자 산정** — 피크 동시 사용자 = 일 방문자 × 피크 집중률 × 평균 체류 시간(분) ÷ 피크 시간(분). 피크 시간은 60분(피크 1시간)으로 둔다(2026-10-21 PERF-F1-04 시작 질문). AI 는 기획서 비기능 요구사항 · 서비스 가이드에서 세 값과 근거 요구 번호를 찾기만 하고 계산은 admin 이 한다(기획서에 비기능 칸이 따로 없어 AI 가 전체에서 성능 관련 줄을 고른다). 못 찾으면 화면이 세 값을 묻는다. 스트레스 테스트의 최대는 피크의 5배가 기본이다
- **상한** — 한 실행의 가상 사용자는 고른 부하 발생 에이전트의 최대 가상 사용자 합까지, 실행 시간은 24시간까지다
- **스모크 테스트** — 본 테스트 전에 가상 사용자 1명으로 1분(트랜잭션을 한 바퀴 넘게) 돈다. 에러가 하나라도 나거나 응답 검증이 실패하거나 요청이 하나도 없으면 본 테스트를 하지 않고 중단한다(사유 `SMOKE_FAILED` — 요청 0건은 2026-10-21 PERF-F1-03)
- **자동 중단** — admin 이 1초 숫자를 합친 뒤 본다
  - 스트레스 테스트 — 95% 응답시간 · 에러율 목표를 10초 이어 벗어나면 중단한다(`TARGET_EXCEEDED`). 벗어나기 시작한 직전 1초의 가상 사용자 수를 **최대 동시 사용자**로 남긴다
  - 모든 유형 — 에러율 20% 이상이 10초 이어지면 대상 서버를 지키려고 중단한다(`ERROR_LIMIT`)
  - 그 실행의 부하를 맡은 에이전트 하나가 30초 동안 아무 통로도 부르지 않으면 중단한다(`AGENT_LOST`). 에이전트가 부르는 모든 통로가 연락이고, 실행 중에는 1초 숫자가 곧 연락이다(세는 기준은 §5.4). 모니터링 에이전트가 끊기면 실행은 이어 가고 실행 로그에 「web-1 모니터링 끊김」 한 줄을 남긴다
  - 사람이 「실행 중단」을 누르면 중단한다(`USER`)
  - 세 수(10초 · 20% · 30초)는 admin 코드 상수 한 곳이다
- **부하 발생 에이전트 하나는 한 번에 실행 하나만 맡는다** — 고른 에이전트가 다른 실행 중이면 그 실행은 대기한다

#### 성능 목표 (결정 6)

- **지표** — 서버: 95% 응답시간(전체 · 트랜잭션별) · 에러율 · TPS(최소). 페이지: LCP · FCP · CLS. 기기: 평균 FPS · 1% Low FPS · 최대 기기 온도 · 메모리 최대 · 앱 실행 시간
- **근거 꼬리표** — 「기획서」(요구 번호와 인용 한 줄) · 「AI 추천」 · 「직접 입력」. 값을 고치면 「직접 입력」이 된다
- **AI 추천 기본값** — 에러율 1% · LCP 2.5초 · FCP 1.8초 · CLS 0.1(Core Web Vitals 「좋음」) · 1% Low FPS 30 · 최대 기기 온도 45도. AI 는 기획서(PRD)에서 숫자를 먼저 찾고 없을 때만 이 값을 쓴다. 추천 근거를 한 줄씩 남긴다(화면 「AI 추천 근거」).
  **서비스 가이드의 숫자는 성능 목표에 쓰지 않는다** — 가이드는 기대값의 근거가 아니다(도메인/작성 §3.6 「★ 서비스 가이드」). 부하 크기 산정에는 쓴다 — 판정 기준이 아니라서다
- **판정** — 모든 목표를 지키면 통과, 하나라도 벗어나면 실패다. 측정값은 끝까지 돈 실행이면 전체 구간, 목표나 에러율 때문에 멈춘 실행이면 멈추기 직전 10초다. TPS 는 최대값이다
- **끝난 모양마다 상태 · 판정 · 까닭** — 이 표가 정본이다(SQL CHECK 가 같은 짝을 지킨다 — 공통/4-데이터모델 「성능 테스트 표」)

  | 끝난 모양 | 상태 `status` | 판정 `verdict` | 까닭 `stop_reason` |
  |---|---|---|---|
  | 끝까지 돌았다(스트레스 테스트는 최대 가상 사용자까지 목표를 지켰다) | 끝 `DONE` | 목표대로 통과 · 실패 | 없음 |
  | 스트레스 테스트가 목표를 벗어나 멈췄다 — 이 유형의 보통 끝이다 | 끝 `DONE` | 실패 — 정한 최대 가상 사용자까지 못 버텼다. 결과의 주인공은 최대 동시 사용자다 | `TARGET_EXCEEDED` |
  | 에러율 20% 를 넘어 대상 서버를 지키려고 멈췄다 | 중단 `STOPPED` | 실패 | `ERROR_LIMIT` |
  | 스모크 테스트가 실패했다 | 중단 `STOPPED` | 없음 — 시나리오를 고칠 일이다 | `SMOKE_FAILED` |
  | 부하를 맡은 에이전트가 끊겼다 | 중단 `STOPPED` | 없음 | `AGENT_LOST` |
  | 사람이 「실행 중단」을 눌렀다 | 중단 `STOPPED` | 없음 | `USER` |
  | admin · 에이전트가 고장 났다 | 오류 `ERROR` | 없음 | 없음 |

  판정이 없는 실행은 화면 · 실행 기록에서 「중단」 · 「오류」로 보이고 성능 저하 견주기에서 빠진다
- **성능 저하** — 같은 시나리오 · 같은 대상 서버 · 같은 유형의 이전 실행(마지막으로 끝난 것)과 견준다. 견주는 지점은 두 실행이 모두 지난 가상 사용자 수 중 가장 큰 값(100명 단위로 내림)이다. 그 지점의 95% 응답시간이 20% 넘게 늘면 「성능 저하」다. 판정과 따로 보인다
- **추적표** — 근거가 「기획서」인 목표는 요구 번호를 든다. PRD 관리 추적표의 그 요구 줄에 「성능 목표 · 최근 판정」이 붙는다(PERF-F1-06 — 도메인/작성 §3.6 「메뉴가 곧 요구사항 추적표다」)

#### 실행 · 결과 (결정 7)

- 번호는 `PRF-` 네 자리 이상(`PRF-0012`)이다. 상태는 대기 → 스모크 → 실행 중 → 끝(통과 · 실패) · 중단 · 오류
- **1초 숫자** — 에이전트가 1초마다 트랜잭션별 요청 수 · 에러 수 · 응답시간 분포와 가상 사용자 수를 보낸다(§5.4). admin 이 같은 초 · 트랜잭션끼리 더하고 전체 한 행(`tx = ''`)을 같이 남긴다(§5.4)
- **분포** — 응답시간을 고정 경계 116칸에 센 개수 배열이다. 칸 0 은 1ms 이하, 칸 i(1~115)는 1.1^(i−1)ms 초과 1.1^i ms 이하이고, 1.1^115ms(약 57.6초)를 넘는 응답도 마지막 칸에 센다. 경계를 세는 코드는 지금 `apps/perf-agent/src/hist.ts` 다. admin 은 같은 코드를 `apps/admin/src/perf/hist.ts` 에 하나 더 두고 두 파일의 경계가 같은지 검사가 본다 — 에이전트 이미지는 저장소 부품을 담지 않아 kit 로 옮기지 못한다(2026-10-21 PERF-F1-03 시작 질문). 합칠 때 칸끼리 더하고 95% · 99% 응답시간은 합친 분포에서 그 칸의 가운데 값(1.1^(i−0.5)ms)으로 센다. 오차는 ±5% 이고 화면은 0.1초 단위로 보인다
- **AI 분석** — 실행이 끝나면 AI 일이 선다. 재료는 admin 이 센 표(목표별 측정값 · 트랜잭션별 · 서버 모니터링 요약 · 이전 실행 대비)뿐이고, AI 는 그 표에 없는 숫자를 쓰지 않는다. 꼴은 제목 한 줄과 개조식 항목(임계점 · 병목 구간 · 원인 추정 · 이전 실행 대비 · 페이지 로딩 · 정상 구간)이다. 못 만들면 「AI 분석을 만들지 못했습니다」와 「다시 만들기」
- **PDF** — 결과 화면 차례 그대로(AI 분석 → 성능 목표 달성 여부 → 시간대별 추이 → 트랜잭션별)다. 케이스 증적(도메인/리포팅 §8.4)과 다른 문서이고 글꼴 규칙은 같다
- **정기 실행** — 시나리오마다 「매일 HH:MM · 대상 서버」(기능 테스트의 정기 실행과 같은 꼴 — 공통/6 §9.2). 알림은 기능 테스트 정기 실행처럼 늘 보내고 판정 · 성능 저하를 문장 머리에 단다(도메인/실행 §8.9 와 같은 Slack 길).
  손으로 돌린 실행은 마법사 3단계 「성능 저하 알림」을 켜 두었고 그 실행이 성능 저하일 때만 보낸다(2026-10-21 PERF-F1-06 시작 질문). 정기 실행은 저장해 둔 마법사 값(부하 설정 · 성능 목표 · 부하 발생 에이전트 · 모니터링 에이전트)으로 실행을 만든다 — 그 값이 없으면 켜지 않는다(400 `INVALID_REQUEST`).
  켜고 끄는 것은 admin 만이고 자리는 시나리오 화면 머리의 「정기 실행」 단추다(§8.14). 정기 실행이 만드는 실행도 실행 만들기와 같은 검사를 지난다 — 그 대상 서버가 그사이 실서비스 서버가 되었거나 지워졌으면 실행을 만들지 않고 정기 실행을 끈 뒤 알림 한 줄을 보낸다
- **Grafana** — 실행마다의 숫자(최대 동시 사용자 · 최대 TPS · 95% 응답시간 · 에러율)를 잇는 추세 패널 하나(도메인/리포팅 §8.5). **판정은 싣지 않는다** — 테스트 결과(판정)는 앱이 맡고 Grafana 는 운영 지표를 맡는다는 2026-10-07 결정을 그대로 따른다. 숫자는 지금 실행 패널(평균 소요시간)과 같은 수준이라 프로젝트를 가리지 않는 Grafana 에 둔다
- 초 단위 표 · 녹화 화면의 보관 기간은 L6 에서 같이 정한다(공통/1 §1.1)

#### 서버 모니터링 (결정 8)

- 모니터링 에이전트도 일이 없을 때 2초마다 일을 받으러 온다. 실행이 그 에이전트를 골랐으면 일 「MONITOR」(시작 시각 · 실행 시간)를 받아 부하와 같은 시작 시각부터 1초마다 보낸다(§5.4). Linux `/proc` 에서 CPU · 메모리 · 디스크 I/O · 네트워크(받기 · 보내기)를 읽는다
- 마법사 4단계에서 고른다. 결과 그래프는 부하 숫자와 같은 시간축이다
- 모니터링 에이전트는 부하 일(SMOKE · LOAD · PAGE)을 받지 않는다 — MONITOR 일만 받는다
- **모니터링 에이전트는 프로젝트 하나에 매인다** — 남의 프로젝트 서버에 깐 에이전트를 골라 그 서버 지표를 받아 가지 못하게 한다. 발급 때 프로젝트를 고르고, 목록 · 고르기는 그 프로젝트 권한이 있는 사람만 한다. 부하 발생 에이전트는 공용이다(내 결정)

#### 페이지 성능 (결정 9)

- k6 browser(Chromium)로 잰다 — 부하 발생 에이전트 이미지에 Chromium · 한글 글꼴이 들었다(2026-10-21 PERF-F1-07 — `apps/perf-agent/Dockerfile`). 스크립트는 생성기가 만든다(`apps/admin/src/perf/pageScript.ts`). 한 번 열 때마다 새 브라우저 문맥이라 앞서 연 것의 캐시가 다음 값을 낮추지 않는다
- **목표는 고정이다** — AI 추천 기본값(LCP 2.5초 · FCP 1.8초 · CLS 0.1)이고 셋을 다 지켜야 그 페이지가 통과다. 값이 없는 지표 · 못 잰 페이지는 실패다. 고치는 칸은 아직 없다(2026-10-21 PERF-F1-07 시작 질문). 실행의 `targets` 에는 페이지마다 세 줄(`metric` `LCP` · `FCP` · `CLS` · `scope` 가 경로)을 쓴다
- **맡는 에이전트** — 연결된 빈 부하 발생 에이전트 중 번호가 가장 작은 것(다 바쁘면 연결된 것 중 가장 작은 번호가 비기를 기다린다). 없으면 409 `NO_AGENT` 다. 스모크 테스트 · 자동 중단은 없다
- **단독 측정** — 고른 페이지마다 3번 열어 가운데 값을 쓴다. 디바이스 PC · 모바일(화면 크기 · 사용자 에이전트), 네트워크 「제한 없음」 · 「Slow 4G」(Lighthouse 모바일 기본 — 지연 150ms · 내려받기 1.6Mbps · 올리기 750kbps)
- **부하 중 측정** — 부하 실행의 「부하 중 페이지 로딩 측정」을 켜면 생성기가 같은 k6 스크립트에 브라우저 시나리오를 하나 더 넣는다. 브라우저 2개(기본)가 고른 페이지를 30초마다 열고, 실행 구간으로 에이전트들에 함께 나뉜다(에이전트 2대면 브라우저 하나씩).
  따로 된 일이 아니라서 「에이전트 하나는 한 번에 실행 하나」 규칙이 그대로다. 스모크 테스트에는 넣지 않는다. 값은 그때의 가상 사용자 수와 같이 남는다(그 초의 전체 줄에서 읽을 때 붙인다).
  **잴 페이지는 그 애플리케이션 · 대상 서버의 가장 최근 단독 측정에서 고른 페이지다**(없으면 메인 `/`). PC · 제한 없음으로 잰다. 웹 애플리케이션만 켜고, 로그인할 페이지가 있는데 계정이나 로그인 화면이 없으면 실행을 만들지 않는다(400 `INVALID_REQUEST` — 오류로 끝날 실행을 만들지 않는다)(2026-10-21 PERF-F1-07 시작 질문)
- **잴 페이지** — AI 가 화면 지도(도메인/작성 §3.6 「화면 기록」)에서 주요 페이지 5개를 골라 제안한다. 재료는 화면 기록의 상태 · 틀 · 이름 · 진짜 주소(기록 첫 줄)와 찾은 화면의 틀 · 이름뿐이다 — 기록 본문에는 로그인 화면의 이름 · 이메일이 들 수 있다. 「페이지 선택」에서 빼거나 경로를 직접 적어 더한다(1~10개, `/` 로 시작하는 경로).
  로그인이 필요한 페이지(로그인 상태로 기록된 화면)는 대상 서버 줄의 테스트 계정으로 로그인 화면을 거쳐 연다 — 로그인 화면은 화면 기록 · 찾은 화면 중 로그아웃 상태에서 주소에 `login` · `signin` 이 들거나 이름에 「로그인」이 든 것이고, 비밀번호 칸과 그 바로 앞 입력 칸에 계정을 넣고 Enter 를 누른 뒤 쿠키만 다음 문맥에 옮긴다. 계정이나 로그인 화면이 없으면 측정을 만들지 않는다(400 `INVALID_REQUEST`)(2026-10-21 PERF-F1-07 시작 질문)
- **견줄 값** — 단독 측정 결과의 「LCP 부하 중」은 같은 대상 서버에서 끝난 가장 최근 부하 실행(부하 중 측정을 켠 것)의 그 페이지 값이다 — 페이지마다 가상 사용자가 가장 많던 때. 거꾸로 실행 중 화면의 「단독 측정」 값은 같은 대상 서버의 가장 최근 끝난 단독 측정이다
- **로딩 워터폴 · AI 분석** — 페이지의 리소스 타이밍(문서 · 스크립트 · API · 이미지)과 LCP 요소를 남기고, AI 가 고칠 곳을 짚는다(「대표 상품 이미지 1.9MB」 · 「이미지 영역 크기 미지정 — CLS 0.18」)

#### 기기 성능 — 모바일 · 게임 (결정 11 · 12)

#### 게임 서버 부하 (결정 13)

- **k6 길** — 트랜잭션 종류에 WebSocket(연결 · 보내기 · 받을 때까지 기다리기) · gRPC(proto 파일 · 메서드 · 메시지)를 더한다. 생성기가 k6 `websockets` · `grpc` 모듈로 만든다
- **더미 클라이언트 길** — 회사가 준 리눅스 실행 파일(zip)을 admin 이 올리면 부하 발생 에이전트가 받아 가상 사용자 몫만큼 띄운다(PERF-F1-10 — 그 전에는 실행 만들기가 더미 클라이언트 시나리오를 400 `INVALID_REQUEST` 로 거절한다. 에이전트도 이 일을 받으면 「아직 못 하는 일」 ERROR 로 끝낸다). 환경값으로 대상(호스트 · 포트) · 가상 사용자 수 · 계정 CSV 경로 · 실행 시간을 준다.
  시나리오는 마법사 1단계에서 「더미 클라이언트」를 고르면 트랜잭션 목록 대신 그 번호를 든다(위 「스크립트는 생성기가 만든다」)
  - **결과는 한 줄씩** — 요청 하나가 끝날 때마다 표준 출력에 JSON 한 줄 `{"t": <epoch ms>, "tx": "<트랜잭션 이름>", "ms": <응답시간>, "ok": true | false}` 을 쓴다. 에이전트가 k6 결과와 같은 1초 분포로 묶어 보내 결과 화면이 같다
  - 더미 클라이언트는 에이전트 컨테이너 안에서만 돈다. 대상 호스트는 환경값으로만 준다 — **더미 클라이언트가 다른 곳을 두드리는 것은 우리가 막지 못한다.** 그래서 올리기는 admin 만 한다
- 가상 사용자는 동시 접속자다. 램프업 · 성능 목표 · 실서비스 금지 규칙은 위와 같다

### 5.4 부하 발생 에이전트 계약 (2026-10-21 · PERF-F1-01)

에이전트가 부르는 QA Hub 통로다. 에이전트는 들어오는 포트를 열지 않는다.

**인증** — `Authorization: Bearer pga_…`(성능 에이전트 토큰). admin 이 「에이전트 추가」에서 에이전트마다 하나 발급하고 서버에는 SHA-256 해시만 둔다(작성 에이전트 토큰과 같은 방식 — 도메인/인증 §7 「인증 적용 범위」). 이 토큰으로는 아래 통로만 열리고 그 밖은 403 `AGENT_TOKEN_SCOPE` 다.

```
POST /api/perf/agent/hello                   연락 { version, host, maxVus? } → 200 { agentId, name, mode, serverTime }
                                             켤 때와 30초마다. mode 'LOAD' | 'MONITOR' 는 발급 때 서버가 정한다
POST /api/perf/agent/claim                   일 받기 (부하 발생 · 모니터링 에이전트 둘 다 — 일이 없으면 2초마다) → 200 { job: null } | { job: <일> }
POST /api/perf/agent/runs/:runId/metrics     1초 숫자 → 200 { stop: boolean }   stop 이면 k6 를 끝내고 done 을 보낸다
POST /api/perf/agent/runs/:runId/done        { status: 'OK' | 'ERROR', reason? } → 204
GET  /api/perf/agent/dummy-clients/:id       더미 클라이언트 zip 받기 — 받은 일에 든 것만
```

**에이전트가 부르는 모든 통로가 연락이다** — 부를 때마다 `last_seen_at` 을 고친다. 실행 중에는 1초 숫자가 연락이라, 그 실행의 부하를 맡은 에이전트에게서 30초 동안 아무것도 안 오면 `AGENT_LOST` 다(§3.9 「자동 중단」 — 모니터링 에이전트가 끊기면 실행은 이어 간다).

일:
```
{ runId, kind: 'SMOKE' | 'LOAD' | 'PAGE' | 'MONITOR',
                                PAGE 는 페이지 단독 측정, MONITOR 는 모니터링 에이전트의 일이다(script · segment 없이 startAt · durationSec 만).
                                부하 중 페이지 측정은 따로 된 일이 아니라 LOAD 의 script 안 브라우저 시나리오다
  startAt,                      서버 시각. 에이전트는 hello 의 serverTime 으로 맞춘 뒤 그때 함께 시작한다
  script,                       생성기가 만든 k6 스크립트 (더미 클라이언트 · MONITOR 면 null)
  segment, segmentSequence,     k6 실행 구간 — 가상 사용자를 나눈다 ("0:1/2" · "0,1/2,1")
  env: { BASE_URL, … },
  accountsCsv?,                 이 에이전트 몫의 계정 줄만 (비밀값)
  dummyClient?: { id, command, users },
  allowedHosts: string[],
  durationSec }
```

1초 숫자:
```
부하      { sec, vus, txs: [{ name, requests, errors, hist: number[116] }], pages? }    sec 는 startAt 부터 센 초. pages 는 부하 중 페이지 측정이 그 초에 연 것
모니터링  { sec, cpu, mem, diskIoKbps, netInKbps, netOutKbps }                      cpu · mem 은 %. sec 는 같은 startAt 부터 센 초
페이지    { sec, pages: [{ url, lcpMs, fcpMs, cls, ttfbMs, lcpElement, resources }] }   단독 측정(PAGE)과 부하의 pages 가 같은 모양이다. url 은 설정의 경로 그대로다. 한 번에 50개까지
```

## 7. 성능 통로

**권한** — 경로의 애플리케이션(`serviceId`, 또는 시나리오 · 실행이 속한 애플리케이션) 프로젝트의 권한으로 본다(도메인/인증 §7 「등급으로 갈리는 자리」 표). 보기는 실행 `read`, 만들기 · 고치기 · 실행 · 중단은 실행 `write` 다. 에이전트 · 더미 클라이언트 목록은 실행 `read` 로 보고(마법사가 고른다), 붙이고 고치고 지우는 일과 정기 실행 켜기는 admin 만이다.
실서비스 서버(`is_prod`)로 부하를 거는 요청은 400 `PROD_ENV_BLOCKED` 다(§3.9 결정 10).

**PERF-F1-03 이 연 통로** (2026-10-21) — 시나리오 다섯(목록 · 만들기 · 보기 · 고치기 · 지우기) · 서버 부하 실행 만들기 · 실행 목록 · 결과 · series · hosts · events · stop · report.pdf · 에이전트 넷. draft · AI 일 · suggest(LOAD · TARGETS)는 PERF-F1-04 가 열었고(아래 「PERF-F1-04 가 연 통로」), schedule · analysis 는 PERF-F1-06 이 열었고(아래 「PERF-F1-06 이 연 통로」), suggest 의 PAGES · pages/measure · runs/:id/pages 는 PERF-F1-07 이 열었고(아래 「PERF-F1-07 이 연 통로」), 나머지(suggest 의 DEVICES · devices · dummy-clients)는 진행판 PERF-F1-08 · 10 이 연다. 그때 정한 꼴은 이렇다.
- 성능 목표 한 줄 — `metric` 은 `P95`(ms) · `ERROR_RATE`(%) · `TPS`, `op` 는 `<=` · `>=`, `source` 는 `PRD`(기획서) · `AI`(AI 추천) · `MANUAL`(직접 입력), `scope` 를 비우면 전체이고 적으면 그 트랜잭션이다
- `POST /api/perf/runs` 에 `basis: 'VUS' | 'TPS'` 를 더 받는다(기본 `VUS` — §3.9 「목표 TPS로 설정」). 목표 TPS 는 한 바퀴의 트랜잭션 수를 `timeUnit` 으로 두어 초당 요청 수로 맞춘다
- `GET /runs/:id/series` → `{ series: [{ sec, tx, vus, requests, errors, p95Ms, p99Ms }] }`(`tx` 가 빈 줄이 전체) · `hosts` → `{ hosts: [{ agentId, agentName, sec, cpu, mem, diskIoKbps, netInKbps, netOutKbps }] }` · `events` → `{ events: [{ at, level, message }] }` · `GET /runs/:id` 는 `code`(`PRF-0012`)를 더 싣는다
- 거절 — 끝난 실행 중단은 409 `NOT_RUNNING`, 끝나지 않은 실행의 PDF 는 409 `NOT_FINISHED`, 겹치는 에이전트 이름은 409 `NAME_TAKEN`
- 에이전트 목록의 `status` 는 `CONNECTED` · `BUSY`(실행을 맡음) · `OFFLINE`(30초 넘게 연락 없음). `installCommand` 는 `docker build -t qahub-perf-agent apps/perf-agent && docker run -d … -e QAHUB_URL=<이 서버> -e AGENT_TOKEN=<토큰> qahub-perf-agent` 한 줄이고 모니터링은 `--network host` 가 붙는다(§5.4)
- 계정 CSV 첫 줄이 머리(`아이디` · `id` · `username` · `login` 으로 시작)면 뺀다

**PERF-F1-04 가 연 통로** (2026-10-21 · 시작 질문 승인) — `POST /api/perf/scenarios/draft` · `POST /api/perf/suggest`(LOAD · TARGETS) · `GET /api/perf/ai-jobs/:id` · 작성 에이전트의 `claim` · `finish`. 코드는 `apps/admin/src/perf/aiRoutes.ts` · `ai.ts` · `record.ts` · `har.ts`, 작성 에이전트는 `scripts/authoring-perf.ts`. 그때 정한 꼴은 이렇다.
- **저장의 출처** — `POST` · `PUT /api/perf/scenarios` 가 `draftJobId?` 를 더 받는다. 같은 애플리케이션의 끝난(`DONE`) 초안 일이면 그 버전의 출처(`source` — `RECORD` · `SWAGGER` · `FILE`)와 녹화 파일 이름(`recording`)을 붙이고, 아니면 400 `INVALID_REQUEST` 다. 없으면 `MANUAL` 이다
- **파일 초안** — 본문을 파일 그대로(`application/octet-stream`, 1MB 까지) 보내고 `?serviceId=&from=FILE&name=` 를 단다. 더미 클라이언트 올리기와 같은 꼴이다. 녹화 · Swagger 는 JSON 본문이다
- **녹화 초안** — `{ serviceId, from: 'RECORD', env, caseIds(1~20개) | scenarioId }`. 케이스는 그 애플리케이션의 웹 케이스(desktop 이 있으면 desktop, 아니면 mobile), E2E 는 그 애플리케이션의 웹 시나리오만 받는다. 일은 녹화가 끝날 때까지 집히지 않고(`RUNNING` · 집은 시각 없음) 끝나면 대기로 선다. 대상 서버 이름이 없으면 400 `ENV_NOT_FOUND` 다.
  러너가 거절하거나 판정을 못 낸(`NA`) 녹화는 실패라 일이 `FAILED` 다 — 반쪽 녹화로 초안을 만들지 않는다. 케이스가 실패(`FAIL`)로 끝난 녹화는 쓴다 — 요청은 다 오갔다
- **녹화 가리기** — 머리글(`Authorization` · 쿠키 · `x-…-token` 꼴) · 쿠키 · 본문과 주소의 비밀 칸(이름 전체가 `password` · `…token` · `secret` · `session` · `api_key` 꼴인 칸 — `author` · `sessionCount` 처럼 일부만 닮은 칸은 아니다)의 값과, 채운 입력값의 비밀 칸 · 대상 서버 계정 · API 인증 값을 모은다. 테스트 계정 아이디(6자 이상) · 비밀번호는 생성기가 아는 `${username}` · `${password}` 로, 나머지는 같은 값이면 같은 `<<비밀N>>` 으로 바꾼다(주소 인코딩 꼴도). 가린 녹화는 `artifacts/perf-record/<jobId>.har` 한 파일로 남기고(정적 리소스는 본문을 버린다) 가리기 전 폴더는 지운다
- **AI 재료 상한** — 녹화 줄 300개 · 요청 본문 4,000자 · 응답 본문 2,000자(JSON · 글만). 브라우저 머리글(쿠키 · 사용자 에이전트 · `sec-` 꼴)은 뺀다 — k6 가 쿠키 통을 따로 쥔다
- **결과 모양** — `DRAFT_*` 는 `{ transactions, notes }`(트랜잭션 한 줄은 저장과 같은 검사), 녹화는 `excluded: [{ url, reason }]`, 파일은 `unconverted: [{ what, why }]` 를 더 든다. 녹화 결과에는 admin 이 센 `recorded: { total, staticExcluded, used, excluded }` 를 붙인다(화면 AI 줄의 숫자).
  `SUGGEST_LOAD` 는 `{ dailyVisitors, peakRatio(0~1), avgStayMin, reqIds, basis }` 이고 못 찾은 값은 null 이다 — admin 이 `peakMinutes: 60` · `peakVus` · `maxVus`(5배)를 붙인다. `SUGGEST_TARGETS` 는 `{ targets, basis }` 이고 근거 꼬리표는 `PRD`(요구 번호 필수) · `AI` 만이다
- **틀린 결과** — 모양이 틀리면 그 일을 `FAILED` 로 닫고 `finish` 가 400 `INVALID_OUTPUT` 을 준다. 끝난 일에 다시 끝을 알리면 409 `NOT_RUNNING` 이다
- **오래 쥔 일** — 집고 20분 안에 끝내지 않은 일과 admin 이 다시 켜져 끊긴 녹화는 `FAILED` 로 닫는다(집기 · 결과 보기 때 본다). 작성 에이전트는 성능 AI 일을 작성 요청과 따로 한 자리에서 하나씩 돌리고 claude 는 도구 · MCP · 스킬 없이(빈 허용 목록) 15분까지 돈다 — 재료가 남이 쓴 글(녹화 응답 · 올린 파일)이라서다. 거절(401 · 403)은 이 고리만 끝내고 작성 고리는 그대로 둔다
- **아직 못 하는 추천** — `suggest` 의 `DEVICES` 는 400 `INVALID_REQUEST` 다(PERF-F1-08 이 연다). `PAGES` 는 PERF-F1-07 이 열었다

**PERF-F1-06 이 연 통로** (2026-10-21 · 시작 질문 승인) — `PUT /api/perf/scenarios/:id/schedule` · `POST /api/perf/runs/:id/analysis`, 그리고 실행 결과 · 실행 목록 · 시나리오 보기 · PRD 응답에 칸을 더했다. 그때 정한 꼴은 이렇다.
- **실행 결과에 더한 칸** — `GET /runs/:id` 가 `scenarioName`(시나리오가 없는 페이지 · 기기 실행이면 빈 글 — 지운 시나리오는 이름이 남는다) · `servicePrefix`(그 실행 애플리케이션의 접두사 — 주소로 바로 여는 화면이 그 애플리케이션 권한으로 단추를 가른다) · `origin`(`MANUAL` · `SCHEDULED`) · `aiJob`(그 실행의 가장 최근 `ANALYZE_RUN` 일 `{ id, status }`, 없으면 null) · `comparePoint` · `transactions` 를 더 싣는다.
  `transactions` 는 트랜잭션마다 `{ tx, p95Ms, errorRate, prevP95Ms, degraded }` 다. 이전 실행이 있으면 §3.9 「성능 저하」와 같은 견줌 지점(두 실행이 모두 지난 가상 사용자 수를 100명 단위로 내린 칸)에서 세고 `comparePoint` 가 그 가상 사용자 수다. 없으면 판정 구간 전체로 세고 `comparePoint` · `prevP95Ms` 는 null 이다. 도는 실행은 빈 목록이다 — 실행 중 화면은 1초 숫자로 어림한다. 화면이 1초 숫자로 셀 수 없어 서버가 센다 — 95% 응답시간은 분포를 합쳐야 나온다
- **실행 목록에 더한 칸** — `GET /runs` 줄이 `testType` · `origin` · `degraded` · `stopReason` 을 더 싣는다(실행 기록 표의 「정기」 꼬리표 · 「성능 저하」 · 중단 사유)
- **AI 분석** — 실행이 끝났고(오류 빼고) 1초 숫자가 있으면 admin 이 `ANALYZE_RUN` 일을 세운다. 결과 모양은 `{ title, items }`(항목 1~10개 — 「임계점: …」 꼴 글)이고 끝나면 그 실행의 `ai` 칸에 쓴다. 다시 만들기는 끝나지 않은 실행이면 409 `NOT_FINISHED`, 1초 숫자가 없으면 409 `NO_DATA`, 같은 실행의 분석 일이 대기 · 진행 중이면 새로 세우지 않고 그 일 번호를 준다
- **정기 실행** — `GET /scenarios/:id` 가 `schedule`(`{ at: 'HH:MM', tz, env }` 또는 null)을 더 싣고, `PUT …/schedule` 은 200 `{ schedule }` 을 준다. 시간대가 틀렸거나 대상 서버가 없거나 마법사 값이 저장돼 있지 않으면 400 `INVALID_REQUEST` 다. admin 이 1분마다 돌 때가 된 시나리오를 집는다 — 기능 테스트 정기 실행과 같은 꼴(하루 한 번 · 1시간 창 · DB 시계)이다. 시각 · 시간대 · 대상 서버 중 하나를 바꿔 저장하면 「마지막으로 돈 때」를 비운다 — 오늘 이미 돈 뒤 시각을 늦춰도 그날 돈다
- **PRD 응답에 더한 칸** — `GET /api/prd` 가 `perf` 를 더 싣는다. 요구 번호 → `{ targets, verdict, runId }` 이고 그 애플리케이션 성능 시나리오 현재 버전의 근거 「기획서」 목표만 센다. `verdict` · `runId` 는 그 번호 목표가 든 가장 최근 판정 있는 실행이고(그 번호 목표가 하나라도 실패면 실패) 없으면 null 이다. 실행 `read` 가 없으면 빈 `{}` 다. 추적표 엑셀은 맨 끝에 「성능 목표」 칸을 더한다

**PERF-F1-07 이 연 통로** (2026-10-21 · 시작 질문 승인) — `POST /api/perf/pages/measure` · `GET /api/perf/runs/:id/pages` · `suggest` 의 `PAGES`, 그리고 `POST /api/perf/runs` 의 `pageCheck`. 코드는 `apps/admin/src/perf/pages.ts` · `pageRoutes.ts` · `pageStats.ts` · `pageScript.ts`. 그때 정한 꼴은 이렇다.
- **측정 요청의 페이지 한 줄** — `{ url, name, login }`. `url` 은 `/` 로 시작하는 경로(`//` 로 시작하면 안 된다 · 500자), 겹치면 400 이다. 웹 애플리케이션만 받는다(아니면 400 `INVALID_REQUEST`)

### 8.14 성능 테스트 화면 (2026-10-21 · 시안 캔버스 버전 14)

**자리는 사이드바 `성능 테스트`** — 하위 `시나리오`(`#/perf/scenarios`) · `페이지 성능`(`#/perf/pages`) · `기기 성능`(`#/perf/devices`) · `실행 기록`(`#/perf/runs`). 정본은 공통/5-화면공통 §8 「자리 목록」. **하위는 고른 애플리케이션 종류에 맞는 것만 선다** — 웹에서는 기기 성능이, Android 앱 · 게임에서는 페이지 성능이, API 에서는 둘 다 빠진다(시나리오 · 실행 기록은 늘 있다. 웹이라도 앱 케이스가 있으면 기기 성능이 선다)(2026-10-21 APP-F1-14 · 페이지 성능은 반영 완료 (2026-10-21, PERF-F1-07 — 종류 표 상수 `apps/admin/src/web/kind.ts`) · 기기 성능은 대기 — PERF-F1-09 가 맡는다 · 도메인/러너 §5.2 「애플리케이션 종류 「Android 앱」」 종류 표). 설정 안 구획 `성능 에이전트`(admin 만)는 도메인/인증 §8.8.

- **시나리오 만들기 — 네 단계 마법사** (2026-10-21 사용자 시안 B 선택). 위 단계 표시 「1 시나리오 · 2 부하 설정 · 3 성능 목표 · 4 실행」. 만든 뒤 고칠 때는 끝낸 단계를 눌러 바로 간다(내 결정 — 마법사의 「고칠 때 오가야 한다」를 메운다)
  1. **시나리오** — 가져오기 버튼 셋(「E2E 녹화」 · 「Swagger 가져오기」 · 「JMeter·nGrinder 가져오기」), 올린 더미 클라이언트가 있는 애플리케이션이면 「더미 클라이언트」 고르개 하나 더 · AI 줄(「녹화 요청 23건 중 API 6건 사용」 · 「정적 리소스 17건 제외」) · 트랜잭션 표(순서 · 트랜잭션 · 요청 · 변수 추출 · Think Time · 삭제). 줄을 펴면 변수 추출 표 · 응답 검증 · AI 설명. 「트랜잭션 추가」 · 「녹화 원본 보기」(비밀번호와 토큰은 마스킹)
  2. **부하 설정** — 테스트 유형 카드 넷(작은 그래프) · AI 동시 사용자 산정(근거 · 식 · 결과 · 「적용」 · 「다시 산정」) · 최대 가상 사용자 · 램프업 시간 · 자동 중단 · 미리 보기 그래프 · 「상세 설정」 · 「목표 TPS로 설정」
  3. **성능 목표** — 표(지표 · 대상 · 목표 · 근거 · 삭제) · 「목표 추가」 · 「성능 저하 알림」 · 「AI 추천 근거」
  4. **실행** — 대상 서버(실서비스 서버는 「부하 테스트 불가」로 흐리게 둔다 — `/auth/me` 의 `isProd`, 도메인/인증 §7 대기 블록. 그 전에는 고르면 서버가 400 `PROD_ENV_BLOCKED`) · 부하 발생 에이전트 · 테스트 계정 · 서버 모니터링 · 부하 중 페이지 로딩 측정 · 실행 요약 · 스모크 테스트 안내 · 「저장」 · 「실행」
- **실행 중** — 머리(테스트 유형 · 대상 서버 · 에이전트 수 · 시작 시각 · 「실행 중 mm:ss / mm:ss」 · 「실행 중단」) · 숫자 넷(가상 사용자 · TPS · 95% 응답시간 · 에러율) · 응답시간과 가상 사용자 추이 · 서버 모니터링 · 부하 발생 에이전트 · 트랜잭션별 현황 · 페이지 로딩(부하 중) · 실행 로그. 5초마다 새 숫자만 받는다
- **결과 — AI 요약 먼저** (2026-10-21 사용자 시안 A 선택) — 머리(판정 배지 · 중단 사유) · 최대 동시 사용자(스트레스 테스트 · 큰 숫자 56px, 화면에 하나) · AI 분석 · 성능 목표 달성 여부(지표 · 대상 · 목표 · 측정값 · 판정 · 근거) · 시간대별 추이(서버 모니터링 줄 겹침) · 트랜잭션별 결과(가상 사용자 N명 시점 · 이전 실행 · 변화 · 「성능 저하」) · 「PDF로 내려받기」 · 「다시 실행」
- **페이지 성능** — 측정 조건(대상 서버 · 디바이스 · 네트워크) · AI 가 고른 페이지와 「페이지 선택」 · 페이지별 측정 결과(LCP 단독 · LCP 부하 중 · FCP · CLS · 판정) · 고른 페이지의 로딩 워터폴 · AI 분석 · 「측정」.
  처음 열면 가장 최근 페이지 실행을 연다. 실행 기록에서 페이지 실행을 누르면 `#/perf/pages?run=<번호>` 로 그 실행이 열린다. 실행이 하나도 없으면 AI 추천을 받고, 화면 기록이 없으면 메인(`/`) 하나로 시작한다(2026-10-21 PERF-F1-07). 실행 중 화면의 「페이지 로딩(부하 중)」 칸과 마법사 4단계 「부하 중 페이지 로딩 측정」은 웹 애플리케이션에만 선다
- **기기 성능**
  - 측정 시작 — 조작 방식(게임이면 「AltTester 시나리오」 · 「직접 플레이」 둘, 일반 앱은 Appium 케이스. 「직접 플레이」 설명은 「팜 PC 에 꽂힌 폰을 손에 들고 플레이」다 — 시안의 「내 컴퓨터에 USB로 연결한 폰」보다 이 명세가 앞선다, §3.9 「어디서 재나」) · 시나리오와 반복 · 빌드(「AltTester SDK 확인됨」) · 측정 기기(AI 사양별 추천과 「추천 적용」) · 성능 목표 · 측정 항목 · 수집 간격 · 화면 녹화 · 「측정 시작」
  - 실행 중 — 시나리오 진행 · 기기 타일(FPS · 기기 온도 · CPU · 메모리 · 배터리 · 「현재 화면 보기」) · 실행 로그. 목표를 벗어난 기기는 타일에 「목표 미달」 글자를 달고 테두리를 실패 색으로 한다 — 색만으로 알리지 않는다
  - 결과 — **녹화 화면과 그래프 먼저** (2026-10-21 사용자 시안 B 선택): AI 분석 → 기기 탭 → 녹화 화면과 「AI가 표시한 장면」 → 구간 띠 · FPS · 기기 온도 · CPU · 메모리 그래프(재생 위치가 같이 움직인다) → 기기별 요약
- **설정 › 성능 에이전트** — 등록된 에이전트 표(이름 · 역할 · 호스트 · 상태 · 최대 가상 사용자 · 최근 접속 · 「편집」 · 「삭제」) · 「에이전트 추가」(역할 「부하 발생」 · 「모니터링」 · 설치 명령 · 「복사」 — 토큰은 이때 한 번만 보인다)
- 「성능 저하」는 판정 배지가 아니라 변화 글자다 — 실행 결과의 「신규 실패」 변화 글자와 같은 규칙으로 실패 글자색에 글자를 같이 단다(DESIGN.md 「실행 결과」 변화 글자). 판정 배지는 판정에만 쓴다(DESIGN.md 원칙 1)
- **정기 실행** — 시나리오 화면 머리의 「정기 실행」 단추(admin 만)가 시각 · 대상 서버 고르개를 연다(§3.9 「실행 · 결과」)
- **더미 클라이언트** — 설정 › 성능 에이전트 화면 아래 구획 「더미 클라이언트」에서 올리고 지운다(admin). zip 한 개 200MB 까지 — 넘으면 413
- **화면 제목** — 하위 화면 제목 앞에 묶음 이름 「성능 테스트 ›」을 세워 기능 테스트의 「실행 기록」과 가른다(공통/5-화면공통 「자리 이름」)
- 휴대폰에서 실행 중 · 결과를 연다 — 숫자 카드는 두 줄로 쌓이고 표는 가로로 민다(공통/5-화면공통 §8 「휴대폰 화면」)
