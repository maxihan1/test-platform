### 3.7 Scenario — 케이스를 이어 돌린다 (2026-09-28 신설)

- **책임**: 시나리오 정의를 버전으로 쌓고, 실행을 만들어 러너에 넘기고, 부품마다 결과를 영속화한다
- **애그리거트 루트**: `Scenario` (식별자 `id`, 화면 번호 `SC-{id}`) → `ScenarioVersion[]` → 부품 목록.
  실행 결과는 `TestRun`(구분 `SCENARIO`) → `ScenarioRunPart[]` → `Step[]`

#### 시나리오는 케이스가 아니다 (결정 1)

케이스 목록과 따로 둔다. 케이스는 요구사항의 도장이고 시나리오는 이음매를 본다.
섞으면 검수 서류에서 둘을 구분할 수 없고, 실행 시간이 달라 도는 범위도 달라진다.
**케이스 파일은 한 글자도 안 바뀐다** — 러너가 불러 쓸 뿐이다 (결정 3).

#### 부품 — 이 표가 정본이다 (결정 2)

다른 절·코드·화면에서 부품을 나열할 때는 이 표를 가리킨다. **개수를 문장에 적지 않는다** (CLAUDE.md §2.7 ⑤).
코드 값(`kind`)은 [공통/3-공유계약.md](../공통/3-공유계약.md) §5.1 `ScenarioPart` 가 정본이다.

| 부품 | `kind` | 무엇 | 언제 끝나나 |
|---|---|---|---|
| 케이스 | `case` | 이미 있는 케이스를 고른다. 입력값·기대값을 부품마다 따로 준다. 넘겨받기 · 이어 주기를 단다 (결정 12) | 그 케이스가 끝나면 |
| API 호출 | `api` | 계정 상태를 뒷문으로 심거나 API 서버를 직접 부른다. 대상 주소 기준 상대 경로 · 메서드 · 본문 · 기대 응답 코드. `service` 로 같은 프로젝트의 다른 애플리케이션 주소를 고른다 (결정 13). API 인증 · 값 주입 · 응답 값 확인을 단다 (결정 14) | 한 번 부르고 끝 |
| 모킹 | `mock` | 주소 무늬에 맞는 요청의 응답을 가짜로 바꿔친다 | **끄기 전까지 계속** (아래 「모킹」) |
| 모킹 끄기 | `unmock` | 같은 무늬로 걸어 둔 모킹을 푼다 | 즉시 |
| 대기 | `wait` | 사이에 끼운다. 60초까지 | 그 시간이 지나면 |

**사람이 고른다 — 도구와 AI 는 후보를 내고, 무엇을 넣을지는 사람이 정한다** (2026-10-10 사용자 · 2026-10-11 PRD-F7-02 반영 · 2026-10-23 결정 15 로 고침). 「어떤 흐름이 중요한가」는 기획서에 안 적힌 위험 판단이라 여전히 사람이 정한다.
조립 화면이 기능 묶음 · 종류 · 설계 기법으로 케이스를 접고 차례를 매기는 것(§8.11)은 보여 주는 순서일 뿐 고르는 일이 아니다 — 무엇을 넣을지는 여전히 사람이 정한다.
도구는 **다음 단계 추천**을 한다 — 맨 뒤 케이스 단계가 머무는 화면에서 이어지는 화면(크롤러 화면 연결)에 닿는 정상 쪽 케이스를 단계 추가 탭의 케이스 목록 맨 위(찾기 칸 위)에 올린다. 케이스 단계가 아직 없으면 **첫 단계 후보**를 올린다(결정 15).
**AI 는 흐름 후보 2~3개를 이유와 함께 내고 사람이 하나를 고른다**(결정 15 — E2E 마법사의 「AI 추천으로 시작」). 고른 뒤에도 단계를 빼고 더하는 것은 사람이다.
**2026-10-10 에는 「AI 가 흐름 초안을 만들지는 않는다」였다** — 중요도는 도구가 모르니 후보도 도구가 내지 않는다는 판단이었다. 2026-10-23 사용자가 「E2E 시나리오 만들기가 어렵다」고 해 뒤집었다.
첫 케이스를 수백 건(데모마켓 조각 MKF 의 활성 케이스)에서 직접 찾는 일이 막혔고, 후보를 여럿 받아 고르는 것은 중요도를 사람이 정하는 것과 부딪히지 않는다. 판단 기준(「중요한 흐름은 사람이 정한다」)은 그대로 남는다 — AI 는 하나로 정하지 않고 고를 거리를 낸다.
2026-10-10 전에는 도구가 후보를 아예 내지 않았다. 어느 화면이 어디로 이어지는지 알 재료가 없었기 때문이다. 크롤러가 화면 연결을 남기면서(PRD-F6-02) 「이어질 수 있는 것」은 기록으로 알게 됐다.
재료는 도메인/작성 §3.6 「★ 표준 기획서」의 지도 ② · 화면 연결이다. 규칙과 화면은 §8.11 「다음 단계 추천」, 통로는 §7 `GET /api/scenarios/next-cases`. AI 흐름 후보의 재료 · 모양은 결정 15
**시나리오 하나는 디바이스 하나다** — 한 브라우저로 이어 도는 것이 요점이라 `platform` 을 시나리오(의 버전)가 갖는다.
앱 · 게임 단계는 이 디바이스와 상관없이 폰 하나에서 돈다 — 시나리오 디바이스는 웹 단계의 창을 정하고, 「Android 앱」 디바이스는 앱 · 게임 애플리케이션이 시작 애플리케이션일 때 고른다(결정 16, 2026-10-28).
**디바이스는 버전마다 적는다** (2026-09-28 사용자) — 디바이스를 바꾼 저장도 새 버전이다. 그래야 옛 실행이 어느 디바이스로 돌았는지 남고, 옛 버전으로 되돌리면 디바이스도 돌아온다.
그 디바이스를 선언하지 않은 케이스는 부품으로 못 고른다(웹 단계만이다 — 앱 · 게임 단계는 `android` 선언을 본다. `android` 시나리오의 웹 단계는 PC 선언을 본다 — 결정 16). 조립 뒤에 케이스가 그 디바이스를 빼면 **실행 때 그 부품이 실패로 멈춘다** (2026-09-28 사용자 — 틀린 조립은 언제나 빨강이다).
**API 호출 부품은 브라우저 로그인(쿠키)을 같이 쓴다** (2026-09-28 사용자) — 한 브라우저로 이어 도는 흐름이라 앞 부품이 로그인한 사람으로 부른다(`service` 로 다른 애플리케이션을 부르면 그 출처의 쿠키만 간다 — 결정 13). API 인증을 고르면 토큰도 붙는다(결정 14). 러너 쪽 모양은 [러너.md](러너.md) §5.2

#### 한 브라우저에서 순서대로 몬다 (결정 3)

러너가 조립 목록을 받아 **Playwright 프로세스 하나, `test()` 하나** 안에서 케이스 본체를 차례로 꺼내 돌린다.
**시나리오마다 테스트 파일을 만들지 않는다** (2026-09-28 — 설계서 「착수 전에 답이 있어야 하는 것」 ①).
러너 이미지 안의 고정 파일 하나가 조립 목록을 받아 케이스 파일을 불러 쓴다. 그래서 읽기 전용 `/tests` 에 쓸 자리가 필요 없다.
러너 쪽 모양은 [러너.md](러너.md) §5.2 가 정본이다.

- **절차 순번은 시나리오 전체에서 이어진다.** 부품마다 순번이 1부터 다시 시작하면 스크린샷이 서로를 덮는다. 부품마다 실패 표시는 새로 세우고 순번만 넘겨받는다(공통/3-공유계약 §5.1)
- **입력값은 부품마다 따로 해석한다.** 같은 케이스를 두 번 써도 값이 다를 수 있다
- **케이스 부품마다 새 창을 연다** (2026-10-06, 결정 12). 브라우저는 하나이고 창(Playwright 브라우저 컨텍스트)만 부품마다 새로 연다.
  앞 창의 로그인 상태(쿠키 · localStorage)만 옮긴다. 시계 고정(`page.clock`) · 주입 스크립트(`addInitScript`) · 열려 있던 주소는 안 넘어간다.
  **케이스의 `request` 도 부품마다 새로 만들고 같은 쿠키를 들고 시작한다** — 로그인 준비를 건너뛰면 API 요청도 로그인한 사람으로 가야 한다.
  옮기는 상태는 앞 부품이 끝났을 때 창의 쿠키 · localStorage 와 그 부품 `request` 의 쿠키를 합친 것이다. 같은 쿠키가 둘에 있으면 창 쪽을 쓴다.
  새 창도 시나리오 디바이스의 설정(화면 크기 · 사용자 에이전트)으로 연다.
  **처음에는 창 하나를 같이 썼다** — 그러다 새 작성 방식의 케이스가 시계를 고정하거나 스크립트를 넣은 채 끝나 다음 부품에 샜다. 넘길 것은 로그인 상태 하나라서 창을 갈아 끼운다
- **앱 · 게임 단계는 창을 열지 않는다** — 폰 연결 하나를 시나리오 끝까지 쥐고 앱을 다시 켜지 않는다(결정 16, 2026-10-28). 위 새 창 규칙은 웹 단계 것이다

#### 준비를 사람이 체크로 끈다 (결정 4)

케이스는 단독으로도 돌아야 해서 자기 준비를 갖고 있다. 조립하면 앞 부품이 이미 세운 준비와 겹친다.
사람이 조립 화면에서 **건너뛸 준비의 체크를 푼다.** 기본값은 「실행」(체크가 켜진 채)이다.

- **건너뛸 수 있는 것은 R16 의 「만들기」 절차뿐이다.** 「확인」 절차는 못 끈다. 그래서 잘못 풀면
  바로 다음 「확인」이 `blocker` 로 그 자리에서 멈춘다 — 틀린 건너뛰기는 **언제나 빨강**이다.
  케이스를 그렇게 쓰는 규칙은 `tpx-cases` R16(`.claude/skills/tpx-cases/references/5-writing.md`)이고, **왜 가르는지는 이 절이 정본이다**
  (R16 이 가리키는 설계서 결정 4 는 여기로 옮겨졌다)
- **「만들기」 절차는 소스에서 판별한다** (2026-09-28 — 「착수 전」 ②). **판정이 하나도 없는 `test.step` 바로 뒤에
  `blocker` 판정을 가진 `test.step` 이 오면** 앞 것이 「만들기」다. 케이스 선언에 표시를 새로 달지 않는다.
  판별은 카탈로그가 소스를 읽는 자리 옆에 있다(`apps/admin/src/catalog/steps.ts`, 2026-09-29).
  **애매하면 「만들기」로 치지 않는다** (2026-09-29 게이트 1 사용자 · 셋째 줄부터는 구현·검사 중에 찾아 게이트 2 에서 확인) — 반복문·도우미 함수 안의 절차(한 제목이 여러 번 돈다) ·
  본문이 `verify` 와 fixture(또는 그 절차 안에서 fixture 로 만든 변수)에서 시작하는 호출 말고 다른 것을 부르는 절차(판정이 소스에서 안 보인다 — 맨 함수 · `kit.verify` · 아래 Page Object 자리 밖의 도우미 객체 · `new`) ·
  안에 다른 절차를 품은 절차(건너뛰면 안쪽 판정까지 사라진다) · 본문을 이름으로 넘긴 절차 · 제목을 글자로 못 읽는 절차가 하나라도 있는 케이스 전체 ·
  `blocker` 를 객체 리터럴이 아닌 값으로 넘긴 다음 절차 · 절차 밖에서 함수를 담은 이름을 쓰는 절차(넘긴 함수 안의 판정이 어느 절차에도 안 세진다, 2026-10-02 PR #130). 틀려도 건너뛰기를 못 할 뿐이다
- **Page Object 호출은 믿는다** (2026-10-02 PR #130) — 케이스 파일 맨 위에서 `./pages/<이름>.page.js` · `./components/<이름>.component.js` · `./helpers/<이름>.helper.js`(2026-10-11 PRD-F4-04 — 같은 K7 을 지고 components 에 있던 로그인 · 자료 도구가 옮겨 간 자리다)로 가져온 클래스, 그 클래스의 `new`,
  파일 어디서든 그 `new` 만 담는 `const` 이름에서 시작하는 호출. 그 파일은 판정 · 절차를 부르지도 들여오지도 못한다(공통/2-명세선언 「Page Object 파일」 K7).
  같은 이름이 다른 것을 한 번이라도 담거나(다시 담기 · 다른 test 의 같은 이름) 경로가 그 꼴이 아니면 믿지 않는다.
  **믿는 이름은 부르는 자리에만 와야 한다** — 대입(메서드 · 프로토타입 바꿔치기) · 인자로 넘기기 · 값으로 쓰기가 한 번이라도 있으면 그 이름(클래스면 그 인스턴스까지)을 믿지 않는다.
  **케이스가 `verify` · `test` 를 부르기 말고 값으로 쓰거나(넘기기 · 옮겨 담기 · `globalThis` 에 걸기) kit 을 통째로 가져오면 그 파일의 Page Object 를 아무것도 믿지 않는다** — Page Object 가 받아 부를 수 있다
- **이 모양이 하나도 없는 케이스(R16 미적용)는 체크를 못 끈다.** 조립 화면이 체크를 누를 수 없게 두고
  `이 케이스는 준비가 분리되어 있지 않아 건너뛸 수 없습니다` 를 띄운다. 서버도 그런 건너뛰기를 400 으로 거절한다 —
  옛 케이스는 첫 절차에 조작과 `blocker` 판정이 한 덩어리라, 건너뛰면 **막는 판정까지 같이 건너뛴다**
- **체크 한 줄은 「만들기」 절차의 제목이다** (2026-09-28 사용자). `precondition` 문장이 아니다 —
  문장과 절차를 잇는 칸이 케이스 선언에 없고, 만들면 모든 케이스를 고쳐야 한다. `precondition` 은 부품 머리에 읽을거리로만 편다
- **그래서 절차 제목이 열쇠다.** 러너는 건너뛸 절차를 **제목으로** 받는다. 한 케이스 안에서 제목이 겹치면
  하나를 지목하다 둘을 건너뛴다 — 그래서 K12(한 케이스 안에서 절차 제목이 서로 다르다)를 둔다 ([공통/2-명세선언.md](../공통/2-명세선언.md) §4)
- **건너뛴 절차도 결과에 남는다** — `StepResult.skipped` 가 참인 줄로. 증적이 `사전 단계 「<절차 제목>」 — N번에서 이미 실행` 을 적는 근거다(글자는 §8.11 「화면 글자」 표)
- **절차 밖 코드는 건너뛸 수 없다** — `finally` · 본문 끝의 뒷정리는 체크와 상관없이 돈다. 거기서 지우는 데이터는 결정 12 의 「뒷정리 미루기」가 시나리오 끝으로 미룬다
- **건너뛸 수 있는 준비는 많지 않다** (2026-10-06 실측 — MKT 절차 712 중 61 · CDY 119 중 42. 표본은 결정 12). 늘리려고 작성 규칙을 바꾸지 않는다(결정 12 원칙).
  못 건너뛰는 준비는 그대로 돌고, 그 준비가 앞 상태를 지우면 결정 12 의 이어 주기로 막는다

**러너가 「확인부터 해 보고 정한다」는 길은 접었다** (설계서 결정 4 인용 상자). 탐침 실행을 증적에 찍을지 또 정해야 하고,
건너뛰지 못하는 경우 확인이 두 번 돌아 느려진다. **전제를 글자로 비교해 자동으로 건너뛰는 길은 금지다** (설계서 §7).

#### 순서가 틀리면 도구가 경고한다 (결정 5)

`[결제] → [로그인]` 처럼 앞 부품이 뒤 부품의 준비를 이미 세웠으면 조립 화면이 **`N번에서 이미 실행` 칩**을 붙인다.
**경고지 금지가 아니다** — 도구는 표시하고 사람이 누른다. 무엇을 「세웠다」로 보는지는 **같은 절차 제목**이 앞 부품에 있는가로 본다. 같은 애플리케이션 단계끼리만 센다(결정 13 — 출처가 다르면 로그인이 안 넘어간다).
맞추지 못해도 조립은 된다 — 칩이 안 뜰 뿐이다.

#### 모킹은 켜면 시나리오 끝까지 유효하다 (결정 6)

끄려면 「모킹 끄기」 부품을 중간에 넣는다.

- **모킹 구간 안에 앱 · 게임 단계를 못 둔다**(조립 400 — 결정 16, 2026-10-28). 앱이 폰에서 보내는 요청은 러너가 못 본다
- **모킹은 브라우저 컨텍스트에 건다** (`page.context().route()`, 2026-09-28 — 「착수 전」 ③). 페이지에 걸면 팝업·새 탭에서 풀린다 —
  **모킹된 줄 알았는데 진짜 서버를 두드린 실행**이 가장 나쁜 실패다
- **케이스의 API 요청도 모킹을 거친다** (2026-10-06, 결정 12). Playwright 의 가로채기(`route`)는 브라우저 요청만 보므로 러너가 케이스가 쓰는 API 도구를 감싼다(러너 §5.2 — 2026-10-06 PR #162 게이트 0 에서 kit 대신 러너 한 곳으로 모았다).
  **API 호출 부품만 모킹을 안 거친다** — 진짜 서버에 상태를 심는 뒷문이라서다. 모킹 구간 안에 API 부품이 있으면 조립 화면이 `이 단계의 API 호출은 모킹되지 않습니다` 를 붙인다.
  처음에는 케이스의 `request` 도 모킹을 안 거쳐 같은 경고를 케이스 부품에도 붙였다(`usesRequest`). 케이스 부품의 경고와 그 칸은 **케이스가 직접 만드는 창 · API 연결까지(아래 줄)
  감싸지는 것을 러너 이미지에서 확인한 뒤에** 뺀다 — **2026-10-06 러너 이미지에서 확인했다**(PR #162 — `/tests` 케이스가 `require` 로 만든 연결의 삭제가 미뤄지고 직접 만든 창의 요청이 모킹됐다). Admin 이 뺐다(2026-10-06 PR #163 — `case-parts` 의 칸과 소스 판별 둘 다)
- **위험은 「계속 유효한 것」이 아니라 「보이지 않는 것」이다.** 조립 화면·실행 결과·증적 양쪽에서 모킹 구간을 칠한다 (§8.11 · 도메인/리포팅 §8.4)
- **부품마다 새 창을 열어도 모킹은 따라간다** — 걸려 있는 모킹을 새 창에 다시 건다(결정 3).
  **케이스가 창이나 API 연결을 직접 새로 만들어도 모킹이 따라가게 한다** — 러너가 그 만들기를 감싼다(결정 12 「한계」 표).
  작성 규칙이 이 모양을 낳는다(다른 역할 계정 · 브라우저를 닫았다 열기, `tpx-cases/references/5-writing.md`) — 창은 10-04 표본 6건(10-06 표본 0) · API 연결은 10-06 표본 18건이다.
  **처음에는 「그런 케이스는 없다」고 적었다** — 표본 하나만 셌다. 작성마다 갈리는 모양이라 둘 다 견디게 한다

#### 저장은 DB 에 버전을 쌓는다. 사람이 저장을 누른다 (결정 7)

저장할 때마다 **버전이 하나 오르고 이전 버전은 고치지 않는다.** 되돌리기는 옛 버전을 복사한 **새 버전**이다.
자동 저장은 없다. git 에 파일로 두지 않는다 — 시나리오는 커밋과 함께 움직이지 않는 **조합 목록**이다.
**동시에 고치면 뒤에 저장한 쪽이 409 를 받는다** — 저장 요청이 「어느 버전을 고쳤나」를 싣고, 그사이 버전이 올랐으면 거절한다.
말없이 덮으면 앞사람의 조립이 이력에서 사라진다.
**부품의 입력값에 비밀값 칸이 있으면 `param_set` 과 같은 규칙이다** ([공통/2-명세선언.md](../공통/2-명세선언.md) §4.1) — 저장은 하되 화면과 증적에서 가린다.

#### 케이스가 바뀌면 건너뛰기를 포기하고 실행한다 (결정 8)

**애매하면 안전한 쪽으로 무너진다** — 느려질 뿐 틀리지 않는다.

| 케이스에 생긴 일 | 어떻게 |
|---|---|
| 체크를 푼 절차 제목이 케이스에서 사라짐 | 그 체크는 **무시하고 실행**한다. 시나리오에 「확인 필요」 · 저장 · 시험 실행도 그 제목을 거절하지 않는다(2026-10-06 사용자 — 조립 화면은 따로 처리하지 않는다) |
| 체크를 푼 절차 제목은 남았는데 건너뛸 수 없는 절차가 됨 | 진짜 실행은 그 체크를 **무시하고 실행**하고 「확인 필요」. 실행을 만들 때 서버가 지금 건너뛸 수 있는 제목만 남겨 러너에 보내고 부품 행에도 그렇게 박제한다(사라진 제목도 같이 빠진다) — 러너는 받은 제목이면 확인 절차도 건너뛴다(2026-10-16 E2E-F1-22 사용자). **저장 · 시험 실행은 위 줄과 달리 그 제목을 400 으로 거절한다**(§7 「400 으로 거절하는 조립」). 조립 화면은 건너뛸 수 있는 절차에만 체크를 그려 사람이 그 체크를 못 푼다 — 지금은 `케이스 바꾸기` · 넘겨받기 끄기로만 풀린다 |
| 「만들기」 절차가 새로 생김 | 새 절차는 **실행이 기본**. **표시하지 않는다** — 저장된 부품에는 건너뛸 제목만 있어 「새로 생긴 절차」와 「사람이 실행으로 둔 절차」를 못 가른다. 가르려면 저장 때의 절차 목록을 따로 찍어 둬야 하는데 칩 하나를 위해 칸을 늘리지 않는다 (2026-09-29 게이트 0 사용자) |
| 입력값 칸이 늘었음 | 아래 「부품 입력값을 채우는 순서」대로 채운다 — 조립에 없는 칸은 케이스의 저장값, 그것도 없으면 `.default()` (K10) |
| 케이스가 비활성이 됨(파일이 사라짐) | 그 시나리오는 **실행 불가**. 실행 요청은 409. 조립 화면의 `케이스 바꾸기` 로 다른 케이스를 넣어 저장하면 풀린다(§8.11) |

- **언제 알아채나** — 목록·상세를 줄 때 서버가 저장된 부품을 지금 카탈로그와 소스에 대 본다. 스캔 때 따로 쓰지 않는다 — 들고 있을 상태가 는다
- **버전은 사람이 고쳐 저장할 때만 오른다.** 케이스가 바뀌었다고 저절로 오르지 않는다 — 버전은 **사람이 조합을 고친 이력**이다
- **실행에는 그때의 조합을 박제한다** — `scenario_run_part` 가 부품 정의와 입력값을 행마다 복사한다. 실행 기록이 케이스 이름과 값을 복사해 두는 것과 같다

**부품 입력값을 채우는 순서** (2026-10-06 사용자) — 값 꽂기(결정 12) → 조립에서 적은 값 → **그 케이스의 저장값(`case_input`)** → **그 실행 대상 서버 줄의 계정**(계정 칸만 — 2026-10-12 도메인/실행 §3.2. 섞인 시나리오는 그 케이스 애플리케이션의 같은 이름 줄 — 결정 13) → 코드 기본값(`.default()`).
단독 실행이 요청에 없는 칸을 저장값으로 채우는 것과 같은 규칙이다(도메인/실행 §3.2). 저장값을 채우는 일은 admin 이 실행을 만들 때 하고, 채운 값까지 부품 행에 박제한다 — 저장값을 나중에 고쳐도 지난 실행은 그대로다.
값 꽂기를 건 칸은 조립에서 값을 받지 않고 **저장값으로도 · 대상 서버 계정으로도 안 채운다** — 그 칸의 실제 값은 실행 결과의 `bound` 에만 있다(2026-10-06 PR #163 게이트 1 사용자 「입력하지 않으면 저장해 둔 값, 입력하면 입력한 값」 — 앞 부품에서 넘겨받는 값도 입력한 값이다).
조립에 그 칸 값이 남아 있어도 거절하지 않는다 — 러너가 꽂은 값으로 덮는다.
**처음에는 저장값을 안 썼다** (2026-09-29) — 부품 입력값을 조립 때 따로 저장하면 된다고 봤다. 그런데 새 작성 방식의 케이스는 거의 다 테스트 계정 비밀번호를 입력값으로 받아,
부품 열 개면 비밀번호를 열 번 적어야 했다. 시험 실행도 같은 순서로 채운다.
**조립에서 비운 칸은 키를 빼고 저장한다** — 서버는 키가 없는 칸만 저장값으로 채운다(정본은 도메인/실행 §3.2 「선택 칸」 줄, 2026-10-06 PR #163 — 조립 화면이 지킬 것)

#### 실패하면 거기서 멈춘다. 전부 통과해야 통과다 (결정 9)

뒤 부품은 **안 돈 것**(`NA`, 오류 `NOT_RUN` — 화면 글자 `– 실행 안 됨`)으로 닫는다. 이어진 흐름이라 앞이 깨지면 뒤 결과를 못 믿는다.
시나리오의 판정은 **모든 부품이 통과일 때만 통과**다. 어디서 깨졌는지는 부품 단위로 남는다.
**멈춰도 미뤄 둔 뒷정리는 보낸다**(결정 12) — 안 보내면 앞 부품이 만든 데이터가 대상 서버에 남는다.

**부품을 판정 없이 닫는 오류 값은 이 표가 정본이다.** 다른 절·스키마 주석은 여기를 가리킨다. 화면 · 증적에 보이는 글자는 §8.11 「화면 글자」 표다.

| `error.message` | 언제 | 누가 적나 |
|---|---|---|
| `NOT_RUN` | 앞 부품이 실패해 거기서 멈췄다 | 러너 |
| `TIMEOUT` | 시나리오 제한 시간에 걸려 끊겼다. 도는 중이던 부품과 그 뒤가 다 이 값이다 — 원인이 앞 부품 실패가 아니다 | 러너 |
| `ABORTED` | admin 이 다시 떠서 도는 중이던 실행을 닫았다 (도메인/실행 §3.2 재기동 복구) | admin |

**실행 묶음의 끝** — 러너 응답을 저장하면 `test_run.status = FINISHED` 다. 부품 하나하나가 따로 끝나지 않는다 — 한 프로세스가 한 번에 돌려준다.
재기동 복구로 닫히면 `ABORTED` 다. **시나리오의 판정(통과·실패·판정 없음)은 `test_run.status` 가 아니다** — 부품 판정을 위 규칙으로 접은 것이고,
목록의 `lastRun.verdict` 가 그것이다(§7).

#### 시나리오 결과는 케이스 이력에 안 들어간다 (결정 10)

케이스 목록의 「마지막 결과」와 판정 흐름 막대는 **단독 실행만** 센다. 시나리오 안에서는 준비를 건너뛰었고 앞 부품이 만든 상태 위에서 돌았다 —
조건이 다르다. 섞으면 「3개월째 초록이었는데 이번에 빨강」이 무엇을 뜻하는지 말할 수 없다.

- **그래서 시나리오 결과는 `run_item` 에 안 쓴다.** `scenario_run_part`·`scenario_run_step` 에 쓴다
- **실행 묶음은 `test_run` 한 행이고 `kind` 칸으로 가른다.** 실행 기록 화면의 탭이 이 칸으로 거른다(도메인/실행 §8.7)
- **`test_run` 을 읽는 운영 코드는 전부 `kind` 를 거른다.** 안 거르면 시나리오 실행이 요구사항 표·대시보드·알림 줄에
  케이스 실행인 척 섞인다. 대상은 `grep -rln "FROM test_run\|JOIN test_run" apps/admin/src` 와 Grafana 대시보드 질의로 센다 — **개수를 여기 적지 않는다**.
  본문 위 알림 줄 · 알림 서랍(`GET /api/notifications`, 2026-10-11)도 거른다 — 처음에 안 걸러 「0 통과 ✓」로 떴다(코드 검토 · spec-review).
  도는 E2E 만은 케이스 실행 칸에 섞지 않고 따로 종류(`kind: 'scenario'` · 단계 수)로 싣는다(2026-10-16 E2E-F1-18 · 공통/5-화면공통 §8 「알림」)
- **실행 번호 하나로 `test_run` 을 짚는 단건 조회도 거른다** (2026-09-29 게이트 0) — 케이스 실행 단건 · 견주기 · 실패 카드는 케이스 실행(`kind IN ('UI','FN')`, 2026-10-02 PR #131)만 보고,
  시나리오 실행 번호면 404 다(모양은 §7). 안 거르면 「항목 0건인 케이스 실행」 모양이 나간다.
  **증적 만들기만 갈라 탄다** — 케이스 실행이면 케이스 증적, 시나리오 실행이면 E2E 증적이다(2026-10-16 PR #277 · 도메인/리포팅 §8.4)
- **예외 — `run_item` 을 거쳐서만 `test_run` 에 닿는 조회는 `kind` 를 안 걸러도 된다.** 시나리오 실행에는 `run_item` 이 없어 저절로 빠진다.
  이 문단이 이 규칙의 정본이다 — 다른 장은 여기를 가리킨다
- `attempt` 를 시나리오의 순서 칸으로 쓰지 않는다 — 이미 「재시도 회차」라는 뜻이 있다

| 이어 주기 | 무엇을 | 누가 거나 | 언제 |
|---|---|---|---|

- **브라우저 요청과 케이스의 API 요청 둘 다에 건다.** Playwright 의 가로채기(`route`)는 브라우저 요청만 본다. 그래서 러너가 케이스가 쓰는 API 도구
  (`request` · `page.request`)와 케이스가 직접 만드는 창 · API 연결(아래 「한계」 표)을 **한 곳에서** 감싼다(러너 §5.2). 모킹(결정 6)도 이 감싸기로 API 요청에 걸린다. API 호출 부품은 감싸지 않는다
- **요청 고르기** — 메서드와 주소 무늬(`urlPattern`, 모킹과 같은 Playwright glob)로 고른다. 앞 부품의 응답은 **그 부품에서 무늬에 처음 맞은 응답**이다.
  맞는 응답이 없으면 이 부품이 `FAIL` 로 멈춘다 — 사유 `<N>번 단계에 맞는 응답이 없다`. 본문을 못 읽었으면 사유 `<N>번 단계 응답 본문을 못 읽었다`.
  케이스의 상대 주소(`page.request.delete('/api/…')`)는 그 도구의 기준 주소로 풀어 맞춘다 — 부품 `request` · `page.request` 는 대상 주소(그 단계 주소 — 결정 13), 직접 만든 연결은 만들 때 받은 `baseURL`. 쿼리(`params`)도 Playwright 와 같은 규칙으로 붙인다(러너 §5.2 「미룬 삭제」).
  API 쪽 무늬 맞추기는 Playwright 의 glob 변환을 옮겨 쓴다(공개 함수가 없다). `*` 로 시작하는 무늬와 절대 주소는 브라우저와 같고, `/` 로 시작하는 무늬는 대상 주소(그 단계 주소)의 origin 을 붙인다.
  상대 무늬의 세부(대소문자 · `..`)까지는 안 옮겼다 — **막기 · 바꿔 보내기는 무늬가 안 맞으면 조용히 안 걸린다.** 그래서 아래 「적용되지 않은 값 연결」 꼬리가 알린다.
  브라우저 쪽 이어 주기는 이 맞추기를 안 쓴다 — Playwright `route` 가 맞춘 무늬를 글자로 골라 건다. 한 주소에 무늬 둘이 맞으면 두 채널 모두 앞 링크가 이긴다.
  **응답 적기** — 브라우저 · API 응답 모두 위 맞추기로 「가리킨 무늬에 처음 맞은 응답」을 고른다. 러너가 준 가짜 응답(모킹 · 막기 · 돌려주기)도 적는다 — 브라우저 쪽은 `fulfill` 한 응답도 응답으로 오므로 두 채널을 같게 한다. 브라우저의 3xx 는 본문을 못 읽어 적지 않는다
- **값 꺼내기** — 값 꽂기와 바꿔 보내기는 앞 응답 JSON 본문에서 점 표기 경로(`data.id` · 배열은 `items.0.id`)로 값을 꺼낸다. 못 꺼내면 이 부품이 `FAIL` — 사유 `<N>번 단계 응답에 <jsonPath> 가 없다`.
  바꿔 보내기는 대상 주소(받는 단계 주소) 끝 `/` 를 떼고 고치기 주소를 잇되 `{}` 자리에 그 값을 주소 글자로 감싸(`encodeURIComponent`) 넣는다 — 값의 `/` 가 다른 경로로 새지 않게. 고치기 주소에 `{}` 가 꼭 하나 있어야 한다 — 없으면 모음 주소로 가고 둘이면 첫 자리만 바뀐다(러너 입구 400).
  값이 빈 글자 · `.` · `..` 면 모음 주소로 가거나 감싸도 그대로라 상위로 풀린다 — 이 부품이 `FAIL`, 사유 `<N>번 단계 응답의 <jsonPath> 값 「<값>」 은 주소에 넣을 수 없다`. 꽂은 값은 실행 결과의 그 부품(`bound`)에 남는다
- **이어 주기 때문에 실패하면 그 사유가 먼저 보인다** — 이어 주기 오류가 있으면 부품 오류 맨 앞에 두고, 케이스 오류가 있으면 ` · ` 뒤에 잇는다. 막은 요청 때문에 케이스가 `net::ERR_FAILED` 로 먼저 실패하면 원인이 가려져서다.
  부품이 실패하면 그 부품에서 한 번도 안 걸린 앞 응답 돌려주기 · 요청 막기 · 바꿔 보내기를 `적용되지 않은 값 연결 — 요청 차단 DELETE **/api/cart` 꼴로 줄을 바꿔 덧붙인다 — 시험 실행에서 이어 주기를 고칠지 넘겨받기를 끌지 고르는 재료다.
  **케이스를 돌리기 전에 실패한 부품**(값 꽂기 · 창 열기)에는 안 붙인다 — 케이스가 안 돌아 모든 이어 주기가 「안 걸림」이라 원인이 아니다 (2026-10-06 PR #162 게이트 2 사용자)
- **막은 요청 · 미룬 삭제에는 성공 응답을 준다** — 케이스 코드는 서버가 받은 줄 안다. 막은 요청은 `200` 과 빈 JSON 객체(`{}`)다.
  **미룬 삭제는 그 제품이 그 주소에 실제로 준 성공 코드로 답한다** (2026-10-16 사용자 — 「플랫폼이 알아서 배운다」). 케이스 정리 함수가 제품의 진짜 코드만 받기도 해서다 —
  데모마켓 탈퇴 정리는 `204` 만 받아 `200 {}` 을 주면 회원 · 글 · 장바구니를 만드는 케이스가 다 「임시 회원 탈퇴 실패: 200」으로 멈췄다(MKT-FN-179 시험 실행).
  코드는 정식 실행 trace 가 서비스 지도(도메인/작성 §3.6 「서비스 지도」)에 남긴 그 DELETE 의 마지막 2xx 코드(`service_api.ok_status`)이고, admin 이 실행 · 시험 실행 요청의 `deleteStatuses` 로 싣는다.
  주소는 지도와 같은 틀(숫자 · 주문번호 꼴 칸 `:n` · uuid · 긴 16진 칸 `:id` · 물음표 뒤 뺌 — [작성.md](작성.md) §3.6 「서비스 지도」)과 호스트로 맞춘다. **본 적 없는 주소는 `204` · 본문 없음이다** — 삭제 API 가 가장 흔히 주는 코드다. `204` 가 아니면 빈 JSON 객체를 붙인다.
  호스트까지 맞추므로 정식 실행을 돌린 적 없는 대상 서버(호스트가 다른 서버)로 시나리오를 돌리면 늘 `204` 다 — 그 서버로 케이스를 한 번 정식 실행하면 배운다.
  배우는 줄은 테스트 코드의 요청 도구(`request` · `page.request`) 줄뿐이다 — 브라우저 쪽 응답은 케이스가 `route` 로 꾸민 것일 수 있고, 미루는 삭제도 요청 도구 쪽뿐이다(러너 §5.2).
  4xx · 5xx 는 남기지 않는다 — 이미 지운 것을 또 지운 `404` 를 흉내 내면 정리 함수가 진짜 실패를 삼킨다. 서비스마다 사람이 코드를 고르는 칸은 두지 않았다 — 시나리오를 조립하기 전에 케이스를 정식으로 돌리므로 배울 재료가 먼저 쌓인다
- **미룬 뒷정리는 시나리오가 실패로 멈춰도 보낸다**(결정 9). 결과(응답 코드 · 오류)는 판정을 바꾸지 않고 실행 결과에 따로 남는다. 하나가 실패하거나 한도 안에 안 끝나도 나머지는 보낸다(러너 §5.2).
  절차 **안**의 삭제와 첫 절차 전의 삭제는 시험 · 준비의 일부라 그대로 보낸다

**안전 규칙 — 요청을 바꾸는 이어 주기(앞 응답 돌려주기 · 요청 막기 · 바꿔 보내기)는 준비 구간에서만 건다.**
준비 구간은 그 부품이 시작해서 **`blocker` 가 아닌 첫 판정**이 나오기 전까지다. 그 뒤 요청은 손대지 않는다 — 시험 대상 자체를 꾸미면 버그를 숨긴다.
준비를 잘못 고쳤으면 뒤 판정이 빨강으로 잡는다 — 틀린 조립은 여전히 빨강이다(결정 4).

**앱 · 게임 단계는 위 표 가운데 값 꽂기 · 뒷정리 미루기만 쓴다** — 앞 응답 돌려주기 · 요청 막기 · 바꿔 보내기 · 넘겨받기 끔은 조립 400 이다(결정 16 표가 정본, 2026-10-28).

**넘겨받기 끔** — 케이스 부품마다 스위치가 있고 기본은 켬이다. 끄면 그 부품은 **로그인 상태 없이 새 창**에서 단독 실행처럼 돈다.
건너뛰기 · 앞 응답 돌려주기 · 요청 막기 · 바꿔 보내기 · 값 꽂기를 걸 수 없다(조립 400). 걸린 모킹과 뒷정리 미루기는 그대로다.
그 부품이 끝났을 때의 로그인 상태는 다음 부품이 넘겨받는다.

**이어지는지는 시험 실행으로 본다** — 도구가 「이 두 부품이 이어지나」를 미리 판정하지 않는다. 조립하고 시험 실행(§7)을 눌러 본다.
안 이어지면 이어 주기를 더하거나 넘겨받기를 끈다.

| 케이스가 Playwright 에서 API 연결을 직접 만든다(`import { request } from '@playwright/test'` 의 `newContext`) | ✅ | 러너가 그 함수를 감싼다. 케이스(`require`)와 고정 spec(`import`)이 **같은 객체**를 본다 — 2026-10-06 러너 이미지에서 쟀다(PR #162). 그 연결로 보내는 `finally` 삭제도 미뤄진다. **처음에는 △ 로 적었다** — 모듈이 두 벌 올라갈 수 있다고 봤다(러너 §5.2 「고정 spec 은 kit 을 값으로 부르지 않는다」). `@playwright/test` 의 ESM 입구가 CJS 의 같은 객체를 다시 내보낸다 |
| 시계 고정 · 주입 스크립트 | ✅ | 부품마다 새 창이라 다음 부품에 안 샌다 |
| 뒤 부품이 자기가 만든 데이터를 확인한다(예: 무작위 제목으로 글을 만들고 목록에서 그 제목을 찾는다) | △ | 바꿔 보내기. 앞 응답 돌려주기로는 안 된다 — 앞 글의 제목이 돌아와 목록에서 내 제목을 못 찾는다. 고치기 통로가 없는 데이터는 넘겨받기를 끈다 |
| 뒤 부품이 비우고 나서 개수를 센다(예: 장바구니를 비우고 세 줄을 담아 「3줄」을 확인) | ✗ | 응답을 꾸며 개수를 맞추면 버그를 숨긴다. 그 부품은 넘겨받기를 끈다 |
| 외부 결제 · 외부 인증 | ✗ | 고정 응답 모킹(결정 6)만 쓴다 |
| 절차 밖 코드가 삭제 말고 다른 요청으로 데이터를 되돌린다 | ✗ | 미루지 않고 그대로 보낸다. 2026-10-06 표본에는 없었다 |

**미확정 · 보류 케이스** (2026-10-06 사용자)
- **미확정 케이스도 부품이 된다.** 그 부품과 실행 결과 · 증적에 「미확정」 꼬리표를 단다(2026-10-11 PRD-F4-02 — 앞 판의 글은 「미확정 포함」). 기대값을 화면에서 본 케이스라(도메인/작성 §3.6 「★ 표준 기획서」 「미확정」) 버그째 담았을 수 있다 —
  표시가 따라간다. 실행을 만들 때 부품 행에 사유를 박제한다 — `run_item.unconfirmed` 와 같은 식 · 같은 까닭이다(도메인/실행 §3.2 · 공통/4-데이터모델).
  **막지 않는 까닭** — 화면에서 케이스를 만든 서비스는 기능 케이스가 전부 미확정이라(2026-10-06 CDY FN 34건) 막으면 E2E 를 하나도 못 만든다
- **미확정이 섞인 통과도 통과로 센다** (2026-10-11 PRD-F4-02 · 도메인/실행 §3.2 「미확정 항목도 그대로 센다」). 목록의 마지막 결과와 E2E 탭 숫자가 통과로 세고 「미확정」 꼬리표만 단다.
  앞 판(2026-10-06 게이트 2)은 정식 통과와 따로 셌다(`summary.unconfirmedPass` · 통과 색을 안 칠함) — 케이스 실행이 숫자를 가르지 않게 되면서 같이 걷었다. 값의 모양은 §7 「판정 접기」
- **보류(`held`) 케이스는 따로 다루지 않는다** — main 에 못 들어온다(CI `check:tests --no-held`, K13). 그래서 카탈로그에 없고 부품으로 못 고른다
- **옛 번호**(`DEMO-001` 처럼 `-UI-` · `-FN-` 이 없는 것)는 지금처럼 기능 테스트로 친다

#### 같은 프로젝트의 애플리케이션을 섞는다 (결정 13, 2026-10-20)

한 시나리오에 같은 프로젝트의 다른 애플리케이션 케이스를 단계로 넣는다. 「쇼핑몰(MKT)에서 주문 → 어드민(ADM)에서 그 주문 확인」이 그 장면이다
(2026-10-19 사용자 「e2e는 다른 서비스의 케이스도 가지고 올수 있어야 하는거 아닌가?」 · 진행판 E2E-F1-27 · 시작 질문 2026-10-20). 층의 정본은 공통/1-제품과-구조 §2 「프로젝트 · 애플리케이션 · API 서버는 다른 층이다」다.

- **시나리오는 만든 애플리케이션 소속 그대로다.** 이 장에서는 그 애플리케이션을 **시작 애플리케이션**이라 부른다 — 목록 · 실행 기록(`test_run.service_id`) · 증적이 거기에 남는다.
  단계가 어느 애플리케이션 것인지는 저장하지 않고 **케이스 번호 앞 글자(접두사)**로 읽는다. 그래서 DB 표와 부품 저장 모양은 안 바뀐다(API 부품에 선택 칸 하나가 는다 — 아래. 2026-10-21 결정 14 가 선택 칸 셋을 더 더했다)
- **섞는 범위는 시작 애플리케이션과 같은 프로젝트의 활성 애플리케이션이다.** 다른 프로젝트 것은 400 이다. 앱 · 게임 애플리케이션도 섞지만 한 시나리오에 하나뿐이다(결정 16, 2026-10-28). 권한은 프로젝트마다 주어(도메인/인증 §3.5) 단계마다 따로 보지 않는다 — 같은 프로젝트면 같은 값이다.
  애플리케이션을 다른 프로젝트로 옮기면 그 애플리케이션 케이스는 이 시나리오에서 빠진 것으로 본다(케이스 단계는 `CASE_INACTIVE` 와 같이 드러나고 실행 불가다. API 단계는 목록 · 상세에는 안 드러나고 실행 요청이 409 `SCENARIO_NOT_RUNNABLE` 로만 막는다)
- **API 호출 단계는 `service`(접두사)를 선택으로 가진다.** 비면 시작 애플리케이션 주소로 부른다. 같은 프로젝트의 애플리케이션이어야 한다
- **대상 서버는 이름으로 짝짓는다.** 실행 때 이름(`env`) 하나를 고르고, 단계마다 그 단계 애플리케이션의 같은 이름 줄(`service_env`)이 주소다. stg 를 고르면 저마다의 stg 다.
  시나리오에 든 애플리케이션 가운데 하나라도 그 이름이 없으면 실행도 시험 실행도 400 `ENV_NOT_FOUND` 다
- **로그인 계정은 단계가 쓰는 케이스의 애플리케이션 대상 서버 줄에 적힌 계정이다.** 입력값을 채우는 순서(위 결정 8 아래의 「부품 입력값을 채우는 순서」)는 그대로이고 계정 줄만 그 케이스 애플리케이션 것을 본다
- **시작 애플리케이션이 아닌 단계는 러너 요청에 단계별 `baseUrl` 이 붙는다.** 러너는 그 단계의 창 · API 연결 · 이어 주기의 무늬 맞추기와 바꿔 보내기에 이 주소를 쓴다(러너 §5.2).
  `baseUrl` 이 없는 단계는 요청 전체 `baseUrl` 로 돈다 — 한 애플리케이션만 쓰는 옛 시나리오는 바뀌는 것이 없다. 부품 행 스냅샷(`scenario_run_part.part`)에도 같은 `baseUrl` 이 박혀 결과가 단계마다 돈 주소를 보인다
- **모킹은 시작 애플리케이션 밖의 단계가 있는 시나리오에서 `/` 로 시작하는 짧은 무늬를 못 쓴다**(조립 400). 짧은 무늬는 걸린 창의 주소로 풀려 어느 애플리케이션을 가리키는지 모호하다. `**/api/**` 나 주소 전체는 받는다
- **로그인 이어받기는 도구가 막지 않는다.** 주소(출처)가 다르면 쿠키 · localStorage 가 안 넘어가서, 다른 애플리케이션 단계의 사전 단계(로그인)를 건너뛰면 다음 확인이 빨갛게 뜬다 — 결정 4 의 「틀린 건너뛰기는 언제나 빨강」 그대로다
- **값 연결은 그대로 된다.** 쇼핑몰 단계 응답에서 꺼낸 주문번호를 어드민 단계 입력값에 꽂을 수 있다. 앞 응답은 **그 앞 단계의 주소**로 무늬를 맞추고, 바꿔 보내기는 **받는 단계의 주소**로 간다
- **미룬 삭제에 줄 성공 코드는 섞인 애플리케이션 모두의 서비스 지도에서 읽는다**(결정 12). 호스트로 맞추므로 합쳐도 겹치지 않는다
- **실행 · 시험 실행의 제한 시간 · 동시성 · 줄은 그대로다.** 단계가 늘어난 만큼 합이 늘 뿐이다

#### API 호출 단계 — API 인증 · 값 주입 · 응답 값 확인 (결정 14, 2026-10-21)

「웹 가입 → 알림 서버에 기기 등록 → 웹 주문 → 그 회원에게 푸시가 갔나」를 한 시나리오로 돌린다(진행판 API-F1-10 · 시작 질문 2026-10-21 사용자 승인).
**API 서버 단계는 케이스 단계가 아니라 API 호출 단계로 잇는다** — API 애플리케이션 케이스는 자기가 만든 데이터를 마지막 절차에서 지운다(`tpx-cases/references/api.md` §4).
절차 안의 삭제는 시험의 일부라 미루지 않으므로(결정 12) 기기 등록 케이스를 단계로 넣으면 주문 전에 기기가 사라진다. 그리고 「주문 완료 푸시」는 쇼핑몰 주문이 있어야 생겨 알림 서버 케이스 혼자서는 못 본다.
그래서 API 호출 단계에 칸 셋을 더했다. 케이스 파일 · 작성 규칙은 안 바꾼다(결정 12 원칙).

| 칸 | 무엇 | 비면 |
|---|---|---|
| API 인증 `auth` | 그 단계 애플리케이션(`service` 없으면 시작 애플리케이션)의 짝지은 대상 서버 줄의 API 인증 이름 하나. 토큰을 받아 `Authorization: Bearer` 로 붙인다 | 지금처럼 쿠키만 간다 |
| 값 주입 `values` | 앞 단계 응답에서 꺼낸 값에 이름을 붙여 경로 · 본문의 `{이름}` 자리에 넣는다. 이름은 영문 · 숫자 · 한글 · `_` 1~20자이고 한 단계 안에서 겹치지 않는다 | 넣지 않는다 |
| 응답 값 확인 `expectJson` | 응답 JSON 의 점 표기 경로 값이 적은 값과 형까지 같아야 한다. 응답 코드가 맞은 뒤에 차례로 본다 | 응답 코드만 본다 |

- **토큰 받기는 케이스의 `api(이름)` 과 같은 규칙이다**(도메인/API §3.8 「API 인증」) — OAuth2 client credentials · Basic · 토큰 주소가 `/` 로 시작하면 그 단계 주소에 붙인다 · 만료 30초 전이면 다시 받는다.
  러너 고정 spec 이 받는다(kit 을 값으로 못 부른다 — 러너 §5.2). **같은 단계 주소 · 같은 이름이면 시나리오 안에서 토큰 하나를 나눠 쓴다** — 케이스와 달리 단계가 한 프로세스에서 돈다
- **없는 이름이면 그 단계가 실패다** — `이 대상 서버에 API 인증 '<이름>' 가 없습니다`. 토큰을 못 받으면 `API 인증 '<이름>' 토큰을 받지 못했습니다 — 401`. 조립은 이름이 있는지 안 본다 — 이름은 대상 서버마다 따로 넣고 실행 때 서버를 고른다
- **인증 원문은 러너 요청에만 싣는다** — 그 단계 애플리케이션 대상 서버 줄의 인증 전부를 부품의 `apiAuths` 로 싣고 부품 기록(`scenario_run_part.part`) · 결과에는 안 넣는다(케이스 단계와 같다 — 도메인/API §3.8 「E2E」). 오류 글은 받은 토큰 · 비밀값 · Basic 머리를 `********` 로 가리고 첫 줄만 남긴다 — Playwright 오류의 호출 기록이 보낸 머리를 늘어놓는다
- **값 주입이 가리키는 단계는 자기보다 앞의 케이스 단계나 API 호출 단계다.** API 호출 단계의 응답도 러너가 적어 둔다 — 그래야 끝에 만든 기기를 지울 수 있다(`DELETE /v1/devices/{기기}`). 고르는 법은 결정 12 「요청 고르기」 그대로이고, API 호출 단계를 가리킬 때는 무늬를 `**` 로 둔다(그 단계 요청 하나뿐이다)
- **경로에 넣는 값은 주소 글자로 감싼다**(`encodeURIComponent`). 빈 글자 · `.` · `..` 면 그 단계가 실패다 — 바꿔 보내기와 같은 규칙(결정 12 「값 꺼내기」). **본문은 글자 전체가 `{이름}` 하나면 값을 형 그대로**(숫자는 숫자) 넣고, 글자 안에 섞였으면 글자로 잇는다. 선언하지 않은 `{…}` 는 그대로 둔다
- **응답 값 확인이 틀리면** — `응답 값이 다릅니다 — items.0.title (기대 주문이 완료되었습니다 · 받은 값 없음)`. 받은 값은 50자까지 싣는다. 첫 틀린 줄만 알린다
- **늦게 생기는 값은 앞에 대기 단계를 끼운다.** 다시 조회하는 칸은 만들지 않았다 — 데모 알림 서버의 주문 푸시 이력은 주문 응답과 함께 생긴다. 실제 서버에서 늦게 생겨 대기가 길어지면 그때 「최대 N초 다시 조회」를 이 표에 더한다
- **API 호출 단계는 여전히 모킹 · 이어 주기 · 뒷정리 미루기를 안 거친다**(결정 6 · 12) — 진짜 서버를 부르는 뒷문이다. 만든 것은 사람이 끝에 지우기 단계를 둔다
- 응답 형식 검사(도메인/API §3.8)는 API 호출 단계에 안 건다(1차) — 케이스 단계만 판과 견준다

#### 마법사로 만든다 — 단계마다 안내하고 AI 가 흐름 후보를 낸다 (결정 15, 2026-10-23)

새 시나리오는 **E2E 마법사**로 만든다(2026-10-22 사용자 「E2E 시나리오 만들기가 어렵다」 · 2026-10-23 계획 승인 · 진행판 E2E-F2). 조립 화면에서 막힌 곳은 셋이었다.
첫 케이스를 수백 건에서 직접 찾는다(첫 단계에는 추천이 없다). 값 연결은 메서드 · URL 패턴 · JSON 경로를 손으로 적고, 틀려도 조용히 안 걸린다(결정 12 「요청 고르기」). 무엇을 해야 다음으로 가는지 화면이 말하지 않는다.
화면은 §8.11 「마법사」, 통로는 §7 「마법사 통로」다.

- **마법사는 조립 화면 앞에 선 길이다. 저장 모양 · 실행은 그대로다** — 마법사가 만든 시나리오도 같은 `ScenarioPart[]` 로 §7 `POST /api/scenarios` 에 저장된다. 그래서 DB 표 · 러너 · kit 은 안 바뀐다.
  조립 화면은 남는다. 저장한 시나리오를 고치는 곳이고, 마법사 머리의 `조립 화면으로` 로 옮겨 갈 수도 있다. 목록의 `새 시나리오` 는 마법사를 연다
- **단계 — 이 표가 정본이다.** 화면 · 안내 글은 §8.11 「마법사」가 이 차례를 따른다.

  | 차례 | 단계 | 하는 일 | 다음으로 넘어가는 조건 |
  |---|---|---|---|
  | 1 | 시작 방법 | 「AI 추천으로 시작」 · 「직접 고르기」 중 하나를 고르고 애플리케이션 · 디바이스를 정한다 | 시작 방법을 골랐다 |
  | 2 | AI 추천 | **AI 경로에만 있다.** 흐름 후보 2~3개 중 하나를 고르면 단계가 채워진다. 「확인하고 싶은 흐름」을 적어 다시 추천받을 수 있다 | 후보를 골랐다 |
  | 3 | 단계 | 단계를 차례로 이어 붙인다 — 첫 단계 후보 · 다음 단계 추천 · 케이스 찾기 · 다른 단계(API 호출 · 모킹 · 대기) | 단계가 하나 이상이다 |
  | 4 | 값 연결 | 로그인 이어받기 · 제안된 값 연결을 확인하거나 고친다 · 입력값 | 빈 칸(JSON 경로 · 값 주입의 입력값 칸)이 남은 값 연결이 없다 |
  | 5 | 시험 실행 | 대상 서버에서 한 번 돌려 본다 | 도는 중이 아니다 — 안 돌려도 넘어간다 |
  | 6 | 저장 | 이름을 적고 요약을 본다. `저장` 또는 `저장하고 실행` | 이름을 적었다 |

  **시험 실행은 저장 조건이 아니다** — 조립 화면도 그렇다(저장 조건은 이름 · 단계 하나 이상 · 조립 거절 400 뿐이다). 마법사는 막지 않고 안내만 한다.
  앞 단계로 돌아가 단계를 바꾸면 시험 결과를 지운다 — 바뀐 조립의 결과가 아니다
- **첫 단계 후보** — 케이스 단계가 하나도 없을 때 「다음 단계 추천」 자리에 선다(조립 화면의 단계 추가 탭도 같다). API 호출 · 모킹 · 대기만 있어도 첫 단계 후보다 — 다음 단계 추천의 기준이 맨 뒤 케이스 단계라서다.
  출발 화면은 그 애플리케이션 대상 서버 주소(`service_env`)의 경로를 같은 틀로 맞춘 화면이다 — 주소에 경로가 없거나(`http://host:3001`) 그 경로의 화면 기록이 없으면 `/` 다. 대상 서버가 여럿이면 그 경로들을 다 출발 화면으로 본다(운영툴처럼 `/ops` 아래에 사는 애플리케이션이 `/` 만 보면 늘 빈다). 상태는 안 가린다 — 크롤러는 시작 화면만 로그아웃 · 로그인 기록을 둘 다 남긴다(도메인/작성 §3.6 「화면 기록과 크롤러」 · `scripts/authoring-crawl-rules.ts` `목록고르기`). 두 상태의 연결을 다 쓰니 로그인 · 가입 케이스도 후보가 된다.
  후보는 지도 ② 의 화면이 출발 화면이거나, 출발 화면에서 화면 연결 한 번으로 닿는 화면인 그 애플리케이션의 활성 케이스다. UI 테스트는 뺀다.
  **머리 · 바닥 메뉴 링크는 빼지 않는다** — 다음 단계 추천에서 빼는 까닭은 「어디서나 가는 곳이 늘 섞인다」였는데, 첫 화면에서는 메뉴가 곧 첫걸음이다.
  정상 쪽 · 디바이스 거르기와 차례는 화면이 다음 단계 추천과 같은 규칙으로 한다. 출발 화면 기록이 없으면 빈 목록이고 화면은 「케이스 찾기」로 고르게 한다
- **AI 흐름 후보** (「AI 추천으로 시작」)
  - **누가 돌리나** — admin 이 재료를 모아 AI 일(`perf_ai_job`, 종류 `SUGGEST_FLOWS`)을 세우고, 작성 에이전트가 성능 AI 일과 같은 자리 · 같은 고리로 집어 claude 로 돌린다(도메인/성능 §7 「AI 일」 — 도구 · MCP 없이 15분까지, 집고 20분 넘으면 `FAILED`, 모델은 작성 에이전트의 기본 모델).
    **집기는 `SUGGEST_FLOWS` 를 먼저 준다** — 사람이 화면 앞에서 기다린다. 성능 일은 실행 뒤에 서서 기다려도 된다. 이미 도는 성능 일은 끊지 않는다(아래 「남는 한계」).
    표를 새로 만들지 않은 까닭 — 일 모양(종류 · 재료 · 결과 · 상태)과 집는 쪽이 같다. 지금 쓰는 구독 안에서 돌아 추가 비용이 없다(성능 결정 14)
  - **재료** — 시작 애플리케이션 하나의 것만 admin 이 담는다.
    ① 요구사항 — 현재 판의 요구 번호 · 기능 묶음 · 종류 · 요구 문장
    ② 케이스 — 고른 디바이스에서 도는 활성 기능 테스트의 번호 · 이름 · 요구 번호들 · 머무는 화면(지도 ②) · 정상 쪽인지(§8.11 「가르는 기준」 — 화면 팔레트와 서버가 같이 부르는 `scenario/flowSide.ts` 한 벌이다. 화면에만 있던 판정을 E2E-F2-03 이 옮겼다. `scenario/next.ts` 가 「서버에 또 두면 어긋난다」며 서버에 안 둔 그 규칙이다)
    ③ 화면 연결 — 출발 · 도착 · 누른 것. 머리 · 바닥 메뉴 링크는 뺀다(§7 `next-cases` 와 같은 규칙)
    ④ 사람이 적은 「확인하고 싶은 흐름」 — 선택, 200자까지
    케이스 파일 원문 · 화면 기록 원문 · 서비스 가이드는 넣지 않는다. 고르고 잇는 데는 이름 · 요구 · 화면이면 되고, 원문은 크고 남이 쓴 글이 섞인다.
    상한은 케이스 1,000건 · 화면 연결 2,000줄 · 요구 1,000줄이다. 넘으면 앞에서부터 그만큼만 담고 재료에 `truncated: true` 를 단다
  - **결과 모양** — `{ candidates: [{ name, why, tcIds, reqIds, links: [{ toSeq, fromSeq, param?, jsonPath }] }] }`. AI 에게는 후보 2~3개를 시키고 결과 검사는 1~3개를 받는다(다듬은 뒤 하나만 남을 수 있다) · `name` 60자 · `why` 300자 · `tcIds` 2~15개다.
    `links` 의 번호는 `tcIds` 차례(1부터)이고 `fromSeq` 가 `toSeq` 보다 앞이다. AI 는 재료에 있는 케이스 번호만 쓴다 — 새 케이스를 만들지 않는다(결정 12)
  - **admin 이 다듬는다** — 재료에 없는 번호와 한 후보 안에서 겹친 번호는 뺀다. 남은 단계가 둘보다 적은 후보는 버린다. 다 버려지면 그 일이 `FAILED` 이고 사유는 `쓸 수 있는 흐름 후보가 없다` 다.
    AI 의 값 연결 짐작은 **아래 「값 연결 제안」이 같은 두 단계에 낸 제안이 있을 때만** 쓴다 — 그 제안의 JSON 경로(값 주입은 입력값 칸까지)만 채운다. 메서드 · URL 패턴 · 수정 주소는 지도에서만 온다. AI 가 주소를 지어내면 조용히 안 걸린다(결정 12). 맞는 제안이 없는 짐작은 버린다
  - **작성 에이전트가 꺼져 있으면** — 요청이 503 `AGENT_OFFLINE` 이고, 화면은 `AI 추천을 지금 쓸 수 없습니다` 와 함께 「직접 고르기」로 이어 가게 한다.
    「꺼짐」은 admin 이 작성 에이전트 계정의 AI 일 집기를 1분 넘게 못 받았고 집힌(`claimed_at` 이 있는) `RUNNING` AI 일도 없을 때다 — 녹화를 기다리는 성능 일은 집히기 전에도 `RUNNING` 이라 세지 않는다. 집으러 오는 계정이 그 애플리케이션의 프로젝트에 배정돼 있지 않아도 「꺼짐」으로 본다 — 집기는 배정된 애플리케이션의 일만 주므로(도메인/성능 §7 「누가 집나」) 맡겨도 아무도 안 집는다. 에이전트는 일이 없으면 5초마다 집으러 온다(`scripts/authoring-perf.ts`).
    마지막 집기 시각은 admin 메모리에 둔다 — admin 이 다시 켜지면 첫 집기가 올 때까지 집힌 `RUNNING` AI 일이 있을 때만 「켜짐」이고 없으면 「꺼짐」이다(쉬는 에이전트면 길어야 5초 · 2026-10-23 E2E-F2-03 끝 검사 — 바쁜 에이전트를 꺼졌다고 보고 대기 일을 닫지 않게).
    요청한 뒤에 에이전트가 꺼지면, 대기(`QUEUED`)가 2분을 넘고 「꺼짐」인 일을 `FAILED` 로 닫는다. 사유는 `작성 에이전트가 꺼져 있다` 다.
    집고 20분 넘게 안 끝난 일(에이전트가 돌다 죽었다)도 같이 닫는다 — 성능 「오래 쥔 일」과 같은 규칙이다. **이 둘은 집기 · 맡기기 때마다, 결과 보기는 안 끝난 일(`QUEUED` · `RUNNING`)을 볼 때마다 본다** — 성능은 집기와 성능 결과 보기 때만 보는데 흐름 추천 결과는 그 통로로 안 읽고, 에이전트가 죽으면 집기도 안 온다
  - **같은 사람이 같은 애플리케이션 · 같은 디바이스 · 같은 「확인하고 싶은 흐름」으로 대기 · 진행 중인 흐름 추천 일이 있으면 새로 세우지 않고 그 일 번호를 준다** — 「다시 추천받기」를 여러 번 눌러 구독 한도를 쓰지 않게(성능 「AI 분석 다시 만들기」와 같은 꼴). 디바이스나 흐름 글을 바꿨으면 새 일이다. 앞 일은 그대로 두고 화면은 새 번호만 묻는다
  - **후보의 값 연결은 케이스 단계에 묶여 다닌다** — `toSeq` · `fromSeq` 는 후보를 받을 때만 쓰는 번호다. 마법사는 값 연결을 받는 케이스 단계에 달고, 가져올 단계는 그 단계 자체를 가리키게 들고 있다가 저장할 때 차례대로 번호를 다시 매긴다(조립 화면이 단계를 옮길 때와 같다).
    다른 단계를 끼우거나 차례를 바꿔도 같은 두 케이스를 잇는다. 가져올 단계가 삭제되거나 받는 단계보다 뒤로 가면 그 값 연결은 `가져올 단계가 삭제됐습니다` 로 남고 「값 연결」에서 다음으로 안 넘어간다 — 고치거나 삭제한다
- **값 연결 제안** — 서비스 지도(도메인/작성 §3.6 「서비스 지도」 — 메서드 · 호스트 · 경로 틀 · 부른 케이스만 있고 **응답 내용은 없다**)로 같은 애플리케이션의 케이스 단계 둘(앞 A · 뒤 B)을 맞춰 본다.
  `<모음>` 은 끝 마디가 `:n` · `:id` 가 아닌 경로 틀이다(`/api/orders`). URL 패턴 · 수정 주소는 조립 화면 「요청 고르기」와 같은 변환(§8.11)으로 만든다.
  - **수정 요청으로 변경** — A 와 B 가 둘 다 `POST <모음>` 을 부르고 그 애플리케이션 지도에 `PUT` 이나 `PATCH <모음>/:n`(또는 `:id`)이 있으면 B 에 낸다.
    B 의 `POST <모음>` 을 `PUT <모음>/{}`(`PUT` 이 없으면 `PATCH`)로 바꾸고, 값은 A 가 같은 `POST` 에서 받은 응답에서 꺼낸다. 결정 12 「한계」의 「뒤 부품이 자기가 만든 데이터를 확인한다」 자리다.
    `<모음>` 중간에 `:n` · `:id` 마디가 있으면(`/api/carts/:n/items`) 안 낸다 — 수정 주소는 `{}` 한 자리만 채워 그 마디가 글자째 남는다(2026-10-24 FIX-F2-05 · 리뷰 L11). 값 주입은 주소를 안 만들어 그대로 낸다
  - **값 주입** — A 가 `POST <모음>` 을 부르고, B 가 `GET` · `PUT` · `PATCH` · `DELETE <모음>/:n`(또는 `:id`)을 부르고, B 에 입력값 칸이 하나라도 있으면 낸다. 이름이 `id` · `Id` · `ID` · `번호` 로 끝나는 칸이 하나뿐이면 그 칸을 넣고, 없거나 둘 이상이면 칸을 비워 `needs` 에 `param` 을 넣는다(AI 경로는 AI 짐작으로 채운다). 입력값 칸이 없는 B 에는 안 낸다. 값은 A 의 그 `POST` 응답에서 꺼낸다
  - **JSON 경로는 비워서 낸다** — 지도에 응답 모양이 없다. AI 경로는 AI 짐작으로 채운다. 빈 칸(JSON 경로 · 값 주입의 입력값 칸 — 응답의 `needs`)이 남은 제안이 있으면 마법사가 「값 연결」에서 다음으로 안 넘어간다 — 빈 칸은 조립 400 이다.
    채운 제안도 사람이 확인하기 전까지 `확인 필요` 로 보인다(§8.11 「마법사」)
  - **안 내는 때** — B 에 같은 종류 · 같은 무늬(값 주입은 같은 칸)의 값 연결이 이미 있다 · 로그인 이어받기를 끈 B(조립 400 이다) · A 와 B 의 애플리케이션이 다르다(지도가 애플리케이션마다다. 결정 13 의 섞인 값 연결은 사람이 건다).
    맞는 A 가 여럿이면 B 에 가장 가까운 것 하나다
  - **(작성, read) 가 없으면 빈 목록이다** — 조립 화면 「요청 고르기」가 지도를 못 보는 사람에게 손으로 적게 하는 것과 같다(§8.11)
  - **단계 목록이 조립의 60분 · 크기 상한(§7 「400 으로 거절하는 조립」)을 넘으면 지도를 읽지 않고 빈 목록이다** (2026-10-24 FIX-F2-03 · 리뷰 L12) — 제안은 단계 수의 제곱으로 돌아 큰 초안 하나가 서버를 수 초 붙잡았다.
    크기 상한 안에도 단계가 수천 개 들어서 60분 상한(케이스 단계 수를 묶는다)도 같이 본다. 넘는 초안은 어차피 저장이 안 된다
- **시험 실행 뒤 값 연결이 쓰였는지 알린다** — 마법사의 시험 실행 칸이 값 연결마다 한 줄씩 적는다. **재료는 지금 결과 칸뿐이다** — 러너 · kit 약속은 안 바꾼다.
  값 주입은 그 단계 결과의 `bound` 에 그 칸이 있으면 `쓰임` 이다. 단계가 돌았는데 없으면 `안 쓰임` 이다.
  요청 차단 · 이전 응답 재사용 · 수정 요청으로 변경은 그 단계가 실패했을 때만 「적용되지 않은 값 연결」 꼬리(결정 12)로 `안 쓰임` 을 안다. 통과한 단계는 `통과 · 쓰였는지는 결과에 남지 않습니다` 로 적는다
- **E2E 는 조합만이다**(결정 12) — 마법사도 AI 도 케이스 · 작성 규칙 · 작성 하네스를 바꾸지 않는다. AI 는 있는 케이스를 고르고 잇기만 한다
- **남는 한계**
  - AI 후보는 시작 애플리케이션 하나의 케이스로만 짠다. 다른 애플리케이션 단계는 「단계」에서 사람이 섞는다(결정 13)
  - 통과한 단계에 요청 차단 · 이전 응답 재사용 · 수정 요청이 실제로 걸렸는지는 결과에 없다. 러너가 건 이어 주기를 결과에 싣는 것은 러너 · kit 약속을 바꾸는 일이라 이번에 안 했다
  - AI 흐름 후보는 작성 에이전트의 한 자리를 성능 AI 일과 같이 쓴다. 먼저 집히긴 해도 이미 도는 성능 일(길면 15분)이 끝나야 집힌다. 그동안 화면은 대기로 남는다
  - admin 이 다시 켜진 뒤 첫 집기가 오기 전(길어야 5초) 맡기기는 503 이다 — 마지막 집기 시각을 메모리에 두는 값이다. 그동안 집힌 일이 돌고 있으면 「켜짐」으로 보는데, 배정을 아직 몰라 그 에이전트가 배정 안 된 애플리케이션도 「켜짐」이다 — 맡긴 일은 2분 뒤 첫 집기가 온 다음 닫기에서 「꺼짐」으로 닫힌다
  - 수정 요청 제안은 B 가 그 `POST` 를 준비 구간(첫 확인 전)에서 불렀는지 모른다 — 지도에 그 구분이 없다. 준비 구간 밖이면 결정 12 안전 규칙대로 안 걸리고, 시험 실행이 실패해야 「적용되지 않은 값 연결」로 드러난다
  - 값 연결 제안은 서비스 지도에 기록이 있는 케이스만 낸다 — 정식 실행을 한 번도 안 한 케이스는 지도 줄이 없다(도메인/작성 §3.6 「서비스 지도」)

#### 앱 · 게임 단계 — 폰 하나에서 이어 돌고 앱을 다시 켜지 않는다 (결정 16, 2026-10-28)

「앱에서 주문 → 운영툴 웹에서 배송중으로 바꿈 → 앱 주문내역에 배송중」 · 「상점에서 사기 → 가방에 들어왔나 → 강화」를 한 시나리오로 돈다(진행판 E2E-F3).
2026-10-28 사용자 「앱으로 e2e를 만들면 좋을거 같은데」 · 「게임도 같이 넣자」 · 「앱 재실행 하지 않고 진행되도록 설계해」.
앱과 웹을 섞는 것도 이번에 같이 한다 — 시작 질문(2026-10-28)에서 처음엔 뒤로 미루자고 했고, 사용자가 위 첫 장면을 들어 「브라우저를 띄어서 설정하고 성공하면 러너가 앱에 알려줘서 확인하게 하면 되잖아」로 뒤집었다.

- **앱 · 게임 단계는 애플리케이션 종류가 Android 앱이나 게임인 애플리케이션의 케이스 단계다**(러너 §5.2 「애플리케이션 종류 「Android 앱」」). 폰에서 돌고, 그 케이스는 `android` 를 선언해야 한다(아니면 조립 400).
  나머지 케이스 단계는 **웹 단계**이고 지금처럼 브라우저 창에서 돈다. 어느 쪽인지는 저장하지 않고 케이스 번호 앞 글자로 그 애플리케이션을 찾아 종류에서 읽는다 — 결정 13 과 같은 읽기다. 그래서 부품 저장 모양은 안 바뀐다.
  러너는 admin 이 고른 대로 받는다 — 요청의 case 부품 줄에 앱 · 게임 단계 표시를 admin 이 싣는다(서버와 러너가 따로 판정하면 어긋난다. 칸 모양은 아래 계약 블록 2)
- **디바이스 「Android 앱」(`android`)** — 시작 애플리케이션이 Android 앱 · 게임 종류일 때 고르는 값이고, 그런 애플리케이션은 이것만 고른다(그 케이스는 `android` 만 선언한다 — 공통/2-명세선언 §4 「Android 앱 케이스」). 웹 애플리케이션은 지금처럼 PC · 모바일이다.
  **시나리오 디바이스는 웹 단계가 어느 창으로 도는지를 정한다** — `android` 시나리오에 섞은 웹 단계와 시작할 때 여는 빈 창(러너 §5.2)은 PC 설정으로 연다. PC · 모바일 시나리오에도 같은 프로젝트의 앱 · 게임 단계를 섞을 수 있고(결정 13), 앱 · 게임 단계는 시나리오 디바이스와 상관없이 폰에서 돈다.
  조립 검사의 「시나리오 디바이스를 선언하지 않은 케이스」는 웹 단계에만 본다(`android` 시나리오면 PC). 앱 · 게임 단계는 `android` 선언을 본다
- **폰 연결은 시나리오에 하나다. 앱 · 게임을 단계 사이에 다시 켜지 않는다** — 러너가 첫 앱 · 게임 단계에서 Appium 연결을 한 번 열어 앱을 한 번 깔고 켜고(게임이면 게임 포트에도 붙는다 — 도메인/게임 §3.10 「게임 연결」), 시나리오 끝(미룬 뒷정리 뒤)에 닫는다. 여는 시간은 그 첫 단계의 한도 안에 든다 — 단독 앱 항목과 같다(2026-10-28 E2E-F3-02).
  다음 앱 · 게임 단계는 **앞 앱 · 게임 단계가 끝난 화면에서** 이어 간다. 그 사이에 웹 단계 · API 호출 · 대기가 끼어도 앱은 켜진 채 기다린다 — 운영툴 웹 단계가 배송 상태를 바꾸면 다음 앱 단계가 그 앱에서 주문내역을 연다.
  웹의 「단계마다 새 창」(결정 3)과 다르다 — 앱의 로그인 상태는 앱 안에 있어 옮길 것이 없고, 다시 켜면 그 상태를 잃는다. 다음 단계 케이스의 로그인 같은 준비는 사람이 체크를 풀어 건너뛴다(결정 4). 「N번에서 이미 실행」 칩(결정 5)이 같은 애플리케이션 단계끼리 세므로 앱 단계끼리도 뜬다
- **한 시나리오의 앱 · 게임 단계는 한 애플리케이션 것이다** — 연결 하나에 앱 하나다. 다른 앱 · 게임 애플리케이션의 단계를 더 넣으면 조립 400 이다. 웹 애플리케이션은 결정 13 대로 몇 개든 섞는다
- **앱 · 게임 단계에 거는 것 — 이 표가 정본이다**

  | 거는 것 | 앱 · 게임 단계 | 까닭 |
  |---|---|---|
  | 준비 건너뛰기 (결정 4) | 된다 | 앱을 다시 켜지 않아 앞 단계가 세운 로그인 위에서 돈다. 대개 꺼야 한다 |
  | 값 꽂기 (결정 12) | 된다 | 앞 단계 응답에서 꺼낸 값(예: 어드민 API 로 만든 캐릭터 번호 812)을 입력값 칸에 넣는다 |
  | 앞 응답 돌려주기 · 요청 막기 · 바꿔 보내기 (결정 12) | 조립 400 | 앱은 폰 안에서 자기 서버와 바로 주고받아 러너가 그 요청을 못 본다. 걸어도 앱 요청은 그대로 서버로 가는데 사람은 걸린 줄 안다 |
  | 모킹 (결정 6) | 모킹 구간 안에 앱 · 게임 단계가 있으면 조립 400 | 같은 까닭이다 — 「모킹된 줄 알았는데 진짜 서버를 두드린 실행」이 가장 나쁜 실패다. 모킹은 웹 단계 앞에 걸고 앱 단계 앞에서 끈다 |
  | 넘겨받기 끔 (결정 12) | 조립 400 | 끄려면 앱을 다시 켜야 한다 |
  | 뒷정리 미루기 (결정 12) | 러너가 늘 | 케이스 코드의 요청 도구(`request` · 게임 `admin`)로 보낸 절차 밖 삭제는 웹처럼 미룬다. 앱 화면이 보낸 삭제는 못 본다 |

  값 꽂기가 꺼내는 응답은 **케이스 코드가 직접 부른 요청 도구의 응답**과 API 호출 단계 응답이다 — 러너가 감싼 것만 본다(결정 12 「요청 고르기」). 앱 화면이 받은 응답은 없다.
  웹 단계가 앱 단계 응답에서, 앱 단계가 웹 단계 응답에서 꺼내는 것도 된다 — 시나리오 안의 앞 단계면 된다
- **API 호출 · 대기 단계는 그대로 쓴다.** API 호출 단계는 지금처럼 마지막 창으로 부른다 — 앞에 웹 단계가 없으면 시작할 때 연 빈 창이라 쿠키 없이 간다. 토큰은 API 인증(결정 14)으로 붙인다. 앱의 로그인은 API 호출 단계에 안 넘어간다
- **앞 단계가 끝난 화면과 다음 앱 단계 케이스의 첫 화면이 달라도 도구가 미리 막지 않는다** — 「이어지는지는 시험 실행으로 본다」(결정 12) 그대로다. 다음 케이스가 첫 화면을 확인하면 그 자리에서 빨강이고, 사람이 단계 차례 · 건너뛰기를 고친다
- **폰은 시나리오 동안 한 번 잡고 한 번 놓는다** — 앱 · 게임 단계가 하나라도 있으면 잡는다.
  정식 실행은 늘 디바이스 팜이다. admin 이 실행을 서버 러너에 보내기 직전에 빈 폰 하나를 잡아 `udid` 로 싣고, 러너가 답하면(통과 · 실패 · 러너 고장 모두) 놓는다. 앱 항목처럼 단계마다 잡고 놓지 않는다 — 놓을 때 팜이 앱을 지운다(러너 §5.2 「디바이스 팜 접속 방식」).
  잡는 시간은 시나리오 제한 시간에 10분을 더한 값이 들어가는 가장 짧은 것(30 · 60 · 120분)이라 늘리기를 부르지 않는다. 못 잡으면 러너에 보내지 않고 첫 단계를 `NA` · 앱 항목과 같은 팜 문장(`apps/admin/src/execution/farm.ts`)으로, 뒤 단계를 `NOT_RUN` 으로 닫는다. 서버에 팜이 없으면(`DEVICE_FARM_URL` 이 비었다) 정식 실행이 409 `FARM_OFF` 다.
  **디바이스 줄의 차례 하나를 시나리오 전체가 쓴다**(도메인/실행 §3.2 「디바이스 줄」 — 게임 실행과 같은 꼴). 그동안 다른 앱 항목은 기다리고 테스트 실행은 `DEVICE_BUSY` 다. 시나리오 동시성 자리(아래 「동시성 · 시간」)도 그대로 하나 쓴다.
  **잡는 순서는 디바이스 줄 → 동시성 자리 → 폰이다** — 디바이스 줄에서 차례를 기다리는 동안 웹 실행 자리를 묶지 않게, 줄에서 차례를 받은 뒤에 동시성 자리를 잡고 그다음 팜에서 폰을 잡는다
- **시험 실행은 지금 규칙 그대로다**(§7 「시험 실행 규칙」) — 내 컴퓨터 러너가 켜져 있으면 그 러너에 꽂은 폰에서 돈다. 팜을 잡지 않는다 — 케이스 테스트 실행과 같다. 꺼져 있으면 서버 러너 + 팜이고 잡는 규칙은 정식 실행과 같다.
  시험 실행도 디바이스 줄 잠금을 쥔다 — **다른 검사를 다 지난 뒤, 동시성 자리보다 먼저** 잠금을 보고 쓰이는 중이면 기다리지 않고 409 `DEVICE_BUSY` 다(케이스 테스트 실행과 같다). 내 컴퓨터 러너가 꺼져 있고 서버에 팜도 없으면 409 `FARM_OFF` 다
- **앱 파일 · 어드민 키는 그 앱 · 게임 애플리케이션의 짝지은 대상 서버 줄에서 온다** — 결정 13 의 이름 짝짓기 그대로, 그 줄의 앱 파일과 (게임이면) 어드민 키를 러너 요청에 싣는다.
  앱 파일은 앱 항목과 같은 규칙이다 — 그 줄에 올린 빌드가 있으면 최신 빌드(서명 주소 · 회사 저장소 주소), 없으면 그 줄의 `app_path`(도메인/실행 §3.11). 서명 주소에 기한이 있어 폰을 잡은 뒤에 정한다(2026-10-29 E2E-F3-03 시작 질문 — 처음엔 `app_path` 만 적었다). 어드민 키는 게임 단계 케이스에만 넘기고 부품 기록(`scenario_run_part.part`) · 결과에는 안 넣는다.
  팜 토큰은 앱 · 게임 단계가 있는 시나리오의 러너 자식에만 넘긴다(러너 §5.2 「팜 토큰은 누른 사람 것이 먼저다」). 같은 프로세스에서 도는 웹 단계 케이스 코드가 환경으로 못 읽게 고정 spec 이 케이스를 불러오기 전에 토큰 · 어드민 키를 떼어 둔다(러너 §5.2 「앱 · 게임 단계」 — 2026-10-28 E2E-F3-02. 처음엔 웹 단계도 읽는 한계로 적었다). 앱 · 게임 단계 케이스는 Android 앱 케이스처럼 연결 안에서 읽을 수 있다
- **결과** — 앱 · 게임 단계 스크린샷은 폰 화면이고 경로와 순번 규칙은 그대로다. 단계 시험 한도는 그 단계 디바이스의 단독 실행 한도다 — 앱 · 게임 단계는 `android` project 의 2분(러너 §5.2 「앱 실행」), 웹 단계는 지금 값이다.
  기기 정보 · 팜 영상 · logcat 은 연결이 하나라 **시나리오에 한 벌**이다(기기 정보는 러너 응답 `device` — 아래 블록). 앱 항목처럼 통과하지 못한 정식 실행만 받고 `artifacts/runs/<runId>/scenario/farm/` 에 둔다. 게임 실패 파일(`game-tree.txt` · `game-errors.txt`)은 실패한 게임 단계의 것이다.
  **게임 대조 값(`game_element`)과 서비스 지도에는 안 남긴다** — 시나리오 결과를 케이스 이력에 안 섞는 규칙(결정 10)과 같다

#### 동시성 · 시간

- **케이스 실행과 같은 동시성 상한(기본 2)을 나눠 쓴다.** 시험 실행도 한 자리를 쓴다 — 상한의 근거가 러너 한 대가 여는 브라우저 수이기 때문이다
- **제한 시간은 부품 몫의 합이다** — 케이스 부품마다 `300000`ms · API 부품마다 `30000`ms · 대기 부품은 그 `ms`. 모킹·모킹 끄기는 몫이 없다.
  **합이 `60000`ms 보다 작으면 `60000`ms 로 올린다** — 대기·모킹만 있는 조립이 0 이 되지 않게 (2026-09-29 게이트 0)
- **60분(`3600000`ms) 상한은 바닥을 올리기 전의 합으로 본다.** 넘으면 저장을 400 으로 거절한다.
  이미 저장된 버전이 넘으면(되돌린 옛 버전 · 뒤에 붙은 API 몫) 저장은 그대로 두고 실행을 막는다 — `runnable` 이 false 다 (§7)
- **케이스 부품 하나는 단독 실행과 같은 시험 한도로 돈다** (2026-10-06). 넘으면 그 부품이 `FAIL` 이고 거기서 멈춘다 — 사유 `단계 제한 시간 <N>ms 를 넘었다`.
  앱 · 게임 단계는 `android` project 한도(2분)다(결정 16, 2026-10-28).
  창을 닫은 뒤 5초 안에 온 절차는 싣는다(러너 §5.2).
  한도는 단독 실행의 Playwright 시험 한도다(지금은 루트 설정에 없어 기본 30초). 시나리오 전용 설정이 루트 설정에서 그 값을 읽어 고정 spec 에 넘긴다 — 루트에 `timeout` 을 넣는 날 둘이 갈리지 않게.
  루트 `timeout` 이 `0`(무제한)이면 부품 한도도 없다 — 모든 부품이 0ms 에 실패하지 않게.
  **천천히 도는 시험 실행은 다섯 배다** (2026-10-17 — §7 「시험 실행 규칙」).
  위 부품 몫 `300000`ms 는 러너가 자식 프로세스를 끊는 벽이라 그대로다.
  **처음에는 부품 한도가 없었다**(시나리오 설정 `timeout: 0`) — 건너뛰기를 잘못 골라 화면 요소를 끝없이 기다리면 시나리오 전체 제한 시간에 걸려
  `TIMEOUT`(판정 없음)으로 끝났다. 「틀린 건너뛰기는 언제나 빨강」(결정 4)이 깨졌다

#### 남는 한계 — 이번에 안 만드는 것

- **진행 표시와 도중 멈춤이 없다.** 러너의 `/progress`·`/abort` 는 `historyId` 로 지목하는데 시나리오 실행에는 그것이 없다.
  제한 시간이 상한이다. `POST /api/runs/:runId/abort` 는 시나리오 실행에 409 다. 필요해지면 러너 지목 열쇠부터 정한다
- **Slack 완료 알림을 안 보낸다** (도메인/실행 §8.9 는 케이스 실행만)
- **시나리오 개수에 기계 상한을 두지 않는다.** 조사 권장은 핵심 여정 10~20개다
- **시나리오 제한 시간에 걸린 부품은 절차가 안 남는다** (`steps: []`). 결과 줄이 부품이 끝날 때 나오기 때문이다 — 앞 부품들은 남는다.
  「어느 절차에서 걸렸나」가 필요해지면 절차마다 줄을 흘리는 것부터 정한다. 부품 시험 한도(「동시성 · 시간」)에 걸린 부품은 다르다 — 러너가 그 부품의 창 · 도구만 닫고 5초 안에 온 절차를 싣는다
- **시나리오 전체 제한 시간에 끊기면 미룬 뒷정리를 못 보낸다**(결정 12). 러너가 자식 프로세스를 죽이기 때문이다. 앞 부품이 만든 데이터가 대상 서버에 남는다.
  미룬 삭제 하나마다 부품 시험 한도를 걸어 보내므로 대상 서버가 아예 안 답하면 뒷정리 전체는 「건수 × 한도」다 — 2026-10-06 표본은 부품마다 0~1건이라 문제가 없지만, 건수가 많으면 시나리오 제한 시간에 걸릴 수 있다
- **여정 뒤에 로그아웃이 있으면 끝의 미룬 삭제가 거절될 수 있다**(결정 12). 미룬 삭제는 모을 때의 쿠키로 보내는데 로그아웃(보통 `POST`)은 안 미뤄져 서버 세션이 먼저 끊긴다. 그 삭제는 `cleanup` 에 401 로 남고 데이터는 대상 서버에 남는다
- **감싸지 않는 요청 꼴이 있다**(결정 12) — 주소 대신 요청 객체를 넘기는 `fetch(Request)` 는 이어 주기 · 미룸 없이 그대로 나간다. 2026-10-06 표본에 0건이다.
  쿼리를 `URLSearchParams` · 글자로 넘기는 꼴은 2026-10-24 부터 무늬 맞추기 · 미룬 삭제 둘 다 붙인다(FIX-F2-05 · 리뷰 L37 — 러너 §5.2 「미룬 삭제」)
- **창을 갈아 끼우면 sessionStorage 는 안 넘어간다**(결정 3). 로그인을 sessionStorage 에 두는 서비스는 로그인 준비를 건너뛸 수 없다 — 건너뛰면 다음 판정이 빨강이다.
  로그인만이 아니다 — 주입 스크립트가 sessionStorage 에 적는 표시(예: MKT 의 안내창 닫힘)도 안 넘어가서, 그 스크립트를 부르는 준비를 건너뛴 부품에는 안내창이 다시 뜰 수 있다

**치운 시나리오 · 비활성 서비스** (2026-09-29 게이트 0) — 치운 시나리오(`is_active = false`)는 **보기만** 된다.
실행 요청 · `PUT` · `restore` 가 409 `{ error: 'SCENARIO_ARCHIVED', detail }` 다.
서비스가 비활성이면 그 시나리오의 실행 요청 · `PUT` · `restore` 는 만들기와 같은 400 `{ error: 'INVALID_REQUEST', detail: '모르는 서비스다: <접두사>' }` 다.

**실행 요청** (`POST /api/scenarios/:id/runs`, 2026-09-29 게이트 1) — 오류는 이렇다.
본문 모양이 틀렸거나 `env` 가 빈 글자 400 `INVALID_REQUEST` · 없는 시나리오 404 `SCENARIO_NOT_FOUND` ·
대상 서버가 그 서비스에 없음 400 `ENV_NOT_FOUND`(케이스 실행과 같은 글자. 섞인 애플리케이션 가운데 하나라도 그 이름이 없으면 같은 오류이고 사유에 그 접두사가 든다 — 결정 13) · 치운 시나리오 409 `SCENARIO_ARCHIVED` · 못 도는 조립 409 `SCENARIO_NOT_RUNNABLE` ·
앱 · 게임 단계가 있는데 서버에 디바이스 팜이 없음 409 `FARM_OFF`(2026-10-28 결정 16 · 2026-10-29 E2E-F3-03 반영 — 실행 행을 세우기 전에 거절한다). 시험 실행(`POST /api/scenario-trials`)은 내 컴퓨터 러너가 꺼져 있고 팜도 없으면 409 `FARM_OFF`, 디바이스 줄이 쓰이는 중이면 409 `DEVICE_BUSY`(detail 없음 — 케이스 테스트 실행과 같다)다(결정 16 「시험 실행은 지금 규칙 그대로다」).
- **`runnable` 이 false 인 것** — 비활성 케이스를 쓴다 · 제한 시간 합이 60분을 넘는다 · 부품 목록이 크기 상한을 넘는다(위 「400 으로 거절하는 조립」) ·
  케이스 파일 경로가 tests 뿌리 밖이다(파일을 못 읽는 케이스와 같게 **비활성으로 친다** — 목록·상세가 죽지 않고, 내부 경로는 응답에 안 싣고 로그에만 남긴다. 2026-09-29 게이트 2). 저장 때 막는 규칙을 **최신 버전에 다시 건다** — 되돌린 옛 버전과 뒤에 붙은 API 몫이 저장 검사를 안 거쳤기 때문이다.
  목록의 `runnable` 과 실행 요청이 **같은 판정**을 본다. **예외 하나 — 저장값을 채운 뒤 크기**(위 「400 으로 거절하는 조립」 아래 2026-10-06 줄)는 실행 요청만 잰다. 목록마다 부품의 저장값을 읽지 않으려고서다 — 그 초과는 실행 409 로만 드러난다. 둘째 예외 — API 단계의 애플리케이션이 프로젝트 밖으로 옮겨진 것(결정 13)도 실행 409 로만 드러난다. 상세에는 `runnable` 칸이 없다 — 비활성은 `checks` 의 `CASE_INACTIVE` 로 드러나고, 60분·크기 초과는 실행 요청의 409 사유로만 드러난다
- **돌리는 것은 최신 버전이다.** `test_run` 에 `kind = 'SCENARIO'` · 시나리오 번호 · 버전 · 그 서비스 · 대상 서버 · 누른 사람을 적고 `notify_slack` 은 false 다(§3.7 「남는 한계」)
- **부품 행 스냅샷의 `timeout_ms`** — 케이스 부품마다 `300000` 이다. 제한 시간 계산의 케이스 몫과 같다(§3.7 「동시성 · 시간」)
- **부품 행 스냅샷의 입력값** — 조립에 없는 칸을 그 케이스의 저장값으로 채운 뒤 박제한다(§3.7 「부품 입력값을 채우는 순서」, 2026-10-06). 미확정 사유도 이때 박제한다(결정 12).
  시험 실행도 같은 순서로 채워 러너에 보낸다

**실행 결과를 적는 규칙** (2026-09-29 게이트 1)
- **러너가 거절(400 · 404 · 500)하거나 닿지 못하면** 실행은 `FINISHED`, 부품은 전부 `NA` 에 같은 `error.message` 다.
  문장은 케이스 실행의 「러너가 거절했다: …」 · 「러너에 닿지 못했습니다」와 같다(도메인/실행 §3.2)
- **저장 순서는 한 트랜잭션이다** — 먼저 `test_run` 을 `WHERE status = 'RUNNING'` 조건으로 `FINISHED` 로 바꾸고, 0행이면 **결과를 버린다**.
  재기동 복구가 이미 `ABORTED` 로 닫은 실행을 늦게 온 결과가 덮지 않게 한다. 그다음 부품(`finished_at IS NULL` 인 행) · 절차를 적는다
- **저장이 던지면** 부품 전부 `NA` + `결과를 저장하지 못했다: <원문>` 으로 닫고 로그에도 남긴다 — 그대로 두면 재기동 때까지 `RUNNING` 으로 남는다
- **러너 응답의 `cleanup` 은 실행 한 벌이다** (2026-10-06) — 줄마다 `fromSeq` 가 가리키는 부품 행의 `cleanup` 에 보낸 순서대로 넣는다. 모르는 `fromSeq` 줄은 버린다. `bound` 는 부품 줄의 것을 그 행에 넣는다
- **러너 응답의 부품 수가 행 수와 다르면** `seq` 로 짝을 맞춘다. 짝 없는 행은 `NA` 이고 문장은 응답 전체의 `error.message`(러너 고장 · `TIMEOUT` 따위)가 있으면 그것, 없으면 `러너가 이 단계 결과를 돌려주지 않았다` 다. 모르는 `seq` · 겹친 `seq` 는 버린다

**실패 기록** (2026-10-17 사용자 「실패했을 때 네트워크 · 콘솔 로그 등 원인 파악에 필요한 정보를 포함」 · 진행판 E2E-F1-26 · 시작 질문 사용자)

- **진짜 실행 · 시험 실행 모두 trace 를 켠다** — 러너가 사진 옆으로 옮긴다(러너 §5.2 「출력 폴더 · trace」). 단계 번호 경계는 kit 이 시나리오 모드에서도 남긴다(공통/3-공유계약 §5.1 ③). 부품이 시작할 때도 앞 번호로 경계를 남겨, 그 전의 일(API 부품 호출 · 앞 부품의 늦은 오류)이 다음 부품 첫 단계로 섞이지 않는다

**판정 접기** — `lastRun.verdict` 와 아래 E2E 탭 집계가 같은 규칙을 쓴다. §3.7 결정 9 의 「전부 통과해야 통과」를 값으로 적은 것이다.
전부 `PASS` → `PASS` · 하나라도 `FAIL` → `FAIL` · 그 밖(`FAIL` 없이 `NA` 가 있다 — `TIMEOUT` · `ABORTED` · 러너 거절·끊김) → `NA` · 실행이 도는 중 → `null`
- **미확정은 판정과 따로 싣는다** (2026-10-06 게이트 2 사용자 · §3.7 결정 12) — 부품 행에 미확정 사유가 하나라도 있으면 그 실행의 `unconfirmed` 가 참이다(목록 `lastRun` · E2E 탭 줄). 꼬리표일 뿐 집계는 가르지 않는다(2026-10-11 PRD-F4-02).
  실행을 만들 때 박제하므로 도는 중에도 참 · 거짓이다 — `verdict` 와 달리 `null` 이 아니다(2026-10-06 PR #163)
  접은 판정 그대로 센다 — `PASS` 이면서 미확정인 실행도 통과다(앞 판은 정식 통과로 안 셌다). `FAIL` 은 미확정이어도 `FAIL` 이다 — 이어진 흐름이 거기서 멈췄다

**실행 목록의 E2E 탭** (`GET /api/runs?kind=scenario`, 모양은 도메인/실행 §7) — 이 문단이 탭 집계의 정본이다.
- `kind` 에 모르는 값이 오면 조용히 `case` 로 본다 — `state` 거르개와 같다
- 줄의 `stoppedAt` 은 처음으로 `PASS` 가 아닌 부품의 `seq` 다. 전부 `PASS` 이거나 도는 중이면 `null`
- `summary.allPass` 는 접은 판정이 `PASS` 인 실행 수(미확정이 섞여도), `hasFail` 은 `FAIL` 인 실행 수다. `state=failed` 는 접은 판정이 `FAIL` 인 실행만 낸다. 앞 판의 `unconfirmedPass`(2026-10-06)는 2026-10-11 PRD-F4-02 에서 뺐다.
  줄마다 `unconfirmed` 를 싣는다 — 위 「판정 접기」
- 줄마다 `verdict` 를 싣는다 — 위 「판정 접기」로 접은 판정(도는 중 `null`). 화면이 줄 색과 판정 칩(도메인/실행 §8.7 「종류는 사이드바 하위 메뉴로 가른다」)을 이것으로 가른다 — `stoppedAt` 만으로는 실패와 시간 초과를 못 가른다 (2026-10-06 게이트 1 사용자)
  **`run_item` 으로 세지 않는다** — 시나리오 실행에는 `run_item` 이 없어 늘 0 이 된다

**케이스 단건 조회에 시나리오 실행 번호가 오면** (§3.7 결정 10, 2026-09-29 게이트 0 · 1)
- `GET /api/runs/:runId` 는 404 `{ error: 'SCENARIO_RUN', detail }` 이다. 번호만 들고 온 화면이 `/scenario` 로 갈아탈 수 있게 없는 번호(`RUN_NOT_FOUND`)와 가른다
- 견주기 · 실패 카드는 404 다 — 직전 실행과 견줄 케이스 항목이 없다. 증적 만들기는 E2E 증적을 만든다(아래 「증적은 기존 통로를 쓴다」)

**시험 실행은 기록에 안 남는다** (§8.11). `test_run` 을 만들지 않고, 결과는 admin 메모리에 두며 24시간 뒤 버린다 —
**admin 이 다시 뜨면 사라진다.** 기록이 아니므로 그래도 된다. 사진은 `artifacts/runs/trial/{trialId}/` 에 쌓이고,
**새 시험 실행이 시작될 때 24시간 지난 `trial/*` 폴더를 치운다** (2026-09-28 — 「착수 전」 ⑤). `trialId` 는 admin 이 만드는 UUID 라 서로 안 덮는다.
**남의 시험 결과를 못 본다** — 결과는 시작한 사람만 읽는다. 다른 사람이 `trialId` 를 쳐도 404 다.

**시험 실행 규칙** (2026-10-04 게이트 0 · 1 — 케이스 「테스트 실행」(도메인/실행 §3.2 · §7)과 같은 보관 규칙이다)
- **상한** — 사람당 동시 1건 · 메모리 전체 50건. 50건을 넘으면 가장 오래된 끝난 것부터 버린다. 50건이 전부 돌고 있거나 그 사람이 이미 돌리고 있으면 409 `{ error: 'TRIAL_BUSY', detail }` 이다.
  케이스 테스트 실행과 **따로 센다** — 이쪽은 내 컴퓨터 러너가 꺼져 있어도 **서버 러너**에서 돌아서 `TRIAL_OFF` 가 없다
- **내 컴퓨터 러너가 켜져 있으면 거기서 창을 띄워 천천히 돈다** (2026-10-17 사용자 — 「테스트가 엄청 빠를 텐데 천천히 볼 수 있게 · 시험 실행일 때만」).
  admin 이 시험을 러너에 보내기 직전에 `LOCAL_RUNNER_URL` 의 `GET /health` 를 2초 안에 물어 답하면 그 러너로, 비었거나 답이 없으면 지금처럼 서버 러너로 보낸다 —
  러너를 안 켰다고 시험이 막히면 안 된다. 어느 러너였는지는 끝 로그 한 줄에 남는다.
  창을 띄우는 러너(`PLATFORM_HEADED=1`)는 시험 실행에만 Playwright 동작(누르기 · 입력 · 이동)마다 1초를 쉰다(러너 §5.2 「내 컴퓨터 러너」 `PLATFORM_SLOW_MO`). 진짜 실행은 그 러너에 안 가고 늦추지도 않는다.
  늦춘 시간이 부품 한도(위 §3.7 「동시성 · 시간」)를 먹으므로 **천천히 도는 시험은 부품 한도가 다섯 배**다 — 끄지 않는 까닭은 틀린 건너뛰기가 빨강 대신 전체 제한 시간에 걸리지 않게 하려는 것이다.
  실패 사진은 그 러너가 저장소 `./artifacts` 에 쓴다. admin 이 같은 폴더를 보면 바로 읽고, 안 보면 그 러너에서 받아 온다(2026-10-27 — 공통/6-인프라 §9.2 「내 컴퓨터 러너」 `PLATFORM_ARTIFACTS_VOLUME`)
- **줄** — 케이스 실행 · 진짜 시나리오 실행과 같은 줄에 한 자리를 쓴다(위 §3.7 「동시성 · 시간」). 앞에 큰 실행이 줄 서 있으면 그것이 끝날 때까지 `RUNNING` 이다 — 대기 상태 칸을 따로 두지 않는다.
  내 컴퓨터 러너로 가도 자리를 쥔다 — 러너는 줄에서 자리를 잡은 뒤에 고르고(위 「내 컴퓨터 러너」 줄), 꺼져 있으면 서버 러너로 가야 해서다 (2026-10-17)
- **조립 거절은 만들기와 같다** — 위 「400 으로 거절하는 조립」 전부가 400 `INVALID_REQUEST` · 모르는(비활성) 서비스 400 `INVALID_REQUEST` · 그 서비스에 없는 대상 서버 400 `ENV_NOT_FOUND` ·
  본문 모양이 틀리면 400 `INVALID_REQUEST`. 대상 주소는 본문이 아니라 그 서비스의 `service_env` 에서 찾는다(섞인 애플리케이션은 각자의 `service_env` 에서 — 결정 13)
- **결과 읽기 · 사진** — 시작한 사람만. 남의 것 · 없는 번호 · 24시간 지난 번호 · UUID 모양이 아닌 번호는 모두 404 `{ error: 'TRIAL_NOT_FOUND', detail }` 다 — 있는지도 알리지 않는다.
  문(인증 §7)도 남의 번호를 서비스 판정 없이 지나보낸다 — 403 이 나가면 그 번호가 살아 있고 어느 서비스 것인지 샌다. 사진이 없으면 404 `SCREENSHOT_NOT_FOUND`, `seq` 가 숫자가 아니면 400 `INVALID_REQUEST`
- **비밀값을 가린다** — 결과 안 글자에서 케이스 부품의 **저장값을 채운 뒤의** `params` · `expected` 와 러너가 돌려준 `bound` 중 비밀 칸(`paramSchema` · `expectedSchema`) 값을 `********` 로 바꾼다.
  조립에서 비운 비밀번호도 저장값에서 채워져 러너로 가기 때문이다(2026-10-06 — 조립 본문만 보면 그 값이 가릴 목록에 안 든다)
- **러너가 거절하거나 닿지 못하면** 진짜 실행과 같은 문장으로 `status: 'NA'` 인 결과다(위 「실행 결과를 적는 규칙」의 첫 줄). 시험 자체가 깨지면 `시험 실행을 끝내지 못했습니다`
- **옛 사진 폴더 치우기** — UUID 모양 이름만 · 링크는 링크만 지운다 · 실패해도 시험은 시작한다. 시작 · 끝은 서버 로그에 한 줄씩 남는다(누가 · 어느 서비스 · 걸린 시간)
- **도중 멈춤이 없다** — 진짜 실행과 같다(§3.7 「남는 한계」). 조립 화면(진행판 E2E-F1-06)도 멈춤 버튼을 두지 않았다 — 필요해지면 그때 정한다

**증적은 기존 통로를 쓴다** — `POST /api/runs/:runId/evidence` 가 `kind = SCENARIO` 인 실행이면 E2E 증적을 만든다(도메인/리포팅 §8.4, 2026-10-16 PR #277).
도는 중이면 케이스 실행과 같이 409 `RUN_NOT_FINISHED` 다. 만든 문서는 `GET /api/runs/:runId/scenario` 의 `evidence` 에 쌓인다.

POST   /api/scenarios/flow-suggestions     AI 흐름 후보를 맡긴다
                                           { service, platform, wish? }   wish 는 「확인하고 싶은 흐름」 200자까지

                                           작성 에이전트가 꺼져 있으면 503 AGENT_OFFLINE. 그 디바이스에서 도는 활성 기능 테스트가 둘보다 적으면 409 NO_DATA. 실행 write

                                                material: { reqs, cases, links, truncated } }   담은 재료 수. 기다리는 동안 화면이 「테스트 N건 · 화면 연결 M건을 읽는 중입니다」로 쓴다

**목록** — 줄마다 번호(`SC-{id}`) · 이름 · 부품 수 · 버전 · 마지막 실행 · 결과(여섯은 다음 줄대로 칸 셋에 접는다). 결정 8 의 「확인 필요」·「실행 불가」 칩이 붙는다.
**칸은 실행 기록과 같은 줄 격자(번호 · 이름 · 오른쪽)로 접는다** (2026-10-16 E2E-F1-23 · PR #165 게이트 2 사용자) — 부품 수 · 버전 · 마지막 실행은 이름 아래 작은 글(`단계 N개 · vN · <시각>`)이고, 표머리는 `번호` · `이름` · `결과` 셋이다. 실행한 적이 없으면 시각 자리에 `실행 전`, 도는 중이면 `실행 중` 이다. 실행 기록 › E2E 는 2026-10-20 ⑬-5 부터 케이스 실행 기록과 같은 A안 줄(띠 · 제목과 작은 글 · 판정)이다(도메인/실행 §8.7 「E2E 탭도 A안이다」).
마지막 실행이 미확정이 섞인 통과면 통과 색으로 칠하고 「미확정」 꼬리표만 단다(결정 12 · §7 「판정 접기」 · 2026-10-11 PRD-F4-02 — 앞 판은 통과 색을 안 칠했다).
주 행동은 `새 시나리오` 다 — 마법사(아래 「마법사」)를 연다(2026-10-23 결정 15 · 앞 판은 빈 조립 화면). 줄의 `실행` 은 툴바에서 고른 대상 서버로 돈다 — 대상 서버는 기본값이 없어서, 안 고르고 누르면 고르라는 문장만 뜬다. 그 서비스에서 마지막에 고른 서버(서버가 하나뿐이면 그 서버)는 미리 골라져 있다 — 조립 화면 시험 실행도 같다(2026-10-19 ⑫-2 · 공통/5-화면공통 §8 「화면을 오가도 하던 일이 풀리지 않는다」).
줄의 `삭제` 는 확인 상자(DESIGN.md 「모달」 ①)를 거쳐 §7 `archive` 를 부르고 그 줄을 화면에서 뺀다 — 이미 없는 시나리오(404)도 뺀다 (2026-10-16 E2E-F1-17 시작 질문 사용자 · 2026-10-19 ⑫-11 에 단추 글자를 `치우기` 에서 `삭제` 로). 실행 불가 줄에도 있다 — 못 도는 시나리오가 먼저 지울 거리다.
되살리는 통로가 없어 상자에 그렇게 적고 첫 포커스는 `취소` 다. 지난 실행 기록 · 증적은 남는다. 조립 화면에는 두지 않는다 — 저장 안 한 변경과 엉킨다.
**「실행 불가」 · 「확인 필요」 줄에는 까닭이 늘 보인다** (2026-10-19 ⑫-11 · 점검 10.4) — 이름 아래에 한 줄씩 `N번 단계 케이스가 비활성입니다 · <tcId>` · `N번 단계에서 건너뛰게 둔 사전 단계를 이제 건너뛸 수 없습니다`(사라졌거나 건너뛸 수 없게 바뀐 절차 — §3.7 결정 8).
재료는 그 줄의 상세 `checks`(§7 `GET /api/scenarios/:id`)다 — 목록 응답은 참 · 거짓만 준다. 비활성 케이스가 없는데 실행 불가면 남는 까닭은 제한 시간 합 · 크기라 `단계 제한 시간 합이 상한을 넘거나 시나리오가 너무 커서 실행할 수 없습니다` 다 — 상한 숫자는 서버만 들고 화면은 옮겨 적지 않는다.
줄마다 상세를 한 번씩 더 읽는다(문제 있는 줄만). 목록 응답에 까닭을 싣는 것은 계약 변경이라 이번에 안 했다.
실행 불가 줄은 `실행` 자리에 `수정`(조립 화면으로)이 선다 — 까닭을 읽은 사람이 다음에 할 일이 그것이다.
줄의 `실행` · 마지막 결과를 누르면 결과 화면이 열리고 그 화면의 돌아가기는 `← E2E 시나리오` 다(아래 「실행 결과」 「돌아갈 곳」).

**단계 추가에 맥락 (2026-10-10 · 2026-10-11 시안 A 「묶음 접어 두기」 · PRD-F7-01).** 단계 추가 탭의 케이스를 기능 묶음으로 접고 정상 케이스를 먼저 보이고, 요구 문장까지 찾는다.
재료는 케이스 목록 응답(도메인/카탈로그 §7 · §8.1 「맥락」) 그대로다 — 서버 · 계약은 그대로. 모양은 [시안 A](https://claude.ai/artifact/A4FwvdPY1MaDCzwvF1mGAm), 규칙은 아래 「조립」의 팔레트 줄이다.
**다음 단계 추천 (2026-10-10 · 2026-10-11 시안 A 「목록 줄 그대로」 · PRD-F7-02).** 맨 뒤 케이스 단계가 머무는 화면에서 이어지는 화면에 닿는 정상 쪽 케이스를 「다음 단계 추천」 칸으로 케이스 목록 맨 위(찾기 칸 위)에 올린다(§3.7 「부품」). 고르는 것은 사람이다.
재료는 §7 `GET /api/scenarios/next-cases` 와 케이스 목록 응답이다. 모양은 [시안 A](https://claude.ai/artifact/Axy7DCmUtLYa394ttSxBme), 규칙은 아래 「조립」의 추천 칸 줄이다.

**조립** — 왼쪽에 부품을 순서대로 쌓고 오른쪽 패널의 `단계 추가` 탭(팔레트)에서 더한다. **팔레트에는 §3.7 부품 표의 부품이 전부 뜬다** —
「모킹 끄기」가 빠지면 모킹의 범위를 화면에서 못 정한다. 왼쪽 카드는 한 줄 요약이고, 누른 부품의 설정은 오른쪽 패널(`N번 설정` 탭)에서 고친다 (2026-10-06 사용자 B안).

- 케이스 부품을 누르면 `precondition` 문장이 읽을거리로 나오고, 그 아래 **「만들기」 절차 제목마다 체크**가 나온다 (§3.7 결정 4).
  R16 미적용 케이스는 체크 대신 안내 문장이다. 앞 부품이 같은 제목의 절차를 가졌으면 **`N번에서 이미 실행` 칩** (결정 5)
- **모킹이 걸린 구간은 왼쪽 세로선으로 칠한다.** 그 안의 API 부품에는 「모킹되지 않음」을 붙인다 (결정 6). 케이스 부품에 붙이던 같은 표시(`usesRequest`)는 결정 6 대로 뺐다(2026-10-06 PR #163)
- **케이스 부품마다 넘겨받기 스위치(`로그인 이어받기`)와 이어 주기 칸(`값 연결`)**이 있다 (결정 12). 이어 주기는 결정 12 표의 조립하는 사람 몫 넷이다.
  앞 부품은 번호로 고르고, 요청은 메서드와 주소 무늬로 적는다. 넘겨받기를 끄면 체크와 이어 주기 칸이 잠긴다
- **미확정 케이스 부품에는 「미확정」 칩**이 붙는다 (결정 12). 입력값 칸은 비워 두면 그 케이스의 저장값으로 돈다고 알린다 (§3.7 「부품 입력값을 채우는 순서」).
  **빈 칸에는 실제로 쓰일 값을 흐리게 보인다** (2026-10-19 ⑫-11 · 점검 10.6) — `저장값 사용 · 1042` · 저장값이 없는 계정 칸(kit `계정칸`)은 `대상 서버의 <역할> 계정 사용` · 그 밖은 `기본값 사용 · 1`, 비밀 칸은 `********`. 채우는 차례는 실행과 같다(저장값 → 대상 서버 계정 → 코드 기본값). 재료는 케이스 단건(도메인/카탈로그 §7)의 저장값과 스키마 기본값이다
- **값 연결의 요청은 가져올 단계가 부른 API 에서 고른다** (2026-10-19 ⑫-11 · 점검 10.5) — `요청 고르기` 에 서비스 지도(도메인/작성 §7 `GET /api/prd/apis`)에서 그 단계 케이스가 거친 API 가 뜨고, 고르면 메서드와 URL 패턴이 찬다 — 지도 주소 틀의 `:n` · `:id` 는 `*`, 앞은 `**`(호스트를 안 가린다), 끝은 물음표 꼬리 `{,?*}`(지도 주소는 물음표 뒤를 뗐다). 칸은 그대로 손으로 고칠 수 있다.
  지도에 그 케이스 기록이 없거나 조립하는 사람이 지도를 못 보면(`(작성, read)` 없음) 앞 판처럼 손으로 적는다. JSON 경로는 손으로 적는다 — 지도에 응답 모양이 없다
- **팔레트의 케이스는 정상 쪽을 위에 두고 나머지는 접어 둔다.** 펼치면 고를 수 있다 — **종류 · 기법으로 막지 않는다**.
  - **가르는 기준** (2026-10-11 PRD-F7-01) — PRD 를 쓰는 서비스에서 요구가 붙은 케이스는 종류(지도 ① 의 축)로 가른다. 경계 · 예외 요구만 덮으면 경계 · 예외 쪽, 그 밖(정상이나 UI 요구가 하나라도 있다)은 정상 쪽이다.
    그 밖의 케이스는 설계 기법으로 가른다(2026-10-06 사용자) — `상태 전이` 가 있거나 기법이 없으면 정상 쪽, `경계값 분석` · `동등 분할` · `결정 테이블` · `오류 추정` 만 있으면 나머지다
  - **PRD 를 쓰는 서비스**(기능 묶음이 붙은 케이스가 하나라도 있다 — 케이스 목록 응답의 `hasFeatures` 그대로라 디바이스를 바꿔도 안 갈린다) — 기능 묶음마다 머리를 세우고 처음엔 다 접어 둔다. 서비스를 바꾸면 다시 다 접는다. 머리는 묶음 이름과 `정상 N · 경계 · 예외 M` 이다.
    묶음 차례는 케이스 목록과 같은 PRD 차례이고 `기능 묶음 없음` 이 맨 뒤다. 묶음을 펴면 정상 쪽이 나오고 나머지는 `경계 · 예외 케이스 N` 으로 한 번 더 접혀 있다.
    줄마다 케이스 목록의 요구 줄(첫 요구 번호 · 요구 문장 · 외 N건, 없으면 `연결된 요구 없음`)이 붙는다. 번호에 고리를 달지 않는다 — 고리가 있으면 누를 때 저장 안 한 조립을 두고 「PRD 관리」로 떠나기 때문이다
  - **찾기 칸은 번호 · 이름 · 요구 번호 · 요구 문장에 맞는다.** PRD 를 쓰는 서비스는 찾는 동안 걸린 묶음과 그 안의 접힌 칸을 다 펴 두고 접지 못하게 한다. 안 걸린 묶음은 숨고 건수는 걸린 것만 센다
  - **PRD 를 안 쓰는 서비스**는 묶음 머리 · 요구 줄 없이 두 덩어리다. 위 덩어리 이름은 `업무 흐름 케이스`, 접는 덩어리는 `입력값 검증 케이스` 다
  접어 둔 케이스는 한 화면에 입력을 바꿔 찌르는 것이라 흐름을 앞으로 보내지 않는 일이 많지만, 정상 쪽 대표(가입 성공)나 조합 하나(쿠폰 결제)가 흐름을 잇기도 한다.
  기법 표시는 PR #158 이후 작성분과 작성 에이전트가 만든 케이스에만 있어서, 막으면 표시가 있느냐에 따라 고를 수 있는 부품이 갈린다. 기법 낱말은 kit `TECHNIQUES` 가 정본이다
- **다른 단계 단추(API 호출 · 모킹 켜기 · 모킹 끄기 · 대기)는 케이스 목록 아래 `다른 단계` 묶음이다** (2026-10-19 ⑫-11 · 점검 10.7) — 케이스를 고르는 일이 대부분이라 드물게 쓰는 단계가 맨 위를 차지하지 않게 한다. 앞 판은 탭 맨 위였다
- **다음 단계 추천 칸** (2026-10-11 PRD-F7-02) — 탭 맨 위, 찾기 칸 위에 선다(2026-10-19 ⑫-11 에 다른 단계 단추가 아래로 내려가 맨 위가 됐다). 머리는 `다음 단계 추천` 과 `N번 단계가 머무는 화면에서 이어지는 정상 케이스 M` 이다.
  줄은 팔레트 줄과 같고(번호 · 이름 · 미확정 칩 · 더하기 · PRD 를 쓰는 서비스면 요구 줄) 끝에 `이어지는 화면 /cart` 한 줄이 붙는다. 같은 케이스는 아래 묶음에도 그대로 있다
  - **기준은 맨 뒤 케이스 단계다** — 뒤에 API 호출 · 모킹 · 대기가 붙어도 브라우저 화면은 그대로라 같은 추천이 뜬다(2026-10-11 시작 질문 — 처음 적은 「마지막 단계가 케이스면」을 바꿨다)
  - **정상 쪽만, 팔레트와 같은 규칙으로** — 위 「가르는 기준」 그대로라 PRD 를 안 쓰는 서비스도 크롤러 화면 연결만 있으면 뜬다. 서버는 이어지는 화면에 닿는 케이스를 다 주고 화면이 거른다.
    디바이스에서 안 도는 케이스는 빼고, 찾는 동안은 찾기에 걸린 것만 남긴다. 차례는 팔레트 목록 차례다(섞은 앱 · 게임 애플리케이션 케이스는 `android` 로 거른다 — 결정 16 · 아래 「같은 프로젝트의 다른 애플리케이션 케이스를 섞는다」)
  - **머리 · 바닥 메뉴 링크는 서버가 뺀다** (2026-10-12 PRD-F9-21) — 같은 상태 화면 절반 넘게에 같은 글자로 있는 링크로 가는 곳은 추천에 안 든다. 규칙은 §7 `GET /api/scenarios/next-cases`
  - **케이스 단계가 없으면 첫 단계 후보를 그린다** (2026-10-23 결정 15) — 머리는 `첫 단계 추천` 과 `첫 화면에서 갈 수 있는 정상 케이스 M` 이고 줄 모양 · 거르기는 위와 같다. 재료는 §7 `next-cases` 에서 `after` 를 뺀 꼴이다
  - **안 그릴 때** — 추천이 비었거나(크롤러가 그 화면을 안 훑었거나 · 그 화면에서 나간 길이 머리 · 바닥 메뉴뿐이거나 · 이어지는 정상 케이스가 없다), `케이스 바꾸기` 중이면 칸을 안 그린다.
    추천을 못 불러오면 그 자리에 오류 글이 뜨고 아래 목록은 그대로 쓴다
- **같은 프로젝트의 다른 애플리케이션 케이스를 섞는다** (2026-10-20 E2E-F1-27 · 시안 A [여기](https://claude.ai/artifact/CV31Sqb1QPEb6GcrSxcymP) · 결정 13) —
  - 단계 추가 탭 맨 위, 추천 칸 위에 **애플리케이션 칩 줄**이 선다. 그 시나리오 서비스와 같은 프로젝트의 활성 애플리케이션이 칩 하나씩이다(애플리케이션 줄 · 휴대폰 위 줄 고르개와 같은 목록). 한 번에 한 곳의 케이스만 목록에 뜬다.
    처음 열면 시나리오 서비스(시작 애플리케이션) 칩이 골라져 있어 한 애플리케이션만 쓰는 사람은 지금과 똑같이 쓴다. 프로젝트에 애플리케이션이 하나뿐이면 칩 줄을 안 그린다
  - **고른 칩의 케이스는 그 단계가 도는 디바이스로 거른다** (2026-10-29 E2E-F3-04 · [시안 A](https://claude.ai/artifact/Dbh4SDgVHHKHnJNtrJ3KND) · §3.7 결정 16) — Android 앱 · 게임 애플리케이션 칩은 시나리오 디바이스와 상관없이 `android` 케이스만, `android` 시나리오의 웹 애플리케이션 칩은 `PC`(desktop) 케이스만 뜬다. 서버 조립 검사와 같은 판정이다.
    시나리오 디바이스와 다르게 돌 때만 칩 줄 아래 한 줄이 붙는다 — `앱 단계는 폰에서 돕니다. Android 앱 케이스만 보입니다` · `웹 단계는 PC 화면으로 돕니다. PC 에서 도는 케이스만 보입니다`. 마법사 「단계」의 칩 줄도 같다
  - **다음 단계 추천은 맨 뒤 케이스 단계와 같은 애플리케이션 칩일 때만 뜬다** — 추천의 재료(화면 연결)는 애플리케이션 하나 안의 것이다(§7 `next-cases`). 다른 애플리케이션 칩이면 추천 칸을 안 그린다
  - **왼쪽 단계 카드에 애플리케이션 이름표**(글자 칩)가 붙는다 — 서비스 색은 화면에 쓰지 않는 규칙이라(공통/5-화면공통 §8) 색 없이 글자로만 가른다. 이웃한 케이스 · API 단계의 애플리케이션이 바뀌는 자리에는 구분선 `여기서 애플리케이션이 바뀝니다` 가 그려진다. 한 애플리케이션만 쓰는 시나리오에는 이름표도 구분선도 없다
  - **API 호출 단계의 설정 패널**에 `부를 애플리케이션` 고르개가 하나 는다(§3.7 결정 13). 기본은 시작 애플리케이션이고, 시작 애플리케이션을 고르면 `service` 칸을 뺀다. 애플리케이션이 하나뿐인 프로젝트에서는 안 그린다
- **API 호출 단계 설정 패널의 `API 인증` · `값 주입` · `응답 값 확인`** (2026-10-21 API-F1-10 · §3.7 결정 14 · 시작 질문의 글자 그림 승인) — 기대 응답 코드 아래에 차례로 선다.
  - `API 인증` 고르개는 `인증 없이` 와 부를 애플리케이션의 대상 서버들에 있는 인증 이름(겹친 것은 하나로 — `/api/auth/me` 의 `envs[].apiAuthNames`)이다. 저장된 이름이 지금 설정에 없어도 고른 채 보인다. 이름이 하나도 없으면 `이 애플리케이션 대상 서버에 등록한 API 인증이 없습니다`
  - `값 주입` 줄은 `이름` 칸 + 케이스 단계 값 주입과 같은 `가져올 단계` · 메서드 · `URL 패턴` · `JSON 경로` 다. 가져올 단계 목록에는 앞의 케이스 단계와 API 호출 단계(`<메서드> <경로>`)가 든다. `+ 값 주입 추가` 는 앞의 케이스 · API 호출 단계 가운데 가장 가까운 것 · `POST` · `**` 로 빈 줄을 만든다(대기 · 모킹 단계는 건너뛴다)
  - `응답 값 확인` 줄은 `JSON 경로` · `기대 값` 이다. 기대 값은 JSON 으로 읽히면 그 값(`3` 은 숫자, `"3"` 은 글자), 아니면 적은 글자 그대로다 — 「주문이 완료되었습니다」를 따옴표 없이 적게
  - 비운 칸은 단계에서 뺀다(빈 목록을 저장하지 않는다). 읽기만 하는 사람에게는 더하기 · 삭제 단추가 없다
  - **조립 화면의 대상 서버 고르개**는 시나리오에 든 애플리케이션 모두에 있는 이름만 고르게 한다. 어느 하나에 없는 이름은 막힌 채 보이고 `<이름> · <접두사>에 없음` 이 붙는다. 이미 고른 이름이 단계를 더해 막히면 고르지 않은 것으로 돌아가 시험 실행 · 실행이 `대상 서버를 먼저 고릅니다` 를 낸다.
    저장 안 한 초안의 단계로 헤아린다. 목록의 `실행` 과 결과의 `다시 실행` 은 이름을 미리 막지 않고 서버가 거절하는 문장(§7 `ENV_NOT_FOUND`)을 그대로 보인다 — 진짜 막는 곳은 서버다
  - **「N번에서 이미 실행」 칩은 같은 애플리케이션 단계끼리만 센다** — 출처가 다르면 쿠키 · localStorage 가 안 넘어가 앞 단계의 로그인을 믿을 수 없다. 값 연결의 요청 고르기가 쓰는 서비스 지도도 그 단계 애플리케이션 것이다
  - 모킹 단계를 설정할 때 시작 애플리케이션 밖의 단계가 있고 URL 패턴이 `/` 로 시작하면 칸 아래에 `시작 애플리케이션 밖의 단계가 섞인 시나리오는 / 로 시작하는 URL 패턴을 쓸 수 없습니다. **/ 로 시작하거나 주소 전체를 적습니다` 가 붙고 저장 · 실행이 막힌다(서버 사유와 같은 뜻)
- 저장은 사람이 누른다. 안 누른 변경이 있으면 머리에 `저장 안 된 변경 있음` 이 뜨고 자리를 뜨려 하면 한 번 묻는다 (결정 7)
- **머리에 정식 실행이 있다** (2026-10-19 ⑫-11 · 점검 10.1) — 대상 서버 고르개 옆에 `시험 실행`(기록 · 증적이 안 남는다고 단추에 마우스를 올리면 뜨는 글로 알린다) · `저장` · `실행` 차례다.
  저장 안 한 변경이 있거나 새 시나리오면 `실행` 이 `저장하고 실행` 이 되어 한 번에 저장 → §7 실행 요청 → 결과 화면으로 간다 — 실행은 저장한 최신 버전으로만 돌기 때문이다(§7 「실행 요청」).
  **앱 · 게임 단계가 하나라도 있으면 머리 아래 실행 위치 안내가 선다** (2026-10-29 E2E-F3-04 · [시안 A](https://claude.ai/artifact/Dbh4SDgVHHKHnJNtrJ3KND) · §3.7 결정 16) — `실행 위치 · 디바이스 팜` 과 `시나리오 하나 동안 빈 폰을 한 번 잡고 다 돌면 놓습니다. 화면 영상과 logcat 은 통과하지 못한 실행에 남습니다`,
  시험 실행이 있는 자리(조립 화면 · 마법사 「시험 실행」)에는 `시험 실행은 내 컴퓨터 테스트 실행기가 켜져 있으면 거기 꽂은 폰에서, 꺼져 있으면 디바이스 팜에서 돕니다` 를 더한다. 정식 실행은 늘 팜이라 고르개가 아니다(케이스 실행 창과 같은 꼴 — 도메인/실행 §8.2 「실행 위치」).
  목록 화면은 그 애플리케이션이 Android 앱 · 게임이면 대상 서버 고르개 옆에 앞의 두 줄만 늘 띄운다. 팜이 없는 서버의 409 `FARM_OFF` · `DEVICE_BUSY` 는 다른 실행 오류처럼 그 자리 한 줄이다
  저장이 거절되면 저장 때와 같은 문장이 뜨고 실행하지 않는다. 새 시나리오를 저장한 뒤 실행만 실패하면 저장된 주소(`#/scenarios/:id`)로 옮겨 그 실패 문장을 보인다 — 새 주소에 남으면 다음 저장이 같은 시나리오를 또 만든다.
  앞 판은 기록이 안 남는 시험 실행만 있어 증적을 받으려면 목록으로 나가 서버를 다시 골라야 했다
- **단계 카드 ✕ 는 한 번 묻는다** (2026-10-19 ⑫-11 · 점검 10.7) — `N번 단계를 삭제할까요?` · `이 단계의 설정도 같이 사라집니다`. 버튼은 `취소` · `삭제`
- **주소 `?step=N` 은 그 단계 설정을 연 채로 연다** (2026-10-19 ⑫-11) — 실패 결과의 `N번 단계 수정` 이 쓴다. 범위 밖 번호는 무시하고 1번을 연다
- **조립 화면의 서비스는 열 때 정해지고 끝까지 간다** (2026-10-16 E2E-F1-23 · PR #165 게이트 2 사용자) — 기존 시나리오는 그 시나리오의 서비스, 새 시나리오는 열 때 서비스 고르개에서 고른 서비스다. 저장 · 권한 판정은 그 값을 쓴다. 팔레트는 처음에 그 서비스의 칩이 골라져 있고 대상 서버는 섞인 애플리케이션과 같이 거른다(아래 「같은 프로젝트의 다른 애플리케이션 케이스를 섞는다」).
  조립 중 고르개를 다른 서비스로 바꾸면 상자로 묻지 않고 머리 아래에 `<서비스> 서비스의 시나리오입니다` 한 줄만 뜬다 — 초안을 잃지도 다른 서비스로 저장하지도 않아 물을 거리가 없다. 위 「한 번 묻는다」 상자는 주소를 옮길 때만 뜬다.
  예외 하나 — `#/scenarios/new`(마법사) · `#/scenarios/new/build`(빈 조립 화면, 2026-10-23 결정 15) 는 목록 자리처럼 고르개 서비스의 실행 칸으로 자리를 본다(`route.ts` 기능자리). 그래서 실행 칸이 `none` 인 서비스로 바꾸면 집으로 옮기고, 저장 안 한 변경이 있으면 그 이동에 위 상자가 뜬다(공통/5-화면공통 §8 「`none` 인 자리」). `#/scenarios/:id` 는 한 건 주소라 옮기지 않는다.
  게이트 1 계획은 새 시나리오 중 고르개를 바꾸면 같은 상자로 묻기였다 — 구현 중 열 때의 서비스를 고정하면서 뺐다
- 버전 이력은 오른쪽 패널의 넷째 탭 `변경 이력` 에서 연다(2026-10-19 ⑫-11 에 머리의 같은 이름 단추를 뺐다 — 같은 일을 하는 단추가 둘이었다). 옛 버전을 보고 `이 버전으로 되돌리기` 를 누를 수 있다 — 새 버전이 생긴다. 저장 안 된 변경이 있으면 되돌리지 않는다
- 케이스를 못 찾는 단계(비활성 · 사라짐 — 결정 8)는 설정 탭에서 `케이스 바꾸기` 로 다른 케이스를 고른다. 그 단계의 준비 · 입력값 설정은 처음부터 다시 한다
- 좁은 창에서는 두 칸이 각자 세로로 구른다. 왼쪽 칸은 280px 아래로 줄지 않고 요약은 말줄임, 조립 영역이 640px 보다 좁으면 그 안에서만 가로로 구른다 (2026-10-06 게이트 1 사용자)

**마법사** (2026-10-23 결정 15 · 진행판 E2E-F2-04 · 05) — 새 시나리오를 단계마다 안내하며 만든다. **모양은 [시안](https://claude.ai/artifact/VmXonHk64n9dzcErhsTVZV)이 정본이다**(2026-10-23 사용자 승인).
짜임은 설정 마법사 C 시안([여기](https://claude.ai/artifact/BHb1EtqU8Gx2FQinHMPnaA))을 따른다 — 화면 전체를 쓰고 왼쪽에 세로 단계 띠, 지금 단계 아래에 안내 칸이 선다. 단계와 넘어가는 조건은 §3.7 결정 15 표가 정본이다.

- **자리 · 주소** — `#/scenarios/new` 가 마법사다. 빈 조립 화면은 `#/scenarios/new/build` 로 옮긴다. 머리에 `E2E 시나리오 › 새 시나리오` · `조립 화면으로` · `나가기` 가 선다.
  `조립 화면으로` 는 지금 초안(애플리케이션 · 디바이스 · 단계 · 값 연결 · 입력값 · 이름)을 들고 빈 조립 화면으로 옮긴다 — 저장하지 않은 초안이라 메모리로 넘긴다. 저장 안 한 내용이 있으면 `나가기` · 주소 옮기기는 조립 화면과 같은 상자로 한 번 묻는다
- **왼쪽 단계 띠** — 번호와 단계 이름. 지난 단계는 체크 표시이고 누르면 그 단계로 돌아간다. 뒤 단계는 못 누른다. 「직접 고르기」면 「AI 추천」 단계가 띠에서 빠진다.
  **지금 단계 아래 안내 칸**(사용자가 말한 「E2E 생성 가이드」 자리)이 그 단계의 그림 한 줄 · 문장 두세 개 · 꼬리표 하나를 보인다 — 글은 아래 「안내 칸 글」 표다
- **본문 머리** — `N / M · <단계 이름>`, 제목 한 줄 · 설명 한 줄. 바닥에 `이전` · `다음`, 마지막 단계는 `저장` · `저장하고 실행` 이다.
  넘어가는 조건이 안 맞으면 `다음` 을 눌렀을 때 바닥에 막는 까닭 한 줄이 뜬다 — 단추를 미리 잠그지 않는다(무엇이 모자라는지 누르기 전에는 안 보인다)
- **시작 방법** — 카드 둘. `AI 추천으로 시작`(`AI 가 테스트와 요구사항을 읽고 흐름 후보를 골라 줍니다` · `후보 2~3개 · 몇 분 걸립니다` · `무엇부터 이어야 할지 모를 때 고릅니다`) ·
  `직접 고르기`(`첫 단계부터 하나씩 이어 붙입니다` · `이어지는 화면을 따라 다음 단계를 추천합니다` · `확인할 흐름이 이미 정해져 있을 때 고릅니다`).
  그 아래 `애플리케이션` 고르개(같은 프로젝트의 활성 애플리케이션, 처음엔 왼쪽 줄에서 고른 것)와 `다른 애플리케이션의 케이스도 단계에서 섞을 수 있습니다`, `디바이스` 칩(`PC` · `모바일`)과 `그 디바이스에서 도는 케이스만 단계로 고를 수 있습니다`.
  Android 앱 · 게임 애플리케이션이면 칩은 `Android 앱` 하나이고 안내는 `Android 앱 애플리케이션은 폰 한 대에서 돌립니다. 단계 사이에 앱을 다시 켜지 않고, 앞 단계가 끝난 화면에서 이어 갑니다` 다(§3.7 결정 16 · 2026-10-29 E2E-F3-04 [시안 A](https://claude.ai/artifact/Dbh4SDgVHHKHnJNtrJ3KND)). 웹 단계 섞기 안내는 아래 「단계」의 칩 줄 한 줄이다.
  애플리케이션을 바꿔 그 디바이스가 새 애플리케이션 칩에 없으면 새 칩의 첫 값(`PC` 또는 `Android 앱`)으로 바꾼다. 조립 화면 머리의 `디바이스` 고르개도 같은 목록이고 값이 하나면 잠근다. 그 목록에 없는 값으로 저장된 옛 시나리오(앱 애플리케이션인데 `PC`)는 그 값도 고르개에 보여 바꿀 수 있게 하고, `이 애플리케이션은 디바이스 「<칩들>」로만 돌립니다. 디바이스를 바꿔 저장합니다` 를 띄운다 — 서버가 그 값으로는 저장 · 실행을 거절한다.
  애플리케이션은 조립 화면처럼 열 때 정한 것이 시나리오 서비스다 — 마법사 안에서 바꾸면 단계 · 추천을 비운다
- **AI 추천** — 처음 들어오면 §7 `flow-suggestions` 를 맡기고 3초마다 결과를 묻는다(성능 마법사의 `usePerfJob` 과 같은 꼴). 위에 `확인하고 싶은 흐름` 칸(선택 · `예: 쿠폰을 쓰고 결제까지`)과 `다시 추천받기` — 칸 아래 `적어 두면 그 흐름에 가까운 후보를 먼저 고릅니다`.
  기다리는 동안 `테스트 N건 · 화면 연결 M건을 읽는 중입니다` · `작성 에이전트가 처리합니다. 보통 몇 분 걸립니다`.
  이미 받은 결과가 있으면 「이전」으로 돌아와도 다시 맡기지 않고 그 후보를 보인다 — 새로 받으려면 `다시 추천받기` 를 누른다. 시작 방법 · 애플리케이션 · 디바이스를 바꾸면 결과를 버린다. 단계는 후보를 고를 때만 바뀐다 — 돌아와서 보기만 하면 고친 단계가 그대로다.
  후보 카드는 이름 · 이유 · 단계 흐름(칩 줄) · `단계 N개 · 값 연결 M곳 · 요구 K건` 이다. 고르면 단계가 그 후보로 바뀌고, 이름을 아직 손대지 않았으면 시나리오 이름이 후보 이름으로 찬다.
  503 `AGENT_OFFLINE` 이면 `AI 추천을 지금 쓸 수 없습니다` 와 `직접 고르기로 바꾸기` 단추, 일이 `FAILED` 면 그 사유와 `다시 추천받기` · `직접 고르기로 바꾸기` 가 선다
- **단계** — 왼쪽 `지금 순서 N단계`(줄마다 번호 · 이름 · 번호와 머무는 화면 · `N번 위로` · `N번 아래로` · `N번 삭제`), 오른쪽 위에서부터 추천 칸(케이스 단계가 없으면 `첫 단계 추천`, 있으면 `다음 단계 추천 N번 「<이름>」 다음 · 이어지는 화면 <화면>`) ·
  `케이스 찾기`(`번호나 이름으로 찾기 · 예: 쿠폰, 197`) · `다른 단계`(`+ API 호출` · `+ 모킹 켜기` · `+ 대기`). 줄의 더하기는 `+ 넣기` 다. 단계가 없으면 `아직 단계가 없습니다. 아래 「첫 단계 추천」에서 넣습니다`, 추천이 비면 `이어지는 화면 기록이 없습니다. 「케이스 찾기」로 고릅니다`.
  케이스 찾기 · 추천 거르기 규칙은 조립 화면 팔레트와 같다. API 호출 · 모킹 · 대기의 설정은 조립 화면의 설정 패널과 같은 칸을 단계 줄 아래에 편다
- **값 연결** — 들어올 때마다 §7 `link-suggestions` 로 제안을 다시 받는다. 이미 확인했거나 고친 값 연결 · AI 후보에서 온 값 연결은 같은 두 케이스 · 같은 종류면 그대로 둔다.
  위에서부터 `로그인 이어받기` · `값 연결 N곳 찾음` · `입력값` 이다.
  - `로그인 이어받기` 는 켜고 끄는 단추 하나다(기본 켬). 켜면 각 케이스 단계의 사전 단계 가운데 같은 애플리케이션 앞 단계에서 같은 제목으로 이미 실행한 것(조립 화면 `N번에서 이미 실행` 칩과 같은 계산 — 결정 5)을 건너뛰게 체크해 둔다.
    그런 사전 단계가 있으면 `N번 「<이름>」부터 끝까지 같은 계정으로 이어 갑니다. 뒤 단계의 로그인 사전 단계는 건너뜁니다` 가 붙는다. 끄면 다 실행한다 — 단계마다 다르게 고르려면 조립 화면에서 한다
  - 값 연결 카드는 `<받는 번호>번 <이름> ← <가져올 번호>번 <이름>` 과 제안의 한 줄(`why`), 꼬리 `서비스 지도에서 찾았습니다 · 종류 「<값 연결 종류>」`(JSON 경로가 AI 짐작이면 `JSON 경로는 AI 가 짐작했습니다` 를 더한다)이다.
    단추는 `맞아요`(누르면 칩 `확인함`, 다시 누르면 `확인 취소`) · `직접 수정`(조립 화면과 같은 칸 — 종류 · 가져올 단계 · 메서드 · URL 패턴 · JSON 경로 · 수정 주소와 `수정 주소의 {} 자리에 가져온 값이 들어갑니다`) · `삭제`.
    확인하기 전에는 `확인 필요` 칩이다. JSON 경로가 비었으면 칸이 펴진 채로 `앞 단계 응답에서 꺼낼 값의 경로를 적습니다 · 예: id, data.id` 가, 값 주입의 입력값 칸이 비었으면 `값을 넣을 입력값 칸을 고릅니다` 가 붙는다.
    제안이 없으면 `넘길 값이 없습니다. 단계끼리 값을 주고받지 않는 흐름입니다`. 제안 밖의 값 연결은 저장한 뒤 조립 화면에서 더한다

  - 확인하지 않은 제안이 남았으면 바닥에 `확인하지 않은 값 연결이 N곳 있습니다` 가 뜬다 — 막지는 않는다

하나라도 있으면 실행 머리에 「미확정」 꼬리표가 뜬다 (결정 12 · 2026-10-11 부터 부품과 같은 글). 비밀 칸에 꽂은 값은 `********` 다(공통/2-명세선언 §4.1). 증적(도메인/리포팅 §8.4)과 같은 표시를 한다.
**앱 · 게임 단계가 있는 실행은 폰 한 벌을 적는다** (2026-10-29 E2E-F3-04 · [시안 A](https://claude.ai/artifact/Dbh4SDgVHHKHnJNtrJ3KND) 사용자 · §3.7 결정 16 「결과」) — 정보 칸 맨 끝에 `폰` · `<모델> · Android <판>`(§7 `device`, 못 읽은 칸은 뺀다 · 둘 다 없으면 줄이 없다),
`단계별 결과` 아래에 `디바이스 팜 기록` 칸(§7 `farm` — 비면 칸이 없다)을 둔다. 칸 안은 앱 항목 실패 카드의 팜 기록과 같은 조각이다 — 화면 영상(누르기 전에는 안 받는다) · `<파일> 받기 (<크기>)`(logcat · 게임 실패 파일 `game-tree.txt` · `game-errors.txt`), 원본은 §7 `GET /api/runs/:runId/scenario/farm/:name`.
영상은 시나리오 전체를 찍은 것이라 실패한 단계 안이 아니라 한 칸에 둔다(시안 B 를 안 고른 까닭). 앱 단계 스크린샷은 웹 단계와 같다 — 실패한 절차의 `실패 화면 보기` 가 폰 화면을 연다. 시험 실행 결과에는 팜 기록이 없다(통과하지 못한 정식 실행만 받는다)
**실패하면 맨 위에 다음 할 일 줄이 선다** (2026-10-19 ⑫-11 · 점검 10.2 · 사용자가 고른 추천안) — `N번 단계 「<케이스 이름>」에서 실패했습니다 · <실패 유형> · <한 줄>`(유형 · 한 줄은 §7 `parts[].failure`) 과 `N번 단계 수정`(조립 화면 `?step=N`) · `<서버>에서 다시 실행`.
멈춘 단계는 실패(FAIL)인 첫 단계, 없으면 그 단계 탓으로 멈춘 판정 없음(NA) 첫 단계다(러너 거절 · 제한 시간 초과 — 러너 거절은 전부 NA 라 1번이 나온다). 앞 단계 때문에 안 돈 단계(`NOT_RUN`)와 서버 재시작으로 닫힌 단계(`ABORTED`)는 고칠 거리가 아니라 줄을 세우지 않는다. 통과한 결과는 이 줄 없이 머리에 `<서버>에서 다시 실행` 만 있다. 두 단추는 `(실행, write)` 일 때만 선다.
다시 실행은 §7 실행 요청을 그 결과의 대상 서버로 다시 보낸다 — 시나리오의 최신 버전으로 돈다(결과의 버전이 아니다).
**돌아갈 곳** — 결과 주소의 `from` 이 들어온 곳이다. 목록에서 오면 `← E2E 시나리오`, 조립 화면에서 실행하면 `← SC-N 시나리오`, 그 밖(알림 · 붙여 둔 주소)은 앞 판대로 `← 실행 기록 › E2E` 다. 실행 기록 › E2E 의 오른쪽 결과 칸 안에서는 목록이 바로 옆이라 이 고리가 없고, 다시 실행해도 주소를 옮기지 않고 새 실행을 그 칸에 연다(2026-10-20 ⑬-5 · 도메인/실행 §8.7).
**E2E 증적은 여기서만 만든다 — 증적 칸은 케이스 결과와 같다** (2026-10-16 E2E-F1-07 시작 질문 사용자) — 결과 머리에 `리포트 생성` 메뉴(형식마다 한 줄 — 2026-10-20 ⑬-5 에 형식별 단추 셋에서 바꿨다), 그 아래 만든 문서 목록.
꼴과 상태는 도메인/리포팅 §8.4 「증적 문서 만들기·받기」가 정본이다. 앞 판의 `E2E 증적 받기` 한 버튼을 형식 버튼으로 바꿨다(그 뒤 2026-10-20 ⑬-5 에 `리포트 생성` 메뉴 하나로) — 같은 칸을 써야 형식마다 「만드는 중」 · 실패를 그린다.
버튼은 첫 케이스 단계의 서비스에서 `(실행, write)` 일 때만 선다 — 시나리오 응답 머리에 서비스 칸이 없어 케이스 결과(tcId 접두사)와 같은 규칙으로 가른다. 결과 화면은 `#/runs/:runId` 그대로이고 `kind` 로 그리는 모양이 갈린다.

**실행 기록 하위 메뉴** — 실행 기록이 사이드바 하위 메뉴(`기능 테스트` · `UI 테스트` · `E2E`, 2026-10-20 순서를 기능 먼저로 바꿨다)로 갈린다(2026-10-02 탭에서 옮김). `E2E` 하위는 이 화면과 함께 넣었다(진행판 E2E-F1-06). 정본은 도메인/실행 §8.7. API 애플리케이션의 `실행 기록` 도 하위가 `기능 테스트` · `E2E` 둘이다(2026-10-29 — 2026-10-28 의 `API` › `E2E 실행 기록` 을 되돌렸다).
