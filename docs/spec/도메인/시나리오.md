### 3.7 Scenario — 케이스를 이어 돌린다 (2026-09-28 신설)

- **책임**: 시나리오 정의를 버전으로 쌓고, 실행을 만들어 러너에 넘기고, 부품마다 결과를 영속화한다
- **애그리거트 루트**: `Scenario` (식별자 `id`, 화면 번호 `SC-{id}`) → `ScenarioVersion[]` → 부품 목록.
  실행 결과는 `TestRun`(구분 `SCENARIO`) → `ScenarioRunPart[]` → `Step[]`

#### 시나리오는 케이스가 아니다 (결정 1)

케이스 목록과 따로 둔다. 케이스는 요구사항의 도장이고 시나리오는 이음매를 본다.
섞으면 검수 서류에서 둘을 구분할 수 없고, 실행 시간이 달라 도는 범위도 달라진다.
**케이스 파일은 한 글자도 안 바뀐다** — 러너가 불러 쓸 뿐이다 (결정 3).

#### 부품 — 이 표가 정본이다 (결정 2)

다른 절·코드·화면에서 부품을 나열할 때는 이 표를 가리킨다. **개수를 문장에 적지 않는다** (CLAUDE.md §2.7 ⑤).
코드 값(`kind`)은 [공통/3-공유계약.md](../공통/3-공유계약.md) §5.1 `ScenarioPart` 가 정본이다.

| 부품 | `kind` | 무엇 | 언제 끝나나 |
|---|---|---|---|
| 케이스 | `case` | 이미 있는 케이스를 고른다. 입력값·기대값을 부품마다 따로 준다 | 그 케이스가 끝나면 |
| API 호출 | `api` | 계정 상태를 뒷문으로 심는다. 대상 주소 기준 상대 경로 · 메서드 · 본문 · 기대 응답 코드 | 한 번 부르고 끝 |
| 모킹 | `mock` | 주소 무늬에 맞는 요청의 응답을 가짜로 바꿔친다 | **끄기 전까지 계속** (아래 「모킹」) |
| 모킹 끄기 | `unmock` | 같은 무늬로 걸어 둔 모킹을 푼다 | 즉시 |
| 대기 | `wait` | 사이에 끼운다. 60초까지 | 그 시간이 지나면 |

**사람이 조립한다.** 「어떤 흐름이 중요한가」는 기획서에 안 적힌 위험 판단이라 도구가 후보를 내지 않는다.
**시나리오 하나는 디바이스 하나다** — 한 브라우저로 이어 도는 것이 요점이라 `platform` 을 시나리오(의 버전)가 갖는다.
**디바이스는 버전마다 적는다** (2026-09-28 사용자) — 디바이스를 바꾼 저장도 새 버전이다. 그래야 옛 실행이 어느 디바이스로 돌았는지 남고, 옛 버전으로 되돌리면 디바이스도 돌아온다.
그 디바이스를 선언하지 않은 케이스는 부품으로 못 고른다. 조립 뒤에 케이스가 그 디바이스를 빼면 **실행 때 그 부품이 실패로 멈춘다** (2026-09-28 사용자 — 틀린 조립은 언제나 빨강이다).
**API 호출 부품은 브라우저 로그인(쿠키)을 같이 쓴다** (2026-09-28 사용자) — 한 브라우저로 이어 도는 흐름이라 앞 부품이 로그인한 사람으로 부른다. 러너 쪽 모양은 [러너.md](러너.md) §5.2

#### 한 브라우저에서 순서대로 몬다 (결정 3)

러너가 조립 목록을 받아 **Playwright 프로세스 하나, `test()` 하나** 안에서 케이스 본체를 차례로 꺼내 돌린다.
**시나리오마다 테스트 파일을 만들지 않는다** (2026-09-28 — 설계서 「착수 전에 답이 있어야 하는 것」 ①).
러너 이미지 안의 고정 파일 하나가 조립 목록을 받아 케이스 파일을 불러 쓴다. 그래서 읽기 전용 `/tests` 에 쓸 자리가 필요 없다.
러너 쪽 모양은 [러너.md](러너.md) §5.2 가 정본이다.

- **절차 순번은 시나리오 전체에서 이어진다.** 부품마다 순번이 1부터 다시 시작하면 스크린샷이 서로를 덮는다. 부품마다 실패 표시는 새로 세우고 순번만 넘겨받는다(공통/3-공유계약 §5.1)
- **입력값은 부품마다 따로 해석한다.** 같은 케이스를 두 번 써도 값이 다를 수 있다

#### 준비를 사람이 체크로 끈다 (결정 4)

케이스는 단독으로도 돌아야 해서 자기 준비를 갖고 있다. 조립하면 앞 부품이 이미 세운 준비와 겹친다.
사람이 조립 화면에서 **건너뛸 준비의 체크를 푼다.** 기본값은 「실행」(체크가 켜진 채)이다.

- **건너뛸 수 있는 것은 R16 의 「만들기」 절차뿐이다.** 「확인」 절차는 못 끈다. 그래서 잘못 풀면
  바로 다음 「확인」이 `blocker` 로 그 자리에서 멈춘다 — 틀린 건너뛰기는 **언제나 빨강**이다.
  케이스를 그렇게 쓰는 규칙은 `tpx-cases` R16(`.claude/skills/tpx-cases/references/5-writing.md`)이고, **왜 가르는지는 이 절이 정본이다**
  (R16 이 가리키는 설계서 결정 4 는 여기로 옮겨졌다)
- **「만들기」 절차는 소스에서 판별한다** (2026-09-28 — 「착수 전」 ②). **판정이 하나도 없는 `test.step` 바로 뒤에
  `blocker` 판정을 가진 `test.step` 이 오면** 앞 것이 「만들기」다. 케이스 선언에 표시를 새로 달지 않는다.
  판별은 카탈로그가 소스를 읽는 자리 옆에 있다(`apps/admin/src/catalog/steps.ts`, 2026-09-29).
  **애매하면 「만들기」로 치지 않는다** (2026-09-29 게이트 1 사용자 · 품은 절차는 구현 중에 찾아 게이트 2 에서 확인) — 반복문·도우미 함수 안의 절차(한 제목이 여러 번 돈다) ·
  본문이 맨 함수를 부르는 절차(그 안의 판정이 소스에서 안 보인다) · 안에 다른 절차를 품은 절차(건너뛰면 안쪽 판정까지 사라진다) ·
  `blocker` 를 객체 리터럴이 아닌 값으로 넘긴 다음 절차. 틀려도 건너뛰기를 못 할 뿐이다
- **이 모양이 하나도 없는 케이스(R16 미적용)는 체크를 못 끈다.** 조립 화면이 체크를 누를 수 없게 두고
  `이 케이스는 준비가 갈려 있지 않아 건너뛸 수 없습니다` 를 띄운다. 서버도 그런 건너뛰기를 400 으로 거절한다 —
  옛 케이스는 첫 절차에 조작과 `blocker` 판정이 한 덩어리라, 건너뛰면 **막는 판정까지 같이 건너뛴다**
- **체크 한 줄은 「만들기」 절차의 제목이다** (2026-09-28 사용자). `precondition` 문장이 아니다 —
  문장과 절차를 잇는 칸이 케이스 선언에 없고, 만들면 모든 케이스를 고쳐야 한다. `precondition` 은 부품 머리에 읽을거리로만 편다
- **그래서 절차 제목이 열쇠다.** 러너는 건너뛸 절차를 **제목으로** 받는다. 한 케이스 안에서 제목이 겹치면
  하나를 지목하다 둘을 건너뛴다 — 그래서 K12(한 케이스 안에서 절차 제목이 서로 다르다)를 둔다 ([공통/2-명세선언.md](../공통/2-명세선언.md) §4)
- **건너뛴 절차도 결과에 남는다** — `StepResult.skipped` 가 참인 줄로. 증적이 「준비 실행 건너뜀 — N번에서 세움」을 적는 근거다

**러너가 「확인부터 해 보고 정한다」는 길은 접었다** (설계서 결정 4 인용 상자). 탐침 실행을 증적에 찍을지 또 정해야 하고,
건너뛰지 못하는 경우 확인이 두 번 돌아 느려진다. **전제를 글자로 비교해 자동으로 건너뛰는 길은 금지다** (설계서 §7).

#### 순서가 틀리면 도구가 경고한다 (결정 5)

`[결제] → [로그인]` 처럼 앞 부품이 뒤 부품의 준비를 이미 세웠으면 조립 화면이 **「N번에서 이미 함」 칩**을 붙인다.
**경고지 금지가 아니다** — 도구는 표시하고 사람이 누른다. 무엇을 「세웠다」로 보는지는 **같은 절차 제목**이 앞 부품에 있는가로 본다.
맞추지 못해도 조립은 된다 — 칩이 안 뜰 뿐이다.

#### 모킹은 켜면 시나리오 끝까지 유효하다 (결정 6)

끄려면 「모킹 끄기」 부품을 중간에 넣는다.

- **모킹은 브라우저 컨텍스트에 건다** (`page.context().route()`, 2026-09-28 — 「착수 전」 ③). 페이지에 걸면 팝업·새 탭에서 풀린다 —
  **모킹된 줄 알았는데 진짜 서버를 두드린 실행**이 가장 나쁜 실패다
- **케이스의 API 직접 호출(`request`)과 API 호출 부품은 모킹을 안 거친다.** 브라우저 밖 통로이기 때문이다.
  모킹 구간 안에 그런 부품이 있으면 조립 화면이 `이 부품의 API 호출은 모킹되지 않습니다` 를 붙인다.
  케이스가 `request` 를 쓰는지는 「만들기」 판별과 같은 자리에서 소스로 본다
- **위험은 「계속 유효한 것」이 아니라 「보이지 않는 것」이다.** 조립 화면·실행 결과·증적 양쪽에서 모킹 구간을 칠한다 (§8.11 · 도메인/리포팅 §8.4)
- **컨텍스트를 새로 만드는 케이스는 모킹이 안 따라간다.** 지금 케이스 중에 그런 것은 없다. 생기면 이 줄을 다시 본다

#### 저장은 DB 에 버전을 쌓는다. 사람이 저장을 누른다 (결정 7)

저장할 때마다 **버전이 하나 오르고 이전 버전은 고치지 않는다.** 되돌리기는 옛 버전을 복사한 **새 버전**이다.
자동 저장은 없다. git 에 파일로 두지 않는다 — 시나리오는 커밋과 함께 움직이지 않는 **조합 목록**이다.
**동시에 고치면 뒤에 저장한 쪽이 409 를 받는다** — 저장 요청이 「어느 버전을 고쳤나」를 싣고, 그사이 버전이 올랐으면 거절한다.
말없이 덮으면 앞사람의 조립이 이력에서 사라진다.
**부품의 입력값에 비밀값 칸이 있으면 `param_set` 과 같은 규칙이다** ([공통/2-명세선언.md](../공통/2-명세선언.md) §4.1) — 저장은 하되 화면과 증적에서 가린다.

#### 케이스가 바뀌면 건너뛰기를 포기하고 실행한다 (결정 8)

**애매하면 안전한 쪽으로 무너진다** — 느려질 뿐 틀리지 않는다.

| 케이스에 생긴 일 | 어떻게 |
|---|---|
| 체크를 푼 절차 제목이 케이스에서 사라짐 | 그 체크는 **무시하고 실행**한다. 시나리오에 「확인 필요」 |
| 「만들기」 절차가 새로 생김 | 새 절차는 **실행이 기본**. 「확인 필요」 |
| 입력값 칸이 늘었음 | 저장된 값에 없는 칸은 케이스의 `.default()` 를 쓴다 (K10) |
| 케이스가 비활성이 됨(파일이 사라짐) | 그 시나리오는 **실행 불가**. 실행 요청은 409 |

- **언제 알아채나** — 목록·상세를 줄 때 서버가 저장된 부품을 지금 카탈로그와 소스에 대 본다. 스캔 때 따로 쓰지 않는다 — 들고 있을 상태가 는다
- **버전은 사람이 고쳐 저장할 때만 오른다.** 케이스가 바뀌었다고 저절로 오르지 않는다 — 버전은 **사람이 조합을 고친 이력**이다
- **실행에는 그때의 조합을 박제한다** — `scenario_run_part` 가 부품 정의와 입력값을 행마다 복사한다. 실행 기록이 케이스 이름과 값을 복사해 두는 것과 같다

#### 실패하면 거기서 멈춘다. 전부 통과해야 통과다 (결정 9)

뒤 부품은 **「안 돌았음」**(`NA`, 오류 `NOT_RUN`)으로 닫는다. 이어진 흐름이라 앞이 깨지면 뒤 결과를 못 믿는다.
시나리오의 판정은 **모든 부품이 통과일 때만 통과**다. 어디서 깨졌는지는 부품 단위로 남는다.

**부품을 판정 없이 닫는 오류 값은 이 표가 정본이다.** 다른 절·스키마 주석은 여기를 가리킨다.

| `error.message` | 언제 | 누가 적나 |
|---|---|---|
| `NOT_RUN` | 앞 부품이 실패해 거기서 멈췄다 | 러너 |
| `TIMEOUT` | 시나리오 제한 시간에 걸려 끊겼다. 도는 중이던 부품과 그 뒤가 다 이 값이다 — 원인이 앞 부품 실패가 아니다 | 러너 |
| `ABORTED` | admin 이 다시 떠서 도는 중이던 실행을 닫았다 (도메인/실행 §3.2 재기동 복구) | admin |

**실행 묶음의 끝** — 러너 응답을 저장하면 `test_run.status = FINISHED` 다. 부품 하나하나가 따로 끝나지 않는다 — 한 프로세스가 한 번에 돌려준다.
재기동 복구로 닫히면 `ABORTED` 다. **시나리오의 판정(통과·실패·판정 없음)은 `test_run.status` 가 아니다** — 부품 판정을 위 규칙으로 접은 것이고,
목록의 `lastRun.verdict` 가 그것이다(§7).

#### 시나리오 결과는 케이스 이력에 안 들어간다 (결정 10)

케이스 목록의 「마지막 결과」와 판정 흐름 막대는 **단독 실행만** 센다. 시나리오 안에서는 준비를 건너뛰었고 앞 부품이 만든 상태 위에서 돌았다 —
조건이 다르다. 섞으면 「3개월째 초록이었는데 이번에 빨강」이 무엇을 뜻하는지 말할 수 없다.

- **그래서 시나리오 결과는 `run_item` 에 안 쓴다.** `scenario_run_part`·`scenario_run_step` 에 쓴다
- **실행 묶음은 `test_run` 한 행이고 `kind` 칸으로 가른다.** 실행 기록 화면의 탭이 이 칸으로 거른다(도메인/실행 §8.7)
- **`test_run` 을 읽는 운영 코드는 전부 `kind` 를 거른다.** 안 거르면 시나리오 실행이 요구사항 표·대시보드·진행 카드에
  케이스 실행인 척 섞인다. 대상은 `grep -rln "FROM test_run\|JOIN test_run" apps/admin/src` 와 Grafana 대시보드 질의로 센다 — **개수를 여기 적지 않는다**
- `attempt` 를 시나리오의 순서 칸으로 쓰지 않는다 — 이미 「재시도 회차」라는 뜻이 있다

#### CI 에서 안 돌린다 (결정 11)

시나리오는 DB 에 사는 조합이고 CI 는 DB 를 모른다. 돌리는 자리는 **화면에서 사람이 누를 때**뿐이다.
정기 실행(`scripts/run-scheduled.ts`)에 얹을지는 필요해지면 정한다.

#### 동시성 · 시간

- **케이스 실행과 같은 동시성 상한(기본 2)을 나눠 쓴다.** 시험 실행도 한 자리를 쓴다 — 상한의 근거가 러너 한 대가 여는 브라우저 수이기 때문이다
- **제한 시간은 케이스 부품마다 `300000`ms 와 대기 부품 시간을 합한 것**이고 60분을 넘지 않는다. 넘으면 저장을 400 으로 거절한다

#### 남는 한계 — 이번에 안 만드는 것

- **진행 표시와 도중 멈춤이 없다.** 러너의 `/progress`·`/abort` 는 `historyId` 로 지목하는데 시나리오 실행에는 그것이 없다.
  제한 시간이 상한이다. `POST /api/runs/:runId/abort` 는 시나리오 실행에 409 다. 필요해지면 러너 지목 열쇠부터 정한다
- **Slack 완료 알림을 안 보낸다** (도메인/실행 §8.9 는 케이스 실행만)
- **시나리오 개수에 기계 상한을 두지 않는다.** 조사 권장은 핵심 여정 10~20개다
- **제한 시간에 걸린 부품은 절차가 안 남는다** (`steps: []`). 결과 줄이 부품이 끝날 때 나오기 때문이다 — 앞 부품들은 남는다.
  「어느 절차에서 걸렸나」가 필요해지면 절차마다 줄을 흘리는 것부터 정한다

## 7. Scenario API (2026-09-28 신설)

**권한은 실행 칸을 쓴다** — 보기는 `(실행, read)`, 저장·치우기·시험 실행·실행은 `(실행, write)`. 표는 [인증.md](인증.md) §7 「등급으로 갈리는 자리」가 정본이다.
경로의 `:id` 는 열 자리 숫자 글자만 받는다 (도메인/리포팅 §7 과 같은 규칙).

```
GET    /api/scenarios?service=           시나리오 목록. service 필수 (접두사)
                                         → { items: [{ id, name, platform, version, partCount, isActive,
                                                        needsCheck: boolean,          결정 8 의 「확인 필요」
                                                        runnable: boolean,            비활성 케이스를 쓰면 false
                                                        lastRun: { runId, status, verdict: ItemStatus | null, finishedAt } | null }] }
                                         status 는 test_run.status, verdict 는 부품 판정을 접은 것 (§3.7 결정 9). 안 끝났으면 verdict 는 null
POST   /api/scenarios                    { service, name, platform, parts: ScenarioPart[] } → 201 { id, version: 1 }
GET    /api/scenarios/:id                최신 버전 + 버전 이력 + 부품마다의 점검
                                         → { id, name, platform, version, parts, isActive,
                                              versions: [{ version, savedBy, savedByName, savedAt }],
                                              checks: [{ seq, reason: 'STEP_GONE' | 'STEP_NEW' | 'CASE_INACTIVE' }] }
GET    /api/scenarios/:id/versions/:v    옛 버전의 platform · parts
PUT    /api/scenarios/:id                { name, platform, parts, baseVersion } → { version }
                                         baseVersion 이 최신이 아니면 409 STALE_VERSION
POST   /api/scenarios/:id/restore        { version } → { version }   옛 버전을 복사한 새 버전
POST   /api/scenarios/:id/archive        목록에서 치운다 (is_active = false). 지우지 않는다 — 지난 실행이 가리킨다
GET    /api/scenarios/case-parts/:tcId   조립 화면이 케이스 부품을 펼 재료
                                         → { tcId, name, platforms, precondition, paramSchema, expectedSchema,
                                              steps: [{ title, skippable: boolean }],   소스 판별 (§3.7 결정 4)
                                              r16: boolean,                             skippable 이 하나라도 있으면 true
                                              usesRequest: boolean }                    모킹 경고 (§3.7 결정 6)
POST   /api/scenarios/:id/runs           { env } → 201 { runId }
                                         test_run(kind = SCENARIO) 과 부품 행을 만들고 줄에 세운다. 기다리지 않는다.
                                         runnable 이 false 면 409 SCENARIO_NOT_RUNNABLE
GET    /api/runs/:runId/scenario         시나리오 실행의 부품 · 절차 · 판정 · 건너뜀 · 모킹 구간
                                         → { scenarioId, version, parts: [{ seq, kind, tcId, tcName, part, status,
                                                                             durationMs, skippedSteps, mocks, steps, error }] }
POST   /api/scenario-trials              { service, env, platform, parts } → 202 { trialId }   저장 안 한 조립도 된다
GET    /api/scenario-trials/:trialId     → { status: 'RUNNING' | 'FINISHED', result?: ScenarioExecuteResponse }
GET    /api/scenario-trials/:trialId/screenshots/:seq   시험 실행의 사진
GET    /api/runs/:runId/scenario/screenshots/:seq        시나리오 실행의 사진 (artifacts/runs/{runId}/scenario/{seq}.png)
                                         서비스 판정은 그 test_run 의 서비스다. kind 가 CASE 면 404
```

**옛 사진 통로 `GET /api/screenshots/:runId/:historyId/:seq.png` 는 그대로 숫자만 받는다** (도메인/실행 §7). `scenario`·`trial` 글자가 그 통로로 들어오면 400 이다 —
그래야 남의 시험 사진을 옛 통로로 우회해 못 본다. 시나리오 사진은 위 두 통로만 낸다.

**400 으로 거절하는 조립** — 비었다 · 모르는 `kind` · 그 서비스 접두사가 아닌 케이스 · 시나리오 디바이스를 선언하지 않은 케이스 ·
`skippable` 이 아닌 절차의 건너뛰기 · 짝 없는 `unmock` · 60초 넘는 대기 · 제한 시간 합이 60분을 넘는다 · API 부품 경로가 `/` 로 시작하지 않거나 `//` 로 시작한다(대상 주소 밖으로 못 나간다 — `//host` 는 다른 호스트로 풀린다. 러너도 400 으로 막는다).

**시험 실행은 기록에 안 남는다** (§8.11). `test_run` 을 만들지 않고, 결과는 admin 메모리에 두며 24시간 뒤 버린다 —
**admin 이 다시 뜨면 사라진다.** 기록이 아니므로 그래도 된다. 사진은 `artifacts/runs/trial/{trialId}/` 에 쌓이고,
**새 시험 실행이 시작될 때 24시간 지난 `trial/*` 폴더를 치운다** (2026-09-28 — 「착수 전」 ⑤). `trialId` 는 admin 이 만드는 UUID 라 서로 안 덮는다.
**남의 시험 결과를 못 본다** — 결과는 시작한 사람만 읽는다. 다른 사람이 `trialId` 를 쳐도 404 다.

**증적은 기존 통로를 쓴다** — `POST /api/runs/:runId/evidence` 가 `kind = SCENARIO` 인 실행이면 E2E 증적을 만든다(도메인/리포팅 §8.4).

```
[계약 변경 필요]
대상:    Admin API — /api/scenarios/** · /api/scenario-trials/** · GET /api/runs/:runId/scenario
현재:    없다
제안:    위 블록
이유:    E2E 시나리오 (설계서 결정 1~11, 2026-09-22 확정 · 「착수 전」 ①~⑤ 2026-09-28 사용자)
영향:    WS-B(시나리오 서버 · 줄 세우기 · 기존 test_run 조회 kind 거르기) · WS-F(인증 표 · auth/gate.ts · auth/scope.ts 두 표) · WS-E(화면)
상태:    대기
```

### 8.11 E2E 시나리오 화면 (2026-09-28 신설)

**목업 다섯 장이 모양의 정본이다** — [여기](https://claude.ai/artifact/RdfUPLjs6ZPZzfC45xFfiW). 픽셀은 목업을 본다.
자리(사이드바)는 [공통/5-화면공통.md](../공통/5-화면공통.md) §8 「자리 목록」의 `E2E 시나리오` 다. 색·간격은 DESIGN.md.
**화면을 만들기 전에 시안을 먼저 보인다** — 이 절은 무엇이 어디에 있는지를 정하고 모양은 시안에서 고른다.

**목록** — 줄마다 번호(`SC-{id}`) · 이름 · 부품 수 · 버전 · 마지막 실행 · 결과. 결정 8 의 「확인 필요」·「실행 불가」 칩이 붙는다.
주 행동은 `새 시나리오`.

**조립** — 왼쪽에 부품을 순서대로 쌓고 오른쪽 팔레트에서 더한다. **팔레트에는 §3.7 부품 표의 부품이 전부 뜬다** —
「모킹 끄기」가 빠지면 모킹의 범위를 화면에서 못 정한다.

- 케이스 부품을 펴면 `precondition` 문장이 읽을거리로 나오고, 그 아래 **「만들기」 절차 제목마다 체크**가 나온다 (§3.7 결정 4).
  R16 미적용 케이스는 체크 대신 안내 문장이다. 앞 부품이 같은 제목의 절차를 가졌으면 **「N번에서 이미 함」 칩** (결정 5)
- **모킹이 걸린 구간은 왼쪽 세로선으로 칠한다.** 그 안의 API 부품과 `usesRequest` 케이스에는 「모킹되지 않음」을 붙인다 (결정 6)
- 저장은 사람이 누른다. 안 누른 변경이 있으면 머리에 `저장 안 된 변경 있음` 이 뜨고 자리를 뜨려 하면 한 번 묻는다 (결정 7)
- 버전 이력을 열어 옛 버전을 보고 `이 버전으로 되돌리기` 를 누를 수 있다 — 새 버전이 생긴다

**시험 실행** — 조립 화면에서 누른다. 대상 서버를 고르고, **성공·실패와 어디서 멈췄는지, 실패한 자리의 사진만** 뜬다.
실행 기록과 증적을 오염시키지 않으려고 기록에 안 남긴다 — 시나리오 하나를 만들며 열 번 돌려도 「어제 무슨 일이 있었나」가 읽혀야 한다.

**실행 결과** — 부품마다 절차와 판정이 펴지고 실패한 자리에 사진이 붙는다. 안 돈 부품은 `–  안 돌았음`.
**건너뛴 준비는 「N번에서 세움」으로 적는다** — 안 적으면 「이 케이스가 로그인을 세웠다」로 읽힌다. 모킹 구간은 조립 화면과 같은 세로선.
**여기서만 `E2E 증적 받기` 가 뜬다.** 결과 화면은 `#/runs/:runId` 그대로이고 `kind` 로 그리는 모양이 갈린다.

**실행 기록 탭** — 실행 기록 화면이 `[ 테스트 케이스 ]` `[ E2E ]` 두 탭으로 갈린다. 정본은 도메인/실행 §8.7.
