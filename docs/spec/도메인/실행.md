### 3.2 Execution — 언제 무슨 값으로 돌렸는가

- **책임**: 실행 요청을 받아 러너에 분배하고 결과를 영속화
- **애그리거트 루트**: `TestRun` (식별자 `runId`) → `RunItem[]` → `Step[]`
- **불변식**
  - `RunItem`은 실행 시점의 `params`/`expected`를 **스냅샷으로 복사해 저장**한다.
    `param_set`을 참조만 하면 나중에 값이 바뀌었을 때 과거 증적이 거짓이 된다.
    문서를 만드는 데 필요한 나머지 값도 같은 이유로 실행 기록에 박제한다 (→ §3.3 증적 재현)
  - **요청에 없는 칸은 그 케이스의 저장값(`case_input`)으로 채운다** (2026-09-29).
    채우는 자리는 실행을 만드는 한 곳이라 **정기 실행(§9.2)도 같은 길을 탄다.** 요청에 있는 칸은 건드리지 않는다.
    - 칸마다 **지금 명세**(`param_schema` · `expected_schema`)로 거른다. 명세에 없는 칸 · 그 칸 규칙에 어긋나는 칸은 채우지 않는다 —
      칸 이름이나 타입이 바뀐 뒤 옛 저장값이 섞이면 실패 원인이 DB 한 줄에 숨는다. 그 칸은 코드 기본값으로 돈다
    - **채운 값도 `run_item` 에 스냅샷으로 박제된다.** 저장값을 나중에 고치거나 지워도 지난 실행은 그대로다
    - 선택 칸(`optional`)을 화면에서 비워 두면 그 칸도 저장값으로 채워진다 — 화면이 비워 둔 선택 칸과 저장된 비밀값 칸을 요청에서 빼고, 서버는 요청에 **키가 없는** 칸만 채운다.
      빈 글자(`""`)로 온 칸은 그대로 둔다 — 그래서 저장값으로 채워 열린 칸을 사람이 지우면 빈 글자로 돈다(2026-10-06 PR #163 게이트 2 — 처음에는 「없는 칸과 비운 칸을 가르지 않는다」로 적었는데 서버 동작과 달랐다. 시나리오 조립 화면은 비운 칸을 키째 뺀다, 시나리오 §3.7)
    - 비밀값 칸도 여기서 채운다. 원문을 아는 것은 서버뿐이다 (§8.2 「비밀값 칸」)
    - **저장값으로도 안 찬 계정 칸은 그 실행 대상 서버 줄의 계정으로 채운다** (2026-10-12 진행판 PRD-F9-02). 차례는 요청 값 → 저장값 → 대상 서버 계정이다.
      어느 칸이 어느 역할의 아이디 · 비밀번호인지는 비밀값 칸의 `account` 꼬리표와 칸 이름으로 가린다 — 정본은 [작성.md](작성.md) §3.6 「★ 역할별 계정」.
      대상 서버는 실행의 `env` 줄이고 케이스 테스트 실행(§7 test-run)은 보낸 `baseUrl` 과 출처가 같은 줄이다(없으면 안 채운다). 운영 줄도 채운다.
      저장값과 같이 `run_item` 에 박제된다 — 그 계정이 나중에 바뀌어도 지난 실행은 그대로다. 그 줄에 그 역할 계정이 없으면 비워 두고 케이스가 「비밀값이 비어 있다」로 실패한다
    - 저장값을 두는 법과 화면에서 칸을 채우는 순서는 §8.2 「저장값 — 케이스마다 한 벌」이 정본이다
  - **종류 「API」 애플리케이션 케이스 실행은 시작 때 API 문서를 받아 지문을 견준다** (2026-10-20 API-F1-01) — 기준 서버면 판을 올리고, 다른 서버면 다를 때 `test_run.api_doc_note` 만 남긴다. 못 받아도 실행은 막지 않는다.
    러너에는 그 대상 서버 줄의 API 인증과 케이스가 만들어진 판 원문을 싣고, 그 판이 없는 항목은 러너에 안 보내고 미실행으로 닫는다. `PASS` 항목을 저장할 때 모양 확인 줄을 `api_call_seen` 에 갈아 끼우고 `FAIL` 이면 그 케이스 줄을 지운다. 문서 견주기는 실행을 기다리게 하지 않는다.
    정본은 [API.md](API.md) §3.8 「API 문서와 판」 · 「응답 모양 확인」 · 「API 커버리지」
  - 동시 실행 수는 설정값(기본 2)을 넘지 않는다. **시나리오 실행과 시나리오 시험 실행도 이 상한의 한 자리씩을 쓴다** (2026-09-28, [시나리오.md](시나리오.md) §3.7 「동시성 · 시간」)
  - **같은 케이스 항목은 하나씩 돈다** (2026-10-13 PRD-F9-36) — 한 실행 안에서 `tc_id` 가 같은 항목(반복 회차 · PC · 모바일)은 앞 항목이 끝나야 다음이 대기줄에 들어간다.
    나란히 돌면 같은 데이터를 두고 부딪힌다 — run 20903 에서 재고 1개 상품을 사는 케이스 · 서버 전체를 초기화하는 케이스가 짝 회차와 같은 시각에 실패했다.
    회차는 케이스 순서로 한 바퀴씩 돌고, 다른 케이스끼리는 위 상한까지 나란히 돈다 — 케이스 하나만 여러 번 돌리면 상한을 다 못 쓴다.
    서로 다른 케이스가 데이터를 나눠 쓰다 부딪히는 것(서버 초기화 케이스가 옆 케이스를 깨는 것)과 다른 실행끼리는 막지 않는다. 코드는 `apps/admin/src/execution/dispatcher.ts` `dispatch`
  - **Android 앱 항목은 그 상한 밖의 「디바이스 줄」에서 한 번에 하나씩 돈다** (2026-10-07). 상한은 컨테이너 러너의 CPU 를 지키는 값이고,
    앱 항목은 러너 CPU 가 아니라 폰을 쓴다. 같은 디바이스에 연결 둘이 겹치면 뒤 연결이 앞을 가로채서 하나씩 세운다.
    **케이스 테스트 실행 · 작성 에이전트의 앱 화면 읽기도 같은 잠금을 쓴다** — 디바이스가 쓰이는 중이면 기다리지 않고 409 `DEVICE_BUSY` 다(§7).
    잠금은 관리 서버 메모리에 하나다. 디바이스 팜에 폰이 여러 대여도 아직 하나씩 돈다 — 폰 수만큼 나란히 돌리는 것은 다음 일이다(2026-10-20 APP-F1-10).
    **게임 실행은 이 줄의 차례 하나를 실행 전체가 쓴다** — 게임 항목을 한 줄로 모아 폰을 한 번 잡고 차례로 돌린 뒤 놓는다(2026-10-23 GAME-F1-09 — 정본은 [게임.md](게임.md) §3.10 「게임 연결」). 그동안 다른 앱 항목 · 테스트 실행은 기다리거나 `DEVICE_BUSY` 다
    **앱 · 게임 단계가 있는 E2E 시나리오 실행 · 시험 실행도 차례 하나를 시나리오 전체가 쓴다**(2026-10-28 — 정본은 [시나리오.md](시나리오.md) §3.7 결정 16)
  - **기기 성능 실행은 이 디바이스 줄과 위 동시 실행 상한 밖이다** (2026-10-21 PERF-F1-08 — [성능.md](성능.md) §3.9 「기기 성능」 · §7 「PERF-F1-08 이 연 통로」). 고른 기기(5대까지)를 팜에서 한꺼번에 잡고
    기기마다 연결을 하나씩 동시에 연다 — 서버 러너에 자식이 기기 수만큼 더 뜬다. 잡은 폰은 그 실행이 끝날 때까지 놓지 않아 그동안 기능 테스트의 앱 항목은 다른 빈 폰을 쓰거나 「빈 폰이 없습니다」가 된다.
    디바이스 잠금(`DEVICE_BUSY`)은 쥐지 않는다 — 폰이 갈려서다. 잡는 시간은 실행 시간에 맞춰 팜이 받는 값(30 · 60 · 120분) 가운데 고르고 모자라면 늘린다(성능 §7 「팜 폰」).
    직접 플레이는 서버 러너를 쓰지 않는다. 내 컴퓨터 러너에 꽂은 폰은 팜이 잡아 주지 않으니 그동안 그 폰으로 케이스 테스트 실행을 하지 않는다 — 두 일이 같은 폰을 같이 쓴다.
    성능 녹화 실행(HAR)은 브라우저 실행이라 위 동시 실행 상한의 한 자리를 쓴다
  - **Android 앱 케이스의 정식 실행은 디바이스 팜에서 돈다** (2026-10-20 APP-F1-10 — 앞 판 2026-10-07 게이트 0 은 팜 전까지 로컬 러너에서 돌렸다).
    서버 러너가 팜에 붙고, 관리 서버가 항목마다 팜의 빈 폰을 잡고 놓는다(게임 애플리케이션은 실행 하나에 한 번 잡는다 — 대기, [게임.md](게임.md) §3.10 「게임 연결」). 로컬은 케이스 테스트 실행 · E2E 시험 실행 전용이 됐다.
    붙인 모양은 [러너.md](러너.md) §5.2 「디바이스 팜 접속 방식」, 거절은 §7 `POST /api/runs` 가 정본이다
  - **케이스 테스트 실행은 기록을 만들지 않는다** (2026-09-30). 실행 창(§8.10)의 「▶ 테스트 실행」이 부른다 — 값을 고치다가 한 번 돌려 보는 용도다.
    `test_run` · `run_item` 을 만들지 않으므로 통계 · 증적 · 알림 · 대시보드에 안 잡히고, 동시 실행 상한의 자리도 쓰지 않는다.
    결과는 관리 서버 메모리에만 24시간 두고, 시작한 사람만 읽는다. 통로와 상한은 §7 「케이스 테스트 실행」이, 화면은 §8.2 「케이스 테스트 실행」이 정본이다.
    **[시나리오.md](시나리오.md) §7 의 「시험 실행」(E2E 시나리오 조립을 저장 전에 돌려 보는 것)과 이름만 비슷한 다른 기능이다** —
    둘 다 기록을 안 남기고 메모리에만 두지만, 시나리오 시험 실행은 러너 동시성 상한의 한 자리를 쓰고 이쪽은 안 쓴다
  - **★ 한 건 실행은 묶음 실행에 붙는다 — 새 실행 기록을 만들지 않는다** (2026-10-30 사용자 · 진행판 WEB-F7-02 · 시안 11판). **이 묶음이 정본이다.**
    앞 판은 한 건도 실행 기록에 새 RUN 한 줄이었다. 어젯밤 전체 테스트에서 깨진 케이스를 고쳐 한 건만 다시 돌려 통과해도 그 RUN 은 실패 그대로였고 대시보드 회귀 실패에서도 안 빠졌다.
    GitHub Actions 의 다시 실행 · TestRail 의 결과 더하기와 같은 계열이다(사용자는 「회차」 낱말을 거절했다 — 반복 회차와 섞인다)
    - **한 건** — `POST /api/runs` 에 케이스 하나 · `repeat` 1 이 온 실행이다. 디바이스 수와 거는 곳(케이스 목록 ▶ · 상세 칸 · 항목 상세 「입력 값 수정 후 다시 실행」 · 「실패 1건 다시 실행」)은 상관없다.
      반복 2 이상은 지금처럼 새 실행이다 — 반복은 테스트 코드 검증(아래 「반복 횟수」)이지 결과를 고치는 일이 아니다. 케이스 한 건짜리 증적 문서가 필요하면 그렇게 건다. 정기 실행 · 빌드 실행은 서버 안에서 만들어 이 규칙 밖이다
    - **저장** — 한 건도 `test_run` 한 줄이다(`origin = SINGLE` — 공통/4-데이터모델 「실행 시작 방식」). 절차 · 화면 · trace · 팜 증적 · 진행 · 멈추기 · 동시 실행 상한을 그대로 쓰려고다.
      **다만 실행으로 서지 않는다** — 실행 기록 목록 · 대시보드(실행 중 줄 포함) · 알림 줄 · 알림 서랍 · Slack · Grafana 에 없다(`notifySlack` 은 버린다). 그래서 RUN 번호가 가끔 하나씩 건너뛴다. 끝을 알리는 것은 건 사람의 진행 창(§8.9)뿐이다.
      **화면을 새로 고쳐도 잃지 않게** 도는 한 건은 그 케이스 상세 「실행 기록」(§7 `history` — 끝나지 않은 줄도 싣는다)에 「진행 중」 줄로 서고, 누르면 진행 창을 다시 연다. 멈추기도 그 창에서 한다(§7 `POST /api/runs/:runId/abort` 그대로)
    - **붙는 곳**(`rerun_of`) — 요청에 `rerunOf` 가 있으면 그 실행이다(「실패 1건 다시 실행」 — 거절 규칙 `BAD_RERUN` 은 그대로이고 그 실행이 한 건 실행이면 거절이 하나 는다, §7).
      **다만 그 실행이 이번과 다른 대상 서버이거나 빌드 스모크면 붙지 않고 아래 「없으면」 규칙으로 이번 대상 서버에서 고른다** (2026-10-30 WEB-F7-11 코드 검토) — qa 에서 깨진 것은 qa 에서 다시 통과해야 고친 것이다(리포팅 §8.12 「회귀 실패는」). **그 실행이 반복 실행이면 한 건이 아니라 지금처럼 RERUN 새 실행이다** — 원래 카드의 「RUN N에서 통과」 꼬리표(§8.3)가 이어지게 둔다. 없으면 그 케이스 항목이 든 **같은 대상 서버의 끝난 실행 가운데 시작이 가장 늦은 것**이다 —
      끝난 것은 `FINISHED` · `ABORTED` 이고(늦게 시작해 먼저 끝난 작은 실행이 밤새 돈 전체 테스트보다 앞선다 — 직전 대비의 「바로 앞 실행」과 같은 차례).
      **이번 한 건이 고른 디바이스와 겹치는 (케이스, 디바이스) 항목이 하나라도 있는 실행만 후보다** — 안 겹치는 실행에 붙으면 「RUN N 결과에 붙습니다」인데 고친 것이 없다. **빌드 스모크(`build_stage = 'SMOKE'`)는 후보가 아니다** — 직전 대비가 스모크를 건너뛰는 것(리포팅 §7 insights previous)과 같은 까닭으로, 스모크에 붙으면 그 빌드의 회귀 실행이 안 고쳐진다. 「실패 다시」(RERUN) 실행은 후보다 — 사람이 본 가장 새 결과라서다 한 건 실행 · 시나리오 실행은 후보가 아니다. 도는 실행은 고르지 않는다.
      **고른 실행이 반복 실행(`repeat` 2 이상)이면 붙이지 않는다** — 회차 요약(§8.3)의 「5회 중 2회 실패」가 한 번 더 돌린 결과에 지워지면 안 된다. 그 앞 실행으로 내려가 찾지도 않는다 — 더 낡은 실행을 고치게 된다.
      붙일 실행이 없으면 `rerun_of = NULL` 이고 케이스 이력에만 남는다. 고르는 때는 실행을 만들 때이고 박제한다 — 도는 사이 새 실행이 끝나도 바꾸지 않는다
    - **디바이스마다 붙는다** — 한 건의 항목은 붙는 실행에 같은 (케이스, 디바이스) 항목이 있을 때만 그 결과를 고친다. 그 실행에 없던 디바이스는 케이스 이력에만 남는다 — 붙어도 실행의 항목 수는 늘지 않는다
    - **판정이 난 것만 고친다** — 한 건 항목이 통과 · 실패로 끝나면 붙는 실행 그 항목의 **지금 결과**가 된다. 미실행(러너 고장 · 제한 시간 초과 · 멈춤)은 덮지 않고 이력에만 남는다 — 실패가 미실행으로 가려지면 안 된다.
      같은 항목에 여럿이 붙으면 가장 늦게 끝난 것이 이긴다. **원래 항목은 지우지도 고치지도 않는다** — 화면의 「지난 결과 보기」 · 증적의 「원래 결과」다(화면 글자만 2026-10-30 사용자가 바꿨다)
    - **어디가 지금 결과로 세나** — 「지금 결과」는 원래 항목 자리에 덮은 한 건 항목을 바꿔 끼운 것이다. 서버의 세는 질의는 바꿔 끼우는 **한 곳**(`execution/single.ts` 의 `지금항목` — 2026-10-30 WEB-F7-11)을 거친다. 화면이 다시 세지 않는다

  - `RunItem`은 생성 시 `status = NA`, `finished_at = NULL`이다. 실행이 끝나야 판정이 들어간다.

  - `TestRun.status`는 모든 `RunItem`이 종료되어야 `FINISHED`가 된다
  - 실행 요청은 **반복 횟수**를 받는다. 요청 **최상위에 하나**이고 항목마다 따로 두지 않는다 —

      미확정을 따로 묶지 않는다 — 미확정 줄에 꼬리표(`미확정 · <사유>` 중립 한 줄 — DESIGN.md 「판정 표기」)를 달고 요약에 「그중 미확정 N건」을 덧붙인다. N 은 `counts.unconfirmed`(진행 중 포함)이고 0 이면 안 쓴다
    - **옛 실행도 새 규칙으로 보인다** — 집계는 조회 때 `run_item.status` 로 세니 옮길 것이 없다. 박제된 사유는 그때 글 그대로다(옛 실행은 꼬리표 사유)
    - **위험은 숫자가 아니라 꼬리표로 보인다** — 화면 값으로 통과한 미확정 케이스가 통과율 · Slack · 대시보드 숫자에 그대로 든다. 2026-10-10 사용자 결정이다(작성 §3.6 「미확정」 「뒤집은 판단」).
      오류 추정 점검 목록 케이스의 미확정 실패는 화면이 점검 목록 기준을 어겨 처음부터 빨간 것이라 버그 의심이다(작성 §3.6 「설계 기법」 「오류 추정」)
    - **뒤집은 판단 (2026-10-11 · PRD-F4-02)** — 앞 판(2026-09-25)은 미확정을 확정 판정에서 빼고 미확정 묶음 안에서 따로 셌다.
      그래서 판정 없음 색(미확정만 돈 실행) · Slack 머리 `[통과 · 미확정 실패 N]` · `[미확정]` · `[미확정 · 실패 N]` · `미확정 N(통과 a · 실패 b · 미실행 c)` 꼴 · 「이미 있는 케이스에 꼬리표를 새로 다는 diff」 경고가 있었다.
      숫자를 가르지 않게 되면서 꼬리표 하나로 확정 실패가 묶음으로 숨는 길이 없어져 경고도 걷었다
    - 모양은 §7 의 `counts` 가, 보이는 자리는 §8.3 · §8.7 · §8.9 가 적는다
  - **`test_run` 에는 시나리오 실행도 있다. `kind` 칸이 가른다** (2026-09-28 · [시나리오.md](시나리오.md) §3.7 결정 10).
    이 장의 규칙 — 항목·회차·집계·완료 알림·진행 — 은 **케이스 실행(`kind` 가 `UI` · `FN`)**의 것이다(동시성 상한과 재기동 복구는 둘 다 걸린다). 시나리오 실행에는 `RunItem` 이 없다.
    **`test_run` 을 읽는 조회는 전부 `kind` 를 거른다** — 목록(§8.7)은 탭으로, 케이스 이력·마지막 결과는 케이스 실행(`UI` · `FN`)만 본다. 알림 줄은 도는 E2E 를 따로 종류(`scenario`)로 싣는다(공통/3-공유계약 §7.1).
    **실행 하나에는 한 종류만 담는다** (2026-10-02 · PR #131) — 종류 정의 · 옛 `CASE` 행 삭제는 [공통/4-데이터모델](../공통/4-데이터모델.md) 「실행 종류」가 정본이다
    **실행 번호 하나로 짚는 단건 조회도 거른다**(시나리오 번호면 404) — **`run_item` 을 거쳐서만 닿는 조회는 예외다.** 정본은 [시나리오.md](시나리오.md) §3.7 결정 10 (2026-09-29).
    **재기동 복구만은 둘 다 닫는다** — `RUNNING` 인 시나리오 실행도 이어갈 주체가 사라지는 것은 같다. 안 끝난 부품은 `NA` + `ABORTED` 다
  - **trace — 정식 실행의 네트워크 · 조작 · 콘솔을 남긴다** (2026-10-16 · 진행판 PRD-F10-03 · L5 해제). 브라우저가 부른 API 가 안 남아(`http_trace` 는 테스트 코드의 `request` 호출뿐)
    실패를 「화면이 깨졌나 · 서버가 5xx 를 줬나」로 못 갈랐다. **trace 파일은 사람이 내려받지 않는다. 에이전트가 참고하는 파일이다**(2026-10-16 사용자) — 「화면이 맞음」 작성 요청이 실패 항목 trace 의 가린 요약을 받는다([작성.md](작성.md) §7 「표준 기획서 통로」 `GET …/:id/trace`)
    - **케이스는 정식 실행의 브라우저 항목에서만 켠다** — 러너가 `runId > 0` 이고 `android` 가 아닐 때 `PLATFORM_TRACE=1` 을 준다(러너 §5.2 「출력 폴더 · trace」). 케이스 테스트 실행 · 작성 관문 · 사람이 직접 돌린 실행은 끈다.
      단계 스크린샷이 이미 있어 화면 녹화 · 소스는 뺀다. 시나리오 실행 · 시험 실행도 켜지만 규칙이 다르다 — 한 zip 에 부품이 섞여 단계 번호로 가르고 실패 부품 몫만 남긴다(정본 [시나리오.md](시나리오.md) §7 「실패 기록」, 2026-10-17).
      2026-10-16 판은 「한 zip 에 부품이 섞이고 사진 자리에 항목 번호가 없다」며 안 켰다 — 단계 번호가 시나리오 전체에서 이어져 부품을 가를 수 있다
    - kit 리포터가 끝난 테스트의 trace 를 `artifacts/runs/{runId}/{historyId}/trace.zip` 으로 옮긴다(스크린샷 옆). 옮기다 실패해도 판정은 그대로다
    - **서버는 항목을 닫은 뒤 따로, 한 번에 하나씩 푼다** — 실행을 늦추지 않고 메모리를 아낀다. 상태는 `run_trace` 한 줄(`DONE` · `NONE` · `FAILED` 와 사유)이다.

    - 남기는 것 — 네트워크(`run_network`): API(fetch · xhr · 요청 도구) · 페이지 이동 · 실패(4xx · 5xx · 끊김)만. 잘 온 이미지 · 글꼴 · 스크립트는 버린다. **헤더는 남기지 않는다.**
      **본문은 실패 항목(통과가 아닌 항목)의 API 줄에만 2000자까지** — 화면이 읽은 응답만 Playwright 가 잡는다. 조작(`run_action`): 케이스 본문이 부른 Playwright 호출(준비 · 정리 · 증적 사진은 뺀다).
      콘솔(`run_console`): 오류 · 경고 · 잡히지 않은 오류. 줄마다 단계 번호와 테스트 시작부터의 시각 — 번호는 kit 이 단계가 끝날 때 다는 `platform-step` 첨부로, 그 앞에 일어난 일에 붙인다. 준비(Before Hooks — 로그인 fixture 의 API 등) 중 · 마지막 단계 뒤 정리 중 줄은 비운다
    - **가림** — 공통/2 §4.1 가림 규칙을 넓혔다. 실행 값 목록(`항목비밀`)을 어디서든 가리고, 비밀 칸 이름(화면 가림과 같은 판정)에 붙은 값 —

      **주소 경로(물음표 · # 앞)에서는 계정 아이디 칸 값을 안 가린다**(2026-10-26 WEB-F6-03 시작 질문 · `execution/trial.ts` `경로비밀`) — 관리자 아이디 `admin` 이 `/api/admin/banners` 를 가려 서비스 지도가 그 API 를 못 맞췄다. 비밀번호 · 토큰은 경로에서도 가리고, 아이디와 같은 글자인 비밀번호도 가린다.
      케이스 정식 실행만이다 — E2E 부품 trace 는 경로도 다 가린다(공통/2 §4.1 · `scenario/runTrace.ts`)
    - **없음** — 앱 실행 · trace 파일이 없는 항목(다른 기계의 러너는 공유 폴더가 없다 · 리포터가 옮기다 실패)은 `NONE` 과 사유다. 이 기능 전의 항목은 상태 줄이 없다
    - 원본 zip 에는 가리지 않은 요청 · 응답 본문(Playwright 옵션으로 못 끈다)과 화면 스냅샷(에이전트가 실패 순간의 화면을 보려고 일부러 켠다 · `snapshots: true`)이 그대로 있다.

### 3.11 빌드마다 돌리기 — CI 가 새 빌드를 알리면 스모크 → 회귀 (2026-10-22 결정 · 2026-10-24 GAME-F1-13 에서 모든 종류로)

처음에는 게임 결정이었다([게임.md](게임.md) §3.10 결정 13). GAME-F1-13 시작 질문에서 사용자가 「웹이나 모바일 ci도 필요 한데 같이 쓸수 있는 거야?」라고 물어
**같은 CI 토큰 · 같은 통로 하나로 웹 · Android 앱 · 게임 · API 를 다 받게** 넓혔다. **이 절이 정본이다.** 통로는 §7 「빌드마다 돌리기」, 칸은 [공통/4](../공통/4-데이터모델.md) 「게임 테스트 표」 smoke 블록.

- **흐름** — CI 가 빌드를 만들면 ① QA Hub 에 빌드를 알린다(빌드 번호 · 대상 서버) ② 그 줄의 최신 빌드가 이것이 되고 QA Hub 가 실행을 건다(시작 방식 「빌드」) ③ 끝나면 지금의 실행 끝 Slack. 「빌드 124 에서 새로 깨짐」은 지금의 지난 실행 견주기로 본다 — 회귀는 같은 빌드의 스모크를 건너뛰고 스모크가 아닌 앞 실행과 견준다. 스모크는 아무 앞 실행과 견준다(2026-10-25 GAME-F2-14 · 정본은 [리포팅.md](리포팅.md) §7 insights previous)
- **사람이 매번 첨부하지 않는다** — CI 가 빌드 끝 단계에서 스스로 부른다. 사람은 처음 한 번 CI 에 그 단계를 붙이고 토큰을 넣는다(사용자 「매번??」에 답한 것 — 시작 질문)
- **무엇을 보내나 — 애플리케이션 종류로 가른다**
  - Android 앱 · 게임 — APK 를 본문 그대로 보내거나, 회사 저장소(S3 · Nexus · 사내 파일 서버)의 APK 주소만 보낸다(`apkUrl` — 사용자 「파일 또는 주소」). 주소는 회귀가 끝날 때까지 살아 있고 디바이스 팜에서 로그인 없이 열려야 한다 — 아니면 회귀 도중에 설치가 깨진다. 둘 다 없으면 400 `APK_REQUIRED`
  - 웹 · API — 올릴 파일이 없다. 배포를 끝낸 뒤 빌드 번호만 알린다. 파일이나 주소를 보내면 400 `APK_NOT_ALLOWED`. 빌드 줄은 파일 없이 남아 실행에 빌드 번호가 붙는다
- **APK 를 QA Hub 가 받는 까닭** — GitHub 아티팩트는 로그인해야 받고 zip 으로 싸여 있어 폰이 바로 못 깐다. 고객사 CI 도 같은 한 통로를 쓴다
- **받는 APK** — 본문 그대로다(multipart 가 아니다 — 1GB 넘는 APK 를 메모리에 안 올리고 디스크로 흘리고, 새 패키지가 필요 없다 · 시작 질문 승인). 크기 한도 2GB(리니지 라이크 APK 는 1GB 를 넘는다 — `execution/buildFile.ts` `빌드상한`). **APK 만** 받는다 — zip 맨 위에 `AndroidManifest.xml` 이 있어야 한다. AAB(`base/manifest/` 아래) · OBB 는 400 `BAD_FILE_TYPE`
- **보관** — 대상 서버 줄마다 최근 5개(`보관개수`). 넘으면 파일과 행을 지운다. 도는 실행이 쥔 빌드는 남긴다
- **스모크 → 회귀** — 스모크 케이스만 먼저 돈다(UI · 기능 실행 둘로 갈린다). 다 통과하면 회귀(정기 실행과 같은 UI · 기능 두 실행 — 활성 케이스 전부)를 건다. 하나라도 실패 · 미실행 · 멈춤이면 회귀는 안 돌고 실행 끝 Slack 이 알린다.
  스모크 케이스가 없으면(디바이스 팜이 없어 앱 스모크를 다 뺐을 때도) 바로 회귀다. 빌드 실행은 늘 Slack 알림을 켠다 — 정기 실행처럼 볼 사람이 없다
- **앞 빌드 건너뛰기** — 새 빌드가 오면 같은 줄 앞 빌드의 빌드 실행 가운데 **끝난 항목이 하나도 없는 것**을 멈춘다(항목이 하나라도 끝났으면 결과가 쌓이는 중이라 둔다). 스모크가 끝났을 때 그 줄에 더 새 빌드가 와 있으면 회귀를 안 건다
- **스모크 표시** — 케이스 선언의 한 칸(`smoke`, [공통/2](../공통/2-명세선언.md))이다. AI 가 작성 때 핵심 경로에 달고 사람이 케이스 목록에서 고친다.
  **사람이 고친 값은 DB 칸 `test_case.smoke_set` 에 둔다** — 스캔이 코드 값(`smoke`)을 계속 채우고, 고친 값이 있으면 그것이 이긴다. `null` 을 보내면 코드 값으로 돌아간다(케이스 저장값과 같은 방식 — 시작 질문 승인). 통로는 [카탈로그.md](카탈로그.md) §7 `PUT /api/cases/:tcId/smoke`
- **빌드는 실행에 고정한다** — 실행을 만들 때 그 줄의 최신 빌드(빌드 실행은 올린 그 빌드)를 실행에 적고(`test_run.build_id` · `build_no`) 끝까지 그 빌드를 깐다. 뒤에 새 빌드가 와도 바뀌지 않는다. 사람 · 정기 · 실패 다시 실행도 같다.
  빌드가 하나도 없는 줄은 지금처럼 `app_path`. 케이스 테스트 실행 · 작성 앱 · 게임 화면도 그 줄 최신 빌드를 깐다(기록을 안 남겨 고정할 자리가 없다).
  작성 앱 · 게임 화면의 줄은 집기 계정과 같은 규칙(`앱줄고르기` — 짚은 줄, 아니면 앱 파일 경로가 있는 첫 줄)으로 고른다 — 앱 파일 경로 없이 빌드만 받는 줄은 작성 요청에 대상 서버를 짚는다
- **디바이스 팜이 받는 주소는 기한 있는 서명 주소다** — 열린 주소면 아무나 받는다. admin 이 폰을 잡은 뒤 만들어 실행 요청의 `app` 칸에 싣는다(저장하지 않는다).
  바탕은 `PLATFORM_PUBLIC_URL` 이다 — 비어 있으면 정식 실행 항목은 까닭 한 줄과 함께 미실행으로 닫히고, 케이스 테스트 실행 · 작성 화면은 옛 `app_path` 로 물러서지 않고 오류로 끝난다(다른 빌드로 케이스를 쓰지 않게).
  스모크를 UI · 기능 둘 다 세운 뒤에 분배한다 — 하나라도 못 세우면 세운 것도 닫고 빌드를 지운 뒤 500 이다(CI 가 같은 번호로 다시 부른다). 실행을 못 걸었을 때도 같다 기한은 다음 정시 뒤 한 시간이라 남은 시간이 1~2시간이다 — 같은 시간대의 게임 항목이 같은 주소를 받아 Appium 이 받아 둔 APK 를 다시 쓴다(작성 AI 가 게임을 늦게 깔아도 안 끊긴다). 서명 열쇠는 세션 열쇠에서 쓰임을 붙여 갈라낸다
- **CI 는 애플리케이션마다 발급하는 CI 토큰(`cit_`)으로 부른다** — 바깥에서 실행을 거는 첫 문이다. 보내면 바로 돈다(사용성이 비밀값 0 보다 앞선다). 성능 에이전트 토큰(`pga_` — [성능.md](성능.md) §5.4)은 숫자를 보내는 문이라 실행을 걸지 않는다
- **왜 「문을 내지 않는다」를 뒤집나 · 무엇은 그대로인가** — 그 결정이 막으려던 것은 「로그인을 거치지 않고 **아무나** 실행을 걸어 대상 서버가 아무 때나 두드려지는 것」이다([인증.md](인증.md) §7 「인증 적용 범위」).
  빌드마다 돌리기는 CI 가 사람 없이 불러야 해서 안에서 만들 길이 없다. 그래서 문을 하나 내되 그 판단은 지킨다 (내 결정 — 아래 셋)
  - **토큰은 발급한 admin 계정에 묶는다**(`service_token.created_by`) — 그 계정이 꺼지거나 지워지거나 admin 이 아니게 되면 토큰도 못 쓴다. 「계정 없는 토큰 · 공용 토큰은 금지」([작성.md](작성.md) §3.6 「★ 인증을 뚫지 않는다」)를 그대로 지킨다. 실행자는 발급한 사람이다(화면은 「빌드 · <이름>」)
  - **토큰 하나는 애플리케이션 하나의 빌드 올리기 하나만 연다** — 다른 통로는 403 `AGENT_TOKEN_SCOPE`, 다른 애플리케이션의 대상 서버 이름은 그 줄이 없는 것과 같아 404. 실행은 그 애플리케이션 활성 케이스로만 서고 무엇을 돌릴지는 고르지 못한다
  - **「실서비스 서버」 줄에는 빌드 실행을 걸지 않는다**(400 `PROD_ENV_BLOCKED`) — 케이스 준비가 어드민 API 로 월드 초기화 · 재화 지급처럼 상태를 바꿔 운영 서버를 망가뜨린다
- **BTS 연결 프로젝트는 프로젝트 배포 신호로도 같은 흐름을 탄다** (2026-10-31 BTS-F1-01) — `deploy.sh` 가 프로젝트에 한 번 알리면 애플리케이션마다 이 절의 스모크 → 회귀를 안에서 부르고, 스모크가 다 통과해야 BTS 이슈를 맡는다. 그 프로젝트의 앱 · 게임 APK 는 이 문으로 올리되 실행은 배포 신호가 건다. 열쇠는 CI 토큰이 아니라 프로젝트 배포 열쇠(`pdk_`)다. 이 절의 `POST /api/builds` 는 그대로 둔다. 정본은 [BTS.md](BTS.md) §3.12 「새 기능 바퀴」
- **실행에 빌드 번호를 남긴다** — 실행 목록 · 상세 줄의 `buildNo`. 화면은 시작 방식 뒤에 「빌드 124」로 적는다(§8.7 · §8.3)
- **「다른 빌드가 깔려 있었다」 경고는 빌드 코드(versionCode)로 견준다** (2026-10-24 GAME-F1-13b 시작 질문 승인) — kit 이 앱 판(versionName)과 같은 `dumpsys package` 출력에서 versionCode 도 읽고(`DeviceInfo.appBuild` — [공통/3](../공통/3-공유계약.md)), 실행 상세가 그 실행의 앱 항목이 읽은 값을 겹침 없이 싣는다(§7 `installedApps`).
  빌드 번호와 다른 빌드 코드가 하나라도 있으면 결과 머리에 중립 꼬리표 `다른 빌드` 를 단 한 줄 「다른 빌드가 깔려 있었습니다 — 실행한 빌드 124 · 폰에 깔린 빌드 123」(판정 색을 쓰지 않는다 — 결과 머리의 빨간 글은 실패로 읽힌다. DESIGN.md §1 · 경고성 칩은 `.case-tag`). **앱 판은 견주지 않는다** — 빌드마다 안 바뀌는 일이 많아 늘 경고가 떠 아무도 안 읽게 된다. 빌드 코드를 못 읽은 폰(Appium adb_shell 이 닫힘 · 이 칸 전 기록)은 견줄 것이 없어 경고하지 않는다. versionCode 는 정수라 **빌드 번호가 숫자만일 때 수로 견주고**(`0124` 와 124 는 같다) `v124` · `1.4.0+124` 같은 꼴은 견주지 않는다(코드 검토 — 늘 경고가 뜨지 않게).
  그래서 CI 는 앱의 versionCode 를 빌드 번호와 같게 둬야 이 경고가 뜻이 있다 — 토큰 구획의 CI 예시 아래 안내가 그렇게 말한다
- **토큰 발급 화면** — 설정 › 애플리케이션 안 「CI 토큰」 구획 · 만든 직후 CI 에 붙일 예시를 바로 복사(시안 C — 시작 질문 승인). 정본은 [인증.md](인증.md) §8.8 「서비스」 표의 「CI 토큰」 줄 (2026-10-24 GAME-F1-13b 반영)

```
[계약 변경 필요]
대상:    DeviceInfo(kit 타입) · GET /api/runs/:runId 응답
현재:    폰의 앱 판(versionName)만 읽고 실행 상세에는 기기 정보가 없다 — 화면이 빌드 번호와 견줄 값이 없다
제안:    DeviceInfo.appBuild?: string | null(versionCode) · 실행 상세 installedApps: [{ appVersion, appBuild }]
이유:    CI 가 올린 빌드와 폰에 실제로 깔린 빌드가 다르면 실행 결과에 알리려고 — 앱 판은 빌드마다 안 바뀌어 견줄 수 없다
영향:    kit(runtime/app.ts) · admin 실행 조회(execution/queries.ts) · 화면(실행 결과 머리)
상태:    반영 완료 (2026-10-24, GAME-F1-13b PR #428 — 시작 질문 승인)
```
- **남는 한계** — 회귀를 한 번만 거는 잠금이 admin 프로세스 하나 안의 것이다(여럿 띄우면 DB 잠금으로 바꾼다) · APK 를 러너와 같이 쓰는 artifacts 볼륨에 둬 root 로 도는 케이스가 APK 내용을 바꿔칠 수 있다 — 바로가기로 비밀값을 빼 가는 길은 내려받기가 막는다([공통/6](../공통/6-인프라.md) §9 「바로가기를 따라가지 않는다」). 더미 클라이언트 zip 은 admin 만 붙이는 볼륨으로 옮겨 풀었고(리뷰 M16) APK 는 아직이다 — 같은 식으로 옮기면 풀린다

### 8.2 실행 설정

**고르는 자리는 실행 창 하나다 (2026-10-07 사용자 · 2026-10-09 반영, UI 개편 묶음 4).** 이 절은 실행할 때 **무엇을 고르는가**를 정하고,
그것을 고르는 화면은 실행 창(§8.10)이다. 목록 줄 ▶(카탈로그 §8.1) · 고르기 바 「실행」 · 실행 결과 「실패 N건 다시 실행」(§8.3) ·
항목 상세 「입력 값 수정 후 다시 실행」(리포팅 §8.4)이 모두 같은 창을 연다.
**앞 판은 한 건짜리 실행 설정 화면(`#/cases/:id/run`)과 여러 건 창이 따로 있었다** — 실행을 거는 곳(§8.10 「여는 곳」 표)이 흩어져
칸 이름(「반복」 ↔ 「반복 횟수」) · 테스트 실행 코드(두 벌) · 화면 머리 모양이 제각각이었다. 옛 주소로 와도 같은 창이 열린다.
**한 건이면 그 창이 디바이스 고르기 · 실행자 · 사전조건 · 입력값 묶음 · 저장값 버튼까지 보인다** — 칸의 규칙은 그대로 이 절이 정본이다(실행 제목 칸은 2026-10-19 에 뺐다 — 아래).

**고른 케이스마다** 그 케이스의 `paramSchema`를 읽어 **입력 폼을 자동 생성**한다.
한 건이든 여러 건이든 만드는 방법은 같다. 여러 건일 때 그 폼을 어디에 어떻게 놓는지는 §8.10이 정본이다.
`enum` → 셀렉트, `boolean` → 토글, `optional` → 선택 입력, `describe` → 라벨.
저장된 `ParamSet`을 불러오는 드롭다운 제공.
칸은 **그 케이스의 저장값이 있으면 저장값으로, 없으면 코드 기본값으로** 채워 열린다 — 아래 「저장값 — 케이스마다 한 벌」이 정본이다.
케이스의 `platforms`에 선언된 **디바이스**만 체크박스로 노출하고, 기본은 전부 선택. 서버도 선언 밖 디바이스를 400 으로 막는다(§7 `POST /api/runs`).
스키마 검증 실패 시 해당 칸 아래에 이유를 표시한다(버튼은 비활성화하지 않는다).

**실행 제목 칸은 없다 — 서버가 시작 방식과 담긴 케이스로 짓는다** (2026-10-19 ⑫ 사용성 개편 · 짓는 규칙은 §7 `POST /api/runs` 「자동 제목」).
앞 판은 칸을 두고 `<tcId> 실행` 으로 미리 채웠고 `title` 이 필수였다. 그 칸은 거의 고쳐지지 않았고 여러 건 창에는 아예 없어서
실행 기록이 「FN-001 외 23건 실행」 같은 제목으로 가득 찼다(점검 1.4 · 4.1). 고치지 않을 칸을 묻는 대신 서버가 줄끼리 갈리는 제목을 짓는다.

- 대상 서버 이름 옆에 그 서버의 주소를 흐린 글씨로 같이 보여준다. 고른 뒤 "어디로 쏘는지"를 확인할 자리가 있어야 한다.
  주소는 설정 화면(§8.8)이 서비스마다 갖고 있고 화면이 직접 적지 않는다

- **반복 횟수는 실행 전체에 하나다.** 항목마다 따로 주지 않는다.
  항목마다 다르면 실행 항목 건수를 미리 계산할 수 없다
- 버튼 옆에 몇 번 도는지를 풀어 적는다 (2026-10-19 ⑫ · 점검 4.8 — 앞 판은 `실행 항목이 N건 생깁니다` 한 문장이라 숫자가 어디서 나왔는지 몰랐다).
  케이스마다 디바이스 수가 같으면 `케이스 3 × 디바이스 2 × 반복 1 = 6번`, 다르면 곱셈이 틀리므로 `케이스 2 (디바이스 합계 3) × 반복 1 = 3번` 이다. **건수의 정본은 아래 합(Σ(케이스마다의 디바이스 수) × 반복 횟수)이다** — 한 건이어도 같은 꼴로 적는다.
  실수로 큰 수를 넣은 것을 누르기 전에 알아야 한다. 반복 칸은 숫자 칸(1 이상 정수)이고 화면이 세는 값과 요청에 싣는 값이 같다
- **왜 곱셈이 아니라 합인가** (2026-09-21 수정) — 앞 판은 `케이스 수 × 디바이스 수 × 횟수`였다.
  그 곱셈은 **모든 케이스의 디바이스 수가 같을 때만** 맞는다. 케이스마다 `platforms` 선언이 달라 성립하지 않는다.
  실측이 반증했다 — 데모 케이스를 한 번에 돌렸더니 케이스 11건에 실행 단위가 13개였다.
  디바이스를 둘 선언한 케이스가 섞여 있었기 때문이다.
  세는 자리는 케이스마다 하나씩이고, 반복 횟수만 실행 전체에 하나다

#### 한 번에 만들 수 있는 실행 항목은 5000건까지 (2026-09-17 결정 · 2026-10-13 PRD-F9-22 에 1000 → 5000)

**막는 것은 `repeat`가 아니라 위에서 이미 계산하는 실행 항목 건수(위 풀이의 합)다.**
그래야 케이스 수가 늘어도 같이 보호된다.

- 5000건을 넘으면 `실행` 버튼을 누를 수 없고, 숫자 옆에 `한 번에 5000건까지 만들 수 있습니다`를 적는다
- 서버도 같은 것을 본다. 넘으면 400 `{ error: 'TOO_MANY_ITEMS', limit, requested }`.
  화면만 막으면 직접 찌르는 요청을 못 막는다
- **왜 상한이 필요한가** — 「동시 실행 2 제한이 있어 서버가 죽지 않는다」가 근거였는데,
  동시 실행 2는 *돌아가는 프로세스 수*를 막지 *INSERT 건수*를 막지 않는다.
  디바이스를 둘씩 선언한 케이스 10건을 골라 디바이스 수의 합이 20이고 `repeat`가 10만이면
  `run_item` 200만 행이 요청 한 번에 들어간다 (2026-09-21에 예시를 위 합 식에 맞췄다.
  앞 판은 `케이스 10 × 디바이스 2 × repeat 10만`이라고 적어 곱셈을 전제하고 있었다)
- **왜 5000인가** — 반복 5회로 흔들림을 재는 실행이 한 번에 들어가야 한다. 1000 일 때 기능 테스트 382건 × 5회(1,910건)가
  `TOO_MANY_ITEMS` 에 걸려 둘로 나눠 돌렸다(⑨ 시험). 5000 이면 MKT 전체 472건 × 5회(2,360건)도 들어간다.
  앞 판의 1000 은 「항목 평균 1분 · 동시 2 로 약 8시간, 하룻밤」 셈이었다 — 그보다 오래 걸리면 멈춤 버튼(§8.3)이 있다.
  숫자를 바꾸려면 이 절을 고친다. 설정값으로 빼지 않는다 — 설정이 늘면 「어느 값이었더라」가 는다
- 이 규칙은 §1.1의 L12(나중에 하는 것)였다. 2026-09-17에 앞당겨 여기로 올렸다
- 반복은 **테스트 코드를 검증하려는 것**이지 실패를 가리려는 것이 아니다. 자동 재시도와 혼동하지 않는다 → §5.2
- **Slack 칸은 그 서비스에 웹훅이 설정돼 있을 때만 보인다** (§8.8). 없으면 흐리게 두지 않고 아예 없다 (§8).
  끝났을 때 무엇이 어떻게 알리는지는 §8.9 가 정본이다

#### 비밀값 칸 (2026-09-16 결정)

`paramSchema`의 어떤 칸에 비밀값 꼬리표가 붙어 있으면(→ §4.1) 화면은 그 칸을 가려서 입력받는다.
타이핑하는 동안 글자가 점으로 보이는 칸이다.

- 저장된 `ParamSet`을 불러왔을 때도 가려진 채로 채운다. 화면 어디에서도 그 값을 글자로 되돌려 보여주지 않는다
- **가리는 것은 보이는 것뿐이다.** 값은 그대로 서버로 간다. 저장 시점에 가리면 같은 값으로 다시 실행할 수 없고
  실패 원인도 볼 수 없다. 테스트 전용 계정에 그것은 과한 대응이다
- 어깨너머로 보는 것을 막는 것이 이 칸의 목적이다. 이 칸은 DB 보호 장치가 아니다
- **저장값(아래 절)의 비밀값 칸은 응답에 원문을 싣지 않는다** (2026-09-29). 저장값은 케이스 목록 응답에 서비스 전체 분량이 실리므로
  가린 채 채워 주는 것만으로는 부족하다. 응답은 저장된 비밀값 칸의 **이름만** `savedSecrets: { params, expected }` 의 같은 자리에 알린다 —
  입력값과 기대결과에 같은 이름 칸이 있을 수 있다. 지금 명세에 없는 칸은 응답에서 뺀다. 이름만으로 비밀을 가리면 이름이 비밀 같지 않은 옛 칸이 원문으로 나간다.
  화면은 그 칸을 값 없이 「저장됨」으로 표시하고, 사람이 비워 두면 그 칸을 요청에 싣지 않는다 — 실행을 만들 때 서버가 채운다 (§3.2).
  위의 「값은 그대로 서버로 간다」는 사람이 **이번에 적은** 값의 이야기다

#### 저장값 — 케이스마다 한 벌 (2026-09-29)

**케이스마다 입력값·기대값을 한 벌 저장해 두면 다음부터 칸이 그 값으로 채워진다.** 팀이 같이 쓴다.
로그인 계정처럼 매번 같은 값을 다시 적던 칸을 위한 것이다. 표는 `case_input`(공통/4-데이터모델 §6), 통로는 §7 「저장값」이다.

**`ParamSet`(입력값 묶음)과 다른 것이다.** 묶음은 이름을 붙여 여러 벌 두고 사람이 골라 불러온다.
저장값은 이름이 없고 한 벌이며 고르지 않아도 칸을 채운다.

- **칸을 채우는 순서는 저장값 → 코드 기본값이다.** 실행 창(§8.10 — 한 건 · 여러 건) · 케이스 목록의 상세 칸(카탈로그 §8.1)이
  같은 순서를 쓴다. 한 자리만 다르면 같은 케이스가 두 값으로 보인다
- **명세와 맞는 칸만 채운다.** 지금 명세에 없거나 그 칸 규칙에 어긋나는 저장값은 버리고 코드 기본값을 쓴다 — 서버가 실행을 만들 때 거르는 규칙(§3.2)과 같다
- 칸 옆 안내 줄은 **「저장값 X · 코드 기본값 Y」** 꼴이다. 저장값이 칸을 채워도 코드 기본값이 화면에서 사라지지 않게 둘 다 적는다
- **한 건 실행 창의 저장 조작은 「저장한 값」 줄 하나로 모았다** (2026-10-19 ⑫ · 점검 4.4 · N5 — 앞 판은 저장값 표시 · 묶음 불러오기 · 묶음 이름 · 묶음 저장 · 코드 기본값으로 · 다음에도 이 값으로 채우기, 여섯 조작이 한 줄에 흩어져 있었다). 저장값 저장은 2026-10-30 WEB-F7-09 부터 칸 아래 출처 줄(§8.10 「칸 아래 출처 줄」)이 맡는다.
  - **「저장한 값」 목록**(select) — `코드 기본값` · `저장값 · 누가 · 언제` · 저장한 묶음들. 저장값이나 묶음이 있을 때만 나온다. 고르면 칸이 채워진다(`코드 기본값`은 칸만 채우고 서버의 저장값은 안 건드린다). 저장값이 있으면 처음 선택이 저장값이다. 목록은 읽기 전용 권한도 본다
  - **「묶음으로 저장」** (2026-10-30 WEB-F7-09 — 앞 이름 「이 값을 저장」) — 누르면 묶음 이름 한 줄이 나온다. 이름을 적어야 그 묶음으로 따로 저장한다 — 비운 채 누르면 저장하지 않고 이름을 적으라고 한다. 저장값 저장은 칸 아래 출처 줄의 「이 값 저장」이 맡는다(§8.10 「칸 아래 출처 줄」 · 아래 「저장값 저장과 묶음 저장」)
  - **「저장값 지우기」** — 저장값이 있고 쓰기 권한일 때만 보인다. 옛 「코드 기본값으로」가 하던 일이다. 새 목록의 `코드 기본값` 은 칸만 채우므로 둘을 합치면 선택만으로 팀 저장값이 지워져 단추를 따로 뒀다
  - **입력값이 하나도 없는 케이스에는 이 줄 전체를 그리지 않는다.** 입력값이 있어도 저장값과 묶음이 없으면 목록 없이 「묶음으로 저장」만 나온다
- 저장값이 있으면 **누가 언제 저장했는지**를 보인다 — 실행 창은 입력값 칸 아래 출처 줄(한 건 · 여러 건, 2026-10-30 WEB-F7-09)과 한 건 창 「저장한 값」 목록이다(2026-10-09. 앞 판 한 건 화면은 입력값 머리였다)
- **「저장값 지우기」(2026-10-19 앞 판 이름 「코드 기본값으로」)는 저장값을 지운다.** 확인 상자를 띄우지 않는다. 누르면 그 자리에서 「지우기 확인」·「취소」 두 버튼으로 바뀌고
  「지우기 확인」을 눌러야 지운다. **지운 뒤 「되돌리기」 줄은 두지 않는다** — 화면이 저장된 비밀값을 몰라 되살릴 수 없다
- 저장하거나 지운 뒤에는 케이스를 다시 읽는다. 화면이 들고 있던 값으로 칸을 그리면 서버가 뺀 칸(기본값과 같은 칸)이 남아 보인다
- 케이스 쓰기 권한 `(케이스, write)` 이 없으면 저장 · 지우기 단추를 그리지 않는다 (인증 §3.5)
- 버튼 자리는 케이스 목록 상세 칸의 「모두에게 저장」과 실행 창 칸 아래 출처 줄의 「이 값 저장」(한 건 · 여러 건)이다 (2026-09-29 시안 A · 2026-10-09 실행 창으로 옮김 · 2026-10-19 ⑫ 줄에서 상세 칸으로 · 2026-10-30 WEB-F7-09 출처 줄로).
  상세 칸의 「모두에게 저장」은 저장값·코드 기본값과 다른 칸이 있을 때만 보이고 **누르기 전에** 「팀 모두와 정기 실행이 이 값을 씁니다」를 곁에 적는다 — 앞 판 목록 줄의 「저장」은 누른 뒤에 4초만 알려 모르고 팀 값을 바꿨다(점검 7.6).
  고친 칸이 없고 저장값이 있으면 「저장값 · 누가 · 언제」를 보인다. 저장에 실패하면 서버의 첫 사유를 단추 아래 한 줄로 적는다.
  「저장값 지우기」는 한 건 실행 창에만 있다
- **저장값 저장과 묶음 저장은 단추가 다르다** (2026-10-30 WEB-F7-09). 저장값은 칸 아래 출처 줄의 「이 값 저장」, 묶음은 한 건 창 「저장한 값」 줄의 「묶음으로 저장」이고 이름이 꼭 있어야 한다.
  앞 판은 「이 값을 저장」 한 단추에서 이름 칸을 비우면 저장값, 적으면 묶음이었다 — 출처 줄에 「이 값 저장」이 생겨 같은 일을 하는 이름 비슷한 단추가 둘이 돼 갈랐다
- **묶음을 불러오면 묶음 값이 저장값을 이긴다.** 화면이 묶음 값을 요청에 싣고, 서버는 요청에 **없는** 칸만 저장값으로 채우기 때문이다 (§3.2)
- **선택 칸을 비워 두면 저장값으로 채워진다.** 저장값을 안 쓰고 돌리려면 「저장한 값」에서 `코드 기본값`을 고른다
- **시나리오 부품은 조립에 없는 칸만 이 저장값으로 채운다** (2026-10-06 사용자). 조립에서 적은 값이 이긴다. 순서의 정본은 [시나리오.md](시나리오.md) §3.7 「부품 입력값을 채우는 순서」.
  처음에는 부품이 저장값을 안 썼다 — 부품 열 개면 테스트 계정 비밀번호를 열 번 적어야 해서 바꿨다
- **케이스 엑셀은 코드 기본값을 싣는다** — 저장값이 아니다 ([카탈로그.md](카탈로그.md) §8.1 「엑셀로 내려받기」)
- **케이스 고치기로 기대값을 코드에 적으면 반영이 병합될 때 그 칸의 저장값이 지워진다** (2026-10-01) — 저장값이 코드 기본값보다 앞서서 안 지우면 반영한 값이 실행에 안 쓰인다. 정본은 [작성.md](작성.md) §3.6 「★ 케이스 고치기」
- 비밀값 칸은 응답에 원문이 오지 않는다 — 위 「비밀값 칸」. 칸의 「바뀜」은 가린 글자가 아니라 원래 값과 견준다.
  가린 글자와 견주면 손대지 않은 칸이 늘 바뀐 것으로 보여 저장이 안 먹은 것처럼 보인다

#### 케이스 테스트 실행 (2026-09-30)

실행 창 바닥의 「실행」 옆에 **「▶ 테스트 실행」** 을 둔다. 값을 고치다가 기록을 쌓지 않고 한 번 돌려 본다.
이름은 2026-10-30 사용자 지시(시안 10판 · WEB-F7-09)로 「테스트 실행」에 돌아왔다 — 2026-10-19 ⑫ · 점검 4.3 은 「▶ 테스트 실행」이 「실행」과 무엇이 다른지 몰라 「▶ 시험해 보기」로 바꿨었다. 그 차이는 이름이 아니라 아래 두 줄 안내 글자가 맡는다.
**두 단추의 차이를 화면 글자로 적는다** — 「테스트 실행」 아래에 `기록·리포트가 남지 않습니다`, 「실행」 아래에 `기록이 남습니다`. 단추 이름 「실행」은 그대로다.
**한 건 · 여러 건이 같은 차례 돌리기 한 벌로 돈다** (2026-10-09 — 앞 판은 한 건짜리 화면에 따로 된 패널이 있었다). 여러 건에서만 다른 점은 §8.10 이 적는다.
**기록이 안 남는다는 규칙과 통로는 §3.2 · §7 「케이스 테스트 실행」이 정본이다.** 여기는 화면만 적는다.

- **열 주소 칸은 기본으로 접혀 있다** (2026-10-19 ⑫ · 점검 4.3 — Docker 안의 이름을 `localhost` 로 바꾸는 개발자 개념이라 늘 보일 까닭이 없다). 본문 맨 아래의 접힌 `고급 · 테스트 실행 설정` 안에 있고, 주소 검사에서 막히면 저절로 펴진다. 기본은 위에서 고른 대상 서버의 주소다. 그 주소가 Docker 안에서만 통하는 이름(`host.docker.internal` 이나 서비스 이름)이면
  내 컴퓨터의 브라우저가 못 여니 `localhost` 로 바꿔 채워 준다. 사람이 고칠 수 있고 `http://` · `https://` 만 받는다
- **결과는 케이스 줄 오른쪽에 뜬다.** 돌고 있는 동안은 「실행 중」, 끝나면 판정 글자(색과 함께) · 소요 시간 · 오류를 보이고,
  **한 건 창이면 그 줄 아래에 절차마다 판정을 펼친다** — 앞 판의 결과 패널이 보여 주던 단계별 결과다.
  결과의 비밀값은 서버가 이미 `********` 로 가려 준다 (§7)
- **꺼져 있으면 눌러도 안내만 뜬다** — 서버 설정 `LOCAL_RUNNER_URL` 이 비어 있는 경우(409 `TRIAL_OFF`). 안내는 켜는 법이 적힌 곳(SETUP.md)을 가리킨다
- **이미 돌리는 것이 있으면 눌러도 안내만 뜬다** — 버튼은 죽이지 않는다(§8.2 「버튼은 비활성화하지 않고 누르면 사유를 보인다」). 서버도 같은 것을 본다(409 `TRIAL_BUSY`, 사람당 1건 · 전체 50건이 전부 돌고 있을 때도 같다).
  Android 앱 케이스에서 디바이스가 다른 실행에 쓰이는 중이면(409 `DEVICE_BUSY`, 2026-10-07) 그 사유를 같은 자리에 보인다
- 「실행」과 같은 칸의 값을 쓴다 — 저장값으로 채운 칸과 사람이 고친 칸이 그대로 간다. 케이스 파일과 저장값은 바뀌지 않는다
- 권한은 `(실행, write)` 부터다. 그보다 낮으면 「실행」과 같이 버튼을 그리지 않는다 (인증 §3.5)
- **이름이 같은 「시험 실행」과 섞지 않는다.** E2E 시나리오의 시험 실행은 조립 화면에 있는 다른 기능이다 ([시나리오.md](시나리오.md) §8.11)

#### 케이스 줄의 입력 칸 이름 (2026-09-30 · 2026-10-19 ⑫ 에 줄 입력 칸이 없어져 고침)

상세 칸(카탈로그 §8.1)과 실행 창(§8.10)은 **한 벌의 규칙**으로 칸 이름을 보인다. 두 자리가 다르게 그리면 같은 칸이 두 이름으로 보인다.

- ~~같이 보이는 칸들의 공통 앞부분을 뗀 짧은 이름을 쓴다~~ · ~~이름에 마우스를 올리면 전체 설명과 칸 이름(key)이 뜬다~~ — 좁은 줄 칸 몫이었고 줄 입력 칸이 없어지며 뺐다(2026-10-19 ⑫).
  **칸 이름은 전체 설명 그대로이고 코드의 칸 이름(key)은 어디에도 안 보인다**(말풍선에도 — 점검 7.12)
- **비워도 되는 칸에는 이름 옆에 「비워도 됨」을 붙인다** — 앞 판 「선택」은 「골라라」로 읽혔다(점검 N14)
- **입력 칸에 마우스를 올리면 지금 값 전체가 뜬다.** 칸이 좁아 잘린 값을 읽는 길이다. **비밀값 칸은 뜨지 않는다**
- **저장된 비밀번호가 있는 칸은 칸 안에 「입력됨」 안내 글씨를 둔다** — 값은 화면이 모르므로 글자로 보이지 않는다(위 「비밀값 칸」). 사람이 적기 시작하면 사라진다

### 8.3 실행 결과 목록
케이스 1건 = 1행. 디바이스별 결과는 판정 칸에 나란히 묶어 보여준다.

`TC ID | 케이스명 | PC 판정 | 모바일 판정 | [상세]`

디바이스별로 행을 쪼개지 않는 이유는 목록 길이가 두 배가 되고,
"PC는 되는데 모바일만 깨짐"이 한 줄에서 안 보이게 되기 때문이다.
지원하지 않는 디바이스의 칸은 `—`로 비운다.
필터는 판정(전체/PASS/FAIL/NA) + 디바이스(전체/PC/모바일) 둘이다. **판정 필터는 요약 띠의 「판정별 보기」 네 칸이 맡는다** (2026-10-08, 아래 「결과 화면은 요약 띠 → 실패 카드 → 통과 줄이다」).

**이 표 모양은 이제 실패가 없는 케이스의 줄이다** (2026-10-08). 실패가 있는 케이스는 아래 실패 카드로 간다(2026-10-11 부터 미확정 실패도).

**판정 칸과 디바이스 필터는 그 실행에 든 디바이스로 정한다** (2026-10-07). 브라우저 항목만 있는 실행은 위처럼 PC · 모바일이다 —
한쪽만 돌았어도 둘 다 둔다(지금과 같다). **Android 앱 항목만 있으면 「Android 앱」 칸 하나**, 둘이 섞이면 셋이다.
Android 앱 케이스는 다른 디바이스와 섞지 않으므로(공통/2-명세선언 §4) 앱만 도는 실행에 PC · 모바일 칸을 두면 모든 줄이 `—` 로 비고 그 필터는 늘 0건이다

**미확정 항목의 행에는 `미확정` 글자와 사유 한 문장을 붙인다** (2026-09-25). 사유는 항목에 박제된
`run_item.unconfirmed` 를 읽는다 — 지금의 케이스를 읽으면 확정된 뒤에 옛 실행이 바뀌어 보인다.
머리의 집계 배지는 §8.7 목록 줄과 같은 꼴이다 — **도는 동안만** 머리에 있고 끝나면 요약 띠가 맡는다(아래 「머리의 집계 숫자는 요약 띠로 옮겼다」). 세는 규칙은 §3.2 「미확정 항목도 그대로 센다」가 정본이다.

**소요시간은 독립 칸으로 두지 않는다** (2026-09-16 결정). 디바이스별 판정 배지 아래에 각각 적는다.
디바이스가 둘인 행에서 소요시간이 하나면 어느 쪽 것인지 알 수 없다.

RUN 머리에 실행 제목·실행 시각·실행자·대상 서버와 주소를 한 줄로 적는다.
이 값들은 실행에 박제된 것을 읽는다 (§6 `test_run`).
대상 서버가 빠지면 같은 케이스의 통과 두 건이 같은 조건으로 보인다.
**2026-10-19 ⑫ — 실행 정보는 이 머리 한 줄이 전부다.** 시작 방식 · 소요 · 디바이스도 이 줄에 붙고(`2026년 10월 16일 23:49 · 직접 실행 · 대상 서버 qa (http://demo:3002) · 맥시 · 7분 48초 · PC`),
옆 칸의 「실행 정보」 구획은 없앤다. 앞 판은 같은 값을 머리 부제와 옆 칸에 두 번 적었고, 창이 900px 보다 좁으면 옆 칸이 맨 아래로 내려가 실행 정보가 화면 끝(7,533px 중 6,567px 지점)에 묻혔다(점검 2.2).
빌드 번호 · 빌드 실행의 실행자 글은 §8.7 「줄」과 같고, 폰에 다른 빌드가 깔려 있었으면 머리 아래 `다른 빌드` 꼬리표를 단 한 줄이 선다(§3.11 「다른 빌드가 깔려 있었다」 · 2026-10-24 GAME-F1-13b).

**상자로 열었을 때는 증적 문서 정보도 이 머리 줄에 붙는다 (2026-09-22 추가).**
만든 시각·형식·받는 길, 그리고 **만드는 중 안내와 실패 사유**까지 넷 다 여기로 온다 (§8.4).
앞 판은 머리 아래에 따로 구획으로 세웠는데, 머리에 이미 「만들기」 버튼이 있어 **같은 말을 두 번** 했고
그 구획이 130px 을 먹었다 — 상자 635px 중 정보 UI 가 95% 를 차지해 **케이스 목록에 32px 만 남았다**
(2026-09-22 실측. 줄 하나가 101px 이라 한 줄도 안 들어갔다).

**넷을 다 옮긴다.** 문서 목록만 옮기면 「만드는 중입니다」와 실패 사유가 갈 곳을 잃는데,
그 글자가 영영 굳는 사고가 2026-09-19 에 한 번 났다 (`docs/archive/LEARNINGS.md`).
화면 전체로 열었을 때(`#/runs/:runId`)는 자리가 넉넉하므로 앞 판 그대로 구획으로 둔다.
**2026-10-08 부터 그 구획은 옆 칸의 「증적 문서」다** — 머리 줄에 붙이는 상자 쪽 규칙은 그대로다.
**2026-10-19 ⑫ — 옆 칸을 걷어 화면 전체 · 결과 칸 모두 머리 줄에 붙인다**(위 상자 쪽 규칙이 둘 다의 규칙이 됐다).

**직전 실행과 견줌·사유 묶음은 접어서 낸다 (2026-09-22 추가).** 기본이 접힘이고 눌러야 펴진다.
접고 펴는 것은 브라우저가 이미 하는 일이라 화면이 상태를 따로 들지 않는다.
**첫 실행에서 그 칸이 아예 없다는 규칙은 그대로다** ([공통/7-데모와-완료.md](../공통/7-데모와-완료.md) §7) —
접는 껍데기를 「있나 없나」 판정 **바깥**에 두면 내용 없는 한 줄이 남아 그 규칙이 깨진다.

**2026-10-08 접기를 그만뒀다 (PR #175 · 게이트 1).** 회귀 실패 · 기존 실패 · 해결 **수**는 요약 띠에, 「같은 사유로 실패」 · 「해결」 목록은 옆 칸에,
케이스마다의 변화는 실패 카드의 디바이스 머리에 붙는다. 접은 까닭은 상자 안 자리(케이스 목록에 32px)였는데,
카드가 변화를 직접 들어 접힌 목록이 할 일이 없어졌다. 상자 안에서는 옆 칸이 요약 띠 아래 접힌 줄 하나로 들어간다.
(2026-10-19 ⑫ — 옆 칸을 걷었다. 「같은 사유로 실패」는 「실패 유형」 칩 줄로, 「해결」은 직전 대비 줄 안으로 갔다 — 아래 「결과 화면은 …」)
**첫 실행에서 대비 칸이 아예 없다는 규칙은 그대로다.**

#### 결과 화면은 요약 띠 → 실패 카드 → 통과 줄이다 (2026-10-08 · PR #175 · UI 개편 묶음 2)

사용자가 「리포트 가독성 — 상단 요약, 실패 먼저」를 들어(2026-10-07) 시안 캔버스의 증거 카드형 C판을 골랐다(DESIGN.md 「컨셉」).
**끝난 실행**은 위에서 아래로 넷이고, 옆 칸(좁으면 아래)에 실행 정보 · 같은 사유로 실패 · 해결 · 증적 문서가 선다.
화면 전체(`#/runs/:runId`)와 상자(§8.7)가 **같은 부품**이다.
**2026-10-19 ⑫ 에서 옆 칸을 걷었다 — 결과는 늘 한 단이다.** 실행 정보는 머리 한 줄(위), 증적 문서는 머리의 단추, 「같은 사유로 실패」는 요약 띠 아래 「실패 유형」 칩 줄(아래 「실패 유형으로 묶는다」),
해결 목록은 요약 띠의 직전 대비 줄 안에 접힌 목록으로 간다. 화면 전체와 실행 기록의 오른쪽 결과 칸(§8.7 A안)이 같은 부품이다 — 결과 상자는 없어졌다.

- **API 애플리케이션 실행** (2026-10-20 API-F1-01) — 머리 아래에 `test_run.api_doc_note` 한 줄(「이 서버의 API 문서가 기준 서버 문서(버전 N)와 다릅니다. 배포 전일 수 있습니다」 · 「API 문서를 받지 못했습니다」). 항목은 케이스 확인 문장 아래 「응답 형식 검사」 줄을 따로 보이고 요청 · 응답 원문을 접어 둔다. 정본은 [API.md](API.md) §3.8 · §8.13 (2026-10-21 API-F1-08)
- **실패 카드의 「관련 요구사항」 줄 · 카드 맨 아래 「화면이 맞음 / 버그」** (2026-10-11 PRD-F5-03 · 시안 A — 2026-10-26 버튼은 테스트 작성 결정 목록으로 옮긴다) — 정본은 [리포팅.md](리포팅.md) 「실패 요구사항」.

- **실패 카드는 접어 둔다** (2026-10-19 ⑫ · 점검 2.3 — 앞 판의 「깨진 디바이스를 모두 펼친다」(2026-10-08)를 뒤집었다).
  앞 판은 한 쪽에 카드 20장을 다 펼쳐 실패가 몇 건 · 무슨 유형인지 훑으려면 화면 몇 장을 내려야 했다. 펼친 까닭(증거를 한 번에 본다)은 카드 머리의 유형 칩 · 사람 말 한 줄이 맡는다 —
  무엇이 왜 깨졌는지는 접힌 줄에서 읽고, 증거(확인 · 화면)는 볼 카드만 연다. 펼침은 화면이 들고 서버는 모른다. 쪽을 넘기면 다시 접힌다
- **실패 유형으로 묶는다** (2026-10-19 ⑫ · 점검 2.6) — 요약 띠 아래 「실패 유형」 칩 줄: `전체 7` · `기대 결과 불일치 6` · `요소 미검출 1` 처럼 이 실행에 있는 유형만 **카드(케이스) 수**와 함께. 누르면 그 유형 카드만 보인다.
  **거르기는 받은 쪽 안에서만 한다**(2026-10-19 WEB-F4-03) — 실패 카드 통로에 유형 조건이 없어서다(승인된 계약 밖 · 위 「디바이스 거르기도 서버가 한다」의 함정을 안다). 그래서 고른 유형의 카드가 다른 쪽에도 있으면 「이 쪽에 N건 · 이 유형 전체 M건 — 나머지는 다른 쪽에 있습니다」 한 줄을 달고, 이 쪽에 하나도 없어도 「실패한 케이스가 없습니다」는 내지 않는다.
  **디바이스를 거른 동안에는 칩 줄을 그리지 않는다** — 유형은 디바이스 차례로 첫 깨진 디바이스 것이라 고른 디바이스의 카드 머리 칩과 어긋난다. 서버가 유형 조건을 받게 되면 이 두 예외를 걷는다
  유형 이름 글자는 대시보드 「실패 유형」과 같다 — 정본은 리포팅 §8.12 「실패 유형」 · `web/DashboardTypes.tsx`.
  **카드 하나의 유형은 하나다** — 디바이스 차례(PC → 모바일 → Android 앱)로 첫 깨진 디바이스의, 처음 실패한 회차의 `failure.type` 이다. 카드 머리의 칩 · 사람 말 한 줄도 그 항목 것이다(다른 디바이스의 이유는 펼친 디바이스 머리에).
  유형은 대시보드 「실패 유형」(리포팅 §8.12)과 같은 다섯이고 같은 함수로 가른다. 앞 판의 「같은 사유로 실패」는 사유가 아니라 실패한 첫 확인 문장으로 묶은 것이라 문장마다 한 덩어리였다.
  재료는 [리포팅.md](리포팅.md) §7 `GET /api/runs/:runId/insights` 의 `실패유형들`, 카드마다는 `failures` 의 `failure`
- **통과율은 통과 ÷ (통과 + 실패 + 미실행)** 이다 — 항목 단위, 회차를 접지 않고, 미확정도 센다(2026-10-11 PRD-F4-02 · §3.2). 이 화면의 다른 수(판정별 보기 · 머리 집계)가 항목 단위라서다.
  분모가 0 이면(끝난 항목 없음) 도넛에 「—」, 아래에 「항목 없음」. 미확정을 빼던 앞 판의 「확정 항목 없음」 글과 4번 「미확정 묶음」 칸은 뺐다. **대시보드(리포팅 §8.12)는 회차를 접은 (실행, 케이스, 디바이스) 단위라 반복 실행에서는 같은 실행의 통과율이 두 화면에서 다를 수 있다.**
  중단 실행은 미실행이 분모에 들어 낮게 나오는 것이 맞다
- **실패 카드 순서는 서버가 정한다** — 케이스의 가장 무거운 디바이스 변화로 회귀 실패 → 기존 실패 → 견줄 앞 없음 → 그 밖, 같으면 `tc_id` 순. 쪽은 실패 **케이스** `카드쪽크기`(`reporting/failuresShape.ts`)개씩
- **디바이스 거르기도 서버가 한다**(`?platform=`) — 화면이 받은 쪽만 거르면 쪽마다 카드 수가 들쭉날쭉하고 쪽 수가 틀린다. 위 「거르는 일은 서버가 한다」와 같은 함정이다
- **판정이 섞인 케이스는 카드에만 있다** — PC 실패 · 모바일 통과면 카드 한 장이고 모바일은 그 카드 안 한 줄이다. 줄 목록에 또 나오지 않는다.
  그래서 판정별 보기 「통과」를 고르면 **실패가 없는** 케이스 중 통과 항목이 **하나라도** 있는 줄만 나와(「미실행」도 같은 꼴), 줄 수가 「통과 N」(항목 수)보다 적을 수 있다.
  실패 카드 안에만 있는 그 판정의 항목이 있으면 줄 목록 아래 「실패한 케이스 안의 항목 N건은 「전체」에서 카드로 봅니다」 한 줄을 단다 — 수와 목록이 어긋나 보이지 않게(2026-10-08 게이트 2).
  판정별 보기 「실패」는 카드만, 「통과」 · 「미실행」은 줄만, 「전체」는 카드 다음 줄이다
- **같은 실패는 한 칸으로 묶는다** — 한 카드 안에서 **입력과 모든 절차 · 확인(문장 · 판정 · 실제 값)이 다 같은** 디바이스들은 절차를 한 번만 그리고 머리에 「PC · 모바일」로 적는다(2026-10-08 게이트 2 — 「같은 확인 · 같은 실제 값」보다 좁혔다. 하나라도 다르면 따로 그린다).
  소요 · 최근 흐름 · 「상세」 링크는 디바이스마다 나란히, **실패 시점 화면도 디바이스마다** 이름을 달아 나란히 둔다 — 화면은 디바이스마다 다른 증거다. 실패한 절차에서 찍은 것만 「실패 시점 화면」이다(통과 절차에서 `capture` 로 찍은 것은 안 넣는다). 펼친 카드 안에서 같은 내용을 두 번 그리지 않는다
  **앱 항목은 그 아래에 팜 「화면 영상」 재생 칸과 「logcat.txt 받기 (n MB)」 링크를 단다** (2026-10-20 APP-F1-12 — 실패 카드에서는 2026-10-30 WEB-F7-13 부터 증거 칸의 탭이다. 탭 목록은 DESIGN.md 「증거 칸은 종류마다 탭만 다르다」) — 재료는 디바이스 칸의 `farm`(리포팅 §7). 영상은 한 조각이 100MB 를 넘어 누르기 전에는 받지 않는다(`preload="none"`). 항목 상세도 절차 아래에 같은 칸을 둔다. 없으면 칸도 없다
- **「상세」 링크는 디바이스 머리마다 둔다**(2026-10-08 게이트 2) — 카드 머리 하나로는 둘째 디바이스 · 카드 안 통과 디바이스의 상세(코드 뷰 · 다른 회차)로 갈 길이 없다. 카드 안 접힌 통과 · 미실행 줄에도 둔다
- **반복 회차는 처음 실패한 회차의 절차를 보이고** 「5회 중 2회 실패」를 단다. 나머지 회차는 상세에서 본다 — 위 「회차 요약」의 「어느 회차가 깨졌는지는 상세에서」와 같다
- **확인 문장 없이 깨진 항목은 오류 첫 줄만** 카드에 적는다(리포팅 §7 insights 의 대표 문장과 같은 자르기). 원문은 상세에만 둔다 — 아래 「러너에 닿지 못했을 때」의 「원문 오류는 목록에 쓰지 않는다」와 같은 까닭이고, 원문에 비밀값이 섞일 수 있다.
  **2026-10-19 ⑫ — 카드 머리의 이유는 서버가 준 사람 말 한 줄(`failure.reason`)이다.** 확인 문장이 하나라도 실패한 항목도 이유를 적는다(앞 판은 그때 오류 줄을 아예 안 내 카드 7장 가운데 6장에 이유가 없었다 — 점검 2.4). 오류 첫 줄은 펼친 카드의 「원문 보기」 안으로 접는다
- **최근 흐름 막대는 케이스 목록의 막대와 같은 부품 · 같은 칸 수다**(DESIGN.md 「최근 판정 흐름 막대」 · 칸 수 `최근몇건`). 다만 뜻이 다르다 — 목록 막대는 대상 서버를 안 가리고 지금 기준이고, 카드 막대는 **같은 대상 서버 · 이 실행까지**다. 그래서 막대 앞에 「<대상 서버> 서버 · 이 실행까지」를 적는다
- **기존 실패 글자는 변화가 「계속깨짐」일 때만** — 「기존 실패 · N회 연속」(N 은 막대 맨 앞에서 이어진 실패 수, 막대가 전부 실패면 「기존 실패 · N회 이상 연속」). 바로 앞 실행에 그 케이스가 없어 변화가 견줄 앞 없음이면 막대에 더 앞의 실패가 이어져도 글자를 내지 않는다
- **도는 동안에는 카드가 없다** — 지금처럼 진행 집계 · `실행 멈추기` · 줄 목록을 그리고 끝나면 카드로 바꾼다(통로도 끝나기 전에는 409 다). 실패가 0 건이면 카드 구획 대신 「실패한 케이스가 없습니다」 한 줄이고 통로를 부르지 않는다.
  **다만 이미 깨진 줄은 맨 위로 올리고 「도는 중에는 실패 카드가 없습니다 — 깨진 줄을 펼치면 이유를 볼 수 있습니다」 한 줄을 단다** (2026-10-19 ⑫ · 점검 2.21). 끝난 항목의 실패도 못 보던 것을, 줄의 `펼치기` 가 부르는 항목 상세(이유 · 절차)로 보게 한다. 카드 통로를 도는 중에도 열자는 것은 서버 약속을 바꾸는 일이라 하지 않았다 — 필요해지면 그때 계약으로 올린다
- **직전 대비 숫자는 누른다** (2026-10-19 ⑫ · 점검 2.20 — 앞 판은 눌러도 아무 일이 없었다). `회귀 실패` · `기존 실패` 는 누르면 실패 카드를 그 변화가 있는 것만 남기고(다시 누르면 푼다), 수가 0 이면 눌리지 않는다. 카드 거르기는 유형 칩과 같이 **받은 쪽 안에서만** 한다(통로에 조건이 없다) — 쪽이 여럿이면 「거른 결과는 이 쪽 카드 안에서만 보입니다 — 다른 쪽도 확인하세요」 한 줄을 단다.
  `해결` 은 누르면 아래 접힌 해결 목록을 연다. 「직전 실행에 있었으나 이번에 실행되지 않은 케이스 N건」은 `목록 보기` 로 이름을 보인다 — 견주기 응답에는 수만 있어서 누른 뒤에 직전 실행을 읽어 이번 실행과 (케이스, 디바이스)로 맞대 본다(서버 약속은 그대로)
- **직전 대비 낱말은 「회귀 실패 · 기존 실패 · 해결」이다** (2026-10-29 사용자 · PR #515) — 앞 판은 「신규 실패 · 연속 실패」였고 실행 기록 줄만 「계속 실패」라 같은 것을 두 이름으로 불렀다. 「신규 실패」는 새로 만든 케이스의 실패로도 읽혀 업계 말 회귀(regression)로 바꿨고, 직전에도 실패한 것은 「기존 실패」 하나로 합쳤다. 세는 규칙은 그대로다 — 회귀 실패는 직전에 실패가 아니던(통과 · 미실행) 케이스가 이번에 실패한 것이다(`새로깨짐`, 리포팅 §7 insights 판정표). 화면 · 대시보드 · 명세가 같은 낱말을 쓴다. 응답 값(`새로깨짐` · `계속깨짐` · `newFail` · `stillFail`)은 그대로다
- **판정한 카드와 안 본 카드를 가른다** (2026-10-19 ⑫ · 점검 2.24). 판정을 남긴 카드는 머리에 `판정함 · 버그` / `판정함 · 화면이 맞음` 꼬리표가 붙고(안 본 카드에는 달지 않는다 — 대부분이 안 본 카드다), 카드 위 `판정 안 한 카드 N` 칩이 안 본 카드만 남긴다. 이것도 받은 쪽 안에서만 거른다
- **다시 돌린 결과를 원래 카드에 잇는다** (2026-10-19 ⑫ · 점검 2.17). 이 실행을 「실패 N건 다시 실행」으로 다시 돌린 실행(`rerunOf` 가 이 번호 · origin RERUN — 2026-10-30 부터 반복 1 실행의 1건은 RERUN 이 아니라 아래 「한 건 실행이 붙은 실행」이다)이 있으면 그 케이스의 카드 머리에 `RUN 130에서 통과` / `RUN 131에서도 실패` / `RUN 131에서 미실행` 꼬리표가 붙고 누르면 그 실행에서 그 케이스 카드가 펼쳐진 채 열린다. 케이스마다 가장 새로 다시 돌린 것 하나다.
  **새 서버 통로 없이** 실행 목록의 `?origin=rerun`(§7)에서 `rerunOf` 가 이 번호인 끝난 실행을 새것부터 셋까지 읽고 각 실행 상세의 항목을 케이스별로 접어(하나라도 실패면 실패, 모두 통과여야 통과, 그 밖은 미실행) 얻는다. 한계 — 목록 첫 쪽만 본다. 원래 실행 뒤로 다시 실행이 아주 많이 쌓였으면 못 찾을 수 있고, 그때는 통로에 `rerunOf` 조건을 연다
- **한 건 실행이 붙은 실행** (2026-10-30 WEB-F7-02 · 시안 11판 — 규칙의 정본은 §3.2 「★ 한 건 실행은 묶음 실행에 붙는다」). 결과 화면의 모든 수는 지금 결과다(통로가 바꿔 끼워 준다 — §7 `GET /api/runs/:runId`).
  - 다시 돌려 **통과한 케이스는 실패 카드에서 통과 줄로 내려간다** — 카드는 지금 실패가 있는 케이스만 세운다(위 표 2). 시안 11판은 카드를 그 자리에 두고 머리만 바꿨는데 그러면 「실패 케이스 N건」과 카드 수가 어긋난다
  - 덮인 디바이스에는 `다시 실행해서 통과` / `다시 실행해서도 실패` 꼬리표와 다시 돈 시각 · 실행자를 단다. 펼치면 다시 돈 항목의 절차 · 확인 · 화면이고, 그 아래 `지난 결과 보기` 가 원래 항목(`rerun.original`)을 접힌 채로 연다.
    시안 이름 「어제 결과 보기」는 어제가 아닐 때도 있어 쓰지 않는다. 앞 이름 「원래 결과 보기」는 2026-10-30 사용자가 「지난 결과 보기」로 바꿨다(같은 뜻 · WEB-F7-18)
  - 위 「다시 돌린 결과를 원래 카드에 잇는다」(실패 N건 다시 실행 · 새 RUN)와 다르다 — 그쪽은 수를 바꾸지 않고 다른 실행으로 가는 꼬리표다
  - 화면 모양은 WEB-F7-12 가 DESIGN.md 에 적는다
- **주소로 카드를 펼친 채 연다** (2026-10-19 ⑫ · 점검 6.1) — `#/runs/fn?run=N&tc=<tcId>` 는 그 실행의 그 케이스 실패 카드를 펼치고 화면에 맞춘다. 카드가 1쪽에 없으면 그 카드가 있는 쪽으로 간다(카드 통로에 케이스 조건이 없어 쪽을 넘기며 찾는다). 대시보드의 회귀 실패 줄 · 다시 돌린 결과 꼬리표가 쓴다. `tc` 는 처음 연 그 실행에서만 듣고 주소창에서는 곧 사라진다
- **머리의 집계 숫자는 요약 띠로 옮겼다** — 머리 부제의 상태 글자(완료 · 중단 · 진행 중)와 바로 아래 요약 띠가 「끝났나 보기」를 맡는다. 같은 숫자를 두 번 두지 않는다. 휴대폰에서는 `실패 N건 다시 실행` 이 아래 탭 위에 붙는다(공통/5-화면공통 §8 「휴대폰 화면」)
- ~~**상자 안에서는 제목 · 닫기만 고정**하고 요약 띠부터 전부 스크롤 칸이다 — 고정 영역이 크면 목록 자리가 32px 로 줄었던 2026-09-22 의 일이 되풀이된다. **상자는 늘 한 단이다** — 옆 칸이 요약 띠 아래 접힌 줄 하나라 둘째 단이 없다. 화면 전체는 한 단 · 두 단을 창 폭이 아니라 **그릇 폭**으로 가른다.~~ (2026-10-08 판 — 고정 영역을 작게 두는 까닭은 결과 칸에도 그대로다)
  **2026-10-19 ⑫ — 상자는 없어지고 옆 칸도 걷어 화면 전체 · 결과 칸 모두 한 단이다.** 결과 칸(§8.7 A안)은 머리(제목 · 머리 한 줄 · 「실패 N건 다시 실행」 · 증적)를 고정하고 요약 띠부터 스크롤한다
- **실패 카드 구획 위에 「통과 케이스로」 건너뛰기를 둔다**(게이트 1 제안 15) — 실패가 수십 건이면 카드가 길어 줄 목록까지 내려가기 멀다. 실패 카드와 줄 목록이 둘 다 있을 때만. 쪽을 넘기면 포커스를 카드 목록 머리로 옮긴다
- 판정 표기 · 색은 DESIGN.md 를 따른다(시안의 옅은 실패 배지가 아니다)
- **머리에 「실패 N건 다시 실행」을 둔다** (2026-10-07 시안 · 2026-10-09 반영, UI 개편 묶음 4 · PR #175 에서 넘겨받음). N 은 그 실행에서 **한 번이라도 실패한 케이스 수**다(디바이스 · 회차를 접는다).
  누르면 그 케이스들로 실행 창(§8.10)이 열리고 대상 서버는 그 실행의 서버로 골라져 있다. 머리의 주 버튼이다(`리포트 생성` 단추는 테두리 버튼).
  **디바이스는 실패한 디바이스만 담는다** (2026-10-19 ⑫ · 점검 2.16 — 앞 판은 PC 가 통과여도 케이스가 선언한 디바이스를 전부 돌렸다). 통과한 디바이스까지 돌리면 실패 때와 다른 조건이라 「다시 하니 통과」가 디바이스를 더 돌린 탓인지 알 수 없다.
  값은 지금의 저장값 · 코드 기본값으로 열린다 — **실패 때 쓴 값 그대로 돌리지는 않는다**(서버가 값을 기억해야 한다). 대신 그 실행이 시작된 뒤 저장값이 바뀐 케이스가 있으면 창 위에 「실행 뒤에 저장값이 바뀐 케이스 <번호> — 실패 때와 다른 값으로 돕니다」를 알린다
  **끝난 실행 · 실패가 있을 때 · 그 실행 서비스의 `(실행, write)` 일 때만** 보인다. ~~**상자 안에서는 두지 않는다** — 상자 위에 창이 겹치면 포커스를 가두는 장치가 둘이 된다(DESIGN.md 「모달」).~~ (상자가 없어져 이 예외도 없어졌다 — 아래)
  **2026-10-19 ⑫ — 실행 기록의 오른쪽 결과 칸(§8.7 A안)에도 둔다.** 결과 칸은 상자가 아니라 창이 겹쳐도 포커스 가두기가 하나다. 목록 → 결과가 주된 길인데 앞 판은 거기서 끊겼다(점검 2.8). 누르면 `rerunOf` 를 실어 건다(§8.10)

아직 안 끝난 항목의 `진행 중` 배지와 2초마다 다시 묻는 자동 갱신은 **이미 만들어져 있다.**
여기에 `ABORTED`를 멈춤 조건으로 더한다 (2026-09-16 결정).
지금 조건이 `status !== 'FINISHED'`라, 중단 기능이 들어오면 중단된 실행에서 갱신이 영원히 멈추지 않는다.

#### 실행 멈추기 (2026-09-16 결정)

실행이 진행 중일 때만 RUN 머리에 `실행 멈추기` 버튼을 둔다. 끝난 실행에는 보이지 않는다.
되돌릴 수 없으므로 누르면 한 번 더 묻는다.

- **대기 중인 항목과 이미 돌고 있는 항목을 둘 다 끊는다.** 대기 중인 것만 취소하면
  5분짜리 케이스가 진행 중에는 버튼이 아무 일도 안 하는 것처럼 보인다. 러너에 끊으라고 알리는 통로는 §5.2다
- 멈춘 실행은 머리에 `중단`을 달고, 돌지 못한 항목은 미실행 배지 옆에 사유(`사용자가 멈춤`)를 적는다.
  사유 없이 미실행으로 두면 러너 고장과 구분되지 않는다
- 버튼을 보일지 말지도, 자동 갱신을 멈출지 말지도 같은 값(`status`)으로 정한다. 화면이 따로 상태를 들지 않는다

#### 회차 요약 (2026-09-16 결정)

반복 횟수를 2 이상으로 준 실행에서는 한 케이스·한 디바이스에 항목이 여러 건 쌓인다.
**행 구조는 바꾸지 않는다.** 판정 칸이 요약이 된다.

| 회차 | 판정 칸 |
|------|--------|
| 1회 | 지금과 같은 판정 배지 |
| N회 전부 통과 | `5/5 통과` (통과 색) |
| N회 중 하나라도 실패 | `3/5 통과` (실패 색) |

- 다섯 번 중 세 번만 통과한 테스트는 **믿을 수 없는 테스트**다. 통과 색으로 칠하지 않는다
- 소요시간은 회차 평균을 적고 옆에 `평균`을 붙인다. 회차마다 값이 다른데 하나만 적으면 어느 회차 것인지 알 수 없다
- 어느 회차가 깨졌는지는 상세에서 본다. 목록은 회차를 펼치지 않는다

#### 러너에 닿지 못했을 때 (2026-09-17 결정)

설계서에 **실행이 러너에 닿지 못했을 때 사람이 보는 것**이 없었다.
적어 두지 않으면 빈 화면이나 원문 오류가 그대로 나온다.

- 돌지 못한 항목은 `NA`로 닫고 미실행 배지 옆에 사유를 적는다 — `러너에 닿지 못했습니다`.
  사용자가 멈춘 것(`사용자가 멈춤`)과 **같은 자리에 다른 문장**으로 적는다. 둘을 구분할 수 없으면 원인을 못 찾는다
- RUN 머리에 한 줄을 띄운다 — `러너에 닿지 못해 N건이 돌지 못했습니다`
- **원문 오류(스택·주소·포트)는 목록에 쓰지 않는다.** 항목 상세의 접힌 자리에 둔다.
  이 도구의 전제는 「코드를 몰라도 쓴다」다 (§1)
- 실행 자체는 `FINISHED`로 닫는다. `ABORTED`는 사람이 멈춘 것이다 — 둘을 섞으면
  중단 통계가 러너 고장으로 오염된다

#### 어떤 값으로 돌린 결과인지 목록에서 바로 본다 (2026-09-16 결정)

케이스명 아래에 그 항목이 실제로 쓴 입력값과 기대값을 한 줄로 적는다.
상세로 들어가야만 보이면 "어떤 값에서 깨졌는가"를 줄 사이에서 비교할 수 없다.

- **사람이 읽을 라벨로 적는다.** `아이디 testuser · 응답 코드 200` 처럼 라벨과 값을 붙여 쓴다. JSON 원문을 그대로 붙이지 않는다
- 라벨과 값은 **항목에 박제된 스냅샷**에서 읽는다 (§3.3). 카탈로그의 지금 스키마에서 읽으면
  설명 문구를 고쳤을 때 과거 행의 라벨이 따라 바뀐다
- **값이 빈 칸은 박제된 스키마의 기본값으로 적는다** — 값을 안 고치고 돌린 항목도 실제로 쓴 값이 보인다. 정본은 [리포팅.md](리포팅.md) §3.3 「값이 빈 칸은 박제된 스키마의 기본값으로 보인다」다
- 비밀값 꼬리표가 붙은 칸은 `********`로 적는다 (§4.1)
- 한 줄을 넘으면 뒤를 `…`로 자른다. 전부는 상세에서 본다
- 입력값이 없는 케이스(`params: null`)는 이 줄을 아예 만들지 않는다. `입력 없음`을 모든 행에 적으면 목록이 시끄러워진다

§8.1의 "JSON 원문을 목록에 노출하지 않는다"는 케이스 목록 규칙이고 여기에는 적용되지 않는다.
라벨과 값을 붙여 쓴 한 줄은 JSON 원문이 아니다.

#### 종류는 사이드바 하위 메뉴로 가른다 (2026-09-28 탭 → 2026-10-02 하위 메뉴)

- **탭마다 다른 줄이다.** 케이스 탭은 이 절의 칸 그대로, E2E 탭은 `시나리오 이름 · 버전 | RUN ID · 실행 시각 · 대상 서버 · 실행자 · 상태 | 판정 · 단계 N개 · 멈춘 단계` 다 (2026-10-20 ⑬-5 — 앞 판은 맨 끝에 `[결과 보기]` 가 있었다. 아래 「E2E 탭도 A안이다」) — 멈춘 단계는 `N번에서 멈춤`, 전부 통과면 `모두 통과` 다. 글자의 정본은 시나리오 §8.11 「화면 글자」 표 (2026-10-06 사용자)
  - **판정 칸은 판정 칩이 맨 위다** (2026-10-16 E2E-F1-20 시작 질문 사용자) — 줄의 `verdict`(시나리오 §7 「판정 접기」)를 결과 화면 · 시나리오 목록과 같은 칩(`통과` · `실패` · `미실행`)으로 세우고, 그 아래 단계 수 · 멈춘 단계를 둔다. 표머리는 `판정` 이다. 도는 중이면 칩 대신 같은 줄 상태 글자와 같은 `진행 중` 이다 — 한 줄에 다른 말이 둘 서면 다른 상태로 읽힌다. 단계 기록 없이 닫혀 멈춘 단계가 없는 실행은 `모두 통과` 를 쓰지 않는다(그 판정은 `미실행` 이다).
    앞 판(2026-10-06 ~ 10-16)은 칩이 없어 실패와 판정 없음(시간 초과 · 강제 종료)이 둘 다 `N번에서 멈춤` 이고 띠 색으로만 갈렸다 — 색만으로 판정을 전하지 않는다(아래 「지킬 것」)
  - **대상 서버를 시각 옆에 적는다** — 케이스 탭과 같은 자리 · 같은 글자(`대상 서버 <서버>`)다. 이름이 같은 실행을 가르는 것이 위 「더할 것 2」의 까닭이다
  - **줄은 케이스 탭과 같은 A안 줄 격자(띠 · 제목과 작은 글 · 판정)다** (2026-10-20 ⑬-5 사용자 — 앞 판 2026-10-16 E2E-F1-23 은 번호 · 이름 · 오른쪽 셋에 `결과 보기` 를 오른쪽에 같이 세웠다) — `RUN <번호>` · 실행 시각 · 대상 서버 · 실행자 · 상태는 이름 · 버전 아래 작은 글 맨 앞부터 적는다(목록 칸이 좁아 번호 칸을 따로 두지 않는다 — 케이스 탭과 같다). 표머리는 케이스 탭과 같은 `실행` · `판정` 둘이라 탭을 오가도 칸 자리가 안 갈린다
- 거르개·검색은 **보고 있는 탭 안에서만** 센다(머리 집계 띠는 두 탭 모두 뺐다). 서버가 `?kind=` 로 거른다 (§7)
- **E2E 탭도 A안이다** (2026-10-20 ⑬-5 사용자 — 시안 https://claude.ai/artifact/1KtHuT1Mi4MksxL5XzPGqG 의 A. B 오른쪽 서랍 · C 줄 안 단계 띠와 펼치기는 고르지 않았다) — 위 「A안」 그대로 왼쪽 목록 · 오른쪽 결과 칸이고, 줄 전체를 누르면 결과 칸이 그 실행으로 바뀐다. 주소는 `#/runs/e2e?run=21044&state=failed` 꼴이고 거르개는 찾기 · 상태(전체 · 진행 중 · 실패)뿐이다.
  결과 칸은 시나리오 결과(시나리오 §8.11 「실행 결과」)와 같은 부품이다 — 칸 머리에 제목 · `RUN <번호>` · 부제 · 판정 칩 · 다시 실행 · 리포트 단추가 고정되고 그 아래(다음 할 일 줄 · 실행 정보 · 단계별 결과)가 스크롤한다. 칸 안에는 돌아갈 곳 고리가 없고, 다시 실행하면 화면을 떠나지 않고 새 실행을 칸에 연다.
  **머리 집계 띠도 뺀다** — 케이스 탭이 뺀 까닭(위 「A안」)이 같다. 앞 판(2026-10-19 ⑫)은 「E2E 탭은 A안이 바꾸지 않는다」였고 줄의 `결과 보기` 가 상자를 열었다 — 같은 메뉴 아래 세 탭 가운데 E2E 만 다른 모양이었다(사용자 지적 14)
- **E2E 탭은 미확정이 섞인 통과도 통과로 센다** (2026-10-11 PRD-F4-02 · §3.2) — 통과 색으로 칠하고 그 줄에 `미확정` 꼬리표만 단다. 앞 판(2026-10-06)의 「미확정 포함」 상태 글 · 집계 띠 `통과 · 미확정 포함 N`(`summary.unconfirmedPass`)은 뺐다. 규칙의 정본은 시나리오 §7 「판정 접기」
- 기본 탭은 `테스트 케이스` 다. 탭은 주소에 남긴다 — 새로고침·뒤로 가기에 풀리면 안 된다

#### 칸마다 이름을 단다 (2026-09-22 결정)

목록 맨 위에 표머리 줄을 두고 위 칸 이름을 적는다. 이름이 없으면 각 칸이 무엇인지 모른다.
표머리의 색은 껍데기 색이다 — 자리는 [공통/5-화면공통.md](../공통/5-화면공통.md) §8 이 정본이다.

**좁은 화면에서 표머리를 감추지 않는다.** 이 화면은 휴대폰에서 여는 화면이다(공통/5-화면공통 §8 「휴대폰 화면」).
감추면 거기서 칸 이름이 통째로 사라진다.
줄이 세로로 접히면 **표머리 대신 줄마다 라벨을 붙인다.**
**휴대폰(창 620px 미만)의 카드 줄도 이 규칙이다** (2026-10-30 · 공통/5-화면공통 §8 「휴대폰 화면」) — 칸 이름 줄은 숨겨도 값만으로 뜻이 안 서는 칸은 줄마다 라벨을 붙인다.
앞 판은 「케이스 목록([카탈로그.md](카탈로그.md) §8.1)은 휴대폰에서 열지 않아 감춰도 된다 — 둘을 같게 만들지 않는다」였다. 2026-10-30 부터 케이스 목록도 휴대폰에서 열려 그 까닭이 없어졌다 — 휴대폰의 케이스 목록도 이 규칙을 따른다. 쌓인 줄의 넓은 PC 창 모양은 카탈로그 §8.1 그대로다.

누르면 **이 목록 위에 상자가 열리고** 그 안에 §8.3 실행 결과가 들어간다.

따로 만들면 같은 화면에서 상자가 두 번 뜨고, 그것은 「모달은 아껴 쓴다」(DESIGN.md)와 부딪힌다.

- **진행 중에 그리는 것** — 진행 막대 · `{끝난 수} / {전체 수} 완료` · **진행 중인 항목마다** 이름과
  지금 몇 번째 절차를 몇 초째 하고 있는지 · 방금 끝난 항목 몇과 실패 사유 한 줄
- **막대는 집계(`counts`)가 나눈 그대로 쓴다** — 통과 · 실패 · 미실행 · 남은 것.
  **「실행 중」과 「대기」로 가르지 않는다.** 그 둘을 가를 신호가 저장된 값에 없다 —
  `run_item` 행은 실행을 걸 때 한꺼번에 만들어지고, 항목이 실제로 시작될 때 시각을 고치지 않는다.
  가른 이름으로 부르면 **없는 구분을 있는 척하게 된다** (2026-09-21 실측)
- **미확정 항목은 막대에서 따로 칸을 두지 않는다** (2026-10-11 PRD-F4-02 · §3.2). 통과 · 실패 · 미실행 · 진행 칸이 미확정까지 세서 칸의 합이 `counts.total` 이다.
  미확정이 있으면 글자 끝에 「그중 미확정 N건」을 붙인다. **완료 모달과 Slack 알림의 숫자 줄도 같은 꼴이다** — 미확정이 없으면 쓰지 않는다.
  앞 판(2026-09-25)은 끝난 미확정을 `미확정` 칸 하나로 떼고 `미확정 5(통과 4 · 실패 1)` 로 적었다
- **진행 중인 항목은 러너가 답한 그대로다. 화면이 고르지 않는다** (2026-09-21 개정).
  admin이 러너에게 물어(§7 의 `GET /api/runs/:runId/progress`) 돌아온 것을 **전부** 그린다 —
  동시 실행이 여럿이면 여럿이 뜬다. 정확히 아는데 하나만 그리면 **알면서 감추는 것**이다.
  항목마다 `절차 N · 제목`과 **머문 시간**을 적고 **제한 시간을 나란히** 둔다 —
  「느린 것」과 「멈춘 것」을 가르는 신호가 그것이고, **전체 절차 수(분모)는 만들 수 없다** (§5.1).
  러너가 아직 첫 절차를 안 흘렸거나 물음이 실패한 순간에는 **절차 줄만 빠지고** 항목 이름은 남는다.
  *앞 판은 이 자리에서 진행 중인 항목을 **근사치**라 부르고 「정확해지려면 러너가 절차마다 알려 주는
  통로가 필요한데 아직 없다」고 적었다. 그 통로가 생겨(§5.2) 사실이 아니게 됐다 (2026-09-21).
  바로 위 문단의 「없는 구분을 있는 척하지 마라」는 그대로 산다 — 분모를 만들지 않는 근거가 그것이다.*
- ~~실행을 건 직후 **자동으로 뜬다.** 단, **이미 끝난 실행을 열 때는 뜨지 않는다** —
  증적을 만들러 옛 실행에 들어가는 길목마다 상자가 서면 안 된다~~ (2026-10-19 ⑫ 에 뒤집었다 — 바로 아래)
- **2026-10-19 ⑫ — 자동으로 뜨지 않는다. 누를 때만 뜬다.** 실행을 걸면 실행 기록의 오른쪽 결과 칸(§8.7 A안)이 그 실행으로 열리고, 결과 칸 머리가 「12/40 완료 · 약 8분 남음」을 적는다.
  그 글을 누르면 이 상자가 뜬다. 진행 숫자가 늘 머리에 있어 상자가 화면을 가릴 까닭이 없어졌다(점검 2.14). 끝났을 때의 완료 모달은 아래 규칙 그대로 — 결과 칸에서 그 실행을 보고 있으면 「그 실행을 보고 있을 때」다
- `{끝난 수} / {전체 수} 완료` 옆에 **남은 시간**을 적는다 — 아래 「남은 시간」

#### 남은 시간 (2026-10-11 사용자 · WEB-F3-04)

진행 상자 · 본문 위 알림 줄(공통/5-화면공통 §8 「알림」)이 `약 6분 남음 · 14:32 종료 예상` 을 적는다. 사용자 불편 「실행 예상 시간 · 진행 상태가 안 보인다」의 답이다.

- **단위는 항목(건)이다.** 절차 수로 세지 않는다 — 전체 절차 수(분모)는 만들 수 없다(위 「진행 중에」)
- 안 끝난 항목마다 예상 = 같은 케이스 · 같은 디바이스의 **다른 실행**에서 끝난 항목 최근 5건 소요 시간의 중간값.
  지난 기록이 없는 항목은 **이번 실행에서 끝난 항목 평균**으로 채운다. 그것도 없으면 셀 수 없다 — 화면은 `남은 시간 계산 중`
- 남은 시간 = max(예상 합 ÷ 칸 수, 가장 긴 케이스의 예상 합) − (지금 − 기준 시각), 0 아래로 내리지 않는다. 같은 케이스 항목은 하나씩 돌아(§3.2 「같은 케이스 항목」) 칸을 나눠 써도 한 케이스의 합보다 빨리 못 끝난다(2026-10-13 PRD-F9-36). **실행 중과 대기를 가르지 않는다** — 안 끝난 것을 다 더한다(위 「진행 중에」의 같은 근거)
  - **기준 시각**은 이번 실행에서 마지막으로 끝난 항목의 시각(없으면 실행 시작)이다. 항목이 끝날 때마다 다시 맞추고 그사이에는 줄어든다 — 빼지 않으면 마지막 10분짜리 항목이 도는 내내 「약 10분 남음」에 머문다(2026-10-11 코드 검토)
  - **칸 수** = min(동시 실행 수, 안 끝난 케이스 수) ÷ 지금 도는 실행 수(1 아래로 안 내림) — 동시 실행 칸은 실행끼리 나눠 쓴다. 같은 케이스 항목은 하나씩 돌아(§3.2 「같은 케이스 항목」) 케이스 하나가 칸 하나다(2026-10-13 PRD-F9-36). 줄 순서와 안드로이드의 따로 선 줄은 셈에 넣지 않는다(어림이다)
- 중단으로 닫힌 항목(`duration_ms = 0`)은 셈에 넣지 않는다
- 셈은 admin 이 한다 — 통로 `GET /api/runs/:runId/progress` 의 `remainingMs` · `GET /api/notifications` 의 도는 실행(공통/3-공유계약 §7.1).
  지난 기록 중간값은 실행마다 한 번 읽어 둔다(2초마다 다시 읽지 않는다). 코드는 `apps/admin/src/execution/eta.ts`
- 화면 글자 — 60초 미만이면 `1분 미만 남음`, 셀 수 없으면 `남은 시간 계산 중`, 그 밖은 `약 {시간} 남음 · {시각} 종료 예상`

#### ★ 여는 이유는 둘이다 — 하나로 합치지 않는다 (2026-09-21 신설)

**상자는 하나지만 「왜 열렸나」는 둘이고, 닫는 뜻도 둘이다.**

| 사람이 닫았다 | 뜻 | 그래서 |
|---|---|---|
| **진행** 상자를 닫았다 | 「진행 중에는 결과 목록을 보고 있을게」 | **끝났을 때 완료 모달을 받는다** |
| **완료** 상자를 닫았다 | 「끝난 건 알았어」 | 그 실행에 대해 다시 뜨지 않는다 |

**둘을 한 상태로 합치면 진행 상자를 닫은 사람이 완료 알림을 영영 못 받는다.**
본문 위 알림 줄(공통/5-화면공통 §8 「알림」)도 그를 구하지 못한다 — 그 줄은 「그 실행 화면에 있던 사람은 모달로 이미 알았다」를
전제로 같은 자리를 두 번 알리지 않기 때문이다(모달로 알린 실행은 읽음이 된다).

진행 상자를 **열어 둔 채** 실행이 끝나면 **한 상자가 그대로 내용만 바꾼다.** 두 번 뜨지 않는다.

**진행 상자를 닫으면 진행 알약으로 줄어든다 (2026-10-30 사용자 · 시안 11판 · 진행판 WEB-F7-10)** — PC 는 본문 오른쪽 아래, 휴대폰은 아래 탭 위에 `RUN <번호>` · 진행 막대 · `<끝난 수> / <전체>` 가 남는다(모양은 DESIGN.md 「모달」 「창이 아닌 떠 있는 것」). 다른 화면으로 옮겨도 남고, 누르면 진행 상자가 다시 열린다.
**알약이 떠 있는 실행은 끝나면 어느 화면에서든 완료 모달이 다시 뜬다** — 알약은 「이 실행을 지켜보고 있다」는 표시라서, 아래 「완료 모달」의 「그 실행의 결과 화면에 있을 때만」의 예외다.
앞 판은 진행 상자를 닫으면 아무것도 남지 않아, 다른 화면으로 가면 그 실행이 어디까지 왔는지 알림 줄에서만 볼 수 있었다.

#### 완료 모달

**그 실행의 결과 화면(§8.3)에 있을 때만 뜬다.** 다른 화면에서는 띄우지 않는다 — **예외 하나, 그 실행의 진행 알약이 떠 있으면 어느 화면에서든 뜬다**(2026-10-30 · 위 「진행 상자를 닫으면 진행 알약으로 줄어든다」).
모달은 하던 일을 가로막는 장치라서, 사람이 **그 실행을 보고 있을 때만** 막을 자격이 있다.
다른 화면에 있는 사람은 §8의 알림 줄이 받는다.

```
┌──────────────────────────────────────┐
│  RUN 2111 실행이 끝났습니다           │
│  결제 회귀 · 대상 서버 qa · 12분 04초  │
│                                      │
│   8 통과    1 실패    1 미실행        │
│                                      │
│  실패한 케이스                        │
│   PAY-002 한도를 넘는 카드로 결제하면… │
│                                      │
│              [닫기]  [결과 보기]      │
└──────────────────────────────────────┘
```

- **실패한 케이스를 모달 안에 적는다.** 숫자만 보여주면 사람이 결국 목록을 뒤져야 한다.
  다섯 건을 넘으면 앞의 다섯만 적고 `외 N건`을 붙인다.
  **줄은 누르면 그 케이스의 깨진 회차 항목 상세로 간다**(2026-10-19 ⑫ · 점검 5.3 — 앞 판은 눌러도 아무 일이 없었다). 가면서 모달은 닫고 「봤다」로 적는다
- 판정은 **색과 글자를 같이** 쓴다 (DESIGN.md). 숫자만 색으로 칠하지 않는다
- 리포트는 이 모달에서 만들지 않는다 — 결과 화면 머리의 `리포트 생성`(도메인/리포팅 §8.4)이 맡는다. 앞 판의 `증적 문서 만들기` 단추는 코드에 들어간 적이 없다. 모달의 단추는 `결과 보기` · `닫기` 다
- `결과 보기`는 모달을 닫는다. 이미 그 화면에 있으므로 다른 곳으로 보내지 않는다
  **한 건 실행은 예외다** (2026-10-30 WEB-F7-02 · §3.2) — 그 실행 화면이 없어서 `결과 보기` 가 붙은 실행의 그 케이스 카드(`#/runs/fn?run=<attachedTo>&tc=<tcId>` — 종류는 그 케이스 것)로 가고, 붙은 곳이 없으면 케이스 상세 「실행 기록」으로 간다.
  끝난 글은 「RUN N 결과에 다시 실행으로 붙었습니다 · 실패 11 → 10」 · 「이 케이스 상세의 「실행 기록」에 남았습니다」 꼴이다(글자는 WEB-F7-12)
- **닫는 길을 셋 둔다** — 버튼 · `Esc` · 바깥 누르기. 포커스는 모달 안에 가두고 닫으면 원래 자리로 돌려준다
- 한 번 닫은 모달은 그 실행에 대해 **다시 뜨지 않는다.** 새로고침해도 마찬가지다
- 중단된 실행(`ABORTED`)에도 뜬다. 「멈췄습니다」로 제목만 바꾼다 — 사람이 멈춘 것도 끝난 것이다

#### Slack 알림

**웹훅으로 보낸다.** 서비스마다 웹훅 주소를 따로 둔다 (§6 `service.slack_webhook`) —
결제팀과 회원팀이 같은 채널을 보지 않는다. 주소는 설정 화면에서 넣는다 (§8.8).

```
[실패] 결제 서비스 · RUN 2111 · 결제 회귀
통과 8 · 실패 1 · 미실행 1 · 12분 04초 · 대상 서버 qa · 실행자 김철수

실패한 케이스
  PAY-002  한도를 넘는 카드로 결제하면 거절 사유가 안내된다

결과 보기 <주소>      증적 문서 <주소>
```

- **머리에 판정을 글자로 적는다** — `[실패]` · `[통과]` · `[중단]`.
  Slack 은 색 막대를 지원하지만 색만으로 전달하지 않는다는 규칙은 여기서도 같다.
  판정은 미확정까지 모든 항목으로 가른다 — 미확정 머리 변형은 없다(2026-10-11 PRD-F4-02 · 앞 판의 `[통과 · 미확정 실패 N]` · `[미확정]` · `[미확정 · 실패 N]` 은 뺐다).
  숫자 줄 끝에 「그중 미확정 N건」, 실패 목록은 `tc_id` 차례 하나이고 미확정 실패에 `(미확정)` 꼬리만 단다. 규칙은 §3.2 「미확정 항목도 그대로 센다」
- **요약 페이지를 새로 만들지 않는다.** `결과 보기` 는 §8.3 그 화면의 주소다.
  주소의 앞부분은 배포 설정 `PLATFORM_PUBLIC_URL` 이 준다 (§9) — 서버는 자기가 바깥에서
  어떤 주소로 열리는지 모른다. **그 값이 비어 있으면 링크 줄을 빼고 본문만 보낸다**
- **증적 문서 주소는 이미 만들어져 있을 때만** 넣는다. 없으면 그 줄을 빼고 결과 보기만 남긴다.
  형식이 여럿이면 **PDF 를 먼저** 고른다 — 제출물이고 눌러서 바로 보인다 (§8.4). PDF 가 없으면 가장 최근 것.
  알림 때문에 증적을 자동으로 만들지 않는다 — 만들기는 실행 `write` 부터라는 규칙(§3.5)을
  스케줄러가 우회하는 자리가 된다
- **주소는 주소일 뿐이다.** 눌러 들어가면 로그인이 여전히 막는다 (§7). 알림은 새 구멍을 내지 않는다

#### 언제 보내나

| 누가 돌렸나 | Slack |
|------------|-------|
| **사람** | 실행 설정에서 **고른다.** 기본은 **꺼짐** (§8.2) |
| **스케줄러** (정기 실행) | 웹훅이 설정돼 있으면 **항상 보낸다** (§9.2) |
| **사람 · 한 건 실행** (2026-10-30 WEB-F7-02) | **보내지 않는다** — 실행으로 서지 않아(§3.2 「★ 한 건 실행은 묶음 실행에 붙는다」) 알림에 걸 실행 화면이 없다. 실행 창의 그 칸도 숨긴다 |

- **사람이 돌릴 때 기본을 끄는 이유** — 자기 확인용으로 한 번 돌려 보는 일이 잦다.
  그것까지 팀 채널에 흘리면 채널이 소음이 되고, 소음이 된 채널은 아무도 안 본다.
  그리고 지금 화면 앞에 있으면 **모달이 이미 알려 준다.** 켜는 것은 「자리를 뜰 때」의 선택이다
- **정기 실행이 항상 보내는 이유** — 새벽에 진행되는 실행을 볼 사람이 없다.
  아침에 Slack 에서 보는 것이 유일한 경로다. 정기 실행에 알림이 필요한 이유가 그것이다
- **웹훅이 설정되지 않은 서비스에서는 이 칸이 아예 보이지 않는다** (§8.2).
  못 하는 것은 흐리게 두지 않는다 (§8)

#### 보내지 못했을 때

**실행은 이미 끝났다. 알림이 실패해도 실행은 실패가 아니다.**

- `test_run.notify_slack` 이 「보내기로 했나」, `notified_at` 이 「실제로 보냈나」다 (§6).
  둘을 갈라 둬야 **보낼 생각이 없었던 것**과 **보내려다 실패한 것**이 구분된다
- 실패하면 결과 화면 머리에 한 줄 — `Slack 알림을 보내지 못했습니다`.
  원문 오류는 적지 않는다. 다시 시도하지 않는다 — 사람이 결과를 이미 볼 수 있는 자리에 있다
- **재시도 줄을 만들지 않는다.** 알림은 편의지 기록이 아니다. 기록은 `test_run` 에 이미 있다

#### 새 부품이 필요 없다

Slack 웹훅은 HTTPS 로 JSON 을 한 번 보내는 것이고 Node 20 에 `fetch` 가 들어 있다 (§9.1).
비밀번호 해시를 `crypto.scrypt` 로 해결한 것과 같은 자리다 — **설치할 것이 없다.**

**보내는 주체는 Execution 이다.** 실행을 닫는 코드에 붙는다.
Reporting 이 하지 않는다 — `test_run.notified_at` 에 write 해야 하는데
§3.3 이 Reporting 의 write 를 `evidence_document` 하나로 막아 뒀다(2026-10-11 실패 카드 「버그」 판정 `run_case_bug` 가 하나 더 들었다 — 실행 표는 여전히 안 쓴다).

### 8.10 실행 창 (2026-09-21 신설 · 2026-10-09 한 건도 이 창)

**실행을 거는 곳은 모두 이 창을 연다** (2026-10-09 UI 개편 묶음 4 — 왜 하나로 모았는지는 §8.2 머리).

| 여는 곳 | 담기는 케이스 | 미리 채우는 것 |
|---------|--------------|---------------|
| 케이스 목록(카탈로그 §8.1) `조건에 맞는 N건 실행` · 고르기 바 `실행` | 조건에 맞는 전부 · 고른 것(바) | 상세 칸에서 고친 값 |
| 케이스 목록 줄 ▶ · 상세 칸 `이 값으로 실행` | 그 한 건 | 상세 칸에서 고친 값 |
| 실행 결과 「실패 N건 다시 실행」(§8.3) | 그 실행에서 한 번이라도 실패한 케이스 — **디바이스는 그 케이스에서 실패한 것만**(2026-10-19 ⑫) | 대상 서버 = 그 실행의 서버. 값은 저장값 · 코드 기본값. 걸 때 `rerunOf` 로 그 실행 번호를 싣는다(2026-10-19 — §7) |
| 항목 상세 「입력 값 수정 후 다시 실행」(리포팅 §8.4) | 그 항목의 케이스 | 그 항목에서 쓴 값 — **비밀값 칸은 비운다**(응답이 `********` 로 가려 준다 · 공통/2 §4.1) |
| 옛 주소 `#/cases/:id/run` | 그 한 건 | — |

- **대상 서버는 여는 쪽이 정해 주지 않으면 그 서비스에서 마지막에 고른 것(서버가 하나뿐이면 그것)을 미리 고른다** — 위 표에서 서버를 적지 않은 줄 전부다(2026-10-19 ⑫-2 · 공통/5-화면공통 §8 「화면을 오가도 하던 일이 풀리지 않는다」). 정해 준 서버(실패 다시 실행)가 서비스에서 지워졌으면 빈 칸으로 연다 — 원래 실행과 다른 서버가 말없이 골라지면 안 된다

- **비활성 케이스는 담지 않는다.** 목록 밖에서 열 때 비활성이 섞여 있으면 빼고 그 번호를 창 안내 줄에 적는다 — 조용히 줄어든 채 걸지 않는다
- 「실패 N건 다시 실행」은 **그 실행에서 쓴 값으로 채우지 않는다** — 실행 목록 응답에는 기대결과 값이 없어 여러 건을 그 값으로 채울 수 없다. 그 값으로 한 건을 다시 돌리려면 항목 상세의 「입력 값 수정 후 다시 실행」이다. 그 실행이 시작된 뒤 저장값이 바뀐 케이스는 창 위에 알린다(§8.3)

**이 창이 실행 설정을 겸한다.** 대상 서버를 고르지 않으면 실행이 시작되지 않으므로
(§8.2 「실행할 때 같이 고르는 것」의 대상 서버 칸) 그 칸이 여기 있어야 한다.
고르는 칸들은 그 표가 정본이고, **여러 건이면 디바이스 칸과 실행자 칸을 뺀 나머지가 여기 있다.** 실행 위치 칸(2026-10-07)도 같은 조건 — 고른 케이스에 Android 앱이 있을 때만, 종류 「Android 앱」 애플리케이션에서는 늘(2026-10-21 · §8.2 표) — 으로 여기 있다.
디바이스를 뺀 이유는 아래에 적었다. 실행자는 사람이 고르는 칸이 아니라 로그인한 사람 이름을
보여주기만 하는 칸이라(§8.2) 여러 건 창이 물을 것이 없다 — 서버가 세션에서 박는다.
**한 건이면 디바이스 · 실행자 · 사전조건 · 입력값 묶음 · 저장값 버튼(§8.2)을 더 보인다** — 앞 판의 한 건짜리 화면이 하던 일이다.
**한 건 · 반복 1 이면 「실행」 위(반복 칸 바로 위)에 「결과가 남는 곳」 한 줄을 둔다** (2026-10-30 WEB-F7-02 · §3.2 「★ 한 건 실행은 묶음 실행에 붙는다」) — 「RUN N 결과에 다시 실행으로 붙습니다 · <그 실행 제목> · <시작 시각>」,
붙을 곳이 없으면 「아직 전체 테스트에 들어간 적이 없어 이 케이스 상세에만 남습니다」(반복 실행이라 못 붙을 때도 같은 글). 재료는 §7 `GET /api/cases/:tcId/rerun-target` 이고 대상 서버를 바꾸면 다시 읽는다.
붙는 곳은 서버가 실행을 만들 때 다시 고른다 — 창을 연 뒤 새 실행이 끝났으면 보인 곳과 다를 수 있고, 그때 진행 창 · 완료 글은 응답의 `attachedTo` 를 따른다(창이 보인 번호를 요청에 싣지 않는다 — 늘 더 새 실행에 붙는 쪽이 맞다).
**한 건 · 반복 1 이면 「끝나면 Slack 으로 알림」 칸을 숨기고**(§8.9 「언제 보내나」 — 서버가 버린다) 반복을 2 이상으로 올리거나 여러 건이 되면 다시 보인다.
반복을 2 이상으로 올리거나 여러 건이면 「실행 기록에 새 RUN 으로 남습니다」다. 「실패 1건 다시 실행」으로 연 창은 통로를 부르지 않고 그 실행 번호를 적는다(반복 실행이면 이력에만 남는다는 글). 글자는 WEB-F7-09 · 12
— **한 건이 붙는 서버(WEB-F7-11) 전에는 한 건도 「실행 기록에 새 RUN 으로 남습니다」였다** (2026-10-30 WEB-F7-09 시작 질문). **WEB-F7-11(PR #529) 뒤 WEB-F7-12 전까지는 그 글이 사실이 아니다** — 서버는 한 건을 붙이는데 창은 아직 「새 RUN」이라 하고, 진행 창 「결과 보기」는 한 건 실행 번호로 가 견주기 · 실패 카드가 404 `SINGLE_RUN` 이다. 이어 달리기로 F7-12 를 바로 붙여 그 틈을 닫는다. 줄은 반복 칸 바로 위에 있고, 붙는 글과 통로 읽기는 WEB-F7-12 가 더한다
**실행 제목 칸은 한 건 · 여러 건 모두 없다** (2026-10-19 ⑫) — 제목은 서버가 짓는다(§7 `POST /api/runs` 「자동 제목」). 앞 판은 한 건이면 `<tcId> 실행` 으로 미리 채운 칸을 두고 여러 건이면 `<맨 앞 tcId> 외 N건 실행` 을 화면이 붙였다.

- **걸기 전에 고친 칸을 명세로 검사한다** (2026-10-09). 어긋나면 그 칸 아래에 사유를 적고 걸지 않는다 — 앞 판의 한 건 화면이 하던 검사다.
  **안 고친 케이스는 검사하지 않는다** — 코드 기본값으로 돌고 K10(§4)이 그 값을 이미 지킨다. 비워 둔 비밀값 칸에 저장값이 있으면 막지 않는다(§8.2 「저장값」)

**모달 자체의 규칙은 `docs/DESIGN.md`가 정본이다** — 바탕·테두리·폭·닫는 길·포커스.
여기에 옮겨 적지 않는다.

- **아무것도 안 고쳐도 돈다.** 규칙 K10(§4)이 「사람이 값을 채워야만 도는 케이스」를 막고 있어
  모든 케이스가 값 없이 돈다. 정기 실행(§9.2)이 이미 같은 길을 돈다 — 새로 여는 길이 아니다
- **목록에서 이미 고친 값이 있으면 그 값으로 열린다** (2026-09-21 ② · 2026-10-19 ⑫ 줄에서 상세 칸으로).
  상세 칸과 이 모달은 **한 벌의 표를 쓴다** — 두 벌이면 같은 케이스를 두 자리가 다른 값으로 보여준다.
  상세 칸의 값 고치기 규칙은 [카탈로그.md](카탈로그.md) §8.1 「상세 칸」이 정본이다
- **칸은 접지 않는다** (2026-09-21 수정). 앞 판은 「기본은 전부 접혀 있고 `값 고치기` 접개가 붙는다」였다.
  **값이 한 뎁스 안에 있으면 무엇으로 도는지 보려고 케이스마다 펴야 했다** — 그것이 접개를 둔 이유를 무너뜨렸다.
  칸이 하나도 없는 케이스에는 그 자리를 아예 두지 않는다 — 빈 자리가 나오는 버튼은 고장으로 보인다
  - **여러 건은 휴대폰도 PC 도 값 칸을 접은 채 시작한다** (2026-10-12 사용자 휴대폰 · 2026-10-19 ⑫ · 점검 4.7 에 PC 로 넓혔다 — 공통/5-화면공통 §8 「휴대폰 화면」). 위 줄의 예외다.
    펼친 칸이 화면 몇 장을 밀어 `실행` 이 멀어졌다. 케이스 줄의 `값` 을 누르면 편다. 실행을 눌렀는데 틀린 칸이 있으면 그 케이스를 펼친다. 한 건 창은 접지 않는다
- **고친 값은 그 실행에만 쓰인다.** 케이스 파일의 기본값은 바뀌지 않는다.
  `POST /api/runs`의 그 항목 `params`·`expected`가 될 뿐이고,
  쓴 값은 `run_item`에 스냅샷으로 박제된다 (§3.2 불변식).
  **다음 실행에도 남기려면 저장값으로 저장한다** (2026-09-29) — 칸은 저장값 → 코드 기본값 순서로 채워 열린다.
  규칙과 버튼은 §8.2 「저장값 — 케이스마다 한 벌」이 정본이다
- **칸 아래 출처 줄** (2026-10-30 WEB-F7-09 · 시안 8 · 9판) — 케이스마다(한 건 · 여러 건) 입력값 칸 아래 한 줄이다.
  손대지 않았으면 `저장값 · 누가 · 언제`, 저장값이 없으면 `코드 기본값`. 칸이 그것과 다르면 `저장값과 다릅니다 · 이번 실행에만 씁니다`(저장값이 없으면 `코드 기본값과 다릅니다 · …`)와 「이 값 저장」 · 「되돌리기」가 선다.
  목록 상세 칸에서 고쳐 온 값 · 불러온 묶음도 저장값과 다르면 이 꼴이다 — 저장하지 않으면 이번 실행에만 가는 값이라서다.
  「이 값 저장」은 보이는 값을 저장값으로 저장하고(§8.2 「저장값」 · 케이스 쓰기 권한일 때만 그린다) 케이스를 다시 읽는다. 단추 곁에 `팀 모두와 정기 실행에 쓰입니다`를 적는다 — 상세 칸 「모두에게 저장」처럼 누르기 전에 팀 값이 바뀐다는 것을 알아야 한다(점검 7.6). 저장한 줄은 `저장값으로 저장했습니다.` 로 바뀐다.
  「되돌리기」는 고친 글자를 버려 저장값(없으면 코드 기본값)으로 돌아가고 실행에 그 케이스 값을 싣지 않는다 — 서버가 같은 저장값으로 채운다.
  **저절로 저장하지 않는다** — 저장값은 팀 모두와 정기 실행에 바로 쓰인다. 명세에 안 맞는 칸이 있으면 저장하지 않고 걸기 전 검사(아래)처럼 칸 아래에 사유를 붙인다
- **저장 안 한 채 닫으면 「저장하고 닫기」까지 묻는다** (2026-10-30 WEB-F7-09) — 이 창에서 고쳤고 저장값과도 다른 케이스가 있으면 `Esc` · `취소` 에 버튼 줄이
  `고친 입력값이 저장되지 않았습니다 · 팀 모두와 정기 실행에 쓰입니다` · `계속 고치기` · `저장 안 하고 닫기` · `저장하고 닫기` 로 바뀐다. 「저장하고 닫기」는 그 케이스들을 저장값으로 저장한 뒤 닫고, 실패하면 닫지 않고 사유를 보인다.
  케이스 쓰기 권한이 없으면 공통/5-화면공통 §8 의 `고친 값이 사라집니다` 줄 그대로다. 묻는 조건(이 창에서 고쳤고 저장값과도 다르다)은 권한과 상관없이 같다 — 고쳤다가 저장값으로 되돌렸으면 잃을 것이 없어 묻지 않는다. 목록 상세 칸에서 고쳐 온 값만 있고 창에서 손대지 않았으면 묻지 않는다 — 창을 닫아도 목록에 남는다
- **디바이스는 케이스가 선언한 것을 전부 쓴다(「실패 N건 다시 실행」은 그중 실패한 것만 담는다 — 위 표). 모달에서 고르지 않는다** —
  케이스마다 `platforms` 선언이 달라 한 자리에서 고르게 하면 「그 케이스엔 없는 디바이스」를
  고를 수 있게 된다. **한 건 창에서는 고른다** — 기본은 선언한 것 전부, 다 끄면 걸지 않고 사유를 적는다.
  둘이 다른 이유는 하나다 — 그 화면은 케이스가 하나뿐이라 고르는 선택지가
  그 케이스의 선언 그대로이고, 여기서는 케이스마다 선언이 갈린다
- **본문만 스크롤하고 머리와 바닥은 고정이다.** 고른 건수가 늘어도 대상 서버 칸과 실행 버튼이 늘 보인다.
  건수가 많을 때 실행 버튼을 찾으러 끝까지 내려가야 하면 대상 서버를 고르지 않은 채 내려간다
- **이 창은 바깥을 눌러도 닫히지 않는다** (2026-09-30). 버튼 · `Esc` 는 그대로 닫는다 — 값을 고쳤으면 버튼 줄이 한 번 묻는다(2026-10-19 ⑫-2 · 공통/5-화면공통 §8 「화면을 오가도 하던 일이 풀리지 않는다」). 폭은 「넓은 상자」(DESIGN.md 「모달」)의 것이다 — 480px 로 좁게 열리던 것을 문서에 맞췄고, 숫자는 DESIGN.md 가 정본이라 여기 적지 않는다.
  이유는 값을 고치는 자리이기 때문이다 — 케이스 여럿의 칸을 고치다가 바깥을 잘못 눌러 입력 중인 값을 통째로 잃는다.
  모달 공통 규칙 「닫는 길 셋」에 대한 예외이고 그 규칙과 근거는 DESIGN.md 「모달」에 있다
- **이 창에서도 「▶ 테스트 실행」(2026-10-19~30 이름 「▶ 시험해 보기」)을 누를 수 있다** (2026-09-30). 「실행」 옆 버튼이고, 고른 케이스를 **차례로 한 건씩** §7 「케이스 테스트 실행」 통로로 돌린다
  (서버가 사람당 한 건만 받는다). 값은 이 창에서 고친 그대로 가고 열 주소 칸은 대상 서버 주소를 기본으로 한다(§8.2 「케이스 테스트 실행」과 같다).
  **디바이스는 케이스가 선언한 것 중 첫째 하나만 돈다**(한 건 창이면 고른 것 중 첫째) — 위의 「전부 쓴다」는 「실행」 버튼의 규칙이고, 테스트 실행은 §8.2 가 정본이다.
  결과는 케이스 줄 오른쪽에 판정 배지와 소요 시간으로 차례로 채워진다. **멈추는 경우** — 서버가 꺼져 있거나(TRIAL_OFF) 이미 돌고 있으면(TRIAL_BUSY) 남은 줄에 그 안내를,
  요청 자체가 실패하면(네트워크 등) 「앞 케이스에서 멈춰 돌리지 못했습니다」를 붙이고 멈춘다. **러너에 못 닿은 것은 멈춤이 아니다** — 서버가 케이스마다 미실행(NA) 결과와 안내 문장을 돌려주므로 줄마다 그대로 보인다.
  **그 케이스의 입력값만 명세와 안 맞으면**(400 INVALID_PARAMS) 그 줄만 안내하고 다음 줄을 이어 돈다.
  **디바이스가 쓰이는 중이면**(409 DEVICE_BUSY, 2026-10-07) 그 줄만 안내하고 다음 줄을 이어 돈다 — 브라우저 케이스는 디바이스와 상관없이 돌 수 있다
  **새 서버 통로는 없다.** 이 창을 닫거나 화면을 떠나면 남은 줄은 시작하지 않는다. 실행 기록에는 남지 않는다
- 만들어질 실행 항목 수와 5000건 상한은 **§8.2가 정본이다.** 여기서 다시 세지 않는다
