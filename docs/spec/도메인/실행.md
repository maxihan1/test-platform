### 3.2 Execution — 언제 무슨 값으로 돌렸는가

- **책임**: 실행 요청을 받아 러너에 분배하고 결과를 영속화
- **애그리거트 루트**: `TestRun` (식별자 `runId`) → `RunItem[]` → `Step[]`
- **불변식**
  - `RunItem`은 실행 시점의 `params`/`expected`를 **스냅샷으로 복사해 저장**한다.
    `param_set`을 참조만 하면 나중에 값이 바뀌었을 때 과거 증적이 거짓이 된다.
    문서를 만드는 데 필요한 나머지 값도 같은 이유로 실행 기록에 박제한다 (→ §3.3 증적 재현)
  - 동시 실행 수는 설정값(기본 2)을 넘지 않는다
  - `RunItem`은 생성 시 `status = NA`, `finished_at = NULL`이다. 실행이 끝나야 판정이 들어간다.
    러너 고장·타임아웃도 `NA`이며 `error`가 채워진 것으로 구분한다
  - `TestRun.status`는 모든 `RunItem`이 종료되어야 `FINISHED`가 된다
  - 실행 요청은 **반복 횟수**를 받는다. 요청 **최상위에 하나**이고 항목마다 따로 두지 않는다 —
    항목별로 다르면 "실행 항목이 몇 건 생깁니다"를 미리 셀 수 없다(§8.2). 같은 케이스·같은 디바이스를
    그 횟수만큼 돌려 `RunItem`을 그만큼 만들고 **회차**(1부터)를 기록한다. 목적은 **테스트 코드 검증**이다 —
    새로 쓴 테스트가 매번 같은 결과를 내는지 여러 번 돌려 본다. 그래서 같은 실행 안의 유일성 조건이
    `(run_id, tc_id, platform)`에서 `(run_id, tc_id, platform, 회차)`로 넓어진다 (2026-09-16 결정).
    컬럼과 인덱스는 §6, 요청 형태는 §7이 정본이다
  - 실행이 끝나면 **알림이 나간다** (§8.9). 알림 전송이 실패해도 **실행은 실패가 아니다** —
    실행은 이미 끝났고 결과는 `test_run` 에 남아 있다. 알림은 편의지 기록이 아니다
  - **도는 동안의 진행은 영속화하지 않는다** (2026-09-21). 러너에게 물어(§3.4 · §5.2) 화면으로
    흘릴 뿐 DB 에 쓰지 않는다 — 절차의 정본은 끝난 뒤의 `run_item_step` 이다.
    조회 모양과 거르는 규칙은 §7이 정본이다
  - **반복 횟수 자체에는 상한을 두지 않되, 한 번에 만들어질 `RunItem` 건수는 막는다** (2026-09-17 수정).
    앞 판은 「상한을 두지 않는다. 동시 실행 2 제한이 이미 있어 서버가 죽지 않는다」였다.
    **동시 실행 2는 돌아가는 프로세스 수를 막지 INSERT 건수를 막지 않는다** — 디바이스를 둘씩 선언한
    케이스 10건이면 디바이스 수의 합이 20이고, 반복 10만이면 `run_item` 200만 행이 요청 한 번에 들어간다.
    **상한의 자리와 숫자도, 건수를 세는 식도 §8.2가 정본이다** (2026-09-21에 예시를 합 식에 맞췄다)
  - **Playwright의 자동 재시도(`retries`, 실패한 테스트를 몰래 한 번 더 돌려 주는 기능)는 쓰지 않는다.
    `0`으로 고정한다.** 실패를 가리는 것과, 드러내려고 여러 번 돌리는 것은 다른 일이다.
    켜려면 이 문서를 먼저 고친다. 설정 파일 변경은 §5.2에 있다
  - 실행은 **도중에 멈출 수 있다** (2026-09-16 결정). 멈추면 아직 시작하지 않은 항목은 대기줄에서 빼고,
    이미 돌고 있는 항목은 러너에게 끊으라고 지시한다(§3.4). 어느 쪽이든 그 항목은 `status = NA`,
    `error.message = 'ABORTED'`로 닫는다. 판정할 근거가 없는 점이 타임아웃과 같으므로 저장 경로도 같은 것을 탄다
  - 멈춘 실행 묶음의 `TestRun.status`는 `FINISHED`가 아니라 **`ABORTED`**다. 스키마에 이미 있던 값인데 쓰는
    코드가 없었다. "끝까지 돌아서 끝난 것"과 "사람이 끊어서 끝난 것"은 증적에서 구분돼야 한다
  - **항목을 닫는 UPDATE에는 언제나 `AND finished_at IS NULL`을 붙인다.** 중단 처리와 러너 응답이 겹칠 수 있다.
    이 조건이 없으면 나중에 도착한 쪽이 먼저 기록된 판정을 덮어써, 사람이 끊은 실행에 통과 판정이 남거나
    그 반대가 된다. 먼저 온 것만 기록한다
  - **admin이 다시 뜰 때도 같은 처리를 한다.** 부팅 직후 `status = 'RUNNING'`인 `test_run`을 찾아
    미완 항목(`finished_at IS NULL`)을 위와 같은 방법으로 닫고 묶음을 `ABORTED`로 바꾼다. 재기동으로 분배기가
    사라지면 그 항목들은 영원히 끝나지 않아 `FINISHED` 조건이 결코 만족되지 않는다.
    컨테이너 재시작 정책은 §9에 있다

### 8.2 실행 설정
**고른 케이스마다** 그 케이스의 `paramSchema`를 읽어 **입력 폼을 자동 생성**한다.
한 건이든 여러 건이든 만드는 방법은 같다. 여러 건일 때 그 폼을 어디에 어떻게 놓는지는 §8.10이 정본이다.
`enum` → 셀렉트, `boolean` → 토글, `optional` → 선택 입력, `describe` → 라벨.
저장된 `ParamSet`을 불러오는 드롭다운 제공.
케이스의 `platforms`에 선언된 **디바이스**만 체크박스로 노출하고, 기본은 전부 선택.
스키마 검증 실패 시 해당 칸 아래에 이유를 표시한다(버튼은 비활성화하지 않는다).

실행 제목 칸은 이미 있고 `<tcId> 실행`으로 미리 채워진다. 계약으로 올려 둔다 —
`POST /api/runs`의 `title`이 필수이고, 실행 목록이 이 제목으로 실행을 가린다.

#### 실행할 때 같이 고르는 것 (2026-09-16 결정)

| 칸 | 모양 | 기본값 | 왜 필요한가 |
|----|------|-------|-----------|
| 디바이스 | 체크박스. 케이스가 선언한 것만 | 전부 선택 | 한 케이스를 PC와 모바일에서 각각 돌린다 |
| 대상 서버 | 드롭다운. **그 서비스의** `service_env`에 등록된 것만 (§6) | 없다. 반드시 고른다 | 같은 케이스라도 어느 서버에 쐈는지가 증적의 전제다 |
| 반복 횟수 | 숫자 칸 하나. 1 이상 | 1 | 새로 쓴 테스트가 안정적인지 여러 번 돌려 본다 |
| 실행자 | 고칠 수 없는 표시 칸. 로그인한 사람 이름 | — | 사람이 직접 적게 두면 남의 이름을 적을 수 있다 (§8.6) |
| 끝나면 Slack 알리기 | 체크박스 하나 | **꺼짐** | 자리를 뜰 실행만 켠다. 자기 확인용까지 팀 채널에 흘리면 채널이 소음이 된다 (§8.9) |

- 대상 서버 이름 옆에 그 서버의 주소를 흐린 글씨로 같이 보여준다. 고른 뒤 "어디로 쏘는지"를 확인할 자리가 있어야 한다.
  주소는 설정 화면(§8.8)이 서비스마다 갖고 있고 화면이 직접 적지 않는다
- **그 목록을 화면이 어디서 받는가** (2026-09-19 결정) — `GET /api/auth/me` 의
  `services[].envs` 다 (§7). Slack 칸의 조건인 `hasSlackWebhook` 도 같은 자리다.
  **`/api/settings/**` 에서 받을 수 없다** — 그쪽은 운영 등급만이라 실행까지 등급이 여기서 403 이 난다.
  통로가 없던 동안 화면은 `env` 를 안 실었고 `POST /api/runs` 가 400 을 냈다
- **반복 횟수는 실행 전체에 하나다.** 항목마다 따로 주지 않는다.
  항목마다 다르면 `실행 항목이 N건 생깁니다`를 계산할 수 없다
- 2 이상을 고르면 `실행 항목이 N건 생깁니다`(**Σ(케이스마다의 디바이스 수) × 반복 횟수**)를 버튼 옆에 적는다.
  실수로 큰 수를 넣은 것을 누르기 전에 알아야 한다
- **왜 곱셈이 아니라 합인가** (2026-09-21 수정) — 앞 판은 `케이스 수 × 디바이스 수 × 횟수`였다.
  그 곱셈은 **모든 케이스의 디바이스 수가 같을 때만** 맞는다. 케이스마다 `platforms` 선언이 달라 성립하지 않는다.
  실측이 반증했다 — 데모 케이스를 한 번에 돌렸더니 케이스 11건에 실행 단위가 13개였다.
  디바이스를 둘 선언한 케이스가 섞여 있었기 때문이다.
  세는 자리는 케이스마다 하나씩이고, 반복 횟수만 실행 전체에 하나다

#### 한 번에 만들 수 있는 실행 항목은 1000건까지 (2026-09-17 결정)

**막는 것은 `repeat`가 아니라 위에서 이미 계산하는 「실행 항목이 N건 생깁니다」 숫자다.**
그래야 케이스 수가 늘어도 같이 보호된다.

- 1000건을 넘으면 `실행` 버튼을 누를 수 없고, 숫자 옆에 `한 번에 1000건까지 만들 수 있습니다`를 적는다
- 서버도 같은 것을 본다. 넘으면 400 `{ error: 'TOO_MANY_ITEMS', limit, requested }`.
  화면만 막으면 직접 찌르는 요청을 못 막는다
- **왜 상한이 필요한가** — 「동시 실행 2 제한이 있어 서버가 죽지 않는다」가 근거였는데,
  동시 실행 2는 *돌아가는 프로세스 수*를 막지 *INSERT 건수*를 막지 않는다.
  디바이스를 둘씩 선언한 케이스 10건을 골라 디바이스 수의 합이 20이고 `repeat`가 10만이면
  `run_item` 200만 행이 요청 한 번에 들어간다 (2026-09-21에 예시를 위 합 식에 맞췄다.
  앞 판은 `케이스 10 × 디바이스 2 × repeat 10만`이라고 적어 곱셈을 전제하고 있었다)
- **왜 1000인가** — 항목 평균 1분이면 동시 2로 약 8시간, 하룻밤에 끝난다.
  전부 5분 타임아웃까지 가는 최악에는 훨씬 길어지지만 그때는 멈춤 버튼(§8.3)이 있다.
  숫자를 바꾸려면 이 절을 고친다. 설정값으로 빼지 않는다 — 설정이 늘면 「어느 값이었더라」가 는다
- 이 규칙은 §1.1의 L12(나중에 하는 것)였다. 2026-09-17에 앞당겨 여기로 올렸다
- 반복은 **테스트 코드를 검증하려는 것**이지 실패를 가리려는 것이 아니다. 자동 재시도와 혼동하지 않는다 → §5.2
- **Slack 칸은 그 서비스에 웹훅이 설정돼 있을 때만 보인다** (§8.8). 없으면 흐리게 두지 않고 아예 없다 (§8).
  끝났을 때 무엇이 어떻게 알리는지는 §8.9 가 정본이다

#### 비밀값 칸 (2026-09-16 결정)

`paramSchema`의 어떤 칸에 비밀값 꼬리표가 붙어 있으면(→ §4.1) 화면은 그 칸을 가려서 입력받는다.
타이핑하는 동안 글자가 점으로 보이는 칸이다.

- 저장된 `ParamSet`을 불러왔을 때도 가려진 채로 채운다. 화면 어디에서도 그 값을 글자로 되돌려 보여주지 않는다
- **가리는 것은 보이는 것뿐이다.** 값은 그대로 서버로 간다. 저장 시점에 가리면 같은 값으로 다시 실행할 수 없고
  실패 원인도 볼 수 없다. 테스트 전용 계정에 그것은 과한 대응이다
- 어깨너머로 보는 것을 막는 것이 이 칸의 목적이다. 이 칸은 DB 보호 장치가 아니다

### 8.3 실행 결과 목록
케이스 1건 = 1행. 디바이스별 결과는 판정 칸에 나란히 묶어 보여준다.

`TC ID | 케이스명 | PC 판정 | 모바일 판정 | [상세]`

디바이스별로 행을 쪼개지 않는 이유는 목록 길이가 두 배가 되고,
"PC는 되는데 모바일만 깨짐"이 한 줄에서 안 보이게 되기 때문이다.
지원하지 않는 디바이스의 칸은 `—`로 비운다.
필터는 판정(전체/PASS/FAIL/NA) + 디바이스(전체/PC/모바일) 둘이다.

**소요시간은 독립 칸으로 두지 않는다** (2026-09-16 결정). 디바이스별 판정 배지 아래에 각각 적는다.
디바이스가 둘인 행에서 소요시간이 하나면 어느 쪽 것인지 알 수 없다.

RUN 머리에 실행 제목·실행 시각·실행자·대상 서버와 주소를 한 줄로 적는다.
이 값들은 실행에 박제된 것을 읽는다 (§6 `test_run`).
대상 서버가 빠지면 같은 케이스의 통과 두 건이 같은 조건으로 보인다.

아직 안 끝난 항목의 `진행 중` 배지와 2초마다 다시 묻는 자동 갱신은 **이미 만들어져 있다.**
여기에 `ABORTED`를 멈춤 조건으로 더한다 (2026-09-16 결정).
지금 조건이 `status !== 'FINISHED'`라, 중단 기능이 들어오면 중단된 실행에서 갱신이 영원히 멈추지 않는다.

#### 실행 멈추기 (2026-09-16 결정)

실행이 도는 중일 때만 RUN 머리에 `실행 멈추기` 버튼을 둔다. 끝난 실행에는 보이지 않는다.
되돌릴 수 없으므로 누르면 한 번 더 묻는다.

- **대기 중인 항목과 이미 돌고 있는 항목을 둘 다 끊는다.** 대기 중인 것만 취소하면
  5분짜리 케이스가 도는 중에는 버튼이 아무 일도 안 하는 것처럼 보인다. 러너에 끊으라고 알리는 통로는 §5.2다
- 멈춘 실행은 머리에 `중단`을 달고, 돌지 못한 항목은 미실행 배지 옆에 사유(`사용자가 멈춤`)를 적는다.
  사유 없이 미실행으로 두면 러너 고장과 구분되지 않는다
- 버튼을 보일지 말지도, 자동 갱신을 멈출지 말지도 같은 값(`status`)으로 정한다. 화면이 따로 상태를 들지 않는다

#### 회차 요약 (2026-09-16 결정)

반복 횟수를 2 이상으로 준 실행에서는 한 케이스·한 디바이스에 항목이 여러 건 쌓인다.
**행 구조는 바꾸지 않는다.** 판정 칸이 요약이 된다.

| 회차 | 판정 칸 |
|------|--------|
| 1회 | 지금과 같은 판정 배지 |
| N회 전부 통과 | `5/5 통과` (통과 색) |
| N회 중 하나라도 실패 | `3/5 통과` (실패 색) |

- 다섯 번 중 세 번만 통과한 테스트는 **믿을 수 없는 테스트**다. 통과 색으로 칠하지 않는다
- 소요시간은 회차 평균을 적고 옆에 `평균`을 붙인다. 회차마다 값이 다른데 하나만 적으면 어느 회차 것인지 알 수 없다
- 어느 회차가 깨졌는지는 상세에서 본다. 목록은 회차를 펼치지 않는다

#### 러너에 닿지 못했을 때 (2026-09-17 결정)

설계서에 **실행이 러너에 닿지 못했을 때 사람이 보는 것**이 없었다.
적어 두지 않으면 빈 화면이나 원문 오류가 그대로 나온다.

- 돌지 못한 항목은 `NA`로 닫고 미실행 배지 옆에 사유를 적는다 — `러너에 닿지 못했습니다`.
  사용자가 멈춘 것(`사용자가 멈춤`)과 **같은 자리에 다른 문장**으로 적는다. 둘을 구분할 수 없으면 원인을 못 찾는다
- RUN 머리에 한 줄을 띄운다 — `러너에 닿지 못해 N건이 돌지 못했습니다`
- **원문 오류(스택·주소·포트)는 목록에 쓰지 않는다.** 항목 상세의 접힌 자리에 둔다.
  이 도구의 전제는 「코드를 몰라도 쓴다」다 (§1)
- 실행 자체는 `FINISHED`로 닫는다. `ABORTED`는 사람이 멈춘 것이다 — 둘을 섞으면
  중단 통계가 러너 고장으로 오염된다

#### 어떤 값으로 돌린 결과인지 목록에서 바로 본다 (2026-09-16 결정)

케이스명 아래에 그 항목이 실제로 쓴 입력값과 기대값을 한 줄로 적는다.
상세로 들어가야만 보이면 "어떤 값에서 깨졌는가"를 줄 사이에서 비교할 수 없다.

- **사람이 읽을 라벨로 적는다.** `아이디 testuser · 응답 코드 200` 처럼 라벨과 값을 붙여 쓴다. JSON 원문을 그대로 붙이지 않는다
- 라벨과 값은 **항목에 박제된 스냅샷**에서 읽는다 (§3.3). 카탈로그의 지금 스키마에서 읽으면
  설명 문구를 고쳤을 때 과거 행의 라벨이 따라 바뀐다
- 비밀값 꼬리표가 붙은 칸은 `********`로 적는다 (§4.1)
- 한 줄을 넘으면 뒤를 `…`로 자른다. 전부는 상세에서 본다
- 입력값이 없는 케이스(`params: null`)는 이 줄을 아예 만들지 않는다. `입력 없음`을 모든 행에 적으면 목록이 시끄러워진다

§8.1의 "JSON 원문을 목록에 노출하지 않는다"는 케이스 목록 규칙이고 여기에는 적용되지 않는다.
라벨과 값을 붙여 쓴 한 줄은 JSON 원문이 아니다.

### 8.7 실행 기록 목록 (2026-09-17 신설)

**이 화면은 이미 만들어져 있다** (`apps/admin/src/web/RunList.tsx`).
설계서에 절이 없는 채로 만들어졌다. 여기는 **무엇을 더하고 무엇을 고치는가**를 적는다.

지금 있는 것 — 위 한 줄과 페이지 넘김, `아직 실행한 기록이 없습니다.`

#### 칸마다 이름을 단다 (2026-09-22 결정)

목록 맨 위에 표머리 줄을 두고 위 칸 이름을 적는다. 이름이 없으면 각 칸이 무엇인지 모른다.
표머리의 색은 껍데기 색이다 — 자리는 [공통/5-화면공통.md](../공통/5-화면공통.md) §8 이 정본이다.

**좁은 화면에서 표머리를 감추지 않는다.** 이 화면은 §8 이 「좁은 화면에서 제대로 되는 둘」로
지정한 하나다. 감추면 거기서 칸 이름이 통째로 사라진다.
줄이 세로로 접히면 **표머리 대신 줄마다 라벨을 붙인다.**
케이스 목록([카탈로그.md](카탈로그.md) §8.1)은 그 둘에 없어서 감춰도 된다 — **둘을 같게 만들지 않는다.**

#### `결과 보기` 는 상자로 연다 (2026-09-22 결정)

누르면 **이 목록 위에 상자가 열리고** 그 안에 §8.3 실행 결과가 들어간다.
앞 판은 화면을 통째로 갈아탔는데, 돌아올 때 **검색 조건이 풀리고 보던 자리를 잃는다.**
실행이 쌓이면 조건을 걸어 찾게 되므로(위 「더할 것 8」) 그 손실이 매번 난다.

- **상자의 규칙은 `docs/DESIGN.md` 가 정본이다** — 거기 「열어서 보는 상자」에 해당한다.
  사람이 눌러서 여는 것이라 가로막는 상자가 아니다
- **주소(`#/runs/:runId`)는 그대로 살아 있다.** Slack 알림이 그 주소를 쓰고(§8.9),
  사이드바의 도는 실행 카드도 그리로 간다. **상자는 목록에서 들어오는 길을 하나 더한 것**이지
  기존 길을 없앤 것이 아니다
- **상자 안에서 또 상자를 열지 않는다.** §8.9 의 진행·완료 상자는 **화면 쪽에만** 붙는다.
  포커스를 가두는 장치가 둘 겹치면 키보드만 쓰는 사람이 빠져나올 길을 잃는다.
  상자로 도는 실행을 열었으면 끝났다는 사실을 **상자 안의 줄**로 적는다
- 닫으면 **누른 `[결과 보기]` 로 돌아오고** 검색 조건과 쪽이 그대로다

##### 거르는 일은 서버가 한다 (2026-09-22 결정)

**화면이 받은 쪽만 거르면 뒤쪽이 조용히 빠진다.** 위 「고칠 것 5」와 같은 함정이고
§8.1 이 `마지막 결과` 에서 이미 겪은 자리다. 조건은 `GET /api/runs` 의 질의 문자열로 간다 (§7).

- **집계도 같은 조건으로 좁아진다.** 거르개를 걸었는데 집계가 전체를 말하면
  사람은 세 줄을 보면서 「42회 중 9회 실패」를 읽는다. **보이는 것과 세는 것이 갈리면 안 된다**
- **평균 소요는 끝난 실행만 센다.** 도는 실행은 소요가 없다.
  몇 회를 센 것인지 부제에 적는다 — 안 적으면 전체의 평균으로 읽힌다
- **빈 목록이 두 갈래다** — 아직 안 돌렸다 / 조건에 안 걸렸다. 검색한 사람에게
  「아직 실행한 기록이 없습니다」는 틀린 문장이다 (아래 「고칠 것 6」의 확장이다)
- **집계 띠의 색은 판정 칸에만 붙는다.** `실행 횟수`·`평균 소요` 는 판정이 아니다 (DESIGN.md 원칙 1)
- **머리에 증적 버튼을 두지 않는다.** 증적은 실행 하나마다 만든다 (§8.4) —
  목록에서 무엇을 받는지가 정해져 있지 않다. 확정 목업에 그 버튼이 있었으나 뺐다

- **좁은 화면에서 제대로 되는 두 화면 중 하나다** (§8). 손가락 영역 44px을 여기에 건다
- 왼쪽 색 띠는 한눈에 훑기 위한 것이고 **판정은 집계 숫자와 글자가 말한다.**
  색만으로 판정을 전달하지 않는다 (DESIGN.md)
- 도는 실행이 있으면 §8의 알림 줄에도 같은 실행이 뜬다. **두 자리가 같은 값(`status`)을 본다**

### 8.9 실행이 끝났을 때 알린다 (2026-09-18 결정)

한 번 돌리면 최악 50분이다. 사람은 그동안 자리를 뜨거나 다른 일을 한다.
**끝난 것을 모르고 있는 시간**을 없애는 것이 이 절의 목적이다.

닿는 길은 셋이고 **서로 다른 상황을 맡는다.** 하나로 다 덮으려 하지 않는다.

| 어디에 있나 | 무엇이 받나 | 어디에 적혔나 |
|------------|-----------|-------------|
| 그 실행 결과 화면을 보고 있다 | **완료 모달** | 아래 |
| 이 플랫폼의 다른 화면에 있다 | 맨 위 **알림 줄**이 「끝났습니다」로 바뀐다 | §8 |
| 플랫폼을 떠나 있다 | **Slack 알림** | 아래 |

#### 도는 동안 — 같은 상자가 진행을 그린다 (2026-09-21 신설)

위 표는 **끝났을 때**만 다뤘다. 한 번 돌리면 최악 50분인데 **도는 동안 그 화면에 있는 사람**이
받을 것이 결과 목록의 숫자뿐이었다. 사람이 러너 로그를 직접 열어 보고 있었다.

**상자를 새로 만들지 않는다. 완료 모달이 쓰던 그 자리에서 내용만 갈라 그린다.**
따로 만들면 같은 화면에서 상자가 두 번 뜨고, 그것은 「모달은 아껴 쓴다」(DESIGN.md)와 부딪힌다.

- **도는 동안 그리는 것** — 진행 막대 · `{끝난 수} / {전체 수} 완료` · **도는 항목마다** 이름과
  지금 몇 번째 절차를 몇 초째 하고 있는지 · 방금 끝난 항목 몇과 실패 사유 한 줄
- **막대는 집계(`counts`)가 나눈 그대로 쓴다** — 통과 · 실패 · 미실행 · 남은 것.
  **「실행 중」과 「대기」로 가르지 않는다.** 그 둘을 가를 신호가 저장된 값에 없다 —
  `run_item` 행은 실행을 걸 때 한꺼번에 만들어지고, 항목이 실제로 시작될 때 시각을 고치지 않는다.
  가른 이름으로 부르면 **없는 구분을 있는 척하게 된다** (2026-09-21 실측)
- **도는 항목은 러너가 답한 그대로다. 화면이 고르지 않는다** (2026-09-21 개정).
  admin이 러너에게 물어(§7 의 `GET /api/runs/:runId/progress`) 돌아온 것을 **전부** 그린다 —
  동시 실행이 여럿이면 여럿이 뜬다. 정확히 아는데 하나만 그리면 **알면서 감추는 것**이다.
  항목마다 `절차 N · 제목`과 **머문 시간**을 적고 **제한 시간을 나란히** 둔다 —
  「느린 것」과 「멈춘 것」을 가르는 신호가 그것이고, **전체 절차 수(분모)는 만들 수 없다** (§5.1).
  러너가 아직 첫 절차를 안 흘렸거나 물음이 실패한 순간에는 **절차 줄만 빠지고** 항목 이름은 남는다.
  *앞 판은 이 자리에서 진행 중인 항목을 **근사치**라 부르고 「정확해지려면 러너가 절차마다 알려 주는
  통로가 필요한데 아직 없다」고 적었다. 그 통로가 생겨(§5.2) 사실이 아니게 됐다 (2026-09-21).
  바로 위 문단의 「없는 구분을 있는 척하지 마라」는 그대로 산다 — 분모를 만들지 않는 근거가 그것이다.*
- 실행을 건 직후 **자동으로 뜬다.** 단, **이미 끝난 실행을 열 때는 뜨지 않는다** —
  증적을 만들러 옛 실행에 들어가는 길목마다 상자가 서면 안 된다

#### ★ 여는 이유는 둘이다 — 하나로 합치지 않는다 (2026-09-21 신설)

**상자는 하나지만 「왜 열렸나」는 둘이고, 닫는 뜻도 둘이다.**

| 사람이 닫았다 | 뜻 | 그래서 |
|---|---|---|
| **진행** 상자를 닫았다 | 「도는 동안은 결과 목록을 보고 있을게」 | **끝났을 때 완료 모달을 받는다** |
| **완료** 상자를 닫았다 | 「끝난 건 알았어」 | 그 실행에 대해 다시 뜨지 않는다 |

**둘을 한 상태로 합치면 진행 상자를 닫은 사람이 완료 알림을 영영 못 받는다.**
§8 의 알림 줄도 그를 구하지 못한다 — 그 줄은 「그 실행 화면에 있던 사람은 모달로 이미 알았다」를
전제로 같은 자리를 두 번 알리지 않기 때문이다.

진행 상자를 **열어 둔 채** 실행이 끝나면 **한 상자가 그대로 내용만 바꾼다.** 두 번 뜨지 않는다.

#### 완료 모달

**그 실행의 결과 화면(§8.3)에 있을 때만 뜬다.** 다른 화면에서는 띄우지 않는다 —
모달은 하던 일을 가로막는 장치라서, 사람이 **그 실행을 보고 있을 때만** 막을 자격이 있다.
다른 화면에 있는 사람은 §8의 알림 줄이 받는다.

```
┌──────────────────────────────────────┐
│  RUN 2111 이 끝났습니다               │
│  결제 회귀 · 대상 서버 qa · 12분 04초  │
│                                      │
│   8 통과    1 실패    1 미실행        │
│                                      │
│  실패한 케이스                        │
│   PAY-002 한도를 넘는 카드로 결제하면… │
│                                      │
│      [증적 문서 만들기]  [결과 보기]   │
└──────────────────────────────────────┘
```

- **실패한 케이스를 모달 안에 적는다.** 숫자만 보여주면 사람이 결국 목록을 뒤져야 한다.
  다섯 건을 넘으면 앞의 다섯만 적고 `외 N건`을 붙인다
- 판정은 **색과 글자를 같이** 쓴다 (DESIGN.md). 숫자만 색으로 칠하지 않는다
- `증적 문서 만들기`는 **실행까지** 등급부터 보인다 (§3.5). 「보기만」에게는 `결과 보기` 하나다
- `결과 보기`는 모달을 닫는다. 이미 그 화면에 있으므로 다른 곳으로 보내지 않는다
- **닫는 길을 셋 둔다** — 버튼 · `Esc` · 바깥 누르기. 포커스는 모달 안에 가두고 닫으면 원래 자리로 돌려준다
- 한 번 닫은 모달은 그 실행에 대해 **다시 뜨지 않는다.** 새로고침해도 마찬가지다
- 중단된 실행(`ABORTED`)에도 뜬다. 「멈췄습니다」로 제목만 바꾼다 — 사람이 멈춘 것도 끝난 것이다

#### Slack 알림

**웹훅으로 보낸다.** 서비스마다 웹훅 주소를 따로 둔다 (§6 `service.slack_webhook`) —
결제팀과 회원팀이 같은 채널을 보지 않는다. 주소는 설정 화면에서 넣는다 (§8.8).

```
[실패] 결제 서비스 · RUN 2111 · 결제 회귀
통과 8 · 실패 1 · 미실행 1 · 12분 04초 · 대상 서버 qa · 실행자 김철수

실패한 케이스
  PAY-002  한도를 넘는 카드로 결제하면 거절 사유가 안내된다

결과 보기 <주소>      증적 문서 <주소>
```

- **머리에 판정을 글자로 적는다** — `[실패]` · `[통과]` · `[중단]`.
  Slack 은 색 막대를 지원하지만 색만으로 전달하지 않는다는 규칙은 여기서도 같다
- **요약 페이지를 새로 만들지 않는다.** `결과 보기` 는 §8.3 그 화면의 주소다.
  주소의 앞부분은 배포 설정 `PLATFORM_PUBLIC_URL` 이 준다 (§9) — 서버는 자기가 바깥에서
  어떤 주소로 열리는지 모른다. **그 값이 비어 있으면 링크 줄을 빼고 본문만 보낸다**
- **증적 문서 주소는 이미 만들어져 있을 때만** 넣는다. 없으면 그 줄을 빼고 결과 보기만 남긴다.
  형식이 여럿이면 **PDF 를 먼저** 고른다 — 제출물이고 눌러서 바로 보인다 (§8.4). PDF 가 없으면 가장 최근 것.
  알림 때문에 증적을 자동으로 만들지 않는다 — 만들기는 `operator` 부터라는 규칙(§3.5)을
  스케줄러가 우회하는 자리가 된다
- **주소는 주소일 뿐이다.** 눌러 들어가면 로그인이 여전히 막는다 (§7). 알림은 새 구멍을 내지 않는다

#### 언제 보내나

| 누가 돌렸나 | Slack |
|------------|-------|
| **사람** | 실행 설정에서 **고른다.** 기본은 **꺼짐** (§8.2) |
| **스케줄러** (정기 실행) | 웹훅이 설정돼 있으면 **항상 보낸다** (§9.2) |

- **사람이 돌릴 때 기본을 끄는 이유** — 자기 확인용으로 한 번 돌려 보는 일이 잦다.
  그것까지 팀 채널에 흘리면 채널이 소음이 되고, 소음이 된 채널은 아무도 안 본다.
  그리고 지금 화면 앞에 있으면 **모달이 이미 알려 준다.** 켜는 것은 「자리를 뜰 때」의 선택이다
- **정기 실행이 항상 보내는 이유** — 새벽에 도는 것을 볼 사람이 없다.
  아침에 Slack 에서 보는 것이 유일한 경로다. 정기 실행에 알림이 필요한 이유가 그것이다
- **웹훅이 설정되지 않은 서비스에서는 이 칸이 아예 보이지 않는다** (§8.2).
  못 하는 것은 흐리게 두지 않는다 (§8)

#### 보내지 못했을 때

**실행은 이미 끝났다. 알림이 실패해도 실행은 실패가 아니다.**

- `test_run.notify_slack` 이 「보내기로 했나」, `notified_at` 이 「실제로 보냈나」다 (§6).
  둘을 갈라 둬야 **보낼 생각이 없었던 것**과 **보내려다 실패한 것**이 구분된다
- 실패하면 결과 화면 머리에 한 줄 — `Slack 알림을 보내지 못했습니다`.
  원문 오류는 적지 않는다. 다시 시도하지 않는다 — 사람이 결과를 이미 볼 수 있는 자리에 있다
- **재시도 줄을 만들지 않는다.** 알림은 편의지 기록이 아니다. 기록은 `test_run` 에 이미 있다

#### 새 부품이 필요 없다

Slack 웹훅은 HTTPS 로 JSON 을 한 번 보내는 것이고 Node 20 에 `fetch` 가 들어 있다 (§9.1).
비밀번호 해시를 `crypto.scrypt` 로 해결한 것과 같은 자리다 — **설치할 것이 없다.**

**보내는 주체는 Execution 이다.** 실행을 닫는 코드에 붙는다.
Reporting 이 하지 않는다 — `test_run.notified_at` 에 write 해야 하는데
§3.3 이 Reporting 의 write 를 `evidence_document` 하나로 막아 뒀다.

### 8.10 여러 건 실행 모달 (2026-09-21 신설)

케이스 목록(§8.1)에서 `전체 실행하기` · `고른 N건 실행하기`를 누르면 열린다.

**이 모달이 실행 설정을 겸한다.** 대상 서버를 고르지 않으면 실행이 시작되지 않으므로
(§8.2 「실행할 때 같이 고르는 것」의 대상 서버 칸) 그 칸이 여기 있어야 한다.
고르는 칸들은 그 표가 정본이고, **디바이스 칸과 실행자 칸을 뺀 나머지가 여기 있다.**
디바이스를 뺀 이유는 아래에 적었다. 실행자는 사람이 고르는 칸이 아니라 로그인한 사람 이름을
보여주기만 하는 칸이라(§8.2) 모달이 물을 것이 없다 — 서버가 세션에서 박는다.

**모달 자체의 규칙은 `docs/DESIGN.md`가 정본이다** — 바탕·테두리·폭·닫는 길·포커스.
여기에 옮겨 적지 않는다.

- **아무것도 안 고쳐도 돈다.** 규칙 K10(§4)이 「사람이 값을 채워야만 도는 케이스」를 막고 있어
  모든 케이스가 값 없이 돈다. 정기 실행(§9.2)이 이미 같은 길을 돈다 — 새로 여는 길이 아니다
- **목록에서 이미 고친 값이 있으면 그 값으로 열린다** (2026-09-21 ②).
  목록 줄과 이 모달은 **한 벌의 표를 쓴다** — 두 벌이면 같은 케이스를 두 자리가 다른 값으로 보여준다.
  줄의 입력 칸 규칙은 [카탈로그.md](카탈로그.md) §8.1 이 정본이다
- **칸은 접지 않는다** (2026-09-21 수정). 앞 판은 「기본은 전부 접혀 있고 `값 고치기` 접개가 붙는다」였다.
  **값이 한 뎁스 안에 있으면 무엇으로 도는지 보려고 케이스마다 펴야 했다** — 그것이 접개를 둔 이유를 무너뜨렸다.
  칸이 하나도 없는 케이스에는 그 자리를 아예 두지 않는다 — 빈 자리가 나오는 버튼은 고장으로 보인다
- **고친 값은 그 실행에만 쓰인다.** 케이스 파일의 기본값은 바뀌지 않는다.
  `POST /api/runs`의 그 항목 `params`·`expected`가 될 뿐이고,
  쓴 값은 `run_item`에 스냅샷으로 박제된다 (§3.2 불변식)
- **디바이스는 케이스가 선언한 것을 전부 쓴다. 모달에서 고르지 않는다** —
  케이스마다 `platforms` 선언이 달라 한 자리에서 고르게 하면 「그 케이스엔 없는 디바이스」를
  고를 수 있게 된다. **한 건짜리 실행 설정(§8.2 위)에서는 지금처럼 고른다.**
  둘이 다른 이유는 하나다 — 그 화면은 케이스가 하나뿐이라 고르는 선택지가
  그 케이스의 선언 그대로이고, 여기서는 케이스마다 선언이 갈린다
- **본문만 스크롤하고 머리와 바닥은 고정이다.** 고른 건수가 늘어도 대상 서버 칸과 실행 버튼이 늘 보인다.
  건수가 많을 때 실행 버튼을 찾으러 끝까지 내려가야 하면 대상 서버를 고르지 않은 채 내려간다
- 만들어질 실행 항목 수와 1000건 상한은 **§8.2가 정본이다.** 여기서 다시 세지 않는다
