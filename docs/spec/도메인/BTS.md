### 3.12 BTS 연동 — 세 바퀴 (2026-10-28 사용자)

사용자(2026-10-27) 「QA 서버에 새 기능이 올라가면 PRD · 테스트 스크립트 · E2E 가 따라 고쳐지고, 테스트 실행에서 나온 버그는 BTS 에 등록돼 BTS 에이전트가 수정 PR 까지 만든다. 에이전트는 MCP 로 프로젝트 전반의 맥락을 알고 일한다」.
아래 결정은 2026-10-27 ~ 28 기획 대화에서 주제마다 정했고 eng review 두 번(1차 10-27 · 2차 10-28, 남은 결정 없음)을 거쳤다. BTS-F1-01 시작 질문(2026-10-31)에서 명세로 옮기는 것을 승인받았다. 다시 묻지 않는다.
「(내 결정)」이 붙은 줄은 명세로 옮기며 정리본이 비워 둔 자리를 정한 것이다 — 그 진행판 줄의 시작 질문에서 바꿀 수 있다.

**까닭** — 지금 작성 AI 는 애플리케이션 하나 몫(PRD · 가이드 · 배운 것 · 지도)만 알고, 「무엇이 새로 배포됐나」를 모르고, 「결함」 판정은 `run_case_bug` 기록에서 멈춘다.
모두의 AI 실험실 최종 제출(2026-12-11)에 「버그 → 수정 PR」 고리가 완제품으로 들어간다.

#### 세 바퀴 한눈에

```
새 기능   PR 병합 ─BTS 규칙→ 「배포 대기」
          deploy.sh 성공 ─→ BTS 웹훅 { 빌드 } ─BTS 규칙→ 「배포 대기」 전부 「QA 요청」
                        └─→ QA Hub 프로젝트 배포 신호 한 번 → 애플리케이션마다 스모크 → 다 통과면 「QA 요청」 · 안 맡은 이슈 맡기
                              task · 스토리 → PRD 초안 → 「결정 필요」 → PRD 새 버전 · 다시 작성 · PR
                              버그          → 회귀가 딸린 케이스도 돌림 → 다 통과면 댓글 · 닫기
                              (QA Hub 가 올린 이슈는 Bunker 유형이 task 여도 버그 — 아래 5 「버그인지 가르기」)

버그      실행 실패 → BTS 「QA 검토」 등록(AI 꼬리표) → 사람이 BTS 에서 판정
              버그 맞음 → 「개발 요청」 → 수정 AI → 초안 PR + 「코드 리뷰」 + 담당자 → 사람 병합 → 배포 → 재검증
              그 밖     → 닫기 사유에 따라 테스트 고침 · 기록만
              「테스트 수정」으로 옮김 → 테스트 고침 · 자동 병합 · 다시 실행 → 닫기 / 「QA 검토」로 되돌리기 (2026-11-11 · 아래 「테스트 수정 바퀴」)

롤백      deploy.sh 가 옛 커밋을 올림 → 사이 커밋의 이슈 키를 BTS 웹훅 · QA Hub 신호에 같이 실음 → BTS 가 「배포 대기」로 → QA Hub 가 PRD · 테스트도 되돌림
```

#### 지킬 것

1. **BTS 없는 프로젝트는 지금처럼 돈다** (회귀 계약 — 사용자 2026-10-28 「어 그러자」). 결정 필요 ② 실패 판정 · 실패 카드 판정 줄 · `run_case_bug` · `POST /api/builds` 흐름이 그대로다. 이 장이 바꾸는 화면 · 통로는 `bts_link` 행이 있는 프로젝트에서만 갈라진다
2. **테스트 작성 AI 는 대상 서비스 코드를 안 본다**(토큰 · 시간 — 사용자 2026-10-28). PRD · 화면 · API 문서 · 노트만 본다. 코드는 수정 AI 만 본다
3. **사람의 Claude Code 연결은 조회만 한다** — MCP 에 작성 요청 넣기 · 실행 걸기 도구가 없다(사용자 「테스트 작성을 시키는 건 플랫폼 정책에 맞지 않는다」)
4. **「버그야, 아니야?」는 BTS 에서만 판정한다** — BTS 연결 프로젝트는 QA Hub 화면에 버그 판정 버튼이 없다

#### 새 기능 바퀴 — 배포 신호 → 맡은 이슈 → PRD 초안

1. PR 병합 → BTS 규칙(지금 있는 `PR_MERGED` 트리거)이 이슈를 「배포 대기」로 옮긴다 — BTS 새 동작 「상태 바꾸기」(BTS-F2-01). BTS 는 PR 제목 · 본문의 `Closes <키>` 처럼 닫기 낱말이 붙은 키만 읽는다 — 수정 AI PR 이 그 줄을 넣는 까닭은 아래 「수정 AI」
2. `deploy.sh` 가 성공했을 때만 마지막 줄에서 BTS 자동화 웹훅 `{ build }` → 규칙이 「배포 대기」 이슈 **전부** 「QA 요청」 + 「QA 서버 N 배포됨」 댓글.
   이어서 QA Hub 프로젝트 배포 신호 한 번(§7 `POST /api/projects/:projectId/deploys`, 열쇠는 「설정 › Issue Bunker 연결」에서 받은 프로젝트 배포 열쇠)
3. QA Hub 는 `bts_deploy` 한 줄을 세우고 목록의 애플리케이션마다 지금 빌드 실행(스모크 → 회귀 — [실행.md](실행.md) §3.11)을 그대로 부른다. 웹 · API 는 빌드 번호만, 앱 · 게임은 그 대상 서버 줄의 최신 빌드를 쓴다
   - **대상 서버** — 본문 `env` 가 있으면 애플리케이션마다 그 이름의 줄이다. 없으면 애플리케이션마다 실서비스 서버가 아닌 줄이 하나여야 하고, 여럿이면 400 `ENV_REQUIRED` (내 결정 — 고를 줄이 하나뿐인 데모마켓은 env 없이 돈다)
   - **BTS 연결 프로젝트의 앱 · 게임 APK** 는 지금 `POST /api/builds` 로 올리되 그 문은 빌드만 남기고 실행을 걸지 않는다 — 실행은 배포 신호가 건다 (내 결정 — 같은 빌드를 두 번 돌리지 않게)
   - **앱 · 게임 APK 가 그 줄에 하나도 없으면** 아무것도 걸지 않고 400 `NO_BUILD` 다 — deploy.sh 가 실패로 끝나야 사람이 바로 안다(2026-10-31 BTS-F5-01 시작 질문 2)
   - 배포가 건 첫 실행(스모크, 스모크 케이스가 없으면 회귀) 번호를 `bts_deploy.run_ids` 에 한 번에 적는다 — 앱 · 게임은 배포 빌드 번호가 아닌 최신 APK 로 돌아 빌드 번호로는 그 배포의 스모크를 못 찾는다(시작 질문 1). 판정은 그 가운데 스모크만 본다. 스모크가 다 끝나기 전에 새 배포가 오면 앞 배포는 말없이 `HELD` 로 닫는다(새 배포가 맡는다 — 새 배포가 `FAILED` 면 앞 배포가 그대로 판정한다)
4. **하나라도 스모크가 깨지면** 이슈를 맡지 않고 「QA 요청」 이슈마다 「스모크 실패 — 보류」 댓글 → 배포 줄은 `HELD` 로 끝난다. 이슈가 「QA 요청」에 남아 다음 배포가 다시 잡는다.
   스모크 실행이 테스트 데이터 준비에서 멈췄으면(`PREP_FAILED` — [실행.md](실행.md) §3.2 「실행 전 준비」) 똑같이 보류하되 댓글은 「테스트 데이터 준비 실패 — 보류」와 까닭 한 줄이다 — 빌드가 깨진 것이 아니다. 한 배포에서 어떤 애플리케이션은 스모크가 깨지고 어떤 것은 준비가 실패하면 지금처럼 댓글 하나에 애플리케이션마다 한 줄이고, 머리는 「스모크 실패 — 보류」, 준비 실패 줄만 「테스트 데이터 준비 실패」와 까닭을 단다 (2026-11-11 SEED-F1-01 · 반영 SEED-F1-03)
5. **다 통과하면** BTS 에서 「QA 요청」이면서 `bts_claim` 에 맡는 중인 줄이 없는 이슈를 찾아 한 묶음으로 맡는다(`bts_claim` 에 배포 · 빌드를 적는다). BTS 규칙이 늦게 끝나 이 묶음에 못 든 이슈는 다음 점검이 따로 작은 초안으로 맡는다(「늦은 이슈」 — 맡은 때(마지막 스모크가 끝난 때, 스모크가 없으면 배포 신호 때)부터 10분 동안 1분마다 다시 찾는다. 가장 새 배포가 맡은 배포일 때만이다(실패한 배포는 건너뛴다). 끝없이 BTS 를 두드리지 않게 · 상수는 `bts/deployLate.ts` `늦은이슈기한분` · BTS-F5-01 시작 질문). 찾은 「QA 요청」 목록에 없는 맡는 중 줄은 놓는다 — QA Hub 가 꺼져 「QA 요청」을 떠난 알림을 놓쳐도 다음 배포가 다시 맡게
   - **버그인지 가르기** — QA Hub 가 실패로 올린 이슈(`bts_issue_case` 에 짝이 있는 키 — 닫힌 짝도 센다)는 Bunker 유형과 상관없이 버그다. 그 밖은 Bunker 유형(`typeKey`)이 `bug` 면 버그, 나머지는 task 로 친다. 실패 등록(아래 「버그 바퀴」)은 이슈 유형을 싣지 않아 Bunker 기본값 Task 로 서기 때문이다 — 유형만 보던 앞 판은 수정 PR 을 배포한 뒤 QA Hub 가 올린 실패 이슈(MQA-113)를 task 로 맡아 재검증 · 닫힘 대신 PRD 초안을 세웠다(2026-11-08 BTS-F9-01 시험 문제 25). 실패 등록 때 유형을 「버그」로 지정하는 것은 회사마다 유형 이름이 달라 연결 설정에 짝짓기가 더 필요해 하지 않았다(같은 날 사용자 승인). 노트 사건(닫힘 → `ISSUE_CLOSE` · `TASK_DONE`)도 같은 가르기를 쓴다(`bts/inbound.ts`). **남는 한계** — 짝이 다 닫힌 이슈(재검증 통과로 닫았는데 BTS 옮기기가 그만둬 「QA 요청」에 남았다)는 버그로 맡지만 아래 재검증은 열린 짝만 봐서 다시 닫지 않는다. 맡은 채 남고 사람이 BTS 에서 닫는다
   - task · 스토리 → 애플리케이션마다 PRD 초안 요청(`PRD_DRAFT`) 하나. 설명이 모자라면 초안이 그 이슈를 「? 확인」 줄 하나로 내 「결정 필요」에서 사람이 정한다(아래 「PRD 초안 → 결정 필요」)
   - 버그 → 맡은 배포 뒤에 선 실행에서 딸린 케이스(`bts_issue_case` — 깨진 대상 서버와 같은 서버)가 다 통과하면 「재검증 통과 — 빌드 N」을 담아 「닫힘」으로 옮긴다(`resolution` `FIXED` · 맡음을 놓는다). 또 실패면 지금처럼 열린 이슈에 댓글이 달리고, 수정 AI 로 넘기는 것은 아래 「수정 AI」 재검증 실패(BTS-F6-01)
     딸린 케이스가 여러 애플리케이션 · 대상 서버에 걸치면 케이스마다 맡은 배포 뒤 그 케이스를 돌린 마지막 실행을 본다
     **따로 실행을 세우지 않는다** — 스모크 뒤 회귀가 활성 케이스 전부라 딸린 케이스도 돈다. 같은 빌드를 두 번 돌리지 않는다(2026-10-31 BTS-F5-01 시작 질문 5 — 기획의 「딸린 케이스만 다시 실행」을 바꿨다. 판단 기준 「통과해야 닫는다」는 그대로다). 「닫힘」 옮기기는 보낼 줄 TRANSITION 이고 이슈 판 번호는 보내기 직전에 읽는다(`bts/outbox.ts` — 그사이 판이 바뀌어 409 면 다시 보내고, 이미 닫혔으면 실은 글을 댓글로만 단다)
     **남는 한계** — 앱 · 게임은 새 APK 없이 다시 배포되면 앞 배포와 같은 빌드로 스모크를 다시 걸어, 그 빌드의 회귀가 이미 있거나 앞 스모크가 깨졌으면 회귀가 다시 안 돈다(실행.md §3.11 「스모크 → 회귀」는 빌드마다 한 번이다). 그때 스모크가 아닌 딸린 케이스의 앱 버그는 새 APK 가 오거나 사람이 그 케이스를 다시 돌릴 때 닫힌다 — 맡은 배포 뒤의 어느 실행이든 센다. 회귀를 배포마다 걸려면 스모크 뒤 판정을 빌드 대신 배포 단위로 바꾼다(BTS-F5-01 spec-review)
   - 딸린 케이스가 없는 버그(사람이 BTS 에 직접 올린 것) → 「딸린 테스트 없음 — 사람이 확인」 댓글만 달고 「QA 요청」에 둔다(2차 R8)
6. 지금 `POST /api/builds` 는 BTS 없는 프로젝트 · APK 올리기용으로 그대로 둔다. 배포 신호는 애플리케이션마다 그 흐름을 안에서 부른다
7. **서버가 스스로 세우는 일의 「누가」** — 배포 실행 · `PRD_DRAFT` · `NOTE` · `BUGFIX` · 닫기 사유가 세운 작성 · `ROLLBACK` 판 · 되돌림 요청은 모두 BTS 연결을 마지막으로 저장한 admin(`bts_link.updated_by`)으로 적고 이름 스냅샷은 「Issue Bunker · <이름>」이다 (내 결정 — CI 토큰의 「실행자는 발급한 사람」과 같은 판단. 그 계정이 꺼지면 연결을 다시 저장해야 돈다)
8. **열린 작성과 부딪힐 때** — `PRD_DRAFT` · `NOTE` · `BUGFIX` 는 테스트 저장소를 안 고쳐 열린 뿌리가 아니다(`chainSql.ts` `열린뿌리식` 은 그대로 `AUTHOR` · `EDIT`). 초안을 고른 뒤의 진행은 지금 결정 진행이라 서버 막기(`AUTHORING_OPEN`)도 그대로다. 롤백 되돌림 요청(`AUTHOR`)은 서버가 세우는 일이라 409 를 받을 사람이 없다 — 되돌림 요청은 곧바로 세우되, 닫기 사유가 세우는 요청처럼 그때 열린 작성을 `decision.after` 로 기다린다(집기가 그 작성이 닫힐 때까지 안 집는다 · BTS-F7-01 반영 2026-11-01 — 기획의 「60초 점검이 나중에 세운다」를 바꿨다. 기다리는 길이 이미 있어 점검을 따로 두지 않는다). `ROLLBACK` 판이 서는 때는 아래.
   **열린 작성이 있으면 `ROLLBACK` 판도 그 작성이 닫힌 뒤에 선다** — 되돌림 요청만 곧바로 세우고(params 에 `rollbackKeys` 를 남긴다), 그 요청을 집을 때 서버가 그때의 판 기록으로 판을 세운 뒤 그 판을 요청의 읽은 판으로 적는다(`bts/rollback.ts` `미룬롤백판세우기`). 결정 진행(`DECISION` 판)이 작성 중에 막히는(`AUTHORING_OPEN`) 것과 같은 까닭이다 — 에이전트 옮기기는 사람이 고친 항목(`byPerson`)만 지키고 합치는데(도메인/작성.md §7 `POST …/:id/prd`) `ROLLBACK` 판 항목은 그 표시가 없어, 판을 바로 세우면 열린 작성이 들고 있던 옛 판 사본으로 판을 올려 되돌림을 말없이 덮고, 되돌림 요청은 「반영할 것이 없다」로 끝났다(BTS-F9-01 시험 2026-11-08 · DMW #15263 이 6판 사본으로 8판을 올려 7판 롤백을 덮었다). 에이전트 저장 쪽에서 막지 않는 까닭 — 덮지 않게만 하면 PRD 는 되돌린 문장인데 그 작성의 테스트는 옛 문장이라 병합 뒤 「반영 안 됨」이 틀어진다.
   기다리는 동안 「PRD 관리」에는 롤백 전 문장이 그대로 보인다(작성이 끝나고 PR 병합을 기다리는 동안도 — 되돌림 요청이 그만큼 기다린다). 실패한 신호를 같은 빌드로 다시 보내면 미룬 요청이 이미 있어 또 세우지 않는다. 판이 서기 전에 다시 배포되면 요청과 함께 판도 안 선다 — 아래 「롤백 바퀴」 4 (2026-11-08 사용자)

#### PRD 초안 → 「결정 필요」 → 다시 작성

- 초안 요청(`PRD_DRAFT`)은 애플리케이션 하나 · 맡은 이슈 여럿이다. 자식은 MCP 로 이슈 글 · 노트 · 지금 PRD 를 읽고 QA 화면을 훑어 줄마다 `{ op: 'ADD'|'EDIT'|'DEL', reqId?, text, basis, issueKeys, sure }` 를 낸다. `sure: false` 가 「? 확인」이다
- **언제 서나** — 배포가 이슈를 맡을 때(묶음 · 늦은 이슈 둘 다) 새로 맡은 task · 스토리(위 「새 기능 바퀴」 5 「버그인지 가르기」로 버그가 아닌 이슈)가 있으면 그 배포의 애플리케이션마다 하나다. 늦은 이슈는 따로 작은 초안이 된다. 대상 서버는 그 배포가 그 애플리케이션에 건 실행의 서버다(스모크가 돈 서버). 실행이 없는 애플리케이션(활성 케이스가 아직 없는 새 애플리케이션)은 배포 신호가 env 없이 고르는 규칙(위 3)대로 실서비스 아닌 줄이 하나면 그 줄이고, 그마저 못 고르면 그 애플리케이션 초안은 서지 않고 서버 기록만 남는다. 맡음과 초안은 한 트랜잭션이다 — 사이에 꺼져 초안 없는 맡음이 남으면 그 이슈를 다시 안 잡는다(`bts/deployFlow.ts` 맡기). `bts_claim.request_id` 는 채우지 않는다 — 애플리케이션마다 초안이 서서 한 칸에 못 담는다. 초안은 요청의 `params.issueKeys` 로 찾는다 (BTS-F5-03 시작 질문 1 · 7)
- **자식** — 테스트 저장소 · 코드 없이 작업 폴더 하나로 돈다(노트 고치기와 같은 틀 · `scripts/authoring-draft.ts`). 도구는 파일 읽기 · 쓰기 · MCP 조회, 웹 애플리케이션이면 저장소에 깔린 `playwright cli` 하나다(앱 · 게임 · API 는 화면을 안 연다). 그 밖의 셸 명령은 막는다 — 자식은 사용자 설정을 읽지 않는다(`Bash(*)` 허용이 섞이면 허용 목록이 무력해진다). 지금 판은 에이전트가 받아 계정 비밀번호를 가려 넘기고, 대상 서버 주소는 환경 변수로만 간다. **계정은 넘기지 않는다** — `playwright cli` 로 로그인하면 비밀번호가 명령 인자와 AI 대화에 펼쳐진다. 로그인 뒤 화면은 **에이전트가 먼저 로그인해 둔 상태 파일**로 연다(BTS-F5-05 · 2026-11-09 사용자) — 에이전트가 자식을 띄우기 전에 대상 서버 줄의 테스트 계정으로 로그인 화면에 들어가 자식 임시 폴더에 상태 파일(0600 · 자식 uid)을 두고, 자식은 `playwright cli open` 다음 `state-load` 로 그 파일만 불러온다. 로그인 화면 찾기와 로그인 꼴은 성능 페이지 측정과 같다([성능.md](성능.md) 「잴 페이지」 — `perf/pages.ts` `로그인화면` · `perf/pageScript.ts` `아이디칸` · `scripts/authoring-draft-login.ts`). 자식은 비밀번호를 못 보지만 상태 파일의 쿠키는 읽을 수 있다 — 지시문이 옮겨 적기를 막고 작업 폴더와 같이 지운다. 로그인 화면이 화면 기록 · 찾은 화면에 없거나 계정이 비었거나(운영 서버 줄) 로그인에 실패하면 지금처럼 로그인이 필요한 화면은 열지 않고 이슈 글로만 쓴다 — 초안 일은 멈추지 않는다(2026-11-08 사용자). 화면은 이슈가 말한 기능만 연다 — 앱 전체를 훑지 않는다 (BTS-F5-03 시작 질문 2)
- **줄 규칙** — 확정 후보(`sure: true`)는 이슈 글에 적힌 것만이다. 화면에서만 본 것은 `sure: false` 에 근거 「화면에서만 봄」. 이슈 설명이 모자라 무엇이 바뀌는지 모르면 그 이슈는 `sure: false` 줄 하나로 내고 근거에 「이슈 설명이 모자람」을 적는다(응답 꼴을 늘리지 않으려고 — BTS-F5-03 시작 질문 4). 같은 요구 번호를 두 줄이 건드리면 서버가 거절한다 — 아래 「한 카드로」가 줄 단위에서도 선다(시작 질문 3). 그 애플리케이션과 상관없는 이슈는 줄이 없고, 하나도 없으면 빈 초안이다
- **사람에게 보이는 자리** — 「PRD 초안」 카드 하나다(§8.15 · BTS-F5-04 반영 2026-10-31 · `bts/draftDecide.ts`). 카드는 초안 요청 하나(배포 한 번 × 애플리케이션 하나)마다 하나다 — 같은 요구를 두 줄이 건드리면 결과 통로가 거절해서, 같은 요구를 건드리는 이슈는 저절로 한 카드 한 줄에 모인다. 초안 요청은 작성 목록 · 작성 완료 알림 · 결정 목록 「반영 대기」에 안 싣고 사람이 다시 돌리지 못한다(400 `BAD_KIND`). 에이전트가 꺼져 멈춘 초안(`AGENT_RESTART`)은 같은 칸으로 새로 서고 멈춘 줄은 폐기로 찍는다 — 같은 이슈 키의 살아 있는 초안은 하나다. 이어하기로 잇지 않는다(남길 작업 폴더가 없다). 실패 · 그 밖의 중단(한도 · 시간 초과)은 저절로 다시 서지 않는다 — 그 맡음도 남는다. 카드가 그 초안을 까닭과 같이 보이고 [다시 만들기](같은 칸으로 새로 세우고 옛 줄은 폐기) · [삭제](폐기)를 준다 (BTS-F5-03 시작 질문 6)
- **고르는 규칙** (BTS-F5-04 시작 질문 — 2026-10-31 사용자 승인)
  - 체크한 줄은 확정으로 들어간다 — 추가는 새 번호(지운 번호는 다시 안 준다)에 기능 이름은 요구 문장에 이름이 든 지금 판의 기능 묶음(여럿이면 긴 이름 — 2026-11-11 · [작성.md](작성.md) §3.6 「목차」 규칙 3. 앞 판은 이슈 제목이라 PRD 목차에 문장이 묶음으로 섰다), 그런 묶음이 없으면 그 줄 첫 이슈의 제목(없으면 이슈 키 — PRD 관리 목차가 「정리 필요」로 띄워 사람이 옮긴다), 수정은 문장을 바꾸고 줄의 근거를 근거 맨 앞에 더한다, 삭제는 지운다. 근거 자리는 이슈 키들(`DM-12 · DM-14`)이다
  - 체크 안 한 「화면만 보고 적음」(`sure: false`) 줄은 버리지 않고 확인 필요로 들어간다 — 추가는 그 문장으로, 수정 · 삭제는 사람이 확정한 요구 문장을 덮지 않고 확인 필요만 단다(수정 줄이 제안한 문장은 근거 맨 앞에 남는다 — 화면에서만 본 값이 기대값이 되지 않게, 결정 6 · code-review). 체크 안 한 확정 후보는 버린다. 사람이 안 고른 줄로 생긴 항목도 `byPerson` 이 붙는다 — 사람이 카드에서 진행한 결정이라 다음 옮기기가 덮지 않는다
  - 고친 항목마다 `fromIssues` 에 그 줄의 이슈 키를 더한다(사람이 PRD 관리에서 저장해도 남는다 — `prd/rules.ts` `표시달기`. 되돌리기는 되돌리는 버전의 꼬리표를 쓴다). 판 기록 `changes` 는 줄마다 ADD · EDIT · DEL · CHECK(안 고른 삭제 줄) + `issueKeys`
  - 확인 필요 결정과 같이 고르면 버전 하나에 담는다. 판이 바뀌었으면 고친 요구 다시 작성 하나가 같이 선다(문장 변경과 같은 요청)
  - 지금 판에 없는 번호를 고친 줄(그 사이 사람이 지웠다)은 고를 수 없다. 체크 안 했으면 건너뛴다. 진행은 고른 줄을 초안 요청 `result.picked = { rows, by, at, version }` 에 남긴다(대시보드 「초안 AI」 셈) — 그 뒤 카드가 사라진다. [초안 삭제]는 `rows: []` 로 남긴다
  - 이슈 제목은 배포가 이슈를 맡을 때 BTS 검색 답의 `summary` 를 `params.titles` 에 적어 둔다(`bts/deployFlow.ts`) — 카드를 열 때마다 BTS 를 부르지 않게
  - E2E 제안은 카드 아래 읽기만 하는 줄이다 — 테스트가 다시 만들어진 뒤에야 케이스를 엮을 수 있어 만들기는 E2E 메뉴에서 한다
- **한 초안 안에서 같은 요구를 건드리는 이슈끼리는 한 줄 · 한 카드로 합친다** — 카드는 초안 요청마다 하나라 다른 배포의 초안은 따로 선다(위 「사람에게 보이는 자리」). 다른 애플리케이션과 엮이면 노트를 보고 E2E 시나리오를 제안한다(케이스 조합만 — 작성 쪽은 안 바꾼다) → 같은 카드 아래 읽기만 하는 줄로 보인다(위 「고르는 규칙」)
- 사람이 고른 줄은 지금 결정 진행 흐름으로 PRD 새 버전(`DECISION`)이 되고, 그 줄의 항목에 `fromIssues` 가 붙는다(롤백이 이것과 판 기록에서 그 키로 지운 번호를 되돌린다 — 아래 「롤백 바퀴」 1). 「? 확인」을 안 고르면 `확인 필요` 요구가 되고 그 케이스는 미확정이다(위 「고르는 규칙」)
- 고르지 않은 카드는 목록에 남는다 — 지금 결정 목록 규칙 그대로

#### 버그 바퀴 — 실패 → BTS 「QA 검토」

- **무엇을 올리나** — 실행이 끝나면 실패 항목마다(케이스 · 대상 서버로 접는다) 이슈 하나. 제목 `[<애플리케이션>] <케이스 이름>` · 환경(대상 서버 · 디바이스 · 빌드) · 재현 단계(= 케이스 step) · 기대(PRD 요구 번호와 문장) vs 실제(실패한 확인 · 실패 원인 한 줄) · 실패한 네트워크 요청 · 콘솔 오류(가린 글 — 앱 · 게임 항목은 그 자리에 폰 logcat 오류 줄, 아래 「앱 · 게임 항목」) · 첨부(실패한 단계의 캡처 — 아래 「첨부 파일은」) · QA Hub 실행 결과 고리(실패한 항목 상세로 바로 간다 — `<PLATFORM_PUBLIC_URL>/#/runs/<그 항목의 실행 번호>/items/<항목 번호(historyId)>`. 한 건 실행이 덮은 항목은 한 건 실행 번호다. 항목 상세는 실행 번호가 맞아야 찾는다 — 2026-11-04 사용자 「들어가보면 404」) · AI 꼬리표 하나. 「관련 이슈」 칸은 1차에 없다(무엇을 관련으로 볼지 정하지 않았다 — BTS-F3-03 spec-review)
- **웹은 어느 화면에서 깨졌는지 적는다** — PC · 모바일 둘 다 깨져도 이슈는 케이스마다 하나다(2026-11-04 사용자 「웹이랑 모바일 둘 다 발생한 버그는 1개로」). 「환경」 바로 아래에 `**화면** — PC · 모바일 둘 다` · `**화면** — 모바일만(PC 는 통과)` 처럼 깨진 화면과 이번 실행에서 통과한 화면을 적는다(한 화면만 돌았으면 그 이름만). 두 화면의 실패한 단계나 실패한 확인이 다르면 재현 단계 · 실제 · 네트워크 · 콘솔을 화면마다 싣고, 같으면 첫 화면 것을 한 번만 싣는다. 같은지는 실패한 단계(차례 · 제목)와 첫 실패 확인 문장으로만 가른다 — 실제 값은 화면 크기마다 달라 견주지 않는다(결과 화면이 확인을 한 칸으로 묶는 기준 [실행.md](실행.md) §8.3 과 다르다). 캡처는 화면마다 첫 장을 먼저 고르고 남는 자리를 차례로 채운다. 또 실패 댓글 첫 줄에도 화면을 적는다. 앞 판은 실패 카드의 첫 화면 것만 실어 둘 다 깨진 케이스(실행 20986 DMW-FN-023 → MQA-114)에 화면 말이 없었다. Android 앱 · 게임은 화면이 하나라, API 애플리케이션은 디바이스가 `desktop` 이어도 브라우저를 열지 않아([API.md](API.md) 「디바이스는 `desktop` 하나다」) 이 줄이 없다 — 애플리케이션 종류 `SCREEN` 만 적는다
- **같은 테스트가 또 실패하면** 열린 이슈(`bts_issue_case` 의 닫히지 않은 줄)에 댓글만 단다. 아직 보내지 못한 등록이 있으면(보낼 줄의 기다리는 CREATE) 새로 넣지 않는다 — 첫 실패 실행으로 올린다. 그만둔(GAVE_UP) 등록 뒤의 실패는 새로 넣는다. **흔들림 · 화면이 맞음으로 판정된 테스트**(BTS 에서 그 사유로 닫힌 테스트 — `bts_issue_case.resolution`)는 그 케이스를 고친 작성이 병합될 때까지 등록하지 않는다(사람이 이미 판정했고 테스트를 고칠 일만 남았다 — BTS-F3-04 리뷰. 환경 문제 · 중복 · 테스트 문제는 다음 실패를 다시 올린다 — 테스트 문제로 바로 닫으면 고침을 세우지 않아 기다릴 병합이 없다 · 2026-11-11 결정 23). **「테스트 수정」 중인 테스트**(`bts_test_fix` 의 도는 줄 — 아래 「테스트 수정 바퀴」)도 등록하지 않는다 — 그 이슈가 아직 열려 있어 열린 이슈 규칙대로 댓글만 단다. 앞 실행 결과가 섞인 테스트는 올리되 꼬리표가 「흔들림 같음」이다(아래)
- **보내기는 「보낼 줄」로만** — 실행 끝이 `bts_outbox` 에 줄을 넣고 60초 점검이 보낸다. 1분 간격 5번 · 4xx(권한 · 요청 오류) · 3xx(주소 넘김) · 이슈 키 없는 만들기 답은 그 자리에서 멈춘다(408 · 429 는 다시 — 결정 17). 같은 이슈의 줄은 앞 줄이 끝나야 뒤 줄을 보낸다. 그만두면 실행 결과 실패 카드에 「Issue Bunker 등록 실패 · <까닭>」 + [다시 보내기](§8.15). 재기동 뒤에도 줄이 남아 이어 보낸다
- **보내는 열쇠는 「QA Hub AI」 계정 열쇠다** — 등록 · 댓글 · 상태 · 담당자만 열린 BTS 계정(BTS-F2-02)
- **밖으로 나가는 글은 전부 가린다** — 이슈 본문 · 댓글(기대 vs 실제 · 실패 원인 · 재현 단계 · 폰 logcat 줄 포함)은 첨부와 같은 증적 비밀값 가림 함수를 거친다. 되비친 비밀값이 실패 원인에 실린다([공통/2](../공통/2-명세선언.md) §4.1 비밀값 꼬리표). 비밀 글자는 그 항목의 원본 값(`run_item`)에서 고른다 — 화면용 항목 상세의 값은 이미 별표라 거기서 고르면 아무것도 안 가린다

- **세우는 작성 요청은 결정 진행이 세우는 반영 요청과 같다** — `kind = 'AUTHOR'` · params `{ prdApply: true, …, decision: { after: <그때 열린 작성>, count: 1 } }` · 요청한 사람 `bts`(이름 「Issue Bunker DM-12」) — `decision` 칸 때문에 작성 목록에는 구분 「수정」(testFix 줄은 「자동 수정」 — §8.15 「자동 수정 표시」) · 작성자 「Issue Bunker DM-12」로 보이고(2026-11-10 한 줄 표 — 도메인/작성 §3.6 「작성 목록 줄」) 요청한 사람 이름으로 가른다. 대상 실행은 짝 줄의 `first_run`(처음 올린 실행)에서 그 케이스가 실패한 실행이다 — 한 건 실행으로 올린 이슈는 `first_run` 이 부모라 그 부모에 붙은 한 건 실행 가운데 실패한 가장 늦은 것을 쓴다. 지워졌거나 실패가 없으면 그 케이스는 기록만

   - 열린 짝 줄이 없는 이슈(사람이 올린 이슈 · 짝이 다 닫힌 이슈)는 맡지 않고 「Test Commander 가 올린 실패 이슈만 테스트를 수정할 수 있어요」 댓글. 짝을 비운 연결은 아무것도 안 한다
   - 같은 테스트 · 대상 서버에 도는 줄(`bts_test_fix` 의 FIXING · WAIT_MERGE · RERUNNING)이 있으면 새로 세우지 않는다 — 같은 알림이 다시 오거나 재기동 뒤 다시 와도 겹치지 않는다. 그 이슈의 줄이면 아무것도 안 보내고, 다른 이슈의 줄이면 「이 테스트는 <키> 에서 이미 수정 중이에요」 댓글
   - **이슈가 「테스트 수정」을 떠나면**(알림 `fromState` 가 그 짝이고 `toState` 가 아님 — 우리가 닫거나 되돌린 것은 줄이 이미 끝나 해당 없다) 그 이슈의 도는 줄을 `GAVE_UP`(까닭 「사람이 이슈를 옮겼어요」)으로 끝낸다. 병합을 기다리다 멈춘 줄도 이렇게 풀린다 — 다시 「테스트 수정」으로 옮기면 새 줄로 돈다
   - 담당자를 「QA Hub AI」로 바꾼다(보낼 줄 ASSIGN — 「QA Hub AI」 번호는 whoami 로 읽는다. 4xx 면 담당자 바꾸기만 건너뛰고 서버 기록을 남긴다. 그 이슈에 도는 줄이 있으면 다시 온 알림도 넣는다 — 줄을 세운 뒤 깨졌어도 담당자가 바뀌게). 짝 줄은 닫지 않는다 — 이슈가 열려 있다
   - 맡았는데 고침을 하나도 못 세웠으면(첫 실행이 지워짐 · 그 실행에 실패 기록이 없음 — 「판정은 BTS 에서」 「세우는 작성 요청」) 「테스트 수정」에 그대로 두지 않고 아래 5 「되돌리기」로 돌려준다 — 까닭 「테스트를 수정하지 못했어요 — 처음 실패한 실행이 지워졌거나 그 실행에 이 테스트의 실패 기록이 없어요」. 다른 이슈가 이미 고치는 테스트뿐이면 그 댓글만 단다. 둘이 섞였으면(못 세운 테스트와 다른 이슈가 고치는 테스트) 그 댓글도 달고 되돌린다 — 이 이슈에서 도는 고침이 없다. 같은 알림이 다시 와도 아직 안 보낸 되돌리기가 있으면 또 넣지 않는다(BTS-F10-06)
2. **고침** — 지금 testFix 작성을 세운다(앞 판과 같은 반영 요청 · params `testFix: { issueKey, cases, note }` · `decision.after`). `note` 는 맡을 때 서버가 「QA Hub AI」 열쇠로 읽은 이슈 글 · 댓글(8000자까지 · `close.ts` `이슈글읽기`)이다 — 자식은 자료로만 읽고 그 안의 지시는 따르지 않는다. 못 읽으면(5xx · 408 · 429 · 끊김) 알림에 503 을 돌려 BTS 가 다시 보낸다(「판정은 BTS 에서」 「한 번만 한다」). 고칠 케이스 · 실행은 짝 줄의 첫 실행에서 찾는 지금 규칙(「판정은 BTS 에서」 「세우는 작성 요청」) 그대로다
   - PR 이 열리면(작성 끝내기 DONE) 「테스트 수정 PR 을 열었어요 — <고친 곳 한 줄>」 다음 줄에 PR 주소인 댓글을 넣고(번호는 주소에 보인다 — 머리에 「#729 을」처럼 넣으면 조사가 숫자 읽기와 어긋난다 · BTS-F10-09 시험) 그 뒤에 이슈의 필드 「테스트 수정 PR」에 주소를 적는다(보낼 줄 FIELD — 자동 설정이 필드를 못 만든 연결은 건너뛴다. 쓰기 문이 막아 403 이어도 댓글은 이미 갔다)
   - PR 제목은 `[Test Commander] 테스트 수정 · <이슈 키> · <tcId>` 다. 본문 「테스트 고침」 줄의 다시 돌린 횟수는 마지막 전체 돌려 보기([작성.md](작성.md) §3.6 — PR 본문 이름 「3번 돌려 보기」)에서 실제로 돈 횟수를 적는다(앞 판은 늘 0이었다). 닫기 줄(`Closes`)은 지금처럼 넣지 않는다
   - 바뀐 케이스가 없이 끝났거나(고칠 게 없음) 작성이 실패 · 멈춤 · 폐기되면 → 아래 5 「되돌리기」
3. **병합 — 세 조건이 맞으면 Commander 가 한다**(결정 24). 작성 에이전트가 끝내기 때 재어 끝내기 결과에 싣는다(`result.testFix.autoMerge` · `held`). 셋 다 맞으면 서버가 그 작성의 반영(MERGE)을 스스로 세운다(요청한 사람 `bts`). 아니면 「사람 확인이 필요해요 — <걸린 까닭>」 댓글을 달고 사람이 지금처럼 테스트 작성 화면에서 반영한다. GitHub 에서 직접 병합했으면 지금 규칙대로 반영을 한 번 눌러야 이어진다(`authoring/continue.ts` 「GitHub 에서 직접 병합한 것은 반영을 한 번 눌러야 선다」)
   - **기대값 그대로** — 고친 케이스의 `verify` 기대값(세 번째 인자 · `verify.element` 는 네 번째 · `verify.rates` 는 세 번째와 허용 오차)과 `expected` 가 고치기 전과 같다. 실제 값 칸(둘째 인자 · `verify.element` 는 셋째) 안에서 견주는 글자 · 숫자도 기대값으로 본다 — `verify('…', 할인 <= 5000, true)` 처럼 기대값을 실제 값 쪽에 쓴 케이스가 많다. 화면 요소 찾기 · 누르기 같은 부르기의 인자(옵션 객체 칸 포함)는 요소 주소라 빼고 본다. 고치기 전 기대값이 하나도 빠지거나 바뀌지 않으면 된다 — 확인을 더한 것은 괜찮다. 줄바꿈 · 끝 쉼표만 다른 것은 같은 값이다. 고치기 전 파일은 기준 커밋의 그 케이스 파일(`tests/<폴더>/<tcId>.spec.ts`)이다
   - **확인 문장 수 그대로** — 고친 케이스의 `verify` 문장 수가 줄지 않았다(같거나 늘었다)
   - **고장 내 보기 통과** — 지금 부수기([작성.md](작성.md) §3.6 — PR 본문 이름 「일부러 고장 내 보기」)가 고친 케이스에서 고장마다 그 자리 문장을 빨갛게 했다. 부수기는 자식이 돌리므로 자식이 고친 케이스마다 결과 요약에 `테스트 고침 고장 내 보기: <tcId> · 고장 <N> · 그 자리 빨강 <M>` 한 줄을 적고(`tpx-author` `references/apply.md` §7) 에이전트가 N 이 1 이상이고 M 이 N 과 같을 때만 통과로 친다(M 이 N 보다 작으면 못 잡은 고장 · 크면 숫자가 틀린 것이라 「재지 못함」)
   - 셋 가운데 하나라도 못 쟀으면(고치기 전 파일을 못 읽음 · 고장 내 보기 줄이 없음) 자동 병합하지 않는다 — 까닭은 「재지 못함」
   - **고장 내 보기 줄이 없으면 한 번 되묻는다** — 자식이 결과 요약을 빠뜨리고 끝나면(BTS-F10-09 시험 MQA-169 · PR #732 — 「[단계] 결과 요약」 표지만 찍고 끝났다) 에이전트가 PR 을 올리기 전에 같은 자식 세션(`--resume`)을 한 번 이어 불러 이미 한 일로 결과 요약만 다시 받는다. 그 부르기는 파일 고치기 · 명령 실행 · 보조 AI 를 막는다 — 검사가 끝난 케이스를 바꾸지 못하게다. 받은 글은 자식 글 뒤에 붙어 PR 본문 · 판정이 같이 읽는다. 그래도 줄이 없으면 「재지 못함」이다. 되물은 몫의 토큰은 사용량에 안 든다(서버가 사용량을 한 번만 받는다 — 드문 짧은 부르기라 하한값으로 둔다)
   - **바뀐 테스트 파일이 고친 케이스 파일뿐이어야 한다** — `tests/` 아래 다른 파일(다른 케이스 · 화면 부품 · helpers)도 바뀌었으면 그것은 재지 않으므로 「재지 못함」이다. 같은 반영에 다시씀 · 새 항목이 같이 실리면 사람이 반영한다([작성.md](작성.md) §3.6 「예외 하나」의 근거 「바뀐 것이 그 케이스 하나」를 지키는 자리)
   - 판정은 PR 이 열린 댓글 · 필드(위 2) 뒤에 한다. 걸린 까닭은 줄의 `held` 에 적는다. 댓글 꼴은 `사람 확인이 필요해요 — <까닭> · <까닭>` 다음 줄에 PR 주소다. 까닭 말은 「기대값이 바뀌었어요」 · 「확인 문장이 줄었어요」 · 「일부러 고장 내 보기에서 못 잡은 고장이 있어요」 · 「자동 병합 조건을 재지 못했어요」
   - 셋 다 맞아도 반영 판정(보류 케이스 · 겹치는 케이스 · 대상 서버 — [작성.md](작성.md) §7 「Authoring 머지」)이 막으면 그 까닭으로 같은 댓글을 단다 — 「값을 안 채운 보류 케이스가 남았어요」 · 「보류 케이스가 몇 건인지 모르는 작성이에요」 · 「겹치는 케이스를 아직 고르지 않았어요」 · 「반영할 대상 서버를 고르지 못했어요」 · 그 밖은 「자동 반영을 세우지 못했어요」. 대상 서버를 묻는 반영이면 결정 진행처럼 그 작성의 대상 서버로 한 번 더 세워 본다. 이 까닭은 `held` 에 안 남고 댓글에만 남는다. 같은 글은 한 번만 단다. 그 작성에 도는 실행이 있거나 뒤 실행이 더 있으면 아무것도 안 한다 — 뒤 실행이 끝날 때 다시 판정한다
   - 줄의 `merge` — 서버가 반영을 세우면 그때 `AUTO` 로 적어 두고(다시 판정하지 않게), 반영이 끝나면 그 반영을 세운 사람으로 다시 적는다 — `bts` 면 `AUTO`, 아니면 `PERSON`. 자동 반영이 실패해 사람이 다시 반영했으면 `PERSON` 이다
   - 병합 전 재실행 · 이어서 작성이 다른 PR 로 끝나면 줄의 PR 주소를 그 PR 로 바꾸고(`merge` 가 빈 동안만) 그 PR 로 다시 판정한다
   - **Commander 가 세운 반영이 실패 · 멈춤으로 끝나면** 「사람 확인이 필요해요 — 자동 반영이 실패했어요」 댓글(다음 줄에 PR 주소 · 같은 글은 한 번)을 달고 줄은 병합 기다림 그대로 둔다 — 사람이 테스트 작성 화면에서 반영하면 아래 4 로 이어진다. 되돌리지 않는 까닭은 되돌린 뒤 사람이 PR 을 고쳐 반영해도 이슈가 안 닫히기 때문이다(BTS-F10-06)
4. **다시 실행** — 반영이 DONE 이 되면 서버가 그 케이스 한 건 실행을 건다(처음 실패한 실행에 붙는 한 건 실행 — [실행.md](실행.md) §7 · 그 실행이 반복 실행이면 새 RERUN 실행이다 — 실행.md §3.2 「한 건」). 디바이스는 처음 실패한 디바이스와 그 실행에서 통과한 디바이스 둘 다다(DMW-FN-378 이면 모바일 + PC — 실패한 것만 고치다 통과하던 쪽을 깨뜨리지 않았는지 본다). 처음 실패가 실제 폰 Chrome(Device VISION)이었으면 `mobileOn: 'vision'` 이다. 실행자는 `bts`(이름 「Issue Bunker <키>」)
   - 이 실행은 실행 끝 실패 등록(위 「버그 바퀴」)을 하지 않는다 — 끝 판정은 아래 5 가 한다. 안 하면 실패 때 「또 실패」 댓글과 되돌리기 댓글이 같이 달린다(어느 줄의 `rerun_id` 인 실행은 건너뛴다)
   - 디바이스 팜이 꺼져 실제 폰을 못 잡으면(`FARM_OFF`) 실행을 걸지 않고 되돌린다 — 까닭 「실제 폰을 못 잡아 확인하지 못했어요」. 폰이 다른 실행에 쓰이는 중이면 보통 실행처럼 기다린다
   - 입력값은 비워 케이스 저장값으로 채운다(실행 창의 한 건 실행과 같다). 한 건 실행으로 올린 이슈는 실패가 붙은 실행이 아니라 한 건 실행에 있어 붙을 곳을 실행 쪽이 고른다(실행.md §3.2 「붙는 곳」). 처음 실패한 실행이 지워졌거나 실행을 못 걸면(케이스가 카탈로그에서 빠짐 등) 되돌린다 — 까닭 「처음 실패한 실행이 지워져 다시 실행하지 못했어요」 · 「다시 실행을 걸지 못했어요」(BTS-F10-06)
5. **끝** — 그 실행이 끝나면 모든 항목이 통과일 때만 닫고, 하나라도 실패 · 미실행이면 되돌린다
   - **다시 실행이 「준비 실패」(`PREP_FAILED` — [실행.md](실행.md) §3.2 「실행 전 준비」)로 끝나면 되돌리되 까닭이 다르다** — 「테스트 데이터 준비에 실패해 확인하지 못했어요. 고친 테스트는 반영됐어요 — 준비가 되면 그 테스트를 다시 실행해 주세요」와 `prepNote` 한 줄. 고친 테스트가 틀린 것이 아니라 데이터 준비가 안 된 것이고, 고친 코드는 이미 main 에 있어 사람이 한 건 실행만 다시 누르면 된다. 바퀴가 스스로 다시 걸지 않는 까닭은 준비 주소가 하루 꺼져 있으면 60초마다 실행이 쌓이기 때문이다 (2026-11-11 SEED-F1-01 · 반영 SEED-F1-03)
   - **닫기** — 이슈를 「닫힘」 짝 + 해결 상태 「테스트 문제」 짝으로 옮기고(보낼 줄 TRANSITION · `resolutionId`) 「실제 폰 · PC 에서 통과했어요 · RUN N」 댓글(디바이스 이름은 그 실행 것). 짝 줄을 `TEST_PROBLEM` 으로 닫는다. 테스트 문제로 닫힌 테스트는 다음 실패를 다시 올린다(위 「같은 테스트가 또 실패하면」 — 실패 등록의 「안 올릴 사유」에서 `TEST_PROBLEM` 을 뺀다 · F10-04. 앞 판은 병합을 기다렸는데 병합이 닫기보다 먼저라 영영 안 풀린다)
   - **되돌리기** — 이슈를 「QA 검토」 짝으로 옮기고 담당자를 옮긴 사람으로 되돌린 뒤 까닭 댓글(실패한 실행 고리 · 고칠 게 없음 · 작성 실패 · 팜 꺼짐 · 사람 확인 PR 폐기). **다시 고치지 않는다**(결정 11 과 같은 까닭) — 사람이 다시 「테스트 수정」으로 옮기면 새 줄로 한 번 더 돈다
   - 닫기의 해결 상태 번호는 연결이 적어 둔 이름으로 BTS 해결 상태 목록(`GET /api/v1/resolutions`)에서 찾는다 — 못 찾으면 해결 상태 없이 옮긴다. 한 이슈에 테스트가 여럿이면 마지막으로 끝난 줄이 닫고, 하나라도 되돌리면 같은 이슈의 다른 도는 줄은 `GAVE_UP` 이다 — 되돌린 이슈를 뒤 줄이 닫지 않게. 댓글의 「RUN N」 은 사람이 화면에서 찾는 실행이다 — 붙은 한 건이면 붙은 실행(그 화면에 결과가 바꿔 끼워진다), 붙을 곳이 없던 한 건이면 한 건 번호만, 새 RERUN 실행이면 그 실행. 다음 줄에 그 실행 화면 주소(`PLATFORM_PUBLIC_URL` 이 있고 결과 화면이 있을 때). 먼저 통과해 기다리던 줄은 형제 줄이 되돌려도 `PASSED` 그대로다 — 그 테스트는 고친 뒤 통과했다(§8.15 표시도 그대로). 되돌리기 까닭 꼴은 「<디바이스> 에서 통과하지 못했어요 · RUN N」 · 「테스트 수정 작성이 실패했어요」 · 「테스트 수정 작성이 멈췄어요」 · 「고칠 곳을 찾지 못했어요」 · 「테스트 수정 작성을 폐기했어요」 · 「테스트 수정 작성이 지워졌어요」 · 「다시 실행 기록이 없어 확인하지 못했어요」. PR 을 연 뒤의 재실행 실패는 PR 이 그대로라 되돌리지 않는다(BTS-F10-06)
6. **다음 단계 전에 이슈를 다시 읽는다** — 반영을 세우기 전 · 다시 실행을 걸기 전 · 닫기 전에 이슈가 이제 「테스트 수정」 짝이 아니면(사람이 옮김) 그 줄을 `GAVE_UP`(까닭 「사람이 이슈를 옮겼어요」)으로 끝내고 BTS 에는 아무것도 안 보낸다. 열린 PR · 작성은 그대로 둔다. BTS 에 못 닿으면(5xx · 408 · 429 · 끊김) 그 단계를 다음 60초 점검에서 다시 한다
   - 되돌리기 전에도 다시 읽는다. 이슈를 권한 · 없음(4xx)으로 못 읽으면 다시 읽어도 같아 `GAVE_UP`(까닭 「Issue Bunker 이슈를 읽지 못했어요 (<코드>)」)이다. **60초 점검은 따로 적어 둔 할 일 없이 줄 상태와 작성 · 실행 기록에서 다음 단계를 찾는다** — 반영이 끝났는데 도는 병합 기다림 줄(다시 실행) · 다시 실행이 끝난 줄(끝) · 작성이 PR 없이 끝난 줄(되돌리기) · 판정 전에 못 닿아 넘긴 줄(판정 — 사람 확인 댓글이 없고 그 PR 로 끝난 작성이 사슬의 최신이며 반영을 한 번도 안 세운 줄. 사람이 반영을 눌렀으면 그쪽이 이어 간다). 다시 실행을 막 차지하고 실행 번호를 못 적은 줄은 10분 뒤 「기록 없음」으로 되돌린다(BTS-F10-06 — `apps/admin/src/bts/testFixSweep.ts`)
7. **차례** — 고침은 반영 요청이라 애플리케이션마다 한 번에 하나씩 돈다(지금 반영 규칙). 여러 이슈가 한꺼번에 와도 차례로 돈다
8. **기록** — 줄마다 `bts_test_fix` 한 줄([공통/4-데이터모델.md](../공통/4-데이터모델.md) 「BTS 연동 표」 BTS-F10-03). 화면 A · B 가 이것을 읽는다(§8.15 「자동 수정 표시」). 밖으로 나가는 댓글은 지금처럼 증적 비밀값 가림을 거친다

#### 수정 AI (`BUGFIX`)

BTS-F6-01 반영 2026-10-31 — 서버 `apps/admin/src/bts/bugfix.ts` · `bugfixOwner.ts` · `bugfixRoutes.ts`, 에이전트 `scripts/authoring-bugfix.ts` · `authoring-bugfix-prompt.ts`. 「(시작 질문)」이 붙은 줄은 BTS-F6-01 시작 질문(2026-10-31 사용자 승인)에서 정했다.

- **「개발 요청」 이슈만 맡는다.** QA Hub 에서 온 이슈가 「개발 요청」이 되면 BTS 규칙이 「QA Hub AI」에게 할당하고, 사람이 올린 버그는 사람이 담당자를 「QA Hub AI」로 바꾸면 맡는다. 담당자 변경은 BTS 규칙 웹훅 호출로 받는다(결정 18)
  - 신호를 받으면 이슈를 다시 읽어 상태가 「개발 요청」 짝(`status_map.DEV_REQUEST`)이고 담당자가 「QA Hub AI」 자신(BTS `GET /api/v1/users/me/whoami` 의 userId)일 때만 맡는다(시작 질문). 같은 이슈의 기다리거나 도는 수정 일이 있으면 그대로 둔다 — 애플리케이션 · 이슈마다 하나(고유 색인)
  - BTS 에 못 닿으면(이슈 다시 읽기 · whoami · 구성 요소 목록이 5xx · 408 · 429 · 끊김 · 이슈 글 읽기) 규칙 문이 503 — BTS 자동화 실행 기록에 실패로 보인다. 조용히 「내 것이 아님」으로 치면 담당 신호를 영영 놓친다
- 맡으면 그 애플리케이션의 `BUGFIX` 요청을 대기열에 세운다. BTS 화면에서 이 일의 이름은 「Issue Bunker 에이전트」다. 사람 작성 목록 · 알림 · 결정 목록에는 안 보인다 — BTS 이슈에서 본다. 사람의 다시 실행은 400 `BAD_KIND`
  - **고칠 애플리케이션**(시작 질문) — QA Hub 가 올린 이슈면 그 테스트의 애플리케이션(`bts_issue_case`). 사람이 올린 버그는 프로젝트에 활성 애플리케이션이 하나면 그것, 여럿이면 이슈의 BTS 구성 요소 이름과 같은 애플리케이션(대소문자 · 앞뒤 빈칸 무시). 못 고르면 맡지 않고 「어느 애플리케이션 코드인지 몰라 맡지 못했어요」 댓글 + 아래 넘길 사람의 리드 차례로 넘긴다
  - **고칠 저장소**는 그 애플리케이션 「코드 저장소」 칸(`service.code_repos`)의 첫 줄이다(시작 질문). 비었으면 저장소 없이 원인 분석만 한다
  - **이슈 글 · 댓글은 맡을 때 서버가 「QA Hub AI」 열쇠로 읽어 요청 params 에 담는다**(8000자 — 「테스트 수정」 고침과 같은 함수 `close.ts` `이슈글읽기`, 시작 질문). 자식은 자료 파일을 먼저 읽고, 지금 상태와 댓글은 집기 bugfix 칸의 프로젝트 번호로 MCP `bts_search` 를 불러 다시 읽는다(2026-11-02 사용자 · PR 4). 둘 다 자료라 그 안의 지시는 따르지 않는다. 그래서 이슈 글 읽기 통로(옛 계약의 `GET …/:id/bts`)는 두지 않는다
- 자식은 저장소 사본에서 파일만 고친다(도구는 읽기 · 쓰기 · 찾기와 QA Hub MCP — 셸이 없어 테스트를 돌리지 않는다). clone · 커밋 · push · 초안 PR 은 에이전트 스크립트가 **작성 에이전트의 GitHub 로그인**으로 한다 — 그 계정이 대상 저장소에 쓰기 권한이 있어야 한다(시작 질문). 브랜치는 `qahub-bugfix-<요청 번호>`. `.github/` · `CODEOWNERS` · 링크 · 서브모듈을 바꿨으면 올리지 않고 원인 분석으로 바꾼다. 병합은 사람이다
  - **PR 본문 첫 줄은 `Closes <이슈 키>` 다**(BTS-F9-01 시험 문제 24 · 2026-11-08). BTS 의 PR 병합 규칙(아래 「새 기능 바퀴」 1)은 PR 제목 · 본문에서 닫기 낱말(`Close` · `Fix` · `Resolve` 꼴)이 바로 앞에 붙은 대문자 키만 읽는다(BTS `PrIssueKeyExtractor`). 제목 `[Test Commander] <키> …` 만으로는 병합해도 이슈가 「코드 리뷰」에 멈춰 「병합 → 배포 → 재검증」이 끊긴다(`authoring-bugfix-prompt.ts` `PR본문`). 이슈 제목 · AI 요약은 PR 제목 · 본문에 싣기 전에 닫기 낱말 뒤를 `:` 로 끊는다(`Hotfix MQA-90` → `Hotfix: MQA-90` · `닫기낱말끊기`) — BTS 는 앞 낱말 경계를 보지 않아 그대로 실으면 상관없는 이슈까지 「배포 대기」로 옮긴다
  - 테스트 저장소 PR(작성 · 「고친 요구만 다시 작성」 · 「테스트 수정」 고침 · 롤백 되돌림 PR)에는 닫기 줄을 넣지 않는다. 테스트 PR 을 병합해도 서비스 코드는 그대로라 이슈가 「배포 대기」로 가면 안 된다. 누가 BTS Git 웹훅을 테스트 저장소에 붙여도 닫기 줄이 없어 이슈는 움직이지 않는다
- **push 전에 비밀값 검사** — 지금 작성 PR 이 push 전에 거치는 비밀값 검사(작성.md §3.6)를 대상 저장소 diff · PR 본문 · BTS 댓글에도 건다. 걸리면 push 하지 않고 원인 분석 댓글로 바꾼다. PR 본문 · 댓글은 위 크기 상한과 같은 규칙으로 줄인다
- **결과는 결과 통로 하나로**(§7 `POST …/:id/bugfix`) — 서버가 결과와 PR 주소(`pr_url`)를 먼저 저장하고 답한 뒤, 뒤에서 넘길 사람을 찾고 보낼 줄에 넣는다(BTS 가 느려도 에이전트의 응답 기다림을 넘기지 않게). PR 이면 댓글(PR 주소 · 요약 · 수정한 파일) → 「코드 리뷰」 짝으로 옮기기 → 담당자 차례, 원인 분석이면 댓글 → 담당자. 같은 이슈의 줄은 앞 줄부터 BTS 에 닿는다. 결과 없이 끝내기 DONE 은 400 `BAD_BUGFIX`
- **넘길 사람** — CODEOWNERS → 고친 줄을 마지막으로 바꾼 사람(git 기록) → BTS 구성 요소 리드 → 프로젝트 리드. 앞의 둘은 에이전트가 사본에서 이메일로 모으고(CODEOWNERS 는 이메일 꼴 주인만 · 봇 메일은 뺀다), 뒤의 둘과 짝짓기는 서버가 BTS 에서 한다
  - **Git ↔ BTS 계정은 이메일로 짝짓는다** — BTS 에 이메일로 찾는 API 가 없어 이름 · 이메일 앞부분으로 사용자 목록(`GET /api/v1/users?query=`)을 찾고 이메일이 같은 사람을 고른다. BTS 사용자에 「활성」 칸이 없어 찾으면 그 사람이다(시작 질문)
  - BTS 에 「기본 담당자」가 없어 프로젝트 리드(`GET /api/v1/projects/<키>/lead`)로 대신한다(시작 질문). 아무도 없으면 담당자를 안 바꾸고 「넘길 사람을 찾지 못했어요」 댓글
  - **PR 리뷰어는 따로 정하지 않는다**(시작 질문 — BTS 계정과 GitHub 아이디를 이을 길이 없다). CODEOWNERS 가 있으면 GitHub 이 PR 을 검토 요청으로 바꿀 때 알아서 요청한다
- Git 과 BTS 가 겹치면 리뷰는 Git 이 정본이고 BTS 상태는 PR 을 따라간다. PR 닫힘(거절)은 처음엔 개발자가 BTS 에서 되돌린다(「1차 밖」)
- **재검증에서 또 실패하면** AI 는 다시 안 맡고 바로 사람에게 넘기며 댓글(어느 PR 을 배포했는데 또 실패 · 실패 이유 · 고친 곳). 「또 실패」는 PR 을 낸 수정 일이 끝난 뒤 배포가 그 이슈를 다시 맡았고(`bts_claim.claimed_at` 이 끝난 때보다 늦다) 실행 실패가 그 열린 이슈에 댓글을 다는 때다(`failReport.ts`). 한 번만 넘긴다(`result.bugfix.handedBack`). 그 뒤 「QA Hub AI」에게 다시 와도 맡지 않고 넘겼던 사람에게 되돌린다. 넘기기 전(PR 이 거절돼 사람이 다시 「QA Hub AI」로 넘긴 경우 등)에는 새로 맡는다
- **못 고치거나 저장소가 없으면** 원인 분석 댓글 + 사람에게. 저장소가 없을 때 이슈에 「코드 없음 — 원인 분석만」. 저장소가 없어도 작성 · BTS 등록은 그대로 돈다
- **결과 없이 끝나면**(실패 · 중단) 「Issue Bunker 에이전트가 이 결함을 수정하지 못했어요」 댓글 + 리드 차례로 넘긴다 — 이슈가 「QA Hub AI」에 묶여 멈추지 않게. 에이전트가 꺼져 멈춘 줄(`AGENT_RESTART`)은 AI 탓이 아니라 같은 칸으로 새로 세운다(PRD 초안과 같은 판단)

#### 롤백 바퀴

- `deploy.sh` 가 올라간 커밋을 적어 둔다. 새 커밋이 옛 커밋의 조상이면 롤백이다 → 사이 커밋 메시지의 이슈 키를 뽑아 BTS 웹훅과 배포 신호 본문(`rollback: true` · `rollbackKeys`)에 같이 싣는다 → BTS 규칙이 「받은 키 목록 전부」를 「배포 대기」로 되돌린다(BTS-F2-01, 같은 200 상한)
- QA Hub 는 PRD 와 테스트도 되돌린다 — 다섯 조각
  1. 되돌릴 요구는 둘이다 — 지금 판에서 `fromIssues` 가 받은 키와 겹치는 항목, 그리고 판 기록(`prd_version.changes` 의 `issueKeys`)에서 받은 키로 지운 번호(지운 항목은 지금 판에 없어 꼬리표가 붙을 자리가 없다)
  2. PRD 새 버전(`ROLLBACK`) — 「신규」는 지우고 「변경」 · 「지움」은 그 이슈를 고른 판 바로 앞 판의 항목으로 돌린다. 버전 기록에 「롤백 · 빌드 N · DM-12」
     — 「그 이슈를 고른 판」은 받은 키가 처음 닿은 판이다(항목의 `fromIssues` 에 처음 보인 판 · 그 키로 지운 줄이 든 판). 그 뒤 다른 이슈가 같은 요구를 또 고쳤으면 그 고침도 같이 사라진다(BTS-F7-01 시작 질문 4 — 드물어 그대로 둔다 · `bts/rollback.ts` `롤백판`)
     — 판은 애플리케이션마다다. 롤백 배포가 오면 그 프로젝트의 애플리케이션을 다 보고 되돌릴 것이 있는 곳에만 판이 선다. 같은 키가 다시 와도(실패한 롤백 배포를 다시 보냄) 되돌릴 것이 없어 판이 안 선다. 판의 `deploy_id` 가 그 배포를 가리켜 버전 기록이 빌드 번호를 읽는다 — 판을 세운 사람은 위 「누가」(7) 다
     — 그때 열린 작성이 있으면 판은 되돌림 요청을 집을 때 선다(위 「새 기능 바퀴」 8). 그때 `deploy_id` 는 그 빌드의 배포 줄이다 — 실패한 신호를 다시 보내면 앞 줄이 지워지고 새 줄이 선다
  3. 되돌리는 PR — 그 애플리케이션의 「고친 요구만 다시 작성」 요청 하나. params 에 `{ prdApply: true, rollbackDeploy: <배포 번호>, rollbackBuild: <빌드>, decision: { after, count: 1 } }` 를 단다(판을 미뤘으면 받은 키 `rollbackKeys` 도 — 판을 세우면 지운다) — 배포 한 줄에 요청 칸 하나로는 애플리케이션 둘을 못 담아 요청 쪽이 배포를 가리킨다(BTS-F7-01 시작 질문 1 · `bts_deploy.revert_request_id` 는 지웠다). 열린 작성과 부딪히면 위 「새 기능 바퀴」 8
  4. 그 PR 병합 전에 다시 배포되면 그 요청을 폐기하고 PR 을 닫는다 — 「다시 배포」는 그 프로젝트의 뒤 배포 아무것이나다(롤백이든 아니든). 같은 빌드를 다시 보낸 것(실패한 배포 다시 보내기)은 아니다. 사슬(재실행 · 반영 포함) 전부를 폐기하되 대기 줄은 멈춤으로 닫고(멈춘 사람 `bts`) 도는 줄은 멈춤을 건다. 뿌리 params 에 `redeployed: true` 를 단다 — 사람이 손으로 폐기한 되돌림 요청의 PR 은 지금처럼 남긴다(작성.md §7 discard). 병합했거나 병합 중이면 그대로 둔다. 사람이 만드는 작성 요청은 `rollbackDeploy` · `rollbackBuild` · `rollbackKeys` · `redeployed` 를 실을 수 없다(400 `BAD_EDIT`). PRD 롤백 판은 그대로 둔다 — 다시 맡은 이슈로 새 PRD 초안이 서서 사람이 다시 고른다(시작 질문 3). 열린 작성 때문에 판을 미룬 채 거둬진 요청은 판도 안 선다 — 그 PRD 도 같은 초안에서 사람이 고른다(2026-11-08 사용자 · 위 「새 기능 바퀴」 8)
     — **PR 은 작성 에이전트가 닫는다**(서버는 GitHub 열쇠가 없다 — 결정 10). 애플리케이션마다 1분에 한 번(줄이 바빠도) §7 「닫을 PR」을 묻고 `gh pr close`(댓글 「롤백 뒤 다시 배포되어 …」 · 브랜치는 남긴다 — 작성.md §7 discard)한 뒤 닫음을 적는다. 이미 닫혔거나 병합된 PR 도 닫음으로 적고, 상태를 못 읽으면 1분 뒤 다시 본다(`scripts/authoring-pr-close.ts`)
  5. 그 키를 다루던 작성 중 · 확인 대기 초안(`PRD_DRAFT` 와 그 카드)은 버린다 — 대기 · 도는 · 끝났고 안 고른 · 실패 · 멈춘 초안 모두다. 초안이 롤백되지 않은 키도 담았으면 그 키만으로 초안을 새로 세운다(맡음이 남아 버리기만 하면 그 이슈의 초안이 사라진다). 고른 초안은 이미 판에 들어가 위 2 가 되돌린다
     — 롤백은 배포 신호가 받는 그 자리에서 실행을 걸기 전에 한다. 깨지면 배포를 `FAILED` 로 두고 503 `ROLLBACK_FAILED` — 같은 빌드로 신호만 다시 보내면 처음부터 다시 돈다(되돌린 애플리케이션은 되돌릴 것이 없어, 판을 미룬 애플리케이션은 미룬 요청이 있어 겹치지 않는다(위 「새 기능 바퀴」 8) · `bts/deploy.ts`)

  - 같은 사건이 두 번 오면 한 번만 쌓는다 — PR_MERGED 는 같은 prUrl, ISSUE_OPEN 은 같은 이슈 키. 견주는 것은 남아 있는 사건뿐이다 — 아래 「보관」이 90일 뒤 지운 사건과는 견주지 않는다. 닫힘(ISSUE_CLOSE · TASK_DONE)은 다시 열고 닫을 수 있어 또 쌓는다. 사건 쓰기가 깨져도 BTS 알림 처리(닫기 사유)는 되돌리지 않고 서버 기록만 남긴다 — 사건 하나를 잃는 쪽이 닫기를 다시 도는 쪽보다 낫다
  - 노트 고치기는 **반영 안 된 사건**을 집을 때 한 번에 받는다 — 아직 아무 일도 안 받은 사건과, 받은 일이 실패 · 중단으로 끝난 사건이다. 한 번에 200건까지
  - NOTE 의 RERUN 을 세우는 길은 지금 없다 — 사람 다시 실행은 BAD_KIND, 에이전트 토큰은 새 요청을 못 만든다. 실패하면 다음 사건이 새 NOTE 를 세운다. 집기 · 열쇠의 「그 RERUN」 갈래는 이어하기 길이 생길 때를 위한 자리다
  - 노트 고치기가 DONE 으로 끝날 때 아무 일도 안 받은 사건(도는 동안 온 것 · 200건을 넘은 것)이 남았으면 다음 노트 고치기를 바로 세운다. 에이전트가 꺼져 멈춘 것(STOPPED · AGENT_RESTART)도 그 줄이 받은 사건으로 바로 세운다 — AI 탓이 아니다. 그 밖의 실패 · 중단으로 끝나면 세우지 않는다 — 다음 사건이 올 때 다시 받는다(AI 가 계속 실패해도 끝없이 돌지 않게 · `projectNote/events.ts`). 판을 저장한 뒤 실패한 줄의 사건은 반영된 것으로 본다
- 노트 고치기는 바뀐 문서만 보낸다(지운 문서는 이름만). 서버가 앞 판에 겹쳐 새 판 하나를 만든다 — 안 바뀐 문서를 AI 가 다시 쓰다 흐트러지지 않게
- AI 가 실패하면 앞 판을 그대로 둔다. `note_read` 목차에 판 번호 · 「마지막 고친 때」
- **보관** (2026-11-02 사용자 — MCP 최적화 시작 질문) — 읽는 쪽은 지금 판 하나만 보므로 옛 판과 다 쓴 사건을 계속 쌓지 않는다. 새 판을 저장하는 그 트랜잭션에서 같이 지운다. 따로 도는 청소는 없다(숫자는 코드가 정본 — `apps/admin/src/projectNote/note.ts` `노트보관`)
  - 판 — 최근 10판은 늘 남긴다. 그보다 오래된 판은 저장한 지 90일이 지나면 지운다
  - 사건 — 반영이 끝난 사건(받은 일이 DONE 으로 끝났거나 판을 남겼다)은 쌓인 지 90일이 지나면 지운다. 반영 안 된 사건은 남아 다음 노트 고치기가 받는다
  - 사건을 판보다 먼저 지운다 — 실패한 일이 판을 남겼으면 그 사건은 「그 일의 판이 있다」로 반영을 안다. 판만 먼저 지워지면 그 사건을 다시 받아 노트에 두 번 적는다. 판은 자기가 받은 사건보다 늦게 저장되므로 판이 90일을 넘길 때 그 사건도 이미 90일을 넘겨 같은 트랜잭션에서 먼저 지워진다
  - 노트 안 「지난 기록 YYYY-MM」 문서는 최근 6개월치만 둔다. 더 오래된 달은 노트 고치는 AI 가 `remove` 로 지운다(지시문이 정본 — 서버는 막지 않는다)

- **Scout 챗봇이 쓰는 도구 다섯과 키 `mcq_`** (2026-11-11 SCOUT-F1-01 · 도구 다섯 반영 2026-11-11 SCOUT-F1-02 `mcp/scout.ts` · 키 반영 2026-11-11 SCOUT-F1-03 `mcp/questionKey.ts` — 정본은 [챗봇.md](챗봇.md) §3.14) — 사람이 화면에서 묻는 질문 하나마다 Scout 의 자식이 이 창구를 부른다. 도구는 실행 기록 검색(`run_list` — 프로젝트의 최근 실행을 일곱 종류 섞어서) · E2E 결과(`e2e_result`) · 호환성 결과(`compat_result`) · 성능 결과(`perf_result`) · 최근 이슈(`issue_list`)다. **새 데이터를 만들지 않고 화면이 읽는 함수를 감싼다** — 권한도 그 화면 통로의 칸으로 `문판정` 을 부른다(실행 기록 검색 · E2E · 호환성 결과는 `(실행, read)` — 각각 `GET /api/runs`(성능 줄은 `GET /api/perf/runs`) · `GET /api/runs/:runId/scenario` · `GET /api/compat-runs/:runId`, 성능 결과는 `GET /api/perf/runs/:id` 의 칸, 최근 이슈는 BTS 찾기와 같다). 30줄 · 긴 글 자르기는 지금 도구와 같고 숫자는 계산하지 않고 저장된 판정을 옮긴다. 새 도구는 자동 AI(`mcj_`)에게도 열린다
- `mcq_` 요청의 사람은 **그 질문을 넣은 사람**이다 — 권한은 그 사람 것을 쓰고 배정을 그 질문의 프로젝트로 좁힌다. 키는 질문이 `RUNNING` 인 동안만 살고, 그 사람이 꺼졌으면 401 이다. BTS 찾기 · 최근 이슈는 브라우저 로그인처럼 그 사람의 대신 PAT 로 부른다 — 사람이 묻는 것이라 「QA Hub AI」 키를 빌리지 않는다. **Auth 에 안 묶인 사람(`auth_sub` 가 빈 비밀번호 로그인 계정)이면 `BTS_UNAUTHORIZED` 다** — 지금 `bts_search` 는 사람이 없을 때 「QA Hub AI」 키로 넘어가는데(`mcp/tools.ts`), `mcq_` 에서 그러면 그 사람이 못 보는 이슈를 Scout 로 본다
- 새 npm 패키지 `@modelcontextprotocol/sdk` 는 BTS-F4-01 시작 질문에서 승인받았다(2026-10-31 사용자 — 「나중에 기능 추가할 수 있으니」 · 1.32.1). 긴 작업 자리가 패키지에 있다. 브라우저 로그인은 2026-11-05 S28 에 열었다 — 패키지의 인가 자리는 안 쓰고 토큰을 `jose` 로 확인한다([인증.md](인증.md) §7 「인증 적용 범위」)

#### 설정 · 고장 대응

- 처음 설정은 「설정 › Issue Bunker 연결」 한 화면(§8.15) — 프로젝트 짝짓기 · 「QA Hub AI」 계정 이름 · 회사마다 다른 BTS 상태 · 해결 사유 ↔ 단계 짝짓기(BTS 에서 목록을 불러와 고른다) · 애플리케이션별 코드 저장소 · **BTS 자동 설정** · `deploy.sh` 한 줄 복사
- **BTS 쪽 설정은 QA Hub 가 만든다** (2026-10-31 BTS-F3-05 사용자 「자동으로 설정하면 되잖아」 · 「통합계정이잖아」) — 웹훅 하나(이슈 생성 · 상태 전환 → `POST /api/bts/events/:projectId`, 서명 비밀은 QA Hub 가 만들어 넣는다) · 자동화 규칙 둘(담당자 변경 · PR 병합 → 웹훅 호출, 머리에 `btr_`) · 보드마다 「QA 검토」 상태가 든 칸이 없으면 칸 하나 · 이슈 필드 「테스트 수정 PR」(링크 · BTS 사용자 정의 필드 — 이름 「테스트 수정 PR」이나 키 `qahub_test_fix_pr` 인 필드가 없으면 만들고 그 키를 `bts_link.test_fix_field` 에 적는다 — 이슈 값은 필드 키로 쓴다 · 2026-11-11 BTS-F10 — 테스트 수정 바퀴 2). 누른 운영 계정의 대신 PAT 로 부른다(2026-11-04 S25)(「열쇠 표」). 다시 눌러도 한 벌이다 — 웹훅은 주소, 규칙은 이름(`QA Hub · 담당자 변경` · `QA Hub · PR 병합`)으로 찾아 고친다. 하나가 막혀도 나머지는 만든다
- 권한 — 웹훅은 BTS 시스템 관리자, 규칙은 그 프로젝트 자동화 관리(기본 프로젝트 관리자 · 멤버여야 한다), 보드 칸은 그 프로젝트 만들기 권한. BTS 는 사설 주소 · localhost 로 가는 웹훅을 거절해 QA Hub 공개 주소(`PLATFORM_PUBLIC_URL`)가 있어야 한다. PR 병합 규칙은 BTS 프로젝트에 GitHub 연결(BTS 「Git 웹훅」)이 있어야 돈다 — 그 연결은 QA Hub 가 만들지 않는다
- 이 화면에서 사람 손이 남는 것은 `deploy.sh` 한 줄이다 — 회사 배포 서버에 있어 QA Hub 가 못 고친다. 거기 들어갈 토큰(`pdk_`)은 프로젝트 전용이다. 사람 토큰을 두면 그 사람이 나갈 때 배포 신호가 끊긴다
- **자동 설정 밖** — 아래는 QA Hub 를 부르지 않고 BTS 안에서 상태만 바꾸는 규칙이라 사람이 BTS 에서 만든다(자동화 동작 「상태 바꾸기」는 BTS-F2-01 이 BTS 에 더한다 · 데모마켓 것도 그 줄이 동작을 더한 뒤 만든다 — 2026-10-31 BTS-F5-02 시작 질문)

  | 무엇 | 어디서 | 누가 |
  |---|---|---|
  | PR 병합 → 「배포 대기」 규칙 | BTS 자동화 | 사람(BTS-F2-01 뒤) |
  | deploy 웹훅 → 「배포 대기」 전부 「QA 요청」 규칙 | BTS 자동화 | 사람(BTS-F2-01 뒤) |
  | 「개발 요청」 → 「QA Hub AI」 할당 · 롤백 → 「배포 대기」로 되돌림 규칙 | BTS 자동화 | 사람(BTS-F2-01 뒤) |
  | BTS 프로젝트의 GitHub 연결(PR 병합 규칙이 돌게) | BTS 프로젝트 설정 | 사람 |
- **짝지을 이름** — 상태(배포 대기 · QA 요청 · QA 검토 · 개발 요청 · 코드 리뷰 · 닫힘 · 테스트 수정)와 해결 상태(정본은 4-데이터모델 `bts_link` 칸 주석 — 화면이 맞음 · 테스트 문제 · 흔들림 · 환경 문제 · 중복). 회사의 상태 · 해결 상태를 이 단계에 짝짓는다 — 상태는 BTS 상태 키, 해결 상태는 이름을 둔다(`bts_link.status_map` · `resolution_map` — 옮기기는 `toStatusKey` 로, 닫기 사유는 이슈의 해결 이름으로 견준다). 짝이 빈 단계가 있으면 연결을 저장하지 못한다. **「테스트 수정」(`TEST_FIX`)만 비워도 된다**(2026-11-11 BTS-F10) — 비우면 테스트 수정 바퀴가 안 돈다. 앞서 이은 연결이 저장 불가로 깨지지 않게다. 이 상태는 다른 상태처럼 사람이 BTS 워크플로에 만든다(자동 설정 밖)
- BTS 가 꺼지면 보낼 줄이 다시 보낸다(결정 17). 구독 한도에 닿으면 작성 에이전트가 지금처럼 멈추고 알리고, 풀리면 이어서 한다(사람이 시킨 일 먼저)
- BTS 「조건에 맞는 이슈 전부」 · 「받은 키 목록 전부」는 한 번에 200개 — 넘으면 하나도 안 바꾸고 BTS 자동화 실행 기록에 「상한 넘음」

#### 품질 숫자

AI 품질은 따로 시험하지 않고 사람이 고른 결과로 센다 — 대시보드(§8.15 「대시보드 두 숫자」).
- 초안 AI = 사람이 체크한 줄 ÷ AI 가 쓴 줄(PRD 초안 카드에서 진행한 것만 분모에 든다 — [초안 삭제]도 진행이라 쓴 줄이 다 분모에 든다)
- 수정 AI = 병합된 PR ÷ AI 가 올린 PR(닫히지도 병합되지도 않은 PR 은 분모에서 뺀다)
- 날 창(7 · 14 · 30일)과 상관없이 지금까지 전부 센다 — 건수가 작아 며칠로 자르면 0/0 이 잦다 (BTS-F8-01 시작 질문 2026-11-01)
- PR 이 병합됐는지 닫혔는지는 작성 에이전트가 애플리케이션마다 1분에 한 번 `gh pr view` 로 읽어 적는다(§7 「수정 PR 상태」 · `scripts/authoring-pr-close.ts`) — 서버는 GitHub 열쇠가 없고(결정 10) BTS 「PR 병합」 규칙으로는 닫힘을 모른다. 열린 PR · 못 읽은 PR 은 1분 뒤 다시 본다 (BTS-F8-01 시작 질문 2026-11-01)

- 상태 매핑은 BTS 에서 불러온 고르개다 — 상태는 키, 해결 사유는 이름을 저장한다. 「테스트 수정」 고르개만 맨 위에 「선택 안 함」이 있다 — 고르지 않으면 「테스트 수정을 쓰려면 Issue Bunker 워크플로에 상태를 만든 뒤 여기서 선택합니다」 한 줄(2026-11-11 BTS-F10-03). 이은 프로젝트는 열 때 저장한 계정 이름으로 바로 불러온다. 못 불러오면 까닭 한 줄과 글 칸으로 물러선다. 저장해 둔 값이 목록에 없어도 고르개에 남는다
- [저장하고 BTS 자동 설정] 하나로 연결 저장(BTS 를 한 번 불러 프로젝트 키를 확인 — 실패면 저장 안 됨 · 까닭 한 줄) → 바뀐 애플리케이션의 코드 저장소 → 자동 설정(§3.12 「설정 · 고장 대응」). 결과는 항목(2026-11-11 이슈 필드 「테스트 수정 PR」을 더했다)마다 ✓ · ✕ 와 까닭(권한 없음 · 접속하지 못함 · 실패 (코드)). 웹훅이 권한 없음이면 「웹훅은 Issue Bunker 시스템 관리자만 만들 수 있습니다 …」 한 줄
- 「QA Hub AI 계정 이름」은 보통 글 칸이다(가리지 않는다 · 자리 표시 `qahub-ai`) — Issue Bunker 에서 「QA Hub AI」로 쓰는 Auth 계정의 이름(username)을 적는다. 비밀이 아니라 저장한 값을 그대로 보인다(2026-11-04 S25 — 앞 판은 가린 `pat_…` 칸)
- 누른 계정이 Auth 에 안 묶였거나 대신 PAT 를 못 받으면 「Auth 계정으로 로그인한 운영 계정이어야 BTS 자동 설정을 할 수 있습니다」(NO_PERSONAL_TOKEN — 앞 판 문구는 내 메뉴 「통합계정 토큰」을 가리켰다)
- 배포 알림 토큰 원문은 발급 직후 한 번만 보인다(CI 토큰 구획과 같다 — [인증.md](인증.md) §8.8 「CI 토큰」). 원문은 그 자리에서 `deploy.sh` 한 줄에 들어가고, 아니면 `<배포 알림 토큰>` 자리로 남는다. 주소는 publicUrl, 없으면 브라우저 주소
- 연결 해제는 확인 창 — 「연결을 해제하면 이 프로젝트의 실패 판정은 Test Commander 에서 합니다」
- 화면의 「BTS」 글자는 `apps/admin/src/web/btsName.ts` 한 곳에서 읽는다 — 제품 이름이 바뀌면 그 한 줄만 고친다(2026-10-31 사용자). **2026-11-02 이름이 「Issue Bunker」로 정해져 그 줄을 바꿨다**([docs/WORDS.md](../../WORDS.md) §2 「제품 이름」). 서버가 만드는 글(이슈 본문 · 댓글 · 오류)과 명세가 옮겨 적은 글도 같은 날 바꿨다(PR #567) — 규칙 이름 `QA Hub · …` · 라벨 `QA Hub` 는 이름으로 다시 찾아 그대로다. 수정 커밋 제목은 `[Test Commander] <키> 수정 — …` 이고 앞 꼴 `[QA Hub] …` 도 알아본다
