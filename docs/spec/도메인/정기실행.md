# 정기 실행

> **이 장이 담는 절** — §3.16 정기 실행 · §7 정기 실행 통로 · §8.20 정기 실행 화면 (2026-11-13 · 진행판 SCHED-F1-01)
> 정기 실행은 **프로젝트에서 이미 만든 테스트를 골라 「세트」로 묶고, 정한 날 · 시각에 돌리고, 달력에서 예정과 지난 결과를 보는 곳이다.** 기능 · UI · E2E · 호환성 테스트를 같은 프로젝트의 여러 애플리케이션에서 섞어 담는다.
> **이 장이 정기 실행의 정본이다.** 다른 장(데이터모델 · 화면공통 · 인증 · 인프라 · 실행 · 안정화)은 자기 칸과 가리키는 줄만 적고 여기를 가리킨다. 성능 시나리오의 정기 실행은 이 장 밖이다 — [성능.md](성능.md) §3.9 「실행 · 결과」 그대로다.
> **쓰는 표** `sched_set` · `sched_set_item` · `sched_set_env` · `sched_occurrence` · `test_run.sched_occurrence_id` — 정의는 [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「정기 실행 표」. 읽기만 하는 표는 `test_case` · `scenario` · `compat_set` · `service_env`.

### 3.16 정기 실행 — 프로젝트 공통 테스트 세트 · 달력 (2026-11-13 사용자)

2026-11-12 까지 정기 실행은 두 곳에 흩어져 있었다 — 설정 › 애플리케이션의 「정기 실행」 구획(애플리케이션의 활성 케이스 전부를 매일 한 번, 운영 admin 만)과 성능 마법사의 시나리오 정기 실행. 무엇이 언제 도는지 한눈에 안 보였고, QA 담당자는 켜지도 못했다.
아래 결정은 2026-11-13 기획 대화(test_platform 배경 세션 8b7a9731)에서 주제마다 정했고, 사용자가 작업 계획을 승인했다(「이어달리기로 작업 진행하자」). 다시 묻지 않는다. 「(내 결정)」이 붙은 줄은 대화에서 알렸고 반대가 없던 것이다.
화면 시안은 [정기 실행 시안](https://claude.ai/artifact/LZdDot7SBakdppDCs7oVCV)(7판 · 시안 B · 눌러 볼 수 있다)이고 사용자가 B 를 골랐다.

#### 세트

- **세트는 프로젝트 하나에 속한다**(`sched_set.project_id`). 이름은 프로젝트 안에서 겹치지 않는다. 프로젝트가 지워지면(마지막 애플리케이션을 다른 프로젝트로 옮겨 빈 프로젝트가 지워질 때 — 인증 §7 `PATCH /api/settings/services/:id`) 세트 · 회차도 같이 지워지고 실행의 회차 번호는 빈다
- **담은 테스트 한 줄**(`sched_set_item`)은 종류 하나다. `seq` 가 화면 차례이자 실행을 만드는 차례다(결정 8).
  - 기능(`FN`) · UI(`UI`) — 애플리케이션 하나와 「전체」(`tc_ids` 비움) 또는 고른 케이스 번호 목록. API 애플리케이션에는 `UI` 줄이 없다(서버가 400)
  - E2E(`E2E`) — 시나리오 하나. 섞인 시나리오도 담는다. 줄의 애플리케이션 칸은 저장할 때 그 시나리오의 시작 애플리케이션이고, **돌 때는 시나리오의 지금 시작 애플리케이션을 다시 읽는다**([시나리오.md](시나리오.md) §3.7 결정 13)
  - 호환성(`COMPAT`) — 호환성 세트 하나. 줄의 애플리케이션은 그 세트의 애플리케이션이다
- **대상 서버는 실행을 만드는 애플리케이션마다 하나다**(`sched_set_env`) — 기능 · UI · 호환성 줄의 애플리케이션과 E2E 의 시작 애플리케이션. 그 애플리케이션의 대상 서버 줄에서 고르고, 실서비스 서버는 고를 수 없다(400 — 정기 실행은 사람 없이 돈다).
  섞인 E2E 의 다른 단계는 시나리오 규칙대로 시작 애플리케이션 서버와 **같은 이름**의 줄로 간다(시나리오 §3.7 「대상 서버는 이름으로 짝짓는다」) — 그 애플리케이션에 따로 고른 서버는 그 E2E 에 안 쓴다. 지나가는 애플리케이션에 같은 이름 줄이 없거나 그 줄이 실서비스 서버면 저장이 400 이다
- **돌 때 빠지는 줄** — 아래 경우 그 줄은 그 회차에서 건너뛰고 까닭을 회차에 남긴다(`sched_occurrence.notes`). 세트에는 남고 카드에 「빠진 케이스 N건」 · 「빠진 테스트 N개」로 보인다. 호환성 세트의 직접 추가 케이스와 같은 규칙이다([호환성.md](호환성.md) 「호환성 세트」)
  - 직접 고른 케이스가 지워지거나 비활성이다(그 케이스만 빠지고 나머지 케이스는 돈다)
  - 시나리오 · 호환성 세트를 치웠다 · 시나리오가 실행 불가다
  - 줄의 애플리케이션이 비활성이거나 다른 프로젝트로 옮겨 갔다(앞 판 정기 실행도 비활성 서비스는 돌지 않았다 — 공통/6-인프라 §9.2 「돌 조건」)
  - 섞인 E2E 가 지나가는 애플리케이션에 같은 이름 서버 줄이 없거나 실서비스 서버다 · 지나가는 애플리케이션이 다른 프로젝트로 옮겨 갔다. 까닭 코드 전체는 §7 세트줄 `skipped`
  - 그 애플리케이션의 대상 서버 줄이 지워졌거나 실서비스 서버가 되었다. 설정에서 대상 서버 줄을 고치는 것은 막지 않는다 — 앞 판 「켜 둔 정기 실행의 대상 서버를 빼면 400」(인증 §7)은 세트에는 없다
- **고칠 때** — 빠진 줄이 남아 있어도 저장은 된다. 새로 넣는 줄만 위 400 검사를 받는다(호환성 세트 「고치기」와 같다)
- **켜고 끈다**(`sched_set.is_on`). 끄면 앞으로의 회차가 안 서고, 줄에 서서 기다리던 회차도 빠진다(`SKIPPED`). 지난 회차는 그대로다
- **고친 내용은 다음에 시작하는 회차부터 쓴다** — 줄에 서서 기다리는 회차도 시작할 때의 세트로 실행을 만든다. 이미 시작한 회차는 안 바뀐다 관리 서버가 회차 도중에 다시 켜지면 그 회차는 그때의 세트로 이어 간다 — 회차가 읽은 세트는 서버 메모리에만 있다 (SCHED-F1-04)
- **저장한 그날은 이미 지난 시각에 돌지 않는다** — 회차는 그날의 정한 시각이 세트를 마지막으로 저장한 때(`updated_at`)보다 뒤일 때만 선다. 14:10 에 「매일 14:00」을 저장하면 다음 날부터다. 「한 번만」의 날짜 · 시각이 이미 지났으면 저장이 400 이다
- **마법사의 케이스 하나씩 고르기는 케이스 목록 통로를 쓴다** — 케이스 `read` 가 없는 사람은 「전체」만 고른다

#### 회차 — 언제 세우고 어떻게 돌리나

회차(`sched_occurrence`)는 세트가 그날 한 번 도는 것이다. 회차 하나가 실행 여러 개를 만든다.

- **admin 이 1분마다 본다** — 지금 정기 실행 점검(공통/6-인프라 §9.2)을 대신한다. HTTP 를 거치지 않는 것도 같다
- **회차를 세운다** — 세트가 켜져 있고 · 오늘(세트 시간대)이 반복에 들고 · 지금이 정한 시각부터 1시간 안이고 · 정한 시각이 마지막 저장 뒤이고 · 그날(`planned_on`) 회차가 아직 없으면 `QUEUED` 회차를 세운다. 그날 하나는 DB 가 막는다(`UNIQUE (set_id, planned_on)`) — 같은 날 시각을 고쳐도 둘째 회차는 안 선다. 1시간 창 · 서버가 꺼져 있었으면 그날 건너뜀 · DB 시계 규칙은 지금 정기 실행과 같다(공통/6-인프라 §9.2 「돌 조건」)
- **줄을 세운다(결정 8)** — 프로젝트마다 `RUNNING` 회차가 없을 때만 `QUEUED` 가운데 정한 시각이 가장 이른 것(같으면 세트 번호 차례)을 `RUNNING` 으로 바꾼다. 기다린 시간은 정한 시각과 실제 시작 시각의 차이다(`planned_at` · `started_at`)
- **줄 차례로 실행을 만든다** — `RUNNING` 회차는 지금 줄(`cur_seq`)의 실행을 만들고, 그 실행이 끝나면(`FINISHED` · `ABORTED` · `PREP_FAILED`) 다음 줄로 간다. 빠지는 줄 · 못 만든 줄은 까닭을 `notes` 에 남기고 바로 다음 줄로 간다. 같은 애플리케이션의 기능 줄 · UI 줄도 차례대로다
- **회차가 끝난다** — 마지막 줄의 실행이 끝나면 `DONE` 이고 다음 회차가 시작한다. 사람이 실행을 멈춰도 끝난 것이다. 기준 세트 회차를 닫으면 점검이 안정화 집계를 맡긴다 — 줄이 차례대로라 실행이 끝날 때마다 부르는 집계는 회차가 도는 동안 기다리기만 한다([안정화.md](안정화.md) §3.15 「집계」 「언제」 · SCHED-F1-02)
- **회차 상한은 6시간이다** — 시작하고 6시간이 지나도 안 끝나면 그 회차를 `DONE` 으로 닫고 `notes` 에 「6시간이 지나 다음 세트를 이어 돌렸습니다」를 남긴다. 도는 실행은 멈추지 않는다. 실행 하나가 끝나지 않아 프로젝트의 정기 실행이 다 멈추는 것을 막는다 (끝 검사 지적 · 내 결정 — 호환성 세트가 2~3시간이라 두 배를 넘게 잡았다)
- **관리 서버가 다시 켜지면** — `RUNNING` 회차는 지금 줄의 실행이 있으면 그 상태로 다시 판정하고, 없으면(만들기 전에 꺼졌다) 그 줄부터 만든다. `QUEUED` 회차는 줄 차례대로 이어서 돈다. 다시 켜진 김에 지난 시각의 회차를 새로 세우지는 않는다(1시간 창)
- **실행자는 `스케줄러` · 시작 방식은 `SCHEDULED`** — 지금 정기 실행과 같다(공통/6-인프라 §9.2). E2E · 호환성 실행도 이번에 `SCHEDULED` 로 만든다(앞 판은 늘 `MANUAL` — 공통/4-데이터모델 「실행 시작 방식」)
- **Slack** — 기능 · UI 실행은 지금 정기 실행처럼 늘 보낸다(실행마다 한 통). E2E · 호환성 실행은 지금처럼 Slack 을 보내지 않는다([시나리오.md](시나리오.md) §3.7 `notify_slack` false · 호환성은 알림 칸이 없다). 회차 요약 한 통은 1차 밖이다

#### 실행 만들기 — 종류마다

| 종류 | 만드는 것 | 제목 |
|---|---|---|
| 기능 · UI | 지금 정기 실행과 같은 실행 하나(`kind` `FN` · `UI`). 「전체」는 그 애플리케이션의 활성 케이스 전부, 직접 고르기는 고른 번호 중 살아 있는 것. Android 앱 케이스는 디바이스 팜이 없는 서버에서 뺀다(공통/6-인프라 §9.2 그대로). 같은 애플리케이션의 기능 줄 · UI 줄은 실행 둘이다. 통과 항목 logcat 받기(안정화 결정 3 · `ExecuteRequest.stability`)는 **기준 세트 회차의 실행만** 싣는다 | `정기 · <세트 이름> · 기능 전체 382건` · `정기 · <세트 이름> · MKT-FN-033 외 3건` (도메인/실행 §7 「자동 제목」의 정기 규칙에 세트 이름을 끼운다) |
| E2E | 그 시나리오의 정식 실행 하나 — 지금 「실행」 단추가 타는 길(만들기 `scenario/runStore.ts` `실행만들기` · 분배 `scenario/runRoutes.ts`)을 함수로 떼어 같이 부른다. 대상 서버는 시작 애플리케이션 것, 모바일 웹 단계는 고르개가 없는 시작이라 서버 흉내다([실행.md](실행.md) §8.2 「모바일 웹 「실행 위치」 고르개」) | `정기 · <세트 이름> · <시나리오 이름>` |
| 호환성 | 그 호환성 세트의 실행 하나 — 지금 「실행」이 타는 길(자동 선택 · 디바이스 확인 · 돌리기 `compat/runRoutes.ts` · 세우기 `compat/runStore.ts` `실행세우기`)을 함수로 떼어 같이 부른다. 케이스 자동 선택은 실행마다 다시 계산하고, 폰이 사용 중이면 호환성 규칙대로 기다린다 | `정기 · <세트 이름> · <호환성 세트 이름>` |

만든 실행은 모두 `test_run.sched_occurrence_id` 에 회차 번호를 단다. 실행 기록은 지금처럼 종류마다의 자리에 선다(기능 · UI · E2E · 호환성) — 정기 실행 메뉴에는 실행 목록이 따로 없다.
달력 · 세트 카드가 회차 번호로 실행을 읽을 때는 종류를 거르지 않는다 — 한 회차가 여러 종류를 만들어서다(「훑는 조회는 `kind` 를 건다」의 예외 — 공통/4-데이터모델 「실행 종류」).
**회차의 결과**는 기능 · UI · E2E 실행 판정을 모은 것이다 — 하나라도 실패가 있으면 「실패 있음」, 아니면 「통과」, 그런 실행이 없으면(호환성만 담은 세트 · 다 빠진 회차 · 항목이 하나도 판정되지 않은 실행뿐) 결과 없이 호환성 의심 화면 수만 보인다.

#### 안정화 기준 세트 · 옮기기 (결정 10 · 11)

- **옮기기는 바꿔 다는 PR(SCHED-F1-04)의 마이그레이션이 한다** — 옛 점검을 끄고 옛 칸을 지우는 것과 같은 때라야, 옮긴 뒤 설정에서 고친 값이 사라지거나 그날 두 번 도는 틈이 없다. 정기 실행을 켜 둔 애플리케이션마다(`service.schedule_at` 이 찬 줄) 세트 하나를 만든다. 이름 `<애플리케이션 이름> 전체 회귀` · 반복 매일 · 시각 · 시간대 · 대상 서버는 그 칸 그대로 · 담은 테스트는 그 애플리케이션의 기능 「전체」와 UI 「전체」(API 애플리케이션은 기능만) · 켜짐(비활성 애플리케이션은 꺼짐 — 옛 점검도 안 돌렸다 · SCHED-F1-04 끝 검사) · `is_base = true`(그 애플리케이션에 마법사로 정한 기준 세트가 이미 있으면 보통 세트 — SCHED-F1-04 끝 검사) · 만든 사람 `스케줄러`. 이름이 겹치면 뒤에 ` (2)` 를 붙인다.
  `schedule_last` 가 그 시간대의 오늘이면 오늘 회차를 `DONE`(실행 없음 · `notes` 「옮기기 전에 이미 돌았습니다」)으로 같이 세운다 — 옮긴 날 두 번 돌지 않는다. 옮긴 대상 서버는 검사하지 않는다 — 실서비스 서버이거나 없는 줄이면 위 「돌 때 빠지는 줄」대로 건너뛰고 카드에 보인다
- **안정화는 기준 세트 회차의 실행과 회차 번호가 빈 옛 정기 실행만 센다.** 묶음은 같은 회차의 UI · 기능 실행이고 하루는 회차의 날짜(`planned_on`)다 — 앞 세트를 기다리다 자정을 넘겨 시작해도 그날 묶음이 섞이지 않는다. 정본은 [안정화.md](안정화.md) §3.15 「묶음」 · 「일별 추이」
- **기준 세트의 꼴** — 자기 애플리케이션의 기능 · UI 줄만 · 반복은 매일 또는 요일 · 애플리케이션마다 하나. 기준 세트를 이 꼴 밖으로 고치면 400 `BASE_SET_SHAPE` 이다. 끄면 그 애플리케이션의 안정화 점이 비고, 직접 고르기로 바꾸면 고른 케이스만 센다
- **기준 정하기 · 풀기** — 기준 세트가 없는 애플리케이션은 이 꼴에 맞는 세트를 마법사 확인 단계의 `안정화 지표에 씁니다` 로 기준으로 정한다. 기준을 풀면 그 애플리케이션의 안정화 점이 그날부터 빈다. 안정화 빈 화면의 안내는 정기 실행 메뉴를 가리킨다(SCHED-F1-05)
- **옛 칸은 SCHED-F1-04 가 지웠다** — `service.schedule_at` · `schedule_tz` · `schedule_env` · `schedule_last` 와 설정 API 의 `schedule` · `lastScheduled` 칸, 설정 화면의 「정기 실행」 구획. 손으로 한 번 돌리는 명령(`scripts/run-scheduled.ts`)은 세트 번호를 받는다
- **빌드 실행(`BUILD`)은 그대로다** — 회귀는 지금처럼 그 애플리케이션의 활성 케이스 전부를 UI · 기능 두 실행으로 만든다([실행.md](실행.md) §3.11). 세트를 거치지 않는다

### 8.20 정기 실행 화면 (2026-11-13 · 시안 LZdDot7SBakdppDCs7oVCV 7판 시안 B 사용자 확정)

- **자리** — 사이드바 「테스트 수행」 맨 끝(`성능 테스트` 다음), 주소 `#/sched`, 영어 `Scheduled runs`. 실행 칸을 쓴다 — 실행이 `none` 이면 자리가 없다. 네 종류(웹 · Android 앱 · 게임 · API) 모두 같다(화면공통 §8 「자리 목록」)
- **머리** — 제목 `정기 실행` · 부제 `<프로젝트 이름> 프로젝트 · 애플리케이션 N개의 세트를 한 달력에 모았습니다` · 오른쪽 `+ 신규 세트`(실행 `write` 만)
- **짜임(시안 B)** — 왼쪽 세트 카드 줄 · 오른쪽 달력. 휴대폰은 세트 카드가 달력 위의 가로로 미는 줄이다
- **세트 카드** — 색 점 · 이름 · 꼬리표(`안정화 기준` · `꺼짐`) · `<반복> <시각> · 다음 <날짜>` · `<애플리케이션 접두사 + …> · <담은 종류>` · `마지막 <날짜> <결과 알약> 결과 →` · `빠진 케이스 N건`(있을 때) · `수정` · `끄기` / `켜기`(실행 `write` 만).
  카드를 누르면 달력이 그 세트만 보이고 다시 누르거나 `전체 보기` 를 누르면 돌아온다
- **달력** — `월` · `주` · `일` 고르개 · `◀ 2026년 11월 ▶` · `오늘`. 처음은 월이고 브라우저가 마지막 보기를 기억한다. 한 주는 월요일부터다
  - 지난 회차 — 결과 색(통과 · 실패 있음) 칩, 호환성 의심 화면은 `의심 N` 으로 따로 단다 — 판정 전이라 판정 색이 아니라 호환성 결과의 의심 화면처럼 잉크 점선 테두리다(SCHED-F1-05, 노란 토큰이 없다)(통과 · 실패에 안 섞는다 — [호환성.md](호환성.md) §3.13 결정 1)
  - 앞으로의 회차 — 회색 점선 칩 `<시각> 예정`. 앞 세트가 길어 늦게 시작할 것 같으면 `<예상 시각>쯤 시작` · `대기`
  - 기다렸다 시작한 회차 — 칩에 `대기`, 창에 `02:00 예정 → 03:50 시작 · 앞 세트 대기 1시간 50분`
  - 월 칸은 세트 셋까지 보이고 넘치면 `+N` — 누르면 그날 일 보기
  - 주 · 일 보기는 세로 시간 줄이다. 지난 회차는 실제로 걸린 시간만큼 막대로, 기다렸으면 정한 시각에 점선과 `<시각> <세트 이름> 예정` 을 남긴다. 세트가 있는 시간대만 펼친다
- **칸 창** — 지난 칸: 세트 이름 · 결과 · `<날짜> <시작 시각> 시작 · 실행 N개` · 실행 줄(애플리케이션 · 종류 · 이름 · 결과 알약 · `#<실행 번호> →`). 줄을 누르면 실행 기록의 그 실행으로 간다. 실행이 하나면 창 없이 바로 간다.
  앞으로의 칸: 담은 테스트 · `세트 수정`(실행 `write` 만). 일 보기는 창 없이 오른쪽에 그날 실행 줄을 펼친다
- **마법사** — 가운데 창 다섯 단계 `1. 세트 이름` · `2. 담을 테스트` · `3. 대상 서버` · `4. 언제` · `5. 확인`. 단계 줄을 눌러 앞 단계로 간다. `다음` 이 빈 칸을 막고 사유를 창 아래에 적는다(`세트 이름을 입력해 주세요` · `담을 테스트를 하나 이상 선택해 주세요` · `요일을 하나 이상 선택해 주세요` · `같은 이름의 세트가 이미 있습니다`). 수정은 같은 창이고 제목이 `세트 수정` 이다
  - 2단계 — 탭 `기능 테스트` · `UI 테스트` · `E2E 테스트` · `호환성 테스트`. 기능 · UI · 호환성은 애플리케이션을 먼저 고른다(고르개에 종류 꼬리표 `· API`). 기능 · UI 는 맨 위 `전체 N건`(`돌릴 때의 활성 케이스 전부입니다. 신규 케이스도 들어갑니다`) 과 그 아래 `번호 · 이름으로 검색` · 케이스 체크 목록(케이스 `read` 가 없으면 「전체」만). E2E 탭은 애플리케이션을 고르지 않고 프로젝트의 시나리오를 다 보이며 지나가는 애플리케이션을 꼬리표로 단다. 아래 `담은 테스트 N개` 에 쌓이고 × 로 뺀다
  - 3단계 — 실행을 만드는 애플리케이션마다 대상 서버 한 줄(§3.16 「세트」). 섞인 E2E 가 있으면 `섞인 단계는 시작 애플리케이션 서버와 같은 이름의 서버로 갑니다` 를 적는다
  - 4단계 — `매일` · `요일 선택` · `한 번만` · 시각(`<시간대> 기준`). 겹칠 수 있는 세트가 있으면 안내 판(`--well` 바탕 — 노란 토큰이 없다, SCHED-F1-05. 아래 두 문구의 「끝난」 · 「돌고」 · 「끝나야」는 화면 낱말표 [docs/WORDS.md](../../WORDS.md) 검사가 막으니 화면에 옮길 때 「완료」 · 「실행」으로 바꾼다) `「결제 회귀」(02:00 · 지난 실행 평균 35분)와 시간이 겹칠 수 있습니다. 겹치면 먼저 시작한 세트가 끝난 뒤 이어서 시작합니다`. 호환성이 들어 있으면 `호환성 테스트가 들어 있습니다. 디바이스를 한 대씩 돌고 AI 점검까지 끝나야 해서 2~3시간 걸릴 수 있습니다`
  - 5단계 — 세트 이름 · 담은 테스트 · 대상 서버 · 언제 · 다음 실행 셋 · 알림. 기준으로 정할 수 있는 세트(§7 `baseable`)면 `안정화 지표에 씁니다` 체크가 선다. `저장` 하면 창이 닫히고 달력이 다음 실행 날짜로 가며 `「<이름>」 세트를 저장했습니다 · 다음 실행 <날짜> <시각>` 이 뜬다. 저장한 그날 이미 지난 시각이면 다음 날부터다(§3.16 「저장한 그날」)
- **빈 상태** — 세트가 없으면 달력 자리에 `아직 세트가 없습니다` · `이미 만든 테스트를 선택해 정해진 시각에 실행합니다`(「골라」 · 「돌립니다」는 낱말표가 막는다 — SCHED-F1-05) · `+ 신규 세트`(실행 `write` 만)
- **읽기만 하는 사람** — `+ 신규 세트` · `수정` · `끄기` · `세트 수정` 이 없다(흐리게 두지 않는다 — 공통/5-화면공통 §8 「등급이 낮아서 못 하는 것은 보이지 않는다」)
- 낱말은 [docs/WORDS.md](../../WORDS.md) 「정기 실행 화면에서만 쓰는 말」
