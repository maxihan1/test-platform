> 정기 실행은 **프로젝트에서 이미 만든 테스트를 골라 「세트」로 묶고, 정한 날 · 시각에 돌리고, 달력에서 예정과 지난 결과를 보는 곳이다.** 기능 · UI · E2E · 호환성 테스트를 같은 프로젝트의 여러 애플리케이션에서 섞어 담는다.

### 3.16 정기 실행 — 프로젝트 공통 테스트 세트 · 달력 (2026-11-13 사용자)

2026-11-12 까지 정기 실행은 두 곳에 흩어져 있었다 — 설정 › 애플리케이션의 「정기 실행」 구획(애플리케이션의 활성 케이스 전부를 매일 한 번, 운영 admin 만)과 성능 마법사의 시나리오 정기 실행. 무엇이 언제 도는지 한눈에 안 보였고, QA 담당자는 켜지도 못했다.
아래 결정은 2026-11-13 기획 대화(test_platform 배경 세션 8b7a9731)에서 주제마다 정했고, 사용자가 작업 계획을 승인했다(「이어달리기로 작업 진행하자」). 다시 묻지 않는다. 「(내 결정)」이 붙은 줄은 대화에서 알렸고 반대가 없던 것이다.

#### 세트

- **세트는 프로젝트 하나에 속한다**(`sched_set.project_id`). 이름은 프로젝트 안에서 겹치지 않는다
- **담은 테스트 한 줄**(`sched_set_item`)은 종류 하나다.
  - 기능(`FN`) · UI(`UI`) — 애플리케이션 하나와 「전체」(`tc_ids` 비움) 또는 고른 케이스 번호 목록. API 애플리케이션에는 `UI` 줄이 없다(서버가 400)
  - E2E(`E2E`) — 시나리오 하나. 줄의 애플리케이션은 그 시나리오의 시작 애플리케이션이다([시나리오.md](시나리오.md) §3.7 결정 13). 섞인 시나리오도 담는다
  - 호환성(`COMPAT`) — 호환성 세트 하나. 줄의 애플리케이션은 그 세트의 애플리케이션이다
- **대상 서버는 실행을 만드는 애플리케이션마다 하나다**(`sched_set_env`) — 기능 · UI · 호환성 줄의 애플리케이션과 E2E 의 시작 애플리케이션. 그 애플리케이션의 대상 서버 줄에서 고르고, 실서비스 서버는 고를 수 없다(400 — 정기 실행은 사람 없이 돈다).
  섞인 E2E 의 다른 단계는 시나리오 규칙대로 시작 애플리케이션 서버와 **같은 이름**의 줄로 간다(시나리오 §3.7 「대상 서버는 이름으로 짝짓는다」) — 그 애플리케이션에 따로 고른 서버는 그 E2E 에 안 쓴다
- **직접 고른 케이스가 지워지거나 비활성이 되면 세트에는 남고 그 회차에서만 건너뛴다.** 세트 카드에 「빠진 케이스 N건」이 보인다. 치운 시나리오 · 호환성 세트도 같다 — 「빠진 테스트 N개」. 호환성 세트의 직접 추가 케이스와 같은 규칙이다([호환성.md](호환성.md) 「호환성 세트」)
- **켜고 끈다**(`sched_set.is_on`). 끄면 앞으로의 회차가 안 서고, 줄에 서서 기다리던 회차도 빠진다(`SKIPPED`). 지난 회차는 그대로다
- **고친 내용은 다음에 시작하는 회차부터 쓴다** — 줄에 서서 기다리는 회차도 시작할 때의 세트로 실행을 만든다. 이미 시작한 회차는 안 바뀐다

#### 회차 — 언제 세우고 어떻게 돌리나

회차(`sched_occurrence`)는 세트가 그날 한 번 도는 것이다. 회차 하나가 실행 여러 개를 만든다.

- **admin 이 1분마다 본다** — 지금 정기 실행 점검(공통/6-인프라 §9.2)을 대신한다. HTTP 를 거치지 않는 것도 같다
- **회차를 세운다** — 세트가 켜져 있고 · 오늘(세트 시간대)이 반복에 들고 · 지금이 정한 시각부터 1시간 안이고 · 그날 회차가 아직 없으면 `QUEUED` 회차를 세운다. 1시간 창 · 서버가 꺼져 있었으면 그날 건너뜀 · DB 시계 규칙은 지금 정기 실행과 같다(공통/6-인프라 §9.2 「돌 조건」)
- **줄을 세운다(결정 8)** — 프로젝트마다 `RUNNING` 회차가 없을 때만 `QUEUED` 가운데 정한 시각이 가장 이른 것(같으면 세트 번호 차례)을 `RUNNING` 으로 바꾸고 실행을 만든다. 기다린 시간은 정한 시각과 실제 시작 시각의 차이다(`planned_at` · `started_at`)
- **실행을 만든다** — 담은 줄마다(아래 「실행 만들기」). 하나를 못 만들어도 나머지는 만든다. 못 만든 줄은 까닭을 회차에 남긴다(`sched_occurrence.notes`). 하나도 못 만들었으면 회차는 바로 `DONE` 이다
- **회차가 끝난다** — 그 회차가 만든 실행이 모두 끝나면(`FINISHED` · `ABORTED` · `PREP_FAILED`) `DONE` 이고 다음 회차가 시작한다. 사람이 실행을 멈춰도 끝난 것이다
- **관리 서버가 다시 켜지면** — `RUNNING` 회차는 실행 상태로 다시 판정하고, `QUEUED` 회차는 줄 차례대로 이어서 돈다. 다시 켜진 김에 지난 시각의 회차를 새로 세우지는 않는다(1시간 창)
- **실행자는 `스케줄러` · 시작 방식은 `SCHEDULED` · Slack 은 늘 보낸다** — 지금 정기 실행과 같다(공통/6-인프라 §9.2). E2E · 호환성 실행도 이번에 `SCHEDULED` 로 만든다(앞 판은 늘 `MANUAL` — 공통/4-데이터모델 「실행 시작 방식」). Slack 은 실행마다 한 통이다 — 회차 요약 한 통은 1차 밖

#### 실행 만들기 — 종류마다

| 종류 | 만드는 것 | 제목 |
|---|---|---|
| 기능 · UI | 지금 정기 실행과 같은 실행 하나(`kind` `FN` · `UI`). 「전체」는 그 애플리케이션의 활성 케이스 전부, 직접 고르기는 고른 번호 중 살아 있는 것. Android 앱 케이스는 디바이스 팜이 없는 서버에서 뺀다(공통/6-인프라 §9.2 그대로). 같은 애플리케이션의 기능 줄 · UI 줄은 실행 둘이다 | `정기 · <세트 이름> · 기능 전체 382건` · `정기 · <세트 이름> · MKT-FN-033 외 3건` (도메인/실행 §7 「자동 제목」의 정기 규칙에 세트 이름을 끼운다) |
| E2E | 그 시나리오의 정식 실행 하나 — 지금 「실행」 단추와 같은 길(`scenario/runStore.ts` `실행만들기`)이고 대상 서버는 시작 애플리케이션 것 | `정기 · <세트 이름> · <시나리오 이름>` |
| 호환성 | 그 호환성 세트의 실행 하나 — 지금 「실행」과 같은 길(`compat/runStore.ts` `실행세우기`). 케이스 자동 선택은 호환성 규칙 그대로 실행마다 다시 계산한다. 폰이 사용 중이면 호환성 규칙대로 기다린다 | `정기 · <세트 이름> · <호환성 세트 이름>` |

만든 실행은 모두 `test_run.sched_occurrence_id` 에 회차 번호를 단다. 실행 기록은 지금처럼 종류마다의 자리에 선다(기능 · UI · E2E · 호환성) — 정기 실행 메뉴에는 실행 목록이 따로 없다.

#### 안정화 기준 세트 · 옮기기 (결정 10 · 11)

- **옮기기** — 정기 실행을 켜 둔 애플리케이션마다(`service.schedule_at` 이 찬 줄) 세트 하나를 만든다. 이름 `<애플리케이션 이름> 전체 회귀` · 반복 매일 · 시각 · 시간대 · 대상 서버는 그 칸 그대로 · 담은 테스트는 그 애플리케이션의 기능 「전체」와 UI 「전체」(API 애플리케이션은 기능만) · 켜짐 · `is_base = true` · 만든 사람 `스케줄러`. 이름이 겹치면 뒤에 ` (2)` 를 붙인다
- **안정화는 기준 세트 회차의 실행과 회차 번호가 빈 옛 정기 실행만 센다.** 하루의 경계는 그 기준 세트의 시간대다(앞 판 `service.schedule_tz`) — 정본은 [안정화.md](안정화.md) §3.15 「묶음」 · 「일별 추이」
- **기준 세트도 고치고 끌 수 있다.** 끄면 그 애플리케이션의 안정화 점이 비고, 직접 고르기로 바꾸면 고른 케이스만 센다. 기준 꼬리표는 화면에서 달거나 떼지 않는다
- **옛 칸은 바꿔 다는 PR(SCHED-F1-04)이 지운다** — `service.schedule_at` · `schedule_tz` · `schedule_env` · `schedule_last` 와 설정 API 의 `schedule` · `lastScheduled` 칸, 설정 화면의 「정기 실행」 구획. 손으로 한 번 돌리는 명령(`scripts/run-scheduled.ts`)은 세트 번호를 받는다
- **빌드 실행(`BUILD`)은 그대로다** — 회귀는 지금처럼 그 애플리케이션의 활성 케이스 전부를 UI · 기능 두 실행으로 만든다([실행.md](실행.md) §3.11). 세트를 거치지 않는다

#### 1차 밖

회차 요약 Slack 한 통 · 세트 지우기 · 이번 한 번 건너뛰기 · 조건으로 케이스 담기 · 성능 시나리오 담기 · 안정화 기준을 화면에서 바꾸기 · 세트를 다른 프로젝트로 옮기기 · 프로젝트를 넘는 줄 세우기(디바이스 팜은 프로젝트끼리 같이 쓴다).

### 8.20 정기 실행 화면 (2026-11-13 · 시안 LZdDot7SBakdppDCs7oVCV 7판 시안 B 사용자 확정)

- **자리** — 사이드바 「테스트 수행」 맨 끝(`성능 테스트` 다음), 주소 `#/sched`, 영어 `Scheduled runs`. 실행 칸을 쓴다 — 실행이 `none` 이면 자리가 없다. 네 종류(웹 · Android 앱 · 게임 · API) 모두 같다(화면공통 §8 「자리 목록」)
- **머리** — 제목 `정기 실행` · 부제 `<프로젝트 이름> 프로젝트 · 애플리케이션 N개의 세트를 한 달력에 모았습니다` · 오른쪽 `+ 신규 세트`(실행 `write` 만)
- **짜임(시안 B)** — 왼쪽 세트 카드 줄 · 오른쪽 달력. 휴대폰은 세트 카드가 달력 위의 가로로 미는 줄이다
- **세트 카드** — 색 점 · 이름 · 꼬리표(`안정화 기준` · `꺼짐`) · `<반복> <시각> · 다음 <날짜>` · `<애플리케이션 접두사 + …> · <담은 종류>` · `마지막 <날짜> <결과 알약> 결과 →` · `빠진 케이스 N건`(있을 때) · `수정` · `끄기` / `켜기`(실행 `write` 만).
  카드를 누르면 달력이 그 세트만 보이고 다시 누르거나 `전체 보기` 를 누르면 돌아온다
- **달력** — `월` · `주` · `일` 고르개 · `◀ 2026년 11월 ▶` · `오늘`. 처음은 월이고 브라우저가 마지막 보기를 기억한다. 한 주는 월요일부터다
  - 지난 회차 — 결과 색(통과 · 실패 있음) 칩, 호환성 의심 화면은 노란 `의심 N` 으로 따로 단다(통과 · 실패에 안 섞는다 — [호환성.md](호환성.md) §3.13 결정 1)
  - 앞으로의 회차 — 회색 점선 칩 `<시각> 예정`. 앞 세트가 길어 늦게 시작할 것 같으면 `<예상 시각>쯤 시작` · `대기`
  - 기다렸다 시작한 회차 — 칩에 `대기`, 창에 `02:00 예정 → 03:50 시작 · 앞 세트 대기 1시간 50분`
  - 월 칸은 세트 셋까지 보이고 넘치면 `+N` — 누르면 그날 일 보기
  - 주 · 일 보기는 세로 시간 줄이다. 지난 회차는 실제로 걸린 시간만큼 막대로, 기다렸으면 정한 시각에 점선과 `<시각> <세트 이름> 예정` 을 남긴다. 세트가 있는 시간대만 펼친다
- **칸 창** — 지난 칸: 세트 이름 · 결과 · `<날짜> <시작 시각> 시작 · 실행 N개` · 실행 줄(애플리케이션 · 종류 · 이름 · 결과 알약 · `#<실행 번호> →`). 줄을 누르면 실행 기록의 그 실행으로 간다. 실행이 하나면 창 없이 바로 간다.
  앞으로의 칸: 담은 테스트 · `세트 수정`(실행 `write` 만). 일 보기는 창 없이 오른쪽에 그날 실행 줄을 펼친다
- **마법사** — 가운데 창 다섯 단계 `1. 세트 이름` · `2. 담을 테스트` · `3. 대상 서버` · `4. 언제` · `5. 확인`. 단계 줄을 눌러 앞 단계로 간다. `다음` 이 빈 칸을 막고 사유를 창 아래에 적는다(`세트 이름을 입력해 주세요` · `담을 테스트를 하나 이상 선택해 주세요` · `요일을 하나 이상 선택해 주세요` · `같은 이름의 세트가 이미 있습니다`). 수정은 같은 창이고 제목이 `세트 수정` 이다
  - 2단계 — 탭 `기능 테스트` · `UI 테스트` · `E2E 테스트` · `호환성 테스트`. 기능 · UI · 호환성은 애플리케이션을 먼저 고른다(고르개에 종류 꼬리표 `· API`). 기능 · UI 는 맨 위 `전체 N건`(`돌릴 때의 활성 케이스 전부입니다. 새로 생긴 케이스도 들어갑니다`) 과 그 아래 `번호 · 이름으로 찾기` · 케이스 체크 목록. E2E 탭은 애플리케이션을 고르지 않고 프로젝트의 시나리오를 다 보이며 지나가는 애플리케이션을 꼬리표로 단다. 아래 `담은 테스트 N개` 에 쌓이고 × 로 뺀다
  - 3단계 — 실행을 만드는 애플리케이션마다 대상 서버 한 줄(§3.16 「세트」). 섞인 E2E 가 있으면 `섞인 단계는 시작 애플리케이션 서버와 같은 이름의 서버로 갑니다` 를 적는다
  - 4단계 — `매일` · `요일 선택` · `한 번만` · 시각(`<시간대> 기준`). 겹칠 수 있는 세트가 있으면 노란 안내 `「결제 회귀」(02:00 · 지난 실행 평균 35분)와 시간이 겹칠 수 있습니다. 겹치면 먼저 시작한 세트가 끝난 뒤 이어서 시작합니다`. 호환성이 들어 있으면 `호환성 테스트가 들어 있습니다. 디바이스를 한 대씩 돌고 AI 점검까지 끝나야 해서 2~3시간 걸릴 수 있습니다`
  - 5단계 — 세트 이름 · 담은 테스트 · 대상 서버 · 언제 · 다음 실행 셋 · 알림. `저장` 하면 창이 닫히고 달력이 다음 실행 날짜로 가며 `「<이름>」 세트를 저장했습니다 · 다음 실행 <날짜> <시각>` 이 뜬다. 오늘 이미 지난 시각이면 다음 날부터다
- **빈 상태** — 세트가 없으면 달력 자리에 `아직 세트가 없습니다` · `이미 만든 테스트를 골라 정해진 시각에 돌립니다` · `+ 신규 세트`(실행 `write` 만)
- **읽기만 하는 사람** — `+ 신규 세트` · `수정` · `끄기` · `세트 수정` 이 없다(흐리게 두지 않는다 — 화면공통 §8.6)
- 낱말은 [docs/WORDS.md](../../WORDS.md) 「정기 실행 화면에서만 쓰는 말」
