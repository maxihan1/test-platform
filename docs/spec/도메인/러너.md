### 3.4 Runner — 실제로 돌린다

- **책임**: 케이스 1건을 주어진 값으로 실행하고 구조화된 결과를 반환.
  **또는 시나리오 1개 — 케이스 여럿과 부품을 한 브라우저에서 순서대로 — 를 실행한다** (2026-09-28, [시나리오.md](시나리오.md) §3.7).
  무엇을 도는지만 늘었다. 아래 무상태 규칙은 그대로다 — 시나리오 정의·버전·결과는 admin 만 안다
- **DB 무상태**. 어떤 테이블에도 접근하지 않는다. 돌고 있는 자식 프로세스의 손잡이만 메모리에 들고 있고,
  러너가 죽으면 그 프로세스와 함께 사라진다. 이 규칙이 깨지면 컨테이너 분리가 무의미해진다
- **중단 통로** (2026-09-16 결정): 돌고 있는 실행을 바깥에서 끊을 수 있어야 한다(§3.2). 러너에 `historyId`로
  지목해 끊는 창구를 하나 낸다. **끊는 동작 자체는 이미 있다** — 타임아웃 때 자식 프로세스 그룹을 통째로 죽이는
  코드가 그것이고, 바깥에서 부를 길만 없었다. 엔드포인트와 응답 형태는 **§5.2가 정본**이다
- **바깥으로 내는 통로가 생겨도 위 무상태 규칙은 깨지지 않는다** (중단·진행. 둘 다 §5.2가 정본이다).
  러너가 들고 있는 것은 살아 있는 프로세스의 손잡이와 그것이 지금 어느 절차까지 왔는지뿐이고
  DB에 저장된 상태가 아니다. 판정·이력·스냅샷은 여전히 admin만 쓴다. §5.3의 이음새를 떠받치는 규칙도 그대로다
- 끊긴 실행은 **타임아웃과 같은 모양으로** 돌아온다. `error.message`만 `TIMEOUT`이 아니라 `ABORTED`다.
  admin 쪽에 저장 경로를 새로 만들지 않기 위해서다 (§5.2)
- 입출력은 §5.2 계약만 사용

### 5.2 Runner HTTP 계약

```
POST http://runner:4000/execute
Content-Type: application/json
Body:     ExecuteRequest
200 OK:   ExecuteResponse
400:      { error: 'INVALID_REQUEST', detail: string }
404:      { error: 'CASE_NOT_FOUND', detail: string }
500:      { error: 'RUNNER_ERROR', detail: string }

POST http://runner:4000/abort
Content-Type: application/json
Body:     { historyId: number }
200 OK:   { aborted: boolean }
          돌고 있던 자식 프로세스를 그룹째 끊었으면 true.
          이미 끝났거나 러너가 모르는 historyId면 false다 — 경합이지 고장이 아니므로 404로 만들지 않는다.
          끊긴 실행의 /execute 응답은 타임아웃과 같은 모양으로 돌아온다 (error.message = 'ABORTED')
400:      { error: 'INVALID_REQUEST', detail: string }

GET  http://runner:4000/progress
200 OK:   { items: RunningStep[] }
          지금 돌고 있는 자식마다 한 건이다. 아직 첫 절차를 안 흘린 자식은 빠진다.
          러너는 runId도 서비스도 모른다 — 거르는 일은 admin이 한다 (§7)

POST http://runner:4000/execute-scenario        (2026-09-28)
Content-Type: application/json
Body:     ScenarioExecuteRequest
200 OK:   ScenarioExecuteResponse
400:      { error: 'INVALID_REQUEST', detail: string }
404:      { error: 'CASE_NOT_FOUND', detail: string }
500:      { error: 'RUNNER_ERROR', detail: string }

GET  http://runner:4000/health   → 200 { ok: true, playwrightVersion: string }
```

- **동기 호출.** Execution이 동시성 2로 제한해 호출한다
- 러너는 `ExecuteRequest.params`를 환경변수 `PLATFORM_PARAMS`(JSON 문자열)로 주입하고
  `npx playwright test <filePath> --project=<platform>`을 자식 프로세스로 실행한다
- 결과는 커스텀 리포터가 stdout에 **JSON 한 줄**(`@@RESULT@@{...}`)로 뱉고 러너가 파싱한다
- **타임아웃**: `timeoutMs`가 지나면 러너가 자식 프로세스를 죽이고 `200`으로
  `{ status: 'NA', error: { message: 'TIMEOUT' }, steps: <파싱된 것이 있으면 그것, 없으면 []> }`을 돌려준다.
  `500`은 러너 자체의 고장(프로세스 기동 실패 등)에만 쓴다
- Execution이 러너를 부를 때의 HTTP 타임아웃은 `timeoutMs + 30초`다. 러너가 먼저 끊어야 부분 결과가 남는다
- 케이스 1건 = Playwright 프로세스 1개(`workers: 1`). 동시 실행은 Execution의 동시성(2)으로만 제어한다.
  **시나리오는 시나리오 1개 = 프로세스 1개다** (2026-09-28). 케이스 여럿이 한 프로세스·한 `test()` 안에서 돈다 — 아래 「시나리오 실행」
- **`baseUrl`**: 그 실행이 두드릴 주소다. 사람은 화면에서 **대상 서버**(개발·QA·스테이징) 이름만 고르고,
  admin이 자기 설정표에서 주소를 찾아 이 칸에 실어 보낸다. 러너는 어떤 대상 서버가 있는지 모른다 — 주소 하나만 받는다.
  러너는 이 값을 환경변수 `PLATFORM_BASE_URL`로 자식 프로세스에 넘기고 `playwright.config.ts`가 `use.baseURL`로 받는다.
  주소를 아는 쪽을 admin 하나로 묶어야 러너가 도메인 상태를 갖지 않는다
- **자동 재시도는 쓰지 않는다. `playwright.config.ts`의 `retries`는 0으로 명시해 고정한다.**
  실패를 가려서 초록불을 만드는 것과, 불안정한지 보려고 일부러 여러 번 돌리는 것은 다른 일이다.
  여러 번 돌리는 쪽은 실행 요청의 `repeat`가 맡는다. 켜려면 이 문장을 먼저 고친다.
  같은 문장을 `playwright.config.ts`의 `retries` 자리에 주석으로도 남긴다 — 설정 파일만 보고 켜 버리는 일을 막는다
- **반복 실행은 러너에 보이지 않는다.** admin이 `historyId`만 다른 같은 요청을 N번 보낼 뿐이다.
  회차(`attempt`)를 러너 계약에 넣지 않는다. 러너는 회차로 아무 일도 하지 않고,
  스크린샷 경로가 이미 `historyId`로 갈라져 있어 서로 덮어쓰지 않는다
- **중단**: `POST /abort`는 `historyId`로 돌고 있는 자식 프로세스를 지목해 **프로세스 그룹째** 끊는다.
  끊는 방식은 타임아웃과 완전히 같다. 바깥에서 부를 통로만 새로 낸 것이다.
  실행 묶음 전체를 끊는 일은 admin이 자기가 아는 `historyId`를 하나씩 부르는 것으로 한다.
  러너에 `runId` 단위 중단을 두면 러너가 실행 묶음을 알아야 한다
- 끊긴 실행의 `POST /execute` 응답은 **타임아웃과 같은 모양**으로 돌아온다.
  `200` + `{ status: 'NA', error: { message: 'ABORTED' }, steps: <파싱된 것이 있으면 그것, 없으면 []> }`.
  모양이 같아야 Execution의 저장 경로에 새 분기가 생기지 않는다
- 이미 끝났거나 러너가 모르는 `historyId`에는 `200 { aborted: false }`를 돌려준다.
  중단 요청과 정상 종료가 겹치는 것은 **경합이지 고장이 아니다.** 404로 만들면 Execution이 정상 상황마다 에러를 받는다
- 러너는 `historyId → 자식 프로세스` 지도를 **메모리에만** 들고 있는다. DB는 여전히 모른다 (§3.4).
  러너가 죽으면 지도도 자식 프로세스도 같이 사라지므로, 남은 항목을 닫는 일은 admin의 재기동 복구가 맡는다
- **진행**: 절차가 시작될 때마다 킷이 stdout에 **JSON 한 줄**(`@@PROGRESS@@{...}`, `StepProgress`)을 흘리고
  러너가 그 줄로 자기 지도의 「지금 도는 절차」를 고쳐 쓴다. 결과 줄과 같은 방식이고 표시자는 둘 다
  `packages/kit/src/runtime/protocol.ts` 한 자리에 모여 있다. 알림은 **판정에 끼어들지 않는다** —
  못 흘려도 삼키고, `PLATFORM_HISTORY_ID`가 없으면(사람이 손으로 돌릴 때다) 아예 안 흘린다
- **★ 리포터가 워커 출력을 되돌려 쓰는 것이 계약의 일부다.** 케이스 코드는 Playwright **워커**에서 돌고
  거기서 `process.stdout.write`는 Playwright 것으로 갈아치워져 IPC로만 간다. 리포터의 `onStdOut`이
  받은 조각을 진짜 stdout으로 **다시 쓰지 않으면 진행 줄이 러너에 한 글자도 안 닿는다.**
  단위 검사가 이 자리를 원리적으로 못 본다 — 케이스는 멀쩡히 통과하고 진행만 조용히 0이 된다 (2026-09-21 실측).
  그리고 **진행 줄만 골라 내보내면 안 된다.** `onStdOut`이 생기는 순간 워커 stdio가 `inherit`에서
  `pipe`로 바뀌어, 안 넘긴 출력은 사라지고 러너가 오류 문장으로 쓰는 stdout 꼬리가 빈 문자열이 된다
- **admin이 묻는다. 러너가 알리지 않는다** (당김. 2026-09-21 결정). 러너에는 로그인 세션이 없어
  러너가 admin에 쓰려면 **로그인 없이 지나가는 자리**를 새로 내야 한다. 그런 예외는 하나 있었고
  2026-09-17에 일부러 없앴다 (§7 인증 적용 범위 — 인증 없이 부를 수 있는 API는 없다).
  admin → 러너 방향은 `/execute`·`/abort`로 **이미 있는 길**이라 문에 구멍을 내지 않는다
- **경과는 러너가 잰다.** 시작 시각을 실어 보내면 러너 컨테이너 시계와 보는 사람 기계 시계의 차가
  그대로 오차가 된다 — 몇 초 어긋나면 화면에 「-3초째」가 뜬다. `elapsedMs`는 물어본 그 순간에 러너가 계산한다
- **진행을 러너가 거르지 않는다.** 응답에는 `runId`도 `serviceId`도 없다. 러너가 그것을 알면
  실행 묶음과 서비스를 아는 것이 되어 §3.4가 깨진다. 거르는 일은 admin 몫이다 (§7)
- **이 통로도 §3.4 무상태를 깨지 않는다.** 러너가 드는 것은 **살아 있는 프로세스의 진행**이지
  저장된 상태가 아니고 러너가 죽으면 같이 사라진다. 중단 통로를 낼 때 쓴 것과 **같은 논거**다

```
[계약 변경 필요]
대상:    playwright.config.ts
현재:    use 블록이 없고 retries 항목도 없다 (Playwright 기본값 0이라 동작은 같다)
제안:    use.baseURL을 process.env.PLATFORM_BASE_URL에서 받게 하고, retries: 0을 명시적으로 새로 적으면서
         "켜려면 SPEC §5.2를 먼저 고친다"를 주석으로 붙인다
이유:    대상 서버를 골라 실행하려면 그날 친 주소가 설정까지 내려와야 한다. retries는 지금 안 적혀 있어
         누가 켜도 아무 표시가 남지 않는다
영향:    WS-C(러너가 PLATFORM_BASE_URL을 넘긴다), WS-B(주소를 찾아 싣는다), 공용 골격이므로 CLAUDE.md §1.2 승인 필요
상태: 반영 완료 (2026-09-17, playwright.config.ts:15 · playwright.config.ts:18)
```

#### 시나리오 실행 (2026-09-28)

**무엇을 왜 도는지는 [시나리오.md](시나리오.md) §3.7 이 정본이다.** 여기는 러너가 어떻게 받고 무엇을 돌려주는지만 적는다.

- **시나리오마다 테스트 파일을 만들지 않는다.** 러너 이미지 안에 **고정 파일 하나**(`apps/runner/scenario/`)와 그것만 보는 설정 파일을 둔다.
  러너는 `npx playwright test --config <그 설정> --project=<platform>` 을 자식 프로세스로 띄우고 조립 목록을 환경변수로 넘긴다.
  **왜 파일을 안 만드나** — `/tests` 는 읽기 전용이고(§9) 기본 설정의 `testDir` 이 `/tests` 라, 밖에 만든 파일은 경로를 줘도 안 잡힌다.
  고정 파일은 케이스 파일을 **불러 쓰기만** 하므로 쓸 자리가 필요 없다 (설계서 「착수 전에 답이 있어야 하는 것」 ①, 2026-09-28).
  **실측으로 확인했다 (2026-09-28, PR #100)** — 기본 설정으로 밖 파일 경로를 주면 `No tests found`, 전용 설정의 고정 spec 이 부르면 된다.
  전용 설정은 `testMatch` 를 고정 spec 이름 하나로 박는다 — 기본 무늬가 같은 폴더의 `*.test.ts`(vitest 검사)까지 잡는다
- **고정 spec 은 kit 을 값으로 부르지 않는다** (2026-09-28 이미지 실측). 케이스 파일이 kit 을 `require` 로 부를지 `import` 로 부를지는
  그 파일이 어디 있느냐로 갈린다 — 러너 이미지의 `/tests` 는 `package.json` 이 없어 `require`, 저장소 안은 `"type": "module"` 이라 `import` 다.
  고정 spec 이 kit 을 한 방식으로 먼저 올리면 같은 kit 파일이 두 방식으로 섞여 죽는다(이미지 `Unexpected token 'export'` · 로컬 `does not provide an export named`).
  그래서 고정 spec 이 kit 과 맞춰야 하는 글자(결과 줄 표시자 · 등록부 열쇠 · 2026-10-06 뒷정리 줄 표시자)는 `apps/runner/scenario/wire.ts` 에 옮겨 적고 `wire.test.ts` 가 같은지 지킨다. 목록의 정본은 `wire.ts` 다.
  **CI(Node 22)는 `require` 쪽을 재현하지 못한다** — 고정 spec 이나 kit 불러오기를 고쳤으면 러너 이미지에서 한 번 부른다
- **케이스 부품의 `filePath` 도 `/execute` 와 같은 경로 검사를 지난다.** 테스트 뿌리 밖을 가리키면 400 이다
- **고정 파일이 `test()` 하나 안에서 부품을 차례로 돈다.** 케이스 부품은 kit 의 시나리오 모드로 본체를 꺼내(공통/3-공유계약 §5.1)
  **부품마다 새 창**(브라우저 컨텍스트)으로 돌리고, 부품마다 입력값을 따로 해석한다. **순번은 시나리오 전체에서 이어진다** — 부품마다 실패 표시는 새로 세우고 순번만 넘겨받는다(정본 공통/3-공유계약 §5.1 시나리오 모드)
- **새 창은 앞 부품의 로그인 상태로 연다** (2026-10-06, 시나리오 §3.7 결정 3 · 12). 앞 창의 `storageState()` 와 앞 부품 `request` 의 쿠키를 합쳐(겹치면 창 쪽) 새 창과 새 `request` 에 넣는다.
  넘겨받기를 끈 부품은 빈 상태로 연다. 새 창은 그 디바이스 프로젝트의 `use` 설정(화면 크기 · 사용자 에이전트)으로 열고, 걸려 있는 모킹을 새 창에 다시 건다. 다 돈 창은 닫는다.
  그래서 고정 spec 은 `page` · `request` fixture 대신 `browser` 를 받아 창을 직접 연다. 디바이스 설정은 Playwright 가 테스트 안에서 만드는 모든 창 · 연결에 프로젝트 `use` 로 채운다 — 고정 spec 은 로그인 상태만 넘긴다.
  전용 설정은 루트 설정의 `use` 를 그대로 받는다 — 회사 서버의 기본 인증 · 사설 인증서 · 창 띄우기(`headless`)가 단독 실행과 같아야 한다 (2026-10-06 PR #162).
  앞 창 상태를 읽고 → 새 창을 열고 → 앞 창을 닫는다. 앞 창을 닫다 실패해도 새 창은 끝에 닫힌다.
  API · 모킹 · 대기 부품은 창을 새로 안 열고 마지막 창을 쓴다. 맨 앞이 API 부품이어도 쿠키를 쌓을 자리가 있게 시작할 때 빈 창 하나를 연다
- **케이스 부품 하나에 단독 실행과 같은 시험 한도를 건다** (2026-10-06, 시나리오 §3.7 「동시성 · 시간」). 넘으면 그 창의 로그인 상태를 찍고 창을 닫고 부품을 `FAIL` · 사유 `부품 제한 시간 <N>ms 를 넘었다` 로 적고 멈춘다.
  창을 닫은 뒤 5초까지 기다려 kit 이 돌려준 절차를 싣는다 — 창이 닫히면 Playwright 동작이 바로 실패해 대개 곧 온다. 못 받으면 `steps: []` 다.
  설정의 `timeout: 0` 은 그대로 둔다 — 시나리오 전체를 끊는 벽은 러너 타이머(`timeoutMs`)다.
  한도 값은 전용 설정이 이미 불러오는 루트 설정의 `timeout` 을 읽어 `metadata.partTimeoutMs` 로 고정 spec 에 넘긴다. 루트에 없으면 Playwright 기본 `30000` 이고, `0`(무제한)이면 부품 한도도 없다
- **이어 주기를 건다** (2026-10-06, 시나리오 §3.7 결정 12 표가 정본). **고정 spec 이 한 곳에서 감싼다** — 브라우저 요청은 새 창에 `route` 로, 케이스의 API 요청은 부품 `request` · `page.request` 를 감싸서(창의 `request` 를 바꿔 끼운 뒤 `newPage` 하면 `page.request` 도 감싼 것이다) 건다(공통/3-공유계약 §5.1 ③, 2026-10-06 PR #162 게이트 0).
  **케이스가 직접 만드는 창과 API 연결도 고정 spec 이 감싼다** — 쥐고 있는 Browser 의 `newContext`(그 창과 그 창의 `request` 에도 모킹 · 이어 주기, 로그인 상태는 안 옮김. `newPage` 도 안에서 이것을 부른다)와 `@playwright/test` 의 `request.newContext`.
  뒤엣것은 케이스(`require`)와 고정 spec(`import`)이 **같은 객체**를 본다 — 러너 이미지에서 쟀다(2026-10-06 PR #162, 바꿔 끼운 `newContext` 가 `/tests` 케이스에서 불렸다). 감싸기는 시나리오가 끝나면 되돌린다.
  가로채기는 kit 이 적는 준비 구간 · 절차 밖 표시판을 읽는다. 앞 부품 응답은 조립이 가리키는 것만 적어 둔다 — 응답이 오는 순간 자리를 잡고 본문은 그 부품이 끝날 때까지 다 읽는다(부품 시험 한도 안에서). 못 읽으면 그 자리에 `<N>번 부품 응답 본문을 못 읽었다` 를 둔다.
  브라우저 `route` 는 모킹을 먼저 걸고 이어 주기를 나중에 건다(Playwright 는 나중 것이 먼저 돈다). 손 안 대는 요청은 `fallback()` 으로 넘긴다 — `continue()` 는 먼저 건 모킹을 건너뛰고 진짜 서버로 간다. 이어 주기 오류면 `abort()` 하고, API 쪽은 요청을 안 보내고 던진다 — 그냥 보내면 막으려던 준비가 서버를 바꾼다.
  막은 요청 · 돌려준 응답 · 미룬 삭제 · API 쪽 모킹에는 `APIResponse` 와 같은 메서드를 가진 가짜 응답을 준다 — Playwright 의 것은 밖에서 못 만들고, 케이스는 판정을 `verify` 로만 한다(K표)
- **미룬 삭제는 마지막 부품 뒤에 거꾸로 보낸다** — 실패로 멈춘 뒤에도 보낸다. 보내기 직전에 목록을 얼리고, 얼린 뒤 오는 삭제는 미루지 않는다.
  모을 때의 로그인 상태(그 도구의 쿠키 — 도구가 이미 닫혔으면 한도에 걸려 찍은 상태)와 그 호출의 머리글 · 그 연결을 만들 때 준 `extraHTTPHeaders` · `httpCredentials` 로 새 API 연결을 만들어 보낸다.
  하나가 401 이거나 실패해도 나머지를 보내고 그 줄에 `status` 나 `error` 를 남긴다. 결과는 결과 줄 표시자와 다른 한 줄(뒷정리 줄)로 흘린다 — 미룬 삭제가 없어도 `[]` 로 흘려 「없었다」와 「끊겨서 모른다」를 가른다.
  러너는 그 줄을 응답의 `cleanup` 에 싣는다. 러너 타이머가 자식을 죽이면 뒷정리 줄이 없고 `cleanup` 도 없다
- **모킹은 `page.context().route()` 로 건다.** `page.route()` 는 쓰지 않는다 — 팝업·새 탭에서 풀린다.
  `unmock` 은 같은 `urlPattern` 으로 건 것을 `unroute` 한다. 케이스의 API 요청에는 고정 spec 이 감싼 도구가 같은 모킹을 건다 — 여럿이 맞으면 나중에 건 것이 이긴다(2026-10-06, 시나리오 §3.7 결정 6 · 12).
  **처음에는 `request` 통로에 모킹이 안 걸렸다** — 브라우저를 안 거치기 때문이다. API 부품의 `page.request` 는 지금도 모킹을 안 거친다
- **API 부품은 `page.request` 로 부른다 — 브라우저 로그인(쿠키)을 같이 쓴다** (2026-09-28 사용자). 앞 부품이 화면에서 로그인했으면 그 사람으로 부른다.
  주소는 `baseUrl` 끝 `/` 를 떼고 `path` 를 **문자열로 잇는다** — `new URL` 로 합치면 대상 주소의 경로(`/shop`)가 날아간다.
  `//` 로 시작하는 `path` 는 400 이다 — `/` 로 시작해도 다른 호스트로 풀린다. 응답 코드가 `expectStatus` 와 다르면 그 부품이 `FAIL` 이고 거기서 멈춘다.
  요청·응답 원문은 결과에 싣지 않는다 — 증적이 싣지 않기 때문이다(도메인/리포팅 §8.4)
- **실패한 부품에서 멈추고** 뒤 부품은 `NA` + `NOT_RUN` 으로 채워 돌려준다. 러너가 채워야 admin 이 「몇 번째에서 멈췄나」를 행으로 적는다.
  **결과 줄은 부품이 끝날 때마다 한 줄**(`@@SCENARIO_PART@@`)이다 — 끝에 한 번이면 제한 시간에 죽였을 때 어디까지 갔는지가 사라진다.
  부품이 예외로 끝나도 고정 spec 이 그 부품 `FAIL` 줄을 흘린다. **안 죽였는데 줄 없이 끝난 부품**(자식 사망 · 설정 오류)은 `NOT_RUN` 이 아니라
  `FAIL` 이고 오류 꼬리를 부품과 전체 `error` 에 싣는다 — 「안 돌았음」으로 두면 원인이 사라진다
- **케이스가 시나리오 디바이스를 선언하지 않았으면 그 부품이 `FAIL` 로 멈춘다** (2026-09-28 사용자). 사유는 `<tcId>은 <디바이스> 환경을 선언하지 않았다`.
  조립 때 서버가 막지만 조립 뒤에 케이스가 디바이스를 뺄 수 있다
- **입구에서 막는 것** — 형태 · 빈 조립 · 대기 60000ms 초과 · case 부품 `filePath` 없음 · 테스트 뿌리 밖(400) · 파일 없음(404 `CASE_NOT_FOUND`) ·
  `trialId` 가 UUID 가 아님(사진 폴더 경로에 그대로 들어간다) · `timeoutMs` 60분 초과 ·
  조립 목록 JSON 120000**바이트** 초과(환경변수 하나로 넘긴다 — 리눅스는 값 하나를 128KiB 바이트로 자르고 한글은 한 글자가 3바이트다).
  admin 은 저장 때 이보다 작은 상한에서 먼저 막는다 — 숫자는 [시나리오.md](시나리오.md) §7 「400 으로 거절하는 조립」 (2026-09-29)
- **결과 줄은 줄 맨 앞의 표시자만, 순번이 제 차례인 것만 받는다** — 케이스 코드도 같은 stdout 에 쓴다. 뒷 순번 줄을 찍으면 돌지 않은 부품이 PASS 로 보인다.
  다음 순번은 새로 받고, 지금 순번은 갈아 끼우고(진짜 줄은 그 부품이 끝난 뒤에 온다), 실패 뒤는 버린다
- **스크린샷 경로는 kit 을 안 고치고 환경변수로 가른다** (§9 · 「착수 전」 ⑤). 실제 실행은 `PLATFORM_RUN_ID=<runId>` · `PLATFORM_HISTORY_ID=scenario`,
  시험 실행은 `PLATFORM_RUN_ID=trial` · `PLATFORM_HISTORY_ID=<trialId>` 다. 순번이 이어지므로 한 폴더 안에서 안 덮는다
- **타임아웃은 케이스와 같은 모양이다** — `200` + `{ status: 'NA', error: { message: 'TIMEOUT' }, parts: <파싱된 것이 있으면 그것> }`.
  안 끝난 부품은 `NOT_RUN` 이 아니라 `TIMEOUT` 이다 — 멈춘 원인이 앞 부품 실패가 아니다
- **HTTP 타임아웃은 케이스와 같다** — admin 이 부를 때 `timeoutMs + 30초`. 러너가 먼저 끊어야 부분 결과가 남는다
- **kit 의 진행 줄과 케이스 결과 줄은 시나리오에서 쓰지 않는다.** 둘 다 `PLATFORM_HISTORY_ID` 를 숫자로 읽는데(`progress.ts` · `reporter.ts`) 시나리오에서는 그 값이 `scenario` 나 `trialId` 라 숫자가 아니다.
  **러너는 시나리오 자식의 `@@PROGRESS@@` 줄을 버리고**, 전용 설정은 케이스 리포터(`PlatformReporter`) 대신 시나리오 결과 표시자를 쓴다
- **진행 알림과 중단 통로는 시나리오에 없다.** 둘 다 `historyId` 로 지목하는데 시나리오 실행에는 그것이 없다. 제한 시간이 상한이다 (시나리오 §3.7 「남는 한계」)
- **결과 줄의 표시자는 `packages/kit/src/runtime/protocol.ts` 한 자리에 더한다.** 케이스의 `@@RESULT@@` 와 섞이지 않게 다른 표시자다.
  워커 출력을 되돌려 쓰는 리포터 규칙(위 「★ 리포터가 워커 출력을 되돌려 쓰는 것이 계약의 일부다」)은 그대로 걸린다

#### 내 컴퓨터 러너 (2026-09-30)

**무엇을 왜 하는지는 [실행.md](실행.md) §7 「케이스 테스트 실행」이 정본이다** (계약 블록도 거기 있다). 여기는 러너가 받는 설정만 적는다.
같은 러너 코드를 **창이 뜨는 모드로 한 벌 더 띄우는 것**이라 새 엔드포인트는 없다 — admin 이 `POST /execute` 를 부른다.

- **`PLATFORM_HEADED=1` 이면 브라우저 창이 뜬다(headed)** — 없으면 지금처럼 창 없이(headless) 돈다.
  값을 자식 프로세스 설정(`playwright.config.ts`)이 읽는다. 기본 러너(컨테이너)는 이 값을 안 준다
- **`HOST` 는 러너가 받는 주소(listen)다.** 기본은 `0.0.0.0` 이라 컨테이너에서 admin 이 닿는다. 내 컴퓨터용은 `127.0.0.1` 로 좁힌다 —
  **러너에는 로그인이 없어서** 같은 망의 다른 기계가 부르면 인증을 건너뛰고 테스트를 돌릴 수 있다 (공통/6-인프라 §9 · 인증 §3.5 가 컨테이너 러너의 포트를 닫는 이유와 같다)
- 루트 `npm run runner:local` 이 `PLATFORM_HEADED=1 HOST=127.0.0.1 PORT=4001 PLATFORM_TESTS_DIR=./tests …` 를 한 줄로 묶는다. 켜는 절차는 SETUP.md 「내 컴퓨터 러너 켜는 법」이 정본이다
- 무상태 규칙(§3.4)은 그대로다 — DB 를 모르고 판정·기록은 admin 만 쓴다. 이 러너가 만든 결과는 admin 이 기록 없이 메모리에만 둔다
