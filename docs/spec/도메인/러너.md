### 3.4 Runner — 실제로 돌린다

- **책임**: 케이스 1건을 주어진 값으로 실행하고 구조화된 결과를 반환.
  **또는 시나리오 1개 — 케이스 여럿과 부품을 한 브라우저에서 순서대로 — 를 실행한다** (2026-09-28, [시나리오.md](시나리오.md) §3.7).
  무엇을 도는지만 늘었다. 아래 무상태 규칙은 그대로다 — 시나리오 정의·버전·결과는 admin 만 안다
- **DB 무상태**. 어떤 테이블에도 접근하지 않는다. 돌고 있는 자식 프로세스의 손잡이만 메모리에 들고 있고,
  러너가 죽으면 그 프로세스와 함께 사라진다. 이 규칙이 깨지면 컨테이너 분리가 무의미해진다
- **중단 통로** (2026-09-16 결정): 돌고 있는 실행을 바깥에서 끊을 수 있어야 한다(§3.2). 러너에 `historyId`로
  지목해 끊는 창구를 하나 낸다. **끊는 동작 자체는 이미 있다** — 타임아웃 때 자식 프로세스 그룹을 통째로 죽이는
  코드가 그것이고, 바깥에서 부를 길만 없었다. 엔드포인트와 응답 형태는 **§5.2가 정본**이다
- **바깥으로 내는 통로가 생겨도 위 무상태 규칙은 깨지지 않는다** (중단·진행. 둘 다 §5.2가 정본이다).
  러너가 들고 있는 것은 살아 있는 프로세스의 손잡이와 그것이 지금 어느 절차까지 왔는지뿐이고
  DB에 저장된 상태가 아니다. 답한 뒤에 도는 팜 증적 받기(§5.2 「디바이스 팜 접속 방식」, 2026-10-20)도 파일만 쓰고 끝난다 — 러너가 꺼지면 그 받기만 사라진다. 판정·이력·스냅샷은 여전히 admin만 쓴다. §5.3의 이음새를 떠받치는 규칙도 그대로다
- 끊긴 실행은 **타임아웃과 같은 모양으로** 돌아온다. `error.message`만 `TIMEOUT`이 아니라 `ABORTED`다.
  admin 쪽에 저장 경로를 새로 만들지 않기 위해서다 (§5.2)
- 입출력은 §5.2 계약만 사용

### 5.2 Runner HTTP 계약

```
POST http://runner:4000/execute
Content-Type: application/json
Body:     ExecuteRequest
200 OK:   ExecuteResponse
400:      { error: 'INVALID_REQUEST', detail: string }
404:      { error: 'CASE_NOT_FOUND', detail: string }
500:      { error: 'RUNNER_ERROR', detail: string }

POST http://runner:4000/abort
Content-Type: application/json
Body:     { historyId: number }
200 OK:   { aborted: boolean }
          돌고 있던 자식 프로세스를 그룹째 끊었으면 true.
          이미 끝났거나 러너가 모르는 historyId면 false다 — 경합이지 고장이 아니므로 404로 만들지 않는다.
          끊긴 실행의 /execute 응답은 타임아웃과 같은 모양으로 돌아온다 (error.message = 'ABORTED')
400:      { error: 'INVALID_REQUEST', detail: string }

GET  http://runner:4000/progress
200 OK:   { items: RunningStep[] }
          지금 돌고 있는 자식마다 한 건이다. 아직 첫 절차를 안 흘린 자식은 빠진다.
          러너는 runId도 서비스도 모른다 — 거르는 일은 admin이 한다 (§7)

POST http://runner:4000/execute-scenario        (2026-09-28)
Content-Type: application/json
Body:     ScenarioExecuteRequest
200 OK:   ScenarioExecuteResponse
400:      { error: 'INVALID_REQUEST', detail: string }
404:      { error: 'CASE_NOT_FOUND', detail: string }

POST http://runner:4000/app-screen              (2026-10-19 · 아래 「앱 화면 읽기」)
Content-Type: application/json
Body:     { app?: string, udid?: string }
200 OK:   { screen: string }
400:      { error: 'INVALID_REQUEST', detail: string }
409:      { error: 'RUNNER_BUSY', detail: string }

POST http://runner:4000/game-screen             (2026-10-23 · 아래 「게임 화면 읽기」 — 요청 · 응답 · 오류는 /app-screen 과 같다)

GET  http://runner:4000/health   → 200 { ok: true, playwrightVersion: string }

GET  http://runner:4000/files?path=<runs/ · perf/ · perf-record/ 아래 상대 경로>   (2026-10-27 · 아래 「러너 토큰 · 파일 내주기」)
200 OK:   파일 내용 (application/octet-stream · content-length 있음)
GET  http://runner:4000/files?dir=<runs/ · perf/ · perf-record/ 아래 상대 경로>
200 OK:   { files: { name: string, bytes: number }[] }   그 폴더의 일반 파일 이름 · 크기만 — 폴더 · 바로가기는 빠진다
400:      { error: 'INVALID_REQUEST', detail: string }   path · dir 이 둘 다 있거나 둘 다 없거나, runs/ · perf/ · perf-record/ 밖이거나 위로 올라간다
404:      { error: 'NOT_FOUND', detail: string }         없거나 가는 길에 바로가기가 끼었다

RUNNER_TOKEN 을 건 러너는 /health 밖의 모든 요청에 Authorization: Bearer <토큰> 을 받는다 (2026-10-27)
401:      { error: 'UNAUTHORIZED', detail: string }
```

- **동기 호출.** Execution이 동시성 2로 제한해 호출한다. Android 앱 항목은 그 상한 밖의 디바이스 줄에서 한 번에 하나씩 서버 러너를 부른다 — 폰은 항목마다 디바이스 팜에서 잡는다 (2026-10-07 · 2026-10-20 APP-F1-10, [실행.md](실행.md) §3.2 · 아래 「디바이스 팜 접속 방식」)
- 러너는 `ExecuteRequest.params`를 환경변수 `PLATFORM_PARAMS`(JSON 문자열)로 주입하고
  `npx playwright test <filePath> --project=<platform>`을 자식 프로세스로 실행한다
- 결과는 커스텀 리포터가 stdout에 **JSON 한 줄**(`@@RESULT@@{...}`)로 뱉고 러너가 파싱한다
- **타임아웃**: `timeoutMs`가 지나면 러너가 자식 프로세스를 죽이고 `200`으로
  `{ status: 'NA', error: { message: 'TIMEOUT' }, steps: <파싱된 것이 있으면 그것, 없으면 []> }`을 돌려준다.
  `500`은 러너 자체의 고장(프로세스 기동 실패 등)에만 쓴다
- Execution이 러너를 부를 때의 HTTP 타임아웃은 `timeoutMs + 30초`다. 러너가 먼저 끊어야 부분 결과가 남는다
- 케이스 1건 = Playwright 프로세스 1개(`workers: 1`). 동시 실행은 Execution의 동시성(2)으로만 제어한다.
  **시나리오는 시나리오 1개 = 프로세스 1개다** (2026-09-28). 케이스 여럿이 한 프로세스·한 `test()` 안에서 돈다 — 아래 「시나리오 실행」
- **`baseUrl`**: 그 실행이 두드릴 주소다. 사람은 화면에서 **대상 서버**(개발·QA·스테이징) 이름만 고르고,
  admin이 자기 설정표에서 주소를 찾아 이 칸에 실어 보낸다. 러너는 어떤 대상 서버가 있는지 모른다 — 주소 하나만 받는다.
  러너는 이 값을 환경변수 `PLATFORM_BASE_URL`로 자식 프로세스에 넘기고 `playwright.config.ts`가 `use.baseURL`로 받는다.
  주소를 아는 쪽을 admin 하나로 묶어야 러너가 도메인 상태를 갖지 않는다
- **자동 재시도는 쓰지 않는다. `playwright.config.ts`의 `retries`는 0으로 명시해 고정한다.**
  실패를 가려서 초록불을 만드는 것과, 불안정한지 보려고 일부러 여러 번 돌리는 것은 다른 일이다.
  여러 번 돌리는 쪽은 실행 요청의 `repeat`가 맡는다. 켜려면 이 문장을 먼저 고친다.
  같은 문장을 `playwright.config.ts`의 `retries` 자리에 주석으로도 남긴다 — 설정 파일만 보고 켜 버리는 일을 막는다
- **반복 실행은 러너에 보이지 않는다.** admin이 `historyId`만 다른 같은 요청을 N번 보낼 뿐이다.
  회차(`attempt`)를 러너 계약에 넣지 않는다. 러너는 회차로 아무 일도 하지 않고,
  스크린샷 경로가 이미 `historyId`로 갈라져 있어 서로 덮어쓰지 않는다
- **출력 폴더 · trace** (2026-10-16 · 진행판 PRD-F10-03). Playwright 는 시작할 때 출력 폴더(`outputDir`)를 통째로 지운다 —
  나란히 도는 실행이 한 폴더를 쓰면 남의 trace 를 옮기기 전에 지운다. 그래서 **러너가 자식마다 `PLATFORM_OUTPUT_ID`(번호 + 무작위)를 주고**
  설정 둘(케이스 · 시나리오)이 `artifacts/playwright/<그 이름>` 을 쓴다. 워커도 설정을 다시 읽지만 환경값을 물려받아 같은 폴더를 본다.
  자식이 끝나면 러너가 그 폴더를 지운다(남는 것은 아무도 안 읽는다). 값이 없으면(사람이 직접 돌릴 때) 예전처럼 `artifacts/playwright/local` 하나다.
  케이스는 정식 실행(`runId > 0`)의 브라우저 항목에만 러너가 `PLATFORM_TRACE=1` 을 준다 — 설정이 그때만 `trace` 를 켠다(화면 녹화 · 소스 끔).
  **시나리오는 진짜 실행 · 시험 실행 모두 준다** (2026-10-17 E2E-F1-26) — 시나리오 리포터는 kit 값을 못 불러와, 자식이 끝나면 러너가 출력 폴더의 `trace.zip`(테스트가 하나라 하나다)을 사진 옆으로 옮긴다.
  자리는 아래 「시나리오 실행」의 사진 폴더와 같다(`runs/{runId}/scenario/trace.zip` · `runs/trial/{trialId}/trace.zip`). 못 옮겨도 판정은 그대로다
  **kit 리포터가 결과 줄을 내기 전에** trace 첨부를 `artifacts/runs/{runId}/{historyId}/trace.zip` 으로 옮긴다 — runId 가 `0` 이면 안 옮기고, 못 옮겨도 판정은 그대로 두고 사유를 stderr 로 낸다.
  리포터는 상대 import 를 못 써서 경로 계산을 한 벌 더 두고 `reporter.test.ts` 가 kit 의 `runDir` 과 같은지 지킨다. 무엇을 남기고 푸는지는 [실행.md](실행.md) §3.2 「trace」
- **중단**: `POST /abort`는 `historyId`로 돌고 있는 자식 프로세스를 지목해 **프로세스 그룹째** 끊는다.
  끊는 방식은 타임아웃과 완전히 같다. 바깥에서 부를 통로만 새로 낸 것이다.
  실행 묶음 전체를 끊는 일은 admin이 자기가 아는 `historyId`를 하나씩 부르는 것으로 한다.
  러너에 `runId` 단위 중단을 두면 러너가 실행 묶음을 알아야 한다
- 끊긴 실행의 `POST /execute` 응답은 **타임아웃과 같은 모양**으로 돌아온다.
  `200` + `{ status: 'NA', error: { message: 'ABORTED' }, steps: <파싱된 것이 있으면 그것, 없으면 []> }`.
  모양이 같아야 Execution의 저장 경로에 새 분기가 생기지 않는다
- 이미 끝났거나 러너가 모르는 `historyId`에는 `200 { aborted: false }`를 돌려준다.
  중단 요청과 정상 종료가 겹치는 것은 **경합이지 고장이 아니다.** 404로 만들면 Execution이 정상 상황마다 에러를 받는다
- 러너는 `historyId → 자식 프로세스` 지도를 **메모리에만** 들고 있는다. DB는 여전히 모른다 (§3.4).
  러너가 죽으면 지도도 자식 프로세스도 같이 사라지므로, 남은 항목을 닫는 일은 admin의 재기동 복구가 맡는다
- **진행**: 절차가 시작될 때마다 킷이 stdout에 **JSON 한 줄**(`@@PROGRESS@@{...}`, `StepProgress`)을 흘리고
  러너가 그 줄로 자기 지도의 「지금 도는 절차」를 고쳐 쓴다. 결과 줄과 같은 방식이고 표시자는 둘 다
  `packages/kit/src/runtime/protocol.ts` 한 자리에 모여 있다. 알림은 **판정에 끼어들지 않는다** —
  못 흘려도 삼키고, `PLATFORM_HISTORY_ID`가 없으면(사람이 손으로 돌릴 때다) 아예 안 흘린다
- **★ 리포터가 워커 출력을 되돌려 쓰는 것이 계약의 일부다.** 케이스 코드는 Playwright **워커**에서 돌고
  거기서 `process.stdout.write`는 Playwright 것으로 갈아치워져 IPC로만 간다. 리포터의 `onStdOut`이
  받은 조각을 진짜 stdout으로 **다시 쓰지 않으면 진행 줄이 러너에 한 글자도 안 닿는다.**
  단위 검사가 이 자리를 원리적으로 못 본다 — 케이스는 멀쩡히 통과하고 진행만 조용히 0이 된다 (2026-09-21 실측).
  그리고 **진행 줄만 골라 내보내면 안 된다.** `onStdOut`이 생기는 순간 워커 stdio가 `inherit`에서
  `pipe`로 바뀌어, 안 넘긴 출력은 사라지고 러너가 오류 문장으로 쓰는 stdout 꼬리가 빈 문자열이 된다
- **케이스 파일을 못 읽으면(문법 오류 · import 실패) 리포터가 그 오류를 stderr로 흘린다** (2026-10-12).
  Playwright는 이 오류를 리포터의 `onError`로만 넘긴다 — 받는 자리가 없으면 stdout · stderr가 둘 다 비어
  결과가 「실패」인데 사유가 빈 글이 된다(실측). 테스트가 하나도 안 돌아 결과 줄이 없으므로 러너는 exit code로 FAIL을 내고
  stderr를(비었으면 stdout 꼬리를) `error.message`로 싣는다. 색 코드는 걷고, 2,000자를 넘으면 원문 첫 줄을 지키고 끝부분을 줄 경계에서 자른다 —
  admin 요약은 그 첫 줄을 사유로 쓰고, 줄 가운데를 자르면 가리기가 못 알아보는 비밀값 조각이 남는다.
  그래서 1,000자 넘는 첫 줄은 자르지 않고 통째로 빼고 「…」로 시작한다. 그런 실패는 요약에서 사유가 「…」인 한 덩어리로 묶인다 —
  비밀값 조각을 남기지 않는 값으로 받아들였다(그런 첫 줄은 드물다. 2026-10-12 사용자). 러너는 stdout · stderr를 UTF-8로 이어 읽는다(조각 경계의 한글이 깨지지 않게)
- **admin이 묻는다. 러너가 알리지 않는다** (당김. 2026-09-21 결정). 러너에는 로그인 세션이 없어
  러너가 admin에 쓰려면 **로그인 없이 지나가는 자리**를 새로 내야 한다. 그런 예외는 하나 있었고
  2026-09-17에 일부러 없앴다 (§7 인증 적용 범위 — 인증 없이 부를 수 있는 API는 없다).
  admin → 러너 방향은 `/execute`·`/abort`로 **이미 있는 길**이라 문에 구멍을 내지 않는다
- **경과는 러너가 잰다.** 시작 시각을 실어 보내면 러너 컨테이너 시계와 보는 사람 기계 시계의 차가
  그대로 오차가 된다 — 몇 초 어긋나면 화면에 「-3초째」가 뜬다. `elapsedMs`는 물어본 그 순간에 러너가 계산한다
- **진행을 러너가 거르지 않는다.** 응답에는 `runId`도 `serviceId`도 없다. 러너가 그것을 알면
  실행 묶음과 서비스를 아는 것이 되어 §3.4가 깨진다. 거르는 일은 admin 몫이다 (§7)
- **이 통로도 §3.4 무상태를 깨지 않는다.** 러너가 드는 것은 **살아 있는 프로세스의 진행**이지
  저장된 상태가 아니고 러너가 죽으면 같이 사라진다. 중단 통로를 낼 때 쓴 것과 **같은 논거**다

```

#### 시나리오 실행 (2026-09-28)

**무엇을 왜 도는지는 [시나리오.md](시나리오.md) §3.7 이 정본이다.** 여기는 러너가 어떻게 받고 무엇을 돌려주는지만 적는다.

- **시나리오마다 테스트 파일을 만들지 않는다.** 러너 이미지 안에 **고정 파일 하나**(`apps/runner/scenario/`)와 그것만 보는 설정 파일을 둔다.

  고정 파일은 케이스 파일을 **불러 쓰기만** 하므로 쓸 자리가 필요 없다 (설계서 「착수 전에 답이 있어야 하는 것」 ①, 2026-09-28).
  **실측으로 확인했다 (2026-09-28, PR #100)** — 기본 설정으로 밖 파일 경로를 주면 `No tests found`, 전용 설정의 고정 spec 이 부르면 된다.
  전용 설정은 `testMatch` 를 고정 spec 이름 하나로 박는다 — 기본 무늬가 같은 폴더의 `*.test.ts`(vitest 검사)까지 잡는다
- **고정 spec 은 kit 을 값으로 부르지 않는다** (2026-09-28 이미지 실측). 케이스 파일이 kit 을 `require` 로 부를지 `import` 로 부를지는
  그 파일이 어디 있느냐로 갈린다 — 러너 이미지의 `/tests` 는 `package.json` 이 없어 `require`, 저장소 안은 `"type": "module"` 이라 `import` 다.
  고정 spec 이 kit 을 한 방식으로 먼저 올리면 같은 kit 파일이 두 방식으로 섞여 죽는다(이미지 `Unexpected token 'export'` · 로컬 `does not provide an export named`).

  **CI(Node 22)는 `require` 쪽을 재현하지 못한다** — 고정 spec 이나 kit 불러오기를 고쳤으면 러너 이미지에서 한 번 부른다
- **케이스 부품의 `filePath` 도 `/execute` 와 같은 경로 검사를 지난다.** 테스트 뿌리 밖을 가리키면 400 이다
- **고정 파일이 `test()` 하나 안에서 부품을 차례로 돈다.** 케이스 부품은 kit 의 시나리오 모드로 본체를 꺼내(공통/3-공유계약 §5.1)
  **부품마다 새 창**(브라우저 컨텍스트)으로 돌리고, 부품마다 입력값을 따로 해석한다. **순번은 시나리오 전체에서 이어진다** — 부품마다 실패 표시는 새로 세우고 순번만 넘겨받는다(정본 공통/3-공유계약 §5.1 시나리오 모드)
- **새 창은 앞 부품의 로그인 상태로 연다** (2026-10-06, 시나리오 §3.7 결정 3 · 12). 앞 창의 `storageState()` 와 앞 부품 `request` 의 쿠키를 합쳐(겹치면 창 쪽) 새 창과 새 `request` 에 넣는다.
  넘겨받기를 끈 부품은 빈 상태로 연다. 새 창은 그 디바이스 프로젝트의 `use` 설정(화면 크기 · 사용자 에이전트)으로 열고, 걸려 있는 모킹을 새 창에 다시 건다. 다 돈 창은 닫는다.
  그래서 고정 spec 은 `page` · `request` fixture 대신 `browser` 를 받아 창을 직접 연다. 디바이스 설정은 Playwright 가 테스트 안에서 만드는 모든 창 · 연결에 프로젝트 `use` 로 채운다 — 고정 spec 은 로그인 상태만 넘긴다.
  전용 설정은 루트 설정의 `use` 를 그대로 받는다 — 회사 서버의 기본 인증 · 사설 인증서 · 창 띄우기(`headless`)가 단독 실행과 같아야 한다 (2026-10-06 PR #162).
  앞 창 상태를 읽고 → 새 창을 열고 → 앞 창을 닫는다. 앞 창을 닫다 실패해도 새 창은 끝에 닫힌다.
  API · 모킹 · 대기 부품은 창을 새로 안 열고 마지막 창을 쓴다. 맨 앞이 API 부품이어도 쿠키를 쌓을 자리가 있게 시작할 때 빈 창 하나를 연다
- **케이스 부품 하나에 단독 실행과 같은 시험 한도를 건다** (2026-10-06, 시나리오 §3.7 「동시성 · 시간」). 넘으면 그 창의 로그인 상태를 찍고(5초까지 기다린다) 그 부품의 창 · 부품 `request` · 케이스가 직접 만든 창과 연결을 닫고 부품을 `FAIL` · 사유 `단계 제한 시간 <N>ms 를 넘었다` 로 적고 멈춘다.
  그 뒤 케이스가 창 · 연결을 새로 만들면 만들자마자 닫고 던진다 — 한도에 걸린 부품의 요청이 뒤에서 서버를 두드리면 안 된다.
  창을 닫은 뒤 5초까지 기다려 kit 이 돌려준 절차를 싣는다 — 창이 닫히면 Playwright 동작이 바로 실패해 대개 곧 온다. 못 받으면 `steps: []` 다.
  설정의 `timeout: 0` 은 그대로 둔다 — 시나리오 전체를 끊는 벽은 러너 타이머(`timeoutMs`)다.
  한도 값은 전용 설정이 이미 불러오는 루트 설정의 `timeout` 을 읽어 `metadata.partTimeoutMs` 로 고정 spec 에 넘긴다. 루트에 없으면 Playwright 기본 `30000` 이고, `0`(무제한)이면 부품 한도도 없다
- **이어 주기를 건다** (2026-10-06, 시나리오 §3.7 결정 12 표가 정본). **고정 spec 이 한 곳에서 감싼다** — 브라우저 요청은 새 창에 `route` 로, 케이스의 API 요청은 부품 `request` · `page.request` 를 감싸서(창의 `request` 를 바꿔 끼운 뒤 `newPage` 하면 `page.request` 도 감싼 것이다) 건다(공통/3-공유계약 §5.1 ③, 2026-10-06 PR #162 게이트 0).
  **케이스가 직접 만드는 창과 API 연결도 고정 spec 이 감싼다** — 쥐고 있는 Browser 의 `newContext`(그 창과 그 창의 `request` 에도 모킹 · 이어 주기, 로그인 상태는 안 옮김. `newPage` 도 안에서 이것을 부른다)와 `@playwright/test` 의 `request.newContext`.
  뒤엣것은 케이스(`require`)와 고정 spec(`import`)이 **같은 객체**를 본다 — 러너 이미지에서 쟀다(2026-10-06 PR #162, 바꿔 끼운 `newContext` 가 `/tests` 케이스에서 불렸다). 감싸기는 시나리오가 끝나면 되돌린다.
  **직접 만든 창 · 연결은 그것을 만든 부품을 따른다** — 거기 거는 이어 주기 · 미룸은 그 부품 것이고, 그 부품이 끝나면(정상이든 한도에 걸렸든) 러너가 부품 창과 함께 닫는다. 부품이 끝난 뒤에는 케이스가 그것을 쓸 일이 없다 (2026-10-06 PR #162 게이트 2 사용자 — 게이트 1 에서는 「정상으로 끝나면 케이스 몫」이었다).
  가로채기는 kit 이 적는 준비 구간 · 절차 밖 표시판을 읽는다. 앞 부품 응답은 조립이 가리키는 것만 적어 둔다 — 응답이 오는 순간 자리를 잡고 본문은 그 부품이 끝날 때까지 다 읽는다(부품 시험 한도 안에서). 못 읽으면 그 자리에 `<N>번 단계 응답 본문을 못 읽었다` 를 둔다.
  브라우저의 3xx 응답은 적지 않는다 — 본문을 못 읽어 자리만 차지한다. API 쪽에 준 가짜 응답(막기 · 돌려주기 · 모킹)도 적는다 — 브라우저 쪽은 `fulfill` 한 응답도 `response` 로 적히므로 같게 한다.
  브라우저 `route` 는 모킹을 먼저 걸고 이어 주기를 나중에 건다(Playwright 는 나중 것이 먼저 돈다). 이어 주기 핸들러는 **route 가 이미 맞춘 무늬를 글자로** 골라 건다 — 손으로 옮긴 무늬 맞추기(시나리오 §3.7 결정 12 「요청 고르기」)와 갈려 막을 요청이 조용히 서버로 새지 않게. 손 안 대는 요청은 `fallback()` 으로 넘긴다 — `continue()` 는 먼저 건 모킹을 건너뛰고 진짜 서버로 간다. 이어 주기 오류면 `abort()` 하고, API 쪽은 요청을 안 보내고 던진다 — 그냥 보내면 막으려던 준비가 서버를 바꾼다.
  막은 요청 · 돌려준 응답 · 미룬 삭제 · API 쪽 모킹에는 `APIResponse` 와 같은 메서드를 가진 가짜 응답을 준다 — Playwright 의 것은 밖에서 못 만들고, 케이스는 판정을 `verify` 로만 한다(K표).
  미룬 삭제의 응답 코드는 요청의 `deleteStatuses` 에서 찾고 없으면 `204` 다(시나리오 §3.7 결정 12 「막은 요청 · 미룬 삭제에는 성공 응답을 준다」). 러너는 그 목록을 환경변수 `PLATFORM_DELETE_STATUSES` 로 고정 spec 에 넘기고, 주소 틀은 admin `API틀` 과 같은 규칙을 고정 spec(`scenario/links.ts`)에 한 벌 더 둔다 — 고정 spec 은 admin 을 못 부른다(둘이 같은지는 admin `apiMap.test.ts` 가 본다). 주소를 못 읽으면(기준 주소 없는 연결의 상대 주소) 던지지 않고 `204` 다.
  1000줄 · 호스트 255자 · 주소 2000자까지 받고, admin 은 그보다 긴 줄을 빼고 싣는다 — 한 줄 때문에 그 서비스의 시나리오가 다 400 이 되지 않게
- **미룬 삭제는 마지막 부품 뒤에 거꾸로 보낸다** — 실패로 멈춘 뒤에도 보낸다. 보내기 직전에 목록을 얼리고, 얼린 뒤 오는 삭제는 미루지 않는다.
  모을 때의 로그인 상태(그 도구의 쿠키 — 도구가 이미 닫혔으면 한도에 걸려 찍은 상태)와 그 호출의 머리글 · 그 연결을 만들 때 준 `extraHTTPHeaders` · `httpCredentials` 로 새 API 연결을 만들어 보낸다.
  주소에는 그 호출의 `params` 를 Playwright 와 같은 규칙으로 붙이고(글자 · `URLSearchParams` 는 물음표 뒤를 갈아 끼우고 — 비었으면 그대로 — 객체는 덧붙인다) 본문(`data` · `form` · `multipart`)도 모을 때의 값으로 싣는다(평범한 객체 · 배열은 모을 때 떠 둔다 — 케이스가 같은 객체를 고쳐 다시 지워도 앞 값이 나간다) —
  주소만 다시 보내면 쿼리나 본문으로 지울 것을 고르는 서버에서 다른 것이 지워지거나 거절된다 (2026-10-24 FIX-F2-05 · 리뷰 L37).
  머리글 · 기본 인증은 **모을 때** Playwright 와 같은 규칙으로 정한다 — 그 도구를 만들 때 그 칸을 안 줬으면 프로젝트 `use` 의 `extraHTTPHeaders` · `httpCredentials`, 줬으면 준 것(부품 `request` · `page.request` 는 늘 프로젝트 값).
  보낼 때 칸을 명시하면 Playwright 가 기본값을 안 채우기 때문이다. 기본 인증이 없으면 그 칸을 아예 안 넣는다 — `undefined` 로라도 넣으면 기본값을 건너뛴다(2026-10-06 재검사).
  하나가 401 이거나 실패해도 나머지를 보내고 그 줄에 `status` 나 `error` 를 남긴다. 하나는 부품 시험 한도(한도 없음이면 30초)를 Playwright 요청 한도로 걸어 보낸다 — 넘으면 Playwright 의 한도 오류를 남기고 다음 것을 보낸다.
  연결 만들기 · 닫기까지 멈추면 5초 더 기다려 `미룬 삭제가 <N>ms 안에 끝나지 않았다` 를 남긴다(바깥 상한을 요청 한도와 같게 두면 아직 날아가는 삭제와 다음 삭제가 겹쳐 거꾸로 보내는 순서가 깨진다). 대상 서버가 안 답해도 다 통과한 시나리오가 판정 없음(`TIMEOUT`)이 되지 않게. 결과는 결과 줄 표시자와 다른 한 줄(뒷정리 줄)로 흘린다 — 미룬 삭제가 없어도 `[]` 로 흘려 「없었다」와 「끊겨서 모른다」를 가른다.
  러너는 그 줄을 응답의 `cleanup` 에 싣는다. 러너 타이머가 자식을 죽이면 뒷정리 줄이 없고 `cleanup` 도 없다
- **모킹은 `page.context().route()` 로 건다.** `page.route()` 는 쓰지 않는다 — 팝업·새 탭에서 풀린다.
  `unmock` 은 같은 `urlPattern` 으로 건 것을 `unroute` 한다. 케이스의 API 요청에는 고정 spec 이 감싼 도구가 같은 모킹을 건다 — 여럿이 맞으면 나중에 건 것이 이긴다(2026-10-06, 시나리오 §3.7 결정 6 · 12).
  **처음에는 `request` 통로에 모킹이 안 걸렸다** — 브라우저를 안 거치기 때문이다. API 부품의 `page.request` 는 지금도 모킹을 안 거친다
- **API 부품은 `page.request` 로 부른다 — 브라우저 로그인(쿠키)을 같이 쓴다** (2026-09-28 사용자). 앞 부품이 화면에서 로그인했으면 그 사람으로 부른다.
  주소는 `baseUrl` 끝 `/` 를 떼고 `path` 를 **문자열로 잇는다** — `new URL` 로 합치면 대상 주소의 경로(`/shop`)가 날아간다.
  `//` 로 시작하는 `path` 는 400 이다 — `/` 로 시작해도 다른 호스트로 풀린다. 응답 코드가 `expectStatus` 와 다르면 그 부품이 `FAIL` 이고 거기서 멈춘다.
  요청·응답 원문은 결과에 싣지 않는다 — 증적이 싣지 않기 때문이다(도메인/리포팅 §8.4). 예외는 응답 값 확인이 틀렸을 때의 받은 값 50자다(아래 · 시나리오 §3.7 결정 14) — 러너가 토큰 · 비밀값을 가린 뒤 싣는다
- **API 부품의 API 인증 · 값 주입 · 응답 값 확인**(2026-10-21, 시나리오 §3.7 결정 14 가 정본) — `apps/runner/scenario/apiPart.ts` 가 한다.
  `auth` 가 있으면 부품 `apiAuths` 에서 그 이름을 찾아 토큰을 받고(같은 창 `request` 로 — 고정 spec 은 kit 을 값으로 못 부른다) `Authorization: Bearer` 를 붙인다. 토큰은 단계 주소 · 이름마다 시나리오 동안 쥔다.
  `values` 는 앞 응답을 결정 12 「값 꺼내기」로 꺼내 `path` · `body` 의 `{이름}` 자리에 넣는다. 부른 응답은 뒤 단계가 가리키면 적어 두고(결정 12 「응답 적기」 — 창을 닫기 전에 본문을 읽는다), 결과의 `bound` 에 넣은 값을 남긴다.
  응답 코드가 맞으면 `expectJson` 을 차례로 본다. 오류 글은 토큰 · 비밀값 · Basic 머리를 가리고 첫 줄만 남긴다 — Playwright 오류의 호출 기록이 보낸 머리를 늘어놓는다
  러너 입구는 `auth`(1~20자) · `values[].name`(영문 · 숫자 · 한글 · `_` 1~20자) · `values[].value`(응답 고르기 모양) · `expectJson[].jsonPath`(빈 글자 아님) · `apiAuths`(케이스 부품과 같은 모양)를 본다
- **실패한 부품에서 멈추고** 뒤 부품은 `NA` + `NOT_RUN` 으로 채워 돌려준다. 러너가 채워야 admin 이 「몇 번째에서 멈췄나」를 행으로 적는다.
  **결과 줄은 부품이 끝날 때마다 한 줄**(`@@SCENARIO_PART@@`)이다 — 끝에 한 번이면 제한 시간에 죽였을 때 어디까지 갔는지가 사라진다.

  `FAIL` 이고 오류 꼬리를 부품과 전체 `error` 에 싣는다 — 안 돈 것(`NOT_RUN`)으로 두면 원인이 사라진다
- **케이스가 시나리오 디바이스를 선언하지 않았으면 그 부품이 `FAIL` 로 멈춘다** (2026-09-28 사용자). 사유는 `<tcId>은 <디바이스> 환경을 선언하지 않았다`. 웹 단계만이다 — 앱 · 게임 단계는 `android` 를 보고, `android` 시나리오의 웹 단계는 `desktop` 을 본다(2026-10-28 결정 16)

| `PLATFORM_APPIUM_URL` | Appium 서버 주소. 필수. protocol · 호스트 · 포트 · 경로 · URL 안 계정까지 그대로 넘긴다(계정은 WebdriverIO `user` · `key` 로). 우리 디바이스 팜은 계정 대신 토큰 머리를 쓴다 — 아래 「디바이스 팜 접속 방식」 |
| `PLATFORM_APPIUM_TOKEN` | 인증 켠 디바이스 팜의 토큰. 선택 — 있으면 WebdriverIO `headers` 로 모든 요청에 `Authorization: Bearer` 를 싣고 URL 안 계정은 넘기지 않는다. 비면 싣지 않는다. 러너는 요청의 `farmToken` 이 있으면 자기 값 대신 그것을 넣는다(2026-10-27 · 2026-10-29 — 아래 「디바이스 팜 접속 방식」 「팜 토큰은 누른 사람 것이 먼저다」) |
| `PLATFORM_APP` | 설치할 apk 경로나 http(s) 주소. 필수 — 다만 요청의 `app` 이 있으면 그것이 앞선다(아래 「대상 서버마다 다른 앱 파일」) |
| `PLATFORM_DEVICE_UDID` | 폰 하나를 지정한다. 선택 — 없으면 Appium 이 연결된 한 대를 고른다. 요청의 `udid`(admin 이 팜에서 잡은 폰)가 있으면 그것이 앞선다(아래 「디바이스 팜 접속 방식」) |

필수 값이 없으면 연결 전에 `Android 앱 케이스를 돌리려면 PLATFORM_APPIUM_URL 이 필요하다`(`PLATFORM_APP` 도 같은 꼴)로 실패한다.
capabilities 는 `platformName: Android` · `automationName: UiAutomator2` · `disableIdLocatorAutocompletion: true` · `app` · (있으면) `udid` 다.
`disableIdLocatorAutocompletion` 은 `id=` 주소 앞에 앱 꾸러미 이름을 저절로 붙이지 않게 한다(2026-10-22) — 꾸러미 없는 resource-id(Compose `testTag` 등)를 쓰는 앱도 `id=` 로 찾는다. 긴 꼴 `id=com.shop:id/login` 은 그대로 찾는다. **짧은 꼴은 꾸러미 없는 resource-id 에만 쓴다** — 화면 글의 id 를 그대로 옮긴다(XML 뷰 앱의 `com.shop:id/login` 을 `id=login` 으로 줄이면 못 찾는다). 작성 AI 의 appium-cli 도 `open` 에 같은 capability 를 준다([작성.md](작성.md) §3.6 「눌러 가며 읽기」 · 자식 지침 `references/app.md` §5).

**대상 서버마다 다른 앱 파일** (2026-10-19 APP-F1-03 · 아래 계약 블록) — 대상 서버 줄에 「앱 파일 경로」(`service_env.app_path`)를 둔다.
admin 은 android 항목에만 그 줄의 경로를 `ExecuteRequest.app` 으로 싣고, 러너는 그 값을 자식의 `PLATFORM_APP` 으로 덮어 넘긴다. 줄이 비었으면 싣지 않고 러너를 켤 때 준 `PLATFORM_APP` 을 쓴다.
정식 실행은 고른 대상 서버 키로, 테스트 실행은 보낸 주소와 출처가 같은 첫 줄(계정 채우기와 같은 줄 — [실행.md](실행.md) §3.2)로 찾는다.
**값은 Appium 이 도는 PC 기준이다** — 디바이스 팜이면 팜 PC 가 받는다. 파일이 있는지는 안 본다(Appium 이 못 찾으면 그 항목이 실패 사유로 말한다).
**파일 경로나 `http(s)` 주소를 받는다** (2026-10-20 APP-F1-10 — 앞 판은 `://` 가 든 값을 다 거절했다. 팜 PC 가 앱을 내려받으므로 주소를 연다). **그 밖의 주소(`file://` 등)는 설정 · 러너 둘 다 400 이다** — 그 PC 의 아무 파일이나 폰에 깔게 된다. 규칙은 kit `앱파일값인가` 하나를 둘이 같이 쓴다. 빈 글자는 없음으로 읽는다. apk 올리기는 저장 자리 · 보관 문제가 붙어 두지 않는다

```
[계약 변경 필요]
대상:    ExecuteRequest(packages/kit/src/types.ts) · 러너 POST /execute · DB service_env · Admin API /api/settings/services 의 envs[]
현재:    앱 파일은 러너 환경값 PLATFORM_APP 하나 — 대상 서버를 바꿔 돌리려면 러너를 다시 켠다
제안:    ExecuteRequest.app?: string(android 만) · service_env.app_path TEXT NULL · envs[] 한 줄 appPath(키가 없으면 유지 · null 이나 빈 글자면 지움)
이유:    2026-10-19 사용자 — 개발 · 운영 서버마다 다른 apk 를 러너를 다시 켜지 않고 돌린다
영향:    contracts(kit · 마이그레이션) · WS-C(러너) · WS-B(정식 실행 · 테스트 실행) · WS-F · WS-E(설정 저장 · 화면)

- **연결은 Playwright fixture 가 맡는다.** fixture 는 여는 손잡이만 건네고, 본문이 보류(`held`)와 다른 project 건너뛰기를 판정한 뒤 연다.
  fixture 정리가 닫는다 — 통과 · 실패 · 예외 · **Playwright 제한 시간**에도 닫힌다(2026-10-07 실측: 제한 시간을 15초로 끊자 그 자리에서 연결을 지웠다). 연결을 여는 도중에 제한 시간이 끝나도 열리기를 기다렸다가 닫는다. 닫다 실패하면 알리되 판정은 안 덮는다
- webdriverio 는 앱 케이스에서만 불러온다(동적 import) — 브라우저 케이스는 싣지 않는다. 기록 수준은 `warn` 이다 — 러너가 자식 stdout 꼬리를 오류 문장으로 쓰기 때문이다
- 스크린샷은 폰 화면이고 경로 규칙은 브라우저와 같다. 한 장은 약 0.5MB 다(보관 기간은 [1-제품과-구조.md](../공통/1-제품과-구조.md) §1.1 L6)
- **기기 정보** (2026-10-19 APP-F1-05) — 연결을 연 직후 kit 이 모델(`deviceModel`) · Android 판(`platformVersion`)을 연결 응답에서 읽고, 앱 판은 폰에 `dumpsys package <앱>` 을 물어 `versionName` 을 읽는다. 같은 출력에서 빌드 코드(`versionCode`)도 읽어 `appBuild` 에 싣는다 — 실행 빌드 번호와 견준다(도메인/실행 §3.11 「다른 빌드」 · 2026-10-24 GAME-F1-13b).
  앱 판은 Appium 을 **`--allow-insecure=uiautomator2:adb_shell`** 로 켜야 읽힌다 — 아니면 그 칸만 비우고 stderr 에 까닭을 한 줄 남긴 채 케이스는 그대로 돈다.
  디바이스 팜은 팜 저장소가 이 옵션을 열어야 한다(아래 「디바이스 팜 접속 방식」 — 2026-10-22). 연결 응답에 앱 꾸러미 이름(`appPackage`)이 없어도 묻지 않고 비운다.
  결과 첨부(`platform-device`) → 결과 줄 `device` → 러너 응답 → `run_item.device` 로 간다. 증적 쪽 규칙은 [리포팅.md](리포팅.md) §8.4 「증적 문서 머리말」
- **엔진은 케이스의 디바이스 칸에서 읽는다** — `android` 면 Appium, 그 밖은 Playwright. 엔진을 정하는 것은 애플리케이션 종류이고(아래 「애플리케이션 종류 「Android 앱」」 결정 3 — 2026-10-21), 지금은 Android 앱의 엔진이 하나라 디바이스 칸으로 고르는 것과 같다
- **러너가 끊어도 연결을 닫는다 — 연결 번호 파일** (2026-10-07). kit 은 연결이 열린 직후 그 실행의 artifacts 폴더(`artifacts/runs/<runId>/<historyId>/`)에
  `appium-session` 파일(글자 한 줄 = Appium sessionId)을 쓰고, fixture 정리에서 닫은 뒤 지운다. 닫기가 실패하면 파일을 남긴다.
  kit 은 같은 번호를 `appium-session-id` 에도 적고 이 파일은 닫아도 안 지운다 — 팜 증적은 닫힌 연결의 것만 받을 수 있다(아래 「디바이스 팜 접속 방식」 · 2026-10-20 APP-F1-12).
  러너는 android 항목이 **어떻게 끝났든**(정상 · 중단 · 러너 제한 시간) 자식이 닫힌 뒤 그 파일을 찾아, 있으면 `DELETE <PLATFORM_APPIUM_URL>/session/<id>` 를 보내고 지운다 —
  그다음에 admin 에 답한다. 그래야 디바이스 줄의 다음 항목이 깨끗한 디바이스에서 연다. 닫기에는 10초 제한을 둔다 — admin 이 러너를 기다리는 유예(30초) 안에 답해야 부분 결과가 남는다.
  파일 이름과 폴더 계산은 kit 의 것을 러너가 같이 쓴다 — 따로 계산하면 경로가 어긋날 때 아무것도 못 닫고 조용히 넘어간다

**앱 화면 읽기** (2026-10-19 APP-F1-06) — 작성 AI 가 앱 케이스를 쓰려면 폰에 떠 있는 화면의 이름표(content-desc) · 글자 · resource-id 를 봐야 요소 주소를 짐작하지 않는다.
**폰에 닿는 러너가 읽는다.** 기획서 쪽 작성 컨테이너는 이 첫 화면 읽기로는 폰에 닿지 않는다(로그인 뒤 화면은 작성 AI 가 appium-cli 로 팜 폰에 직접 닿는다 — [작성.md](작성.md) §3.6 「앱 화면」 「눌러 가며 읽기」, 2026-10-20). 작성 에이전트의 읽기는 서버 러너가 디바이스 팜의 폰에서 한다 — admin 중계가 팜에서 빈 폰을 잡아 요청의 `udid` 로 넘기고 끝나면 놓는다(2026-10-20 APP-F1-10 · 아래 「디바이스 팜 접속 방식」). 내 PC 에 연결한 기기도 같은 통로로 읽힌다.

```
[계약 변경 필요]
대상:    Runner HTTP — POST /app-screen (새 엔드포인트)
현재:    러너가 폰 화면을 읽어 주는 통로가 없다 — 앱 케이스는 기획서만 보고 요소 주소를 짐작해 썼다
제안:    요청 { app?: 파일 경로, udid?: string } · 응답 200 { screen: string }(줄인 화면 글) · 400 INVALID_REQUEST(app 에 :// · app 이나 udid 가 빈 글자) · 409 RUNNER_BUSY · 500 RUNNER_ERROR(Appium 설정 없음 · 연결 실패)
이유:    2026-10-19 사용자 — 화면을 읽는 도구는 Appium(mobilecli 아님). 읽는 통로를 러너에 두고 작성 AI 는 그 통로만 부른다
영향:    WS-C(러너) · WS-작성(통로를 부르는 쪽)
상태:    반영 완료 (2026-10-19, apps/runner/src/{appScreen,routes}.ts — APP-F1-06)

- **Appium 으로 앱을 한 번 띄워 `GET /session/<번호>/source` 를 받고 닫는다.** 연결 설정은 케이스와 같다 — 환경값 `PLATFORM_APPIUM_URL` · `PLATFORM_APP` · `PLATFORM_DEVICE_UDID`, 요청의 `app` · `udid` 가 환경값보다 앞선다.
  webdriverio 없이 Appium 의 HTTP 주소를 직접 부른다(연결 닫기와 같은 길 — `appSession.ts`). 읽을 때마다 앱을 띄우므로 3~4초 더 걸린다(첫 회 앱 설치는 9.4초)
- **줄인 화면 글이 응답이다.** 첫 줄은 `화면 <폭>x<높이> · 요소 N개`, 다음부터 요소마다 한 줄 — `클래스 text="…" desc="…" id=… 클릭 스크롤 체크됨 꺼짐 [위치]` 중 있는 것만. 이름표도 글자도 id 도 없고 누르지도 못하는 껍데기 요소는 뺀다.
  **비밀번호 칸의 글자는 싣지 않는다.** 실측: 같은 첫 화면이 Appium 원본 78,545자 · 111개인 것이 이 거르기로 줄어든다([plans/2026-10-07-appium-시험.md](../../archive/plans/2026-10-07-appium-시험.md) 「e. 화면 읽기」)
- **돌고 있는 앱 항목이 있으면 409 `RUNNER_BUSY` 다** (admin 디바이스 줄 잠금의 `DEVICE_BUSY` 와 다른 코드다 — 이쪽은 폰이 아니라 러너가 바쁘다는 뜻이고, 두 잠금은 서로를 보지 못한다). 같은 폰에 연결 둘이 겹치면 뒤 연결이 앞 연결을 가로챈다. 러너에 android `/execute` 항목이 도는 중이거나 다른 화면 읽기가 도는 중이면 거절한다 — 기다려 주지 않는다.
  **앱 · 게임 단계가 있는 E2E 시나리오도 센다** — 폰 연결을 쥐고 있다(2026-10-28 E2E-F3-02 · 시나리오 §3.7 결정 16). **브라우저 항목 · 웹만의 E2E 시나리오는 세지 않는다** — 폰을 안 쓴다 (2026-10-20 APP-F1-10 — 앞 판은 `/execute` 항목이 하나라도 돌면 거절했다. 폰 옆 로컬 러너를 전제로 한 규칙이라, 읽기가 서버 러너로 옮긴 뒤로는 웹 정식 실행 · 정기 실행 동안 작성의 앱 화면 읽기가 늘 실패했다). **반대쪽은 막지 않는다** — 화면을 읽는 도중(보통 5~15초)에 android 실행이 들어오면 그 실행이 폰을 가로채 읽기가 실패한다. 작성 에이전트의 읽기는 admin 중계가 **admin 의 폰 잠금을 쥐고** 읽으므로 admin 이 보낸 정식 실행과 서로 막는다([작성.md](작성.md) §7 「앱 화면 통로」). 잠금 밖에서 러너를 직접 부르는 길(손으로 `curl` · 케이스 테스트 실행)은 못 막는다 — 쓰는 사람이 폰을 겹쳐 쓰지 않는다는 약속에 맡긴다
- 제한: 연결 열기 60초 · 화면 받기 30초 · 닫기 10초. 연결을 여는 도중에 시간이 끝나면 Appium 이 뒤늦게 연결을 만들 수 있다 — 기본 60초 뒤에 풀린다(아래 「한계」의 같은 항목)
- **읽은 화면은 기대값이 아니다.** 요소 주소(이름표 · id)를 고르는 데만 쓴다 — 기대값은 사람이 판정한 기획서에서만 온다(CLAUDE.md §3 「playwright-cli」 절과 같은 규칙)

```
[계약 변경 필요]
대상:    작성 에이전트(author 컨테이너의 자식 세션)가 러너 POST /app-screen 에 닿는 길
현재:    자식 세션은 빈 환경이고 author 컨테이너는 admin 하고만 닿는 망이다 — 러너 주소를 알 길도 닿을 길도 없다
제안:    ① admin 이 중계한다 — Admin API `GET /api/authoring/requests/:id/app-screen`(작성 에이전트 전용)을 더하고, 에이전트가 AI 를 띄우기 전에 앱 첫 화면을 받아 자료 폴더 파일과 프롬프트 절로 넘긴다. AI 는 러너에 닿지 않는다(자식 환경 · 작성 망 그대로). ② 러너 주소를 자식에게 넘기는 길은 택하지 않았다 — 로그인 없는 러너를 AI 가 부르게 된다
이유:    2026-10-19 사용자가 ① 을 골랐다. 러너에는 로그인이 없어 닿으면 케이스 실행 · 중단도 부를 수 있다. 전제 — ① 은 admin 이 `LOCAL_RUNNER_URL` 로 그 러너에 닿는 배치(폰을 꽂은 맥의 Docker Desktop)에서만 된다
영향:    WS-작성(서버 라우트 · 에이전트 · 스킬) · WS-F(토큰 통로 허용 목록 · 등급표)
상태:    반영 완료 (2026-10-19, apps/admin/src/authoring/appScreen.ts · auth/routeTable.ts · scripts/authoring-app-screen.ts — APP-F1-08)

**2026-10-20 APP-F1-10 부터 중계는 `LOCAL_RUNNER_URL` 이 아니라 서버 러너(`RUNNER_URL`) + 팜 폰이다** — 위 블록의 「전제」는 걷혔다. 팜(`DEVICE_FARM_URL`)이 없으면 까닭 「디바이스 팜(DEVICE_FARM_URL)이 연결되어 있지 않다」만 돌려준다.

**게임 화면 읽기** (2026-10-23 GAME-F1-10) — 종류 「게임」 애플리케이션의 첫 화면이다. Unity 화면은 Appium 에게 빈 판 하나로만 보여 위 앱 화면 읽기로는 오브젝트 이름이 안 나온다.

- **팜 토큰은 누른 사람 것이 먼저다** (2026-10-29 APP-F1-13 사용자 — 앞 판 「토큰은 서버 몫 하나다」는 2026-10-27 OPS-F4-07 「판단 2 A」) — 인증 켠 팜은 모든 요청에 개인 액세스 토큰(`Authorization: Bearer pat_…`)을 받고, 토큰 주인을 Auth_platform 에 묻는다(OPS-F3-05 부터 팜 `DF_BTS_URL=https://auth.maxihan.com`, 2026-10-27). 그래서 Auth_platform 에서 발급한 토큰이다.
  팜은 폰을 잡은 사람과 연결을 여는 사람이 같아야 받고, 연결이 남긴 영상 · logcat 도 그 사람에게만 준다(남의 것은 404 — 팜 `integration-appium` `artifact()`). 그래서 **한 연결의 잡기 · 붙기 · 닫기 · 놓기 · 늘리기 · 증적 받기는 한 토큰으로 한다**
  - **누른 사람 토큰** — 사람마다 내 메뉴(2026-10-30 앞 이름 계정 메뉴) 「통합계정 토큰」(2026-10-31 BTS-F3-05 앞 이름 「디바이스 팜 토큰」)에 자기 Auth 토큰을 넣는다(`app_user.farm_token` · [인증.md](인증.md) §7 `PUT /api/auth/farm-token`). **사람이 누른 실행이면 그 사람 토큰으로 돈다** — 실행 기록의 시작 방식이 `MANUAL` · `RERUN` · `SINGLE`(한 건 실행 — 2026-10-30, [실행.md](실행.md) §3.2) 이면 `triggered_by` 계정의 토큰, E2E 시험 실행은 누른 사람의 토큰이다. 팜 화면에 그 사람이 쓰는 중으로 뜬다
  - **서버 몫 토큰** — 정기(`SCHEDULED`) · 빌드(`BUILD`) 실행 · 작성 AI · 기기 성능 · 기기 목록, 토큰을 안 넣은 사람이 누른 실행, 그리고 **SSO 를 끈 설치의 모든 실행**(넣고 지우는 통로 · 메뉴가 SSO 설치에만 있어 남은 토큰을 지울 길이 없다)은 `.env` 의 `DEVICE_FARM_TOKEN` 하나로 돈다. compose 가 admin 에는 `DEVICE_FARM_TOKEN` 으로, 서버 러너 · author 에는 `PLATFORM_APPIUM_TOKEN`(appium-cli 와 같은 이름)으로 준다
  - **admin 이 고르고 러너는 받은 것을 쓴다** — admin 이 실행 항목마다(게임은 실행 하나에 한 번) 토큰을 골라 그 토큰으로 폰을 잡고, 누른 사람 토큰이면 `ExecuteRequest.farmToken` · `ScenarioExecuteRequest.farmToken` 에 실어 보낸다. 러너는 그 값이 있으면 자기 `PLATFORM_APPIUM_TOKEN` 대신 케이스 · 시나리오 프로세스에 넘기고, 연결 닫기 · 팜 증적 받기에도 쓴다. 없으면 지금처럼 자기 환경값이다. 실행 도중 사람이 토큰을 바꿔도 이미 잡은 폰은 처음 고른 토큰으로 끝까지 간다
  - **통과 항목 영상 보기도 그 실행의 토큰이다** — admin 이 누를 때마다 그 실행을 누른 사람의 지금 토큰으로 팜에 묻고, 못 받으면(404 · 401 등) 서버 몫 토큰으로 한 번 더 묻는다. 토큰을 넣기 전에 돈 실행은 서버 몫이 주인이고, 그 뒤 폐기 · 기간 끝이면 401 이어서다. 토큰을 못 읽으면(DB 오류) 서버 몫으로 묻고 admin 로그에 남긴다. **토큰을 지우거나 바꾸면 그 사람이 앞서 돌린 실행의 영상은 못 본다** — 러너가 받아 둔 실패 항목 영상은 그대로 뜬다
  - 싣는 곳 — admin 의 폰 잡기 · 놓기 · 늘리기 · 기기 목록 · 통과 항목 영상 보기 · 기기 성능(`apps/admin/src/execution/farm.ts` `팜머리` · 누른 사람 토큰은 `farmToken.ts`) · 러너의 앱 연결 닫기 · 앱/게임 화면 읽기 · 팜 증적 받기 · kit `openApp` · 게임 명령 · 작성 에이전트의 AI 가 남긴 폰 놓기 · 폰에서 서버 두드리기. 작성 AI 의 appium-cli · 게임 작성의 control-cli 는 같은 이름을 스스로 읽는다
  - **토큰이 URL 안 계정보다 앞선다.** WebdriverIO `user` · `key` 는 연결 열기 요청에만 붙어 그 뒤 명령이 401 이 된다. 같이 넘기면 연결 열기 요청의 머리를 Basic 으로 덮어서, 토큰이 있으면 넘기지 않는다
  - 비면 머리를 안 싣는다 — 같은 맥 안의 인증 없는 팜은 지금과 똑같이 돈다
  - **Android 앱 · 게임 케이스(AI 가 쓴 코드)와 작성 AI 가 이 토큰을 읽을 수 있다** — 러너는 android 항목의 케이스 프로세스와 앱 · 게임 단계가 있는 시나리오 프로세스에만 토큰을 넘기고(웹 · API 케이스 · 웹만의 시나리오에는 뺀다 — 시나리오는 2026-10-28 결정 16), 작성 에이전트는 자식 세션에 환경을 통째로 준다. **새면 팜과 BTS 를 토큰 주인 이름으로 쓸 수 있다** — 팜은 폰 잡기 · 놓기 · 앱 설치, 팜이 열면 adb 명령(`uiautomator2:adb_shell`)까지. **무엇이 종류마다 다른지의 정본은 이 소절의 종류 표다** — 다른 장은 여기를 가리킨다. 사이드바 · 헤더 모양은 [5-화면공통.md](../공통/5-화면공통.md) §8 「자리 목록」 · 「껍데기」가 맡는다.

#### API 케이스 실행 — 인증 · 응답 모양 (2026-10-20 · API-F1-01)

**무엇을 왜 하는지는 [API.md](API.md) §3.8 이 정본이다.** 여기는 러너가 무엇을 받아 kit 에 어떻게 넘기는지만 적는다.

- `ExecuteRequest` 에 두 칸이 는다(공통/3-공유계약 「API 테스트 타입」) — `apiAuths`(그 대상 서버 줄의 API 인증 전부, 비밀값 원문) · `apiDoc`(케이스가 만들어진 판 원문). admin 은 종류 「API」 애플리케이션 케이스에만 싣는다
- 게임 항목은 `engine` · `udid` · `adminKey` 를 환경변수 셋으로 넘긴다 — `PLATFORM_ENGINE`(`GAME` 또는 빈 값) · `PLATFORM_GAME_LINK`(udid 가 있으면 `farm`, 없으면 `usb`, 게임이 아니면 빈 값) · `PLATFORM_ADMIN_KEY`(JSON, 없으면 빈 값). 셋 다 늘 적는다 — 러너를 켠 셸의 값을 자식이 물려받지 않게(2026-10-23 GAME-F1-09 — 꼴은 [공통/3](../공통/3-공유계약.md) 「게임 테스트 타입」)
- 러너는 `apiAuths` 를 환경변수 `PLATFORM_API_AUTHS`(JSON)로, `apiDoc.doc` 을 항목 폴더(`artifacts/runs/{runId}/{historyId}/api-doc-<출력 이름>.json` — 시험 실행은 runId 가 0 이라 두 실행이 한 이름을 쓰지 않게 출력 폴더 이름을 붙인다)에 써서 그 경로를 `PLATFORM_API_DOC_FILE` 로 넘긴다 — 판 원문은 수 MB 라 환경값 한 칸에 안 든다. 항목이 끝나면 그 파일을 지운다(사진처럼 남길 것이 아니다)
- **본문 상한을 16MB 로 올린다** — 판 원문이 5MB 까지라 러너의 지금 상한(Fastify 기본 1MiB)이면 413 이 난다. `/execute` · `/execute-scenario` 둘 다. 한계 — 서로 다른 큰 판을 셋 넘게 섞은 시나리오는 넘을 수 있고 그때는 413 으로 그 실행이 실패한다. 생기면 판을 파일로 넘기는 길로 올린다
- **토큰을 받고 응답을 견주는 것은 kit 이다** — 러너는 값을 넘기기만 한다. 러너가 토큰을 들면 만료 처리가 두 곳으로 갈린다(API.md §3.8 「API 인증」)
- 러너 입구는 `apiAuths` 의 칸 모양(이름 1~20자 · 주소 · 아이디 · 비밀값 글자)과 `apiDoc.version` 이 1 이상 정수인지 · `apiDoc.doc` 이 JSON 객체인지만 본다. 틀리면 400 `INVALID_REQUEST`
- **E2E** — `POST /execute-scenario` 의 케이스 부품에도 같은 두 칸이 부품마다 붙는다. 그 부품 케이스의 애플리케이션 · 짝지은 대상 서버의 인증이다(시나리오 §3.7 결정 13).
  시나리오는 한 프로세스라 환경값 한 칸으로 못 나눈다 — **부품마다의 인증은 조립 목록(`PLATFORM_SCENARIO`)의 그 부품 줄에 싣고, 판 원문은 `artifacts/runs/{runId}/scenario/api-doc-<부품 순번>.json`(시험 실행은 `runs/trial/<trialId>/`)에 써서 부품 줄에 경로(`apiDocFile`)를 싣는다.**
  kit 은 부품이 바뀔 때마다 받은 토큰과 읽은 판을 버리고 그 부품 값으로 새로 받는다 — 앞 부품 애플리케이션의 토큰으로 다음 부품 서버를 부르지 않게. 파일은 시나리오가 끝나면 지운다

```
[계약 변경 필요]
대상:    Runner HTTP — POST /execute 의 ExecuteRequest(apiAuths · apiDoc) · POST /execute-scenario 케이스 부품의 같은 두 칸 · 본문 상한 16MB · 자식 프로세스 환경값 PLATFORM_API_AUTHS · PLATFORM_API_DOC_FILE

#### 러너 토큰 · 파일 내주기 (2026-10-27 · OPS-F5-10)

admin 이 클라우드 서버로 가고 러너는 서버 · 맥 어느 쪽이든 설정으로 고르게 된 뒤의 두 장치다 — 사용자(2026-10-27) 「서버/로컬에서 할지 옵션화 할 수 있을까? 나중에 또 코드 수정하지 않게」.
맥 러너를 서버에 잇는 터널 · 받는 주소는 [공통/6-인프라](../공통/6-인프라.md) §9.2 「내 컴퓨터 러너」의 「admin 이 다른 기계에 있을 때」가 정본이다.

- **토큰** — 러너가 `RUNNER_TOKEN` 을 받으면 `GET /health` 밖의 요청은 `Authorization: Bearer <토큰>` 이 맞아야 받는다. 틀리거나 없으면 401 `UNAUTHORIZED` 다.
  비면 지금처럼 묻지 않는다 — 옆 `runner` 컨테이너는 바깥 포트가 없어 compose 망 안에서만 닿는다. **터널로 이은 러너는 꼭 건다** — 서버의 다른 앱 컨테이너도 터널 끝(Docker 다리 주소)에 닿는다.
  admin 은 같은 이름의 값 하나를 모든 러너 호출(실행 · 시나리오 · 중단 · 진행 · 앱 · 게임 화면 · 기기 측정 · 파일)에 싣는다(`apps/admin/src/execution/runnerAddr.ts` 의 `러너머리`). `/health` 를 비워 둔 것은 아래 잠자기 확인과 사람의 손 확인(SETUP 의 `wget`)이 토큰 없이 묻게 하려는 것이다 — 이 통로는 판 번호만 낸다. 터널 스크립트는 거꾸로 토큰 없이 `/progress` 를 불러 401 이 오는지로 토큰 건 러너인지 본다
- **파일 내주기** — `GET /files` 는 러너의 `PLATFORM_ARTIFACTS_DIR` 에서 `runs/`(실행 산출물) · `perf/`(기기 녹화) · `perf-record/`(녹화 실행 HAR) 아래만 내준다(러너가 쓰는 자리. 증적 문서 · 빌드 · 작성 자료는 admin 의 것이다). 이 목록은 러너 `remote.ts` 와 admin `artifactFile.ts` 에 한 벌씩 있다 — 하나를 고치면 다른 하나도 고친다.
  케이스가 root 로 돌아 볼륨에 바로가기를 걸 수 있어 **가는 길에 바로가기가 하나라도 끼면 404** 다 — 따라가면 러너의 `/proc/self/environ`(토큰 · 비밀값)이 나간다. admin 의 `볼륨파일` 과 같은 기준이다.
  admin 은 자기 볼륨에 없을 때만 부르고 받은 것을 남긴다(공통/3 §5.3 「러너 여러 대」). 길이(`content-length`)가 없거나 512MB 를 넘으면 받지 않는다.
  폴더 목록(`dir`)이 크기를 같이 내는 것은 admin 이 목록만 그리려고 영상을 통째로 받지 않게 하려는 것이다
- **잠자기 확인** — 맥이 잠들면 서버 쪽 터널 끝(sshd)이 연결은 받고 답을 안 줘, 끝나야 머리를 보내는 `/execute` · `/execute-scenario` 가 `timeoutMs + 30초` 까지 매달린다.
  admin 은 이 둘을 보내기 전에 `GET /health` 를 **2초** 안에 묻고, 답이 없으면 보내지 않고 「러너에 닿지 못했습니다」(원문은 접힌 자리 — 실행 §8.3)로 접는다. 무슨 상태 코드든 답하면 깨어 있는 것으로 친다 — 고장은 응답이 가린다.
  파일 받기 · 폴더 목록도 같은 확인을 먼저 하고, 답이 없던 러너는 30초 동안 다시 묻지 않는다(사진 여러 장을 열 때 2초씩 쌓이지 않게).
  실행 · 시나리오 보내기는 매번 새로 묻는다. 진행은 이미 3초 제한이 있어 따로 묻지 않는다. 앱 · 게임 화면 읽기(작성 중 한 번)는 묻지 않고 제 제한 시간(110 · 260초)까지 기다린다 — 정식 실행 러너를 맥으로 돌린 채 맥이 잠들었을 때만 걸린다

```
[계약 변경 필요]
대상:    러너 HTTP — GET /files(path · dir) 신설 · RUNNER_TOKEN 머리(401) · 환경변수 admin · runner RUNNER_TOKEN · admin RUNNER_URL 을 .env 로
현재:    러너는 로그인이 없고 admin 과 같은 볼륨을 본다는 전제라 파일을 내주는 통로가 없다. compose 는 RUNNER_URL 을 http://runner:4000 으로 박았다
제안:    위 세 장치. 러너가 admin 옆이면 지금과 똑같이 돈다(토큰을 안 걸면 묻지 않고, 볼륨에 있으면 받으러 가지 않는다)
이유:    OPS-F5-10 — 클라우드 admin 이 터널로 이은 맥 러너를 쓴다. 2026-10-27 사용자 시작 질문 승인(GET /files · 토큰 · 받는 주소 172.17.0.1:14001 · 창 뜨는 러너는 npm)
영향:    WS-C(러너 — remote.ts) · WS-B(admin — runnerAddr.ts · runner.ts · artifactFile.ts · farmEvidence.ts) · perf(deviceRecorder · devices · record) · authoring(appScreen) · COMPOSE · SETUP §10

#### 내 컴퓨터 러너 (2026-09-30)

**무엇을 왜 하는지는 [실행.md](실행.md) §7 「케이스 테스트 실행」이 정본이다** (계약 블록도 거기 있다). 여기는 러너가 받는 설정만 적는다.
같은 러너 코드를 **창이 뜨는 모드로 한 벌 더 띄우는 것**이라 케이스 테스트 실행에는 새 엔드포인트가 없다 — admin 이 `POST /execute` 를 부른다. 기기 성능 직접 플레이의 통로 넷은 아래 「성능 테스트 — 녹화 실행 · 기기 측정」이다(2026-10-22 PERF-F1-08).
**E2E 시험 실행도 이 러너가 켜져 있으면 여기로 온다**(`POST /execute-scenario` — 정본은 [시나리오.md](시나리오.md) §7 「시험 실행 규칙」, 2026-10-17).

- **`PLATFORM_HEADED=1` 이면 브라우저 창이 뜬다(headed)** — 없으면 지금처럼 창 없이(headless) 돈다.
  값을 자식 프로세스 설정(`playwright.config.ts`)이 읽는다. 기본 러너(컨테이너)는 이 값을 안 준다
- **이 값이 `1` 인 러너는 E2E 시험 실행(`runId: null`)의 자식에만 `PLATFORM_SLOW_MO=1000` 을 준다** (2026-10-17) — 설정이 `launchOptions.slowMo` 로 읽어 동작마다 1초 쉬고,
  시나리오 전용 설정은 부품 한도를 다섯 배로 늘린다. 진짜 실행 · 케이스 테스트 실행 · 창 없는 러너는 늦추지 않는다
- **`HOST` 는 러너가 받는 주소(listen)다.** 기본은 `0.0.0.0` 이라 컨테이너에서 admin 이 닿는다. 내 컴퓨터용은 `127.0.0.1` 로 좁힌다 —
  **러너에는 로그인이 없어서** 같은 망의 다른 기계가 부르면 인증을 건너뛰고 테스트를 돌릴 수 있다 (공통/6-인프라 §9 · 인증 §3.5 가 컨테이너 러너의 포트를 닫는 이유와 같다).
  `RUNNER_TOKEN` 을 주면 토큰 없는 요청을 거절한다(위 「러너 토큰 · 파일 내주기」) — 터널로 클라우드 admin 에 이을 때는 꼭 준다. `npm run runner:local` 은 셸의 값을 그대로 넘긴다
- 루트 `npm run runner:local` 이 `PLATFORM_HEADED=1 HOST=127.0.0.1 PORT=4001 PLATFORM_TESTS_DIR=./tests …` 를 한 줄로 묶는다. 켜는 절차는 SETUP.md 「내 컴퓨터 러너 켜는 법」이 정본이다
- 무상태 규칙(§3.4)은 그대로다 — DB 를 모르고 판정·기록은 admin 만 쓴다. 이 러너가 만든 결과는 admin 이 기록 없이 메모리에만 둔다
  (2026-10-07 부터 Android 앱 정식 실행만 이 러너의 결과를 기록에 남기던 예외는 2026-10-20 APP-F1-10 에 걷었다 — 정식 실행은 서버 러너 + 디바이스 팜이다)
- `npm run runner:local` 은 `PLATFORM_APPIUM_URL=http://127.0.0.1:4723` 도 싣는다 (2026-10-07). **`PLATFORM_APP` 은 싣지 않는다 — 켤 때 사람이 apk 경로를 주거나 대상 서버 줄의 「앱 파일 경로」를 채운다** (위 「앱 실행」).
  같은 맥에 디바이스 팜이 4723 으로 떠 있으면 이 주소가 곧 팜이다 — 케이스 테스트 실행 전에 팜 화면에서 「쓰기」로 폰을 잡는다(위 「디바이스 팜 접속 방식」)

#### 성능 테스트 — 녹화 실행 · 기기 측정 (2026-10-21 · PERF-F1-01 · 대기)

**무엇을 왜 하는지는 [성능.md](성능.md) §3.9 가 정본이다.** 여기는 러너 · 디바이스 팜 · 내 컴퓨터 러너가 무엇을 받고 무엇을 남기는지만 적는다.
**부하는 러너가 걸지 않는다** — 부하 발생 에이전트가 건다(성능 §5.4). 러너와 같은 기계에서 부하를 걸면 기능 테스트가 느려지고 측정값이 흔들린다.

- **녹화 실행** (2026-10-21 PERF-F1-04 반영 — 아래 블록의 나머지는 기기 측정 PERF-F1-08) — `ExecuteRequest.recordHar`(공통/3-공유계약 「성능 테스트 타입」 — `{ jobId }`)가 오면 러너가 `artifacts/perf-record/<jobId>/` 를 만들고, 브라우저 연결이 HAR 를 `<차례>.har` 로 바로 쓴다.
  케이스는 자식 환경 `PLATFORM_RECORD_HAR`(파일 경로)를 루트 `playwright.config.ts` 가 `contextOptions.recordHar` 로, 시나리오는 `PLATFORM_RECORD_HAR_DIR`(폴더)를 `scenario/window.ts` 가 창마다 받는다. HAR 는 창을 닫을 때 써져서 창 여럿이 열려 있어도 번호가 겹치지 않게 직전에 준 번호를 넘긴다.
  두 환경값은 녹화가 아닐 때도 빈 값으로 늘 싣는다 — 러너를 켠 셸에 값이 있으면 모든 실행이 녹화된다.
  녹화는 서버 러너(`RUNNER_URL`)로만 돈다 — HAR 가 admin 이 읽는 산출물 폴더에 떨어져야 해서 내 컴퓨터 러너가 켜져 있어도 쓰지 않는다. `RUNNER_URL` 을 터널로 이은 맥으로 바꿨으면 admin 이 `perf-record/` 를 그 러너에서 받아 온다(2026-10-27 · 아래 「러너 토큰 · 파일 내주기」). 기능 테스트와 같은 실행 줄의 한 자리를 쓴다.
  기록 · 증적에 안 남는다 — 케이스는 runId 0(케이스 테스트 실행과 같은 꼴), 시나리오는 runId null(시험 실행과 같은 꼴)이다. admin 이 비밀번호 · 토큰을 가려 AI 일에 넘기고 가리기 전 원본은 지운다
- **한 줄 꼴** — 팜 · 내 컴퓨터 러너 둘 다 `{ sec, fps, jankPct, freezeCount, cpu, memMb, tempC, batteryPct }` 다(못 읽은 칸은 null · `sec` 는 정수 · `memMb` · `freezeCount` 는 정수 — 표 칸이 정수라 admin 이 소수를 받으면 반올림한다). `sec` 는 그 기기의 측정을 켠 때부터의 초다 — admin 이 실행 기준 초로 옮긴다(2026-10-21 PERF-F1-08).
  `freezeCount` 는 그 간격에 그리는 데 0.7초 넘게 걸린 프레임(프리징) 수다(2026-10-31 WEB-F7-26). 팜이 아직 안 싣으면 admin 이 null 로 받는다
- **기기 측정 — 팜 폰** — 팜이 잡기(hold) 동안 1초 측정값 파일 `perf-metrics.jsonl` 과 화면 녹화를 남긴다. 켜는 길은 잡기 요청의 `perf: { package, intervalSec, record }` 다 — 팜이 그 앱의 CPU · 메모리를 읽고 실행 시간을 재야 해서 앱 이름이 든다(2026-10-21 PERF-F1-08 시작 질문 — 앞 판은 `perf: true`).
  폰을 잡고 놓는 것이 admin 이라(위 「디바이스 팜 접속 방식」) 측정값도 admin 이 폰 번호로 받는다 — 실행 중에는 5초마다 `GET /api/devices/{serial}/perf?since=<sec>` → `{ rows, launchMs }`(`since` 보다 큰 초만 · `launchMs` 는 못 쟀으면 null)로 새 줄만 받고,
  놓기 직전 `GET /api/devices/{serial}/perf/files` → `{ files: [{ name, bytes }] }` 의 녹화 조각(`rec-<시작 초>.mp4`)을 `GET /api/devices/{serial}/perf/files/{name}` 으로 `artifacts/perf/<runId>/<serial>/` 에 받는다.
  통과 못 한 항목만 러너가 연결 번호로 받는 지금의 팜 증적 길(`farmArtifacts`)과 다른 길이다. 직접 플레이도 이 길이다 — 사람이 팜 PC 에 꽂힌 폰을 손에 든다(회사 서버 설치에서도 된다).
  **팜 쪽은 Devicefarm 저장소가 고칠 일이다** — 그쪽 문서가 정본이 되고 여기는 우리가 기대하는 모양만 적는다. 팜의 기기별 Appium 이 `adb_shell` 을 열든 말든(위 「디바이스 팜 접속 방식」) 팜 PC 가 직접 adb 로 읽으니 상관없다.
  admin 쪽은 PERF-F1-08 이 이 모양대로 붙였다(`apps/admin/src/perf/deviceRun.ts`) — 팜이 이 통로를 열기 전에는 팜 폰 측정이 실행 로그에 「디바이스 팜이 측정값을 주지 않았습니다」를 한 번 남기고 30초 뒤 중단(`AGENT_LOST`)된다. 팜이 잡기의 `perf` 를 거절하면 「디바이스 팜이 폰을 내주지 않았습니다」 오류로 끝난다
- **기기 측정 — 내 컴퓨터 러너(직접 플레이)** — 새 통로 넷(2026-10-21 PERF-F1-08 — `apps/runner/src/perfDevice.ts`). `GET /perf/devices` → `{ devices: [{ serial, model, os }] }`(adb 에 붙은 폰) · `POST /perf/device/start { runId, serial, package, intervalSec, record }` → `{ recId }` · `GET /perf/device/:recId?since=<sec>` → `{ rows, launchMs }` · `POST /perf/device/:recId/stop` → `{ files }`(녹화 파일 이름 목록).
  러너가 adb 로 읽고, 녹화는 `adb shell screenrecord` 3분 조각을 이어 받는다. 파일은 `artifacts/perf/<runId>/<serial>/` 에 둔다(측정값 `perf-metrics.jsonl` · 녹화 `rec-<시작 초>.mp4`) — compose 와 같은 checkout 의 `./artifacts` 면 admin 이 바로 읽고, 아니면 측정을 멈출 때 그 러너에서 받아 온다(2026-10-27 · 공통/6-인프라 「내 컴퓨터 러너」 `PLATFORM_ARTIFACTS_VOLUME`).
  `sec` 는 시계로 센다 — 읽기가 간격보다 오래 걸려 한 번 건너뛰면 초가 그만큼 뛴다. 2분 넘게 아무도 새 줄을 받아 가지 않으면(admin 이 다시 켜져 이 기록기를 잊었다) 기록기가 스스로 멈추고 폰을 푼다. 통로는 서버 러너에도 걸리지만 그 컨테이너에는 adb 가 없어 폰 목록이 늘 비어 있다.
  그 앱이 폰에 없으면 시작이 400 `INVALID_REQUEST`, 폰이 adb 에 없으면 404 `DEVICE_NOT_FOUND` 다. 같은 폰을 이미 재고 있으면 409 `DEVICE_BUSY` 다. 모르는 `recId` 는 404 다.
  서버와 사람 기계가 같은 설치에서만 쓰는 길이다 — 회사 서버 설치는 내 컴퓨터 러너가 꺼져 있어 위 팜 폰 길을 쓴다
- **Android 에서 읽는 곳** — FPS · 프레임 드랍은 `dumpsys gfxinfo <앱>` 의 렌더링한 프레임 · 끊긴 프레임 수를 간격마다 빼서 세고, 그 값이 0 이면(게임 · SurfaceView) `dumpsys SurfaceFlinger --latency` 의 그 앱 층 프레임 시각으로 센다 — 이 길은 FPS 만 세고 프레임 드랍률은 null 이다. 프리징은 같은 `gfxinfo` 의 프레임 시간 막대(`HISTOGRAM:` 줄 — `GPU HISTOGRAM` 은 아니다)에서 700ms 칸부터 그 위 칸의 수를 더해 간격마다 뺀다(150ms 위 칸 이름은 50ms 칸의 아래 끝이라 700ms 칸이 700~749ms 다) — 0.7초 넘게 걸린 프레임은 Android 가 정지된 프레임(frozen frame)으로 세는 기준이다. gfxinfo 로 한 프레임도 안 그린 앱(게임 · SurfaceView)은 null 이다 — SurfaceFlinger 표시 시각 사이는 가만히 있는 것과 굳은 것을 못 가른다(2026-10-31 WEB-F7-26). CPU 는 `/proc/<pid>/stat` 와 `/proc/stat` 의 차이(전체 코어 기준 %), 메모리는 `dumpsys meminfo <앱>` 의 TOTAL PSS, 온도 · 배터리는 `dumpsys battery`(온도는 0.1°C 단위)다
- **게임 항목 FPS** (2026-10-31 WEB-F7-25) — 게임 정식 실행 항목(`engine: 'GAME'` · `runId` > 0)이 도는 동안 러너가 1초마다 위 「Android 에서 읽는 곳」의 SurfaceFlinger 프레임 시각 셈(`perfRead.ts` `표시프레임으로`)을 돌려 `ExecuteResponse.fps` 에 싣는다. 테스트 실행(runId 0)은 기록이 안 남아 안 잰다.
  서버 러너는 팜 폰에 adb 로 닿지 못해 케이스가 연 Appium 연결(kit 의 번호 파일 `appium-session`)에 `mobile: shell` 로 묻는다 — 팜의 기기별 Appium 은 `uiautomator2:adb_shell` 을 연다(위 「디바이스 팜 접속 방식」). 앱 층은 `mobile: getCurrentPackage` 로 앞에 뜬 앱 이름을 찾는다.
  줄마다 그때 돌던 절차 번호(`seq` — 진행 줄의 마지막 것)를 붙이고, 첫 절차 전(앱을 켜는 동안)이나 번호 파일이 없는 초는 안 남긴다. 못 읽은 초는 `fps: null` 이고 까닭은 항목마다 한 번만 알린다. 하나도 못 읽었으면 칸을 안 싣는다. 게임은 SurfaceView 라 gfxinfo 는 묻지 않는다 — 케이스와 같은 연결이라(Appium 은 연결마다 명령을 하나씩 받는다) 층을 찾은 뒤에는 1초에 한 번만 묻는다. 묻기 하나는 5초에서 끊고, 앞 묻기가 안 끝났으면 그 초를 건너뛰며, 케이스가 끝나면 도는 묻기를 끊는다
- **앱 실행 시간** — 기록기가 측정을 켤 때 앱을 멈추고(`am force-stop`) `am start -W` 의 TotalTime 을 한 번 잰다 — 콜드 스타트다. Appium 케이스는 연결이 앱을 다시 깔고 띄우고 게임 케이스는 깐 앱을 다시 켜므로([게임.md](게임.md) §3.10 「게임 연결」) 팜이 첫 실행 때 잰다
- **여러 기기 나란히** — 기기 성능 실행은 기기마다 연결을 하나씩 동시에 연다(상한 5대). 위 「디바이스 줄은 그대로 하나다」는 기능 테스트 실행의 규칙이고 기기 성능 실행은 따로 센다
- 판정 · 저장은 그대로 admin 만 한다(§3.4)
