#### 게임 연결 — 디바이스 팜 · USB (결정 12)

| | 정식 실행 · 작성 AI | 테스트 실행 |
|---|---|---|
| 폰 | 디바이스 팜 폰 — 지금처럼 빈 폰 하나를 잡는다(`apps/admin/src/execution/farm.ts`) | 디바이스 팜 폰 — 정식 실행과 같다(`apps/admin/src/execution/trialRoutes.ts`). **2026-11-03 TMO-F3-02 부터다**(도메인/실행 §3.2 「테스트 모드」) — 앞 판은 내 컴퓨터 러너(`LOCAL_RUNNER_URL`)에 USB 로 꽂은 폰이었다 |
| 게임에 닿는 길 | kit · CLI 가 팜의 게임 명령 주소 `POST /api/devices/{serial}/game` 으로 보낸다 — 본문은 게임 명령 JSON 하나, 답은 `{"value": <게임 답 그대로>}`(게임이 `ok:false` 여도 200). 오류도 `value` 에 `{error, message}` 로 와서 성공과 오류는 HTTP 코드로 가른다 — 게임에 못 닿음 · 15초 안에 답 없음 502 · 잡은 사람이 아님 · 폰 다시 켜는 중 409 · 본문이 JSON 객체가 아님 400 · 415 · 501(표는 안내서 7절). 팜이 명령마다 `adb forward` 를 걸고 답을 받으면 지운다 · 잡은 사람만 · 그 사람의 자동 테스트 중에도 받는다. 정본은 Devicefarm 안내서 `docs/guides/test-platform.md` 12절 | 왼쪽 칸과 같다(2026-11-03 TMO-F3-02 — 앞 판은 내 컴퓨터 러너가 꽂힌 폰에 직접 `adb forward` 를 걸고 TCP 로 보냈다) |
| 화면 영상 · logcat | 팜이 남긴다(지금 앱과 같다) | 없다(앱과 같다) |

- **설치는 Appium 이, 실행은 kit 이 한다** — 지금 앱 케이스 길 그대로 Appium 이 앱 파일(대상 서버 줄의 `app_path`)을 깔고 kit `앱을켠다`가 켠 뒤(러너.md §5.2 「앱 켜기」) kit 이 게임 포트에 붙는다. 스크린샷 · 기기 정보(`DeviceInfo`)도 Appium 세션에서 그대로 받는다
- **게임은 실행 하나 동안 폰을 한 번 잡고 한 번 깐다** — 앱은 항목마다 잡고 놓아(놓을 때 정리가 앱을 지운다 — `apps/admin/src/execution/farm.ts`) 항목마다 다시 깐다. 게임은 APK 가 크고 켜는 데 오래 걸려, 항목 사이엔 앱만 다시 켜고 상태는 어드민 API 로 맞춘다. 첫 실행 상태가 필요한 케이스(튜토리얼)만 앱 데이터를 지운다 — **표시할 칸이 아직 없어 1차에는 모든 항목이 데이터를 둔다**(2026-10-23 GAME-F1-09 시작 질문 승인 — 칸은 튜토리얼 케이스가 나올 때 계약으로 더한다).
  **붙인 모양 (2026-10-23 GAME-F1-09)** — admin 이 게임 실행의 android 항목을 한 줄로 모아 디바이스 줄 차례 하나 안에서 빈 폰을 **120분** 잡고, 항목마다 보내기 전에 늘리기(`/hold/extend` — 끝나기 10분 전부터 30분, 그 전이면 팜이 409 로 거절해 그냥 넘긴다)를 부른 뒤 같은 폰 번호로 차례로 보낸다. 다 돌면 한 번 놓는다(`apps/admin/src/execution/dispatcher.ts` · `farm.ts`). 항목마다 Appium 연결만 새로 연다 — kit 이 게임 항목 연결을 `noReset` · `shouldTerminateApp` 으로 열고 켜기 전에 앱을 끄고 켜서(러너.md §5.2 「앱 켜기」 — 2026-11-16 까지는 `forceAppLaunch`) 한 번 깐 앱을 데이터째 두고 다시 켠다(`packages/kit/src/runtime/app.ts`)
  **아직 못 막는 것 (2026-10-25 GAME-F2-15)** — `noReset` 이면 Appium 이 같은 패키지가 깔린 폰에는 넘긴 APK 를 판을 견주지 않고 안 깐다. 잡은 폰에 같은 게임의 다른 판이 남아 있으면(팜에 처음 등록할 때부터 있던 패키지와 그 위에 덮어 깐 빌드는 놓을 때 지우지 않는다 — Devicefarm 안내서 11절 「앱 설치」. 10-24 의 0.1.25 처럼 잡기 밖에서 깐 판도 남아 있었다) 첫 항목도 그 판을 켜고, 실행은 넘긴 빌드가 아닌 그 판을 돈다. 게임 화면 읽기는 `noReset` 을 끄고 `enforceAppInstall` 을 켜서 막았다 — 끄기만 하면 깔린 판이 같거나 높을 때 또 안 깐다([러너.md](러너.md) §5.2 「게임 화면 읽기」). 실행 쪽은 admin 이 첫 항목을 러너에 알려야 해서 러너 요청 칸(계약)이 바뀐다 — 시작 질문(2026-10-25)에서 이번 줄 밖으로 뒀다
  **지금 잡는 규칙(항목마다 — [실행.md](실행.md) §3.2 「디바이스 줄」)이 바뀌는 자리다** — 회귀 실행 하나가 폰을 몇 시간 쥘 수 있어, 그동안 작성의 폰 잡기는 기다리지 않고 「폰이 다른 실행에 쓰이는 중이다」를 받는다(지금 앱 화면 읽기와 같다). 이 거절은 빈 폰만 고르는 QA Hub 쪽이 한다 — 작성은 서버 몫 토큰으로 붙어(`farm.ts` `팜머리` — [러너.md](러너.md) §5.2 「디바이스 팜 접속 방식」 「팜 토큰은 누른 사람 것이 먼저다」 · 2026-10-27. 그 전에는 토큰 없이 붙었다) 팜의 「잡은 사람만」은 토큰을 안 넣은 사람의 정식 실행과 작성을 한 사람으로 본다. 2026-10-29 부터 사람이 누른 실행은 그 사람 이름이라(2026-11-04 S25 부터 Auth 대신 PAT — Auth 에 안 묶인 계정은 서버 몫) 팜이 가른다. 팜 폰이 한 대인 동안의 한계다. 아래 §7 블록이 잡는 단위를 같이 바꾼다
- **작성 중 폰 잡기** — 훑기 · 눌러 보기 · 돌려 보기 단계마다 잡고 놓는다. appium-cli 처럼 한 번에 30분을 넘겨 쥐지 않는다 — 그 사이 정식 실행이 폰을 쓴다. 그래서 30분이 넘는 게임 시나리오는 작성 중에 끝까지 못 돌려 본다(아래 「1차 밖 · 나중」).
  놓은 직후 다시 잡으면 팜이 정리하는 2~4초 동안 빈 폰이 아니다 — control-cli `hold`(v0.1.1 · 2026-10-25 GAME-F2-15)는 정리 중(`cleaning`)인 폰이 있을 때만 20초까지 기다리고, 없으면 바로 「다른 실행에 쓰이는 중」으로, 한도를 넘기면 「팜이 정리하는 중」으로 거절한다. QA Hub 폰 잡기(`apps/admin/src/execution/farm.ts`)와 같은 규칙이다
- 게임 포트는 폰 안 `127.0.0.1` 에만 연다 — 같은 와이파이의 다른 기기가 QA 빌드를 조작하지 못한다
- **명령 하나는 15초 안에 끝난다** — 팜이 15초에 502 로 끊고, SDK 는 10초에 스스로 「답하지 않았다」를 준다. 「뜰 때까지 기다리기」는 짧은 명령을 되풀이하는 꼴이어야 두 길(디바이스 팜 · USB)이 같게 돈다 — 게임 드라이버 `waitFor` 가 0.3초마다 `find` 를 보낸다(GAME-F1-06 · kit 도 같은 드라이버를 쓴다 — GAME-F1-09)

#### 윈도우 PC — VISION 기기 (결정 26 ~ 28 · 2026-11-19 · 진행판 GAME-F4)

**PC 게임은 따로 등록한 애플리케이션이다** (결정 27 · 2026-11-19 기획 대화 — GAME-F4-04 가 고쳐 썼다). 애플리케이션 표에 게임 플랫폼 칸(`service.game_platform` — `android` 모바일 게임 · `windows` PC 게임)과 지원 패드 칸(`service.game_pads`)이 있다([공통/4](../공통/4-데이터모델.md) 「게임 애플리케이션 플랫폼」).

- **등록** — 종류 카드 「모바일 게임」 · 「PC 게임」이 둘 다 종류 `GAME` 을 만들고 플랫폼만 다르다. 만든 뒤에는 플랫폼을 못 바꾼다(종류와 같은 규칙 — [인증.md](인증.md) §7 설정 API). 2026-11-19 에 등록된 게임은 전부 모바일이라 마이그레이션이 `android` 로 채운다
- **지원 패드** — 「새 작성」 첫 단계(가이드가 비었으면 「애플리케이션 정보 입력」 · 있으면 「가이드 확인」)의 맨 위에 PC 게임에만 PS5 · PS4 · Switch · Xbox 체크가 선다 — 가이드 세 칸 아래면 스크롤해야 보여 지나친다(2026-11-20 시안). 확인 단계 요약에 「지원 패드 PS5 · Xbox」(다 풀었으면 「없음 — 키보드만」) 줄이 선다. 작성을 시작하면 서버가 애플리케이션에 남기고 다음 작성 때 그 체크를 채워 연다. 작성 AI 는 이 목록을 받아 버튼 그림 케이스의 선언에 쓴다([작성.md](작성.md) §7 claim `gamePads`). 하나도 안 체크하면 패드 케이스가 없다
- **Windows 빌드가 없으면 작성을 시작하지 못한다** — 작성 AI 가 PC 에 깔 빌드가 없어서다. 화면이 막고(GAME-F4-06 — `/auth/me` 의 `latestBuildNo` 가 null 이면 「새 작성」 첫 단계에 빨간 줄로 알리고 시작 단추를 잠근다. 값은 대상 서버를 안 고른 작성이 깔 빌드다 — 운영 줄을 빼고 대상 서버 이름 차례로 빌드가 있는 첫 줄, 작성의 빌드 고르기와 같은 규칙), 통로로 들어온 요청은 에이전트가 AI 를 띄우기 전에 멈춘다 — 게임 첫 화면 통로가 「Windows 빌드가 없다」를 주면 그 까닭으로 FAILED 다(2026-11-20 반영 GAME-F4-07 — 아래 「작성」). 서버 400 은 두지 않는다 — 어느 대상 서버 줄의 빌드를 쓸지는 작성이 정해서다

폰 게임 길에서 Appium 만 빠진다. 폰은 Appium 이 깔고 kit 이 켜지만, PC 는 서버가 VISION 에 zip 을 올려 깔고 kit 이 VISION 에 켜고 끄라고 부탁한다. 게임 명령은 폰과 같은 VISION 게임 명령 주소(`POST /api/devices/{serial}/game` — 위 「게임 연결」 표)로 간다.

| `windows` | Windows | 없음 — 키보드 · 마우스. 가상 패드를 만들지 않는다 |
| `windows-ps5` | Windows · PS5 패드 | PS5 — kit 이 control-cli `Game.pad('ps5')` 로 정한다 |
| `windows-ps4` | Windows · PS4 패드 | PS4 — `Game.pad('ps4')` |
| `windows-switch` | Windows · Switch 패드 | Switch — `Game.pad('switch')` |
| `windows-xbox` | Windows · Xbox 패드 | Xbox — `Game.pad('xbox')` |

- **선언한 값마다 한 항목이다** — 보통 케이스는 `platforms: ['windows']` 로 키보드 · 마우스에서 한 번 돈다. 「연결한 패드의 버튼 그림이 화면에 뜨나」 케이스만 지원 패드 값을 적는다 — 예 `['windows-ps5', 'windows-xbox']` 면 PS5 · Xbox 에서 한 번씩 돈다. 작성 AI 가 애플리케이션의 지원 패드로 적는다(2026-11-20 반영 GAME-F4-07 — `tpx-cases` `game.md` §8)
- **지원 패드에서 뺀 패드는 안 돈다** — 실행 만들기는 선언한 패드 값 가운데 지금 애플리케이션 지원 패드(`game_pads`)에 있는 것만 펼친다. 다음 작성에서 Xbox 체크를 풀면 케이스를 다시 쓰기 전에도 Xbox 항목이 안 생긴다. 스캐너는 지원 패드에 없는 선언 값을 문제 줄로 알린다
- **선언에서 막는 것** — 윈도우 값과 `android` 를 같이 적지 않는다(게임 하나에 플랫폼 하나 — `defineCase` 가 던진다). `desktop` · `mobile` 과도 섞지 않는다. 애플리케이션 플랫폼과 다른 값(모바일 게임의 `windows` · PC 게임의 `android`)은 kit 이 종류를 몰라 스캐너(문제 줄)와 작성 빠른 검사가 짚는다. 사람이 거는 실행은 400 으로 막고 정기 · 빌드 · 배포 신호 실행은 그 항목만 빼고 돈다 — 케이스 하나 때문에 밤 정기 실행 전체가 멈추지 않게(§7 마지막 블록 · [공통/2](../공통/2-명세선언.md) K5 · [실행.md](실행.md) §7 `POST /api/runs`)
- **패드별 결과는 `run_item.platform` 이 가른다** — 새 칸이 없다. 결과 · 실패 분석 · 추적표에서 디바이스마다 칸 · 항목이 하나다. PC 게임 실행에는 윈도우 값만 들고 패드 값은 버튼 그림 케이스에만 있다. **결과 화면은 돈 값마다 칸 하나다**(2026-11-20 GAME-F4-06 시안 — 이 줄이 정본) — 실패 수 꼬리표 · 디바이스 탭 · 실패 카드 칸이 「Windows」 · 「Windows · PS5 패드」 · 「Windows · Xbox 패드」로 서고 브라우저 PC · 모바일 칸은 끼우지 않는다. 웹의 PC · 모바일 칸과 같은 짜임이라 「PS5 만 깨짐」이 한 줄에서 보인다. 좁은 실행 기록 줄만 「Windows ·」를 빼고 「PS5 패드」로 적는다 — 그대로 쓰면 줄이 세로로 세 배 늘었다
- **실행 창에는 패드 칸이 없다** — PC 게임 케이스는 디바이스 「Windows」 하나만 보이고, 서버가 케이스 선언대로 항목을 펼친다(`windows` 는 한 번 · 패드 값은 적힌 패드 가운데 지원 패드에 있는 것마다 — 아래 줄). 정기 · 빌드 실행도 같다. 실패 다시 실행은 원래 항목의 값 그대로다 — PS5 항목만 실패했으면 PS5 만 다시 돈다. 사람이 값 하나하나로 건 항목은 지원 패드를 안 본다
- **시험 실행은 「Windows」 칸이면 선언한 윈도우 값을 하나씩 차례로 보낸다** — 지원 패드로 거른 값이다. 버튼 그림 케이스(`['windows-ps5', 'windows-xbox']`)를 시험하면 PS5 · Xbox 가 차례로 돈다. 시험 통로는 선언한 값 하나만 받는다([실행.md](실행.md) §7 test-run)
- **펼친 항목이 없는 케이스는 빠진다** — 지원 패드를 다 풀어 버튼 그림 케이스의 패드 값이 하나도 안 남으면 그 케이스는 항목 없이 빠진다(다른 디바이스가 맞지 않는 케이스와 같다). 실행 전체에 항목이 없으면 지금처럼 돌릴 케이스가 없다
- **패드 실행은 Unity Input System 을 쓰는 게임만 된다** — 옛 Input Manager · Rewired · Steam Input 게임은 가상 패드를 못 읽는다(control_cli 계획 「먼저 알아 둘 사실」). 키보드 키는 옛 Input Manager 게임도 SDK 의 가짜 `Input` 으로 받는다(결정 2)

**실행 하나의 흐름** — 폰 게임 실행(위 「게임 연결」 「붙인 모양」)과 같은 꼴이다.

1. admin 이 그 실행의 `windows*` 게임 항목을 한 줄로 모아 **PC 줄**에 세운 뒤 VISION 에서 PC 를 **120분** 잡는다 — `POST /api/devices/acquire { minutes: 120, filter: 'platform=windows' }` → `held.serial` · `held.sessionId`. **`platform` 조건이 없으면 VISION 은 폰만 고른다.** 토큰은 폰과 같은 규칙이다(서버 몫은 `DEVICE_FARM_RUN_AS` 대신 PAT — [러너.md](러너.md) §5.2 「디바이스 팜 접속 방식」). VISION 이 빈 PC 가 없다고 거절하면 1분마다 다시 잡아 보고, 120분 동안 못 잡거나 그 밖의 까닭으로 거절되면 그 항목들은 「빈 Windows PC 가 없습니다」(또는 VISION 이 준 까닭)로 미실행이다. 잡기 답을 못 받았으면(끊김 · 제한 시간) 다시 부르지 않고 그 까닭으로 미실행이다 — 다시 부르면 PC 를 하나 더 잡는다(VISION 안내서 4절 · 2026-11-19 사용자). 기다리는 동안 실행을 멈추면 그만둔다
2. admin 이 그 실행에 고정한 빌드(`build_id` — PC 게임의 빌드는 늘 zip 이다)를 VISION 에 한 번 깐다 — `POST /api/devices/{serial}/install`(본문 zip 바이트 · `Content-Type: application/zip`) → 게임 이름. 10분까지 기다린다(VISION 이 1GB 까지 받고 풀기를 5분까지 기다린다). 실패하면 PC 를 놓고 항목들을 그 까닭으로 미실행으로 닫는다. 빌드가 없으면 깔지 않고 「Windows 빌드가 없습니다」로 미실행이다 — 폰처럼 대상 서버 줄의 `app_path` 로 물러서지 않는다
3. 항목마다 보내기 전에 잡기를 늘리고(`/hold/extend` — 폰과 같다) 러너에 `{ platform: 'windows…', udid: <serial>, app: <게임 이름>, engine: 'GAME' }` 을 보낸다. 러너 · kit 은 Appium 세션을 만들지 않는다 — VISION 의 `/wd/hub` 는 PC 에 400 이다. kit 이 앞 항목이 남긴 게임을 `pcStop` 으로 끄고(폰의 「끄고 켜기」와 같다) `pcLaunch` 로 켜고 게임이 ping 에 답할 때까지(120초) 기다린 뒤 패드 값이면 control-cli `Game.pad(<종류>)` 를 한 번 부르고 몸통을 부른다(케이스 몸통의 `game.pad()` 는 읽기만 한다 — 아래 「게임 드라이버에 더하는 것」). 몸통이 어떻게 끝나든 증적을 남긴 뒤 `pcStop` 으로 끈다([러너.md](러너.md) §5.2 「윈도우 PC 게임 항목」)
4. 다 돌면 admin 이 놓는다(`DELETE /api/devices/{serial}/hold`) — VISION 이 자기가 켠 게임을 끄고 Unity 데이터를 지운다. 깐 빌드는 PC 에 남는다(다음 실행이 다시 깔아 덮는다)

- **PC 는 폰 「디바이스 줄」에 서지 않고 따로 선 「PC 줄」에 선다** — 폰 줄에 서면 몇 시간 도는 PC 실행이 폰 테스트를 다 막는다. PC 줄은 관리 서버 메모리의 잠금 하나이고 실행 하나의 PC 항목 묶음이 차례 하나를 쓴다 — 빌드 · 정기 실행은 UI · 기능 실행 둘이 한꺼번에 서서, 기다리지 않으면 PC 한 대인 동안 둘째 실행이 늘 미실행이 되고 스모크가 회귀로 못 넘어간다. 다른 사람 · 다른 서버와의 다툼은 VISION 잡기가 가르고 위 1 처럼 기다린다([실행.md](실행.md) §3.2 「디바이스 줄」). PC 가 여러 대여도 1차에는 하나씩 돈다(아래 「1차 밖 · 나중」)
- **PC 한 대는 한 번에 항목 하나다** — 게임 명령 포트(13100)가 PC 에 하나뿐이다. **VISION 이 켜지 않은 게임이 그 PC 에 떠 있으면 명령이 그 게임에 붙는다** — 시험 PC 에 사람이 켠 게임을 띄워 두지 않는다(`by: "person"` 으로 깐 게임도 사람이 켜면 같다)
- **항목 사이에 게임 데이터를 두는 것은 폰과 같다** — 항목마다 끄고 다시 켜고 데이터는 놓을 때 VISION 이 지운다. 첫 실행 상태가 필요한 케이스는 폰처럼 1차 밖이다(위 「게임 연결」)
- **케이스 테스트 실행도 같은 길이다** — 시험 하나가 PC 를 잡고 그 줄 최신 빌드를 깔고 돌린 뒤 놓는다. 폰처럼 기다리지 않는다 — PC 줄이 쓰이는 중이면 409 `DEVICE_BUSY`, VISION 이 빈 PC 가 없다고 하면 결과가 그 까닭의 미실행이다
- **폰을 고르는 길은 PC 를 거른다** — VISION 기기 목록(`GET /api/devices`)에는 `pc-<이름>` 줄(`platform: "windows"` · `formFactor: "pc"`)이 폰과 같이 `IDLE` 로 온다. 목록에서 첫 빈 기기를 고르는 폰 잡기(`apps/admin/src/execution/farm.ts` `빈폰을고른다`)와 호환성 · 기기 성능의 기기 목록은 `platform` 이 `windows` 인 줄을 뺀다 — 안 빼면 Android 항목이 PC 를 잡아 `/wd/hub` 400 으로 미실행이 된다(VISION 의 조건 잡기는 `platform` 조건이 없으면 폰만 고르지만 우리는 목록 + `/hold` 길이다 — 거르기는 `farm.ts` `PC기기인가`, GAME-F4-03)
- **내 컴퓨터 러너 · USB 길은 PC 에 없다** — 사람이 PC 앞에서 손으로 볼 때는 control-cli `open --pc`(같은 컴퓨터의 게임에 바로 붙기)를 쓴다. kit 은 `udid` 없는 `windows*` 항목을 받지 않는다

**빌드 — zip 하나** ([실행.md](실행.md) §3.11 · [공통/4](../공통/4-데이터모델.md) 「윈도우 PC 빌드」 · 「게임 애플리케이션 플랫폼」)

- CI 가 지금 빌드 올리기 통로(`POST /api/builds`)에 Unity 빌드 폴더를 통째로 싼 zip 을 본문 그대로 올린다. **요청 칸은 늘지 않는다** — 서버가 zip 목차로 가른다. 맨 위에 `AndroidManifest.xml` 이 있으면 지금처럼 Android, 맨 위나 한 폴더 아래에 `.exe` 가 꼭 하나 있으면(`UnityCrashHandler*` 는 세지 않는다 — VISION 깔기와 같은 규칙) 윈도우다. 둘 다 아니면 지금처럼 400 `BAD_FILE_TYPE`
- **애플리케이션 플랫폼과 다른 파일은 거절한다** (2026-11-19 기획 대화 · GAME-F4-04) — 모바일 게임에 윈도우 zip, PC 게임에 APK(본문이든 회사 저장소 주소 `apkUrl` 이든)를 올리면 400 `BAD_FILE_TYPE` 이다. Android 앱 애플리케이션의 윈도우 zip 도 지금처럼 400 `BAD_FILE_TYPE`. 윈도우 zip 크기 한도는 VISION 과 같은 **1GB** 다. PC 게임은 회사 저장소 주소를 못 쓴다 — 서버가 목차를 볼 수 없어서다
- **실행 빌드 칸은 하나다** — 한 애플리케이션의 빌드는 늘 한 플랫폼이라 최신 빌드 · 보관 5개 · 같은 번호 409 · 실행 고정(`test_run.build_id` · `build_no`) · 빌드 실행을 잇는 셈(스모크 뒤 회귀 · 앞 빌드 건너뛰기 · 더 새 빌드 · 보관 지키기) · 「앞 빌드」가 다 지금 Android 앱 · 모바일 게임과 같은 규칙이다. PC 게임의 빌드 실행은 스모크 → 회귀 모두 그 애플리케이션 케이스를 선언대로 펼쳐 돈다. QA 리포트의 빌드 묶음도 다른 애플리케이션과 같이 든다. `app_build.platform` 칸은 파일 종류 기록으로 남는다

**게임 드라이버에 더하는 것** — 꼴은 [공통/3](../공통/3-공유계약.md) 「게임 테스트 타입」 아래 「윈도우 PC 게임」. control-cli `Game` 에서 고른 것만 낸다(좌표 금지 그대로).

- `key(name, { duration? })` · `keyDown(keys)` · `keyUp(keys)` — Unity KeyCode 이름(`Escape` · `Space` · `I` · `F1`)과 패드 버튼 `Pad.<이름>`(`Pad.Cross` · `Pad.A`). 폰에서도 쓴다(`Escape` 는 폰 뒤로 키). 눌러 둔 키는 몸통이 떼지 않고 끝나도 kit 정리 단계가 거둔다(`touchUp` 과 같다)
- `pad()` — 읽기만 한다. 지금 패드 종류와 버튼 표시 이름(`{ type, buttons? }`)을 돌려준다. **패드를 바꾸는 메서드는 내지 않는다** — 패드는 케이스 선언이 정한다(결정 27)
- **확인 · 취소는 패드마다 자리가 다르다** — Switch 는 오른쪽 A 가 확인 · 아래 B 가 취소, Xbox 는 아래 A 가 확인이다. 버튼 그림 케이스는 패드마다 돌므로 누를 버튼과 기대할 그림 이름을 `game.pad()` 로 갈라 고른다. 다른 패드의 버튼 이름(`windows-switch` 에서 `Pad.Cross`)을 쓰면 SDK 가 거절해 그 항목은 실패로 멈춘다. 그림 이름을 화면 목록에서 못 읽으면 「개발팀에 요청할 것」으로 올린다(결정 25). 쓰는 법은 작성 지침 `tpx-cases` `game.md` §8 이 맡는다(2026-11-20 GAME-F4-07)

**증적 · 결과** (결정 28)

- 단계 · 실패 스크린샷은 Appium 대신 control-cli `Game.screenshot()` 으로 kit 이 찍는다(케이스 몸통의 `game` 에는 내지 않는다 — 폰의 스크린샷도 kit 몫이다). 실패 항목의 `game-tree.txt` · `game-errors.txt` 는 폰과 같은 자리 · 같은 꼴이다(위 「실행 결과」)
- 실행 · 시험 실행 진행 창의 PC 항목 카드는 브라우저처럼 가로 틀 하나다(2026-11-20 GAME-F4-06 시안) — PC 는 한 대라 PC 카드도 한 번에 하나다. 머리에 VISION 기기 이름(`pc-pc1`)과 「Device VISION ↗」 링크([실행.md](실행.md) §3.2 「테스트 모드」)가 붙고, 장면은 폰 장면처럼 1초 간격으로 묻는다. 첫 단계 전 글은 PC 를 잡기 전 「빈 Windows PC 를 기다리는 중」 · 잡은 뒤 「게임을 여는 중」이다. 시험 실행 창의 「동작마다 1초 천천히」는 PC 에 안 뜬다(Appium 처럼 안 늦춘다)
- 화면 영상 · logcat · FPS · 통과 항목 「영상 보기」는 PC 항목에 없다 — 결과 화면의 그 칸이 비어 있다. VISION 은 잡기 하나를 통째로 녹화해(`GET /api/sessions/<held.sessionId>/artifacts` → `video-N.mp4` · `game.log`) 항목마다 자르는 길을 따로 정한다(아래 「1차 밖 · 나중」)
- 기기 정보는 모델 칸에 VISION 기기 이름(`pc-pc1`), OS 칸에 「Windows」다. 앱 판 · 빌드 코드는 읽지 않는다 — 「다른 빌드가 깔려 있었다」 경고([실행.md](실행.md) §3.11)는 PC 항목에 안 뜬다

**작성 — PC 게임은 PC 에서 읽고 돌려 본다** (결정 28 · 2026-11-20 반영 GAME-F4-07 — `scripts/authoring-run.ts` · `authoring-app-screen.ts` · `authoring-run3-game.ts` · `authoring-run3-env.ts` · `authoring-check-game.ts` · 지침 `tpx-author` `game.md` §3 「PC 게임」 · `tpx-cases` `game.md` §8)

- **어느 빌드를 깔까** — 대상 서버 줄은 앱 · 모바일 게임과 같은 규칙(`앱줄고르기` — 짚은 줄, 아니면 운영 아닌 첫 줄)인데 「앱 파일 경로가 있는 줄」 대신 「빌드가 있는 줄」을 본다. PC 게임은 `app_path` 로 물러서지 않아서다. 그 줄 최신 zip 의 서명 주소는 지금 있는 앱 링크 통로(`GET …/app-link` — [작성.md](작성.md) §7)가 주고 작성 동안 갈아 끼운다
- **첫 화면은 미리 받지 않는다** — 게임 첫 화면 통로(§7 `game-screen`)는 PC 게임이면 폰을 잡지 않고 `screen` 이 null · 까닭 「PC 게임은 작성 AI 가 PC 에서 읽는다」다. 대신 `game` 에 팜 주소 · 위 줄의 zip 서명 주소 · 토큰을 실어 AI 가 PC 를 잡고 깔 수 있게 한다(팜이 안 붙었으면 null). 빌드가 없으면 `game` 이 null 이고 까닭은 「Windows 빌드가 없다 …」다(§7 마지막 블록 · 2026-11-20). 첫 화면은 AI 가 PC 를 잡은 뒤 control-cli 로 읽는다
- **PC 게임인데 `game` 이 없으면 에이전트가 AI 를 띄우지 않고 FAILED 로 끝낸다** — 까닭은 서버가 준 것(빌드 없음) · 통로를 못 불렀으면 그 까닭(서버 오류 · 시간 초과), 팜이 안 붙었으면 「Device VISION 이 연결되어 있지 않아 PC 를 잡을 수 없다」다. 모바일 게임은 팜이 없어도 첫 화면 없이 가지만 PC 게임은 AI 가 읽을 것이 하나도 없어서다(`authoring-app-screen.ts` `PC게임못함` — 2026-11-20 사용자 승인)
- 작성 에이전트가 control-cli `hold --pc` 로 VISION 에서 PC 하나를 잡고 그 줄의 최신 Windows 빌드를 깐 뒤, 창 훑기 · 눌러 가며 읽기 · 케이스마다 1번 돌려 보기를 그 PC 한 대에서 한다. 폰처럼 여러 대로 나눠 돌리지 않는다. 다 쓰면 놓는다 — 놓기를 잊은 것은 에이전트가 작업 폴더의 잡기 기록을 보고 놓는다(폰과 같은 손)
- 에이전트가 애플리케이션의 지원 패드(집기 응답 `gamePads`)를 프롬프트 게임 화면 절에 싣는다. 자식은 보통 케이스를 `windows` 로, 버튼 그림 케이스 하나를 지원 패드 값으로 선언한다
- **케이스마다 1번 돌려 보기는 잡은 PC 한 대에서 선언한 윈도우 값마다 따로 돈다** — Playwright 프로젝트가 값마다 하나이고 패드는 항목마다 `PLATFORM_PAD` 하나라서다. 덤 PC 는 잡지 않는다. 같은 파일의 패드 결과가 섞이지 않게 기록 이름의 PC 번호에 패드 꼬리(`pc-pc1:ps5`)를 붙여 판정에서 다른 「폰」으로 읽는다 — 한 패드에서만 빨가면 「폰 차이」(PS5 패드에서만 빨강)로 찍히고 다른 PC 로 다시 보지 않는다. 선언한 값이 다 돌기 전에는 초록으로 세지 않는다(시간이 모자라 한 패드가 안 돌았으면 안 돈 것) · 윈도우 값이 없는 케이스가 있으면 돌리지 않고 2 로 끝난다. 명령은 게임을 다시 깔지 않는다 — AI 가 탐색 때 `open` 이 찍은 게임 이름을 `PLATFORM_PC_GAME` 으로 넘긴다(`authoring-run3-game.ts` · `authoring-run3-env.ts`)
- 작성 빠른 검사의 「platforms 는 `['android']` 하나」(위 「작성 — 한 바퀴」 6 · 붙인 모양 GAME-F1-12)는 애플리케이션 플랫폼 기준이다 — 모바일 게임은 `['android']` 하나, PC 게임은 윈도우 값만이다(에이전트가 PC 게임이면 자식 환경에 `AUTHORING_GAME_PLATFORM=windows` 를 준다). 웹 마지막 돌려 보기는 PC 게임 케이스도 앱 케이스처럼 뺀다 — 웹 프로젝트에서 「선언하지 않은 환경」 건너뜀이 초록으로 세지지 않게
- 키보드 · 마우스 요구를 `환경 한계` 머리 「PC 전용」으로 빼는 규칙([작성.md](작성.md) §3.6 「게임 기획서 빈 곳」)은 모바일 게임에만 쓴다. PC 게임에서는 키보드 · 마우스가 그 게임의 조작이라 케이스로 쓴다
- **작성과 실행이 PC 한 대를 다투는 일은 다루지 않는다** (2026-11-19 사용자 「아직 실행할 일 없으니 고려하지 마」) — 작성의 잡기와 실행의 PC 줄은 서로 모르고, 둘이 겹치면 VISION 잡기가 먼저 온 쪽에 PC 를 준다. 실행 쪽은 위 1 처럼 기다린다

**두 갈래가 같이 쓰는 것**

- **준비와 정리** (결정 20) — 상태는 어드민 API 또는 GM 명령으로 만든다(결정 16 — 새 캐릭터 · 골드 · 아이템 · 위치 · 레벨 · 결과 고정 · 확률 설정 · 몬스터 놓기 · 봇 치우기). 걸어가지 않고 순간이동한다(이동 자체를 보는 게임 시나리오는 아래 「이동」).

  준비 명령이 시작 조건까지 바꾸는지 본다 — Boss Room `/gm killall` 은 몬스터를 치우면서 경험치를 줘 레벨을 올린다(ARG-FN-480 · 481). 시작 조건(레벨 · 장비)은 준비가 다 끝난 뒤에 맞춘다
- **확인 수단** — 보이는 글자는 화면, 서버가 정하는 값(재화 · 아이템 · 강화 결과)은 서버 API 와 화면 둘 다, 게임이 폰에서 계산하는 값(이동 속도 · 데미지)은 SDK 로 게임 안 속성을 읽는다. 어드민 API 가 없고 GM 명령만 있는 게임은 화면 값 · GM 조회 명령으로 확인하고 결과 요약에 「서버 값 확인 없음」을 적는다
- **간섭 차단** — 케이스마다 계정 앞머리를 쓰고, 봇과 다른 몬스터는 치운 뒤 정해진 자리에 하나만 둔다. 세계 전체를 되돌리는 명령(Ashveil `/admin/world/reset`)은 서버 초기화로 보고 새 케이스에 쓰지 않는다 — 자기가 부르거나 자기 자리에 있는 것만 치운다(결정 20 의 까닭과 같다 — 같은 서버를 다른 실행이 같이 쓴다, 내 결정). 정리는 위 「준비와 정리」의 정리 자리다(앞 판은 finally).

- **기다림** — 고정 시간 쉬기 금지. 「오브젝트가 뜰 때까지 · 글자가 들 때까지 · 사라질 때까지」는 게임 드라이버 `waitFor` 로 기다린다(SDK 에 기다리기 명령은 없다 — 드라이버가 `find` 를 되풀이한다). 「값이 될 때까지」는 `get` 을 되풀이한다 — kit 이 게임 드라이버에 더한 `waitForValue`(GAME-F1-09 — [공통/3](../공통/3-공유계약.md) 「게임 테스트 타입」), 쓰는 법은 작성 지침 `5-stable.md` 「게임 — 기다림」(2026-10-23 GAME-F1-11)
- **주소** — 오브젝트 이름 → 겹치면 `/` 로 시작하는 경로(같은 이름 형제는 `[순번]`, 0부터 — `/HudCanvas/Inventory/Grid/Slot[2]`). 좌표 금지. 여럿 생기는 것(몬스터 · 드랍)은 정해진 자리에 하나 두고 찾는다
- **기대값** — 표준 기획서에서만 온다. 화면 · 창 기록 · 게임 지도 · API 지도는 근거가 아니다(웹과 같다 — CLAUDE.md 「playwright-cli」 절)
- **어드민 키는 케이스에 글자로 쓰지 않는다** — 대상 서버 줄의 어드민 키 칸(`service_env.admin_key` — 머리 이름 + 값, 설정 화면은 끝 4자리만 — [인증.md](인증.md) §7 「envs[] 한 줄」 `adminKey`)을 kit 이 몸통 `admin` 요청 도구의 머리로 넣고 기록에서 가린다(GAME-F1-09 — [공통/3](../공통/3-공유계약.md) 「게임 테스트 타입」). 작성 중에는 빠른 검사의 「비밀번호 노출 점검」이 케이스 · 표 · 가이드에서 키 값을 찾는다(아래 「작성 — 한 바퀴」 붙인 모양 GAME-F1-12b). Ashveil 은 머리 하나(`X-Admin-Key`)로 열려 OAuth 꼴 API 인증 칸(`api_auths`)에 안 맞는다
- **느린 망 흉내는 1차에 없다** — 게임은 kit 을 거치지 않고 자기 서버와 바로 통신한다

**기능 테스트** — 지금 꼴 그대로다. 조작 한 번 → 화면 · 서버 값 확인. 경계값 · 설계 칸(아래 「설계 칸」) · 확률 세 겹 · 화면 잘림 배치 확인 · 버튼 반응이 여기 든다. 제한 시간도 지금 그대로다(케이스 120초 — [러너.md](러너.md) §5.2).
머리 위 숫자처럼 **화면에 보여야 하는 값**은 로그로 못 본다 — 그 확인은 기능 테스트에 둔다.

**게임 시나리오** (결정 19 · 21 ~ 25)

미션 양식 — 미션 하나가 테스트 하나다. 전투형 Boss Room 예.
```
미션: 레벨 5 탱커가 임프 3마리를 잡는다
시작 조건: 탱커 · 레벨 5 · 강철 롱소드 · 사슬 갑옷 · 3명 파티
할 일: 강철 롱소드로 임프 3마리 처치
성공 조건: 처치 기록 3줄
확인할 로그
 - 준 피해 줄: 전부 12 (최소 3줄) — 기획서 규칙 번호
 - 받은 피해 줄: 전부 12 (최소 1줄) — 기획서 규칙 번호
```
통과 규칙
1. 셋이 다 맞아야 통과 — 성공 조건 달성 · 확인할 로그가 최소 줄 수 이상 · 모든 줄이 기대값(랜덤이면 범위) 안
2. 확인할 로그가 한 줄도 안 찍혔으면 통과가 아니라 「확인 못 함」이다 — 결과에는 그 규칙 문장이 실패로 남고 문장 머리가 「확인 못 함 — 」다(판정 값 넷째를 만들지 않는다 — 화면 · 집계 · 리포트가 다 바뀌어서, 내 결정)
3. 시작 조건은 미션 하나에 하나다. 조건이 다르면 미션을 나눈다(레벨 1 과 레벨 5 는 다른 미션)
4. 양식에 없는 종류의 줄 · 시작 조건과 다르게 찍힌 줄은 실패로 치지 않고 「설명 안 되는 줄」로 따로 표시해 사람이 본다 — 결과에 판정에 안 드는 문장(NA)으로 남는다. 인원 보정처럼 기획서에 없는 규칙이 여기서 드러난다
5. 결과는 미션 단위가 아니라 기획서 규칙 단위로 남긴다 — 미션 양식의 「확인할 로그」 항목 하나가 판정 문장 하나이고 문장에 기획서 규칙 번호를 단다

- **로그는 미션을 시작할 때 번호를 적고 끝나면 그 뒤 줄만 받아 온다** — kit 은 게임마다 다른 줄 꼴을 모른다. 로그 주소를 부르는 법과 줄 꼴은 서비스 가이드 · 상태 도우미 몫이다(꼴은 공통/3 「게임 시나리오 도구」 `gameLog`). 로그를 지우지 않는다(Boss Room `clear=1` 을 안 쓴다) — 같은 서버를 다른 실행이 같이 써서다. 그래서 받은 줄에서 **자기 계정 줄만 고른다**(Boss Room 은 사람 쪽 칸의 `user`)
- **기대값은 줄에 찍힌 조건을 기획서 공식에 넣어 다시 계산한 값이다** — 줄마다 그때 레벨 · 직업 · 장비 · 인원이 같이 찍힌다. 게임이 셈한 배율을 그대로 믿으면 게임 값으로 게임 값을 확인하는 꼴이 된다
- **경계값 미션은 만들지 않는다** — 경계값은 기능 테스트에서 본다(사용자 「어차피 로그 기반이니」)
- **제한 시간** (결정 21) — 테스트 전체 한도가 없다(kit 이 Playwright 한도를 끄고 러너가 프로세스를 끊는 타이머도 안 건다 — 공통/3 「게임 시나리오 도구」). 잡는 것은 둘이다.
  ① 한 번의 기다림이 너무 길다 — `waitFor` · `waitForValue` 가 이미 한도를 가진다(기본 10초 · 명령 하나 15초 — 위 「게임 연결」). 던전 입장처럼 오래 걸리는 기다림은 그 자리에 한도를 넉넉히 적는다.
  ② 미션이 성공 쪽으로 한동안 나아가지 않는다 — 되풀이 조작은 진행 값(처치 줄 수)을 읽으면서 돌고, 진행 값이 정해 둔 시간 동안 안 늘면 끝낸다(공통/3 「게임 시나리오 도구」 `repeatUntil`). 실패 유형은 「타임아웃」이다.
  사람이 실행을 멈추는 것은 지금처럼 된다
- **조작 · 이동** (결정 22) — 그 게임에서 어떻게 조작 · 이동하나는 조작 맵의 행이 정본이다(결정 30 · 35 — 아래 예의 Boss Room 사실은 처음 맵을 채울 때 행으로 옮긴다). 조작은 스크립트다. 전투는 「적이 남아 있는 동안 가까운 적을 골라 공격」 같은 되풀이로 쓴다 — 판정이 로그라서 조작이 서툴러도 로그만 찍히면 된다. Boss Room 은 적을 누르면 고르기만 되고 「공격」 버튼을 눌러야 친다(2026-11-18 폰 확인).
  **이동**은 ① 이동이 확인할 대상이 아니면 순간이동 치트(Boss Room `/gm tp`) ② 게임에 자동 이동(퀘스트를 누르면 알아서 간다)이 있으면 그것을 쓰고 도착만 기다린다 ③ 둘 다 없거나 이동 자체를 확인하면 거쳐 갈 지점 목록(게임 안 위치 — 2026-11-19 부터 탐색 플레이가 조작 맵 이동 · 조작 행으로 쌓는다(결정 30), 반영 전까지는 서비스 가이드에)을 적고 스크립트가 내 위치를 읽으며 다음 지점 쪽으로 이동 입력을 되풀이한다 — 도착은 위치 값으로 보고, 위치가 한동안 안 가까워지면 ② 처럼 끝낸다. 금지인 좌표는 화면 좌표다. 게임 안 위치는 값이라 쓴다(아래 「작성 — 한 바퀴」 GAME-F1-12 — 순간이동 본문 · 위치 기대값의 `{ x, y }` 는 안 막는다). ③ 은 지형 · 맵이 바뀌면 지점 목록을 고쳐야 한다
- **게임 종류 셋** (결정 23) — 로그에 무엇이 찍히느냐로 가른다. 서비스 가이드에 적는다.

  | 종류 | 로그가 찍히는 때 | 예 | 규칙 |
  |------|------------------|----|------|
  | 전투형 | 타격 · 회복 · 처치 · 획득 · 레벨 업마다 | RPG · 액션 · 슈팅 (Boss Room) | 위 양식 · 통과 규칙 |
  | 판 규칙형 | 한 수마다 판 상태 · 점수 | 퍼즐 · 카드 · 보드 | 아직 안 쓴다 — 그 종류 게임이 올 때 |
  | 성장 재화형 | 재화가 늘고 줄 때마다 | 방치형 · 경영 · 수집 | 아직 안 쓴다 — 그 종류 게임이 올 때 |

- **누가 무엇을 하나** (결정 24 · 33 — 2026-11-19 승인을 뺐다)
  1. 사람 — 게임 사정을 서비스 가이드에 적는다(치트 · 로그 받는 법 · 게임 종류). 한 번. 이동 지점 목록은 탐색 플레이가 조작 맵에 쌓는다(결정 30 · 35)
  2. AI — 기획서 규칙을 읽고 미션 목록을 양식대로 채운다. 시작 조건 · 할 일 · 성공 조건은 조작 맵의 경로 검색 결과에서 옮기고(결정 33), 확인할 로그의 기대값은 기획서 공식으로 셈한다
  3. 프로그램 — 확인하는 미션이 없는 기획서 규칙 · 빈 칸을 검사한다. 그 결과는 PR 머리 한 줄 `게임 시나리오 미션:`(꼴은 아래 「어떻게 도나」 ②)로 보인다 — 서버에는 올리지 않는다(2026-11-20 GAME-F5-07, 미션 승인 탭을 걷으며)(공식 빈칸은 `확인 필요` 항목이라 판정 요청 카드로도 온다 — 아래 「탐색 플레이 · 조작 맵」 셋째 블록)
  4. ~~사람 — 미션 목록을 보고 승인한다~~ (2026-11-19 결정 33 이 없앴다 — 앞 판은 「결정 필요」 「미션 승인」에서 체크한 미션만 쓰고 승인 전에는 게임 시나리오를 쓰지 않았다. 승인 화면 · 통로는 2026-11-20 GAME-F5-07 이 걷었다)
  5. AI — 같은 작성에서 테스트를 쓰고 폰에서 돌린다. 값이 안 맞는 줄 · 설명 안 되는 줄은 사람이 버그인지 기획서가 틀렸는지 판정한다(값이 안 맞는 줄은 실패라 「결정 필요」 결함 판정의 실패 판정, 설명 안 되는 줄은 같은 탭의 「설명 안 되는 줄」 — [작성.md](작성.md) §3.6 「★ 결정 목록」 · 2026-11-18 GAME-F3-06)
- **길이 없을 때** (결정 25) — 미션에 필요한 것(로그 · 치트 · 싸우는 봇)이 게임에 없으면 먼저 치트 · 테스트 주소 · 봇 · 화면 조작으로 해낼 길을 찾는다. 그래도 없을 때만 작성 결과 요약(PR 본문)에 「개발팀에 요청할 것」으로 따로 올린다 — 테스트 절차를 고칠 것 · 보류와 섞지 않는다(결과 요약 줄 `개발팀에 요청할 것:` — 쓰는 법은 `tpx-cases` `references/game-scenario.md` §6 · 2026-11-18 GAME-F3-03). 로그 주소가 없는 게임은 게임 시나리오를 쓰지 않는다(아래 「게임 쪽이 준비할 것」)

#### 확률 세 겹 (결정 3)

| 겹 | 무엇을 보나 | 어떻게 |
|----|-------------|--------|
| ① 결과 처리 | 성공 · 실패 · 파괴가 났을 때 화면 · 서버 값이 맞나 | 어드민 API 로 결과를 고정하고(Ashveil `/admin/forced`) 한 번 한다 |
| ② 표를 읽나 | 게임이 실제 사용자 흐름에서 확률표를 읽는가 | 표 값을 100% · 0% 로 바꾸고(`/admin/config/*`) 화면으로 N번 반복한다 — 늘 성공 · 늘 실패여야 한다 |
| ③ 분포 | 기본 확률표대로 나오나 | API 로 대량(예 1,000번) 시도하고 검정한다. 횟수 · 허용 오차는 AI 가 추천하고 사람이 고친다(입력값 칸 — 추천 식은 `tpx-cases` `test-design.md` 「확률 규칙 줄 하나 = 케이스 셋」). 정기 실행 때와 확률표가 바뀔 때만 돈다 — **거를 칸이 아직 없어 1차는 회귀에 같이 돈다**(2026-10-23 GAME-F1-11 시작 질문 승인) |

- ③ 은 시도마다 독립인 확률에만 쓴다 — 기획서가 천장 · 실패 누적 같은 보정을 적었으면 그 보정은 자기 규칙(「5번 연속 실패하면 다음은 성공」 → 성공 0% 로 두고 6번째가 성공하나)이고 ③ 을 안 쓴다. ② 의 0% 반복도 같다 — 천장이 걸려 성공이 나온다. 독립인지 기획서가 안 적었으면 표준 기획서에서 `확인 필요` 고, 그동안은 ① 과 ② 의 100% 만 쓴다([작성.md](작성.md) §3.6 「게임 기획서 빈 곳」 공식 칸 · 2026-11-18 AUT-F4-12)
- ③ 의 검정 도우미는 kit 의 `verify.rates` 다(GAME-F1-09) — 결과마다 나온 비율이 기대 확률 ± 허용 오차(비율 차이) 안이면 통과, 표에 없는 결과가 한 번이라도 나오면 실패다. 꼴은 [공통/3](../공통/3-공유계약.md) 「게임 테스트 타입」. 서버의 시도마다 확률 · 뽑은 숫자 기록은 고객사 요청 목록에만 넣는다(아래 「게임 쪽이 준비할 것」)

- **첫 세션** — 프롬프트 「탐색 플레이」 절이 「표준 기획서 옮기기 · 게임 지도 · 창 훑기 뒤 `[단계] 탐색 플레이` 를 말하고, 케이스는 쓰지 말고 끝내라」를 준다. 자식은 자료 폴더 `game-explore.json`(`{ 목표: [{ 기능, 열쇠: [목표 열쇠…], 출발?, 결과: '경로 확보' | '진행 불가' | null, 까닭? }] }`)에 목표부터 적고, 통과한 동작 · 진행 불가 행은 `game-route.json`(§7 PUT game-route 본문 꼴)에 적는다. 끝내기 전에 `npx tsx scripts/authoring-explore.ts <자료 폴더>`(0 지남 · 1 못 지남)로 스스로 본다. 결과 요약 대신 「탐색 플레이 끝」 한 줄로 끝낸다
- **경로 검색은 아직 안 올린 행도 읽는다** — `game-route.txt` 에 `game-route.json` 의 행을 얹는다(같은 행(종류 · 출발 · 동작)은 새 행이 이기고 remove 는 뺀다. 서버 올리기(§7 PUT)와 같이 빌드를 안 실은 확인 행은 「재확인 필요」 행을 풀지 않는다). 앞 목표에서 찾은 길을 다음 목표 · 케이스 작성이 바로 쓴다
- **체크포인트** — 첫 세션이 제대로 끝나면(멈춤 · 시간초과 · 끊김이면 지금처럼 끝내고 폴더가 남아 이어하기가 탐색부터 잇는다) 에이전트가 앞 자식을 거두고 잡은 폰을 놓은 뒤, `game-route.json` 을 올리고(PUT — 돌발 팝업 행은 넣지도 지우지도 않는다 · 아래 「돌발 팝업 자동 닫기」) 맵 글을 다시 받는다. 그 맵(받은 글 + 아직 안 올린 행)으로 목표마다 결과가 있나 · 진행 불가에 까닭이 있나 · 「경로 확보」면 경로 검색이 「확인」 행만으로 길을 다 내나(종료 코드 0) 본다. 목표가 하나도 없거나(두 번째 작성도 기능 단위마다 목표가 있다 — 맵에 길이 있으면 폰 없이 「경로 확보」일 뿐이다) 목표 파일이 없거나 깨졌거나 맵 행 파일이 4MB 를 넘거나 서버가 맵 행을 꼴로 거절했어도(400) 못 지난다 — 그 밖의 올리기 실패는 PR 머리 줄에만 적는다
- **못 지나면** 올리기 거절(`REJECTED`)로 멈춘다 — 까닭에 못 지난 목표가 적힌다. 「이어서 작성」이 그 까닭부터 고친다(`tpx-author` `references/resume.md`). 진행 불가 목표가 있는 것은 못 지난 것이 아니다
- **지나면** 결과 줄을 자료 폴더 `game-explore.done` 에 남기고 같은 폴더 · 같은 임시 자리에서 새 세션을 띄운다 — 이어하기 절(까닭 「탐색 플레이를 마침」 · 진행 메모)과 「탐색 플레이」 끝 절(창 훑기 · 탐색 플레이를 다시 하지 말고 요구별 케이스 목록부터 · 준비 · 조작은 경로 검색 차례를 옮긴다 · 화면 객체 함수 이름을 그 행 `fields.fn` 에 채운다 · 결과 줄을 결과 요약에 그대로). 대화는 넘기지 않는다. `game-explore.done` 이 있는 폴더를 이어받으면 첫 세션을 건너뛴다. 새 세션이 아예 안 뜨면 실패가 아니라 끊김(`CRASH`)으로 멈춘다 — 실패는 폴더를 지워 탐색한 것을 잃는다. 크레딧 자식([작성.md](작성.md) §7 「이어하기」 크레딧 예외)은 세션마다 그대로 돈다 — 새 세션에서 크레딧이 떨어져 이어 띄우는 자식의 까닭은 「API 크레딧이 떨어짐」이다. 토큰은 다 더해 한 번 알린다
- **결과 줄** — `탐색 플레이: 목표 N개 — 경로 확보 A · 진행 불가 B — <기능>(<까닭>) · …`(까닭은 다섯까지 · 계정 비밀번호가 섞이면 자르기 전에 보고 까닭을 안 적는다). 작성 끝에 PR 머리에 그 줄 · 「조작 맵: 행 N개 올림」(케이스 작성이 채운 `fields.fn` 과 같이 다시 올린다) · 「올리지 않은 돌발 팝업 행 N — <창>」(이번 작성이 `game-route.json` 에 적은 「확인」 팝업 전부 — 맵에 있던 창을 다시 적은 것도 센다. 서버에는 안 올리고 그 작성의 돌려 보기에서만 쓴다 · 2026-11-20 사용자)을 싣는다

**조작 맵 — 한 행에 동작 하나.** 행 종류 다섯을 표 하나에 칸으로 나눈다(게임 지도 — 위 「게임에만 있는 지도 넷」 — 와 같은 꼴).

| 행 종류 | 적는 것 | 예 (Boss Room) |
|---|---|---|
| 이동 · 조작 | 출발 열쇠 → 동작 → 도착 열쇠 · 소요 시간 · 그 동작을 하는 도우미 · 화면 객체 함수 이름(탐색 플레이 때는 함수가 아직 없어 빈다 — 케이스 작성(위 「작성 — 한 바퀴」 4 · 5)이 그 동작을 함수로 만들면 채워 작성 끝에 다시 올린다). 되풀이 동작은 진행 값도 | `zone:Dungeon` → 적 누르기 후 「공격」 누르기 → 처치 · 진행 값 처치 줄 수 · `던전화면.공격` |
| 상태 설정 | GM 명령 · 어드민 API 와 바뀌는 상태 열쇠 · **다른 상태까지 바꾸는 부작용은 경고로** | `/gm killall` → `state:몬스터 없음` · ⚠ 경험치를 줘 레벨이 오른다 — 레벨 맞추기보다 먼저 |
| 로그 | 어떤 동작에 어떤 로그 줄 종류가 어떤 칸으로 남나. **값은 적지 않는다** | 임프 처치 → 처치 줄(user · 경험치 · 레벨 · 직업 · 인원) · 물약 마시기 → 로그 없음(⚠ 회복 규칙은 미션 불가 — 개발팀에 요청할 것) |
| 용어 | 기획서 낱말 = 게임 열쇠 = 화면 글자 | 대장장이 = `npc:Blacksmith` = 「대장장이 브론」 · 「공격」 버튼의 역할 = `Image.sprite.name` |
| 돌발 팝업 | 아무 때나 뜨는 창의 주소와 닫는 법 — 출발 열쇠가 창 열쇠, 동작 칸이 닫을 때 누르는 오브젝트 주소(kit 이 그 주소를 누른다 — 아래 「돌발 팝업 자동 닫기」) | 초대 창 `game:Main/Canvas/Invite` → `/Canvas/Invite/Decline`(「거절」) |

- **열쇠는 지금 꼴 그대로다** — 창 `game:<장면>/<창 경로>` · 구역 `zone:` · 상태 `state:` · NPC · 아이템은 게임 지도 열쇠. 창 기록 · 게임 지도와 바로 이어진다
- **행 상태는 셋** — 확인(그 빌드에서 통과) · 재확인 필요(정식 실행에서 그 동작의 조작이 실패 — 다는 쪽은 정식 실행뿐이다, 아래 「정식 실행이 맵을 고친다」. 창 지문이 바뀐 창에 닿는 목표는 행 상태와 상관없이 위 차례 2 가 다시 해 볼 목표로 남긴다. 푸는 쪽은 그 행을 디바이스에서 다시 해 본 쪽이다 — 탐색 플레이와 테스트 고침(아래 「실패 자동 수정」 3)) · 진행 불가(까닭). 경로 검색은 「확인」 행으로만 길을 낸다
- **기대값의 근거가 아니다** — 「어떻게 가나」만 담는다. 해 보며 본 값은 맵에 적지 않는다. 그 값이 기획서가 비운 `확인 필요` 항목(위 「게임 기획서 빈 곳」 — 공식 칸 · 데이터로 닿나 · PC 전용 · 잠깐 뜨는 표시 — [작성.md](작성.md) §3.6)에 닿으면 그 항목의 「현재 동작」으로 남긴다(결정 34 · 같은 장 「★ 결정 목록」 「판정 요청 카드」). **`확정` 항목과 다른 값은 현재 동작으로 남기지 않는다** — AI 는 관찰로 확정을 `확인 필요` 로 내리지 못한다. 그 요구의 케이스는 기획서 값으로 판정하고 다르면 지금처럼 「결정 필요」 결함 판정의 실패 판정으로 간다. 카드가 걸린 동안 그 `확인 필요` 항목의 케이스는 지금 규칙대로 기준 없이 확인되는 만큼만 쓴 미확정 케이스다(탐색 플레이에서 본 값을 기대값으로 쓰지 않는다 — 화면 값 예외 목록은 작성 §3.6 「★ 역방향」 그대로). 화면 값을 기대값으로 쓰는 예외는 지금 규칙 그대로다(CLAUDE.md 「playwright-cli」 절)
- **애플리케이션마다 하나다** — 게임 하나에 플랫폼 하나라(진행판 GAME-F4 · 2026-11-19 사용자) 플랫폼으로 행을 나누지 않는다
- **PC 패드 · 키 조작도 같은 이동 · 조작 행이다** — PC 게임의 버튼 그림 케이스 하나만 패드마다 돈다(진행판 GAME-F4)

**경로 검색** — 작성 AI 와 보조 AI 는 맵 글을 통째로 읽지 않고 경로 검색 명령만 부른다(자료 폴더의 맵 글을 읽는 로컬 명령 · 폰 없음 · 읽기만). 목표 열쇠(창 · 구역 · 상태 묶음)를 주면 지금 위치(로그인 직후 월드)에서 거기까지 상태 설정 → 이동 · 조작 차례를 몇 줄로 찍고, 지나는 행의 경고 · 남는 로그 · 돌발 팝업을 붙인다.

```
$ npx tsx scripts/authoring-game-route.ts <자료 폴더> 'state:직업=탱커,레벨=1,몬스터 없음' zone:Dungeon/ImpRoom
# 경로 검색 — 목표 state:직업=탱커,레벨=1,몬스터 없음 zone:Dungeon/ImpRoom · 출발 game:Main — 「확인」 행으로만 길을 낸다 · 기대값의 근거가 아니다
1. [상태 설정] game:Main → /gm killall → state:몬스터 없음 · 확인 · 빌드 15 · ⚠ 경험치를 줘 레벨이 오른다 — 레벨 맞추기보다 먼저
2. [상태 설정] game:Main → /gm char tank → state:직업=탱커 · 확인 · 빌드 15
3. [상태 설정] game:Main → /gm level 1 → state:레벨=1 · 확인 · 빌드 15
4. [상태 설정] game:Main → /gm tp Dungeon → zone:Dungeon · 확인 · 빌드 15 · 소요 3000ms
5. [이동 · 조작] zone:Dungeon → 동쪽 문 지나기 → zone:Dungeon/ImpRoom · 확인 · 빌드 15

남는 로그: zone:Dungeon/ImpRoom → 임프 처치 → 처치 줄 · 확인 · 칸 {"칸":["user","경험치","레벨","직업","인원"]}
```

**붙인 모양 (2026-11-20 GAME-F5-04)** — `scripts/authoring-game-route.ts`. 목표 열쇠는 `state:` 묶음(여럿이면 합친다)과 창 · 구역 열쇠 하나다. 차례 줄과 붙이는 줄은 맵 글 줄(§7 「조작 맵」 GET game-route)을 그대로 찍는다 — 빌드 · 소요 · 도우미 · 함수 · 경고 · 칸이 같이 나온다. 칸(fields)의 열쇠 이름(위 「진행 값」 같은 것)은 게임 작성 지침(진행판 GAME-F5-08)이 정한다.
- **출발** — 맵에 나오는 장면 첫 화면(`game:<장면>` — 창 훑기가 로그인 직후 시작 화면을 적는 꼴)이 하나뿐이면 거기서 출발한다. 여럿이거나 없으면 `--from <열쇠>` 를 꼭 준다(안 주면 2) — 장면이 여럿이면 어느 것이 로그인 직후인지 몰라 「게임 시작」 같은 장면 이동 걸음을 빼먹은 길을 낼 수 있다
- **상태 설정** — 상태 조각마다 도착 열쇠의 상태 묶음에 그 조각이 든 상태 설정 행을 고른다. 한 행이 조각 여럿을 맞추면 그 행 하나로, 맞추는 수가 같으면 목표 밖 상태를 덜 건드리는 행으로. 값은 맵에 적힌 그대로만 맞춘다(`/gm level <n>` 같은 틀은 풀지 않는다). **다른 상태를 흔드는 행을 먼저 친다** — 경고가 달린 행과, 목표 조각과 이름이 같고 값이 다른 조각을 같이 바꾸는 행이다. 흔드는 명령 뒤에 맞춘 값이 남게 하려는 것이다(위 「왜」의 `/gm killall` · 2026-11-20 GAME-F5-04 시작 질문). 그래도 끝에 남는 값이 목표와 다르면(흔드는 행끼리 서로 덮는다) 그 조각은 길 없음이다. 행의 출발 열쇠(그 명령을 치는 자리)가 지금 자리가 아니면 먼저 그리로 간다
- **이동** — 이동 · 조작 행과 도착이 `state:` 가 아닌 상태 설정 행(순간이동)으로 걸음 수가 가장 적은 길을 낸다
- **붙이는 것** — 그 자리에서 하는 동작은 목표 자리에서 나가는 이동 · 조작 행(되풀이 동작)이다. 그 가운데 「확인」이 아닌 행은 「확인 안 된 동작」 줄로 붙이고 1 로 끝난다 — 정식 실행이 실패로 다는 행은 대개 목표 자리의 동작이라 길이 나도 다시 해 볼 목표다(위 차례 2). 남는 로그는 지난 행과 출발 열쇠 · 동작이 같은 로그 행에 목표 자리의 로그 행을 더한다 — 지나는 행의 로그는 로그 행 동작 칸이 그 행 동작 글과 글자까지 같아야 붙는다(적는 법은 게임 작성 지침 — 진행판 GAME-F5-08). 돌발 팝업은 「확인」 행 전부다(창이 장면을 가리지 않고 뜬다 — 아래 「돌발 팝업 자동 닫기」 붙인 모양). 용어 행은 길에 쓰지 않는다
- **길이 없으면** — 찾은 데까지 찍고 목표마다 「길 없음」 줄에 그 목표에 닿는 진행 불가 · 재확인 필요 행을 붙인다. 「재확인 필요」 행을 지나야만 닿는 자리면 그 행도 붙인다(위 차례 2 의 다시 해 볼 목표). 종료 코드는 다 찾음 0 · 길 없는 목표나 확인 안 된 동작 있음 1 · 부를 수 없음(맵 글이 없음 · 출발을 못 정함 · 목표가 비거나 같은 상태 이름에 값이 둘) 2

**미션과의 관계** (결정 33) — 미션 양식의 시작 조건은 상태 설정 행, 할 일은 이동 · 조작 행과 되풀이 동작, 성공 조건은 로그 행에서 온다. 확인할 로그의 기대값만 기획서 공식으로 셈한다(위 「케이스 꼴」 「게임 시나리오」). 미션 목록은 사람 승인 없이 같은 작성이 게임 시나리오 케이스까지 쓴다.
로그 행이 「로그 없음」인 규칙은 미션을 쓰기 전에 「개발팀에 요청할 것」으로 올린다(결정 25). 조작 · 이동의 게임 고유 사실(결정 22 의 「Boss Room 은 적을 누르면 고르기만 된다」)은 맵 행이 맡는다(결정 35).

**돌발 팝업 자동 닫기** (결정 31) — 정식 실행 · 테스트 실행 · 작성 돌려 보기에서(작성 돌려 보기는 2026-11-20 GAME-F5-05 — 아래 「붙인 모양」) 게임 드라이버가 동작이 막히거나 기다림이 끝나지 않을 때 그 애플리케이션의 돌발 팝업 행과 지금 화면을 견주고, 맞는 창이 있으면 그 행의 닫는 법으로 닫은 뒤 그 동작을 한 번 더 한다. 절차 기록에 「돌발 팝업 닫음 — <창>」 한 줄을 남긴다(그 절차의 통과 확인 줄이다 — 절차 · 증적 화면이 손대지 않고 보인다). 다시 해 보는 동작은 누르기 · 끌기 · 글자 넣기 · 손가락 누르기 · 기다리기 · 값 기다리기다 — 읽기(text · get)는 창에 가려도 읽혀 막히지 않는다. 한 번 더 해도 실패면 그 실패다. 목록에 없는 창이면 지금처럼 실패고 다음 탐색 플레이가 행을 적는다(실패 자동 수정은 팝업 행을 더하지 않는다 — 아래 「실패 자동 수정」 3). **작성이 적은 돌발 팝업 행은 서버에 올리지 않고 PR 머리에 「올리지 않은 돌발 팝업 행 N — <창>」으로 싣는다**(2026-11-20 사용자 · GAME-F5-05 — 맵에 있던 창을 다시 적은 것도 센다. 아래 붙인 모양 GAME-F5-05 「결과 줄」) — 올리는 순간 다음 정식 실행부터 kit 이 그 창을 닫아(관리 서버 `돌발팝업들` 은 PR 반영을 보지 않는다) 오류 창을 팝업 행으로 잘못 적으면 PR 을 보기도 전에 실패가 통과가 되고, PR 을 반려해도 행이 남는다. 그 작성의 돌려 보기에서만 쓴다. 병합 뒤 맵에 올리는 길은 진행판 GAME-F5-15 다. 앞 판(2026-11-19)은 「작성이 더한 행을 PR 머리에 싣고 사람이 PR 에서 본다」였다. 케이스가 그 창 자체를 확인하는 단계(초대 창을 보는 케이스)에서는 닫지 않는다 — 케이스가 다루는 주소가 그 창이거나 창 안 오브젝트면 건너뛴다.
**붙인 모양 (2026-11-19 GAME-F5-03)** — 싣는 곳은 정식 실행과 테스트 실행이다(칸 꼴은 [공통/3](../공통/3-공유계약.md) 「게임 테스트 타입」 `gamePopups`). 관리 서버가 그 애플리케이션의 「확인」 POPUP 행을 읽어 창 열쇠에서 장면 머리(`game:<장면>`)를 떼고 싣는다 — 공지 · 초대 창은 장면을 가리지 않고 뜬다. 열쇠가 `game:` 꼴이 아닌 행(주소로 적은 행)은 그대로 싣는다. 작성 돌려 보기는 돌려 보기 명령이 자료 폴더의 맵 글과 이번 작성이 적은 행(`game-route.json`)의 「확인」 팝업을 같은 꼴(장면 머리 떼기 · 제어 문자와 200자 넘는 행 빼기 · 100개까지)로 `PLATFORM_GAME_POPUPS` 에 넘긴다(2026-11-20 GAME-F5-05 — `scripts/authoring-run3-env.ts` `돌발팝업값`). 앱 갈래는 빈 값을 넘겨 셸의 값을 덮는다. E2E 시나리오 · 호환성 · 기기 성능 실행에는 아직 안 싣는다(그 요청에 칸이 없다).

**정식 실행이 맵을 고친다** (결정 32) — 끝난 게임 실행마다 항목이 지난 행에 그 빌드 번호를 적고, 실패한 항목의 실패 동작 행을 「재확인 필요」로 바꾼다. 어느 행을 지났는지는 함수 이름으로 맞춘다(아래 붙인 모양). 실패한 항목 가운데 조작 실패는 BTS 를 잇지 않은 프로젝트에서 이어서 아래 「실패 자동 수정」이 맡는다(결정 36) — 고침이 서면 「재확인 필요」 행을 다음 작성까지 두지 않고 그 고침이 먼저 다시 해 본다.
**붙인 모양 (2026-11-20 GAME-F5-06 · 시작 질문 승인)** — 앞 판은 「절차 기록의 게임 동작을 행의 열쇠 · 동작과 맞춘다」였는데, 행의 동작 칸은 「적 누르기 후 「공격」 누르기」 같은 문장이라 케이스가 누른 오브젝트 주소로는 맞출 수가 없다. 케이스가 그 동작을 부르는 함수 이름이 유일한 열쇠다.
- **맞추는 열쇠는 함수 이름이다** — kit 이 절차마다 게임 동작 · 대상 서버 API 호출이 지나던 화면 객체 함수(`던전화면.공격`) · 도우미(`GM골드`) 이름을 싣고([공통/3](../공통/3-공유계약.md) 「게임 테스트 타입」 `StepResult.gameFns` · `gameFailedFns`), 관리 서버가 그 이름을 행의 함수 칸(`fields.fn`)이나 도우미 칸(`helper`)과 견준다. 행에 `던전화면.공격()` 처럼 괄호를 달아 적었어도 괄호 앞까지만 본다. 행 종류는 가리지 않는다. **함수 칸도 도우미 칸도 빈 행은 실행이 못 고친다** — 케이스 작성이 그 동작을 함수로 만들며 채운다(위 「탐색 플레이 · 조작 맵」 붙인 모양 「지나면」). 이름 꼴은 §7 「조작 맵」 PUT 의 `fields.fn` 이 정본이다
- **통과한 항목** — 그 항목의 절차가 지난 이름과 맞는 「확인」 행에 그 실행의 빌드 번호(`test_run.build_no`)를 적는다. 빌드 목록에 없는 앱으로 돈 실행은 번호가 없어 적지 않는다. 지난 이름은 끝까지 된 동작의 것만이다 — 화면 객체가 「없으면 넘어가기」로 삼킨 실패는 지난 것으로 세지 않는다(깨진 행에 새 빌드가 적힌다). 행의 빌드는 「마지막으로 통과한 실행의 빌드」다 — 옛 빌드로 돌린 실행이 늦게 통과하면 그 번호가 적힌다
- **통과 못 한 항목**(실패 · 미실행) — 조작이 실패한 절차만 본다. 그 절차를 멈춘 오류가 지나던 이름과 맞는 「확인」 행이 「재확인 필요」가 된다. 조작 실패는 실패 유형 「요소를 찾지 못함」 · 「타임아웃」 둘이다(가르는 것은 그 절차의 오류 글 하나다 — `reporting/failureType.ts`). 아래 「실패 자동 수정」이 맡는 실패와 유형 이름은 같지만 보는 자리가 다르다 — 자동 수정은 항목의 실패 유형을 봐서 확인 문장 실패가 하나라도 있으면 「기대 결과 불일치」가 이긴다. 앞 절차의 확인 문장이 실패하고 뒤 절차가 요소를 못 찾아 멈춘 항목은 행이 「재확인 필요」가 돼도 자동 수정은 맡지 않는다(그 행은 다음 탐색 플레이가 다시 해 본다). 기대값이 달라 난 실패 · 연결 문제 · 그 밖의 오류는 길이 틀린 것이 아니라 행을 건드리지 않는다. 실패한 항목은 지난 행에 빌드를 적지 않는다. 화면 객체 함수가 도우미 안에서 불렸으면 둘 다 그 오류가 지나던 이름이라 두 행이 같이 「재확인 필요」가 된다
- **통과는 「재확인 필요」를 풀지 못한다** — 빌드 적기도 「재확인 필요」로 바꾸기도 「확인」 행만 고친다. 같은 실행에서 한 케이스는 통과하고 다른 케이스는 실패한 행은 항목이 끝난 차례와 상관없이 「재확인 필요」로 남는다. 푸는 쪽은 그 행을 디바이스에서 다시 해 본 쪽뿐이다(위 「행 상태는 셋」). 「진행 불가」 행은 실행이 건드리지 않는다
- **언제** — 기록이 남는 케이스 실행(한 건 실행 · 반복 실행도 같다)의 항목이 닫힐 때마다 고친다(`execution/gameResult.ts` — 판정을 넣는 트랜잭션 안, 맵을 못 고쳐도 판정은 남기고 게임 지도 · 서비스 지도 채우기와도 따로 되돌린다). 실행이 끝났을 때는 그 실행 몫이 다 고쳐져 있다. 테스트 실행 · E2E 시나리오 · 호환성 · 기기 성능 실행은 맵을 고치지 않는다. 절차 밖에서 부른 동작과 돌발 팝업 닫기는 지난 행으로 세지 않는다

#### 실패 자동 수정 (결정 36 — 2026-11-20 · 진행판 GAME-F5-11 ~ 14)

**왜** — 게임 케이스는 조작을 몰라서 깨지는 일이 많다(위 「탐색 플레이 · 조작 맵」 「왜」 — ARG 는 반영 뒤 사람이 손으로 고친 케이스 20건 가운데 16건). 그런데 BTS 를 잇지 않은 프로젝트의 실패 판정은 「이슈 등록」 · 「PRD 수정」 둘뿐이라([작성.md](작성.md) §3.6 「★ 결정 목록」 결함 판정) 기획서는 그대로 두고 테스트만 고치는 길이 없다. 그래서 사람이 케이스 파일을 PR 로 고쳤다(PR #833 · #836).
테스트를 고쳐 반영하고 다시 돌려 확인하는 장치는 이미 있다 — [BTS.md](BTS.md) §3.12 「테스트 수정 바퀴」. 다만 사람이 BTS 이슈를 「테스트 수정」으로 옮겨야 시작하고 게임에서는 돈 적이 없다. **이 절은 그 바퀴의 고침 · 반영 조건 · 다시 실행을 그대로 쓰고 시작만 사람 판정에서 실패 유형으로 바꾼다.**

**반영 차례** — 이 절이 적은 것은 목표 꼴이다. 진행판 GAME-F5-12(서버) · GAME-F5-13(에이전트 · 지침)이 반영하기 전까지 게임 실패는 지금처럼 사람 판정으로만 간다. 「재확인 필요」 행과 경로 검색을 쓰므로 GAME-F5-05 · 06 · 08 뒤에 붙인다.

1. **맡는 실패는 조작 실패 둘이다** — 게임 애플리케이션의 케이스 정식 실행이 끝나면 통과 못 한 항목을 실패 유형([리포팅.md](리포팅.md) §8.12 「실패 유형」 — 가르는 함수는 `apps/admin/src/reporting/failureType.ts` 의 `원인을가른다`)으로 가르고 **「요소를 찾지 못함」 · 「타임아웃」만 맡는다**(2026-11-20 사용자 「조작 실패만」). 「기대 결과 불일치」는 게임이 기획서와 다르게 움직인 것일 수 있어 지금처럼 사람이 판정한다. 「환경 오류」와 실행이 멈춰 닫힌 미실행은 테스트를 고칠 일이 아니고 「그 밖」은 까닭을 몰라서 맡지 않는다
   - **「타임아웃」은 유형 통째로 맡는다** — 값 기다리기(「…이 되지 않았습니다」) · 미션 멈춤 · 「게임이 N초 안에 답하지 않았습니다」도 든다. 조작을 몰라 깨진 케이스가 이 꼴로 나온다 — 적을 누르기만 하면 처치 로그가 안 찍혀 미션이 멈춘다(결정 22). 게임이 정말 안 움직여서 난 타임아웃은 아래 3 의 「기획서가 적은 동작이 게임에서 안 되면 고치지 않는다」와 4 의 기다리는 값 재기가 거른다
   - 가르는 실행은 기록이 남는 케이스 실행이다 — 시험 실행 · E2E 시나리오 · 호환성 · 기기 성능 실행은 아니다. 맵 고치기(위 「정식 실행이 맵을 고친다」)가 끝난 뒤에 세운다 — 고침이 「재확인 필요」 행을 읽는다. 자동 수정이 건 다시 실행(아래 5)에서는 새로 세우지 않는다. 한 건 실행 · 반복 실행을 어떻게 볼지는 반영 줄(GAME-F5-12)의 시작 질문에서 정한다
   - **BTS 를 이은 프로젝트는 세우지 않는다** — 그 프로젝트의 실패는 지금처럼 BTS 에 등록되고 사람이 「테스트 수정」으로 옮기면 바퀴가 돈다([BTS.md](BTS.md) §3.12 「지킬 것」 4 · 「테스트 수정 바퀴」). 같은 실패를 두 길이 같이 잡지 않게다. 그 바퀴가 게임 케이스를 고칠 때도 아래 3 의 게임 갈래 지침과 4 의 기다리는 값 재기는 같이 걸린다 — 자식 지침과 재는 코드가 하나다(GAME-F5-13)
2. **실행 하나에 고침 하나** — 맡은 케이스를 작성 요청 하나에 담는다(BTS 바퀴는 이슈의 테스트마다 하나다). 폰이 하나라 케이스마다 따로 잡고 깔고 켜면 그 시간이 고침보다 길고, 같은 까닭(버튼 이름이 바뀜)으로 깨진 케이스 여럿은 한 번에 고쳐야 한다
   - **그 애플리케이션에 열린 작성이 있으면 세우지 않는다** — 사람 확인을 기다리는 앞 자동 수정도 열린 작성이다([작성.md](작성.md) §3.6 「★ 결정 목록」 「서버 막기」). 뒤에 세워 기다리게 하면 실행마다 요청이 쌓이고 그 사이 다른 작성이 같은 케이스를 고친다. 다음 실행이 다시 가른다 — 서버가 스스로 세우는 「기획서에 없는 화면」 작성이 같은 판정으로 안 서는 것과 같다
   - 맡을 실패가 너무 많으면 세우지 않는다 — 빌드나 팜이 깨진 것으로 본다. 상한은 반영 줄(GAME-F5-12)의 시작 질문에서 정한다
   - 고침이 도는 케이스(같은 케이스 · 대상 서버 — 아래 5 의 다시 실행이 끝나기 전까지)는 새로 세우지 않는다(테스트 수정 바퀴 1 과 같다)
   - **자동 수정이 실패 · 그만둠으로 끝난 케이스는 다음 실행에서 또 조작 실패여도 다시 맡지 않는다** — 실행마다 같은 고침을 되풀이하면 폰 시간과 사용 한도만 쓴다([BTS.md](BTS.md) §3.12 결정 11 과 같은 까닭). 언제 다시 맡는지(그 뒤 실행에서 통과 · 그 케이스를 고친 작성의 반영)는 반영 줄의 시작 질문에서 정한다.
     「다시 돌리니 통과」로 끝난 케이스(아래 3 의 1)는 여기 들지 않는다 — 한 번 흔들린 것 때문에 뒤에 오는 진짜 조작 실패를 놓치지 않게다. 같은 케이스가 되풀이해 흔들릴 때 몇 번까지 맡을지도 그 시작 질문에서 정한다
3. **고침** — 작성 에이전트의 게임 자식이 폰(PC 게임은 PC — 결정 28)에서 한다. 지침은 `tpx-author` `references/apply.md` §7 「테스트 고침」에 게임 갈래를 더한다(GAME-F5-13)
   1. **케이스마다 그대로 한 번 돌려 본다.** 통과한 케이스는 고치지 않는다 — 흔들림이라 고칠 곳이 없다. 「다시 돌리니 통과했어요」로 적고 나머지 케이스를 이어 간다. 처음 실행의 그 실패는 그대로 남아 사람이 본다. 그 케이스 때문에 「재확인 필요」가 된 행은 아래 2 · 3 대로 다시 해 보고 올린다 — 행이 풀려야 경로 검색이 그 길을 낸다
   2. **실패한 동작을 다시 해 본다** — 그 케이스의 실패 절차와 정식 실행이 「재확인 필요」로 단 행을 폰에서 해 본다. 넘기는 자료는 실패한 절차 · 오류 원문 · 실패 순간 오브젝트 목록(`game-tree.txt`) · 게임 오류 로그(`game-errors.txt` — 아래 「실행 결과」)다. 지금 실패 자료 통로([작성.md](작성.md) §7 `GET …/:id/trace`)는 브라우저 trace 요약만 주는데 게임 항목은 trace 를 안 남긴다 — 게임 자료를 넘기는 길은 아래 블록 몫이다
   3. **맵 행을 고친다** — 다시 해 본 행은 빌드를 실어 「확인」이나 「진행 불가」로 올린다(§7 「조작 맵」 — 빌드를 실은 행만 「재확인 필요」를 푼다). 바뀐 길은 새 행으로 적는다. 맵에 길이 없던 동작도 폰에서 통과하면 행으로 적는다(탐색 플레이 차례 3 과 같다)
   4. **케이스를 고친다** — 준비 · 조작 단계를 경로 검색 결과로 다시 옮긴다(위 「경로 검색」). **기대값과 확인 문장은 건드리지 않는다** — 고치는 것은 「어떻게 가나」뿐이다. **기다리는 값도 기대값이다** — `waitFor` 의 `text` · `waitForValue` 의 값 · `repeatUntil` 의 `goal` 은 그대로 둔다. 그 값이 될 때까지 기다리는 문장이 게임 케이스에서는 확인 노릇을 한다. 얼마나 기다리나(`timeoutMs` · `stallMs`)는 고쳐도 된다
   5. **게임 돌려 보기와 일부러 고장 내 보기를 한다** — 고친 케이스를 디바이스 팜 폰에서 돌리고 고장을 내 본다(위 「작성 — 한 바퀴」 6). 지금 「테스트 고침」 지침은 웹 돌려 보기 명령(`authoring:run -- 한번`)만 적는데 그 명령은 게임 케이스를 빼고 돌아 「돌릴 케이스가 없다」로 끝난다 — GAME-F5-13 이 게임 돌려 보기(`authoring:run -- 게임 <폴더>`)와 고장 내 보기의 게임 갈래를 단다. PR 본문 「테스트 고침」 줄의 다시 돌린 횟수도 게임 돌려 보기 기록을 세게 한다(지금은 웹 돌려 보기 기록만 세어 게임은 늘 0 이다)
   - **기획서가 적은 동작이 게임에서 안 되면 고치지 않는다** — 버튼이 없어졌거나 창이 안 열리는 것은 게임 결함일 수 있다. 다른 길로 돌아가 통과시키면 그 결함이 가려진다. 「고칠 곳을 찾지 못했어요」와 본 것 한 줄을 남기고 끝낸다
   - **돌발 팝업 행은 더하지 않는다** — 올린 팝업 행은 PR 반영과 상관없이 다음 실행부터 kit 이 그 창을 닫는다(관리 서버가 「확인」 팝업 행을 전부 싣는다 — 위 「돌발 팝업 자동 닫기」 붙인 모양). 오류 창을 잘못 올리면 사람이 PR 을 보기도 전에 실패가 통과로 바뀐다. 목록에 없는 창에 막혔으면 고치지 않고 그 창을 적어 끝낸다 — 행은 다음 작성의 탐색 플레이가 적는다(작성도 서버에는 안 올리고 PR 머리에만 싣는다 — 병합 뒤 맵에 올리는 길은 진행판 GAME-F5-15 · 2026-11-20 사용자)
   - 다시 해 보기가 헛돌지 않게 끝을 둔다 — 시간 상한(탐색 플레이 차례 4)으로 할지 목표마다 시도 횟수([작성.md](작성.md) §3.6 「★ 앱 탐색」 결정 7 — 사용자가 앱에서는 시간 상한을 물리고 횟수를 골랐다)로 할지는 GAME-F5-13 시작 질문에서 정한다
   - **PR 없이 끝난 요청은 서버가 스스로 폐기한다** — 고칠 것이 없던 요청(모두 「다시 돌리니 통과」이거나 「고칠 곳을 찾지 못했어요」)은 사람이 승인할 것이 없다. 끝난 작성은 폐기 전까지 열린 작성이라 그대로 두면 그 애플리케이션의 새 작성과 다음 자동 수정을 막는다
4. **반영** — 테스트 수정 바퀴 3 의 세 조건(기대값 그대로 · 확인 문장 수 그대로 · 일부러 고장 내 보기 통과)이 고친 케이스마다 맞으면 Commander 가 반영을 스스로 세운다([BTS.md](BTS.md) §3.12 결정 24 · 2026-11-11 사용자 「B」). 하나라도 어긋나거나 못 쟀으면 그 PR 전체를 사람이 테스트 작성 「결정 필요」 승인 대기에서 반영한다. 재는 법 · 「재지 못함」 규칙은 그 절이 정본이다
   - **서버가 스스로 반영하는 예외가 넓어진다** — 지금 예외([작성.md](작성.md) §3.6 「예외 하나」)는 Issue Bunker 바퀴의 PR 이고 근거가 「바뀐 것이 그 케이스 하나」다. 이 길은 이슈가 없고 한 PR 에 케이스가 여럿이라 근거가 「바뀐 테스트 파일이 고친 케이스 파일들뿐이고 케이스마다 세 조건이 맞는다」가 된다. 그 문장을 고치는 것은 아래 블록 몫이다
   - **게임 케이스는 기다리는 값도 잰다** — 위 3 의 4 가 적은 기다리는 값이 고치기 전과 같아야 한다. 바퀴의 「기대값 그대로」는 `verify` 만 재서 기다리는 값을 바꾼 고침이 세 조건을 그냥 지난다. 재는 법은 GAME-F5-13 이 더한다
   - **화면 객체 · 도우미 파일을 고친 고침은 지금 규칙으로 사람이 반영한다** — 바퀴는 바뀐 테스트 파일이 고친 케이스 파일뿐일 때만 잰다(그 절 3 「바뀐 테스트 파일이 고친 케이스 파일뿐이어야 한다」). 게임 조작은 화면 객체 함수에 모여 있어 이 경우가 많을 수 있다 — 넓힐지는 실측(GAME-F5-14)을 보고 정한다
5. **확인** — 반영이 끝나면 서버가 고친 케이스만 다시 실행한다. 디바이스 고르기 · 디바이스 팜이 꺼졌을 때 · 준비 실패는 테스트 수정 바퀴 4 · 5 와 같다. 다 통과하면 「수정 후 통과」로 끝난다. 하나라도 실패 · 미실행이면 **다시 고치지 않고 사람에게 넘긴다** — 처음 실행의 실패 카드가 그대로 서고([실행.md](실행.md) §8.3), 판정이 실패이고 덮는 요구가 지금 판에 있는 케이스는 「결정 필요」 결함 판정에도 선다([작성.md](작성.md) §3.6 「★ 결정 목록」 「실패 판정에 드는 것」). 미실행으로 끝난 케이스와 요구가 없는 케이스는 결함 판정에 들지 않아 실패 카드에서만 보인다 — 자동 수정이 실패했다는 표시를 그 카드에 다는 것은 아래 7 의 시안이 정한다
   - 처음 실행의 통과 · 실패 숫자는 바꾸지 않는다([BTS.md](BTS.md) §8.15 「자동 수정 표시」 B). 실행이 스스로 다시 도는 것이 아니라 고친 뒤 확인하는 실행이다 — 자동 재시도를 쓰지 않는 규칙([실행.md](실행.md) §3.2)과 어긋나지 않는다
6. **차례** — 열린 작성이 없을 때만 서므로(위 2) 애플리케이션마다 한 번에 하나다. 자동 수정 요청도 열린 작성이라([작성.md](작성.md) §3.6 「★ 결정 목록」 「서버 막기」) 반영되거나 폐기될 때까지 그 애플리케이션의 새 작성은 409 `AUTHORING_OPEN` 이고 다음 자동 수정도 서지 않는다 — 세 조건이 맞으면 바로 반영되고 사람 확인에 걸리면 승인 대기에 남는다
7. **보이는 곳** — 새 화면은 없다. 테스트 수정 바퀴의 「자동 수정 표시」([BTS.md](BTS.md) §8.15 — 케이스 목록 표시 · 서랍 「자동 수정 기록」 · 실패 카드 「수정 후 통과」 · 작성 목록 구분 「자동 수정」)를 BTS 없는 게임 프로젝트에도 보인다. 요청한 사람이 서버라 작성 목록의 작성자는 「Agent」로 적는다 — 지금 「Agent」는 미검증 화면 줄뿐이라([작성.md](작성.md) §3.6 「★ 결정 목록」 「작성 목록 줄」) 이 줄을 더하는 것은 아래 블록 몫이다. 사람 · 이슈가 없는 「요청」 줄에 무엇을 적을지, 사람 확인에 걸린 까닭(BTS 바퀴는 이슈 댓글)을 어디에 보일지, 고침이 도는 동안과 실패로 끝난 뒤 실패 카드 · 결함 판정 항목에 상태를 어떻게 보일지는 시안으로 정한다(GAME-F5-12 — 시안 먼저)
8. **기록** — 케이스마다 테스트 수정 바퀴의 기록(`bts_test_fix` — [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「BTS 연동 표」)과 같은 것을 남긴다. 그 표를 넓힐지 새 표를 둘지는 아래 블록대로 반영 줄이 정한다

#### 창 훑기 — 게임 화면 지도 (CLI `crawl`)

- **단위** — 창(UI Canvas 아래 켜지고 꺼지는 묶음)과 장소(구역). 웹의 「같은 틀」 자리가 창 루트 경로다 — 같은 창의 목록 줄 · 슬롯은 대표 하나다
- **차례** — ① 로그아웃 상태 창(로그인 · 가입 · 서버 설정) ② 로그인 → 캐릭터 선택 · 생성 창 ③ 월드 HUD 버튼을 하나씩 눌러 열리는 창을 찍고 닫는다(창 안 버튼은 한 단계 더) ④ 장소마다 어드민 API 로 순간이동해 그 자리를 찍는다.
  CLI `crawl` 은 지금 화면에서 ③ 꼴(버튼을 하나씩 눌러 새로 뜬 창을 찍고 닫기 버튼 → 저절로 사라지기 → 폰 뒤로 키로 닫기)만 한다. ①② 로 화면을 맞추고 `crawl` 을 다시 부르는 것은 작성 AI 다 — 상태마다 폴더를 나눠(`game-crawl/<이름>/`) 훑고 훑자마자 견주기 명령(`npx tsx scripts/authoring-game-crawl.ts <폴더> '<상태>'`)을 돌린다(GAME-F1-10 · 자식 지침 `tpx-author` `references/game.md` §4).
  **④ 장소마다 순간이동과 조건이 있어야 열리는 창은 상태 도우미 부르기 명령으로 한다** (2026-10-24 GAME-F1-12b — 위 「작성 — 한 바퀴」 붙인 모양) — 둘 다 작성 중에 상태 도우미(어드민 API · GM 명령)를 불러야 해서 어드민 키를 넘기는 줄로 미뤘다(2026-10-23 GAME-F1-10 시작 질문 승인 · GAME-F1-11 에서 F1-12 로 옮김 → GAME-F1-12 에서 GAME-F1-12b 로 나눔).
  장소는 게임 지도의 `zone:` 요소마다 도우미의 순간이동으로 옮긴 뒤 `crawl --max 1 --out game-crawl/zone-<구역>` 으로 그 자리만 찍고 견주기 명령에 구역을 준다(`… '<상태>' <구역>`) — 시작 화면이 장소 기록 `game:<장면>/zone:<구역>` 이 되고 견주기가 `game.json` 에 구역을 남겨 에이전트가 같은 열쇠로 올린다. 조건부 창은 도우미로 조건(골드 · 아이템 · 레벨)을 만든 뒤 그 창을 연 화면에서 `crawl` 을 다시 부른다(폴더를 나눈다). 구역 이름은 글자 · 숫자 · `_` `-` 64자까지다(`scripts/authoring-game-crawl.ts` `구역꼴`). 어드민 API 가 없고 GM 명령만 있으면 잡은 폰의 채팅 칸에 control-cli 로 넣는다(위 「작성 — 한 바퀴」 붙인 모양 GAME-F1-12b). 둘 다 가이드에 없으면 안 한다. 결과 파일 꼴의 정본은 control_cli README 「창 훑기」
- **위험한 누르기** — 크롤 전용 버림 캐릭터로 돈다(캐릭터 이름 앞머리 `qacrawl` · 끝나면 정리 — 작성 끝에 상태 도우미의 캐릭터 지우기를 부르기 명령으로 부른다. 가이드에 지우는 길이 없으면 남기고 결과 요약에 적는다 · 2026-10-24 GAME-F1-12b). 캐릭터 삭제 · 탈퇴처럼 크롤을 끝내는 버튼은 누르지 않는다(웹 「탈퇴 멈춤」과 같다)
- **상한** — 창 60개 · 10분 안쪽, 작성 30분 예산 안이다. 숫자의 정본은 CLI 코드 상수 `CRAWL`(control_cli `src/crawl.ts`)이다
- **재사용** — 창마다 글자 · 구조 지문을 남긴다. 다음 작성 때 지문이 같으면 다시 안 훑는다(웹 30일 그물). 바뀐 창만 다시 훑는다.
  **붙인 모양 (2026-10-23 GAME-F1-10)** — `crawl` 은 지문을 재려고 창을 다 연다. 다시 안 하는 것은 AI 의 정리와 올리기다. 견주기 명령이 창마다 `같음`(같은 상태 · 같은 열쇠의 저장 기록과 지문 둘 다 같고 훑은 지 30일 안) · `변경` · `새 창` 을 찍고(`scripts/authoring-game-crawl.ts`), AI 는 같음이면 `game-kept/` 의 저장 기록을 읽고 바뀜 · 새 창만 기록 파일 끝에 「## 정리」(무엇 하는 창 · 주요 오브젝트 · 이어지는 항목)를 덧붙인다.
  에이전트는 견주기 명령이 남긴 표시(`game.json` — 상태 · list.json 지문 · 창마다 같음)대로 바뀜 · 새 창만 화면 기록으로 올린다(`PUT …/screens` — 열쇠는 아래 「지도」의 `game:<장면>/<창 경로>`(창 경로는 같은 이름 형제 순번을 뗀 틀) · 시작 화면은 `game:<장면>` · 연결은 창을 연 버튼). 자식이 본 판정과 올리는 판정이 같아야 정리를 덧붙이지 않은 창이 정리된 기록을 덮지 않는다(웹이 크롤 목록의 「같음」을 믿는 것과 같다). 견주기 뒤에 같은 폴더를 다시 훑었으면(지문이 다르다) 그 폴더는 안 올린다.
  같음은 안 올려 훑은 날이 그대로라 30일 그물이 돈다 — 다만 같음 창에서 서버가 모르는 창으로 가는 연결이 생겼으면(지난 훑기가 상한에 걸려 못 연 창) 서버의 기록 · 지문 · 훑은 때를 그대로 둔 채 연결만 보태 다시 올린다. 본 창은 전부 찾은 창(`…/screens/done` 의 seen)으로 남긴다.
  **못 본 창의 옛 기록은 지우지 않는다**(done 의 complete 빈 목록) — 한 화면에서 시작한 훑기라 그 상태를 다 봤는지 모른다. 사라진 창의 기록이 남는 한계는 상태 도우미로 다 도는 훑기가 생길 때 다시 본다. 기록 · 이름 · 연결에 테스트 계정 비밀번호가 있으면 하나도 안 올리고 PR 본문 머리 줄에 적는다
- **AI 몫** — 프로그램이 못 연 조건부 창을 연다(GAME-F1-12b — 상태 도우미) · 창 기록에 「무엇 하는 창 · 주요 오브젝트 · 이어지는 기획서 항목」을 적는다 · 창 기록은 기대값 근거가 아니다
- **역기획서** (2026-11-04 사용자 「게임은 역기획서만」 · 진행판 APP-F2-01 결정 · 반영 APP-F2-06) — 기획서 없이 「실제 화면과 대조」로 보내면 이 창 훑기 기록으로 표준 기획서 게임 절 항목(전부 `확인 필요`)과 미확정 케이스를 쓴다. 규칙 · 확률 · 데이터 표는 화면으로 정하지 않는다.
  게임은 지금처럼 SDK 를 넣은 QA 빌드(APK)로 돌린다 — 스토어 패키지 이름은 받지 않는다(설정 400 — 정본은 [러너.md](러너.md) §5.2 「플레이스토어 앱 — 패키지 이름」). 역기획서 쪽은 [작성.md](작성.md) §3.6 「★ 역방향」 「앱 · 게임 역방향」(1 · 5 · 11 · 12), 자식 절차는 `tpx-author` `references/game.md` §7 이다

  **게임 애플리케이션 요청의 화면 기록 셋(`GET` · `PUT …/screens` · `POST …/screens/done`)은 앱 줄에 둔다**(2026-10-23 GAME-F1-10 시작 질문 승인 — `apps/admin/src/prd/agentRoutes.ts` `화면줄`). 앱 줄은 게임 첫 화면을 읽는 줄과 같다(요청에 대상 서버가 있으면 그 줄, 없으면 앱 파일 경로가 있는 첫 줄 · 운영 줄은 건너뛴다). 창 훑기는 그 줄의 앱 파일로 켠 게임을 본 것이다. 앱 줄이 없으면 웹처럼 빈 목록 · 400 `BAD_SCREEN` `env` 다
- **지도는 화면에 보이지 않는다** — 웹 지도처럼 AI 가 다음 작성 때 읽는 내부 기록이다. 새 화면 · 카드 · 탭을 더하지 않는다(2026-10-22 사용자 「이 지도를 보여주지 않는데」). 웹에서 지도에서 뽑아 보이는 것은 「케이스가 안 거친 API」 카드 수 하나뿐이다(2026-10-26 — 그 카드는 테스트 작성 결정 목록 「미검증 API」로 옮긴다 · 도메인/작성 §3.6 「★ 결정 목록」)

- **담는 법** (내 결정) — 지도마다 표를 만들지 않고 표 둘에 종류만 나눈다: 게임 요소(종류 · 열쇠 · 이름 · 값 · 근거 요구 번호)와 요소를 거친 케이스. 케이스는 선언에 닿는 요소를 적는다(`defineCase` 의 `elements` — `techniques` 처럼 AI 가 쓰고 빠른 검사가 지도에 있는지 본다)
- **서버 값** — 데이터 대조 케이스(API 로 표 전 줄 대조)가 kit 도우미로 줄마다 결과를 남기고, 실행 결과(`elementChecks` — 공통/3-공유계약 「게임 테스트 타입」)로 admin 이 요소에 쓴다(열쇠마다 마지막 값 하나 — 항목마다 받은 줄은 `run_item.element_checks` 에 따로 남아 실패 카드 「오브젝트」 탭이 된다, 2026-10-31 WEB-F7-24). 지도가 「기획서 값 · 서버 값 · 같음 / 다름」으로 보인다(AI 가 읽는다)
- **덮음** — 재화 흐름은 케이스 선언 + 통과로 센다. 실행 뒤 서버 원장 기록 종류로 자동으로 맞추는 것은 나중이다
- AI 는 작성 전에 지도를 파일로 받는다(웹 `api-map.txt` 꼴). 지도는 기대값 근거가 아니다 — 근거는 표준 기획서 항목뿐이다

- **통신 끊기(요청 중 와이파이 끊기)도 1차에 넣는다** — 0단계에서 디바이스 팜 Appium 의 `mobile: setConnectivity { wifi: false }` 가 됐다(되돌리기도 됐다). 모바일 데이터는 팜 폰에 SIM 이 없어 못 봤다 — 와이파이만 끊는다(케이스는 `폰상태에서(driver, { 네트워크: '끊김' }, …)` 로 끊는다 — 켜져 있는 것만 끈다. 정본은 [러너.md](러너.md) §5.2 「범용 앱 부품」)
- **붙인 모양 (2026-10-23 GAME-F1-11 시작 질문 승인)** — 설계 판정(`scripts/authoring-design.ts`)이 **종류 「게임」 애플리케이션 요구에만** 게임 낱말 칸을 더한다 — 「구매」 · 「저장」은 웹 기획서에도 있어 웹 판정을 흔들지 않게. 게임 여부는 에이전트가 원장을 지을 때(원장 준비 · 원본 원장과 옮기기 대조 · 올리기 판정 · 반영 계획)와 자식이 원장을 다시 지을 재료(`ledger-base.json` 의 `게임`)로 넘긴다.
  칸은 웹과 같은 경계 · 예외이고 기법도 웹 다섯 안이라 빠진 칸 막기 · 「설계 거절」 · 기법 대조가 그대로 돈다 — 확률 「성공 40%」 → 경계 0% · 100%(②) + 예외 결정 테이블(①) · 정상 칸은 ③ · 재화 쓰는 곳 「1,000골드」 → 경계 999 · 1,000골드(금액이 없으면 「비용 − 1 · 비용」) · 재화 모자람 → 예외 동등 분할 · 상태 바뀜(사망 · 성향 · PK · 장착 · 해제) → 예외 상태 전이 · 「리젠 20초」 · 「반경 25m」 · 「Z 200 부터」 → 경계 바로 앞 · 그 값(한도 낱말이 붙으면 웹과 같은 2값 — 「25m 이내」 → 25m · 26m. 좌표는 「좌표」가 앞에 오거나 한도 낱말이 뒤에 올 때만) · 끊김 뒤를 적은 문장(재접속 · 저장된다 · 유지된다) → 예외 상태 전이.
  **데이터 표는 칸을 뽑지 않는다** — 정상 케이스 하나에 API 전 줄 대조 · 화면 대표 줄 절차 둘이다. **기획서가 적지 않은 연타 · 끊김은 오류 추정 줄이다** — 두 번 누르기에 구매 · 강화 · 판매를 더하고 게임 항목 셋(통신 끊기 · 다시 켜기 · 내렸다 올리기)을 더한다. 서버 실패는 게임이 요청 실패를 거는 길을 서비스 가이드에 적었을 때만, 그 길이 실패시키는 요청을 부르는 동작에만 쓰고, 남의 것 · 없는 주소는 안 쓴다(AUT-F4-12). 정본은 [작성.md](작성.md) §3.6 「설계 기법」 「오류 추정」이다(앱도 통신 끊기를 쓰지만 해 보는 법이 다르다. 종류마다 드는 항목은 같은 장 「종류별 작성 AI」 「종류별 기준」 · 2026-11-18). 줄 쓰는 법은 `tpx-cases` `test-design.md` 「게임 애플리케이션」.
  「PRD 관리」의 「설계 미리보기」는 화면이 애플리케이션 종류를 몰라 웹 칸만 보인다

#### 실행 결과 (결정 11)

새 화면은 없다. 앱 케이스 결과 화면을 그대로 쓴다 — 단계별 판정 · 캡처 스크린샷 · 기기 정보 · 통과 못 한 항목의 팜 화면 영상 · logcat(`apps/admin/src/web/FarmEvidence.tsx`) · 실패 유형과 한 줄([리포팅.md](리포팅.md) §8.12 「실패 유형」).

- **실패 유형** — 게임 드라이버 오류 문구를 실패 유형 분류(`apps/admin/src/reporting/failureType.ts`)가 알아보게 맞춘다: 오브젝트 못 찾음 → 요소를 찾지 못함(2026-11-06 앞 이름 「요소 미검출」) · 기다림 초과 → 타임아웃 · 게임 연결 끊김 → 환경 오류(이름은 화면 · [리포팅.md](리포팅.md) §8.12 「실패 유형」 것. 맞춘 문구는 그 절 차례 ③ ~ ⑤ — 2026-10-23 GAME-F1-09)
- **통과 못 한 항목에 둘을 더 남긴다** — ① 실패 순간 화면에 있던 오브젝트 목록(트리 파일 `game-tree.txt` — 「이름이 바뀌었나 · 창이 안 열렸나」) ② 케이스 동안 게임에서 난 오류 로그(`game-errors.txt` — Unity 예외 · 에러 — SDK 가 받아 둔다. 웹 「콘솔 오류」 자리. 없으면 파일이 없다 — 정기 실행은 오류가 없어도 머리 줄만 있는 파일을 두고, 통과 항목도 Exception 만 남긴다. 통과 항목의 것은 안정화 지표 몫이라 결과 화면에는 안 보인다 · [안정화](안정화.md) §7 kit 블록). 자리는 화면 영상 · logcat 옆 「다운로드」 줄이다 — kit 이 팜 증적 폴더에 두어 지금 목록이 그대로 낸다(GAME-F1-09 — 꼴은 [공통/3](../공통/3-공유계약.md) 「게임 테스트 타입」). 실행 결과 실패 카드에서는 ① 이 「다운로드」 줄 대신 증거 칸 「오브젝트」 탭에 그 항목의 게임 요소 대조 표와 같이 펼쳐 보인다(2026-10-31 WEB-F7-24 · [DESIGN.md](../../DESIGN.md) 「증거 칸은 종류마다 탭만 다르다」). 항목 상세 · E2E 결과는 「다운로드」 줄 그대로다
- **통과한 항목의 「영상 보기」** — 누르면 디바이스 팜에서 받아 온다(팜 보관 30일 안). 같은 화면이라 앱 케이스에도 붙는다. 30일이 지났거나 팜이 꺼져 있으면 까닭 한 줄을 보인다.
  **첫 조각(3분)만 보인다** — 팜이 3분마다 파일을 나누는데 항목 하나는 길어야 5분이라 대부분 한 조각이다(게임 시나리오는 한도가 없어 길어질 수 있다 — 첫 3분만 보인다)(2026-10-23 GAME-F1-09 시작 질문 승인). 러너는 통과 항목의 Appium 연결 번호 파일을 남기고, admin 이 그 번호로 팜에 묻는다(받아 저장하지 않고 흘려보낸다 — 우리 저장 공간이 그대로다)
- 추적표 · 정기 실행 · 흔들림 표시는 그대로다
- **항목이 닫힐 때 조작 맵 행을 고친다** (2026-11-20 GAME-F5-06) — 통과한 항목이 지난 행에 빌드를 적고 조작이 실패한 동작의 행을 「재확인 필요」로 바꾼다. 정본은 위 「탐색 플레이 · 조작 맵」 「정식 실행이 맵을 고친다」

#### 게임 쪽이 준비할 것 (결정 16)

Ashveil 은 QA Hub 를 염두에 두고 만들어 어드민 API(상태 만들기 · 결과 고정 · 확률 설정 · 정리)가 있다. 고객사 게임에는 없을 수 있다. 이 목록은 납품 문서(고객사 요청 목록)로 쓴다.

- **꼭** — ① QA 빌드에 우리 SDK ② 상태를 만드는 길(어드민 API 또는 GM 명령) — 캐릭터 · 재화 · 아이템 · 위치 · 결과 고정 · 확률 설정 · 정리 · 계정 초기화 ③ 테스트 계정 만들기(아이디 · 비밀번호, 또는 QA 빌드의 게스트 · 개발용 로그인 — 소셜 로그인만 있는 게임) ④ QA 빌드에 QA 서버 주소를 박는다(아래 「서버 주소는 QA 빌드에 박는다」)
  ⑤ **전투 · 재화 로그**(게임 시나리오를 쓰려면 — 결정 19 · 2026-11-18) — 게임 서버가 일어난 일을 한 줄씩 쌓고 「이 번호 뒤 줄」을 내주는 주소. 줄마다 이어지는 번호 · 시각 · 종류 · 누가 · 누구에게 · 무엇으로(스킬 · 아이템) · 값 · 그때 조건(레벨 · 직업 · 장비 · 인원)이 찍힌다. 게임이 셈한 배율은 안 찍어도 된다 — 판정이 조건으로 다시 계산한다. 시험 서버에서만 쌓는다. 게임 종류마다 찍히는 때가 다르다(위 「게임 시나리오」 「게임 종류 셋」 — 판 규칙형은 한 수마다 · 성장 재화형은 재화가 늘고 줄 때마다). 없으면 게임 시나리오는 못 쓰고 「개발팀에 요청할 것」으로 올린다(결정 25)
  Boss Room 예(boss-room `showcase` 커밋 9b089a0 · 31b2196) — `GET /test/log?since=N`(어드민 키 머리) → `{ ok, last, lines: [{ seq, at, kind, players, … }] }`. `kind` 는 `hit` · `heal` · `kill` · `item` · `levelup`, `hit` · `heal` 은 `from` · `to` · `skill` · `value` · `hpBefore`, `kill` 은 `by` · `npc` · `gold` · `exp` · `party`, `item` 은 `by` · `item` · `count`. 사람 쪽 칸(`from` · `to` · `by`)에 `user` · `level` · `job` · `weapon` · `armor` · `accessory` 가 같이 찍힌다. `BOSSROOM_GM=1` 서버에서만 쌓고 5,000줄까지다. 계정을 되돌릴 때 찍히는 기본 지급 아이템 줄은 `user` 가 비어 있다 — 자기 계정 줄을 고르면 빠진다
- **있으면 좋은 것** — 시도마다 적용 확률 · 뽑은 숫자 기록(확률 ③ 을 서버 쪽에서도 본다) · QA 환경 요청 기록(창 → API 지도를 채운다) · 요청 실패 걸기(다음 요청 N번을 실패시키는 시험 주소 — 오류 추정 「서버 실패」를 쓰려면. Boss Room `POST /test/fail { path, count }` · 2026-11-18 AUT-F4-12)
- GM 명령은 SDK 가 채팅 창에 대신 친다 — UI 조작이라 SDK 에 새 기능이 없다(글자 넣기 · 보내기). 둘 다 없으면 그 케이스는 보류다(사냥으로 준비하지 않는다)
- **서버 주소는 QA 빌드에 박는다** (2026-10-25 GAME-F2-18 시작 질문 승인) — QA Hub 는 게임에 서버 주소를 넘기지 않는다. 대상 서버 줄 주소는 게임에 가지 않고 케이스의 어드민 · 서버 API 와 작성 · 부하 쪽이 쓴다.
  폰에 넣는 설정 파일(Ashveil `server-config.json`)은 디바이스 팜이 폰을 놓을 때 앱 데이터와 함께 지우고, 로그인 화면의 서버 설정 버튼은 게임마다 화면이 달라 케이스마다 주소를 넣는 조작이 따로 든다. GAME-F1-14 의 빌드 39 는 주소를 비워 만들어 폰 안 `127.0.0.1:8080` 으로 갔다.
  Ashveil 에서는 빌드 단계의 기본 서버 주소 칸(저장소 변수 `GAME_SERVER_URL` · 수동 실행 입력 `serverUrl`)을 채우면 된다 — 빌드 39 까지는 비어 있었고, 채우는 것은 Ashveil 쪽 일이다.
  **박은 서버와 대상 서버 줄 주소는 같은 서버여야 한다** — 케이스가 어드민 API 로 만든 캐릭터 · 아이템을 게임이 봐야 한다. QA Hub 는 둘이 같은지 보지 않는다 — 어긋나면 준비한 상태가 게임에 안 보여 케이스가 빨개진다.
