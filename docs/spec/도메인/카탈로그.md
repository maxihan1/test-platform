### 3.1 Catalog — 무엇을 테스트할 수 있는가

- **책임**: 소스 폴더를 스캔해 `CaseSpec`을 추출하고 검색 가능하게 유지
- **애그리거트 루트**: `TestCase` (식별자 `tcId`)
- **불변식**
  - `tcId`는 전역 유일. 중복 발견 시 스캔 실패시키고 양쪽 파일 경로를 보고한다
  - **코드가 진실의 원천**. DB의 `test_case`는 캐시이며, 스캔 때마다 덮어쓴다
  - 코드에서 사라진 케이스는 삭제하지 않고 `is_active = false`로 둔다 (과거 실행 이력이 참조하므로)
  - **카탈로그는 실행 결과를 알지 못한다.** `test_run`·`run_item`을 읽지 않는다. 목록의 `마지막 결과` 칸은
    실행 컨텍스트가 내는 응답으로 채운다. 이 경계가 무너지면 카탈로그가 실행 테이블 구조에 묶여
    §5.3의 이음새가 같이 무너진다. 검색 조건과 화면 규칙은 **§8.1이 정본**이다
  - **예외 하나 — 저장값 `case_input` 은 읽는다** (2026-09-29). 실행 결과가 아니라 케이스마다 한 벌 둔 입력값이고,
    케이스 응답의 `savedInput` 에 싣는다(§7). 표의 주인은 실행이고 카탈로그는 **SQL 로 읽기만 한다**(공통/4-데이터모델 §6)
  - **`test_case`의 `param_schema`·`expected_schema`는 캐시다.** 스캔 때마다 덮어쓰므로 과거 실행의 증적은
    이 테이블을 읽어 만들지 않는다. 증적이 읽을 값은 실행 기록에 따로 박제한다 (§3.3 증적 재현)
  - 나중에 검색엔진을 붙이더라도 옮기는 것은 **케이스 속성뿐**이고 실행 결과는 옮기지 않는다.
    색인해 두면 실행이 끝날 때마다 어긋나고, 어긋난 색인은 조용히 틀린 목록을 보여준다 (→ §5.3)
- **추출 방식** (2026-09-16 결정): 스캐너는 `tests/**/*.spec.ts`를 환경변수 `PLATFORM_SCAN=1`을 켠 채
  동적으로 import 해 `export const spec`을 읽는다. kit의 `test()`는 이 변수가 켜져 있으면 Playwright에
  등록하지 않고 조용히 반환한다. zod 스키마는 실행해야 JSON Schema가 되므로 텍스트 파싱은 하지 않는다.
  admin 이미지에 `@platform/kit`·`zod`·`@playwright/test`가 설치돼 있어야 한다
- **스캔 시점** (2026-09-16 결정): admin은 **기동할 때 한 번** 자동으로 스캔한다. 배포는 컨테이너 재기동이므로
  배포 직후 목록이 최신이 된다. 그 밖에는 화면의 `다시 스캔` 버튼(→ `POST /api/catalog/scan`)으로 돌린다.
  기동 시 스캔이 실패(tcId 중복 등)해도 admin은 뜬다. 실패 사유는 마지막 스캔 결과(`GET /api/catalog/scan`)에 남기고
  목록 화면 위에 보여준다
- **미확정 꼬리표** (2026-09-25): 스캐너는 `spec.unconfirmed` 를 읽어 `test_case.unconfirmed` 에 둔다.
  미확정이 무엇인지는 [작성.md](작성.md) §3.6 「★ 역방향 — 화면과 대조한다」 · 「★ 테스트 두 갈래」, 꼬리표와 K11 은
  [공통/2-명세선언.md](../공통/2-명세선언.md), 칸은 [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「역방향 칸」이 정본이다
  - `test_case.unconfirmed_since` 는 **스캐너가 관리한다.** 처음 미확정으로 본 스캔의 시각을 넣고,
    **미확정인 동안은 그대로 둔다** — 사유 글자가 바뀌어도 유지한다. 꼬리표가 풀릴 때만 `NULL` 로 돌린다.
    **스캔마다 덮어쓰지 않는다** — 덮으면 나이가 매번 0 이 돼 오래된 미확정이 안 보인다
  - **왜 사유가 바뀌어도 유지하나** — 작성 에이전트가 같은 케이스를 다시 만들며 사유 문장을 조금만 바꿔도 나이가 0 으로 돌아가면,
    오래 답을 못 받은 미확정이 「새것」처럼 보여 잊힌다. 나이는 「기획 답을 얼마나 기다렸나」이지 「이 문장이 언제 생겼나」가 아니다 (2026-09-25 [5] 컨트롤러)
  - 실행 쪽 박제(`run_item.unconfirmed`)는 카탈로그가 하지 않는다. 실행을 만들 때 Execution 이 한다 ([실행.md](실행.md) §3.2)
  - **목록 · 상세 · 엑셀이 보이는 미확정은 꼬리표가 아니라 계산한 값이다** (2026-10-11 PRD-F4-02) — 아래 「지도」 ① 과 표준 기획서 지금 판에서 계산하고
    (`apps/admin/src/prd/unconfirmed.ts` — 실행 박제와 같은 식, [실행.md](실행.md) §3.2), 확인 필요가 없을 때는 꼬리표 사유를 쓰되 사람이 확정한 요구가 덮으면 확정이다(실행 §3.2 「넘어가는 동안의 갈래」).
    나이는 표준 기획서 항목의 `checkSince` 가 들고 「PRD 관리」 메뉴가 보인다 — 응답에서 `unconfirmedSince` · `oldestSince` 를 뺐다.
    **꼬리표 · 위 두 칸은 진행판 PRD-F4-05 가 뺀다** — 그때까지 스캐너는 꼬리표를 지금처럼 칸에 옮긴다([작성.md](작성.md) §3.6 「★ 표준 기획서」 「미확정」 「차례가 있다」)
- **지도** (2026-10-10 · ① 반영 2026-10-11 PR #204 — `apps/admin/src/catalog/reqMap.ts` · ② 대기 PRD-F4-04): 스캐너가 스캔마다 그 서비스 몫을 지우고 다시 채운다. **사본이라 손으로 안 고친다.**
  ① 요구 ↔ 케이스는 요구사항 표(`docs/cases/<접두사>.md`) 출처 칸의 번호와 축 칸, ② 케이스 ↔ 화면 파일 ↔ 화면 주소는 케이스 파일이 부르는 Page Object 와 그 파일의 화면 주소 값에서 읽는다.
  표는 [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「표준 기획서 · 지도 · 화면 기록 표」, 무엇을 왜 하는지는 [작성.md](작성.md) §3.6 「★ 표준 기획서」 「지도」가 정본이다.
  - ① 의 출처 칸 번호는 원장 대조와 같은 함수(`번호찾기`)로 읽는다 — 번호를 두 곳이 다르게 읽으면 「덮었다」는 셈과 지도가 어긋난다. 표준 기획서에 없는 번호(옛 표의 원본 번호)도 그대로 넣는다. 줄을 거르는 기준은 다르다 — 원장 대조가 형식 오류로 빼는 줄(출처 번호 10개 넘음)도 지도는 넣고, tcId 는 카탈로그에 실제로 들 수 있는 꼴(K2 의 세 자리)만 받는다
  - tcId 칸이 번호 꼴이 아닌 줄(「제거함(…)」 · 「—」) · 그 서비스 접두사가 아닌 줄 · 축이 넷(정상 · 경계 · 예외 · UI) 밖인 줄은 건너뛴다 — 넣으면 축 제약 한 줄에 그 서비스 지도 전체가 안 바뀐다
  - 표 파일이 없으면 그 서비스 지도를 비운다(덮는 것이 없다). 표 뿌리 폴더(`PLATFORM_CASES_DIR`)가 통째로 없거나 다른 읽기 오류면 옛 지도를 두고 스캔 결과에 문제 한 줄을 남긴다 — 마운트가 빠진 것을 「표 없음」으로 읽으면 모든 서비스 지도가 말없이 사라진다. 지도와 케이스 갱신은 서로 따로 간다(케이스 폴더가 깨지거나 번호가 겹쳐도 지도는 갱신한다)
  카탈로그는 표준 기획서 지금 판을 **읽기만** 한다 — 목록 맥락(§8.1)의 기능 묶음 · 요구 문장을 거기서 가져온다. 쓰는 것은 작성 쪽이다
- **설계 기법** (2026-10-05 · PR #158): 스캐너는 `spec.techniques` 를 읽어 `test_case.techniques` 에 둔다. 없으면 `'{}'` 이고 다시 스캔하면 덮어쓴다.
  기법이 무엇이고 칸마다 어떤 기법이어야 하는지는 [작성.md](작성.md) §3.6 「설계 기법」, 선언과 K14 는 [공통/2-명세선언.md](../공통/2-명세선언.md),
  칸은 [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「설계 기법 칸」, 목록 · 거르기 · 엑셀은 아래 §7 · §8.1 이 정본이다
  - **기법 이름은 바꾸지 않는 식별자다** — `test_case` 칸 · `?technique=` 값 · 케이스 파일 글자가 같은 낱말(kit `TECHNIQUES`)이다.
    화면에 보이는 글은 `messages` 표가 옮긴다. 이름을 바꿀 날이 오면 옛 이름을 별칭으로 계속 받는다 —
    안 받으면 케이스 파일 · 저장해 둔 주소 · DB 행이 한꺼번에 「모르는 기법」이 된다 (2026-10-05 게이트 1)

## 7. Admin API

```
# Catalog
POST   /api/catalog/scan                 소스 폴더 재스캔 → { added, updated, deactivated, duplicates[] }
GET    /api/catalog/scan                 마지막 스캔 결과 → { scannedAt, added, updated, deactivated, duplicates[], error? }
GET    /api/catalog/cases                케이스 검색. 아래 조건을 AND로 겹친다 (조건 정의는 §8.1)
         ?service=    **필수.** 보고 있는 서비스의 접두사 (예: PAY). 배정받지 않은 것이면 403
         ?q=          글자. 이름·tcId 부분 일치
         ?platform=   디바이스. desktop | mobile
         ?active=     활성 여부. true | false. 생략하면 활성만
         ?kind=       종류. ui(번호에 -UI-) | fn(그 밖 — 옛 꼴 · -FN-). 없거나 모르면 둘 다 (2026-10-02 PR #132 · 사이드바 하위 메뉴).
                      미확정 요약(unconfirmed)은 종류를 따른다 — 종류는 검색 조건이 아니라 사이드바가 고른 범위다(UI 목록 부제에 기능 미확정이 섞이지 않게).
                      q · platform · active 를 안 따르는 것은 그대로다
         ?technique=  설계 기법. kit TECHNIQUES 의 낱말 하나면 그 기법을 가진 것, none 이면 기법이 없는 것(「기법 없음」 — 뜻은 §8.1) (2026-10-05 PR #158).
                      모르는 값은 400 { error: 'BAD_TECHNIQUE' } — ?kind= 와 달리 이 조건을 보내는 옛 화면이 없고, 거르지 않고 전부 내면 거른 줄 알고 틀린 목록을 믿는다.
                      검색 조건이므로 미확정 요약(unconfirmed)은 따르지 않는다
         ?page=
       → { items, total, totalIsExact, sort, page, pageSize }
         items[] 에 techniques: string[] 이 붙는다 — 기법이 없으면 [] (2026-10-05 PR #158). 단건 응답에도 실린다
         미확정이 붙는다 (2026-09-25 · 2026-10-11 PRD-F4-02 에서 바꿈 — 아래 계약 블록 둘) —
         items[] 에 unconfirmed(사유 또는 null — 표준 기획서가 정하면 「확인 필요 — <요구 번호들>」, 아니면 꼬리표 사유. §3.1 「미확정 꼬리표」),
         최상위에 unconfirmed: { count } — 그 서비스의 **활성 케이스 전부**를 센다. 앞 판의 unconfirmedSince · oldestSince 는 뺐다.
         검색 조건을 따르지 않는다. 머리의 알림이 검색에 따라 사라지면 잊힌다 (§8.1)
         items[] 에 savedInput 이 붙는다 (2026-09-29 · 실행 §8.2 「저장값 — 케이스마다 한 벌」)
GET    /api/catalog/cases/:tcId          단건 + 스키마. savedInput 이 붙는다 (2026-09-29)
         savedInput: { params, expected, savedSecrets, savedBy, savedAt } | null — 저장값이 없으면 null
           params · expected 에 **비밀값 칸의 값은 싣지 않는다.** 저장된 비밀값 칸은 이름만 savedSecrets({ params: string[]; expected: string[] })의 같은 자리에 알린다.
           지금 명세(param_schema · expected_schema properties)에 없는 칸은 싣지 않는다 (실행 §8.2 「비밀값 칸」)
GET    /api/catalog/export               케이스 목록 엑셀 (2026-09-29 · 아래 계약 블록 반영 완료)
         ?service=&q=&platform=&active=&kind=&technique=   /cases 와 같은 조건(모르는 technique 도 같은 400). 쪽(page)은 없다 — 조건에 맞는 것 전부
       → .xlsx 첨부 `<접두사>-테스트케이스-<YYYY-MM-DD>.xlsx` (한글 이름은 filename*=UTF-8'' 로 싣는다).
         kind 를 주면 `<접두사>-테스트케이스-UI-<날짜>.xlsx` · `-FN-` — 따로 받으면 이름이 같아 덮어쓴다 (PR #132)
         권한은 (케이스, read). 남의 서비스면 403
         시트 ① 「테스트 케이스」 — TC ID · 케이스명 · 기기(PC/모바일) · 전제(줄바꿈으로) ·
           입력값(칸 설명 = 기본값, 비밀값은 ••••, 기본값 없으면 「(실행 때 넣음)」) · 기대값(같은 모양) · 상태 · 마지막 결과(판정 · 시각) ·
           설계 기법(맨 끝 — 기법을 ` · ` 로 잇고 없으면 빈칸. kind=ui 면 이 열이 없다, 2026-10-05 PR #158. 열을 번호로 읽는 검사가 있어 끝에 둔다)
           상태 = 「정식」 · 「미확정 — <사유>」, 전제에 「가짜 응답(모킹)」이 있으면 「모킹」 덧붙임,
           반영된 보류 입력이 있으면 「사람이 값 채움 — 작성 요청 #<뿌리> · <누가>」 덧붙임
           **권한 빈칸** — (실행, read) 가 없으면 「마지막 결과」 칸을 비운다 · (작성, read) 가 없으면 「사람이 값 채움」 부분을 붙이지 않는다.
           케이스 read 만으로 실행·작성 기록이 새면 안 된다
         시트 ② 「보류 처리 기록」 — (작성, read) 가 있을 때만 붙는다.
           작성 요청(#뿌리) · TC ID · 구분(판정 불가/보류) · 왜 보류됐나 · 처리(값 채움/제거함/값 필요) · 넣은 값(칸 설명 = 값) · 누가 · 언제 · 반영(반영됨/반영 전)
           **뿌리마다 가장 최근에 끝난 작성 실행 한 건만 싣는다** — 보류 입력은 이어받을 때 옮겨 적혀 실행마다 중복된다.
           반영됨 = 그 뿌리에 병합을 마친(MERGE DONE) 실행이 있다. 제거한 보류 케이스는 코드에서 사라지므로 이 시트에서만 찾는다
           폐기한 뿌리는 싣지 않는다 — 단 반영됨이면(이미 코드에 들어갔다) 싣는다 (2026-09-29)
```

### 8.1 케이스 목록
`(거터: 판정 색) 고르는 칸 | TC ID | 케이스명 | 입력 칸 | 지원 디바이스 | 마지막 결과 + 판정 흐름 | [상세] [▶]`
→ JSON 원문은 목록에 절대 노출하지 않는다.

**목록은 종류(UI 테스트 · 기능 테스트)로 갈린다 (2026-10-02 · PR #132).** 사이드바 하위 메뉴가 고르고 서버가 `?kind=` 로 거른다(§7). 부제 맨 앞에 종류를 적고(`기능 테스트 · 모두 N건`) 종류를 바꾸면 고른 것 · 쪽 · 검색어 · 설계 기법을 비운다(UI 목록에는 기법 고르개가 없어 남으면 보이지 않는 거르기가 된다 — 2026-10-05 PR #158). 자리 규칙의 정본은 [공통/5-화면공통](../공통/5-화면공통.md) §8 「자리 목록」의 하위 메뉴 줄이다.

**줄의 입력 칸 이름은 짧게 보이고 마우스를 올리면 전체가 뜨며, 저장된 비밀번호는 칸 안에 「입력됨」으로 보인다 (2026-09-30).** 그 규칙의 정본은 [실행.md](실행.md) §8.2 「케이스 줄의 입력 칸 이름」이다 — 여기 옮겨 적지 않는다.

**칸마다 이름을 단다 (2026-09-22 결정).** 목록 맨 위에 표머리 줄을 두고 위 칸 이름을 적는다.
이름이 없으면 각 칸이 무엇인지 화면만 봐서는 모른다.
표머리의 색은 껍데기 색이다 — 자리는 [공통/5-화면공통.md](../공통/5-화면공통.md) §8 이 정본이다.

**케이스명과 입력 칸은 다른 칸이다 (2026-09-22 수정).** 앞 판은 `케이스명 + 입력 칸` 으로 묶여 있었다.
한 칸에 넣으면 이름 아래에 입력칸이 붙어 **한 줄이 두 덩어리로 보이고 표머리를 달 수 없다.**

- **케이스명 칸에 최소 너비를 준다.** 칸이 하나 늘었으므로 이름이 밀린다.
  넘치면 `…` 로 자르고 전체는 상세에서 본다. 이름이 두세 글자만 남으면 목록이 못 쓰게 된다
- **목록이 좁아 줄이 쌓이면 칸 이름을 감추고 「이 쪽 전체 선택」 한 줄만 남긴다** (2026-10-05 · PR #159). 칸이 세로로 누워 칸 이름이 뜻을 잃기 때문이다.
  기준은 창이 아니라 목록 폭이다 — 사이드바를 편 1024px 창도 쌓인다. 폭과 모양의 정본은 [DESIGN.md](../../DESIGN.md) 「반응형」이다.
  케이스 목록은 §8 의 「좁은 화면에서 제대로 되는 둘」에 **없다** —
  거기 있는 실행 기록([실행.md](실행.md) §8.7)은 감추지 않고 줄마다 라벨을 붙인다

`마지막 결과` 칸은 `GET /api/runs/last-by-case` 한 번으로 전부 채운다 (§7.1).
케이스마다 이력을 따로 부르지 않는다.
**스캔 결과는 화면 머리의 부제에 적는다 (2026-09-22 수정).** 마지막 스캔 시각·결과
(추가/갱신/비활성/중복)와 **실패 사유**가 거기 같이 붙는다. `다시 스캔` 는 그 머리의 주 행동이라
이미 같은 줄에 있다 — 자리 구성은 [공통/5-화면공통.md](../공통/5-화면공통.md) §8 「화면 머리」가 정본이다.

**미확정이 있는 서비스는 머리에 그 건수를 적는다** (2026-09-25 · 2026-10-11 PRD-F4-02 에서 나이를 뺐다) —
`미확정 7건` 꼴이다. 없으면 적지 않는다. 값은 §7 응답 최상위의 `unconfirmed` 다.
**나이는 「PRD 관리」 메뉴의 「확인 필요 N건 · 가장 오래된 것 N일째」가 보인다** — 확정하는 자리가 그 메뉴라 잊히지 않게 거기 둔다([작성.md](작성.md) §3.6 「★ 표준 기획서」 「미확정」).
앞 판은 `미확정 7건 · 가장 오래된 것 23일째` 였다 — 그때는 기획 답을 기다리는 나이를 케이스 꼬리표가 들었다.
줄에는 케이스명 옆에 `미확정` 배지를 붙이고 사유 한 문장은 상세에서 본다.

**앞 판은 「목록 위에 따로 줄로 둔다」였다.** 그 줄이 49px 을 먹었는데, 이 화면은 표가 창을 채우는 것이
일이라 그만큼 표가 잘렸다 — 창 794px 에서 표에 206px 만 남아 **줄 하나 반**밖에 안 보였다 (2026-09-22 실측).
**적히는 것은 하나도 안 줄었다. 자리만 옮겼다** — 특히 실패 사유는 그대로 따라간다.

#### 설계 기법 (2026-10-05 · PR #158 · 시안 A1)

**기능 테스트 목록에만 있다** — UI 테스트 목록에는 태그도 고르개도 없다(UI 케이스는 기법을 안 단다 — 공통/2-명세선언 K14). 값과 이름 규칙은 §3.1 「설계 기법」이 정본이다.

- **줄** — 케이스명 아래 작은 줄(「지원 디바이스」가 적힌 줄)에 `설계 기법` 글자와 기법 태그를 붙인다. 기법이 없으면 안 그린다.
  케이스명 옆에는 `미확정` 배지만 둔다 — 이름 옆에 두면 기법이 둘일 때 둘째 태그가 다음 줄로 밀린다
- **태그는 판정 색이 아니다** — 설명 정보라 `미확정`(할 일을 알리는 배지)과도 다르게 보인다. 모양의 정본은 `docs/DESIGN.md` 「설계 기법 태그」다
- **고르개** — 검색 줄에 `설계 기법` 라벨과 고르개(select) 하나를 둔다. 값은 `전체` · kit `TECHNIQUES` 의 기법 · `기법 없음` 이고 고르면 서버가 `?technique=` 로 거른다(§7).
  **칩으로 늘어놓지 않는다** — 칩으로 두면 창 1150px 에서 두 줄이 됐다(2026-10-05 계획 검토 실측). 처음에는 찾기와 조건 칩이 한 줄에 서는 것(2026-09-22 — 두 줄이면 132px 을 먹었다)을 지키려 했으나
  **기능 목록의 도구 줄은 두 줄을 받아들인다** (2026-10-05 게이트 2 사용자) — 도구 줄은 최대 폭(약 1390px)에서 멈춰 넓은 창에서도 고르개(라벨 포함 약 170px)가 들어가면 두 줄이고, 1440px 이하 창은 그 전부터 두 줄이었다. 라벨과 고르개는 한 덩어리라 갈라지지 않는다
- 고르면 첫 쪽으로 간다. 고른 것은 디바이스 · 표시 칩처럼 그대로 둔다(2026-10-05 게이트 2 승인 — 계획은 비움이었다). 검색 지우기는 기법도 비운다. 「전체 실행」과 엑셀은 같은 조건을 탄다 — 「경계값 분석만 돌리기」가 따로 만든 것 없이 된다
- **「기법 없음」은 기법이 안 적힌 케이스 전부다** — 정상 칸 · 설계 밖 예외 칸 · 이 기능 전 케이스 · 사람 세션이 쓴 케이스 · 원장 없는 작성이 다 여기 든다. 정상 케이스만 모이는 자리가 아니다.
  **기존 케이스는 따로 채우지 않는다** — 다시 작성하면 채워진다(2026-10-05 사용자). 채우는 명령은 만들지 않는다
- **상세** — 상자 맨 위에 `설계 기법` 구획을 두고 같은 태그를 그린다. 기법이 없으면 구획을 안 그린다

#### 맥락 — 기능 묶음 · 요구 · 종류 · 화면 (2026-10-10 · 대기 — PRD-F5-01)

케이스 이름만 보고는 무슨 테스트인지 모른다(2026-10-10 사용자). 표준 기획서와 지도(§3.1 「지도」)에서 맥락을 붙인다. 화면은 시안 A·B·C 를 먼저 고른다.
- **접기** — 기능 묶음 > 화면 > 화면 조각 셋으로 접는다. 더 잘게 쪼개지 않는다. 지도에 없는 케이스(사람이 쓴 케이스 · 옛 표)는 「기능 묶음 없음」에 모인다
- **줄 아래** — 요구 번호 · 요구 문장 · 종류(정상 · 경계 · 예외 · UI) · 기법 · 화면. 요구 번호를 누르면 「PRD 관리」 메뉴의 그 항목으로 간다 — 작성 `read` 가 없으면 글자만 보인다
- **거르기** — 기능 묶음 · 요구 번호 · 종류 · 화면(아래 「검색 조건」 7~10)
- **요구 문장은 케이스 `read` 로 보인다** — 케이스 이름과 같은 무게로 본다. 근거 · 판 이력 · 상태 고치기는 「PRD 관리」 메뉴(작성 칸)에만 있다
- E2E 단계 추가 탭([시나리오.md](시나리오.md) §8.11)도 같은 맥락을 쓴다. 진행판 WEB-F2-11 · 14 · 15(조건 줄 · 기법 덩어리 · 표머리)를 이때 같이 고친다

#### 줄에서 값을 고치고 상세를 연다 (2026-09-21 결정 · 2026-09-22 상자로)

값을 보려고 다른 화면으로 나가던 것을 없앤다. 목록이 **거기서 끝나는 자리**가 된다.

**① 입력 칸** — 케이스가 선언한 값이 **기본값이 채워진 채로 고칠 수 있는 칸**으로 줄에 나온다.
**채우는 순서는 저장값 → 코드 기본값이다** (2026-09-29). 저장값이 있으면 그 값으로, 없으면 코드 기본값으로 채운다 —
상세 상자와 실행 창도 같은 순서다. 정본은 실행 §8.2 「저장값 — 케이스마다 한 벌」이다.
칸을 만드는 규칙은 실행 §8.2 의 폼 자동 생성이 정본이고 목록이 그것을 그대로 쓴다 —
**두 벌을 만들지 않는다.** 비밀값 가림도 거기서 온다.

- **줄에 보이는 칸은 넷까지다.** 넘으면 `N개 더` 가 상세를 연다.
  DESIGN.md 의 「8개를 넘으면 구획을 나눈다」를 줄에서는 할 수 없어서 상한으로 대신한다
- **객체·배열 기본값은 줄에 안 낸다.** 펴면 JSON 원문이 되고 그것은 금지다 (위 줄 · DESIGN.md 「금지」).
  그 칸도 상세로 간다
- **고친 값은 그 실행에만 쓰인다.** 케이스 파일의 기본값은 안 바뀐다 —
  `POST /api/runs` 의 그 항목 `params`·`expected` 가 될 뿐이고 `run_item` 에 스냅샷으로 박힌다 (§3.2).
  다음 실행에도 남기는 길은 저장값이다 — 고친 칸이 있으면 줄 끝에 「저장」이 생긴다 (실행 §8.2 「저장값 — 케이스마다 한 벌」)
- **고친 값의 수명** — 쪽을 넘겼다 돌아오면 남고, **서비스를 바꾸면 버린다**.
  칸 이름이 같으면(`env`·`userId`) 남의 서비스 케이스에 그대로 붙는다.
  실행 창(실행 §8.10)과 **같은 표를 쓴다** — 두 벌이면 두 자리가 다른 값을 보여준다

**② 상세** — `[상세]` 를 누르면 **상자가 열린다.** 사전조건 · 입력값 · 기대결과 ·
시험 절차(마지막 실행에서) · 실행 이력(최근 N건)이고, 기능 테스트에 기법이 있으면 맨 위에 「설계 기법」 구획이 선다(위 「설계 기법」).

**2026-09-22 에 펼침에서 상자로 바꿨다.** 앞 판은 「그 줄 아래가 펼쳐진다」였는데
**눌러도 열렸다는 느낌이 없다**는 지적을 받았다. 줄 아래로 늘어나면 시선이 그대로라
무엇이 바뀌었는지 눈에 안 들어오고, 긴 목록에서는 펴진 자리가 화면 밖으로 밀린다.
**상자의 규칙은 `docs/DESIGN.md` 가 정본이다** — 거기 「열어서 보는 상자」에 해당한다.
사람이 눌러서 여는 것이라 가로막는 상자가 아니다.

- **위의 「케이스마다 이력을 따로 부르지 않는다」를 어기지 않는다.** 그 규칙은 **목록**을 두고 한 말이고,
  여기는 **사람이 한 줄을 열었을 때** 부른다. 목록이 부르는 것이 아니다
- **한 번 받은 것은 닫았다 열어도 다시 안 받는다.** 닫을 때마다 버리면 그 예외가 위반으로 바뀐다.
  **받아 둔 것은 목록이 들고 있는다** — 상자가 들면 닫는 순간 같이 사라진다
- 시험 절차는 마지막 실행이 있을 때만 있다. 없으면 그 사실을 적는다.
  통로 하나가 실패해도 나머지는 그린다
- 닫으면 **누른 `[상세]` 버튼으로 돌아온다** (DESIGN.md 포커스 규칙)
- **「코드 기본값 바꾸기 요청」 자리를 둔다** (2026-10-01 — [작성.md](작성.md) §3.6 「★ 케이스 고치기」가 정본). 작성 `write` 일 때만 보인다.
  - 위 기대결과 칸(이번 실행 값 · 저장값)과 **이름을 갈라** 섞이지 않게 한다. 칸은 **코드 기본값**으로 채워 열리고 바꾼 칸만 보낸다.
    비밀값 칸과 다섯 꼴(글자 · 수 · 정수 · 참거짓 · 선택지) 밖의 칸은 안 보인다
  - 그 칸에 저장값이 있으면 「반영되면 이 저장값은 지워집니다」를 적는다
  - 미확정 케이스면 「확정」 고르개를 둔다. 곁에 미확정 사유와 지금 기대값을 보인다 — 확정은 그것을 보고 맞다고 판정하는 일이다.
    **표준 기획서가 정한 미확정(사유가 「확인 필요 — 」로 시작)에는 두지 않고 「「PRD 관리」에서 확정합니다」 한 줄만 보인다** (2026-10-11 PRD-F4-02) —
    그 미확정은 케이스 파일 꼬리표가 아니라 기획서 항목이 정해서 「확정」 PR 로는 안 풀린다. 이 고르개는 꼬리표와 함께 PRD-F4-05 가 뺀다([작성.md](작성.md) §3.6 「★ 표준 기획서」 「미확정」)
  - 「케이스 삭제 요청」은 두 번 눌러야 간다(「삭제 확인」 · 「취소」). 누르면 그 케이스를 쓰는 E2E 시나리오를 번호 · 이름으로 보인다. 지우면 다른 케이스로 바꿀 때까지 그 시나리오를 실행할 수 없다(시나리오 §3.7 결정 8). 목록을 못 읽으면 못 돈다는 문장만 적는다
  - 보낸 뒤 「작성 요청 N번」 연결을 보인다 — 반영(머지)은 테스트 작성 화면에서 한다

**③ 판정 흐름** — 마지막 결과 옆에 최근 판정이 작은 막대로 늘어선다. **디바이스마다 하나다** —
데이터가 `(케이스, 디바이스)` 단위이고 줄도 디바이스마다 배지를 그린다.
**색만으로 전달하지 않는다** — 판정마다 막대 높이가 다르고 개수를 글자로 같이 적는다 (DESIGN.md).
다섯에 못 미치면 남는 자리를 빈 칸으로 채워 길이를 지킨다.

#### 여러 건 골라 한 번에 돌린다 (2026-09-21 결정)

케이스는 `[실행]`으로 한 건씩만 돌릴 수 있었다. 그런데 §8.2는 이미 여러 건을 전제해
실행 항목 수를 세고 있었다 — **고르는 자리가 없어 그 「케이스 수」가 영원히 1이었다.**
명세가 자기 안에서 어긋나 있던 것을 여기서 맞춘다. `[실행]`은 그대로 둔다.
**2026-10-09 에 줄의 `[실행]` 은 ▶ 아이콘 버튼이 됐고 누르면 그 한 건으로 같은 실행 창(실행 §8.10)이 열린다** (UI 개편 묶음 4).
글자를 아이콘으로 바꾼 까닭은 영어 화면에서 「Run」이 「Details」 아래로 밀려 내려갔기 때문이다(진행판 WEB-F2-12). 이름은 화면 읽기가 「<tcId> 실행」으로 말한다.
**고르면 머리 버튼이 셋 · 넷으로 늘어 좁은 창에서 제목이 세로로 섰다**(WEB-F2-10) — 화면 머리는 제목 칸이 모자라면 버튼 묶음을 아랫줄로 보낸다(공통/5-화면공통 §8 「화면 머리」).

- **고르는 칸은 왼쪽 거터 칸 옆, 케이스 번호 앞에 둔다.** 줄 내용 쪽 첫 요소로 두지 않는다 —
  목록이 좁아 줄이 쌓이면(DESIGN.md 「반응형」) 내용 쪽 첫 요소가
  케이스명 위에 홀로 한 줄이 된다
- **표머리의 첫 칸에 「이 쪽 전체 선택」 체크박스를 둔다** (2026-09-30). 지금 보이는 쪽의 케이스를 한 번에 고르고, 전부 골랐으면 한 번에 푼다.
  일부만 골랐으면 「일부 선택」 모양이고 누르면 나머지까지 고른다. **다른 쪽에서 고른 것은 건드리지 않는다.** 모든 쪽을 대상으로 하는 것은 아래 「전체 실행」이 이미 한다. 목록이 좁아 줄이 쌓여도 이 체크박스는 「이 쪽 전체 선택」 글과 함께 남는다(위 「칸마다 이름을 단다」 · 2026-10-05 PR #159 — 전에는 휴대폰 폭에서 표머리와 함께 감춰 줄마다 골라야 했다)
- **고른 것으로 「삭제 요청」 · 「확정 요청」을 낸다** (2026-10-01 — [작성.md](작성.md) §3.6 「★ 케이스 고치기」). 작성 `write` 이고 하나라도 골랐을 때만 보인다.
  「확정 요청」은 고른 것 가운데 꼬리표 미확정 수를 글자에 싣고(`미확정 N건 확정 요청`) 0 이면 안 보인다 — 표준 기획서가 정한 미확정은 세지 않는다(위 줄 · 2026-10-11). **「확정 요청」은 PRD-F4-05 에서 없어진다**.
  둘 다 확인 상자를 거친다 — 삭제 상자는 위 「케이스 삭제 요청」과 같은 시나리오 줄을 띄우고, 확정 상자는 케이스마다 미확정 사유와 지금 기대값을 보인다. 한 번에 고를 수 있는 건수는 서버 상한([작성.md](작성.md) §3.6 「★ 케이스 고치기」 「한 요청」)까지 — 넘으면 상자가 막고 까닭을 적는다
- **버튼은 하나이고 글자가 바뀐다.** 아무것도 안 고르면 `전체 실행`,
  하나라도 고르면 `선택한 N건 실행`. 자리는 목록 위 `다시 스캔` 옆이다.
  **버튼을 둘로 나누지 않는다** — 같은 자리에서 같은 일을 하고 담는 대상만 다르다
- 누르면 실행 창이 열린다. 그 안에서 무엇을 정하는지는 **[실행.md](실행.md) §8.10이 정본이다**

##### 「전체」는 보이는 쪽이 아니라 모든 쪽이다

목록은 한 쪽씩 받아 온다(§7 `?page=`, 한 쪽 분량은 응답의 `pageSize`가 알려준다).
화면에 지금 떠 있는 쪽만 담으면 `전체 실행`가 거짓말이 된다.

- **버튼을 누르면 화면이 쪽을 돌며 전부 받아 온다.** 받는 동안 버튼을 누를 수 없고,
  받고 있다는 사실을 **화면 줄**로 적는다. 말풍선으로 적지 않는다 (DESIGN.md 접근성 기준)
- 몇 쪽을 돌지 총건수로 계산하지 않는다. 다음 쪽이 있는지는 응답이 알려주는 값으로 판단한다
  (아래 「목록 화면이 지킬 것 셋」의 셋째)

##### `마지막 결과`로 걸러도 빠지는 것이 없다

아래 검색 조건 표에서 **화면이 거르는 것은 `마지막 결과` 하나뿐**이고 나머지는 서버가 거른다.
그 하나가 걸려 있을 때도 「전체」가 한 쪽에 갇히지 않는다 —
`마지막 결과`를 채우는 표는 쪽 없이 그 서비스 전체를 한 번에 받기 때문이다
(`GET /api/runs/last-by-case`, §7.1).

- **모든 쪽을 모은 뒤 그 표로 한 번 더 거른다.** 순서가 반대면 받아 온 쪽 안에서만 걸러져
  뒤쪽에 있던 것이 빠진다

#### 엑셀로 내려받기 (2026-09-29 · 시안 B)

검색 줄 끝에 `이 결과 엑셀로 (N건)` 버튼을 둔다. N 은 목록 응답의 `total` 이고, 받는 파일은 **지금 건 검색 조건 그대로** 쪽 없이 전부다 (§7 `GET /api/catalog/export`).
0건이면 누를 수 없다. 받는 동안 버튼을 막고 `만드는 중…` 으로 바꾼다. 실패(403 · 500)면 목록 위에 알림 한 줄을 띄운다.
화면의 `마지막 결과` 칩(조건 5)은 화면에서 거르는 것이라 파일에 걸리지 않는다.
**입력값·기대값 칸은 코드 기본값을 싣는다. 저장값(실행 §8.2)은 싣지 않는다** (2026-09-29).
기능 테스트 목록에서 받은 파일은 시트 ① 맨 끝에 `설계 기법` 열이 있고 UI 테스트 목록에서 받은 파일에는 없다 — 고르개(조건 6)도 파일에 걸린다. 열 모양은 §7 (2026-10-05 PR #158).

| 왜 비었나 | 무엇을 보여주나 | 다음 행동 |
|----------|---------------|----------|
| 아직 한 번도 안 불러옴 (`scannedAt`이 없다) | `아직 케이스를 불러오지 않았습니다` + 무엇을 하는 것인지 두 줄 | 가운데 큰 `케이스 불러오기` 버튼 |
| 불러왔는데 0건 (`scannedAt`은 있고 전체 건수가 0) | `불러왔지만 케이스가 하나도 없습니다` | `규칙에 걸린 파일 N건 · 사유 보기` |
| 검색·필터에 안 걸림 (조건이 하나라도 걸려 있다) | `'장바구니'에 맞는 케이스가 없습니다` — 친 글자를 그대로 넣는다 | `검색 지우기` |

- **세 갈래를 가르는 값은 응답에 이미 있다** — `scannedAt`과 전체 건수, 화면이 건 조건.
  새 API가 필요하지 않다
- 둘째 줄의 `사유 보기`는 스캔 결과의 `duplicates[]`와 규칙 위반 목록으로 간다.
  「하나도 없다」만 말하고 왜인지 안 말하면 사람이 할 수 있는 일이 없다

#### 목록 화면이 지킬 것 셋 (2026-09-16 결정)

- **목록을 부르는 자리를 한 곳에 모은다.** 화면 여러 곳에서 각자 부르면 갈아 끼울 때 다 찾아야 한다
- **정렬 순서를 화면이 정하지 않는다.** 응답이 준 순서 그대로 그린다.
  순서가 관련도순으로 바뀌는 날, 화면이 `tcId` 순을 전제하면 목록이 뒤죽박죽으로 보인다
- **`모두 N건`을 정확한 값으로 전제하지 않는다.** 이 숫자는 안내로만 쓰고, 다음 페이지가 있는지는 응답이 알려주는 값으로 판단한다.
  **지금 케이스 목록 화면이 이 숫자로 페이지 수까지 계산하고 있다. 이것부터 고친다** — 총건수가 근사치가 되는 날 빈 페이지가 생긴다
