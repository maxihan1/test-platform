### 3.1 Catalog — 무엇을 테스트할 수 있는가

- **책임**: 소스 폴더를 스캔해 `CaseSpec`을 추출하고 검색 가능하게 유지
- **애그리거트 루트**: `TestCase` (식별자 `tcId`)
- **불변식**
  - `tcId`는 전역 유일. 중복 발견 시 스캔 실패시키고 양쪽 파일 경로를 보고한다
  - **코드가 진실의 원천**. DB의 `test_case`는 캐시이며, 스캔 때마다 덮어쓴다
  - 코드에서 사라진 케이스는 삭제하지 않고 `is_active = false`로 둔다 (과거 실행 이력이 참조하므로)
  - **카탈로그는 실행 결과를 알지 못한다.** `test_run`·`run_item`을 읽지 않는다. 목록의 `마지막 결과` 칸은
    실행 컨텍스트가 내는 응답으로 채운다. 이 경계가 무너지면 카탈로그가 실행 테이블 구조에 묶여
    §5.3의 이음새가 같이 무너진다. 검색 조건과 화면 규칙은 **§8.1이 정본**이다
  - **`test_case`의 `param_schema`·`expected_schema`는 캐시다.** 스캔 때마다 덮어쓰므로 과거 실행의 증적은
    이 테이블을 읽어 만들지 않는다. 증적이 읽을 값은 실행 기록에 따로 박제한다 (§3.3 증적 재현)
  - 나중에 검색엔진을 붙이더라도 옮기는 것은 **케이스 속성뿐**이고 실행 결과는 옮기지 않는다.
    색인해 두면 실행이 끝날 때마다 어긋나고, 어긋난 색인은 조용히 틀린 목록을 보여준다 (→ §5.3)
- **추출 방식** (2026-09-16 결정): 스캐너는 `tests/**/*.spec.ts`를 환경변수 `PLATFORM_SCAN=1`을 켠 채
  동적으로 import 해 `export const spec`을 읽는다. kit의 `test()`는 이 변수가 켜져 있으면 Playwright에
  등록하지 않고 조용히 반환한다. zod 스키마는 실행해야 JSON Schema가 되므로 텍스트 파싱은 하지 않는다.
  admin 이미지에 `@platform/kit`·`zod`·`@playwright/test`가 설치돼 있어야 한다
- **스캔 시점** (2026-09-16 결정): admin은 **기동할 때 한 번** 자동으로 스캔한다. 배포는 컨테이너 재기동이므로
  배포 직후 목록이 최신이 된다. 그 밖에는 화면의 `다시 스캔하기` 버튼(→ `POST /api/catalog/scan`)으로 돌린다.
  기동 시 스캔이 실패(tcId 중복 등)해도 admin은 뜬다. 실패 사유는 마지막 스캔 결과(`GET /api/catalog/scan`)에 남기고
  목록 화면 위에 보여준다

## 7. Admin API

```
# Catalog
POST   /api/catalog/scan                 소스 폴더 재스캔 → { added, updated, deactivated, duplicates[] }
GET    /api/catalog/scan                 마지막 스캔 결과 → { scannedAt, added, updated, deactivated, duplicates[], error? }
GET    /api/catalog/cases                케이스 검색. 아래 조건을 AND로 겹친다 (조건 정의는 §8.1)
         ?service=    **필수.** 보고 있는 서비스의 접두사 (예: PAY). 배정받지 않은 것이면 403
         ?q=          글자. 이름·tcId 부분 일치
         ?platform=   디바이스. desktop | mobile
         ?active=     활성 여부. true | false. 생략하면 활성만
         ?page=
       → { items, total, totalIsExact, sort, page, pageSize }
GET    /api/catalog/cases/:tcId          단건 + 스키마
```

### 8.1 케이스 목록
`(거터: 판정 색) 고르는 칸 | TC ID | 케이스명 + 입력 칸 | 지원 디바이스 | 마지막 결과 + 판정 흐름 | [상세] [실행]`
→ JSON 원문은 목록에 절대 노출하지 않는다.
`마지막 결과` 칸은 `GET /api/runs/last-by-case` 한 번으로 전부 채운다 (§7.1).
케이스마다 이력을 따로 부르지 않는다.
목록 위에 `다시 스캔하기` 버튼과 마지막 스캔 시각·결과(추가/갱신/비활성/중복)를 둔다.
스캔이 실패했으면 그 사유를 같은 자리에 보여준다.

#### 줄에서 값을 고치고 상세를 펼친다 (2026-09-21 결정)

값을 보려고 다른 화면으로 나가던 것을 없앤다. 목록이 **거기서 끝나는 자리**가 된다.

**① 입력 칸** — 케이스가 선언한 값이 **기본값이 채워진 채로 고칠 수 있는 칸**으로 줄에 나온다.
칸을 만드는 규칙은 실행 §8.2 의 폼 자동 생성이 정본이고 목록이 그것을 그대로 쓴다 —
**두 벌을 만들지 않는다.** 비밀값 가림도 거기서 온다.

- **줄에 보이는 칸은 넷까지다.** 넘으면 `N개 더` 가 상세를 편다.
  DESIGN.md 의 「8개를 넘으면 구획을 나눈다」를 줄에서는 할 수 없어서 상한으로 대신한다
- **객체·배열 기본값은 줄에 안 낸다.** 펴면 JSON 원문이 되고 그것은 금지다 (위 줄 · DESIGN.md 「금지」).
  그 칸도 상세로 간다
- **고친 값은 그 실행에만 쓰인다.** 케이스 파일의 기본값은 안 바뀐다 —
  `POST /api/runs` 의 그 항목 `params`·`expected` 가 될 뿐이고 `run_item` 에 스냅샷으로 박힌다 (§3.2)
- **고친 값의 수명** — 쪽을 넘겼다 돌아오면 남고, **서비스를 바꾸면 버린다**.
  칸 이름이 같으면(`env`·`userId`) 남의 서비스 케이스에 그대로 붙는다.
  여러 건 실행 모달(실행 §8.10)과 **같은 표를 쓴다** — 두 벌이면 두 자리가 다른 값을 보여준다

**② 상세 펼침** — `[상세]` 를 누르면 그 줄 아래가 펼쳐진다. 사전조건 · 입력값 · 기대결과 ·
시험 절차(마지막 실행에서) · 실행 이력(최근 N건) 다섯이다.

- **위의 「케이스마다 이력을 따로 부르지 않는다」를 어기지 않는다.** 그 규칙은 **목록**을 두고 한 말이고,
  여기는 **사람이 한 줄을 폈을 때** 부른다. 목록이 부르는 것이 아니다
- **한 번 받은 것은 접었다 펴도 다시 안 받는다.** 접을 때마다 버리면 그 예외가 위반으로 바뀐다
- 시험 절차는 마지막 실행이 있을 때만 있다. 없으면 그 사실을 적는다.
  통로 하나가 실패해도 나머지는 그린다

**③ 판정 흐름** — 마지막 결과 옆에 최근 판정이 작은 막대로 늘어선다. **디바이스마다 하나다** —
데이터가 `(케이스, 디바이스)` 단위이고 줄도 디바이스마다 배지를 그린다.
**색만으로 전달하지 않는다** — 판정마다 막대 높이가 다르고 개수를 글자로 같이 적는다 (DESIGN.md).
다섯에 못 미치면 남는 자리를 빈 칸으로 채워 길이를 지킨다.

#### 여러 건 골라 한 번에 돌린다 (2026-09-21 결정)

케이스는 `[실행]`으로 한 건씩만 돌릴 수 있었다. 그런데 §8.2는 이미 여러 건을 전제해
실행 항목 수를 세고 있었다 — **고르는 자리가 없어 그 「케이스 수」가 영원히 1이었다.**
명세가 자기 안에서 어긋나 있던 것을 여기서 맞춘다. `[실행]`은 그대로 둔다.

- **고르는 칸은 왼쪽 거터 칸 옆, 케이스 번호 앞에 둔다.** 줄 내용 쪽 첫 요소로 두지 않는다 —
  620px 미만에서 줄이 2단(거터 + 내용)으로 접히면(DESIGN.md 반응형) 내용 쪽 첫 요소가
  케이스명 위에 홀로 한 줄이 된다
- **버튼은 하나이고 글자가 바뀐다.** 아무것도 안 고르면 `전체 실행하기`,
  하나라도 고르면 `고른 N건 실행하기`. 자리는 목록 위 `다시 스캔하기` 옆이다.
  **버튼을 둘로 나누지 않는다** — 같은 자리에서 같은 일을 하고 담는 대상만 다르다
- 누르면 여러 건 실행 모달이 열린다. 그 안에서 무엇을 정하는지는 **[실행.md](실행.md) §8.10이 정본이다**

##### 「전체」는 보이는 쪽이 아니라 모든 쪽이다

목록은 한 쪽씩 받아 온다(§7 `?page=`, 한 쪽 분량은 응답의 `pageSize`가 알려준다).
화면에 지금 떠 있는 쪽만 담으면 `전체 실행하기`가 거짓말이 된다.

- **버튼을 누르면 화면이 쪽을 돌며 전부 받아 온다.** 받는 동안 버튼을 누를 수 없고,
  받고 있다는 사실을 **화면 줄**로 적는다. 말풍선으로 적지 않는다 (DESIGN.md 접근성 기준)
- 몇 쪽을 돌지 총건수로 계산하지 않는다. 다음 쪽이 있는지는 응답이 알려주는 값으로 판단한다
  (아래 「목록 화면이 지킬 것 셋」의 셋째)

##### `마지막 결과`로 걸러도 빠지는 것이 없다

아래 검색 조건 표에서 **화면이 거르는 것은 `마지막 결과` 하나뿐**이고 나머지는 서버가 거른다.
그 하나가 걸려 있을 때도 「전체」가 한 쪽에 갇히지 않는다 —
`마지막 결과`를 채우는 표는 쪽 없이 그 서비스 전체를 한 번에 받기 때문이다
(`GET /api/runs/last-by-case`, §7.1).

- **모든 쪽을 모은 뒤 그 표로 한 번 더 거른다.** 순서가 반대면 받아 온 쪽 안에서만 걸러져
  뒤쪽에 있던 것이 빠진다

#### 검색 조건 (2026-09-16 결정 · 2026-09-17 넷으로)

글자 검색은 이미 있다. 여기에 셋을 더해 **넷**으로 거른다. **이 표가 검색 조건의 정본이다.**
서비스는 조건이 아니라 사이드바 서비스 고르개의 선택이고 서버가 늘 적용한다 (§8).

| # | 조건 | 화면 모양 | 무엇으로 거르나 | 거르는 곳 |
|---|------|----------|---------------|----------|
| 1 | 글자 | 검색창 한 칸 | 케이스명·`tcId` 부분 일치 | 서버 |
| 2 | ~~기능 영역~~ | — | **2026-09-17에 검색 조건에서 뺐다.** 목록이 한 서비스로 좁혀지면(§8) 그 안의 접두사는 전부 같아 거를 것이 없다. 서비스는 사이드바 서비스 고르개에서 고르고 서버가 `?service=`로 늘 적용한다 | 사이드바 |
| 3 | 디바이스 | 칩(전체/PC/모바일) | 케이스가 선언한 `platforms` | 서버 |
| 4 | 활성 여부 | 칩(활성만/전체). 기본은 활성만 | `is_active` | 서버 |
| 5 | 마지막 결과 | 칩(전체/통과/실패/미실행) | `GET /api/runs/last-by-case` 응답 | 화면 |

- 조건은 **두 갈래**다. 1~4는 케이스의 속성이라 스캔할 때만 바뀌고, 5는 실행할 때마다 바뀐다
- **1~4만 나중에 검색엔진으로 옮길 수 있다. 5는 옮기지 않는다** — 값이 실행마다 바뀌어 색인이 늘 어긋난다.
  검색엔진을 지금 쓰지 않는 이유는 §1 범위 밖에, 갈아 끼울 때의 전제는 §5.3에, 질의 문자열과 응답 형태는 §7에 있다
- 지금은 케이스 속성을 서버에서 거르고 마지막 결과를 화면에서 겹쳐 거른다.
  카탈로그가 `run_item`을 읽으면 컨텍스트 경계가 깨진다 (§3.1·§7.1).
  케이스가 수백 건이 되어 페이지를 나눠 받게 되면 서버 쪽으로 옮긴다
- 서비스 선택지 목록은 **카탈로그가 아니라 로그인 응답이 낸다** (`GET /api/auth/me`의 `services`). 배정받은 것만 뜬다
- 비활성 케이스를 기본으로 감춘다. 코드에서 사라진 케이스는 지우지 않고 남겨 두므로(§3.1) 시간이 지날수록 목록이 과거로 채워진다

#### 목록이 비었을 때 (2026-09-17 결정)

지금은 0건이면 언제나 `찾는 케이스가 없습니다.` 하나다.
**검색한 적 없는 사람에게도 「찾는」이라고 말한다.**
이 화면은 이 도구를 처음 켠 사람이 만나는 자리다. 여기서 막히면 도구가 고장난 것처럼 보인다.

| 왜 비었나 | 무엇을 보여주나 | 다음 행동 |
|----------|---------------|----------|
| 아직 한 번도 안 불러옴 (`scannedAt`이 없다) | `아직 케이스를 불러오지 않았습니다` + 무엇을 하는 것인지 두 줄 | 가운데 큰 `케이스 불러오기` 버튼 |
| 불러왔는데 0건 (`scannedAt`은 있고 전체 건수가 0) | `불러왔지만 케이스가 하나도 없습니다` | `규칙에 걸린 파일 N건 · 사유 보기` |
| 검색·필터에 안 걸림 (조건이 하나라도 걸려 있다) | `'장바구니'에 맞는 케이스가 없습니다` — 친 글자를 그대로 넣는다 | `검색 지우기` |

- **세 갈래를 가르는 값은 응답에 이미 있다** — `scannedAt`과 전체 건수, 화면이 건 조건.
  새 API가 필요하지 않다
- 둘째 줄의 `사유 보기`는 스캔 결과의 `duplicates[]`와 규칙 위반 목록으로 간다.
  「하나도 없다」만 말하고 왜인지 안 말하면 사람이 할 수 있는 일이 없다

#### 목록 화면이 지킬 것 셋 (2026-09-16 결정)

- **목록을 부르는 자리를 한 곳에 모은다.** 화면 여러 곳에서 각자 부르면 갈아 끼울 때 다 찾아야 한다
- **정렬 순서를 화면이 정하지 않는다.** 응답이 준 순서 그대로 그린다.
  순서가 관련도순으로 바뀌는 날, 화면이 `tcId` 순을 전제하면 목록이 뒤죽박죽으로 보인다
- **`모두 N건`을 정확한 값으로 전제하지 않는다.** 이 숫자는 안내로만 쓰고, 다음 페이지가 있는지는 응답이 알려주는 값으로 판단한다.
  **지금 케이스 목록 화면이 이 숫자로 페이지 수까지 계산하고 있다. 이것부터 고친다** — 총건수가 근사치가 되는 날 빈 페이지가 생긴다
