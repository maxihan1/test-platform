### 3.1 Catalog — 무엇을 테스트할 수 있는가

- **책임**: 소스 폴더를 스캔해 `CaseSpec`을 추출하고 검색 가능하게 유지
- **애그리거트 루트**: `TestCase` (식별자 `tcId`)
- **불변식**
  - `tcId`는 전역 유일. 중복 발견 시 스캔 실패시키고 양쪽 파일 경로를 보고한다
  - **코드가 진실의 원천**. DB의 `test_case`는 캐시이며, 스캔 때마다 덮어쓴다
  - 코드에서 사라진 케이스는 삭제하지 않고 `is_active = false`로 둔다 (과거 실행 이력이 참조하므로)
  - **카탈로그는 실행 결과를 알지 못한다.** `test_run`·`run_item`을 읽지 않는다. 목록의 `마지막 결과` 칸은
    실행 컨텍스트가 내는 응답으로 채운다. 이 경계가 무너지면 카탈로그가 실행 테이블 구조에 묶여
    §5.3의 이음새가 같이 무너진다. 검색 조건과 화면 규칙은 **§8.1이 정본**이다.
    마지막 결과로 거르기(2026-10-19 ⑫ · §7 `?last=`)도 이 경계를 지킨다 — 실행 쪽 함수가 준 판정으로 거를 뿐 카탈로그 질의는 그 표를 읽지 않는다
  - **예외 하나 — 저장값 `case_input` 은 읽는다** (2026-09-29). 실행 결과가 아니라 케이스마다 한 벌 둔 입력값이고,
    케이스 응답의 `savedInput` 에 싣는다(§7). 표의 주인은 실행이고 카탈로그는 **SQL 로 읽기만 한다**(공통/4-데이터모델 §6)
  - **`test_case`의 `param_schema`·`expected_schema`는 캐시다.** 스캔 때마다 덮어쓰므로 과거 실행의 증적은
    이 테이블을 읽어 만들지 않는다. 증적이 읽을 값은 실행 기록에 따로 박제한다 (§3.3 증적 재현)
  - 나중에 검색엔진을 붙이더라도 옮기는 것은 **케이스 속성뿐**이고 실행 결과는 옮기지 않는다.
    색인해 두면 실행이 끝날 때마다 어긋나고, 어긋난 색인은 조용히 틀린 목록을 보여준다 (→ §5.3)
- **추출 방식** (2026-09-16 결정): 스캐너는 `tests/**/*.spec.ts`를 환경변수 `PLATFORM_SCAN=1`을 켠 채
  동적으로 import 해 `export const spec`을 읽는다. kit의 `test()`는 이 변수가 켜져 있으면 Playwright에
  등록하지 않고 조용히 반환한다. zod 스키마는 실행해야 JSON Schema가 되므로 텍스트 파싱은 하지 않는다.
  admin 이미지에 `@platform/kit`·`zod`·`@playwright/test`가 설치돼 있어야 한다
- **스캔 시점** (2026-09-16 결정): admin은 **기동할 때 한 번** 자동으로 스캔한다. 배포는 컨테이너 재기동이므로
  배포 직후 목록이 최신이 된다. 그 밖에는 화면의 `다시 스캔` 버튼(→ `POST /api/catalog/scan?service=` — 지금 보는 서비스만)으로 돌린다.
  **작성 결과 병합이 끝나면 서버가 그 서비스만 다시 훑는다** (2026-10-12 PRD-F9-03) — 에이전트가 main 을 받아 왔다고 알린 병합(MERGE DONE · `result.pulled: true`)에서만이다.
  응답을 기다리지 않고 뒤에서 돈다(큰 서비스는 에이전트의 30초 제한을 넘긴다). 다른 서비스의 결과는 지난 스캔 것을 그대로 두고, 기동 스캔이 아직이면 그것이 끝난 뒤에 돈다
  **서버와 맥에 나눠 띄운 서버는 하나 더 있다** (2026-10-27 OPS-F4-07) — 에이전트가 받아 온 것은 맥 checkout 이라 위 병합 뒤 훑기는 서버의 옛 파일을 본다.
  서버의 pull timer 가 main 을 받은 뒤 `scripts/scan.ts` 로 전부 다시 훑는다. 옛 파일 훑기가 늦게 끝나면 새 케이스를 덮어서 60초 기다린다 — 정본은 공통/6-인프라 §9.2 「서버와 맥에 나눠 띄우기」
  기동 시 스캔이 실패(tcId 중복 등)해도 admin은 뜬다. 실패 사유는 마지막 스캔 결과(`GET /api/catalog/scan`)에 남기고
  목록 화면 위에 보여준다
  - **서비스 테스트 폴더가 없고 내릴 케이스도 없으면 문제가 아니다** (2026-10-12 PRD-F9-19 · 2026-10-22 좁힘) — 아직 테스트를 안 쓴 새 서비스다. 문제 줄을 안 남기고 목록이 「아직 테스트가 없습니다」를 보인다(§8.1 「목록이 비었을 때」). 내릴 케이스가 있으면 아래 「케이스 폴더를 비우면」을 따른다. 테스트 뿌리 폴더(`PLATFORM_TESTS_DIR`)까지 없으면 마운트가 빠진 것이라 서비스마다 문제 줄로 알린다. 그때는 그 서비스 케이스를 지난 스캔 그대로 둔다
  - **케이스 폴더를 비우면 그 서비스 케이스를 비활성으로 내린다** (2026-10-22 사용자) — 서비스 폴더가 없거나 케이스가 0건인데 뿌리 폴더에 숨김 항목(`.` 으로 시작) · `lost+found` 말고 다른 것이 있으면 마운트는 멀쩡하다. 0건으로 훑은 것처럼 저장해 그 접두사 케이스를 전부 내린다. 내린 건수는 스캔 결과에 문제 한 줄로 남긴다(일부러 비운 것과 폴더 이름을 잘못 적은 사고를 사람이 가르게). git 은 빈 폴더를 안 남겨 케이스를 비운 폴더는 사라진다. 앞 판은 어느 쪽이든 지난 스캔 그대로 뒀다. 10-18 에 비운 MKT 폴더의 케이스 472건이 목록에 남았다. 실행하니 러너가 `CASE_NOT_FOUND` 로 거절해 절차가 빈 `NA` 결과가 쌓였다. 뿌리 폴더가 없거나 못 읽거나 숨김 항목뿐이면 마운트가 덜 된 쪽이 그럴듯해 지금처럼 아무것도 내리지 않는다
- **미확정** (2026-09-25 · 2026-10-11 PRD-F4-02 계산 · PRD-F4-05 꼬리표 빼기): **목록 · 상세 · 엑셀이 보이는 미확정은 계산한 값이다** — 아래 「지도」 ① 과 표준 기획서 지금 판에서 계산한다
  (`apps/admin/src/prd/unconfirmed.ts` — 실행 박제와 같은 식, [실행.md](실행.md) §3.2). 덮는 요구 가운데 확인 필요가 있으면 미확정이고 없으면 확정이다. 무엇을 왜 하는지는 [작성.md](작성.md) §3.6 「★ 표준 기획서」 「미확정」이 정본이다.
  나이는 표준 기획서 항목의 `checkSince` 가 들고 테스트 작성 결정 목록이 줄마다 보인다(2026-10-26 — 앞 판은 「PRD 관리」 메뉴 · [작성.md](작성.md) §3.6 「★ 결정 목록」) — 응답에 `unconfirmedSince` · `oldestSince` 가 없다.
  - **스캐너는 미확정을 안 읽는다** — 앞 판은 케이스 꼬리표 `spec.unconfirmed` 를 `test_case.unconfirmed` 에 옮기고 처음 본 때를 `unconfirmed_since` 에 뒀다. 꼬리표 · K11 · 두 칸은 2026-10-11 PRD-F4-05 에서 없앴다
  - 실행 쪽 박제(`run_item.unconfirmed`)는 카탈로그가 하지 않는다. 실행을 만들 때 Execution 이 한다 ([실행.md](실행.md) §3.2)
- **지도** (2026-10-10 · ① 반영 2026-10-11 PR #204 — `apps/admin/src/catalog/reqMap.ts` · ② 반영 2026-10-11 PRD-F4-04 — `apps/admin/src/catalog/screenMap.ts`): 스캐너가 스캔마다 그 서비스 몫을 지우고 다시 채운다. **사본이라 손으로 안 고친다.**
  ① 요구 ↔ 케이스는 요구사항 표(`docs/cases/<접두사>.md`) 출처 칸의 번호와 축 칸, ② 케이스 ↔ 화면 파일 ↔ 화면 주소는 케이스 파일이 직접 가져오는 Page Object · 화면 조각과 그 파일의 화면 주소 값 · 파일 안 이동이 여는 주소 틀(`open_urls` — 2026-10-26 WEB-F6-03)에서 읽는다.
  표는 [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「표준 기획서 · 지도 · 화면 기록 표」, 무엇을 왜 하는지는 [작성.md](작성.md) §3.6 「★ 표준 기획서」 「지도」가 정본이다.
  - ① 의 출처 칸 번호는 원장 대조와 같은 함수(`덮는번호들` — `번호찾기` 위)로 읽는다 — 번호를 두 곳이 다르게 읽으면 「덮었다」는 셈과 지도가 어긋난다.
    **오류 추정 줄의 첫 번호는 넣지 않는다** (2026-10-12 PRD-F9-08) — 화면을 잡으려고 적은 요구라 그 테스트가 확인하지 않는다. 뒤 번호(그 결과를 올린 확인 필요 항목)만 넣는다 — 번호가 하나뿐이면 그 번호를 넣는다([작성.md](작성.md) §3.6 「설계 기법」 「오류 추정」). 표준 기획서에 없는 번호(옛 표의 원본 번호)도 그대로 넣는다. 줄을 거르는 기준은 다르다 — 원장 대조가 형식 오류로 빼는 줄(출처 번호 10개 넘음)도 지도는 넣고, tcId 는 카탈로그에 실제로 들 수 있는 꼴(K2 의 세 자리)만 받는다
  - tcId 칸이 번호 꼴이 아닌 줄(「제거함(…)」 · 「—」) · 그 서비스 접두사가 아닌 줄 · 축이 넷(정상 · 경계 · 예외 · UI) 밖인 줄은 건너뛴다 — 넣으면 축 제약 한 줄에 그 서비스 지도 전체가 안 바뀐다
  - 표 파일이 없으면 그 서비스 지도를 비운다(덮는 것이 없다). 표 뿌리 폴더(`PLATFORM_CASES_DIR`)가 통째로 없거나 다른 읽기 오류면 옛 지도를 두고 스캔 결과에 문제 한 줄을 남긴다 — 마운트가 빠진 것을 「표 없음」으로 읽으면 모든 서비스 지도가 말없이 사라진다. ① 과 케이스 갱신은 서로 따로 간다(케이스 폴더가 깨지거나 번호가 겹쳐도 ① 은 갱신한다)
  - ② 는 케이스를 저장한 **뒤에** 그 서비스 케이스(`<접두사>-%`) 몫을 지우고 다시 채운다 — 표가 `test_case` 를 외래 키로 건다. 그래서 번호가 겹쳐 케이스 저장을 건너뛰면 ② 도 옛 것을 둔다. 읽지 못한 케이스 파일이 있으면 읽은 케이스 몫만 바꾸고 나머지 줄은 둔다 — 비활성 처리를 건너뛰는 것과 같은 까닭이다(무엇이 정말 사라졌는지 모른다)
  - ② 에 드는 것은 케이스 파일 맨 위 `import` 가운데 `./pages/<이름>.page.js` · `./components/<이름>.component.js` 꼴뿐이다(타입만 가져오기 · `../` · `helpers/` 는 빠진다. 경로를 앞뒤로 못 박는 꼴은 E2E 「만들기」 판별과 같되, 그 판별은 `helpers/` 도 믿는다 — 도메인/시나리오 §3.7). `file` 은 저장소 뿌리 기준 경로(`tests/<폴더>/pages/<이름>.page.ts`), 주소는 그 파일 클래스의 `static 주소` 값을 따옴표 글자 그대로만 읽는다(계산식 · 없음 · 화면 조각이면 NULL). 화면 파일을 못 읽으면 옛 ② 를 두고 스캔 결과에 문제 한 줄을 남긴다
  카탈로그는 표준 기획서 지금 판을 **읽기만** 한다 — 목록 맥락(§8.1)의 기능 묶음 · 요구 문장을 거기서 가져온다. 쓰는 것은 작성 쪽이다.
  맥락을 붙이고 묶음 차례를 짓는 판단은 `apps/admin/src/catalog/context.ts` 한 곳이다 — 목록과 엑셀이 같은 함수를 탄다
- **설계 기법** (2026-10-05 · PR #158): 스캐너는 `spec.techniques` 를 읽어 `test_case.techniques` 에 둔다. 없으면 `'{}'` 이고 다시 스캔하면 덮어쓴다.
  기법이 무엇이고 칸마다 어떤 기법이어야 하는지는 [작성.md](작성.md) §3.6 「설계 기법」, 선언과 K14 는 [공통/2-명세선언.md](../공통/2-명세선언.md),
  칸은 [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「설계 기법 칸」, 목록 · 거르기 · 엑셀은 아래 §7 · §8.1 이 정본이다
  - **기법 이름은 바꾸지 않는 식별자다** — `test_case` 칸 · `?technique=` 값 · 케이스 파일 글자가 같은 낱말(kit `TECHNIQUES`)이다.
    화면에 보이는 글은 `messages` 표가 옮긴다. 이름을 바꿀 날이 오면 옛 이름을 별칭으로 계속 받는다 —
    안 받으면 케이스 파일 · 저장해 둔 주소 · DB 행이 한꺼번에 「모르는 기법」이 된다 (2026-10-05 게이트 1)

## 7. Admin API

```
# Catalog
POST   /api/catalog/scan                 소스 폴더 재스캔 → { added, updated, deactivated, duplicates[] }
GET    /api/catalog/scan                 마지막 스캔 결과 → { scannedAt, added, updated, deactivated, duplicates[], error? }
         ?service=    둘 다. 그 서비스 결과만 낸다(목록 화면이 지금 보는 서비스). POST 는 그 서비스만 훑는다. 없거나 비면 볼 수 있는 서비스 전부 — 케이스 read 거르기는 그대로다 (2026-10-12 PRD-F9-19 · 아래 계약 블록)
         scannedAt 은 고른 서비스 가운데 가장 오래전에 훑은 때다 — 한 서비스만 다시 훑으면 다른 서비스는 지난 때 그대로다
GET    /api/catalog/cases                케이스 검색. 아래 조건을 AND로 겹친다 (조건 정의는 §8.1)
         ?service=    **필수.** 보고 있는 서비스의 접두사 (예: PAY). 배정받지 않은 것이면 403
```

### 8.1 케이스 목록
`(거터: 판정 색) 고르는 칸 | TC ID | 케이스명 | 마지막 결과 + 판정 흐름 | [▶]` — 케이스명을 누르면 오른쪽 서랍으로 상세 칸이 들어온다(아래 「상세 칸」)
→ JSON 원문은 목록에 절대 노출하지 않는다.

**2026-10-19 ⑫ 시안 A — 목록 | 오른쪽 상세 칸.** 실행 기록 A안([실행.md](실행.md) §8.7)과 같은 짜임이다. 시안은 A(오른쪽 칸) · B(탭으로 나눈 상자) · C(따로 연 화면)에서 A 를 골랐다(2026-10-19 사용자).
B 는 열 때마다 목록이 가려 여러 케이스를 훑기 어렵고, C 는 케이스를 옮겨 볼 때마다 목록을 오가야 해서 뺐다.
**2026-10-20 ⑬-2 — 칸을 오른쪽 서랍으로 바꿨다.** 목록 옆에 붙은 칸이 목록 폭을 줄여 케이스명이 밀렸다. 이제 목록은 늘 전체 폭을 쓰고 상세 칸은 목록 위에 겹치는 서랍으로 오른쪽에서 미끄러져 들어온다(대시보드 회귀 실패와 같은 공용 서랍 — [DESIGN.md](../../DESIGN.md) 「모달」의 서랍 줄). Esc · ✕ 로 닫고 닫으면 누른 이름으로 포커스가 돌아온다.
- **줄의 입력 칸 · `[상세]` 버튼을 뺐다.** 값은 상세 칸에서 고친다. 입력 칸이 줄 높이를 두 배로 만들어 창 높이 578px 에서 목록이 한 줄만 보였다(점검 N1)
- **집계 띠를 뺐다.** 네 수는 마지막 결과 탭이 건수로 단다(`실패 7`, §7 `lastCounts` · 2026-10-30 WEB-F7-07 앞 판은 칩). 실행 read 가 없으면 탭을 안 그린다 — 서버가 last 를 무시한다
- 연 케이스는 주소(`case=<tcId>`)에 남는다 — 다른 화면에 갔다 뒤로 와도 그 칸이 열려 있다. 연 줄은 고른 줄 색(실행 기록 고른 줄과 같다)이다. 그 케이스가 지금 쪽에 없으면 칸을 안 그린다.
  다른 화면의 케이스 고리(`케이스주소`)는 그 번호로 찾은 목록(`q=<tcId>&case=<tcId>`)을 연다 — 목록 첫 쪽(50건) 밖 케이스도 칸이 열린다(2026-10-24 FIX-F4-04)

#### 설계 기법 (2026-10-05 · PR #158 · 시안 A1)

**기능 테스트 목록에만 있다** — UI 테스트 목록에는 태그도 필터 판의 줄도 없다(UI 케이스는 기법을 안 단다 — 공통/2-명세선언 K14). 값과 이름 규칙은 §3.1 「설계 기법」이 정본이다.

- **줄** — 케이스명 아래 작은 줄에 `설계 기법` 글자와 기법 태그를 한 덩어리로 붙인다. 기법이 없으면 안 그린다. 덩어리 앞에 가운뎃점을 두지 않는다(위 「맥락」 작은 줄).

#### API 서버 (2026-10-20 · PRJ-F1-04 · 시안 A)

케이스가 뒤에서 어느 서버(인증 · 결제 · 주문)를 불렀는지 목록에서 가른다. **층이 아니라 꼬리표**다 — 정본은 [공통/1-제품과-구조.md](../공통/1-제품과-구조.md) §2 「프로젝트 · 애플리케이션 · API 서버는 다른 층이다」.
시안은 A(호스트 표 + 위쪽 칩 줄) · B(이름별 묶음 + 줄 칩을 눌러 거르기) · C(호스트 표 + 여러 개 고르개)에서 A 를 골랐다(2026-10-20 시작 질문). B 는 칩이 있는 줄 몰라 눌러 보기 전에는 거를 수 있는 줄도 모르고, C 는 줄만 봐서는 어느 서버를 부르는지 안 보인다.

- **꼬리표는 사람이 케이스마다 고르지 않는다.** 설정에서 호스트에 이름을 붙이면(도메인/인증 §8.8 「프로젝트」) 그 호스트를 부른 케이스에 이름이 저절로 붙는다. 한 화면(「결제하기」)이 인증 · 결제 · 주문을 다 부르므로 케이스 하나에 여러 이름이 붙는다
- **케이스를 실행해서 본 호출만 따른다** — 서비스 지도의 케이스 줄(`service_api_use` 의 `tc_id`). 화면 훑기(크롤러)가 본 호출은 케이스가 부른 것이 아니라서 안 센다. 케이스를 아직 실행하지 않았으면 꼬리표가 없다
- **줄** — 케이스명 아래 작은 줄에 이름 태그를 단다. 태그는 판정 색이 아니고 설명 정보다(`설계 기법` 태그와 같은 모양 — `docs/DESIGN.md` 「설계 기법 태그」). 붙은 이름이 없으면 안 그린다
- **필터 판의 줄** — `필터` 판에 `API 서버` 줄을 두고 `전체` · 이름마다 칩 하나를 둔다(2026-10-30 WEB-F7-07 — 앞 판은 검색 줄의 칩 줄). 칩에 건수가 붙는다(`인증 12`, §7 `apiServers[].count`). 하나만 고른다(`aria-pressed`) — 다시 누르면 `전체`로 돌아간다.
  **이름이 하나도 없으면 그 줄을 안 그린다**(§7 `apiServers` 가 `[]`). 고른 이름은 표 위에 `API 서버 인증` 칩으로 남는다
- 고르면 첫 쪽으로 가고 주소에 남는다(`api=<이름>`). 검색 지우기는 이것도 비운다. 「조건에 맞는 N건 실행」과 엑셀은 같은 조건을 탄다. 서비스를 바꾸면 비운다 — 이름은 프로젝트의 것이라 다른 프로젝트로 가면 뜻이 없다
- **주소에 남은 이름이 사라졌으면**(설정에서 이름을 지웠거나 바꿨다) 빈 목록이 뜨고 걸린 조건 칩의 ✕ 로 푼다 — 말없이 전체를 보이지 않는다
- 상세 칸에는 안 그린다 — 줄의 태그가 같은 정보를 이미 보인다

#### 스모크 (2026-10-24 · GAME-F1-13b)

새 빌드가 오면 먼저 도는 핵심 경로 케이스를 목록에서 보고 고친다. 무엇이고 어떻게 도는지는 [실행.md](실행.md) §3.11 「스모크 표시」 · 「스모크 → 회귀」가 정본이다.

- **줄** — 케이스명 옆, `미확정` 배지 뒤에 칩 하나. 켜진 줄은 「● 스모크」(잉크로 진한 중립 테두리 — 대표색 자리 목록(공통/5-화면공통 §8 「대표색」) 밖이고 링크 색은 본문 링크 몫이다). 꺼진 줄은 흐린 「○ 스모크」가 **줄에 마우스를 올리거나 줄 안에 포커스가 있을 때만** 보인다 — 줄마다 흐린 칩이 서면 시끄럽다(시작 질문 승인). 판정 색은 쓰지 않는다
- **누르면 켜고 끈다** — 케이스 쓰기 권한(§7 `PUT /api/cases/:tcId/smoke` 와 같은 칸)이 있을 때만 버튼이다. 사람이 고친 값이 없으면 반대로 보내고, 있으면 `null` 을 보내 AI 가 정한 값(코드 값)으로 되돌린다. 저장이 실패하면 칩 옆에 오류 한 줄. 권한이 없으면 켜진 칩만 글자 꼬리표로 보인다
- **사람이 고친 값**(`smokeSet` 이 null 이 아님) — 칩 끝에 「· 직접」을 붙이고 마우스를 올리면 「직접 고친 값입니다. 다시 누르면 AI 가 정한 값으로 돌아갑니다」. 직접 꺼 둔 칩은 되돌릴 길이라 늘 보인다
- **거르기** — `필터` 판의 `스모크` 줄에 `전체` · `스모크만` 칩(아래 「검색 조건」 12 · 2026-10-30 WEB-F7-07 앞 판은 검색 줄). 고르면 표 위에 `스모크만` 칩이 남는다. 고르면 첫 쪽으로 가고 주소에 남는다(`smoke=1`). 검색 지우기는 이것도 비운다. 「조건에 맞는 N건 실행」과 엑셀은 같은 조건을 탄다 — 「스모크만 돌리기」가 따로 만든 것 없이 된다
- 상세 칸에는 안 그린다 — 줄의 칩이 같은 정보를 이미 보인다

B 는 나무가 236px 을 먹어 1280px 창에서 줄이 쌓이고, C 는 케이스까지 두 번 눌러야 와서 뺐다.

- **접기 — 줄 사이에 묶음 머리 줄을 끼운다.** 기능 묶음 > 화면(API 는 엔드포인트) > 화면 조각 셋이고 더 잘게 쪼개지 않는다. 머리를 누르면 그 아래 머리 · 줄이 접힌다. 처음에는 다 펴져 있다
  - 줄 차례는 서버가 정한다(§7 `sort` 'feature' — 아래 「목록 화면이 지킬 것 셋」). 화면은 이웃한 줄끼리 묶인 자리가 바뀌는 곳에 머리를 끼울 뿐이다
  - 케이스의 기능 묶음은 덮는 요구 가운데 표준 기획서 차례가 가장 앞인 요구의 묶음이다. 지도에 없거나 지금 판에 없는 번호만 덮는 케이스(사람이 쓴 케이스 · 옛 표)는 맨 뒤 「기능 묶음 없음」에 모인다
  - 화면 머리는 **주소 차례**다(주소가 없으면 파일 경로) — 파일 이름 차례로 세우면 `signup-done` 이 `signup` 앞에 섰다(2026-10-11 화면 확인)

  - 화면을 안 쓰는 케이스는 그 묶음 맨 앞에 머리 줄 없이 선다 — 뒤에 서면 바로 위 화면 머리에 딸린 것처럼 보인다
  - **API 애플리케이션은 화면 자리에 엔드포인트가 선다** (2026-10-30 WEB-F7-22 · 시안 11판 「종류마다 달라지는 칸」). 머리는 `POST /api/orders` 와 `엔드포인트` 꼬리표(게임은 `창` · `창 조각`, 화면 코드 `kind.ts` 묶음말). 차례는 경로 틀이 앞인 것(같으면 메서드)이다.

  - **서비스에 기능 묶음이 하나도 없으면(PRD 를 안 쓴다) 기능 묶음 머리를 세우지 않는다** — 「기능 묶음 없음」 머리 하나에 줄 하나를 버린다. 판단은 지금 걸린 조건이 아니라 서비스 전체다(§7 `hasFeatures`) — 걸린 묶음으로 가르면 「기능 묶음 없음」만 보기에서 머리 · `모두 접기` · `연결된 요구 없음`이 사라졌다
  - 머리에는 이름 · `N건` · 실패가 있으면 `실패 N` 을 적고, 「기능 묶음 없음」 머리에는 `PRD 에 연결되지 않은 케이스` 를 붙인다. 건수는 **쪽이 아니라 조건에 맞은 전부**다(§7 `groups`) — 한 쪽 50건이라 큰 묶음은 다음 쪽으로 이어지고, 그때 다음 쪽 머리에 `앞 쪽에서 이어짐` 을 붙인다.

    (2026-10-19 ⑫ — 마지막 결과도 서버가 걸러 `groups` 가 그 조건을 따른다. 예외가 없어졌다)
    실패는 그 묶음 케이스 가운데 어느 디바이스든 마지막 결과가 실패인 것(아래 「마지막판정」과 같다). 카탈로그는 실행 결과를 모르니 화면이 `GET /api/runs/last-by-case` 로 센다. 미실행은 디바이스 목록이 없어 안 센다
  - 화면 · 화면 조각 머리는 **화면 파일 클래스 이름**(`게시판목록화면` → 「게시판목록 화면」 · `머리글`)을 보이고 `화면` · `화면 조각` 꼬리표를 단다. 이름은 지도 ② 가 스캔 때 화면 파일에서 읽는다(작성 규칙이 한글로 짓는다).
    못 읽었으면 화면은 주소(없으면 파일 이름), 화면 조각은 파일 이름이다(2026-10-12 PRD-F9-18 — 앞 판은 「/board 화면」 · 「header 화면 조각」처럼 주소와 영문 파일 이름이 그대로 보였다). 줄 아래 작은 줄의 화면도 같고 주소는 마우스를 올리면 보인다
  - 머리 끝 `이것만 보기` 는 그 묶음 자리로 다시 부른다(§7 `?feature=` · `?screen=` · `?part=` — API 는 `?endpoint=`). 걸린 조건은 표 위 줄에 칩(`회원가입 › 회원가입 화면`)으로 보이고 ✕ 로 푼다. 「조건에 맞는 N건 실행」 · 엑셀도 그 묶음만 담는다.
    거르는 기준은 **묶인 자리**다 — 케이스가 쓰는 다른 화면으로 걸면 고른 묶음에 다른 묶음 머리가 섞여 보인다. 화면 없이 화면 조각만 쓰는 머리는 「화면 없음」까지 건다(§7 `?screen=` 빈 글자)
  - 화면 머리 행동에 `모두 접기` / `모두 펴기` 가 선다(기능 묶음 머리가 있을 때만). 쪽이 아니라 기능 묶음 전부를 접는다. 접은 것은 쪽을 넘겨도 남고 서비스를 바꾸면 버린다
- **줄 아래 두 줄** — 케이스명 아래에
  - **요구 줄**: 첫 요구 번호 · 요구 문장(한 줄로 자르고 전체는 마우스를 올려 본다) · 요구가 더 있으면 `외 N건`. 전부는 상세 칸 「요구」 구획에서 본다.
    지금 판에 없는 번호는 고리 없이 `PRD 에 없는 번호예요` 를 적는다. 덮는 요구가 없으면 `연결된 요구 없음` — PRD 를 안 쓰는 서비스에서는 이 줄을 안 그린다
  - **작은 줄**: 종류(정상 · 경계 · 예외 — UI 목록은 전부 UI 라 안 적는다) · 화면(API 는 엔드포인트) · 설계 기법. 덩어리마다 통째로 넘어가고 가운뎃점으로 잇지 않는다 — 다음 줄이 점으로 시작했다(진행판 WEB-F2-14).
    지원 디바이스는 2026-10-19 ⑫ 에서 뺐다 — 마지막 결과 칸이 디바이스마다 이름을 달아(`실행 기록 없음` 포함) 한 줄에 두 번 나왔다(점검 7.12)
- **요구 번호를 누르면 「PRD 관리」 그 항목으로 간다** — 주소 `#/prd/<번호>`(번호 꼴 `<접두사>-REQ-<3자리>` 만). 번호 앞머리가 곧 서비스라 띠가 다른 서비스면 그 번호의 배정 서비스로 띠를 바꿔 연다 — 다른 서비스 실행의 실패 카드도 요구 고리를 건다(2026-10-24 FIX-F4-04). 메뉴가 그 묶음과 줄을 편 채로 열고 그 줄로 가서 한 단계 밝은 면으로 보인다.
  작성 `read` 가 없으면 번호가 글자뿐이다
- **요구 문장은 케이스 `read` 로 보인다** — 케이스 이름과 같은 무게로 본다. 근거 · 판 이력 · 상태 고치기는 「PRD 관리」 메뉴(작성 칸)에만 있다

#### 상세 칸 (2026-10-19 ⑫ 시안 A · 앞 판 2026-09-21 줄 입력 칸 · 2026-09-22 상자)

값을 보려고 다른 화면으로 나가던 것을 없앤다. 목록이 **거기서 끝나는 자리**가 된다.
케이스명을 누르면 오른쪽 서랍으로 상세 칸이 들어온다(2026-10-20 ⑬-2). 같은 이름을 다시 누르거나 ✕ · Esc 를 누르면 닫히고, 닫으면 누른 이름으로 포커스가 돌아온다 (DESIGN.md 포커스 규칙).

**앞 판 둘을 뒤집었다.** 2026-09-21 에는 값을 줄의 입력 칸에서 고쳤고, 2026-09-22 에는 상세를 상자로 열었다(펼침은 열렸다는 느낌이 없어서였다).
줄의 입력 칸은 줄 높이를 두 배로 만들어 목록이 몇 줄만 보였고(점검 N1), 상자는 열 때마다 목록을 가리고 길어서 절차 · 값 · 이력을 오가려면 한참 내려가야 했다(점검 7.12).
칸은 목록 옆에 서서 열렸다는 것이 바로 보이고 목록을 가리지 않았다. ⑬-2 부터는 목록 오른쪽 위에 겹치는 서랍이다 — 목록 오른쪽 일부를 가리는 대신 목록 폭이 줄지 않아 케이스명이 밀리지 않는다.

**칸에 서는 차례** — 위에서부터
1. **미확정 사유** — 미확정 케이스면 `미확정` 과 사유 한 문장(§7 `unconfirmed`)
2. **요구** · **설계 기법** · **사전조건**
3. **시험 절차** — 마지막 실행에서. 꼬리에 `RUN <번호> · <때>`. 마지막이 한 건 실행이면 `RUN <붙은 실행> 다시 실행 · <때>`, 붙지 않았으면 `한 건 실행 · <때>` 다(2026-10-30 WEB-F7-02 · [실행.md](실행.md) §3.2).
   - **디바이스마다 고른다.** 둘 이상 돌았으면 `PC 통과` · `모바일 실패` 칩이 서고 **처음에는 깨진 디바이스**가 열린다 — 앞 판은 첫 디바이스(PC) 것만 보여 모바일만 깨진 케이스가 통과 절차로 보였다(점검 7.7)
   - **실패한 절차 아래에 실패 이유 한 줄**(유형 칩 + 사람 말 — [실행.md](실행.md) §8.3 「실패 이유」)과 실패 화면이 있으면 `실패 화면 보기` 를 단다. 응답에 둘 다 있는데 안 그렸다(점검 7.9). 오류 원문은 항목 상세에서 본다
4. **입력값 · 기대결과** — 아래 「값 고치기」. 그 아래 단추 줄에 `모두에게 저장` · `이 값으로 실행`(값이 없는 케이스는 `실행`)
5. **실행 기록** — 실행 하나에 한 줄이다(`실행 N번`). 한 건 실행도 한 줄이고 머리가 `한 건 실행` · `다시 실행 · RUN N 에 붙음` · 도는 중이면 `진행 중`(누르면 진행 창)이다(2026-10-30 WEB-F7-02 · [실행.md](실행.md) §3.2 · §7 `history` 의 `origin` · `rerunOf`). 반복 실행은 `10번 · 실패 3 · 통과 7` 로 한 줄에 접는다 — 앞 판은 회차마다 같은 제목으로 열 줄 넘게 나왔다(점검 N7). 디바이스가 둘이면 같은 줄에 적고, 수는 디바이스 · 회차마다 하나씩 센 판정 수다(PC · 모바일을 한 번 돌리면 `2번`)
6. **코드 기본값 바꾸기 요청** — 접어 둔다(아래)

**값 고치기** — 케이스가 선언한 값이 **기본값이 채워진 채로 고칠 수 있는 칸**으로 나온다.
**채우는 순서는 저장값 → 코드 기본값이다** (2026-09-29). 정본은 실행 §8.2 「저장값 — 케이스마다 한 벌」이다.
칸을 만드는 규칙은 실행 §8.2 의 폼 자동 생성이 정본이고 상세 칸이 그것을 그대로 쓴다 —
**두 벌을 만들지 않는다.** 비밀값 가림도 거기서 온다. 칸 이름에 코드의 칸 이름을 붙이지 않는다(말풍선에도 — 점검 7.12).

- **고친 값은 그 실행에만 쓰인다.** 케이스 파일의 기본값은 안 바뀐다 —
  `POST /api/runs` 의 그 항목 `params`·`expected` 가 될 뿐이고 `run_item` 에 스냅샷으로 박힌다 (§3.2).
  `이 값으로 실행` 은 고친 값을 실은 실행 창(실행 §8.10)을 연다 — 앞 판 상세 상자에는 값을 고칠 수 있는데 단추가 `닫기` 뿐이었다(점검 7.10)
- **다음 실행에도 남기는 길은 저장값이다** — 고친 칸이 있으면 `모두에게 저장` 이 생긴다 (실행 §8.2 「저장값 — 케이스마다 한 벌」).
  **누르기 전에** 그 옆에 `팀 모두와 정기 실행이 이 값을 씁니다` 를 적는다 — 앞 판은 줄의 `저장` 을 누른 뒤에 4초만 떠서 모르고 팀 값을 바꿨다(점검 7.6)
- **고친 값의 수명** — 칸을 닫거나 쪽을 넘겼다 돌아오면 남고, **서비스를 바꾸면 버린다**.
  칸 이름이 같으면(`env`·`userId`) 남의 서비스 케이스에 그대로 붙는다.
  실행 창(실행 §8.10)과 **같은 표를 쓴다** — 두 벌이면 두 자리가 다른 값을 보여준다

**부르기**
- **위의 「케이스마다 이력을 따로 부르지 않는다」를 어기지 않는다.** 그 규칙은 **목록**을 두고 한 말이고,
  여기는 **사람이 한 줄을 열었을 때** 부른다. 목록이 부르는 것이 아니다
- **한 번 받은 것은 닫았다 열어도 다시 안 받는다.** 닫을 때마다 버리면 그 예외가 위반으로 바뀐다.
  **받아 둔 것은 목록이 들고 있는다** — 칸이 들면 닫는 순간 같이 사라진다. 디바이스를 바꿔 부른 절차도 같다
- 시험 절차는 마지막 실행이 있을 때만 있다. 없으면 그 사실을 적는다. 통로 하나가 실패해도 나머지는 그린다

**「코드 기본값 바꾸기 요청」** (2026-10-01 — [작성.md](작성.md) §3.6 「★ 케이스 고치기」가 정본). 작성 `write` 일 때만 보인다.
- **칸 맨 아래에 접어 둔다**(2026-10-19 ⑫) — 펴 두면 위 기대결과 칸과 두 벌로 보여 어느 것이 이번 실행 값인지 헷갈렸다(점검 7.11). 펴면 아래가 보인다
- 위 기대결과 칸(이번 실행 값 · 저장값)과 **이름을 갈라** 섞이지 않게 한다. 칸은 **코드 기본값**으로 채워 열리고 바꾼 칸만 보낸다.
  비밀값 칸과 다섯 꼴(글자 · 수 · 정수 · 참거짓 · 선택지) 밖의 칸은 안 보인다. **바꿀 칸이 하나도 없으면 `요청 보내기` 를 안 그린다** — 누를 수 없는 단추가 섰다(점검 N8)
- 그 칸에 저장값이 있으면 「반영되면 이 저장값은 지워집니다」를 적는다
- **「확정」 고르개는 없앴다** (2026-10-11 PRD-F4-05 — 꼬리표와 함께). 미확정은 테스트 작성 「결정 필요」에서 확정한다(2026-10-26 앞 판은 「PRD 관리」 · [작성.md](작성.md) §3.6 「★ 표준 기획서」 「미확정」)
- 「케이스 삭제 요청」은 두 번 눌러야 간다(「삭제 확인」 · 「취소」). 누르면 그 케이스를 쓰는 E2E 시나리오를 번호 · 이름으로 보인다. 지우면 다른 케이스로 바꿀 때까지 그 시나리오를 실행할 수 없다(시나리오 §3.7 결정 8). 목록을 못 읽으면 못 돈다는 문장만 적는다
- 보낸 뒤 「작성 요청 N번」 연결을 보인다 — 반영(머지)은 테스트 작성 화면에서 한다

**③ 판정 흐름** — 마지막 결과 옆에 최근 판정이 작은 막대로 늘어선다. **디바이스마다 하나다** —
데이터가 `(케이스, 디바이스)` 단위이고 줄도 디바이스마다 배지를 그린다.
**색만으로 전달하지 않는다** — 판정마다 막대 높이가 다르고 개수를 글자로 같이 적는다 (DESIGN.md).
다섯에 못 미치면 남는 자리를 빈 칸으로 채워 길이를 지킨다.

#### 여러 건 골라 한 번에 돌린다 (2026-09-21 결정)

케이스는 `[실행]`으로 한 건씩만 돌릴 수 있었다. 그런데 §8.2는 이미 여러 건을 전제해
실행 항목 수를 세고 있었다 — **고르는 자리가 없어 그 「케이스 수」가 영원히 1이었다.**
명세가 자기 안에서 어긋나 있던 것을 여기서 맞춘다. `[실행]`은 그대로 둔다.
**2026-10-09 에 줄의 `[실행]` 은 ▶ 아이콘 버튼이 됐고 누르면 그 한 건으로 같은 실행 창(실행 §8.10)이 열린다** (UI 개편 묶음 4).
글자를 아이콘으로 바꾼 까닭은 영어 화면에서 「Run」이 「Details」 아래로 밀려 내려갔기 때문이다(진행판 WEB-F2-12). 이름은 화면 읽기가 「<tcId> 실행」으로 말한다.
**고르면 머리 버튼이 셋 · 넷으로 늘어 좁은 창에서 제목이 세로로 섰다**(WEB-F2-10) — 화면 머리는 제목 칸이 모자라면 버튼 묶음을 아랫줄로 보낸다(공통/5-화면공통 §8 「화면 머리」). 2026-10-30 WEB-F7-08 부터는 고른 것의 단추가 고르기 바에 있어 골라도 머리가 늘지 않는다.

- **고르는 칸은 왼쪽 거터 칸 옆, 케이스 번호 앞에 둔다.** 줄 내용 쪽 첫 요소로 두지 않는다 —
  목록이 좁아 줄이 쌓이면(DESIGN.md 「반응형」) 내용 쪽 첫 요소가
  케이스명 위에 홀로 한 줄이 된다
- **표머리의 첫 칸에 「이 쪽 전체 선택」 체크박스를 둔다** (2026-09-30). 지금 보이는 쪽의 케이스를 한 번에 고르고, 전부 골랐으면 한 번에 푼다.
  일부만 골랐으면 「일부 선택」 모양이고 누르면 나머지까지 고른다. **다른 쪽에서 고른 것은 건드리지 않는다.** 모든 쪽으로 넓히는 것은 아래 「모두 고르기」 띠다. 모두 고른 동안은 이 체크박스가 「전부 선택」 모양이고 누르면 전부 풀린다. 목록이 좁아 줄이 쌓여도 이 체크박스는 「이 쪽 전체 선택」 글과 함께 남는다(위 「칸마다 이름을 단다」 · 2026-10-05 PR #159 — 전에는 휴대폰 폭에서 표머리와 함께 감춰 줄마다 골라야 했다)
- **이 쪽을 다 고르면 표머리 아래에 「모두 고르기」 띠가 선다** (2026-10-30 WEB-F7-08 · 시안 11판). `이 쪽 50건을 모두 골랐습니다 · 조건에 맞는 120건 모두 고르기`.
  누르면 **쪽을 넘기지도 줄을 받아 오지도 않고** 「조건에 맞는 전부」를 고른 상태가 된다 — `조건에 맞는 120건을 모두 골랐습니다 · 고르기 풀기`. 받아 오는 것은 그것으로 무엇을 할 때다(아래 「「전체」는 보이는 쪽이 아니라 모든 쪽이다」).
  이 쪽이 조건에 맞는 전부면(`total` 이 보이는 줄 수와 같으면) 넓힐 것이 없어 띠가 서지 않는다. 모두 고른 동안은 쪽을 넘겨도 줄이 다 고른 모양이다.
  필터 · 찾기 · 결과 탭을 바꾸면 「모두」는 풀린다(다른 목록을 가리키게 된다). 하나씩 고른 줄은 그대로 남는다. 모두 고른 채 줄 하나를 풀면 「모두」가 풀리고 이 쪽에서 고른 것만 남는다(Gmail · Jira 와 같다)
- **상한은 띠가 미리 알린다** — 모두 고른 뒤에야 단추가 잠기면 까닭을 모른다. 띠가 서는 순간부터 적는다.
  - 삭제 요청 상한([작성.md](작성.md) §3.6 「★ 케이스 고치기」 「한 요청」)보다 조건에 맞는 것이 많으면 `모두 고르면 삭제 요청은 보낼 수 없습니다(한 번에 <상한>건까지)`. 모두 고른 동안 고르기 바의 `삭제 요청` 은 잠긴다. 작성 `write` 가 없으면 안 적는다
  - 실행이 쪽을 돌며 담는 한계(아래 「「전체」는 보이는 쪽이 아니라 모든 쪽이다」 — 화면 코드 `useRunPick.ts` `쪽상한` × 쪽 크기)보다 많으면 `실행은 앞 N건까지만 담습니다`. 실행 `write` 가 없으면 안 적는다
- **Shift 를 누른 채 줄을 고르면 지난번 누른 줄부터 이 줄까지가 한 번에 바뀐다** — 이 줄이 고르기로 바뀌면 사이 줄을 다 고르고, 풀기로 바뀌면 다 푼다. 사이는 눈에 보이는 줄만이다 — 접은 묶음 안의 줄은 바뀌지 않는다. 지난번 줄이 이 쪽에 없으면(쪽을 넘겼다) 이 줄 하나만 바뀐다. 고르기를 풀면 지난번 줄도 잊는다
- **하나라도 고르면 목록 아래 가운데에 고르기 바가 뜬다**(실행 `write` 도 작성 `write` 도 없으면 할 일이 없어 안 뜬다) — 고른 수(`3건 고름` · `조건에 맞는 120건 모두 고름`) · `실행` · `삭제 요청` · `고르기 풀기`. 모양은 [DESIGN.md](../../DESIGN.md) 「고르기 바」가 정본이다.
  **고른 것으로 하는 일은 바에만 있다.** 바가 사라지면(고르기 풀기 · 요청을 보낸 상자를 닫음) 포커스는 머리의 실행 단추로, 실행 권한이 없어 그 단추가 없으면 「이 쪽 전체 선택」으로 간다
- **고른 것으로 「삭제 요청」을 낸다** (2026-10-01 — [작성.md](작성.md) §3.6 「★ 케이스 고치기」). 작성 `write` 이고 하나라도 골랐을 때만 고르기 바에 보인다(2026-10-30 앞 판은 화면 머리).
  「확정 요청」은 2026-10-11 PRD-F4-05 에서 없앴다 — 미확정은 테스트 작성 「결정 필요」에서 확정한다(2026-10-26 앞 판은 「PRD 관리」).
  확인 상자를 거친다 — 위 「케이스 삭제 요청」과 같은 시나리오 줄을 띄운다. 한 번에 고를 수 있는 건수는 서버 상한([작성.md](작성.md) §3.6 「★ 케이스 고치기」 「한 요청」)까지 — 넘으면 상자가 막고 까닭을 적는다
- **화면 머리의 실행 단추는 늘 `조건에 맞는 N건 실행` 이다**(N 은 목록 응답의 `total`). 골라 두어도 글자도 대상도 안 바뀐다 — 고른 것의 실행은 고르기 바의 `실행` 이다.
  앞 판은 `전체 실행` 이라 적어 놓고 조건에 맞는 것만 걸었다(점검 7.8). 자리는 목록 위 `다시 스캔` 옆이다.
  **앞 판(2026-09-21 ~ 10-30)은 단추 하나가 고르면 `선택한 N건 실행` 으로 글자가 바뀌었다** — 같은 일을 하는 단추가 둘이면 안 된다는 판단이었다.
  고르기 바가 생기며 고른 것의 실행이 바에 서야 해서 머리까지 바뀌면 같은 일을 하는 단추가 두 자리에 선다. 그래서 머리는 조건, 바는 고른 것으로 나눴다(2026-10-30 WEB-F7-08 시작 질문). 「같은 일을 하는 단추를 두 자리에 두지 않는다」는 그대로다
- 누르면 실행 창이 열린다. 그 안에서 무엇을 정하는지는 **[실행.md](실행.md) §8.10이 정본이다**

##### 「전체」는 보이는 쪽이 아니라 모든 쪽이다

목록은 한 쪽씩 받아 온다(§7 `?page=`, 한 쪽 분량은 응답의 `pageSize`가 알려준다).
화면에 지금 떠 있는 쪽만 담으면 `조건에 맞는 N건 실행` 이 거짓말이 된다.

- **버튼을 누르면 화면이 쪽을 돌며 전부 받아 온다.** 받는 동안 버튼을 누를 수 없고,
  받고 있다는 사실을 **화면 줄**로 적는다. 말풍선으로 적지 않는다 (DESIGN.md 접근성 기준)
- 몇 쪽을 돌지 총건수로 계산하지 않는다. 다음 쪽이 있는지는 응답이 알려주는 값으로 판단한다
  (아래 「목록 화면이 지킬 것 셋」의 셋째)

#### 엑셀로 내려받기 (2026-09-29 · 시안 B)

화면 머리(`다시 스캔` 옆)에 `이 결과 엑셀로 (N건)` 버튼을 둔다(2026-10-30 WEB-F7-07 — 앞 판은 검색 줄 끝, 표 위를 한 줄로 줄이며 옮겼다). N 은 목록 응답의 `total` 이고, 받는 파일은 **지금 건 검색 조건 그대로** 쪽 없이 전부다 (§7 `GET /api/catalog/export`).
0건이면 누를 수 없다. 받는 동안 버튼을 막고 `만드는 중…` 으로 바꾼다. 실패(403 · 500)면 목록 위에 알림 한 줄을 띄운다.
화면의 `마지막 결과` 탭(조건 5)도 파일에 걸린다 (2026-10-19 ⑫ — 서버가 거르게 되면서. 앞 판은 화면에서 걸러 파일에 안 걸렸고 버튼이 「실패」를 걸어도 「(382건)」이었다). N 은 그 조건의 `total` 이다.
**입력값·기대값 칸은 코드 기본값을 싣는다. 저장값(실행 §8.2)은 싣지 않는다** (2026-09-29).
기능 테스트 목록에서 받은 파일은 시트 ① 에 `설계 기법` 열이 있고 UI 테스트 목록에서 받은 파일에는 없다 — 설계 기법(조건 6)도 파일에 걸린다. 열 모양은 §7 (2026-10-05 PR #158).
맨 끝에는 `기능 묶음` · `요구 번호` 열이 있고 조건 7~10 도 파일에 걸린다 — 줄 차례도 목록과 같다 (2026-10-11 PRD-F5-01).

#### 목록이 비었을 때 (2026-09-17 결정)

지금은 0건이면 언제나 `찾는 케이스가 없습니다.` 하나다.
**검색한 적 없는 사람에게도 「찾는」이라고 말한다.**
이 화면은 이 도구를 처음 켠 사람이 만나는 자리다. 여기서 막히면 도구가 고장난 것처럼 보인다.

| 왜 비었나 | 무엇을 보여주나 | 다음 행동 |
|----------|---------------|----------|
| 아직 한 번도 안 불러옴 (`scannedAt`이 없다) | `아직 케이스를 불러오지 않았습니다` + 무엇을 하는 것인지 두 줄 | 가운데 큰 `케이스 불러오기` 버튼 |
| 아직 테스트가 없음 (`scannedAt`은 있고 전체 건수가 0 · 이 서비스 스캔에 겹친 번호 · 오류가 없다 — 테스트 폴더가 없는 새 서비스 · 폴더를 비운 서비스의 다음 스캔부터, 2026-10-12 PRD-F9-19) | `아직 테스트가 없습니다` + `「테스트 작성」에서 처음 작성을 시작합니다` | `다시 스캔` |
| 불러왔는데 0건 (`scannedAt`은 있고 전체 건수가 0 · 이 서비스 스캔에 겹친 번호나 오류가 있다 — 폴더를 비워 케이스를 내린 바로 그 스캔도 여기다. 사유에 내린 건수가 보인다, §3.1) | `불러왔지만 케이스가 하나도 없습니다` | `규칙에 걸린 파일 N건 · 사유 보기` |
| 검색·필터에 안 걸림 (조건이 하나라도 걸려 있다) | `'장바구니'에 맞는 케이스가 없습니다` — 친 글자를 그대로 넣는다 | `검색 지우기` |

- **갈래를 가르는 값은 응답에 이미 있다** — `scannedAt`과 전체 건수, 화면이 건 조건, 그 서비스 스캔 결과의 `duplicates[]` · `error`(`?service=` 로 받는다).
  새 API가 필요하지 않다
- 둘째 줄의 `사유 보기`는 스캔 결과의 `duplicates[]`와 규칙 위반 목록으로 간다.
  「하나도 없다」만 말하고 왜인지 안 말하면 사람이 할 수 있는 일이 없다

#### 목록 화면이 지킬 것 셋 (2026-09-16 결정)

- **목록을 부르는 자리를 한 곳에 모은다.** 화면 여러 곳에서 각자 부르면 갈아 끼울 때 다 찾아야 한다
- **정렬 순서를 화면이 정하지 않는다.** 응답이 준 순서 그대로 그린다.
  순서가 관련도순으로 바뀌는 날, 화면이 `tcId` 순을 전제하면 목록이 뒤죽박죽으로 보인다
- **`모두 N건`을 정확한 값으로 전제하지 않는다.** 이 숫자는 안내로만 쓰고, 다음 페이지가 있는지는 응답이 알려주는 값으로 판단한다.
  **지금 케이스 목록 화면이 이 숫자로 페이지 수까지 계산하고 있다. 이것부터 고친다** — 총건수가 근사치가 되는 날 빈 페이지가 생긴다
