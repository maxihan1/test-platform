### 3.8 API 테스트 — Swagger 로 API 를 시험한다 (2026-10-20 사용자)

사용자(2026-10-20) 「제품 API가 sms나 노티피케이션 server to server api 등 이런걸 자동화 테스트 하려는거야」 · 「스웨거나 API문서를 넣으면 AI가 테스트 스크립트까지 작성하고 그걸 E2E에도 활용 할 수 있어야 함 … API 문서에 따라 응답값이 제대로 오는지도 확인」.
아래 결정 표는 같은 날 대화로 정했고 시작 질문(API-F1-01)에서 약속 묶음을 승인받았다. 다시 묻지 않는다.

#### 꼬리표와 다르다

공통/1 §2 「API 서버」(`project_api_server`)는 **화면 케이스가 뒤에서 부른 호스트에 붙는 칩**이다 — 사람이 고르지 않고 실행 기록이 붙인다.
종류 「API」 애플리케이션은 **그 API 자체를 직접 두드리는 시험 대상**이다. 케이스 번호 접두사를 받고 프로젝트에 속하고 E2E 에서 다른 애플리케이션과 섞인다.
같은 호스트가 둘 다일 수 있다 — 쇼핑몰 화면 케이스의 칩 [알림] 과, 알림 서버를 직접 시험하는 「데모마켓 알림」 애플리케이션.

- **종류는 만들 때 정하고 바꾸지 않는다** — 접두사처럼. 바꾸면 이미 있는 케이스가 화면 케이스인지 API 케이스인지 섞인다. 설정 API 는 만들 때만 `kind` 를 받는다(도메인/인증 §7)
- API 애플리케이션의 케이스는 기능 테스트(`-FN-`)뿐이다. UI 테스트(`-UI-`)는 화면이 없어 작성이 만들지 않는다(작성 지침 — API-F1-06)
- **API 애플리케이션 케이스의 호출은 서비스 지도(`service_api`)에 넣지 않는다** — 자기 자신이라, 넣으면 자기 호스트가 「API 서버」 칩 후보로 뜬다. 화면 케이스가 이 API 를 부른 것은 지금처럼 지도에 든다
- 디바이스는 `desktop` 하나다 — 브라우저를 열지 않지만 러너가 Playwright 프로젝트 이름으로 돌리므로 값은 있어야 한다. `apiDoc` 을 단 케이스가 `platforms` 에 다른 값을 적으면 `defineCase` 가 던진다(K8) — 같은 API 를 두 번 부르는 항목이 생기지 않게. 화면 · 리포트는 API 애플리케이션 케이스의 디바이스 칸을 그리지 않는다

#### API 문서와 판

- **문서 주소 = 대상 서버 주소 + 문서 경로**(`service.api_doc_path`, 예: `/openapi.json`). 대상 서버마다 같은 경로로 받아 볼 수 있다. 다른 호스트에 있는 문서는 파일로 올린다
- **받는 것은 OpenAPI 3.0 · 3.1 JSON 하나다.** 최상위 `openapi` 가 `3.` 으로 시작하지 않거나 JSON 이 아니면 400 `BAD_API_DOC` 과 이유 한 줄. Swagger 2.0 은 변환해서 올리라고 이유에 적는다. YAML 은 1차 밖(결정 12). 상한 5MB — 넘으면 413
- **지문** — 키를 정렬하고 공백을 뺀 JSON 의 SHA-256. 들여쓰기 · 키 차례만 다른 문서는 같은 판이다.
  한계 — 문서에 만든 시각 같은 값을 매번 다르게 싣는 서버는 실행마다 판이 오른다. 그런 서버가 나오면 지문에서 뺄 칸을 이 절에 더한다
- **판은 마지막 판과 지문이 다를 때만 오른다.** 옛 판과 같은 내용으로 돌아가도 새 판이다(마지막 판하고만 견준다). 판 번호는 애플리케이션마다 1 부터
- **판이 오르는 길은 셋** — ① 실행 시작(기준 서버로 돌 때) ② 「지금 받기」(기준 서버 주소에서) ③ 파일 올리기. 같은 애플리케이션의 판 올리기는 서비스 행을 잠그고 해서 동시에 둘이 같은 번호를 만들지 않는다
- **실행 시작 때 견주기** — 케이스 실행(`test_run.kind` 가 `UI` · `FN` — `execution/runKind.ts` 의 종류조건)이고 애플리케이션이 API 종류이고 문서 경로가 있을 때만. 서버가 그 대상 서버 주소 + 경로에서 10초 안에 받는다. **실행을 기다리게 하지 않는다** — 실행과 항목을 먼저 세워 러너에 보내고 견주기는 옆에서 돌다 끝나면 아래 칸을 채운다. 항목은 케이스가 만들어진 판을 DB 에서 읽으므로 견주기를 기다릴 까닭이 없다
  - 기준 서버(`service.api_doc_env`)면 다르면 판을 올린다(누른 사람 = 그 실행의 실행자, 정기 실행이면 비움)
  - 다른 서버면 판을 올리지 않고 마지막 판과 다를 때 `test_run.api_doc_note = 'DIFFERS'` — 실행 결과 머리에 「이 서버의 API 문서가 기준 서버 문서(버전 N)와 다릅니다. 배포 전일 수 있습니다」 한 줄
  - 못 받았으면 `'FETCH_FAILED'` — 「API 문서를 받지 못했습니다」 한 줄. **실행은 막지 않는다** — 문서 서버가 잠깐 죽었다고 회귀 시험이 멈추면 안 된다
  - 견주기를 마친 때의 마지막 판 번호를 `test_run.api_doc_version` 에 박제한다. 견주기가 안 끝났으면 둘 다 비어 있다
  - E2E 시나리오 실행은 견주지 않는다(1차) — 시나리오는 여러 애플리케이션을 섞는다

#### API 인증

- **대상 서버 줄마다 이름 붙은 인증 여럿**(`service_env.api_auths`) — 이름 · 토큰 받는 주소 · 클라이언트 아이디 · 비밀값. 이름은 1~20자이고 한 줄 안에서 겹치지 않는다
- **케이스는 이름만 안다** — `api('고객사 A')` 가 토큰이 붙은 요청 도구를 준다. 지금 `request` 는 「인증 없이」 그대로다(공통/3 「API 테스트 타입」 · 공통/2 §4 「API 케이스」). 같은 이름을 대상 서버마다 넣어 두면 케이스는 서버를 몰라도 된다
- **토큰 받기는 OAuth2 client credentials(RFC 6749 4.4절)다** — `POST <토큰 주소>`, 본문 `grant_type=client_credentials`(form), 클라이언트 인증은 HTTP Basic. 응답의 `access_token` 을 `Authorization: Bearer` 로 붙이고 `expires_in`(초)로 만료를 잰다. `expires_in` 이 없으면 그 항목이 끝날 때까지 쓴다.
  토큰 주소가 `/` 로 시작하면 케이스의 요청과 같은 규칙(Playwright `baseURL`)으로 그 대상 서버 주소에 붙이고, 아니면 `http(s)://` 주소여야 한다
- **토큰은 항목(케이스 1건 프로세스)마다 처음 `api(이름)` 을 부를 때 받고, 요청마다 만료 30초 전이면 다시 받는다.** 실행 전체에서 나눠 쓰지 않는다 — 항목마다 프로세스가 따로라 나누려면 러너가 토큰을 들고 만료 처리가 두 곳으로 갈린다.
  한계 — 항목 수만큼 토큰을 받는다. 토큰 주소가 횟수를 막으면(429) 그때 러너가 실행 단위로 들고 나눠 주게 올린다
- **없는 이름을 부르면 그 항목은 실패다** — 「이 대상 서버에 API 인증 '고객사 A' 가 없습니다」(kit 은 대상 서버 이름을 모른다 — 실행 머리에 이미 보인다). 토큰을 못 받으면(주소 오류 · 401 · 시간 초과) 「API 인증 '고객사 A' 토큰을 받지 못했습니다 — 401」로 실패한다
- **비밀값은 화면 · 응답에 되돌려 보이지 않는다** — 끝 4자리만(`clientSecretLast4`). 고치기는 설정이라 admin 만이다(도메인/인증 §7). `service_env` 는 `grafana_ro` 에 주지 않는다
- **가림** — kit 이 절차 기록(`httpTrace`)을 남길 때 실행 §3.2 「가림」(trace 기록)과 같은 이름 목록(인증 머리 · 세션 · 쿠키 · `api_key` · `Bearer` · `Basic` 꼴 · 비밀 칸 이름)에 더해 본문 · 응답의 `access_token` · `accessToken` · `refresh_token` · `refreshToken` · `client_secret` · `clientSecret` 키의 값, 이번 항목이 받은 토큰과 비밀값 글자를 `********` 로 바꾼다. 저장 · 화면 · 리포트는 이미 가린 것만 본다. 서버의 비밀 입력값 가림(공통/2 §4.1)은 그대로 한 번 더 돈다
- **작성 에이전트도 받는다** — 작성 중 케이스를 돌려 보려면 인증이 있어야 한다. 집기 응답이 고른 대상 서버의 인증을 실어 주고 비밀값은 에이전트가 가리는 목록에 든다(도메인/작성 §3.6 「★ 역할별 계정」과 같은 규칙)
- **E2E** — 단계마다 그 단계 케이스의 애플리케이션 · 짝지은 대상 서버의 인증을 받는다(도메인/러너 §5.2 「API 케이스 실행」). API 호출 단계도 인증 이름을 고르면 같은 인증으로 토큰을 받는다(도메인/시나리오 §3.7 결정 14 — 2026-10-21 API-F1-10). **인증과 판 원문은 러너로 보내기만 하고 부품 기록(`scenario_run_part.part`)과 시나리오 응답에는 넣지 않는다** — 그 칸은 그때의 부품 정의 · 입력값 스냅샷이라 넣으면 비밀값이 DB 와 화면에 남는다

#### 응답 모양 확인

- **어느 판과 견주나** — 케이스가 만들어진 판이다. 케이스 머리 `apiDoc: <판>`(공통/2 §4 「API 케이스」)을 스캐너가 `test_case.api_doc` 에 담고, 서버가 실행 때 그 판 원문을 러너에 싣는다. 그 판이 없으면 그 항목을 러너에 보내지 않고 미실행(`NA`)으로 닫는다 — 「API 문서 버전 9 이(가) 없습니다」. **API 애플리케이션 케이스에 `apiDoc` 이 없어도**(손으로 썼거나 작성이 빠뜨림) 같이 미실행으로 닫는다 — 「케이스에 API 문서 버전이 적혀 있지 않습니다」. 모양 확인 없이 조용히 통과하지 않게다.
  **E2E 시나리오의 case 부품은 판이 있으면 싣고, 없으면 모양 확인 없이 돈다**(1차) — 부품 하나 때문에 시나리오 전체를 미실행으로 닫지 않는다. 실행 시작 때 견주기를 E2E 에서 안 하는 것과 같은 1차 범위다
- **무엇을 견주나** — 그 항목이 `request` · `api(…)` 로 보낸 모든 요청의 응답. kit 이 응답을 받은 자리에서 본다 — 절차 기록은 2000자에서 잘리지만 모양 확인은 잘리기 전 본문을 본다
- **어느 API 인가** — 메서드와 경로로 문서의 `paths` 틀을 찾는다(`/v1/pushes/{id}`). 문서 `servers[0].url` 에 경로가 있으면 틀 앞에 붙여 맞춘다. 글자 구간이 많은 틀이 이긴다(`/v1/pushes/batch` 가 `/v1/pushes/{id}` 보다 먼저). **문서에 없는 경로는 견주지 않는다** — 토큰 주소처럼 문서 밖 요청이 있다
- **어느 응답인가** — 받은 코드와 같은 줄 → `4XX` 같은 범위 줄 → `default` 차례로 찾는다. 셋 다 없으면 실패 「문서에 없는 응답 코드 418」
- **모양** — 그 응답의 `application/json` 스키마(`$ref` 는 문서 안에서 푼다)를 zod `z.fromJSONSchema` 로 바꿔 본문을 견준다(OpenAPI 3.0 문서는 `defaultTarget: 'openapi-3.0'` — 새 패키지 없음).
  필수 칸 빠짐 · 형 다름 · `enum` 밖 값은 실패, 문서에 없는 추가 칸은 통과(결정 8). **문서가 `additionalProperties: false` 라고 적은 곳만 추가 칸을 막는다** — 문서가 그렇게 약속했기 때문이다. 스키마가 있는데 본문이 JSON 이 아니면 실패 「JSON 이 아닙니다」
- **스키마가 없으면 코드만 본다** — 결과 `NO_SHAPE`, 화면 · 리포트에 「문서에 응답 형식 없음」. 통과로 센다.
  zod 가 못 읽는 스키마(`not` · `if/then/else` · 문서 밖 `$ref`)도 같이 `NO_SHAPE` 다 — 문서 쪽 한계로 케이스를 깨지 않는다. kit 이 그 까닭을 표준 오류에 한 줄 남긴다
  - 서버 주소 변수(`servers[0].url` 의 `{port}`)는 0 으로 채워 읽고, 그래도 못 읽으면 앞 경로를 안 붙인다
- **결과는 절차마다 `shapeChecks` 줄로 따로 싣는다**(공통/3 「API 테스트 타입」 `ShapeCheck`) — 케이스의 확인 문장과 섞지 않는다. 한 줄 = 요청 하나. 저장은 `run_item_step.shape_checks` · `scenario_run_step.shape_checks`(공통/4-데이터모델 「API 테스트 표」)다. 실패면 문제를 한 줄씩 최대 5개(「필수 필드 없음 — status」 · 「타입이 다름 — total (문서 number · 받은 값 string)」). 문제 줄에 응답 값은 enum 밖 값(50자까지)만 싣고, 저장 · 화면은 절차 기록처럼 가린 것을 본다
- **모양 실패는 그 절차와 항목을 실패로 만든다.** 실행을 멈추지는 않는다(`blocker` 가 아니다). 실패 사유 한 줄(리포팅 §8.4 · 실행 §8.3)은 실패한 확인 문장이 먼저, 다음은 절차를 멈춘 예외이고, 둘 다 없으면 첫 모양 문제 「응답 형식이 API 문서와 다릅니다 — POST /v1/pushes 201 · 필수 필드 없음 — status」다

#### API 커버리지 — API × 응답 코드

- **분모** — 그 애플리케이션 마지막 판의 (메서드 · 경로 · 문서에 숫자로 적힌 응답 코드). `4XX` · `default` 는 분모에 안 든다 — 「어느 코드를 받아야 덮었나」가 정해지지 않는다
- **분자** — 분모 가운데 통과한 항목에서 받은 적이 있는 것. 서버가 `PASS` 항목을 저장할 때 그 항목의 `shapeChecks`(메서드 · 틀 · 코드)를 `api_call_seen` 에 넣는다 — **그 케이스의 줄을 지우고 이번 것으로 갈아 끼운다.** 케이스를 고쳐 더 안 부르는 API 가 남아 있지 않게다
- **`FAIL` 항목을 저장할 때는 그 케이스의 줄을 지운다** — 깨진 케이스가 지난 통과로 덮은 것처럼 남지 않게. 미실행(`NA`)은 줄을 그대로 둔다(돌지 않았으니 알 수 없다). **집계는 지금 활성인 케이스(`test_case.is_active`) 줄만 센다** — 지운 케이스가 덮은 것으로 남지 않게
- 실패 · 미실행 항목은 안 센다. **네거티브 케이스가 기대한 400 을 받고 통과하면 400 이 덮인다** — 그것이 네거티브 시험의 몫이다
- 케이스 실행만 센다. E2E 시나리오는 1차에 안 센다
- `api_call_seen` 은 「이 API 를 어느 케이스가 부르나」도 답한다 — 바뀐 API 만 다시 작성(아래)이 그것으로 케이스를 찾는다

#### 작성 — API 문서 판 + 기획서

**작성 절차의 정본은 도메인/작성 §3.6 이다.** API 애플리케이션에서 다른 것만 적는다. 자식이 따르는 지침은 `tpx-cases/references/api.md` 다(2026-10-21 API-F1-06) — 에이전트가 줄 프롬프트에 `--- API 문서 ---` 절을 붙여 그 파일을 열게 한다.

- **자료** — 「API 문서 판」 하나(`authoring_asset.kind = 'API_DOC'`)와 기획서(정책 · 표준 기획서). API 애플리케이션 작성 요청은 API 문서 판이 꼭 하나다(없으면 400 `API_DOC_REQUIRED`). 자료 종류 표는 도메인/작성 §7 「자료」
- **기대값 근거는 둘이다** — 정책(예약 발송은 5분 뒤부터 · 하루 1,000건)은 표준 기획서, 응답 코드 · 모양 · 경계 숫자(`minLength` · `maximum` · `enum`)는 API 문서. 둘 다 사람이 쓴 문서다. 화면이 없으니 화면 값을 기대값으로 쓰는 미확정 케이스가 없다
- **원장** — 표준 기획서 번호에 더해 API 문서의 (메서드 · 경로 · 숫자 응답 코드) 줄마다 케이스나 「제외」로 덮는다. 번호 꼴은 `API POST /v1/pushes 201`(가족 `API`). 일부러 만들 수 없는 응답(500 · 503)은 제외 종류 「만들 수 없는 응답」으로 덮는다 — API 줄에만 쓴다(관문 0 이 형식 오류로 잡는다. 종류 목록의 정본은 `scripts/authoring-ledger-check.ts` 의 `제외종류`)
  - 에이전트가 집기 응답의 판 원문으로 API 줄을 만들어 표준 기획서 항목 뒤에 붙인다 — 자식이 결과 파일을 고쳐 원장을 다시 만들 때(`npm run prd:ledger`)는 자료 폴더의 판 파일로 같은 줄을 붙인다. 판정은 에이전트 메모리의 판으로 한다
  - **API 줄은 「정식 줄은 원장 번호 하나」 셈에 안 든다**(도메인/작성 §3.6 「칸과 번호」) — 케이스 하나가 기획서 요구 하나와 그 요청이 받는 API 줄을 같이 덮는다(`NTF-REQ-004 · API POST /v1/pushes 400`). 칸은 기획서 요구가 정하고, API 줄만 덮는 케이스는 그 API 줄이 칸이다
  - 기획서 파일 없이 판만 넣은 요청은 표준 기획서로 옮길 것이 없다 — 원장은 지금 판 항목과 API 줄이다
- **건너뛰는 단계** — 화면 훑기 · 요소 찾기 · 화면 지도. 화면이 없다
- **케이스 머리** — `apiDoc: <판>`(작성에 쓴 판). 케이스 = API × 규칙 하나
- **작성 중 돌려 보기** — 고른 대상 서버의 API 인증을 받아 돈다(위 「API 인증」). 에이전트가 정식 실행과 같은 이름의 환경 변수로 넘긴다 — `PLATFORM_BASE_URL`(그 줄 주소) · `PLATFORM_API_AUTHS`(인증 원문) · `PLATFORM_API_DOC_FILE`(자료 폴더의 판 원문 `api-doc.json`). 그래서 작성 중에도 kit 이 응답 모양을 견준다. 프롬프트에는 인증 이름만 싣고 비밀값은 에이전트 · 자식 양쪽 가림 목록에 든다
- **집기 응답의 `target` 은 에이전트가 따로 떼어 둔다** — 에이전트는 `target` 이 있으면 역방향(화면 대조)으로 도므로 API 행은 판이 실린 것을 보고 `target` 을 API 묶음으로 옮긴다
- **재실행 · 이어서 작성 · 남은 요구로 이어 작성**은 원본의 env 를 물려받아 다시 판정한다(그 사이 「실서비스 서버」로 체크됐으면 400 `BAD_ENV`). 이어 작성은 자료의 판 행도 그대로 복사한다
- 한계(2026-10-21) — 집기 응답의 API 칸은 작성 · 재실행 행에만 싣는다. **보류 값을 채운 반영(MERGE)의 3회 실행과 표준 기획서 반영 요청(`prdApply`)은 API 인증 · 판을 아직 안 받는다** — API 애플리케이션 보류 케이스를 값으로 풀면 그 3회 실행이 토큰 없이 돌아 빨개진다. 쓰임이 오면 머지 집기 칸에 같은 칸을 싣는다

#### 케이스 꼴 (결정 11)

- **사전조건 · 절차 · 확인(AAA)** — 준비(자기 데이터를 만든다) → 부른다 → 확인한다. 만든 데이터는 끝에 지운다(지우는 API 가 있으면)
- **비동기(202)** — 받은 뒤 상태 조회를 최대 10초 다시 부르며 기다린다(Playwright `expect.poll` 꼴). 10초를 넘으면 실패다
- **네거티브 묶음** — API 마다 필수 칸 빠짐 · 형 다름 · 경계(문서 숫자 바로 안 · 밖) · 인증 없이 401 · 남의 것(고객사 B 토큰으로 고객사 A 자원 → 404, OWASP BOLA) · 없는 자원 404. **같은 요청 다시 보내기(`Idempotency-Key`) · 너무 많이(429)는 문서에 적혀 있을 때만**
- **반복 동작은 API 도우미 파일** — `tests/<폴더>/helpers/api.helper.ts`(기기 등록 · 푸시 보내기 · 지우기). 페이지 오브젝트 규칙(공통/2 §4 「Page Object 파일」)과 같은 자리다
- 예 — 「예약 발송 시각이 5분 안이면 400 이다」: 사전조건 「고객사 A 기기가 하나 등록돼 있다」 → 절차 「`scheduledAt` 을 지금+1분으로 푸시를 보낸다」 → 확인 「응답 코드가 400 이다」 · 「오류 코드가 SCHEDULE_TOO_SOON 이다」

#### 바뀐 API 만 다시 작성

- **판 비교** — 두 판의 API(메서드 · 경로)마다 새 · 바뀜 · 없어짐과 깨는 변경 여부. 바뀜은 요청 칸 · 응답 코드 · 응답 스키마가 달라진 것. **깨는 변경** — API 없어짐 · 응답 코드 없어짐 · 요청 필수 칸 생김 · 응답 칸 없어짐 · 칸의 형 바뀜
- **누를 때만 돈다**(결정 7) — 「바뀐 API 만 다시 작성」(화면 버튼 「바뀐 API N건 테스트에 반영」 — §8.13)이 작성 요청 하나를 세운다. 자료는 새 판 하나, `params.apiApply = { fromVersion, toVersion, operations: [{ method, path, change, breaking, notes, tcIds }] }`. 자식은 그 API 의 케이스만 새 판으로 다시 쓰고 새 API 는 새로 쓴다 — 고친 요구만 다시 작성(도메인/작성 §3.6 「표준 기획서」 · PRD-F4-03)과 같은 흐름이다
  - **서버가 누를 때 채운다** (2026-10-21 API-F1-07) — 고른 API 가운데 판 비교에 든 것만 남기고(없어진 API 뿐이면 할 일이 없다 — 400 `NOTHING_TO_APPLY`), 줄마다 판 비교 한 줄(`change` · `breaking` · `notes`)과 그때 그 API 를 부르던 활성 케이스(`api_call_seen` · `test_case.is_active` — 커버리지와 같은 규칙)를 `tcIds` 로 박아 둔다. 에이전트는 DB 를 안 보므로 이것이 자식이 받는 전부다. 돌려 본 적 없는 케이스는 `tcIds` 에 없다 — 자식이 그 API 를 부르는 케이스를 더 찾으면 같이 고친다
  - 에이전트는 이 칸을 자료 폴더 `api-apply.json` 에 새 판의 그 API 원장 번호(`API POST /v1/pushes 201`)와 같이 쓰고 줄 프롬프트에 「바뀐 API 만 다시 작성」 절을 붙인다. 칸 모양이 틀리거나 `toVersion` 이 자료의 판과 다르면 자식을 안 띄우고 FAILED 다. 자식 지침은 `tpx-author` `references/apply.md` §6 이다
  - **원장의 API 줄은 고른 API 것만 든다** — 안 고른 새 API 줄이 main 표에 없어 관문 0 이 막지 않게. 그 밖 API 줄을 출처로 단 표 줄은 「원장에 없는 번호」 경고로만 남는다. 기획서 번호는 전체 그대로다
  - 바뀐 API 안에서 응답 코드가 없어져 덮을 코드가 없는 케이스도 지우지 않는다 — 자식이 결과 요약에 「지우기 제안」으로 적는다
  - **한 번에 하나** — 같은 애플리케이션에 대기 · 도는 중인 다시 작성이 있으면 409 `APPLY_OPEN`(표준 기획서 반영과 같은 까닭). 새 판은 마지막 판이어야 한다(400 `NOT_LATEST_VERSION` — 옛 판으로 다시 쓰면 케이스 머리의 판이 뒤로 간다)
  - PR 본문 머리 — `API 문서 반영: 판 a → 판 b · 바뀜 n · 새 API m · 없어진 API k` 와 부르던 케이스가 있는 없어진 API 마다 `지우기 제안 — <메서드> <경로> 가 없어졌다: <tcId 들>`
  - 재실행 · 이어서 작성은 원본의 `apiApply` · env 를 물려받는다. 남은 요구로 이어 작성은 `apiApply` 를 안 물려받는다 — 누를 때 박아 둔 케이스로 또 다시 쓰지 않게. 작성 요청 만들기 · 재실행 본문에 `apiApply` 를 실으면 400 `BAD_API_APPLY` 다(도메인/작성 §7)
- **없어진 API 의 케이스는 지우지 않는다** — PR 본문에 「지우기 제안」으로만 적는다. 지우기는 사람이 케이스 고치기(도메인/작성 §3.6 「★ 케이스 고치기」)로 한다

#### 리포트 — 원문을 접어 넣는다 (결정 10)

**리포팅 §8.4 「코드와 `httpTrace` 를 넣지 않는다」의 예외다.** 정본은 이 줄이고 리포팅 §8.4 가 가리킨다.

- **API 애플리케이션 케이스만** — 블록의 절차마다 「요청 · 응답 원문」을 접어 둔다. 요청은 메서드 · 주소 · 머리 · 본문, 응답은 코드 · 본문(kit 이 이미 가리고 2000자에서 자른 것 — 잘렸으면 「… 2000자에서 잘림」). HTML 은 `details`, PDF 는 부록(접힌 줄과 같은 길 — 리포팅 §8.4 「증적 문서는 요약 띠 → …」), 엑셀은 안 넣는다(한 행 = 한 확인 문장)
- **모양 확인 줄은 확인 문장 아래 따로** — 화면 이름은 「응답 형식 검사」다(2026-10-21 API-F1-08). 「✓ POST /v1/pushes 201 문서와 같습니다」 · 「POST /v1/pushes 400 문서에 응답 형식 없음」 · 실패면 「✗ … 문서와 다릅니다」 아래 문제 줄
- 화면의 항목 상세도 같다 — 케이스 확인과 모양 확인을 따로 보이고 원문을 접어 둔다
- 화면 케이스(웹 · 앱)는 지금 규칙 그대로다 — 원문을 안 넣는다

## 7. API 문서 통로

**권한** — 경로의 `:id` 로 애플리케이션을 짚고(그 애플리케이션 프로젝트의 권한 — 도메인/인증 §7 「인증 적용 범위」 표), 보기는 작성 `read`, 올리기 · 받기 · 다시 작성은 작성 `write`(도메인/인증 §3.5). 애플리케이션 종류 · 문서 경로 · 기준 서버 · API 인증은 설정 API(도메인/인증 §7)다 — admin 만.
API 종류가 아닌 애플리케이션이면 모든 통로가 400 `{ error: 'NOT_API_SERVICE' }`. 경로의 번호는 숫자 글자만 받는다 — 문과 같은 규칙(`routeParams.ts` 정수 · 판 번호는 INTEGER 상한까지), 그 밖은 400 `INVALID_REQUEST`.

```

POST   /api/services/:id/api-docs/:version/rewrite    바뀐 API 만 다시 작성 { fromVersion, env, operations: [{ method, path }] } → 201 { requestId }

                                                      :version 이 마지막 판이 아니면 400 NOT_LATEST_VERSION · 대기 · 도는 중인 다시 작성이 있으면 409 APPLY_OPEN. method 는 대문자로 읽는다 · env 는 작성 중 돌려 볼 대상 서버 — 작성 요청 만들기의 API 판정과 같다(없거나 그 애플리케이션 줄이 아니거나 「실서비스 서버」면 400 BAD_ENV, 도메인/작성 §7 「AUTHOR API 문서 판」)
```

### 8.13 API 문서 화면 (2026-10-20 · 2026-10-21 시안 C 「할 일 먼저」 — API-F1-08)

**자리는 사이드바 `API` › `API 문서`** — 정본은 공통/5-화면공통 §8 「자리 목록」. 주소는 `#/api/docs`, 작성 상세의 자료 고리는 `#/api/docs/<버전>`(그 버전 원문을 편 채 연다).

**배치는 PRD 관리 · 애플리케이션 가이드와 같다** (2026-10-21 사용자 — 「기존 디자인이랑 어느게 맞아? 그리고 워딩도 다른 페이지 참고해서 가지고 와」).
머리 → (펼친) 버전 기록 표 → 할 일 카드 둘 → 전체 API. 탭 셋(시안 B) · 두 버전을 아무거나 골라 견주는 칸(시안 A)은 다른 화면에 없는 모양이라 뺐다.
**화면 낱말** — 명세의 「판」은 화면에서 「버전」이다(PRD 화면과 같다). 바뀐 종류는 PRD 관리 「반영 안 됨」 카드와 같은 「바뀜 · 새 항목 · 지움」, 깨는 변경은 「기존 테스트가 실패할 수 있음」, 모양 확인은 「응답 형식 검사」다.
사용자(2026-10-21) 「판은 도대체 뭐야? 번역체 같은 말투 쓰지 말라니깐」 — 저장소 말을 화면에 옮기지 않는다.

- **고른 애플리케이션이 API 종류가 아니면** 본문에 한 줄 「API 애플리케이션을 고르면 API 문서가 보입니다」와 「설정에서 종류 보기」 고리(admin 만)
- **머리** — 위치 `API ›` · 제목 「API 문서」 · 부제 「버전 3 · API 9개 · stg 서버」. 행동은 「테스트 작성 요청」 · 「문서 새로 받기」(설정에 문서 경로 · 기준 서버가 있을 때만) · 「파일 첨부」 · 「버전 기록」. 받기 · 첨부 · 반영은 작성 `write`
- **버전 기록** — PRD 버전 기록과 같은 표에 「받은 곳」 칸 하나를 더했다: 버전 · 받은 곳(「stg 서버」 · 「파일 notify.json」) · 저장한 사람(정기 실행이 올린 버전은 「정기 실행」) · 저장 일시 · 바뀐 것(앞 버전과 견준 「바뀜 2건 · 새 항목 1건」, 눌러 펴면 API 마다 판 비교 notes) · 「버전 N 보기」(원문 JSON). 맨 위 줄에 「현재 버전」
- **「반영 안 됨 N건」 카드** — 현재 버전과 바로 앞 버전의 판 비교. 줄마다 종류 · 메서드 · 경로 · notes, 깨는 변경이면 「기존 테스트가 실패할 수 있음」. 「대상 서버」(실서비스 서버 뺌)를 고르고 「바뀐 API N건 테스트에 반영」 — 지운 API 는 빼고 보낸다(그 케이스는 PR 에 삭제 제안). 세운 뒤에는 「작성 요청 N번을 만들었습니다」와 그 요청 고리. 버전이 하나뿐이면 카드가 없다
  - 한계 — 반영이 병합돼도 다음 버전이 오기 전까지 카드가 남는다. 케이스가 어느 버전으로 쓰였는지(`test_case.api_doc`)를 화면이 받지 않기 때문이다. 쓰임이 오면 커버리지 응답에 그 칸을 싣는다
- **「케이스가 안 거친 응답 N개」 카드** — 요구사항 화면의 「케이스가 안 거친 API」 카드와 같은 꼴. 처음엔 접혀 있고 「펴기」로 API 마다 안 받은 코드를 보인다
- **전체 API** — 현재 버전의 API 를 문서의 첫 태그로 묶어 한 줄씩(태그가 없으면 「태그 없음」). 응답 코드마다 ●(통과한 케이스가 받음) ○(아직 안 받음), 문서에 응답 형식이 없는 코드엔 「응답 형식 없음」. 머리에 「확인한 응답 17/30」 · 경로 · 이름 검색. ● ○ 는 판정이 아니라 판정 색을 쓰지 않는다(DESIGN.md 원칙 1)
- 실행 결과 머리의 「이 서버의 API 문서가 기준 서버 문서(버전 N)와 다릅니다. 배포 전일 수 있습니다」 · 「API 문서를 받지 못했습니다」 한 줄은 실행 §8.3 결과 화면 머리에 붙는다
- **테스트 작성 › 새 요청** — API 애플리케이션이면 「API 문서」 버전 고르개(기본은 현재 버전) · 「대상 서버」(기본은 설정의 기준 서버 — 「실서비스 서버」 표시는 `/auth/me` 에 없어 거르지 못하고 서버가 BAD_ENV 로 막는다) · 「PRD」 첨부(없어도 된다)만 보이고 「피그마 주소」 · 「실제 화면과 대조」는 없다. 버전이 하나도 없으면 「API 문서가 아직 없습니다. API 문서 화면에서 먼저 받습니다」와 고리를 보이고 보내지 못한다. 자료 개수 상한에 API 문서 한 칸을 센다. 작성 상세의 자료는 「API 문서 버전 N」 고리(`#/api/docs/N`)
- 항목 상세 절차마다 확인 문장 아래 「응답 형식 검사」 줄(위 §3.8 「리포트」). E2E 시나리오 결과 화면은 절차를 제목 · 판정만 그려 1차에 이 줄이 없다
