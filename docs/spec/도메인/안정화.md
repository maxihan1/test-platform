# 안정화

> **이 장이 담는 절** — §3.15 안정화 지표 · §7 안정화 통로 · §8.19 안정화 지표 화면 (2026-11-12 · 진행판 STAB-F1-01)
> 안정화 지표는 **정기 실행이 남긴 로그로 「테스트는 통과했는데 속으로 오류가 난 것」을 날짜별로 보여 주는 화면이다.** 웹은 콘솔 · 네트워크, 앱은 크래시 · ANR, 게임은 처리 안 된 Exception 을 세고, 같은 오류를 지문으로 묶어 이전 실행과 견준다.
> **이 장이 안정화 지표의 정본이다.** 다른 장(데이터모델 · 화면공통 · 인증 · 러너 · 성능 · 실행)은 자기 칸과 가리키는 줄만 적고 여기를 가리킨다.
> **쓰는 표** `stab_run` · `stab_error` · `stab_run_error` · `stab_occurrence` · `stab_sample` · `perf_ai_job`(종류 `STAB_SUMMARY`) — 정의는 [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「안정화 표」. 읽기만 하는 표는 `test_run` · `run_item` · `run_item_step` · `run_trace` · `run_network` · `run_console` · `req_case`.
> 전체 목차와 작업별 읽기 동선은 [SPEC.md](../../SPEC.md).

### 3.15 안정화 지표 — 정기 실행 로그로 보는 빌드 안정화 (2026-11-12 사용자)

아래 결정 1~12 는 2026-11-12 기획 대화에서 주제마다 정했고 사용자가 시안 6판까지 확인했다. 다시 묻지 않는다. 「(내 결정)」이 붙은 줄은 이 명세 줄(STAB-F1-01)에서 칸 모양을 정하며 고른 것이다.
화면 시안은 [안정화 지표 시안](https://claude.ai/artifact/2PGYX36cvXP1wPxtKG3AUC)의 **6판(일곱째 줄 A6 · Detail6 · A6m · Detail6m)** 이다. 1~5판은 기록이다.
실서비스 지표(사용자 세션 · 크래시 없는 세션 %)는 서비스 단계에서 따로 정한다 — 이 장은 QA 빌드 · QA 서버만 본다.

#### 집계 — 언제 무엇을 읽나

- **언제** — 그날 정기 실행 묶음이 다 `FINISHED` 로 끝나면 묶음을 한 번 집계한다. 묶음 중 하나라도 `ABORTED` · `PREP_FAILED` 면 그날은 집계하지 않는다(그날 점이 비는 것이 맞다 — 반쪽 분모로 점이 튀지 않게)
- **묶음** (2026-11-12 사용자 · STAB-F1-03) — 정기 실행 한 번은 UI 실행과 기능 실행 둘로 선다([공통/6-인프라.md](../공통/6-인프라.md) §9.2 · [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「실행 종류」). 같은 애플리케이션 · 대상 서버에서 그날(정기 실행 시간대 — 아래 「일별 추이」) 시작한 정기 UI · 기능 실행이 한 묶음이다 — 정기 실행은 하루 한 번만 돈다. 집계 줄 번호(`stab_run.run_id`)는 묶음의 뒤 실행 번호고, 재발 · 해결 확인을 가르는 실행 시작은 묶음의 앞 실행 시작이다. 이 장에서 집계 · 이전 실행 · 상태를 말하는 「실행」은 이 묶음이다. 실행마다 따로 세면 기능 실행의 이전 실행이 같은 날 UI 실행이 돼 UI 에만 나는 오류가 날마다 출렁인다
- **기다림** — 웹 줄은 항목을 닫은 뒤 따로 풀리고([실행.md](실행.md) §3.2 「trace」), 앱 · 게임 logcat 은 러너가 답한 뒤 따로 받는다([러너.md](러너.md) §5.2 「증적 영상 · logcat」). 그래서 집계는 그 실행 항목의 trace 풀기와 팜 증적 받기가 끝나길 기다린다 (내 결정 · 상한은 코드 상수가 정본)
  - **웹** — 항목마다 `run_trace` 상태 줄(`DONE` · `NONE` · `FAILED`)이 설 때까지 기다린다. 풀기는 서버 전체에서 하나씩이라 다른 실행이 밀려 있으면 오래 걸린다 — 시간으로 끊으면 서버가 바쁜 날만 분모가 줄어 추이가 흔들리므로 상한을 길게(2시간) 둔다. 풀기는 실패해도 상태 줄을 세우고 다시 켜지면 다시 푼다
  - **앱 · 게임** — logcat 파일이 생길 때까지 기다린다. 상한 15분(팜 파일 하나 상한 10분에 여유를 더했다) — 러너가 못 받으면 파일이 영영 안 생겨서다
  - 상한을 넘긴 항목은 「기록 없음」이다
- **하나씩 차례로** — 집계는 서버 전체에서 한 번에 하나, 실행 시작 차례로 돈다. 같은 애플리케이션 · 대상 서버에 이 묶음보다 뒤 실행 번호의 집계 줄이 이미 있으면 그 묶음은 집계하지 않는다 — 앞 실행을 뒤에 끼워 넣으면 이전 실행 · 최초 발생 · 상태가 뒤집힌다
- **관리 서버가 다시 켜지면** — 24시간 안에 끝난 정기 실행 중 집계 줄(`stab_run`)이 없는 것을 위 차례대로 집계한다
- **분모(케이스)** — 그 묶음에서 기록이 있는 케이스 수다. 같은 케이스가 디바이스 · 반복으로 여러 항목이면 하나로 센다. 기록 없음(웹은 `run_trace` 가 `DONE` 이 아님 · 앱은 logcat 파일이 없음 · 게임은 게임 오류 파일이 없음 — 게임 항목에 logcat 만 없으면 기록은 있고 그 항목의 크래시 · ANR 만 0 으로 본다)인 항목만 있는 케이스는 분모에서 뺀다 — 다른 기계의 러너는 공유 폴더가 없어 늘 기록 없음이다
- **집계는 그때 값으로 굳는다** — 집계 뒤 「다시 실행」이 그 실행의 결과를 고쳐도([실행.md](실행.md) §3.2 한 건 실행) 집계는 그대로다

#### 무엇을 세나

| 출처 | 센다 | 안 센다 |
|---|---|---|
| 웹 콘솔 `run_console` | `pageerror`(잡히지 않은 오류) · `error` | `warning` · **메아리 줄** — `Failed to load resource` 로 시작하거나 같은 항목의 실패 네트워크 줄과 주소가 같은 `error` 줄. 같은 실패가 네트워크 줄로 이미 들어오므로 축과 상관없이 늘 뺀다 |
| 웹 네트워크 `run_network` | 실패 줄 — 응답 코드 400 이상이거나 응답 없이 `failure` 가 있는 줄 | 예외 축 케이스의 실패 줄 전부(결정 4) · 3xx 이하 |
| 앱 · 게임 logcat | `FATAL EXCEPTION` 덩어리 중 `Process: <앱 패키지>, PID: …` 줄이 그 애플리케이션 패키지인 것 하나 = 크래시 한 번 · `ANR in <앱 패키지>` 하나 = ANR 한 번. 앱 PID 를 몰라도 패키지 이름으로 가른다 — 앱이 이미 떠 있어 `Start proc` 줄이 없는 항목에서 남의 크래시를 세지 않게 | 그 밖의 E · F 줄 · 다른 앱 줄 · 네이티브 크래시(`Fatal signal` — 1차 밖) |
| 게임 SDK `errors` | type `Exception` | `Error` · `Assert` · `Warning` · `Log` |

- 같은 줄이 한 항목에서 여러 번 나오면 **발생 횟수**는 그대로 더하고 **발생 케이스**는 하나다
- 예외 축 판정은 집계 때 `req_case` 를 읽는다(그 애플리케이션 · 케이스 번호의 줄 중 `axis = '예외'` 가 하나라도 있으면 예외)

#### 지문 — 같은 오류를 하나로 묶는다

지문은 아래 재료를 이어 붙인 글의 SHA-256 이다. 애플리케이션 · 대상 서버마다 따로 묶는다(`stab_error` 는 `(service_id, env, fingerprint)` 하나) (내 결정) — 이전 실행 · 추이가 대상 서버끼리라서, 한 서버의 해결 처리 · 해결 확인 · 최초 발생이 다른 서버로 새지 않게 한다. 정기 실행 대상 서버를 바꾸면 새 서버의 첫 집계는 모두 신규다.

| 출처 | 재료 | 화면 이름(`title`) |
|---|---|---|
| 웹 콘솔 | 종류(`run_console.level` 값 `pageerror` · `error` 그대로) + 메시지 틀 + 화면 주소 틀 | `<첫 단어 오류 이름> · <메시지 틀 앞 80자>` — 오류 이름이 없으면 `콘솔 오류 · …` |
| 웹 네트워크 | `HTTP <코드>` 또는 `요청 끊김` + 메서드 + 요청 주소 틀 + 화면 주소 틀 | `HTTP 500 · POST /api/v1/statuses/:n` |
| 앱 크래시 | 예외 클래스 + 위에서 앱 프레임 셋(클래스.메서드 — 줄 번호 · 파일 이름 뺌) | `<예외 클래스 짧은 이름> · <첫 앱 프레임 클래스.메서드>` |
| 앱 ANR | `ANR` + 앱 패키지 + 액티비티 + Reason 틀 | `ANR · <액티비티 짧은 이름>` |
| 게임 Exception | 예외 이름(메시지의 `:` 앞) + 위에서 게임 프레임 셋(네임스페이스 뺀 클래스.메서드 — 인자 · `[파일:줄]` 뺌) | `NullReferenceException · ClientCharacter.OnAnimEvent` |

- **메시지 틀** — 숫자 · uuid · 16자 넘는 16진 · 따옴표 안 값 · 주소 물음표 뒤를 `*` 로 바꾸고 200자에서 자른다(Drain 꼴을 한 줄로 줄였다 — 값이 바뀔 때마다 갈라지지 않게)
- **주소 틀** — 서비스 지도와 같은 `prd/apiMap.ts` `API틀`(숫자 · 주문번호 꼴 칸은 `:n`, uuid · 긴 16진 칸은 `:id` 로 바꾸고 물음표 뒤를 뺀 경로)의 `host + path` 다 — 같은 경로라도 다른 호스트(CDN · API 서버)는 다른 오류다. 화면 이름에는 경로만 쓴다. `API틀` 이 null 인 주소(`data:` · `ws:` · `blob:` 등)는 `<프로토콜>:` 한 낱말로 둔다. **화면 주소**는 그 줄 바로 앞의 페이지 이동(`run_network.resource_type = 'document'`) 주소이고, 없으면 실행 대상 주소의 경로 `/` 다
- **앱 프레임** — 애플리케이션의 앱 패키지 이름으로 시작하는 클래스 프레임. 하나도 없으면 맨 위 셋을 그대로 쓴다
- **게임 프레임** — `UnityEngine.` · `UnityEditor.` · `System.` · `Mono.` 로 시작하는 프레임을 뺀 맨 위 셋. 하나도 없으면 맨 위 셋을 그대로 쓴다
- **단계(`seq`)** — 웹은 그 줄의 단계 번호(`run_console.seq` · `run_network.seq`) 그대로다. 게임은 오류의 `occurredAt`(SDK 0.7 부터 · UTC)이 단계 시작 시각(`StepResult.startedAt` — kit 이 싣는다) 이상인 마지막 단계다 — 디바이스와 러너 시계가 어긋나도 단계 하나 안팎이라 받아들인다. `occurredAt` 이나 단계 시작 시각이 없으면 NULL. 앱 logcat 은 디바이스 지역 시각이라 1차는 늘 NULL 이다
- **난독화** — 1차는 되돌리지 않는다. 앱은 디버그 빌드를 쓴다(결정 11). 웹 소스맵 · R8 매핑 · IL2CPP 매핑은 나중이다

#### 상태 — 오류 종류마다 이번 실행에서

**이전 실행**은 같은 애플리케이션 · 같은 대상 서버의 바로 앞 집계 줄이다. 대상 서버가 바뀌었으면 이전 실행이 없다.
이번 실행에 남은 종류(발생 케이스 1건 이상)는 아래 차례로 처음 맞는 상태 하나를 받는다.

| 차례 | 상태 | 조건 |
|---|---|---|
| 1 | 신규 | 처음 보는 지문이다. 이 실행이 **최초 발생**이다. 그 애플리케이션 · 대상 서버의 첫 집계에서는 모두 신규다 |
| 2 | 재발 | 이 실행이 **시작하기 전에** 해결 처리돼 있던 종류다(해결 · 해결 확인 둘 다). 해결 처리를 걷는다. 실행이 도는 중에 누른 해결 처리는 그 실행이 고친 코드를 지났는지 모르므로 건드리지 않는다 — 다음 표 차례로 상태를 받고 해결 처리는 그대로 남는다 |
| 3 | 증가 | 이전 실행에도 남았고 이번 발생 케이스가 더 많다 |
| 4 | 기존 | 그 밖 — 이전 실행에 안 남았다가 다시 남은 것도 해결 처리를 안 했으니 기존이다 |

- **해결** — 사람이 상세 화면에서 「해결 처리」를 누른 종류다. 그 뒤에 시작한 정기 실행이 아직 집계되지 않았다
- **해결 확인** — 해결 처리 뒤에 **시작한** 정기 실행에서 그 종류가 안 남았다. 그 실행 집계가 확인 표시를 단다. 남았으면 재발이다
- **숫자 칸 「해결」** — 그 실행 집계 때 해결 상태(확인 전)인 종류 수다. 아래 줄 `해결 확인 N종` 은 **그 실행이** 해결 확인한 종류 수다. 누계가 아니다 — 확인된 종류는 다음 실행부터 칸에서 빠진다. 고른 실행이 가장 최근이면 「해결」은 지금 값이다(집계 뒤에 누른 해결 처리가 바로 보이게)
- **잔여 오류** — 그 실행에 남은 종류 수다(신규 · 증가 · 재발 · 기존의 합)
- **오류 발생 케이스** — 센 오류가 하나라도 남은 케이스 수. **판정과의 차이**는 그중 판정이 통과인 케이스 수다
- **크래시** — 앱 · 게임 항목의 크래시 · ANR 횟수의 합. 웹은 이 칸이 없다(§8.19)
- 해결 처리는 되돌리지 않는다(1차) — 잘못 눌렀어도 다음 실행에서 남으면 재발로 돌아온다

#### 일별 추이

- **하루의 경계** — 집계 때 그 애플리케이션의 정기 실행 시간대(`service.schedule_tz` · 비었으면 UTC)로 실행 시작 날짜를 정해 `stab_run.day` 에 굳힌다. 화면 시간대를 받지 않는다 — 정기 실행 시각(「매일 03:00」)이 그 시간대라서다
- **날마다 한 점** — 그날의 마지막 집계 줄 값이다(정기 실행은 하루 한 번이 보통이다). 실행이 없는 날은 점 없이 앞뒤 점을 잇는다
- **창** — 고른 실행의 날짜까지 7일 · 30일. 같은 대상 서버의 줄만 쓴다
- **빌드 적용일** — 그날 실행의 빌드 번호(`test_run.build_no`)가 창 안 바로 앞 점과 다르면 날짜 아래 「#22 적용」. 빌드 번호가 없는 실행(웹 대부분)은 표시하지 않는다
- 선은 잔여 오류, 바닥 막대는 그날 신규 오류 종류 수다

#### AI 실행 요약

- **맡기기** — 집계가 끝나면 `perf_ai_job` 한 줄(종류 `STAB_SUMMARY` · `service_id` 는 그 애플리케이션 · `run_id` 는 NULL · `input` 은 `{ runId }` · `created_by` 는 정기 실행의 `triggered_by` 와 같은 `스케줄러`)을 세운다. 작성 에이전트가 성능 AI 일과 같은 통로로 가져간다 — 작성 계정이 배정된 애플리케이션 일만 가져가는 규칙도 같다([성능.md](성능.md) §7 「AI 일」 「누가 집나」)
- **재료** — 가져갈 때 관리 서버가 만든다. 그 실행과 이전 실행의 숫자 · 이번 실행의 종류(신규 · 증가 · 재발 먼저, 많아야 30종 — 종류마다 상태 · 발생 케이스 · 이전 실행 발생 케이스 · 최초 발생 · 해결 처리 시각 · 견본 하나의 앞 1,500자 · 발생 케이스 번호와 단계) · 이번에 해결 확인된 종류 · 최근 7일 점 · 그 실행의 케이스 번호와 이름 전부(많아야 500건). 원문 로그 전체는 넣지 않는다
- **결과 모양** (내 결정)
  ```
  { headline: string,                                   // 한 줄 결론 — 120자까지
    changes: [{ errorId, text }],                       // 주요 변화 — 신규 · 증가 · 재발만, 많아야 5개. 칩은 화면이 상태로 단다
    features: [{ name, tcIds: string[] }],              // 기능 묶음 — 많아야 8개. 숫자는 AI 가 세지 않는다
    verified: string, trend: string,                    // 해결 확인 · 추세 한 줄씩 — 각 120자까지
    errors: [{ errorId, headline, impact, previous, cause }] }   // 신규 · 증가 · 재발 종류마다 상세의 AI 요약 — 각 칸 120자까지
  ```
  관리 서버는 끝 알리기에서 모양을 보고, 재료에 없는 `errorId` · `tcIds` 를 버린다. 모양이 틀리면 일을 `FAILED` 로 둔다
- **숫자는 서버가 센다** — 기능별 오류 발생 케이스는 AI 가 묶은 케이스 번호 중 오류 발생 케이스를 서버가 센 것이고, 판정과의 차이는 집계 숫자다. AI 글 안의 숫자도 재료에 있는 것만 옮기라고 지시문에 적는다
- **지시문이 정하는 것** — 개조식 · 배포 판단 문구 금지(「출시해도 된다」 「배포 가능」 꼴) · 지어내지 않기 · 원인은 「추정」으로만(코드를 읽지 않는다 — 화면이 「코드 미확인」을 붙인다) · 낱말은 [docs/WORDS.md](../../WORDS.md)(지금 장치 그대로 `scripts/authoring-prompt-common.ts` 「낱말」이 싣는다)
- **상세의 AI 요약** — 그 실행에서 신규 · 증가 · 재발인 종류는 그 실행 요약의 `errors` 를 보인다. 기존인 종류는 그 종류의 가장 최근 AI 요약을 보이고, 한 번도 없으면 판을 숨긴다
- **에이전트가 꺼졌거나 실패하면** — 숫자 · 그래프 · 목록은 그대로 보이고 요약 판만 「AI 요약 작성 중」 · 「AI 요약을 만들지 못했습니다」다

#### 견본 · 가림

- **견본** — 종류마다 셋을 둔다. 새 실행에서 남으면 그 실행 것으로 앞에서부터 갈아 끼운다(가장 최근 셋). 글은 8,000자에서 자른다
- **가림** — 웹 줄은 이미 가려 넣었다([실행.md](실행.md) §3.2 「trace」 「가림」). 앱 logcat · 게임 오류 글은 넣을 때 그 항목 값의 비밀값을 글자째 가린다(Issue Bunker 실패 본문의 logcat 줄과 같은 가림). 게임 SDK 는 40자 넘는 영숫자 토막을 이미 가린다

#### Issue Bunker 등록

- 상세의 「Issue Bunker 등록」은 그 프로젝트가 이은 Issue Bunker 에 이슈 하나를 올린다 — 제목 `[<애플리케이션>] <오류 화면 이름>` · 본문은 상태 · 최초 발생(날짜 · 빌드) · 발생 케이스 번호와 단계 · 견본 하나 · AI 요약 · Test Commander 상세 링크. 실패 등록과 같은 보내기 줄(`bts_outbox`)을 타되 **종류는 새 `STAB_CREATE`** 다 (내 결정) — 실패 등록의 `CREATE` 는 케이스 · 대상 서버가 꼭 있어야 하고 「한 케이스 · 대상 서버에 기다리는 등록 하나」 고유 색인이 걸려 있어, 오류 종류(케이스 여럿)를 넣으면 그 케이스의 실패 등록과 부딪힌다. `STAB_CREATE` 는 `tc_id` 를 비우고 `payload` 에 오류 번호를 싣는다. 보낸 뒤 이슈 키는 `stab_error.issue_key` 에 적고 `bts_issue_case` 에는 넣지 않는다 — 넣으면 그 케이스의 다음 실패 댓글이 이 이슈에 붙는다. 보내는 규칙(다시 보내기 · 포기)은 [BTS.md](BTS.md) §3.12 「버그 바퀴」 그대로다
- **나중에 보낸다** — 누르면 보내기 줄에 넣고 바로 `202` 로 답한다. 키는 보낸 뒤에 채워져 상세를 다시 읽을 때 보인다. 그동안 버튼 자리에 `등록 중` 이 선다
- 한 종류에 한 번이다 — 기다리는 `STAB_CREATE` 줄이 있거나 키가 찼으면 다시 누를 수 없다. 올린 뒤에는 버튼 자리에 이슈 키 링크가 선다. 프로젝트가 Issue Bunker 를 잇지 않았으면 버튼이 없다
