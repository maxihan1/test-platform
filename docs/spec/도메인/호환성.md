# 호환성

> **이 장이 담는 절** — §3.13 기기 호환성 · §7 호환성 통로 · §8.17 호환성 화면 (2026-11-07 · 진행판 COMPAT-F1-01)
> 호환성은 **테스트가 지나간 화면을 디바이스마다 비전 AI 가 보고 UI 결함 의심을 짚는 것**이다. 테스트의 통과 · 실패는 화면에 가는 수단일 뿐이라 결과 숫자에 안 넣는다.
> **이 장이 기기 호환성의 정본이다.** 다른 장(데이터모델 · 러너 · 실행 · 인증 · 게임)은 자기 칸과 가리키는 줄만 적고 여기를 가리킨다.
> **비전 쪽 정본은 Device VISION 저장소다** — ADR-052(`farm:uiCheck` · `ui-check.json`) · ADR-059(화면 단서) · 안내서 `docs/guides/test-platform.md` 3절(capability `farm:uiCheck`) · 10절 「UI 점검」 · 11절 「기기 목록」 · 13절 「실제 폰 Chrome」. 이 장은 그 꼴을 옮겨 적지 않고 받는 쪽 규칙만 적는다.
> **쓰는 표** `compat_set` · `compat_run_device` · `compat_run_case` · `compat_screen` · `compat_verdict` · `test_run.kind`(`COMPAT`) · `test_run.compat_set_id` — 정의는 [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「호환성 표」. 읽기만 하는 표는 `case_screen` · `screen_found` · `screen_record` · `game_element` · `game_element_case`.
> 전체 목차와 작업별 읽기 동선은 [SPEC.md](../../SPEC.md).

### 3.13 기기 호환성 — 디바이스마다 화면을 AI 가 점검한다 (2026-11-07 사용자)

사용자(2026-11-06) — 호환성을 「폰끼리 통과 · 실패를 견주는 것」으로 처음 잡았다가 사용자가 고쳐 줬다. Appium 은 버튼이 밀려 제목과 겹쳐도 찾고 누를 수 있으면 통과한다.
그래서 호환성은 「테스트 범위 안에서 디바이스마다 화면이 틀어지지 않았나」를 비전 AI 가 보는 일이다(Device VISION ADR-052 맥락).
아래 결정은 2026-11-06 ~ 07 기획 대화(test_platform 세션 cef10a)에서 주제마다 정했고 시작 질문(COMPAT-F1-01)에서 명세로 옮기는 것을 승인받았다. 다시 묻지 않는다. 「(내 결정)」이 붙은 줄은 시작 질문에서 알렸고 반대가 없던 것이다.
화면 시안은 [호환성 시안](https://claude.ai/artifact/FSGHPH6CyRpaa6hdaWtVYE)(다섯 장 — 목록 · 세트 · 디바이스 선택 · 실행 중 · 결과 · 실행 기록)이고 사용자가 확정했다(2026-11-07 「그러자」).

#### 화면 낱말 (결정 10 · 2026-11-07 사용자)

| 뜻 | 화면 낱말 | 쓰지 않는 말 |
|---|---|---|
| AI 가 짚은 것 | **UI 결함 의심** (줄여 「결함 의심」) | 깨짐 · 이상 · 오류 |
| 사람이 맞다고 한 것 | **결함 확정** | 버그 맞음 |
| 사람이 아니라고 한 것 | **결함 아님** | 오탐 · 헛짚음 |
| 아직 아무도 안 본 의심 | **미판정** | 대기 · 확인 필요 |
| 테스트가 못 가거나 AI 가 못 본 화면 | **미점검 화면** | 못 본 화면 |
| 전체 화면 중 세트가 지나는 화면의 몫 | **화면 커버리지** | 덮은 화면 |
| 세트의 어떤 케이스도 안 지나는 화면 | **미커버 화면** | 빠진 화면 |
| 폰 | **디바이스** | 기기 · 폰(화면에서) |
| 한 대씩 차례로 | **순차 실행** | 하나씩 |
| 같은 모델은 한 대만 | **모델별 1대** | — |
| 케이스를 고른 길 | **자동 선택** · **직접 추가** | 자동 몫 · 사람 몫 |

「깨짐」은 화면에 쓰지 않는다. 명세 · 코드 주석은 위 낱말을 따르되 비전 문서를 옮겨 적을 때만 원문 그대로 둔다.

#### 호환성 세트

- **세트 = 애플리케이션 하나의 이름 · 디바이스 목록 · 직접 추가한 케이스**다. 자동 선택 케이스는 저장하지 않는다 — 실행할 때마다 다시 계산한다(결정 5)
- **디바이스 목록은 고른 디바이스(serial)와 그때의 모델 · 기종명 사본이다.** 고른 차례가 실행 순서다
- **「모델별 1대」를 켜 둔 세트**는 차례가 온 디바이스가 사용 중이거나 등록에서 빠졌으면 **같은 모델의 다른 빈 디바이스**가 대신한다(모델이 단위라서다). 끈 세트는 고른 디바이스만 쓴다. **놓기 · 늘리기는 실제로 잡은 디바이스(`compat_run_device.held_serial`)로 한다** — `compat_run_device.serial` 은 세트에 고른 디바이스라 바꿔 잡았으면 다르다. 중단 · admin 다시 켜기도 이 칸으로 놓는다
- **직접 추가한 케이스가 나중에 지워지거나 폰에서 안 돌게 되면** 세트에는 남고 셈에서만 빠진다(실행 때 건너뛴다). 고치기는 이미 세트에 있던 그런 케이스를 거절하지 않는다 — 상세가 준 몸을 그대로 다시 보내도 저장된다. 새로 넣는 케이스만 `UNKNOWN_CASE` 로 본다 (2026-11-07 COMPAT-F1-04 끝 검사)
- **「모델별 1대」를 켠 세트는 같은 모델을 한 대만 담는다** — 서버도 막는다(400). 화면만 막으면 오래된 화면 · API 로 같은 모델이 두 번 돈다
- **직접 추가한 케이스는 뺄 수 있고, 자동 선택 케이스는 뺄 수 없다** — 시안 문구 `자동 선택 케이스는 제외할 수 없습니다`. 직접 추가한 케이스가 자동 선택에도 들면 한 번만 돈다(자동 선택 쪽으로 센다)
- **세트는 지우지 않고 치운다**(`is_active = false`) — 지난 실행이 그 세트를 가리킨다. 시나리오와 같다([시나리오.md](시나리오.md) §3.7)
- 세트에 대상 서버를 담지 않는다 — 실행할 때 시작 확인 창에서 고른다(마지막에 고른 것을 미리 고른다 — [실행.md](실행.md) §8.2 와 같은 장치). 앱 빌드는 그 대상 서버 줄의 앱이다([실행.md](실행.md) §3.11 「빌드마다 돌리기」의 빌드 규칙 그대로)

#### 자동 선택 — 화면 커버리지가 가장 높은 작은 묶음 (결정 5)

**전체 화면 목록(U)** — 그 애플리케이션의 화면 열쇠를 모은다. 열쇠 꼴은 [공통/4-데이터모델.md](../공통/4-데이터모델.md) 「게임 테스트 표」 「화면 기록 표의 열쇠 꼴」이 정본이다.

| 애플리케이션 종류 | 전체 화면 목록 | 케이스가 지나는 화면 |
|---|---|---|
| 웹(모바일 웹) | `screen_found.url` ∪ `screen_record.url`(대상 서버 · 상태를 가리지 않고 같은 틀로 모은다) | `case_screen.screen_url` · `open_urls` 를 같은 틀 함수(`scripts/authoring-crawl-rules.ts` `주소틀` — `app:` · `game:` 열쇠는 그대로 둔다, 작성.md §3.6)로 바꾼 것 |
| Android 앱 | 위와 같다 — 열쇠가 `app:<activity>/<이름표>` 다(appium-cli `crawl`) | `case_screen.screen_url`(앱 화면 파일의 `주소` 값이 `app:` 열쇠다 — 작성.md §3.6 「앱 · 게임 역방향」 7) |
| 게임 | 창 `game:<장면>/<창 경로>`(위와 같다) ∪ 장소 — `game_element.key`(`kind = 'WORLD'` 의 `zone:<구역>`)를 화면 기록 꼴 `game:World/zone:<구역>` 으로 바꿔 넣는다. 화면 기록에 이미 있는 장소와 한 번만 센다 | 창은 `case_screen.screen_url`, 장소는 `game_element_case` 의 열쇠를 같은 꼴로 바꾼 것 |

- **장소는 화면 커버리지에만 센다** — 장소를 지나는 케이스를 고르게 하려는 것이다. 찍힌 화면은 창으로만 찾아(아래 「화면 찾기」) 결과 표 · 미점검에는 장소 줄이 서지 않는다. 장소에서 찍힌 화면은 그 창(대개 HUD) 줄에 든다
- **케이스가 화면을 지나는가는 「PRD 에 없는 화면」 셈과 같은 규칙이다** — 케이스의 화면 주소 · 여는 주소를 `주소틀` 로 바꾼 틀에 전체 화면 목록의 열쇠가 `틀닿나`(인자 없는 주소는 인자 붙은 틀도 덮는다 — `scripts/authoring-crawl-rules.ts`)로 닿으면 지난다. 같은 화면을 두 곳에서 다르게 세면 숫자가 어긋난다(코드 `apps/admin/src/compat/select.ts` · `prd/found.ts`)
- **고르는 법은 탐욕 근사다** — 아직 안 덮은 화면을 가장 많이 더하는 케이스를 하나씩 고르고, 더할 것이 없으면 멈춘다. 같으면 지나는 화면(전체 목록에서 그 케이스가 지나는 것)이 적은 케이스(짧은 케이스) → `tc_id` 차례다.
  정확한 최소 묶음은 화면 수백 개에서 비싸다. 탐욕 근사는 최소의 몇 배 안쪽이라 「최소 조합」이라는 시안 문구는 그대로 쓴다. 숫자가 눈에 띄게 크면 그때 바꾼다
- **고를 수 있는 케이스** — 그 애플리케이션의 활성 케이스 가운데 폰에서 도는 것(`android` · `mobile`)이다. UI · 기능 둘 다 고른다. 미확정 케이스도 고른다 — 호환성은 기대값이 아니라 화면을 본다. 보류(`held`) 케이스는 따로 거르지 않는다 — 값을 안 채운 보류 케이스는 main 에 못 들어가 카탈로그에 없다(K13 `check:tests --no-held`, 2026-11-07 COMPAT-F1-04)
- **화면 커버리지** = 고른 케이스(자동 선택 ∪ 직접 추가)가 지나는 화면 ∩ U 의 수 / U 의 수. **미커버 화면** = U − 지나는 화면이다. 시안 문구 `해당 화면을 지나는 TC 를 작성하면 다음 실행부터 자동 포함됩니다`
- **크롤 화면 기록이 비면**(`screen_found` · `screen_record` 둘 다 — 앱은 2026-11-04 기준 0) 고를 수 있는 케이스가 아는 화면(`case_screen` 의 화면 주소 · 여는 주소)을 U 로 쓰고 세트 화면에 `전체 화면 목록이 없어 케이스가 아는 화면으로 셉니다` 를 보인다. 미커버 화면은 0 이 된다(장소 말고는). 게임 장소는 그때도 위 표대로 더해서 어떤 케이스도 안 지나는 장소는 미커버로 남는다
- **실행을 만들 때 그때 계산한 케이스를 실행에 박제한다**(`compat_run_case`) — 지난 실행을 열면 그때 돈 케이스가 보인다

#### 디바이스 · 점검 상태 (결정 6 · 9)

- **디바이스 목록은 호환성 전용 통로 `GET /api/compat-devices`(아래 §7)가 준다** — 기기 성능의 기기 목록(`GET /api/perf/devices` — [성능.md](성능.md) §7)은 쓰지 않는다. 그쪽은 비전 상태를 `IDLE` · `BUSY` 둘로 접고 제조사 · 해상도를 버리며 내 컴퓨터 러너 폰(AI 점검이 안 된다)도 섞는다. 이 통로는 팜 폰만, 비전 `GET /api/devices` 의 칸과 상태 넷(`IDLE` · `OCCUPIED` · `MAINTENANCE` · `OFFLINE`)을 그대로 옮겨 싣는다
- **디바이스 선택 상자(시안 ②-1)의 칸** — 기종 · 모델 · 제조사 · Android · 해상도 · 밀도 · 화면(인치) · 형태(폰 · 폴더블 · 태블릿) · 상태. 기종명 · 밀도 · 인치 · 형태는 비전이 등록 때 한 번 읽어 싣는다(안내서 11절 · DEV-F4-09 — 아래 「비전에 기대는 것」 2). **못 읽은 칸은 없다** — 화면은 빈 칸을 `-` 로 두고 형태가 없으면 `폰` 으로 본다
- **세트의 모델 · 기종명 사본**은 저장할 때 팜 목록에서 채운다 — 기종명은 `marketName`, 없으면 모델이다. 팜에 없는 디바이스는 이미 그 세트에 있던 것이면 옛 사본을 둔다(등록에서 빠진 폰도 세트는 읽힌다). 새로 넣는 것이면 `UNKNOWN_DEVICE` 이고, 팜이 답하지 않아 확인할 수 없으면 `FARM_UNREACHABLE` 이다 (2026-11-07 COMPAT-F1-04 시작 질문)
- **점검 상태** — 폴더블이 아니면 디바이스 하나가 상태 하나, 폴더블은 `펼침` · `접힘` 둘이다. 셈 · 실행 순서 · 결과 열 · 예상 시간이 모두 점검 상태 단위다. 비전은 폴더블을 가르지만(`formFactor: 'foldable'` · `fold`) **원격으로 접고 펴기가 아직 없다**(안내서 11절 「폴더블은 펼친 채 꽂는다」) — 그동안 폴더블도 상태 하나라 점검 상태 수 = 디바이스 수다.
  **원격 접기가 생기기 전에는 꽂힌 상태 그대로 한 번 점검하고, 결과 열에 그때 상태(`compat_run_device.fold` — 잡을 때 팜 `fold` 를 `OPEN` · `FOLDED` 로 옮긴다)를 적는다. 접힌 화면도 보려면 폴더블 한 대를 접은 채 꽂아 세트에 따로 담는다** (2026-11-07 사용자 · COMPAT-F1-05 시작 질문 — 결정 9 는 원격 접기가 생기면 그대로 연다)
- **예상 소요 시간** = 케이스 수 × 점검 상태 수 × 케이스 평균 시간(케이스마다 최근 통과 실행 5건의 `duration_ms` 평균 — 없으면 1분) + AI 점검 몫(마지막 상태의 화면 수 × 화면당 7초 — 비전 측정 중앙값 6.7초). 화면 수는 케이스마다 그 케이스가 아는 화면(화면 주소 · 여는 주소의 틀 — 장소 빼고, 0 이면 1) 수의 합이다. 전체 목록과 겹치는지는 안 본다 — 찍히는 것은 케이스가 실제로 여는 화면이라서다. 케이스 세션마다 따로 찍고 한 세션에 40장까지라 케이스마다 40 에서 자른다. 분은 올림이다. 평균은 폰(`mobile` · `android`) 항목만 본다 — PC 소요는 폰보다 훨씬 짧다. 시안 `케이스 9 × 점검 상태 14 = 126 회 실행` · `테스트 약 72 분 · AI 점검 완료까지 약 10 분 추가`

#### 실행 — 순차 실행 (결정 6 · 7)

1. 시작 — 실행 `write` 가 세트에서 `실행`(시작 확인 창 — 대상 서버 · 디바이스 · 케이스 수 · 예상 시간)을 누르면 서버가 `test_run` 한 줄(`kind = 'COMPAT'`)을 만들고, 자동 선택을 다시 계산해 케이스를 박제하고, 점검 상태마다 `compat_run_device` 줄을 `WAIT` 로 세운다
2. **점검 상태를 차례로 하나씩 돈다.** 그 디바이스를 실행을 누른 사람 이름으로 잡고(`POST /api/devices/{serial}/hold` — [러너.md](러너.md) §5.2 「잡기 규칙」 · 「팜 토큰은 누른 사람 것이 먼저다」. 잡은 serial 은 `compat_run_device.held_serial` 에, 잡은 폰의 팜 목록 줄은 `device` 에 바로 쓴다 — 놓으면 `held_serial` 은 비고 결과는 `device` 의 serial 로 실제로 돈 폰을 보인다) 박제한 케이스를 한 건씩 러너 `/execute` 로 보낸다 — `udid` 는 그 디바이스, 앱 · 게임은 `uiCheck: true`(아래 §7 「러너 · kit」).
   **모바일 웹은 케이스마다 admin 이 그 폰 Chrome 을 `POST /api/devices/{serial}/chrome` `{"uiCheck":true}` 로 켜고 답의 `cdpUrl` 을 러너에 싣는다** — 러너는 점검을 모른다. 점검 결과는 admin 이 답의 `sessionId` 로 `GET /api/sessions/{sessionId}/artifacts/ui-check.json` 을 받고 의심 화면 PNG 를 실행 폴더(`artifacts/runs/<runId>/<compat_run_case.id>/farm/`)에 받아 둔다. 영상은 없다(비전 안내서 13절 「UI 점검」, 2026-11-07 COMPAT-F1-05). `sessionId` 를 안 주는 옛 비전이면 점검 없이 돌아 그 화면은 미점검이다
   **디바이스 줄(`DEVICE_BUSY` 잠금) 밖에서 돈다** — 기기 성능 실행과 같다([실행.md](실행.md) §3.2 디바이스 줄 문단). 폰이 갈려서 잠금이 필요 없고, 잠금을 쥐면 72분짜리 실행이 서버의 모든 앱 항목 · 테스트 실행을 막아 결정 6(기다리는 폰은 다른 실행이 쓴다)과 거꾸로다. **폰은 상태마다 한 번 잡는다**(앱 항목의 「항목마다 잡고 놓는다」 예외 — [러너.md](러너.md) §5.2) — 잡는 시간은 그 상태의 예상 시간에 맞춰 팜이 받는 값(30 · 60 · 120분) 가운데 고르고 모자라면 늘린다(`/hold/extend` — 성능 §7 「팜 폰」과 같다). 모바일 웹도 같은 규칙이다
3. **차례가 온 디바이스가 사용 중이면 뒤로 미루고 다음 상태를 먼저 한다.** 남은 상태가 모두 사용 중이면 30초마다 다시 본다. **한 상태를 30분 넘게 못 잡으면** 그 상태는 `SKIPPED` 이고 그 열의 화면은 모두 미점검(`디바이스를 잡지 못했습니다`)이다. 「모델별 1대」 세트는 미루기 전에 같은 모델의 빈 디바이스를 먼저 찾는다
4. **그 상태의 케이스가 다 끝나면 디바이스를 바로 놓는다** — AI 점검은 비전에서 이어 돌고, 놓은 디바이스는 다른 실행이 쓴다(결정 6). 상태는 `CHECKING` 이 되고 그 상태의 `ui-check.json` 이 모두 끝나면 `DONE` 이다
5. **AI 점검이 다 끝나야 실행이 끝난다**(결정 7) — **케이스마다 그 케이스가 끝난 뒤 60분** 안에 점검이 안 끝나면 그 케이스의 화면은 미점검(`AI 점검 결과를 받지 못했습니다` · `check_state = 'missing'`)이다. 러너가 그만 받는 때와 같은 잣대라 둘이 어긋나지 않는다(아래 §7 「러너 · kit」). **모든 상태가 `DONE` · `SKIPPED` · `STOPPED` 이고 모든 케이스의 `check_state` 가 끝난 값(`checking` 이 아님)이면 실행이 끝난다** — 이 끝내기는 호환성 몫이다. 케이스 실행의 끝내기(`execution/runLifecycle.ts` `finishRun` — 「안 끝난 `run_item` 이 없으면 끝」)는 `run_item` 이 없는 호환성 실행을 곧바로 끝내 버려서 `kind = 'COMPAT'` 에는 부르지 않는다. 비전이 `limit` 이면 남은 화면은 `AI 사용 한도 초과로 점검 중단` 이다
6. **중단** — `실행 중단` 은 지금 통로(`POST /api/runs/:runId/abort`)를 쓰되 **호환성 가지를 새로 단다** — 지금 중단(`runLifecycle.ts` `abortRun`)은 `run_item` 만 닫아 호환성 실행에서는 아무것도 안 끊는다. 호환성 가지는 도는 케이스의 `compat_run_case.id` 로 러너 `/abort` 를 부르고, 아직 안 돈 케이스는 `NA` 로 닫고, 잡은 디바이스를 놓고(실제로 잡은 serial — 아래 「모델별 1대」), 남은 상태는 `STOPPED` 다. `test_run.status` 는 **바로 `ABORTED`** 다 — 알림 줄 · 실행 기록이 「도는 중」으로 남지 않게. 돌던 상태의 점검 결과는 끝난 실행에도 이어서 받아 쓴다(아래 줄). **이미 점검을 마친 화면은 결과에 남는다**(시안 `중단 시 점검을 마친 화면까지 결과에 남습니다`). 돌던 상태의 점검은 끝날 때까지 받는다(위 5 의 60분 안)
   **admin 이 다시 켜지면** 도는 호환성 실행은 이어 가지 않는다 — 차례 돌기 · 잡기 기다리기 · 점검 기다리기가 admin 메모리에 산다. 다시 켤 때 정리(`recoverRunning`)에 호환성 가지를 단다 — 끝나지 않은 상태는 `STOPPED`(`서버가 다시 켜져 실행이 멈췄습니다`), `checking` 인 케이스는 `missing`, 잡혀 있던 디바이스는 놓는다. 이미 받은 점검 화면은 남는다
7. 알림 — 도는 호환성 실행은 알림 줄에 오르고 끝나면 알린다. `GET /api/notifications` 의 `running` 에 `kind: 'compat'` 줄(`runId` · `title` · `states: { done, total }` · `checks: { done, total }` · `startedAt`)로 싣고, **끝난 호환성 실행은 `recent` 에 담는다** — `testKind: 'COMPAT'` 이고 `counts` 대신 `compat: { pending, unchecked }` 다. E2E 와 다르다 — 끝난 E2E 는 집계가 늘 0 이라 `recent` 에서 뺐지만 호환성은 미판정 수가 곧 할 일이다([공통/3-공유계약.md](../공통/3-공유계약.md) §7.1 · [공통/5-화면공통.md](../공통/5-화면공통.md) §8 「알림」 · [실행.md](실행.md) §8.9)

케이스의 통과 · 실패는 `compat_run_case` 에만 남는다 — 화면에는 「미점검 화면」의 까닭(`DMA-UI-040 이 5단계에서 실패`)으로만 보인다(결정 1). 실패 카드 · 증적 · Issue Bunker 등록은 없다.

#### 화면 찾기 — 찍힌 화면이 어느 화면인가 (결정 12)

`ui-check.json` 화면 줄마다 비전이 **단서**를 싣는다 — 정본은 비전 안내서 10절 「어느 화면인가」 · ADR-059 이고 이 표는 받는 쪽 규칙만 적는다(2026-11-07 비전 PR #102 ~ #104 확정 · COMPAT-F1-05 반영). 얻은 단서만 칸이 있다. 서버가 단서를 화면 열쇠로 바꾼다(코드 `apps/admin/src/compat/uiCheck.ts`).

| 종류 | 단서 | 화면 열쇠로 바꾸는 법 |
|---|---|---|
| Android 앱 | `locator: { using, value }` — 누른 요소를 찾을 때 쓴 찾기(요소 · 요소들 · 요소 안 찾기) 그대로. `actions` · `mobile: …Gesture` 처럼 요소 없는 명령 · 세션에서 2,000개를 넘게 찾은 뒤 오래된 요소는 칸이 없다 | 그 케이스가 쓰는 화면 파일(`case_screen.file` 가운데 화면 주소가 있는 것)에서 그 `value` 를 낱말로 담은 파일을 찾아 `screen_url` 을 쓴다 — 팜은 짧은 id 에 패키지를 붙여 보내(`com.x:id/cart`) 패키지를 뗀 것(`cart`)으로도 찾는다. 앞뒤가 낱말 글자면 안 맞는다(`title` 이 `sub_title` 에 안 맞게). 둘 이상이면 앞 화면 줄과 같은 파일을 고르고, 그래도 둘이면 「화면 모름」 |
| 게임 | `game: { target }` — 게임 명령의 `target` 그대로이고 오브젝트 이름이다(이름이 겹칠 때만 경로). `tap`(좌표)에는 없다. `type` 의 글자는 안 옮긴다(비밀번호일 수 있다) | 경로(`/` 로 시작)면 그 케이스 화면 파일의 `game:<장면>/<창 경로>` 가운데 그 경로를 품는 가장 깊은 창이다. 이름이면 그 케이스 화면 파일 가운데 그 이름을 낱말로 담은 파일이다 — 둘 이상이면 앱과 같이 앞 화면 줄을 따르고, 그래도 둘이면 「화면 모름」 |
| 모바일 웹 | `url` — 그 누르기를 받은 탭의 주소(맨 위 프레임). 쿼리(`?…`) · `#…` 는 비전이 뺀다 | 같은 틀 함수(`주소틀`)로 바꾼다 |

- **화면 모름** — 단서가 없거나 못 바꾼 화면은 열쇠 `unknown:<tcId>#<단계>` 로 둔다. 표에는 `화면 모름 — DMA-UI-031 4단계` 줄로 선다. 의심이 없으면 표에 안 오르니 대부분 안 보인다
- **단계** — 찍은 시각(`at`)을 그 케이스의 단계 시간에 맞춘다. 러너 응답의 단계는 걸린 시간만 있어 **항목이 끝난 때에서 거꾸로 단계 시간을 빼** 단계마다 시작 시각을 셈한다(근사 — 앞쪽에는 연결 · 앱 설치가 끼어 항목 시작에서 세면 단계가 뒤로 밀린다. 기기 성능 구간과 같은 까닭이다). 첫 단계보다 앞이면 1단계다. 카드 문구 `DMA-UI-031 4단계 · 터치 직전 캡처`
- 의심 없는 화면도 열쇠를 찾아 「점검 화면」 · 「이상 없음」으로 센다 — 비전은 의심 없는 화면의 PNG 를 지우지만 화면 줄은 남긴다

#### 결과 · 판정 (결정 13)

- **셈 단위는 칸(화면 × 점검 상태)이다.** 칸 하나는 `이상 없음` · `미판정` · `결함 확정` · `결함 아님` · `미점검` 가운데 하나다 — 의심이 하나라도 있으면 판정 전 `미판정`, 점검한 화면 줄이 하나도 없고 그 케이스가 그 화면을 지나야 했으면 `미점검` 이다
- **그 칸이 지나야 했던 화면** = 그 상태에서 돈 케이스들의 `case_screen` 화면 + 실제로 찍힌 화면이다. 찍혔지만 의심 없는 화면은 `이상 없음` 이다
- **미점검 까닭** — 디바이스를 못 잡았으면 `디바이스를 잡지 못했습니다`, 그 화면을 지나는 케이스가 실패했으면 `<tcId> 이 N단계에서 실패`(N 은 실패 단계), 케이스를 못 돌렸으면 그 상태가 멈춘 까닭(`실행을 중단했습니다` · `서버가 다시 켜져 실행이 멈췄습니다`), 비전이 `limit` 면 `AI 사용 한도 초과로 점검 중단` · `failed` 면 `AI 점검이 실패했습니다`, 60분 안에 점검이 안 끝났으면 `AI 점검 결과를 받지 못했습니다`, 그 밖은 `찍힌 화면이 없습니다`. 위 차례로 먼저 맞는 것 하나다. **돌거나 점검 중인 칸은 아직 값이 없다** — 결과 통로가 그 칸을 안 싣는다(코드 `apps/admin/src/compat/result.ts`)
- **머리 숫자** — 점검 화면(이상 없음 · 의심이 있는 화면 수) · 디바이스 · 점검 상태 · 결함 확정 · 미판정 · 결함 아님(칸 수) · 미점검 화면(미점검 칸이 하나라도 있는 화면 수). 시안 `31 점검 화면 · 12 디바이스 · 점검 상태 14 · 2 결함 확정 · 4 미판정 · 1 결함 아님 · 2 미점검 화면`
- **판정은 칸마다 하나다** — 실행 `write` 가 카드의 `결함 확정` · `결함 아님` 을 누른다. 누가 · 언제를 남기고, 다시 누르면 바꾸거나 되돌린다(미판정으로). 판정은 그 실행에만 남는다 — 다음 실행에 이어 가지 않는다(화면이 바뀌었을 수 있다)
- **결과는 회귀 숫자에 안 섞인다**(결정 1) — 대시보드 · Grafana · 직전 대비 · 케이스 이력은 `kind IN ('UI','FN')` 만 본다([공통/4-데이터모델.md](../공통/4-데이터모델.md) 「실행 종류」). **`kind <> 'SCENARIO'` · `=== 'SCENARIO'` 꼴로 「E2E 만 빼는」 자리는 COMPAT 를 케이스 실행으로 받아들인다** — 그래서 Issue Bunker 실패 카드 · 실패 보고(`bts/card.ts` · `bts/failReport.ts`) · 알림(`notifications/store.ts`)을 「케이스 실행」 조건(`runKind.ts` 의 `종류조건('case')` · `케이스실행인가`)으로 바꿨다(COMPAT-F1-02). 새 종류를 더할 때 `SCENARIO` 를 grep 한다

#### 비전에 기대는 것 (Device VISION 저장소 몫 — 2026-11-07 세션 「Devicefarm · 호환성 비전 할 일 1~5」)

꼴은 비전이 정하고, 정해지면 아래 §7 「비전 약속」 블록을 그 꼴로 고친다. 그 전에는 해당 줄이 「비전 대기」다.

1. **Chrome 화면 찍기 · 세션 번호** — 끝(2026-11-07 비전 ADR-059 · 안내서 13절 「UI 점검」). `POST /api/devices/{serial}/chrome` `{"uiCheck":true}` 의 답 `sessionId` 로 `/api/sessions/<번호>/artifacts` 에서 `ui-check.json` 을 받는다. 그 폰 다리의 첫 연결이 보낸 누르기 · 터치 시작 · 글자 넣기 직전마다 폰 화면 통째를 찍는다(키 누르기는 안 찍는다). 받는 쪽은 위 「실행」 2 · COMPAT-F1-05
2. **디바이스 정보 칸** — 끝(2026-11-07 비전 DEV-F4-09 · 안내서 11절). `marketName` · `density`(dpi 숫자) · `inches`(숫자) · `formFactor`(`phone` · `foldable` · `tablet`)이고 못 읽은 칸은 없다. `GET /api/compat-devices` 가 그대로 옮긴다(COMPAT-F1-04)
3. **폴더블** — 판별(힌지 센서 — `formFactor: 'foldable'`) · 내장 화면들(`displays: [{ size, inches }]`, 큰 것부터) · 지금 상태(`fold: 'unfolded' | 'folded'`, 30초마다)는 끝(2026-11-07 안내서 11절). **접힘 상태 바꾸기는 아직 없다** — 그동안은 꽂힌 상태 그대로 한 번 점검하고 접힌 화면은 접어 꽂은 한 대로 따로 본다(위 「디바이스 · 점검 상태」, 2026-11-07 사용자)
4. **화면 단서(`locator` · `url` · `game`)** — 끝(2026-11-07 비전 ADR-059 · 안내서 10절). 받는 쪽은 위 「화면 찾기」
5. 모델 Haiku · 엣지 패널 지시 한 줄 — 결정 8. Commander 쪽 할 일은 없다

#### 러너 · kit — `farm:uiCheck` 켜기 · 통과 항목도 점검 결과 받기

- **`ExecuteRequest.uiCheck?: true`** — 호환성 실행 항목에만 싣는다. 오면 러너가 android 항목에만 자식 환경값 `PLATFORM_UI_CHECK=1` 을 주고 kit 이 Appium 연결 capability 에 `farm:uiCheck: true` 를 넣는다(앱 · 게임 — 게임 명령도 같은 연결이 열려 있으면 비전이 찍는다, ADR-052 결정 2). 모바일 웹 항목에는 안 싣는다 — admin 이 Chrome 을 켤 때 점검을 켜고 결과도 admin 이 받는다(위 「실행」 2, COMPAT-F1-05)
- **`historyId` 자리에 `compat_run_case.id` 를 싣는다** — 러너는 폴더 이름(`artifacts/runs/<runId>/<historyId>/`)만이 아니라 도는 자식 지도 · `/abort` · `/progress` 의 열쇠로 `historyId` 하나만 쓴다(`apps/runner/src/execute.ts` `running`). 그래서 **`compat_run_case.id` 는 `run_item.history_id` 와 같은 번호 줄(시퀀스)에서 받는다** — 따로 세면 같은 번호의 케이스 실행 항목과 부딪혀 한쪽 중단이 다른 쪽을 끊는다. 러너가 진행을 알리면 admin 은 실행의 `kind` 를 보고 `compat_run_case` 에서 찾는다
- **러너는 `uiCheck` 항목이면 통과해도 점검 결과를 받는다** — 지금은 통과하지 못한 정식 실행 항목만 받는다([러너.md](러너.md) §5.2 「증적 영상 · logcat 은 통과하지 못한 정식 실행 항목만 받는다」). `uiCheck` 항목은 판정과 상관없이 **`ui-check.json` 과 `ui-*.png` 만** 받고 영상은 안 받는다(통과 항목 영상이 100MB 를 넘는 까닭 그대로). 실패한 `uiCheck` 항목은 지금처럼 영상 · logcat 도 받는다
- **`status` 가 `checking` 이면 1분마다 다시 받는다** — `done` · `failed` · `limit` 가 되거나 **그 항목이 끝난 뒤 60분**(위 「실행」 5 와 같은 잣대)이 지나면 그만 받는다. 러너는 실행의 마지막 항목을 모르니 항목마다 잰다. 받는 동안 다른 항목 받기를 막지 않게 점검 기다리기는 받기 줄(러너 하나에 하나씩)과 따로 돈다. 끝난 파일은 `farm/ui-check.json` 에 두고 의심 화면 PNG 는 그 옆에 둔다. 덜 받은 것은 옆 폴더 `farm.ui.part` 다 — 실패 항목의 영상 받기(`farm.part`)와 같은 때 돌 수 있어 이름을 따로 둔다. 실패 항목의 영상 받기에 딸려 온 점검 중 파일은 `farm` 에 옮기지 않는다
- 팜이 `ui-check.json` 을 아예 안 주거나(비전 꺼짐) 세션을 모르면(404) 한 번 묻고 그만 받는다 — 기다려도 안 생긴다. 그 화면은 admin 이 60분 뒤 미점검으로 닫는다
- admin 은 `farm/ui-check.json` 을 읽어 `compat_screen` 줄을 쓰고 PNG 를 그 실행 폴더에 둔 채 가리킨다. 팜 30일 보관과 상관없이 우리 쪽에 남는다 — 의심 화면만이라 작다

### 8.17 호환성 화면 (2026-11-07 · 시안 FSGHPH6CyRpaa6hdaWtVYE 사용자 확정)

시안 다섯 장이 짜임의 정본이다. 여기는 시안에 안 보이는 규칙만 적는다. 문구는 시안 그대로 쓰고 위 「화면 낱말」을 지킨다.

- **메뉴** — `테스트 실행 › 호환성`(세트 목록 · 세트) · `실행 기록 › 호환성`. 둘 다 이름 곁에 `신규` 꼬리표다. 메뉴는 애플리케이션 종류 하나로 정한다는 규칙 그대로 웹 · Android 앱 · 게임에 서고 API 에는 없다 — 정본은 공통/5-화면공통 §8 「메뉴는 고른 애플리케이션의 종류 하나로만 정한다」 표다. 웹에서는 모바일 웹 케이스가 하나도 없으면 고를 케이스가 없어 세트 화면이 그 까닭(`실제 폰에서 도는 모바일 웹 케이스가 없습니다`)을 보인다 — 메뉴를 숨기지 않는다(케이스가 있나 없나로 자리가 바뀌지 않는다는 같은 규칙)
- **① 세트 목록** — 표 열 `세트` · `디바이스` · `케이스` · `화면 커버리지` · `최근 실행`. 최근 실행 칸은 결함 확정 · 미판정 · 미점검 알약이고 0 은 안 보인다. 줄 끝 `실행`. 표 아래 안내 `케이스는 실행할 때마다 화면 커버리지가 가장 높은 최소 조합으로 자동 선택합니다 · 결과는 「실행 기록 › 호환성」에 남습니다`
- **② 세트** — 구획 셋(디바이스 · 케이스 · 화면 커버리지)과 예상 소요 시간. 디바이스 구획 머리에 요약(Android 범위 · 형태별 수 · 폴더블 안내 · 해상도 종류 · 제조사별 수)과 `디바이스 선택`. 케이스 구획은 자동 선택(4건 + `외 N건`)과 직접 추가(줄마다 `제외`) · `케이스 추가`(케이스 목록 고르개 — [카탈로그.md](카탈로그.md) §8.1 고르는 칸)
- **②-1 디바이스 선택 상자** — 거르는 칩(제조사 · Android · 형태) · 검색 · `같은 모델은 1대만` · `사용 가능만`. 같은 모델의 두 번째부터는 `같은 모델` 꼬리표로 흐리게 서고, `같은 모델은 1대만` 을 끄면 고를 수 있다. `점검 중`(비전 `MAINTENANCE`) · 연결 끊김(`OFFLINE`) 디바이스는 잠긴다. 바닥에 `N 대 선택 · 점검 상태 M 개` 와 요약
- **③ 실행 중** — [실행.md](실행.md) §8.16 실행 창 한 틀(크기 · 머리 단계 표시 · 바닥 · 닫는 길)을 그대로 쓴다. 왼쪽은 지금 디바이스 카드(케이스 `6 / 9` · 지금 케이스 · 경과 · `AI 점검 40 / 61 장`)와 `실행 순서` 목록(완료 · 실행 중 · 대기 — 폴더블은 `펼침` · `접힘` 두 줄. 원격 접기가 없는 동안은 한 줄 — 위 「디바이스 · 점검 상태」), 오른쪽은 지금 디바이스 실시간 화면(정식 실행 장면 — [실행.md](실행.md) §3.2 · 비전 링크)과 `최근 UI 결함 의심 화면` 작은 그림. 안내 `결함 판정은 결과 화면에서 합니다`. 바닥 왼쪽 `실행 중단`
- **④ 결과** — 머리 숫자 띠 → `화면 × 디바이스` 표(의심 · 미점검이 있는 화면만, `이상 없는 화면 N개 숨김`, 열은 점검 상태 — 폴더블 두 열, 원격 접기가 없는 동안은 한 열) → 카드(거르개 `미판정 먼저` · `결함 확정` · `전체`) → 미점검 화면 → 참고 · 미커버 화면. 표 칸을 누르면 그 카드로 내려간다. 카드는 의심이 나온 칸만이고 한 화면의 카드들을 한 묶음으로 접는다(`펼치기`). 카드 안 그림은 의심 화면 PNG 에 `box` 네모를 그린다 — `box` 는 근사값이다(비전 안내서)
- **⑤ 실행 기록 › 호환성** — 표 열 `실행` · `세트` · `디바이스` · `점검 화면` · `UI 결함` · `미점검` · `실행 일시 · 실행자`. 머리 안내 `호환성 실행은 기능 · UI 실행 기록과 통과율에 포함하지 않습니다`. 줄을 누르면 ④ 로 간다. 거르기 · 쪽 넘기기는 실행 기록 목록 규칙 그대로다([실행.md](실행.md) §8.7 「거르는 일은 서버가 한다」)
- **휴대폰** — 표 둘(① · ⑤)은 카드 줄이다([실행.md](실행.md) §8.7 과 같다). ④ 의 `화면 × 디바이스` 표는 첫 열(화면)을 고정하고 가로로 민다
