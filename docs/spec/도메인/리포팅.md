### 3.3 Reporting — 결과를 어떻게 보여주는가

- **책임**: 저장된 결과를 읽어 증적 문서와 지표를 만든다
- **읽기 전용**. 이 컨텍스트는 어떤 테이블에도 write 하지 않는다 (`evidence_document` · `run_case_bug` 제외 — 「버그」는 결과를 바꾸지 않고 판정만 남긴다, 아래 「실패 요구사항」)
- **불변식 — 증적 재현**: **같은 실행의 증적은 언제 뽑아도 같은 문서가 나온다** (2026-09-16 결정).
  **예외 하나 (2026-10-10 사용자 · 2026-10-11 PRD-F4-02 반영)** — 미확정 새 규칙 뒤에는 옛 실행의 증적도 미확정을 따로 묶지 않고 그대로 센 모양으로 다시 나온다(도메인/작성 §3.6 「★ 표준 기획서」 「미확정」 「옛 실행도 새 규칙」). 박제 값은 그대로이고 세는 방식만 바뀌었다.
  **증적 C 양식(2026-10-12 WEB-F3-10)도 같다** — 옛 실행의 증적을 다시 뽑으면 C 양식 배치(요약 띠 · 카드 · 줄 · 부록)로 나온다. 박제 값과 내용은 그대로이고 배치만 바뀌었다. 이미 만든 파일은 안 바뀐다(아래 §8.4 「증적 문서는 요약 띠 → 실패 카드 → 통과 · 미실행 줄이다」)
  **E2E 요약도 예외다 (2026-10-16 PR #277) — 이 줄이 정본이다.** 케이스 증적 끝의 E2E 요약(§8.4 「E2E 시나리오 증적」)은 다른 실행(시나리오 실행)을 문서를 만드는 때 읽는다.
  같은 실행의 증적을 다시 뽑으면 그 절만 달라질 수 있어 절 머리에 「이 요약은 문서를 만든 때 기준이다」를 적는다. 그 절 밖의 글자는 그대로다.
  **한 건 실행이 붙은 실행도 예외다 (2026-10-30 WEB-F7-02 — 규칙은 실행.md §3.2 「★ 한 건 실행은 묶음 실행에 붙는다」).** 붙은 뒤에 뽑은 증적은 지금 결과로 쓴다 — 붙기 전에 뽑은 것과 판정 · 수가 다르다.
  원래 항목은 지우지 않으므로 원래 결과도 문서에 그대로 남는다(§8.4 「다시 실행이 붙은 실행」). 머리에 「다시 실행 N건 포함 · 마지막 <시각>」을 적어 언제 기준인지 보인다. 이미 만든 파일은 안 바뀐다
  실행 직후에 뽑든 반년 뒤에 뽑든 글자 하나 달라지지 않는다. 증적은 "그때 무슨 값으로 돌려 어떻게 나왔는가"의
  기록이고, 지금의 코드 상태가 섞여 들어가면 기록이 아니라 추정이 된다.
  - **지금은 이 원칙이 지켜지지 않는다.** 증적의 `입력` 칸은 라벨-값 쌍인데(§8.4), 값(`params`·`expected`)만
    `run_item`에 스냅샷으로 남고 **라벨은 `test_case.param_schema`의 `description`에서 온다.**
    그 테이블은 스캔 때마다 덮어쓰는 캐시다(§3.1). 케이스 코드의 `.describe('아이디')`를 `.describe('사용자 ID')`로
    고치고 다시 스캔하면, 작년 실행의 증적을 오늘 뽑았을 때 라벨이 바뀌어 나온다.
    제한 시간·케이스 파일 경로·불러온 입력값 묶음도 같은 문제를 갖는다
  - **그래서 문서를 만드는 데 필요한 것을 전부 실행 기록에 박제한다.** 박제할 자리는 **사실의 크기**로 가른다.
    - 한 번의 실행 전체에 걸린 사실은 **`test_run`**에 넣는다 — 서비스 이름, 테스트 저장소 주소,
      대상 서버, 대상 주소, 실행자 이름(§3.5). 항목마다 반복될 값이 아니다
    - 항목 하나에만 걸린 사실은 **`run_item`**에 넣는다 — `param_schema`·`expected_schema`(라벨과 입력 칸 정의),
      회차, 제한 시간, 불러온 입력값 묶음, 케이스 파일 경로
    - 컬럼 정의는 **§6이 정본**이다
  - **리포팅은 문서를 만들 때 `test_case`를 읽지 않는다.** 읽는 순간 이 불변식이 깨진다
  - **값이 빈 칸은 박제된 스키마의 기본값으로 보인다** (2026-10-01). 화면에서 값을 안 고치고 실행하면 그 칸은 요청에서 빠지고
    `run_item.params`·`expected` 에도 빈 채로 박제된다. 케이스는 그 칸을 **코드 기본값으로 돌았고**([실행.md](실행.md) §3.2),
    그 값은 함께 박제된 `param_schema`·`expected_schema` 의 `default` 에 남아 있다. 값만 읽으면 기대결과가 있는 케이스도
    「기대 결과 없음」으로 찍힌다(2026-10-01 버그). **증적 · 항목 상세 · 결과 목록의 값 한 줄(실행 §8.3)이 모두 이 규칙이다**
    - **박제된 스키마의 칸 순서로 걷는다** — 값이 있으면 값, 없으면 `default`. 스키마에 없는 값 칸은 맨 뒤에 붙인다.
      값만 따라가면 같은 케이스도 어느 칸을 고쳐 돌렸느냐에 따라 순서가 바뀐다. 값이 다 찬 행은 값과 스키마의 키 순서가 같아 전과 글자 하나 다르지 않다
    - **값도 `default` 도 없는 칸은 만들지 않는다.** 지어내지 않는다. 비밀값 칸의 기본값도 다른 값처럼 가린다(§4.1)
    - 기본값에서 온 칸을 따로 표시하지 않는다 — 그 실행이 실제로 쓴 값이다
    - 값 글자는 증적과 화면이 갈린다 — 증적은 값을 그대로 적고(참거짓은 `true` · `false`, 아래 §8.4 견본의 「기대 true」 · 객체와 배열은 JSON 한 줄 — 2026-10-17 AUT-F3-23), 화면은 `예` · `아니오` 로 적는다
    - **이미 만든 증적 문서 파일은 안 바뀐다.** 저장된 PDF · 엑셀 · HTML 은 새로 뽑아야 기본값이 보인다.
      스키마를 박제하기 전 행(아래 「박제 이전에 쌓인 행」)은 `default` 가 없어 새로 뽑아도 「없음」이다
    - 서버(`reporting/collect.ts`)와 화면(`web/mask.ts`)이 같은 규칙을 따로 갖는다 — 컨텍스트가 달라 import 하지 않는다. 두 검사가 같은 입력 · 같은 순서를 쓴다.
      다만 확인 값 · 사유에 되비친 비밀 글자는 실행 조회 응답과 같은 `execution/trial.ts` 의 `항목비밀` 로 가린다(2026-10-12 · 공통/2 §4.1)
  - **박제 이전에 쌓인 행에는 이 원칙이 성립하지 않는다.** 컬럼을 더하기 전 실행은 라벨도 저장소 주소도 비어 있다.
    빈 값은 지어내지 말고 화면과 문서에 `기록 없음`으로 적는다
  - **라벨을 고치지 못하게 막지는 않는다.** "설명 문구는 절대 수정 금지" 같은 규율에 기대는 구조를 만들지 않기
    위해서다. 구조가 막아 주므로 고쳐도 과거 증적은 안전하다. 다만 라벨은 화면·문서·검수자의 기억이 모두 걸린
    문구이므로 **함부로 고치지 않는다**는 원칙은 남긴다
  - 증적 문서 머리말에는 **서비스 이름과 테스트 저장소 주소**를 적는다. "무엇을 시험한 것인가"가 문서에
    남아야 한다 (§8.4)
- 산출물 2종
  - **증적 문서**: 어떤 형식으로 내는지는 **§8.4가 정본이다.** HTML 생성 → PDF 변환,
    엑셀은 같은 데이터를 표로 따로 편다.
    PDF 변환은 admin이 Playwright의 `page.pdf()`로 직접 한다 (2026-09-16 결정).
    그래서 admin 이미지도 Playwright 공식 이미지에서 시작한다 (§9)
  - **지표**: Grafana가 Postgres를 직접 조회. 별도 시계열 DB 없음

#### 실패 요구사항 — 실패를 요구로 모은다 (2026-10-10 · 2026-10-11 PRD-F5-03)

케이스 이름만으로는 무엇이 실패했는지 모른다. 실패를 표준 기획서 요구로 모아 보인다. 표준 기획서 · 지도는 [작성.md](작성.md) §3.6 「★ 표준 기획서」가 정본이다.
**이 절이 정본이다** — 실행 §8.3 결과 화면 표 · 작성 §3.6 「목록 · 리포트 · E2E 에 맥락」은 여기를 가리킨다.
화면은 시안 A 「요약 바로 아래 한 칸」이었다(2026-10-11 시작 질문 — B 「요구로 묶어 보기」 · C 「옆 칸」 중 사용자가 A). 그 칸은 2026-10-19 ⑫ 에 뺐고 지금은 카드의 「관련 요구사항」 줄만 남았다.
화면 문구는 「실패 요구사항」 · 「실패 케이스」 · 「관련 요구사항」이다 — 명세 첫 판의 「깨진 요구」를 시안에서 보고 사용자가 「깨진 이런 단어들이 거슬린다」(2026-10-11).

- **요약 띠 바로 아래 「실패 요구사항 N건」 칸 — 2026-10-19 ⑫ 에 뺐다** (사용자 · 점검 2.1). 아래 카드의 「관련 요구사항」 줄과 같은 내용이 두 번 나왔다.
  재료였던 insights 의 `실패요구들` 도 지운다(같은 날 사용자 결정 — 읽는 곳이 없는 계산을 남기지 않는다). 아래는 뺀 칸의 옛 규칙이다.

  **BTS 연결 프로젝트는 이 줄이 「BTS DM-12 에서 확인 중」과 이슈 고리다**(2026-10-31 BTS-F1-01) — 「화면이 맞음으로 바꾸기」가 없고 `run_case_bug` 에 쓰지 않는다. 등록을 그만뒀으면 「BTS 등록 실패 · 까닭」 + [다시 보내기]. 정본은 [BTS.md](BTS.md) §3.12 「판정은 BTS 에서」 · §8.15 「실행 결과 실패 카드」
  **「화면이 맞음으로 바꾸기」는 누르면 한 번 더 묻는다**(점검 2.10 · 2.11) — AI 작성 요청을 바로 세운다. 확인 창은 「아니오」 · 「화면이 맞음」 둘이다(앞 판은 두 버튼 다 물었고 「버그」 창은 나중에 바꿀 수 있다고 적었다)
  - 「화면이 맞음」 — 그 케이스가 덮는 요구를 화면 기준으로 고쳐 쓰는 작성 요청을 세운다(표준 기획서 새 판 · 케이스 다시 작성 · PR 하나).
    사람이 화면이 맞다고 판정했으므로 고친 항목은 `확정` 이고 사람이 고친 것으로 친다(`byPerson`) — 다음 옮기기가 옛 문서 문장으로 되돌리지 않는다.

### 8.4 항목 상세 — 명세 기반 포맷
```
AUTH-002  유효한 이메일과 비밀번호로 로그인하면 토큰이 발급된다   [모바일]  [FAIL]

사전조건   · 가입 완료된 사용자 계정이 존재한다
           · 계정이 잠금 상태가 아니다

입력       아이디      testuser
           비밀번호    ********

기대 결과  토큰이 발급된다   true

시험 절차
  1. 로그인 API를 호출한다                                    PASS  (312ms)
       ✓ 응답 코드가 정상이다          기대 200      실제 200
  2. 토큰을 검증한다                                          FAIL  (88ms)
       ✗ 토큰이 발급된다               기대 true     실제 false

       [스크린샷 썸네일 — 클릭 시 원본]

       ▸ 실패 지점 코드                                    (접힌 상태가 기본)
           18  const body = await res.json();
           19  await verify('토큰이 발급된다', !!body.token, expected.hasToken);
           20  await verify('유효기간이 3600초다', body.expiresIn, 3600);
```

스크린샷은 실패한 검증 문장 바로 아래에 둔다. 스텝 헤더가 아니라 문장 아래다.
어느 확인에서 깨졌는지와 그때 화면이 나란히 붙어야 의미가 있다.
실행을 멈추게 한 검증 문장(`blocker`)에는 옆에 `실행 중단`을 표시한다. 그 뒤 절차가 왜 없는지 설명이 필요하다.

**코드 뷰**는 실패한 스텝에만, 접힌 상태로, 상세 맨 아래가 아니라 해당 스텝 안에 둔다.
이 플랫폼의 전제는 "코드를 몰라도 쓴다"이므로 기본 노출은 하지 않는다.
증적 문서에는 코드와 `httpTrace`를 넣지 않는다 — 스크린샷만 들어간다.
**예외는 둘이다 — E2E 증적의 「무엇이 대체됐다」 한 줄과 앱 항목의 「팜 기록」 한 줄(아래)**. 앞엣것은 2026-09-28, 아래 「E2E 시나리오 증적」이다.
막은 것은 **요청·응답 원문을 통째로 붙이는 것**이고(서류가 개발자 로그가 된다), 여는 것은 **주소 무늬와 응답 코드 한 줄**이다.
**원문(본문·머리)은 여전히 안 넣는다.** 이 구분을 지우고 원문까지 넓히지 않는다.
**디바이스 팜의 화면 영상 · logcat 은 문서에 못 넣는다** (2026-10-20 APP-F1-12) — 받아 둔 앱 항목은 시험 절차 뒤에 「팜 기록」 한 줄만 둔다
(`화면 영상 2개 · logcat.txt — 실행 화면의 이 항목에서 받는다`). 파일은 실행 화면의 실패 카드 · 항목 상세에서 본다(실행 §7 항목 상세 `farm` · 「팜 증적 원본」).
러너가 실행이 끝난 뒤에 받으므로 끝나자마자 만든 문서에는 이 줄이 빠질 수 있다 — 문서는 만든 때의 것으로 남는다(§3.3) 받는 규칙은 도메인/러너 §5.2 「디바이스 팜 접속 방식」
**세 번째 예외 — 종류 「API」 애플리케이션 케이스는 절차마다 요청 · 응답 원문을 접어 넣는다** (2026-10-20 사용자 · API-F1-01). 화면이 없어 원문이 유일한 증거다.
kit 이 이미 가린 원문만 넣고, 모양 확인 줄을 확인 문장 아래 따로 둔다. 무엇을 어느 형식에 어떻게 넣는지는 [API.md](API.md) §3.8 「리포트 — 원문을 접어 넣는다」가 정본이다. 화면 케이스(웹 · 앱)는 위 규칙 그대로다.

**화면의 상세 아래에 「값 바꿔 재실행」을 둔다** (2026-10-09 바뀜, UI 개편 묶음 4). 누르면 그 항목에서 쓴 값으로 채운 실행 창(실행 §8.10)이 열린다 —
앞 판은 한 건짜리 실행 설정 화면으로 옮겨 가 값을 다시 적어야 했다. **비밀값 칸은 비워서 연다** — 이 응답은 비밀값을 `********` 로 가려 주므로(공통/2 §4.1) 그대로 채우면 별표가 비밀번호로 나간다.
그 항목 서비스의 `(실행, write)` 일 때만 보인다. 증적 문서에는 없다 — 화면에서만 하는 일이다.

**화면의 항목 상세는 위에 실행 줄을 둔다** (2026-10-19 ⑫ · 점검 3.2 · 3.4 · 3.5 — 증적 문서에는 없다, 화면에서만 하는 일이다). 항목 하나만 보면 같은 실행의 다른 실패로 가는 길도, 판정을 남길 자리도 없었다.
- 머리 아래 한 줄 — 반복 실행이면 `2/5회차`, 이 실행의 실패가 있으면 `← 이전 실패 · 실패 12건 중 3번째 · 다음 실패 →`(케이스 · 디바이스마다 처음 깨진 항목을 돌린 차례로 잇는다. 이 항목이 실패가 아니면 순서 번호 없이 앞뒤 실패로만 간다), 그 줄 끝에 `리포트 생성` 단추(2026-10-20 — 앞 판은 형식별 증적 만들기 단추). 리포트 단추 · 안내 · 만든 문서 줄은 결과 화면 머리와 같은 부품이다(실행.md §8.3) — 실행 `write` 부터 만들기, 받기는 `read`
- 이 항목이 실패이고 실행이 끝났으면 그 케이스의 `관련 요구사항` 줄과 `판정`(화면이 맞음 · 버그) 줄을 결과 화면의 실패 카드와 같은 부품으로 단다(2026-10-26 — 판정 버튼은 결정 목록으로 옮기고 판정 한 줄 · 고리만 남는다 · 위 「실패 요구사항」). 재료는 `GET /api/runs/:runId/failures` 의 카드인데 통로에 케이스 조건이 없어 쪽을 넘기며 찾는다 — 실패가 수백 건이면 요청이 쪽 수만큼 늘어난다(느려지면 통로에 `tcId` 조건을 연다). 못 찾으면 이 두 줄만 빠지고 항목 상세는 선다
- 머리의 `이력 <번호>` 는 뺀다 — `history_id` 는 내부 번호라 사용자가 쓸 데가 없다(결과 줄 주소에는 그대로 쓰인다). 절차 소요는 다른 화면처럼 초로 적는다(`0.09초`, 앞 판은 `88ms`)
- 결과 화면의 `상세` · 판정 고리는 **깨진 회차의 항목**으로 간다. 앞 판은 늘 첫 디바이스의 첫 회차로 가서 반복 실행에서 통과한 회차를 보게 됐다

증적 문서는 **실행(run) 단위로 1부**다. 항목(`history_id`)마다 위 블록이 하나씩 문서에 남고,
디바이스가 2개인 케이스는 디바이스별로 2번 나온다. 화면의 상세는 항목 1건, 문서는 항목 전부 — 블록 모양은 같다.
반복 실행한 케이스는 회차마다 한 블록씩 나온다. 회차 번호를 블록 머리에 적는다.
블록을 어디에 두는지는 바로 아래 절이 정한다 — 블록 머리는 디바이스 · 회차 · 판정 · 소요 · 사유 한 줄이고, TC ID · 케이스 이름은 카드 · 줄 · 부록 머리가 케이스마다 한 번 적는다.

#### 증적 문서는 요약 띠 → 실패 카드 → 통과 · 미실행 줄이다 (2026-10-12 · 진행판 WEB-F3-10)

리포트 화면과 증적은 같은 증거 카드 C 양식이다(2026-10-07 사용자 「pdf도 c와 동일한 양식으로」 · DESIGN.md 「컨셉」).
화면은 PR #175 에서 바뀌었고 무엇이 카드에 드는지는 [실행.md](실행.md) §8.3 「결과 화면은 요약 띠 → 실패 카드 → 통과 줄이다」가 정본이다. **이 절은 증적이 화면과 다른 자리만 적는다.**

| 차례 | 무엇 | 규칙 |
|---|---|---|
| 1 | **머리말** | 아래 「증적 문서 머리말」 |
| 2 | **요약 띠** | 통과율 · 「실패 N건」 · 「항목 N건 중 M건 통과」 · 판정 한 줄(아래 머리말 절). 숫자는 화면 요약 띠와 같다 — 다만 「실패 N건」은 항목 수다. 화면 요약 띠의 큰 숫자는 2026-10-19 ⑫ 부터 「실패 케이스 N건」(케이스 수 · 실행 §8.3)이라 반복 · 여러 디바이스 실행에서는 두 수가 다르다. 증적 글자를 바꾸는 것은 이번 결정 밖이다 |
| 3 | **실패 카드** | 실패가 하나라도 있는 케이스마다 한 장. 깨진 디바이스마다 **처음 실패한 회차** 블록을 펼치고 회차가 여럿이면 「N회 중 M회 실패」. 나머지 회차와 그 케이스의 통과 · 미실행 디바이스는 카드 안 **접힌 줄**(블록 머리 한 줄). 실패가 없으면 카드 대신 「실패한 케이스가 없습니다」 한 줄 |
| 4 | **통과 · 미실행 줄** | 실패가 없는 케이스마다 한 줄 — 판정 · TC ID · 이름 · 디바이스마다 판정(회차가 여럿이면 「PC 3/3 통과」) · 미실행 사유 · 미확정 사유 |
| 5 | **E2E 요약** (2026-10-16 PR #277) | 아래 「E2E 시나리오 증적」의 전체 증적 요약. 그 서비스에 치우지 않은 시나리오가 없으면 절을 그리지 않는다 |
| 6 | **부록** (PDF 만) | 접힌 줄의 블록을 케이스마다 모은다. 새 쪽에서 시작한다 |

- **접힌 줄은 형식마다 다르게 편다** — HTML 은 그 자리에서 펼치고(`details`), PDF 는 줄이 **부록의 그 자리로 가는 고리**다(줄 끝에 「부록에서 보기」). 닫힌 `details` 는 인쇄되지 않아 PDF 에서 펼침을 쓸 수 없다.
  어느 형식이든 **모든 항목 · 모든 회차가 블록으로 문서에 남는다** — 화면은 「나머지 회차는 상세에서」지만 서류에는 상세 화면이 없다(PR #175 계획 검토 주의 13 의 「카드는 처음 실패 회차만인데 §8.4 는 회차마다 블록」을 이렇게 풀었다, 2026-10-12 시작 질문)
- **차례는 케이스 번호 차례다** — 카드와 줄 모두. 화면 카드는 회귀 실패를 먼저 세우지만 그 변화는 문서에 안 넣는다(바로 아래 줄)
- **넣지 않는 것** — 최근 흐름 막대 · 직전 실행 대비(회귀 실패 · 기존 실패 · 해결 글자) · 실패 요구사항 칸과 「화면이 맞음 / 버그」(위 「실패 요구사항」) · 판정별 보기 · 「통과 케이스로」 건너뛰기 · 「상세」 고리.
  앞의 셋은 **다른 실행이나 지금 지도로 세는 값**이라 같은 실행의 증적을 반년 뒤에 뽑으면 글자가 달라진다(위 §3.3 「증적 재현」). 뒤의 셋은 화면에서 누르는 것이다.
  다른 실행을 읽는데도 넣는 것은 E2E 요약 하나다 — 예외의 정본은 §3.3 「증적 재현」
- **같은 실패를 한 칸으로 묶지 않는다** — 화면은 입력 · 절차 · 확인이 다 같은 디바이스들을 「PC · 모바일」 한 칸으로 그리지만(실행 §8.3), 문서는 디바이스마다 따로 그린다. 서류는 디바이스마다 증거가 따로 서 있는 쪽이 대조하기 쉽다(2026-10-12 시작 질문)
- 코드는 `apps/admin/src/reporting/html.ts`(배치) · `htmlItem.ts`(블록) · `htmlStyle.ts`(글꼴 · 종이 색)

#### 다시 실행이 붙은 실행 (2026-10-30 WEB-F7-02)

한 건 실행이 붙은 실행(규칙의 정본은 [실행.md](실행.md) §3.2 「★ 한 건 실행은 묶음 실행에 붙는다」)의 증적은 **지금 결과로 쓰고 원래 결과를 지우지 않는다** — 서류에서 「처음에는 깨졌다」가 사라지면 기록이 아니다.

- **요약 띠 · 카드 · 줄은 지금 결과다** — 다시 돌려 통과한 케이스는 실패 카드가 아니라 통과 줄에 선다. 화면(실행 §8.3 「한 건 실행이 붙은 실행」)과 같다
- **덮인 디바이스는 블록 머리에 「다시 실행 · <시각> · <실행자> · 원래 결과 <판정>」을 적고, 블록은 다시 돈 항목이다**
- **원래 항목은 그 디바이스의 접힌 줄 「원래 결과」로 남는다** — HTML 은 그 자리 펼침, PDF 는 부록이다(위 「접힌 줄은 형식마다 다르게 편다」 그대로). 위 「모든 항목 · 모든 회차가 블록으로 문서에 남는다」를 지킨다
- **머리말 판정 한 줄 끝에 「다시 실행 N건 포함 · 마지막 <시각>」** 을 붙인다(아래 「증적 문서 머리말」). N 은 덮인 항목 수, 시각은 그중 가장 늦게 끝난 것이다. 없으면 붙이지 않는다
- **엑셀은 두 항목을 다 행으로 펴고 맨 끝 「다시 실행」 칸으로 가른다** — 아래 「엑셀 표 모양」
- 붙지 않은 한 건 실행은 증적이 없다 — 실행으로 서지 않아 「리포트 생성」 단추가 놓일 실행 화면이 없다. 케이스 한 건짜리 증적이 필요하면 반복 2 이상으로 걸어 새 실행으로 만든다

#### 증적 문서 머리말 (2026-09-16 결정)

문서 맨 앞에 **서비스 이름**과 **테스트 저장소 주소**를 적는다.
그 아래에 실행 제목·종류·실행 시각·실행자·대상 서버와 주소를 적는다.
- **종류는 사람 말로 적는다** — 「UI 테스트」 · 「기능 테스트」 (2026-10-02 PR #131). 실행 하나에 한 종류다(공통/4-데이터모델 「실행 종류」)
- **앱 항목이 있는 실행은 「기기」 줄을 더한다** (2026-10-19 APP-F1-05 · 아래 계약 블록) — `SM-G996N · Android 14 · 앱 1.4.2` 꼴로 그 실행의 앱 항목이 쓴 폰 · 앱 판을 겹치지 않게 모아 ` / ` 로 잇는다.
  못 읽은 칸은 `모델 모름` · `판 모름` 으로 적는다 — 빈칸이면 「없는 판」으로 읽힌다. 브라우저 실행에는 줄이 없다.
  케이스 실행은 이 값만 실행이 아니라 **항목에 박제된 값**(`run_item.device`)을 읽는다 — 폰은 항목마다 연결을 새로 연다. 읽는 법은 도메인/러너 §5.2 「기기 정보」
  **E2E 증적은 앱 · 게임 단계가 있는 시나리오만 같은 꼴로 한 줄이다** (2026-10-29 E2E-F3-04 사용자) — 폰 연결이 시나리오에 하나라 실행에 박제된 한 벌(`test_run.device`)을 읽는다(도메인/시나리오 §3.7 결정 16 「결과」). 웹만의 시나리오에는 줄이 없다.

```
[계약 변경 필요]
대상:    ExecuteResponse(packages/kit/src/types.ts) · DeviceInfo · 러너 POST /execute 응답 · DB run_item.device
현재:    증적에 어느 폰 · 어느 앱 판으로 돌렸는지 남지 않는다
제안:    ExecuteResponse.device?: { model, osVersion, appVersion }(android 만 · 못 읽은 칸 null) · run_item.device JSONB NULL · 증적 머리 「기기」 줄 · 엑셀 맨 끝 「기기」 칸

상태:    반영 완료 (2026-10-19, db/migrations/20261019000003_run_item_device.sql · packages/kit/src/runtime/app.ts · apps/admin/src/reporting/collect.ts — APP-F1-05)
```

- 이 값들은(위 케이스 실행의 「기기」 줄은 빼고) 한 번의 실행 전체에 걸린 사실이라 **실행에 박제된 값**을 읽는다 (§6 `test_run`). 항목마다 반복될 값이 아니다
- 저장소 주소가 없으면 "무엇을 시험한 것인가"가 문서에 남지 않는다. 서비스마다 다른 저장소를 보므로
  문서만 떼어 놓으면 알아낼 방법이 없다
- 서비스 이름은 **실행 시점 이름**이다 (§6 `test_run.service_name`). 설정에서 이름을 고쳐도
  과거 문서는 그때 이름 그대로여야 한다. 지금 이름을 읽어 오면 반년 전 증적이 조용히 바뀐다
- 실행자 이름이 비어 있으면 `실행자 미상 (인증 도입 이전)`, 정기 실행이면 `스케줄러`로 적는다 (§3.5)
- **판정 한 줄을 적는다** (2026-09-26 · 2026-10-12 부터 머리말 칸이 아니라 바로 아래 요약 띠에) — `통과 4 · 실패 2 · 미실행 0 · 그중 미확정 2건`.
  **항목 행 하나가 하나**이고 회차를 접지 않는다(실행 결과 화면의 수와 같다). 통과 · 실패 · 미실행은 미확정까지 세고 0 도 적는다.
  「그중 미확정 N건」은 미확정이 있을 때만 붙는다 — 꼴은 [실행.md](실행.md) §3.2 「미확정 항목도 그대로 센다」가 정본이고, 아래 「미확정 항목은 꼬리표로 보인다」가 증적 쪽 규칙이다.
  한 건 실행이 붙은 실행은 수가 지금 결과이고 끝에 「다시 실행 N건 포함 · 마지막 <시각>」이 붙는다(2026-10-30 — 위 「다시 실행이 붙은 실행」)

#### 미확정 항목은 꼬리표로 보인다 (2026-09-25 · 2026-10-11 PRD-F4-02 에서 묶음을 뺐다)

미확정이 무엇인지는 [작성.md](작성.md) §3.6 「★ 표준 기획서」 「미확정」, 세는 규칙은
[실행.md](실행.md) §3.2 「미확정 항목도 그대로 센다」가 정본이다. 여기는 증적에 어떻게 들어가는지만 적는다.

- **요약 띠는 미확정까지 센 판정 한 줄에 「그중 미확정 N건」을 붙인다**(위 「판정 한 줄」). 미확정이 없으면 붙이지 않는다
- **미확정 케이스는 제자리에 둔다.** 따로 묶지 않고 실패면 카드, 아니면 케이스 번호 차례의 줄이다(위 「증적 문서는 요약 띠 → 실패 카드 → 통과 · 미실행 줄이다」). 카드 머리 · 줄 · 부록 머리에 `미확정 · <사유 한 문장>` 을 붙인다. 블록 모양은 위 §8.4 그대로다
- 판정과 사유는 **`run_item` 에 박제된 값**을 읽는다 (`run_item.unconfirmed`). 위 §3.3 의 「리포팅은 `test_case`를 읽지 않는다」가
  여기서도 같다 — 확인 필요 항목이 확정된 뒤 옛 실행의 증적을 다시 뽑아도 그날의 미확정 꼬리표가 그대로 나와야 한다
- **아래 「내는 형식」 표의 모든 형식에 같다.** 엑셀은 아래 표 모양의 `미확정 사유` 칸이 꼬리표다 — 비면 확정 항목이다
- **뒤집은 판단** — 앞 판은 통과 · 실패 · 미실행을 확정 항목만 세고, 본문에 「미확정 — 기획 답 대기」 묶음을 따로 두었다. 숫자를 가르지 않게 된 까닭은 [작성.md](작성.md) §3.6 「미확정」 「뒤집은 판단」

#### E2E 시나리오 증적 (2026-09-28)

시나리오가 무엇인지는 [시나리오.md](시나리오.md) §3.7 이 정본이다. 여기는 증적에 어떻게 들어가는지만 적는다.

**전체 증적에는 요약만, 상세는 따로 받는다.** 한 파일로 합치면 분량이 두 배가 되고 같은 케이스가 두 번 나와
「어느 것이 진짜인가」를 묻게 된다.

| | 어디서 만드나 | 무엇이 |
|---|---|---|
| **전체 증적**(케이스 실행) | 지금처럼 실행 결과 목록의 RUN 머리 | 통과 · 미실행 줄 뒤에 **E2E 요약**(§8.4 「증적 문서는 요약 띠 → …」 차례 표 5) — 시나리오당 한 줄(시각 · 판정 · 멈춘 단계 · 미확정) |
| **E2E 증적**(시나리오 실행) | 시나리오 실행 결과 머리의 증적 칸 — 케이스 결과와 같은 `리포트 생성` 메뉴 (아래 「증적 문서 만들기·받기」) | 부품별 절차 · 판정 · 스크린샷 전부 |

**E2E 요약의 출처는 그 서비스의 활성 시나리오마다 「마지막으로 끝난 실행」이다.** 케이스 실행 안에는 시나리오가 없어서다.
- **줄마다 그 실행의 시각을 적는다.** 요구사항 표와 다른 시점의 결과라 날짜가 없으면 같은 실행의 일부로 읽힌다
- **한 번도 안 돌린 시나리오는 `실행 이력 없음` 으로 적는다.** 빼면 시나리오가 있는지조차 서류에서 사라진다
- **요약 마지막 줄은 `케이스 판정은 위 카드와 줄이 정본이다` 다** (2026-10-12 — C 양식에는 요구사항별 표가 없어 앞 판의 「요구사항 판정은 위 표가 정본이다」를 바꿨다)
- **「끝난」은 도는 중이 아닌 것이다** — 멈춘(`ABORTED`) 실행도 끝난 것으로 친다. 더 나중 실행이 아직 돌면 그 앞의 끝난 실행을 읽는다
- **엑셀에는 안 넣는다** (2026-10-16 시작 질문) — 엑셀은 한 행 = 한 검증 문장이라 요약 줄이 들 칸이 없다. PDF · HTML 만이다
- **박제 원칙과 부딪치지 않게 한다** — 요약은 **증적을 만든 그 시점**의 마지막 실행을 읽어 문서에 굳힌다.
  같은 케이스 실행의 증적을 나중에 다시 뽑으면 요약이 달라질 수 있다. 그래서 요약 머리에 **「이 요약은 문서를 만든 때 기준이다」**를 적는다

**E2E 증적의 모양 — 기존 증적과 같은 판에 부품 층이 하나 더 있다.** 같은 글꼴·같은 토큰이다.
**증적에 찍는 글자는 결과 화면과 같다** — 명세 용어와 화면 글자의 대응은 도메인/시나리오 §8.11 「화면 글자」 표가 정본이다(부품은 `단계`, 이어 주기는 `값 연결` 따위, 2026-10-06 사용자).

```
시나리오 SC-002  결제 흐름  v3   ❌ FAIL
 └ 1단계  케이스 PAY-001  로그인         ✅
     └ 절차 · 판정 · 스크린샷 (위 §8.4 블록 그대로)
 └ 2단계  모킹  /api/pg/**  →  200 (실제 서버 응답이 아님)
 └ 3단계  케이스 PAY-004  결제            ❌   ▎모킹 구간
     건너뜀 · 사전 단계 「로그인」 — 1번에서 이미 실행
     값 주입 · orderId = 812 ← 1번
 └ 4단계  케이스 PAY-007  영수증          – 실행 안 됨
 테스트 데이터 정리 · 마지막에 실행 DELETE /api/orders/812 → 204 (1번이 미룸)
```

- **케이스가 아닌 부품도 자리가 있다** — 어느 것들인지는 시나리오 §3.7 「부품」 표가 든다. 여기 목록을 옮겨 적지 않는다
- **모킹 표시** — 모킹 부품은 `<urlPattern> → <status> (실제 서버 응답이 아님)` 한 줄, 그 모킹이 걸린 동안의 부품에는
  **「모킹 구간」 표시**를 붙인다(`scenario_run_part.mocks`). 안 넣으면 가짜 응답으로 통과한 것이 **진짜로 읽힌다** — 검수 서류로서 치명적이다
- **API 부품** — `<메서드> <경로> → <기대 응답 코드>` 한 줄(결과 화면 카드와 같은 글자). 실패하면 실제 응답 코드는 「실패 사유」 줄에 나온다. 본문은 안 넣는다(위 예외의 범위)
- **건너뛴 준비** — 단계에 「건너뜀」 줄을 두고 결과 화면과 같은 글자(`사전 단계 「<절차 제목>」 — N번에서 이미 실행`, 글자의 정본은 시나리오 §8.11 「화면 글자」 표)로 적는다. 절차 목록에는 `skipped` 절차를 「건너뜀」으로 적는다.
  안 붙이면 이 케이스가 준비까지 한 것으로 읽힌다. 확인 절차는 늘 돌았으므로 그 판정은 그대로 적는다
- **안 돈 부품** — `실행 안 됨` 한 줄. 절차를 그리지 않는다
- **이어 주기** (2026-10-06, 시나리오 §3.7 결정 12) — 부품마다 건 것을 한 줄씩 적는다. `이전 응답 재사용 · POST /api/posts ← 2번` · `요청 차단 · DELETE /api/cart (서버에 안 보냄)` ·
  `수정 요청으로 변경 · POST /api/posts → PUT /api/posts/812` · `값 주입 · postId = 812 ← 2번`. **모킹 표시와 같은 까닭이다** — 안 적으면 꾸민 응답으로 통과한 것이 진짜로 읽힌다.
  비밀 칸에 꽂은 값은 `********` 로 적는다(공통/2-명세선언 §4.1) — 입력 칸을 가리는 규칙과 같다.
  넘겨받기를 끈 부품은 머리에 `단독 실행`
- **미확정** (2026-10-06 사용자) — 미확정 부품과 시나리오 머리에 `미확정`(`scenario_run_part.unconfirmed` — 2026-10-11 부터 머리도 같은 글. 앞 판은 `미확정 포함`). 전체 증적의 E2E 요약 줄에도 붙인다. 꼬리표일 뿐 판정은 그대로다 — 미확정이 섞인 통과도 통과다(2026-10-11 PRD-F4-02 · 실행 §3.2)
- **끝에 보낸 뒷정리** — 마지막 부품 뒤에 `테스트 데이터 정리 · 마지막에 실행 <메서드> <주소> → <응답 코드> (N번이 미룸)`(2026-10-19 ⑫-11 — 화면 글자 표, 시나리오 §8.11) 한 줄씩. 못 보냈으면 그 오류. 판정에는 안 든다(시나리오 §3.7 결정 12)
- **형식은 아래 「내는 형식」 표 그대로다.** 엑셀은 한 행 = 한 검증 문장 모양에 **부품 칸이 앞에 하나 더** 붙는다(머리 `단계`).
  케이스가 아닌 단계 · 안 돈 단계 · 끝에 보낸 정리도 한 행씩 남기고, 모킹 구간 · 건너뛴 준비 · 값 연결은 그 단계 칸 안에 줄로 적는다 — 빼면 엑셀에서 꾸민 응답이 진짜로 읽힌다
- 판정과 부품은 **`scenario_run_part`·`scenario_run_step` 에 박제된 값**을 읽는다. 시나리오를 고친 뒤 옛 실행을 다시 뽑아도 그날 모양이 나와야 한다

**검사가 이 예외를 따라와야 한다** — `apps/admin/src/reporting/html.test.ts` 가 `httpTrace` 금지를 강제한다.
E2E 증적은 `htmlScenario.test.ts` 가 **원문(요청 · 응답 본문 · 코드)이 없음**을 보고 한 줄 표시만 허용한다(2026-10-16).

#### 증적 문서 만들기·받기 (2026-09-16 결정)

지금까지 증적 문서에 관한 문장만 있고 누를 것이 없었다.
증적은 실행 단위 1부이므로 버튼은 항목 상세가 아니라 **실행 결과 목록(§8.3)의 RUN 머리**에 둔다.

**화면 글자는 「리포트」다** (2026-10-20 ⑬-5 사용자 — 「증적 문서 만들기 버튼명 → 리포트 생성」). RUN 머리에 `리포트 생성 ▾` 단추 하나를 두고, 누르면 **형식마다 한 줄인 메뉴**가 열린다.
앞 판(2026-09-16 ~ 10-19)은 형식마다 단추(`PDF 만들기` · `엑셀 만들기` · `HTML 만들기`)가 머리에 늘어섰다 — 단추가 셋이라 머리가 붐볐다.
명세 · 코드 · DB 의 이름(증적 · `evidence_document`)과 문서 안 글자는 그대로다 — 바뀐 것은 화면 단추 · 메뉴 · 목록 머리(`리포트`) · 안내 · 실패 줄 글자뿐이다.
결과 머리 밖 화면 문장(대상 서버 안내 · 시나리오 화면 안내 · 오류 문장 · 서버가 실패 행에 남기는 사유 `리포트를 만들지 못했습니다`)도 같은 날 「리포트」로 맞췄다(사용자 「리포트로 맞춰」) — 화면 낱말 규칙은 공통/5-화면공통 §8 「화면 낱말은 하나로」 표가 정본이다. 리포트 파일 안 글자 · 내려받는 파일 이름은 그대로다.
메뉴 줄의 `{라벨}`은 아래 「내는 형식」 표의 이름이다 — 그 표가 정본이므로 개수를 여기 적지 않는다. 아래 상태는 **그 형식 하나에 대한 상태**다.

| 지금 상태 | 메뉴 줄 |
|----------|------|
| 실행이 진행 중 | 단추를 아예 그리지 않는다. 그 자리에 `실행이 끝나면 리포트를 만들 수 있습니다` 한 줄만 둔다 |
| 끝났고 문서가 없다 | `{라벨}` → `POST /api/runs/:runId/evidence` |
| 만드는 중 (`PENDING`) | `{라벨} 생성 중`으로 바꾸고 **그 형식만** 다시 눌리지 않게 한다. 머리 단추는 `리포트 생성 중` 이 된다 — 고르면 메뉴가 닫혀 무엇이 도는지 머리가 말해야 한다 |
| 실패했다 (`FAILED`) | `{라벨} 다시 생성` + 화면 줄로 `{라벨} 리포트를 만들지 못했습니다 — 사유` (**조사를 타지 않는 꼴로 적는다** — `{라벨} 를` 로 쓰면 `엑셀 를`·`HTML 를` 가 된다). 원문 오류를 그대로 쓰지 않는다 |
| 만들어졌다 (`READY`) | `{라벨} 다시 생성`. 만들어진 것은 아래 `리포트` 목록에 형식마다 가장 새 한 줄로 남는다 |

모든 형식이 만드는 중이면 머리 단추가 눌리지 않는다.

**누르면 끝난 뒤 바로 받아진다** (2026-10-19 ⑫ · 점검 2.18). 앞 판은 `만들기` 를 누른 뒤 아래 목록 줄의 `열기 ↗` · `받기` 를 한 번 더 눌러야 했다. 이제 `POST` 가 돌려준 문서 번호가 `READY` 가 되는 것을 화면이 보고(실행 결과가 2초마다 다시 묻는다) 그 문서를 내려받는다 —
새 창을 열지 않는 내려받기라 팝업 차단에 걸리지 않는다. `FAILED` 로 닫히면 받지 않고 위 표의 실패 줄이 선다. 목록 줄은 그대로 남아 다시 열 수 있다

**상태가 형식마다 따로인 이유는 DB 가 그렇게 막기 때문이다.** 부분 유일 인덱스가
`(run_id, format) WHERE status = 'PENDING'` 이라 (§6) PDF 는 다 만들어졌는데 엑셀은 만드는 중인
상황이 실제로 생긴다. 상태를 실행 단위로 하나만 두면 그 화면을 그릴 수 없다.

**「만드는 중」은 화면이 아니라 DB가 기억한다** (2026-09-17 결정).
`evidence_document.status`에 `PENDING`으로 행을 먼저 만들고, 같은 실행·같은 형식의 `PENDING`은
부분 유일 인덱스가 하나로 막는다 (§6). 화면 상태로만 막으면 **새로고침할 때마다 또 눌리고
문서 행이 쌓인다.** §3.3이 리포팅의 쓰기를 이 표로만 막아 둬서 상태를 둘 다른 자리도 없다.

#### 만든 문서는 목록으로 쌓고 새 창에서 본다 (2026-09-17 결정)

```
│  리포트                                 │
│  · 9월 15일 17:25 만듦 · 엑셀   [받기]  │
│  · 9월 15일 17:22 만듦 · PDF  [열기 ↗] │
│  · 9월 15일 17:20 만듦 · PDF  [열기 ↗] │
```

- **줄마다 형식을 적는다.** 받는 법이 형식마다 다르므로(`열기 ↗` / `받기`) 형식이 안 보이면
  같은 줄에 왜 다른 버튼이 붙는지 읽히지 않는다. **만드는 버튼은 여기가 아니라 위 RUN 머리에 있다** (§8.4 위)
- **받기 전에 볼 수 있어야 한다.** 화면의 `항목 상세`는 항목 **한 건**이고 증적 문서는 실행 **전체 한 부**다.
  앞 판의 명세대로면 사람은 **검수처에 내는 문서 전체를 한 번도 못 보고 낸다**
- **브라우저가 보여줄 수 있는 것만 `열기 ↗`다.** PDF·HTML 은 새 창으로 열고 저장은 거기서 한다.
  **엑셀은 브라우저가 못 연다 — `받기`로 내려받는다.** 버튼 글자가 형식에 따라 다른 이유가 이것이고,
  「열린다」고 해 놓고 파일이 떨어지면 사람이 어디로 갔는지 찾는다
- **형식마다 가장 새 한 줄만 둔다** (2026-10-19 ⑫ · 점검 2.18 — 앞 판은 `만든 것이 여럿이면 만든 시각과 함께 줄로 쌓는다`였다). 같은 실행의 증적은 언제 뽑아도 같은 문서(§3.3)라 누를 때마다 같은 줄이 쌓이는 것은 소음이었다.
  행은 DB 에 남고 화면이 형식별 마지막 `READY` 만 보인다. 앞 판이 쌓은 까닭(파일 이름 `(1)`·`(2)` 로는 어느 것이 최신인지 모른다)은 한 줄로 줄며 사라졌다
- `받기`는 **실행 `read`** 도 할 수 있고 `리포트 생성` 메뉴(`{라벨}` · `{라벨} 다시 생성`)는 **실행 `write`** 부터다 (§3.5).
  받는 것은 읽기이고 만드는 것은 서버에 파일을 남기는 쓰기다

#### 내는 형식 (2026-09-18 결정)

**이 표가 형식의 정본이다.** 골라 만드는 자리는 §8.4 위에서 정한
**실행 결과 목록(§8.3)의 RUN 머리**다 — 자리를 여기 다시 적지 않는다.
개수를 다른 곳에 적지 않는다 — 형식이 늘거나 줄면 여기만 고친다 (CLAUDE.md §2.7).

| 형식 | 누가 쓰나 | 버튼 | 무엇이 들어가나 |
|------|----------|------|----------------|
| **PDF** (기본) | 검수처에 낸다 | `열기 ↗` | §8.4 모양 그대로(C 양식 — 접힌 줄은 부록 고리). 스크린샷 포함 |
| **엑셀** (`XLSX`) | 사내에서 가공한다 | `받기` | 아래 표 모양. 스크린샷은 **경로만** |
| **HTML** | 브라우저에서 찾고 링크로 나눈다 | `열기 ↗` | PDF 와 같은 모양에 접힌 줄을 그 자리에서 펼친다(부록 없음). `Ctrl+F` 가 된다 — Chrome · Edge 는 접힌 줄 안 글자도 찾아 펼친다. 종이로 낼 때는 PDF 다(HTML 을 인쇄하면 접힌 줄이 빠진다) |

- 앞 판은 **PDF 하나**였고 HTML 은 「PDF 를 만드는 중간 산물」이라 내주지 않았다.
  **이미 만들고 있는 것을 감출 이유가 없다** — 주는 비용이 0 이고 긴 문서에서 글자를 찾을 수 있다
- **CSV·JSON·JUnit XML 은 넣지 않는다.** CSV 는 엑셀이 덮고(엑셀에서 「CSV로 저장」하면 된다),
  JSON 은 사람이 받을 물건이 아니며 API 가 이미 준다.
  JUnit XML 은 **이 플랫폼이 CI 리포터가 아니기 때문**이다 — §1 이 Playwright 기본 HTML 리포트를
  영구 제외한 것과 같은 이유다
- **형식이 늘어도 재현 원칙은 같다** (§3.3). 다만 그것은 **내용**이 같다는 뜻이다 —
  엑셀 파일 안에 들어가는 「만든 시각」 같은 메타데이터까지 같지는 않다. 그건 증적의 내용이 아니다
- **글꼴 파일은 증적의 입력이다. 이 줄이 정본이다.** PDF·HTML 은 글꼴을 이름으로 부르지 않고
  **파일을 문서 안에 담아** 나간다. 화면 번들은 다른 길로 같은 것을 한다 (공통/6-인프라 §9).
  이름만 부르면 admin 컨테이너에 한글 글꼴이 없어 다른 글꼴로 조용히 떨어지고 글자 모양과 줄바꿈이 통째로 달라진다.
  **그래서 글꼴 파일을 바꾸면 과거 실행의 증적을 다시 뽑았을 때 바이트가 달라진다** —
  §3.3 이 「오늘 뽑든 한 달 뒤에 뽑든 글자 하나까지 같다」를 요구하므로 글꼴 교체는 그 요구를 건드리는 변경이다
- 비밀값 칸은 어느 형식에서든 `********` 다 (§4.1)

#### 엑셀 표 모양 — 한 행 = 한 검증 문장 (2026-09-18 결정)

시트 하나. 머리행 고정. **가장 잘게 편다.**

```
실행    RUN · 실행일시 · 서비스 · 대상서버 · 주소 · 실행자
케이스  tcId · 케이스명 · 디바이스 · 회차 · 판정 · 소요(ms) · 미실행·판정불가 사유 · 미확정 사유 · 사전조건 · 입력값 · 기대값
절차    절차번호 · 절차명 · 절차판정 · 절차소요(ms)
검증    검증문장 · 기대 · 실제 · 판정 · 스크린샷경로
끝      종류 · 기기 · 팜 기록 · 다시 실행
```

- **`종류` 는 앞 묶음이 아니라 끝 묶음에 둔다** (2026-10-02 PR #131) — 실행 단위 값이라 앞 묶음에 들어갈 자리지만, 끼우면 이 엑셀을 칸 위치로 읽는 시트가 전부 한 칸씩 밀린다
- **`기기` 는 그 뒤다** (2026-10-19 APP-F1-05) — 그 항목의 폰 · 앱 판 한 줄(위 「증적 문서 머리말」의 꼴). 브라우저 항목은 빈칸이다. E2E 엑셀에는 없다
- **`팜 기록` 은 맨 끝이다** (2026-10-20 APP-F1-12) — §8.4 의 「팜 기록」 한 줄과 같은 글자다. 팜 증적을 받지 않은 항목은 빈칸이다. E2E 엑셀에는 없다
- **`다시 실행` 은 그 뒤다** (2026-10-30 WEB-F7-02 · 위 「다시 실행이 붙은 실행」) — 한 건 실행이 덮은 디바이스는 원래 항목과 다시 돈 항목을 둘 다 행으로 편다. 원래 항목 행은 `원래 결과`, 다시 돈 항목 행은 `다시 실행 · <시각> · <실행자>`, 그 밖은 빈칸이다.
  지금 결과만 세려면 `원래 결과` 행을 걸러 낸다. 앞 묶음 칸(`RUN` · `회차`)은 원래 실행 것을 반복한다 — 다시 돈 행도 그 실행의 행이다. E2E 엑셀에는 없다
- 새 칸은 늘 맨 끝에 붙인다 — 끼우면 칸 위치로 읽는 시트가 밀린다

- **상위 정보를 앞 칸에 반복한다.** 병합 셀을 쓰지 않는다 — 걸러 내기·피벗이 안 된다
- **왜 가장 잘게 펴나** — 잘게 편 것은 피벗으로 접을 수 있지만 굵게 편 것은 못 쪼갠다.
  검수처 양식이 무엇이든 여기서 **옮겨 담는 출발점**이 된다
- 스크린샷은 **경로만** 넣는다. 이미지를 박으면 파일이 무거워지고 열기 느려진다.
  이미지가 필요한 제출물은 PDF 다
- 검증 문장이 없는 절차(전부 건너뜀 등)도 **한 행을 남긴다.** 행이 없으면 절차가 없었던 것처럼 보인다
- 이미 만든 문서가 있어도 다시 만들 수 있다. **같은 실행의 증적은 언제 뽑아도 같은 문서가 나오므로**(§3.3 박제 규칙)
  다시 만들어도 내용이 달라지지 않는다. 만든 시각만 새로 적힌다(E2E 요약 절은 예외 — §3.3 「증적 재현」)
- 중단된 실행(`ABORTED`)도 만들 수 있다. 돌지 못한 항목은 미실행과 사유로 문서에 남는다.
  "여기까지 돌았고 나머지는 사람이 멈췄다"가 증적으로 성립한다
- **`미실행·판정불가 사유` 칸은 두 가지를 같이 싣는다**(예외로 깨진 `FAIL` 은 아래) — 아예 못 돈 항목의 사유와,
  돌았지만 판정을 못 낸 `NA` 항목의 사유다. 한쪽만 덮는 이름을 쓰면 나머지 한쪽이 이름 없는 칸에 들어간다.
  **칸 자리는 `판정`·`소요(ms)` 옆이다** — 사유는 **항목 단위**이고 행은 **검증 문장 단위**라
  검증 묶음에 두면 "이 검증 문장이 왜 안 돌았나"로 읽힌다. 한 항목이 여러 행이면 같은 사유가 반복되는데,
  위의 「상위 정보를 앞 칸에 반복한다」가 그것이다
- **확인 문장 없이 예외로 깨진 `FAIL` 도 이 칸에 오류 원문의 첫 줄을 싣는다** (2026-10-17 AUT-F3-23) — 항목 오류가 먼저고 없으면 절차 오류이며, 비밀 글자를 가린 뒤 120자에서 자르고 「…」를 붙인다.
  원문을 통째로 붙이지 않는 §8.4 「코드와 `httpTrace` 를 넣지 않는다」와 같은 까닭으로 첫 줄만 싣고, 실패한 확인 문장이 있으면 그 문장이 사유라 싣지 않는다.
  화면 실패 카드(실행 §8.3)와 견주기는 항목 오류만 본다 — 절차 오류로 넘어가는 것은 증적만이다(2026-10-19 ⑫ 의 카드 사람 말 한 줄 `failure.reason` 도 항목 오류만 본다 — 실행 §7 항목 상세). 케이스 증적만의 규칙이고 E2E 증적은 따로 적은 「실패 사유」 줄을 쓴다
- **응답 모양만 틀려 깨진 `FAIL`** (2026-10-20 API-F1-01) — 실패한 확인 문장이 없으면 첫 모양 문제를 싣는다. 화면 카드도 같다. 문장은 [API.md](API.md) §3.8 「응답 모양 확인」이 정본이다

### 8.5 대시보드 (Grafana)
평균 소요시간 / 최근 실행 목록 / 작성에 걸린 시간 / 작성 토큰 / 작성 커버리지.
**개편 뒤 (2026-10-07 게이트 1 사용자 결정)** — 테스트 결과를 보는 일(성공률 · 실패)은 앱 대시보드(아래 §8.12)가 맡고,
Grafana 는 소요 시간 · 작성 시간 · 토큰 같은 운영 지표를 맡는다. 그래서 **`성공률 추이`와 `실패 TOP 10 케이스` 두 패널을 뺐다** —
같은 숫자를 두 곳에 두면 한쪽이 먼저 어긋난다. 위치는 공통/5-화면공통 §8.
Postgres 데이터소스로 `run_item`을 직접 조회한다.
**한 건 실행(`test_run.origin = 'SINGLE'`)은 모든 실행 패널에서 뺀다** (2026-10-30 WEB-F7-02 · 실행.md §3.2) — 실행으로 서지 않는 기록이라 「최근 실행 목록」에 뜨면 안 되고, 실행 하나의 평균 소요시간이 한 건짜리로 흐려진다.
`run_item` 을 읽는 패널도 `test_run` 을 이어 `origin` 으로 거른다 — 실행 단위 패널만 거르면 한 대시보드 안에서 수가 어긋난다.
붙은 결과로 바꿔 끼우지도 않는다 — 판정은 앱 대시보드 몫이다(아래 개편 결정)
**실행 패널(평균 소요시간 · 최근 실행 목록)이 읽는 표는 `test_run`과 `run_item`뿐이다.** 대시보드 계정은 `test_run` 에만 표 단위 권한이 있고,
`run_item` 을 비롯한 다른 표는 **패널이 읽는 칸에만** 권한을 준다 — 작성 현황(아래)이 그렇게 섰고(2026-09-26), `run_item` 은 입력값 칸에 비밀번호 원문이 들어 2026-10-23 FIX-F1-04 에서 줄였다.
어느 칸을 여는지는 [데이터모델](../공통/4-데이터모델.md) §6 「대시보드 칸 권한」이 정본이다 (§6).
**성능 실행 추세 패널을 하나 더한다** (2026-10-21 · PERF-F1-06 반영). 실행마다 최대 동시 사용자 · 최대 TPS · 95% 응답시간 · 에러율을 잇는 선이고 `perf_run` 의 숫자 칸만 읽는다.
**판정은 싣지 않는다** — 위 2026-10-07 결정(테스트 결과는 앱, Grafana 는 운영 지표)을 그대로 따른다. 성능 판정 · 결과는 QA Hub 화면이 맡는다 — 정본은 [성능.md](성능.md) §3.9 「실행 · 결과」.

#### 남은 패널 점검 (2026-10-12 WEB-F3-09)

두 패널을 앱으로 옮긴 뒤 남은 다섯 패널을 다시 봤다. **판정(통과 · 실패 · 미실행)을 세는 패널은 없다.**

- `평균 소요시간` 은 측정치이고(아래 「접지 않는다」), `최근 실행 목록` 의 상태 칸은 실행이 도는지 끝났는지(`RUNNING` · `FINISHED` · `ABORTED`)이지 판정이 아니다. 나머지 셋은 아래 「작성 현황」이다
- **`작성 커버리지` 와 앱 「요구사항 커버리지」(§8.12)는 둘 다 남긴다** (2026-10-12 시작 질문 사용자). 같은 칸(`authoring_request.coverage_*`)을 읽고
  둘 다 **저장된 수를 그대로** 낸다. 성공률 패널을 뺀 까닭은 같은 접기 계산을 두 곳이 따로 해서였다 — 여기서 두 곳이 따로 하는 계산은 % 하나뿐이고 **둘 다 내림한다**(아래 「작성 커버리지」).
  고르는 것이 다르다 — 앱은 서비스마다 **마지막 성공 실행 하나**(지금 얼마나 덮였나), Grafana 는 30일 동안의 **실행 하나하나**(실패 · 중단 · 원장 없음까지)다.
  실행마다 빠짐이 몇 건이었는지 한 표로 보는 곳은 Grafana 뿐이다. 번호도 다르다 — Grafana 「번호」는 그 실행 자기 번호이고 앱 링크는 원본 요청 번호라, 재실행 · 이어서 작성 줄은 두 화면의 번호가 다르다
- 「가장 오래된 미확정」을 뺄 때 남았던 칸 권한 넷과 읽는 패널이 없던 `tokens_model` 을 이때 거뒀다 — 규칙은 [데이터모델](../공통/4-데이터모델.md) 「대시보드 칸 권한」

#### 반복 실행이 지표를 오염시키지 않게 한다 (2026-09-17 결정)

`run_item`을 그대로 세면 **불안정한 케이스를 20번 돌린 그 20행이 성공률 분모에 전부 들어간다.**
회차를 유일성 조건에 넣으면서(§6) 생긴 문제다.

- **세는 단위는 행이 아니라 `(실행, 케이스, 디바이스)` 하나다.** 회차는 그 안으로 접는다
- 접는 규칙은 §8.3의 회차 요약과 **같다** — 전 회차 통과해야 통과다.
  다섯 번 중 세 번 통과한 테스트는 믿을 수 없는 테스트이므로 통과로 세지 않는다
- 화면과 대시보드가 같은 규칙을 쓰면 「목록에서는 실패인데 그래프에서는 통과」가 생기지 않는다
- 정기 실행은 `repeat`를 1로 고정하지만(§9.2) 그것에 기대지 않는다.
  사람이 돌린 반복이 같은 기간에 섞여도 지표가 흔들리지 않아야 한다
- **접는 것은 판정을 세는 칸뿐이다** — 앱 대시보드(§8.12)의 통과율 · 일별 결과 · 히트맵 · 실패 유형이 접고(두 패널을 앱으로 옮긴 2026-10-07 이후 Grafana 에는 판정을 세는 패널이 없다),
  **Grafana `평균 소요시간`은 접지 않는다.** 소요시간은 판정이 아니라 **측정치**라서 회차 하나하나가 다 표본이고,
  접으면 표본이 줄어 평균이 덜 정확해진다. 판정은 반대다 — 회차를 그대로 세면 같은 케이스가 여러 번 세어진다
- **실패를 세는 조건은 `bool_or(status = 'FAIL')`이다.** 통과를 세는 `bool_and(status = 'PASS')`의
  반대로 실패를 세면 `NA`(미실행)까지 「통과 아님」으로 묶여 **한 번도 못 돈 케이스가 실패로 세어진다**(앱 대시보드 §8.12 의 히트맵 · 회귀 실패).
  §8.3이 미실행과 실패를 갈라 둔 것을 대시보드가 다시 뒤섞는 셈이고, 러너가 고장 난 것이 케이스 탓으로 보인다
- **판정을 세는 칸은 미확정 항목도 그대로 센다** (2026-10-11 PRD-F4-02 · 2026-10-07 부터 앱 대시보드 §8.12 의 칸). 규칙은 [실행.md](실행.md) §3.2 「미확정 항목도 그대로 센다」가 정본이다.
  앞 판(2026-09-25)은 `run_item.unconfirmed IS NULL` 로 미확정을 뺐다.
  판정 칸은 앱 대시보드가 플랫폼 계정으로 읽어 `grafana_ro` 권한과 상관없다(`run_item` 은 2026-10-23 부터 `grafana_ro` 에 칸 둘만 열린다)
- **시나리오 실행은 모든 패널에서 뺀다** (2026-09-28 · `test_run.kind IN ('UI','FN')` — 2026-10-02 PR #131 에서 `CASE` 를 둘로 갈랐다. 최근 실행 목록에는 「종류」 칸). 시나리오 결과는 `run_item` 에 안 들어가지만
  `최근 실행 목록`처럼 `test_run` 을 읽는 패널에는 섞인다 — 케이스 실행인 척 보인다. 규칙은 [시나리오.md](시나리오.md) §3.7 결정 10 이 정본이다

추이는 **정기 실행이 있어야 선이 된다** (2026-09-16 결정. 2026-10-07 부터 대상은 앱 대시보드 §8.12 의 통과율 · 일별 결과다 —
Grafana 성공률 패널을 앱으로 옮겼지만 판단은 그대로라 남긴다).
사람이 누를 때만 돌면 점 몇 개가 흩어질 뿐이라 추이가 아니고, 그 점은 품질이 아니라 근무 시간을 그린다.
거는 자리는 §9.2다. 테스트 대상이 아직 데모 사이트여도 켠다 — 지표의 내용보다 **장치가 도는지 검증**하는 것이 지금 목적이다.

#### 작성 현황 — 작성에 걸린 시간 · 작성 토큰 · 작성 커버리지 (2026-09-26 · 토큰 2026-09-27 · 커버리지 2026-09-30 · 가장 오래된 미확정은 2026-10-11 뺐다)

기획서를 넣고 초안 PR 이 나오기까지 얼마나 걸리는가를 본다.
판정을 세지 않으므로 위의 회차 접기와 상관없다.

- **가장 오래된 미확정** — **없앴다 (2026-10-11 PRD-F4-05, 칸 `unconfirmed_since` 와 함께)** — 나이는 「PRD 관리」 메뉴의 「확인 필요 N건 · 가장 오래된 것 N일째」가 보인다(2026-10-26 결정 목록 줄마다 「N일째」로 옮긴다 · 작성 §3.6 「★ 결정 목록」). 대시보드 계정에 기획서 글을 열지 않으려고 패널을 옮기지 않았다([작성.md](작성.md) §3.6 「★ 표준 기획서」 「미확정」). 앞 판은 서비스마다 꼬리표 미확정 건수와 가장 오래된 것의 나이(일)를 `test_case.unconfirmed_since` 로 셌다
- **작성에 걸린 시간** — 최근 30일(**끝난 시각** 기준)에 끝난 작성 요청(`AUTHOR` · `RERUN`)을 서비스 × 방식(보통 / 화면과 대조 / 재실행)으로 묶는다.
  칸은 성공(`DONE`) 수 · 실패(`FAILED`) 수 · **중단**(`STOPPED`, 2026-09-27) 수 · **대기** 중간값 · **작업** 중간값 · 작업 최대이고 단위는 분이다.
  **끝난 요청 = 성공 + 실패 + 중단**이다 — 「끝난」 한 칸으로 두면 무엇이 든 합계인지 읽는 사람이 갈린다
  - 대기 = 요청 행이 생긴 때 → 작성 에이전트가 집어 간 때. **자료 올리기와 대기줄에서 기다린 시간이 든다** — 제출 시각 칸은 없다
  - 작업 = 집어 간 때 → 끝난 때. 대조 요청은 초안 PR 뒤 원본 표시까지 마친 때가 끝이다(역기획서는 2026-10-10 PRD-F3-02 부터 안 만든다)
  - **실패 수를 같은 줄에 둔다.** 성공만 세면 시간초과로 실패한 느린 건이 빠져 중간값이 좋아 보인다. 시간 칸은 `DONE` 만 센다
  - 방식을 가르는 까닭 — 대조는 화면을 훑느라 훨씬 오래 걸려 섞으면 보통 요청이 느려진 것처럼 보인다.
    기획서 없이 화면만 훑는 요청도 대조 줄에 든다
  - **재실행(`RERUN`)은 따로 한 줄이다** (2026-10-13 PRD-F9-23) — 이어하기 · 다시 작성도 시간이 든다. ⑧ 일괄 시험에서 다시 돈 작성의 시간이 어디에도 안 보였다.
    보통 줄에 섞지 않는 까닭은 같은 자료를 다시 돈 것이라 섞으면 요청 하나를 두 번 세서다. 「작성 토큰」 · 「작성 커버리지」의 재실행 줄과 같다.
    앞 판(2026-09-28)은 같은 까닭으로 아예 세지 않았다
- **작성 토큰** (2026-09-27) — 최근 30일(**끝난 시각** 기준) 작성 요청이 쓴 토큰. 받는 법은 [작성.md](작성.md) §7 「토큰 사용량」
  - 줄은 서비스 × 방식(보통 / 화면과 대조 / 재실행) × 결과(성공 / **중단 · <이유>** / 끊김 / 그 밖 실패). 중단(`STOPPED`, 2026-09-27)을 **끊김보다 먼저** 가른다 —
    멈춘 요청은 결과 없이 끊겨 하한값이지만 까닭이 이미 있다. 이유별로 보면 시간초과 비율이 드러난다(`stop_reason` 칸을 연다). **재실행은 따로 한 줄**이다 —
    원본의 방식을 모르지만 토큰은 실제로 썼으므로 빼면 합계가 적게 나온다
  - 끊김은 `tokens_partial` 로 가른다 — 중단이 아닌데 결과 없이 끊긴 것이다. 시간초과는 「중단 · 시간초과」로, 자식이 일하다 죽은 것은 「중단 · 작성 중 끊김」(2026-09-28)으로 먼저 빠진다. 중단 이유 글은 도메인/작성 §7 이유 표와 같은 말이다. 둘 다 결과 없이 센 **하한값**이라 성공 줄과 섞으면 안 된다. 오류 글(`error`)은 대시보드에 열지 않는다
  - 칸은 실행 수 · **입력 · 출력 · 캐시 읽기 · 캐시 쓰기 각각의** 중간값과 합계 · **API 환산(청구 아님)** 합계와 비용이 있는 실행 수 (2026-09-29 사용자 — 넷을 합치지 않는다).
    한 줄이 **실행 하나**다 — 이어서 작성 · 다시 작성도 각각 센다(요청 번호는 하나여도 토큰은 실행마다 썼다, 도메인/작성 §7 「실행 기록」).
    넷을 가르는 까닭 — 긴 세션은 캐시 읽기가 대부분이라 합치면 줄일 자리가 안 보이고, 입력과 출력은 값이 달라 섞으면 비용을 못 가늠한다.
    환산 비용은 구독이라 청구액이 아니고, 끊긴 실행은 비용이 비어 합계가 적게 나온다 — 그래서 비용 있는 실행 수를 옆에 둔다
  - 사용량을 알리지 않은 실행(옛 요청 · claude 를 돌리기 전에 실패)은 세지 않는다 — 실행 수가 「작성에 걸린 시간」과 다를 수 있다
- **작성 커버리지** (2026-09-30) — 최근 30일(**끝난 시각** 기준) 작성 · 재실행 실행이 기획서 요구를 얼마나 케이스로 덮었나. 셈의 뜻은 [작성.md](작성.md) §3.6 「★ 원장」 「셈을 남긴다」
  - **한 줄이 실행 하나**다 — 최근 것부터 30줄. 뿌리(요청)로 묶지 않는다 — 묶으려면 `source_id` · `resume_from` 을 더 열어야 한다
  - 칸은 번호 · 서비스 · 방식(보통 / 화면과 대조 / 재실행) · 결과(성공 / 중단 · <이유> / 실패 — 중단 이유 글은 「작성 토큰」과 같은 말) · 요구 · 케이스로 덮음 · **케이스 %** · 기능으로 덮음 · 기능 % · UI 로 덮음 · UI % · 보류로만 · 제외 · 빠짐 · 비고 · 끝난 시각
  - 기능으로 덮음 · UI 로 덮음은 그 갈래 케이스가 하나라도 덮은 요구다(2026-10-09 — 뜻은 [작성.md](작성.md) §3.6 「셈을 남긴다」 「갈래」). 두 갈래가 같이 덮으면 둘 다에 들어 합이 케이스로 덮음을 넘을 수 있다. 이 칸이 생기기 전 실행은 갈래 칸과 그 % 가 빈다
  - 케이스 % 는 `케이스로 덮음 / 요구` 이고 요구가 0 이면 비운다(`NULLIF`) — 문단 모드에서 원장이 0개로 통과할 수 있다. 기능 % · UI % 도 같은 분모다.
    **앱(§8.12)처럼 내림한다**(2026-10-12) — 반올림하면 200개 중 199개를 덮어도 100 이 되어 다 덮은 것처럼 읽히고, 같은 실행을 앱은 99 로 보인다
  - 칸이 찬 실행과 **성공인데 칸이 빈 실행**을 싣는다 — 뒤엣것은 비고에 「원장 없음」. 칸이 빈 실패 · 중단은 대조 전에 끝난 것이라 뺀다. 반영(`MERGE`)은 셈이 없어 뺀다
  - **한계** — 「다음 요청」 수와 원장에 못 넣은 자료는 칸이 없어 여기 없다(요청 상세의 Status 카드에서 본다).
    「원장 없음」 줄에는 진짜 원장 없음 말고도 **셈을 뺀 성공 실행**(모양 검사 · 크기 · `BAD_COVERAGE` 로 셈 없이 보낸 것)과 **이 칸이 생기기 전에 끝난 성공 실행**(30일 동안)이 섞인다 — 칸만으로는 못 가른다

- **검토할 것** (2026-10-30 WEB-F7-06 · 시안 11판 · 시작 질문 승인) — 실행 중 줄 아래 세 칸이 사람이 오늘 손댈 것을 숫자 하나씩으로 먼저 보인다. 칸마다 큰 숫자 · 이름 · 한 줄 설명이고, 수가 있으면 칸 전체가 누르는 자리다.
  - **회귀 실패** — 서비스별 `newFailureCount` 의 합(표가 상한에서 자르기 전 전체 — 아래 「회귀 실패는」). 누르면 같은 화면의 회귀 실패 표로 내려간다(실행 기록이 아니다 — 표가 이미 그 목록이다)

    한 애플리케이션을 세다 실패하면 그 애플리케이션만 빼고 서버 기록에 남긴다 — 대시보드 전체가 멈추지 않게.
    누르면 그 애플리케이션을 고르고 테스트 작성 결정 목록(`#/authoring?todo=1`)으로 간다. 여럿이면 가장 많은 애플리케이션(같으면 번호가 작은 것)이다. 작성 칸 read 인 애플리케이션이 없으면 숫자 대신 「—」이고 누르지 못한다
  - **환경 오류** — 실패 유형 칸의 환경 오류 줄 수(실패 + 미실행 — 아래 「실패 유형」). 실행 기록에 유형으로 거르는 조건이 없어 실패 유형 이름 고리와 같은 곳(실행 기록 `state=failed` · `days`)으로 간다
  - 수가 0 이면 숫자를 흐리게 두고 누르지 못한다
- **종류별 칸** (2026-10-30 WEB-F7-06) — 서비스 고르개로 애플리케이션 하나를 골랐을 때만 통과율 아래에 선다(`byKind` — 「전체」면 null 이고 칸이 없다. 여러 종류가 섞이면 줄 단위가 서로 맞지 않는다).
  세는 단위와 규칙은 통과율과 같다 — 이번 창의 접은 줄(실행, 케이스, 디바이스)을 아래 단위로 나눈 통과 · 실패 · 미실행 수이고 통과율 분모도 셋의 합이다. 줄은 이름 차례이고 단위를 모르는 줄(이름 null)은 맨 뒤 한 줄로 모은다.
  - **웹(`SCREEN`) — 「브라우저별 결과」** — 줄은 디바이스(PC · 모바일)다. 러너 브라우저가 Chromium 하나라 「PC · Chromium」 · 「모바일 · Chromium」으로 적는다
  - **Android 앱(`APP`) — 「기기별 결과」** — 줄은 항목에 남은 기기(`run_item.device` 의 모델 · Android 버전)다. 회차마다 기기가 다르면 모델 글자 차례로 앞선 것이다(빈 모델 글자는 고르지 않는다). 기기를 안 남긴 항목(디바이스 팜 전 로컬 실행)은 「기기 정보 없음」
  - **게임(`GAME`) — 「창별 결과」** — 줄은 케이스가 쓰는 화면 파일(지도 ② `case_screen` 의 `.page.ts`)의 이름이다. 둘 이상이면 케이스 목록 묶음과 같이 주소(없으면 파일) 차례로 앞선 하나다(카탈로그 §8.1 「맥락」). 없으면 「창 정보 없음」
  - **API(`API`) — 「엔드포인트별 결과」** — 줄은 서비스 지도(`service_api`)의 메서드 · 경로 틀이다(대상 서버 host 가 달라도 한 줄). 수는 그 엔드포인트를 거친 케이스(`service_api_use` 케이스 줄)의 접은 줄이라 한 케이스가 여러 엔드포인트를 거치면 줄마다 센다. 지도에 없는 케이스는 「엔드포인트 정보 없음」 한 줄이다 — 빼면 지도를 아직 안 쌓은 애플리케이션이 「결과가 없습니다」로 읽혀 옆 통과율과 어긋난다.
    95% 응답(`p95Ms`)은 이번 창 그 애플리케이션 실행의 요청 기록(`run_network`)을 서비스 지도와 같은 틀(`apps/admin/src/prd/apiMap.ts` `API틀`)로 접어 맞춘 걸린 시간의 95번째 백분위수(가장 가까운 순위)다. 기록이 없으면 null 이고 화면은 「—」. 다른 종류의 줄은 늘 null 이다
  - 줄이 하나도 없으면 「최근 N일 결과가 없습니다」 한 줄
  - **칸 아래 한 줄** (2026-10-31 WEB-F7-23 · 시작 질문 승인 — 2026-10-30 WEB-F7-06 에서 미뤘던 시안 11판의 줄) — 셀 것이 없으면 줄이 없다. API 는 늘 없다.
    - **웹 · 앱 — 「한 곳에서만 실패」(`onlyFail`)** — 이번 창 접은 줄을 케이스마다 모아, 실패한 단위가 딱 하나이고 다른 단위에서는 통과한 케이스를 그 단위 몫으로 센다. 미실행 줄과 단위를 모르는 줄(기기 정보 없음)은 보지 않는다 — 어느 기기인지 모르면 「거기서만」을 말할 수 없다.
      웹은 단위가 디바이스이고 모바일 몫만 싣는다(「모바일에서만 실패한 케이스 N건」). 앱은 단위가 위 기기 이름이고 기기마다 싣는다 — 많은 차례(같으면 이름 차례)로 쉼표를 넣어 이어 적는다(「Galaxy A34 · Android 13 에서만 실패한 케이스 9건」). 시안의 뒷말(「대부분 「장바구니」 화면」)은 넣지 않았다
    - **게임 — FPS(`fps`)** — 기능 테스트 항목도 2026-10-31 WEB-F7-25 부터 FPS 를 남기지만(run_item.fps — 게임 정식 실행 항목만) 이 칸은 그대로 같은 창에 시작해 끝난(`DONE`) 그 애플리케이션의 게임 성능 측정(`perf_run` 기기 측정)의 1초 숫자(`perf_device_metric.fps`, 빈 값 뺌)를 쓴다.
      평균 FPS 는 1초 숫자 전부의 평균(소수 한 자리)이고 — 성능 화면의 평균 FPS(기기마다 · [성능.md](성능.md) 「세는 법」)와 달리 창 안의 측정 · 기기를 한데 모은 평균이라 두 숫자가 다를 수 있다 —  떨어짐은 기기마다 초 차례로 놓고 `낮은FPS` 이상이던 숫자가 바로 다음 초에 그 밑으로 넘어간 번수다 — 밑에 머문 초를 세면 한 번 끊긴 것도 수십 번이 된다. 첫 숫자가 밑이거나 바로 앞 초가 빈 값이면 세지 않는다. 도는 · 멈춘 · 오류 측정은 반쪽 숫자라 뺀다.
      글 앞에 측정 수를 붙여 어디서 온 숫자인지 보인다(「게임 성능 측정 2회 · 평균 FPS 54.3 · 30 아래로 떨어짐 3회」). 측정이 없으면 null 이다. 기능 테스트 결과가 없어도 측정이 있으면 줄이 선다
- **실패 유형** (2026-10-12 WEB-F3-07 · 시작 질문 B) — 이번 창의 접은 줄 가운데 **판정이 실패이거나 미실행인 줄**을 원인 다섯으로 나눈다. 새 칸 없이 이미 저장된 값(실패한 확인 문장 · 오류 원문)만 본다.
  - **미실행도 센다.** 동작 제한 시간(`actionTimeout`)을 두지 않아 요소를 못 찾은 케이스는 테스트 제한 시간까지 기다리다 미실행이 되고(kit 리포터가 `timedOut` 을 `NA` 로 적는다), 러너 고장 · 제한 시간 초과도 미실행이다.
    실패만 세면 요소 미검출 · 타임아웃 · 환경 오류 줄이 거의 늘 0 이다(A 「실패만」은 고르지 않았다). 미실행을 실패로 세지 않는다는 §8.5 규칙은 그대로다 — 줄마다 실패 수와 미실행 수를 나눠 싣고 화면도 막대를 판정 색으로 나눠 칠한다
  - **원인을 볼 회차** — 접은 판정이 실패면 첫 실패 회차, 미실행이면 첫 미실행 회차다. 오류 원문은 항목 오류와 첫 절차 오류를 따로 읽는다 — 테스트 제한 시간 미실행은 항목 쪽에 「Test timeout」만 있고 기다리던 요소는 절차 쪽에 있다
  - **차례대로 가른다**(정본은 코드 `apps/admin/src/reporting/failureType.ts` 의 `원인을가른다`) — ① 실행이 멈춰 닫힌 미실행(`ABORTED`)은 유형에 넣지 않고 `stopped` 로만 센다 — 사람이 멈춘 것과 서버가 다시 뜨며 닫은 것(`recoverRunning`)이 같은 글자라 DB 가 못 가른다. 증적(`collect.ts`)처럼 가르는 척하지 않고 화면도 「실행이 멈춰 돌지 못한 N건」으로 적는다 ② 실패한 확인 문장이 있으면 **기대 결과 불일치** ③ 연결 오류(`net::ERR_` · `ECONNREFUSED` · `fetch failed` 등 — 앱이 스스로 이동을 끊은 `net::ERR_ABORTED` 는 뺀다)이거나 미실행 항목 오류의 **글 머리**가 서버가 넣은 러너 사유(러너에 닿지 못함 · 러너가 거절 · 디바이스 팜 없음 · 팜이 폰을 못 내줌 — 2026-10-20 APP-F1-10 · 그 전 기록의 「로컬 러너 없음」도)면 **환경 오류** — 「러너」가 어디든 들어 있나로 보면 「러너 상태」 같은 요소를 기다린 케이스까지 환경 오류가 된다.
    게임 연결이 끊긴 글(「게임 포트 N 에 붙지 못했습니다」 · 「게임이 답 없이 연결을 닫았습니다」 · 「디바이스 팜이 게임 명령을 HTTP N 로 거절했습니다」)도 환경 오류다 — 켜지기를 기다리다 그렇게 끝난 「게임이 120초 안에 답하지 않았습니다 — 게임 포트 …」도 여기 든다(2026-10-23 GAME-F1-09 — 게임 드라이버 문구는 [게임.md](게임.md) §3.10 「실행 결과」)
    ④ 요소를 기다린 기록(`waiting for locator` 등)이 있고 찾았다는 기록(`resolved to`)이 없거나 게임 드라이버의 「켜진 오브젝트 중에 X 이 없습니다」면 **요소 미검출** ⑤ 시간 초과(러너 `TIMEOUT` · `Timeout Nms exceeded` · `Test timeout` · 게임 기다림의 「N초 안에 뜨지 않았습니다 · 사라지지 않았습니다 · 「…」이 되지 않았습니다」 · 「게임이 N초 안에 답하지 않았습니다」)면 **타임아웃** ⑥ 나머지는 **그 밖** — 모르는 것을 넷 중 하나로 지어내지 않는다
  - 다섯 줄은 수가 0 이어도 늘 같은 차례로 낸다. 실패 · 미실행이 없으면 줄 대신 「없습니다」 한 줄이고, 멈춘 미실행뿐이면 그 말도 띄우지 않고 멈춘 수 한 줄만 둔다 — 통과율 칸에는 그 미실행이 보인다. 유형의 실패 합은 통과율 칸의 실패 수, 미실행 합 + `stopped` 는 미실행 수와 같다
  - **한계** — 글자 맞추기다. Playwright · 러너가 오류 글을 바꾸면 그 밖으로 빠진다. 테스트 코드가 던진 오류(「테스트 계정 비밀값이 비어 있다」 같은 것)는 환경 탓이어도 그 밖이다. 테스트 제한 시간에 끊기며 절차 기록이 안 남았으면 기다리던 요소를 몰라 요소 미검출이 아니라 타임아웃으로 센다(kit 리포터는 항목에 첫 오류 「Test timeout」만 싣는다)

- **서비스별 품질 줄** — 서비스마다 통과율 · 최근 실행 흐름(상한 `흐름실행수` · 실행마다 「실패 있음 · 전부 통과 · 그 밖」 셋 중 하나) · 회귀 실패 수 · 해결 수.
  해결은 §7 insights 의 「고쳐짐」과 같은 규칙이고, 그 뒤 **같은 대상 서버**에서 다시 실패하지 않은 것만 센다(아래 회귀 실패의 「지금도」와 같은 최근 판정)
- **볼 수 있는 서비스** — 실행 칸 read 이상인 배정 서비스(요구사항 커버리지만 작성 칸 read). `project` 를 주면 그 프로젝트 안만이다(§7). 사람의 dashboard 칸은 Grafana 전용이다([인증.md](인증.md) §3.5).
  admin 도 **배정된 서비스만** 본다 — `last-by-case` 와 같다. 스캔이 admin 에게 활성 서비스 전부를 보이는 것과 다르다
- **세는 규칙은 §8.5 와 같다**(다만 한 건 실행이 붙은 실행은 다르다 — 이 화면은 지금 결과, §8.5 는 원래 결과) — 세는 단위는 (실행, 케이스, 디바이스) · 회차 접기(전부 통과 = 통과 · 하나라도 실패 = 실패 · 나머지 미실행, 정본은 실행 §8.3 회차 요약) ·
  미확정 항목도 센다(실행 §3.2 · 2026-10-11 PRD-F4-02 — 앞 판은 뺐다) · 시나리오 실행은 뺀다.
  **한 건 실행은 실행으로 세지 않고(실행 중 줄에도 없다) 붙은 실행의 칸은 지금 결과로 센다** (2026-10-30 WEB-F7-02 · 실행 §3.2 「★ 한 건 실행은 묶음 실행에 붙는다」) — 어젯밤 실행에 붙어 통과하면 어젯밤 날짜의 일별 막대 · 통과율 · 히트맵이 바뀐다.
  회귀 실패의 「지금도 실패」를 가르는 가장 최근 판정은 붙지 않은 한 건 항목도 본다(아래 「회귀 실패는」). **사람이 돌린 것도 정기 실행도 모두 센다** — 추이는 정기 실행이 있어야 뜻이 있다(§8.5 의 판단)
- **창 길이는 7 · 14 · 30일 가운데 고른다. 기본은 14일이다**(`창날수` — 2026-10-19 ⑫ · 점검 6.3 에 「고정」을 뒤집었다). 앞 판은 고르는 칸이 없어 배정된 서비스 전부가 14일로 섞여 한 서비스의 최근 한 주를 볼 수 없었다. 14 를 기본으로 둔 까닭(두 주면 요일 편차가 한 번씩 겹쳐 오른다 · 직전 창과 견줄 만큼 길다)은 그대로다
- **머리에 서비스 고르개와 기간 고르개가 있다** (2026-10-19 ⑫ · 점검 6.3). 서비스는 `전체 서비스` + 볼 수 있는 서비스(`services`), 기간은 `최근 7일 · 14일 · 30일`. 고른 값은 주소에 남긴다 — `#/dashboard?service=<서비스 번호>&days=7`(접두사가 아니라 번호다 — 응답에 접두사가 없다). 기본값(전체 · 14)은 주소에 안 적는다. 주소의 서비스 번호가 `services` 에 없으면 전체로 되돌린다.
  조건을 바꾸면 불러오는 중으로 돌아가 다시 읽고, 가장 나중에 보낸 요청의 응답만 받는다. 15초 새로고침(`only=running`)도 같은 조건을 싣는다. 부제는 서비스를 고르면 「<이름> · 최근 N일 · <시각> 기준」이다. 이 고르개는 애플리케이션 줄(2026-10-29 까지는 헤더의 애플리케이션 고르개)과 별개다(대시보드는 여러 애플리케이션을 가로지르는 화면이라 애플리케이션 줄을 따르지 않는다 — 아래 「자리」).
  **대신 고른 프로젝트(사이드바 바닥의 고르개 — 2026-10-30 앞 자리는 헤더)는 따른다** (2026-10-20 ⑬-3 사용자 「고른 프로젝트만」) — 고른 애플리케이션의 프로젝트 번호를 `project` 로 싣고, 서비스 고르개 · 집계 · 커버리지가 모두 그 프로젝트 안이다. 프로젝트를 바꾸면 고른 서비스를 비우고(다른 프로젝트 것이다) 다시 읽는다. 앞 판은 프로젝트를 안 가려 프로젝트를 바꿔도 숫자가 그대로였다
- **칸에서 원인으로 내려간다** (2026-10-19 ⑫ · 점검 6.1 · 6.2 — 앞 판은 이름만 실행 결과 맨 위로 가고 나머지는 눌리지 않았다). 회귀 실패 줄의 케이스 이름은 그 실행의 그 케이스 실패 카드를 펼친 채 연다 — 2026-10-20 ⑬-2 부터 대시보드를 떠나지 않고 오른쪽 서랍에 그 카드 하나를 그리고(판정 버튼은 안 단다 — 대시보드는 서비스마다의 권한을 모른다), 서랍 아래 「실행 기록에서 보기」가 앞 판의 이동 주소(`실행기록주소(tcId, runId, true)` · 실행 §8.3 「주소로 카드를 펼친 채 연다」)로 간다. 새 탭으로 열면 서랍 없이 그 주소로 간다. 표에 대상 서버(`env`)를 TC 아래에 서비스와 함께 적고, 서버가 상한(`신규실패상한`)에서 자른 만큼은 「N건 더 있습니다 · 실행 기록에서 보기」로 실행 기록(`state=failed`)에 잇는다(전체 수는 서비스별 `newFailureCount` 합에서 얻어 응답은 그대로다).
  실패 유형 이름(건수가 있는 줄) · 서비스별 품질의 서비스 이름 · 일별 막대(실행한 날) · 히트맵의 케이스(서비스가 하나로 정해졌을 때만 `케이스주소` 링크, 여럿 중 어느 서비스인지 모르면 글자만)도 눌린다 — 가장 가까운 기존 조건(`state=failed` · `days`)의 실행 기록이나 케이스 상세로 간다.
  실행 기록의 종류(`#/runs/fn` · `#/runs/ui`)는 그 칸의 UI 몫(§7 `daily[].ui` · `byService[].currentUi`)으로 고른다 — 기능 쪽에 보낼 것(`state=failed` 를 다는 고리는 실패, 아니면 돌린 줄)이 있으면 기능, 없고 UI 쪽에만 있으면 UI, 둘 다면 기능이다.
  날 · 서비스에 안 매인 「N건 더 있습니다」 · 실패 유형 이름은 이번 창 전체(통과율 이번 창과 daily UI 몫의 합)로 고른다 — 「N건 더 있습니다」는 fail, 실패 유형 이름은 그 칸이 세는 fail · notRun 을 견준다(2026-10-24 FIX-F4-04 — 앞 판은 늘 기능 목록이라 UI 실패로 못 내려갔다). 유형으로 · 날짜로 거르는 조건이 실행 기록에 없어 유형 · 날짜까지 좁히지는 못한다(창 길이 `days` 는 그대로 싣는다 — 실행 기록도 7 · 14 · 30일을 안다). 링크를 넣은 SVG · 히트맵 그리드는 `role="group"` 이다
- **커버리지 고리는 「테스트 없는 요구 N건 보기」다** (2026-10-19 ⑫ · 점검 6.4 — 앞 판은 「10월 3일 · 요청 #57」이라 눌러서 무엇이 나오는지 몰랐다). 누르면 그 서비스를 고르고 PRD 관리(`#/prd`)로 간다. N 은 게이지의 나머지(`요구 − 테스트 있는 요구`)다 — 보류 · 제외가 섞여 「미작성」과 다를 수 있어 그 낱말을 쓰지 않는다. 0 이면 고리를 그리지 않는다. 마지막 작성의 날짜 · 요청 번호는 마우스를 올리면 보이는 말풍선으로 남긴다
- **낱말** (2026-10-19 ⑫ · 점검 6.5) — 「테스트 스크립트로 가기」→「케이스 보기」, 실패 유형 설명의 「스크립트 오류 등」→「위 넷에 들지 않는 그 밖의 오류」. 실행 중 줄은 실행 제목을 앞에 두고 「서비스 · RUN n」을 뒤에 둔다. 회귀 실패 표 응답에는 실행 제목이 없어 `RUN n` 그대로다
- **통과율의 「▲ 88%p 직전 14일 대비」는 직전 창에 실행이 없으면 내지 않는다** (점검 N12) — 0% 와 견주면 크게 오른 것처럼 보인다. 그때는 「직전 N일 실행 없음」(N 은 `window.days`)만 보인다
- **통과율의 분모는 통과 + 실패 + 미실행이다** — 미실행을 빼면 러너가 고장 난 날이 좋아 보인다
- **진행 중 실행(`RUNNING`)은 집계에서 뺀다.** 실행 중 줄에서만 보인다. 시나리오 실행은 실행 중 줄에서도 뺀다
- **회귀 실패는 §7 insights 의 「새로깨짐」과 같은 규칙이다** — 실행마다 같은 서비스 · 같은 대상 서버 · 같은 종류의 **바로 앞 끝난 실행**과 견준다(앞 실행이 창 밖이어도 찾는다. 스모크 아닌 실행은 스모크를 건너뛴다 — 고르기 정본은 §7 insights previous).
  앞이 미실행이던 실패도 신규다. 앞 실행에 없던 케이스는 견주지 않는다. 미확정도 견준다(2026-10-11 PRD-F4-02 — 앞 판은 어느 한쪽이 미확정이면 안 견줬다).
  **이번 창 실행에서 생긴 것만** 싣고, **지금도 실패인 것만** 싣는다 — 같은 대상 서버 · 케이스 · 디바이스의 가장 최근 판정(미실행은 판정으로 치지 않는다. 미확정은 친다 — 2026-10-11 PRD-F4-02)이 실패일 때다.
  가장 최근 판정에는 한 건 항목도 든다(2026-10-30 WEB-F7-02) — 붙었으면 그 실행의 지금 결과로, 붙지 않았어도(그 실행에 없던 디바이스 · 반복 실행) 끝난 때로 줄을 선다. 회귀 실패 자체(새로깨짐)는 지금 결과로 판다 — 붙은 한 건이 통과면 그 실행의 회귀 실패가 아니다.
  표의 「실패 사유」 칸은 2026-10-19 ⑫ 에 「실패 유형」 칸이 됐다(§7 newFailures 의 type · WEB-F4-03) — 칸에는 유형 이름을 적고 대표 문장은 마우스를 올리면 보이는 말풍선(title)으로만 둔다. **같은 대상 서버에서 다시 통과해야 빠진다** — 다른 서버에서 통과하거나 못 돌았다고 고친 것이 아니다 (2026-10-07 게이트 2 사용자). 같은 대상 서버 · 케이스 · 디바이스는 가장 최근 새로 깨진 하나다. 상한은 `신규실패상한`. 화면 이름은 「회귀 실패」다 — DESIGN.md 가 「새로깨짐」을 그렇게 부른다
- **히트맵** — 이번 창에서 실패가 많은 케이스 상위(`히트맵케이스수`)를 날짜별로 편다. 순서는 실패 수 → `tc_id` 다.
  칸 값은 그날 접은 실패 수이고 색은 단계 0 · 1 · 2+ 셋이다
- **요구사항 커버리지** — 서비스마다 최근 `커버리지날수` 안에서 **마지막으로 성공(`DONE`)한** 작성 실행(`AUTHOR` · `RERUN`, 커버리지 칸이 찬 것) 하나의 셈을
  **기능 · UI 로 나눠** 보인다(2026-10-09 시안 A) — 게이지 둘(기능 · UI, 서비스를 합친 것 — 게이지 아래 글은 「테스트 있는 요구 N / 전체」, 2026-10-12 앞 글 「덮은 요구」 · 작성.md §3.6 「★ 역할별 계정」)과 서비스마다 막대 두 줄.
  갈래 수의 뜻은 [작성.md](작성.md) §3.6 「셈을 남긴다」 「갈래」. 갈래를 못 센 실행(그 칸 전)은 줄이 막대 하나(「전체」 — 케이스로 덮음 / 요구)이고 게이지 합에서 빠진다 — 넣으면 분모만 늘어 낮아 보인다.
  빠진 서비스가 있으면 게이지 아래에 그 수를 한 줄로 적는다 — 아래 줄에는 보이는데 분모에 없는 까닭이 화면에 없으면 게이지가 그 서비스까지 센 것으로 읽힌다.
  요구가 0 이면 비운다. 중단(`STOPPED`)은 뺀다 — 대조 뒤 거절이라 덮음이 끝나지 않았다. 셈의 뜻은 [작성.md](작성.md) §3.6 「셈을 남긴다」.
  **단위가 실행 하나의 원장이라** 칸 머리에 「마지막 작성 기준」을 달고 서비스 줄에 「테스트 없는 요구 N건 보기」를 단다(날짜 · 요청 번호는 말풍선 — 아래 「커버리지 고리」)
  % 는 내림한다 — 덜 덮었는데 100 으로 읽히지 않게. 실행마다의 기록은 Grafana 「작성 커버리지」가 같은 내림으로 보인다 — 둘을 다 두는 까닭은 §8.5 「남은 패널 점검」
- **하루의 경계는 화면이 보낸 `tz` 다.** PostgreSQL `pg_timezone_names` 에 있는 이름만 받는다 — 없거나 틀리면 400 `INVALID_REQUEST`, detail 에 받은 값을 싣는다.
  `'+09'` · `'KST'` 같은 값은 오류 없이 받히고 POSIX 꼴은 부호가 반대라 **날이 조용히 틀려서** 이름표만 받는다. 「오늘」과 창의 하한도 같은 tz 다.
  값은 SQL 에 끼워 넣지 않고 바인드한다. 400 이면 화면은 판 하나에 이유를 띄우고 사이드바는 산다
- **새로 고침** — 열 때 집계를 한 번 · 실행 중인 것이 있으면 `새로고침간격`(apps/admin/src/web/Dashboard.tsx)마다 실행 중 줄만(`only=running`) · 실행이 하나 끝나면 집계를 한 번 더 · 등장 움직임은 처음 한 번만
- **자리** — 실행 칸 read 인 배정 서비스가 하나라도 있으면 사이드바 맨 위다. 집 순서는 대시보드 → 테스트 케이스 → 테스트 작성 → 실행 기록

- **쌓이는 순서(좁은 화면 · 화면 읽기 순서)** — 실행 중 줄 → 검토할 것 → 회귀 실패 → 통과율 → 종류별 칸(있을 때) → 서비스별 품질 → 일별 → 히트맵 → 실패 유형 → 커버리지. 「실패를 먼저」(사용자).
  넓은 화면 배치는 DESIGN.md 「대시보드」 절이 정본이다
- **표의 링크** — 줄 제목(케이스 이름)이 잉크 링크로 그 실행을 연다. 링크 열을 따로 두지 않는다
- **빈 상태** — 실행이 하나도 없으면 칸 대신 안내 한 장(정기 실행 안내 한 줄 — 설정 화면에 갈 수 있는 운영 계정에게는 그 옆에 「설정에서 정기 실행 켜기」 링크. 일별 칸의 안내 줄도 같다. 2026-10-12 WEB-F3-08 · 켜는 자리는 공통/6-인프라 §9.2). 칸마다 셋으로 가른다 — 실행 없음 · 견줄 앞 실행 없음 · 회귀 실패 없음(좋은 소식이라 짧게).
  직전 창이 비면 「직전 N일 실행 없음」(N 은 `window.days`). 창 안에 미확정 줄이 있으면 통과율 칸에 「그중 미확정 N건」 한 줄을 단다(2026-10-11 PRD-F4-02 — 앞 판은 「미확정 N건은 따로 셉니다」)
- **좁은 화면** — 칸을 쌓는다. 휴대폰에서는 아래 탭 `대시보드` 로 연다(공통/5-화면공통 §8 「휴대폰 화면」).
