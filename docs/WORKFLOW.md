# WORKFLOW.md — 작업 흐름

> 지금 어디까지 왔는지, 다음으로 넘어가도 되는지를 여기서 판단한다.
> 무엇을 만드는가는 `SPEC.md`(색인 — 본문은 `docs/spec/` 아래 여러 장), 어떻게 일하는가는 `CLAUDE.md`,
> 누가 어느 폴더를 맡는가는 `WORKSTREAMS.md`.

## 전체 흐름

```
 [0] 계획 검토        SPEC을 워크플로우로 스트레스 테스트
       ↓  게이트 G0 — SPEC 수정 완료
 [1] Phase 0 골격     단독 세션. 계약 확정 + 얇은 관통
       ↓  게이트 G1 — 관통 확인 ★사용자 확인
 [2] Phase 1 병렬     계약 반영 → 갈래 병렬 (목록은 WORKSTREAMS.md)
       ↓  게이트 G2 — 갈래별 spec-review 통과
 [3] 전체 검사        다른 세션이 spec-review 전체 범위
       ↓  게이트 G3 — 치명 0건 ★사용자 확인
 [4] 병합             5단계 순차
       ↓  게이트 G4 — 완료 기준 전항목 ★사용자 확인
 [5] 완성
```

★ 표시는 **Maxi님이 직접 클릭해서 확인**하는 지점이다. 건너뛰면 안 된다.

**같은 날 「실행 상태」가 열렸다** (「실행상태」 PR #36). 둘이다.

- **진행 상자** — 실행이 도는 동안 **무엇이 도는지**를 보여준다 (SPEC §8.9).
  완료 알림과 **같은 상자**이고 내용만 갈라 그린다. 다만 **여는 이유는 둘이라**
  진행 상자를 닫은 사람도 끝났을 때 알림을 받는다
- **직전 실행 비교와 실패 사유 묶기** — `GET /api/runs/:runId/insights` (SPEC 도메인/리포팅 §7).
  케이스마다 `새로깨짐 · 계속깨짐 · 고쳐짐 · 그대로`, 같은 사유로 깨진 실패를 한 덩어리로

**같은 날 「절차 단위 진행」이 열렸다** (「절차단위진행」 PR, 2026-09-21).
진행 상자가 말하던 「진행 중인 항목」이 **근사치였는데 그것을 걷어냈다** —
이제 **도는 항목마다** `절차 N · 제목` 과 **그 절차에 머문 시간**을 제한 시간과 나란히 그린다.
kit 이 절차를 시작할 때 stdout 에 한 줄(`@@PROGRESS@@`)을 흘리고, 러너가 그것을 모아
`GET /progress` 로 답하고, admin 이 **자기 실행의 것만 걸러** `GET /api/runs/:runId/progress` 로 낸다
(SPEC 도메인/러너 §5.2 · 도메인/실행 §7 · §8.9). **DB 도 마이그레이션도 없다.**

**방향이 계획과 반대로 뒤집혔다** — `ExecuteRequest.progressUrl` 로 **러너가 admin 에 미는** 안이었는데
게이트 0 에서 **당김**(admin 이 러너에게 묻는다)을 골랐다. 러너에 로그인 세션이 없어 미는 쪽은
admin 문에 「로그인 없이 지나가는 자리」를 새로 내야 했고, 그런 예외는 **2026-09-17 에 일부러 없앤 것**이다.
**`progressUrl` 은 만들지 않았다** — 그 제안이 적힌 계약 블록 둘은
`docs/plans/2026-09-21-청사진스킨.md` 에서 `철회됨` 으로 닫혔다.

**완료 기준 상자가 몇 개이고 그중 몇 개가 확인 끝났는지는 여기 적지 않는다** —
`npm run count:done` 이 센다.

**2026-09-20 에 「스펙 기능이 다 만들어졌나」를 전수 조사했다.** 그때 근거로 쓴 것이
**「코드에 미구현 표시(TODO·throw) 0건」**이었는데 **그 근거가 틀렸다.** 형식 고르는 버튼은
「쓰다 만 코드」가 아니라 **아예 없던 코드**여서 TODO 도 안 붙어 있었다 —
**없는 것에는 표시가 안 남는다.** 그래서 이 판단의 근거를 바꿨다.
**이제는 SPEC §8 이 요구하는 화면 자리를 하나씩 열어서 본다.**
그 약속은 `spec-review` 의 **F10** 이 붙든다.

**「기능 구현은 됐다」의 지금 근거** — 증적 형식을 고르는 자리를 **실제로 열어서 확인했다.**
`apps/admin/src/web/evidence.ts` 의 `형식들` 표를 `증적버튼들()` 이 훑어 **형식마다 버튼 하나**를 내고,
`apps/admin/src/web/RunResult.tsx` 가 `makeEvidence(runId, 버튼.format)` 으로 **누른 그 형식**을 보낸다.
그 자리가 비면 `apps/admin/src/web/RunResult.test.tsx` 의 첫 단언이 깨진다 —
`['PDF 만들기', '엑셀 만들기', 'HTML 만들기']` 를 통째로 물고 있다.
형식 이름이 네 곳에서 갈라지면 `npm run check:evidence-formats` 가 CI 에서 잡는다.
그래서 남은 일은 만드는 것이 아니라 **사람이 눌러서 확인하는 것**이다 (아래 「눌러볼 길」).

**★ 자리를 명세에 세운 PR(2026-09-22) 다음은 「완료 기준 확인」이다. 화면 PR 은 그 뒤다.**
아래 ⏸ 둘을 막고 있던 것이 풀렸지만 순서는 그대로다 — 남은 완료 기준이 몇 개인지는
`npm run count:done` 이 센다. **명세를 세우는 일은 그 숫자를 하나도 안 줄인다.**
사람이 눌러야만 줄어드는 숫자이고, **화면을 더 얹을수록 확인할 것만 는다.**


   쓴 말이고 플랫폼이 지어내지 않는다 (SPEC 공통/5-화면공통 §8 「다국어」)
2. **테스트케이스 목록** — 맨 위에 칸 이름(`TC ID · 케이스명 · 입력값 · 마지막 결과`)이 있고,
   입력칸이 케이스 이름 **오른쪽 칸**에 있다 (전에는 이름 아래였다)
3. 아무 줄의 **`상세`** 를 누르면 **상자가 뜬다.** 전에는 줄 아래로 펼쳐질 뿐이었다.

4. **실행 기록**에도 칸 이름이 있고 **`결과 보기`** 가 상자로 뜬다.
   먼저 제목으로 검색해 두고 눌러 본다 — **닫으면 검색어가 그대로 남아 있다.**
   전에는 화면을 갈아타서 돌아올 때 조건이 풀렸다

**되돌아오면 안 되는 것 하나** — 증적 문서(PDF·엑셀)는 **언어를 바꿔도 한국어다.**
검수처에 내는 산출물이라 화면 언어를 따라가면 같은 실행의 문서가 둘이 된다.

### 눌러볼 길 — 화면리뉴얼 ③ 를 병합한 뒤 (2026-09-22)

**리뉴얼의 마지막 판이다.** 확정 목업이 그린 화면 일곱이 전부 옮겨졌다.

```

```

**볼 것 다섯**

1. **어느 화면이든 제목이 맨 위 머리 줄에 있다** — 본문 상자 바깥이고 바탕이 다르다.

   평균 옆에 `끝난 N회 기준` 이 적혀 있다 (도는 실행은 소요가 없어 빠진다)
3. **실행 기록에서 제목으로 찾고 상태로 거른다.** 거르면 **집계 숫자도 같이 줄어든다** —
   세 줄 보이는데 「42회」라고 말하지 않는다
4. **로그인 화면**이 짙은 바탕 위 밝은 상자 하나다
5. **설정 화면** 머리에 `운영 등급만 볼 수 있는 자리다` 가 적혀 있다

**일부러 안 넣은 것 하나** — 목업의 실행 기록 머리에 `증적 문서 받기` 버튼이 있었는데 뺐다.
증적은 실행 하나마다 만드는 것이고(§8.4) 목록에서 무엇을 받는지가 명세에 없다.

### 눌러볼 길 — 「여러건실행」 을 병합한 뒤 (2026-09-21)

1. **`docker compose up -d --build admin`** — **이걸 빼면 고르는 칸이 안 보인다.**
   화면은 번들로 구워져 이미지 안에 들어가므로 다시 빌드해야 새 칸과 새 버튼이 들어간다.

3. **목록 위 버튼 글자가 바뀌는 것을 본다** — `전체 실행하기` → `고른 N건 실행하기`.

   **모달 안 줄에 사유**가 뜬다 (`대상 서버를 고르세요…`). 눌렀는데 아무 일도 안 일어나면 안 된다

**모달 아래 한 줄이 넷을 겸한다** — 방금 누른 것에 대한 답 · 버튼이 죽은 이유 ·
걸었다 거절당한 사유 · 만들어질 건수 안내. 사유는 **건수 안내만** 덮는다.

   화면은 번들로 구워져 admin 이미지 안에 들어가고, **절차 줄을 실어 나르는 리포터는 러너 이미지 안에 있다.**
   **러너를 빼먹으면 절차 줄이 한 글자도 안 나온다** — 화면은 멀쩡히 뜨고 절차만 조용히 비어 있어
   PR 이 실패한 것처럼 보인다. 그때는 **이 단계를 반만 한 것이다**
2. **절차가 여럿인 케이스로 실행을 하나 건다** — `DEMO-006` 이 지금 가장 많다.
   절차가 하나뿐인 케이스는 줄이 한 번 떴다 사라져서 볼 틈이 없다. 걸면 **진행 상자가 저절로 뜬다**
3. **`진행 중` 아래 줄을 본다.** 항목 이름 바로 밑에
   `절차 4 · 결제 수단 목록에서 카드를 고른다` · **`12초째`** · `/ 제한 5분` 이 한 덩어리로 붙어 있다.
   **`12초째` 가 2초마다 커지는 것**이 핵심이다 — 그 숫자가 멈춰 있으면 실행도 멈춘 것이다
4. **동시에 도는 것이 여럿이면 여럿이 뜬다** — 하나만 골라 그리지 않는다.
   여러 건 실행으로 걸어 보면 보인다 (동시 실행 기본값은 2이고 `EXECUTION_CONCURRENCY` 로 바꾼다)
5. **상자를 닫고 기다려 본다** — 끝나면 **완료 모달이 다시 뜬다.**
   「닫았다」와 「알았다」는 다른 말이다 (SPEC §8.9)

⚠️ **절차 줄이 안 보여도 케이스는 멀쩡히 통과한다.** 이 자리는 단위 검사가 원리적으로 못 본다 —
Playwright 워커의 `process.stdout.write` 가 갈아치워져 있어서, 리포터가 받은 조각을 되돌려 쓰지 않으면
**진행만 조용히 0 이 된다** (LEARNINGS 2026-09-21). 그래서 **사람이 한 번 실물로 본다.**

**그러면 `docs/spec/공통/7-데모와-완료.md` 의 Phase 2 상자가 하나 열린다.**
「실행을 걸면 그 결과 화면에 진행 상자가 뜬다. 막대가 차고, **도는 항목마다 이름과
「지금 몇 번째 절차를 몇 초째」**가 제한 시간과 나란히 보인다」.
**상자는 세션이 체크하지 않는다.** 누르는 사람이 Maxi님이고, 체크도 그때 한다.

**2026-09-19 에 WS-E 가 넘긴 것 셋을 닫았다** (PR #28). ① `Dockerfile` 이 `scripts/` 를 안 실어
`SETUP.md` 의 첫 계정 만들기가 죽던 것 ② 문이 **번호로 부르는 경로 열둘**을 서비스 검사 없이
지나보내던 것 ③ SPEC §8 과 §8.8 의 색 규칙 충돌(게이트 0 승인).

그 과정에서 **검사 렌즈 넷이 인증 우회 둘을 더 찾았다.** 주소의 `api` 를 `%61pi` 로 감싸면
문이 통째로 비켜서 **로그인 없이** 전 계정 목록과 관리자 비밀번호 재발급이 됐다.
원래부터 있던 것이고, 뿌리는 **문이 주소 글자를 읽고 라우터는 디코딩한 뒤 라우트를 찾는 것**이었다.
이제 문은 등록된 라우트 틀과 `req.params` 만 본다. 자세한 것은
[reviews/2026-09-19-넘긴것-셋.md](reviews/2026-09-19-넘긴것-셋.md).

⚠️ **돌고 있는 admin 컨테이너는 다시 빌드해야 이 수정이 적용된다** — `docker compose up -d --build admin`.

2026-09-17~18 개정이 WS-A·B·C·E 가 만들어 둔 것 위에 할 일을 더 얹었다.
「완료」였던 넷을 전부 `pending` 으로 되돌렸고, 개정으로 더 할 것을 각 킥오프에 적었다.
2026-09-18 에 `contracts`(공용 밑작업) · `WS-A`(카탈로그) · `WS-B`(실행) · `WS-F`(인증)를 한 세션에서 이어서 돌렸다.
**이제 나머지 갈래가 전부 풀렸다** — `service` 표와 `ExecuteRequest.baseUrl` 이 들어왔다.
갈래별 할 일은 `docs/WORKSTREAMS.md` 의 킥오프 절이 정본이다.

**2026-09-19 에 `WS-C`(러너)가 끝났다** (PR #23). 개정 SPEC 의 WS-C 할 일 넷 중 셋(`baseUrl` 전달 ·
`retries: 0` · DB 무상태)은 이미 코드에 있었고, 남은 **중단 통로**(`POST /abort`)를 냈다.
그 과정에서 WS-B 영역의 버그 둘도 같이 고쳤다 — `finishItem()` 의 덮어쓰기 가드와 검사 파일 간 간섭.

**2026-09-19 에 `WS-D`(리포팅)도 끝났다** (PR #24). 증적 문서 세 형식(HTML·PDF·엑셀) ·
증적 API 둘 · Grafana 패널 넷 · 부팅 복구. 검사에서 치명 둘을 잡아 고쳤다 —
**스크린샷이 세 형식 어디에서도 안 떴고**(경로로 두면 HTML 은 404, PDF 는 요청조차 안 나간다)
**박제 이전 행의 비밀값이 평문으로 나갔다**(표시가 없으면 안 가렸다).
남은 것과 다음 세션이 알아야 할 것은 `docs/progress/WS-D.md` 에 있다.
**병합 뒤 `docker compose restart grafana` 를 한 번 돌려야 대시보드가 뜬다.**

**2026-09-19 에 `WS-E`(화면) ① 뼈대가 끝났다** (PR #25). **화면이 아예 안 뜨던 것을 되살렸다** —
`WS-F` 가 모든 `/api/**` 앞에 로그인 문을 세우고 `WS-A`·`WS-B` 가 목록 둘에 `?service=` 를
필수로 만들었는데 화면이 셋 다 모르고 있었다. 로그인 화면 · 서비스 띠 · 자리 목록 · 알림 줄 ·
등급 숨김을 넣고 버그 둘(중단된 실행에서 폴링이 안 멈춤 · 항목 상세에 비밀번호 평문)을 닫았다.
검사에서 **바깥 렌즈(`/code-review`)가 자기검사가 놓친 HIGH 를 잡았다** — 세션이 도중에 끊겨도
로그인 화면이 끝내 안 뜨던 것이다. 전말은 `docs/reviews/2026-09-19-WS-E.md`.

**2026-09-19 에 `WS-E` ② 화면 고치기도 끝났다** (PR #26). **실행이 끝까지 돌게 됐다** —
`RunSetup` 이 실행 요청에 `env`(대상 서버)를 안 실어 서버가 400 을 내고 있었다.
그 칸을 만들 통로가 없어 **게이트 0 을 거쳤다** — `/auth/me` 의 `services` 에
`envs`·`hasSlackWebhook` 을 더했다 (SPEC §7 이 필드를 전부 나열한 닫힌 자리였다).
대상 서버 · 반복 횟수 · Slack 칸 · 멈춤 · 회차 요약 · 증적 문서 · 완료 알림 · 빈 목록 세 갈래가 들어왔다.

**바깥 렌즈가 또 자기검사보다 무거운 것을 잡았다** — `/code-review` 가 아홉을 찾았고
둘이 심각했다(실패한 테스트를 러너 장애로 표시 · 증적이 「만드는 중」에서 영영 굳음).

**게이트 2 에서 「고치고 재검사」를 받아 지적 셋을 기계로 옮겼다** (제품 코드는 안 건드렸다) —

## 세션 이어받기

세션이 죽거나 다음 날 이어서 할 때, 새 세션의 첫 프롬프트는 항상 이렇다.

## 막혔을 때 되돌아갈 지점

각 게이트를 통과할 때 태그를 찍는다.

```bash
git tag g1-skeleton      # Phase 0 관통 확인 직후
git tag g2-ws-a          # WS-A 완료 직후
git tag g3-review        # 전체 검사 통과 직후
```

되돌릴 때는 파일을 지우지 말고 `git checkout -b recover <태그>`로 새 브랜치를 판다.
망가진 브랜치를 남겨둬야 무엇이 잘못됐는지 비교할 수 있다.

**되돌릴 판단 기준**: 같은 문제를 세 세션에 걸쳐 고치고 있으면 되돌린다.
고치는 비용이 다시 만드는 비용을 넘은 상태다.
