## 전체 흐름

```
 [0] 계획 검토        SPEC을 워크플로우로 스트레스 테스트
       ↓  게이트 G0 — SPEC 수정 완료
 [1] Phase 0 골격     단독 세션. 계약 확정 + 얇은 관통
       ↓  게이트 G1 — 관통 확인 ★사용자 확인
 [2] Phase 1 병렬     계약 반영 → 갈래 병렬 (목록은 WORKSTREAMS.md)
       ↓  게이트 G2 — 갈래별 spec-review 통과
 [3] 전체 검사        다른 세션이 spec-review 전체 범위
       ↓  게이트 G3 — 치명 0건 ★사용자 확인
 [4] 병합             5단계 순차
       ↓  게이트 G4 — 완료 기준 전항목 ★사용자 확인
 [5] 완성
```

★ 표시는 **Maxi님이 직접 클릭해서 확인**하는 지점이다. 건너뛰면 안 된다.

**현재 위치**: [2] Phase 1 병렬 (2026-09-18). **`contracts` · `WS-A` · `WS-B` · `WS-F` 가 끝났다.**

2026-09-17~18 개정이 WS-A·B·C·E 가 만들어 둔 것 위에 할 일을 더 얹었다.
「완료」였던 넷을 전부 `pending` 으로 되돌렸고, 개정으로 더 할 것을 각 킥오프에 적었다.
2026-09-18 에 `contracts`(공용 밑작업) · `WS-A`(카탈로그) · `WS-B`(실행) · `WS-F`(인증)를 한 세션에서 이어서 돌렸다.
**이제 나머지 갈래가 전부 풀렸다** — `service` 표와 `ExecuteRequest.baseUrl` 이 들어왔다.
갈래별 할 일은 `docs/WORKSTREAMS.md` 의 킥오프 절이 정본이다.

**다음에 돌릴 것은 WS-C(러너) 나 WS-D(리포팅) 다.** 둘 다 `contracts` 만 기다리고 있었고 그것은 끝났다.
`WS-E`(화면)는 `WS-D` 와 `WS-F` 를 함께 기다리는데 `WS-F` 는 섰으므로 `WS-D` 만 남았다.
**`contracts` 는 2026-09-18 에 `main` 으로 병합됐다** (PR #12).
**2026-09-17~18 SPEC이 크게 개정됐다.** 분량은 `docs/SPEC.md` 색인의 장 목록이 정본이다 —
여기에 숫자를 적지 않는다 (CLAUDE.md §2.7 ⑤).
발표 스크립트 대조 10건 + 기술·화면 검토 13건 + 사용자 결정 2건이 반영됐고,
§1.1·§3.5·§4.1·§8.6·§8.7·§8.8·§8.9·§9.2·§11 이 새로 들어오거나 다시 쓰였다.
개정분의 코드 반영은 **`contracts` · `WS-A` · `WS-B` · `WS-F` 까지 끝났다** (위 「현재 위치」 참조).
개정 SPEC의 Phase 1 완료 기준이 `K1~K10`을 요구하고 (§11), 검사기는 2026-09-18부터 열 가지를 전부 본다.
단계가 끝날 때마다 이 줄을 고친다.

## 단계별 진입·완료 조건

### [0] 계획 검토 — 반나절

새 세션에서 `/effort ultracode`로 돌린다.

```
docs/SPEC.md(색인)를 읽고, 거기서 가리키는 장을 전부 읽고, 이 계획의 구멍을 찾아줘.
구현하지 말고 검토만 해라. 특히 이것들을 봐줘.

1. 타입 계약만으로 갈래 병렬 작업이 실제로 안 밟는지
2. 러너가 DB를 모르는 상태로 스크린샷 경로를 남기는 게 성립하는지
3. 디바이스(platform) 축이 증적 문서 구조와 충돌하지 않는지
4. Phase 0의 '얇은 관통'이 계약을 실제로 검증하는지

각 항목에 대해 문제 없음 / 문제 있음(무엇이 어떻게) 으로 답해라.
```

1차 검토 결과는 `docs/reviews/2026-09-16-G0.md`에 있다. 위 프롬프트를 돌릴 때 이 파일도 같이
읽히고, 거기 적힌 "결정 필요" 항목이 SPEC에 반영됐는지부터 보게 한다.

**완료 조건 G0**: 지적 사항을 SPEC에 반영했거나, 반영 안 할 이유를 정했다.

### [1] Phase 0 골격 — 3~5일

단독 세션. `WORKSTREAMS.md`의 Phase 0 킥오프 프롬프트를 쓴다.

**완료 조건 G1** — 아래를 **직접 해본다**.
- [ ] `docker compose up` → 컨테이너 4개가 뜬다
- [ ] `curl localhost:4000/health` → 200
- [ ] 러너 컨테이너 로그에 Playwright가 실제로 브라우저를 띄운 흔적이 있다 (스텁 응답이 아니다)
- [ ] 하드코딩 실행 1건 → `run_item`에 1행이 쌓인다
- [ ] 그 1행을 SQL로 열어 `params`에 값이 **복사되어** 들어있다

마지막 항목이 핵심이다. 여기서 참조로 들어가 있으면 Phase 1 전체가 어긋난다.

**여기서 발견된 구멍은 SPEC을 고치고 넘어간다.** 고치지 않고 진행하면 갈래마다 각자 다르게 처리한다.

### [2] Phase 1 병렬 — 3~5주

`WORKSTREAMS.md`의 갈래별 킥오프 프롬프트. 한 번에 2~3개씩이 무난하다.
WS-C가 가장 오래 걸리므로 가장 먼저 시작한다.

**갈래별 완료 조건 G2**

- [ ] `spec-review` 치명 0건
- [ ] PR 을 Ready 로 바꿔 CI 초록불 (`typecheck` · `test` · `check:tests` · `check:spec`).
      **초안에서는 푸시해도 안 돈다** (2026-09-18)
- [ ] `npm test` 를 **연속 3회** 돌려 전부 통과 (1회 통과는 증거가 못 된다. DB 를 붙이고 돈다)

### [3] 전체 검사 — 1일

어느 갈래도 담당하지 않은 **새 세션**. `/effort ultracode`.

**완료 조건 G3**: 치명 0건. 중대는 Maxi님이 판단한다.

## 세션 이어받기

세션이 죽거나 다음 날 이어서 할 때, 새 세션의 첫 프롬프트는 항상 이렇다.

```
docs/SPEC.md(색인)를 읽고 WS-<X>가 읽을 장만 읽어줘. CLAUDE.md, docs/LEARNINGS.md도 읽어줘.
너는 WS-<X> 담당이다. docs/progress/WS-<X>.md에 이전 진행 상황이 있다.

읽고 나서, 이어서 할 작업을 3~5줄로 요약해 보고해라.
파일은 내 승인 전에 만들지 마라.
```

이어받은 세션이 가장 먼저 확인할 것은 **마지막 커밋이 어디까지인가**다.
`docs/progress/WS-X.md`의 기록과 실제 커밋이 어긋나면, 기록이 아니라 커밋을 믿는다.

## 막혔을 때 되돌아갈 지점

각 게이트를 통과할 때 태그를 찍는다.

```bash
git tag g1-skeleton      # Phase 0 관통 확인 직후
git tag g2-ws-a          # WS-A 완료 직후
git tag g3-review        # 전체 검사 통과 직후
```

되돌릴 때는 파일을 지우지 말고 `git checkout -b recover <태그>`로 새 브랜치를 판다.
망가진 브랜치를 남겨둬야 무엇이 잘못됐는지 비교할 수 있다.

**되돌릴 판단 기준**: 같은 문제를 세 세션에 걸쳐 고치고 있으면 되돌린다.
고치는 비용이 다시 만드는 비용을 넘은 상태다.
