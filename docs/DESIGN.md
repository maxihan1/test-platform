# DESIGN.md — 어드민 디자인 기준

> `docs/design-mockup.html`이 이 문서의 시각적 기준이다.
> WS-E는 목업을 먼저 열어보고 시작한다. 토큰 값은 여기서 그대로 가져다 쓴다.

---

## 컨셉

**대시보드가 아니라 검사 기록지.**

이 화면이 하는 일의 본질은 지표 모니터링이 아니라 **판정**이고,
그 판정이 그대로 제출 문서가 된다. 그래서 시험성적서의 구조 논리
— 항목번호 / 사전조건 / 시험절차 / 판정 — 를 화면 구조로 가져온다.

결과 상세 화면(§화면 3)과 증적 문서 PDF는 **같은 레이아웃**이어야 한다.
화면을 보던 사람이 문서를 받았을 때 다시 배울 것이 없어야 한다.

## 원칙 3가지

### 1. 색은 판정만 갖는다
통과·실패·미실행에만 색을 쓴다. 나머지는 전부 잉크색과 종이색이다.
버튼도, 링크도, 강조도 색을 쓰지 않는다. **줄 안에서 색이 보이면 그건 판정이다.**

**서비스 색은 2026-09-22 에 화면에서 걷었다.** 어느 자리에도 안 쓴다 —
걷은 근거는 SPEC §8 이 정본이고 여기에 옮겨 적지 않는다.
**이 금지에 이제 구멍이 하나도 없다.** 줄 안에서 색이 보이면 그건 언제나 판정이다.

**껍데기에는 판정이 아닌 청색 잉크(`--chrome`)를 쓴다 (2026-09-21).**
금지를 통째로 푸는 대신 자리를 못 박아 구멍의 크기를 고정한다.
**자리 목록의 정본은 SPEC 공통/5-화면공통 §8 이고, 여기에도 개수를 적지 않는다** —
손으로 센 숫자는 자리가 늘 때 조용히 틀려진다 (CLAUDE.md §2.7 ⑤).

- 맨 위 띠
- 자리 목록의 밑줄
- 표머리 라벨과 그 바로 아래 괘선
- 구획 제목 라벨

**이 목록 밖에서는 `--chrome` 을 쓰지 않는다.** 행 안에서, 배지에서, 본문 글자에서
색을 보면 그것은 여전히 판정이다. **자리 목록의 정본은 SPEC §8 이고 여기는 사본이다** —
개수를 세지 않는 이유도 거기 적혀 있다.

### 2. 면은 떠 있고 행은 괘선으로 나눈다 (2026-09-21 뒤집었다)

**행을 쪼개지 않는다는 판단은 그대로다.** 테스트 결과는 나열이지 독립된 객체가 아니라서
행마다 카드를 두르지 않는다. 행은 여전히 얇은 괘선으로 구분한다.

**바뀐 것은 「면」이다.** 목록·집계·상세 같은 덩어리는 `border-radius: 14px` 에
아주 옅은 그림자를 준다. 컨트롤은 8~9px.

```css
--lift: 0 1px 2px rgba(25,23,19,.04), 0 10px 28px -16px rgba(25,23,19,.22);
```

**왜 뒤집었나** — 앞 판은 「카드 radius 와 box-shadow 는 쓰지 않는다」였다.
그 결과 한 톤 베이지에 1px 선만 남아 **껍데기와 내용이 같은 밝기**가 됐고,
사용자가 「사내에서 대충 만든 어드민 느낌」이라고 지적했다.
경계를 1px 선 하나에 맡긴 것이 원인이었다.

**막으려던 것은 지금도 막힌다** — 금지의 목적은 「행마다 카드를 둘러 나열을 객체로 만드는 것」이었고
그것은 여전히 안 한다. 그림자는 **면 하나당 하나**고 행에는 없다.

### 3. 숫자는 세로로 맞춘다
TC ID, 소요시간, 응답 코드가 세로로 정렬돼야 훑을 수 있다.
`font-variant-numeric: tabular-nums` 를 body 에 건다 (아래 「타이포」의 글꼴 항목 참조).

## 토큰

```css
:root{
  /* 껍데기 — 사이드바를 짙게 눌러 내용과 갈라 놓는다.
     쓰는 자리 목록의 정본은 SPEC 공통/5-화면공통 §8 이다. 개수를 적지 않는다 */
  --rail:       #26231F;  /* 사이드바 바탕 */
  --rail-2:     #332F29;  /* 사이드바 hover · 지금 있는 자리 */
  --rail-ink:   #EFEBE1;  /* 사이드바 글자              --rail 위 13.14 */
  --rail-dim:   #ABA598;  /* 사이드바 보조 글자          --rail 위  6.38 */
  --rail-acc:   #F0A77F;  /* 지금 있는 자리 표시         --rail 위  7.85 */

  /* 바탕과 면 */
  --paper:      #F2EFE7;  /* 페이지 바탕. 따뜻한 아이보리 */
  --sheet:      #FFFDF9;  /* 기록지 면 */
  --sheet-2:    #F7F4EC;  /* 행 hover */

  /* 잉크 — 세 단계 전부 본문 기준(4.5:1)을 넘는다. 아래 「명암비」 참조 */
  --ink:        #191713;  /* 본문                     기록지 위 17.62 */
  --ink-muted:  #524F47;  /* 라벨, 보조                기록지 위  8.05 */
  --ink-faint:  #6A675E;  /* 힌트, 부가 정보            기록지 위  5.56 */

  /* 괘선 */
  --rule:       #E5E1D6;  /* 구획 경계 */
  --rule-soft:  #F0EDE5;  /* 행 구분 */

  /* 밝은 면 위의 악센트 — 표머리 라벨 · 구획 제목 라벨 */
  --chrome:     #9E4A27;

  /* 값 칩의 바탕. 기록지도 종이도 아닌 세 번째 면이라 그 위 글자를 따로 잰다 */
  --chip:       #F1EEE5;

  /* 판정 */
  --pass:       #2E6B4F;  --pass-bg: #E3EDE6;
  --fail:       #9B2418;  --fail-bg: #F6E4DF;
  --na:         #7A6535;  --na-bg:   #F0EAD8;

  /* 면이 바탕에서 떠 보이게 하는 그림자 하나 (원칙 2) */
  --lift: 0 1px 2px rgba(25,23,19,.04), 0 10px 28px -16px rgba(25,23,19,.22);
}
```

**2026-09-21 에 「제도 청사진」에서 갈아끼웠다.** 차가운 청회색을 따뜻한 아이보리로 옮기고
**사이드바를 짙게 눌렀다.** 컨셉(검사 기록지)과 원칙 1·3 은 그대로다.
원칙 2 만 뒤집었고 왜인지는 그 절에 적었다.

**왜 사이드바를 짙게 했나** — 앞 판은 껍데기와 내용이 같은 밝기여서 경계가 1px 선뿐이었다.
밝기를 갈라 놓으면 「여기까지가 껍데기」가 읽기 전에 보인다.

**바탕에 격자를 깔지 않는다 (2026-09-21).** 28px 방안지 격자를 걷어냈다 —
완성된 제품이 아니라 아직 안 그린 와이어프레임으로 읽히던 가장 큰 원인이었다.
`styles.test.ts` 가 격자가 되돌아오는 것을 막는다.

**2026-09-21 에 「제도 청사진」으로 갈아끼웠다.** 회녹색 종이를 차가운 청회색으로 옮기고
껍데기 잉크와 칩 바탕을 더했다. 컨셉(검사 기록지)과 원칙 셋은 그대로다.
판정 세 색은 색조만 차갑게 맞췄다.

`--ink-faint` 는 시안 값 `#64727C` 가 **종이 위 3.87 · 행 hover 위 4.44 로 미달**이라
`#59666F` 로 내렸다. 세 단계(15.47 · 8.21 · 5.64)는 여전히 벌어져 있다.

**2026-09-18에 잉크 세 단계와 `--na`를 어둡게 했다.** 「색만으로 판정 금지」는 있는데
**숫자 기준이 없어서** `--ink-faint`(2.96)와 미실행 배지(3.68)가 본문 기준에 미달인 채로
쓰이고 있었다. 색조는 그대로 두고 밝기만 내렸다.
그때의 판단이 2026-09-21 에도 그대로 살아 시안 값을 걸러 냈다.

## 타이포

**IBM Plex Sans KR 과 IBM Plex Mono 두 벌 (2026-09-21).** 별도 제목용 서체를 쓰지 않는다.

- **본문은 IBM Plex Sans KR**, 굵기 **400·600 둘만** 싣는다. 가변 글꼴이 아니라 굵기마다 파일이 따로다
- **숫자·ID 는 IBM Plex Mono** — TC ID · 소요시간 · 응답 코드 · RUN 번호 · 값 칩. 라틴만 쓴다
- 등폭은 **제목용이 아니라 숫자용**이다. 「숫자는 세로로 맞춘다」(원칙 3)를 글꼴이 보장한다

**벌 수를 늘리지 않는다.** 증적 문서가 글꼴 파일을 base64 로 통째로 담으므로
(`reporting/html.ts`) 벌이 늘면 문서가 그대로 무거워진다. `html.test.ts` 가 **4MB 상한**을 지킨다.

실측 (2026-09-21) — 새 넷을 합쳐 **972KB** 로 옛 Pretendard 한 벌(2.0MB)보다 작다.
증적 문서에 심기는 크기가 2.68MB 에서 **1.24MB** 로 줄었다.
본문 글꼴은 **한글 음절 11172 자를 통째로** 들고 있어 두부(□)가 뜨지 않는다.

**글꼴 파일은 제품 안에 넣는다** (2026-09-18 결정). 바깥 주소(CDN)에서 받아오지 않는다.

- **왜** — 사내망에서 그 주소가 막히면 글꼴이 시스템 기본으로 조용히 떨어진다.
  화면이 조금 달라 보이는 정도가 아니라 **「숫자는 세로로 맞춘다」 규칙이 같이 깨진다** —
  숫자 폭이 제각각인 글꼴로 바뀌면 TC ID·소요시간·응답 코드가 어긋난다
- **어디** — 화면 번들에 담고 `apps/admin/Dockerfile` 의 화면 빌드 단계가 이미지에 싣는다 (SPEC §9)
- **숫자 정렬은 글꼴에만 기대지 않는다.** `font-feature-settings: "tnum"` 대신
  표준 속성 `font-variant-numeric: tabular-nums` 를 쓰고, 폴백 스택도 숫자 폭이 고정인 것으로 적는다

  ```css
  font-family: "IBM Plex Sans KR", "Apple SD Gothic Neo", "Noto Sans KR", system-ui, sans-serif;
  font-variant-numeric: tabular-nums;
  ```

- **`docs/design-mockup.html` 은 예외다.** 저장소에서 바로 열어 보는 참고 문서이고
  제품이 아니다. 여기서는 CDN 을 써도 된다

| 용도 | 크기 | 굵기 | 글꼴 |
|------|------|------|------|
| RUN 번호 · 화면 제목 | 25px | 600 | 본문 (RUN 번호는 등폭) |
| 집계 숫자 | 30px | 600 | 등폭 |
| 케이스명 (상세 헤더) | 21px | 600 | 본문 |
| 목록 케이스명 | 14.5px | 600 | 본문 |
| 본문 · 안내 문장 | 14px | 400 | 본문 |
| 입력값, 검증 문장 | 13px | 400 | 값은 등폭 |
| TC ID · 소요시간 · 응답 코드 | 12px | 500 | **등폭** |
| 구획 제목 · 표머리 라벨 | 11px | 600 (자간 0.04em) | 본문 |
| 판정 배지 | 11.5px | 600 | 본문 |

**굵기는 400 과 600 둘뿐이다.** 500 을 쓰지 않는다 — 파일이 한 벌 더 늘고
그만큼 증적 문서가 커진다. 등폭은 라틴만이라 400·500 둘을 다 실어도 부담이 없다.

- **대문자 라벨 금지.** 구획 제목도 한국어 문장으로 쓴다 (`사전조건`, `시험 절차`).
  **표머리와 구획 라벨의 라틴 대문자만 예외다** (`TC ID`) — 한국어 문장은 그대로 금지 (2026-09-21)
- **가운뎃점 나열 금지** (`A · B · C`) — 헤더 메타 한 줄은 예외로 허용
- 버튼 문구에 화살표를 붙이지 않는다
- **버튼은 그 행위의 이름으로 적는다** (2026-09-21): `실행`, `편집`, `다시 스캔`, `실행 중단`.
  **`~하기` 로 맺지 않는다.** 화면의 버튼은 「누르면 무슨 일이 일어난다」가 자리로 정해져 있어서
  명사형이 더 짧고 더 또렷하다. **안내 문장은 그대로 존댓말 서술형으로 둔다** —
  짧아지는 것은 버튼과 라벨뿐이다

## 판정 표기

| 상태 | 배지 | 행 좌측 거터 |
|------|------|------------|
| 통과 | `--pass-bg` 바탕 + `--pass` 글자 | `--pass` 4px |
| 실패 | `--fail` 바탕 + 흰 글자 (유일한 반전) | `--fail` 4px |
| 미실행 | `--na-bg` 바탕 + `--na` 글자 | `--na` 4px |

**최근 판정 흐름 막대 (2026-09-21 ② 신설).** 네모 하나가 실행 한 번이고 **맨 앞이 새 것**이다.

| 상태 | 네모 | 높이 |
|------|------|------|
| 통과 | `--pass` | 8px |
| 실패 | `--fail` | **16px** |
| 미실행 | `--na` | 12px |
| 아직 안 채워진 자리 | 바탕 없음 + `--rule` 1px 테두리 | 8px |

**높이가 판정마다 다른 것이 규칙이다.** 색만 다르면 색을 못 보는 사람에게는 회색 네모 다섯이다.
막대 옆에 `통과 4 · 실패 1` 을 글자로 같이 적는다.
다섯에 못 미치면 남는 자리를 빈 칸으로 채운다 — 안 채우면 막대 길이가 케이스마다 달라져 세로로 못 훑는다 (원칙 3).
**몇 칸인지는 `apps/admin/src/execution/history.ts` 의 `최근몇건` 이 정본이다.** 여기에 숫자를 적지 않는다.

**미확정 (2026-09-26 WS-E ①).** 미확정은 **판정이 아니다** — 화면 값을 기대값으로 삼은 케이스라 확정 판정에서 뺀다
(세는 규칙은 명세 도메인/실행 §3.2). 그래서 **판정 색 셋을 쓰지 않는다.**

| 자리 | 표기 |
|------|------|
| 케이스 목록 줄 | 케이스명 옆 `미확정` 배지 — 설정 목록의 「비활성」과 같은 중립 테두리(`.case-tag` = `.set-off` 꼴) |
| 케이스 목록 머리 부제 | `미확정 7건 · 가장 오래된 것 23일째`. 오늘 생긴 것뿐이면 `오늘`, 처음 시각을 모르면 건수만. 없으면 안 적는다 |
| 진행 막대 · 결과 막대 | 끝난 미확정이 따로 한 칸 — `--ink-faint`, 앞에 2px 틈(`.stripe i.u`). 옆 미실행 칸과 명도가 거의 같아(1.01:1) 틈 없이는 한 칸으로 보인다. 칸의 합은 여전히 전체 항목 수다 |
| 집계 숫자 줄 · 알림 줄 · 진행·완료 모달 | 확정 칸 뒤에 `미확정 5(통과 4 · 실패 1)` 글자 하나. 판정 칸에 미확정 칸을 따로 두지 않는다(같은 수가 두 번 나온다). 0 인 칸은 빼고, 미확정이 없으면 묶음을 안 쓴다. 미확정만 돌린 실행의 알림 줄은 `0 통과` 를 안 쓴다 |
| 실행 기록 줄의 거터 | 미확정만 돌린 실행은 `--rule` — 성공 색도 실패 색도 아니다 |
| 실행 결과 행 | 케이스명 아래 `미확정 · <박제된 사유>` 한 줄 — 기본 `small`(중립). 미실행 사유의 `.why`(판정 색)를 쓰지 않는다 |

글자를 만드는 규칙은 `apps/admin/src/web/unconfirmed.ts` 한 곳이다 — 자리마다 따로 적으면 같은 실행이 두 숫자로 보인다.

**과감함은 실패 한 곳에만 쓴다.** 실패 배지만 색 반전이고,
실패한 검증 문장 줄만 `--fail-bg` 배경을 갖는다. 나머지는 전부 조용하게.

`2번 절차에서 실패 — 토큰이 발급된다`

## 디바이스 표기

케이스 1건 = 1행. 판정 칸에 `PC` / `모바일` 두 배지를 나란히 둔다.
지원하지 않는 디바이스는 `—`로 비우고 배지를 그리지 않는다.
디바이스 이름은 화면에서 `PC` / `모바일`로 쓴다 (`desktop`/`mobile`은 코드 안에서만).

디바이스(`platform`)와 대상 서버(`env`)는 다른 축이다 (SPEC §2).
디바이스는 **무엇으로 여는가**, 대상 서버는 **어디에 붙는가**다.
한 실행에서 디바이스는 여럿일 수 있지만 대상 서버는 하나다. 화면에서 `환경`이라는 낱말은 쓰지 않는다.

  상세 제목은 `#<뿌리>`, 상태 카드 · 다음 단계는 최신 실행 것이다(실패한 머지는 건너뛴다), 차이 · 산출물은 최신 작성 실행 것. 예전 실행 번호로 들어오면 뿌리 쪽으로 넘긴다.

- **보류 케이스** (2026-09-29 사용자 · 시안 A — 정본은 명세 도메인/작성 §3.6 「★ 보류 케이스」). 화면 `web/AuthoringHeld.tsx`
  - **다음 단계 카드** — `보류 케이스 N건 중 M건 처리` + 잉크 진척 막대 + `보류 케이스로 가기`(아래 표로 내려간다).
    **링크가 아니라 버튼이다** — `href="#held"` 는 해시 라우터 주소(`#/authoring/N`)를 덮어 「없는 주소」로 간다. 주소는 두고 표로 스크롤만 한다.
    남은 보류가 있으면 `테스트 반영하기` 를 막고 이유 한 줄 `보류 케이스 N건이 남아 있어 아직 반영할 수 없습니다.` —
    다 처리했을 때만 버튼 아래 `반영하면 넣은 값을 테스트 코드에 적고, 값을 채운 케이스를 3번 돌려 모두 통과해야 합칩니다.`
    막는 것은 서버다(`HELD_OPEN`) — 화면이 막는 것은 편의다
  - **보류 목록을 못 읽은 실행**(`heldUnknown`)이면 `테스트 반영하기` 를 막고 `보류 케이스를 읽지 못했습니다. 같은 자료로 다시 작성하세요.` — 서버도 `HELD_UNKNOWN` 으로 막는다
  - **정방향 요청이면 반영 때 대상 서버를 고른다** — 남은 보류가 0이고 값을 채운 케이스가 있을 때만 고르기가 보인다.
    목록은 서버가 준 `mergeEnvs`(테스트 계정 아이디 · 비밀번호가 둘 다 있는 줄)뿐이다 — 운영 줄을 보이면 고른 뒤에야 `BAD_ENV` 로 막힌다.
    그런 줄이 없으면 고르기 대신 `테스트 계정을 넣은 대상 서버가 없습니다. 설정 > 서비스에서 넣으세요.` 한 줄 + 반영 막힘.
    대조 요청은 원본의 대상 서버를 그대로 쓰므로 고르지 않는다
  - **두 단 아래 온 폭에 `보류 케이스` 표** — 칸은 케이스(tcId + 칩 `판정 불가`(점선) 또는 `보류`) · 무엇을 확인하나(케이스 이름, 그 아래 흐린 글씨로 파일 경로 — 이름이 없는 옛 결과는 경로만) · 왜 보류됐나(`held` 사유에서 머리를 뗀 문장) ·
    상태(`값 필요` · `값 채움` · `제거함` + 누가 · 언제) · 버튼(`값 넣기`/`접기` · `제거` · `되돌리기`). **보류가 0건이면 표를 안 그린다**
  - **`값 넣기`는 그 줄 아래를 펼쳐** 칸마다 입력을 보인다. 작은 머리 `넣을 값`(params) · `기대 결과`(expected) 아래에 칸 설명을 라벨로 쓴다 — 칸 이름(key)은 안쪽 말이라 앞에 두지 않는다.
    타입대로 글 · 숫자 · 켜고 끄기 · 고르기. **칸을 벗어나면 저장한다**(저장 버튼 없음). 비밀값 칸은 표에 안 나오고 반영 때 대상 서버 줄의 테스트 계정으로 채운다.
    펼친 칸은 `position: sticky; left: 0` — 좁은 화면에서 표를 옆으로 굴려 `값 넣기` 를 눌러도 입력 칸이 보이는 자리에 그려진다
  - **`제거`는 모달 없이 줄 안에서** 바로 한다 — `되돌리기` 로 되살릴 수 있어서다. 칸이 없는(fields 가 빈) 케이스는 `값 넣기` 없이 `제거` 만
  - **판정 색을 안 쓴다** (원칙 1) — 보류는 결과가 아니라 사람이 할 일이다. 칩 · 상태 글 · 거터 모두 잉크와 `--rule` 로
  - **반영 실패**(3회 중 실패)면 상태 카드의 실패 까닭 상자에 `3회 실행에서 실패했다 — <파일> — <첫 실패 문장> · …` 로 케이스마다 첫 실패 문장이 실린다(자르지 않는다 — 상자가 줄을 바꿔 다 보인다).
    넣은 값은 남아 고쳐 다시 누를 수 있다. 넣은 값에 테스트 계정 비밀번호가 들어 있으면 올리지 않고 `넣은 값에 테스트 계정 비밀번호가 들어 있어 올리지 않았다` 로 실패한다(값은 안 싣는다)
  - 860px 밑에서는 한 단으로 접고, 표는 옆으로 구른다(`overflow-x: auto`)
- **목록 한 줄 글** — 올리기 거절로 멈췄으면 `올리기 거절 — <까닭 첫 줄>`. 몇 단계에서 멈췄는지보다 고칠 것이 먼저다
- **재실행의 대조 상세는 자기 입력 목록으로 「화면만」을 가리지 않는다** — 입력이 원본 요청에 있어 자기 목록은 늘 비므로(원본이 화면만이었는지는 원본 상세가 말한다) `입력은 원본 요청 #N 것을 그대로 씁니다`. 표시 사본 설명도 `원본 요청 #N의 자료` 를 가리킨다
- **중단은 판정이 아니다** (원칙 1). 사람이나 한도가 멈춘 것이라 거터를 판정 색 아닌 `--rule` 로 둔다

- **숫자 칸 셋** — `만든 케이스 파일` · `훑은 화면`(역방향 아니면 `—`) · `토큰 (캐시 읽기 포함 · 지금까지)`(짧게 `1.2M`, 끝나면 `토큰 (캐시 읽기 포함)`. Grafana 「작성 토큰」은 입력+출력이라 수십 배 작다 — 라벨이 그 차이를 적는다)
- **마지막 활동** — 자식이 도는 동안 마지막 동작(에이전트의 `· `·`» ` 표지는 뗀다)과 `N초 전` · `N분 N초 전`. 아니면 `지금 하는 일` 에 단계 글
- **목록 줄** — 날것 단계 글(`끝` · 빈 칸) 대신 한 문장(`에이전트 순서를 기다리는 중` · `케이스 작성 단계에서 멈췄습니다` · `케이스 파일 N개를 만들었습니다`, `authoringStatus.ts` 의 `목록글`).

- 상태 칩의 색은 판정에만 — `완료` 는 `--pass`, `실패`·`응답 없음` 은 `--fail`, 나머지는 잉크 (원칙 1)

## 모달 (2026-09-18 추가)

**상자는 두 종류다 (2026-09-22 에 갈랐다).** 생김새는 같고 **여는 주체가 다르다.**

#### ① 가로막는 상자 — 화면이 연다. 아껴 쓴다

사람이 다른 일을 하고 있는데 화면이 끼어드는 것이다. **아래 목록뿐이다** (개수를 적지 않는다 — 셋이라 적힌 채 넷이 돼 있었다).

- 되돌릴 수 없는 일을 하기 전 확인 (SPEC §8.3 실행 멈추기)
- 작성 요청 중단 · 폐기 확인 (도메인/작성 §7 「중단 · 폐기 · 진척」) — 실행 멈추기와 같은 상자·같은 버튼 모양이다
- **실행이 진행 중의 진행과, 끝났을 때의 알림** (SPEC §8.9) — **한 상자가 갈라 그린다**
- **테스트 작성을 시작한 직후의 접수 확인과 진행** (위 「작성 상태」 · 시작 모달, 2026-09-28) — 방금 누른 사람에게만 뜬다.
  「화면을 갈아타면 무엇을 잃는가」 — 목록과 새 요청 폼을 잃는다. 한 건 더 넣으려는 사람이 돌아와야 한다
- 여러 건을 한 번에 실행하기 전 확인 (SPEC §8.10 여러 건 실행 모달)

**그 밖에는 화면이 상자를 열지 않는다.** 알림·안내·오류는 화면 안의 줄로 적는다.

**2026-09-18 에는 두 자리였다.** 가로막는 자리를 늘리면 가로막힘이 흔해지고,
흔해지면 사람이 읽지 않고 닫는다 — **아껴 쓴다는 그 판단은 그대로 살아 있다.**
**2026-09-21 에 여러 건 실행 확인을 더했다.** 여러 건을 거는 것은 시간과 실행 기록을 쓰는 일이라
누르기 전에 무엇이 도는지 확인할 자리가 필요하다.
목록에서 고른 것이 확인 없이 바로 걸리면 무엇이 걸렸는지 볼 자리가 아예 없다.

#### ② 열어서 보는 상자 — 사람이 연다. 목록에서 안 나가려고 쓴다

**가로막는 것이 아니다.** 사람이 「보여 달라」고 눌러서 열린다.
막 대신 **목록 위에 겹쳐 띄워, 닫으면 보던 자리와 검색 조건이 그대로 남게** 하는 장치다.
화면을 통째로 갈아타면 돌아올 때 조건이 풀리고 스크롤 자리를 잃는다.

- 케이스 상세 (SPEC §8.1) — `[상세]` 를 눌러서 연다
- 실행 하나의 결과 (SPEC §8.7 → §8.3) — `[결과 보기]` 를 눌러서 연다

**이 목록도 닫혀 있다.** 「사람이 눌렀으니 괜찮다」가 아무 데나 상자를 여는 핑계가 되면
①의 절약이 뒷문으로 무너진다. 늘리려면 **「화면을 갈아타면 무엇을 잃는가」에 먼저 답한다.**

**②는 ①을 안에 담지 않는다.** 포커스를 가두는 장치가 둘 겹치면
키보드만 쓰는 사람이 빠져나올 길을 잃는다. ② 안에서 알릴 일이 생기면 **상자 안의 줄**로 적는다.

**왜 2026-09-22 에 갈랐나** — 앞 판은 종류를 안 나누고 「모달은 가로막는 장치다」 한 줄로 시작해

## 반응형

620px 미만에서 목록 행은 **3단**으로 접힌다 — 거터가 전체 높이를 덮고 번호·이름·오른쪽이 세로로 쌓인다.
**2026-09-21 에 2단에서 3단으로 고쳤다** — 앞 판이 「2단」이라 적고 있었는데 실제 격자는 세 줄이었다.
줄에 입력 칸이 들어가면 그만큼 더 길어진다.

입력 폼은 라벨이 값 위로 올라간다. 목록 줄의 입력 칸도 같다 — 62px 라벨 열을 그대로 두면 375px 에서 값 칸이 안 남는다.
**손가락으로 누르는 자리는 44px 이다** — 줄의 `상세`·`실행` 버튼과 입력 칸.
증적 문서 출력은 A4 고정폭이므로 반응형 대상이 아니다.

## 접근성 기준

- 포커스 링은 `--ink` 2px, `outline-offset: -1px`. 버튼은 `--fail` 2px로 구분
- 판정은 색만으로 전달하지 않는다. 항상 글자를 같이 쓴다
- **비활성 버튼의 이유는 말풍선(`title`)이 아니라 화면 줄로 적는다** (2026-09-20 결정).
  `title` 은 마우스를 올려야 뜨는데 **휴대폰에는 올릴 마우스가 없고**,
  `disabled` 버튼은 키보드 탭 대상에서도 빠져서 키보드로도 못 닿는다.
  완료 기준이 실행 결과 화면을 **휴대폰에서 보게** 요구한다 (아래 44px 줄과 같은 두 화면이다).
  「폼 자동 생성 규칙」의 「버튼을 비활성화하지 말고 누르면 오류를 보여준다」와는 다른 자리다 —
  그쪽은 **폼 칸의 검증 실패**를 칸 아래에 적는 규칙이고, 이쪽은 **비활성화가 맞는 버튼**의 이유를 어디에 두느냐다

### 명암비 (2026-09-18 결정)

**글자는 4.5:1, 큰 글자와 UI 요소는 3:1.** WCAG 2.1 AA 다.
「큰 글자」는 24px 이상, 또는 굵게(700 이상) 쓴 18.5px 이상이다 — 집계 숫자(20px/800)가 여기 해당한다.

지금 색 조합의 실측값이다 (2026-09-21 재측정). 토큰을 바꾸면 **이 표를 다시 재고 고친다.**

**서비스 색 대조는 2026-09-22 에 걷었다.** 그 색이 화면 어디에도 안 앉으므로 잴 면이 없다.
설정 화면의 색 고르개도 같이 없앴다 — **쓰이지 않는 것을 고르게 하지 않는다.**

**남겨 두는 교훈 하나** — 앞 판은 「기준 면을 밝은 면으로 못 박는다」였다.
사이드바가 짙어지면서 색 네모가 어두운 바탕에 닿아 **기준의 방향이 뒤집혔기** 때문이다
(기본값 `#3A5FCD` 가 밝은 면에서 5.68, 짙은 사이드바에서 2.75 로 미달이었다).
**사람이 고르는 임의의 색은 앉는 면이 바뀔 때마다 기준이 흔들린다** —
색을 다시 들일 일이 생기면 이 문장부터 읽는다.

**앞 판이 여기에 세 문단을 더 들이고 있었다** — 네모에 밝은 테두리를 둘러 기준 면을 지키는 법,
기준을 4.5 에서 3 으로 내린 근거, 색 격자 전수 확인. **2026-09-22 에 전부 걷었다.**
잴 네모가 없어져 근거가 사실이 아니게 됐기 때문이다 (CLAUDE.md §2.7 ②).
쓸모 있는 한 줄만 위에 남겼다 — **앉는 면이 바뀌면 기준의 방향이 뒤집힌다.**

**괘선(`--rule` 1.61 · `--rule-soft`)은 기준 밖이다.** 정보를 전달하는 UI 요소가 아니라
행 사이를 눈으로 쉬게 하는 장식이고, 행 구분은 **간격과 배치**가 이미 하고 있다.
괘선이 안 보여도 목록을 읽는 데 지장이 없어야 한다 — 그것이 이 예외의 조건이다.
- 손가락으로 누르는 영역 최소 44px 은 **실행 기록 목록과 실행 결과** 두 화면에만 건다 (2026-09-17 결정).
  휴대폰으로 하는 일을 「끝났나 보기」 하나로 좁혔기 때문이다 (SPEC §8). 나머지 화면은 책상용이다
- `prefers-reduced-motion`을 존중한다. 애초에 전환 효과를 거의 쓰지 않는다
