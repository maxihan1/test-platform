## 왜

직전 PR #32 의 검사가 **치명 1** 로 냈다. SPEC §8.4 의 「내는 형식」 표가
**「이 표가 형식의 정본이다. 결과 화면에서 골라 만든다」**고 못 박았는데
`RunResult.tsx:127` 이 `api.makeEvidence(data.runId, 'PDF')` 로 **PDF 를 박아 놨다.**

**서버는 처음부터 셋을 다 받고 있었다.** 화면만 안 물어봤다.
그래서 완료 기준 상자 넷이 **누를 버튼이 없어서** 못 채워진 채였다.

같이 **비밀값 꼬리표를 단 데모 케이스**를 만든다. 지금 `tests/demo/` 열 건 어디에도
비밀값 칸이 없다(꼬리표 0건 · 이름으로 걸리는 것 0건) — **가리기가 되는지 화면에서 볼 방법 자체가 없다.**
상자 하나가 더 열린다.

## ★ 화면 설계 — 계획이 정한다 (구현자에게 넘기지 않는다)

**버튼 셋을 RUN 머리에 나란히 둔다.** `PDF 만들기` · `엑셀 만들기` · `HTML 만들기`.

**모달은 탈락이다.** `docs/DESIGN.md:169` 가 **「모달은 두 자리에만 쓴다 — 되돌릴 수 없는 일을 하기 전
확인과 실행 완료 알림. 그 밖에는 쓰지 않는다」**고 명시한다. 형식 고르기는 둘 다 아니다.

**드롭다운 + 버튼 하나도 탈락이다.** 형식마다 상태가 따로다 —
DB 의 부분 유일 인덱스가 `(run_id, format) WHERE status='PENDING'` 이라
**PDF 는 다 만들어졌는데 엑셀은 만드는 중**인 상황이 실제로 생긴다.
드롭다운은 **고른 하나의 상태만 보여주고 나머지 둘을 숨긴다.**
셋을 나란히 두면 세 상태가 한눈에 보이고, **고른 형식을 기억하는 화면 상태를 안 만들어도 된다**(버그 날 자리 하나 줄어든다).

**버튼 자리는 지금과 같다** — `evidence.ts:2` 가 「증적은 실행 단위 1부이므로 버튼은
항목 상세가 아니라 **실행 결과의 RUN 머리**에 둔다」고 적어 뒀다. 그 판단을 뒤집지 않는다.

**버튼 글자는 동사로 끝난다** (`DESIGN.md:118`). 상태별로 이렇다.

| 그 형식의 상태 | 글 | 누를 수 있나 |
|---|---|---|
| 실행이 도는 중 | `PDF 만들기` | ✗ (`title` 에 「실행이 끝나면 만들 수 있습니다」) |
| 그 형식이 `PENDING` | `PDF 만드는 중입니다` | ✗ |
| 그 형식의 마지막이 `FAILED` | `PDF 다시 만들기` | ✓ (`title` 에 사유) |
| 그 형식을 이미 만들었다 | `PDF 다시 만들기` | ✓ |
| 그 형식이 없다 | `PDF 만들기` | ✓ |

**좁은 화면** — `.tally` 에 `flex-wrap` 이 없다(`styles.css:150`). 지금은 버튼 하나여서 안 넘쳤다.
셋이 되면 넘치므로 `flex-wrap: wrap` 을 더한다. 완료 기준에
「휴대폰으로 실행 기록 목록과 실행 결과를 보고 누를 수 있다」 상자가 있다.
