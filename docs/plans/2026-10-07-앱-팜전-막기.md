# 디바이스 팜 전에 막을 것 둘 — 요청 디바이스 대조 · timeoutMs 상한 (APP-F1-07)

등급: 3 · 갈래: WS-B · 2026-10-07 · PR #176

## 도메인 정리

| 무엇 | 지금 | 이번 뒤 |
|------|------|--------|
| 정식 실행 `POST /api/runs` 의 항목 `platforms` | 케이스 선언(`test_case.platforms`)과 대조하지 않는다 — 앱 케이스를 `['desktop']` 으로 보내면 실행 위치 검사 · 디바이스 줄을 건너뛰고 컨테이너 러너로 간다 | 선언 밖 디바이스가 하나라도 있으면 400 `INVALID_REQUEST` — 실행을 만들기 전에(트랜잭션 안, `CASE_NOT_FOUND` 다음) |
| 항목 `timeoutMs` | 양의 정수면 받는다. `run_item.timeout_ms` 가 INTEGER 라 약 24.8일까지 들어가고, 그만큼 디바이스 잠금 · 전역 동시성 자리를 쥔다 | 300000(5분)을 넘으면 400 `INVALID_REQUEST`. 기본 300000 그대로 — 줄이는 데만 쓴다 |
| 케이스 테스트 실행 | 이미 선언을 대조하고(400) 제한을 300000 으로 고정한다 | 그대로 |
| 러너 `/execute` | `timeoutMs` 상한 없음 | **안 고친다** — 부르는 쪽이 admin 하나라 admin 에서 막으면 된다 |
| 화면 | 선언된 디바이스만 체크박스로 보내고 `timeoutMs` 를 안 싣는다 | 바뀌는 것 없음 |

관련 절 — 도메인/실행 §7 `POST /api/runs` · §8.2(디바이스 체크박스), 공통/3-공유계약 §7.1 `timeoutMs` 줄.

## 왜

- PR #174 게이트 2 보안 검사가 넘긴 주의 둘(진행판 `APP-F1-07`). 로컬 정식 실행은 디바이스 팜 전까지의 임시 길이고, 그동안 디바이스 잠금(`phone.ts`)이 유일한 방어다
- **게이트 0 (2026-10-07 사용자)** — 두 거절을 명세에 적고 코드로 막는다. 상한은 **5분** — 사용자가 5 · 30 · 60분 중 골랐다.
  근거: 화면 실행 기본값 · 테스트 실행 고정값 · 시나리오 케이스 한 칸 몫이 모두 300000 이고, 정식 실행 검사 · 스크립트 어디에도 300000 넘게 보내는 곳이 없다.
  느린 팜 폰 때문에 더 필요해지면 그때 올린다
- 사용자 질문 「디바이스 팜에서 예약제로 쓸 건데 문제 있어?」 → 없다. 예약은 「누가 언제 폰을 쓰나」, 이번 일은 「잘못된 요청 거르기」라 팜이 붙어도 둘 다 필요하다. 예약 끝 시각과 제한 시간의 관계는 팜 작업 때 정한다
- 실측(코드 · 검사) — 정식 실행을 부르는 검사(`store` · `routes` · `runs` · `unconfirmed` · `savedInput` · `auth/gate`)는 전부 선언 안의 디바이스만 요청한다(`auth/gate.test.ts` 는 기본 선언 `["desktop"]` 에 desktop). 그래서 기존 검사를 고칠 일은 없다. `timeoutMs` 는 5000 · 7000 · 300000 뿐이다(300010 · 330010 은 시나리오 검사 — 이번 통로 밖)
- LEARNINGS
  - 2026-10-07 PR #174 — detail 이 화면 문장과 같은 말이면 두 번 뜬다 → 새 detail 은 「무엇이 틀렸나」(케이스 번호 · 디바이스)만 싣는다. 화면 `INVALID_REQUEST` 문장은 「입력한 값 중에 형식이 맞지 않는 것이 있습니다」
  - 2026-10-06 zod `z.object` 는 모르는 칸을 버린다 → 상한은 `runBody` 의 `timeoutMs` 칸 자체에 건다

## 명세가 안 정한 것 — 정한 것

| 무엇 | 정한 것 |
|------|--------|
| 거절 코드 | 새 코드를 만들지 않고 `INVALID_REQUEST` — 화면은 이런 요청을 만들지 않아 새 안내 문장이 필요 없다. 테스트 실행의 같은 거절도 `INVALID_REQUEST` 다 |
| 대조 자리 | `createRun` 안 — 이미 `test_case` 를 읽는 질의에 `platforms` 를 더한다. 트랜잭션이 되돌리므로 `test_run` 이 안 남는다 |
| 거절 순서 | 실행 위치 검사(`실행위치를본다`)가 먼저다. 그래서 웹 케이스를 `['android']` + `farm` 으로 보내면 409 `FARM_OFF` 가 먼저 난다 — 어느 쪽이든 거절이라 순서를 바꾸지 않는다 |
| 상한 숫자의 자리 | **게이트 1 반영** — `DEFAULT_TIMEOUT_MS` 를 `store.ts` 에서 `location.ts` 로 옮기고 `runBody` 상한과 `createRun` 기본값이 같은 상수를 쓴다(쓰는 곳은 `store.ts` 한 곳뿐). 「기본값이 곧 상한」이 한 자리에서 지켜진다. 테스트 실행의 `제한ms` 는 이번에 묶지 않는다 |
| 대조 자리 (게이트 1 반영) | 판정은 `location.ts` 의 순수 함수 `선언밖디바이스(items, 선언)` → `{ tcId, platform } \| null`. 문장은 `store.ts` 가 자기 `PLATFORM_LABEL` 로 만든다 — `store.ts` 가 이미 398줄이라 판정 루프를 거기 두지 않는다 |

android 항목은 전부 디바이스 줄에 한꺼번에 선다(dispatcher.ts:72). 반복 1000(상한)이면 요청 하나가 디바이스를 최대 약 83시간 쥐고 그동안 테스트 실행은 `DEVICE_BUSY`. 팜 예약 끝 시각과 부딪힌다. 팜 러너가 admin 밖에서 닿게 되면 「러너는 안 고친다」의 전제(부르는 쪽이 admin 하나)도 바뀐다.
고칠 것: 이번엔 안 고친다. WORKSTREAMS 「📐 Appium」 팜 항목에 한 줄 남긴다

### 주의 7 — 선언이 바뀌기 전 열어 둔 실행 창 · 정기 실행이 드물게 400 을 받는다 (ceo · 경미)
그대로 받아들여도 된다. detail 에 케이스 번호와 디바이스가 들어 원인은 보인다

### 통과한 것
- 구멍을 닫는 자리가 맞다 — `createRun` 이 정식 실행의 유일한 생성 길이고, 트랜잭션 안 `CASE_NOT_FOUND` 다음 · `INSERT test_run` 앞이라 되돌리면 `test_run` 이 안 남는다. 라우트가 그 밖 `RunInputError` 를 400 + `detail` 로 낸다(routes.ts:88-95)
- 두 길(앱 케이스를 desktop 으로 · 웹 케이스를 android 로)이 다 막힌다. 정기 실행 · 화면 두 길(RunSetup · pickRun)은 선언값만 보내 안 깨진다. 시나리오는 요청이 디바이스를 정하지 않아 같은 구멍이 없다
- 기존 검사 영향 없음. `gate.test.ts` 는 가짜 `/runs` 라 `createRun` 까지 안 간다 — 결론은 맞고 근거 문장만 다르다
- 거절 순서 유지가 맞다 — `routes.test.ts` FARM_OFF 검사(`XBR-010` 이 표에 없음)는 위치 검사가 먼저여야 409 를 받는다
- 상한은 `runBody` 칸에 거는 것이 맞다. `savedInput` 은 `timeoutMs` 를 채우지 않아 우회 길이 없다
- `XBP` 접두사 충돌 없음 · 명세 정본 하나 + 가리키기 둘 · 계약 블록 대기 → 반영 완료 흐름이 §1.2 · §2.7 과 맞다 · CI 에 postgres 가 있어 DB 검사도 CI 에서 돈다
- 참고(범위 밖): `routes.test.ts` 2줄 「CI에는 postgres가 없다」 주석은 낡았다
