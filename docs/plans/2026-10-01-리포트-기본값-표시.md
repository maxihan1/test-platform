# 증적 · 항목 상세에 기대결과가 「없음」으로 나오는 버그

등급: 3 · 갈래: WS-D(리포팅) · WS-E(화면) · 2026-10-01 · PR #123 (여섯 요청 중 묶음 ①)

## 도메인 정리

- BC: 리포팅(§3.3 증적 재현 · §8.4 항목 상세) · 실행(§3.2 스냅샷 · §8.3 값 한 줄). **계약 변경 없음** — kit 타입 · 러너 HTTP · DB 칸 · Admin API 응답 모양이 그대로다
- 이 PR 이 바꾸는 표면: 서버 증적 수집(`reporting/collect.ts`) · 화면 칸 만들기(`web/mask.ts`) · 항목 상세 화면(`web/ItemDetail.tsx`) · 명세 문장 세 곳

| 누가 | 무엇이 바뀌나 |
|---|---|
| 증적(PDF · 엑셀 · HTML) | 값이 빈 칸을 박제된 스키마의 기본값으로 채운다 → 「기대 결과 없음」 · 「입력 없음」이 기본값으로 돈 케이스에서 사라진다 |
| 결과 목록의 값 한 줄 | 같은 규칙. 기본값으로 돈 항목도 「어떤 값으로 돌렸나」가 보인다 |
| 항목 상세 화면 | 위 규칙 + **기대결과 칸을 더한다**(§8.4 「블록 모양은 같다」 — HTML 증적에는 이미 있다) |

## 왜

케이스 값을 안 고치고 실행하면 그 칸은 요청에 `{}` 로 실리고(`web/pickRun.ts` · `scripts/run-scheduled.ts` 등) 그대로 `run_item.expected` · `params` 에 박제된다.
케이스는 kit 안(`packages/kit/src/runtime/inputs.ts`)에서 코드 기본값으로 돌지만 그 값은 기록에 안 돌아온다.
`collect.ts` `toFields()` 와 `mask.ts` `fieldsOf()` 가 **값 쪽만** 훑어 빈 목록을 만들고, HTML 증적은 그것을 「기대 결과 없음」으로 그린다.

박제된 스키마(`run_item.expected_schema` · `param_schema`)에는 그 실행 때의 `default` 가 들어 있다 — kit 이 `z.toJSONSchema(..., { io: 'input' })` 로 기본값을 남긴다.
그 실행이 쓴 기본값과 같은 값이고 박제 값만 읽으므로 §3.3 「리포팅은 test_case 를 읽지 않는다」가 그대로 지켜진다. 지난 실행도 다시 뽑으면 바르게 나온다.

**실행을 만들 때 기본값을 채워 박제하는 길(쓰는 쪽)은 이번에 안 한다.** 지난 실행을 못 고치고, 러너에 가는 값이 바뀌는 일이라 범위가 넓다.
읽는 쪽 한 곳씩(서버 · 화면)이면 지난 실행과 앞으로의 실행이 같이 고쳐진다.

## 명세가 안 정한 것 — 제안

| 무엇 | 정한 것 |
|---|---|
| 칸 순서 | **박제된 값의 순서를 먼저, 그 뒤에 기본값으로 채운 칸을 스키마 순서로.** 값이 다 차 있던 행은 지금과 글자 하나 다르지 않다(§3.3) |
| 기본값도 값도 없는 칸 | 만들지 않는다(지어내지 않는다). 선택 칸이 이 경우다 |
| 비밀값 칸의 기본값 | 다른 칸과 같이 `********` 로 가린다 |
| 기본값에서 온 칸 표시 | 따로 표시하지 않는다. 그 실행이 실제로 쓴 값이기 때문이다 |

## Plan

### 할 일 1. 증적 수집이 빈 칸을 박제 스키마의 기본값으로 채운다

- **RED** — `collect.test.ts` 에 실행 「XDC 기본값」을 더한다. `expected '{}'` + 스키마에 `default` 셋(하나는 비밀값), `params` 는 한 칸만 차 있고 나머지는 기본값 · 기본값 없는 선택 칸 하나. 단언: 기대값 칸이 기본값으로 차고 비밀값은 가려진다 · 입력값은 차 있던 칸이 먼저 오고 기본값 칸이 뒤에 온다 · 기본값 없는 칸은 없다. 지금은 `Object.entries(values)` 만 훑어 기대값이 `[]` 다
- **GREEN** — `toFields()` 가 값 쪽을 다 돈 뒤 스키마 `properties` 에서 값에 없고 `default` 가 있는 키를 이어 붙인다
- **REFACTOR** — 없음
