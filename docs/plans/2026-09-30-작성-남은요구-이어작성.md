# 작성 누락 막기 ③ — 남은 요구로 이어 작성

등급: 3 · 갈래: WS-작성 · 2026-09-30 · PR #121 (셋 중 ③ · REV-F3-12)

## 도메인 정리

- BC: 작성(도메인/작성 §3.6 「★ 원장」 · §7). 계약 블록은 §3.6 「★ 원장」 끝의 `continueFrom` 블록(2026-09-30 게이트 0 승인)과
  이번 게이트 0 추가분(상세 `continueFrom` · `canContinue` · `continuedBy` · 목록 `continueFrom` · 409 `ALREADY_CONTINUED` · `NOTHING_LEFT` 재료)이다
- 「병합됐다」 = 원본 뿌리의 최신 실행이 성공한 반영(MERGE DONE) — 게이트 0 사용자 결정. GitHub 에서 사람이 직접 병합한 요청은 이어 작성하지 않는다

| 누가 | 무엇이 바뀌나 |
|---|---|
| DB | `authoring_request.continue_from` · CHECK(AUTHOR 만) · 유일 색인(폐기 안 된 것 하나) |
| 서버 | `POST /api/authoring/requests { kind: 'AUTHOR', continueFrom }` — 판정 · 자료 복사 · 줄 세우기 · 상세 `canContinue` · `continuedBy` · 목록 `continueFrom` |
| 에이전트 | 집을 때 원장을 main 표와 맞대 남은 번호를 센다 · 자식에게 `--- 이어 작성 ---` 절 · 남은 게 없으면 FAILED |
| 자식 스킬 | `tpx-author` `references/continue.md` — 남은 번호만 맡는다 |
| 화면 | 반영 끝난 요청의 「다음 단계」에 「남은 요구로 이어 작성」 · 이어받은 요청 표시 |

## 왜

요청 하나는 120분이라 큰 기획서는 한 번에 못 덮는다. 5877(데모마켓)은 172개 중 48개만 케이스가 됐고 124개가 `다음 요청` 으로 표에 남았다(`docs/cases/MKT.md`).
원장 대조(PR #119)와 셈(PR #120)이 남은 것을 보이게 했지만 그것을 다음 요청으로 넘길 길이 없다 — 지금은 같은 기획서를 새로 넣어 처음부터 돌리는 수밖에 없다.

LEARNINGS 근거:
- 2026-09-28 「재실행은 자기 자료가 없는데 요청 번호 = 자료 주인으로 쓴 자리가 셋 더 있었다」 — 자료를 **참조**하면 같은 사고가 난다. 그래서 **복사**한다(아래 제안 표)
- 2026-09-30 「셈 줄을 최신 실행에 붙여 반영하면 사라질 뻔했다」 — 남은 수는 「머지를 뺀 최신 작성 실행」이 아니라 **반영된 그 실행**(MERGE 의 원본)의 셈을 본다
- 2026-09-30 「셈 거절로 PR · 이어하기를 잃을 뻔했다」 — 이어 작성의 남은 번호 계산이 실패해도 끝내기 몸을 막지 않는다(자식 전 FAILED 는 설정 · 자료 문제만)

## 명세가 안 정한 것 — 제안 (게이트 1 에서 정한다)

| 무엇 | 제안 |
|---|---|
| 자료 물려받기 | **복사.** 원본 뿌리의 `INPUT` 자료 행과 파일을 새 요청 것으로 복사한다(표시 사본 · 역기획서는 안 가져온다). 새 요청은 보통 작성 요청과 같아 내려받기 · 표시 사본 `source` · 화면만 판정 · 에이전트 자료 읽기 · 다시 작성이 그대로 돈다. **게이트 0 에서 승인한 집기 `continuation.assetsFrom` 은 필요 없어진다(좁힘)** — 집기에는 행 칸 `continueFrom` 만 실린다. 대가 — 서버 디스크에 자료가 두 벌(한 요청 최대 20개 · 한 파일 20MB) |
| 옛 본문 · params | `spec_text` · `params` 도 원본 것을 복사한다 |
| 세우는 순서 | 한 묶음으로 DRAFT 행 + 자료 행 → 파일 복사 → 실패하면 행 · 폴더를 지우고 500 → DRAFT→PENDING. 파일이 다 복사되기 전에 에이전트가 집지 않게(지금 자료 올리기와 같은 이유) |
| 판정 순서 | 같이 온 칸 400 → 원본 확인(400 · 404 · 403) → `BAD_SOURCE`(AUTHOR 아님 · DRAFT · 폐기) → **뿌리 잠금 안에서** `NOT_MERGED` → `ALREADY_CONTINUED` → `NOTHING_LEFT` → 대조 재판정(`BAD_ENV` · `BAD_START_URL`) |
| 같이 온 칸 | `continueFrom` 과 `figma`(빈 배열 아님) → 400 `BAD_FIGMA_URL` · `compare` · `env` · `startUrl` → 400 `BAD_ENV`. 재실행이 역방향 칸을 거절하는 것과 같은 코드다 |
| `continueFrom` 모양 | 양의 정수가 아니면 400 `SOURCE_ID_REQUIRED` · RERUN · MERGE 번호면 409 `BAD_SOURCE` — 화면은 `rootId` 를 보낸다 |
| 병합됨 | 뿌리의 최신 실행(실패한 머지는 뺀다 — `최신실행`)이 `DONE` 인 `MERGE` |
| `NOTHING_LEFT` 재료 | 그 MERGE 의 원본(반영된 작성 실행)의 `result.coverage`. 번호 셈인데 `later` · `missing` 이 둘 다 비었거나 `{ none }` 이면 409. **셈이 없으면(옛 요청) 받는다** — 에이전트가 main 표로 다시 센다 |
| 한 번만 | 뿌리 잠금 안에서 폐기 안 된 이어 작성이 있으면 409 `ALREADY_CONTINUED`. 유일 색인 `authoring_request_continue_from_once`(`WHERE continue_from IS NOT NULL AND discarded_at IS NULL`)가 동시 누름을 한 번 더 막는다. 이어 작성한 요청을 폐기하면 다시 누를 수 있다 |
| `canContinue` | **뿌리 기준**(어느 실행 번호로 읽어도 같다) — 병합됨 ∧ 폐기 안 된 이어 작성 없음 ∧ 셈이 「남은 것 없음」이 아님. 권한은 화면이 본다(`canResume` 과 같다) |
| `continuedBy` | 폐기 안 된 이어 작성 요청의 번호. 없으면 null |
| 목록 `continueFrom` | 줄의 **뿌리** 것. 줄의 다른 칸은 최신 실행 것이지만 이 칸은 최신 실행(재실행 · 머지)에 없다 |
| 에이전트 남은 번호 | 집을 때 원장을 다시 뽑고(지금도 한다) **기준 SHA 의 main 표 · 케이스**와 맞대 `빠짐` ∪ `다음 요청` 제외. 저장된 `later` · `missing` 은 안 쓴다(사본이라 사람이 표를 고치면 낡는다 — WORKSTREAMS ② 「③ 에 넘길 것」) |
| 남은 게 없거나 원장 없음 | 자식을 띄우지 않고 `FAILED` — 「남은 요구가 없다 — main 의 표가 원장을 다 덮었다」 · 「원장이 없어 남은 요구를 모른다 — <까닭>」. 설정 · 자료 문제라 다시 해도 같다 |
| 자식에게 | 줄 프롬프트에 `--- 이어 작성 ---` 절(원본 번호 · 남은 수 · 앞 20개 · 전체는 `<자료>/continue.json`). 절차는 `tpx-author` `references/continue.md` — 남은 번호만 맡고 표의 다른 줄은 손대지 않는다 |
| 셈 | 이어 작성 실행도 **전체 원장** 기준(지금 규칙 그대로). 앞 요청이 덮은 것까지 들어 누적 진척이 보인다 |
| 다시 작성 · 이어서 작성 | 이어 작성 요청의 재실행 · 이어서 작성도 이어 작성 모드다 — 에이전트가 원본 상세(재실행이면 지금도 읽는다)의 `continueFrom` 을 본다 |
| 화면 버튼 | 「다음 단계」의 반영 끝(DONE MERGE) 상태에 항목 「남은 요구로 이어 작성」. 설명에 남은 수(셈이 있으면 `다음 요청 a · 빠짐 b`, 없으면 「에이전트가 main 의 표로 다시 센다」). 누르면 **새 번호** 상세로 간다 — 새 요청이라 실행 기록 규칙(같은 쪽에 머문다)의 예외다 |
| 이어받음 표시 | `continuedBy` 가 있으면 그 자리에 「이어 작성한 요청 #M」 링크. 이어 작성 요청은 상세 머리 부제와 목록 줄에 「#N 에서 이어 작성」 |
| Grafana | `continue_from` 칸 권한은 이번에 안 더한다 — 기획서 하나의 누적을 대시보드로 볼 때 후속(WORKSTREAMS) |
