**두 차로 나눈다.**
1차는 **스킨** — 색·글꼴·컨트롤 모양·문구. 갈래는 WS-E(화면) + WS-D(리포팅).

## 왜

사용자 판단은 「기능은 됐는데 어드민 페이지처럼 보인다」였다. 실물을 뜯어 본 원인은 셋이다.

1. **방안지 격자 배경** — `styles.css` 의 `body` 가 28px 격자를 두 겹 깐다.
   완성된 제품이 아니라 아직 안 그린 와이어프레임으로 읽힌다. 이것이 가장 크다
2. **글자가 전부 12~14px** — 크기 위계가 없어서 무엇부터 볼지 눈이 못 고른다
3. **조건이 테두리 칩 여덟 개 줄** — `조건칩들` 이 같은 모양 버튼을 한 줄에 늘어놓는다.
   도구 모음이 아니라 실험실 스위치판으로 보인다

**컨셉은 그대로 둔다.** 「대시보드가 아니라 검사 기록지」도, 「색은 판정만」도, 「카드 대신 괘선」도
그대로다. 바꾸는 것은 표현이다 — 바탕색, 글자 크기, 컨트롤 모양, 버튼 문구.

### 글꼴 — 시안대로 간다 (2026-09-21 결정)

**본문을 IBM Plex Sans KR 로 바꾸고 숫자·ID 에 IBM Plex Mono 를 쓴다.** Pretendard 는 걷어낸다.

처음 계획은 Pretendard 를 유지하자는 것이었다. 아래 문제 때문이다.

- `apps/admin/src/reporting/html.ts:128` 이 글꼴 파일을 **base64 로 증적 문서 안에 심는다.**
  지금 `PretendardVariable.woff2` 가 **2.0MB** 이고 base64 로 부풀어 약 2.7MB 가 문서마다 들어간다
- Pretendard 는 가변(variable, 파일 하나로 굵기 여러 단을 내는) 글꼴이라 한 벌로 끝나는데
  **IBM Plex Sans KR 은 가변이 아니다.** 굵기마다 파일이 따로다

**사용자가 시안대로 가기로 정했다.** 그래서 문제를 없애는 대신 **크기를 묶어 둔다.**

#### 굵기를 둘만 싣는다

시안은 400·500·600 셋을 썼다. **400 과 600 둘만 싣는다.**
목록 케이스명을 500 대신 **400** 으로 내리고, 강조가 필요한 자리는 600 을 쓴다.
아래 「타이포 크기표」가 이 둘만 쓰도록 이미 맞춰져 있다.

#### 증적 문서 크기에 상한을 건다

**1단계에 측정을 넣는다.** 글꼴을 갈아끼운 뒤 증적 문서 한 부를 실제로 뽑아 크기를 잰다.

| 기준 | 값 |
|------|-----|
| 지금 (Pretendard 한 벌) | 심기는 2.0MB, base64 약 2.7MB |
| 목표 | **base64 합 4MB 이하** |
| 넘으면 | 부분집합(subset, 안 쓰는 글자를 덜어낸 글꼴)으로 줄인다 |

> **부분집합을 만들 때 한글 음절 11172 자를 통째로 남긴다.** 상용 2350 자로 줄이지 않는다 —
> 케이스 이름과 입력값은 사람이 적는 값이라 어떤 글자가 올지 모른다.
> 증적 문서에 두부(□)가 하나라도 뜨면 그것은 제출물의 결함이다.
> 한자와 이모지는 덜어내도 된다 — 폴백이 받는다.

#### IBM Plex Mono 는 라틴만

TC ID · 소요시간 · 응답 코드 · RUN 번호 · 입력값 이름과 값에만 쓴다.
라틴 글자만 필요해서 굵기 둘(400·500)을 합쳐 50KB 안쪽이다. 증적 문서에 심어도 부담이 없다.

#### 공통

**CDN 은 쓰지 않는다** — 제품 안에 파일로 넣는다 (DESIGN.md 2026-09-18 결정 그대로).
폴백 스택도 숫자 폭이 고정인 것으로 적는 규칙은 그대로다.

> npm 패키지가 아니라 글꼴 파일을 받아 `apps/admin/src/web/fonts/` 에 넣는 일이다.
> 둘 다 라이선스가 OFL 이라 재배포에 걸림이 없다.
> 받는 것은 사람이 한 번 한다 (SETUP.md 에 절차를 적는다).
> **Pretendard 파일은 지운다** — 2.0MB 가 빠지므로 새 글꼴이 들어갈 자리가 그만큼 생긴다.

### 껍데기와 본문을 가르는 선 — 이 개정의 핵심

「판정 외의 색 금지」에 구멍을 내는 것이라 **어디까지가 껍데기인지를 숫자로 못 박는다.**
껍데기는 다음 넷뿐이다.

1. 맨 위 띠
2. 자리 넷의 밑줄
3. 표머리의 라벨과 그 바로 아래 괘선
4. 구획 제목 라벨

**이 넷 밖에서는 `--chrome` 을 쓰지 않는다.** 행 안에서, 배지에서, 본문 글자에서 색을 보면
그것은 여전히 판정이다. 이 문장이 SPEC 의 「본문의 색은 언제나 판정이다」와 짝이 되어야 한다 —
그래서 아래 §1.2 블록 둘째가 필요하다.

## 1차 계약 변경 (CLAUDE.md §1.2) — **2026-09-21 승인됨**

아래 두 블록은 사용자가 승인했다. `상태:` 는 아직 `대기` 다 — **SPEC 에 반영되지 않았다는 뜻**이다.
6단계에서 SPEC 에 옮겨 적고 **그 자리에서 `반영 완료 (2026-09-21, 어디에)` 로 바꾼다.**
승인과 반영을 한 낱말로 섞지 않는다 — 2026-09-20 에 끝난 할 일 넷이 「아직 안 했다」로 남은 자리다.

```

대상:    SPEC 공통/5-화면공통 §8 「맨 위 띠」
```

### B — 리포트의 직전 실행 비교와 실패 사유 묶기

**DB 는 안 바뀐다.** 필요한 값이 전부 이미 저장돼 있다 —
`run_item (tc_id, platform, started_at DESC)` 인덱스가 직전 실행 조회를 받고,
사유는 `run_item.error` 와 `run_item_step.assertions` 에 들어 있다.

새로 필요한 것은 조회 하나다. **기존 `GET /api/runs/:runId` 의 응답을 늘리지 않고
`GET /api/runs/:runId/insights` 를 새로 만든다** — 옛 응답을 건드리면 지금 화면이 같이 흔들린다.

돌려줄 것 — 직전 실행의 `runId` 와 시각, 케이스별로 `새로깨짐 | 계속깨짐 | 고쳐짐 | 그대로` 넷,
같은 사유로 묶은 실패 덩어리(대표 문장 · 건수 · 속한 항목).

- 「직전」은 **같은 서비스 · 같은 대상 서버**의 바로 앞 실행이다. 다른 서버와 견주면 거짓말이 된다
- 앞 실행이 없으면 그 칸을 통째로 안 그린다. 빈 칸을 자리만 잡아 두지 않는다 (SPEC §8)
- **검증** — 앞 실행이 없는 첫 RUN 에서 칸이 사라지는지. 통과→실패가 `새로깨짐` 으로 잡히는지

`ExecuteRequest` 에 `progressUrl` 을 더하고 admin 에 받는 자리를 하나 만든다.
`/execute` 를 스트리밍으로 바꾸지 않는다 — 러너와 admin 양쪽을 다 뜯어야 한다.

> 표면에 `MIGRATION` 이 안 붙는다. admin 을 여러 벌 띄우게 되면 그때 밖으로 옮긴다.

## 정말 이번 범위 밖
