## 왜

사용자 요청 3 · 4 · 6 (2026-10-01). 지금 케이스 코드를 바꾸는 길은 기획서 작성 · 재실행 · 보류 값 반영뿐이다.
어드민 서버는 git 권한이 없고 코드가 원본이라 DB 행을 지우거나 고쳐도 다음 스캔이 되돌린다. 그래서 코드는 에이전트가 PR 로만 바꾼다(§1 「영구히 하지 않는다」 — 화면은 코드 본문을 들지 않는다. 값과 동작만 보낸다).
보류 반영(`scripts/authoring-held-apply.ts` `값적기` · `표고치기`, `authoring-held-merge.ts` `계산` · `적용`)이 이미 「`.default(값)` 적기 · 파일 지우기 · 표 「제거함」」을 한다. 같은 장치를 main 위에서 돌린다.

## 명세가 안 정한 것 — 제안 (게이트 1 반영)

| 무엇 | 정한 것 |
|---|---|
| 한 요청의 범위 | **한 서비스 · 케이스 1~50건**. 같은 tcId 가 두 번 오면 400. 케이스마다 `{ tcId, delete: true }` 또는 `{ tcId, expected?, confirm? }`(둘 중 하나 이상). `delete` 와 다른 것은 같이 못 온다 |
| 기대값 칸 | 지금 카탈로그의 `expected_schema` 에 있는 칸만 · 글자 · 수 · 정수 · 참거짓 · 선택지(enum) 다섯 꼴만 · 칸 규칙(min · max · 길이 · 선택지)은 `execution/validate.ts` 로 본다 · **비밀값 칸은 거절**(표시 또는 이름) · 그 서비스 대상 서버 줄의 **테스트 계정 비밀번호와 같은 값은 거절**(코드에 원문이 박혀 저장소로 나간다) · 어긋나면 400 `BAD_EDIT` + `detail: '<tcId>.<칸>'` |
| 케이스 확인 | 케이스가 없거나 비활성 · 남의 서비스 접두사면 400 `BAD_EDIT`. `confirm` 인데 미확정이 아니면 400 `BAD_EDIT` |
| 겹치는 요청 | 같은 서비스에 **열린 케이스 고치기**(폐기 안 됨 · 최신 실행이 병합된 반영이 아님)가 같은 tcId 를 가지면 409 `EDIT_OPEN` + `detail: [요청 번호]`. 서비스 잠금 안에서 확인과 넣기를 한 번에 (게이트 1 — BLOCKER ⒜) |
| 다시 적용 | 원본이 케이스 고치기인 **재실행**을 받는다 — 원본의 `edits` 를 그대로 복사해 새 main 위에서 다시 계산하고 `author-<뿌리>` 에 덮어쓴다. 충돌한 고치기를 푸는 길이다 (게이트 1 — BLOCKER ⒝). 이어하기(`resume`)는 안 받는다 — 넘겨받을 작업 폴더가 없다(409 `NOT_RESUMABLE`) |
| 고치기 실행 | 케이스 고치기와 그 다시 적용 행은 `params.edits` 를 가진다 — 서버 · 에이전트가 이것으로 「고치기 실행」을 가른다 |
| 중단 · 폐기 | 고치기 실행은 **대기 중일 때만** 멈춘다(도는 중엔 자식이 없어 멈출 자리가 없다). 폐기는 FAILED · STOPPED 에 더해 **병합 안 된 DONE** 도 된다 — 버리지 못하면 그 tcId 가 영영 `EDIT_OPEN` 에 걸린다. 폐기해도 GitHub 의 PR 은 남는다(사람이 닫는다) (게이트 1 — 주의 3) |
| 에이전트 | 자식 없이 돈다 · 동시 상한의 자리 하나를 쓴다(타입 검사를 돌린다) · `도는번호` 에 올려 정리가 사본을 안 지운다 · 사본 기준은 GitHub main · 커밋 메시지는 지금 에이전트 모양(`[WS-작성] <서비스> 작성 요청 <뿌리>번 케이스`) · 올리는 파일은 `tests/**` · `docs/cases/*.md` 뿐(cases-only) · **바뀐 것이 없으면** FAILED 「고칠 것이 이미 반영돼 있다」 · 다시 켜질 때 도는 고치기 실행은 FAILED 로 닫는다(이어갈 폴더가 없다) |
| 확정 | `unconfirmed` 속성 줄을 통째로 뺀다(보류 `held` 빼기와 같은 함수). 요구사항 표는 안 고친다 — 표의 결과 칸은 그때 사람이 읽을 문장이고 기대값의 정본은 코드다. **PR 본문에 케이스마다 미확정 사유와 지금 기대값을 싣는다** — 확정은 화면에서 읽은 값을 정식 기대값으로 올리는 사람의 판단이다 (게이트 1 — 주의 5) |
| 삭제 | 케이스 파일을 지우고 요구사항 표의 그 tcId 칸을 「제거함(<tcId>)」로(보류 제거와 같은 함수). 실행 이력 · `test_case` 행 · 저장값은 남는다 — 다음 스캔이 비활성으로 돌리고, 비활성 케이스는 실행 대상이 아니라 저장값이 쓰이지 않는다 |
| PR 본문 | 케이스마다 한 줄 — `삭제` · `확정 — <미확정 사유> · 지금 기대값 <칸 값 …>` · `기대값 <칸>: <옛 값> → <새 값>` |
| 저장값 지우기 | 반영(MERGE)의 끝내기가 DONE 이고 원본이 고치기 실행이고 `result.pulled` 가 `false` 가 아니면, **같은 트랜잭션에서** 그 케이스 저장값의 **바꾼 기대값 칸만** 지운다. 남는 칸이 없으면 행을 지운다. 함수는 표 주인 쪽(`execution/savedInput.ts`)에 둔다 (게이트 1 — 주의 1 · 7) |
| 받아 온 뒤 끝낸다 | 반영 에이전트가 병합 뒤 **main 을 받아 온 다음** 끝내기를 보낸다. 못 받아 왔으면 `result.pulled: false` 를 싣고, 서버는 저장값을 안 지우고 error 에 「main 을 못 받아 와 저장값을 안 지웠다」를 남긴다 — 러너가 옛 기본값으로 도는데 저장값까지 없으면 판정이 뒤집힌다 (게이트 1 — 주의 2) |
| 목록 뒤 스캔 | 지금 반영과 같다 — 목록은 「다시 스캔」 뒤 바뀐다. 화면 PR(②-2)이 반영 완료 자리에 그 안내를 단다 |

### BLOCKER 1 — 병합이 안 되는 EDIT 는 빠져나갈 길이 없다
같은 케이스를 고치는 EDIT 둘, 또는 EDIT 와 열린 AUTHOR PR(같은 `docs/cases/<SVC>.md`)이 겹치면 뒤에 반영하는 쪽이 충돌한다. 다시 작성은 원본이 AUTHOR 가 아니라 막히고(routes.ts:157), DONE 은 폐기할 수 없어(stop.ts:95 · 151) 고칠 수 없는 PR 이 목록에 남는다.
고칠 것: ⒜ 같은 tcId 를 가진 미병합 EDIT 가 있으면 409 `EDIT_OPEN` ⒝ 원본이 EDIT 인 재실행(「다시 적용」)을 허락해 새 main 위에서 다시 계산하고 `author-<원본>` 에 덮어쓴다

### 주의 1 — 저장값 지우기가 끝내기와 같은 트랜잭션이 아니다
`끝내기` 는 풀 연결을 따로 쓴다(agentStore.ts:111). 고칠 것: `끝내기` 가 `손` 을 받게 하고 같은 트랜잭션에서 지운다

### 주의 2 — 지우는 때가 코드가 쓰이기 전이다
DONE 보고가 main 받아 오기보다 먼저 간다(authoring-merge.ts:202-207). 받아 오기를 건너뛰면 러너는 옛 기본값으로 도는데 저장값은 이미 없다. 고칠 것: 받아 온 뒤에 끝내고, 못 받아 왔으면 그 사실을 실어 서버가 안 지운다

### 주의 3 — 중단 · 재시작 규칙이 EDIT 와 안 맞는다
EDIT 는 진척을 안 올려 작성 중 내내 「중단」이 켜진다 · 에이전트가 다시 켜지면 `닫을RUNNING` 이 STOPPED 로 닫는다 · `도는번호` 를 안 넣으면 정리가 사본을 지운다. 고칠 것: 대기 중일 때만 멈춤 · 다시 켜질 때 FAILED · `도는번호` 등록

### 주의 4 — 화면 할 일 10 에서 빠진 자리
