## 도메인 정리

- BC: 작성(도메인/작성 §3.6 · §7) — 새 요청 종류 `EDIT`(케이스 고치기). 카탈로그(§8.1 상세 상자 · 목록 고르기)가 요청을 만든다
- **게이트 0 (2026-10-01 사용자 · 넷 다 권장안)**
  - 계약 변경 승인 — `authoring_request.kind` 에 `EDIT` · `source_id` 짝 CHECK · 새 통로 `POST /api/authoring/edits` · 집기(EDIT) 응답 `edits` · 확정 규칙
  - 기대결과를 바꾼 케이스를 **PR 전에 돌리지 않는다** — 타입 · 케이스 규칙 검사만. 기대값이 기획 기준이면 지금 화면이 틀려 실패할 수 있고, 그 실패가 곧 버그 신호다
  - 반영(머지)이 **병합되면 그 칸의 저장값을 지운다** — 저장값이 코드 기본값보다 앞서서, 안 지우면 반영한 값이 실행에 안 쓰인다
  - 요청은 **작성 쓰기**, 병합은 지금처럼 **admin**

| 누가 | 무엇이 바뀌나 |
|---|---|
| DB | `kind` CHECK 에 `EDIT` · 원본 짝 CHECK 를 `kind IN ('AUTHOR','EDIT') = (source_id IS NULL)` 로. **새 칸 없음** — 고칠 내용은 `params` 에 `{ edits: [...] }` |
| 서버 | `POST /api/authoring/edits` 가 고칠 내용을 검사하고 `EDIT` 행을 `PENDING` 으로 세운다 · 목록 · 상세 · 반영이 `EDIT` 를 뿌리로 본다 · 집기에 `edits` · 반영이 병합으로 끝나면 저장값 지우기 |
| 에이전트 | `EDIT` 를 집으면 자식(Claude) 없이 main 에서 사본을 떠 AST 로 고치고(보류 「값 적기」 재사용) 타입 · 케이스 규칙 검사 → `author-<번호>` 에 올려 초안 PR → DONE |
| 화면 | 케이스 상세 상자에 「코드 고치기」(기대결과 기본값 · 확정 · 삭제) · 목록에서 고른 것 「삭제 요청」 「확정 요청」 · 작성 목록 · 상세가 `EDIT` 를 「케이스 고치기」로 보이고 고칠 내용을 보인다 |
| 라우트 표 | `auth/routeTable.ts` 등급표(작성 쓰기) · `auth/scope.ts` 라우트표(질의) |

## 왜

사용자 요청 3 · 4 · 6 (2026-10-01). 지금 케이스 코드를 바꾸는 길은 기획서 작성 · 재실행 · 보류 값 반영뿐이다.
어드민 서버는 git 권한이 없고 코드가 원본이라 DB 행을 지우거나 고쳐도 다음 스캔이 되돌린다. 그래서 코드는 에이전트가 PR 로만 바꾼다(§1 「영구히 하지 않는다」 — 화면은 코드 본문을 들지 않는다. 값과 동작만 보낸다).
보류 반영(`scripts/authoring-held-apply.ts` `값적기` · `표고치기`, `authoring-held-merge.ts` `계산` · `적용`)이 이미 「`.default(값)` 적기 · 파일 지우기 · 표 「제거함」」을 한다. 같은 장치를 main 위에서 돌린다.

## 명세가 안 정한 것 — 제안

| 무엇 | 정한 것 |
|---|---|
| 한 요청의 범위 | **한 서비스 · 케이스 1~50건**. 같은 tcId 가 두 번 오면 400. 케이스마다 `{ tcId, delete: true }` 또는 `{ tcId, expected?, confirm? }`(둘 중 하나 이상). `delete` 와 다른 것은 같이 못 온다 |
| 기대값 칸 | 지금 카탈로그의 `expected_schema` 에 있는 칸만 · 글자 · 수(정수 칸은 정수만) · 참거짓 · 선택지(enum 값 중 하나) 넷만 · **비밀값 칸은 거절**(코드에 원문이 박힌다) · 칸이 없거나 타입이 틀리면 400 `BAD_EDIT` + `detail: '<tcId>.<칸>'` |
| 케이스 확인 | 케이스가 없거나 비활성 · 남의 서비스 접두사면 400 `BAD_EDIT`. `confirm` 인데 미확정이 아니면 400 `BAD_EDIT` |
| 상태 | 자료를 안 받으므로 `DRAFT` 없이 곧장 `PENDING`. 중단 · 폐기는 작성 요청과 같은 통로 · 같은 규칙. 재실행(RERUN) · 이어하기 · 이어 작성은 안 받는다(원본이 AUTHOR 가 아니면 409 `BAD_SOURCE` — 지금 규칙 그대로) |
| 에이전트 | 자식 없이 돈다 · 동시 상한의 자리 하나를 쓴다(타입 검사를 돌린다) · 사본 기준은 GitHub main · 커밋 메시지는 지금 에이전트 모양(`[WS-작성] <서비스> 작성 요청 <번호>번 케이스`) — 덮어쓰기 검사가 에이전트 것으로 읽는다 · 올리는 파일은 `tests/**` · `docs/cases/*.md` 뿐(cases-only) |
| 확정 | `unconfirmed` 속성 줄을 통째로 뺀다(보류 `held` 빼기와 같은 방식). 요구사항 표는 안 고친다 — 표의 결과 칸은 그때 사람이 읽을 문장이고 기대값의 정본은 코드다 |
| 삭제 | 케이스 파일을 지우고 요구사항 표의 그 tcId 칸을 「제거함(<tcId>)」로(보류 제거와 같은 함수). 실행 이력과 `test_case` 행은 남는다 — 다음 스캔이 비활성으로 돌린다 |
| PR 본문 | 케이스마다 한 줄 — `삭제` · `확정` · `기대값 <칸>: <옛 값> → <새 값>`. 비밀값은 받지 않으므로 실릴 수 없다 |
| 저장값 지우기 | 반영(MERGE) 이 DONE 으로 끝나는 끝내기 안에서(같은 뿌리 잠금) 원본이 `EDIT` 이면 그 케이스 저장값의 **바꾼 기대값 칸만** 지운다. 남는 칸이 없으면 행을 지운다(`savedInput.ts` 규칙과 같다). 삭제한 케이스의 저장값은 그대로 둔다(행이 남아 FK 가 걸린다) |
| 목록 뒤 스캔 | 지금 반영과 같다 — 병합 뒤 에이전트가 main 을 당기고, 목록은 「다시 스캔」 뒤 바뀐다. 이번에 안 바꾼다 |

### BLOCKER 1 — 병합이 안 되는 EDIT 는 빠져나갈 길이 없다
같은 케이스를 고치는 EDIT 둘, 또는 EDIT 와 열린 AUTHOR PR(같은 `docs/cases/<SVC>.md`)이 겹치면 뒤에 반영하는 쪽이 충돌한다. 다시 작성은 원본이 AUTHOR 가 아니라 막히고(routes.ts:157), DONE 은 폐기할 수 없어(stop.ts:95 · 151) 고칠 수 없는 PR 이 목록에 남는다.
고칠 것: ⒜ 같은 tcId 를 가진 미병합 EDIT 가 있으면 409 `EDIT_OPEN` ⒝ 원본이 EDIT 인 재실행(「다시 적용」)을 허락해 새 main 위에서 다시 계산하고 `author-<원본>` 에 덮어쓴다

### 주의 1 — 저장값 지우기가 끝내기와 같은 트랜잭션이 아니다
`끝내기` 는 풀 연결을 따로 쓴다(agentStore.ts:111). 고칠 것: `끝내기` 가 `손` 을 받게 하고 같은 트랜잭션에서 지운다

### 주의 2 — 지우는 때가 코드가 쓰이기 전이다
DONE 보고가 main 받아 오기보다 먼저 간다(authoring-merge.ts:202-207). 받아 오기를 건너뛰면 러너는 옛 기본값으로 도는데 저장값은 이미 없다. 고칠 것: 받아 온 뒤에 끝내고, 못 받아 왔으면 그 사실을 실어 서버가 안 지운다

### 주의 3 — 중단 · 재시작 규칙이 EDIT 와 안 맞는다
EDIT 는 진척을 안 올려 작성 중 내내 「중단」이 켜진다 · 에이전트가 다시 켜지면 `닫을RUNNING` 이 STOPPED 로 닫는다 · `도는번호` 를 안 넣으면 정리가 사본을 지운다. 고칠 것: 대기 중일 때만 멈춤 · 다시 켜질 때 FAILED · `도는번호` 등록

### 주의 4 — 화면 할 일 10 에서 빠진 자리
`AuthoringTodo.tsx`(이어서 작성 안내 · 다시 작성 칸 · 반영 완료 문구) · `authoringStatus.ts`(5칸 막대 · 멈춘 단계 글) · `AuthoringStatusCard` 칩. 반영 완료에는 「다시 스캔」 안내
