# E2E 시나리오 서버 ① — 시나리오 실행이 케이스 자리에 안 섞이게 먼저 막는다

등급: 2 · 갈래: WS-B (WS-시나리오) · 2026-09-29 · PR #106

## 도메인 정리

- BC: Execution(`apps/admin/src/execution/**`) · Reporting 의 견주기(`reporting/insights.ts`) · Grafana 대시보드(`infra/grafana/**`)
- 정본: 도메인/시나리오 §3.7 결정 10 「`test_run` 을 읽는 운영 코드는 전부 `kind` 를 거른다」 · 도메인/실행 §3.2(재기동 복구는 둘 다 닫는다) · §7(중단은 시나리오 실행에 409) · 리포팅 §8.5(모든 패널에서 뺀다)
- **계약 변경 없음.** 이 PR 이 끝내는 `대기` 계약 블록도 없다 — 시나리오 §7 블록은 ②③, 리포팅 블록은 WS-D 몫

| 자리 | 섞이나 | 이번에 |
|---|---|---|
| 실행 목록 `listRuns` · 머리 집계 `runSummary` (`거르는조건` 하나를 같이 쓴다) | **섞인다** — 서비스의 `test_run` 을 훑는다 | `r.kind = 'CASE'` |
| 견주기 「직전 실행」 (`compareWithPrevious`) | **섞인다** — 같은 서비스·대상 서버의 바로 앞 행을 고른다. 시나리오 실행이 고르면 모든 케이스가 「빠졌다」로 뜬다 | `kind = 'CASE'` |
| 중단 `abortRun` | 시나리오 실행이면 러너에 끊을 통로가 없다 | 409 |
| 재기동 복구 `recoverRunning` | 이미 시나리오 실행도 닫는다. **부품 행은 안 닫는다** | 안 끝난 부품 `NA` + `ABORTED` |
| Grafana 4패널 | 「최근 실행 목록」은 섞인다. 나머지 셋은 `run_item` 을 거쳐 구조상 안 섞인다 | 넷 다 `kind = 'CASE'` (명세가 「대시보드 질의도 단다」) |
| 번호 하나로 짚는 조회 — `findRun` · `collectRun` · `notify` · 증적 `실행상태` · `auth/scope` `자원의서비스` | 안 섞인다 — 부르는 쪽이 실행을 골랐다 | 그대로. 시나리오 실행의 단건 모양은 ③ · WS-D |
| `run_item` 을 거치는 조회 — 케이스 이력 `history.ts` | 안 섞인다 — 시나리오는 `run_item` 에 안 쓴다(결정 10) | 그대로 |

## 왜

사용자가 서버를 PR 셋으로 나눴다(2026-09-29). **이것을 먼저 넣는 까닭** — ③ 이 시나리오 실행을 만드는 순간부터
실행 기록·머리 집계·견주기·Grafana 「최근 실행 목록」에 케이스 실행인 척 섞인다. 거르기가 먼저 서 있으면 ②③ 은 쓰기만 하면 된다.
`?kind=scenario` 목록(E2E 탭)은 **③ 으로 넘긴다** — 시나리오 실행을 만드는 PR 에서 실제 부품 행으로 검사하는 편이 맞다.
