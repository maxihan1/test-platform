# 절차 단위 진행 — 무엇이 도는지 절차까지 보여준다

등급: 3 · 갈래: WS-C(주도) + WS-B + WS-E + WS-F(한 줄) · 2026-09-21

## 도메인 정리

| BC | 무엇이 바뀌나 |
|---|---|
| **Runner** (§3.4) | 돌고 있는 자식마다 **지금 몇 번째 절차인지**를 메모리에 들고, 물어보면 답한다. **DB 는 여전히 모른다** — 드는 것은 살아 있는 프로세스의 진행이지 저장된 상태가 아니다. 중단 통로(`POST /abort`)를 낼 때 쓴 것과 **같은 논거**다 |
| **Execution** (§3.2) | 러너에게 물어 화면에 그대로 흘린다. **영속화하지 않는다** — 증적의 정본은 끝난 뒤의 `run_item_step` 이다 |
| **Catalog / Reporting / 인증** | 안 건드린다. DB·마이그레이션 없음 |

관련 절 — §3.4 · §5.1 · §5.2 · §5.3 · §7 · §8.9.

## 왜

한 번 돌리면 최악 50분이다. 지금 진행 상자가 말하는 **「진행 중인 항목」은 근사치**다 —
`finishedAt === null` 인 **첫 항목 하나**를 고르는데, 동시 실행이 2라 도는 것이 여럿이고
상세 조회가 `tc_id, platform` 순이라 요청 순서와도 다르다 (`runProgress.ts` 의 주석이 이유 셋을 적어 뒀다).

그리고 **항목 안에서 절차가 어디까지 갔는지는 알 길이 아예 없다.**
그래서 「10분째 도는 중」과 「10분째 멈춘 것」이 화면에서 **똑같이 보인다.**
사람이 러너 로그를 직접 열어 보고 있는 이유가 그것이다.

### 게이트 0 — 방향을 뒤집었다 (2026-09-21 승인)

**계획 원안(`2026-09-21-청사진스킨.md` 의 A-2 절)의 밀기(push)는 철회됐다.**

원안은 `ExecuteRequest.progressUrl` 을 더해 **러너가 admin 에 POST** 하는 것이었다.
2단계가 코드를 읽어 막았다 — **러너에는 로그인 세션이 없다.**
`apps/admin/src/auth/scope.ts` 의 라우트표는 「등록된 모든 `/api` 경로가 여기 있어야 하고,
**표에 없으면 문이 막는다**」이다. 러너가 POST 하려면 **로그인 없이 지나가는 자리**를 새로 내야 하는데,
그런 예외가 **딱 하나 있었고 2026-09-17 에 일부러 삭제됐다** (`gate.ts:136` 에 기록이 남아 있다).

**당김(pull)이면 그 문제가 통째로 사라진다.** admin → 러너 방향은 **이미 있는 길**이다
(`apps/admin/src/execution/runner.ts` 에 `/execute` 와 `/abort` 가 있다).

```
[계약 변경 필요]
대상:    러너 HTTP (SPEC §5.2) — GET /progress 신설
         Admin API (SPEC §7) — GET /api/runs/:runId/progress 신설
         Shared Kernel (SPEC §5.1) — StepProgress 타입 신설
현재:    러너는 POST /execute 로 한 번 부르고 끝날 때 한 번 돌려줄 뿐이다.
         도는 동안 절차가 어디까지 갔는지 밖에서 볼 길이 아예 없다
제안:    1) 러너에 GET /progress 를 낸다. 지금 돌고 있는 항목마다
            { historyId, seq, title, startedAt } 을 돌려준다.
            러너는 이미 historyId 별 자식 프로세스 지도를 메모리에 들고 있다 (execute.ts 의 running)
         2) admin 이 그것을 그대로 화면에 흘린다. DB 에 넣지 않는다 — 마이그레이션 없음
         3) 기존 POST /execute · POST /abort · GET /api/runs/:runId 의
            요청·응답 모양은 한 글자도 바꾸지 않는다
이유:    한 번 돌리면 최악 50분이다. 항목 단위만으로는 「도는 중」과 「멈춘 것」이
         구분되지 않아 사람이 러너 로그를 직접 열어 보고 있다.
         당김이면 admin 에 인증 없는 통로를 새로 내지 않아도 된다 —
         admin 에서 러너로 가는 방향은 이미 있는 길이다 (execution/runner.ts)
영향:    WS-C(러너가 진행을 들고 답한다), WS-B(물어보고 흘린다),
         WS-E(모달이 그린다), WS-F(문 라우트표에 새 경로 한 줄)
상태:    대기
```

### ★ `totalSteps` 를 넣지 않는다 — 채울 값이 없다

원안의 알림 내용은 `{ historyId, seq, title, totalSteps }` 였다. **`totalSteps` 는 만들 수 없다.**

절차는 코드가 돌면서 하나씩 선언된다 — `packages/kit/src/runtime/step.ts` 의 `const seq = ++run.seq` 다.
**케이스가 끝나기 전에는 전체 개수를 아무도 모른다.** Playwright 도 모른다.
조건에 따라 절차 수가 갈리는 케이스도 있다.

「3 / 7」의 7을 채우려면 **없는 수를 지어내야 한다.** 지난 PR 에서 막대 네 칸을
`실행중`·`대기`로 가르려다 같은 함정에 빠졌다 — 그 구분을 가를 신호가 DB 에 없었다
(LEARNINGS 2026-09-21 「없는 구분을 있는 척하는 화면을 그릴 뻔했다」).

**지난 실행의 `run_item_step` 개수를 분모로 쓸 수도 있지만 이번에 하지 않는다.**
틀린 분모는 「거의 다 됐다」는 **거짓 신호**를 준다 — 그것은 모르는 것보다 나쁘다.
**「지금 4번째 절차: 로그인 후 화면을 확인한다 (12초째)」까지만 적는다.**

`startedAt` 이 이 기능의 핵심이다. **「몇 초째 이 절차에 머물러 있나」가
「도는 중」과 「멈춘 것」을 가르는 유일한 신호**이기 때문이다.

### ★ 가장 위험한 자리를 어떻게 가두나

`packages/kit/src/runtime/step.ts` 는 **모든 테스트 케이스가 지나가는 자리**다.
게이트 0 에서 A-2 를 미뤘던 이유가 정확히 이 파일이다. 세 겹으로 가둔다.

1. **diff 는 한 줄이다.** `const seq = ++run.seq` 바로 뒤, `await stepScope.run(...)` **앞**이다.
   판정 로직(`status` · `failed` · `stopped` · `assertions` · `screenshotPath`)에 **전혀 닿지 않는다**
2. **그 한 줄은 절대 던지지 않는다.** `progress.ts` 안에서 `try/catch` 로 삼킨다 —
   **진행 알림이 케이스를 깨뜨리면 안 된다.** 에러를 삼키지 않는다는 규칙(CLAUDE.md §3)의
   예외이고, 그 이유를 그 자리 주석에 적는다
3. **`PLATFORM_HISTORY_ID` 가 없으면 아무 일도 안 한다.** 사람이 손으로
   `npx playwright test` 를 돌릴 때, 그리고 `step.test.ts` 가 돌 때가 그 경우다.
   **기존 `step.test.ts` 가 한 줄도 안 바뀌고 전부 통과하는 것**이 할 일 2 의 검증이다

### BLOCKER 1 — 계획대로 하면 **진행 줄이 러너에 아예 도착하지 않는다**

**무엇이.** 할 일 2 는 `step.ts` 가 `process.stdout.write` 로 진행 줄을 흘린다고 적었다.
**kit 의 절차 코드는 Playwright 의 「워커 프로세스」 안에서 돈다.** 그리고 Playwright 는
워커에서 `process.stdout.write` 를 **자기 함수로 갈아치운다.**

```
node_modules/playwright/lib/worker/workerProcessEntry.js:1384
    process.stdout.write = (chunk, cb) => {
      this.dispatchEvent("stdOut", ipc.stdioChunkToParams(chunk));   ← IPC 로 보낼 뿐
      ...
      return true;                                                    ← 파일에 안 쓴다
    };

node_modules/playwright/lib/runner/index.js:288
      this._reporter.onStdOut?.(chunk, test, result);                 ← 리포터에게 넘긴다
```

`PlatformReporter` 에는 **`onStdOut` 이 없다.** 그래서 그 조각은 **그대로 버려진다.**
러너의 `child.stdout` 에는 한 글자도 안 온다.

**왜 문제.** 기능이 통째로 죽는다. 그런데 **검사는 초록이다** — 할 일 2 의 RED 는
vitest 에서 `process.stdout.write` 를 훔쳐보는데, vitest 는 Playwright 워커가 아니라
갈아치우기가 일어나지 않는다. **「검사가 원리적으로 못 보는 자리」가 또 나왔다**
(LEARNINGS 2026-09-21 — 높이 0 이었던 진행 막대와 같은 모양이다).

**고칠 것 — 길이 둘이고 서로 배타적이다. 계획이 하나를 골라 근거를 적어야 한다.**

| | 어떻게 | 대가 |
|---|---|---|
| **(a) 리포터가 넘겨준다** *(권장)* | `reporter.ts` 에 `onStdOut` 을 만들어 **모든 조각을 진짜 stdout 으로 다시 쓴다** | 계획의 「`reporter.ts` 에 손대지 마라」가 **틀렸다.** 그리고 마커를 상대 import 로 못 가져와 **글자를 복사해 둬야 한다** — 그 파일이 이미 `RESULT_MARKER` 로 같은 일을 하고 있고 `reporter.test.ts` 가 둘이 같은지 지킨다 |
| **(b) `fs.writeSync(1, …)`** | 갈아치운 함수를 건너뛰고 파일 서술자에 직접 쓴다 | **지금은 된다** — `runner/index.js:1926` 이 `options.onStdOut ? "pipe" : "inherit"` 라, 리포터에 `onStdOut` 이 없는 지금은 워커의 fd 1 이 러너 파이프 그 자체다. **누가 `onStdOut` 을 더하는 순간 조용히 끊긴다.** 문서에 없는 내부 동작에 기댄다 |

**★ (a) 를 고르면 함께 지켜야 할 것** — `onStdOut` 이 생기는 순간 워커 stdio 가
`inherit` 에서 `pipe` 로 **바뀐다.** 지금 그냥 흘러가던 테스트의 보통 출력까지 리포터를 거치게 된다.
**진행 줄만 골라 넘기면 나머지 출력이 사라지고**, 그러면 `execute.ts` 의
`tail(stderr) || tail(stdout)` 오류 문장이 **빈 문자열이 된다** (케이스가 문법 오류로
아예 안 돌았을 때 사람이 보는 유일한 단서다). **전부 다시 써야 한다.**

**그리고 검증을 바꿔야 한다.** vitest 단위 검사로는 이 자리를 영영 못 본다.
**케이스 하나를 러너로 실제로 돌려 진행 줄이 도착하는지**를 봐야 한다.

### BLOCKER 2 — 남의 서비스 절차 제목이 새어 나간다

**무엇이.** 계획이 「러너는 **목록**을 돌려주고 admin 이 **그대로** 화면에 흘린다」고 적었다.
러너의 `running` 은 **모든 실행의 자식**을 담는다 — 서비스가 섞여 있다.

**왜 문제.** 결제팀 사람이 자기 실행 화면을 열면, 동시에 돌고 있는 **회원팀 케이스의
절차 제목**이 상자에 뜬다. `auth/scope.ts` 는 **「이 `runId` 를 볼 자격이 있나」만** 본다 —
**응답 내용물은 안 본다.** 이 저장소는 2026-09-19 에 같은 모양의 구멍(IDOR)을 이미 한 번 겪었다.

**고칠 것.** admin 이 **자기 DB 에서 그 `runId` 의 `historyId` 목록을 읽어 교집합만** 남긴다.
「그대로 흘린다」를 계획에서 지운다. 할 일 5 의 RED 에 **「남의 실행의 진행은 안 나온다」**를 박는다.

### 주의 1 — `startedAt` 을 브라우저가 빼면 시계가 어긋난다

「12초째」를 브라우저가 `Date.now() - startedAt` 으로 계산하면 **러너 컨테이너 시계와

**러너가 잰 경과를 실어 보내거나** admin 이 서버에서 계산한다. 이 기능의 **핵심 신호**라
틀리면 기능 전체가 못 믿을 것이 된다.

도는 것이 **둘**이고 절차 제목은 **사람이 쓴 한국어 문장**이라 길다.
지난 PR 에서 「좁은 화면에서 제목이 한 글자씩 세로로 흘렀다」가 **2회** 났다.
계획에 **자르는 규칙이 없다.** 최소 셋이 필요하다 — 한 줄로 자르고 `…`,
flex 자식에 `min-width: 0` (이게 없으면 안 줄어든다), 한국어에 `word-break: keep-all`.
**jsdom 은 이 셋 중 무엇도 못 본다** — 지난 PR 처럼 `styles.test.ts` 에 **규칙이 있는지**를
단언하고 375px 로 눈으로 본다.

### 주의 3 — 절차 줄이 생겼다 없어지며 상자가 출렁인다

러너에 못 물어봤을 때 · 첫 절차 전 · 항목이 바뀌는 순간마다 줄이 사라진다.
2초마다 다시 묻는 화면이라 **상자 높이가 2초마다 튄다.** 자리를 비워 두지 않는 규칙(SPEC §8)과
부딪히지 않으면서 안 튀게 하려면 그 줄이 **항목 이름과 같은 덩어리 안**에 있어야 한다.

### 주의 4 — 「4번째 절차」는 진행이 아니라 그냥 번호로 읽힌다

분모가 없는 순번은 사람에게 **얼마나 왔는지를 말해 주지 않는다.**
이 화면에서 진행을 실제로 말하는 것은 **경과 시간이 2초마다 바뀌는 것**이다.
그러니 순번보다 **경과를 크게** 둔다. 그리고 그 값만으로는 **「느린 것」과 「멈춘 것」이
여전히 안 갈린다** — `run_item.timeout_ms` 가 이미 박제돼 있으니 **「12초째 / 제한 5분」**
으로 같이 적으면 그 구분이 생긴다. 새 값이 필요 없다 (§7.1).

BLOCKER 2 를 admin 쪽에서 거르기로 하면 계획에 그 말을 **명시**해야 한다.
러너에 `runId` 를 담게 하는 길도 있다 (`ExecuteRequest.runId` 를 이미 받는다).
**어느 쪽이든 정하고 적는다** — 안 적으면 구현자가 「그대로 흘린다」를 글자대로 읽는다.

### 주의 7 — 같은 실행을 여럿이 보면 러너 호출이 사람 수만큼 는다

2초마다 사람당 한 번이다. 지금 규모에서는 문제가 아니지만 **계획에 한 줄 적어 둔다.**

### 주의 8 — `공통/3-공유계약.md` §5.3 「러너 여러 대」 행

당김이면 admin 이 **모든 러너에게** 물어야 한다. 계획이 이미 §2.7 목록에 넣었다 — **좋다.**
다만 그 행이 지금 중단만 다루므로 **진행도 같은 전제**라는 것을 적어야 한다.

### 통과한 것

- **당김 방향 자체는 옳다.** 인증 구멍을 새로 내지 않고, `admin → 러너` 는 이미 있는 길이다
- **`totalSteps` 를 뺀 판단이 옳다.** 없는 수를 지어내는 것보다 모른다고 두는 것이 낫다.
  지난 실행을 분모로 쓰는 안을 검토하고 근거를 적어 거절한 것까지 맞다
- **D3(별도 조회)의 근거가 옳다.** 끝난 실행을 열 때마다 러너를 부르는 것은 실제 비용이다
- **D5(못 물어보면 빈 목록)가 옳다.** 한 번 실패를 러너 고장으로 말하면 거짓말이 된다
- **D4(도는 것 전부)가 옳다.** 정확히 아는데 하나만 그리면 알면서 감추는 것이다
- **`Running` 에 선택 칸으로 더하는 판단이 옳다.** 기존 리터럴이 안 깨진다
- **할 일 3 의 「줄을 셋으로 쪼개 먹인다」 RED 가 옳다.** 우연한 통과를 정확히 막는다
- **이번에 안 하는 것 넷의 근거가 전부 성립한다.** 특히 `vite.config.ts` 를 안 건드리는 판단 —
  Vite 내부 동작이라 파고들면 CLAUDE.md §6 의 3회 규칙에 걸릴 자리다
- **값어치 대비 크기가 맞는다.** 위험이 파일 하나·한 줄에 모이고, BLOCKER 1 을 (a) 로 풀면
  기계가 대부분 리포터와 러너로 옮겨 가 `step.ts` 는 한 줄로 남는다
