## 왜

지금은 에이전트가 **서비스마다 대기열 하나**를 돌리고 한 건을 끝내야 다음 건을 가져간다(`scripts/authoring-agent.ts:188-239`).
서버 SQL 은 서비스 단위로 막지 않는다(`agentStore.ts` `집기` 는 PENDING 하나만 본다). 반영(머지)도 같은 줄이라 CI 를 기다리는 최대 17분 동안 그 서비스의 다른 작성이 멈춘다.

그냥 풀면 두 요청이 같은 main 에서 출발해 **같은 다음 번호**를 고른다 — 자식은 「표와 폴더의 가장 큰 번호 다음」을 고르고(스킬 문서뿐, 계산기 없음) 다른 열린 PR 을 못 본다.
케이스 파일(`tests/<폴더>/<tcId>.spec.ts`)은 add/add 충돌, 요구사항 표(`docs/cases/<접두사>.md`)는 거의 확실히 텍스트 충돌이 난다.
반영은 rebase 도 update-branch 도 안 해서(`authoring-merge.ts`) 충돌하면 CI 가 안 뜨고 17분 뒤 FAILED 가 된다. 파일 이름이 우연히 다르면 **같은 tcId 가 main 에 둘** 들어가고, 그러면 카탈로그 스캔이 그 서비스 캐시를 아예 갱신하지 않는다(`catalog/routes.ts`).
원장 · 커버리지는 요청마다 따로라 안 섞인다.

## 명세가 안 정한 것 — 제안 (게이트 1 에서 정한다)

| 무엇 | 제안 |
|---|---|
| 동시 실행 | 작성 · 재실행 · 케이스 고치기 · 보류 있는 반영은 **자리(동시 상한)만 있으면** 같은 서비스도 나란히. 보류 없는 반영은 자리를 안 쓰고 **서비스마다 한 줄**로 차례로(main 에 차례로 들어가야 견주기가 맞다). 한 뿌리에 한 실행(`RUN_ACTIVE`)은 그대로 |
| 가져가는 순서 | 서비스 줄이 가져간 작성이 자리를 기다리는 동안 그 줄은 다음 것을 안 가져간다(지금과 같다) — 자리가 다 찬 동안 그 서비스의 반영은 자리가 빌 때까지 기다린다. 가져가기에 종류 거르기를 더하면 계약이 하나 더 늘어 안 했다 → 남는 한계 |
| 견주는 기준 | GitHub 이 말하는 **지금 main**(`진짜main받기`) · PR 머리 · 둘의 갈래점(merge-base). git 객체만 읽는다 — 작업방을 안 연다 |
| 견주는 대상 | 이 PR 이 **새로 더한** 케이스 파일(`tests/<폴더>/*.spec.ts`, 갈래점 → PR 머리에서 `A`). 바꾼 케이스(R9 바꾸기)는 겹침이 아니다 |
| ⒜ 같은 tcId | 그 tcId 케이스 파일이 지금 main 에 있다(경로가 달라도) |
| ⒝ 같은 요구 번호 | PR 표에서 그 tcId 줄의 출처 칸 번호(`번호찾기`)가, **갈래점 뒤 main 에 새로 들어온 케이스**의 main 표 줄 번호와 겹친다. 그 전부터 있던 케이스와 같은 번호를 덮는 것은 자식이 일부러 고른 것이다(한 요구에 케이스 여럿은 원래 된다 — `ledger-check` 덮음) |
| ⒞ 같은 이름 | 케이스 `name` 을 정적으로 읽어(AST — 실행하지 않는다) 앞뒤 공백을 떼고 빈칸을 하나로 · 영문 대소문자를 무시해 같으면. 상대는 **지금 main 의 모든 케이스**(이름이 같은 케이스는 원래 피한다 — 관문 2) |
| 결과 한 줄 | `{ tcId, name, file, kinds: ('TCID' \| 'REQUIREMENT' \| 'NAME')[], with: [{ tcId, name, file, requirements? }] }` — 한 케이스에 여럿이면 `kinds` 에 모은다. 끝내기는 반영 행 `FAILED` + `error: 겹치는 케이스 N건 — 케이스마다 고른 뒤 다시 반영한다` + `result.conflicts` |
| 결정 | `RENUMBER`(새 번호로 바꿔 반영) · `DROP`(이 케이스 빼기). 원본(작성 실행) 행의 `conflict_input` 에 `{ [tcId]: { action, by, at } }`. 고른 것이 **지금 겹침 목록에 있는 tcId** 일 때만 받는다 |
| 새 번호 | 지금 main 과 PR 의 그 접두사 번호 가운데 가장 큰 것 + 1 부터 차례로(자릿수는 셋 이상 · 지금 꼴을 따른다). 파일 이름 · 파일 안 `tcId: '…'` (AST 로 그 자리만) · PR 표의 그 tcId 칸을 바꾼다 |
| 빼기 | 그 케이스 파일을 지우고 **PR 표에서 그 tcId 를 가진 줄**을 지운다(그 PR 이 더한 줄이다 — 보류 제거처럼 「제거함」으로 남기지 않는다. 남기면 main 의 같은 tcId 줄과 섞인다) |
| main 합치기 | 반영할 때 PR 머리가 지금 main 을 품고 있지 않으면 작업방에서 `git merge` 로 main 을 합친다. **요구사항 표만** 줄 단위 합치기(git `union`, 에이전트 쪽 속성 파일로만 — 저장소 `.gitattributes` 는 안 건드린다). 합친 뒤 `**덮는 범위**` 줄이 둘이면 이 PR 쪽 줄만 남긴다. 그 밖 파일이 충돌하면 병합하지 않고 `FAILED` — 「main 과 같은 파일을 고쳐 합치지 못했다 — <경로>. 다시 작성(고치기는 다시 적용)한다」 |
| 앞 반영 커밋 | 작업방은 자식이 끝낸 커밋에서 연다 — 머리가 에이전트의 반영 커밋(보류 값 · main 합침)이면 첫 부모로 거슬러 간다(지금은 한 번만 간다) |
| 관문 | 번호 바꾸기 · 빼기 · main 합치기는 케이스를 안 돌린다 — 동작이 안 바뀐다. 타입 · K 규칙은 CI 가벼운 길이 본다. 보류 값을 채운 케이스는 지금처럼 3회 |
| 고르기 통로 | `PUT /api/authoring/requests/:id/conflicts/:tcId` `{ action }` · `DELETE` 같은 경로. 작성 write. 뿌리 잠금 안에서 `MERGE_ACTIVE` · `NOT_LATEST` (보류 통로와 같은 판정). 목록에 없는 tcId 는 404 `NOT_FOUND`, 모양이 틀리면 400 `BAD_CONFLICT` |
| 반영 막기 | 반영 통로가 최신 반영 결과에 겹침이 있고 결정이 빠진 것이 있으면 409 `CONFLICT_OPEN`(detail 남은 수). 보류 판정 다음에 · 뿌리 잠금 안에서 |
| 상세 칸 | `conflicts: [...결과 한 줄, input]` · `conflictsOpen` — 그 작성 실행을 원본으로 하는 **가장 최근 반영**이 겹침으로 실패했을 때만. 그 뒤 반영이 성공하거나 새 작성 실행이 서면 안 보인다 |
| 가져가기 칸 | 반영 행을 가져가면 `conflicts: [{ tcId, action }]` — 원본의 결정 가운데 지금 목록에 있는 것만 |
| 끝내기 검사 | 반영 `FAILED` 의 `result.conflicts` 모양이 틀리면 400 `BAD_CONFLICTS`(보류 · 셈과 같은 자리) |

### BLOCKER (설계 1) — 겹침을 PR 머리에서 찾는데 작업방은 자식 커밋에서 다시 지어, 한 번 적용한 결정이 다음 반영에서 사라진다
반영#2 가 번호를 바꿔 올린 뒤 CI 가 빨개지면 「지금 목록」이 비어 반영#3 에 결정이 안 실리고, 작업방은 자식 커밋(옛 번호)부터 다시 지어 옛 번호가 되살아난다.
고칠 것 — 겹침은 **자식이 끝낸 커밋**과 지금 main 으로 찾는다. 가져가기는 원본의 결정을 전부 싣고 거르기는 에이전트가 새 결과로 한다. 「적용 → CI 빨강 → 다시 반영」 검사를 더한다

### BLOCKER (설계 2 · 제품 주의 3) — 보류 있는 반영이 서비스 반영 줄 밖에서 나란히 돈다
같은 서비스 반영 둘이 같은 main 으로 견주고 둘 다 통과한다(main 보호 `strict:false`). 고칠 것 — **반영은 전부 서비스마다 한 줄**, 보류 있는 반영은 그 안에서 자리도 하나 잡는다

### BLOCKER (설계 3) — 줄 단위 합치기(union)가 요구사항 표를 말없이 망가뜨린다
「요구」 차례 번호가 늘 겹치고(둘 다 46부터), 머리 문단 · 같은 줄을 양쪽이 고친 것이 둘 다 남으며, 새 서비스의 첫 요청 둘은 표가 통째로 섞인다.
고칠 것 — union 대신 `git merge-file --diff3` 덩이를 코드로 푼다: 바탕이 빈 덩이(양쪽이 더하기만)는 main → PR 순으로 잇고 PR 줄의 「요구」 번호를 main 최대값 뒤로 다시 매긴다 · 덮는 범위는 PR 쪽 · 그 밖 양쪽 고침과 표 add/add 는 쉬운 문장으로 FAILED

### BLOCKER (제품 1) — 상한보다 많이 넣으면 멀쩡한 요청이 「응답 없음」으로 보인다
지금은 가져간 뒤(RUNNING) 자리를 기다린다. 셋째 요청이 가져가진 채 단계 글 없이 30분을 넘기면 화면이 「응답 없음」을 띄우고 그 서비스 반영도 못 가져간다.
고칠 것 — **자리를 먼저 잡고** 가져간다. 가져온 것이 보류 없는 반영이면 자리를 바로 놓는다. 「자리가 다 차면 반영도 기다린다」는 남는 한계로

### BLOCKER (제품 2 · 설계 주의 1 · 2) — 「비슷한 케이스」 판정과 선택지를 계약에 넣기 전에 다시 정해야 한다
