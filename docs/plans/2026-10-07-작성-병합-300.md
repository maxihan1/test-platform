# 작성 에이전트 병합이 파일 300개 넘는 PR 에서 멈추지 않게 (AUT-F3-47)

- 자리: 작성 에이전트의 병합 직전 「테스트만」 판정 — 도메인/작성 §3.6 「신뢰 경계」(192~200줄) · HOOKS.md 「무엇으로 판정하나」(판정 정본 `.claude/scripts/cases-only.mjs`)

## 왜

2026-10-07 요청 5873(#144, 349파일)이 CI 를 통과하고도 병합되지 않았다. 병합 직전 판정의 파일 목록(`gh pr diff --name-only`)을 GitHub 이 거절했다 — `HTTP 406: Sorry, the diff exceeded the maximum number of files (300)`. 같은 판정을 손으로 돌려 병합했고 플랫폼 기록은 「실패」로 남았다.

**실측 (규칙 8 — 실제 출력 여덟 PR)** — `gh api --paginate repos/<저장소>/pulls/<번호>/files` 가 낸 줄 수와 `gh pr view --json changedFiles` 가 모두 같았다.

| PR | 읽은 줄 | changedFiles | 상태 | `gh pr diff --name-only` |
|---|---|---|---|---|
| #144 | 349 | 349 | added 349 | **HTTP 406** |
| #165 | 105 | 105 | modified 45 · added 60 | 성공 |
| #135 | 74 | 74 | added 74 | 성공 |
| #129 · #130 · #131 · #133 · #108 | 50 · 25 · 45 · 17 · 60 | 같음 | modified · added | 성공 |

**찾은 것 둘**
1. **이름 바꾼 파일의 옛 경로** — 이 API 는 이름 바꾼 파일을 `status: renamed` 와 `previous_filename` 으로 준다(GitHub 문서. 위 여덟 PR 은 PR 전체로 보면 이름 바꾼 것이 0이라 실측은 없다). 새 이름만 보면 `apps/…/x.ts` 를 `tests/…/X-001.spec.ts` 로 옮긴 PR 이 「테스트만」으로 통과한다. **지금 `gh pr diff --name-only` 도 새 이름만 준다** — 빈틈은 원래 있었다. 올리기 전 판정(`올린파일인자`)은 `--no-renames` 로 옛 경로를 「지움」으로 따로 본다. 병합 직전도 옛 경로를 넣어야 둘이 같다
2. **3000개 상한** — 이 API 는 파일 3000개까지만 준다(GitHub 문서). 잘린 목록으로 판정하면 뒤쪽 코드 파일을 못 본다. 판정 직전에 PR 의 바뀐 파일 수를 **새로** 읽어 읽은 줄 수와 다르면 병합하지 않는다 — 함수 앞에서 읽은 PR 정보(66줄)는 보류 빼기 커밋(`반영올리기`) 전 것이라 낡았다

|---|---|---|
| 목록을 다 못 읽었을 때 | 병합하지 않는다(실패로 끝낸다). 오류 글자 `PR 의 바뀐 파일 수(N)와 읽은 목록(M)이 달라 판정하지 않는다 — 맥은 병합하지 않는다` | 명세 「병합 직전 판정」을 지키는 닫힌 쪽 실패라 명세에 새로 안 적고 판정 문서 HOOKS.md 에 한 줄(할 일 3). 옆의 「최신 main 을 못 받아 판정을 못 했다」도 명세에 없다 |
