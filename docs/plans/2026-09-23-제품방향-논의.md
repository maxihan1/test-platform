# 제품 방향 논의 — 경쟁 비교 · 납품 우선순위 · Appium 조사

등급: 0 (이 문서 자체) · 갈래: 없음 · 2026-09-23 작성

> **이건 확정 설계도 할 일 계획서도 아니다. 논의 기록이다.**
> 여기서 무엇을 만들기로 고르면 그때 `/tpx` 가 계획서를 따로 쓴다 — 이 문서는 **그 선택의 입력**이다.
> 경쟁 제품 기능은 2026-09-23 웹 검색 기준이다. 가격·세부 동작은 확인하지 않았다.

**전제** — 사업 목표는 **회사에 도구 도입** 또는 **QA 자동화 아웃소싱(컨설팅)으로 고객 서버에 자동화 세트 설치**다.
배포는 SaaS 가 아니라 회사마다 서버 한 대에 설치해 중앙 관리한다. 폐쇄망에서는 쓰지 않는다.

---

### Q1. BrowserStack 대비 필요한 것은? (디바이스 팜 제외)
없는 것: 수동 케이스 관리, flaky 판정, 시각 회귀(Percy), 접근성 검사, Jira 연동.
있는 것: 검수 증적 문서(우리만), 기획서로 AI 케이스 작성.

### Q2. 앞으로 넣을 E2E 시나리오 조립이 Test Management 와 같은가?
다르다. Test Management 의 Test Run 은 결과를 적는 체크리스트다. 우리 조립은 케이스를 **한 브라우저에서 이어 실행**한다
([E2E 시나리오 설계](2026-09-21-E2E-시나리오-설계.md)).
가까운 것은 BrowserStack Low Code 의 재사용 단계 묶음이다.

### Q3. 조립이 들어가면 한 단계 위인가?
실행 면에서는 그렇다. 단 아직 설계만 됐고, 모킹·API 호출이 증적에 안 남는 구멍(설계 §12)을 막아야 강점이 된다.

### Q4. mabl · Testsigma 와 비교하면?

| 기능 | BrowserStack | mabl | Testsigma | 우리 |
|---|---|---|---|---|
| 기획서·피그마 → 케이스 | 글 케이스 | 앱을 보고 AI 생성 | Jira·Figma·문장 | 있음 (코드 PR) |
| 공통 단계 재사용 | Low Code 모듈 | reusable flows | step groups | E2E 조립 (설계만) |
| 요소 자동 복구 | 있음 | 있음 | 있음 | 없음 |
| 실패 원인 분석 | 있음 | 있음 | 있음 | 사유 묶기·직전 비교 |
| 중복·빈틈 찾기 | - | 있음 | 있음 | 없음 |
| Jira 동기화 | 있음 | 있음 | 있음 | 없음 |
| 검수 증적 문서 | 없음 | 없음 | 없음 | **우리만** |
| 테스트 형식 | - | 자기 형식 | 자기 형식 | **Playwright 코드** |

**AI 작성은 차별점이 아니다.** 진짜 차별점은 검수 증적 문서와 저장소에 남는 코드다.
자동 복구는 **그대로 따라 하지 않는다** — 엉뚱한 요소로 「고쳐져서」 통과하면 증적이 거짓이 된다.
대신 AI 가 고친 코드를 PR 로 올리고 사람이 머지하는 **복구 PR 제안**이 우리 방식이다.

### Q5. 경쟁력이 없나? 사내·협력사 기준 매력은?
사내 설치·중앙 관리형으로 보면 같은 종류는 ReportPortal · Allure TestOps(결과 수집형)다.
그들은 실행을 안 하고 비개발자가 값을 바꿔 돌릴 수 없다 → **이 종류에선 경쟁력 있다.**
약점: Playwright 전용, ML 실패 분류 없음, 유지보수 인력 필요.

### Q6. 회사마다 서버에 설치하면?
설치·업데이트가 매력을 좌우한다. 지금은 소스를 받아 빌드하고(고객 서버에 소스가 남는다),
버전 표시가 없고, 테스트 저장소 연결은 고객 몫이다(`spec/공통/6-인프라` §9.2).

### Q7. 도입 / 아웃소싱 목표라면 무엇부터?
① 이미지 설치 꾸러미·버전 표시 ② 요구사항 대비 자동화 현황(납품 보고) ③ E2E 조립 ④ 복구 PR 제안(유지보수 비용) ⑤ Appium(수요 보고).
①②는 납품 최소 조건이고 ③부터 경쟁력이다. AI 작성은 우리 맥에서 하고 고객 서버엔 PR 만 들어가므로 오히려 유리하다.
확인할 것: Claude 구독을 고객 일에 써도 되는지(약관). 코드 저장소 위치는 고객마다 정해도 된다(`tests_repo` 설정).

### Q8. 아웃소싱 = 자동화 테스트 컨설팅?
그렇다. 진단 → AI 작성 → 설치 → 인수인계 → 증적 보고 → 유지보수.
강점은 AI 작성으로 남는 마진과 눈에 보이는 납품물이다.

### Q9. Appium 을 추가할 수 있는 구조인가?
**가능하다.** 러너 뼈대·판정·DB(`platform` 칸에 값 제한 없음)·증적은 그대로 쓴다. Appium 서버와 기기는 러너 밖에 둔다.
Playwright Test 를 실행기로 그대로 두고 WebdriverIO 를 fixture 로 넘기는 방식이 이미 쓰인다.

- **고칠 곳** — `packages/kit/src/runtime/test.ts`(driver 넘기기·스크린샷·크롬 안 띄우기),
  `desktop`/`mobile` 값이 박힌 약 20곳, `playwright.config.ts`(project 추가, 제한 시간 — 지금 기본 30초)
- **계약(3등급)** — `Platform` 타입, SPEC 디바이스 정의, `webdriverio` 승인, compose 에 Appium 주소
- **막히는 것** — 중단 시 원격 세션이 안 풀린다(`apps/runner/src/kill.ts`), 동시 실행 2가 기기 수를 모른다
  (`apps/admin/src/execution/dispatcher.ts`), 앱 모킹 불가(E2E 설계 결정 6), 작성 스킬이 앱 화면을 못 읽는다,
  환경마다 다른 앱 파일을 둘 자리가 없다
- **첫걸음** — Android 에뮬레이터 1대로 케이스 1건 → 증적까지 (2~3일 추정, 실측 아님)

### Q10. 앱에서 ① 자동 작성 ② 기기 연결 ③ 네이티브·Unity 는?
1. **자동 작성: 된다.** 앱 화면 구조를 읽는 도구가 있다(Q11~Q13). 조건 — 개발자가 `accessibility id` 이름표를 달아야 한다(아웃소싱이면 계약에 넣는다).
2. **기기 연결: 된다.** 러너는 Appium 주소만 알면 된다. 에뮬레이터 / USB 실기기 / 클라우드 팜(Appium 호환)을 설정으로 바꾼다.
   iOS 는 맥 + Xcode + 애플 서명이 필요하다. 기기별 잠금이 필요하다.
3. **네이티브·React Native·Flutter: 된다. Unity: 비싸다.** Appium 이 Unity 화면 속 버튼을 못 본다 →
   AltTester SDK 를 빌드에 넣어야 하는데 TypeScript 를 지원하지 않는다(C#·Python·Java·Robot). 게임 고객이 생기면 한다.

### Q11. Appium MCP 말고 CLI 는 없나?
**있다. 만들 필요 없다.**
- **mobilecli**(mobile-next) — Android·iOS 기기 목록·탭·입력·화면 구조 덤프. Claude Code 용 스킬이 같이 있다.
  지금 `tpx-cases` §4 의 `playwright cli` 자리에 그대로 대응한다
- **maestro hierarchy** — 화면 구조 출력. Maestro 는 자기 YAML 형식 도구라 읽기용으로만
- 설치 없이 — Android `adb shell uiautomator dump`

조건: 읽는 도구와 실행 도구(Appium)가 **같은 속성**(`resource-id`, `content-desc` = accessibility id)을 봐야 주소가 그대로 옮겨간다.
Android 는 둘 다 UiAutomator, iOS 는 둘 다 WDA 라 맞다. 새 도구라 도입 전 승인이 필요하다(CLAUDE.md §3).
화면에서 기대값을 읽지 않는 규칙은 앱에서도 그대로다.

### Q12. Appium 전용 CLI 는 없나?
**화면을 읽고 조작하는 공식 CLI 는 없다.** `appium` 명령은 서버 실행·드라이버 설치(`appium driver install`, `appium driver doctor`)용이고 Inspector 는 GUI 다.
대안: 테스트용으로 어차피 들일 `webdriverio` 로 얇은 탐침 스크립트(접속 → 화면 구조·스크린샷 저장)를 만들면
**실행과 같은 눈**으로 읽는다. 여러 화면을 넘나드는 탐색이 필요하면 mobilecli 를 같이 쓴다.

### Q13. mobilecli vs Appium MCP — 토큰·정확성 모두 고려하면?
**mobilecli.**
- 토큰 — MCP 는 도구 설명이 세션마다 실리고 화면 구조 XML 이 대화에 통째로 들어온다. CLI 는 파일로 떨구고 필요한 줄만 읽는다(`tpx-cases` §4 와 같은 방식)
- 속도 — mobilecli 는 상주 데몬, Appium 은 세션 생성에 수 초~수십 초
- 정확성 — MCP 가 Appium 눈으로 봐서 앞서지만, 작성 관문 3 이 케이스를 **실제로 Appium 으로 돌리므로** 틀린 주소는 거기서 잡힌다. 격차가 작다

MCP 가 나은 경우: iOS 에서 주소가 자주 어긋날 때, Appium 전용 주소 문법(`UiSelector` 등)을 써야 할 때.
토큰 비교는 구조를 보고 한 판단이다. Appium 시험 때 같은 화면을 두 도구로 읽어 실측한다.

### Q14. 그럼 앱 테스트 자동 생성도 되나?
**된다. 순서와 조건이 있다.**
- 순서 — ① Appium 실행 시험(Android 1건) ② `tpx-cases` 에 앱용 절(mobilecli 로 화면 읽기, 관문 3 을 Appium 으로) + 작성 입력에 앱 파일(apk/ipa). 피그마 자료는 그대로 쓴다
- 조건 — 앱에 `accessibility id`, Unity 제외
- 유리한 점 — 작성 에이전트가 맥에서 돌아 Android 에뮬레이터와 **iOS 시뮬레이터를 둘 다** 띄울 수 있다. 실행 서버의 iOS 문제는 따로 남는다
