# 어드민 화면 전면 리뉴얼 ② — 목록에서 값을 고치고 상세를 펼친다

등급: 3 · 갈래: WS-E · 2026-09-21

## 도메인 정리

| BC | 무엇을 건드리나 | 관련 절 |
|---|---|---|
| Execution | `GET /api/runs/last-by-case` 응답에 `recent` 를 더한다. 질의 하나 | 실행 §7 · 공유계약 §7.1 |
| Catalog | 목록 화면의 줄 구성이 바뀐다. **카탈로그 API 는 안 바뀐다** | 카탈로그 §8.1 |
| Reporting | 건드리지 않는다 | — |

**경계를 넘지 않는다.** 판정 흐름 데이터는 `run_item` 에서 오므로 **실행 쪽이 낸다** —
카탈로그가 `run_item` 을 읽으면 컨텍스트 경계가 깨진다 (카탈로그 §3.1).
지금 `last-by-case` 가 그 이유로 실행 쪽에 있고, 같은 자리에 얹는다.

## 왜

케이스 목록이 **읽는 자리**에 머물러 있다. 하나를 돌리려면 목록 → 실행 설정 화면으로 나가고,
그 케이스가 무슨 값을 쓰는지 보려면 또 한 번 들어간다. 값이 무엇인지 확인하는 데 화면 둘을 건넌다.

이 PR 이 목록을 **거기서 끝나는 자리**로 만든다.

### 착수 전에 코드를 읽어 알아낸 것 — 새로 만들 것이 생각보다 적다

| 하려는 것 | 필요한 데이터 | 이미 있나 |
|---|---|---|
| 파라미터 인라인 입력 | `paramSchema` · `expectedSchema` | **목록 응답에 이미 있다.** `schema.ts` 의 `schemaToFields` · `initialText` · `toValues` 가 그대로 쓰인다 |
| 고친 값을 실행으로 | `POST /api/runs` 의 `params` · `expected` | **이미 그렇게 돈다.** 모달이 쓰는 `글자표` 와 같은 모양이면 그대로 이어진다 (실행 §8.10) |
| 상세 — 사전조건 · 입력값 · 기대결과 | `precondition` · 스키마 둘 | **목록 응답에 이미 있다.** 부를 것이 없다 |
| 상세 — 시험 절차 | 마지막 실행의 절차 | `GET /api/runs/:runId/items/:historyId` (실행 §7) |
| 상세 — 실행 이력 | 최근 N회 | `GET /api/cases/:tcId/history` (실행 §7) |
| **줄의 판정 흐름 막대** | 케이스×디바이스마다 **최근 5회** | **없다** ← 계약 변경 하나. 게이트 0 승인 |

### 왜 흐름 막대만 통로가 필요한가

카탈로그 §8.1 이 못을 박아 뒀다 — 「`마지막 결과` 칸은 `GET /api/runs/last-by-case` **한 번**으로
전부 채운다. 케이스마다 이력을 따로 부르지 않는다」.

줄마다 막대를 그리려면 케이스 수만큼 이력을 불러야 해 그 규칙을 정면으로 어긴다.
그래서 **이미 한 번 부르는 그 응답에 얹는다.** 부르는 횟수는 그대로 1회다.

**상세 펼침은 이 규칙에 안 걸린다** — 목록이 부르는 것이 아니라 **사람이 한 줄을 폈을 때** 한 번 부른다.

- `도메인/실행.md:92` 는 응답 설명 한 줄만 고친다
- `도메인/카탈로그.md §8.1` — 줄 구성에 **입력칸 · `상세` 버튼 · 판정 흐름** 을 더한다.

  이번 변경이 그 규칙을 지키려고 한 것이므로 근거가 살아 있다 (§2.7 ②)
- **상세 펼침이 그 규칙의 예외임을 그 자리에 적는다.** 안 적으면 다음 세션이 「이력을 부르네」로 읽고 되돌린다
