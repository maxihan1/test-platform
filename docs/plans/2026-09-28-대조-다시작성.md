# 화면대조 요청도 「같은 자료로 다시 작성」

등급: 3 · 갈래: WS-작성 · 2026-09-28 · PR #92

## 도메인 정리

작성 BC. 계약 셋(게이트 0 승인, 2026-09-28).

| 계약 | 지금 | 바꾼 뒤 |
|---|---|---|
| DB `authoring_request_compare_check` | 대조는 `kind = 'AUTHOR'` 에만 | `kind IN ('AUTHOR','RERUN')` — 머지는 여전히 안 됨 |
| `POST /authoring/requests` RERUN | 대조 원본이면 409 `BAD_SOURCE`(COMPARE) | 받는다. 재실행 행이 원본의 `compare`·`env`·`start_url` 을 그대로 물려받는다. 본문의 역방향 칸은 여전히 400 `BAD_ENV` |
| `POST /authoring/requests/:id/outputs` MARKED `source` | 같은 요청의 INPUT 파일만 | 행이 RERUN 이면 **원본 요청**의 INPUT 파일 — 에이전트가 원본 자료로 사본을 만든다(`자료출처`) |

에이전트(`scripts/authoring-*`)는 집기 응답의 `target` 만 보고 대조로 돈다 — 안 바뀐다.
Grafana 쿼리는 `kind` 로 재실행을 먼저 떼어 센다 — 안 바뀐다. 까닭 문장만 고친다.

**범위 밖 (사용자 결정 2026-09-28).** 멈춘 자리부터 잇는 이어하기(작업방 보관 · 세션 재개)는 다음 PR 에서 정방향·대조 함께.

## 왜

대조 요청이 시간초과·중단으로 끝나면 지금은 자료를 처음부터 다시 올리고 대상 서버·시작 주소를 다시 골라야 한다.
2026-09-26 게이트 1 에서 「고친 기획서는 어차피 새 요청」이라 막았으나, 실패·중단은 기획서가 그대로인 경우가 대부분이다(5871 · 5872).

### BLOCKER 1 — 에이전트가 원본 파일을 재실행 번호로 받는다 (eng)
`scripts/authoring-upload.ts:201` 이 `표시준비(역, 것.id, …)` — 안의 `자료받기`(`authoring-marking.ts:31`)가 `/requests/<재실행>/assets/<원본 자료>` 로 받아 404.
그대로면 대조 재실행의 문서 표시가 전부 「원본을 다시 받지 못했다」로 끝나고 할 일 3 이 쓰일 일이 없다.
고칠 것 — `것.id` 대신 `자료출처(것)`. 「에이전트 불변」 전제를 걷는다.

### BLOCKER 2 — 설명 글이 「다시 작성할 수 없습니다」를 그대로 띄운다 (eng · design)
`AuthoringTodo.tsx:183-187` 이 `compare` 면 먼저 그 문구를 고른다. 할 일 4 files 에 없다. `AuthoringDetail.test.tsx:288` 이 옛 문구를 기대한다.

### 주의 1 — down 마이그레이션이 옛 제약에 걸린다 (eng)
옛 CHECK 의 ELSE 는 `env`·`start_url` 도 NULL 을 요구한다. compare 만 끄면 다시 걸 때 실패. 셋 다 비운다.

### 주의 2 — 재실행 때 대상 서버·계정을 다시 보지 않는다 (eng · ceo)
원본 뒤에 env 줄이나 계정이 빠졌으면 201 로 줄에 서고 에이전트가 집을 때에야 FAILED. 재실행 시점에 AUTHOR 와 같은 확인으로 400 BAD_ENV 를 줄지 게이트 1 에서 정한다.

### 주의 3 — 「처음부터 다시」가 늘 보이지 않는다 (design)
FAILED 설명엔 「처음부터」가 없다. 이어하기로 오해할 수 있다. 두 상태 모두 「처음부터 다시」, 대조면 「같은 대상 서버·시작 주소로」.

### 주의 4 — 화면만 원본의 재실행 검사가 없다 (ceo)
할 일 2 RED 에 「입력 0 · 시작 주소만」 원본을 명시한다.

### 주의 5 — Grafana 토큰 패널에서 대조 재실행이 정방향 재실행과 섞인다 (eng)
패널은 kind 를 먼저 본다. 「안 바뀐다」로 둘지 게이트 1 에서 확인한다.
