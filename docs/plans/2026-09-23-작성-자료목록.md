## 왜

기획서는 붙여넣는 본문이 아니라 **PDF·워드 파일**로 온다. 피그마도 같이 온다. 문서도 피그마도 **여럿이 한 세트**다
(사용자가 세 번에 걸쳐 못박았다 — PR #61 인계 코멘트 §1).

**`DRAFT` 가 핵심이다.** 요청을 만들고 파일을 하나씩 올리는 동안 줄에 서 있으면 맥이 집어 가 빈 것을 보고 실패한다.
다 올린 뒤 「줄에 세우기」가 `DRAFT → PENDING` 으로 바꾼다.

### 흐름

```
화면  POST /requests {kind:AUTHOR, figma:[주소…]}  → DRAFT 행 + FIGMA 자료 행(정규화한 주소)  → 201 {id}
화면  POST /requests/:id/assets?name=기획서.pdf  (원시 바이트)  × 파일 수     → FILE 자료 행
화면  POST /requests/:id/submit                    → DRAFT → PENDING (자료 0 이면 409)
맥    POST /requests/claim                          → 집은 한 건 + assets (+ 피그마 자료가 있으면 figmaToken)
맥    GET  /requests/:id/assets/:assetId            → 파일 받아 임시 폴더에
맥    doc·docx 는 textutil 로 글자만 · pdf·md·txt 는 그대로 · 피그마 주소는 프롬프트에
맥    claude -p --add-dir <임시 폴더>  (자식 환경에만 FIGMA_TOKEN)  → tpx-cases 가 npx figma-reader-cli 로 피그마를 읽는다
```

- **`RERUN` 은 `DRAFT` 를 안 거친다.** 자료를 새로 안 받는다. 원본은 **`AUTHOR` 이고 `DRAFT` 가 아닌 행**으로 좁히고(서버),
  맥은 원본 행의 자료를 읽는다 — 곧장 `PENDING`
- **`MERGE` 는 지금 그대로다** (자료 없음 · 바로 `PENDING`)
- **옛 행** (마이그레이션 전 AUTHOR) — 자료 0 이고 `spec_text` 가 있다. 맥은 그 글을 그대로 쓴다
- **파일 저장 자리는 `authoring-assets/<요청번호>/<자료번호>.<확장자>`** — 사진 폴더 `authoring/<번호>/` 안에 두면
  사진 장수 상한(`readdir` 200)이 자료까지 센다. 뿌리는 사진과 같은 `PLATFORM_ARTIFACTS_DIR` (볼륨으로 묶인 유일한 자리)

| 무엇 | 정한 것 |
|---|---|
| 받는 파일 종류 | `.pdf` · `.docx` · `.doc` · `.md` · `.txt`. 그 밖(`.hwp`·`.pptx` 등)은 거부하고 **이유를 문구로** 보인다 |

| `spec_text` 를 맥이 채우나 | 칸만 풀고 채우는 일은 미룬다 — 지금 그 값을 만드는 쪽도 읽는 쪽도 없다 |
| `figma-reader-cli` 스킬 설치 | 안 한다. `tpx-cases` 가 `npx --yes figma-reader-cli@<고정 판> inspect` 를 직접 부른다 |
| FigJam(`/board`) | **안 받는다** — 화면 디자인이 아니다. 400 과 이유 문구. 필요해지면 정규화 함수에 한 갈래 |

## LEARNINGS 근거

- 넓은 `DELETE ... LIKE` 가 남의 fixture 를 지운 일 (CLAUDE.md §3) — 새 접두사 `XWS`(assetStore) · `XWU`(assets 통로)를 CLAUDE.md 에 적고 **자기 `service_id` 로만** 지운다. 서비스 부모 행과 임시 자료 폴더까지 치운다
- 경로 번호를 느슨하게 읽어 문과 라우트가 다른 값을 본 일 — `:assetId` 도 `번호()` 로 읽는다
- 폴더 거슬러 오르기 — 디스크 이름은 **자료 행 번호**로 짓고 사람이 준 이름은 표에만
- 맥이 보낸 값을 명령줄에 끼운 일(`pr_url`) — 피그마 주소는 **다시 조립해 저장**한다. 저장값에 셸 특수 글자가 원천적으로 없다

### 주의 6 — 동시 올리기에서 순서 번호·개수 상한·파일 쓰기 순서가 어긋난다 (eng)
MAX+1 은 겹치면 `UNIQUE` 에 걸려 500. 읽고 넣는 상한은 21개째를 통과시킨다. 행 먼저 넣고 파일 쓰기가 실패하면 내려받기가 ENOENT.
**고칠 것** — 개수 검사와 position 을 한 문장 `INSERT … SELECT` 로, 충돌은 409. 순서는 행 → 파일 → 실패 시 행 지우기.

### 주의 7 — `migrate:down` 이 안 되돌아간다 (eng)
DRAFT 행이나 `spec_text IS NULL` 행이 하나라도 있으면 down 의 `SET NOT NULL` 과 옛 CHECK 가 실패한다. 기존 CHECK 는 이름이 없어 자동 이름(`authoring_request_status_check`)을 맞춰야 한다.
**고칠 것** — down 에서 그 행들을 어떻게 치울지 적고, 새 CHECK 에 이름을 붙이고, 검증에 up → down → up.

### 주의 8 — 「Fastify 는 파서 상한이 이긴다」는 전제가 반대다 (eng, 실측)

**고칠 것** — 결론(새 파일)은 300줄 때문에 그대로. 근거 문장만 바꾼다. 틀린 근거를 코드 주석에 옮기지 않는다.
