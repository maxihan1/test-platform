## 도메인 정리

- **BC**: Runner (§3.4). 완전 무상태이고 DB 에 닿지 않는다
- **관련 절**: §3.4 중단 통로 · §5.2 Runner HTTP 계약
- **영향**

| 갈래 | 무엇이 걸리나 |
|---|---|
| WS-C | 이번 작업. `apps/runner/**` 만 |
| WS-B | 호출자 `abortRunner()` 가 **이미 있다.** 짝이 생기면 그대로 동작한다 — WS-B 코드는 건드리지 않는다 |
| WS-E | 화면의 「멈춤」 버튼이 WS-B 를 거쳐 여기에 닿는다. 직접 의존 없음 |

**계약 변경 없음.** §5.2 가 `POST /abort` 를 이미 정본으로 적어 뒀다.

## 왜

지금은 사용자가 화면에서 실행을 멈춰도 **러너 쪽 브라우저가 끝까지 돈다.**
`abortRun()` 이 DB 에서 항목을 닫지만, 5분짜리 케이스가 도는 중이면 그 5분이 그대로 흐른다.

끊는 코드는 **이미 완성돼 있다.** `kill.ts` 의 `killTree()` 가 타임아웃 때 프로세스 그룹을 통째로
죽이고 있고, 2026-09-16 에 「`child.kill()` 은 npx 만 죽이고 브라우저가 남는다」를 고치며 검증까지 끝났다.
**없는 것은 바깥에서 부를 자리 하나뿐이다.**

`apps/admin/src/execution/runner.ts:27` 의 `abortRunner()` 가 이미 `POST /abort` 를 부르고 있다.
받는 쪽이 없어서 지금은 `fetch` 가 실패하고 조용히 `false` 로 떨어진다.

## 설계 — 두 갈림길을 여기서 정한다

**① 레지스트리는 `execute.ts` 모듈 스코프 `Map` 하나.**
넣고 빼는 자리가 전부 `execute()` 안이다. `server.ts` 가 들고 주입하면 `execute()` 시그니처가 바뀌고
넣고 빼는 책임이 두 파일로 갈린다. 지도는 메모리에만 산다 — 러너가 죽으면 같이 사라진다 (§3.4).

**② `timedOut` 불린을 사유 문자열로 바꾼다.**

```
지금:  let timedOut = false            → error.message = 'TIMEOUT'
바꿈:  entry.killedBy: 'TIMEOUT' | 'ABORTED' | null
```

지역 변수가 아니라 **레지스트리에 들어가는 핸들 객체의 칸**이어야 한다.
`abort()` 는 바깥에서 불리므로 `execute()` 의 지역 변수에 닿을 수 없다.
`statusFromExit(code, timedOut)` 의 시그니처는 그대로 두고 `killedBy !== null` 을 넘긴다.

### 주의 1 — 테스트가 레지스트리를 공유한다. 정리 구문이 계획에 없다

`running` 은 모듈 스코프 `Map` 이라 한 파일 안의 테스트가 전부 같은 지도를 본다.
할 일 2 가 `running.set(1, …)` 로 넣은 항목을 지우는 책임이 **`execute()` 의 `finally` 에만** 있는데,
테스트는 `execute()` 를 거치지 않는다.

**왜 문제인가.** 다음 테스트가 남은 엔트리를 보고 엉뚱하게 통과하거나 실패한다.
죽은 프로세스 핸들이 지도에 남으면 그 뒤 `abort()` 가 `true` 를 돌려준다 — 거짓 초록불이다.

**고칠 것.** 할 일 1·2 의 테스트에 `afterEach(() => running.clear())` 를 넣는다.
`beforeEach` 가 아니라 `afterEach` 여야 한다. 실패로 중단된 테스트가 남긴 것까지 치운다.

### 주의 2 — 할 일 3 의 RED 에 「깨진 결과 줄」 케이스가 빠졌다

`killedResponse()` 가 감싸는 기존 코드에는 `parseAfterKill()` 이 있고, 그 안에 `try/catch` 가 있다.
프로세스를 죽이면 `@@RESULT@@` 줄이 **중간에 잘려** JSON 이 깨질 수 있어서 넣어 둔 것이다.

계획의 RED 는 「부분 결과가 있으면 살아남고 없으면 `[]`」 둘만 단언한다.
**깨진 줄이 들어왔을 때 `[]` 가 되는 세 번째 경로가 빠졌다.**

**왜 문제인가.** 그 경로가 이번에 함수로 옮겨지는데 테스트가 없다. 옮기다 `try/catch` 를 떨어뜨리면
러너가 500 으로 죽는다 — 사용자 눈에는 「러너에 닿지 못했습니다」로 보이고, 진짜 원인은 묻힌다.
기존 동작을 옮기는 자리이므로 **회귀 테스트로 다룬다.**

**고칠 것.** 할 일 3 의 RED 에 `killedResponse(1, 'ABORTED', 5, '@@RESULT@@{"steps":[')` 처럼
잘린 줄을 넣어 `steps` 가 `[]` 이고 예외가 안 새는지 단언하는 케이스를 더한다.

### 주의 3 — 끊는 요청과 정상 종료가 겹치면 PASS 가 ABORTED 로 뒤집힌다

자식이 실제로는 끝났지만 `close` 이벤트가 아직 안 온 창(stdout 파이프가 닫히기 전)에 `abort()` 가 들어오면,
지도에 엔트리가 남아 있어 `killedBy = 'ABORTED'` 가 박힌다.
`stdout` 에는 `@@RESULT@@` 가 이미 다 들어와 있는데도 `killedResponse` 가 나간다.

**왜 문제인가.** 통과한 케이스가 `NA` + `ABORTED` 로 기록된다.

**실질 영향은 낮다.** admin 의 `store.ts:284` 가 닫는 `UPDATE` 마다 `AND finished_at IS NULL` 을 붙여 두었고,
그 주석이 「중단 처리와 러너 응답이 겹칠 수 있다」고 정확히 이 경합을 적고 있다. 먼저 닫힌 쪽이 이긴다.
사용자가 멈춘 상황이라 admin 은 이미 그 항목을 `ABORTED` 로 닫은 뒤다.

**고칠 것.** 이번에 코드로 막지 않는다. 창이 밀리초이고 admin 이 이미 막고 있다.
대신 `abort()` 에 **왜 여기서 이기려 하지 않는지**를 한 줄 주석으로 남긴다 — 다음 세션이 같은 것을 또 판단하지 않게.

### 주의 4 — 할 일 4 가 이번 일과 무관한 라우트 둘을 같이 옮긴다

`/health` 와 `/execute` 는 이번 작업과 상관없는데 `routes.ts` 로 함께 이동한다. diff 가 커진다.

  ④`runId` 단위 중단 없음 — 계약 스키마가 `historyId` 만 받아 구조적으로 막힌다 ⑤`killTree` 로 그룹째
- **`killedResponse()` 추출은 과한 추상화가 아니다.** 같은 파일 `execute.ts:21` 의 `statusFromExit` 이
  **같은 이유**(자식 프로세스 없이 판정 규칙만 테스트한다)로 이미 뽑혀 있다. 선례와 같은 결이다
- **레지스트리를 `execute.ts` 모듈 스코프에 둔 결정이 맞다.** 넣고 빼는 자리가 전부 `execute()` 안이다.
  `abort()` 가 지도에서 지우지 않는 것도 맞다 — 지우면 `execute()` 의 `finally` 가 no-op 이 되고
  끊긴 뒤에도 `close` 를 기다리는 흐름이 끊긴다
- **새 의존성 0 · 새 클래스 0 · 파일 6개.** 복잡도 게이트(8파일 / 2클래스) 미달. 범위가 붙어 있다
- **이미 있는 것을 다시 만들지 않는다.** `killTree`(검증 완료) · `parseAfterKill` · `statusFromExit` 선례 ·
  WS-B 의 `abortRunner` 호출자 · 계약 §5.2 — 전부 재사용한다. 새로 쓰는 것은 지도와 라우트뿐이다

- **끊긴 실행의 부분 스크린샷 정리** — `artifacts/` 청소는 러너 몫이 아니다. SPEC 에 없다
