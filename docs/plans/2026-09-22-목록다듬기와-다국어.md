## 왜

화면을 실제로 쓰면서 나온 지적 12건이다. 셋으로 갈린다.

**① 목록이 표로 안 읽힌다** — 컬럼 이름이 없어 각 칸이 무엇인지 모른다. 케이스 목록·실행 기록 둘 다 그렇다.
파라미터 입력칸이 케이스명 *아래* 붙어 있어 한 줄이 두 덩어리로 보인다.

**② 「열렸다」가 안 느껴진다** — `상세` 는 줄 아래로 펼쳐질 뿐이고, `결과 보기` 는 반대로
화면을 통째로 갈아타 보던 자리와 검색 조건을 잃는다.

**③ 글자가 만든 사람의 말이다** — 「도는 중」·「끝남」·「실패 섞임」·「기록 없음」.

여기에 **사이드바의 파란 네모와 `DEMO-` 가 무엇을 뜻하는지 화면만 봐서는 모른다**는 지적이 붙었다.
둘 다 걷고 남는 서비스 고르개를 제대로 만든다.

**다국어는 이 참에 같이 한다.** 어차피 화면 글자 대부분을 건드리므로 나중에 하면 같은 파일을 두 번 고친다.
사용자가 「전 화면 한 번에」를 골랐다.

### 다국어 설계 — 키를 한국어 원문으로 쓴다

**표를 한 벌만 둔다.** `en` 표가 `한국어 원문 → English` 를 담고, `ko` 는 키 자체가 답이다.

```
t('진행 중')  →  ko: '진행 중' (키 그대로)  ·  en: 'Running' (표에서)
```

- 표가 **둘이 아니라 하나**다. 322 × 2 = 644 가 아니라 322 개다
- 코드가 읽힌다. `t('cases.status.running')` 은 무엇이 나올지 파일을 열어야 안다
- **빠진 번역이 화면을 깨지 않는다.** 표에 없으면 한국어가 그대로 나온다

대신 **조용히 빠지는 것**을 기계가 잡아야 한다. 검사 둘을 같이 만든다 (할 일 1).

| 검사 | 무엇을 막나 |
|---|---|
| 소스의 `t('…')` 키가 전부 `en` 표에 있다 | 번역을 빠뜨린 채 초록불이 뜨는 것 |
| `en` 표의 키가 전부 소스에 있다 | 워딩을 고친 뒤 옛 키가 표에 남는 것 |
