## 왜

지금 고정 spec 은 창(`page`) 하나와 `request` 하나를 모든 케이스 부품에 같이 넘기고, kit 은 `traced` 로만 감싼다.
그래서 앞 케이스의 시계 고정 · 주입 스크립트가 뒤로 새고, `finally` 의 API 삭제가 앞 부품 데이터를 지우고, 케이스 API 요청에는 모킹이 안 걸린다(10-04~06 실측 — 시나리오 §3.7 결정 12 표).

**코드 실측 (2026-10-06, Playwright 1.63)** — 감싸는 자리를 정하려고 번들을 읽었다.
- `Page` 는 만들 때 `this.request = this._browserContext.request` 로 받는다 → 러너가 창의 `request` 를 바꿔 끼운 뒤 `newPage()` 하면 `page.request` 도 감싼 것이다
- `Browser.newPage()` 는 안에서 `this.newContext()` 를 부른다 → `browser.newContext` 하나만 감싸면 둘 다 잡힌다
- `@playwright/test` 의 ESM 입구(`index.mjs` → `playwright/test.mjs`)는 CJS `test.js` 의 `playwright.request` 객체를 그대로 다시 내보낸다 → 케이스(`require`)와 고정 spec(`import`)이 **같은 객체**를 볼 가능성이 크다. 러너 이미지에서 잰다(할 일 1 탐침 · 할 일 9 한 바퀴, LEARNINGS [WS-C] 2026-09-28)
- 무늬 맞추기는 공개 함수가 없다(`globToRegexPattern` · `resolveGlobBase` 는 번들 내부). glob 변환만 옮긴다 — 아래 결정 7

**LEARNINGS 근거** — [WS-C] 2026-09-28 「로컬 · CI 초록인 러너가 이미지에서만 죽었다 — kit 이 require 와 import 로 섞여 불렸다」.
그래서 `window.ts` · `links.ts` · `parts.ts` 는 kit 을 **타입으로만** 가져오고(값은 `wire.ts` 사본), 이미지 실측(할 일 1 · 9)을 완료 조건에 둔다.

### 주의 2 — 이어 주기 `route` 핸들러의 끝맺음이 정해지지 않았다 (eng)
손 안 댈 요청에 `continue()` 를 부르면 먼저 건 모킹을 건너뛰고 진짜 서버로 간다(명세가 「가장 나쁜 실패」라 부른 것). `fail` 판정 요청을 그냥 보내면 막으려던 준비가 서버를 바꾼다.
고칠 것: 손 안 대면 `route.fallback()` · 바꿔 보내기는 `fallback({ method, url })` · `fail` 이면 `route.abort()` + 부품 오류. API 쪽 `fail` 도 안 보내고 던진다. e2e 에 「모킹과 이어 주기가 같은 주소, 판정 뒤에는 모킹 응답」.

### 주의 3 — 응답 듣기의 「처음 맞은 응답」 경합 · 기다림 상한 (eng)
본문을 다 읽은 뒤 「이미 적었나」를 보면 거의 동시에 온 둘째가 첫째를 덮는다. 3xx · 닫힌 창은 본문을 못 읽는다. 「끝에서 다 적을 때까지 기다림」에 상한이 없어 롱폴에 걸리면 시나리오 전체가 `TIMEOUT`.
고칠 것: 이벤트가 오는 순간 자리를 잡고 본문은 Promise 로. 부품 끝에서 남은 부품 한도 안에서 `allSettled`. 못 읽으면 「<N>번 부품 응답 본문을 못 읽었다」. 리스너는 창 단위.

### 주의 4 — 부품 시험 한도의 구멍 넷 (eng)
① 창만 닫으면 부품 request · 직접 만든 연결은 계속 돈다 ② 창을 닫은 뒤 `finally` 삭제가 미룸으로 오면 닫힌 도구에 `storageState()` 를 불러 예외 — 삭제가 사라진다 ③ 5초 뒤 늦은 삭제가 뒷정리 보내기와 겹친다 ④ 루트 `timeout: 0`(무제한)이면 모든 부품이 0ms 에 `FAIL`.
고칠 것: 걸리면 닫기 전에 상태를 찍고 창 · 부품 request · 그 부품이 만든 연결을 함께 닫는다. 부품이 끝난 뒤 그 부품 도구로 오는 요청은 하나로 정한다. 뒷정리 목록은 보내기 직전에 얼린다. `timeout` 0 은 한도 없음. parts.test 에 「한도 뒤 늦은 삭제」 · 「0 은 무제한」.

### 주의 5 — 이어 주기 실패 원인이 사람에게 안 보인다 (ceo)
돌려줄 응답이 없어 요청을 막으면 케이스가 먼저 `net::ERR_FAILED` · JSON 오류로 실패한다. 걸어 둔 막기 · 바꿔 보내기가 한 번도 안 걸려도 기록이 없다.
고칠 것: 이음 오류를 케이스 오류보다 앞에 두고 둘 다 싣는다. 부품이 `FAIL` 이면 한 번도 안 걸린 이어 주기를 메시지 끝에 붙인다(`error.message` 는 문자열이라 계약 그대로). parts.test 두 경우.

### 주의 6 — API 쪽 무늬가 브라우저와 달라도 빨강이 안 날 수 있다 (ceo)
결정 7 근거 「어긋나면 시험 실행이 빨강」은 돌려주기만 맞다. 막기 · 바꿔 보내기 · API 모킹은 안 맞으면 조용히 서버로 간다.
고칠 것: e2e 에 같은 (무늬, 주소) 묶음을 진짜 `context.route` 와 `무늬맞음` 에 넣어 같은지 보는 표 검사. 결정 7 근거를 「막기 · 바꿔 보내기는 조용히 안 걸릴 수 있다 — 주의 5 의 미발동 표시가 알린다」로.

### 주의 7 — 디바이스 칸을 손으로 고르지 않아도 된다 · 루트 `use` 가 시나리오에 안 온다 (eng 주의 7 · ceo 주의 5)
Playwright 1.63 은 테스트 안의 모든 `browser.newContext` · `request.newContext` 에 프로젝트 `use` 를 채운다(`playwright/lib/index.js` `runBeforeCreateBrowserContext` — 컨트롤러가 확인). 시나리오 설정은 루트 `use` 에서 `baseURL` 만 가져와 `httpCredentials` · `ignoreHTTPSErrors` · `headless:false` 가 시나리오에 안 온다 — 회사 서버에서 단독은 초록 · 시나리오는 빨강이 원인 없이 난다.
고칠 것: window.ts 는 `storageState` 만 넘긴다. 시나리오 설정 `use: { ...root.use, baseURL }`. 실측에 「루트 use 의 칸 하나가 부품 창까지 간다」.

### 주의 8 — 결정 6 근거가 틀렸다 · 로그아웃 뒤 미룬 삭제 401 (eng 주의 6 · ceo 주의 6)
러너가 `newContext` 를 감싸므로 만들 때 옵션(`baseURL` · `extraHTTPHeaders` · `httpCredentials`)을 직접 받는다. 여정 뒤에 로그아웃(POST — 안 미뤄진다)이 있으면 끝의 삭제가 401 이고 데이터가 남는다.
고칠 것: 감싼 도구마다 그 옵션을 기억해 미룬 삭제에 싣는다. 로그아웃 401 은 「남는 한계」에 한 줄. parts.test ⑤ 에 「하나가 401 · 예외여도 나머지를 보내고 그 줄에 status · error」.

### 주의 9 — 이미지 실측이 늦다 · 의존 · 리눅스 줄 (ceo 주의 2 · eng 주의 8)
실측 결과에 따라 할 일 6 · 8 이 바뀌는데 판정은 「같은 객체인가」 한 번이면 끝난다. 이미지 실측은 HTTP 입구를 거쳐 할 일 3 이 없으면 `links` 가 사라진다. `e2e-server` 를 고정 포트로 혼자 띄우는 입구가 없다. 리눅스는 `--add-host` 와 0.0.0.0 바인드가 필요하다(SETUP 555 · 616줄).
고칠 것: 7a(같은 객체인지만, 묶음 1) · 7b(지금 자리, 한 바퀴). 7b depends-on [3, 6]. e2e-server 에 포트 인자 입구. SETUP 에 리눅스 두 줄.
