## 왜

지금 작성 경로는 정방향 하나다 — 기획서만 보고 케이스를 만든다. 기획서가 늦거나 화면과 어긋나면
그 어긋남이 케이스 작성 도중에 조용히 묻힌다. 2026-09-25 설계 대화에서 사용자가 역방향 결정 9개를 정했고
(아래 표), 같은 날 게이트 0 에서 계약 변경을 승인했다.

| # | 결정 |
|---|---|
| 1 | 기획서와 실제 화면을 **대조**한다 |
| 2 | 같으면 정식 케이스 — 기대값은 기획서, 화면에서는 요소 주소만 |
| 3 | 다르면 **원본 기획서에 표시**해 기획자에게 넘기고, 그동안 **화면 기준 임시 케이스** |
| 4 | 임시 케이스는 **「미확정」 꼬리표**. 실행하되 통과율·증적에서 **따로 묶는다**. 수정된 기획서가 다시 오면(R9 대조) 확정하거나 지운다 |
| 5 | 화면에만 있는 것도 3과 같다 — 「문서에 없음」 표시 + 미확정 케이스 |
| 6 | 훑는 범위 = 기획서가 말하는 화면 + 거기서 바로 이어지는 한 칸 |
| 7 | 로그인 = 설정의 대상 서버 줄마다 테스트 계정 |
| 8 | 표시 = 워드는 메모 단 사본 · 피그마는 그 화면에 댓글 · PDF 는 스티커 메모 사본(새 npm 패키지 승인 뒤) |
| 9 | 작성 화면에 「실제 화면과 대조」 체크박스 하나. 역방향이면 대상 서버도 고른다(게이트 0) |

**3 은 「기대값은 사람이 판정한 것에서만」 규칙의 예외다.** 사용자가 위험(답이 안 오면 버그를 지키는 케이스가
초록으로 남는다)을 듣고 골랐고, 4 의 꼬리표가 그 위험을 막는 장치다. 규칙이 적힌 자리마다 예외를 같이 적는다.

### BLOCKER 1 — 기획서 없는 역방향이 빠졌다 (사용자, 검토 중 추가 요구)

**무엇이** — 사용자가 검토 도중 요구를 더했다. 「기획서 없이 화면만 보고도 테스트 코드를 만들 수 있어야 하고, 그 경우 화면 기준으로 역기획서가 나와야 한다」.
계획은 결정 1(기획서↔화면 대조)만 다룬다.
**왜 문제** — 지금 계약으로는 그 요청이 설 수조차 없다. 줄에 세우기가 자료 0 이면 `409 NO_ASSETS`(작성 §7)이고, 훑는 범위(결정 6)가 「기획서가 말하는 화면」이라 기획서가 없으면 범위가 없다.
**고칠 것** — ⒜ 기획서 없는 요청은 **시작 주소**를 받고 범위는 그 화면 + 한 칸 옆 ⒝ 그 요청의 케이스는 **전부 미확정**(사람이 판정한 기대값이 없다) ⒞ 산출물 **역기획서**(화면에서 뽑은 요구사항 문서, 항목마다 「확인 필요」) — 기획자가 확인해 다시 올리면 정방향 R9 대조로 확정 ⒟ 계약 추가(자료 0 허용 조건 · 시작 주소 칸 · 자료 역할에 「역기획서」)는 **게이트 0 추가 승인**이 필요하다

### BLOCKER 2 — 테스트 계정 비밀번호가 설정 저장 한 번에 지워진다

**무엇이** — 할 일 2·5 는 비밀번호를 `service_env` 에 둔다. 그런데 설정 저장은 그 서비스의 `service_env` 를 **전부 지우고 다시 넣는다**(`apps/admin/src/settings/store.ts:71`). 비밀번호는 되돌려 보여주지 않으니 화면이 다시 보낼 수도 없다.
**왜 문제** — 누가 서비스 이름만 고쳐도 모든 환경의 테스트 계정이 조용히 사라지고, 다음 역방향 요청이 로그인에서 실패한다.
**고칠 것** — 명세에 「`envs` 줄에 비밀번호가 비어 오면 **그 환경의 기존 값을 유지**한다(환경 키로 맞춘다)」를 적는다. 또는 계정을 별도 표로 뺀다

### 주의 1 — 자식 Claude 가 테스트 계정 비밀번호를 든다

역방향은 자식이 브라우저로 로그인해야 해서 비밀번호가 자식 환경에 들어간다. 자식은 외부 기획서를 읽으므로 숨긴 지시로 밖에 보낼 수 있다(피그마 토큰과 같은 한계, 작성 §3.6 「남는 한계」). **남는 한계에 적고**, 테스트 계정은 **권한 낮은 전용 계정**을 쓰라고 SETUP 에 적는다.
생성된 케이스에 계정 값이 **글자로 박히면 안 된다** — `params` 의 비밀값 칸(`.meta({ secret: true })`, K9)으로만 받는다고 명세에 못박는다

### 주의 2 — 훑기가 대상 서버의 데이터를 바꿀 수 있다

「한 칸 옆」을 훑다가 삭제·결제·발송 버튼을 누르면 실제 qa 데이터가 바뀐다. **훑기는 이동·열기만 하고 저장·삭제·결제·발송은 누르지 않는다**를 명세에 적는다. 그런 흐름은 케이스로만 만들고 관문 실행에서 돈다(정방향과 같다)

### 주의 3 — 미확정이 영원히 남을 수 있다

기획자 답이 안 오면 미확정 케이스가 계속 돈다. 목록·대시보드에 **미확정 건수와 가장 오래된 것의 나이**를 보이게 해야 잊히지 않는다. 증적 문서 머리에도 미확정 수를 싣는다

### 주의 4 — 미확정 묶음 안의 실패를 숨기지 않는다

`counts.unconfirmed` 하나로 뭉치면 미확정 케이스가 **실패**해도 안 보인다. 화면 기준 케이스의 실패는 「화면이 바뀌었다」는 신호다. 미확정 묶음은 **그 안의 통과·실패를 따로** 보인다(예: 미확정 5 — 통과 4 · 실패 1)

### 주의 5 — 피그마 댓글·PDF 표시가 안 될 때의 길

지금 발급 안내는 피그마 토큰을 읽기 전용으로 만들라고 한다. 권한이 없으면 댓글이 실패한다. PDF 는 새 패키지 승인 전이다. **어느 경우든 요청 전체를 실패시키지 않고** 차이를 결과(차이 목록)에 남기고 「표시 못 함 — 이유」를 보인다고 적는다

### 주의 6 — 할 일 1 이 크다

할 일 1 이 새 소절과 §7 통로 넷과 계약 블록을 한 번에 쓴다. 2~5분 규칙보다 크다. 문서라 위험은 낮지만, [6] 이 한 절 안의 앞뒤 어긋남을 보도록 검사 목록에 올린다

### 통과한 것

- 코드 0줄 · 계약 블록 `상태: 대기` 로 두고 구현 PR 이 반영 완료로 바꾸는 흐름 — 되돌리기 쉽다
- 기대값 규칙의 예외를 **규칙이 적힌 세 자리 모두에** 적는 할 일 6 — §2.7 ① 을 지킨다
- 코드 상수(`counts` 타입 · K 검사기)를 이번에 고치지 않고 갈래 항목으로 넘기는 판단
- 사업 방향과 맞는다 — 문서 없는 기존 서비스에 들어가는 컨설팅에서 **역기획서 자체가 납품물**이 된다 (BLOCKER 1 의 가치)
