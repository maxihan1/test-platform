### 주의 1 — 「다시 보내도 안전하다」는 연결 오류 전부에 맞지는 않다
`fetch failed` 는 요청이 **나가기 전** 끊긴 경우(이번 #3336)와 **나간 뒤 답을 받기 전** 끊긴 경우를 구분하지 않는다.
단계 보고(PATCH)·끝내기는 두 번 가도 결과가 같지만, **집기(claim)는 두 번 가면 두 건을 집을 수 있다** — 첫 건은 맥이 모른 채 RUNNING 으로 남는다.
지금도 그 경우 첫 건은 잃으므로(던지고 끝) 나빠지는 것은 「한 건 더 집는다」뿐이고, 다음 켤 때 멈춘 RUNNING 을 닫는 장치가 있다.
**고칠 것**: 계획의 「안전하다」 문장을 이 한계로 고치고, 코드 주석에 `ponytail:` 로 천장을 적는다. 집기만 빼는 것은 과하다 — 이번 사고가 난 자리가 오히려 집기 뒤 첫 보고다.

### 주의 2 — 30초 시간 제한은 시도마다 새로 걸어야 한다
`AbortSignal.timeout(30_000)` 을 바깥에서 한 번 만들어 두 시도가 나눠 쓰면 두 번째 시도가 남은 시간만 받는다.
**고칠 것**: 시도마다 새 signal. 할 일 2 에 「두 번째 시도에 새 signal 이 간다」 단언을 더한다.

### 주의 3 — RED 가 정말 빨간지 먼저 본다
재현 검사는 「막힌 뒤 곧바로 부르면 닫힌 연결을 다시 쓴다」는 가정에 기댄다. 이벤트 루프가 먼저 FIN 을 처리하면 옛 코드로도 통과해 **헛검사**가 된다
(LEARNINGS 「항진명제」 재발형). **고칠 것**: 고치기 전에 옛 코드로 돌려 실패를 눈으로 보고 PR 코멘트에 원문을 싣는다. 안 빨개지면 서버가 응답 뒤 소켓을 바로 끊는 쪽으로 바꾼다.
