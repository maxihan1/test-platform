# 케이스를 여러 건 골라 한 번에 실행하는 자리

등급: 3 · 갈래: 없음(명세 + 화면) · 2026-09-21

## 도메인 정리

건드리는 BC 는 **카탈로그**(§8.1 케이스 목록)와 **실행**(§8.2 실행 설정) 둘이다.

| 영향 | 무엇 |
|------|------|
| 계약 | **없음.** 실행 만들기 API 의 `items` 가 이미 배열이고 상한이 없다 |
| DB | 없음 |
| 러너 | 없음 |
| 화면 | 케이스 목록에 고르는 칸과 실행 버튼, 고른 것을 확인하는 모달 |
| 명세 | 카탈로그 §8.1 줄 모양 표 · 실행 §8.2 · DESIGN 모달 규칙 |

## 왜

**여러 건 실행은 이미 세 곳에 있고 화면에만 없다.**

| 어디 | 무엇이 이미 되나 |
|------|----------------|
| 실행 만들기 API | `items` 가 `z.array(...).min(1)` 이고 상한 없음 |
| 정기 실행 (`scripts/run-scheduled.ts`) | 그 서비스 활성 케이스 **전부**를 `params: {}` 로 한 요청에 건다 |
| 화면 계산기 (`web/runPlan.ts`) | `항목수(케이스수, 디바이스수, 반복)` 이 **케이스 수를 인자로 받는다** |

그런데 `RunSetup.tsx:77` 이 `항목수(1, platforms.length, ...)` 로 **`1` 을 박아 놨다.**
케이스 목록에는 고르는 칸이 아예 없다.

**명세가 자기 안에서 어긋나 있다.** 실행 §8.2 는 항목 수를 「케이스 수 × 디바이스 수 × 횟수」로 세고
1000건 상한의 근거를 「케이스 10 × 디바이스 2 × 반복」으로 적었는데, 카탈로그 §8.1 의 줄 모양
`TC ID | 케이스명 | 지원 디바이스 | 마지막 결과 | [실행]` 에 **고르는 칸이 없어 그 「케이스 수」는 영원히 1이다.**

실측 확인 — API 로 11케이스(실행 단위 13개)를 한 요청으로 돌렸다. RUN 8802, 통과 10 · 실패 2 · 미실행 1.
**서버는 아무 문제 없이 받았다.**

## 화면 설계 — 이 계획이 정한다

게이트 0 의 답 넷을 그대로 따른다. 「구현자가 정한다」로 넘기지 않는다.

### ① 고르는 칸과 버튼

케이스 목록 각 줄의 **거터 바로 오른쪽, `tcId` 왼쪽**에 고르는 칸을 둔다.
620px 미만에서 줄이 2단(거터 + 내용)으로 접히므로 **내용 쪽 첫 요소**로 둔다 (DESIGN.md 반응형).

목록 위 `다시 스캔하기` 옆에 버튼 하나를 둔다. **글자가 상태에 따라 바뀐다.**

| 고른 것 | 버튼 글자 | 무엇을 담나 |
|---------|----------|------------|
| 없음 | `전체 실행하기` | 지금 걸러진 목록의 **활성 케이스 전부** |
| 1건 이상 | `고른 N건 실행하기` | 고른 것만 |

**버튼을 둘로 나누지 않는다.** 같은 자리에서 같은 일을 하고 담는 대상만 다르다.
두 개를 나란히 두면 「전체 실행」과 「고른 것 실행」이 동시에 눌릴 수 있는 것처럼 보인다.

버튼은 동사로 끝나고 화살표를 붙이지 않는다 (DESIGN.md).

### ② 고른 것을 확인하는 모달

버튼을 누르면 모달이 뜬다. **모달이 실행 설정을 겸한다** — 대상 서버를 안 고르면 실행이 시작되지 않아야
하므로(§8.2) 그 칸이 반드시 여기 있어야 한다.

```
┌─ 실행할 케이스 N건 ──────────── 최대 480px ─┐
│ 대상 서버  [드롭다운]  주소를 흐리게 옆에     │  ← 머리 (고정)
├──────────────────────────────────────────┤
│ DEMO-001  메인 화면이 열린다        PC       │  ← 본문 (여기만 스크롤)
│ DEMO-002  할 일을 하나 …    PC   [값 고치기] │
│   ↳ 펼치면 그 케이스의 입력칸이 나온다        │
│ …                                          │
├──────────────────────────────────────────┤
│ 반복 [1]   □ 끝나면 Slack 알리기             │  ← 바닥 (고정)
│ 실행 항목이 N건 생깁니다                      │
│                        [취소]  [실행하기]    │
└──────────────────────────────────────────┘
```

- **기본은 전부 접혀 있다.** 접힌 케이스는 **코드에 적힌 기본값**으로 돈다. K10 이 「사람이 값을
  채워야만 도는 케이스」를 막고 있어 **모든 케이스가 값 없이 돈다** — 정기 실행이 이미 그렇게 돈다
- **`[값 고치기]` 는 입력칸이 있는 케이스에만 붙는다.** 없는 케이스는 그 자리가 비어 있다
- 고친 값은 **그 실행에만** 쓰인다. 케이스 코드의 기본값은 안 바뀐다 — **이건 이미 그렇게 돼 있다.**
  실행할 때 준 값은 `run_item` 에 박히고 케이스 파일은 아무도 안 건드린다
- **디바이스는 케이스마다 자기가 선언한 것을 전부 쓴다.** 모달에서 따로 안 고른다 — 정기 실행과 같다.
  케이스마다 선언이 달라 한 자리에서 고르게 하면 「이 케이스엔 없는 디바이스」를 고를 수 있게 된다
- **본문만 스크롤한다.** 머리와 바닥은 고정이다. 11건이든 100건이든 대상 서버와 실행 버튼이 늘 보인다
- 480px 을 지킨다. 모달 규칙의 나머지(닫는 길 셋 · 포커스 가두기 · 애니메이션 없음 · 뒤 화면 잉크 40%)도 그대로다

### ③ 상한을 넘겼을 때

`실행 항목이 N건 생깁니다` 를 바닥에 적고, 1000건을 넘으면 `실행하기` 를 못 누르게 하고
**그 이유를 화면 줄로 적는다** (DESIGN.md `:205` — 말풍선에 적지 않는다).

### ④ 모달 규칙을 세 자리로 늘린다

`DESIGN.md` 가 「모달은 두 자리에만 쓴다」고 못 박고 있다. 게이트 0 이 **늘리는 쪽으로 승인**했다.
**왜 늘렸는지를 규칙 옆에 같이 적는다** (CLAUDE.md §2.7 ②) — 여러 건을 거는 것은 시간과 기록을
쓰는 일이라 누르기 전에 무엇이 도는지 확인할 자리가 필요하다.

### ⑤ 300줄 규칙 — 이번에 쪼갠다

`CaseList.tsx` 가 이미 **308줄**이고 여기에 고르는 상태와 버튼이 더해진다. **이번에 쪼갠다.**
직전 PR 이 이 판단을 게이트 2 까지 들고 갔다가 그 자리에서 쪼갰다 — 같은 일을 반복하지 않는다.

- **`pickRun.ts` (새 파일)** — 고른 것에서 실행 항목을 만드는 **순수 로직**. 화면이 없어 jsdom 없이 검사한다
- **`RunPickModal.tsx` (새 파일)** — 모달
- `CaseList.tsx` 는 목록과 고르는 상태만 남는다

**`RunSetup.tsx` 는 안 건드린다.** 한 건짜리 화면은 그대로 두고 여러 건은 모달이 맡는다.
`항목수(1, ...)` 도 한 건 화면에서는 맞는 값이다.
