# 케이스를 여러 건 골라 한 번에 실행하는 자리

등급: 3 · 갈래: 없음(명세 + 화면) · 2026-09-21
**개정 1 (2026-09-21)** — 계획 검토의 치명 3건을 반영했다. 게이트 1 에서 「세 가지 고치고 만든다」로 승인.

## 도메인 정리

건드리는 BC 는 **카탈로그**(§8.1 케이스 목록)와 **실행**(§8.2 실행 설정) 둘이다.

| 영향 | 무엇 |
|------|------|
| 계약 | **없음.** `items` 가 이미 배열이고 상한이 없다. 목록 route 는 `page` 를 이미 받으므로 **쪽을 돌아 전부 받는 데 계약 변경이 필요 없다** |
| DB · 러너 | 없음 |
| 화면 | 케이스 목록의 고르는 칸과 실행 버튼, 고른 것을 확인하는 모달, 항목 수 계산기 |
| 명세 | 카탈로그 §8.1 · 실행 §8.2(항목 수 식 포함) · DESIGN 모달 규칙 |

## 왜

**여러 건 실행은 이미 세 곳에 있고 화면에만 없다.** 실행 만들기 API 의 `items` 는 배열이고,
정기 실행은 활성 케이스 전부를 한 요청에 걸며, 화면 계산기도 케이스 수를 인자로 받는다.
그런데 `RunSetup.tsx` 가 `항목수(1, ...)` 로 **`1` 을 박아 놨고** 목록에는 고르는 칸이 없다.

실측 — API 로 11케이스를 한 요청으로 돌렸다. **실행 단위 13개**, 통과 10 · 실패 2 · 미실행 1.

## 화면 설계 — 이 계획이 정한다

### ① 고르는 칸과 버튼

케이스 목록 각 줄에 고르는 칸을 둔다. 목록 위 `다시 스캔하기` 옆에 **버튼 하나**를 두고
글자가 상태에 따라 바뀐다.

| 고른 것 | 버튼 글자 | 무엇을 담나 |
|---------|----------|------------|
| 없음 | `전체 실행하기` | **지금 조건에 맞는 모든 쪽**의 활성 케이스 |
| 1건 이상 | `고른 N건 실행하기` | 고른 것만 |

**★「전체」는 보이는 쪽이 아니라 모든 쪽이다** (검토 치명 2).
목록 route 는 한 번에 50건만 준다. **버튼을 누르면 화면이 쪽을 돌며 전부 받아 온다.**
route 가 `page` 를 이미 받으므로 계약을 안 바꾼다. 받는 동안 버튼은 못 누르고 그 사실을 화면 줄로 적는다.

**★「마지막 결과」로 걸러도 빠지는 것이 없다** (검토 치명 3).
그 조건만 화면에서 거르는데, **마지막 결과 표는 이미 서비스 전체를 한 번에 받는다**(`lastByCase()` 는
쪽이 없다). 그래서 모든 쪽을 받아 온 뒤 그 표로 한 번 더 거르면 **한 쪽에 갇히지 않는다.**

### ② 620px 에서 고르는 칸이 어디 있나

줄이 2단(거터 + 내용)으로 접힌다. 고르는 칸을 **거터 칸 안에 판정 색 아래로** 넣는다.
내용 쪽 첫 요소로 두면 좁은 화면에서 **케이스명 위에 체크박스만 홀로 한 줄**이 된다 (검토 주의 4).

### ③ ★ 항목 수는 곱하기가 아니라 더하기다 (검토 치명 1)

명세 §8.2 의 「케이스 수 × 디바이스 수 × 횟수」는 **모든 케이스의 디바이스 수가 같을 때만** 맞다.
실측이 이미 반증한다 — 케이스 11건이 실행 단위 13개였다.

```
올바른 식 =  Σ(케이스마다의 디바이스 수)  ×  반복 횟수
```

`runPlan.ts` 의 `항목수(케이스수, 디바이스수, 반복)` 를 **`항목수(디바이스수들: number[], 반복)`** 로 바꾼다.
한 건 화면은 `항목수([platforms.length], repeat)` 로 부른다 — **`RunSetup.tsx` 가 한 줄 바뀐다.**

> **F9 판단을 밝혀 둔다** — `RunSetup.tsx`(364줄)에 화면 검사 파일이 없는데 이번에 **한 줄만** 바뀐다.
> 그 한 줄은 인자 모양 변경이라 **타입 검사가 틀리면 바로 잡는다.** 셈 자체는 `runPlan.test.ts` 가 덮는다.
> 그래서 `RunSetup.test.tsx` 를 이번에 만들지 않는다. **이 판단을 게이트 2 요약에 싣는다.**

### ④ 고른 것을 확인하는 모달

```
┌─ 실행할 케이스 N건 ──────────── 최대 480px ─┐
│ 대상 서버  [드롭다운]  주소를 흐리게 옆에     │  ← 머리 (고정)
├──────────────────────────────────────────┤
│ DEMO-001  메인 화면이 열린다        PC       │  ← 본문 (여기만 스크롤)
│ DEMO-002  할 일을 하나 …    PC   [값 고치기] │
├──────────────────────────────────────────┤
│ 반복 [1]   □ 끝나면 Slack 알리기             │  ← 바닥 (고정)
│ 실행 항목이 N건 생깁니다                      │
│                        [취소]  [실행하기]    │
└──────────────────────────────────────────┘
```

- **기본은 전부 접혀 있고 코드에 적힌 기본값으로 돈다.** K10 이 「값을 채워야만 도는 케이스」를 막고
  정기 실행이 이미 같은 길을 돈다
- `[값 고치기]` 는 **입력칸이 있는 케이스에만** 붙는다
- 고친 값은 **그 실행에만** 쓰인다 — 이미 그렇게 돼 있다. `run_item` 에 박히고 케이스 파일은 안 바뀐다
- **디바이스는 케이스가 선언한 것을 전부 쓴다.** 모달에서 안 고른다
- 본문만 스크롤한다. 머리와 바닥은 고정이라 건수가 늘어도 실행 버튼이 늘 보인다
- 480px · 닫는 길 셋 · 포커스 가두기 · 애니메이션 없음 · 뒤 화면 잉크 40%
- **★목업을 모달 구현보다 먼저 그린다** (검토 주의 3) — 480px 에 들어가는지를 그림으로 먼저 본다

### BLOCKER 1 — §8.2 의 항목 수 식이 여러 건에서 틀리다. 계획이 「그대로 둔다」고 못 박았다

「케이스 수 × 디바이스 수 × 횟수」는 **모든 케이스의 디바이스 수가 같을 때만** 맞다.
실측 — 케이스 11건을 돌렸더니 실행 단위가 **13개**였다(`DEMO-008`·`DEMO-009` 는 둘, `DEMO-010` 은 하나).
올바른 식은 **Σ(케이스별 디바이스 수) × 횟수** 다.

**왜 문제인가** — 화면이 「실행 항목이 N건 생깁니다」를 **틀린 수로** 적는다.
1000건 상한도 틀린 수로 막아 넘지 않았는데 막거나 넘었는데 통과시킨다.
계획은 할 일 5 에서 「케이스 수 두 줄은 **그대로 둔다 — 이제 사실이 된다**」고 적었는데 **사실이 되지 않는다.**

**고칠 것** — §8.2 의 식을 고치고, `runPlan.ts` 의 `항목수()` 서명도 같이 바꾼다(지금은 `디바이스수` 하나를 받는다).

### BLOCKER 2 — 「전체 실행하기」가 보이는 한 쪽만 돌린다

케이스 목록은 서버에서 **한 쪽(50건)만** 받는다 (`catalog/routes.ts` `PAGE_SIZE = 50`).
계획은 「고른 것 없으면 걸러진 목록 **전부**」라고만 적고 그 「전부」가 무엇인지 안 정했다.
손에 있는 것을 쓰면 **51건째부터 조용히 빠진다.** 버튼 글자는 「전체」라고 말한다.

**왜 문제인가** — **지금 데모가 11건이라 어떤 검사에서도 안 드러난다.**
실제 서비스 케이스가 51건이 되는 날 처음 터지고, 그때 사람은 전부 돌린 줄 안다.

**고칠 것** — 정기 실행이 하는 대로 `pageSize: MAX_ITEMS` 로 다시 받아 오거나,
버튼 글자를 「이 쪽 전부」로 낮춘다. **둘 중 하나를 계획이 고르고 그 경계를 검사로 박는다.**

### BLOCKER 3 — 「마지막 결과」 조건이 걸리면 전체 실행의 뜻이 깨진다

검색 조건 다섯 중 **「마지막 결과」만 화면에서 거른다** (§8.1 표 「거르는 곳: 화면」).
그래서 「실패한 것만 전체 실행」은 **한 쪽 안에서만** 참이다.
명세도 이미 이 한계를 안다 — 「이 쪽에는 …인 케이스가 없습니다 / **다음 쪽에 있을 수 있습니다**」.

**왜 문제인가** — 「실패한 것 전부 다시 돌리기」가 이 기능의 가장 쓸모 있는 쓰임새인데 **그게 정확히 안 되는 조합**이다.

**고칠 것** — 그 조건이 걸렸을 때 전체 실행이 무엇을 담는지 명세와 **화면 줄**에 적는다.

### 주의 1 — 묶음 ②는 실제로 직렬이다

할 일 2와 3이 `styles.css` 를 같이 건드린다. `tpx-plan` §2 가 「`files` 가 겹치는 두 할 일은
`depends-on` 이 없어도 **자동으로 직렬화된다**」고 정했다. 묶음 수는 맞지만 그 안이 순차다.
계획이 이 사실을 안 적어 [5] 가 병렬로 던졌다가 충돌한다.

### 주의 2 — `몇건()` 이 `항목수()` 의 사본이 된다

상한 판정은 재사용하기로 해 놓고 계산은 새로 만든다. BLOCKER 1 을 고치면서 `항목수()` 자체를
여러 건용으로 바꾸는 편이 사본을 안 만든다.

### 주의 3 — 목업을 할 일 3보다 먼저 그려야 한다

모달 480px 안에 대상 서버 + 케이스 N줄 + 반복 + Slack + 항목 수 + 버튼 둘이 들어간다.
**계획이 실측 없이 「들어간다」고 단정했다.** 목업(할 일 6)이 묶음 ① 이라 순서는 맞지만
**계획이 이 의존을 안 적었다.** 안 들어가는 것이 할 일 3 뒤에 드러나면 구현을 다시 한다.

### 주의 4 — 620px 에서 고르는 칸이 혼자 뜬다

목록 행이 2단(거터 + 내용)으로 접히는데 고르는 칸을 「내용 쪽 첫 요소」로 두면
좁은 화면에서 **케이스명 위에 체크박스만 홀로 한 줄**이 된다. 계획이 이 모양을 안 그렸다.

### 주의 5 — 안 보이는 고름

조건 변경·쪽 넘김 너머로 고름을 유지하면 **화면에 없는 케이스를 실행하게 된다.**
모달이 전부 나열하므로 마지막에 볼 수는 있지만, 11건을 고른 줄 알았는데 모달에 23건이 뜨는 일이 생긴다.

### 제품 관점 — 이 버튼의 값은 「지금 당장」뿐이다

**정기 실행이 이미 같은 일을 한다.** 사람이 정기 실행을 켜 뒀다면 이 버튼이 주는 것은 「기다리지 않고 지금」이다.
완료 기준 상자 문구를 그 값에 맞춰 적어야 한다 — 「전부 돌릴 수 있다」가 아니라
「**기다리지 않고 지금** 골라 돌릴 수 있다」다.
