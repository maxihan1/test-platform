## 왜

MKT 를 세 번 작성하니 케이스가 148 · 141 · 227개로 갈렸다. 조사(2026-10-04)는 가장 큰 원인을 「요구 여러 줄을 케이스 하나로 묶는 판단(R15)」으로 봤고,
차례 번호라 묶기가 하나만 달라도 같은 `MKT-FN-010` 이 실행마다 다른 케이스가 된다고 짚었다. 그런데 이 진단은 눈으로 한 것이고 숫자가 없다.
9번(같은 입력이면 같은 결과)의 뒤 PR(묶기 · 번호를 코드로)이 효과가 있는지 보려면 기준선이 먼저다 — LEARNINGS 2026-10-03 「속도를 바꾸는 일은 품질 숫자 기준선을 먼저 만들고 시작한다」.

재는 숫자 넷(두 실행씩).

| 숫자 | 뜻 | 재료 |
|---|---|---|
| 같은 번호 같은 내용 | 두 실행에 다 있는 tcId 가운데, 확인 문장 집합이 절반 이상 겹치는(자카드 ≥ 0.5) 비율 | 케이스 파일 |
| 확인 문장 겹침 | 두 실행의 확인 문장 전체 집합의 자카드(겹친 수 ÷ 합친 수) | 케이스 파일 |
| 화면 파일 겹침 | `pages/` · `components/` 파일 이름 집합의 자카드 | 파일 경로 |
| 요구별 케이스 수 일치 | 원장 번호마다 덮은 tcId 수가 같은 비율. 표가 둘 다 있을 때만 | 요구사항 표 |

확인 문장은 `verify('<문장>', …)` 의 첫 인자다. 빈칸만 하나로 모아 글자 그대로 견준다 — R11 이 표의 결과 칸을 글자 그대로 옮기게 하므로
같은 요구면 같은 문장이 나와야 한다. 말만 조금 바뀐 것도 다른 문장으로 친다(엄격한 쪽).

## 게이트 1 결정 (2026-10-04 · 지적 반영하고 진행) — 아래 할 일보다 이 절이 우선

숫자를 다섯으로 바꾼다. 원장 번호를 쓰는 셋은 두 표에 원장 번호가 다 있을 때만 잰다.

| 숫자 | 정의 | 없을 때 |
|---|---|---|
| 같은 번호 같은 요구 | 두 실행에 다 있고 **한쪽이라도 원장 번호를 덮은** tcId 가운데(둘 다 안 덮으면 분모에서 뺀다), 덮은 원장 번호 집합의 자카드 ≥ 0.5 인 비율 | 표 없음 · 원장 없음 · 같은 번호 없음 |
| 묶인 번호 짝 겹침 | tcId 마다 덮은 원장 번호를 둘씩 짝지은 집합, 두 실행 짝 집합의 자카드(R15 묶기) | 표 없음 · 원장 없음 · 짝 없음 |
| 한쪽만 덮은 번호 | 한 실행만 케이스로 덮은 원장 번호 수(a만 · b만) | 표 없음 · 원장 없음 |
| 확인 문장 겹침(표현까지) | 확인 문장 전체 집합의 자카드 | 문장 없음 |
| 화면 파일 겹침 | `pages/…` · `components/…` 상대 경로 집합의 자카드. 경로 마디로 판정 | 파일 없음 |

- 자카드는 합집합이 0 이면 null → 줄에 「— 짝 없음」처럼 재료가 없다고 찍는다(「없음」만 쓰면 「겹침 0」으로 읽힌다 — 검사 지적). NaN 을 내지 않는다
- 표 tcId 칸은 백틱을 벗기고 그 폴더에 파일이 있는 tcId 만 쓴다. 맞는 줄이 하나도 없으면 표를 잘못 준 것이라 멈춘다
- 출처 칸의 번호 꼴 글자 가운데 tcId 가족(`MKT-FN`)과, 표 전체(제외 표 포함)에서 서로 다른 번호가 원장 하한(`authoring-ledger.ts` 의 `가족하한` 을 export 해 재사용) 미만인 가족은 원장 번호로 치지 않는다 — R18 근거(`ISO-8601`)가 가짜 짝을 만든다
- 명령은 절대 경로로 받는다. 준 표 파일이 없거나 폴더 자리가 폴더가 아니거나 쉼표 조각이 셋이면 끝 코드 2. 2차 표는 `git show origin/author-5873:docs/cases/MKT.md` · `origin/author-10779:docs/cases/CDY.md` 로 임시 자리에, CDY 1차 표는 `~/Projects/cdy-run-pr143/PR143-body.md`
- 할 일 2 의 files 에 `scripts/authoring-ledger.ts`(export 한 줄)를 더한다(검사 지적 뒤 — 처음엔 `authoring-ledger-check.ts` 의 `tcId꼴` 이었으나 필요 없어 되돌렸다)
