## 왜

지금은 에이전트가 **서비스마다 대기열 하나**를 돌리고 한 건을 끝내야 다음 건을 가져간다(`scripts/authoring-agent.ts:188-239`).
서버 SQL 은 서비스 단위로 막지 않는다(`agentStore.ts` `집기` 는 PENDING 하나만 본다). 반영(머지)도 같은 줄이라 CI 를 기다리는 최대 17분 동안 그 서비스의 다른 작성이 멈춘다.

그냥 풀면 두 요청이 같은 main 에서 출발해 **같은 다음 번호**를 고른다 — 자식은 「표와 폴더의 가장 큰 번호 다음」을 고르고(스킬 문서뿐, 계산기 없음) 다른 열린 PR 을 못 본다.
케이스 파일(`tests/<폴더>/<tcId>.spec.ts`)은 add/add 충돌, 요구사항 표(`docs/cases/<접두사>.md`)는 거의 확실히 텍스트 충돌이 난다.
반영은 rebase 도 update-branch 도 안 해서(`authoring-merge.ts`) 충돌하면 CI 가 안 뜨고 17분 뒤 FAILED 가 된다. 파일 이름이 우연히 다르면 **같은 tcId 가 main 에 둘** 들어가고, 그러면 카탈로그 스캔이 그 서비스 캐시를 아예 갱신하지 않는다(`catalog/routes.ts`).
원장 · 커버리지는 요청마다 따로라 안 섞인다.

## 정한 것 — 사람이 보는 장면 (명세 작성 §3.6 새 절의 재료)

| 무엇 | 정한 것 |
|---|---|
| 동시 실행 | 작성 · 재실행 · 케이스 고치기는 **자리(동시 상한, 모든 서비스 합쳐 기본 2)** 만 있으면 같은 서비스도 나란히 돈다. 자리가 없으면 「대기 중」으로 남는다 — **에이전트가 자리를 먼저 잡고 나서 가져간다**(가져간 채 자리를 기다리면 30분 뒤 「응답 없음」으로 보인다) |
| 반영은 한 줄 | **같은 서비스의 반영은 모두 차례로**(보류가 있든 없든) — main 에 차례로 들어가야 견주기가 맞다. 보류 있는 반영은 케이스를 돌려서 자리도 하나 쓴다. 앞 반영을 기다리는 반영은 단계 글 「앞 반영을 기다리는 중」을 몇 분마다 다시 올린다 |
| 무엇을 견주나 | 이 요청이 **새로 더한** 케이스마다(바꾼 케이스는 안 본다) ⒜ **같은 tc_id** — 지금 main 의 케이스 파일이나 요구사항 표(「제거함(…)」 포함)에 그 tc_id 가 있다 ⒝ **같은 요구 번호** — 이 요청이 작성을 시작한 뒤 main 에 새로 들어온 케이스가 같은 요구 번호를 덮는다(문단 번호 `P-001` 꼴은 요청마다 1부터라 뺀다) ⒞ **같은 이름** — 이 요청이 작성을 시작한 뒤 main 에 새로 들어온 케이스와 이름이 같다(앞뒤 공백 · 겹친 빈칸 · 영문 대소문자 무시). 예전부터 있던 케이스는 자식이 작성할 때 이미 보고 만들었으므로 ⒝ · ⒞ 로 안 잡는다 |
| 걸리면 | 반영하지 않고 실패로 끝난다 — 「겹치는 케이스 N건 — 케이스마다 고른 뒤 다시 반영한다」. 보류에서 「제거」한 케이스는 겹침으로 안 센다 |
| 고르기 | 케이스마다 **남긴다(KEEP)** · **뺀다(DROP)**. 남기면 tc_id 가 겹칠 때만 새 번호를 받고 안 겹치면 그대로 들어간다. 빼면 이 요청에서 그 케이스 파일과 그 tc_id 를 가진 표 줄이 빠진다(「제거함」으로 남기지 않는다 — main 의 같은 tc_id 줄과 섞인다). 작성 write. 다 고르기 전에는 반영이 409 `CONFLICT_OPEN` |
| 새 번호 | 지금 main 의 케이스 파일 · 요구사항 표(「제거함」 포함)와 이 요청의 번호 가운데 가장 큰 것 + 1 부터 차례로 — 지운 번호를 다시 쓰면 옛 실행 이력이 새 케이스에 붙는다. 999 를 넘으면 실패(파일 이름 규칙이 세 자리다) |
| 요구사항 표 합치기 | main 이 이 요청이 시작한 뒤 이 서비스의 표나 테스트 폴더를 바꿨을 때만 main 을 요청 브랜치에 합친다. 표에서 **양쪽이 같은 자리에 줄을 더하기만 한 곳**은 main 줄 → 이 요청 줄 순으로 잇고 「요구」 차례 번호가 겹치면 이 요청 줄을 main 최대값 뒤로 다시 매긴다. **「덮는 범위」 줄**은 이 요청 것을 남긴다. 그 밖에 양쪽이 같은 곳을 고쳤거나, 새 서비스의 첫 요청 둘이 표를 각자 만들었거나, 케이스 파일이 충돌하면 반영하지 않고 쉬운 문장으로 실패 — 「main 과 같은 곳을 고쳐 합치지 못했다 — <경로>. 다시 작성한다」. 합친 표는 원장 형식 검사를 돌려 깨졌으면 같은 식으로 실패 |
| 케이스를 돌리나 | 번호 바꾸기 · 빼기 · 합치기는 케이스를 안 돌린다(동작이 안 바뀐다). 타입 · K 규칙은 CI 가벼운 길이 본다. 보류 값을 채운 케이스만 지금처럼 3회 |
| PR 본문 | 반영 때 「겹침 처리: MKT-042 → MKT-061 · MKT-050 뺌」 줄을 더한다 — 관문 3 기록이 옛 tc_id 를 가리키지 않게 |
| 배포 순서 | ③-2(화면) 가 들어가기 전에는 author 컨테이너를 이 판으로 다시 켜지 않는다 — 겹침이 생기면 고를 화면이 없다 |

**남는 한계 (명세에 적는다)** — 자리가 다 차면 반영도 기다린다 · 「덮는 범위」 줄은 마지막 반영 것만 남는다 · 빼기 뒤 합친 줄 · 판정 불가 절의 언급과 그 요청의 셈(coverage)은 옛것이다 · 열린 요청끼리는 반영 때에야 드러나고 먼저 반영한 쪽이 기준이다 · main 쪽 케이스를 빼려면 케이스 고치기로 지운다 · GitHub 에서 직접 병합하면 이 검사를 안 거친다

## 구현 세부 — 계약 모양

| 무엇 | 모양 |
|---|---|
| 견주는 기준 | GitHub 이 말하는 지금 main · **자식이 끝낸 커밋**(PR 머리에서 에이전트의 반영 커밋 — 보류 값 · 겹침 처리 · main 합침 — 을 첫 부모로 거슬러 간 곳) · 둘의 갈래점. 서버 저장소에서 git 객체만 읽는다(`한번에하나` 안) — 작업방을 안 연다. 다시 반영할 때 작업방도 같은 커밋에서 다시 짓는다 |
| 결과 한 줄 | `{ tcId, name, file, kinds: ('TCID' \| 'REQUIREMENT' \| 'NAME')[], with: [{ tcId, name, file }], requirements?: string[] }` · 끝내기는 반영 `FAILED` + `result.conflicts`(200건까지) |
| 칸 | 원본(작성 실행) 행의 `conflict_input JSONB` = `{ [tcId]: { action: 'KEEP' \| 'DROP', by, at } }` |
| 통로 | `PUT /api/authoring/requests/:id/conflicts/:tcId` `{ action }` · `DELETE` 같은 경로 · 작성 write · 뿌리 잠금 안 `MERGE_ACTIVE` · `NOT_LATEST`(보류 통로와 같은 판정) · 목록에 없는 tcId 와 틀린 action 은 400 `BAD_CONFLICT`(detail tcId) |
| 상세 | `conflicts: [...결과 한 줄, input]` · `conflictsOpen` — 그 실행을 원본으로 하는 가장 최근 반영이 겹침으로 실패했을 때만 |
| 반영 막기 | 반영 통로가 보류 판정 다음, 뿌리 잠금 안에서 409 `CONFLICT_OPEN` — detail 은 문장 「겹치는 케이스 N건을 아직 고르지 않았다」(화면이 모르는 코드면 detail 만 보인다) |
| 가져가기 | 반영 행을 가져가면 `conflicts: [{ tcId, action }]` — 원본의 결정 **전부**. 거르기는 에이전트가 새 겹침 목록으로 한다(한 번 적용한 결정이 CI 빨강 뒤 다시 반영에서 사라지지 않게) |
| 끝내기 검사 | 반영 `FAILED` 의 `result.conflicts` 모양이 틀리거나 200건을 넘으면 400 `BAD_CONFLICTS` |
| 자리 없는 작업방 | 보류 없는 반영의 작업방(번호 바꾸기 · 빼기 · 합치기)은 트리의 코드를 하나도 돌리지 않는다 — 자식이 쓴 코드가 에이전트 계정으로 돌면 안 된다 |
| 뒤에서 도는 일 | 「서버가 거절했다」를 받으면 지금처럼 모두 멈추고 자식을 거둔다 · 끝낼 때 도는 일을 다 기다린다 |
