## 왜

### ① 첫걸음이 막혀 있다

`apps/admin/Dockerfile` 이 `COPY tsconfig.json playwright.config.ts ./` · `COPY packages` ·
`COPY apps/admin` 셋만 한다. **`scripts/` 가 이미지에 없다.**

공통/6-인프라 §9.2 는 이미 이렇게 못 박았다 — 「이 스크립트를 admin 안 어느 경로에 둘지는 공용 골격을
맡은 갈래가 정한다. **2026-09-18에 저장소 루트의 `scripts/`로 정했고 확장자는 `.ts`다.** 컨테이너가
이미 `tsx`로 돌고 있어(`CMD ["npx","tsx",…]`) 명령도 같은 것으로 돈다」.

그래서 `docs/SETUP.md` 가 안내하는 맨 첫걸음이 실제로는 안 된다. **회원가입 화면이 없으므로
(§8.6) 처음 띄우는 사람은 로그인 자체를 못 한다.**

### ② 문이 번호를 안 본다

도메인/인증 §7 「인증 적용 범위」가 이미 규정했다 — 「**서비스 경계도 여기서 막는다.
배정받지 않은 서비스의 자원을 부르면 403 이다.**」

`gate.ts` 의 `닿는서비스()` 는 둘만 본다.

1. `?service=` 질의 문자열
2. `POST /api/runs` 본문 `items[].tcId` 의 접두사

**나머지 열두 경로가 그냥 지나간다.** 컨트롤러가 라우트를 전수 조사했다.

**A. 경로에 접두사가 박혀 있다 — DB 를 안 읽어도 된다**

| 경로 | 새는 것 |
|---|---|
| `GET /api/cases/:tcId/history` | 남의 케이스 이력 |
| `GET /api/cases/:tcId/param-sets` | 남의 저장된 입력값 |
| `POST /api/cases/:tcId/param-sets` | **쓰기** — 남의 케이스에 입력값을 만든다 |
| `GET /api/catalog/cases/:tcId` | 남의 케이스 상세 |
| `GET /api/catalog/cases/:tcId/source?line=` | **남의 테스트 소스 코드** |

`tcId` 는 `<접두사>-<3자리>` 라(§2) 앞을 자르면 곧 서비스다.
`닿는서비스()` 가 `POST /api/runs` 본문에서 이미 쓰는 바로 그 논리다.

**B. 번호로 부른다 — 그 번호가 어느 서비스인지 DB 를 읽어야 안다**

| 경로 | 새는 것 | 무엇으로 찾나 |
|---|---|---|
| `GET /api/runs/:runId` | 남의 실행 기록 | `test_run.service_id` |
| `GET /api/runs/:runId/items/:historyId` | 남의 항목 상세 (입력값·오류 원문) | 〃 |
| `GET /api/screenshots/:runId/:historyId/:seq.png` | 남의 화면 사진 | 〃 |
| `POST /api/runs/:runId/abort` | **쓰기 — 남의 실행을 멈춘다** | 〃 |
| `POST /api/runs/:runId/evidence` | **쓰기 — 남의 증적 문서를 만든다** | 〃 |
| `GET /api/evidence/:id` | 남의 증적 문서 | `evidence_document.run_id` → `test_run.service_id` |
| `DELETE /api/param-sets/:id` | **쓰기 — 남의 입력값 묶음을 지운다** | `param_set.tc_id` 접두사 |

#### 어디에 두나 — 근거

**문(gate)이 맞다.** §7 의 「서비스 경계도 **여기서** 막는다」의 '여기'가 인증 적용 범위이고
그것을 실행하는 자리가 문이다. 라우트마다 흩어 두면 새 라우트가 늘 때마다 빠뜨린다.

**§3.5 불변식과 어긋나지 않는다.** 그 불변식은 「누구인지 알아내는 부분」(`identify()`)과
「그 이름으로 무슨 일을 하는 부분」을 가르라고 한다. 경계 검사는 **확인이 끝난 뒤에 오는 별개의 일**이다.
SSO 로 갈아 끼울 때 바뀌는 곳은 여전히 `identify()` 하나다.

**새 파일 `apps/admin/src/auth/scope.ts` 하나.** 순수 판정(경로 → 무엇을 찾아야 하나)과
DB 질의를 한 파일에 두되 **순수 함수를 따로 내보낸다.** CI 에 postgres 가 없어
DB 검사는 `describe.skipIf` 로 건너뛰는데, 순수 부분은 CI 에서도 돈다.

#### 없는 번호는 어떻게 하나

**문을 지나보내고 라우트가 404 를 낸다.** 없는 자원은 아무것도 안 샌다.
SPEC §7 이 「404로 감추지 않는다 — 화면이 그 자리를 아예 안 보여주므로 여기까지 닿은 요청은
화면의 버그이거나 직접 찌른 것이고, 둘 다 감추는 편이 더 나쁘다」로 이미 정했다.

#### `service_id` 가 NULL 인 옛 실행은 — **403 으로 막는다**

서비스 통합 이전 행이다 (`CHECK ((service_id IS NULL) = (service_name = ''))`).

1. **이미 목록에 안 뜬다.** `listRuns()` 가 `WHERE r.service_id = (SELECT id FROM service WHERE prefix=$3)`
   라서 어느 서비스로 걸러도 안 나온다. 막아도 **화면에서 보이던 것이 사라지지 않는다**
2. §7 이 막으라 한 것은 「배정받지 않은 서비스의 자원」이고, 서비스가 없는 행은 어느 배정에도 안 든다
3. LEARNINGS 「실패 방향을 열린 쪽으로 뒀다 — 비밀값이 「모르면 보여준다」였다」가 fail-closed 를
   이미 교훈으로 남겼다

실측 — 개발 DB 의 `test_run` 12행 중 **11행이 NULL** 이다. 그래서 이 판단을 여기 적어 둔다.

### ③ 명세 두 절이 서로를 막는다

공통/5-화면공통 §8 — 「**서비스 색은 이 띠에서만 쓴다.** 본문의 색은 언제나 판정이다」
도메인/인증 §8.8 — 「이름 · 색 | **언제든 고친다**」

각각은 맞는데 한 화면에서 만나면 **색을 안 보여주고 색을 고르게 하라**가 된다.
설정 화면은 그 색을 **만드는** 자리라 띠 미리보기가 있어야 흰 글자가 읽히는지 볼 수 있고,
그것이 명암비 경고(DESIGN.md 4.5:1)와 짝이다.

WS-E ③ 의 코드 리뷰와 화면 QA **두 렌즈가 독립적으로 같은 제안을 냈다.**
게이트 0 에서 「승인 — 명세를 먼저 고친다」를 받았다.

**이미 코드는 예외대로 돌고 있다.** `SettingsService.tsx` 가 본문에서 서비스 색을 쓴다 —
**명세만 안 따라온 상태**라 이번에 명세를 맞춘다. 화면 코드는 안 바꾼다.
