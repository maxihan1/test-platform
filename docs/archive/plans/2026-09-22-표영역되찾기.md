# 표 영역 되찾기 — 좌우 · 세로 · 칸 어긋남 · 사이드바 언어 · 모달

등급: 3 · 갈래: WS-E · 2026-09-22

## 도메인 정리

BC 는 Catalog(케이스 목록)와 Execution(실행 기록·실행 결과) 둘이다. **도메인 규칙은 안 건드린다** —
바뀌는 것은 화면이 자리를 어떻게 나누는가뿐이고, 불러오는 API 도 보여주는 값도 그대로다.

| 무엇 | 어느 절 | 이번에 |
|---|---|---|
| 케이스 목록 줄 구성 | `도메인/카탈로그` §8.1 | 칸 **구성은 그대로**, 격자 정의만 합친다 |
| 스캔 결과 자리 | `도메인/카탈로그` §8.1 | 목록 위 → 화면 머리 부제 (**S1**) |
| 화면 머리 부제 정의 | `공통/5-화면공통` 화면 머리 절 | 스캔 결과를 받게 넓힌다 (**S2**) |
| 실행 결과 RUN 머리 | `도메인/실행` §8.3 | 증적 문서 정보를 더한다 (**S3**) |
| 실행 기록 줄 구성 · 집계 띠 | `도메인/실행` §8.7 | 내용 그대로. 배치만 |
| 모달 폭 | `docs/DESIGN.md` (정본, `실행.md:520` 이 가리킨다) | 880 → 1400px (**D1**) |

계약 넷(`packages/kit/src/types.ts` · 러너 HTTP · DB 표·칸 · Admin API)은 **하나도 안 건드린다.**

## 왜

PR #54 병합 뒤 사용자가 준 지적 다섯 건이다. 전부 돌고 있는 앱에서 직접 쟀다 — 창 1680 × 794.

**표가 안 보인다.** 위아래 정보 UI 가 자리를 다 먹는다.

| 화면 | 표에 남은 자리 | 보이는 줄 | 줄 높이 |
|---|---|---|---|
| 테스트케이스 목록 | 940 × **206px** (표머리 38 빼면 168) | **1.5줄** | 111px |
| 실행 기록 | 940 × **323px** | 3.9줄 | 73px |
| 실행 결과 모달 | 880 × 635px 중 **32px** | **0.3줄 — 한 줄도 안 들어간다** | 101px |

목록 화면은 창 794px 중 **564px** 을 머리(113) · 집계띠(120) · 스캔 줄(49) · 필터 두 줄(132) ·
바닥 줄(50) · body 여백(104) 이 먼저 가져간다. 모달은 635px 중 **603px(95%)** 이 정보 UI 다.

**좌우도 남아돈다.** `.wrap` 의 `max-width: 1204px` 때문에 1680px 모니터에서 좌우로 **222px 씩** 버려지고
표가 940px 에 갇힌다.

**칸이 어긋나 있다.** 표머리와 줄이 서로 다른 격자를 쓴다 — 「입력값」 머리가 실제 입력칸보다
**121px** 오른쪽에 있다(「마지막 결과」 116px · 실행 기록 「판정」 166px). 사용자가
「입력란이 좌측에 너무 쏠려있다」 로 지적한 자리이고 **제품 버그**다.

**사이드바 언어 고르개에 CSS 가 한 줄도 없다.** 브라우저가 `select` 를 OS 기본 흰 상자로 그린다.
`docs/LEARNINGS.md:214` 가 2026-09-21 에 이미 적어 둔 사고의 **두 번째**다.

### BLOCKER 1 — 할 일 5 의 제목 20px 이 접근성 계약을 깬다

**어디** `apps/admin/src/web/styles.test.ts:115~121`

```js
it('화면 제목이 큰 글자 기준을 넘는다', () => {
  // DESIGN.md 명암비 — 24px 이상이면 「큰 글자」라 3:1 이 기준이 된다.
  // 제목이 그보다 작으면 4.5 기준으로 다시 재야 한다
```

**무엇** 할 일 5 가 `.head h1` 을 26px → 20px 로 내린다. 이 검사는 24px 미만이면 **무조건 빨갛다.**

아래는 4.5:1 이다. 구현 세션이 이 지시를 읽고 **검사 숫자를 24 → 20 으로 내리면**
그 경계가 조용히 사라지고, 다음에 제목 색을 바꾸는 사람이 틀린 기준으로 잰다.

26→24 로 **2px 뿐**이고 나머지는 `padding: 20px 22px 16px` 다. 접근성 계약을 안 건드리고 목표를 채운다.

### 범위 제안 1 — 줄 높이는 **대체재가 아니라 보완재다** (실측으로 확인)

「표가 안 보인다가 본질이면 줄 높이가 더 큰 레버 아닌가」를 숫자로 재 봤다.

```
                                     목록 화면 (표머리 38px 제외)
지금                    206 − 38 = 168 ÷ 111 = 1.5줄
줄 높이만 줄이면        206 − 38 = 168 ÷  76 = 2.2줄   ← +0.7줄
계획대로 (줄 111 유지)  558 − 38 = 520 ÷ 111 = 4.7줄   ← +3.2줄
둘 다                   558 − 38 = 520 ÷  76 = 6.8줄   ← +5.3줄
```

**계획이 고른 레버가 줄 높이보다 4.5배 크다.** 「줄 높이를 먼저 했어야 하나」는 **아니다** —
범위 밖으로 뺀 판단이 맞았다. 다만 둘은 **곱해지는** 관계라, 이번 PR 이 끝난 뒤
다음 세션이 집으면 4.7 → 6.8줄이 된다. 계획의 「범위 밖」 절이 그 숫자를 적어 둔 것이 옳다.
