### 할 일 4. `tp-merge` 가 로컬 브랜치를 정리한다

Step 4(작업방 탈출 + main 최신화) 뒤에 붙인다. **`-d` 만 쓴다. `-D` 는 절대 쓰지 않는다.**

`-d` 는 병합 안 된 커밋이 있으면 git 이 스스로 거부한다 — **소실이 구조적으로 불가능하다.**
거부당하면 그 브랜치를 보고에 싣고 사람에게 넘긴다.

**순서를 본문에 못 박는다** (검토 주의 1) — `git branch -d` 는 그 브랜치가 어느 작업방에든
체크아웃돼 있으면 **거부한다.** 반드시 **작업방 제거 → 브랜치 삭제** 순서다.

**원격 삭제는 폴백으로 적는다** (검토 주의 2) — 할 일 3 의 `--delete-branch` 가 이미 지운다.
`git push origin --delete` 는 그것이 「main is already used by worktree」로 실패했을 때만 돈다.

- **RED** — 판별식에 「정리 단계에 `git branch -d` 가 있고 `-D` 는 없다」+「작업방 제거가 먼저」를 단언. 실패
- **GREEN** — 정리 단계 신설
- **REFACTOR** — 없음

### BLOCKER 1 — 할 일 5 가 git 이 추적하지 않는 파일을 고친다

`.git/hooks/pre-push` 는 **저장소에 안 들어간다.** 그래서

- **PR 에 안 실린다** — 검토도 검사도 못 받는다
- **판별식이 못 본다** — 산문으로만 남고 조용히 썩는다
- **다른 기계에서 사라진다** — Maxi 님이 새로 클론하면 없다

계획은 이걸 보통 변경처럼 적었다. 「파일: `.git/hooks/pre-push` (추적 밖)」 한 마디로는 부족하다.

**고를 것 둘.**

| | 어떻게 | 값 |
|---|---|---|
| **A** | 훅을 `.claude/hooks/pre-push` 로 옮기고 `core.hooksPath` 를 그쪽으로 | 버전 관리됨 · 판별식이 봄 · **설정 한 번 필요** |
| **B** | 지금 자리에 두고 `docs/HOOKS.md` 에 「이 훅은 기계마다 따로 깐다」를 명시 | 건드릴 게 적음 · **다음 기계에서 또 겪는다** |

**A 를 권한다.** 이미 `.claude/scripts/` 에 훅 본체(`guard.mjs`)가 버전 관리되고 있다 —
pre-push 만 밖에 있는 것이 일관되지 않다.

**다만 이번 PR 범위 밖으로 빼는 것도 답이다.** 할 일 5 의 값어치는 「테스트가 여섯 번 도는
낭비」를 없애는 것뿐이고, 브랜치 정리 자동화와 묶일 이유가 없다.

### 주의 1 — 할 일 4 의 순서가 안 적혔다

`git branch -d <이름>` 은 그 브랜치가 **어느 작업방에든 체크아웃돼 있으면 거부한다.**
반드시 **작업방 제거 → 브랜치 삭제** 순서다. 2026-09-18 에 실제로 이 순서로 했다.

계획이 「Step 4 뒤에 붙인다」고만 적었다. **순서를 본문에 못 박아야 한다** — 안 그러면
다음 세션이 뒤집는다.

### 주의 2 — 할 일 3 과 4 가 원격 삭제를 겹쳐 한다

`gh pr merge --delete-branch` 가 이미 원격을 지운다. 할 일 4 의 `git push origin --delete` 는
**대개 「이미 없음」이 된다.**

지우자는 게 아니다 — `--delete-branch` 는 「main is already used by worktree」로 실패하는
알려진 함정이 있어 **폴백이 필요하다.** 다만 계획이 그걸 폴백이라고 안 적었다.
**「실패했을 때만 돈다」를 명시한다.**

### 주의 3 — 가드를 느슨하게 하는 변경이다

할 일 1 은 **안전 장치를 덜 막게** 만든다. 이런 변경은 틀렸을 때 비싸다.

계획의 RED 이 양방향(통과해야 할 것 · 막아야 할 것)을 다 단언하는 것은 맞다.
**거기에 더해 뮤테이션을 요구한다** — 따옴표 제거 로직을 일부러 깨뜨려
`git branch -D foo` 가 다시 통과하는지 본다. 통과하면 검사가 공허한 것이다.
