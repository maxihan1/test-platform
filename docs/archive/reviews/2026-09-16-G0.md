## WORKFLOW [0]의 4가지 질문에 대한 답

| # | 질문 | 판정 |
|---|------|------|
| 1 | 타입 계약만으로 5갈래가 서로 안 밟는가 | **문제 있음.** `apps/admin` 안의 공용 파일(서버 부트스트랩·DB 풀·package.json)을 아무도 소유하지 않아 A·B·D가 전부 건드려야 했다. 기술 스택도 미정이라 세 갈래가 각자 다른 프레임워크를 고를 수 있었다 → 공용 골격 목록을 WORKSTREAMS에 추가하고 Phase 0가 만들게 함. 스택은 결정 필요 ①. |

| 4 | Phase 0의 얇은 관통이 계약을 검증하는가 | **부분적.** 러너 스텁이 가짜 응답을 주면 컨테이너 안 Playwright 실행(브라우저·읽기 전용 마운트·모듈 해석)이 검증되지 않는다 → 관통에 실제 실행을 포함시킴(§11, Phase 0 프롬프트, G1). |

## 치명 — Phase 0 전에 반드시

### 1. 기술 스택이 어디에도 없다 → 결정 필요 ①
어디:   SPEC 전체, WORKSTREAMS
무엇:   admin 서버 프레임워크, 화면 방식, DB 접근 방식, 마이그레이션 도구, 단위 테스트 러너가 미정
왜 문제: WS-A·B·D가 같은 `apps/admin`에 살면서 각자 고르면 병합 때 셋을 하나로 다시 짜야 한다.
        pre-push의 `npm test`도 러너가 없으면 빈 명령이다.

### 2. 카탈로그가 명세를 읽어내는 방법이 없다 → 결정 필요 ②
어디:   SPEC §3.1, §4
무엇:   `defineCase`의 zod 스키마를 JSON Schema로 바꾸려면 파일을 실제로 import해야 하는데,
        같은 파일의 `test(spec, ...)`가 Playwright 밖에서는 예외를 던진다
왜 문제: WS-A가 시작하자마자 막히고, 해결 방식에 따라 WS-C의 kit 설계가 달라진다.

### 3. `apps/admin`의 공용 파일에 주인이 없었다 → 고침
어디:   WORKSTREAMS 소유 경로 표
무엇:   서버 부트스트랩, 라우트 등록, DB 풀, `package.json`, kit 배럴(`index.ts`)
왜 문제: `ownership` 훅이 A·B·D 전부를 막거나, 훅을 끄면 셋이 같은 파일을 동시에 고친다.
고침:   "Phase 0가 만들고 이후 잠그는 공용 골격" 목록 추가. 라우트는 폴더별 `routes.ts` 규약으로 등록.

### 4. 증적 PDF를 만들 브라우저가 admin에 없다 → 결정 필요 ③
어디:   SPEC §3.3, §9, WS-D 프롬프트
무엇:   WS-D 프롬프트는 `page.pdf()`를 쓰라 하는데 admin 컨테이너는 Playwright 이미지가 아니다
왜 문제: WS-D가 PDF 단계에서 멈추거나, 몰래 러너 계약을 바꾸게 된다.

## 중대

### 5. `ExecuteRequest`에 `runId`가 없었다 → 고침 (계약 필드 추가)
스크린샷 경로 `artifacts/runs/{runId}/{historyId}/{seq}.png`를 러너가 만들 수 없었다. 필드를 추가했다.
러너는 이 값을 경로 외에 쓰지 않는다. 계약 변경이므로 **확인 요망**.

### 6. admin 컨테이너에 `./tests`와 `artifacts` 마운트가 없었다 → 고침
스캔·실패 지점 코드 발췌·스크린샷 서빙·증적 저장 전부 admin이 하는데 볼륨이 러너에만 있었다.
Grafana 프로비저닝 마운트, postgres 데이터 볼륨, 최상위 `volumes:` 선언도 추가.

### 7. `verify` 위치와 실패 규칙이 서로 어긋난다 → 결정 필요 ⑤
§4 예시는 `verify`를 절차(`test.step`) **밖**에서 부르는데, 데이터 모델(`StepResult.assertions`)과
§8.4 화면은 검증 문장이 절차 **안**에 있다. 실패한 뒤 나머지 검증을 계속 볼지도 없다.
공통 전제로 "verify는 절차 안에서만"을 두고, 실패 후 동작만 묻는다.

### 8. Phase 0 프롬프트와 `tests` 훅이 충돌했다 → 고침 (훅)
Phase 0는 데모 테스트를 "순수 Playwright(expect)"로 쓰라 하고, `tests` 훅은 `expect`를 막는다.
Phase 0(`ALLOW_PROTECTED=1`)에서는 `tests` 검사를 건너뛰게 했다.

### 9. WS-E 킥오프 프롬프트가 SPEC과 두 군데 모순 → 고침
목록 열이 "사전조건"이었으나 SPEC §8.1은 "지원 환경". "검증 실패 시 버튼 비활성화"였으나
SPEC §8.2와 DESIGN은 "비활성화하지 말고 이유 표시". 둘 다 SPEC 쪽으로 맞췄다.

### 10. Bash로 고치면 훅이 안 걸렸다 → 고침 (훅)
`sed -i`, `>` 리다이렉트, `tee`, `mv`, `cp`, `rm`으로 보호 파일·남의 폴더를 고쳐도 통과했다.
`bash` 모드에 "경로 앞 쓰기 연산자" 휴리스틱을 넣었다. `python -c` 같은 우회는 못 잡으므로
최종 방어선은 spec-review A1~A3(git log)이다.

### 11. 전역 CLAUDE.md와 프로젝트 규칙이 충돌한다 → 고침
- 전역 §6 "모든 새 파일 첫 줄에 한국어 주석" ↔ SPEC §4 "`tests/**` 주석 금지" + 훅 차단
- 전역 §7 "`checklist.md`·`context-notes.md`" ↔ 프로젝트의 `docs/progress/`·`LEARNINGS.md`
프로젝트 CLAUDE.md에 예외와 대응 관계를 명시했다. ponytail 플러그인과의 우선순위(TDD·주석)도 같이.

## 경미

### 12. `run_item`이 실행 전에 어떤 상태인지 없었다 → 고침
`status`가 NOT NULL인데 PASS/FAIL/NA뿐이라 대기 중 항목을 넣을 값이 없었다.
"생성 시 NA, `finished_at`이 NULL이면 실행 전"으로 정했다. 러너 고장·타임아웃도 NA + `error`.

### 13. `workers: 2`와 "케이스 1건 = 프로세스 1개"가 안 맞았다 → 고침
동시성은 Execution의 2로만 제어하고 Playwright 프로세스는 `workers: 1`. 타임아웃 응답 형태(200 + NA)와
admin 쪽 HTTP 타임아웃(`timeoutMs + 30초`)도 §5.2에 적었다.

### 14. `review` 훅은 "중단"이 아니라 경고였다 → 문서 정정
코드는 exit 1(경고)인데 HOOKS.md는 "중단"이라 적혀 있었다. Stop 훅은 매 응답마다 돌기 때문에
경고가 맞다. 실제 차단은 pre-push. 문서를 코드에 맞췄다.

### 15. 작은 오류들 → 고침
§4 예시에서 `page`를 안 받고 쓰고 있었음. `test.step` 옵션 위치를 Playwright 순서(`title, fn, options`)로.
§10 "8건" → "10건". §5.1 `JsonSchema` 타입 미정의. `.gitignore`에 `.DS_Store` 등.

### 16. 아직 안 정해도 되는 것 → SETUP.md §6 "나중에 정할 것"
`test_run.ABORTED`를 누가 넣는가(WS-B 전), 비밀번호 마스킹 규칙(WS-E 전), 증적 양식(WS-D 전).

## 후속 결정 (같은 날)
- 테스트 코드 기계 검사 `npm run check:tests` + GitHub Actions CI 추가 (SPEC §4 K1~K8).
  사람이 쓴 테스트 코드도 같은 규칙을 지키게 하기 위해서다. 품질(문장이 읽히는가)은 spec-review E4가 본다

  깜빡한 것과 정말 없는 것을 구분하기 위해서다. DB·타입 계약은 변경 없음
- 스캔 시점 — admin 기동 시 자동 스캔 1회 + 화면 `다시 스캔하기` 버튼. `GET /api/catalog/scan`(마지막 결과) 추가
