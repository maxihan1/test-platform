## 기타 — 체크리스트에 없는 것 둘

**① `running` 지도를 `export` 한다.** 테스트가 직접 넣고 비우기 위해서다.
SPEC 위반은 아니고 러너는 파일 일곱 개짜리라 실질 위험도 낮지만, 제품 코드가 아닌 쪽 사정으로 뚫린 구멍이다.
**체크리스트 항목으로 추가할 만하지 않다** — 한 번 나온 일이고, 막으려면 테스트를 위한 별도 API 를 만들어야 해서
치료가 병보다 나쁘다.

**② `docs/spec/도메인/러너.md` 끝에 낡은 `[계약 변경 필요]` 블록이 남아 있다 (범위 밖).**
그 제안(`use.baseURL` · `retries: 0`)은 **이미 `playwright.config.ts` 에 반영됐다.**
승인·반영이 끝난 제안이 아직 「필요」라고 적혀 있어서, 다음 세션이 이 장을 읽으면 아직 승인이 안 난 것으로 읽는다.

**SPEC 변경 제안 한 줄** — 그 블록을 지우거나 「2026-09-18 반영 완료」를 붙인다.
SPEC 은 3등급이라 이번 범위에서 고치지 않았다. 게이트 2 요약에 싣는다.

**③ [WS-B 로 넘김] `finishItem()` 의 UPDATE 에 `finished_at IS NULL` 가드가 없다.**

`apps/admin/src/execution/store.ts:267` 이 러너 응답을 이렇게 기록한다.

```sql
UPDATE run_item SET status = $2, ... , finished_at = now() WHERE history_id = $1
```

**바로 아래 `CLOSE_UNFINISHED` 위의 주석이 「닫는 UPDATE 에는 언제나 `AND finished_at IS NULL` 을 붙인다」고
규정하는데, `finishItem` 은 그 규칙을 안 지킨다.** 가드가 붙은 곳은 `CLOSE_UNFINISHED` 하나뿐이다.

**깨지는 자리.** 사람이 실행을 멈춘다 → `abortRun()` 이 항목을 `NA`·`ABORTED` 로 닫는다 →
그런데 그 항목의 `runOne()` 은 이미 러너를 부르는 중이다 → 자식이 마침 정상 종료했거나 러너에 닿지 못해
`callRunner` 가 `PASS` 를 들고 돌아온다 → `finishItem()` 이 **가드 없이 이미 닫힌 행을 덮어쓴다.**
결과는 `test_run` 은 `ABORTED` 인데 항목은 `PASS` 이고 `finished_at` 이 다시 찍힌다.

**이 항목이 이번 작업에 중요한 이유.** 러너의 `abort()` 가 처음에 이 가드를 근거로 경합을 안 막았다.
근거가 사실이 아니었으므로 **주석을 사실에 맞게 고쳤다.** 러너 쪽에서 더 할 수 있는 일은 없다 —
덮어쓰기를 막는 자리는 admin 의 SQL 이다.

**고쳤다 (게이트 2 에서 사용자가 「WS-B 2건도 지금 고친다」를 골랐다).**
`finishItem` 의 UPDATE 에 `AND finished_at IS NULL` 을 붙이고, 0행이면 절차 기록도 넣지 않고 `ROLLBACK` 한다 —
묶음은 `ABORTED` 인데 절차만 `PASS` 로 쌓이면 증적이 어긋난다. 재현 테스트를 먼저 썼고 **실제로 `PASS` 가 나왔다.**

**④ [WS-B 로 넘김] `queries.test.ts` 가 간헐적으로 깨진다.**

전체를 3회 돌려 **2회차에서 3건이 깨졌다** (1·3회차는 통과). 전부
`apps/admin/src/execution/queries.test.ts` 다. `lastByCase()` 가 `XBQ-001` 로 2건을 봤는데 1건을 기대했다.

**이번 변경과 무관하다.** 바뀐 파일이 `apps/runner/**` 와 문서뿐이고, 러너만 3회 연속 돌리면 전부 통과한다.

**원인을 끝까지 짚었다.** 정리 구문이 아니라 **제품 코드였다.**
`recoverRunning()` (`store.ts:340`) 이 `SELECT run_id FROM test_run WHERE status = 'RUNNING'` 으로
**DB 전체**를 훑어 미완 항목을 닫는다. `store.test.ts:299` 가 그 함수를 부르면
병렬로 돌던 `queries.test.ts` 의 미완 mobile 항목까지 닫혀, `lastByCase()` 가 2건을 보고
`listRuns` 의 `counts.running: 1` 도 깨진다. 실패 3건이 전부 이 하나로 설명된다.

**고쳤다.** 3회차에서 쓴 해법(함수에 범위를 받게 한다)이 여기서는 안 통한다 —
부팅 직후 남은 것을 전부 닫는 것이 `recoverRunning()` 의 존재 이유고 프로덕션에서는 그게 옳다.
`vitest.config.ts` 에 **`fileParallelism: false`** 를 넣어 구조로 끊었다.
313건 2.6초 → 314건 15.3초. **연속 3회 전부 종료 코드 0.**
