## 확정된 결정 5건

### D1. 정기 실행은 바깥 문을 열지 않는다

**문제** — §7(901행)은 "login 빼고 모든 `/api/**`는 401"이라 하고, §8.6(1197행)은 "인증 없이 부를 수 있는 것은 `POST /api/runs` 하나"라고 한다. **같은 계약을 두 절이 정반대로 말한다.**
게다가 §3.5(309행)는 러너 포트를 닫는 이유를 "로그인을 거치지 않고 실행을 시킬 수 있는 뒷길"이라 적어 놓고, §8.6은 같은 성질의 구멍을 admin에 낸다. §8.6의 방어 논리("사칭할 수 없다")는 **귀속**을 말할 뿐 **접근**을 막지 못한다.

**결정** — cron이 HTTP를 쓰지 않는다. `docker compose exec admin node scripts/run-scheduled.js` 로 컨테이너 **안에서** 실행을 만든다. §9.2의 계정 생성(`add-user.js`)과 같은 모양이라 새 개념이 0개다.

**할 일** — §7:901을 정본으로 두고 **§8.6의 「인증 없이 들어오는 실행」 절을 삭제**한다. §9.2 정기 실행 절을 명령 방식으로 고친다.

### D2. 대시보드 계정은 기본을 잠그고 필요한 것만 연다

**문제** — §6(832행)이 "기존 `GRANT SELECT ON ALL TABLES`는 그때 있던 표에만 붙었으므로 `app_user`는 자동으로 포함되지 않는다"고 적었다. **사실이 아니다.**

`db/init/01-grafana-readonly.sql`
```sql
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO grafana_ro;
```
`docker-compose.yml:8`이 `POSTGRES_USER: platform`이고 마이그레이션도 같은 계정으로 돈다. 즉 **이 계정이 앞으로 만드는 모든 표에 자동으로 SELECT가 붙는다.** 비밀번호 해시 표도 포함이다.
SPEC이 적은 `REVOKE ALL ON app_user`가 그 표 하나는 막아 주지만, **틀린 설명이 계약 문서에 남으면 다음 표는 아무도 안 막는다.**

**결정** — 기본 허용을 끈다. 마이그레이션에 `ALTER DEFAULT PRIVILEGES ... REVOKE SELECT ...`를 넣어 **기존 DB에도** 적용되게 하고, Grafana가 실제로 읽는 표에만 명시적으로 `GRANT` 한다.

### D3. 반복 실행은 만들어질 건수로 막는다

**문제** — §7.1(920행)이 "`repeat` 상한을 두지 않는다. 동시 실행 2 제한이 이미 있어 몇 번을 넣든 서버가 죽지 않는다"고 한다. 동시 실행 2는 **돌아가는 프로세스 수**를 막지 **INSERT 건수**를 막지 않는다. 케이스 10 × 디바이스 2 × `repeat` 10만 = `run_item` 200만 행이 요청 한 번에 들어간다.

**결정** — §8.2가 이미 계산하는 "실행 항목이 몇 건 생깁니다" 숫자에 상한을 건다. `repeat`가 아니라 실제 생성 건수를 막아 케이스 수가 늘어도 같이 보호된다.

**주의** — §1.1의 **L12(한 번에 요청할 수 있는 실행 건수 상한)** 가 이것을 "나중에"로 미뤄 둔 항목이다. 이 결정은 L12를 앞당기는 것이므로 **L12를 표에서 빼고 본문 규칙으로 올린다.**

### D4. 증적 항목 이름이 비면 바로 실패시킨다

**문제** — §6의 마이그레이션 초안이 `env`·`base_url`·`instance_name`·`tests_repo`·`file_path`는 `DROP DEFAULT` 하면서 **`param_schema`·`expected_schema`는 `DEFAULT '{}'`를 남긴다.** 이 두 칸이 증적 문서 라벨의 유일한 원천인데, INSERT가 빠뜨리면 **조용히** 비고 문서의 입력 칸이 전부 `기록 없음`이 된다. 박제 설계 전체가 막으려던 실패가 아무 소리 없이 일어난다.

**결정** — `file_path`와 똑같이 `ADD COLUMN ... DEFAULT` 후 `DROP DEFAULT`. 이미 쌓인 행은 `'{}'`로 남고 화면은 `기록 없음`으로 적는다.

**같이 볼 것** — `timeout_ms`도 같은 성질이다. NULL이 "마이그레이션 이전 행"을 뜻한다고 §6(708행)이 적었는데, INSERT 누락도 NULL이라 버그와 역사가 구분되지 않는다.

### D5. 서비스를 한 벌로 합치고, 충돌은 접두사 배정으로 막는다 ★ 가장 큰 결정

**배경** — §9.2는 "서비스마다 인스턴스를 따로 띄운다. DB도 따로다"를 골랐다. 그러면 한 회사가 서비스 둘을 쓸 때 **사람마다 계정이 둘**이 된다. 사용자가 이것을 받아들이지 않았다.

**결정** — 프로그램과 저장소를 **한 벌로 합친다.** 로그인 한 번으로 모든 서비스를 본다.

**충돌 해법 (사용자 제안)** — 서비스를 만들 때 **케이스 번호 접두사를 배정한다** (`PAY-`, `MEM-`). 이 한 가지가 가장 비싼 세 문제를 없앤다.

| 합칠 때 생길 문제 | 접두사 배정으로 |
|---|---|
| 케이스 번호 충돌 | 배정 단계에서 막으니 애초에 안 부딪힌다 |
| 모든 표에 "어느 서비스" 칸 추가 | **필요 없다.** 번호가 이미 서비스를 말한다 |
| 권한 표 신설 | **필요 없다.** "`PAY-`로 시작하는 것만 본다" 한 줄 |

**접두사는 자유 형식으로 한다** (사용자 결정). 플랫폼은 접두사의 **뜻을 모른다.** 뜻은 조직이 정한다.

근거를 코드로 확인했다. 접두사를 검사하는 곳은 `apps/admin/src/catalog/rules.ts:152`의 `/^[A-Z]{2,6}-\d{3}$/` **한 줄뿐이고, 접두사를 잘라 쓰는 코드는 저장소·러너·화면 어디에도 없다.** 문서만 "기능 영역을 뜻한다"고 주장하고 있었다.

**할 일** — 검사 규칙 한 줄을 자유 형식으로. §2의 "도메인은 기능 영역을 뜻한다"를 "뜻은 조직이 정한다. 플랫폼은 모양과 중복만 본다"로. §8.1 검색 조건의 "기능 영역"을 "접두사"로.

**남은 미결** — **테스트 코드 저장소.** 서비스별 테스트가 서로 다른 git 저장소에 있으면 플랫폼이 여러 폴더를 읽는 코드가 실제로 필요하다. "모든 서비스의 테스트를 한 저장소에 모은다"를 조직 규칙으로 정하면 지금 코드 그대로 간다. **조직 상황이라 판단 보류.**
