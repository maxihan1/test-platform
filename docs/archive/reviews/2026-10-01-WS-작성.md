### B11 · C4 [재발] — 서버 검사를 건너뛴 고침이 에이전트까지 간다
어디:   `apps/admin/src/authoring/routes.ts` (POST `/authoring/requests` — AUTHOR 의 `준비세우기({… 값})`, 원본이 AUTHOR 인 RERUN 의 `값`) ·
        `apps/admin/src/authoring/agentRoutes.ts` 집기(`행의고칠것(집은것.params)` — kind 를 안 본다) ·
        `scripts/authoring-edit.ts` `고치기실행인가`(`kind === 'EDIT' || edits !== undefined`) · 같은 파일 `편집들` 주석 「칸 규칙(스키마 · 비밀번호)은 서버가 이미 봤다」
무엇:   작성 write 권한이면 `/api/authoring/requests` 본문에 `params: { edits: [...] }` 를 실어 AUTHOR 나 RERUN 을 세울 수 있다.
        그 행은 집기 응답에 `edits` 를 싣고 에이전트는 그것을 고치기 실행으로 받아 모양만 보고 코드를 고쳐 push 한다.
        `/api/authoring/edits` 의 검사(비밀값 칸 · 테스트 계정 비밀번호 · `expected_schema` · 활성 · `EDIT_OPEN`)를 하나도 안 거친다.
        에이전트 쪽에는 push 전 비밀번호 검사가 없다(고치기 실행은 대상 계정을 안 받는다). 주석이 믿는 서버 검사는 다른 통로로 돌아갈 수 있다
왜 문제: 명세가 막으려던 것이 그대로 일어난다. 비밀번호 원문이 케이스 코드에 박혀 GitHub 브랜치로 나간다(§3.6 「★ 케이스 고치기」 기대값 줄).
        사람이 반영을 누르기 전에 이미 저장소 이력에 남는다. 같은 행은 DONE 이어도 폐기되고, 반영되면 그 tcId 저장값이 지워진다
고칠 곳: WS-작성 — 작업 트리에 미커밋 수정이 있다(`routes.ts` 가 `params.edits` 를 400 으로 막음 · 집기가 kind 를 봄). 커밋하고 명세 §7 POST requests 에
        「params.edits → 400 BAD_EDIT」 줄을, §3.6 「고치기 실행」 정의를 「EDIT 행과 원본이 EDIT 인 RERUN」으로 같이 고친다(지금 정의 「params.edits 를 가진 행」이 이 구멍의 뿌리다)
재발:   LEARNINGS 2026-09-22 「경로를 갈라 권한을 지켰다고 여겼는데, 문은 경로를 보고 라우트는 본문을 받는다」와 같은 꼴이다.
        제안 — spec-review C 절에 「새 통로가 검사하는 칸을 옛 통로가 본문으로 받는가」 한 줄을 더한다

고칠 곳: 명세(작성 §3.6 「실행 기록」 · §7 목록) — ②-2 킥오프에 항목으로
