## 중대

### G6 — 설정 화면에서 서비스를 고치면 맨 위 띠가 새로고침 전까지 옛 값이다 `[재발]`

어디:   `apps/admin/src/web/Settings.tsx` — `Settings()` 가 `onSelf` 를 `UserSection` 에만 넘긴다.
        `ServiceSection` 은 `onDone={services.reload}` 하나뿐이다

무엇:   맨 위 띠는 `GET /api/auth/me` 의 `services` 로 그린다. 그 응답은 서비스의
        **이름·색·대상 서버·활성 여부**를 전부 싣는다 (`auth/store.ts:67` 이 `s.is_active` 로 거른다).
        설정 화면에서 서비스를 고치면 설정 목록만 다시 읽고 `/auth/me` 는 안 읽는다.
        계정 쪽은 같은 문제를 `onSelf` 로 이미 막아 뒀는데 서비스 쪽에만 안 걸렸다

왜 문제: 세 가지가 조용히 어긋난다.
        ① **비활성으로 내린 서비스가 띠에 그대로 남는다.** SPEC §8.8 은 「비활성 서비스는
        띠의 목록에서 사라진다」고 적었다. 남아 있으면 운영자가 방금 내린 서비스를 골라
        그 안에서 계속 일한다 — 내린 줄 알고 내렸는데 안 내려간 것이다
        ② **이름·색을 고쳐도 띠가 안 바뀐다.** 색을 고치는 **유일한 이유**가 띠를 고치는 것인데
        (SPEC §8 「띠의 바탕색은 그 서비스의 색」), 고친 사람이 안 먹혔다고 판단하고 또 고친다
        ③ 대상 서버를 더해도 실행 설정의 드롭다운이 새로고침 전까지 비어 있다 (§8.2)

왜 재발: 이번 diff 가 고친 버그 둘 중 하나가 **정확히 같은 것**이다 — 「자기 자신을 배정해도
        띠가 안 바뀐다」. 계정 경로에만 `onSelf` 를 걸고 서비스 경로는 안 봤다.
        G6 이 2026-09-19 에 생긴 이유(「확인 방법이 그 경로를 안 밟는다」)와 같은 자리다.
        **브라우저로 눌러 본 경로가 계정 쪽이었고 서비스 쪽은 안 눌러 봤다.**

고칠 곳: WS-E. `ServiceSection` 의 `onDone` 도 `/auth/me` 를 다시 읽게 한다

재발을 멈추려면: 이 화면의 `onDone` 을 **경로마다 다르게 두지 않는다.**
        설정 화면은 `/auth/me` 의 **재료를 고치는 자리**이므로 여기서 무엇을 저장하든
        띠를 다시 읽는 것이 기본값이어야 한다. 「자기 자신일 때만」이 예외를 만들었다.

> **작업 트리에 커밋 안 된 수정이 있다.** `git status` 가 `M apps/admin/src/web/Settings.tsx`
> 를 낸다 — `onSelf` 를 `onMeChanged` 로 고쳐 이 지적을 막으려는 것으로 보이는데
> **49행이 아직 `onSelf` 를 가리켜 지금 상태로는 타입 검사가 깨진다.**
> 이 검사는 `origin/main...HEAD`(커밋된 것)만 봤다. 고친 뒤 다시 재야 한다.

## 경미

### 기타-1 — 서비스 색과 판정 색을 본문에서 쓴다

어디:   `apps/admin/src/web/Settings.tsx` — `.set-swatch`(목록 행의 4px 색띠, 88행) ·
        `.set-preview`(띠 미리보기, 208행) · `input[type=color]`(201행)
        `apps/admin/src/web/styles.css:1155-1157` — `.set-pw` 가 `--na` · `--na-bg`

무엇:   SPEC 공통/5-화면공통 §8 은 「**서비스 색은 이 띠에서만 쓴다**」,
        DESIGN.md 원칙 1 은 「색은 판정만 갖는다. **예외는 맨 위 띠 한 줄뿐이다**」다.
        설정 화면 본문이 서비스 색을 세 자리에서 쓰고, 임시 비밀번호 칸이
        **미실행 판정 색**(`--na`)을 판정과 무관한 안내 상자에 쓴다.
        `--na` 가 판정 밖에 쓰인 것은 이번이 처음이다 (`styles.css:829` 의 기존 용례는
        「돌지 못한 사유」라 판정 안이다)

왜 문제: 사람이 본문에서 색을 봤을 때 그것이 판정인지 아닌지를 매번 판단해야 한다.
        지금은 설정 화면에 판정이 하나도 없어 헷갈릴 일이 없지만,
        **예외가 한 번 뚫리면 다음 화면에서 같은 근거로 또 뚫린다** — SPEC 이 이 규칙에
        「본문의 색은 언제나 판정이다」라는 절대형을 쓴 이유가 그것이다

고칠 곳: WS-E (색 쓰는 자리) 또는 SPEC (예외를 명시)

**SPEC 변경 제안 한 줄** — §8.8 이 「이름·색을 언제든 고친다」고 시켜 놓고 §8 이 띠 밖 사용을
전부 막아 **둘이 부딪힌다.** 색을 안 보여주고 색을 고르게 할 수는 없다.
§8 에 「설정 화면(§8.8)의 색 칸과 미리보기는 예외」 한 줄을 더하는 것이 맞다.
`.set-pw` 의 판정 색은 예외로 둘 이유가 없다 — `--rule` 과 굵은 글자로 충분하다.

## 기타 (체크리스트 밖)

### `Dockerfile` 에 `COPY scripts` 가 없다 — 보고만 하고 넘긴 판단은 **맞다**

재현했다. `apps/admin/Dockerfile` 이 `COPY packages` · `COPY apps/admin` 만 하고
`scripts` 를 안 싣는다. `docker-compose.yml` 의 admin 볼륨도 `./tests:ro` 와 `artifacts` 둘뿐이라
**이미지에도 마운트에도 `scripts/` 가 없다.** `docs/SETUP.md:216` 이 안내하는 두 명령
(`add-user.ts` · `add-service.ts`)이 둘 다 `ERR_MODULE_NOT_FOUND` 로 죽는다.

Dockerfile 은 3등급(`COMPOSE`) 표면이고, 이번 일에 **필요한** 것이 아니라 **잘못돼 보이는** 것이다.
CLAUDE.md §1.1 이 그 둘을 갈라 「앞엣것은 여전히 보고만 한다」고 적었다. 판단대로다.

**다만 딸린 결과가 하나 있다.** 이번에 고친 `scripts/add-service.ts` 의 기본색
(`#5B7FDE` → `#3A5FCD`)도 **SETUP.md 가 안내하는 경로로는 닿지 않는다.**
그 명령이 안 돌기 때문이다. 고친 값이 실제로 쓰이려면 Dockerfile 이 먼저 고쳐져야 한다.
넘기는 항목에 이 한 줄을 붙여 두는 편이 낫다 — 받는 쪽이 「급하지 않다」고 판단할 수 있다.

### SPEC §7 이 설정 API 오류 코드를 다 안 적는다

서버 `settings/routes.ts` 가 `USERNAME_TAKEN`(409) · `INVALID_REQUEST`(400) · `NOT_FOUND`(404) 를
내는데 SPEC §7 의 설정 API 블록에는 `PREFIX_TAKEN` · `PREFIX_SHAPE` · `PREFIX_IMMUTABLE` · `LAST_ADMIN`
넷만 적혀 있다. 이번 화면의 `오류말` 표가 일곱 개를 전부 사람 말로 옮기고 있다 —
**화면이 SPEC 보다 많이 안다.** `origin/main` 의 기존 간극이고 이번 diff 탓이 아니다.
제안 한 줄: §7 설정 API 블록에 세 코드를 더한다.

### 접두사 정규식이 두 곳에 있다 — 지금은 맞지만 기계가 안 본다

`apps/admin/src/settings/routes.ts:20` 과 `apps/admin/src/web/settingsView.ts` 가
`/^[A-Z][A-Z0-9]{0,11}$/` 를 각각 들고 있다. SPEC 공통/1-제품과-구조 §2:184 와 글자까지 같다.
두 파일 다 주석으로 서로와 SPEC §2 를 가리키고, 화면이 서버 모듈을 import 못 하는 이유
(fastify 가 번들에 끌려온다)도 적혀 있다. **지금은 어긋난 곳이 없다.**
다만 §2 를 고칠 때 둘 다 움직여야 하는데 `npm run check:spec` 은 절 번호·링크·분량만 본다.
승격 후보 한 줄 — `check:spec` 이 SPEC §2 의 정규식 문자열과 두 코드의 리터럴을 대조하게 한다.

| 계정 폼만 버튼을 죽이고 이유를 안 적는다 (SPEC §8.2 위반) | 명세 · 코드 · 화면 |
| 서비스 색을 띠 밖에서 쓴다 (DESIGN.md 원칙 1) | 명세 · 화면 — **아래 「판단이 필요한 것」** |
| 색 코드에 아무 글자나 넣어도 저장된다 | 코드 · 화면 |
| 대상 서버 줄의 `key` 가 순서다 | 코드 · 화면 |

## 고친 것 — 사람이 막히던 것

- **계정 목록이 실패하면 영영 「불러오는 중입니다」** — `users.error` 를 보는 자리가 없었다
- **빈 대상 서버 줄이 그대로 서버로 갔다** — 400 이 오는데 어느 칸인지 말해 주는 것이 없었다
- **안내가 엉뚱한 칸을 가리켰다** — 접두사만 비었는데 「이름과 테스트 폴더」라고 했다
- **계정 폼만 버튼을 죽였다** — 같은 화면 안에서 두 폼이 반대로 굴었다

## 고친 것 — 되돌릴 수 없는 일

- **임시 비밀번호가 화면 밖에 떴다.** 계정이 열 명만 돼도 안 보인다. **그 사이 옛 비밀번호는
  이미 죽어 있어** 본인은 영문도 모르고 로그인이 막힌다 → 화면 안으로 끌어오고 포커스·`aria-live`
- **`비밀번호 다시 만들기` 가 저장 옆이고 확인이 없었다** → 왼쪽 끝 + 두 걸음
- **보조 버튼 셋이 연타를 안 막았다** → 셋 다 `보내는중` 을 세운다
- **웹훅 「다시 넣기」에서 되돌아갈 길이 없었다** → 「그대로 두기」

## 고친 것 — 화면이 디자인을 안 입고 있었다

- `input[type='text']` 선택자에 **`input:not([type])` 을 더했다** — 다음 사람이 또 빠뜨려도 먹는다
- **`format('woff2-variations')` 는 표준값이 아니다** — 못 알아보는 브라우저가 `src` 를 건너뛰어
  **글꼴이 아예 안 실린다.** 이 변경이 막으려던 바로 그 상태다
- 임시 비밀번호 상자가 미실행 판정색(`--na`)을 썼다 · 「비활성」 배지가 `.chip` 이라 손가락 커서

## 고친 것 — 그 밖에

`INVALID_REQUEST` 의 `detail`(어느 칸인지)을 버리던 것 · 세 곳의 오류 말투가 갈리던 것 ·
`api.me()` 재요청에 `.catch` 가 없던 것 · 기본 서비스색이 두 곳에 손으로 적혀 있던 것 ·
배정 없는 운영자에게 다음 할 일을 안 알려 주던 것.

**파일을 나눴다 (CLAUDE.md §3 — 300줄).** 606줄이던 `Settings.tsx` 가 다섯으로 갈렸다 —
틀(62) · 서비스(302) · 계정(287) · 대상 서버(69) · 임시 비밀번호(39).

## 판단이 필요한 것 — SPEC 두 절이 부딪힌다

**§8.8 은 「이름·색을 언제든 고친다」고 시키는데 §8 은 「서비스 색은 맨 위 띠에서만 쓴다」고 막는다.**
DESIGN.md 원칙 1 도 「색은 판정만 갖는다. 예외는 맨 위 띠 한 줄뿐」이다.

색을 안 보여주고 색을 고르게 할 수는 없다. 지금 설정 화면은 세 자리에서 서비스 색을 쓴다 —
목록 줄의 4px 띠 · 색 고르개 · 띠 미리보기. **미리보기는 흰 글자가 실제로 읽히는지 보는 자리라
명암비 경고와 짝이다.**

두 렌즈가 같은 제안을 냈다 — **§8 에 「설정 화면(§8.8)의 색 칸과 미리보기는 예외」 한 줄을 더한다.**
SPEC 변경이라 게이트 0 이 필요하고 등급이 3으로 올라간다. 게이트 2 에서 사용자가 정한다.
