## 치명

### H2 — §13 「명세」 행이 고쳐야 할 SPEC 장을 다 안 든다

어디:   `docs/plans/2026-09-21-E2E-시나리오-설계.md` §13 「명세」 행

무엇:   그 행이 드는 것은 **증적의 `httpTrace` 금지**와 **화면 자리 목록·영어 이름** 둘뿐이다.
        그런데 이 문서가 확정한 설계는 **계약 장 넷**을 더 고쳐야 한다.

| 빠진 장 | 무엇이 부딪치나 | 어디에 적혀 있나 |
|---|---|---|
| `도메인/러너.md` | **「책임: 케이스 1건을 실행한다」**(11줄)와 **「케이스 1건 = Playwright 프로세스 1개」**(63줄). **결정 3 이 이것을 정면으로 바꾼다** — 여러 케이스를 한 프로세스에서 몬다 | 색인 라우터 표 「러너가 주고받는 모양을 바꾼다 → 도메인/러너 §5.2 — **계약이다**」 |
| `공통/4-데이터모델.md` §6 | 시나리오 정의·결과 표 신설, `test_run` 에 구분 칸 (§13 DB 행 셋) | 색인 라우터 표 「표에 칸을 더한다 → **계약이다. CLAUDE.md §1.2 절차를 먼저 밟는다**」 |
| `도메인/실행.md` §7 | 시나리오 CRUD·실행·시험 실행 API 경로 (§13 서버 행) | Admin API 경로는 §7 이 정본 (A5) |
| `공통/3-공유계약.md` §5.1 | 케이스 본체 꺼내기·절차 지목 (§13 kit 행) | `packages/kit/src/types.ts` 는 §5.1 이 정본 (A1) |

왜 문제: **§13 이 「착수할 때 이 표가 계획서의 입력」이고 「명세부터 고친다. 나머지가 전부
        거기에 달려 있다」라고 못 박았다.** 목록이 불완전하면 그 문장이 거짓말이 된다.

        착수 세션이 §13 명세 행대로 **화면·증적 명세만 고치고 구현에 들어가면**,
        러너·DB·API·kit 을 SPEC 에 없는 모양으로 만들게 된다. 그것은 **`spec-review`
        A1·A4·A5·A6 이 병합 직전에 잡는 치명**이고, 그때는 이미 다 만든 뒤다.

        **CLAUDE.md §1.3 이 「공용 파일은 SPEC 에 적힌 대로만 바꾼다」이고 잠금 장치는
        2026-09-17 에 걷혔다.** 막는 것이 사후 검사뿐이라, 계획 입력이 빠뜨리면 끝까지 간다.

고칠 곳: 이 PR (§13 명세 행에 네 장을 더한다)

## 중대

### H3 — 색인(`docs/SPEC.md`)의 라우터 표에 줄을 더하는 일이 §13 에 없다

어디:   `docs/plans/2026-09-21-E2E-시나리오-설계.md` §13

무엇:   「E2E 시나리오」는 **새 개념**이다. 색인의 **「기능을 더하거나 고칠 때」 라우터 표**에
        그 줄이 있어야 다음 사람이 어느 장을 열지 찾는다. §13 어디에도 그 항목이 없다.

왜 문제: **CLAUDE.md §2.7 ③ 이 「이 자리를 가장 잘 빠뜨린다」라고 콕 집어 적어 둔 자리다.**
        라우터에 없으면 다음 세션이 「시나리오를 고치려면 어디를 보나」에서 길을 잃고,
        설계 문서(`docs/plans/`)를 직접 찾아야 한다 — 그 문서는 **계획의 입력이지 명세가 아니다.**

고칠 곳: 이 PR (§13 명세 행에 색인 라우터 줄을 더한다)

## 기타

### 사용자가 물은 것 둘에 대한 답

**① 「SPEC 을 한 글자도 안 고쳤는데 지금 §1.2 절차를 밟아야 하나」 — 안 밟아도 된다.**
CLAUDE.md §1.2 는 「바꿔야 한다고 판단되면 즉시 멈추고 보고」인데, 이 PR 은 계약을 **지금
바꾸지 않는다.** 착수 PR 에서 밟는 것이 맞고, 설계 문서가 §8 「나」·「바」와 §10 에
게이트 0 을 명시했다. **다만 위 치명이 그 목록을 불완전하게 만들었다** — 밟을 절차가
어느 장에 붙는지를 착수 세션이 알 수 없다.

**② 「H5 를 넓힌 것이 타당한가」 — 타당하다.**
CLAUDE.md §2.5 표가 `spec-review` 체크리스트를 **직접 고치는 범위**로 두고,
같은 유형이 이 PR 안에서만 세 번 났다(부품 개수 · 「걸리는 것 셋」 · 「결정 열하나」).
**다만 이 검사가 자기를 고친 PR 을 검사하는 순환**이라, 그 판단은 병합 전 다른 세션이 다시 본다.

### 체크리스트에 더할 만한 것 하나

**「설계를 확정하는 문서가 계약 장을 건드릴 때, 그 장 목록이 문서 안에 다 있는가」**
— 이번 치명이 그 자리다. H 절은 SPEC 안의 정합만 보고, **SPEC 밖 문서가 SPEC 변경을
예고하는 경우**를 안 본다. 색인 라우터 표가 「이럴 땐 어느 장」을 이미 들고 있으므로
**그 표와 대조**하면 기계에 가깝게 볼 수 있다. H6 후보로 제안한다 — 이번 범위 밖이라 적기만 한다.
