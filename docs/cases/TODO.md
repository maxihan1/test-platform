## 분해 근거

**R1 — 한 문단을 셋으로 끊었다.** §2 첫 문단에 「~되며」와 마침표로 요구가 셋 붙어 있었다
(등록 · 남은 개수 표시 · 빈 목록 숨김).

**워딩 통일** — 기획서의 「등록된다」·「반영된다」를 **「목록에 ~이 보인다」** 하나로 모았다.
화면에서 눈으로 확인할 수 있는 문장이어야 `verify()` 가 실제 값을 볼 수 있다.

**R2 에만 경계 축이 붙었다** (R3). 기획서가 「할 일이 하나도 없을 때는」이라고
**0건을 명시**했기 때문이다. 나머지 요구사항에는 범위·개수·상한이 안 적혀 있어 경계를 만들지 않았다.

**예외 축은 하나도 안 만들었다** (R4). 기획서에 실패·오류 화면이 적혀 있지 않다.

**판정 불가 셋은 케이스로 만들지 않는다.** 여기서 AI 가 「그럴듯하게」 해석하면
돌릴 때마다 다른 케이스가 나온다. 기획자에게 되물어야 할 자리다.

## 용어 사전

화면을 실제로 열어 확정했다 (`ariaSnapshot` 탐침, 2026-09-21).
**케이스 전부가 이 표만 본다.** 화면이 바뀌면 고칠 자리가 한 곳이다.

| 도메인 용어 | 화면에서 무엇 | locator |
|---|---|---|
| 화면 제목 | 맨 위 제목 | `getByRole('heading', { name: 'todos' })` |
| 할 일 입력칸 | 제목 아래 텍스트 상자 | `getByPlaceholder('What needs to be done?')` |
| 할 일 항목 | 목록의 한 줄 | `getByTestId('todo-item')` |
| 할 일 글자 | 그 줄에 보이는 글자 | `getByTestId('todo-title')` |
| 남은 개수 | 목록 아래 문구 | `getByTestId('todo-count')` |
| 완료 표시 | 할 일 왼쪽 동그란 칸 | `getByRole('checkbox', { name: 'Toggle Todo' })` |

## R4 가 보류로 남은 이유

기획서 §3 은 마감일을 요구하는데 **화면에 그 요소가 없다.** 탐침 결과다.

```
마감일 낱말 적중: []          ← 본문에 마감·due·date·deadline 이 없다
date 입력칸: 0
input type 전부: [text, checkbox, checkbox, text]
```

여기서 그럴듯한 selector 를 지어내면 케이스가 5건이 되고 숫자는 좋아 보이지만,
그중 하나는 **아무것도 확인하지 않는 초록불**이 된다. **기대값은 기획서에서만 온다** (R14).

**기획자에게 물어야 할 것** — 마감일이 아직 안 만들어진 것인가, 이번 범위가 아닌가.
