## 분해 근거

### 1차 (v0.3)

**요구 1~3 은 한 문단을 셋으로 끊은 것이다** (규칙 R1). §2 첫 문단에 「~되며」와 마침표로
요구가 셋 붙어 있었다 — 등록 · 남은 개수 표시 · 빈 목록 숨김.

**워딩 통일** — 기획서의 「등록된다」·「반영된다」를 **「목록에 ~이 보인다」** 하나로 모았다.
화면에서 눈으로 확인할 수 있는 문장이어야 `verify()` 가 실제 값을 볼 수 있다.

**요구 2 에만 경계 축이 붙었다** (규칙 R3). 기획서가 「할 일이 하나도 없을 때는」이라고
**0건을 명시**했기 때문이다. 나머지에는 범위·개수·상한이 안 적혀 있어 경계를 만들지 않았다.

**요구 1 과 2 는 전제·조작이 거의 같지만 합치지 않았다.** 기획서가 「등록」과 「개수 표시」를
별개로 적었고, 합치면 **회귀에서 어느 요구가 깨졌는지 못 가린다.**

**판정 불가 셋은 케이스로 만들지 않는다.** 여기서 AI 가 「그럴듯하게」 해석하면 돌릴 때마다
다른 케이스가 나온다. 기획자에게 되물어야 할 자리다.

### 2차 (v0.4) — 규칙 R9 판정

개정분을 기존 표에 합쳤다. 줄마다 **더하기 · 바꾸기 · 없애기** 중 무엇인지 먼저 갈랐다.

| 판정 | 어느 줄 | 무엇을 했나 |
|---|---|---|
| **바꾸기** | 요구 2 정상 · 요구 3 | 결과 칸의 문장만 고쳤다. **`TODO-002`·`TODO-004` 번호는 그대로 둔다** |
| **없애기** | 요구 4 (마감일) | 상태를 `철회됨` 으로 바꾸고 **줄은 남긴다** |
| **더하기** | 요구 8~17 | 새로 붙였다. `TODO-005`~`TODO-012` |
| **손 안 댐** | 요구 1 · 요구 2 경계 · 요구 5~7 | v0.4 가 안 건드렸다 |

**번호를 새로 따지 않는 이유** (규칙 R9). `TODO-002` 를 `TODO-013` 으로 옮기면
「3개월째 초록이었는데 이번에 빨강」이라는 **회귀 이력이 끊긴다.** 고친 것은 판정 문장이지
그 요구사항이 다른 요구사항이 된 것이 아니다.

**철회된 줄을 지우지 않는 이유.** 지우면 다음 세션이 「마감일은 애초에 검토된 적 없다」로 읽는다.
남겨 두면 **한 번 물었고 미뤄진 것**임을 안다.

**★ 철회해도 전제·조작·결과 칸은 비우지 않는다.** 비우면 줄만 남고 **무엇을 물었는지가 사라져서**
다음 분기에 마감일이 돌아왔을 때 1차의 탐침(아래 「1차의 마감일 탐침 결과」)을 **처음부터 다시 해야 한다.**
철회 사실은 `작성 시점` 칸에만 적는다.

**「0 items left」의 복수형은 기획서에 없다.** v0.4 §2 는 「`1 item left` 처럼」이라고만 적었고
**0건일 때 `item` 인지 `items` 인지는 한 줄도 안 적혀 있다.** 지금 값은 화면과 같아서 초록이지
**사람이 정해서 초록인 것이 아니다** — 규칙 R10 이 경계하는 자리다. 기획자에게 물어야 한다.
1건짜리(`TODO-002`)는 기획서가 글자 그대로 적었으므로 문제없다.

**요구 8~10 은 §5 한 문단을 셋으로 끊은 것이다** (규칙 R1). 「~보여 주고」·「~남기며」로
요구가 셋 붙어 있었다 — 1차의 §2 첫 문단과 같은 모양이다.

**요구 11·12 는 §6 두 문장을 그대로 둘로 뒀다.** 「버튼이 나타난다」와 「누르면 사라진다」는
전제가 다르다 — 앞엣것은 버튼의 등장 조건이고 뒤엣것은 버튼의 동작이다.

**요구 15 가 이 표의 첫 예외 축이다** (규칙 R4). v0.4 §7 이 「이름을 모두 지우고 엔터」라는
**어긋난 입력과 그때의 화면**을 적었고, 그것을 **화면 조작만으로 일으킬 수 있다.**
서버 응답을 바꿔야 하는 것이었으면 `모킹 필요` 로 남기고 안 만들었다.

**§5·§6·§7 에 경계 축을 안 만들었다** (규칙 R3). 범위·개수·상한이 한 줄도 안 적혀 있다.

**요구 16 은 기획서에 있고 화면에 없다.** 1차의 마감일과 같은 자리다 — 탐침 결과는 아래에 있다.

### 3차 (v0.5) — 규칙 R9 판정

v0.5 는 신설 두 절만 담은 개정분이다. 줄마다 갈랐더니 **전부 더하기**였다.

| 판정 | 어느 줄 | 무엇을 했나 |
|---|---|---|
| **더하기** | 요구 18~20 | 새로 붙였다. `TODO-013`~`TODO-015` |
| **손 안 댐** | 요구 1~17 | v0.5 가 한 줄도 안 건드렸다 |

**요구 18·19 는 §10 한 문단을 둘로 끊은 것이다** (규칙 R1). 「~바뀐다. 그러면 ~이 된다」로
요구가 둘 붙어 있었다 — 1차의 §2 첫 문단, 2차의 §5 와 같은 모양이다.
**전제와 조작이 완전히 같지만 합치지 않았다.** 기획서가 「모두 끝난 것으로 바뀐다」와
「남은 개수는 0 이 된다」를 별개로 적었고, 합치면 **화살표가 표시만 바꾸고 개수를 안 고치는 버그**와
**개수만 고치고 표시를 안 바꾸는 버그**를 회귀에서 못 가린다.

**요구 18 의 결과를 「모두 끝난 것으로 바뀐다」 그대로 쓰지 않았다.** 눈으로 확인할 수 있는
문장이 아니다. 「완료 표시가 켜진 할 일이 두 건 보인다」로 옮겼다 — `getByRole` 의 `checked`
옵션이 켜진 것만 세므로 CSS 선택자 없이 판정된다.

**요구 19 의 「0 items left」는 2차와 같은 자리에 걸려 있다.** v0.5 §10 도 「남은 개수는 0」이라고만
적었지 **글자를 안 적었다.** `TODO-004` 가 이미 쓰는 문장을 그대로 썼으므로 두 케이스가 같이 초록이고
같이 빨강이 되지만, **사람이 정해서 초록인 것이 아니다** (규칙 R10). 기획자에게 물어야 한다.

**요구 20 의 결과는 「그대로 남아 있다」가 아니라 「목록에 「우유 사기」만 보인다」다.**
「그대로」는 개수와 내용을 한꺼번에 주장하므로 한 값으로 비교한다 (규칙 R12).

**경계·예외 축을 하나도 안 만들었다** (규칙 R3·R4). §10·§11 에 범위·개수·상한이 없고
실패 화면도 안 적혀 있다. 「이미 다 끝낸 상태에서 화살표를 누르면」은 기획서가 안 적은 것이라
지어내지 않았다.

## 용어 사전

화면을 실제로 열어 확정했다 (`ariaSnapshot` 탐침).

- **화면 스냅샷 해시**: `73d937f42658` (빈 화면 · **sha256 앞 12자** · 2026-09-21)
- **2차 실행에서 해시가 같았다.** 빈 화면 해석을 건너뛰고 아래 표의 위 일곱 줄을 그대로 썼다.
  새로 늘어난 것은 **v0.4 가 부른 요소들**뿐이다 (아래 「2차에서 늘어난 것」)
- **3차 실행에서도 해시가 같았다.** 빈 화면 해석을 또 건너뛰었다.
  새로 늘어난 것은 **v0.5 가 부른 요소들**뿐이다 (아래 「3차에서 늘어난 것」)

**다음 실행은 탐침을 돌려 해시를 비교한다.** 같으면 아래 표를 그대로 쓰고 **빈 화면 해석을 하지 않는다.**
다르면 바뀐 부분만 다시 본다. 이 사전이 아끼는 것은 유지보수가 아니라 **생성 비용**이다 —
케이스 파일들은 각자 locator 를 들고 있다.

| 도메인 용어 | 화면에서 무엇 | locator |
|---|---|---|
| 화면 제목 | 맨 위 제목 | `getByRole('heading', { name: 'todos' })` |
| 할 일 입력칸 | 제목 아래 텍스트 상자 | `getByPlaceholder('What needs to be done?')` |
| 할 일 항목 | 목록의 한 줄 | `getByTestId('todo-item')` |
| 할 일 글자 | 그 줄에 보이는 글자 | `getByTestId('todo-title')` |
| 남은 개수 | 목록 아래 문구 | `getByTestId('todo-count')` |
| 완료 표시 | 할 일 왼쪽 동그란 칸 | `getByRole('checkbox', { name: 'Toggle Todo' })` |
| 완료분 지우기 | 완료된 것이 있을 때만 나오는 버튼 | `getByRole('button', { name: 'Clear completed' })` |

### 2차에서 늘어난 것 (v0.4 가 부른 요소)

**빈 화면 해시가 같았으므로 위 일곱 줄은 다시 해석하지 않았다.** 아래 넷은 v0.4 의 요구사항이
새로 부른 것이라 **그 상태를 따로 탐침했다** — 목록에 두 건을 넣고 한 건을 완료한 상태,
그리고 할 일을 두 번 누른 편집 상태.

| 도메인 용어 | 화면에서 무엇 | locator |
|---|---|---|
| 보기 「All」 | 목록 아래 보기 고르개 첫째 | `getByRole('link', { name: 'All' })` |
| 보기 「Active」 | 보기 고르개 둘째 | `getByRole('link', { name: 'Active' })` |
| 보기 「Completed」 | 보기 고르개 셋째 | `getByRole('link', { name: 'Completed' })` |
| 이름 고치기 입력칸 | 할 일을 두 번 눌렀을 때 그 자리에 뜨는 입력칸 | `getByRole('textbox', { name: 'Edit' })` |

**이름 고치기 입력칸은 조건부로 그려진다** — 편집 아님 상태에서 `count()` 가 **0**, 편집 중에 **1** 이다.
`todo-title` 이 숨겨지는 것과 **다른 DOM 사건**이라, 앞엣것을 앵커로 두고 뒤엣것을 판정해도
판정이 공허해지지 않는다 (`TODO-010`).

**우선순위(요구 16)에 해당하는 요소는 없었다.**

```
본문 낱말 적중: []        ← 우선순위·높음·보통·낮음·priority 가 한 번도 안 나온다
select 수: 0
input type 전부: [text, checkbox, checkbox, text]
```

### 3차에서 늘어난 것 (v0.5 가 부른 요소)

**빈 화면 해시가 또 같았으므로 위 일곱 줄은 다시 해석하지 않았다.** 아래 둘은 v0.5 의 요구사항이
새로 부른 것이라 **그 상태를 따로 탐침했다** — 목록에 두 건을 넣은 상태, 그리고 화살표를 누른 뒤.

| 도메인 용어 | 화면에서 무엇 | locator |
|---|---|---|
| 화살표 표시 | 입력칸 왼쪽, 할 일이 한 건이라도 있을 때만 나오는 칸 | `getByRole('checkbox', { name: 'Mark all as complete' })` |
| 완료 표시가 켜진 할 일 | 완료 표시에 체크가 들어간 줄 | `getByRole('checkbox', { name: 'Toggle Todo', checked: true })` |

**화살표 표시의 접근 이름 앞에는 화살표 글자가 붙어 있다** — 스냅샷에 `❯Mark all as complete` 로
나온다. `getByRole` 의 이름 맞추기는 **부분 일치**라 `'Mark all as complete'` 만 적어도 잡힌다.
화살표 글자를 적으면 오히려 깨지기 쉽다.

**「완료 표시가 켜진 것만」을 세는 데 CSS 선택자가 필요 없다.** `getByRole` 의 `checked` 옵션이
그 일을 한다 — 완료된 줄에 붙는 클래스를 보러 갈 이유가 없다.

**할 일은 `localStorage` 의 `react-todos` 에 저장된다** (요구 20 탐침). 케이스마다 브라우저
컨텍스트가 새로 생기므로 앞 케이스가 남긴 것이 넘어오지 않는다 — 기존 열두 건이 전부 빈 목록을
전제로 초록인 것이 그 증거다.

## 이 화면에서 걸린 것

같은 화면은 같은 데서 걸린다. 다음 케이스가 처음부터 알게 적어 둔다.

- **빈 목록에서 남은 개수 영역은 DOM 에 아예 없다.** `count()` 는 0, `isVisible()` 은 `false`.
  **「보이지 않는다」를 확인할 때는 `isVisible()` 을 쓴다** — `count()` 는 「없다」를 보는 것이라
  문장과 뜻이 어긋나고 재시도도 하지 않는다
- **완료 표시를 누른 뒤 남은 개수를 읽기 전에 기다려야 한다.** 앵커는 `Clear completed` 버튼이다 —
  완료된 것이 생겨야 나타난다(0 → 1). 기대값과 무관한 앵커라 진단을 흐리지 않는다
- **입력 직후 목록을 읽기 전에** `getByTestId('todo-item')` 이 보일 때까지 기다린다

2차에서 새로 걸린 것 넷 — **셋은 첫 실행에서 빨강 8개를 냈다.**

- **`waitForURL` 은 보기를 바꾼 뒤의 앵커로 못 쓴다.** 주소(`#/active`)는 바로 바뀌는데
  목록 다시 그리기는 그 뒤에 온다. 그래서 **읽은 값이 한 단계씩 밀렸다** —
  Active 를 골랐는데 All 의 값이, Completed 를 골랐는데 Active 의 값이 나왔다.
  **목록 길이가 줄어드는 것**을 앵커로 쓴다 — `getByTestId('todo-item').nth(1).waitFor({ state: 'detached' })`
- **보기를 바꿀 때는 목록 길이가 실제로 바뀌는 쪽으로만 옮긴다.** Active(1건) → Completed(1건) 처럼
  길이가 그대로면 그 앵커가 **묵은 화면에서 바로 통과한다.** 준비 상태(2건)에서 곧장 간다
- **편집 중에도 `todo-title` 은 DOM 에 남는다. 숨겨질 뿐이다** — `isVisible()` 은 `false` 인데
  `state: 'detached'` 로 기다리면 30초를 채우고 죽는다. **`state: 'hidden'` 을 쓴다**
- **값이 바뀌기를 기다려 주는 읽기는 하나도 없다** (규칙 R13). `count()`·`allInnerTexts()`·
  `isVisible()` 은 **아무것도 안 기다리고**, `innerText()`·`click()`·`check()` 는 **요소가 붙는 것까지만**
  기다린다 — `todo-count` 처럼 **늘 붙어 있는** 요소에는 `innerText()` 도 묵은 값을 읽는다.
  **읽기 앞에는 반드시 앵커를 둔다.** 값을 기다려야 하면 그 값으로 기다린다 —
  `getByTestId('todo-title').filter({ hasText: '빵 사기' }).waitFor()` 처럼.
  2차의 빨강 8개가 전부 앵커가 없거나 틀린 자리였다
- **앵커는 판정과 다른 것으로 고른다.** 판정하려는 바로 그 값을 기다리면 **그 케이스는 못 깨진다** —
  깨져도 「기대값 0 · 실제값 1」이 아니라 **locator 시간 초과**가 찍혀 증적이 원인을 안 가리킨다.
  `TODO-012` 가 「`todo-count` 가 사라질 때까지」로 기다리고 「할 일이 0건」을 판정하고 있었다 —
  **같은 말이라 판정이 공허했다.** 편집칸이 닫히는 것으로 바꿨다 (2026-09-21 검토 지적)

3차는 **첫 실행이 3/3 초록이었다.** 2차가 남긴 앵커 규칙을 그대로 적용했기 때문이다 —
같은 화면이 같은 데서 걸린다는 것이 이번에 값으로 돌아왔다. **그런데 검토가 하나를 더 잡았다.**

- **화살표 표시는 빈 목록에 없다.** 할 일이 한 건이라도 있어야 나타난다. 그래서 요구 18·19 의
  준비 스텝은 **두 건을 넣고 목록에 붙는 것을 기다린 뒤에** 화살표를 누른다
- **화살표를 누른 뒤의 앵커는 `Clear completed` 버튼이다** — 완료된 것이 생겨야 나타난다(0 → 1).
  요구 18 의 판정(완료 켜진 개수)과도, 요구 19 의 판정(남은 개수 문구)과도 다른 요소라
  깨졌을 때 **판정 문장이 그대로 에러에 찍힌다.** 관문 4 에서 확인했다 —
  기대값을 틀리게 주입하니 셋 다 `검증 실패: <판정 문장>` 이 나왔지 locator 시간 초과가 아니었다
- **★ 다시 불러오기 뒤의 앵커로 `todo-count` 를 쓰면 안 된다.** 처음에 그렇게 썼다가
  검토에서 걸렸다 — `todo-count` 는 **할 일이 1건 이상일 때만 그려진다**(위 첫 줄, `TODO-003`).
  요구 20 이 잡으려는 회귀가 **바로 저장이 깨져 목록이 비는 것**이므로, 그 회귀가 나면
  앵커가 30초를 채우고 죽어서 **판정 문장이 영영 안 찍힌다.** 2차의 `TODO-012` 와 같은 결함이다.
  **`getByPlaceholder('What needs to be done?')` 를 앵커로 쓴다** — 할 일 유무와 무관하게 늘 그려지고
  React 가 같은 렌더에서 목록과 함께 붙이므로 값이 밀리지도 않는다.
  저장을 비우고 재현해 확인했다 — 앵커는 **14ms** 에 통과하고 판정값이 `''` 로 나와
  `검증 실패: 목록에 「우유 사기」만 보인다` 가 찍혔다
- **준비 스텝의 판정도 앵커와 달라야 한다.** 요구 18·19 의 준비가 처음에
  「둘째 항목이 붙기를 기다린 뒤 개수가 2」였는데 **같은 말이라 아무것도 확인하지 않았다.**
  「2 items left」로 바꿨다 — 전제가 「아직 끝내지 않은」이므로 **개수가 아니라 안 끝낸 수**를
  확인하는 것이 맞다. 같은 자리를 `TODO-006`·`007`·`009` 는 처음부터 그렇게 쓰고 있었다

## 요구 16 이 보류로 남은 이유

v0.4 §8 은 우선순위를 요구하는데 **화면에 그 요소가 없다.** 탐침 결과는 아래 「2차에서 늘어난 것」에 있다.

여기서 그럴듯한 selector 를 지어내면 케이스가 한 건 늘고 숫자는 좋아 보이지만,
그중 하나는 **아무것도 확인하지 않는 초록불**이 된다. **기대값은 사람이 판정한 것에서만 온다** (규칙 R10).

**기획자에게 물어야 할 것** — 우선순위가 아직 안 만들어진 것인가, 이번 범위가 아닌가.
1차의 마감일과 같은 질문이다.
